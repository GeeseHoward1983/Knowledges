# Rust、Swift 与 C++ ABI 互操作

> [!abstract] TL;DR
> Rust 与 Swift 都提供与 C ABI 互操作的机制，但各自拥有不稳定或私有的本地 ABI。Rust 通过 `extern "C"` + `#[repr(C)]` 跨越 FFI 边界，其默认 ABI（`extern "Rust"`）故意未稳定；Swift 自 5.0 起具有稳定 ABI（仅限 Apple 平台），其 existential container（三字 inline buffer + value witness table + metadata 指针）、protocol witness table、`swiftcall` 调用约定以及 `_$s` 前缀 name mangling 构成了独立于 C++ 的完整运行时体系。在 iOS/macOS 混合二进制（Swift + ObjC + C++）和游戏引擎（Rust + C++）这两大主流场景中，理解三种语言 ABI 的交汇点——FFI 边界的数据布局契约、name mangling 风格差异、跨语言异常/错误传播——是逆向和工程落地的必备基础。

## 概述与定位

现代大型软件很少是单一语言的产物。iOS App 中 Swift、Objective-C 和 C++ 三者共存；游戏引擎（如 Bevy、Godot 4）将 Rust 热循环与 C++ 渲染后端并列；系统软件（Firefox、Android）里 Rust 安全模块与 C/C++ 遗留代码通过 FFI 对接。在这些场景下，编译器与链接器必须就**调用约定、数据布局、符号命名、错误传播**达成跨语言契约——而这套契约正是本章的主题。

C ABI（System V AMD64 psABI 或 Win64 ABI）是事实上的跨语言公共通货。任何语言若想与外部模块互操作，都必须在 FFI 边界把本语言对象「投影」到 C 表示，或反向「接收」C 表示并包装为本语言对象。Rust 和 Swift 都走这条路，但它们各自的本地 ABI 远比 C ABI 复杂，理解从本地 ABI 到 C ABI 的转换规则，才能在反汇编中准确识别边界、重建接口、分析行为。

本篇与系列 36（Objective-C 与 iOS 运行时）深度衔接：Swift 与 ObjC 的互操作建立在 ObjC runtime 之上，Swift 类（`class`）本质上是 ObjC 类，可通过 `objc_msgSend` 派发；而 C++ 对象则不参与 ObjC 消息机制，需要显式桥接。三种语言在同一进程空间的协作，正是逆向 iOS 二进制最富挑战性的部分。

## 原理与机制

### Rust FFI 基础：`extern "C"` 与 ABI 字符串

Rust 用**字符串字面量**标注函数的调用约定，称为 **ABI 字符串（ABI string）**：

```rust
// 导出给 C 调用的函数——采用 C 调用约定，符号不做 Rust mangling
#[no_mangle]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 {
    a + b
}

// 声明外部 C 函数——告知编译器按 C ABI 调用
extern "C" {
    fn c_strlen(s: *const u8) -> usize;
}
```

常用 ABI 字符串：

| ABI 字符串 | 含义 |
|-----------|------|
| `"C"` | 平台 C ABI（System V AMD64 或 Win64） |
| `"Rust"` | Rust 默认 ABI（**未稳定，跨版本不保证兼容**） |
| `"system"` | Windows 上等同 `"stdcall"`，其他平台等同 `"C"` |
| `"win64"` | 强制 Win64 ABI（即使在 Linux 上） |
| `"sysv64"` | 强制 System V AMD64 ABI |
| `"C-unwind"` | C ABI 但允许跨边界传播 Rust panic（RFC 2945） |

**`extern "Rust"` 的刻意不稳定**：Rust 编译器团队明确声明，`extern "Rust"` 的调用约定细节（寄存器使用、参数排布、返回值传递方式）在不同 rustc 版本之间可能改变，这为优化留下空间（例如将多返回值打包进寄存器对）。因此，任何跨语言调用或跨 crate FFI 边界都**必须**使用 `extern "C"` 而非依赖 `extern "Rust"`。

### `#[repr(C)]`：让 Rust 类型布局与 C 对齐

Rust 编译器默认可以对结构体字段重排（类似 C++ 的非标准布局 UB 场景），以获得更好的对齐和填充结构。`#[repr(C)]` 强制使用 C 语言的布局规则：字段按声明顺序排列，每个字段对齐到其自身大小，整个结构体对齐到最大字段的对齐要求。

```rust
// 默认 repr：编译器可自由重排字段
struct DefaultRepr {
    a: u8,    // 可能被移到 b 之后以减少 padding
    b: u64,
    c: u16,
}

// repr(C)：字段顺序固定，与 C 的 struct { uint8_t a; uint64_t b; uint16_t c; } 相同
#[repr(C)]
struct CRepr {
    a: u8,    // offset 0
    // 7 字节 padding（为对齐 b 到 8 字节）
    b: u64,   // offset 8
    c: u16,   // offset 16
    // 6 字节 padding（为对齐整个结构体到 8 字节）
}
// sizeof(CRepr) = 24，与 C 完全一致
```

`#[repr(C)]` 的约束范围：

- **结构体（struct）**：字段顺序锁定，padding 规则同 C。
- **枚举（enum）**：整个枚举体的内存布局由 C 的 tagged union 规则决定。对于无数据字段的枚举，等价于 C `enum`（通常为 `int`）；带数据字段的枚举需要结合 `#[repr(C, u8)]` 等混合标注。
- **联合体（union）**：字段共享同一起始地址，大小为最大字段大小，对齐为所有字段中最严格的对齐。

```rust
// repr(C) 枚举：等价于 C 的 int 枚举
#[repr(C)]
enum Color { Red = 0, Green = 1, Blue = 2 }

// repr(C) 带数据枚举（Rust 特有的 tagged union）
// 在 C 这端，需要手写对应的 tagged union 结构
#[repr(C)]
enum Result<T, E> {
    Ok(T),
    Err(E),
}
// 在 C 中对应（以 i32/i32 为例）：
// struct { int tag; union { int ok_val; int err_val; } data; }
```

### `#[repr(transparent)]`：零开销包装类型

`#[repr(transparent)]` 用于**只有一个非零大小字段**的结构体，使其 ABI 与内部字段完全一致——不仅布局相同，参数传递方式（寄存器 vs 内存）也相同。这对 newtype 模式极为重要：

```rust
// 零开销包装：强类型 UserId 与裸 u64 有完全相同的 ABI
#[repr(transparent)]
struct UserId(u64);

extern "C" fn get_user(id: UserId) -> bool {
    // 编译器在调用约定上将 UserId 当成 u64 处理
    // 汇编层面：id 在 rdi 寄存器传入（System V）
    id.0 > 0
}
```

与 `#[repr(C)]` 区别：`repr(C)` 改变布局规则；`repr(transparent)` 改变参数传递规则（使其与内部类型等同）。二者可以组合：`#[repr(C, u8)]` 等。

### Rust Name Mangling：v0 方案与 legacy 方案

#### Legacy Mangling（rustc 1.0–1.56）

早期 Rust 使用基于哈希的 mangling：

```
_ZN<crate_hash><module_path><symbol_name>E<哈希后缀>
```

例如 `std::vec::Vec::<i32>::new` 可能生成：

```
_ZN3std3vec3Vec17h1234567890abcdeE
```

`_ZN…E` 结构与 Itanium C++ ABI 相同（都以 `_Z` 开头），但中间的编码语义完全不同，`c++filt` 无法正确 demangle，因为 Rust 的 crate 路径编码规则与 C++ 的类/命名空间编码不同。

#### v0 Mangling（rustc 1.56+，稳定）

v0 使用 `_R` 前缀，彻底与 C++ ABI 区分，并设计为可完整还原符号路径（包括泛型参数、常量泛型、生命周期等信息）：

```
_R <符号路径编码> [<泛型参数编码>]
```

示例：`std::vec::Vec::<i32>::new` 的 v0 mangled 名：

```
_RNvMNtNtCslpNzO3std3vec3VecINtB3_3VeciE3new
   ^   ^^^^^^^^ ^^^^^^^^^^^^^^^^ ^^^
   |   |        |                |
   |   Nv=方法  crate路径前缀    泛型参数 i32
   _R 前缀
```

v0 编码元素：

| 前缀字母 | 含义 |
|---------|------|
| `N` | 命名空间分隔符 |
| `v` | value 命名空间（函数、常量） |
| `t` | type 命名空间（类型别名、结构体） |
| `Cs` | crate（`s` = 短路径编码） |
| `M` | 方法（`impl` 块内的关联函数） |
| `X` | 特化（`impl<T> Trait for Type` 中的方法） |
| `B<idx>_` | 反向引用（压缩重复路径前缀） |

**工具**：`rustfilt`（cargo 安装）或 `rust-demangler` 可还原 v0 符号；GDB 12+ 自动识别 `_R` 前缀并内置 demangle。

```bash
$ rustfilt _RNvMNtNtCslpNzO3std3vec3VecINtB3_3VeciE3new
std::vec::Vec::<i32>::new
```

### Swift Name Mangling：`_$s` / `$s` 前缀

Swift 的 mangling 方案随版本演进：Swift 4.0 之前用 `_T`，4.0+ 用 `_$S`，4.2+ 稳定为 `_$s`（小写）：

```
_$s <模块名编码> <类型名编码> <方法名编码> [<标签编码>] <返回类型编码>
```

示例：`MyModule.MyClass.init(x:y:)` 的 mangled 名：

```
_$s8MyModule7MyClassC4init1x1ySi_SftcFC
   ^^^^^^^^ ^^^^^^^ ^^^^ ^^ ^^
   |        |       |    |  |
   模块名   类名    方法  参数标签  类型编码
```

Swift mangling 编码规则（关键元素）：

| 编码片段 | 含义 |
|---------|------|
| `_$s` 或 `$s` | Swift 5+ mangling 前缀（有无下划线取决于导出场景） |
| `C` | class 类型 |
| `V` | struct 类型 |
| `O` | enum 类型 |
| `P` | protocol 类型 |
| `F` | 普通函数 |
| `i` | init |
| `d` | deinit |
| `g` | getter |
| `s` | setter |
| `Si` | Swift.Int |
| `Sf` | Swift.Float |
| `Sb` | Swift.Bool |
| `SS` | Swift.String |
| `Sq<T>` | Optional<T> |

**demangle 工具**：`xcrun swift-demangle`（macOS）或 `swift-demangle` 独立工具：

```bash
$ swift-demangle _$s8MyModule7MyClassC4init1x1ySi_SftcFC
MyModule.MyClass.init(x:y:)
```

JADX / Ghidra / IDA 的 Swift 插件会自动调用此 demangle 逻辑，逆向 iOS 二进制时可以直接看到还原后的 Swift 符号名。

### Swift ABI 稳定性：Swift 5.0 的里程碑

Swift 5.0（随 Xcode 10.2，2019 年发布）宣布 **ABI Stability**，仅在 Apple 平台生效（iOS 12.2+、macOS 10.14.4+）。这意味着：

1. Swift 标准库随操作系统分发，App 无需再打包 `libswiftCore.dylib`（瘦身约 6MB）。
2. 不同 Swift 版本编译的代码可以在二进制层面互操作，只要遵守稳定的 ABI 规则。
3. **不在 Apple 平台（Linux、Windows）上不保证 ABI 稳定**，各发行版 Swift 依然可能 ABI 不兼容。

ABI 稳定覆盖的契约范围：
- 类型的内存布局（struct/class/enum 的字段偏移）
- 函数调用约定（`swiftcall` 规则）
- 协议 witness table 的结构
- 类型 metadata 的格式
- existential container 的布局

## 结构/算法/伪代码详解

### Swift Existential Container：协议类型的运行时表示

当 Swift 中一个变量的类型是**协议类型**（protocol type，即 `any Protocol` 语法，Swift 5.7 之前用裸协议类型）时，编译器无法在编译期确定实际类型，需要在运行时携带足够信息。这套机制叫 **existential container**（存在容器），是 Swift ABI 的核心构件之一。

existential container 由 **5 个指针大小（5 × 8 = 40 字节，64 位平台）**的字段组成：

```
┌─────────────────────────────────────────────────────┐
│  word 0 │ inline value buffer[0]  (8 字节)           │  ← 共 3 word 内联缓冲
│  word 1 │ inline value buffer[1]  (8 字节)           │
│  word 2 │ inline value buffer[2]  (8 字节)           │
│  word 3 │ value witness table 指针 (8 字节)          │  ← 描述类型操作
│  word 4 │ type metadata 指针      (8 字节)           │  ← 描述类型本身
└─────────────────────────────────────────────────────┘
          总大小：40 字节（5 × 8）
```

**Inline buffer 策略**：若实际值的大小 ≤ 3 × 8 = 24 字节，且对齐要求 ≤ 8 字节，值直接存放在 word 0–2（inline，无堆分配）。否则，word 0 存放一个指向堆分配区域的指针，word 1–2 未使用（或用于额外元数据）。

对于类类型（`class`），由于 Swift 类是引用类型，word 0 直接存放对象指针（类对象本身在堆上），不需要额外堆分配。

**Protocol existential（单协议）与 Protocol Composition（多协议）**：

单协议 existential（`any Drawable`）：1 个 protocol witness table 指针，总大小 40 字节。

多协议 existential（`any Drawable & Serializable`）：每多一个协议增加 1 个 witness table 指针，总大小 = 3×8 + 1×8（metadata）+ N×8（N 个 witness table）。

```swift
// Swift 示意：以下变量 d 持有一个 existential container
var d: any Drawable = Circle(radius: 5.0)
// 内存布局（Circle 为 struct，sizeof ≤ 24B 时）：
// [word0]=Circle字段1 [word1]=Circle字段2 [word2]=0或字段3
// [word3]=&Circle_value_witness_table
// [word4]=&Circle_metadata
```

### Value Witness Table（VWT）：类型操作的运行时分派

Value Witness Table 描述了一个类型在值语义下的所有操作——即如何拷贝、移动、销毁一个值，以及其大小和对齐信息。它是 Swift 的「泛型类型操作 ABI」。

VWT 的结构（简化，按 Swift 5 ABI 规范）：

```c
// C 伪代码描述 VWT 布局
struct SwiftValueWitnessTable {
    // 类型操作函数指针
    void* (*initializeWithCopy)(void* dest, const void* src, const void* metadata);
    void* (*assignWithCopy)(void* dest, const void* src, const void* metadata);
    void* (*initializeWithTake)(void* dest, void* src, const void* metadata);
    void* (*assignWithTake)(void* dest, void* src, const void* metadata);
    void  (*destroy)(void* obj, const void* metadata);

    // 类型信息（编码在最后几个 word，使用低位 flag 压缩）
    size_t   size;         // 类型大小（字节）
    size_t   stride;       // 数组元素间距（size 向上对齐到 alignment）
    uint32_t flags;        // isPOD、isValueInline、hasSpareBits 等标志位
    uint32_t extraInhabitantCount; // 用于 Optional 的 spare bit 优化
};
```

**VWT 的逆向意义**：在反汇编中，对泛型函数的调用会传入 VWT 指针（通常在 `r13` 或约定的寄存器中），用于对泛型值进行拷贝、移动操作。识别 VWT 调用是理解 Swift 泛型代码反汇编的关键。

### Protocol Witness Table（PWT）：协议实现的运行时分派

Protocol Witness Table 是 Swift 协议机制的核心——它记录了某个具体类型对某个协议所有 requirement 的实现（函数指针）。类似 C++ vtable，但不绑定在对象内部，而是独立于类型存在，通过 existential container 中的指针引用。

```c
// PWT 布局（简化）
struct SwiftProtocolWitnessTable {
    // 第0项：协议的描述符指针（指向 protocol descriptor）
    const SwiftProtocolDescriptor* protocol;

    // 第1项起：协议每个 requirement 的实现函数指针
    void* (*requirement_0)(/* self, ... */);
    void* (*requirement_1)(/* self, ... */);
    // ... 与协议中 requirement 数目一一对应
};
```

与 C++ vtable 对比：

| 特性 | C++ vtable | Swift Protocol Witness Table |
|------|-----------|------------------------------|
| 绑定位置 | 对象内部（vptr 字段） | existential container 中独立指针 |
| 生成时机 | 编译期（每个多态类） | 编译期（每个 `conformance` 在编译期生成） |
| 运行时合并 | 不支持 | Conditional conformance 可在运行时确定 |
| 泛型联动 | 通过模板特化 | 通过 PWT + 泛型约束（`some Protocol`）|
| 逆向标识 | `_ZTV` 前缀符号 | `_$s…WP` 后缀符号（WP = Witness Table Protocol） |

### Swift 调用约定：`swiftcall` 与特殊寄存器

Swift 定义了独立于 C 的调用约定 **`swiftcall`**，由 LLVM 后端实现（`cc 16` 内部编号），用于 Swift 内部函数调用（跨 Swift 模块但同 ABI）。

`swiftcall` 的关键特征（x86-64，Swift 5+ ABI）：

**Self 寄存器（`r13`）**：方法调用时，`self`（接收者）通过 `r13` 传入，而非压入普通参数寄存器序列。这与 C++ 的 `rdi`（System V）或 `rcx`（Win64）传 `this` 不同。

```asm
; Swift 方法调用示意（x86-64 swiftcall）
; Circle.area() 调用
mov r13, rcx      ; self = Circle 实例地址（放入 r13）
call _$s6shapes6CircleV4areaSdyF   ; 调用 area() 方法
; 返回值在 xmm0（Double 类型）
```

**Error 寄存器（`r12`、`rax` 低位标志）**：Swift 的 `throws` 函数通过 `r12` 传入错误结果缓冲区指针（输出参数），若函数抛出错误，`rax` 的低位（bit 0）设为 1，同时将 `Error` 对象写入 `r12` 指向的位置；成功时 `rax` 低位为 0。这消除了异常机制的 unwinding 开销，改用检查返回值的轻量方式。

```asm
; Swift throws 函数调用的汇编模式
lea r12, [rsp - 8]    ; r12 指向错误输出槽
call _$s6module4funcSiyKF   ; 调用 throws 函数
test al, 1             ; 检查错误标志位
jnz .handle_error      ; 若出错跳转
; 正常路径：返回值在 rax
```

**多返回值**：`swiftcall` 允许通过多个寄存器返回复合值，例如返回一个 `(Int, Int)` 元组时，两个值分别在 `rax` 和 `rdx` 中返回，无需通过内存传递。

**泛型元数据传递**：泛型函数调用时，类型的 metadata 指针通过额外隐式参数传入（通常放在寄存器 `r8`、`r9` 等）：

```swift
// 泛型函数
func swap<T>(_ a: inout T, _ b: inout T) { ... }
// 汇编层面额外传入 T 的 metadata 指针和 VWT 指针
```

### Swift Type Metadata：运行时类型描述符

每个 Swift 类型在二进制中都有一份 **type metadata**，作为全局数据存在，描述该类型的运行时信息。其结构因类型种类不同而有差异，但 class metadata 与 ObjC 的 `isa` 机制直接兼容：

**Class Metadata（继承自 ObjC isa）**：

```c
struct SwiftClassMetadata {
    // === ObjC 兼容层（偏移与 ObjC class 结构相同）===
    SwiftClassMetadata* superclass;   // 与 ObjC 的 superclass 字段重合
    uintptr_t           cache[2];     // ObjC cache（Swift 不使用，置0）
    uintptr_t           data;         // ObjC data 指针，低位 flags

    // === Swift 专有层 ===
    uint32_t kind;                    // MetadataKind（Class=0, Struct=1...）
    uint32_t flags;
    uint32_t instanceAddressPoint;
    uint32_t instanceSize;
    uint16_t instanceAlignMask;
    uint16_t reserved;
    uint32_t classSize;
    uint32_t classAddressPoint;
    const void* description;          // 指向 class descriptor（名字、字段等）
    // ... 随后是 vtable 槽（Swift 方法）
};
```

逆向要点：Swift class metadata 的前几个字段（superclass + cache + data）在内存中与 ObjC class 重合，因此 ObjC runtime 函数可以直接操作 Swift class 实例；但 Swift 的虚方法分派发生在 metadata 的 vtable 槽（从 `classAddressPoint` 偏移后的位置），而非 ObjC `objc_msgSend`。

**Struct/Enum Metadata**：结构体和枚举的 metadata 没有 ObjC 兼容层，较为简单：

```c
struct SwiftStructMetadata {
    uintptr_t            kind;         // MetadataKind（Struct=512=0x200）
    const void*          description;  // 指向 struct descriptor
};
```

`description` 指向类型描述符（`TypeContextDescriptor`），包含字段数目、字段偏移表、协议 conformance 列表等信息，是逆向时重建 Swift struct 字段布局的主要数据来源。

### Protocol Conformance 与 Witness Table 的存储

Swift 协议 conformance（类型实现协议的声明）在二进制中以 **conformance record** 的形式存储在 `__TEXT,__swift5_proto` 节（macOS/iOS）。这些记录在程序启动时被 Swift runtime（`libswiftCore.dylib`）扫描注册，以支持运行时的协议检查（`is`、`as?`）。

```
__TEXT,__swift5_proto 节：
  ┌──────────────────────────────────────────────────────┐
  │ ConformanceDescriptor {                              │
  │   int32_t protocol_descriptor_offset;   // 指向协议描述符 │
  │   int32_t type_ref_offset;              // 指向类型引用   │
  │   int32_t witness_table_pattern_offset; // 指向 PWT     │
  │   uint32_t flags;                       // conformance 标志│
  │ }                                                    │
  └──────────────────────────────────────────────────────┘
```

逆向 iOS 二进制时，通过解析 `__swift5_proto` 节可以重建所有协议遵守关系，相当于 C++ 中从 `_ZTV` vtable 重建类继承层次。

## 工具视角与实战

### `cxx` crate：Rust 与 C++ 的安全桥接

直接使用 `extern "C"` 跨 Rust/C++ 边界有两个痛点：一是 C++ 类型（`std::string`、`std::vector`、类层次）无法直接映射到 C；二是手写 unsafe FFI 极容易出错（生命周期、所有权语义不匹配）。`cxx` crate 通过**代码生成**解决这两个问题：

```rust
// Rust 侧（src/main.rs）
#[cxx::bridge]
mod ffi {
    // 将 C++ 端的类型声明映射到 Rust
    unsafe extern "C++" {
        include!("my_lib.h");

        type MyClass;  // C++ class MyClass

        fn process(self: &MyClass, input: &str) -> String;
        fn create() -> UniquePtr<MyClass>;
    }

    // 将 Rust 侧的函数导出给 C++
    extern "Rust" {
        fn rust_callback(data: &[u8]) -> bool;
    }
}
```

`cxx` 的工作原理：

1. **proc macro** 展开 `#[cxx::bridge]`，生成 Rust 端的 `unsafe` 包装函数（`extern "C"` 边界）。
2. **build.rs** 调用 `cxx_build::bridge("src/main.rs")` 生成对应的 C++ 胶水代码（`.cpp` 文件），其中包含函数签名与 Rust 端完全匹配的 `extern "C"` 声明。
3. C++ 胶水代码中，`rust::Str`（对应 Rust `&str`）、`rust::String`（`String`）、`rust::Slice<T>`（`&[T]`）等类型有固定的 ABI 布局，确保两侧读写同一内存时语义一致。

`rust::Str` 的 ABI 布局（`extern "C"` 可见）：

```c
// cxx.h 中的定义
struct StrRef {
    const char* ptr;    // 指向 UTF-8 字节的指针
    size_t      len;    // 字节长度（非字符数）
};
// 与 Rust 的 &str fat pointer（ptr + len）在 repr(C) 下完全相同
```

### `bindgen`：从 C/C++ 头文件自动生成 Rust FFI 绑定

`bindgen` 解析 C/C++ 头文件，生成对应的 Rust `extern "C"` 声明和 `#[repr(C)]` 类型定义：

```bash
# 安装
cargo install bindgen-cli

# 从 my_lib.h 生成 Rust 绑定
bindgen my_lib.h \
    --allowlist-function 'my_.*' \
    --allowlist-type 'MyStruct' \
    -o src/bindings.rs \
    -- -I/path/to/include
```

生成结果示例（`my_lib.h` 中有 `struct Point { float x; float y; }`）：

```rust
// 自动生成的 bindings.rs（片段）
#[repr(C)]
#[derive(Debug, Copy, Clone)]
pub struct Point {
    pub x: f32,
    pub y: f32,
}

extern "C" {
    pub fn create_point(x: f32, y: f32) -> Point;
    pub fn distance(a: *const Point, b: *const Point) -> f32;
}
```

**bindgen 的 C++ 支持局限**：`bindgen` 对纯 C 支持完善，对 C++ 的支持有以下限制：
- 不支持 C++ 模板（模板实例化后的具体类型可以）；
- 不支持 C++ 异常（跨 FFI 边界的 C++ 异常属于 UB）；
- 不支持带虚函数的类（vtable 布局不映射，只映射字段）；
- 不支持 C++ 重载（重载函数需要手动 `allowlist-function` 并指定精确签名）。

### `cbindgen`：从 Rust 生成 C/C++ 头文件

方向相反——`cbindgen` 解析 Rust 源码中的 `#[repr(C)]` 类型和 `extern "C"` 函数，生成 C/C++ 头文件：

```bash
cbindgen --config cbindgen.toml --crate my_lib --output my_lib.h
```

典型 `cbindgen.toml`：

```toml
language = "C++"
namespace = "my_lib"
include_guard = "MY_LIB_H"

[export]
include = ["MyStruct", "my_function"]
```

`cbindgen` 能处理 `#[repr(C)]` 结构体、`#[repr(C)]` 枚举、`extern "C"` 函数、以及满足条件的泛型特化（泛型类型在 Rust 端必须已经被实例化为具体类型）。

### 逆向 iOS 混合二进制：Swift + ObjC + C++ 三语言交织

iOS App 二进制（Mach-O 格式）中三种语言共存，逆向时主要挑战在于：
1. 区分 Swift、ObjC、C++ 的符号与调用约定；
2. 还原 Swift class/struct 的字段布局；
3. 追踪跨语言边界的数据流。

#### 第一步：符号辨认

```bash
# 用 nm 配合 swift-demangle 查看 Mach-O 的 Swift 符号
nm -gU MyApp | grep '^\$s\|^_\$s' | swift-demangle

# 用 otool 查看 ObjC 方法列表（Swift class 也在其中）
otool -oV MyApp | grep -A3 'method_list'

# 用 nm 查看 C++ 符号（_Z 前缀）
nm -gU MyApp | c++filt | grep '_Z'
```

三种前缀一览：

| 前缀 | 语言 | demangle 工具 |
|------|------|--------------|
| `_Z` | C++（Itanium） | `c++filt` |
| `_R` | Rust（v0） | `rustfilt` |
| `_$s` / `$s` | Swift 5+ | `swift-demangle` |
| `_T` | Swift 4.0 之前 | `swift-demangle` |
| `-[Class method:]` | ObjC | 直接可读 |

#### 第二步：Swift class 字段布局重建

Swift struct 的字段偏移可从 type descriptor（`__TEXT,__swift5_types` 节）中解析，或通过运行时 API `MemoryLayout<T>.offset(of:)` 查询。逆向工具链（如 Hex-Rays IDA + swift_types 插件、Ghidra + SwiftGhidra 插件）能自动解析 Swift 5 metadata 并重建结构体布局。

手动方法：

```python
# LLDB 中查询 Swift struct 字段偏移
(lldb) p MemoryLayout<Circle>.size         # Circle struct 大小
(lldb) p MemoryLayout<Circle>.alignment    # 对齐
(lldb) expression -l swift -- import MyModule; print(MemoryLayout<MyModule.Circle>.size)
```

#### 第三步：识别 swiftcall 调用模式

在 IDA / Ghidra 的反汇编视图中，`swiftcall` 的特征：

```asm
; 典型 Swift 方法调用特征（x86-64）
; 1. self 在 r13（不是 rdi）
mov  r13, [rbp-0x20]       ; 加载 self

; 2. 泛型元数据通过额外寄存器传入
mov  r8,  qword [rip + _$s9SwiftCore3IntVMf+8]  ; Int metadata

; 3. throws 函数：r12 为错误输出槽
lea  r12, [rsp-0x8]

; 4. 调用 Swift mangled 符号
call _$s6shapes6CircleV4areaSdyF

; 5. 检查错误标志
test al, 1
jnz  .error_path
```

#### 第四步：Swift 与 ObjC 互操作边界

Swift class 继承自 `NSObject` 或使用 `@objc` 标注时，其方法通过 ObjC `objc_msgSend` 分派。逆向时这类方法会在 ObjC method list 中出现，同时也有 Swift mangled 符号（两套入口）：

```
ObjC 入口：-[MyView drawRect:]          ← objc_msgSend 路径
Swift 入口：_$s6MyApp6MyViewC9drawRectyyXlF  ← 直接调用路径
```

纯 Swift 方法（没有 `@objc`）只有 Swift mangled 符号，不在 ObjC method list 中，`objc_msgSend` 无法调用——这是逆向时容易漏掉覆盖点的地方。

### `@_cdecl`：Swift 向 C 导出函数

Swift 可以用 `@_cdecl("c_function_name")` 将函数按 C ABI 导出（类似 Rust 的 `#[no_mangle] pub extern "C" fn`）：

```swift
@_cdecl("swift_compute")
public func compute(x: Int32, y: Int32) -> Int32 {
    return x + y
}
```

导出结果：二进制中存在 `_swift_compute` 符号（C ABI，不含 Swift mangling），可以被 C/C++/Rust 直接 `extern "C"` 声明后调用。注意 `@_cdecl` 是非官方属性（带下划线前缀），官方建议通过 C interop module（`@_implementationOnly import` + header 生成）替代，但实际项目中 `@_cdecl` 使用非常普遍。

### Rust `panic` 与跨 FFI 边界

Rust 的 `panic!` 在默认配置（`panic = "unwind"`）下通过 LLVM 的 unwind 机制传播，其 personality 函数（`rust_eh_personality`）与 C++ 的 `__gxx_personality_v0` 不同。如果 Rust panic 跨越 `extern "C"` FFI 边界传递到 C/C++ 代码，行为是**未定义的**（UB）。

解决方案：

**方案 1**：编译时 `panic = "abort"`（`Cargo.toml`）——panic 直接调用 `abort()`，不展开，绝对不跨 FFI 边界。适用于安全关键场景。

**方案 2**：在 FFI 边界函数内用 `std::panic::catch_unwind` 捕获 panic，转换为错误码返回：

```rust
use std::panic;

#[no_mangle]
pub extern "C" fn safe_ffi_function(input: i32) -> i32 {
    let result = panic::catch_unwind(|| {
        risky_rust_function(input)
    });
    match result {
        Ok(val) => val,
        Err(_)  => -1,  // panic 转换为错误码
    }
}
```

**方案 3**（RFC 2945，rustc 1.71+ 稳定）：使用 `extern "C-unwind"` ABI——此 ABI 允许 Rust 的 unwind 安全地跨越 FFI 边界传播（unwinder 已协商），但要求 C/C++ 侧也编译时开启异常支持（`-fexceptions`）。

## 安全性与正确使用

### ABI 不稳定性：Rust 本地 ABI 的工程约束

`extern "Rust"` ABI 未稳定这一事实有直接工程影响：

**跨 crate 函数调用必须通过 C ABI**：若动态库（`.so`/`.dylib`/`.dll`）以 Rust 实现并导出给其他 Rust crate 调用，不能依赖 `extern "Rust"` ABI——需要用 `extern "C"` + `#[repr(C)]` 定义公共接口。Rust 标准库本身也遵守此规则：`libstd` 的跨 crate 公共接口不暴露 `extern "Rust"` 函数，而通过稳定的类型和 trait 约束。

**结构体字段不允许 `pub` 但无 `#[repr(C)]`**：若一个库的公共接口包含 Rust struct（无 `#[repr(C)]`），另一个 crate 的代码若依赖其具体字段偏移（通过 transmute 或 raw pointer），升级库版本后编译器重排字段会导致静默内存错误。正确做法：公共 ABI 结构体必须 `#[repr(C)]`，或者完全封装（只通过 accessor 方法访问）。

**`unsafe` 的边界定位**：每一个 `extern "C"` 块引入的外部函数都需要在 Rust 端用 `unsafe` 调用，这是 Rust 将 FFI 风险显式化的机制。`cxx` crate 通过安全抽象将部分 unsafe 封装，但底层依然是 `unsafe`——理解这一点，才能在代码审查中重点关注 FFI 边界附近的 invariant。

### Swift ABI 稳定性的边界条件

Swift 5.0 的 ABI 稳定仅在 **Apple 平台**有效，且有以下重要约束：

**模块稳定性（Module Stability）与 ABI 稳定性的区别**：ABI 稳定指编译产物（`.swiftmodule` 之外的 `.o`/`.dylib`）二进制兼容，但 `.swiftmodule` 格式本身（包含 Swift 源码级描述符，用于 import 时的语义检查）不保证跨版本兼容。模块稳定性（XCFramework + `.swiftinterface` 文件，Xcode 11.4+）才解决了这个问题——`.swiftinterface` 是文本格式，跨版本可解析。

**`@frozen` 与非 frozen 的布局保证**：Swift 标准库类型和第三方框架中，只有标注 `@frozen` 的 struct/enum 保证 ABI 稳定的字段布局（其他代码可以对其做 in-place 操作）。非 `@frozen` 类型的布局可能在未来版本改变，调用方必须通过函数接口访问（不能直接按偏移读写字段）。

**泛型特化（Specialization）**：Swift 的泛型特化（`@_specialize` 属性或编译器自动特化）产生的代码不属于稳定 ABI——特化函数的符号是内部的（不 mangling 进公共符号表），不能跨模块直接调用特化版本。

### 跨语言边界的内存所有权协议

跨 Rust/C++/Swift 边界时，内存所有权的语义不匹配是最常见的错误来源：

| 场景 | 正确做法 |
|------|---------|
| Rust 将堆分配字符串传给 C++ | `CString::into_raw()` 转移所有权；C++ 使用后调用 `my_free_string(ptr)` 回调 Rust 的 `CString::from_raw()` 释放 |
| C++ 将字符串传给 Rust | Rust 端做拷贝（`CStr::from_ptr().to_string_lossy()`），不持有 C++ 的所有权 |
| Swift 向 Rust 传 Data（NSData） | 通过 `Data.withUnsafeBytes { ptr in rust_fn(ptr.baseAddress, ptr.count) }`，Rust 端在闭包期间持有借用，不复制 |
| Rust 向 Swift 回调 | 通过 `extern "C"` 函数指针 + `UnsafeRawPointer` 作为 context，Swift 在 `deinit` 时调用 C 析构函数释放 Rust 侧资源 |

**Rust 的 `Send`/`Sync` 与跨语言线程安全**：Rust 编译器在跨线程场景要求类型满足 `Send`（可跨线程传递所有权）或 `Sync`（可跨线程共享引用）。通过 FFI 传入的 C/C++ 指针默认不满足这些 trait（裸指针 `*mut T` 既不 `Send` 也不 `Sync`），若需要跨线程传递，必须包装在 `unsafe impl Send for MyWrapper { }` 并确保实际线程安全。

### `extern "C"` 与 C++ 异常的交互

若 C++ 函数可能抛出异常，且通过 `extern "C"` 声明供 Rust 调用，则异常跨越 FFI 边界是 UB。正确做法是在 C++ 端写 wrapper，用 `try`/`catch` 将异常转换为错误码：

```cpp
// C++ wrapper：将异常转为错误码
extern "C" int safe_cpp_func(const char* input, char* output, int out_len) {
    try {
        std::string result = risky_cpp_function(input);
        strncpy(output, result.c_str(), out_len);
        return 0;  // 成功
    } catch (const std::exception& e) {
        return -1; // 失败
    } catch (...) {
        return -2; // 未知异常
    }
}
```

Rust 侧：

```rust
extern "C" {
    fn safe_cpp_func(input: *const u8, output: *mut u8, out_len: i32) -> i32;
}

pub fn call_cpp(input: &str) -> Result<String, i32> {
    let c_input = CString::new(input).unwrap();
    let mut buf = vec![0u8; 1024];
    let ret = unsafe {
        safe_cpp_func(c_input.as_ptr() as *const u8, buf.as_mut_ptr(), buf.len() as i32)
    };
    if ret == 0 {
        Ok(String::from_utf8_lossy(&buf).trim_end_matches('\0').to_string())
    } else {
        Err(ret)
    }
}
```

## 小结

| 知识点 | 核心结论 |
|--------|---------|
| Rust `extern "C"` | 跨语言 FFI 的唯一稳定入口；`extern "Rust"` 未稳定，不可跨版本依赖 |
| `#[repr(C)]` | 锁定 Rust struct 字段顺序为 C 规则，是所有 FFI 结构体的必要标注 |
| `#[repr(transparent)]` | 零开销包装类型，与内部字段完全相同的参数传递 ABI |
| Rust v0 mangling | `_R` 前缀，`rustfilt`/GDB 12+ 可 demangle；与 C++ `_Z` 不同 |
| Rust legacy mangling | `_ZN…E` 结构但 Rust 语义，`c++filt` 无法正确解读 |
| Swift mangling | `_$s` 前缀（Swift 5+），`swift-demangle` 工具解码 |
| Existential container | 5 word（40 字节）：3 word inline buffer + VWT 指针 + metadata 指针 |
| Value Witness Table | 类型的拷贝/移动/销毁操作表，泛型函数隐式参数传入 |
| Protocol Witness Table | 协议 requirement 实现表，类比 C++ vtable 但独立于对象 |
| `swiftcall` | Swift 原生调用约定：`r13` 传 self，`r12` 传错误输出槽 |
| Swift ABI 稳定 | Swift 5.0+ 仅 Apple 平台稳定；`@frozen` 保证布局稳定 |
| `cxx` crate | Rust/C++ 安全桥接，自动生成两侧胶水代码，支持 `std::string` 等 C++ 类型 |
| `bindgen`/`cbindgen` | 头文件 ↔ Rust 绑定的双向代码生成 |
| iOS 逆向三语言 | `_Z`/`_$s`/`-[…]` 前缀区分 C++/Swift/ObjC；`swiftcall` r13/r12 特征识别 |
| Panic 跨边界 | `extern "C"` 边界不能让 Rust panic 穿透；用 `catch_unwind` 或 `panic=abort` |
| 内存所有权 | 跨语言边界须明确所有权协议；C++ 异常须在 C++ 侧捕获转错误码 |

跨语言 ABI 互操作的核心教训是：**C ABI 是唯一可信的跨语言公共语言**。Rust 的 `extern "Rust"` 和 Swift 的 `swiftcall` 都是各自语言内部使用的私有协议——高效但不对外稳定。所有跨边界的数据和函数都必须经过 C ABI 投影，配合正确的 `repr` 标注、所有权协议与错误传播约定，才能构建安全稳固的多语言系统。
