# ObjC运行时（05）· 消息转发机制

## 概述与定位

> [!abstract] TL;DR
> `objc_msgSend` 沿 superclass 链仍找不到 IMP 时，不会立即崩溃，而是进入**消息转发（Message Forwarding）**流程——运行时给了三次"自救"机会：① 动态方法解析（`resolveInstanceMethod:`）、② 快速转发（`forwardingTargetForSelector:`）、③ 完整转发（`methodSignatureForSelector:` + `forwardInvocation:`）。三次均无回应，`doesNotRecognizeSelector:` 才抛出经典崩溃 `unrecognized selector sent to instance`。理解这三阶段是实现 AOP、防崩溃兜底、消息中转、接口适配的底层基础。

消息转发是 [[01.Objective-C运行时概览]] 中所述"消息发送"机制的延伸兜底层。[[04.objc_msgSend消息发送]] 已详细讲解 `objc_msgSend` 在 `cache_t` 中快速查找、命中则调 IMP、未命中则沿 `superclass` 链逐级查找的全过程；本篇聚焦那条路彻底走完仍无 IMP 时发生了什么。

---

## 原理与机制

### 触发条件

[[04.objc_msgSend消息发送]] 在慢速查找路径（`_class_lookupMethodAndLoadCache3` / `lookUpImpOrForward`）遍历完整个 superclass 链后仍未找到 SEL 对应的 IMP，就会返回一个特殊的占位 IMP：`_objc_msgForward`（或 `_objc_msgForward_stret`，用于结构体返回约定；ARM64 ABI 下结构体返回经 x8 间接返回，已不再需要 stret 变体，统一使用 `_objc_msgForward`）。`_objc_msgForward` 是转发入口 stub，被执行时即进入转发流程。

```
objc_msgSend(receiver, @selector(unknownMethod:), arg)
       │
       ▼
  cache_t 快速查找 ── 命中 → 直接调 IMP
       │
       ✗ 未命中
       │
       ▼
  慢速查找 lookUpImpOrForward
       │ 遍历 superclass 链
       ✗ 全部未命中
       │
       ▼
  返回 _objc_msgForward（触发转发）
```

### 三阶段转发总流程

```mermaid
graph TD
    MISS["objc_msgSend<br/>未找到 IMP"] --> PHASE1["① 动态方法解析<br/>+resolveInstanceMethod: / +resolveClassMethod:"]
    PHASE1 -->|返回 YES<br/>class_addMethod 补上 IMP| RETRY["重新走 lookUpImpOrForward<br/>（含缓存）"]
    RETRY --> DONE1["找到 IMP → 调用"]
    PHASE1 -->|返回 NO 或未处理| PHASE2["② 快速转发（备援接收者）<br/>-forwardingTargetForSelector:"]
    PHASE2 -->|返回非 nil 对象| REDIRECT["把消息原样发给备援对象<br/>objc_msgSend(target, sel, ...)"]
    REDIRECT --> DONE2["备援对象处理完毕"]
    PHASE2 -->|返回 nil 或 self| PHASE3A["-methodSignatureForSelector:"]
    PHASE3A -->|返回 nil| CRASH["doesNotRecognizeSelector:<br/>unrecognized selector 崩溃"]
    PHASE3A -->|返回 NSMethodSignature| PHASE3B["③ 完整转发<br/>-forwardInvocation:<br/>拿到 NSInvocation"]
    PHASE3B -->|调用或忽略| DONE3["转发完毕（或静默丢弃）"]
    PHASE3B -->|调用 [super forwardInvocation:]| CRASH
```

## 结构与流程详解

### 阶段一：动态方法解析

**触发时机**：`_objc_msgForward` 被调用后，运行时第一步先问类本身：「你愿意临时补上这个方法吗？」

```objc
// 对实例方法（普通对象收到未知消息）
+ (BOOL)resolveInstanceMethod:(SEL)sel;

// 对类方法（类对象收到未知消息）
+ (BOOL)resolveClassMethod:(SEL)sel;
```

实现者在这两个方法里调用 `class_addMethod` 动态注册一个 IMP，然后返回 `YES`。运行时收到 `YES` 后**重新触发 `lookUpImpOrForward`**，此时新注册的 IMP 可被找到、正常调用。

```objc
// 源码级伪代码（基于 objc4 objc-runtime-new.mm 逻辑）
static IMP resolveMethod_locked(id inst, SEL sel, Class cls, int behavior) {
    // 对实例方法调 +resolveInstanceMethod:
    BOOL resolved = [cls resolveInstanceMethod:sel];
    if (resolved) {
        // 重启查找，新 IMP 已注册进 class_rw_t
        return lookUpImpOrNil(inst, sel, cls);
    }
    return nil;
}
```

**典型用途：`@dynamic` 属性**

`@dynamic` 告诉编译器"存取器在运行时提供"，不自动合成 getter/setter。配合 `resolveInstanceMethod:` 可在运行时动态合成任意属性的存取器，CoreData 的 `NSManagedObject` 正是如此实现属性访问的。

```objc
// 示例：动态为 @dynamic 属性合成 getter
+ (BOOL)resolveInstanceMethod:(SEL)sel {
    NSString *selName = NSStringFromSelector(sel);
    if ([selName hasPrefix:@"dynamic_"]) {
        class_addMethod(self, sel,
                        (IMP)dynamicGetterIMP,
                        "@@:");   // 方法签名：返回 id，参数 self(id) + _cmd(SEL)
        return YES;
    }
    return [super resolveInstanceMethod:sel];
}
```

与 [[03.类、元类与方法列表]] 中描述的 `class_rw_t` 方法列表直接相关：`class_addMethod` 在运行时向 `class_rw_t` 的 methods 列表追加一条 `method_t`，后续查找即可命中。

---

### 阶段二：快速转发（备援接收者）

动态解析返回 `NO`（或没覆盖该方法默认返回 `NO`）后，运行时问：「有没有另一个对象能代你处理这条消息？」

```objc
- (id)forwardingTargetForSelector:(SEL)aSelector;
```

返回一个非 `nil`、非 `self` 的对象，运行时直接把**原始消息（含全部参数）** 原样发给该对象，相当于：

```objc
objc_msgSend(returnedTarget, aSelector, originalArgs...);
```

**特点**：
- 开销极小——运行时直接跳转，不构造 `NSInvocation`
- 对调用方完全透明，**无法修改参数**
- 可模拟"多继承"或"组合式代理"：将多个功能对象组合进一个宿主，宿主自身不实现方法，全部转给内部子对象

```objc
// 示例：组合代理
@interface Facade : NSObject
@property (nonatomic, strong) SubComponentA *compA;
@property (nonatomic, strong) SubComponentB *compB;
@end

@implementation Facade
- (id)forwardingTargetForSelector:(SEL)aSelector {
    if ([self.compA respondsToSelector:aSelector]) return self.compA;
    if ([self.compB respondsToSelector:aSelector]) return self.compB;
    return nil;   // nil → 进入完整转发
}
@end
```

---

### 阶段三：完整转发

快速转发返回 `nil` 或 `self` 后，进入代价最高但也最灵活的完整转发。分两步。

#### 步骤 3a：`-methodSignatureForSelector:`

```objc
- (NSMethodSignature *)methodSignatureForSelector:(SEL)aSelector;
```

运行时需要知道方法的参数类型和返回值类型，才能构造 `NSInvocation`。若返回 `nil`，流程**直接跳到 `doesNotRecognizeSelector:` 崩溃**，不再往下走。

```objc
// 示例：为转发方法手动提供签名
- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    NSMethodSignature *sig = [super methodSignatureForSelector:sel];
    if (!sig) {
        // 手动构造：v@: 代表 void 返回、id self、SEL _cmd
        sig = [NSMethodSignature signatureWithObjCTypes:"v@:"];
    }
    return sig;
}
```

`NSMethodSignature` 内部封装了 ObjC 类型编码字符串（`@encode(type)` 所产生的格式），与 [[03.类、元类与方法列表]] 中 `method_t::types` 字段的格式完全一致。

#### 步骤 3b：`-forwardInvocation:`

```objc
- (void)forwardInvocation:(NSInvocation *)anInvocation;
```

运行时把消息封装成一个 `NSInvocation` 对象（包含 target、selector、所有参数、返回值槽），交给 `-forwardInvocation:`。实现者可以：

- 修改 `anInvocation.target` 后调用 `[anInvocation invoke]`——转发给另一个对象
- 修改 `anInvocation.selector`——映射到另一个选择器
- 读写参数（`[anInvocation getArgument:&val atIndex:i]` / `setArgument:atIndex:`）
- 把同一个 invocation 发给多个对象（广播）
- 记录日志、延迟执行（`[anInvocation retainArguments]` 后入队）
- 直接忽略（即静默丢弃消息，等效于空实现）

```objc
// 示例：广播转发
- (void)forwardInvocation:(NSInvocation *)inv {
    [inv setTarget:self.observerA];
    [inv invoke];
    [inv setTarget:self.observerB];
    [inv invoke];
}
```

如果不知道如何处理，调 `[super forwardInvocation:inv]`，最终会到 `NSObject` 的默认实现——调 `doesNotRecognizeSelector:` 崩溃。

---

### `doesNotRecognizeSelector:`

```objc
- (void)doesNotRecognizeSelector:(SEL)aSelector;
```

三阶段均无回应（或 `methodSignatureForSelector:` 返回 `nil`），最终调此方法，默认实现抛出：

```
-[SomeClass unknownMethod:]: unrecognized selector sent to instance 0x...
```

可覆盖 `doesNotRecognizeSelector:` 做最终兜底（如只记日志不崩溃），但**不要调 `super`**，否则还是崩溃。

---

### `NSInvocation` 数据结构概览

```
NSInvocation {
    NSMethodSignature *sig;   // 参数/返回值类型描述
    id                target; // 消息接收者（可改）
    SEL               selector;
    void             *args[]; // 捕获的原始参数（arg[0]=self, arg[1]=_cmd, arg[2+]=实参）
    void             *retVal; // 返回值缓冲区
}
```

构造和使用开销远高于直接 IMP 调用，底层需要 `mprotect`-safe 的栈帧重建，是完整转发比快速转发慢一个量级的根本原因。

## 逆向实践

### Hook `forwardInvocation:` 监控未实现调用

逆向分析或动态插桩时，hook `-forwardInvocation:` 可以捕获所有到达该阶段的未实现消息，常用于：

- 调查第三方 SDK 的私有 API 调用
- 记录 App 运行时意外丢失的消息

Frida 示例（监控全局 forwardInvocation）：

```javascript
// Frida 脚本示例（说明用）
const NSObject = ObjC.classes.NSObject;
const origFwd = NSObject['- forwardInvocation:'];
Interceptor.attach(origFwd.implementation, {
    onEnter(args) {
        // args[0] = self (ObjC.Object)
        // args[2] = NSInvocation *
        const inv = new ObjC.Object(args[2]);
        console.log('[forwardInvocation]', args[0], '->', inv.selector());
    }
});
```

> [!warning] 示例输出为示意
> 以上 Frida 脚本仅作原理说明，实际输出取决于目标 App 的运行时行为。

### LLDB 断点观察转发链

```bash
(lldb) b -[NSObject forwardInvocation:]
(lldb) b -[NSObject methodSignatureForSelector:]
(lldb) b -[NSObject doesNotRecognizeSelector:]
```

> [!warning] 示例输出为示意
> 断点命中时可通过 `po $arg2`（ARM64 第三个参数）打印 SEL 或 NSInvocation。

### class-dump 与转发接口

class-dump 还原头文件时，实现了 `forwardInvocation:` 但 `methodSignatureForSelector:` 只返回通用签名的类，往往是"消息中转层"——在逆向中是值得重点分析的关键类。参见 [[11.Mach-O中的ObjC元数据]] 对 `__objc_classlist` 的解析。

## 与 Method Swizzling 的区别

[[08.Method Swizzling]] 是在方法**已存在**的前提下，将两个 IMP 互换：

```
Method Swizzling：methodA.imp ↔ methodB.imp
    → 调用 methodA 实际执行 methodB 的代码
    → 原方法在 class_rw_t 中是存在的
```

消息转发是方法**根本不存在**时的兜底：

```
消息转发：SEL 在整条 superclass 链上无 IMP
    → 三阶段给机会临时处理
    → 最终无人处理则崩溃
```

| 维度 | 消息转发 | Method Swizzling |
|---|---|---|
| 前提 | 方法不存在（或 `_objc_msgForward`） | 方法已存在于方法列表 |
| 阶段 | `lookUpImpOrForward` 返回占位 IMP 后 | `method_exchangeImplementations` 直接改 `method_t.imp` |
| 性能 | 慢（完整转发需构造 NSInvocation） | 几乎无额外运行时开销 |
| 典型场景 | 动态代理、防崩溃兜底、`@dynamic` | AOP hook、测试 mock、行为替换 |
| 源码层 | `objc-runtime-new.mm` 转发分支 | `objc_method.h method_exchangeImplementations` |

## 应用场景

### 消息中转与多重代理

`Facade` 对象通过 `forwardingTargetForSelector:` 或 `forwardInvocation:` 将消息路由到内部多个组件，对外表现为"单一接口"，实现类似多重继承的效果而不依赖类继承体系。

### AOP（面向切面编程）

`forwardInvocation:` 适合在不修改原有 IMP 的前提下，包装日志、埋点、性能统计逻辑——先记录再转发，或转发后记录。相比 [[08.Method Swizzling]]，转发路径对原逻辑侵入更小，但代价是只能拦截"没有原始实现"的方法，或需要额外将方法替换为 `_objc_msgForward` 来强制进入转发流程（这是一些 AOP 框架的做法）。

### 防崩溃兜底框架

覆盖 `resolveInstanceMethod:` 或 `forwardInvocation:`，为所有"未识别的 selector"提供一个空实现或降级逻辑，防止 `unrecognized selector` crash 在生产环境中扩散：

```objc
// 兜底：对任意未知消息返回通用签名 + 空转发
- (NSMethodSignature *)methodSignatureForSelector:(SEL)sel {
    NSMethodSignature *sig = [super methodSignatureForSelector:sel];
    return sig ?: [NSMethodSignature signatureWithObjCTypes:"v@:"];
}

- (void)forwardInvocation:(NSInvocation *)inv {
    // 只记日志，不 invoke，静默丢弃
    NSLog(@"[SafeProxy] dropped unknown selector: %@", NSStringFromSelector(inv.selector));
}
```

> [!caution] 兜底慎用
> 全量静默兜底会掩盖真实 bug，建议仅在边界层（如第三方 SDK 调用点）有限度使用，并配合日志/监控。

### 接口适配（Adapter 模式）

将旧 API 的消息在运行时重映射到新 API，无需修改调用方代码：

```objc
- (void)forwardInvocation:(NSInvocation *)inv {
    SEL newSel = mappingTable[inv.selector];  // 查旧→新映射表
    if (newSel) {
        [inv setSelector:newSel];
        [inv invokeWithTarget:self.realImpl];
    }
}
```

## 安全性与正确使用

### 性能：三阶段代价不等

| 阶段 | 相对开销 | 原因 |
|---|---|---|
| 动态方法解析（阶段①） | 低（一次性） | 仅首次触发，补上 IMP 后后续走正常缓存命中 |
| 快速转发（阶段②） | 低 | 直接转发消息，不构造 NSInvocation |
| 完整转发（阶段③） | 高 | 需构造 NSInvocation（栈帧捕获、参数拷贝、类型编码解析） |

热路径（每帧/高频调用）上绝对不应依赖完整转发，应在设计阶段用协议/多态替代。

### 签名不匹配崩溃

`methodSignatureForSelector:` 返回的签名必须与实际调用的参数类型精确匹配。若签名声明 2 个参数而 IMP 期望 3 个，`NSInvocation invoke` 时会出现栈污染，可能导致：

- 随机崩溃（参数读取越界）
- 寄存器/内存破坏（ARM64 参数通过 x0–x7 传递）
- 静默数据错误（最危险）

务必使用 `[target methodSignatureForSelector:realSel]` 从实际实现对象处获取签名，而非手写类型字符串。

### 转发链中的循环

若两个对象互相把消息转发给对方（A → B → A → ...），会导致无限递归直至栈溢出崩溃。加入 `-respondsToSelector:` 前置检查可预防：

```objc
- (id)forwardingTargetForSelector:(SEL)sel {
    if ([self.delegate respondsToSelector:sel]) {
        return self.delegate;  // 确认备援对象真的能响应
    }
    return nil;
}
```

### 过度依赖转发的可读性问题

滥用消息转发会让代码的"哪个对象真正处理了这条消息"变得极其难以追踪，IDE 的跳转/补全也会失效（因为方法在源码中并不存在）。建议：

- 有明确协议约束时用协议 + 组合，不用转发
- 使用转发时在 `-forwardingTargetForSelector:` 中加 `assert` 或日志辅助调试
- 逆向分析中遇到转发链时，用 LLDB `b -[NSObject forwardInvocation:]` 断点顺藤摸瓜

### 与 [[01.Objective-C运行时概览]] 合规边界

消息转发本质上是运行时提供的**合法公开 API**（Foundation 框架声明），用于自有代码完全合规。若用于 hook 第三方 App 的 `forwardInvocation:`（越狱环境下的逆向分析），属于安全研究范畴，参考 [[13.iOS安全与砸壳]] 的合规原则：仅限自有 App 评估与授权样本分析。

## 小结

1. `objc_msgSend` 未命中 IMP → 返回 `_objc_msgForward` 占位 IMP → 进入转发。
2. **阶段①动态解析**：`resolveInstanceMethod:` / `resolveClassMethod:` + `class_addMethod` 补 IMP，返回 YES 重启查找；`@dynamic` 属性的标准实现方式；与 [[03.类、元类与方法列表]] 的 `class_rw_t` 直接联动。
3. **阶段②快速转发**：`forwardingTargetForSelector:` 返回备援对象，原样转发消息，开销最小；可实现组合代理/伪多继承。
4. **阶段③完整转发**：先 `methodSignatureForSelector:` 提供签名（缺一不可），再 `forwardInvocation:` 接收 `NSInvocation`，可读写 target/selector/参数，最灵活但最慢。
5. 三阶段均无回应 → `doesNotRecognizeSelector:` → crash。
6. 与 [[08.Method Swizzling]] 的本质区别：转发是"无方法时兜底"，Swizzling 是"已有方法时替换"。
7. 逆向视角：hook `forwardInvocation:` 可监控未实现调用；class-dump 中实现该方法的类往往是关键转发层。
