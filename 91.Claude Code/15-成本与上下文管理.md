# 15 · 成本与上下文管理

> [!abstract] TL;DR
> 用对模型、控住上下文长度、善用 prompt caching，是把 Claude Code 费用压到合理范围的三板斧。`/cost` 随时查花费，`/compact` 在上下文撑满前压缩而非清空，子代理隔离支线任务以保护主会话 token 预算。

---

## 概述与定位

Claude Code 按 API 调用计费：**输入 token × 单价 + 输出 token × 单价**。长对话、大文件全量注入、频繁调用最强模型，是费用失控的三大来源。本篇从"选对模型"、"管住上下文"、"用好 prompt caching"三个维度提供可操作的实践，并说明如何用 `/cost`、`/compact`、`/clear`、`/rewind` 等内置命令监控和干预。

---

## 原理与机制

### API 计费基础

每次与 Claude 交互，实际发送给 API 的是**完整的对话历史**（所有轮次的用户消息 + 助手回复 + 工具调用结果），而不仅仅是最新一句话。这意味着：

- 对话越长，每次调用的**输入 token 数**越大；
- 上下文一旦包含大量文件内容，单轮费用可能是"只聊两句"的数十倍；
- 每轮助手的思考与回复构成**输出 token**，通常比输入贵。

### Prompt Caching

Anthropic 对**重复的上下文前缀**提供缓存折扣（缓存命中时输入价格大幅下降）。缓存以 **5 分钟 TTL** 为单位维持：若前缀相同、且两次调用间隔在 5 分钟以内，命中缓存；超时则失效，下次调用重新按全价计算。

Claude Code 会自动在合适的位置插入缓存断点（cache breakpoints），无需手动干预，但了解 TTL 有助于判断"短暂离开再回来"是否还能命中缓存。

### 上下文增长曲线

```
token 数
  ▲
  │          /compact 压缩
  │  xxxxxx /                        ← 压缩后恢复到摘要基准线
  │  x    /
  │  x   /          ← 任务继续，上下文再增长
  │  x  /
  │ xx /   ← 对话开始后持续增长
  │xx /
  └──────────────────────────────▶ 时间/轮数
```

不加干预时，上下文会单调增长直到触达模型上限（Claude 3.7 系最大 200K token）；触达限制前 Claude Code 会**自动发出警告**。

## 结构/算法/伪代码详解

### 模型分层经验法则

| 任务类型 | 推荐模型 | 理由 |
|---|---|---|
| 扫描目录、搜索关键字、读文件结构 | `haiku` 或 `sonnet` | 机械性多、不需深推理，速度快、价格低 |
| 代码审查、单元测试生成、格式整理 | `sonnet` | 中等复杂度，性价比最佳 |
| 架构设计、复杂 bug 定位、跨文件重构 | `opus` | 需要长链推理，质量优先 |
| 子代理调研任务 | `haiku`/`sonnet`（按任务） | 隔离上下文，汇总结论给主会话 |

子代理的 `model` 字段可单独指定，不继承主会话模型：

```markdown
---
name: file-scanner
description: 快速扫描目录结构，汇报相关文件路径。
tools: Glob, Grep, Read
model: haiku
---
你是文件扫描助手，只做搜索，不做修改，返回简洁的文件路径列表。
```

**注意**：若使用第三方中转 token 且无 haiku 权限，`model: haiku` 会触发 403 静默失败。无权限时改为 `model: sonnet` 或直接省略（继承主会话模型）。

### 上下文管理决策流程

```mermaid
flowchart TD
    A[收到新任务] --> B{上下文是否<br/>已很长?}
    B -- 否 --> C[直接继续对话]
    B -- 是 --> D{任务是否需要<br/>之前的完整历史?}
    D -- 需要 --> E[/compact 压缩<br/>保留摘要继续]
    D -- 不需要 --> F{是否是全新<br/>独立任务?}
    F -- 是 --> G[/clear 清空<br/>全新开始]
    F -- 否 --> E
    C --> H[执行任务]
    E --> H
    G --> H
```

### `/compact`、`/clear`、`/rewind` 的区别

| 命令 | 效果 | 何时用 |
|---|---|---|
| `/compact` | 把当前对话**压缩成摘要**，摘要替换原始历史，继续对话 | 任务还在进行，但上下文太长，需要减负而不丢失进展 |
| `/clear` | **完全清空**对话历史，回到空白状态 | 当前任务已完成，要开始全新的不相关任务 |
| `/rewind` | **回退**到指定的历史轮次，删除该轮之后的所有内容 | 发现某次操作走偏，想从岔路口重新来过 |

`/compact` 可以接受自定义指令，指定压缩时重点保留哪些信息：

```
/compact 保留所有已修改文件的路径和变更摘要，以及未完成的 TODO 列表
```

## 工具视角与实战

### 查看当前花费：`/cost`

在任意时刻输入 `/cost`，Claude Code 显示**本次会话**的 token 消耗与估算费用（基于当前选定模型的定价）：

```
Session cost: $0.42
  Input tokens:  48,320  (cached: 31,200)
  Output tokens: 3,840
  Cache savings: ~$0.19
```

重点关注 **cached** 比例：缓存命中率高说明上下文前缀稳定、重用效率好。

### 长任务的上下文控制节奏

长任务（如重构整个模块、批量处理文件）最容易撑爆上下文，推荐节奏：

1. **任务开始前**：确认上下文基本干净，或 `/clear` 后再开始；
2. **每完成一个阶段**：用 `/compact` 压缩，把已完成阶段变成摘要；
3. **遇到支线调研**：委派子代理（见 [[91.Claude Code/07-Subagents与工作流.md]]），子代理结束后只把**结论文本**带回主会话；
4. **主会话不直接 Read 超大文件**：让子代理读，主会话只看摘要；
5. **阶段完成后**开新会话：把上一阶段产出写成文件或 CLAUDE.md 注记，下次会话从文件读，不依赖对话历史。

### 避免不必要的大上下文调用

- **不要一次性把整个代码库倒进上下文**：用 `Glob`/`Grep` 精准定位相关文件，只 Read 必要的部分；
- **图片/二进制文件不要反复附入**：每次附入都是额外的输入 token；
- **长系统提示（CLAUDE.md）注意精简**：CLAUDE.md 随每次请求注入，过长会持续消耗输入 token（见 [[91.Claude Code/16-CLAUDEmd编写实践.md]]）；
- **工具调用结果很长时及时用 `/compact`**：grep 返回几千行的工具结果会直接堆进上下文。

### 用子代理隔离上下文省主会话 token

子代理拥有**独立的上下文窗口**：它消耗的 token 计在它自己的上下文里，只有**最终返回给主会话的文本**才进入主会话的 token 计数。

典型场景：

```
主会话（聚焦架构决策，上下文保持轻量）
   │  "扫一遍 src/controllers/，告诉我有哪些接口、每个接口的方法签名"
   ▼
file-scanner 子代理（model: haiku）
   │  Glob + Read 若干文件，总计消耗 20K 输入 token
   │  只返回 500 字的接口摘要
   ▼
主会话（拿到 500 字摘要，继续讨论，实际只增加了 500 token）
```

详细的子代理定义与并行用法见 [[91.Claude Code/07-Subagents与工作流.md]]。

## 安全性与正确使用

> [!note] 成本失控的常见原因与规避
>
> **原因一：无意识的大文件注入**
> 在主会话中直接 `Read` 一个 5000 行的源文件，之后的每次对话都带着这 5000 行进输入。规避：只读你真正需要对比或引用的片段；其余交给子代理或 Grep 精准搜索。
>
> **原因二：长会话不清理，任务其实已经换了**
> 原来在调试 A 功能，现在要写 B 功能，但上下文还带着调试 A 的全部历史。规避：任务切换时 `/clear` 或开新会话。
>
> **原因三：用最贵模型做最简单的事**
> 让 `opus` 帮你批量重命名变量、生成注释等低复杂度任务。规避：建 `haiku`/`sonnet` 子代理专门处理机械性任务。
>
> **原因四：prompt caching 失效**
> 频繁修改 CLAUDE.md 或系统提示，导致缓存断点前移，大段已缓存内容全部失效，重新全价计算。规避：批量修改 CLAUDE.md，避免每轮都微调。
>
> **原因五：子代理未指定模型，默认继承 opus**
> 若主会话用 opus，子代理不指定 model 则继承，批量并行子代理可能几十秒内消耗大量 opus token。规避：在子代理 frontmatter 显式写 `model: sonnet` 或 `model: haiku`。

---

## 小结

成本与上下文管理的核心逻辑是**分层隔离**：用便宜模型做简单任务、用子代理隔离支线调研、用 `/compact` 而非 `/clear` 在不丢进展的前提下给上下文减重、靠 prompt caching 把重复前缀的费用摊薄。`/cost` 是健康检查的第一步，养成每隔几轮看一次的习惯，比事后复盘账单更省心。
