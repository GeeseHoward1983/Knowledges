# 动态链接与加载器（12）· TLS的实现

> [!abstract] TL;DR
> - **TLS（Thread-Local Storage，线程局部存储）** 让每个线程拥有变量的私有副本：同一个符号名，读写的却是各线程独立的内存块，彼此不干扰。
> - ELF 用 `PT_TLS` 程序头描述 TLS 模板（`.tdata` 初始化数据 + `.tbss` 清零区），运行时库为每个线程克隆这份模板；`fs` 段寄存器（x86-64）指向线程控制块（TCB），TCB 内嵌动态线程向量（DTV）索引各模块的 TLS 块。
> - 编译器按访问模型选不同指令序列：**Local Exec** 最快（主程序自用，`%fs:offset` 一步到位），**Initial Exec** 次之（加载时绑定），**Local/General Dynamic** 最通用但需调用 `__tls_get_addr`；较新的 **TLSDESC** 用描述符间接调用进一步降低 GD 模型的慢路径代价。
> - Windows 走完全不同的路：`IMAGE_TLS_DIRECTORY`、`_tls_index`、静态 TLS（`__declspec(thread)`）vs 动态 `TlsAlloc`；TLS 回调（`PIMAGE_TLS_CALLBACK`）早于 `WinMain` 执行，是逆向分析高价值点。
> - macOS 在 arm64 上引入编译器内建 TLS 路径，绕过 `__tls_get_addr`，结合 dyld4 实现近似 IE 的延迟初始化语义。

TLS 是多线程编程的基础设施，但它的实现横跨编译器、链接器、动态链接器、操作系统内核四个层次，各平台形态差异极大。本篇以 x86-64 Linux 的 ELF TLS 模型为主干，讲透数据结构、访问模型与编译器生成代码，再以 Windows/macOS 做对照，最后给出三平台汇总与实操命令。

前置知识：`PT_TLS` 程序头已在 [[11.ELF文件详解/03.程序头表.md]] §§PT_TLS 一节描述，Windows `IMAGE_TLS_DIRECTORY` 与 TLS 回调详见 [[13.PE文件详解/17-详解PE文件(十七)：TLS表.md]]，本篇在这两篇基础上往纵深挖。

## 概述与定位

### 为什么需要 TLS

多线程程序里有些状态天然是"线程私有"的：C 标准库的 `errno`、locale 设置、`strtok` 内部指针、openssl 的错误队列……若这些用全局变量，多线程并发访问必须加锁，性能极差；若用函数参数传递则需大规模改接口。TLS 的思路是：**用同一个变量名，让每个线程映射到各自私有的内存块**。

语言层面，三种关键字都实现了这个语义：

```c
/* C11 及之前，GCC/Clang 扩展 */
__thread int tls_counter;

/* C11 */
_Thread_local int tls_counter;

/* C++11 */
thread_local int tls_counter;
```

三者在 ELF 文件格式层面均产生相同的节属性（`SHF_TLS`）与重定位类型，差异仅在析构语义（`thread_local` 支持非平凡析构，`__thread`/`_Thread_local` 仅支持 POD）。

### TLS 在本系列的位置

本篇是 [[11.初始化与析构顺序]] 的直接后续——`__cxa_thread_atexit` 注册的 TLS 析构是在线程退出时由运行库调用的，而 TLS 块本身的创建正是本篇主题。[[13.符号版本与二进制兼容]] 将讨论 `__tls_get_addr` 等运行库接口的版本约束。

## 原理与机制

### ELF TLS 的数据模型

ELF 规范把 TLS 分为三层：

1. **TLS 模板**：编译期产物，储存在 `.tdata`（有初始值）和 `.tbss`（清零区）节中，由 `PT_TLS` 程序头描述（`p_filesz = .tdata` 大小，`p_memsz = .tdata + .tbss` 大小）。每个需要 TLS 的模块（可执行文件或 DSO）都有自己的 TLS 模板。

2. **TLS 块（TLS Block）**：运行期，每当新线程创建时，运行库为每个已加载模块克隆一份模板，得到该线程对该模块的 TLS 块。块大小 = `p_memsz`，前 `p_filesz` 字节复制模板数据，其余清零。

3. **寻址结构**：线程怎么找到自己的 TLS 块？这是本篇核心。

### TCB、DTV 与段寄存器

x86-64 Linux 上，运行库（glibc `nptl`）使用如下结构管理 TLS：

```
┌──────────────────────────────────────────────────────────┐
│  %fs 段寄存器（x86-64）/ %gs（x86-32 / x32）             │
│  指向当前线程的 TCB 起点（或 TCB 内部某偏移）             │
└──────────────────────────────────────────────────────────┘
                          │
                          ▼
┌──────────────────────────────────────────────────────────┐
│  TCB（Thread Control Block）                              │
│  glibc 中即 struct pthread（pthread_t 所指）              │
│                                                          │
│  ┌────────────────┐  ←──── %fs:0 自引用指针（tcbhead_t）  │
│  │ self ptr       │                                      │
│  ├────────────────┤                                      │
│  │ DTV 指针       │──────┐                               │
│  ├────────────────┤      │                               │
│  │ ... 其他字段   │      │                               │
│  └────────────────┘      │                               │
│                          ▼                               │
│  ┌────────────────────────────────────────────────────┐  │
│  │ DTV（Dynamic Thread Vector）                       │  │
│  │ dtv[-1] = DTV 分配大小（元数据）                    │  │
│  │ dtv[0]  = 生成代数（generation counter）           │  │
│  │ dtv[1]  → 模块 1 TLS 块基址（主程序）              │  │
│  │ dtv[2]  → 模块 2 TLS 块基址（第一个 DSO）          │  │
│  │ dtv[n]  → 第 n 个模块的 TLS 块基址（或 NULL）      │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  每个 dtv[n] 指向对应模块的 TLS 块（.tdata 副本）        │
└──────────────────────────────────────────────────────────┘
```

**`%fs` 寄存器的设置机制**：线程创建时，glibc `nptl` 调用 `arch_prctl(ARCH_SET_FS, tcb_addr)` 系统调用（x86-64），由内核把 `tcb_addr` 写入当前线程的 FS.base MSR（`IA32_FS_BASE`，MSR 地址 `0xC0000100`）。从此 `%fs:0` 在该线程里就是 TCB 地址，`%fs:offset` 可直接访问 TCB 内的 TLS 数据，无需任何函数调用。

**各架构段寄存器对应**：

| 架构 | 线程指针寄存器 | 设置系统调用 |
|---|---|---|
| x86-64 | `%fs` | `arch_prctl(ARCH_SET_FS)` |
| x86-32 | `%gs` | `set_thread_area()` |
| AArch64 | `tpidr_el0` | `mrs/msr` 指令 |
| RISC-V | `tp` (x4) 寄存器 | `prctl` 或 clone 参数 |
| MIPS | `rdhwr` 读 ULR(hwr29) | |

**DTV 结构细节**（glibc `sysdeps/generic/dl-dtv.h`）：

```c
typedef union dtv_t {
    size_t counter;
    struct {
        void      *val;         /* TLS 块基址 */
        bool       is_static;   /* 是否在静态 TLS 区域（tcb_offset 有效）*/
    } pointer;
} dtv_t;

/* dtv[-1].counter = DTV 数组分配大小（槽位数）*/
/* dtv[0].counter  = 生成代数（dtv_epoch，与全局 dl_tls_generation 比较）*/
/* dtv[n] (n≥1)   = 第 n 个模块的 TLS 块指针 */
```

`dtv[0].counter` 是**生成代数（generation count）**，每次 `dlopen` 或 `dlclose` 加载/卸载含 TLS 的库时都会递增全局 `dl_tls_generation`。`__tls_get_addr` 调用时若检测到线程 DTV 的代数落后于全局代数，就知道 DTV 过时，需要扩容或更新槽位——这是 DTV 懒惰扩展的关键。

    TCB -->|tcbhead_t.dtv| DTV["DTV 数组<br/>dtv[-1]: 分配大小<br/>dtv[0]: generation 代数<br/>dtv[1]: 模块1 TLS块<br/>dtv[2]: 模块2 TLS块<br/>dtv[n]: 模块n TLS块"]

## 数据结构 / 流程详解

### ELF 端：`.tdata` / `.tbss` / `PT_TLS`

编译器为 `thread_local int x = 42;` 生成：

```
.tdata 节（SHF_TLS | SHF_ALLOC | SHF_WRITE，sh_type = SHT_PROGBITS）
  └── int x 的初始值：42（4 字节）

.tbss 节（SHF_TLS | SHF_ALLOC | SHF_WRITE，sh_type = SHT_NOBITS）
  └── 未初始化 TLS 变量（仅记录大小，文件中无内容）
```

链接器把所有带 `SHF_TLS` 的节汇入 `PT_TLS` 段：

```
PT_TLS
  p_filesz = .tdata 总大小     ← 有初始值，需从文件复制
  p_memsz  = .tdata + .tbss    ← 内存总大小（.tbss 部分运行时清零）
  p_align  = max(.tdata, .tbss 对齐要求)
  p_flags  = PF_R              ← 只读（TLS 模板本身不可写，副本可写）
```

详见 [[11.ELF文件详解/03.程序头表.md]] §PT_TLS。

### 四种 TLS 访问模型（x86-64）

编译器根据"变量定义在哪里"与"当前编译单元是否在主程序"，选择不同访问模型。从最通用到最受限（同时也从最慢到最快）：

#### General Dynamic（GD，通用动态）

**适用**：任何 TLS 变量，包括定义在 `dlopen` 延迟加载 DSO 中的变量。  
**性能**：最慢——每次需调用 `__tls_get_addr`。  
**编译标志**：`-ftls-model=global-dynamic`（默认用于共享库）。

```nasm
; x86-64 GD 模型（示意偏移，非真实地址）
leaq    tls_var@tlsgd(%rip), %rdi      ; rdi = GD 重定位描述符地址
                                        ;       R_X86_64_TLSGD 重定位
rex.W call __tls_get_addr@plt           ; 调用 __tls_get_addr(module_id, offset)
                                        ; 返回：rax = tls_var 在当前线程中的地址
movl    (%rax), %eax                    ; 读取变量值
```

`leaq tls_var@tlsgd(%rip), %rdi` 产生 `R_X86_64_TLSGD` 重定位，链接器在 `.got` 中为 `tls_var` 分配 **2 个连续 GOT 槽位**：`[模块ID, TLS 块内偏移]`，加载时由 `ld.so` 填充。`__tls_get_addr` 用这两个值查 DTV 得到变量地址。

**`__tls_get_addr` 的作用与慢路径**：

```c
/* glibc sysdeps/x86_64/dl-tls.S（伪 C）*/
void * __tls_get_addr(tls_index *ti) {
    dtv_t *dtv = THREAD_DTV();               /* 读当前线程 DTV 指针 */
    if (__builtin_expect(dtv[0].counter != dl_tls_generation, 0))
        return __tls_get_addr_slow(ti);      /* 慢路径：DTV 过时，扩容/重分配 */
    void *p = dtv[ti->ti_module].pointer.val;
    if (__builtin_expect(p == TLS_DTV_UNSET, 0))
        return __tls_get_addr_slow(ti);      /* 慢路径：该模块 TLS 块未分配 */
    return p + ti->ti_offset;               /* 快路径：直接索引 DTV */
}
```

多数情况下走快路径（DTV 已更新且槽位已分配），但仍有函数调用与 DTV 检查的开销，这就是 GD 比 IE/LE 慢的原因。

#### Local Dynamic（LD，本地动态）

**适用**：访问同一 DSO 内多个 TLS 变量时的优化。  
**思路**：先用一次 `__tls_get_addr` 得到**本模块 TLS 块的基址**，然后用 `leaq offset(%rax), %rax` 计算各变量地址，省去多次 `__tls_get_addr` 调用。  
**关键重定位**：`R_X86_64_TLSLD` + `R_X86_64_DTPOFF32/64`。

```nasm
; LD 模型：先取模块 TLS 基址
leaq    tls_module_base@tlsld(%rip), %rdi
call    __tls_get_addr@plt              ; rax = 本模块 TLS 块基址

; 再访问各变量
leaq    var_a@dtpoff(%rax), %rcx        ; rcx = &tls_var_a（用 DTPOFF 偏移）
leaq    var_b@dtpoff(%rax), %rdx        ; rdx = &tls_var_b
```

相比 GD，LD 在同一函数中访问多个本模块 TLS 变量时，只需一次 `__tls_get_addr`，性能更好。

#### Initial Exec（IE，初始执行）

**适用**：变量定义在**加载时已知模块**（主程序或启动时加载的 DSO）中，不经 `dlopen`。  
**性能**：快——`__tls_get_addr` 调用消失，改为 `%fs:` 一次读 GOT + 一次访问。  
**关键重定位**：`R_X86_64_GOTTPOFF`（GOT 项存的是变量相对线程指针的 `tp_offset`）。

```nasm
; IE 模型：从 GOT 取 tpoff，再经 %fs 访问
movq    tls_var@gottpoff(%rip), %rax    ; rax = GOT[tls_var] = tp_offset（相对 %fs:0 的偏移）
                                        ; R_X86_64_GOTTPOFF 重定位
movl    %fs:(%rax), %eax                ; 读取 %fs + tp_offset 处的值
```

`tp_offset` 是负值（在 x86-64 上，静态 TLS 分配在 TCB 低地址侧，所以偏移为负）。加载时 `ld.so` 填入 `GOT[tls_var] = &tls_var - __tls_tp`。

**限制**：IE 模型要求 TLS 变量来自加载时已知的模块，`dlopen` 后加载的库不能使用 IE 模型的变量（链接器/运行库无法预留静态 TLS 空间）。

#### Local Exec（LE，本地执行）

**适用**：主程序（可执行文件，非 DSO）自身定义并访问的 TLS 变量。  
**性能**：最快——编译时已知 `tp_offset`，直接 `%fs:constant_offset`，零额外开销。  
**关键重定位**：`R_X86_64_TPOFF32` 或 `R_X86_64_TPOFF64`（链接时直接把 `tp_offset` 作为立即数嵌入指令）。

```nasm
; LE 模型：最快，%fs + 编译期常量
movl    %fs:tls_var@tpoff, %eax         ; 直接 %fs:(-24)，无 GOT，无函数调用
```

`tls_var@tpoff` 在链接期就被替换为具体的负立即数（如 `-24`），运行时这条指令等价于 `movl %fs:-24, %eax`，性能与访问普通全局变量相差无几。

#### 四种模型总结对比

| 模型 | 别名 | 可用场景 | GOT 槽位 | 函数调用 | 访问序列 |
|---|---|---|---|---|---|
| General Dynamic | GD | 任意（含 dlopen）| 2 个（模块ID + 偏移）| `__tls_get_addr` | `leaq @tlsgd; call __tls_get_addr` |
| Local Dynamic | LD | 同模块多变量 | 1 个（模块基址）| `__tls_get_addr`（一次）| `leaq @tlsld; call; leaq @dtpoff` |
| Initial Exec | IE | 加载时已知模块 | 1 个（tp_offset）| 无 | `movq @gottpoff; %fs:(%rax)` |
| Local Exec | LE | 主程序自身 | 0 个 | 无 | `%fs:constant` |

> [!note] 编译器如何选模型
> - 编译 PIE 主程序时，若优化得当，编译器对本文件定义的 TLS 变量可用 LE；对外部定义的 TLS 变量默认用 IE（因为主程序不会被 `dlopen`）。
> - 编译共享库（`-fPIC`）时，默认用 GD；若库确知自身不被 `dlopen` 加载（用 `-ftls-model=initial-exec` 强制指定），可用 IE，但若被 `dlopen` 则运行时崩溃。
> - `-ftls-model=` 编译选项可手动覆盖；链接器也可能做 GD→IE/LE 的 **TLS 松弛优化**（TLS relaxation，详见下文）。

### TLS 松弛优化（TLS Relaxation）

链接器在最终链接时，拥有更多信息（主程序？DSO？是否 `dlopen`？），可以**把编译器生成的保守 GD/IE 模型降级为更快的 IE/LE 模型**：

| 松弛前 | 松弛后 | 条件 |
|---|---|---|
| GD `R_X86_64_TLSGD` | IE `R_X86_64_GOTTPOFF` | 链接主程序时，GD 变量可降为 IE |
| GD `R_X86_64_TLSGD` | LE `R_X86_64_TPOFF32` | 链接主程序且变量在本模块 |
| IE `R_X86_64_GOTTPOFF` | LE `R_X86_64_TPOFF32` | 链接主程序且变量在本模块 |
| LD `R_X86_64_TLSLD` | LE `R_X86_64_TPOFF32` | 链接主程序 |

松弛时链接器同时修改指令字节（把 `leaq ... (%rip); rex.W call` 序列改写为 `movq; nop` 或直接 `%fs:offset`），是二进制级别的重写，依赖特定的指令序列格式（`R_X86_64_TLSGD` 前必须是 `.byte 0x66; leaq` 的特定编码）。

### TLSDESC：更快的 GD 替代方案

传统 GD 模型通过 `__tls_get_addr` 调用走 ABI 接口，在 `dlopen` 场景下慢路径不可避免。**TLSDESC（TLS Descriptor）** 是 ARM/RISC-V/x86-64（gcc 14+ 支持 `x86-tlsdesc`）提供的改进方案：

- GOT 中为每个 GD 变量分配一个描述符（2 个槽位），第一个槽是**函数指针**，第二个是参数。
- 快路径下，函数指针直接指向一个仅做"DTV 索引 + 加偏移"的极短函数（比 `__tls_get_addr` 轻量得多，不需要完整的 ABI 调用约定）。
- 慢路径时，函数指针指向慢解析函数。

```nasm
; TLSDESC 模型（AArch64，示意）
adrp    x0, :tlsdesc:tls_var           ; x0 = TLSDESC GOT 页地址
ldr     x1, [x0, :tlsdesc_lo12:tls_var]
add     x0, x0, :tlsdesc_lo12:tls_var
.tlsdesccall tls_var
blr     x1                             ; 间接调用描述符里的函数指针
mrs     x2, tpidr_el0                  ; x2 = 线程指针
add     x0, x0, x2                     ; x0 = tls_var 地址
```

TLSDESC 的优势在于：描述符函数指针可以在库被初始化后换成"只读 offset 加法"的极轻量实现，避免每次都进完整的符号查找流程。

### `dlopen` 的库：TLS 按需分配与 DTV 扩展

`dlopen` 后加载的 DSO（如果它含有 TLS）会面临以下问题：

1. **DTV 容量不足**：加载前 DTV 长度只有已知模块数，新模块编号超出 DTV 末尾。解决：下次该线程调用 `__tls_get_addr` 时（进入慢路径），`ld.so` 重新 `malloc` 一个更大的 DTV，复制旧内容，更新线程 DTV 指针。

2. **TLS 块未分配**：新模块的 `dtv[module_id]` 初始为 `TLS_DTV_UNSET`。`__tls_get_addr` 慢路径调用 `allocate_tls_init`，为当前线程 `malloc` 该模块的 TLS 块、复制 TLS 模板数据，再把指针写入 DTV。

3. **其他已有线程**：其余线程的 DTV 也是过时的（`dtv[0].counter` 落后于全局 `dl_tls_generation`）。它们下次调用 `__tls_get_addr` 时各自触发慢路径更新。

这解释了**为什么 `dlopen` 的库必须走 GD 或 LD 模型**——IE/LE 要求静态 TLS 区域（TCB 附近的连续内存），而 `dlopen` 加载时这块区域已定型、无法扩展（有些实现保留有限的"静态 TLS 预留区"，允许少量 `dlopen` 库使用 IE，但容量极有限，见 glibc `TLS_STATIC_SURPLUS`）。

## Windows TLS 实现

### 静态 TLS：`__declspec(thread)`

MSVC `__declspec(thread)` 变量落入 `.tls` 节（或 MSVC 的 `.CRT$XL*` 系列节），链接器聚合后生成 `IMAGE_TLS_DIRECTORY`（数据目录索引 9）。详细字段已在 [[13.PE文件详解/17-详解PE文件(十七)：TLS表.md]] 系统讲解，此处重点补充运行时机制：

```c
typedef struct _IMAGE_TLS_DIRECTORY64 {
    ULONGLONG   StartAddressOfRawData;  /* TLS 模板起始 VA */
    ULONGLONG   EndAddressOfRawData;    /* TLS 模板结束 VA */
    ULONGLONG   AddressOfIndex;         /* _tls_index 变量 VA */
    ULONGLONG   AddressOfCallBacks;     /* TLS 回调数组 VA（NULL 终止）*/
    DWORD       SizeOfZeroFill;         /* 额外零填充字节数 */
    DWORD       Characteristics;        /* 保留，为 0 */
} IMAGE_TLS_DIRECTORY64;
```

**`_tls_index`**：Loader 为每个加载的模块分配一个唯一整数索引（写入 `AddressOfIndex` 指向的 DWORD），类似 ELF 的模块编号。线程通过 `TEB.TlsSlots[_tls_index]` 找到本模块的 TLS 块指针（MSVC 运行库自动生成访问代码，开发者无需显式使用）。

```
TEB（每线程一个，GS:[0] 在 x86-64 Windows 上）
┌─────────────────────────────┐
│ ...                         │
│ TlsSlots[64]                │  ← GS:[0x1480]（x64）/ FS:[0x0E10]（x86）
│   [0] → 模块A TLS 块指针    │
│   [1] → 模块B TLS 块指针    │
│   ...（最多 64 个直接槽）   │
│ TlsExpansionSlots*          │  ← 超过 64 个时扩展区指针
└─────────────────────────────┘
```

与 ELF DTV 对应关系：Windows 的 `TlsSlots` 是 ELF `DTV` 的等价物，`_tls_index` 对应 ELF 的模块编号。

**静态 TLS 的关键限制**：`__declspec(thread)` 要求 DLL 在进程启动时就已加载（静态导入或 `LoadLibrary` 在 `DLL_PROCESS_ATTACH` 之前）。对 `LoadLibrary` 动态加载进来的 DLL，若其包含静态 TLS，Windows XP 及以前版本会崩溃；Vista+ 通过 **FlsAlloc/FlsGetValue**（Fiber Local Storage）机制改进，但程序员仍不应在动态加载的 DLL 中使用 `__declspec(thread)`。

### 动态 TLS：`TlsAlloc` / `TlsGetValue`

动态 TLS API 是 Windows 的 `dlopen` 友好替代，等价于 ELF 的 `__tls_get_addr` 慢路径手动化：

```c
DWORD tlsIdx = TlsAlloc();              /* 分配全局 TLS 槽位（类似 ELF 的模块编号） */

/* 每个线程独立调用（或通过 DLL_THREAD_ATTACH 统一初始化）*/
TlsSetValue(tlsIdx, malloc(sizeof(MyData)));  /* 在当前线程存储私有数据 */

MyData *data = (MyData *)TlsGetValue(tlsIdx); /* 在当前线程取出私有数据 */

TlsFree(tlsIdx);                        /* 释放槽位（不自动 free 各线程的数据！）*/
```

API 实现走 TEB.TlsSlots（前 64 个槽）或 TEB.TlsExpansionSlots（第 65 个以上）。`TlsAlloc` 分配全局槽位编号，`TlsGetValue` 用当前线程的 GS 段寄存器指向的 TEB 取对应槽位的指针——这与 ELF 的 `%fs:dtv_offset` 本质相同，只是 API 化而非指令级内联。

### PIMAGE_TLS_CALLBACK：TLS 回调与攻防

TLS 回调（定义在 `AddressOfCallBacks` 指向的 NULL 终止数组里）具有签名：

```c
void NTAPI TlsCallback(PVOID DllHandle, DWORD Reason, PVOID Reserved);
/* Reason: DLL_PROCESS_ATTACH / DLL_THREAD_ATTACH / DLL_THREAD_DETACH / DLL_PROCESS_DETACH */
```

**执行时机**：Windows Loader 在调用 `WinMain` / `DllMain(DLL_PROCESS_ATTACH)` **之前**，就会按数组顺序逐一以 `DLL_PROCESS_ATTACH` 调用所有 TLS 回调。这意味着 TLS 回调是程序中**最先执行的用户代码**，比入口点还早。

> [!warning] 攻防高价值点
> TLS 回调是恶意软件和 Anti-Debug 的常用"前置入口"：
> 1. **反调试检测**：在调试器命中入口断点（`AddressOfEntryPoint`）之前，TLS 回调已跑完。若仅在 OD/x64dbg 设置"在入口点中断"，反调试逻辑会悄无声息地执行完毕，随后抹去自身或改变程序逻辑。
> 2. **解密/解壳**：先在回调里用 TLS 模板数据作为密钥解密后续代码，入口点拿到的是解密后状态。
> 3. **沙箱/VM 检测**：在主逻辑前嗅探环境（CPUID、计时、API 存在性），若判断在沙箱则将后续函数指针替换为空操作。
>
> **逆向对策**：在 IDA/Ghidra 中先检查 `.tls` 节和 `AddressOfCallBacks`；OD/x64dbg 用"DLL 事件暂停"（System Breakpoint）或显式在 TLS 回调 VA 设断点，不要只靠 OEP 断点。

## macOS TLS 实现

### Mach-O TLS 节布局

macOS 上的 `thread_local` 变量（Clang 生成）分散于以下节：

| 节名 | `__segment,__section` | 作用 |
|---|---|---|
| `__thread_vars` | `__DATA,__thread_vars` | `tlv_descriptor` 结构体数组，每个 TLS 变量一条 |
| `__thread_data` | `__DATA,__thread_data` | 有初始值的 TLS 变量模板（类似 `.tdata`） |
| `__thread_bss` | `__DATA,__thread_bss` | 零初始化 TLS 变量（类似 `.tbss`） |
| `__thread_init` | `__DATA,__thread_init` | 需要 C++ 构造的 TLS 对象的初始化回调 |

每个 TLS 变量在 `__thread_vars` 中对应一个 `tlv_descriptor`：

```c
typedef struct TLVDescriptor {
    void *(*thunk)(struct TLVDescriptor *);  /* 获取变量地址的函数指针 */
    unsigned long  key;                       /* pthread_key_t */
    unsigned long  offset;                    /* 块内偏移 */
} TLVDescriptor;
```

访问 TLS 变量时，编译器生成：

```nasm
; arm64 访问 thread_local 变量（示意）
adrp    x0, _tls_var@TLVP@PAGE          ; x0 指向 tlv_descriptor 页
ldr     x1, [x0, _tls_var@TLVP@PAGEOFF] ; x1 = thunk 函数指针
blr     x1                              ; 调用 thunk(descriptor)，返回变量地址
ldr     w0, [x0]                        ; 读取变量值
```

### dyld4 的优化

旧版（macOS 10.x）`thunk` 指针始终指向 `tlv_get_addr`，每次访问都是一个函数调用（类似 ELF 的 `__tls_get_addr`，代价相当）。

dyld4（macOS 12+）对 arm64 引入编译器内建 TLS 优化路径：

- 若 TLS 变量来自**已在启动时加载的模块**，dyld 在绑定期把 `thunk` 指针替换为一个极轻量的"直接 `tpidr_el0 + offset` 返回"的内联实现，消除函数调用开销——效果类似 ELF 的 IE/LE 优化。
- `pthread_key_t` 仍保留以支持慢路径（`dlopen` 加载的库、首次访问时需初始化等）。
- x86-64 macOS 仍走 `%gs:` 段寄存器，但寻址路径被 dyld 和 libpthread 协同优化。

```c
/* tls_demo.c */
__thread int tls_var = 42;              /* .tdata */
__thread char tls_buf[64];             /* .tbss  */

int read_tls(void) {
    return tls_var;
}
```

编译为共享库（GD 模型）：

```bash
gcc -fPIC -shared -ftls-model=global-dynamic -O2 -o libtls_demo.so tls_demo.c
readelf -r libtls_demo.so | grep -i tls
```

```text
# 示例输出（代表性，非本机实跑）
Relocation section '.rela.dyn' at offset ...:
  Offset          Info           Type                    Sym. Value  Sym. Name + Addend
  ...
  000000003ff0  000400000013 R_X86_64_TLSGD        0000000000000000 tls_var + 0
```

> [!warning] 示例输出为示意
> `R_X86_64_TLSGD` 类型常量值为 `0x13`（十进制 19），重定位紧跟 GOT 的连续两个槽位（GD 模型需要 2 槽：模块 ID + 偏移）；真实偏移随链接地址变化。

```bash
gcc -O2 -o tls_demo tls_demo.c

```

```text
# 示例输出（代表性，非本机实跑）
<read_tls>:
   ...
   401150:  64 8b 04 25 f8 ff ff ff    movl   %fs:0xfffffff8, %eax    ; %fs:-8
   401158:  c3                         retq
```

> [!warning] 示例输出为示意
> 链接器把 GD 重定位松弛为 LE：`movl %fs:<negative_offset>, %eax`，`0xfffffff8` 是 `-8` 的 32 位有符号表示。整个函数退化为 2 条指令，性能媲美普通全局变量访问。

## 攻防 / 陷阱

### LE 模型的隐患：`dlopen` 主程序变量

若主程序里有 `__thread` 变量，且程序把自身当 DSO 被别的程序通过 `dlopen` 加载（少见但存在），LE 模型生成的 `%fs:constant` 指令会用主程序静态 TLS 偏移——而 `dlopen` 的加载方有完全不同的 TLS 布局，直接导致**访问错误内存**。规避方法：供 `dlopen` 使用的代码应编译为 `-ftls-model=global-dynamic`。

### TLS 析构顺序陷阱

C++ `thread_local` 对象的析构在线程退出时由 `__cxa_thread_atexit` 注册的析构函数链调用（`__cxa_thread_atexit` 是 C++ ABI 层接口，底层可借 `pthread_key_create` 的线程退出回调驱动）。若 TLS 对象的析构函数间接访问另一个已被析构的 TLS 对象，则是 undefined behavior——即 "phoenix" 析构顺序问题。glibc 通过 POSIX `pthread_key_create` 实现 TLS 析构，析构顺序由注册顺序的逆序决定，但跨 DSO 的析构顺序不由规范保证。详见 [[11.初始化与析构顺序]]。

### Windows 静态 TLS 与 `LoadLibrary`

如前所述，`__declspec(thread)` 在动态加载的 DLL 中不可靠（Vista 前版本直接崩溃）。即使在 Vista+ 上，Loader 对动态加载 DLL 的 TLS 支持也有静态 TLS 槽位数量限制。安全做法：在动态加载的 DLL 里一律改用 `TlsAlloc`/`TlsGetValue`。

### TLS 大小膨胀对共享内存的影响

含 `thread_local` 的 DSO，其 `.tdata`/`.tbss` 数据对每个线程都会被复制一份。一个有 1000 个线程的进程加载了一个有 1 MiB TLS 变量的 DSO，意味着 ~1 GiB 私有内存。TLS 变量应尽量紧凑，大型线程私有缓冲区应改为 `thread_local` 指针 + 显式 `new/delete`。

## 小结

1. **TLS 四层模型（GD/LD/IE/LE）由编译器按"变量来源 + 当前模块类型"选择**：主程序自用变量走 LE（`%fs:常量`，最快）；来自加载时已知 DSO 走 IE（GOT 查 tp_offset，无函数调用）；来自任意 DSO（含 `dlopen`）必须走 GD/LD（调 `__tls_get_addr`，最通用最慢）；链接器在最终链接时可做 TLS 松弛（GD→IE/LE）。
2. **寻址链是 `%fs → TCB → DTV → TLS 块`**：`%fs:0` 指向 TCB（glibc 中的 `struct pthread`），TCB 内 DTV 指针索引各模块的 TLS 块，`dtv[module_id].pointer.val + offset` 就是变量地址；LE 模型直接用 `%fs:negative_constant` 跳过 DTV。
3. **`dlopen` 的 DSO 必须走 GD 慢路径**：因为静态 TLS 区域已定型、无法扩展；`__tls_get_addr` 慢路径负责按需扩展 DTV、分配 TLS 块。TLSDESC 通过可替换的函数指针描述符，把慢路径收敛为更轻量的间接调用。
4. **Windows 两套 TLS**：静态（`__declspec(thread)` + `IMAGE_TLS_DIRECTORY` + Loader 填 `_tls_index`）与动态（`TlsAlloc/GetValue/SetValue/Free` API）；TLS 回调（`PIMAGE_TLS_CALLBACK`）先于入口点执行，是逆向分析/反调试的高价值点。
5. **macOS 用 `tlv_descriptor` 的函数指针间接层统一了访问接口**；dyld4 在 arm64 上能把 `thunk` 替换为极轻量的"直接返回 `tpidr_el0 + offset`"路径，接近 ELF IE 性能。
6. **陷阱**：LE 模型不可在被 `dlopen` 的代码中使用；`thread_local` 析构顺序跨 DSO 不保证；Windows 动态加载的 DLL 不能用 `__declspec(thread)`，应改用 `TlsAlloc` API；大 TLS 块会以线程数倍数放大内存占用。
