# 动态链接与加载器（8）· PLT 与 GOT 与延迟绑定

> [!abstract] TL;DR
> - **问题**：一个可执行文件可能引用上千个外部函数（`printf`/`malloc`/`pthread_create`…），若在启动瞬间就把它们全部解析并回填地址，启动延迟会被白白拉长——而其中绝大多数函数本次运行根本不会被调用。
> - **方案**：把"调外部函数"拆成两层间接——代码段调用一个固定的小跳板 `foo@plt`（位于 `.plt`），跳板读 `.got.plt` 里的一个槽位决定真正跳哪。**首次**调用时该槽位回指一段"解析桩"，触发 `_dl_runtime_resolve(struct link_map *, reloc_index)` 去查符号、把真实地址**回填进同一个槽位**；**之后**再调用，跳板直接读到真实地址，零额外解析。这就是 **lazy binding（延迟绑定 / PLT-and-GOT 间接）**。
> - **三平台一句话**：Linux 用 `.plt`/`.got.plt` + `_dl_runtime_resolve`；macOS 用 `__stubs` + `__la_symbol_ptr` + `dyld_stub_binder`（新版 chained fixups 下惰性绑定基本退场）；Windows PE **导入即绑定**（IAT 在加载时一次填满，没有 lazy PLT），只有显式标了延迟加载的导入才走 `.didat` + `__delayLoadHelper2`。
> - **核心三保留项**：`GOT[0]=.dynamic` 地址、`GOT[1]=link_map`、`GOT[2]=_dl_runtime_resolve`——它们是整套延迟绑定能跑起来的"接线盒"。
> - **安全**：可写的 `.got.plt` 是 GOT 改写劫持的经典目标；`ret2dl-resolve` 进一步伪造重定位/符号结构去骗 `_dl_runtime_resolve`。`Full RELRO` + `BIND_NOW` 关掉 lazy 即可把 `.got.plt` 锁成只读。

本篇是「动态链接与加载器详解」系列承上启下的**机制硬核篇**：前面 [[07.重定位机制详解]] 讲清了"占位地址如何被改写成真实地址"，本篇把镜头对准**函数调用专用的那条重定位通道**——`JUMP_SLOT` + PLT/GOT，并把首次调用时 `_dl_runtime_resolve` 的解析过程逐步拆开。函数 GOT 的静态结构在 [[11.ELF文件详解/21.got.plt节.md]] 已有系统介绍，本篇与它强相关、口径一致，但视角不同：那篇讲"文件里这张表长什么样"，本篇讲"运行时这张表怎么被一步步填活"。

## 概述与定位

### 为什么需要延迟绑定

动态链接的代价里，有相当一块是**符号解析**：动态链接器要在 `.dynsym` / `gnu_hash` 里查名字、跨多个已加载 DSO 做符号查找、处理符号版本（`GLIBC_2.x`），最后才把地址回填到 GOT。对一个数据符号，这没法省——程序一旦跑起来随时可能读它，加载时就得把 `.got` 填好（参见 [[11.ELF文件详解/17.got节.md]] 的 `GLOB_DAT`/`RELATIVE`）。

但**函数**不一样：函数引用是"被调用时"才需要地址，而一次运行往往只触达全部引用函数中的一小部分（典型程序里大量是错误处理路径、罕见分支才用到的库函数）。于是产生了一个朴素而有效的优化：

> **把外部函数地址的解析，从"加载时全量"推迟到"首次调用时按需"。** 没被调用的函数永远不解析，启动期省下的就是这部分查找成本。

这个"推迟"必须满足三个约束，缺一不可：

1. **代码段只读且可共享**——调用点不能写死目标地址（PIE/PIC 下加载基址每次都变，且代码段要被多进程共享同一份物理页），所以必须有一层**可写的间接表**（GOT）承接"地址会变"这件事。这与 [[09.ASLR与位置无关代码]] 的 PIC 诉求是同一个根。
2. **首次调用要能"自己触发解析"**——调用点不知道地址，得有机制在跳转扑空时把控制权交给动态链接器。这就是 `.plt` 跳板 + "解析桩"的职责。
3. **解析一次就够**——回填后，后续调用必须直达，不能每次都进动态链接器。这要求"回填的位置"正好就是"下次读的位置"，于是**解析桩和正常跳转读的是同一个 GOT 槽位**。

延迟绑定就是同时满足这三条的工程解。它不是唯一解（`BIND_NOW` 就是放弃延迟、换取安全与确定性），但它是默认解。

## 原理与机制

### 一句话模型

调用一个外部函数 `foo`，编译器并不直接 `call foo`，而是 `call foo@plt`。`foo@plt` 是 `.plt` 里属于 `foo` 的一小段 stub，它做的唯一一件事是 **`jmp *foo@GOTPCREL(%rip)`**——间接跳到 `.got.plt` 中 `foo` 那个槽位里存的地址。这个槽位的值，决定了控制流去哪：

- **首次调用前**：槽位里是个"回退地址"，指回 `foo@plt` 内部的下一条指令（一条 `push reloc_index`），紧接着 `jmp PLT0`。PLT0 把 `link_map` 压栈、跳 `_dl_runtime_resolve`——于是首次跳转其实是"扑空 → 自投动态链接器"。
- **首次调用后**：`_dl_runtime_resolve` 把 `foo` 的真实地址写进了**同一个槽位**。于是第二次起，`jmp *foo@GOTPCREL(%rip)` 直接落到 `foo` 真身，动态链接器再不介入。

```mermaid
sequenceDiagram
    autonumber
    participant C as 调用方<br/>call foo@plt
    participant PLTn as foo@plt<br/>(.plt[n])
    participant GOTn as .got.plt[n]<br/>(foo 的槽位)
    participant PLT0 as PLT0<br/>(.plt 头)
    participant RES as _dl_runtime_resolve<br/>(GOT[2])
    participant FIX as _dl_fixup()
    participant FOO as foo 真实代码

    rect rgb(245, 238, 224)
    Note over C,FOO: 首次调用（lazy resolve）
    C->>PLTn: call foo@plt
    PLTn->>GOTn: jmp *foo@GOTPCREL(%rip)
    Note over GOTn: 槽位初值 = foo@plt 内的 push 指令地址
    GOTn-->>PLTn: 回跳到 push $reloc_index
    PLTn->>PLT0: push $reloc_index; jmp PLT0
    PLT0->>PLT0: push GOT[1] (link_map)
    PLT0->>RES: jmp *GOT[2]
    RES->>FIX: _dl_fixup(link_map, reloc_index)
    FIX->>GOTn: 把 foo 真实地址回填进 .got.plt[n]
    FIX->>FOO: 尾跳转执行 foo（参数/寄存器已恢复）
    Note over GOTn: 槽位现在 = foo 真实地址
    end

    rect rgb(224, 240, 232)
    Note over C,FOO: 后续调用（直达，零动态链接器介入）
    C->>PLTn: call foo@plt
    PLTn->>GOTn: jmp *foo@GOTPCREL(%rip)
    GOTn->>FOO: 直接跳 foo 真实地址
    end
```

> **图解**：上半段（米色）是首次调用，注意三个关键跳转——`foo@plt` 第一跳读 GOT 槽位"扑空"回到自己内部、PLT0 完成"`push link_map` + `jmp _dl_runtime_resolve`"、`_dl_fixup` 完成"回填 + 尾跳到真身"。**回填的槽位 `.got.plt[n]` 和正常路径读的槽位是同一个**，这是"解析一次就够"的关键。下半段（绿色）是后续调用：同样的 `jmp *foo@GOTPCREL(%rip)`，但槽位里已是真实地址，于是一步到位。两段路径**共用同一条 `foo@plt` 指令**，差别只在 GOT 槽位的内容——这正是延迟绑定"对调用方完全透明"的根因。

### 为什么是"两次跳转 + 一个可写槽位"这种形状

可以把延迟绑定的设计反推一遍，每个组件都是被约束逼出来的：

- 调用点要**位置无关**且只读 → 不能含目标地址 → 必须 `call` 一个**固定位置**的跳板（`.plt` 在镜像内偏移固定，PC-relative 可达）。
- 跳板要能"跳到运行期才知道的地址" → 必须**间接跳转**，从一个**可写**的位置读地址 → 这就是 `.got.plt` 槽位（`SHF_WRITE`）。
- 首次"还没地址"也要能继续 → 槽位初值不能是 0（跳 0 直接崩），得是个**有意义的回退点** → 让它指回 stub 内部的"解析引导序列"。
- 解析引导要告诉动态链接器"解析的是哪个符号" → 需要一个 **`reloc_index`**（在 `.rela.plt` 中的下标）和**本模块身份**（`link_map`）→ 分别由 stub 的 `push` 和 PLT0 的 `push GOT[1]` 提供。
- 解析完要让后续调用免税 → 把真实地址写回**那个被读的槽位** → `_dl_fixup` 回填 `.got.plt[n]`。

这套形状的精妙在于：**后续调用路径上没有任何"是否已解析"的判断分支**——已解析与否的状态，被隐式编码进了 GOT 槽位的值本身。这是它比"每次调用查表判断"高效得多的原因。

## 三平台对照

延迟绑定是个普遍诉求，但三大平台给出的形态差异巨大——尤其 Windows 与 macOS 新版本，实际上都在"弱化甚至放弃"运行期惰性符号解析。

| 维度 | Linux（ELF / ld.so） | macOS（Mach-O / dyld） | Windows（PE / Loader） |
|---|---|---|---|
| 调用跳板节 | `.plt`（启用 CET 时为 `.plt.sec`，见下文） | `__TEXT,__stubs` | 无独立 stub 节；`call [__imp_foo]` 直接间接调用 |
| 间接地址表 | `.got.plt`（函数 GOT） | `__DATA,__la_symbol_ptr`（lazy）/ `__got`（non-lazy） | **IAT**（Import Address Table，`.idata` 内） |
| 配套重定位/元数据 | `.rela.plt` 的 `R_X86_64_JUMP_SLOT` | `LC_DYLD_INFO` 的 lazy bind opcodes（旧）/ chained fixups（新） | 导入目录 INT/IAT 配对（名称或序号） |
| 惰性解析器 | `_dl_runtime_resolve` → `_dl_fixup` | `dyld_stub_binder`（旧 lazy 路径） | **无惰性解析器**（普通导入） |
| 默认绑定时机 | **lazy**（首次调用）；`BIND_NOW` 可改为加载时 | 现代 dyld 趋向**加载时一次绑定**（见下） | **加载时全量绑定**（导入即绑定） |
| 显式延迟加载 | `-z lazy`（默认）/`-z now` | dyld 历史 lazy；现以 chained fixups + 启动期绑定为主 | **延迟导入表**：`.didat` + `__delayLoadHelper2`（见下） |
| GOT/IAT 写保护 | `Full RELRO` 后只读 | dyld 绑定后页保护；chained fixups 利于只读化 | IAT 通常可写（曾是 IAT hook 经典目标） |

### Linux：本篇主角

`.plt` + `.got.plt` + `_dl_runtime_resolve` 的三件套，下文「数据结构 / 流程详解」「代码与汇编」会逐行拆解，此处不展开。要点：**默认 lazy**，`.got.plt` 默认可写，这同时是性能优化点和安全弱点。

### macOS：从 lazy 到 chained fixups

经典 Mach-O 的惰性绑定与 ELF 形似而神不同：

- 调用点 `call foo` → 跳到 `__TEXT,__stubs` 里的 stub → stub `jmp *(__la_symbol_ptr 槽位)`。这一步和 ELF 的 `.plt → .got.plt` 几乎一一对应（`__stubs` ≈ `.plt`，`__la_symbol_ptr` ≈ `.got.plt` 的函数部分）。
- 首次扑空时，槽位回指 `__stub_helper` 里的一小段，它把一个 lazy-binding 信息偏移压栈、跳 `dyld_stub_binder`（角色等同 `_dl_runtime_resolve`）。`dyld` 解释 `LC_DYLD_INFO` 里的 lazy bind opcode 流，解析符号、回填 `__la_symbol_ptr`。`__la_symbol_ptr` 的结构详见 [[12.Mach-O文件详解/30.Mach-O __la_symbol_ptr节.md]]。

**新版变化（重点）**：自 dyld3/dyld4 起，Apple 全面转向 **chained fixups**（`LC_DYLD_CHAINED_FIXUPS`）——把所有需要修补的指针组织成镜像内的"链表"，由 dyld 在加载/页错误时统一处理。其直接后果是：

- **运行期惰性符号解析基本退场**：绑定信息不再是"首次调用时按 opcode 解析"，而是随 chained fixup 在镜像装载时（或首次触页时）成批应用，`__stub_helper` / `dyld_stub_binder` 的经典 lazy 路径在 arm64 + chained fixups 的二进制里已大幅边缘化。
- 好处是**指针表更容易做只读化**、攻击面收窄；代价是放弃了"完全不调用就完全不解析"的极致惰性。可以把它理解为 macOS 默认靠拢了 ELF 的 `BIND_NOW` 哲学。

> 一句话：**ELF 默认 lazy、可选 now；现代 macOS 默认接近 now（chained fixups）、lazy 退居历史**。

### Windows：导入即绑定，延迟加载是"opt-in"

PE 的常规导入根本没有 lazy 这一层：

- 加载器解析 `IMAGE_IMPORT_DESCRIPTOR`，按 INT（Import Name Table）逐条查 DLL 导出，把真实地址**全部写进 IAT**，**在交还控制权给程序入口之前就完成**。调用点 `call qword ptr [__imp_foo]` 直接读 IAT，没有 stub、没有"首次解析"。等价于 ELF 一上来就 `BIND_NOW`。
- 想要"延迟到首次调用"，必须**显式开启延迟加载**（链接器 `/DELAYLOAD:foo.dll`）。此时编译器/链接器为该 DLL 生成**延迟导入表**，元数据落在 **`.didat`** 节，调用点改为经一段桩跳到 **`__delayLoadHelper2`**：首次调用时它 `LoadLibrary` + `GetProcAddress` 解析，并把结果回填进延迟 IAT；后续直达。这才是 PE 世界里和 ELF lazy binding 形态最接近的东西，细节见 [[13.PE文件详解/21-详解PE文件(二十一)：延迟导入表.md]]。

三平台对照的一个有用心智模型：**ELF 把"延迟"作为默认、把"立即"作为加固选项；Windows 把"立即"作为默认、把"延迟"作为优化选项；现代 macOS 用 chained fixups 把天平整体压向"立即"。**

## 数据结构 / 流程详解

### `.plt` / `.plt.sec` / `.got.plt` 的分工

x86-64 上一个开启 CET/IBT 的现代二进制，PLT 实际被拆成两节，理解它们的分工对读反汇编很关键：

| 节 | 角色 | 是否含 `endbr64` | 调用方实际 `call` 的目标 |
|---|---|---|---|
| `.plt` | 传统 PLT；含 PLT0（解析引导头）+ 各函数的"慢路径"桩 | PLT0 含 | 启用 `.plt.sec` 时，调用方**不**直接 call 这里 |
| `.plt.sec` | "secure PLT"，每个函数一条，仅 `endbr64` + `jmp *GOT` 的快路径 | 每条含 | **调用方 `call foo` 实际落在这里** |
| `.got.plt` | 函数 GOT，存每个函数的运行期地址（含三保留项） | — | 被上面两节用 `jmp *...(%rip)` 间接读 |

为什么要拆 `.plt.sec`？Intel CET 的 **IBT（Indirect Branch Tracking）** 要求所有"间接跳转/调用的落点"首指令必须是 `endbr64`，否则触发 `#CP` 异常。把"调用方真正 call 的入口"（需要 `endbr64`）和"解析引导/`push` 慢路径"（不应被外部直接间接跳入）分到两节，既满足 IBT、又不让攻击者把 `.plt` 里的 `push;jmp` 片段当作合法间接跳转落点。**未启用 CET 时通常只有 `.plt`**，PLT0 与各函数桩都在其中（也就是 [[11.ELF文件详解/21.got.plt节.md]] 给出的经典布局）。

### `.got.plt` 的三个保留项（运行时接线盒）

这是延迟绑定能跑起来的"地基"，硬事实，必须用标准约定值：

```text
.got.plt 布局（每项一个指针宽，x86-64 为 8 字节）：
  [0]  →  .dynamic 节的虚拟地址     ← 链接器填（PIE 下可能填 0，由 ld.so 加载时修正）
  [1]  →  本模块 struct link_map *  ← ld.so 加载时填（初值 0）
  [2]  →  _dl_runtime_resolve 地址  ← ld.so 加载时填（初值 0）
  [3]  →  第 1 个外部函数的槽位       ← 初值回指其 .plt 慢路径 push 指令；首次调用后变真实地址
  [4]  →  第 2 个外部函数的槽位
  ...
```

| 槽位 | 含义 | 谁来填、何时填 | 在解析流程中的作用 |
|---|---|---|---|
| **GOT[0]** | `.dynamic` 地址 | 链接器（PIE 下 ld.so 修正） | ld.so 借它快速定位 `.dynamic`，免去重新扫 `PT_DYNAMIC` 程序头 |
| **GOT[1]** | `link_map` 指针 | ld.so 加载时 | **PLT0 把它压栈**，作为 `_dl_runtime_resolve` 的第一个参数——告诉解析器"是哪个模块在解析" |
| **GOT[2]** | `_dl_runtime_resolve` | ld.so 加载时 | **PLT0 `jmp *GOT[2]`** 把控制权交给惰性解析器 |
| **GOT[3+]** | 各函数地址 | 初值由链接器（指回 PLT 慢路径）；真实值由 `_dl_fixup` 回填 | 既是"扑空回退点"，又是"解析结果落点"——同一个槽位身兼二职 |

> [!note] 为什么 GOT[1]/GOT[2] 加载时才填、且需要可写
> 这两项的值（本进程的 `link_map`、本进程映射到的 `_dl_runtime_resolve` 地址）都是**运行期才确定**的——ASLR 下每次加载地址都不同。所以它们不能在链接时写死，必须由 ld.so 自举后填入，`.got.plt` 因此必须**至少在加载早期可写**。这也解释了为什么 `Full RELRO` 要等到"前三项填好 + 全部 JUMP_SLOT 解析完"之后，才能把 `.got.plt` 整体 `mprotect` 成只读。

### `.rela.plt` 与 `reloc_index` 的对应

每个函数槽位的"身份证"是 `.rela.plt` 里的一条 `R_X86_64_JUMP_SLOT` 重定位。**`reloc_index` 就是该函数在 `.rela.plt` 中的条目下标**（注意：x86-64 上 PLT 里 `push` 的是"下标"，不是字节偏移；这与早期 i386 push 偏移的约定不同）：

```c
// Elf64_Rela —— .rela.plt 中每条 JUMP_SLOT 重定位
typedef struct {
    Elf64_Addr   r_offset;  // 目标：本函数对应的 .got.plt 槽位虚拟地址
    Elf64_Xword  r_info;    // 高 32 位=.dynsym 符号索引；低 32 位=类型=R_X86_64_JUMP_SLOT(7)
    Elf64_Sxword r_addend;  // JUMP_SLOT 通常为 0
} Elf64_Rela;
```

`R_X86_64_JUMP_SLOT` 的常量值是 **7**（硬事实，ELF x86-64 ABI 固定）。`_dl_fixup` 拿到 `reloc_index` 后，直接 `&JMPREL[reloc_index]` 定位到这条重定位，从 `r_info` 取符号索引去 `.dynsym` 拿符号名，查找成功后把地址写到 `r_offset` 所指的 `.got.plt` 槽位。`.dynamic` 里的 `DT_JMPREL` 指向 `.rela.plt`、`DT_PLTGOT` 指向 `.got.plt`、`DT_PLTREL` 标明用 RELA——这三个标签把整条链接起来（参见 [[11.ELF文件详解/19.rel.plt节.md]]）。

### `_dl_runtime_resolve` → `_dl_fixup` 解析全过程（逐步）

这是本篇最核心的流程。`_dl_runtime_resolve` 是 ld.so 里一段**手写汇编 trampoline**（glibc 源码 `sysdeps/x86_64/dl-trampoline.h`），`_dl_fixup` 是它调用的 C 函数（`elf/dl-runtime.c`）。逐步拆解：

1. **进入 `_dl_runtime_resolve`**，此刻栈顶布局（由前面 stub 压入）：`[rsp] = reloc_index`、`[rsp+8] = link_map`。寄存器里仍是调用方传给 `foo` 的实参（`rdi/rsi/rdx/rcx/r8/r9` 和 `xmm0-7`，遵循 System V AMD64 约定，见 [[22.调用规约/00.总览.md]]）——**解析过程绝不能破坏它们**，否则解析完跳进 `foo` 时参数就错了。
2. **保存易失寄存器**：trampoline 把所有调用约定里的传参寄存器（整数 + SSE）压栈/保存。这是它必须用汇编手写的根本原因——C 编译器不保证保留这些寄存器的原值。新版还会按 CPU 特性保存更宽的向量状态（AVX 用 `_dl_runtime_resolve_xsavec` 等变体，靠 `xsave`/`xsavec`）。
3. **从栈上取出 `link_map` / `reloc_index`，分别装入 `rdi` / `rsi` 后 `call _dl_fixup`**。
4. **`_dl_fixup(struct link_map *l, ElfW(Word) reloc_arg)` 内部**：
   - 由 `l` 取本模块的 `.rela.plt`（`l->l_info[DT_JMPREL]`）与符号表 `.dynsym`、串表 `.dynstr`。
   - `reloc = &JMPREL[reloc_arg]`，从 `reloc->r_info` 取符号索引 `symidx`，拿到 `sym = &symtab[symidx]`、符号名 `strtab + sym->st_name`。
   - 调 `_dl_lookup_symbol_x`：按**符号查找作用域**（本模块的 `l_scope`，本质是 [[06.符号解析与符号查找]] 讲的作用域链）遍历各 DSO 的 `gnu_hash`，找到定义该符号的模块与地址；处理**符号版本**（若有 `versym`）。
   - 计算最终地址 `value = 定义模块基址 + 定义符号 st_value`（含 IFUNC 解析、`addend` 等修正）。
   - **回填**：`*(GOT 槽位 = l->l_addr + reloc->r_offset) = value`。这一步让该函数从此"已绑定"。
   - 返回 `value`。
5. **回到 `_dl_runtime_resolve`**：恢复第 2 步保存的所有寄存器（参数原样复位），把 `_dl_fixup` 返回的 `value` 放进一个临时寄存器（如 `r11`），**清理之前压入的 `reloc_index`/`link_map`，使栈恢复到"就像调用方直接 `call foo`"的样子**，最后 **`jmp *r11`** 尾跳进 `foo`。
6. **`foo` 执行**：它看到的栈和寄存器与"被直接调用"完全一致，`ret` 时正常返回到调用方 `call foo@plt` 的下一条指令。整个解析对 `foo` 和调用方都**透明**。

> [!note] 为什么是 `jmp` 而不是 `call` 进 `foo`
> `_dl_runtime_resolve` 用**尾跳转**进入 `foo`，而不是 `call foo; ret`。原因：调用方原本就是 `call foo@plt`，返回地址早已在栈上指向调用点的下一条指令。若再 `call`，会多压一层返回地址、多一个栈帧，`foo` 的 `ret` 也会回错地方。用 `jmp` 直接让 `foo` "继承"调用方留下的返回地址，栈深度和直接调用完全一致——这也是延迟绑定"零语义副作用"的保证。

### lazy 与 now 的开关

| 配置 | 链接/环境 | `.got.plt` 函数项初值 | 解析时机 | `.got.plt` 最终可写性 |
|---|---|---|---|---|
| lazy（默认） | `-z lazy`（默认） | 回指 PLT 慢路径 | 首次调用 | 可写（除非 Full RELRO） |
| now（运行期强制） | `LD_BIND_NOW=1` 环境变量 | 加载时即被填真实地址 | 加载时全量 | 可写（仅环境变量，不动节属性） |
| Full RELRO | `-Wl,-z,relro,-z,now` | 加载时即被填真实地址 | 加载时全量 | **只读**（`mprotect`） |

`LD_BIND_NOW=1` 让 ld.so 在加载时就遍历全部 `JUMP_SLOT` 做解析（等于把"首次调用解析"提前到"加载时"），但它只改时机、不改节属性，`.got.plt` 仍可写。要让 `.got.plt` 真正只读，必须链接期 `-z now`（关 lazy）配合 `-z relro`（划入 `PT_GNU_RELRO`），即 **Full RELRO**——此时 ld.so 解析完所有 JUMP_SLOT 后把整段 `mprotect(PROT_READ)`。与 `.got`（Partial RELRO 即只读）的差异，正源于 `.got.plt` 必须撑到"全部函数解析完"才能上锁。这条线索在 [[15.加载器视角的安全]] 会继续展开。

## 代码与汇编

下面用一个最小例子，逐行读 PLT stub。源码：

```c
// demo.c
#include <stdio.h>
int main(void) {
    puts("first call");   // 首次调用 puts → 触发解析
    puts("second call");  // 第二次调用 puts → 直达
    return 0;
}
```

### x86-64 典型 PLT stub 逐行解读

下面给出**两种布局**：未启用 CET 的经典 `.plt`，以及现代发行版默认（启用 IBT）的 `.plt` + `.plt.sec`。地址均为**示意偏移**，不代表任何真实运行期地址。

#### 布局 A：经典 `.plt`（无 CET）

```nasm
; ---- PLT0：解析引导头（每个镜像只有一个）----
0000000000401020 <.plt>:
  401020:  ff 35 e2 2f 00 00     push   QWORD PTR [rip+0x2fe2]   ; push .got.plt[1] = link_map
  401026:  ff 25 e4 2f 00 00     jmp    QWORD PTR [rip+0x2fe4]   ; jmp  *.got.plt[2] = _dl_runtime_resolve
  40102c:  0f 1f 40 00           nop    DWORD PTR [rax+0x0]      ; 对齐填充

; ---- puts 的 PLT 慢路径桩 ----
0000000000401030 <puts@plt>:
  401030:  ff 25 e2 2f 00 00     jmp    QWORD PTR [rip+0x2fe2]   ; jmp *.got.plt[n]（puts 的槽位）
  401036:  68 00 00 00 00        push   0x0                      ; push reloc_index = 0（.rela.plt 下标）
  40103b:  e9 e0 ff ff ff        jmp    401020 <.plt>            ; jmp PLT0 → 触发解析
```

逐行讲透 `puts@plt`：

- **`401030: jmp *.got.plt[n]`**——这是调用方 `call puts@plt` 实际执行的第一条。`rip+0x2fe2` 是"当前指令末地址 + 0x2fe2"，正好落在 `puts` 的 `.got.plt` 槽位。
  - **首次**：该槽位初值 = `0x401036`（即下一条 `push` 的地址）。于是这条 `jmp` 的效果是"跳到自己下面那条 `push`"——看似原地踏步，实则是**故意的扑空回退**。
  - **后续**：该槽位已是 `puts` 真实地址，这条 `jmp` 直接到 libc 里的 `puts`，下面两条指令永不执行。
- **`401036: push 0x0`**——把 `reloc_index = 0` 压栈（`puts` 是 `.rela.plt` 第 0 条）。这是给 `_dl_fixup` 的"查哪个符号"的凭据。
- **`40103b: jmp PLT0`**——跳回 `0x401020`。

PLT0（`0x401020`）承接慢路径：

- **`401020: push .got.plt[1]`**——把 `link_map` 压栈。此刻栈顶 = `reloc_index`、栈顶+8 = `link_map`，正是 `_dl_runtime_resolve` 期望的入参布局。
- **`401026: jmp *.got.plt[2]`**——间接跳到 `_dl_runtime_resolve`，控制权移交 ld.so。**`_dl_runtime_resolve` 在此首次登场**，与「数据结构 / 流程详解」里逐步拆的解析过程无缝衔接。

#### 布局 B：现代默认 `.plt.sec` + `.plt`（启用 IBT/CET）

启用 CET 后，调用方 `call puts@plt` 实际落在 `.plt.sec`：

```nasm
; ---- 调用方真正 call 的目标：.plt.sec 快路径（每函数一条）----
0000000000401050 <puts@plt>:          ; 符号显示为 puts@plt，但物理上在 .plt.sec
  401050:  f3 0f 1e fa           endbr64                          ; IBT 落点标记（间接跳转合法终点）
  401054:  f2 ff 25 c6 2f 00 00  bnd jmp QWORD PTR [rip+0x2fc6]  ; jmp *.got.plt[n]（puts 槽位）
  40105b:  66 0f 1f 44 00 00     nop    WORD PTR [rax+rax*1+0x0]  ; 对齐

; ---- .plt：PLT0 + 慢路径仍在（供首次扑空后引导解析）----
0000000000401020 <.plt>:
  401020:  f3 0f 1e fa           endbr64
  401024:  ff 35 de 2f 00 00     push   QWORD PTR [rip+0x2fde]    ; push .got.plt[1] = link_map
  40102a:  f2 ff 25 e0 2f 00 00  bnd jmp QWORD PTR [rip+0x2fe0]   ; jmp *.got.plt[2] = _dl_runtime_resolve
  ...
0000000000401040 <.plt+0x20>:         ; puts 的 .plt 慢路径条目（与 .plt.sec 同名，靠节区分）
  401040:  f3 0f 1e fa           endbr64
  401044:  68 00 00 00 00        push   0x0                       ; reloc_index = 0
  401049:  f2 e9 d2 ff ff ff     bnd jmp 401020 <.plt>            ; → PLT0
```

差异要点：

- 快路径 `.plt.sec` 首指令是 **`endbr64`**——满足 IBT 对"间接跳转落点"的要求（`.got.plt` 槽位是间接跳转目标，落点 stub 必须以 `endbr64` 开头）。
- **首次扑空**时，`.got.plt[n]` 初值改为指向 `.plt` 慢路径条目（`0x401040`，同样以 `endbr64` 开头），由它 `push reloc_index` 后 `jmp PLT0` —— 后半段与布局 A 完全一致，`_dl_runtime_resolve` 的解析逻辑不变。
- 也就是说：**CET 只改变了"调用入口落在哪、扑空回退到哪"，没有改变 `_dl_runtime_resolve` 的解析本质**。读现代二进制反汇编时，看到 `.plt.sec` 与满地 `endbr64` 不必意外。

### `.got.plt` 的运行期演化（与汇编对应）

```text
                         首次调用 puts 前            首次调用 puts 后
.got.plt[0] (.dynamic)   <.dynamic 虚拟地址>         <不变>
.got.plt[1] (link_map)   <ld.so 填的 link_map>       <不变>
.got.plt[2] (resolver)   <_dl_runtime_resolve 地址>  <不变>
.got.plt[n] (puts)       0x0000000000401036 ←回指    0x00007f....（puts 真实地址，示意）
                          ↑ push 指令地址              ↑ _dl_fixup 回填
```

> [!note] 一句话对应关系
> `puts@plt` 第一条 `jmp *.got.plt[n]` 读的，就是上表 `.got.plt[n]` 这一格。"首次前"它指回 `push`（触发解析），"首次后"它是真实地址（直达）。**整套延迟绑定的状态机，物理上就压缩在这一格 8 字节里。**

### 关掉 lazy 的编译对照

```bash
# 默认 lazy：puts 槽位首次调用才解析
cc demo.c -o demo_lazy

# Full RELRO：链接期解析全部 JUMP_SLOT，.got.plt 加载后只读
cc demo.c -o demo_now -Wl,-z,relro,-z,now
```

`demo_now` 与 `demo_lazy` 的 `.plt`/`.plt.sec` 反汇编**几乎一样**（stub 指令不变），差别在运行期：`demo_now` 加载时 `.got.plt[n]` 就已是 `puts` 真实地址，那条 `push reloc_index; jmp PLT0` 的慢路径**永远不会被执行到**，且 `.got.plt` 随后被 `mprotect` 成只读。这印证了一个常被误解的点：**lazy/now 的差异在"GOT 槽位初值 + 节可写性"，不在 PLT 指令本身**。

## 攻防 / 陷阱

延迟绑定为了"首次调用能回填"，必须让 `.got.plt` 在解析前保持可写——这正是它最大的攻击面。

### GOT 改写劫持（GOT Overwrite）

最经典的 Linux 控制流劫持：利用任意写漏洞（格式化字符串 `%n`、堆/栈溢出、UAF 等），把 `.got.plt` 里某个常被调用函数的槽位，从真实地址改成攻击者控制的地址。

```text
改写前：.got.plt[puts] → 0x7f....   （libc 中 puts 真实地址）
改写后：.got.plt[puts] → &system    （或 one_gadget / ROP 链入口）
```

之后任何 `puts(...)` 调用都会经 `jmp *.got.plt[puts]` 跳到攻击者目标。若再配合可控参数（如让 `puts` 的实参恰为 `"/bin/sh"` 字符串地址），等效于 `system("/bin/sh")`。这种手法的威力来自延迟绑定的设计前提——**槽位可写、且调用点对槽位内容无条件信任**。

**与 RELRO 的关系**：

- **Partial RELRO** 把 `.got`（数据 GOT，`GLOB_DAT`）设为只读，但 `.got.plt`（函数 GOT）**仍可写**（因为延迟绑定需要回填）。所以 Partial RELRO **挡不住 GOT 改写**——这是个常见误区。
- **Full RELRO**（`-z relro,-z now`）关掉 lazy、解析完全部 JUMP_SLOT 后把 `.got.plt` 也设为只读，从根上堵死改写。代价是启动期要解析所有外部函数。这条权衡与 [[11.ELF文件详解/17.got节.md]]、[[15.加载器视角的安全]] 的论述一致。

### GOT 地址泄漏：ASLR 绕过的前置步骤

在 ASLR 开启的现代系统中，攻击者在执行 GOT 改写之前，往往需要先**获知 libc 在进程中的加载基址**——因为改写目标（如 `&system`）是 libc 内部的地址，ASLR 使其在每次运行时都不同。**GOT 地址泄漏**是当前最主流的 ASLR 绕过前置手段。

#### 原理：读取已绑定的 GOT 表项

一旦某个外部函数（如 `puts`）被调用过一次，其 `.got.plt` 槽位就已被 `_dl_fixup` 回填为 **libc 中的真实运行期地址**。攻击者若能读取这个槽位的值（例如通过格式化字符串漏洞泄漏内存），就能得到一个指向 libc 内部的绝对地址。

再用这个地址减去该函数在 libc 中的固定偏移（即 **`puts` 在 libc 文件中的 `st_value`**），即可算出 libc 的加载基址（`libc_base`）：

```text
libc_base = leaked_puts_address - puts_offset_in_libc
                                    ↑
                       用 readelf -s libc.so.6 | grep ' puts' 查得
```

一旦知道 `libc_base`，进程地址空间中所有 libc 函数的运行期地址都可以通过"基址 + 静态偏移"计算出来，ASLR 对 libc 的随机化就被彻底绕过。

#### 格式化字符串读 GOT 的典型手法

格式化字符串漏洞（`printf(user_input)` 形式）可以借 `%s` 参数读取任意地址的内容，或借 `%p` 泄漏栈上已有的地址值。在有格式化字符串漏洞的程序中，泄漏 GOT 的概念性流程如下：

```text
步骤 1：找到目标函数（如 puts）的 .got.plt 槽位地址
        → 用 readelf -r target | grep JUMP_SLOT 或 objdump -d 确认
        → 假设槽位在 0x404020（链接期地址，PIE 下需先泄漏镜像基址）

步骤 2：构造格式化字符串，把 0x404020 写上栈，再用 %N$s 读取该地址内容
        → 泄漏出当前 puts 真实地址（8 字节，小端）

步骤 3：计算 libc 基址
        puts_real_addr = 泄漏值
        libc_base      = puts_real_addr - readelf -s libc.so.6 结果中 puts 的 Value

步骤 4：计算 system/one_gadget 等目标地址
        system_addr = libc_base + system_offset
```

> [!warning] 前置条件
> 上述流程要求目标函数（`puts`）**已经被调用过至少一次**，否则其 `.got.plt` 槽位仍回指 PLT 慢路径，读到的不是 libc 地址。实践中攻击者会选择在泄漏之前已必然被调用过的函数（如 `printf`/`puts`/`setvbuf` 等程序初始化时就使用的函数）。

#### 与 ret2dl-resolve 的链路衔接

GOT 地址泄漏与 `ret2dl-resolve` 是两种针对不同防护配置的互补手段，构成一条递进的攻击链：

```text
无任何保护（早期 CTF 题目）:
    直接 GOT 改写 → system("/bin/sh")

Partial RELRO（.got 只读，.got.plt 可写）：
    格式化字符串泄漏 GOT → 计算 libc_base → 改写 .got.plt 为 system/one_gadget

Full RELRO（.got.plt 也只读）：
    ret2dl-resolve → 伪造 Elf64_Rela + Elf64_Sym → 骗 _dl_runtime_resolve 解析 system
                                  ↑
               此时不需要先泄漏 libc_base（解析器自己去查）
```

因此，GOT 地址泄漏在"有 Partial RELRO、无 Full RELRO"的场景中是最常用的前置步骤，而一旦 Full RELRO 封闭了 `.got.plt` 的可写性，攻击者才转向 `ret2dl-resolve`——直接攻击解析逻辑本身（详见 [[33.二进制漏洞与利用基础/07.GOT劫持与ret2dl-resolve]]）。

> [!note] 防御要点
> GOT 地址泄漏是一种**信息泄漏**，防御的根本是消除读取任意内存的通道（修复格式化字符串/越界读漏洞）。在此基础上，**Full RELRO + BIND_NOW** 把 `.got.plt` 设为只读，让泄漏到的值无法被后续改写；**PIE（Position Independent Executable）** 使镜像基址也随机，要泄漏 `.got.plt` 槽位地址本身还需要额外泄漏镜像基址，提高了泄漏链的复杂度。

### ret2plt 变体：利用 PLT 桩本身

#### 经典 ret2plt 思路

`ret2plt`（Return to PLT）是在函数 PLT stub 本身作为跳转目标的技巧。与 GOT 改写不同，ret2plt **不修改任何内存**，而是**利用现有 PLT 桩的跳转行为**来调用任意 libc 函数——这使它在 `.got.plt` 可写但地址未知、或需要绕过某些写保护时特别有用。

核心利用点：`puts@plt` 这个地址是**链接期固定的 PLT 桩地址**（非 PIE 时在二进制中直接可读，PIE 时相对于镜像基址固定偏移）。当控制流跳到 `puts@plt` 时：

1. 执行 `jmp *.got.plt[puts]`——此时槽位已绑定，直接调用 libc 的 `puts`
2. 攻击者只需控制 `rdi`（x86-64 第一参数寄存器）的值，就能把任意内存地址传给 `puts` 打印出来

这正是 GOT 地址泄漏最常见的实现方式之一：**ret2plt 跳到 `puts@plt`、把 `.got.plt[puts]` 地址作为参数 → `puts` 打印出该槽位内容（即 `puts` 真实 libc 地址）→ 读取打印输出、计算 `libc_base`**。

```text
ROP 链结构（概念性，x86-64）：
  [overflow padding]
  [pop rdi; ret gadget]       ← 用 ROPgadget/ropper 从二进制中找
  [.got.plt[puts] 地址]       ← 要泄漏的 GOT 槽位地址（readelf -r 查得）
  [puts@plt 地址]             ← puts 的 PLT 桩地址（readelf -r / objdump 查得）
  [程序循环回到 main 或 vuln]  ← 为了第二轮写入 shell payload
```

#### 延迟绑定状态对 ret2plt 的影响

ret2plt 依赖于跳到 PLT 时目标函数 GOT 槽位**已被绑定**（否则跳到 PLT 会触发 `_dl_runtime_resolve`，而不是直接执行目标函数逻辑，泄漏的将是 PLT 慢路径地址而非 libc 地址）。确保"已绑定"的方式：

- 选择程序初始化期间**必然被调用**的函数（`printf`、`puts`、`__libc_start_main` 等）
- 在漏洞触发前先让程序走过包含该函数调用的代码路径

对于 `BIND_NOW`/Full RELRO 的目标，所有外部函数在加载时就已绑定，`.got.plt` 已是真实 libc 地址——但此时 `.got.plt` 只读，GOT 改写无效，ret2plt 泄漏技术本身仍可用（读 GOT 值不需要写权限）。

#### 不同于 GOT 改写的攻击面

ret2plt 的本质是**读**（通过控制函数参数读取内存内容），而 GOT 改写是**写**（改写槽位指针）。两者攻击面不同：

| 技术 | 操作 | 需要的漏洞类型 | 防护障碍 |
|---|---|---|---|
| ret2plt 泄漏 | 读 `.got.plt` 槽位值 | 控制流劫持（栈溢出/ROP）+ 可控参数 | PIE 增加镜像基址泄漏前置步骤 |
| GOT 改写 | 写 `.got.plt` 槽位 | 任意写（格式化字符串/溢出）| Partial RELRO 不防，Full RELRO 防 |
| ret2dl-resolve | 伪造重定位结构 | 控制流劫持 + 可写内存区域 | 现代 glibc 有边界校验；Full RELRO + BIND_NOW 根治 |

> [!note] 防御要点
> ret2plt 泄漏链的起点是**控制流劫持**（通常来自栈溢出）。防御的根本是消除栈溢出通道（Stack Canary + Shadow Stack 等 CET 机制）。**PIE** 使镜像基址随机化，要通过 ret2plt 跳到 `puts@plt` 还需要先泄漏镜像基址，增加利用链复杂度。CFI（Control Flow Integrity）在编译器层面限制间接跳转目标，是更深层次的防线。

### `ret2dl-resolve`：直接骗解析器

当目标开了 Full RELRO（`.got.plt` 已只读，改不动），攻击者转而攻击**解析过程本身**。`ret2dl-resolve` 的核心思路：既然 `_dl_runtime_resolve(link_map, reloc_index)` 会"按 `reloc_index` 去 `.rela.plt` 取重定位、按 `r_info` 去 `.dynsym` 取符号名、查找后回填"，那么——

1. 攻击者在可写内存（如 `.bss`/栈）里**伪造一条 `Elf64_Rela`**、一个 `Elf64_Sym`、以及符号名字符串，让符号名指向 `"system"` 之类。
2. 构造调用，使控制流走到 PLT0（或直接 `push 伪造index; jmp PLT0`），并让 `reloc_index` 越界指向那条伪造的重定位。
3. `_dl_fixup` 信以为真，按伪造结构查到 `system` 地址、回填、尾跳 —— 等于"借动态链接器之手"调用了任意 libc 函数，**绕过了 GOT 只读**。

> [!warning] 缓解与现状
> 现代 glibc 对此已有针对性硬化：`_dl_fixup` 会校验 `reloc_index` 是否落在 `.rela.plt` 合法范围（防越界索引），并对符号表项做边界/类型检查。但 `ret2dl-resolve` 仍是理解"为什么 `Full RELRO` 不是银弹"的经典案例。最稳的防线仍是 **`BIND_NOW` 关闭 lazy（让 `_dl_runtime_resolve` 在运行期根本不被调用）+ Full RELRO 锁死 `.got.plt`**。

### 其它陷阱

- **误判 Partial RELRO 已安全**：见上，Partial 只保护 `.got` 不保护 `.got.plt`。审计二进制时务必 `checksec` 区分 Partial / Full。
- **把 `LD_BIND_NOW=1` 当成只读保护**：环境变量只改解析时机，**不改节属性**，`.got.plt` 仍可写。要只读必须链接期 `-z now`（Full RELRO）。
- **CET/`.plt.sec` 的误读**：`.plt.sec` 不是"另一个 GOT"，它只是为满足 IBT 而拆出的快路径调用入口；真正的地址表仍是唯一的 `.got.plt`。读反汇编时别把 `.plt` 与 `.plt.sec` 当成两套机制。
- **`reloc_index` 是下标不是偏移**：x86-64 PLT `push` 的是 `.rela.plt` 的**条目下标**，不要按字节偏移去换算（i386 旧约定 push 的才是偏移），否则手算定位会全错。
- **IFUNC 的解析点不同**：`STT_GNU_IFUNC` 符号在解析时会先执行 resolver 选出实现（如按 CPU 特性选 `memcpy` 变体），其地址来自运行 resolver 的返回值而非静态 `st_value`——首次"解析"的代价比普通符号高，但只发生一次。

## 小结

1. **延迟绑定 = 两层间接 + 一个可写槽位**：调用点 `call foo@plt` → `.plt` stub `jmp *foo@GOTPCREL(%rip)` 读 `.got.plt` 槽位决定去向；槽位"首次前回指 PLT 慢路径、首次后存真实地址"，状态机压缩在这 8 字节里，对调用方完全透明。
2. **`_dl_runtime_resolve` 是核心枢纽**：PLT0 `push link_map(GOT[1]); jmp *GOT[2]` 把控制权交给它；它保存易失寄存器、调 `_dl_fixup(link_map, reloc_index)` 按 `.rela.plt`→`.dynsym` 查符号、回填 `.got.plt` 槽位、恢复寄存器后**尾跳**进目标函数——`jmp` 而非 `call`，保证栈深度与直接调用一致。
3. **三保留项是地基**：`GOT[0]=.dynamic`、`GOT[1]=link_map`、`GOT[2]=_dl_runtime_resolve`，后两者运行期才由 ld.so 填入，这正是 `.got.plt` 必须可写、`Full RELRO` 只能在最后才上锁的原因。
4. **三平台天平不同**：ELF 默认 lazy（`.plt`/`.got.plt`/`_dl_runtime_resolve`）、可选 `now`；现代 macOS 用 chained fixups 把惰性解析压向"加载时绑定"，经典 `dyld_stub_binder` 路径退场；Windows 普通导入"加载即填满 IAT"（等同 `now`），只有显式 `/DELAYLOAD` 才经 `.didat` + `__delayLoadHelper2` 走延迟。
5. **lazy 的代价是安全面**：可写 `.got.plt` 是 GOT 改写劫持的经典目标，`ret2dl-resolve` 进一步伪造重定位/符号结构骗 `_dl_runtime_resolve`；**Partial RELRO 挡不住函数 GOT 改写**，唯有 `BIND_NOW + Full RELRO` 关 lazy 并把 `.got.plt` 锁成只读才根治。
6. **读现代二进制的注意点**：CET/IBT 下多出 `.plt.sec` 与满地 `endbr64`，那只是为满足"间接跳转合法落点"拆出的快路径调用入口，地址表仍是唯一的 `.got.plt`，解析本质不变。
