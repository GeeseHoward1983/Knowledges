# 详解Mach-O(十八)Mach-O section

> [!abstract] TL;DR
> **节（Section）是段（Segment）内的细粒度数据单位**，由 `section_64`（64 位，80 字节）/ `section`（32 位，68 字节）结构描述。它紧跟在段头之后排布，由 `LC_SEGMENT_64` 的 `nsects` 字段决定数量（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。
> 一个节由四类信息刻画：**位置**（`addr` 虚拟地址 / `offset` 文件偏移 / `size` 大小）、**对齐**（`align`，以 2 的幂表示）、**重定位**（`reloff` / `nreloc`）、**身份**（`flags` = 低 8 位"类型" + 高 24 位"属性"）。
> `flags` 的低 8 位（`flags & SECTION_TYPE`）是**类型**，回答"这是什么节、`dyld`/链接器该怎么处理"——`S_REGULAR`（普通）、`S_ZEROFILL`（零填充）、`S_CSTRING_LITERALS`（C 字符串）、`S_SYMBOL_STUBS`（符号桩）、`S_THREAD_LOCAL_*`（线程局部）等；高 24 位（`flags & SECTION_ATTRIBUTES`）是**属性**位掩码——`S_ATTR_PURE_INSTRUCTIONS`（纯指令）、`S_ATTR_NO_DEAD_STRIP`（禁死代码消除）等。
> 三个 `reserved` 字段会因节类型被"复用"：符号指针节/桩节的 `reserved1` 是**间接符号表起始索引**（配合 [[06.Mach-O LC_DYSYMTAB]]）、`reserved2` 是**每个 stub 的字节大小**（用于推算条目数）、`reserved3` 真正保留。读懂 `section_64` 这一通用模型，后续每个具体节（`__text`/`__cstring`/`__stubs`…）都只是它的一个实例。

## 概述与定位

[[11.Mach-O Segments]] 把进程地址空间切成若干带统一权限的段，**节则在段内进一步把数据按用途分类组织**。可以这样理解二者分工：

- **段**是写给**内核 / dyld** 看的——它关心"把哪段文件字节映射到哪个虚拟地址、给什么读写执行权限"，是页对齐的映射与保护单位。
- **节**是写给**链接器（`ld`）与分析工具（`otool`/`nm`/`dyld`）** 看的——它关心"这块数据是代码、是字符串、是指针表、还是未初始化变量"，是逻辑内容单位。

一个段里装多个节，**同段内所有节共享该段的内存保护**。所以"只读字符串"`__cstring` 要放进 `r-x` 的 `__TEXT`，而"可写指针表"`__data` 要放进 `rw-` 的 `__DATA`——节的归属不是随意的，而是由它需要的权限决定的。

所有节，无论装的是机器码、字符串、指针还是 Objective-C 元数据，都共用**同一个**描述结构 `section_64`，区别只在字段取值——尤其是 `flags` 里的**类型位**，它单字段就决定了 `dyld` 与链接器对这个节的全部处理策略。本篇是 [[19.Mach-O __text节]] 起各分篇的"公共字段说明书"：把 `section_64` 的每个字段、`flags` 的每个类型与属性、`reserved` 的每种复用讲透，后续具体节只需说"它是 `S_xxx` 类型、`flags` 取值如何"即可。

> [!note] 节名总要带段名：`段名,节名`
> 节名（`sectname`）在 Mach-O 里**几乎从不单独出现**，而是写作 `段名,节名` 的二元组，如 `__TEXT,__text`、`__DATA,__data`、`__DATA_CONST,__got`。原因有二：① 节名只在 16 字节内唯一，不同段可以有同名节（理论上）；② `section_64` 结构本身就**冗余回填了 `segname`**，让单看一个节头就能知道它属于哪个段。`otool -s __TEXT __text` 这类命令也要求段名+节名一起给。

## 核心原理与字段详解

### 1. `section_64` 完整字段（64 位）

来自 `<mach-o/loader.h>`，逐字段注释如下：

```c
struct section_64 {          /* for 64-bit architectures */
    char     sectname[16];   // 节名，定长 16 字节、不足补 \0，如 "__text"、"__cstring"
    char     segname[16];    // 所属段名，冗余回填，如 "__TEXT"（与段头 segname 一致）
    uint64_t addr;           // 节加载后的虚拟地址（内存侧起点）
    uint64_t size;           // 节大小（字节）
    uint32_t offset;         // 节数据在文件中的偏移（文件侧起点）
    uint32_t align;          // 对齐，以 2 的幂的指数表示（如 4 → 2^4 = 16 字节对齐）
    uint32_t reloff;         // 重定位项在文件中的偏移（链接前的 .o 才常用）
    uint32_t nreloc;         // 重定位项数量
    uint32_t flags;          // 类型(低 8 位 SECTION_TYPE) + 属性(高 24 位 SECTION_ATTRIBUTES)
    uint32_t reserved1;      // 保留：因节类型而异（如间接符号表起始索引）
    uint32_t reserved2;      // 保留：因节类型而异（如每个 stub 的字节大小）
    uint32_t reserved3;      // 保留：仅 section_64 有（32 位 section 无此字段）
};
```

字段在文件里的精确偏移（共 **80 字节**）：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `sectname` | char[16] | 16 | 节名，定长、`\0` 补足 |
| 16 | `segname` | char[16] | 16 | 所属段名，冗余回填 |
| 32 | `addr` | uint64_t | 8 | 节虚拟地址 |
| 40 | `size` | uint64_t | 8 | 节大小 |
| 48 | `offset` | uint32_t | 4 | 节文件偏移 |
| 52 | `align` | uint32_t | 4 | 对齐（2 的幂指数） |
| 56 | `reloff` | uint32_t | 4 | 重定位项文件偏移 |
| 60 | `nreloc` | uint32_t | 4 | 重定位项数量 |
| 64 | `flags` | uint32_t | 4 | 类型 + 属性 |
| 68 | `reserved1` | uint32_t | 4 | 保留（索引/偏移） |
| 72 | `reserved2` | uint32_t | 4 | 保留（计数/项大小） |
| 76 | `reserved3` | uint32_t | 4 | 保留 |

> [!note] `sectname` 与 `segname` 都是定长 16 字节、可不以 `\0` 结尾
> 两个名字字段都是 `char[16]` 定长数组：名字短于 16 字节时尾部补 `\0`，**恰好 16 字节时不留终止符**。解析时务必按"最多读 16 字节"处理，不能当成 C 字符串无脑 `strlen`，否则会越界读到下一字段。`segname` 与所属段头的 `segname` 应当一致——若不一致，多半是文件被篡改或工具异常。

### 2. `section` 完整字段（32 位）

32 位变体结构同构、仅 `addr`/`size` 降为 32 位，且**没有 `reserved3`**（固定 68 字节）：

```c
struct section {             /* for 32-bit architectures */
    char     sectname[16];   // 节名
    char     segname[16];    // 所属段名
    uint32_t addr;           // 节虚拟地址（32 位）
    uint32_t size;           // 节大小（32 位）
    uint32_t offset;         // 节文件偏移
    uint32_t align;          // 对齐（2 的幂指数）
    uint32_t reloff;         // 重定位项文件偏移
    uint32_t nreloc;         // 重定位项数量
    uint32_t flags;          // 类型 + 属性
    uint32_t reserved1;      // 保留
    uint32_t reserved2;      // 保留
    // 注意：没有 reserved3
};
```

| 维度 | `section`（32 位） | `section_64`（64 位） |
|---|---|---|
| `addr` / `size` 位宽 | `uint32_t`（4B） | `uint64_t`（8B） |
| 是否有 `reserved3` | **无** | **有** |
| 单个结构大小 | **68** 字节 | **80** 字节 |
| 宿主段命令 | `LC_SEGMENT` | `LC_SEGMENT_64` |
| 段 `cmdsize` 贡献 | `68 * nsects` | `80 * nsects` |

> [!note] 架构差异速记
> 两者布局**同构**，差别仅在 `addr`/`size` 的位宽（32→64）以及 64 位多出的 `reserved3`。当代 Apple 设备（arm64、x86_64）一律使用 64 位变体；`section`（32 位）只在老的 i386 / armv7 二进制里出现。解析时要先看 Header 的 `magic`/`cputype` 决定按哪套读（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 的架构判定）。

### 3. `addr` / `offset` / `size`：内存侧与文件侧

节和段一样，要区分"内存里在哪"和"文件里在哪"：

- `addr`：节加载后的**虚拟地址**（内存侧）。它落在所属段的 `[vmaddr, vmaddr+vmsize)` 区间内。开启 ASLR 后实际地址 = `addr + slide`（slide 是内核给整个镜像统一加的随机偏移，见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。
- `offset`：节数据在**文件**中的偏移（文件侧）。**注意只有 4 字节**（即便在 64 位的 `section_64` 里也是 `uint32_t`）——因为单个 Mach-O 切片不会超过 4GB，文件内偏移用 32 位足够。
- `size`：节的字节数。在 64 位结构里是 8 字节（`uint64_t`），可表示极大的内存节（如 `S_GB_ZEROFILL`）。

> [!note] 零填充节的 `offset` 不指向真实文件数据
> 对 `S_ZEROFILL` / `S_GB_ZEROFILL` / `S_THREAD_LOCAL_ZEROFILL` 这类**不占文件**的节（典型如 `__bss`，见 [[28.Mach-O __bss节]]），`offset` 字段虽然填了值，但**那里并没有真正属于本节的初始化字节**——节的内容在运行时由内核零填充。判断一个节是否占文件，要看它的**类型**（是不是某种 zerofill），而不是 `offset` 是否非零。`addr` 与 `size` 决定它在内存里占多大，`size` 不计入文件大小。

### 4. `align`：以 2 的幂表示的对齐

`align` 字段存的**不是字节数，而是 2 的幂的指数**：实际对齐字节数 = `2^align`。这样用一个小整数就能表示很大的对齐。

| `align` 值 | 实际对齐 | 典型用途 |
|---|---|---|
| `0` | `2^0 = 1` 字节 | 无对齐要求（如紧凑的字符串） |
| `1` | `2^1 = 2` 字节 | |
| `2` | `2^2 = 4` 字节 | 4 字节标量、指令对齐下限 |
| `3` | `2^3 = 8` 字节 | 8 字节指针 / 双精度 |
| `4` | `2^4 = 16` 字节 | SIMD 向量、`__text` 常见 |
| `5` | `2^5 = 32` 字节 | 缓存行 / AVX 向量 |
| `6` | `2^6 = 64` 字节 | 缓存行对齐 |
| `12` | `2^12 = 4096` 字节 | 页对齐（x86_64 页） |
| `14` | `2^14 = 16384` 字节 | 页对齐（arm64 16KB 页） |

链接器在把各 `.o` 的同名节拼进最终段时，会让每个节的 `addr` 满足其 `align` 要求，必要时在前一个节末尾插入填充字节。`align` 与页大小协同——arm64 16KB 页、x86_64 4KB 页会影响节在段内的整体排布（段必须页对齐，节在段内按各自 `align` 对齐）。

> [!warning] `otool` 显示的 `align` 是 `2^N (M)` 形式
> `otool -l` 输出里 `align` 写作 `2^2 (4)`：前面 `2^2` 是结构里存的原始指数值（`align=2`），括号里 `(4)` 是工具替你算好的实际字节数（`2^2=4`）。别把 `4` 误当成存储值——存储的是 `2`。

### 5. `reloff` / `nreloc`：节级重定位

`reloff`（重定位项文件偏移）与 `nreloc`（重定位项数量）描述本节关联的**重定位表**。它们主要用于**未链接的目标文件（`.o`，`MH_OBJECT`）**：编译器为每个节生成一串 `relocation_info`，告诉链接器"本节哪些位置引用了还没定地址的符号/节，链接时怎么填"。

对**已链接的最终产物**（可执行文件 / dylib），节级重定位基本被 dyld 的 rebase/bind（旧）或链式 fixups（新，`LC_DYLD_CHAINED_FIXUPS`）取代，因此最终文件里多数节的 `reloff = 0`、`nreloc = 0`。逆向已链接二进制时这两个字段通常是 0，看符号绑定要去 `LC_DYLD_INFO` / `LC_DYLD_CHAINED_FIXUPS` 与间接符号表（见 [[06.Mach-O LC_DYSYMTAB]]）。

### 6. `flags`：低 8 位"类型" + 高 24 位"属性"

`flags` 是节描述里**信息密度最高**的字段，被两个掩码切成两半：

```c
#define SECTION_TYPE        0x000000ff  /* 低 8 位：节类型（256 种之一，互斥）*/
#define SECTION_ATTRIBUTES  0xffffff00  /* 高 24 位：节属性（可按位或组合）*/
#define SECTION_ATTRIBUTES_USR 0xff000000  /* 高 8 位：用户可设属性 */
#define SECTION_ATTRIBUTES_SYS 0x00ffff00  /* 中 16 位：系统设置属性 */
```

- **类型**（`flags & SECTION_TYPE`）：低 8 位，**互斥**取值（一个节只能是一种类型）。它回答"这是什么节"，决定 `dyld`/链接器的根本处理方式。完整类型表见第 7 节。
- **属性**（`flags & SECTION_ATTRIBUTES`）：高 24 位，**位掩码**（可多个并存）。它在类型之上叠加修饰，如"只含纯指令""禁止死代码消除"。完整属性表见第 8 节。

取出两部分的标准写法：

```c
uint8_t  type = sect->flags & SECTION_TYPE;          // 例如 0x00 = S_REGULAR
uint32_t attr = sect->flags & SECTION_ATTRIBUTES;    // 例如 0x80000400
```

> [!note] 为什么 `__text` 的 `flags` 是 `0x80000400`
> 拆开看：`0x80000400 & 0xff = 0x00`（类型 = `S_REGULAR`，普通节），`0x80000400 & 0xffffff00 = 0x80000400`（属性 = `S_ATTR_PURE_INSTRUCTIONS 0x80000000` | `S_ATTR_SOME_INSTRUCTIONS 0x00000400`）。所以这串值的含义是"一个只含纯机器指令的普通节"——这正是代码节 `__text` 的标准标记。

### 7. 完整节类型表（`flags & SECTION_TYPE`，低 8 位）

下面是 `<mach-o/loader.h>` 定义的**全部节类型**（值 + 含义 + 代表节）。这些值互斥，是节身份的核心：

| 类型 | 值 | 含义 | 代表节 |
|---|---|---|---|
| `S_REGULAR` | `0x0` | 普通节，无特殊处理（默认类型） | `__text`、`__data`、`__const` |
| `S_ZEROFILL` | `0x1` | 零填充、不占文件，运行时按需零填充 | `__bss`、`__common` |
| `S_CSTRING_LITERALS` | `0x2` | C 字符串字面量（`\0` 结尾），可去重合并 | `__cstring` |
| `S_4BYTE_LITERALS` | `0x3` | 仅含 4 字节字面常量，可去重 | `__literal4`（`float`/`int` 常量池） |
| `S_8BYTE_LITERALS` | `0x4` | 仅含 8 字节字面常量，可去重 | `__literal8`（`double`/64 位常量） |
| `S_LITERAL_POINTERS` | `0x5` | 仅含指向字面量的指针 | `__literal_pointers` |
| `S_NON_LAZY_SYMBOL_POINTERS` | `0x6` | 非惰性符号指针，加载时即绑定 | `__got`、`__nl_symbol_ptr`（见 [[31.Mach-O __nl_symbol_ptr节]]） |
| `S_LAZY_SYMBOL_POINTERS` | `0x7` | 惰性符号指针，首次调用时才绑定 | `__la_symbol_ptr`（见 [[30.Mach-O __la_symbol_ptr节]]） |
| `S_SYMBOL_STUBS` | `0x8` | 符号桩，含跳转到符号地址的小段代码 | `__stubs`（见 [[22.Mach-O __stubs节]]） |
| `S_MOD_INIT_FUNC_POINTERS` | `0x9` | 模块初始化函数指针数组（C++ 全局构造、`__attribute__((constructor))`） | `__mod_init_func`（见 [[32.Mach-O __mod_init_func节]]） |
| `S_MOD_TERM_FUNC_POINTERS` | `0xa` | 模块终止函数指针数组（析构/`destructor`） | `__mod_term_func` |
| `S_COALESCED` | `0xb` | 可合并符号节：同名符号（C++ 内联函数/模板/vtable 等弱定义）多份只留一份 | `__textcoal_nt` 等 |
| `S_GB_ZEROFILL` | `0xc` | "GB 级"零填充节，专为超大（GB 量级）零填充区设计，放置上不挤占其他节布局 | 大块占位 |
| `S_INTERPOSING` | `0xd` | 仅含成对的函数指针，用于符号 interpose（替换）机制 | `__interpose` |
| `S_16BYTE_LITERALS` | `0xe` | 仅含 16 字节字面常量（如 `long double`、128 位向量常量），可去重 | `__literal16` |
| `S_DTRACE_DOF` | `0xf` | 含 DTrace 探针的 DOF（DTrace Object Format）数据 | `__dof_*` |
| `S_LAZY_DYLIB_SYMBOL_POINTERS` | `0x10` | 指向"惰性加载 dylib"的惰性符号指针 | `__ld_symbol_ptr` |
| `S_THREAD_LOCAL_REGULAR` | `0x11` | TLV（线程局部变量）初始值模板（有初值的 TLS 数据） | `__thread_data` |
| `S_THREAD_LOCAL_ZEROFILL` | `0x12` | TLV 零填充模板（无初值的 TLS，零初始化） | `__thread_bss` |
| `S_THREAD_LOCAL_VARIABLES` | `0x13` | TLV 描述符（每个线程局部变量一个，运行时由它定位实际存储） | `__thread_vars` |
| `S_THREAD_LOCAL_VARIABLE_POINTERS` | `0x14` | 指向 TLV 描述符的指针 | `__thread_ptrs` |
| `S_THREAD_LOCAL_INIT_FUNCTION_POINTERS` | `0x15` | 初始化 TLV 值需调用的函数指针 | `__thread_init` |
| `S_INIT_FUNC_OFFSETS` | `0x16` | 初始化函数的 **32 位偏移**数组（取代 `__mod_init_func` 的指针数组，免运行时 rebase；配合链式 fixups） | `__init_offsets` |

> [!note] 线程局部存储（TLS / TLV）的一组类型
> `S_THREAD_LOCAL_*`（`0x11`~`0x15`）是 C/C++ 的 `__thread` / `thread_local` 变量在 Mach-O 里的落地形式：每个线程拥有变量的独立副本。`S_THREAD_LOCAL_REGULAR`/`ZEROFILL` 存"初值模板"（新线程按模板初始化），`S_THREAD_LOCAL_VARIABLES` 存描述符（`tlv_descriptor`，含一个 getter 函数指针 + key + 偏移），代码访问线程局部变量时其实是调描述符里的函数拿到本线程地址。这些节通常住在 `__DATA` 段。

> [!note] `S_INIT_FUNC_OFFSETS（0x16）`：现代加固的新成员
> 这是目前**已知编号最高**的节类型（LLVM 标为 `LAST_KNOWN_SECTION_TYPE`）。传统 `__mod_init_func`（`S_MOD_INIT_FUNC_POINTERS`）存的是**绝对函数指针**，加载时要逐个 rebase（叠加 slide）才能用；启用链式 fixups 的现代 macOS/iOS 二进制改用 `__init_offsets`，存**相对镜像基址的 32 位偏移**，运行时直接 `基址 + 偏移` 即得，**无需 rebase、也不留可写指针**，缩小了攻击面。逆向新二进制时若找不到 `__mod_init_func`，初始化器很可能在 `__init_offsets` 里。

### 8. 完整节属性表（`flags & SECTION_ATTRIBUTES`，高 24 位）

属性是**可按位或组合**的修饰位，定义于 `<mach-o/loader.h>`。它们指导链接器拷贝节、指导工具显示节，但**不被 dyld 使用**：

| 属性 | 值 | 含义 |
|---|---|---|
| `S_ATTR_PURE_INSTRUCTIONS` | `0x80000000` | 本节**只含**真正的机器指令（纯代码）。标准工具给 `__text`、`__symbol_stub`、`__picsymbol_stub` 打此标 |
| `S_ATTR_NO_TOC` | `0x40000000` | 本节含可合并符号，**不应**进静态库归档的目录（SYMDEF / TOC） |
| `S_ATTR_STRIP_STATIC_SYMS` | `0x20000000` | 若镜像设了 `MH_DYLDLINK`，本节里的静态符号**可被 strip 掉** |
| `S_ATTR_NO_DEAD_STRIP` | `0x10000000` | **禁止死代码消除**：即便看似无人引用，链接器也不得删除本节 |
| `S_ATTR_LIVE_SUPPORT` | `0x08000000` | 本节的块"引用了存活块就视为存活"（参与活性分析的支持节） |
| `S_ATTR_SELF_MODIFYING_CODE` | `0x04000000` | 自修改代码，配合 i386 上由 dyld 改写的代码桩使用 |
| `S_ATTR_DEBUG` | `0x02000000` | 调试节（如 DWARF 的 `__debug_*`）。同一段内调试节与非调试节不可混 |
| `S_ATTR_SOME_INSTRUCTIONS` | `0x00000400` | 本节**含有**机器指令（但可能也含其他数据，与 `PURE` 区别在"含有"vs"只含"） |
| `S_ATTR_EXT_RELOC` | `0x00000200` | 本节含**外部重定位**（引用其他文件里的数据/未定义符号）；要求所属段 `maxprot` 允许读写 |
| `S_ATTR_LOC_RELOC` | `0x00000100` | 本节含**本地重定位**（引用本文件内的数据） |

按掩码归类：高 8 位（`0xff000000`，`SECTION_ATTRIBUTES_USR`）是**用户可设**属性（`PURE_INSTRUCTIONS`/`NO_TOC`/`STRIP_STATIC_SYMS`/`NO_DEAD_STRIP`/`LIVE_SUPPORT`/`SELF_MODIFYING_CODE`/`DEBUG`）；中 16 位（`0x00ffff00`，`SECTION_ATTRIBUTES_SYS`）是**系统设置**属性（`SOME_INSTRUCTIONS`/`EXT_RELOC`/`LOC_RELOC`）。

> [!note] `PURE_INSTRUCTIONS` 与 `SOME_INSTRUCTIONS` 的区别
> 二者都标记"有代码"，但语义不同：`S_ATTR_PURE_INSTRUCTIONS` 表示本节**纯粹只有**指令、没有夹杂数据（反汇编器可以从头到尾直接反汇编）；`S_ATTR_SOME_INSTRUCTIONS` 表示本节**包含**指令但可能掺有数据（需谨慎区分代码与数据）。`__text` 通常两个都带（`0x80000400`），表达"只含指令、且确实有指令"。

### 9. `reserved1` / `reserved2` / `reserved3` 的精确复用

三个 `reserved` 字段名义"保留"，实际会被特定节类型**复用**承载关键信息。这是解析符号桩/符号指针节时绕不开的细节：

**`reserved1` —— 间接符号表起始索引（offset / index）**

对**符号指针节**（`S_NON_LAZY_SYMBOL_POINTERS` 的 `__got`/`__nl_symbol_ptr`、`S_LAZY_SYMBOL_POINTERS` 的 `__la_symbol_ptr`）与**符号桩节**（`S_SYMBOL_STUBS` 的 `__stubs`），`reserved1` 存的是：本节第一个条目在**间接符号表（indirect symbol table）** 中的**起始索引**。间接符号表本身由 `LC_DYSYMTAB` 的 `indirectsymoff`/`nindirectsyms` 定位（见 [[06.Mach-O LC_DYSYMTAB]]）。本节的第 `i` 个条目，对应间接符号表第 `reserved1 + i` 项；该项是一个 32 位索引，再指向常规符号表里那个真正的符号。

**`reserved2` —— 每个 stub 的字节大小（count / sizeof）**

节头**不直接存条目数**，条目数靠 `size ÷ 单项大小` 推算：

- 对**符号指针节**，单项就是一个指针——64 位 8 字节、32 位 4 字节，所以条目数 = `size / 8`（或 `/4`），`reserved2` 通常为 0、不用。
- 对**符号桩节**（`__stubs`），每个 stub 是一小段跳转代码，其字节大小因 CPU 架构而异（不是固定指针宽度），于是**把 stub 大小存进 `reserved2`**，条目数 = `size / reserved2`。

**`reserved3` —— 真正保留**

`reserved3` 目前没有被赋予用途，恒为 0（且只有 64 位 `section_64` 才有这个字段，32 位 `section` 根本没有它）。

把三者串起来，解析一个 `__la_symbol_ptr` / `__stubs` 节的流程是：

1. 读节的 `reserved1` → 得到它在间接符号表中的起始索引 `base`。
2. 算条目数 `n`：指针节用 `size / 指针宽度`，桩节用 `size / reserved2`。
3. 对第 `i ∈ [0, n)` 个条目，取间接符号表第 `base + i` 项 → 得一个符号表索引 → 查常规符号表 → 拿到该条目真正引用的外部符号名。

> [!note] 一图记牢复用语义
> 速记：**`reserved1` 管"从间接符号表哪里开始"（起点索引），`reserved2` 管"每个 stub 多大"（用来算个数），`reserved3` 不用**。这套机制让节头不必显式存条目数（数目由 `size` 推导），保持结构紧凑——代价是解析器必须知道这层约定。`__stubs`（见 [[22.Mach-O __stubs节]]）与 `__la_symbol_ptr`（见 [[30.Mach-O __la_symbol_ptr节]]）正是靠它和间接符号表联动完成惰性绑定的。

### 10. 节如何被组织进段：`cmdsize` 视角

节头不是独立的加载命令，而是**寄生在段命令体内**：`LC_SEGMENT_64` 的固定头（`segment_command_64`，72 字节）之后，紧跟 `nsects` 个 `section_64`（每个 80 字节），这一串节头的总长**已计入段头的 `cmdsize`**：

```text
cmdsize(段) = 72 + 80 * nsects        // 64 位
cmdsize(段) = 56 + 68 * nsects        // 32 位
```

因此遍历 Load Commands 时按 `ptr += cmdsize` 跳到下一条命令，会**自动跨过本段全部节头**，不会把节头误当成独立命令。`nsects == 0` 的段（如 `__PAGEZERO`、`__LINKEDIT`）命令体就只有那 72 字节段头、没有任何节头。健壮解析器会校验 `cmdsize == 72 + 80*nsects` 自洽——对不上说明 `nsects` 被篡改或命令越界（这一遍历与校验细节见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。

## 实操：用工具查看

### 示例 1：`otool -l` 看节头（`Section` 块）

`otool -l` 会把每个段命令后面的节头逐个打印成 `Section` 块：

```bash
otool -l /bin/ls | grep -A 12 "Section"   # 看每个节的完整节头
otool -lv /bin/ls                          # -v 把 flags 显示成符号名（S_REGULAR | S_ATTR_* …）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Section
  sectname __text
   segname __TEXT
      addr 0x0000000100001000      ; 节虚拟地址（落在 __TEXT 段范围内）
      size 0x0000000000002a30      ; 节大小 ≈ 10KB
    offset 4096                    ; 文件偏移
     align 2^2 (4)                 ; 存储值 align=2，实际 4 字节对齐
    reloff 0                       ; 已链接产物，无节级重定位
    nreloc 0
     flags 0x80000400              ; S_REGULAR | S_ATTR_PURE_INSTRUCTIONS | S_ATTR_SOME_INSTRUCTIONS
 reserved1 0
 reserved2 0
 reserved3 0
```

> 说明：`flags 0x80000400` 拆开 = 类型 `S_REGULAR`（`&0xff=0`）+ 属性纯指令/含指令——这是代码节 `__text` 的标准标记；`align 2^2 (4)` 里 `2^2` 是存储的指数、`(4)` 是实际字节；`reserved*` 全 0 因为 `__text` 不是符号桩/指针节。

### 示例 2：`otool -l` 看符号桩节的 `reserved1`/`reserved2`

`__stubs`（`S_SYMBOL_STUBS`）会用到 `reserved1`（间接符号表起始索引）与 `reserved2`（每个 stub 大小）：

> [!warning] 示例输出为示意
> 数值为构造，仅示意符号桩节如何复用 reserved 字段。

```text
Section
  sectname __stubs
   segname __TEXT
      addr 0x0000000100003a40
      size 0x0000000000000078      ; 120 字节
    offset 14912
     align 2^1 (2)
    reloff 0
    nreloc 0
     flags 0x80000408              ; 类型 S_SYMBOL_STUBS(0x8) | S_ATTR_PURE_INSTRUCTIONS(0x80000000)
 reserved1 5                       ; 本节首条目 → 间接符号表第 5 项
 reserved2 12                      ; 每个 stub 12 字节 → 条目数 = 120 / 12 = 10
 reserved3 0
```

> 说明：`flags & 0xff = 0x08`（`S_SYMBOL_STUBS`），`reserved2=12`（arm64 上一个 stub 常 12 字节），所以这个节有 `120/12 = 10` 个桩；它们对应间接符号表第 5、6、7…14 项，逐项再查常规符号表得到被调外部函数名（联动 [[06.Mach-O LC_DYSYMTAB]]）。

### 示例 3：`otool -s` 直接 dump 节的原始字节

`otool -s 段名 节名` 以十六进制 dump 指定节的内容（不加 `-v` 是裸十六进制，加 `-V`/对 `__text` 用 `-tV` 可反汇编）：

```bash
otool -s __TEXT __cstring /bin/ls    # dump __cstring 节的原始字节（看到一串 C 字符串）
otool -s __DATA __data /bin/ls       # dump __data 节
otool -tV /bin/ls                    # 反汇编 __TEXT,__text（-t 专指代码节）
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意 `otool -s` 的"地址 + 十六进制"逐行格式。

```text

Contents of (__TEXT,__cstring) section
0000000100003f00  2f 75 73 72 2f 6c 69 62 2f 64 79 6c 64 00 25 73   /usr/lib/dyld.%s
0000000100003f10  3a 20 00 6c 73 00 25 73 00 00 00 00 00 00 00 00   : .ls.%s........
```

> 说明：左列是该字节的虚拟地址（= 节 `addr` 起算），中间是十六进制，`otool -s` 默认不解析含义；可见 `__cstring` 里就是一串以 `\0` 分隔的 C 字符串（`/usr/lib/dyld`、`%s` 等），印证它的类型 `S_CSTRING_LITERALS`。


> [!warning] 示例输出为示意

```text
    Section __text: 10800 (addr 0x100001000 offset 4096)
```

## FAQ

> [!question] `flags` 的"类型"和"属性"到底怎么拆？为什么类型只有 8 位？
> `flags`（32 位）按 `SECTION_TYPE = 0x000000ff` 与 `SECTION_ATTRIBUTES = 0xffffff00` 切两半：**低 8 位是类型**（256 种之一，互斥——一个节只能是 `S_REGULAR`、`S_ZEROFILL`、`S_SYMBOL_STUBS`… 中的某一种），**高 24 位是属性**（位掩码，可多个并存，如纯指令 + 禁死代码消除）。类型用 8 位是因为类型是枚举（互斥、数量有限，目前到 `0x16`），用一个字节足够；属性是开关位集合，需要独立比特位，所以占高 24 位。取值用 `flags & SECTION_TYPE` 取类型、`flags & SECTION_ATTRIBUTES` 取属性。

> [!question] `reserved1` 和 `reserved2` 不是"保留"吗，为什么有值？
> 名为保留，实为"按节类型复用"。对**符号指针节**（`__got`/`__nl_symbol_ptr`/`__la_symbol_ptr`）和**符号桩节**（`__stubs`），`reserved1` 是该节在**间接符号表**里的**起始索引**，`reserved2` 是**每个 stub 的字节大小**（仅桩节用，指针节项大小固定为指针宽度故不用）。节头不直接存条目数，而是用 `size ÷ 单项大小` 算：桩节用 `size / reserved2`，指针节用 `size / 8`（64 位）。`reserved3` 才是真正没用、恒 0（且只有 64 位结构有它）。其他普通节（`__text`/`__data` 等）这三个字段都是 0。

> [!question] `align` 写的 `4` 到底是 4 字节还是 16 字节对齐？
> 取决于你看的是**存储值**还是**实际值**。`align` 字段存的是 **2 的幂的指数**：存 `4` 意味着 `2^4 = 16` 字节对齐，存 `2` 意味着 `2^2 = 4` 字节对齐。容易混的是 `otool` 的显示——它印成 `2^4 (16)`，前者 `2^4` 是原始存储值（指数 4），括号 `(16)` 是替你算好的字节数。所以"`align` 是 4"这句话有歧义：如果指字段存储值，那是 16 字节对齐；如果指实际字节数，对应的存储值是 2。看 `otool` 输出以括号里的字节数为准。

> [!question] `__bss` 这种零填充节，`offset` 指向的文件位置有数据吗？
> 没有真正属于它的初始化数据。`S_ZEROFILL`（`__bss`）、`S_GB_ZEROFILL`、`S_THREAD_LOCAL_ZEROFILL` 这类节**不占文件**：`size` 计入节的**内存**大小、运行时由内核零填充，但**不计入文件大小**，`offset` 字段填的值并不指向本节专属的初始化字节。判断一个节是否占文件、要不要从磁盘读，**看它的类型是不是某种 zerofill，而不是看 `offset` 是否非零**。这也是为什么含 `__bss` 的 `__DATA` 段会出现 `vmsize > filesize`（见 [[28.Mach-O __bss节]] 与 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。

> [!question] 节和段，到底哪个是给谁看的？为什么需要两层？
> **段是给内核/dyld 看的映射与权限单位**（页对齐、有 `vmaddr`/`initprot`），**节是给链接器/分析工具看的内容分类单位**（`__text`/`__cstring`/`__data`…）。需要两层是因为两件事的粒度不同：内存保护只能按页、按"一段一套权限"施加，太粗；而数据需要按用途细分（代码、只读串、可写数据、指针表…）才能让链接器正确合并、让工具正确解读。于是 Mach-O 让"多个用途相近、权限相同的节"装进"一个段"——节决定内容与处理方式，段决定它们共享的映射与权限。dyld 处理段（建内存布局），链接器处理节（拼数据）。

## 小结

- 节是段内细粒度内容单位，统一由 `section_64`（64 位 80 字节）/ `section`（32 位 68 字节，无 `reserved3`）描述；节名总写作 `段名,节名`。
- 四类字段：位置（`addr`/`offset`/`size`，`offset` 恒 4 字节）、对齐（`align`，存的是 2 的幂指数，实际对齐 = `2^align`）、重定位（`reloff`/`nreloc`，已链接产物多为 0）、身份（`flags`）。
- `flags` 由 `SECTION_TYPE(0x000000ff)` 与 `SECTION_ATTRIBUTES(0xffffff00)` 切成低 8 位"类型"（互斥，`S_REGULAR 0x0`~`S_INIT_FUNC_OFFSETS 0x16`，含 `S_THREAD_LOCAL_*` 系列）与高 24 位"属性"（位掩码，`S_ATTR_PURE_INSTRUCTIONS`/`S_ATTR_NO_DEAD_STRIP` 等）。
- `reserved1` = 间接符号表起始索引、`reserved2` = 每个 stub 字节大小（用于推算条目数 `size/reserved2`）、`reserved3` 真正保留；仅符号桩/指针节复用前两者，联动 `LC_DYSYMTAB` 的间接符号表。
- 零填充类型（`S_ZEROFILL`/`S_GB_ZEROFILL`/`S_THREAD_LOCAL_ZEROFILL`）不占文件，`offset` 不指真实初始化数据，是 `vmsize > filesize` 的成因之一。

### TLS 节与 ObjC imageinfo

本节深入展开两类在通用节类型表里已列名、但细节未尽的节族：线程局部存储（TLS/TLV）相关节组和 `__objc_imageinfo` 节。

#### TLS 节：`S_THREAD_LOCAL_*` 系列机制

C11/C++11 的 `thread_local`（以及 GCC/Clang 扩展的 `__thread`）关键字在 Mach-O 里的实现由**五种 TLS 节类型**（`0x11`–`0x15`）协同完成，每种节承担不同职责。

**五种 TLS 节类型的分工**：

| 节类型 | 值 | 典型节名 | 承载内容 |
|---|---|---|---|
| `S_THREAD_LOCAL_REGULAR` | `0x11` | `__thread_data` | 有初值的 TLS 变量的**初值模板**（字节数组，按变量原始值填充）|
| `S_THREAD_LOCAL_ZEROFILL` | `0x12` | `__thread_bss` | 无初值（零初始化）的 TLS 变量占位（零填充，不占文件）|
| `S_THREAD_LOCAL_VARIABLES` | `0x13` | `__thread_vars` | `tlv_descriptor` 结构体数组（每个 TLS 变量一个）|
| `S_THREAD_LOCAL_VARIABLE_POINTERS` | `0x14` | `__thread_ptrs` | 指向 `tlv_descriptor` 的指针（用于间接访问，较少见）|
| `S_THREAD_LOCAL_INIT_FUNCTION_POINTERS` | `0x15` | `__thread_init` | TLS 动态初始化函数指针（C++ 复杂初始化器，如全局构造函数内的 `thread_local`）|

**`tlv_descriptor` 结构体**（`__thread_vars` 节里每个 TLS 变量存一个）：

```c
// 来自 dyld 源码 / libpthread 实现
struct tlv_descriptor {
    void* (*thunk)(struct tlv_descriptor*);  // getter 函数指针
                                              // 初始指向 tlv_allocate_and_initialize_for_key
                                              // 首次调用后改写为 tlv_get_addr
    unsigned long key;    // pthread_key_t，标识本线程的 TLS 存储块
    unsigned long offset; // 本变量在线程存储块内的字节偏移
};
```

**字节级布局**（arm64，每个 `tlv_descriptor` 24 字节）：

```
偏移  0：uint64_t thunk    — getter 函数指针（8字节）
偏移  8：uint64_t key      — pthread_key_t（8字节）
偏移 16：uint64_t offset   — 块内偏移（8字节）
```

**TLS 变量访问的完整路径**：

```
源码:  int x = my_tls_var;       // my_tls_var 是 thread_local int

编译器生成:
  adrp x0, __thread_vars@PAGE         // 取 __thread_vars 节内该变量的 tlv_descriptor 地址
  add  x0, x0, __thread_vars@PAGEOFF  //
  ldr  x8, [x0]                       // 取 thunk 字段（getter 函数指针）
  blr  x8                             // 调用 getter(descriptor)
                                      // 返回值 x0 = 本线程该变量的内存地址
  ldr  w9, [x0]                       // 读取变量值

首次调用（thunk = tlv_allocate_and_initialize_for_key）：
  1. 用 pthread_getspecific(key) 查本线程的存储块
  2. 若不存在→ malloc 一块新内存，用 __thread_data 的初值模板 memcpy 初始化
  3. pthread_setspecific(key, block)
  4. 把 thunk 字段改写为 tlv_get_addr（快路径）
  5. 返回 block + offset

此后调用（thunk = tlv_get_addr）：
  1. pthread_getspecific(key)
  2. 返回 block + offset  （O(1)，只有一次系统调用）
```

**`__thread_data` 与 `__thread_bss` 的关系**（类比 `__data` 与 `__bss`）：

- `__thread_data`（`S_THREAD_LOCAL_REGULAR`）：存有初值的 TLS 变量的初始字节，**占文件**，dyld 加载时拿来 memcpy 初始化每个线程的存储块。
- `__thread_bss`（`S_THREAD_LOCAL_ZEROFILL`）：零初始化 TLS 变量的占位，**不占文件**（零填充），运行时用 calloc/bzero 初始化，节的 `size` 给出所需字节数。

两者在各线程的存储块里**紧邻排布**：块总大小 = `__thread_data.size + __thread_bss.size`。

**`__thread_init`（`S_THREAD_LOCAL_INIT_FUNCTION_POINTERS`）**：C++ `thread_local` 变量若有复杂的构造函数（非 POD 类型），编译器为其生成初始化函数并将函数指针放入此节。dyld 在初始化 TLS 块后按序调用这些函数（类似 `__mod_init_func` 但仅针对 TLS）。

**`otool` 查看 TLS 相关节**：

```bash
# 查看 __thread_vars 节的 tlv_descriptor 数组
otool -s __DATA __thread_vars MyApp
# 输出（示意）：每 24 字节一个描述符，按 thunk/key/offset 排布

# 反汇编访问 TLS 变量的代码
otool -tV MyApp | grep -A 5 "thread_vars"
# 可见 adrp + add + ldr + blr 的模式

# 查看 TLS 初值模板
otool -s __DATA __thread_data MyApp
```

**LLDB 调试 TLS 变量**：

```bash
# 查找 TLS 变量的当前线程地址
(lldb) expr (void *)_tlv_address(&myTLSVar)   # 伪示意
# 或直接打印
(lldb) p my_tls_var   # LLDB 能理解 thread_local，自动走 getter
```

**逆向 TLS 的关键识别特征**：

- 代码里出现 `adrp + add + ldr + blr` 四指令序列，目标在 `__thread_vars` 节 → 必然是 TLS 变量访问
- `__thread_vars` 节大小 = 变量数 × 24（每个描述符 24 字节）
- 对应 `__thread_data`/`__thread_bss` 节存初值/零填充
- 初始 `thunk` 值（在 `__thread_vars` 里的第一个指针）是 dyld 内部符号 `tlv_allocate_and_initialize_for_key` 的地址（通过 bind 信息绑定）

#### `__objc_imageinfo` 节：ObjC 运行时的镜像元数据标志

`__objc_imageinfo`（`__DATA_CONST,__objc_imageinfo` 或 `__DATA,__objc_imageinfo`）是 ObjC 运行时识别镜像能力的**唯一来源**，仅 8 字节，但信息密度极高。

**节结构（字节级）**：

```c
// 来自 objc-abi.h / objc-runtime-new.h
struct objc_image_info {
    uint32_t version;   // 通常为 0（保留，历史上曾用于表示 GC 配置，现在无意义）
    uint32_t flags;     // 详见下表
};
```

字段在节内的精确偏移（节大小固定 8 字节）：

| 偏移 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0 | `version` | uint32_t | 固定 0（历史字段，已无实际作用）|
| 4 | `flags` | uint32_t | 运行时能力与语言标志的位掩码 |

**`flags` 字段完整位定义**（来自 `objc-abi.h`）：

| 位 | 掩码 | 常量名 | 含义 |
|---|---|---|---|
| 0 | `0x00000001` | `IsReplacement` | 此镜像替换了另一个镜像（复写）|
| 1 | `0x00000002` | `SupportsGC` | 支持垃圾回收（macOS 10.6–10.13 era，现已废弃）|
| 2 | `0x00000004` | `RequiresGC` | 需要垃圾回收（已废弃）|
| 3 | `0x00000008` | `OptimizedByDyld` | 已被 dyld 优化（共享缓存构建时写入）|
| 4 | `0x00000010` | `CorrectedSynthesize` | 已修正合成属性（历史兼容位）|
| 5 | `0x00000020` | `IsSimulated` | 模拟器环境（Simulator）|
| 6 | `0x00000040` | `HasCategoryClassProperties` | 存在 category 含 class properties |
| 7 | `0x00000080` | `OptimizedByDyldClosure` | 已被 dyld closure 优化 |
| 8–15 | `0x0000FF00` | `SwiftVersion` | **Swift 版本标志**（见下详解）|
| 16–31 | `0xFFFF0000` | 保留 | 未使用 |

**Swift 版本标志（`flags & 0xFF00`，即 bit8–15）**：

这是 ObjC 运行时区分"纯 Swift"与"Swift/ObjC 混合"二进制的关键字段：

| `(flags >> 8) & 0xFF` | 含义 |
|---|---|
| `0x00` | 纯 Objective-C，无 Swift 代码 |
| `0x01` | Swift 1.x（早期 Swift，已几乎不见）|
| `0x02` | Swift 2.x |
| `0x03` | Swift 3.x（大量遗留 App）|
| `0x04` | Swift 4.x |
| `0x05` | Swift 4.1 / 4.2 |
| `0x06` | Swift 5.0（ABI 稳定，当前主流起点）|
| `0x07` | Swift 5.1（opaque return types）|
| `0x08` | Swift 5.2（函数构建器）|
| `0x09` | Swift 5.3 |
| `0x0A`+| Swift 5.4 及以上（随版本递增）|

**读取方法**：

```c
uint32_t flags = imageinfo->flags;
uint8_t  swift_version = (flags >> 8) & 0xFF;
bool is_swift = (swift_version != 0);
bool is_swift5_or_later = (swift_version >= 6);   // ABI 稳定版本起
```

**常见值快速判断（`otool -s __DATA __objc_imageinfo` 输出）**：

```text
# 纯 ObjC 二进制（flags = 0x00000000）
00000000 00000000

# Swift 5.x App（flags = 0x00000640）
# 0x00000640 = (6<<8) | 0x40 = SwiftVersion=6 | HasCategoryClassProperties
40060000 00000000

# 已优化的共享缓存库（flags = 0x00000008 = OptimizedByDyld）
08000000 00000000
```

注意字节序：arm64 是小端，`otool -s` 的输出按实际字节排列，`00000640` 代表 `version=0`，`flags` 以字节流显示为 `40 06 00 00`（即 `uint32_t flags = 0x00000640`）。

**ObjC 运行时如何使用 imageinfo**：

```
dyld 加载镜像 →
  objc_init() →
    _read_images() →
      遍历所有已加载镜像的 __objc_imageinfo →
        检查 flags:
          OptimizedByDyld? → 跳过部分初始化步骤（类已在共享缓存中注册）
          SwiftVersion > 0? → 按 Swift ABI 解析 Swift 类（调用 Swift runtime）
          SupportsGC? → 启用 GC 路径（已废弃，现代运行时忽略）
          IsReplacement? → 处理运行时替换（用于 Mock/Swizzle 框架）
```

**逆向识别 Swift App 的一线工具**：

```bash
# 查看 __objc_imageinfo（判断是否 Swift 及版本）
otool -s __DATA __objc_imageinfo MyApp.app/MyApp | head -2
# 或（现代 macOS，__DATA_CONST 下）
otool -s __DATA_CONST __objc_imageinfo MyApp.app/MyApp | head -2

# 解读 flags 值（Python 快速脚本）：
python3 -c "
flags = 0x00000640
print(f'Swift version: {(flags>>8)&0xFF}')   # 6 → Swift 5.0
print(f'OptimizedByDyld: {bool(flags & 0x8)}')
print(f'HasCategoryClassProperties: {bool(flags & 0x40)}')
"

# LLDB 查看运行期的 imageinfo
(lldb) image list -d MyApp   # 找到基址
(lldb) memory read --size 4 --count 2 <imageinfo_addr>
```

**`__objc_imageinfo` 在哪个段**（版本差异）：

- **macOS/iOS 旧版（Pre-chained-fixups）**：通常在 `__DATA,__objc_imageinfo`（`rw-`，因包含运行时写入的位）
- **现代（链式 fixups 启用后）**：可能移至 `__DATA_CONST,__objc_imageinfo`（加载期写 OptimizedByDyld 位后降只读）
- **共享缓存构建时**：dyld_cache_builder 在构建时写入 `OptimizedByDyld` 位（`0x08`），之后整段 `mprotect` 成只读
