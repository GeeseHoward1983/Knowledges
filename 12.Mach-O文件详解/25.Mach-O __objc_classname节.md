# 详解Mach-O(二十五)Mach-O __objc_classname节

> [!abstract] TL;DR
> **`__objc_classname` 是 Objective-C 类名的字符串池**——`NSObject`、`ViewController`、`NSString` 等所有 ObjC 类的名字文本，以 NUL 结尾的 C 字符串形式集中存放在这里，只读位于 `__TEXT` 段（权限 `r-x`）。
> 它的节类型与 [[20.Mach-O __cstring节]] 完全一样，都是 **`S_CSTRING_LITERALS`（`flags & SECTION_TYPE = 0x2`）**——编译器生成它时用的正是 `.section __TEXT,__objc_classname,cstring_literals`。所以它享受和 `__cstring` 一样的链接器去重特权（相同类名只存一份），逆向工具也能用 `strings`/`otool -s` 直接扫出。它与 [[24.Mach-O __objc_methname节]]（方法名池）、[[26.Mach-O __objc_methtype节]]（方法类型编码池）三者同构，区别只在装的内容是"类名"。
> **谁引用它**：每个类的只读元数据结构 `class_ro_t` 有一个 `name` 字段，是一个指针，直接指向本节里的类名字符串。runtime 启动时遍历 [[36.Mach-O __objc_classlist节]] 里的类指针数组，对每个类沿 `class_ro_t.name` 取出类名，登记进全局命名类哈希表（`gdb_objc_realized_classes`）——这张表正是 `objc_getClass` / `NSClassFromString` 按名字查类的依据。
> **Swift 类的特殊性**：纯 Swift 类桥接到 ObjC 时，存进本节的不是裸类名而是 **修饰名（mangled name）**，形如 `_TtC9NameSpace14SomeSwiftClass`（= `NameSpace.SomeSwiftClass`），把 Swift 的命名空间塞进 ObjC 的扁平命名空间。
> **逆向价值**：类名直接暴露程序结构——业务类、第三方 SDK、控制器命名一目了然；配合方法名池可大致还原每个类的接口轮廓，是 class-dump 类工具的核心数据源之一。

## 概述与定位

每个 ObjC 类都有一个名字，而这个名字在运行期被高频使用：runtime 注册类要它、`NSClassFromString("ViewController")` 反查类对象要它、KVC（`valueForKey:`）和归档（`NSKeyedArchiver`）要它、`NSStringFromClass([obj class])` 打印日志也要它。把这些名字字符串集中存成一个池子，既省体积（去重）又便于 runtime 统一遍历，于是有了 `__objc_classname`。

它在 Mach-O 的层级里处于这样的位置：

- 它继承 [[13.Mach-O __TEXT]] 段的**只读、可执行**属性（`r-x`）——类名是编译期就定死的常量，运行期不该改，放进只读段恰如其分，也让多个进程能共享同一份物理页。
- 它是 [[18.Mach-O section]] 通用模型里**类型为 `S_CSTRING_LITERALS`（`0x2`）的具体节**：同一套 `section_64` 结构描述它，与 `__cstring` 唯一的差别是 `sectname` 取 `__objc_classname`（而非 `__cstring`）——类型位、内容形态（NUL 结尾 C 串）、去重特权全都一样。换句话说，**`__objc_classname` 本质上就是一个"专供 ObjC 类名"的 `__cstring`**。
- 它是 ObjC 元数据"三大字符串池"之一，与 [[24.Mach-O __objc_methname节]]（方法名 / 选择器名）、[[26.Mach-O __objc_methtype节]]（方法类型编码）并列。三者结构同构、定位平行，只是被各自的元数据结构（类的 `class_ro_t.name`、方法的 `method_t.name` / `method_t.types`）分别引用。

一句话定位：**`__objc_classname` = `__TEXT` 段里、类型 `S_CSTRING_LITERALS`、专门存放 ObjC 类名（含 Swift 桥接类的修饰名）的只读 C 字符串池，被各类 `class_ro_t` 的 `name` 字段引用**。

> [!note] 为什么类名不直接放 `__cstring`，要单切一个节？
> 既然类型、形态都和 `__cstring` 一样，为何不混在一起？因为 ObjC 元数据需要**按"种类"分门别类地被 runtime 和工具批量遍历**：runtime 关心的是"哪些是类名、哪些是方法名、哪些是选择器引用（`__objc_selrefs`）"，class-dump 类工具也按节名定位"类名都在 `__objc_classname`、方法名都在 `__objc_methname`"。把类名、方法名、普通 C 串混在一个 `__cstring` 里，runtime 就无从快速、精确地枚举"所有类名"。所以 Mach-O 用**专用节名**把这些语义不同的字符串切开——节类型相同（都是 `S_CSTRING_LITERALS`），但节名携带了"这堆字符串是干什么用的"这一层语义。这也是为什么逆向时"在 `__cstring` 里找不到某个 ObjC 类名"——它根本不在那儿，而在 `__objc_classname`。

## 核心原理与字段详解

### 1. 内容布局：以 `\0` 分隔/结尾的类名紧凑排布

`__objc_classname` 的物理内容就是**一整块连续字节**，里面是一个接一个、以 `\0`（0x00）分隔并收尾的 ObjC 类名 C 字符串。和 `__cstring` 一样：没有长度前缀、没有索引表、没有对齐填充（`align` 通常为 0，即 1 字节对齐）——类名首尾相接、最省空间地塞在一起。

举例，若程序里定义/引用了 `NSObject`、`ViewController` 两个类，节内字节可能是这样（首尾相接，各自 `\0` 收尾）：

```text
4e 53 4f 62 6a 65 63 74 00 | 56 69 65 77 43 6f 6e 74 72 6f 6c 6c 65 72 00
N  S  O  b  j  e  c  t  \0 | V  i  e  w  C  o  n  t  r  o  l  l  e  r  \0
```

代码侧（更准确说是**元数据侧**）并不"按下标"访问它，而是**持有某个类名首字节的地址**。编译器为每个类的名字生成一个内部标号（如 `L_OBJC_CLASS_NAME_`），把它发射进本节，再让该类的 `class_ro_t.name` 字段保存这个标号的地址。链接期标号解析成具体虚拟地址，运行期 runtime 把这个地址当 `const char *` 读到 `\0` 为止，得到类名。

> [!note] 编译器如何声明这个节
> 编译器处理 `@implementation` 时，发射的汇编里类名节是用带 `cstring_literals` 属性声明的，和 `__cstring` 如出一辙：
> ```asm
>     .section __TEXT,__objc_classname,cstring_literals
> L_OBJC_CLASS_NAME_:
>     .asciz "ViewController"
> ```
> 第三参数 `cstring_literals` 正是把本节类型位设为 `S_CSTRING_LITERALS`，于是它和 `__cstring` 一样可去重。而这个 `L_OBJC_CLASS_NAME_` 标号，会被该类的 `class_ro_t` 结构里那一行 `.quad L_OBJC_CLASS_NAME_`（即 `name` 字段）引用——这就是"类名字符串池"与"类元数据"之间的物理纽带。

### 2. 谁引用它：`class_ro_t.name` 指针

ObjC 现代运行时（`__OBJC2__`）把一个类拆成三层结构：`objc_class`（含 `isa`、`superclass`、方法缓存和一个 `bits` 字段）→ `class_rw_t`（可读写、运行期可变的数据）→ `class_ro_t`（**只读、编译期定死的数据**）。类名就住在最底层的 `class_ro_t` 里。来自 Apple objc4 `objc-runtime-new.h` 的 `class_ro_t` 定义（以 objc4-781 为例）：

```c
struct class_ro_t {
    uint32_t flags;           // 类标志位（如 RO_META 表示这是元类的 ro）
    uint32_t instanceStart;   // 实例数据起始偏移
    uint32_t instanceSize;    // 实例大小
#ifdef __LP64__
    uint32_t reserved;        // 仅 64 位存在的对齐保留字
#endif
    const uint8_t * ivarLayout;
    const char    * name;     // ★ 指向 __objc_classname 里的类名字符串
    method_list_t * baseMethodList;   // 方法列表
    protocol_list_t * baseProtocols;  // 协议列表
    const ivar_list_t * ivars;        // 实例变量列表
    const uint8_t * weakIvarLayout;
    property_list_t * baseProperties; // 属性列表
};
```

关键就是那一行 `const char * name`——它是一个**裸指针**，运行期解析后指向 `__objc_classname` 节里某个类名字符串的首字节。注意 `class_ro_t` 里**只存一个指针**，类名文本本体并不在 `class_ro_t` 里、而在 `__objc_classname` 池里；这样多个引用同名类的地方、以及类与元类共享一个名字时，都指向池里那唯一一份，省体积。

> [!note] 类 vs 元类共享同一个名字
> 每个类 `@implementation` 编译时实际生成**两个** `class_ro_t`：一个给类本身（`l_OBJC_CLASS_RO_$_SomeClass`），一个给它的元类（`l_OBJC_METACLASS_RO_$_SomeClass`，`flags` 带 `RO_META` 位）。在发射的汇编里，这两个 `class_ro_t` 的 `name` 字段是**同一行** `.quad L_OBJC_CLASS_NAME_`——也就是说类和元类**共用 `__objc_classname` 里同一份类名字符串**，并不各存一份。这是去重特权在元数据层面的又一次体现。

### 3. 节类型 `S_CSTRING_LITERALS` 与去重特权

`__objc_classname` 节头 `flags` 字段的低 8 位（`flags & SECTION_TYPE`）等于 `0x2`，即 `S_CSTRING_LITERALS`——和 [[20.Mach-O __cstring节]] 一模一样。这意味着：

- **链接器可去重合并**：多个 `.o`（或同一 `.o` 内）出现相同类名字面量时，链接器 `ld` 把它们折叠成一份，所有 `class_ro_t.name` 重定位到这唯一的一份上。典型场景：基类 `NSObject` 被无数子类继承，但 `"NSObject"` 这个字符串在最终二进制里通常只有一份。
- **`strings`/`otool` 能直扫**：因为内容是 NUL 结尾的可打印 ASCII 串，`strings` 的"连续可打印字符 + 终止"扫描和 `otool -s __TEXT __objc_classname` 的逐行 dump 都能直接读出类名，无需解析复杂结构。这也是 class-dump 之外、最轻量的"列出二进制里有哪些类"的办法。

> [!note] 和 `__objc_methname` / `__objc_methtype` 的同构关系
> 这三个 ObjC 字符串池**节类型完全相同**（都是 `S_CSTRING_LITERALS`）、布局完全相同（NUL 结尾 C 串紧凑排布）、去重特权完全相同。它们的区别**仅在节名所携带的语义**和**谁来引用**：`__objc_classname` 被 `class_ro_t.name` 引用、装类名；`__objc_methname`（见 [[24.Mach-O __objc_methname节]]）被 `method_t.name` 引用、装方法名（也即 SEL 的名字）；`__objc_methtype`（见 [[26.Mach-O __objc_methtype节]]）被 `method_t.types` 引用、装方法的类型编码串（如 `v16@0:8`）。理解了其中一个，另两个的原理是平移的。

### 4. runtime 类注册：从 `__objc_classlist` 到全局命名类表

`__objc_classname` 不是孤立的——它是 ObjC runtime 启动期"类注册"流程的终点之一。完整链路（基于 Apple objc4 源码）：

1. **dyld 加载镜像 → `_objc_init` → `map_images` → `_read_images`**：进程启动或 `dlopen` 一个含 ObjC 代码的 Mach-O 时，dyld 回调进 runtime 的 `_read_images`，这是类注册的总入口。
2. **取类列表**：`_read_images` 对每个镜像调用 `_getObjc2ClassList(hi, &count)`，这个宏（`GETSECT(_getObjc2ClassList, classref_t, "__objc_classlist")`）就是去读 [[36.Mach-O __objc_classlist节]] 那个**类指针数组**——数组里每个元素是一个指向类对象的指针，元素个数 = 节字节数 ÷ 指针宽度（节大小隐含了类的数量）。
3. **逐类 `readClass`**：对数组里每个类指针 `classlist[i]`，runtime 调 `readClass(cls, ...)`。`readClass` 内部沿该类的 `bits → class_ro_t` 取到 `ro->name`，也就是**解引用了 `__objc_classname` 里的那个类名字符串**。
4. **登记进命名类表**：runtime 把"类名 → 类对象"这条映射插进一张全局哈希表 `gdb_objc_realized_classes`（一个 `NXMapTable`，键是类名 C 串、值是 `Class` 指针；插入走 `addNamedClass` → `NXMapInsert(gdb_objc_realized_classes, name, cls)`）。**至此 `__objc_classname` 里的字符串就从"静态数据"变成了"运行期可按名查找的索引键"**。

```text
dyld 加载镜像
   │
   ▼
_objc_init → map_images → _read_images
   │  _getObjc2ClassList() 读 __DATA,__objc_classlist（类指针数组）
   ▼
对每个类 classlist[i]:
   readClass(cls)  ──沿 bits→class_ro_t──>  ro->name  ──指向──>  __TEXT,__objc_classname 里的 "ViewController\0"
   │
   ▼
addNamedClass → NXMapInsert(gdb_objc_realized_classes, "ViewController", cls)
   │
   ▼
全局命名类表建成 → objc_getClass("ViewController") 可查
```

> [!note] 懒加载 vs 非懒加载类
> 类是否实现 `+load` 方法，决定它何时被"实现（realize）"：**非懒加载类**（实现了 `+load`）在 `_read_images` 阶段就走 `realizeClassWithoutSwift` 完整初始化；**懒加载类**则推迟到第一次收到消息时才实现。但无论哪种，**类名的注册（进 `gdb_objc_realized_classes`）都依赖 `__objc_classname` 里的字符串**——只是"完整实现"的时机不同，"名字登记"这一步都绕不开本节。

### 5. `objc_getClass` / `NSClassFromString`：按名字反查类

第 4 步建好的命名类表，正是 `NSClassFromString` / `objc_getClass` 工作的底座。这条"用字符串拿到 Class 对象"的能力，是 ObjC 动态特性（按名实例化、KVC、归档、`class-dump`）的根基。调用链（基于 objc4-756 等版本，函数名随版本略有移动）：

- **Foundation 入口** `NSClassFromString(@"ViewController")`：它是个薄封装，最终调进 runtime 的 `objc_getClass("ViewController")`。
- **runtime 入口** `objc_getClass`：名字非空就调 `look_up_class(name, NO, YES)`。
- **核心查表** `getClass_impl`：对类名做 `NXMapGet(gdb_objc_realized_classes, name)`——就是去第 4 步那张哈希表里按名字捞 `Class`；若没命中，再 `getPreoptimizedClass(name)` 去 dyld 共享缓存的预优化类表里找一遍。
- **命中即返回该 `Class` 对象**；都没命中返回 `Nil`。

所以一句话：**`objc_getClass` 本质就是拿你给的字符串，去那张以 `__objc_classname` 字符串为键建起来的 `NXMapTable` 里查值**。理解了这条链，就明白为何"砍掉/混淆 `__objc_classname`"能让 `NSClassFromString` 失效——键没了，查不到。

> [!note] `objc_getClass` 与 `objc_lookUpClass` 的区别
> 还有个近亲 `objc_lookUpClass`（旧名 `objc_getClassWithoutWarning`），它调的是 `look_up_class(name, NO, NO)`——和 `objc_getClass` 唯一差别是**最后一个参数为 `NO`，即查不到时不触发 class handler 回调**。日常用 `NSClassFromString`/`objc_getClass` 即可；`objc_lookUpClass` 多见于 runtime 内部和不希望触发"未找到类"副作用的场景。

### 6. Swift 桥接类的修饰名（mangled name）

纯 Swift 类（`class Foo {}`，无 `@objc(自定义名)`）桥接到 ObjC runtime 时，存进 `__objc_classname` 的**不是裸类名 `Foo`，而是修饰名（mangled name）**。这是因为 Swift 有命名空间（模块）、ObjC 没有，必须把模块信息编码进一个扁平字符串。规则：

```text
_TtC<模块名长度><模块名><类名长度><类名>
例：模块 NameSpace 里的类 SomeSwiftClass
    → _TtC 9 NameSpace 14 SomeSwiftClass
    → 即字符串 "_TtC9NameSpace14SomeSwiftClass"
    → 反修饰（demangle）后 = "NameSpace.SomeSwiftClass"
```

- 存进 `__objc_classname`（即 `class_ro_t.name`）的是**修饰名** `_TtC9NameSpace14SomeSwiftClass`。
- 但 `class_getName(cls)` 返回的却是**反修饰后的** `NameSpace.SomeSwiftClass`——因为 runtime 里有 `copySwiftV1DemangledName` 等函数，在取名字时把 `_TtC...` 实时解开成人类可读形式。
- 两种名字 `objc_getClass` **都能查到**：`objc_getClass("_TtC9NameSpace14SomeSwiftClass")` 直接命中；`objc_getClass("NameSpace.SomeSwiftClass")` 也行——runtime 在直接查不到时会用 `copySwiftV1MangledName` 把点号名再修饰回 `_TtC...` 形式重试一次（"二次机会"）。

> [!note] 逆向时看到 `_TtC...` 不要慌
> 在 `otool -s __TEXT __objc_classname` 或 `strings` 输出里看到一堆 `_TtC...`、`_TtGC...`（泛型类）、`_TtCs...` 开头的怪名字，就是 Swift 类的修饰名。手工反修饰可对照规则拆"长度+名字"，或用 `swift demangle _TtC9NameSpace14SomeSwiftClass` 一键还原。带 `@objc(MyName)` 显式指定名字的 Swift 类则例外——它在本节里就是裸的 `MyName`，和纯 ObjC 类无异。

### 7. 逆向价值：暴露类结构

正因为 `__objc_classname` 集中存放了程序里**所有定义/引用过的 ObjC 类名**，它是静态逆向、App 结构还原的**直接富矿**：

- **业务类命名**：`LoginViewController`、`PaymentManager`、`UserModel`——光看类名就能猜出 App 的模块划分与核心功能。
- **第三方 SDK 指纹**：`AFHTTPSessionManager`（AFNetworking）、`FIRApp`（Firebase）、`AppsFlyerLib`、`UMSocialManager`（友盟）等——类名前缀直接暴露集成了哪些 SDK，是做 App 画像、合规审计、竞品分析的素材。
- **控制器/视图层次**：`*ViewController`、`*View`、`*Cell` 一扫便知 UI 结构。
- **还原接口轮廓**：把 `__objc_classname`（类名）和 [[24.Mach-O __objc_methname节]]（方法名）、[[26.Mach-O __objc_methtype节]]（方法类型）合起来，就能大致重建"每个类有哪些方法、参数返回值类型是什么"——这正是 `class-dump`/`dsdump` 类工具的工作原理：遍历 `__objc_classlist`，沿每个类的 `bits → class_ro_t → name` 取类名，再顺 `baseMethodList` 取方法，拼出近似的 `.h` 头文件。

工作流：先 `otool -s __TEXT __objc_classname`（或 `strings`）把类名全 dump，`grep` 关注前缀（SDK 指纹）或关键词（`Login`、`Pay`、`Crypto`…）；命中后用 `class-dump`/`dsdump` 把对应类的完整接口拉出来；再回到反汇编里找该类方法的实现，定位关键逻辑。

> [!warning] 类名看不到 ≠ 没有：当心剥离与混淆
> ① **Swift `@objc` 收窄**：纯 Swift 类若不暴露给 ObjC、且全程用 Swift 静态派发，可能根本不进 `__objc_classname`（它走的是 Swift 自己的元数据 `__swift5_types` 等，不在本节）。② **符号混淆**：成熟的商业 App 常上**类名混淆**（把 `PaymentManager` 改成 `a1b2c3`），本节里只剩无意义乱码——这时类名失去情报价值，需结合方法行为、字符串、网络流量等其他线索。③ **类名加密/运行时构造**：极端情况下类用 `objc_allocateClassPair` 运行期动态创建、名字由密文解密得到，静态 `__objc_classname` 里压根没有。所以"`__objc_classname` 干净/乱"不等于"程序没有有意义的类"。

> [!note] 架构差异：内容字节序无关，仅地址/对齐随位宽变
> `__objc_classname` 的内容是**字节序无关**的字符数据（ASCII/UTF-8 逐字节存储，arm64 与 x86_64 的字节完全一致），跨架构不变。差异只体现在**节的虚拟地址、文件偏移、对齐**会随位宽（32/64 位）与页大小（arm64 16KB、x86_64 4KB）不同，以及 `class_ro_t.name` 那个**指针字段的宽度**（64 位为 8 字节）——但这是 [[18.Mach-O section]] / 指针位宽层面的通用差异，不是 `__objc_classname` 特有。同一份源码在两种架构上编译，类名字符串字节一模一样，只是落在不同地址、被不同宽度的指针引用。

## 实操：用工具查看

### 示例 1：`otool -s __TEXT __objc_classname` dump 类名池原始字节

`otool -s 段名 节名` 以"地址 + 十六进制 + ASCII"逐行 dump 指定节。这是看 `__objc_classname` 最直接的方式：

```bash
otool -s __TEXT __objc_classname /path/to/ObjCBinary   # dump 类名池原始字节
otool -V -s __TEXT __objc_classname /path/to/ObjCBinary  # -V 让 otool 尝试更可读地解析
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/字节仅示意 `otool -s` 的逐行格式，实际数值以你机器上的 `otool` 为准。

```text
/path/to/ObjCBinary:
Contents of (__TEXT,__objc_classname) section
0000000100003c00  4e 53 4f 62 6a 65 63 74 00 56 69 65 77 43 6f 6e  NSObject.ViewCon
0000000100003c10  74 72 6f 6c 6c 65 72 00 50 61 79 6d 65 6e 74 4d  troller.PaymentM

0000000100003c30  53 70 61 63 65 31 34 53 6f 6d 65 53 77 69 66 74  Space14SomeSwift
0000000100003c40  43 6c 61 73 73 00 00 00 00 00 00 00 00 00 00 00  Class...........
```

> 说明：左列是该行首字节的**虚拟地址**（从节 `addr` 起算）；中间是十六进制；右列是可打印 ASCII（不可打印字节显示为 `.`）。可见 `NSObject\0`、`ViewController\0`、`PaymentManager\0` 三个 ObjC 类名，以及一个 Swift 修饰名 `_TtC9NameSpace14SomeSwiftClass\0`（反修饰 = `NameSpace.SomeSwiftClass`）**首尾相接、各自以 `\0` 收尾**——这正是 `S_CSTRING_LITERALS` 的典型布局，与 `__cstring` 完全一致。

### 示例 2：`otool -ov` 查看 ObjC 元数据中类名的引用

`otool -ov` 解析并打印 Mach-O 的 ObjC 运行时元数据（类列表、每个类的方法/属性/协议等），从中能看到 `class_ro_t.name` 是如何指向 `__objc_classname` 里的字符串的：

```bash
otool -ov /path/to/ObjCBinary                       # 打印全部 ObjC 元数据
otool -ov /path/to/ObjCBinary | grep -i "name"       # 只看 name 字段（类名/方法名）
```

> [!warning] 示例输出为示意
> 下列为构造样例，仅示意 `otool -ov` 把 `class_ro_t` 的 `name` 解析成具体类名、并标出其地址（指回 `__objc_classname`）的形态，字段值/地址均为示意。

```text
Contents of (__DATA,__objc_classlist) section
00000001000080a0 0x100008100 _OBJC_CLASS_$_ViewController
       isa        0x1000080c8 _OBJC_METACLASS_$_ViewController
       superclass 0x0  _OBJC_CLASS_$_UIViewController
       ...
       data       0x100008130 (struct class_ro_t *)
                    flags        0x80
                    instanceStart 8
                    instanceSize  16
                    name  0x100003c08 ViewController     ← 指回 __TEXT,__objc_classname
                    baseMethods   0x100008150 (struct method_list_t *)
                    ...
```

> 说明：`data` 指向该类的 `class_ro_t`，其中 `name 0x100003c08 ViewController` 这一行——地址 `0x100003c08` 正落在示例 1 dump 的 `__objc_classname` 节范围内（`ViewController` 的首字节），`otool` 顺着指针把它解析成了可读类名。这直观印证了第 2 节讲的 **`class_ro_t.name` → `__objc_classname` 字符串** 这条引用链。

### 示例 3：从类名反查代码（逆向工作流缩影）

逆向常见套路是"先在类名池里锁定可疑/关键类，再用 class-dump 拉出它的接口、回到反汇编找方法实现"：

```bash
# 1) 先列出所有类名，grep 关注的 SDK 指纹或业务关键词
otool -s __TEXT __objc_classname ./target | grep -iE "Pay|Login|Crypt|AFNetworking"
# 2) 用 class-dump 拉出某个类的完整接口（方法签名 = 类名 + 方法名 + 方法类型 三池拼成）
class-dump --arch arm64 ./target | grep -A40 "@interface PaymentManager"
```

> [!warning] 示例输出为示意
> 数值/签名为构造，仅示意"类名 → 用 class-dump 还原该类接口"的过程。

```text
@interface PaymentManager : NSObject
{
    NSString *_apiKey;       // ← 实例变量也可能暴露敏感字段名
}
- (BOOL)verifyReceipt:(NSData *)receipt;     // 方法名来自 __objc_methname
- (void)chargeAmount:(double)amount;         // 类型编码来自 __objc_methtype
@end
```

> 说明：`class-dump` 输出的 `@interface PaymentManager` 这一行里的 `PaymentManager`，正是从 `__objc_classname` 取的；冒号后的 `verifyReceipt:`/`chargeAmount:` 是方法名（`__objc_methname`），参数/返回值类型来自方法类型编码（`__objc_methtype`）。**三个字符串池拼起来 = 一份近似的头文件**——这就是 `__objc_classname` 作为逆向"切入点/富矿"的实操含义：拿到类名 → 还原接口 → 顺方法回到反汇编定位逻辑。

## 与相邻章节的关系

- [[36.Mach-O __objc_classlist节]]：类指针数组，runtime 遍历它做类注册；每个类沿 `bits → class_ro_t → name` 指回本节取类名。是"谁来用本节"的上游。
- [[24.Mach-O __objc_methname节]]：方法名（选择器名）字符串池，与本节**同构**（同为 `S_CSTRING_LITERALS`），被 `method_t.name` 引用；和类名拼起来还原接口。
- [[26.Mach-O __objc_methtype节]]：方法类型编码字符串池，同样同构，被 `method_t.types` 引用；提供方法的参数/返回值类型。
- [[20.Mach-O __cstring节]]：通用 C 字符串池，与本节**节类型完全相同**（`S_CSTRING_LITERALS`、可去重、`strings` 可扫）；区别仅在节名语义——本节专供 ObjC 类名，是"为什么类名不直接放 `__cstring`"的对照。

## 小结

- `__objc_classname` 是 **ObjC 类名字符串池**——所有类名（含 Swift 桥接类的修饰名）以 NUL 结尾 C 串集中存放，只读位于 `__TEXT` 段。节类型是 `S_CSTRING_LITERALS`（`flags & 0xff = 0x2`），与 [[20.Mach-O __cstring节]] 完全一致，**享受链接器去重特权、`strings`/`otool` 可直扫**。
- 它与 [[24.Mach-O __objc_methname节]]、[[26.Mach-O __objc_methtype节]] 三者**同构**，区别仅在节名语义与"谁来引用"：本节被每个类的 **`class_ro_t.name` 指针**引用，类名本体在池里、`class_ro_t` 只存指针（类与元类还共享同一份）。
- **runtime 类注册**：dyld → `_objc_init` → `_read_images` 遍历 [[36.Mach-O __objc_classlist节]] 的类指针数组，对每个类沿 `class_ro_t.name` 取名，插进全局命名类表 `gdb_objc_realized_classes`（`NXMapTable`，名字→Class）。
- **按名查类**：`NSClassFromString` → `objc_getClass` → `getClass_impl` 就是去那张以本节字符串为键的哈希表里 `NXMapGet`；Swift 类用修饰名 `_TtC<模块长><模块><类长><类>` 存储，`class_getName` 返回反修饰后的点号名，两种名字 `objc_getClass` 都能查。
- **逆向富矿**：类名直接暴露业务模块、第三方 SDK 指纹、UI 层次；配合方法名/类型池可用 `class-dump`/`dsdump` 还原近似头文件。注意符号混淆、Swift `@objc` 收窄、运行时动态建类会让本节"看不到真名"。
