# 详解Mach-O(二十九)Mach-O __common节

> [!abstract] TL;DR
> **`__common` 存放 C 语言"暂定定义（tentative definition）"产生的未初始化外部全局符号**——即写在文件作用域、既不带 `static`、也不带初值的全局变量（典型如 `int g_counter;`）。它属于 [[14.Mach-O __DATA]] 段，节类型与 [[28.Mach-O __bss节]] 一样是 `S_ZEROFILL`（`0x1`，零填充、不占文件）。
> 它与 `__bss` 的**本质区别在符号语义，而非存储形式**：`__bss` 装的是已经"定型"的私有/已确定全局零数据（`static int x;`），`__common` 装的是**外部可见、尚待链接器合并**的暂定定义——多个目标文件可以各写一份 `int g;`，链接器不报"重复定义"，而是**合并为一处、大小取最大者、对齐取最严者**（这是 COMMON 符号区别于普通符号的核心规则）。
> 暂定定义这一行为受编译选项 `-fcommon`/`-fno-common` 控制。**GCC 10、Clang 11 起默认 `-fno-common`**：暂定定义被当作普通定义、直接进 `__bss`，同名重复定义直接报链接错误。因此 **`__common` 在当代二进制里已相当罕见**——要复现它，往往得显式 `-fcommon` 编译。读懂 `__common` 的关键，是理解"C 暂定定义 → COMMON 符号 → 链接器合并 → 落进零填充节"这条从语言规则到二进制布局的完整链路。

## 概述与定位

C 语言有一条容易被忽视的历史规则：**在文件作用域写下 `int g;`（无初值、无 `static`、无 `extern`）不是普通定义，而是"暂定定义"**。这意味着同一个 `int g;` 允许在多个翻译单元（`.c` 文件）里各出现一次，链接时这些同名暂定定义会被合并成同一个符号，而**不会**触发"重复定义"错误。承载这类符号的容器，传统上就是 `__common` 节。

把它放进 [[18.Mach-O section]] 建立的节模型里看：`__common` 的节类型（`flags & SECTION_TYPE`）是 `S_ZEROFILL`，和 [[28.Mach-O __bss节]] 完全相同——都是"零填充、不占文件"的内存占位节，都住在 `rw-` 权限的 [[14.Mach-O __DATA]] 段里。从"占不占磁盘、运行时怎么来"的角度，二者一模一样；它们的分野**纯粹在符号的链接语义上**：

- **`__bss`**：装"**已经定型**的未初始化数据"——文件内私有的 `static` 变量，或已被确定为本文件唯一定义的全局零数据。它们**没有"待合并"问题**，地址与大小在编译单个 `.o` 时就基本敲定。
- **`__common`**：装"**尚待合并**的暂定定义"——外部可见、可能在别的 `.o` 里还有同名兄弟、也可能在别处被一个带初值的真定义覆盖。它们的最终归宿（地址、大小、甚至是否被覆盖）**要等链接器做完符号解析才确定**。

一句话定位：**`__bss` 是"私有/已定型的零数据"，`__common` 是"外部可合并的零数据（暂定定义）"。** 这也是 Apple 官方 Mach-O 文档的明确分工——*"未初始化的 static 数据在 `__DATA` 段的 `__bss` 节；符合 ANSI C「暂定定义」、未声明为 `extern` 的符号在 `__DATA` 段的 `__common` 节。"*

> [!note] 为什么"暂定定义"是 C 特有、且 C++ 没有
> C++ 没有暂定定义这一概念：在 C++ 里 `int g;` 就是一个**确定的定义**，同名在多个翻译单元出现即违反 ODR（单一定义规则）、直接报重复定义。暂定定义是 C 从早期 Unix 编译器继承下来的"宽松"语义，本质是为了兼容 Fortran COMMON 块那种"多处声明、链接合并"的历史用法。正因为它**不符合 C++、也不符合 C 标准对"定义"的直觉**，现代工具链才用 `-fno-common` 把它收紧（详见第 4 节）。

## 核心原理与字段详解

### 1. C 的"暂定定义"规则：`__common` 的语言学源头

要讲清 `__common`，得先讲清它装的东西从哪来。C 标准把文件作用域的对象声明分成三类，区别只在"有没有初值、有没有 `extern`"：

| C 写法（文件作用域） | 标准术语 | 含义 | 典型归宿 |
|---|---|---|---|
| `int g = 42;` | **外部定义**（带初值） | 唯一、确定的定义，分配存储并赋初值 | `__data`（见 [[27.Mach-O __data节]]） |
| `int g;` | **暂定定义**（tentative definition） | 无初值、无 `static`、无 `extern`；可在多 TU 各写一次，链接合并 | `__common`（`-fcommon`）/ `__bss`（`-fno-common`） |
| `extern int g;` | **声明**（非定义） | 只声明、不分配存储，承诺"定义在别处" | 不产生符号存储，只产生引用 |
| `static int g;` | **内部定义** | 文件内私有（internal linkage），无合并问题 | `__bss`（未初始化）/ `__data`（带初值） |

暂定定义的两条标准语义是 `__common` 存在的全部理由：

1. **同一 TU 内可重复**：一个文件里写 `int g; int g;` 合法（仍是同一个暂定定义），只要别处没给它带初值的真定义，翻译单元结束时它就**等价于 `int g = 0;`**——这就是"未初始化全局变量初值为 0"的来源（C 标准对静态存储期对象的零初始化规定）。
2. **跨 TU 可合并**：不同 `.c` 文件各写一份 `int g;`，传统 Unix 链接器**不报错、合并为一**。这正是 COMMON 符号机制要解决的问题。

> [!note] "未初始化全局变量值为 0"是标准保证，不是巧合
> `int g;` 在运行时一定读到 0，是 C 标准对**静态存储期**对象的强制规定（指针型则为空指针、浮点为正零、聚合体逐成员零初始化）。`__common`/`__bss` 用"零填充、运行时由内核清零"来落实这条规定，所以它们**不必把这些零字节真的存进文件**——这是"用零换体积"的根基，与 [[28.Mach-O __bss节]] 同理。

### 2. `__common` 存什么：未初始化的"外部"全局符号

把第 1 节落到 Mach-O：**编译器看到一个暂定定义（且处于 `-fcommon` 模式）时，就为它生成一个 COMMON 符号**，而不是一个普通的已定义符号。这个 COMMON 符号的特别之处在于——它携带的是 `(名字, 大小, 对齐)`，但**还没有确定的节内地址**，因为编译器此刻还不知道别的 `.o` 里会不会有同名兄弟、谁的尺寸更大。

只有当链接器把所有 `.o` 拼起来、做完符号解析、确认这个 COMMON 符号最终没有被任何带初值的真定义覆盖时，它才会被**转成一个真正的已定义符号，落进输出文件的 `__common` 节**（一块零填充区域）。因此可以说：

- 在**未链接的 `.o`（`MH_OBJECT`）** 里，暂定定义表现为 COMMON 符号（`nm` 标 `C`，见第 6 节），通常**还没有 `__common` 节实体**，只是符号表里一条带大小/对齐的 COMMON 记录。
- 在**已链接的最终产物**里，残留的 COMMON 符号被链接器"定型"成 `__common` 节里的实际零填充条目（`nm` 标变为 `S` / `b` 之类，落到具体节）。

`__common` 里**只放外部可见的暂定定义**，文件内 `static` 的未初始化变量从一开始就是确定的、走 `__bss`，不经过 COMMON 这条路。

### 3. 链接器如何合并同名暂定定义：取最大 size、取最严 align

这是 COMMON 符号区别于一切普通符号的**标志性规则**，也是面试与逆向常考点：

**规则一：同名 COMMON 不算冲突，合并为一。** 普通已定义符号同名 = 重复定义错误；但**多个同名 COMMON 符号合并成一个，不报错**。这是 COMMON 符号"宽松"的本质。

**规则二：大小取最大者（max size）。** 若 `a.c` 写 `char g;`（1 字节）、`b.c` 写 `int g;`（4 字节），合并后 `g` 的大小**取 4 字节**。Mach-O 的 ld64 也遵循同一约定——*"由尺寸最大的那份决定（对齐）"*。

**规则三：对齐取最严者（max alignment）。** 多份 COMMON 的对齐要求不一致时，合并结果取**最严格**（最大）的对齐。在符号层面，COMMON 符号的"对齐"被编码进符号记录（ELF 里放 `st_value`、Mach-O 里放 `nlist` 的 `n_desc`，均以 2 的幂表示），不是地址。

**规则四：真定义胜出（defined > tentative > undefined）。** 链接器的符号优先级是**已定义符号 > 暂定符号 > 未定义符号**。所以一旦某 TU 提供了带初值的真定义 `int g = 42;`，它**压过**所有同名暂定定义——`g` 取该真定义的值、落进 `__data`，所有暂定份额被丢弃。

> [!warning] `-fcommon` 下"暂定定义被静默覆盖"是真实的坑
> 规则四有个危险后果：你在 `a.c` 写 `int g;`、以为它初值为 0，而别人在 `b.c` 写了 `int g = 1;`——`-fcommon` 下链接器**默默用 `=1` 覆盖**你的暂定定义，`a.c` 读到的 `g` 是 1 而非 0，且**没有任何报错**。GNU `ld`/`lld` 的 `--warn-common`、以及现代默认的 `-fno-common`，正是为堵这个坑而生（详见第 4 节）。

> [!note] Mach-O 特有：`-commons` 决定暂定定义如何与 dylib 交互
> Apple 链接器 ld64 有个 `-commons` 选项，控制暂定定义与动态库（dylib）的关系，三种取值：`ignore_dylibs`（**默认**——直接把 `.o` 里的暂定定义转成真定义，**不去 dylib 里查冲突**）、`use_dylibs`（去已链接 dylib 里找定义来替换暂定定义）、`error`（暂定定义与 dylib 里的外部符号冲突时报错）。另有历史约束：**ld 默认构建的多模块共享库不能含 COMMON 符号**——要消除它，要么给该符号一个带初值的真定义，要么直接用 `-fno-common` 编译。

### 4. `-fcommon` 与 `-fno-common`：现代默认翻转，`__common` 走向罕见

暂定定义到底变成 COMMON 符号（进 `__common`）还是普通已定义符号（进 `__bss`），由编译选项决定。这里有一次**影响深远的默认值翻转**：

| 选项 | 行为 | 同名重复定义 | 暂定定义归宿 | 默认时期 |
|---|---|---|---|---|
| `-fcommon` | 暂定定义 → **COMMON 符号**，允许链接器合并同名 | **不报错**（合并，可能被真定义静默覆盖） | `__common` | GCC ≤ 9、Clang ≤ 10 的传统默认 |
| `-fno-common` | 暂定定义 → **普通已定义符号**，禁止合并 | **报"multiple definition"链接错误** | 直接进 `__bss` | **GCC 10+、Clang 11+ 的现代默认** |

**默认值翻转的来龙去脉**：

- 历史上 GCC/Clang 对 C 默认 `-fcommon`，沿袭传统 Unix 编译器"暂定定义可跨 TU 合并"的宽松行为——但这**既不符合 C 标准、也不符合 C++**。
- **GCC 自 10、Clang 自 11 起把默认改为 `-fno-common`**。Clang 这一改动（LLVM 评审 D75056）的官方理由是：`-fno-common` **有性能与代码体积收益、对 C 更符合标准、且与 GCC 10 行为一致**。
- 翻转的直接后果：那些"在头文件里漏写 `extern`、导致多个 `.c` 各定义一份同名全局变量"的老代码，过去靠 `-fcommon` 默默合并、能链接通过，现在会**报 multiple-definition 链接错误**。这是 GCC 10 / Clang 11 升级后最常见的破坏性变化之一。

**正确的修法（而非退回 `-fcommon`）**：在头文件里用 `extern int g;` 声明全局变量，并**确保该变量在且仅在一个 `.c` 文件里有定义**（最好给个显式初值，哪怕是 `int g = 0;`，以彻底避开"暂定陷阱"）。只有在无法立刻改源码时，才用 `-fcommon` 作临时回退。

> [!note] 为什么"现代二进制里 `__common` 罕见"
> 把上面串起来：现代默认 `-fno-common` ⇒ 编译器不再为暂定定义生成 COMMON 符号 ⇒ 它们直接当普通定义进 `__bss` ⇒ 链接产物里**根本不产生 `__common` 节**。所以你在今天用 `clang`（Apple/上游均 ≥ 11）默认编出来的 macOS/iOS 二进制里，**多半看不到 `__common`**。要亲眼看到它，需显式 `-fcommon` 编译，或分析老工具链产出的旧二进制。换句话说，`__common` 更多是一段**需要理解、但日渐少见**的历史机制。

### 5. 与 `__bss` 的语义区别：一张对照表说清

`__common` 和 `__bss` 长得像（都 `S_ZEROFILL`、都不占文件、都在 `__DATA`），最容易混。把区别钉死在"符号语义"这一维：

| 维度 | `__bss`（见 [[28.Mach-O __bss节]]） | `__common`（本篇） |
|---|---|---|
| 节类型（`flags & SECTION_TYPE`） | `S_ZEROFILL`（`0x1`） | `S_ZEROFILL`（`0x1`）——**相同** |
| 占文件吗 | 否，零填充、运行时清零 | 否，零填充、运行时清零——**相同** |
| 宿主段 | [[14.Mach-O __DATA]]（`rw-`） | [[14.Mach-O __DATA]]（`rw-`）——**相同** |
| 装什么符号 | 已**定型**的未初始化数据：`static` 私有变量、已确定的全局零数据 | **暂定定义**：外部可见、未初始化、未带初值、未 `static` 的全局变量 |
| 链接语义 | 无合并问题，编译期基本定型 | **可被链接器合并同名**（max size / max align），**可被真定义覆盖** |
| 同名跨 TU | `static` 各自独立；非 static 同名即冲突 | 同名 COMMON **合并为一、不报错** |
| `nm` 标记 | `b`（局部）/ `B`（全局）BSS | `.o` 里标 `C`/`c`（common），链接后定型 |
| 是否随现代默认消失 | 否，`__bss` 一直在用 | **是**，`-fno-common` 默认下并入 `__bss`，故罕见 |

> [!note] 一句话记牢
> **类型、存储、宿主段三者，`__common` 和 `__bss` 完全一样；唯一的差别在符号语义——`__bss` 是"私有/已定型的零数据"，`__common` 是"外部可合并、待链接器定型的暂定定义"。** 现代 `-fno-common` 把后者也并进前者，所以 `__common` 越来越像一个"理论上存在、实际少见"的历史分类。

> [!note] 架构无关，只与编译选项有关
> `__common` 的零填充、对齐特性与 CPU 架构无关（arm64 / x86_64 表现一致），其对齐随所在零页大小（arm64 16KB / x86_64 4KB）协同。**它是否出现，取决于编译选项（`-fcommon` vs `-fno-common`）而非架构**——这点与 [[18.Mach-O section]] 里多数节"行为随架构变"不同。

### 6. `nm` 如何显示 COMMON 符号：`C` / `(common)`

逆向时识别暂定定义，靠 `nm` 的符号类型字母最直接：

- **`C` / `c`**：COMMON 符号（common，未初始化数据）。`nm` 文档明确："the symbol is common，common symbols are uninitialized data"；大写 `C` 表外部（全局），小写 `c` 表局部。
- **`B` / `b`**：位于 BSS 节的符号（未初始化/零初始化）。大写全局、小写局部。
- **`D` / `d`**：位于已初始化 `data` 节的符号（带初值）。

一个关键现象：**同一个未初始化全局变量，在未链接的 `.o` 里常显示为 `C`（common），链接成可执行文件后会变成 `B`（落 BSS）或 `D`（若别处有带初值真定义）**——这正是"COMMON 符号在链接期被定型"的外在表现，和第 2、3 节的机制对得上。

Apple 平台上还有 **`nm -m`** 这个 Mach-O 专用格式：它把落在 `__common` 的符号显示为 **`(common)`**，并附带该符号的对齐（编码在 `nlist` 的 `n_desc` 里，同样以 2 的幂表示）。

## 实操：用工具查看

由于现代默认 `-fno-common`，**直接编译多半得不到 `__common`**；下面给出"显式 `-fcommon` 复现 → 用工具观察"的完整路径。

```bash
# 1) 故意制造两个 TU 的同名暂定定义，并用 -fcommon 复现 __common（现代默认不会生成它）
#    a.c: int g_counter;          // 暂定定义
#    b.c: int g_counter;          // 同名暂定定义
clang -fcommon -c a.c -o a.o
clang -fcommon -c b.c -o b.o
clang -fcommon a.o b.o -o a.out  # 链接器合并同名暂定定义为一处

# 2) 看 __common 节头（已链接产物里链接器定型出的零填充节）
otool -l a.out | grep -A 6 "sectname __common"

# 3) 看 .o 里暂定定义被标为 (common)；以及对照"链接后变 B/D"
nm -m a.o | grep g_counter        # 未链接：常见 (common)
nm a.out  | grep g_counter        # 已链接：定型为 B（BSS）或 D（若有真定义）

# 4) 对照实验：默认 -fno-common 下，同名暂定定义会直接报重复定义链接错误
clang -c a.c -o a.o && clang -c b.c -o b.o && clang a.o b.o -o a.out
#   => ld: multiple definition of '_g_counter'   （现代默认行为）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识与权威文档构造，**实际数值、对齐、是否出现 `__common` 均以你机器上的 `otool`/`nm` 为准**（尤其取决于你的 `clang` 版本与是否加 `-fcommon`）。

`otool -l` 看 `__common` 节头（注意它和 `__bss` 一样是 `S_ZEROFILL`、`offset` 不指真实文件数据）：

```text
Section
  sectname __common
   segname __DATA
      addr 0x000000010000c020      ; 落在 __DATA 段范围内
      size 0x0000000000000040      ; 合并后大小 = 同名暂定定义里的最大者（这里 64 字节）
    offset 0                       ; S_ZEROFILL：不指向真实文件字节
     align 2^2 (4)                 ; 对齐取最严者；存储值 align=2，实际 4 字节
    reloff 0
    nreloc 0
     flags 0x00000001              ; 类型 = S_ZEROFILL（&0xff=0x1），与 __bss 同类型
 reserved1 0
 reserved2 0
 reserved3 0
```

> 说明：`flags 0x00000001` 拆开 = 类型 `S_ZEROFILL`（`&0xff=0x1`）、无附加属性——与 [[28.Mach-O __bss节]] 的节类型**完全一致**；`offset 0` + `S_ZEROFILL` 表示文件里不存它的字节、运行时由内核清零；`size 0x40` 体现"合并取最大 size"的结果。判断它是不是零填充、要不要从磁盘读，**看类型 `S_ZEROFILL` 而不是 `offset` 是否为 0**（这条与 [[18.Mach-O section]] 对 zerofill 的判定一致）。

`nm -m` 看暂定符号被标为 `(common)`：

```text
# nm -m a.o  （未链接的 .o：暂定定义显示为 common，前面是对齐而非地址）
0000000000000004 (common) _g_counter   ; (common) 标记 + 对齐编码（这里 4 字节对齐）

# nm a.out   （已链接：同一符号被定型，落入 BSS 显示为 B；若别处有带初值真定义则显示 D）
000000010000c020 B _g_counter
```

> 说明：未链接 `.o` 里 `_g_counter` 标 `(common)`、前缀是**对齐值**（非地址，符合 COMMON 符号"value 字段存对齐"的约定）；链接成可执行后，它被链接器定型、落进 BSS，`nm` 改标 `B` 并给出真实地址——这就是"COMMON 符号链接期定型"的可观测证据，印证第 2、6 节。

## 与相邻章节的关系

- [[28.Mach-O __bss节]]：同为 `S_ZEROFILL`、零填充不占文件的未初始化数据节；二者**类型/存储/宿主段全同，仅符号语义不同**（`__bss` 私有/已定型，`__common` 外部可合并）。`-fno-common` 默认下暂定定义并入 `__bss`，是 `__common` 罕见的直接原因。
- [[27.Mach-O __data节]]：带初值的可写数据节，占文件。**真定义（`int g = 42;`）胜过暂定定义**时，符号落 `__data` 而非 `__common`，是符号优先级"已定义 > 暂定"的体现。
- [[14.Mach-O __DATA]]：`__common` 的宿主段（`rw-`）；它和 `__bss` 一样是 `__DATA` 段 `vmsize > filesize` 的成因之一（零填充计内存、不计文件）。
- [[18.Mach-O section]]：节通用模型与 `flags` 类型位的"公共字段说明书"；`__common` 只是 `S_ZEROFILL` 类型的一个具体实例。

## 小结

- `__common` 存 **C 暂定定义**（文件作用域、无初值、无 `static`、无 `extern` 的全局变量，如 `int g;`）产生的**未初始化外部全局符号**；编译器把暂定定义编为 **COMMON 符号**，链接器在符号解析后将残留的 COMMON 定型进 `__common` 节。
- 节类型是 `S_ZEROFILL`（`0x1`），与 [[28.Mach-O __bss节]] **完全相同**：零填充、不占文件、运行时由内核清零，住在 [[14.Mach-O __DATA]] 段。
- 链接器对同名暂定定义的处理：**合并为一、大小取最大者、对齐取最严者、不报重复定义**；但**带初值的真定义会覆盖暂定定义**（优先级：已定义 > 暂定 > 未定义），覆盖后符号改落 [[27.Mach-O __data节]]。
- 与 `__bss` 的**唯一本质区别在符号语义**：`__bss` = 私有/已定型的零数据；`__common` = 外部可见、待链接器合并的暂定定义。
- 受 `-fcommon`/`-fno-common` 控制：**GCC 10、Clang 11 起默认 `-fno-common`**，暂定定义直接进 `__bss`、同名重复即报错，故 **`__common` 在当代二进制里罕见**，需显式 `-fcommon` 才易复现。
- 识别：`nm` 里 COMMON 符号标 **`C`/`c`**（`.o` 中），链接后定型为 `B`（BSS）或 `D`（有真定义）；Apple 的 `nm -m` 显示为 **`(common)`** 并附对齐。
