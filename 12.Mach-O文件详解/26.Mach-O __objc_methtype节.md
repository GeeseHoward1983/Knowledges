# 详解Mach-O(二十六)Mach-O __objc_methtype节

> [!abstract] TL;DR
> **`__objc_methtype` 节存放 Objective-C 方法的"类型编码"（type encoding）字符串**——用一串紧凑的 ASCII 字符，把方法的「返回值类型 + 所有参数类型」压缩描述出来。例如 `v@:@` 一眼读作"返回 `void`，隐含 `self`（`@`）、隐含 `_cmd`（`:`），外加一个对象参数（`@`）"。这串编码就是 C `@encode()` 指令在编译期对方法签名的"快照"。
> 它与 [[24.Mach-O __objc_methname节]]（方法名）、[[25.Mach-O __objc_classname节]]（类名）是同段并列的三个 **ObjC 只读字符串池**，都住在只读可执行的 `__TEXT` 段（权限 `r-x`），底层和 [[20.Mach-O __cstring节]] 一样是"一串以 `\0` 分隔的 C 字符串"，区别只在于装的内容专门是类型编码、并打了独立的节名以便 runtime 按用途取用。
> **谁引用它**：每个方法的 `method_t` 结构体里有一个 `types` 字段，是个指针，直指本节内的某条编码字符串——`__objc_methname` 给出方法叫什么名字（selector），`__objc_methtype` 给出这个方法长什么样（签名），两者一一配对，共同把一个方法描述完整。
> **runtime 拿它干什么**：凡是"只知道 selector、却需要知道方法精确签名"的动态场景都靠它——消息转发（`methodSignatureForSelector:` + `forwardInvocation:`）、`NSInvocation` 的参数布局与取值、`NSMethodSignature` 的构造、KVC、`NSCoding` 归档、桥接与反射。逆向时它帮你把被剥离符号的方法**还原出原型**（参数几个、各是什么类型、返回什么）。
> 一句话：`__cstring` 是给人和 C 库读的明文文案，`__objc_methtype` 是给 **ObjC runtime 读的"方法形状说明书"**。

## 概述与定位

Objective-C 是一门**动态语言**：方法调用走的是消息发送（`objc_msgSend`），运行时经常处在"我手上只有一个 selector（方法名），但我得知道这个方法接收几个参数、每个参数什么类型、返回值什么类型"的局面。**类型编码（type encoding）就是把 C 的类型系统压缩成一行字符串的方案**，而 `__objc_methtype` 节正是这些方法签名编码的集中存放处。它在 Mach-O 的层级里处于这样的位置：

- 它继承 [[13.Mach-O __TEXT]] 段的**只读、可执行**属性（`r-x`）——类型编码是编译期定死的常量元数据，运行期绝不应被改，放进只读段恰如其分，也让多个进程共享同一份物理页。
- 它是 [[18.Mach-O section]] 通用模型里一个**具体的字符串节**：和 [[20.Mach-O __cstring节]] 同构（一串以 `\0` 分隔、首尾相接的 C 字符串），`section_64` 结构相同，区别只在 `sectname` 为 `__objc_methtype`、内容专装类型编码。
- 它与 [[24.Mach-O __objc_methname节]]、[[25.Mach-O __objc_classname节]] 是**三胞胎 ObjC 字符串池**：方法名、类名、方法类型各占一节，被切开是为了让 runtime 和工具能按"这是哪类元数据"精准取用，而不必在一锅大字符串里靠语义猜。

一句话定位：**`__objc_methtype` = `__TEXT` 段里、专门存放 Objective-C 方法「类型编码字符串」的只读节，补全了"方法名 + 方法签名"这对核心元信息中的"签名"一半**。

> [!note] 它和 `__cstring` 什么关系？为什么不直接塞进 `__cstring`？
> 物理形态上，`__objc_methtype` 和 [[20.Mach-O __cstring节]] 一模一样——都是"一串以 `\0` 收尾、紧凑排布的 C 字符串"，理论上把 `v@:@` 当成普通字符串扔进 `__cstring` 也能存。**之所以单切一节，是为了"按用途分类"**：① runtime 加载类时要批量解析方法表的 `types`，独立成节让它能直接定位、不必在海量明文文案里大海捞针；② 工具（`otool -ov`、class-dump、Hopper）能据节名一眼分辨"这堆字符串是方法签名而非提示文案"；③ 便于链接器/优化器对这类专用字符串单独做去重与排布。和 `__objc_methname`（存方法名）、`__objc_classname`（存类名）一样，都是"内容本是 C 字符串、但因语义专门而独立成节"的设计。

> [!note] type encoding 不只用于方法签名
> `__objc_methtype` 里装的是**方法的**类型编码，但同一套编码方案（`@encode()`）用途更广：**属性的 `@property` 特性串**（如 `T@"NSString",&,V_foo`）、**实例变量（ivar）的类型**、**协议方法描述** 都用它。换句话说，你在别处（如 `__objc_const` 里的属性表、ivar 表）也会看到同样风格的编码字符。本篇聚焦"方法签名"这一最典型用法，但读懂这套字符表，到处都能用。

## 核心原理与字段详解

### 1. 类型编码是什么：把 C 类型系统压成一行字符

为了协助 runtime，**编译器把每个方法的返回类型与各参数类型编码成一个字符串，并与方法的 selector 关联起来**。这套编码方案同样以 `@encode()` 编译器指令公开：给它一个类型，它返回该类型的编码字符串（如 `@encode(int)` → `"i"`、`@encode(double)` → `"d"`），凡是能作为 C `sizeof()` 操作数的类型——基本类型、指针、结构体、联合、类名——都能被编码。

类型编码的精髓是**绝大多数类型就是一个单字符**：`int` 是 `i`、`double` 是 `d`、`void` 是 `v`、对象是 `@`、SEL 是 `:`。少数复合类型（数组、结构体、联合、指针、带类名的对象）才用多字符或带括号的形式展开。

### 2. 完整的 type encoding 字符表

这是读懂本节内容的**核心速查表**，整理自 Apple《Type Encodings》文档（Objective-C Runtime Programming Guide）。建议对照记忆：

| 编码 | C/ObjC 类型 | 备注 |
|---|---|---|
| `c` | `char` | 有符号字符；注意 `BOOL` 在很多平台被编码为 `c`（历史上 `BOOL` 即 `signed char`） |
| `i` | `int` | |
| `s` | `short` | |
| `l` | `long` | **在 64 位程序里也按 32 位量处理**（历史约定） |
| `q` | `long long` | 64 位整型；`NSInteger` 在 64 位上常编码为 `q` |
| `C` | `unsigned char` | |
| `I` | `unsigned int` | |
| `S` | `unsigned short` | |
| `L` | `unsigned long` | 同样按 32 位量处理 |
| `Q` | `unsigned long long` | `NSUInteger` 在 64 位上常编码为 `Q` |
| `f` | `float` | |
| `d` | `double` | **`long double` 也返回 `d`**（ObjC 不单独支持 `long double`） |
| `B` | `bool` / `_Bool` | C++ `bool` 或 C99 `_Bool` |
| `v` | `void` | 最常见的返回类型编码 |
| `*` | `char *` | C 字符串指针 |
| `@` | 对象（`id` 或某类实例） | 见下条：指定类时写作 `@"NSString"` |
| `#` | `Class` | 类对象本身（元类引用） |
| `:` | `SEL` | 方法选择器；方法签名里紧跟 `self` 之后那一位 |
| `[N type]` | 数组 | 如 `[12^f]` = 12 个 `float*` 的数组（元素数写在类型前） |
| `{name=types...}` | 结构体 | 如 `{CGSize=dd}`、`{CGRect={CGPoint=dd}{CGSize=dd}}`（递归展开） |
| `(name=types...)` | 联合体 union | 圆括号包裹，成员依次列出 |
| `b N` | 位域 bit field | `bN` 表示 N 位的位域 |
| `^type` | 指向 type 的指针 | 如 `^i` = `int*`、`^@` = `id*`、`^v` = `void*` |
| `?` | 未知类型 | 典型用于**函数指针**；块（block）编码为 `@?` |
| `@?` | 块（block） | "对象 + 函数指针"组合；**不含**块的参数/返回类型信息 |
| `@"ClassName"` | 指定类的对象 | 如 `@"NSString"`、`@"NSArray"`，类名带双引号 |

几条容易踩坑的细节，单独强调：

- **对象 `@` vs 指定类 `@"NSString"`**：纯 `id` 编码为 `@`；静态类型的对象会**把类名加引号附在后面**，如 `NSString *` 编码为 `@"NSString"`。这一点在逆向时极有价值——它直接告诉你参数的具体类，而不只是"某个对象"。
- **块是 `@?`**：块被当对象看待，但其编码**不携带**块的参数和返回类型信息，统一是 `@?`（"对象" `@` + "函数指针/未知" `?` 的组合）。官方老表没覆盖块，这是 clang 源码 `ASTContext::getObjCEncodingForTypeImpl` 里的实际行为。
- **结构体递归展开**：`CGRect` 编码为 `{CGRect={CGPoint=dd}{CGSize=dd}}`——外层结构体里嵌内层结构体，逐层用 `{name=...}` 展开。C++ 复杂类型会让编码变得**很长**，显著增大二进制体积（这是 `__objc_methtype` 有时意外膨胀的原因）。
- **`@encode` 与 runtime 略有差异**：`@encode` 指令返回的编码可能和 runtime（如 `ivar_getTypeEncoding`）返回的**略有不同**——比如结构体成员名，`@encode` 不加、runtime 会加。比较两份编码时要留意这点。

> [!note] 类型限定符（type qualifier）：`@encode` 不返回、协议里才出现
> 除上表外，runtime 还为**协议中声明方法**时用的**类型限定符**保留了一组前缀编码，但 `@encode()` 指令本身**不会**返回它们：`r`（const）、`n`（in）、`N`（inout）、`o`（out）、`O`（bycopy）、`R`（byref）、`V`（oneway）。这些（`in`/`out`/`inout`/`bycopy`/`byref`/`oneway`）是 **Distributed Objects（分布式对象）** 这一进程间消息协议的遗产——当年 Cocoa 应用甚至能跨网络机器互发消息，需要标注参数的传递方向与拷贝语义。今天它们罕见，但在某些协议方法的编码里仍可能出现（如 `oneway void` 编码带 `V` 前缀），逆向时见到别当成乱码。

### 3. 方法签名的拼装规则：返回类型 + self(`@`) + SEL(`:`) + 各参数 + 偏移数字

方法签名编码**不是**把参数随便拼一起，而是有固定的排列顺序和可选的偏移数字。规则如下：

**第一步——排列顺序**：`返回类型` + `self` + `_cmd` + `参数1` + `参数2` + …

- **返回类型**打头。
- 紧跟两个**隐含参数**：每个 ObjC 方法都隐式接收 `self`（接收者对象，编码 `@`）和 `_cmd`（被调用的 selector，编码 `:`）作为前两个参数——**这就是为什么几乎所有方法编码都以 `…@:…` 起头**。
- 然后才是源码里显式写出的参数，依次排列。

举例（先不看偏移数字）：

| ObjC 方法声明 | 编码（无偏移形式） | 拆解 |
|---|---|---|
| `- (void)foo` | `v@:` | `v`=void 返回；`@`=self；`:`=_cmd |
| `- (NSInteger)count` | `q@:` | `q`=long long 返回；`@`=self；`:`=_cmd（64 位 `NSInteger`→`q`） |
| `- (void)setName:(NSString *)n` | `v@:@` | `v`=void；`@`=self；`:`=_cmd；末 `@`=对象参数 |
| `- (id)objectAtIndex:(NSUInteger)i` | `@@:Q` | `@`=返回对象；`@`=self；`:`=_cmd；`Q`=unsigned long long 参数 |
| `- (CGRect)bounds` | `{CGRect={CGPoint=dd}{CGSize=dd}}@:` | 结构体返回；self；_cmd |

**第二步——偏移数字（offset numbers）**：在每个类型字符后面，编码里**常附带一个十进制数字**，且在返回类型后还有一个"总帧大小"数字。完整形式形如 `v24@0:8@16`，逐段读：

| 片段 | 含义 |
|---|---|
| `v` | 返回类型 = `void` |
| `24` | **参数帧（argument frame）总大小 = 24 字节** |
| `@0` | 第 1 个参数是对象（`self`），位于**偏移 0** |
| `:8` | 第 2 个参数是 SEL（`_cmd`），位于**偏移 8** |
| `@16` | 第 3 个参数是对象（要设置的新值），位于**偏移 16** |

在 64 位系统上指针各占 8 字节，所以偏移按 0 → 8 → 16 递进，总帧 24。**这套 `v24@0:8@16` 就是一个标准 setter 的完整编码**（与之对应，`@property NSString *foo` 还会生成 getter 的 `@16@0:8`、ivar 的 `@"NSString"`、property 特性串 `T@"NSString",&,V_foo` 共四条）。再如返回 `CGRect` 的 getter：`{CGRect={CGPoint=dd}{CGSize=dd}}16@0:8`——结构体类型 + 帧大小 16 + self`@0` + _cmd`:8`（getter 无显式参数）。

> [!note] 偏移数字今天基本是"装饰"，类型字符才是主角
> 这些偏移源自早期消息分发机制需要按字节布局参数帧的年代。**在现代 ObjC runtime 里，偏移数字大多已是 vestigial（退化遗留），真正起作用的是类型字符本身**——introspection、`respondsToSelector:` 配对、消息转发判定，看的都是 `v@:@` 这层类型信息。所以你常会看到两种写法：带偏移的 `v24@0:8@16`（runtime 实际存储/生成）和不带偏移的 `v@:@`（很多文档、`class_addMethod` 调用、人工书写时用）。**两者描述的是同一个方法**，读编码时可以先把数字滤掉、只看字符串骨架。

> [!warning] 偏移数字依赖 ABI，跨架构会变
> 类型字符部分是纯文本、跨架构一致（`v@:@` 在 arm64 和 x86_64 上完全相同）；但**偏移/总帧数字反映栈帧与寄存器布局，会随 ABI 不同**（arm64 与 x86_64 的寄存器数量、对齐约定不一样）。解析偏移时必须以**目标架构的调用约定**为准，别把 x86_64 的偏移套到 arm64 上。

### 4. 谁引用它：`method_t.types` 指针

在 objc4 runtime 内部，每个方法由一个 `method_t` 结构体表示（定义在 `objc-runtime-new.h`），它有三个核心字段：

```c
struct method_t {
    SEL name;          // 方法名 → 指向 __objc_methname 里的 selector 字符串
    const char *types; // 类型编码 → 指向 __objc_methtype 里的签名字符串  ← 本节
    IMP imp;           // 函数实现地址 → 指向 __text 里的机器码
};
```

`types` 字段就是一个 `const char *`，**直指 `__objc_methtype` 节内的某条编码字符串**。这把"方法名 / 方法签名 / 方法实现"三件套串了起来：`name` 说它叫什么（来自 [[24.Mach-O __objc_methname节]]），`types` 说它什么形状（来自本节），`imp` 说它怎么执行。类的方法列表（`method_list_t`）由 [[36.Mach-O __objc_classlist节]] 指向的类元数据持有，runtime 加载类时会遍历这张表，逐条读出 `types` 来登记方法签名。

需要在运行时凭 selector 拿签名时，runtime 把这条 `types` 字符串喂给 `NSMethodSignature`：`+[NSMethodSignature signatureWithObjCTypes:]`（自 Leopard 起公开）能用一条编码串现造一个 `NSMethodSignature` 对象，再由它解析出"返回类型、参数个数、各参数类型与偏移"，供 `NSInvocation` 按布局摆放参数和取返回值。

### 5. runtime 用途场景：消息转发、NSInvocation、KVC、归档

凡是"只有 selector、却需要知道方法精确签名"的动态场景，都依赖本节的类型编码：

- **消息转发（message forwarding）**——这是最经典的用途。当对象收到一个自己不直接响应的消息，runtime 走转发流程：先调 `methodSignatureForSelector:` 要一个 `NSMethodSignature`（其内部就是一条类型编码，如 `"v@:@"`），用它把这次调用打包成一个 `NSInvocation`，再交给 `forwardInvocation:` 处理——你可以在这里把 invocation 重定向到别的对象（`invokeWithTarget:`），或最终 `doesNotRecognizeSelector:` 兜底。**没有正确的类型编码，runtime 就不知道该给 `NSInvocation` 分配多大参数帧、参数各在哪——转发无从谈起**。
- **`NSInvocation`**——它是"一次方法调用的快照对象"：目标、selector、各参数值、返回值，全是它的属性，且都可改、可重放、可改投到别的 target。它正是靠 `NSMethodSignature`（来自类型编码）来确定参数布局的。
- **KVC（键值编码）**——`setValue:forKey:` / `valueForKey:` 在动态存取属性时，需凭类型编码判断属性是对象还是标量（标量要装箱成 `NSNumber`/`NSValue`），从而正确读写。
- **归档（`NSCoding` / `NSKeyedArchiver`）**——序列化时要知道每个被编码值的类型，类型编码与归档用的编码字符**大量重叠**（但不完全相同：有些码归档能用、`@encode` 不生成，反之亦然）。
- **桥接与反射**——Swift/C 与 ObjC 互调、运行时动态构造调用、`libffi` 之类按签名生成 trampoline，都得先读类型编码确定调用约定。

> [!warning] 消息转发很慢，类型编码解析是其一环
> 转发链路代价高昂：即便目标对象响应该消息（快路径），也比直接派发慢约 20 倍；走到 `NSInvocation` 的慢路径更是约 100 倍。其中解析类型编码、构造 `NSMethodSignature`、按偏移摆放参数都要开销。这解释了为何转发只宜用于少量动态场景，不能放进热路径。

> [!note] 逆向价值：从编码还原方法原型
> 二进制被剥符号后，方法的人类可读原型丢失，但 `__objc_methname` + `__objc_methtype` 仍在。把两者配对，就能**重建方法签名**：`__objc_methname` 给 `setName:`，`__objc_methtype` 给 `v@:@`——合起来即 `- (void)setName:(id)arg`。这正是 class-dump、Hopper、IDA 的 ObjC 解析器还原头文件的原理。带 `@"NSString"` 这种指定类编码时，还能进一步还原出参数的具体类型而非泛泛的 `id`。

> [!note] 架构差异：字符跨架构一致，偏移随 ABI 变
> 类型编码的**字符骨架是文本、字节序无关**（`v@:@` 在 arm64 与 x86_64 上逐字节相同），跨架构不变。差异只在**附带的偏移/总帧数字**——它们反映栈帧布局，随 ABI（寄存器/对齐约定）不同。这与 [[18.Mach-O section]] 层面"内容字节序无关、仅地址随位宽变"的通用规律一致：同一份源码两架构编译，`__objc_methtype` 的字符串骨架一样，只是偏移数字与所处地址不同。

## 实操：用工具查看

### 示例 1：`otool -s __TEXT __objc_methtype` dump 节的原始字节

`otool -s 段名 节名` 以"地址 + 十六进制 + ASCII"逐行 dump 指定节内容，是看本节最直接的方式：

```bash
otool -s __TEXT __objc_methtype /path/to/ObjCBinary    # dump 原始字节（以 \0 分隔的编码串）
otool -V -s __TEXT __objc_methtype /path/to/ObjCBinary  # -V 尝试更可读地解析
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/字节仅示意 `otool -s` 的逐行格式，实际数值以你机器上的 `otool` 为准。

```text
ObjCBinary:
Contents of (__TEXT,__objc_methtype) section
0000000100003e00  76 40 3a 40 00 40 31 36 40 30 3a 38 00 76 32 34  v@:@.@16@0:8.v24
0000000100003e10  40 30 3a 38 40 31 36 00 71 40 3a 00              @0:8@16.q@:.
```

> 说明：左列是该行首字节的**虚拟地址**（从节 `addr` 起算）；中间是十六进制；右列是可打印 ASCII。可逐条读出 `\0` 分隔的编码：`v@:@\0`（返回 void、self、SEL、一个对象参数）、`@16@0:8\0`（带偏移的 getter：返回对象、帧 16、self@0、_cmd:8）、`v24@0:8@16\0`（带偏移的 setter）、`q@:\0`（返回 `long long`、self、_cmd，如某个 `count` 方法）。**首尾相接、各自以 `\0` 收尾**，这正是 ObjC 字符串池与 [[20.Mach-O __cstring节]] 同构的布局印证。

### 示例 2：`otool -ov` 解析 ObjC 元数据，看签名与方法名的配对

`otool -ov`（`-o` 打印 ObjC 运行时段、`-v` 展开）会把类、方法列表整理出来，**直接把方法名和它的类型编码并排展示**，比裸看字节直观得多：

```bash
otool -ov /path/to/ObjCBinary           # 打印 ObjC 类/方法元数据（含 name 与 types 配对）
otool -ov /path/to/ObjCBinary | grep -A3 "name 0x"   # 聚焦每个方法的 name/types 行
```

> [!warning] 示例输出为示意
> 下列为构造样例，仅示意 `otool -ov` 把 `method_t` 的 `name`(方法名) 与 `types`(类型编码) 并列呈现的格式，实际地址/内容以你机器上的 `otool` 为准。

```text
            baseMethods 0x100008010 (struct method_list_t *)
              entsize 24
              count 2
              name  0x100003d20 setName:
              types 0x100003e0d v24@0:8@16          ← setName: 的签名：void 返回，含对象参数
              imp   0x100002a40 -[MyView setName:]
              name  0x100003d28 count
              types 0x100003e25 q@:                 ← count 的签名：返回 long long，无显式参数
              imp   0x100002a80 -[MyView count]
```

> 说明：`name` 来自 [[24.Mach-O __objc_methname节]]（如 `setName:`、`count`），`types` 来自**本节**（如 `v24@0:8@16`、`q@:`），`imp` 指向 [[19.Mach-O __text节]] 里的实现。把 `name` 与 `types` 合读即可**还原方法原型**：`setName:` + `v24@0:8@16` → `- (void)setName:(id)arg`；`count` + `q@:` → `- (long long)count`。这就是 `method_t` 三字段在工具里的可视化呈现。

### 示例 3：用 `@encode()` 在源码侧反推编码，对照本节内容

不想反汇编、只想确认"某个类型/签名编码长什么样"时，最快的办法是写几行 ObjC 用 `@encode()` 现场打印，再拿结果对照本节 dump 出的字节：

```objc
NSLog(@"%s", @encode(int));                 // i
NSLog(@"%s", @encode(NSString *));          // @"NSString"
NSLog(@"%s", @encode(void (^)(int)));       // @?           (块统一编码，丢参数信息)
NSLog(@"%s", @encode(CGRect));              // {CGRect={CGPoint=dd}{CGSize=dd}}
// 取某方法的完整签名（带偏移）：
Method m = class_getInstanceMethod([NSString class], @selector(hasPrefix:));
NSLog(@"%s", method_getTypeEncoding(m));    // 形如 B24@0:8@16 (返回 BOOL/c-or-B, 一个对象参数)
```

> [!warning] 示例输出为示意
> 上方注释里的编码为基于规则推断的典型结果，**不同 SDK 版本/架构下偏移数字与个别字符可能不同**（如 `BOOL` 在某些平台编码为 `c` 而非 `B`）。以你本机实际运行 `@encode()` / `method_getTypeEncoding()` 的输出为准。

> 说明：`@encode(类型)` 给出**单个类型**的编码，`method_getTypeEncoding(Method)` 给出**整条方法签名**（带偏移，等价于 `__objc_methtype` 里那条 `types`）。两者结合，既能逐字符验证上文字符表，又能把"源码方法 → 编码字符串"的映射对上号，是理解本节内容最直接的实验手段。

## FAQ

> [!question] `v@:` 到底怎么读？为什么几乎每个方法都以 `@:` 起头？
> 逐字符读：`v` = 返回 `void`；`@` = 第一个隐含参数 `self`（接收消息的对象，类型 `id`）；`:` = 第二个隐含参数 `_cmd`（被调用的 selector，类型 `SEL`）。**关键在于：每个 ObjC 方法都隐式接收 `self` 和 `_cmd` 作为前两个参数**——这是消息发送机制决定的（`objc_msgSend(self, _cmd, ...)`），所以返回类型之后必然跟 `@:`，之后才是源码里显式写的参数。`v@:` 就是"无返回值、无显式参数"的最简方法（如 `- (void)foo`）；`v@:@` 则是它多带一个对象参数（如一个 setter）。带偏移时写作 `v16@0:8` 之类，把数字滤掉看字符即可。

> [!question] 编码里 `v24@0:8@16` 那些数字（24、0、8、16）是什么意思？能忽略吗？
> 它们是**参数帧布局信息**：返回类型后的第一个数字（`24`）是**整个参数帧的总字节数**；每个类型字符后的数字是该参数在帧内的**字节偏移**——`@0`（self 在偏移 0）、`:8`（_cmd 在偏移 8）、`@16`（下一个参数在偏移 16）。64 位上指针 8 字节，故 0→8→16 递进、总长 24。**理解类型时基本可以忽略它们**：现代 runtime 里偏移多为退化遗留，真正参与 introspection / 转发判定的是类型字符（`v@:@`）。但要注意：①偏移依赖 ABI，**跨架构会变**，别照搬；②同一方法你会看到带偏移（`v24@0:8@16`，runtime 生成）和不带偏移（`v@:@`，文档/手写）两种写法，二者等价。

> [!question] `@` 和 `@"NSString"` 有什么区别？块（block）又怎么编码？
> `@` 表示"某个对象"，但不指明类（即 `id`，或编码时类型信息不足）；`@"NSString"` 表示"一个 `NSString` 类型的对象"——**静态类型已知时，类名会带双引号附在 `@` 后面**。这对逆向极有用：它把"某对象参数"细化成"具体是哪个类的对象"，让还原出的原型更精确（`- (void)setName:(NSString *)` 而非泛泛的 `id`）。**块统一编码为 `@?`**（"对象 `@`" + "函数指针/未知 `?`"），且**不携带块的参数与返回类型**——这是 Apple 老编码表没覆盖、需查 clang 源码才确认的行为，所以你无法仅凭 `@?` 知道块的签名。

> [!question] `__objc_methtype` 和 `__objc_methname`、`__cstring` 三者怎么分工？
> 三者都是 `__TEXT` 段里"一串以 `\0` 分隔的 C 字符串"，物理同构，但**装的东西按用途分了节**：① [[20.Mach-O __cstring节]] 装**普通 C 字符串字面量**（提示文案、`printf` 格式串、URL、路径……），给人和 C 库读；② [[24.Mach-O __objc_methname节]] 装**方法名 / selector**（`setName:`、`count`），是方法"叫什么"；③ 本节 `__objc_methtype` 装**方法类型编码**（`v@:@`、`q@:`），是方法"什么形状"。②和③一一配对（靠 `method_t` 的 `name` 与 `types` 两个指针），合起来才完整描述一个方法。之所以不合并进 `__cstring`，是为了让 runtime 加载类时能直接定位方法元数据、让工具按节名分辨语义，详见上文第 1 节的 `[!note]`。

> [!question] 逆向时编码里出现 `r`、`n`、`N`、`V`、`O` 这类前缀，是乱码吗？
> 不是。它们是**类型限定符（type qualifier）**，`@encode()` 不返回、但 runtime 为**协议中声明的方法**保留：`r`=const、`n`=in、`N`=inout、`o`=out、`O`=bycopy、`R`=byref、`V`=oneway。这套是 **Distributed Objects（分布式对象，进程间/跨机消息）** 的历史遗产，用来标注参数传递方向与拷贝语义。今天罕见，但在某些协议方法编码里仍会出现（如 `oneway void` 带 `V` 前缀）。见到这些字符当作合法限定符解析即可，别误判为损坏。

## 与相邻章节的关系

- [[24.Mach-O __objc_methname节]]：存方法名（selector），与本节的方法类型**一一配对**——`method_t` 的 `name` 指向方法名节、`types` 指向本节，两者合起来才完整描述一个方法。还原方法原型时必须同时读这两节。
- [[25.Mach-O __objc_classname节]]：并列的第三个 ObjC 只读字符串池，装类名（`NSObject`、`MyView`）。三胞胎（方法名 / 类名 / 方法类型）同段同构、按用途分节。
- [[36.Mach-O __objc_classlist节]]：类元数据列表，类的方法表（`method_list_t`）里每个 `method_t` 的 `types` 字段都引用**本节**的类型编码字符串——runtime 加载类时正是顺着它来读签名。
- [[20.Mach-O __cstring节]]：本节的"物理原型"——同样是一串 `\0` 分隔的 C 字符串，理解了 `__cstring` 的布局就理解了本节的字节结构，区别只在内容语义（普通文案 vs 方法签名）与节名。
- [[19.Mach-O __text节]]：`method_t.imp` 指向这里的机器码；`name`/`types`/`imp` 三件套分别落在方法名节、本节、`__text`。

## 小结

- `__objc_methtype` 存 **Objective-C 方法的类型编码字符串**：用紧凑 ASCII 字符描述"返回值 + 各参数"类型，位于只读可执行的 `__TEXT` 段，物理上与 [[20.Mach-O __cstring节]] 同构（`\0` 分隔的 C 字符串），按用途独立成节。
- **完整字符表**要记牢：`v`=void、`@`=对象、`:`=SEL、`#`=Class、`i/I`=int/uint、`q/Q`=longlong/ulonglong、`f/d`=float/double、`B`=bool、`c/C s/S l/L`=各宽度整型、`*`=char*、`^`=指针、`{}`=结构体、`()`=union、`[]`=数组、`?`=未知(函数指针)、`@?`=块、`@"NSString"`=指定类对象。
- **签名拼装规则**：`返回类型` + `self(@)` + `_cmd(:)` + `各参数`，每段可附偏移数字（`v24@0:8@16` 中 24=帧总长、0/8/16=各参数偏移）。隐含的 `self`/`_cmd` 是几乎所有编码都以 `@:` 起头的原因；偏移随 ABI 变、现代 runtime 里基本退化为装饰，看类型字符即可。
- **`method_t.types` 指针**指向本节；`name`(方法名节)/`types`(本节)/`imp`(`__text`) 三件套合起来描述一个方法。runtime 据此构造 `NSMethodSignature` / `NSInvocation`。
- **用途**：消息转发（`methodSignatureForSelector:`+`forwardInvocation:`）、`NSInvocation` 参数布局、KVC、`NSCoding` 归档、桥接反射——凡"只有 selector、需知精确签名"皆靠它（转发慢，约 20~100x，类型解析是其一环）。
- **逆向**：`__objc_methname` + `__objc_methtype` 配对可**还原方法原型**（`setName:` + `v@:@` → `- (void)setName:(id)`），`@"类名"` 编码还能还原参数具体类型；`otool -s __TEXT __objc_methtype` 看字节、`otool -ov` 看 name/types 配对、源码侧 `@encode()`/`method_getTypeEncoding()` 反推验证。
