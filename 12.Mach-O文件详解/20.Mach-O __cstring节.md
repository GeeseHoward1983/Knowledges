# 详解Mach-O(二十)Mach-O __cstring节

> [!abstract] TL;DR
> **`__cstring` 节存放程序里的 C 字符串字面量**——源码中用双引号写的、以 `\0`（NUL）结尾的 UTF-8 字符序列，绝大多数都落在这里。它住在只读可执行的 `__TEXT` 段（权限 `r-x`），是 [[18.Mach-O section]] 通用模型里一个具体实例。
> 它的节类型是 **`S_CSTRING_LITERALS`（`flags & SECTION_TYPE = 0x2`）**。这个类型不是装饰，而是给链接器（`ld`）的一纸"合并许可证"：因为本节**只**含自描述的 NUL 结尾字符串，链接器可以放心地把**内容完全相同的字面量去重合并（coalescing）**——多处用到 `"hello"`，最终文件里只存一份，所有引用指向同一地址。
> 因为它在 `__TEXT` 段里，所以**只读**：试图改写字符串字面量（`char *s="x"; s[0]='y';`）会因写入只读页而崩溃（`EXC_BAD_ACCESS` / `SIGBUS`）。
> 节内布局极朴素：一串字节，字符串之间靠 `\0` 分隔/收尾，代码用"指向某字符串首字节的地址"来引用它。
> 逆向时 `__cstring` 是**头号富矿**：硬编码的提示文案、`printf` 格式串、URL、文件路径、版本号乃至明文写死的密钥/口令，往往都在这里裸奔——`strings -a` 或 `otool -s __TEXT __cstring` 一扫即得。

## 概述与定位

源码里写的 `"..."` 字面量，绝大多数会被编译器收集进 `__cstring` 这一"字符串常量池"。它在 Mach-O 的层级里处于这样的位置：

- 它继承 [[13.Mach-O __TEXT]] 段的**只读、可执行**属性（`r-x`）——字符串是常量、运行期不应被改，放进只读段恰如其分，也让多个进程能共享同一份物理页。
- 它是 [[18.Mach-O section]] 通用模型里**类型为 `S_CSTRING_LITERALS` 的具体节**：同一套 `section_64` 结构描述它，区别只在 `flags` 的类型位取 `0x2`、`sectname` 为 `__cstring`。
- 它与 [[21.Mach-O __const节]] 是同段并列的"只读数据"姊妹节——区别在于 `__const` 装的是任意只读常量（`S_REGULAR`、不去重），`__cstring` 专装 C 字符串（`S_CSTRING_LITERALS`、可去重），详见下文对比表。

一句话定位：**`__cstring` = `__TEXT` 段里、类型 `S_CSTRING_LITERALS`、专门存放可去重的 NUL 结尾 C 字符串字面量的只读节**。

> [!note] 不是所有字符串都进 `__cstring`
> `__cstring` 只收**纯 C 字符串字面量**（UTF-8 / ASCII、以 `\0` 结尾）。几类"看起来像字符串"的东西另有归宿，别混淆：① **UTF-16 宽字符串**进 `__TEXT,__ustring`（类型 `S_REGULAR`，不去重，见下文对比）；② **Objective-C 的方法名/类名/类型编码**进 `__TEXT,__objc_methname` / `__objc_classname` / `__objc_methtype`（见 [[24.Mach-O __objc_methname节]]）；③ **`CFString`/`NSString` 常量对象**的"对象头"在 `__DATA(_CONST),__cfstring`（见 [[34.Mach-O __cfstring节]]），但它内部的 C 字符数据仍指回 `__cstring`；④ **`os_log` 的格式串**可能落在 `__TEXT,__oslogstring`。所以"在 `__cstring` 里没找到某个串"不代表它不存在，可能只是被分流到了专用节。

## 核心原理与字段详解

### 1. 内容布局：以 `\0` 分隔/结尾的字符串紧凑排布

`__cstring` 的物理内容就是**一整块连续字节**，里面是一个接一个、以 `\0`（0x00）分隔并收尾的 C 字符串。没有长度前缀、没有索引表、没有对齐填充（`align` 通常为 0，即 1 字节对齐）——字符串首尾相接、最省空间地塞在一起。

代码侧并不"按下标"访问它，而是**持有某个字符串首字节的地址**（编译期由编译器生成一个内部标号如 `L_.str`、`L_.str.1`，链接期解析成具体虚拟地址；arm64 上典型用 `adrp + add` 算出地址，x86_64 用 `lea` 相对寻址）。运行时把这个地址当 `const char *` 传给 `printf`/`strcmp` 等函数，由它们一路读到 `\0` 为止。

举个例子，源码里若先后出现 `"hello %s\n"` 和 `"Version: %s"`，节内字节可能是这样（首尾相接，各自 `\0` 收尾）：

```text
68 65 6c 6c 6f 20 25 73 0a 00 | 56 65 72 73 69 6f 6e 3a 20 25 73 00
h  e  l  l  o     %  s  \n \0 | V  e  r  s  i  o  n  :     %  s  \0
```

> [!note] 子串共享：一个巧妙的去重副作用
> 因为字符串以 `\0` 结尾且首尾相接，链接器（和某些编译器优化）有时能做**后缀共享（tail merging）**：如果字面量 `" World"` 恰好是 `"Hello World"` 的后缀，理论上 `"World"` 的引用可以直接指向 `"Hello World"` 里 `W` 那个字节，复用同一段尾巴和同一个 `\0`，无需再单独存一份 `"World\0"`。这是 NUL 结尾 + 紧凑排布带来的额外节省，但是否启用取决于链接器版本与优化级别，逆向时若发现两个字符串地址"套娃"重叠，多半就是它。

### 2. 类型 `S_CSTRING_LITERALS`（0x2）：给链接器的"去重许可证"

`__cstring` 节头 `flags` 字段的**低 8 位**（`flags & SECTION_TYPE`）等于 `0x2`，即 `S_CSTRING_LITERALS`。来自 `<mach-o/loader.h>` 的一手定义：

```c
#define SECTION_TYPE           0x000000ff  /* 低 8 位：节类型掩码 */
#define S_REGULAR              0x0  /* 普通节，无特殊语义 */
#define S_ZEROFILL             0x1  /* 零填充节 */
#define S_CSTRING_LITERALS     0x2  /* 只含 C 字符串字面量的节  ← __cstring */
#define S_4BYTE_LITERALS       0x3  /* 只含 4 字节字面常量 */
#define S_8BYTE_LITERALS       0x4  /* 只含 8 字节字面常量 */
#define S_LITERAL_POINTERS     0x5  /* 只含指向字面量的指针 */
```

这个类型值是整个节最关键的"身份证"，它对链接器和工具传达了一条强约束：**本节里装的全部是、且仅是 NUL 结尾的 C 字符串字面量，没有夹杂任何别的数据**。正因为有了这条"纯字面量"保证，链接器才被允许做下一节讲的去重合并——这也是 Mach-O 把字符串单独切一个 `S_CSTRING_LITERALS` 节、而不是随便扔进 `S_REGULAR` 的 `__const` 的根本原因。

> [!note] 汇编里如何声明这个节
> 编译器生成的汇编中，`__cstring` 节是用带 `cstring_literals` 属性的指令声明的，字符串则用 `.asciz`（自动补 `\0`）定义：
> ```asm
>     .section __TEXT,__cstring,cstring_literals
> L_.str:
>     .asciz "hello %s\n"
> L_.str.1:
>     .asciz "Version: %s"
> ```
> 那个第三参数 `cstring_literals` 正是告诉汇编器把本节的类型位设为 `S_CSTRING_LITERALS`。对照 `__const` 的声明是 `.section __TEXT,__const`（无第三参数，默认 `S_REGULAR`）——一个字之差，决定了去不去重。

### 3. 链接器去重合并机制（coalescing / 字面量池）

这是 `S_CSTRING_LITERALS` 类型最实际的收益。机制可以拆成"编译期"和"链接期"两层：

**编译期（单个翻译单元内）**：同一个 `.c`/`.m` 文件里多次出现的相同字面量，编译器（开启 `-fmerge-constants`，优化档默认开）已经会做**字符串驻留（string interning）**——只生成一个标号、存一份。验证方法很经典：比较两个相同字面量的指针，若地址相等就说明只有一份。

**链接期（跨翻译单元 / 跨 `.o`）**：编译期的去重只在单文件内有效；不同 `.o` 各自存了一份 `"error"`。链接器 `ld` 把多个 `.o` 的 `__cstring` 节合并进最终二进制时，会**把所有内容相同的字面量折叠成一份**，让原先散落在各 `.o` 的引用统统重定位到这唯一的一份上。之所以能这么做且不出错，正是因为类型 `S_CSTRING_LITERALS` 担保了"节内全是自描述（NUL 结尾）、顺序无关的字面量"——既然每个串都自带边界、谁在前谁在后无所谓，那合并、重排、丢弃重复就都是安全的。

```text
            链接前（三个 .o 各存一份）              链接后（合并去重，只剩一份）
   a.o __cstring: ... "OK\0" ...                  ┌─────────────────────────────┐
   b.o __cstring: ... "OK\0" ... "Fail\0" ...  →  │ ... "OK\0" "Fail\0" ...      │
   c.o __cstring: ... "OK\0" ...                  └──────────▲──────▲───────────┘
                                                  a.o/b.o/c.o 的所有 "OK" 引用 ┘ 都指这里
```

效果：① **减小体积**——重复文案不再冗余；② **可做指针相等比较的副作用**——同一字面量去重后地址相同，但**绝不能依赖**它（不同优化档/不同编译器结论不同，标准也不保证），这只是实现细节而非语言契约。

> [!note] 与 `S_REGULAR` 的"不去重"形成鲜明对比
> 为什么 `__const`（`S_REGULAR`）里的只读常量不会被这样去重？因为 `S_REGULAR` 没有"内容自描述、顺序无关"的保证——里面可能是结构体、数组、任意字节，链接器无从判断"这两段字节能否合并、合并后引用是否仍正确"，只能原样保留。**去重能力是 `S_CSTRING_LITERALS`（以及 `S_4/8/16BYTE_LITERALS`、`S_LITERAL_POINTERS` 这些字面量类型）专属的特权**，本质上是用"类型即契约"换来的优化空间。

### 4. 只读不可改：写字面量必崩溃

`__cstring` 在 `__TEXT` 段内，段的内存保护是 `r-x`（读 + 执行，**不可写**）。于是字符串字面量的内容在运行期**物理上无法被修改**——这不是约定，而是 MMU 页保护的硬约束。

经典踩坑：
```c
char *s = "immutable";   // s 指向 __cstring 里的只读字节
s[0] = 'I';              // ✗ 写只读页 → EXC_BAD_ACCESS(SIGBUS) 崩溃
```
这段代码能编译通过（C 里字符串字面量类型是 `char[]`，可隐式转 `char *`，历史包袱），但一运行到 `s[0]='I'` 就崩。正确做法是把它放进**可写**的数组（拷贝一份到栈/堆）：
```c
char s[] = "immutable";  // ✓ 字面量被拷进栈上数组，s 可改
s[0] = 'I';              // ✓ 改的是栈上副本，不是 __cstring
```
区别就在 `char *s = "..."`（指向只读 `__cstring`）与 `char s[] = "..."`（把字面量内容**复制**进可写数组）——后者会在 `__cstring` 留一份"模板"、运行时拷贝到可写内存。

> [!warning] "字符串字面量可写"是 UB，平台间表现不一
> C 标准规定修改字符串字面量是**未定义行为（UB）**。在 macOS/iOS 这类把 `__cstring` 放只读 `__TEXT` 的平台上，UB 的具体表现是"立即崩溃"；某些老旧/嵌入式平台可能把字面量放可写区而"看似改成功"。**绝不要依赖任何一种表现**——写只读字面量在 Apple 平台是确定的崩溃源，逆向时看到 `__cstring` 地址被当作写入目标，基本可断定是 bug 或攻击尝试。

### 5. 与 `__const` / `__ustring` 的区别（三节对比）

`__cstring`、`__const`、`__ustring` 常被一起提及，但定位泾渭分明。三者都在 `__TEXT` 段、都只读，区别在"装什么 + 什么类型 + 去不去重"：

| 维度 | `__cstring` | `__const`（见 [[21.Mach-O __const节]]） | `__ustring` |
|---|---|---|---|
| 装什么 | C 字符串字面量（UTF-8/ASCII，`\0` 结尾） | 任意只读常量（const 结构体/数组/标量、跳转表等） | UTF-16 宽字符串（`u"..."` / 宽字符常量） |
| 节类型 `flags & 0xff` | **`S_CSTRING_LITERALS`（0x2）** | **`S_REGULAR`（0x0）** | **`S_REGULAR`（0x0）** |
| 链接器去重 | **会**（相同字面量合并成一份） | **不会**（原样保留） | **不会**（无专用字面量类型） |
| 元素边界 | 靠 `\0` 自描述、顺序无关 | 无统一边界、顺序相关 | 靠 `\0\0`（双字节 NUL）收尾，元素 2 字节宽 |
| 所在段 | `__TEXT`（`r-x`） | `__TEXT`（`r-x`） | `__TEXT`（`r-x`） |
| `strings` 默认能扫到 | **能**（ASCII 路径） | 视内容（含可打印串才行） | 默认**扫不全**（需 `strings -e l` 按 UTF-16 解） |

要点提炼：
- **`__cstring` vs `__const`**：本质差别是"有没有去重特权"。字符串自描述（NUL 结尾），所以能享受 `S_CSTRING_LITERALS` 的合并；普通常量没这保证，只能 `S_REGULAR` 原样存。
- **`__cstring` vs `__ustring`**：差别是"编码 + 类型"。`__ustring` 装 UTF-16（每字符 2 字节），但 Mach-O **没有**为 UTF-16 设专门的字面量类型，于是它退回 `S_REGULAR`、**不能去重**。逆向 `__ustring` 时记得按 `char16_t *` / 宽字符解读（如 LLDB 里 `(char16_t *)addr`），别当成 `char *`。

> [!note] 为什么没有 `S_USTRING_LITERALS`？
> 历史与权衡使然：C 字符串（UTF-8/ASCII、`\0` 结尾）是 Unix/C 生态的"一等公民"，用量巨大、去重收益高，值得专门设类型。UTF-16 字面量在 macOS/iOS 上相对少见（Cocoa 多用 `NSString`/`CFString`，其常量对象走 `__cfstring`，底层 C 数据仍回 `__cstring`），收益不足以单列一个类型，便沿用通用 `S_REGULAR`。这也解释了 `__ustring` 享受不到自动去重的"待遇差"。

### 6. 逆向价值：硬编码文本与密钥的富矿

正因为 `__cstring` 集中存放了程序里**所有明文写死的字符串**，它是静态逆向、恶意软件分析的**第一站**。常见能从这里直接捞到的东西：

- **提示/错误文案**：`"invalid licence code"`、`"thanks for registering"`——往往直接暴露程序的逻辑分支与判定点（顺着文案找 xref 就能定位校验函数）。
- **格式串**：`printf`/`NSLog` 的 `"%s=%d"` 之类——揭示数据结构与字段。
- **URL / IP / 域名**：网络回连地址、API 端点、CDN——恶意样本的 C2 服务器常在此现形，是提取 IoC、写 YARA 规则的素材。
- **文件路径 / 配置键**：程序读写哪些文件、读哪些 plist/注册表项。
- **版本号 / 编译信息 / 库名**：辅助识别软件身份与依赖。
- **明文密钥 / 口令**：把 API key、加密密钥、硬编码密码当字符串写死是**极常见的安全失误**——分析者搜 `key`、`token`、`password`、`secret` 经常一搜一个准。

工作流：先 `strings`/`otool -s` 把 `__cstring` 全 dump 成文本文件，再 `grep` 关键词（`http`、`key`、`password`、`/api/`…），命中后回到反汇编里找引用该字符串的代码（xref），即可顺藤摸瓜定位关键逻辑。

> [!warning] 字符串看不到 ≠ 没有：当心混淆与运行时解密
> `strings`/`otool` 只能看见**明文**。成熟的恶意软件常**混淆字符串**：把密文字节存进 `__data`，运行时 XOR/解密成明文（有的还先 `vm_protect` 把只读页临时改可写再解密）。这种情况下 `__cstring` 里看不到有意义的串，必须转**动态分析**（断点、内存 dump、跟踪解密函数）。所以"`__cstring` 干净"不等于"程序没有敏感字符串"。

> [!note] 架构差异：内容字节序无关，仅地址/对齐随位宽变
> `__cstring` 的内容是**字节序无关**的字符数据（ASCII/UTF-8 逐字节存储，arm64 与 x86_64 的字节完全一致），跨架构不变。差异只体现在**节的虚拟地址、文件偏移、对齐**会随位宽（32/64 位）与页大小（arm64 16KB、x86_64 4KB）不同——但这是 [[18.Mach-O section]] 层面的通用差异，不是 `__cstring` 特有。换言之：同一份源码在 arm64 和 x86_64 上编译，`__cstring` 里的字符串字节一模一样，只是落在不同地址。

## 实操：用工具查看

### 示例 1：`otool -s __TEXT __cstring` dump 节的原始字节

`otool -s 段名 节名` 以"地址 + 十六进制 + ASCII"逐行 dump 指定节内容。这是看 `__cstring` 最直接的方式：

```bash
otool -s __TEXT __cstring /bin/ls      # dump __cstring 的原始字节（一串以 \0 分隔的 C 字符串）
otool -V -s __TEXT __cstring /bin/ls    # -V 让 otool 尝试把字节解析得更可读
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/字节仅示意 `otool -s` 的逐行格式，实际数值以你机器上的 `otool` 为准。

```text
/bin/ls:
Contents of (__TEXT,__cstring) section
0000000100003f00  68 65 6c 6c 6f 20 25 73 0a 00 56 65 72 73 69 6f  hello %s..Versio
0000000100003f10  6e 3a 20 25 73 00 2f 75 73 72 2f 6c 69 62 2f 64  n: %s./usr/lib/d
0000000100003f20  79 6c 64 00 25 73 3a 20 00 00 00 00 00 00 00 00  yld.%s: ........
```

> 说明：左列是该行首字节的**虚拟地址**（从节 `addr` 起算）；中间是十六进制；右列是可打印 ASCII（不可打印字节显示为 `.`）。`68 65 6c 6c 6f` 即 `"hello"`，紧跟的 `00` 是该串结束符；可见多个字面量（`"hello %s\n"`、`"Version: %s"`、`"/usr/lib/dyld"`、`"%s: "`）**首尾相接、各自以 `\0` 收尾**，这正是 `S_CSTRING_LITERALS` 的典型布局印证。

### 示例 2：`strings -a` 快速扫所有可打印字符串

`strings` 扫描文件中所有"连续 N 个（默认 4）可打印字符 + 终止"的序列，是最快的字符串提取手段：

```bash
strings -a /bin/ls                       # -a: 扫整个文件（不只默认节）
strings -a -n 6 /bin/ls                   # -n 6: 只要长度 ≥ 6 的串，过滤短噪声
strings -a /bin/ls | grep -i -E 'http|key|password|/api/'   # 配合 grep 关键词捞料
```

> [!warning] 示例输出为示意
> 下列为构造样例，仅示意 `strings` 的"逐行打印可读串"格式与逆向时关注的内容类型。

```text
hello %s
Version: %s
/usr/lib/dyld
https://example.com/api/v1/report      ← 可疑回连地址（逆向重点）
X-Auth-Token: %s                        ← 鉴权头格式串
licence code invalid                    ← 揭示校验逻辑的文案
```

> 说明：`strings` 不区分节、扫整个文件，所以噪声比 `otool -s __TEXT __cstring` 多（会带上 `__objc_methname`、符号名等其他可打印数据）。**精确只看 C 字符串用 `otool -s __TEXT __cstring`；快速广撒网用 `strings -a`**。注意 `strings` 默认按单字节解码，**漏掉 UTF-16 的 `__ustring`**——要扫宽字符串得加 `strings -e l`（little-endian 16-bit）。

### 示例 3：从文案反查代码（逆向工作流缩影）

逆向的常见套路是"先在 `__cstring` 里找到关键文案，再回到反汇编里找谁引用了它"：

```bash
# 1) 先确认目标文案在 __cstring 里、拿到它的地址
otool -s __TEXT __cstring ./target | grep -A1 "licence"
# 2) 反汇编 __text，搜索引用该字符串地址的指令（arm64 看 adrp/add，x86_64 看 lea）
otool -tV ./target | grep -B2 -A2 "0000000100003f40"   # 假设文案在此地址
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意"字符串地址 → 引用它的代码"的关联过程。

```text
; __text 中某处（arm64），取 "licence code invalid" 的地址并传给打印函数
0000000100002a10  adrp  x0, 0x100003000        ; 定位到 __cstring 所在页
0000000100002a14  add   x0, x0, #0xf40         ; + 偏移 → x0 = 0x100003f40（那条文案）
0000000100002a18  bl    _puts                  ; 打印它 → 这附近就是 licence 校验失败分支
```

> 说明：找到字符串后顺着引用它的 `adrp+add`（或 x86_64 的 `lea`）回到代码，就**定位到了使用该文案的函数**——校验失败分支、错误处理、网络请求构造点等关键逻辑，往往就在这种"字符串 xref"附近。这也是 `__cstring` 被称为逆向"切入点/富矿"的实操含义。

## FAQ

> [!question] `__cstring` 和 `__const` 都在 `__TEXT` 段、都只读，到底差在哪？
> 差在**类型与去重特权**。`__cstring` 的类型是 `S_CSTRING_LITERALS`（0x2），向链接器担保"节内全是 NUL 结尾、自描述、顺序无关的 C 字符串"，于是链接器**可以去重合并**相同字面量（多处 `"OK"` 只存一份）。`__const` 的类型是 `S_REGULAR`（0x0），装的是任意只读常量（结构体、数组、跳转表…），没有"自描述、顺序无关"的保证，链接器**无法去重**、只能原样保留。一句话：**`__cstring` 是"能去重的字符串专用只读节"，`__const` 是"不能去重的通用只读节"**。两者对照表见上文第 5 节与 [[21.Mach-O __const节]]。

> [!question] 为什么改字符串字面量（`s[0]='x'`）会崩溃？怎么才能改？
> 因为 `__cstring` 在 `__TEXT` 段、内存保护是 `r-x`（**不可写**），写它就是写只读页 → MMU 直接抛 `EXC_BAD_ACCESS`(SIGBUS) 崩溃。这是硬件页保护，不是约定。`char *s = "x"; s[0]='y';` 里 `s` 指向只读 `__cstring`，所以崩；要可改就用 `char s[] = "x";`——它会把字面量内容**拷贝**进栈上可写数组，改的是副本而非 `__cstring`。另外，C 标准里修改字符串字面量本就是**未定义行为**，别依赖任何平台的具体表现。

> [!question] 链接器去重后，两个相同字面量的指针一定相等吗？能用 `==` 比较字符串吗？
> **不能依赖**。开启去重（优化档默认）时，同一字面量合并成一份、地址确实相同，看起来 `==` 能"判等"；但这只是**实现细节**：不同优化级别、不同编译器、跨翻译单元的边界情况都可能让结论变化，C/C++ 标准也**不保证**相同字面量共享地址。比较字符串内容永远用 `strcmp`/`strncmp`，**绝不要用指针 `==`**。去重是链接器为省体积做的优化，不是可依赖的语言契约。

> [!question] 逆向时 `strings` 扫不到我要找的字符串，是不是程序里就没有？
> 不一定。三种常见原因：① **编码不对**——若是 UTF-16 宽字符串，它在 `__ustring`，默认 `strings` 漏扫，要用 `strings -e l`；② **被分流到专用节**——ObjC 方法名/类名在 `__objc_methname` 等（见 [[24.Mach-O __objc_methname节]]）、`CFString` 常量在 `__cfstring`（见 [[34.Mach-O __cfstring节]]），不在 `__cstring`；③ **被混淆/加密**——恶意软件常把密文存 `__data`、运行时才解密成明文，静态 `strings` 自然看不到，需转动态分析。所以"扫不到"要先排除编码与分节，再考虑混淆。

> [!question] `otool -s __TEXT __cstring` 和 `strings` 该用哪个？
> 看目的。**要"只看 C 字符串、不要噪声"用 `otool -s __TEXT __cstring`**——它精确 dump 该节字节，且带虚拟地址（方便回查代码 xref）。**要"快速广撒网、扫全文件所有可读串"用 `strings -a`**——它不区分节、连符号名/其他节的可打印数据一并扫出，噪声多但全。逆向实战常两者配合：`strings` 先广撒网定位线索关键词，再用 `otool -s` 精确看 `__cstring` 拿地址、回到反汇编找引用。

## 与相邻章节的关系

- [[13.Mach-O __TEXT]]：`__cstring` 的宿主段——它的 `r-x` 只读属性正来自 `__TEXT`，"写字面量崩溃"的根因在此。
- [[21.Mach-O __const节]]：同段并列的姊妹只读节，二者核心差异是"去不去重"（`S_CSTRING_LITERALS` vs `S_REGULAR`），完整对比表见上文第 5 节与该篇。
- [[18.Mach-O section]]：`__cstring` 是其通用模型的一个实例——`section_64` 结构、`flags` 类型位（这里取 `0x2`）、`align`/`offset` 等字段语义都在那篇讲透。
- [[24.Mach-O __objc_methname节]]：ObjC 的方法名等"特殊字符串"走专用节，**不混入** `__cstring`，是判断"字符串在不在 `__cstring`"时必须区分的对象。

## 小结

- `__cstring` 存 **C 字符串字面量**（UTF-8/ASCII、`\0` 结尾），位于只读可执行的 `__TEXT` 段，是 [[18.Mach-O section]] 模型里类型为 `S_CSTRING_LITERALS`（`flags & 0xff = 0x2`）的具体节。
- 类型 `S_CSTRING_LITERALS` 是给链接器的"去重许可证"：因节内全是自描述、顺序无关的字面量，链接器可**跨 `.o` 把相同字符串合并成一份**（coalescing），省体积。这是 `S_REGULAR` 节（如 `__const`/`__ustring`）享受不到的特权。
- 内容是一串**以 `\0` 分隔/收尾、首尾相接**的字节，`align` 通常为 0（1 字节对齐）；代码靠"字符串首字节地址"引用它（arm64 `adrp+add`、x86_64 `lea`）。
- **只读不可改**：写字面量（`char *s="x"; s[0]='y';`）会因写 `r-x` 页崩溃（`EXC_BAD_ACCESS`/SIGBUS），且是 C 的 UB；要可改须用 `char s[]="x"` 把内容拷进可写数组。
- 与姊妹节的边界：`__const`（`S_REGULAR`、任意只读常量、不去重）、`__ustring`（`S_REGULAR`、UTF-16、不去重）；ObjC 字符串走 `__objc_methname` 等专用节。
- **逆向富矿**：硬编码文案、格式串、URL、路径、版本号乃至明文密钥/口令常裸存于此；`otool -s __TEXT __cstring`（精确）或 `strings -a`（广撒网）一扫即得，再顺字符串 xref 回查代码逻辑。注意混淆/加密字符串需转动态分析。
