# 详解Mach-O(三十五)Mach-O __objc_selrefs节

> [!abstract] TL;DR
> **`__objc_selrefs` 是"selector 引用表"（selector references）**：一张**指针数组**，每一项（64 位 8 字节 / 32 位 4 字节）初值都指向 [[24.Mach-O __objc_methname节]] 里的一个 selector 名字符串（如 `"setName:"`）。源码里每出现一处 `@selector(setName:)`，编译器就在本表里生成一个槽，并把对该方法名的引用编译成"对本表某槽的读取"。
> **镜像加载时，ObjC runtime 在 `_read_images` 阶段遍历本表**：用 `_getObjc2SelectorRefs` 拿到本节，对每个名字调用 `sel_registerName`（实际是 `sel_registerNameNoLock`）注册成**全局唯一的 `SEL`**——同名 selector 全进程只留一个指针——然后把槽位**回填**为这个唯一 `SEL` 指针。
> 之所以放在**可写**的 `__DATA`（现代二进制经链式 fixups 后并入 `__DATA_CONST`、回填后再只读化），正是因为这些槽要被运行期**改写**。它是"方法名字符串 → 运行时唯一 selector"的桥梁，唯一化之后 `objc_msgSend` 才能拿 `SEL` **指针相等**做缓存键，把消息派发的快路径压到极致。
> 它属于 ObjC **四大"引用类"节**（`selrefs`/`classrefs`/`superrefs`/`protorefs`）之一——存的是"对元数据的**引用**"，而不是元数据本身（名字本体在 `__objc_methname`、类本体在 `__objc_data`）。`flags` 典型值 `0x10000005` = 类型 `S_LITERAL_POINTERS(0x5)` + 属性 `S_ATTR_NO_DEAD_STRIP(0x10000000)`。

## 概述与定位

要理解 `__objc_selrefs` 为什么存在，得先看 Objective-C 消息派发的一条铁律：**`objc_msgSend(obj, sel, …)` 里的 `sel` 必须是全进程唯一的指针**。同一个方法名（如 `length`、`setName:`）无论在哪个 `.m` 文件、哪个库里被引用，最终都必须解析到**同一个 `SEL` 值**。只有这样，runtime 才能用"比较指针"代替"比较字符串"来识别方法——这是 ObjC 缓存与派发性能的根基。

但编译器在编译单个 `.o` 时，**根本不知道运行时那个唯一 `SEL` 是多少**（它跨整个进程、由 runtime 在加载期才确定）。编译器能做的，只是把方法名当成一个普通 C 字符串写进 [[24.Mach-O __objc_methname节]]，再在 `__objc_selrefs` 里留一个**指向该字符串的指针槽**，作为"这处代码引用了这个名字"的占位。真正把"名字字符串"换成"唯一 `SEL` 指针"的工作，推迟到加载期由 runtime 完成——这个**编译期占位、加载期回填**的两段式设计，就是 `__objc_selrefs` 的全部意义。

把它放到 [[18.Mach-O section.md|节（section）的通用模型]] 里看：`__objc_selrefs` 是一个 `flags` 类型为 `S_LITERAL_POINTERS`（"仅含指向字面量的指针"，见 [[18.Mach-O section.md|第 7 节类型表]] 的 `0x5`）的节，住在可写段。它和 [[40.Mach-O __objc_classrefs节]]、`__objc_superrefs`、[[42.Mach-O __objc_protorefs节]] 一道，构成 ObjC 元数据里的**"引用类"四节**——它们都不存元数据本体，只存"指向本体的、需要被加载期修正的指针"。runtime 在 [[36.Mach-O __objc_classlist节]] 等"列表类"节注册类的同期，统一处理这四张引用表。

> [!note] "引用 vs 名字"：`__objc_selrefs` 与 `__objc_methname` 的分工
> 这是本篇最容易混的一对概念，务必分清：
> - **`__objc_methname`（被指方）**：类型 `S_CSTRING_LITERALS`，住在**只读** `__TEXT`，存的是 **selector 名字符串本体**（`"setName:\0"` 这样的字节），可被链接器跨编译单元**去重合并**（同名只留一份字节）。它是"数据"。
> - **`__objc_selrefs`（指向方）**：类型 `S_LITERAL_POINTERS`，住在**可写** `__DATA`/`__DATA_CONST`，存的是**指向上面那些字符串的指针**，且这些指针要被 runtime 回填成唯一 `SEL`。它是"指向数据的、可变的引用"。
> 一句话：**`__objc_methname` 管"名字长什么样"，`__objc_selrefs` 管"代码在哪里用到了这个名字、运行时它对应哪个唯一 selector"**。一个名字字符串（methname 里一份）可以被任意多处 `@selector`（selrefs 里多个槽）引用。

## 核心原理与字段详解

### 1. 内容布局：一张"指向 selector 名"的指针数组

`__objc_selrefs` 在文件里就是一段**连续的指针数组**，没有头部、没有计数字段——和所有节一样，**条目数由 `节大小 size ÷ 指针宽度` 推算**（64 位 `size/8`、32 位 `size/4`，参见 [[18.Mach-O section.md|节的 size 与条目数推算]]）。每个槽的**编译期初值**是一个指针，指向 `__objc_methname` 里对应的 selector 名字符串首字节。

编译器为源码里**用到的每个不同 `@selector(...)`** 生成一个槽。注意触发点不止显式的 `@selector(foo)`：每一句 `[obj doSomething]`、每一个 `performSelector:` 的字面 selector、KVC/KVO 里的方法名等，凡是编译期能确定的 selector 引用，最终都会落成 selrefs 里的一个槽 + methname 里的一段字符串。多处引用**同一个名字**时，selrefs 里会有多个槽，但它们的初值都指向 methname 里**同一份**去重后的字符串。

> [!note] 它由编译器/链接器协作生成，不是手写
> Clang 发射 selector 引用时，等价于这样两段汇编指令：把名字字符串放进 `__TEXT,__cstring,cstring_literals`，把指向它的指针放进 `.section __DATA,__objc_selrefs,literal_pointers,no_dead_strip`，槽里的 `.quad`（64 位）就指向那个字符串标签。`literal_pointers` 对应节类型 `S_LITERAL_POINTERS(0x5)`，`no_dead_strip` 对应属性 `S_ATTR_NO_DEAD_STRIP(0x10000000)`——所以本节 `flags` 常见为 `0x10000005`（见下文第 6 节）。

### 2. 加载期唯一化与回填：`_read_images` → `map_selrefs` → `sel_registerName`

镜像被 `dyld` 映射进来后，ObjC runtime 在 `_objc_init` → `map_images` → **`_read_images`** 里完成 selector 引用的修正。核心流程（基于 Apple `objc4` 源码）：

1. **取节**：runtime 用 `_getObjc2SelectorRefs(hi, &count)` 拿到当前镜像的 `__objc_selrefs` 节，类型化为一个 `SEL[]`（`count = size / 指针宽度`）。这个访问器由 `objc-file.mm` 里的 `GETSECT(_getObjc2SelectorRefs, SEL, "__objc_selrefs")` 宏生成——**它读的就是名为 `"__objc_selrefs"` 的节**，节名写错就拿不到，selector 注册不上。
2. **逐项注册并回填**（`map_selrefs`）：对第 `i` 个槽，`sel = sel_registerNameNoLock((const char *)sels[i], copy)`：
   - `sel_registerName`/`sel_registerNameNoLock` 拿名字字符串去**全局 selector 表**里查：已注册则返回既有 `SEL`，未注册则插入新表项并返回新 `SEL`。这一步保证了**全进程唯一化**（uniquing）。
   - 然后**仅当 `sels[i] != sel` 时**才把 `sels[i] = sel` 写回去。这个"不等才写"的判断是有意为之：**回填会弄脏（dirty）该内存页**，若槽里已经是正确的唯一 `SEL`（典型见下文 dyld 预优化场景），就跳过写入，**避免无谓地把干净的共享页变成脏页**、增加内存压力。
3. **完成**：这一遍跑完，runtime 打日志 `IMAGE TIMES: fix up selector references`。此后代码任何时候读这个槽，拿到的都是**唯一 `SEL` 指针**，可直接喂给 `objc_msgSend`。

> [!note] 注册前先"数数"：`selrefCount` 与 `sel_init`
> 在真正回填之前，runtime 还会在 `map_images_nolock` 里先**遍历各镜像统计 selref 总数**（`_getObjc2SelectorRefs` 累加到 `selrefCount`，再加上 `_getObjc2MessageRefs` 的 `__objc_msgrefs`），第一次时用 `sel_init(selrefCount)` 据此**预分配 selector 哈希表的容量**，并先把 libobjc 自己要用的内建 selector（`load`、`initialize`、`.cxx_construct`/`.cxx_destruct`、`retain`/`release` 等）注册进去。先数后填，避免边注册边扩容。

### 3. 唯一化为何是性能根基：`objc_msgSend` 用 `SEL` 指针做 cache key

selector 唯一化不是为了好看，而是直接服务于消息派发的快路径。`objc_msgSend` 的工作大致是：拿 `(receiver, SEL)`，先查 receiver 所属类的**方法缓存（method cache）**，命中就直接跳到 `IMP`（函数实现）。

关键在于：**因为 `SEL` 是全进程唯一的指针，缓存可以直接用这个指针值当哈希键、用指针相等（`==`）判断命中**，而**不必做字符串比较**。这把"找方法"从一次 `strcmp` 级别的操作降为一次指针比较 + 哈希查表。`objc_msgSend` 的汇编快路径因此能压到只有寥寥几条指令；只有缓存未命中时才走慢路径 `lookUpImpOrForward` 沿继承链查方法列表，并把结果填回缓存。

> [!note] 不只是 selrefs，方法列表里的 selector 也必须唯一
> 同样的唯一化要求也施加在每个类的**方法列表**（method list）上：缓存里存的 `SEL`、方法列表里每个方法的 `SEL`、以及 `objc_msgSend` 传入的 `SEL`，三者必须是**同一套**唯一指针，比较才有意义。所以 runtime（及 dyld 共享缓存）不仅 unique `__objc_selrefs`，也会让方法列表里的 selector 指向同一批唯一字符串/`SEL`。`__objc_selrefs` 是这套唯一化体系**面向"代码里的引用点"**的那一半。

### 4. 为什么住在可写段（`__DATA` / `__DATA_CONST`）

理由很直接：**槽要被运行期回填（改写成唯一 `SEL`）**，而代码段 `__TEXT` 是 `r-x`（只读可执行）、写不了，所以 selrefs 不能放 `__TEXT`，只能放可写的数据段。

- **传统布局**：放在 `__DATA`（`rw-`），加载期 dyld 的 bind/rebase 或 runtime 的 `map_selrefs` 直接改写即可。
- **现代布局（链式 fixups）**：现代 macOS/iOS 二进制把这四张引用表搬到了 **`__DATA_CONST`**。`__DATA_CONST` 的特点是"**加载期可写、之后只读**"——dyld 先按链式 fixups（`LC_DYLD_CHAINED_FIXUPS`，见 [[18.Mach-O section.md|节级重定位一节]]提到的链式 fixups）遍历这些指针、完成 rebase/bind 与回填，**回填完再把这些页重新保护为只读**。这样既满足"加载期要回填"的写需求，又能在运行期享受只读页的安全收益（防止 selector 指针被篡改）。

> [!note] 架构差异与 dyld 共享缓存预优化
> ① **指针宽度**：64 位每槽 8 字节、32 位 4 字节，条目数相应用 `size/8` 或 `size/4` 算。
> ② **链式 fixups**：新版 dyld 改变了"回填"的**机制**（指针以链式编码、由 dyld 统一遍历），但"selref 槽 → 名字 → 唯一 `SEL`"的**语义不变**。
> ③ **共享缓存预优化（dyld shared cache）**：对系统库，dyld 在**构建共享缓存时**就把所有 selector 预先 unique 成一张完美哈希表（perfect hash）烤进 libobjc，并对 selref 应用 LOH（把 `ADRP`/`LDR` 指令对改写成 `ADRP`/`ADD`，因为地址已知）。这种镜像里 selref 槽**装载时就已经是正确的唯一 `SEL`**，runtime 的 `map_selrefs` 会因 `sels[i] == sel` 而跳过写入——这正是第 2 节"不等才写"判断省下脏页的来源，也是 Snow Leopard 起"ObjC 启动开销减半、每 app 省几百 KB"优化的核心。

### 5. ObjC 四大"引用类"节对照（selrefs / classrefs / superrefs / protorefs）

`__objc_selrefs` 不是孤例。ObjC 元数据里有**四张并列的引用表**，结构同型（都是"加载期被回填的指针数组"），只是指向的对象不同、由不同的 `GETSECT` 访问器读取：

| 引用节 | 每槽指向 | 回填后是什么 | runtime 访问器 | 对应被引用的本体 |
|---|---|---|---|---|
| **`__objc_selrefs`** | `__objc_methname` 里的 selector 名字串 | 全局唯一 `SEL` | `_getObjc2SelectorRefs` | [[24.Mach-O __objc_methname节]] |
| `__objc_classrefs` | 类对象（`objc_class`） | 已实现的 `Class` 指针 | `_getObjc2ClassRefs` | [[40.Mach-O __objc_classrefs节]] |
| `__objc_superrefs` | 父类对象 | 父类 `Class` 指针（`[super …]` 用） | `_getObjc2SuperRefs` | （父类本体） |
| `__objc_protorefs` | 协议对象（`protocol_t`） | 唯一化的 `Protocol *` | `_getObjc2ProtocolRefs` | [[42.Mach-O __objc_protorefs节]] |

它们的共性是：**编译期是"指向本体的弱占位指针"，加载期被 runtime/dyld 修正为"运行时真正可用的唯一对象指针"**。差异只在"被指的本体是什么、用什么注册函数唯一化"。`__objc_selrefs` 是其中最高频、最能体现"唯一化 → 指针相等 → 快派发"逻辑的一张。

> [!note] 与"列表类"节的区别
> 别把"引用类"四节和 [[36.Mach-O __objc_classlist节]] 这类"**列表类**"节混了：`__objc_classlist`/`__objc_nlclslist`/`__objc_catlist` 列的是"**本镜像定义了哪些类/分类**"（供 runtime 注册"我提供的元数据"），而 `selrefs`/`classrefs`/`superrefs`/`protorefs` 记的是"**本镜像代码引用了哪些 selector/类/协议**"（供 runtime 修正"我要用到的引用"）。一个是"我有什么"，一个是"我用什么"。runtime 在 `_read_images` 里两件事同期处理。

### 6. `flags` 解读：`S_LITERAL_POINTERS` + `S_ATTR_NO_DEAD_STRIP`

回到 [[18.Mach-O section.md|节头 flags]] 的视角，`__objc_selrefs` 的 `flags` 典型值是 **`0x10000005`**，按 `SECTION_TYPE(0x000000ff)` / `SECTION_ATTRIBUTES(0xffffff00)` 拆开：

- **类型** `0x10000005 & 0xff = 0x05` = **`S_LITERAL_POINTERS`**（"仅含指向字面量的指针"）。这准确描述了本节内容：一组指向 `__objc_methname` 字面字符串的指针。
- **属性** `0x10000005 & 0xffffff00 = 0x10000000` = **`S_ATTR_NO_DEAD_STRIP`**（禁止死代码消除）。即便链接器静态分析觉得某个 selref"看似没人引用"，也**不得删除**——因为 ObjC selector 常被运行时动态使用（`performSelector:`、KVC、消息转发），静态可达性分析不可靠，删了会导致运行时找不到 selector。

> [!note] `no_dead_strip` 不是可有可无
> `S_ATTR_NO_DEAD_STRIP` 对正确性很关键：ObjC 的方法调用大量是**运行期动态决议**的，编译期"这个 selector 没被引用"的判断经常是错的。给 selrefs 打上 `no_dead_strip`，等于告诉链接器"别用静态分析删我"，保证所有出现在源码里的 selector 都能在运行时被注册、被找到。历史上也确有 LLVM 期望本节带此标记。

## 实操：用工具查看

### 示例 1：`otool -s __DATA __objc_selrefs` dump 原始指针

`otool -s 段名 节名` 以十六进制 dump 指定节的原始字节。注意**段名要按你二进制的实际布局给**——现代二进制多在 `__DATA_CONST`，老二进制在 `__DATA`：

```bash
otool -s __DATA __objc_selrefs /path/to/ObjCBinary        # 老布局/部分二进制
otool -s __DATA_CONST __objc_selrefs /path/to/ObjCBinary  # 现代布局（链式 fixups）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，**地址/字节均为示意**，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__objc_selrefs) section
0000000100009100  00 3a 00 00 01 00 00 00      ; selref[0] → 0x10003a00 = __objc_methname "setName:"
0000000100009108  0c 3a 00 00 01 00 00 00      ; selref[1] → 0x10003a0c = __objc_methname "name"
0000000100009110  18 3a 00 00 01 00 00 00      ; selref[2] → 0x10003a18 = __objc_methname "length"
```

> 说明：左列是该槽自身的虚拟地址（从节 `addr` 起算），右列 8 字节是**小端**指针值（`00 3a 00 00 01 00 00 00` → `0x0000000100003a00`），逐个指向 `__objc_methname` 里的字符串首址。本节大小 `0x18` → 条目数 `0x18 / 8 = 3` 个。**这是磁盘上的初值（指向名字串）；进程加载并 fixup 后，这些槽会被回填成唯一 `SEL`，运行期读到的是 `SEL` 而非字符串地址。**

### 示例 2：`otool -ov` 把 selector 引用解析成名字

`otool -ov`（`-o` 解析 ObjC 元数据、`-v` 符号化）会把 selref 直接显示成它指向的方法名，比裸十六进制直观得多：

```bash
otool -ov /path/to/ObjCBinary                  # 完整 dump ObjC 段（含 selrefs 解析）
otool -ov /path/to/ObjCBinary | grep -A 2 -i selref   # 只看 selector 引用片段
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意 `otool -ov` 如何把 selref 槽解析回 selector 名字。

```text
Contents of (__DATA_CONST,__objc_selrefs) section
0x0000000100009100  0x0000000100003a00 setName:
0x0000000100009108  0x0000000100003a0c name
0x0000000100009110  0x0000000100003a18 length
```

> 说明：`otool -ov` 替你把每个槽的指针顺藤摸瓜解析到 `__objc_methname` 的字符串并打印出来（行尾的 `setName:`/`name`/`length`）。这正是逆向时定位"某段代码到底在调哪些方法"的常用手段——selref 表几乎就是这个二进制"用到的方法名清单"。

> [!note] 逆向提醒：从共享缓存抽出的 dylib 可能解析不出名字
> 当一个库被从 **dyld 共享缓存**单独抽取出来时，它的 selref 指针可能指向**抽取后已不在本文件内**的地址（名字串还留在共享缓存里）。此时 `otool`/Ghidra 等工具会显示成 `DAT_<address>` 这类裸地址、解析不出 selector 名。要正确解析，需用**感知共享缓存**的工具或在完整缓存环境下分析。

## FAQ

> [!question] `__objc_selrefs` 和 `__objc_methname` 到底什么关系？为什么要分两节？
> `__objc_methname` 存 **selector 名字符串本体**（`"setName:\0"`），类型 `S_CSTRING_LITERALS`、住**只读** `__TEXT`、可跨编译单元去重；`__objc_selrefs` 存**指向这些字符串的指针**，类型 `S_LITERAL_POINTERS`、住**可写** `__DATA`/`__DATA_CONST`、会被 runtime 回填成唯一 `SEL`。分两节是因为二者职责与权限都不同：**名字是只读的、可共享去重的"数据"**；**引用是每处使用一个、需要运行期改写的"指针"**。一个名字（methname 一份）可被多处 `@selector`（selrefs 多个槽）引用。简记：methname 是"字典词条"，selrefs 是"正文里引用该词条的脚注"。

> [!question] `@selector(foo)` 在二进制里到底变成了什么？
> 变成**对 `__objc_selrefs` 里某个槽的读取**。编译器把 `"foo"` 写进 `__objc_methname`，在 `__objc_selrefs` 建一个指向它的槽，并把 `@selector(foo)` 这处代码编译成"加载该 selref 槽的值"。**磁盘上**这个槽的值是名字字符串地址；**加载后**被 runtime 回填成全局唯一 `SEL`，所以运行时 `@selector(foo)` 求值得到的是那个唯一 `SEL` 指针，可直接用于 `objc_msgSend` 或 `respondsToSelector:`。整个过程对源码透明——你写 `@selector(foo)`，编译期占位、加载期回填替你把它接到唯一 selector 上。

> [!question] 既然名字都在 `__objc_methname` 了，为什么 runtime 还要逐个 `sel_registerName` 再回填？直接用字符串地址当 SEL 不行吗？
> 不行，因为**唯一性跨不了模块**。`__objc_methname` 的去重只在**单个链接产物内部**生效——你的 App 里 `"length"` 是一份，但系统库 Foundation 里也有自己的 `"length"`，两个二进制里这俩字符串是**不同地址**。若直接拿字符串地址当 `SEL`，跨库的同名 selector 就成了不同指针，`objc_msgSend` 的指针相等比较会失效。`sel_registerName` 的作用正是把"任意模块里任意一份同名字符串"都归一到**全进程同一个 `SEL`**（已注册返回既有、未注册才新建），回填后所有模块的该 selref 槽都指向这唯一一个 `SEL`——这才是 `objc_msgSend` 敢用指针相等做 cache key 的前提。

> [!question] 为什么 `__objc_selrefs` 要放在可写段，而不是和名字一样放只读 `__TEXT`？
> 因为它的槽**必须在加载期被改写**（从"名字串地址"回填成"唯一 `SEL`"），而 `__TEXT` 是只读的写不了。传统上它放 `rw-` 的 `__DATA`；现代二进制放 **`__DATA_CONST`**——这是一种"加载期可写、fixup 完再转只读"的折中：dyld 用链式 fixups 遍历回填完这些指针后，把页重新保护成只读，**既满足回填的写需求，又让运行期享受只读页的防篡改收益**。所以你会看到同一个 selref 节在老二进制属 `__DATA`、在新二进制属 `__DATA_CONST`，但语义一致。

> [!question] runtime 回填时为什么要判断"不相等才写"？
> 为了**避免把干净的共享内存页弄脏**。`map_selrefs` 里是 `if (sels[i] != sel) sels[i] = sel;`——只在槽里的值确实需要改变时才写。对经 **dyld 共享缓存预优化**的系统库，selref 槽在装载时**就已经是正确的唯一 `SEL`** 了，此时 `sels[i] == sel`，跳过写入就不会触发写时复制（COW）、不会把本可多进程共享的干净页变成各进程私有的脏页，**省内存**。这是 ObjC 启动优化（Snow Leopard 起"开销减半、每 app 省几百 KB"）的一个具体体现。

## 小结

- `__objc_selrefs` 是 **selector 引用表**：一张指针数组，每槽**初值指向 `__objc_methname` 的名字字符串**，编译期由 `@selector(...)`/方法调用生成；`flags` 典型 `0x10000005`（`S_LITERAL_POINTERS` + `S_ATTR_NO_DEAD_STRIP`），条目数 = `size ÷ 指针宽度`。
- **加载期**：runtime 在 `_read_images` 用 `_getObjc2SelectorRefs` 取节，对每个名字 `sel_registerName` 注册成**全局唯一 `SEL`** 并**回填槽位**（"不等才写"以省脏页）；注册前先 `sel_init(selrefCount)` 预分配表容量。
- **为何唯一化**：唯一 `SEL` 让 `objc_msgSend` 能用**指针相等**做方法缓存键，省去字符串比较，是消息派发快路径的根基；方法列表里的 selector 也同受此唯一化约束。
- **为何在可写段**：槽要被运行期回填，故放可写 `__DATA`；现代二进制放 `__DATA_CONST`（链式 fixups 回填后再只读化），dyld 共享缓存更会预先 unique 好、装载即正确。
- **四大引用节**：`selrefs`/`classrefs`/`superrefs`/`protorefs` 同型（加载期回填的指针数组），区别在被指本体；与"列表类"节（`classlist` 等）分管"我用什么" vs "我有什么"。
