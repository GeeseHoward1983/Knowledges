# 详解Mach-O(二十四)Mach-O __objc_methname节

> [!abstract] TL;DR
> **`__objc_methname` 是 Objective-C 方法名（selector 名字）的字符串池**：程序里出现过的每一个方法选择子（SEL）的文本——`alloc`、`init`、`setName:`、`setObject:forKey:`——都以 NUL 结尾的 C 字符串形式集中存放在这里。它住在只读可执行的 `__TEXT` 段（权限 `r-x`），是 [[18.Mach-O section]] 通用模型里又一个具体实例。
> 它的节类型与 [[20.Mach-O __cstring节]] 一样是 **`S_CSTRING_LITERALS`（`flags & SECTION_TYPE = 0x2`）**：物理形态就是一串 `\0` 分隔的 C 字符串，链接器同样能对它做去重合并。但它**专供 Objective-C 运行时**使用、被单独切成一节，而不是混进通用 `__cstring`——原因是 runtime 在加载期要对这些名字做 **SEL 唯一化（uniquing）**，需要一个"按段名就能稳定、批量定位全部 selector 名字"的入口。
> 真正把"字符串"变成"可用于发消息的 SEL"的，是它的搭档 [[35.Mach-O __objc_selrefs节]]：`__objc_selrefs` 里存的是**指向 `__objc_methname` 字符串的指针**；镜像加载时 runtime 遍历这些指针，把每个名字注册进全局 selector 表得到唯一 SEL，再把指针槽**回填**成该唯一 SEL。此后 `objc_msgSend(receiver, sel)` 拿到的就是这个全局唯一指针，方法缓存与方法列表全靠"指针相等"高速命中。
> 逆向价值：`__objc_methname` 几乎等于一份**未脱壳的 API 清单**——把它 dump 出来就能看到目标用了哪些方法、调了哪些系统 selector（`decryptData:`、`isJailbroken`、`stringWithFormat:`…），是还原 ObjC 程序行为的头号线索之一，与 [[25.Mach-O __objc_classname节]]、[[26.Mach-O __objc_methtype节]] 三节配合可拼出类与方法的大半骨架。

## 概述与定位

Objective-C 的方法调用不是 C/C++ 那样"按地址直接 call 函数"，而是**发消息**：`[receiver setName:@"x"]` 经编译器改写为 `objc_msgSend(receiver, @selector(setName:), @"x")`。这条消息里第二个参数 `@selector(setName:)` 的本质是一个 **SEL**（selector，选择子），而 SEL 在 Apple 的 runtime 实现里"就是一个唯一化后的字符串指针"——它指向的那段文本 `"setName:"`，正是存放在 `__objc_methname` 里。

把 `__objc_methname` 放进 Mach-O 的层级里看：

- 它继承 [[13.Mach-O __TEXT]] 段的**只读、可执行**属性（`r-x`）——selector 名字是编译期就定死的常量、运行期不应被改写，放进只读段恰如其分，也让多个进程共享同一份物理页。
- 它是 [[18.Mach-O section]] 通用模型里**类型为 `S_CSTRING_LITERALS` 的具体节**：用同一套 `section_64` 结构描述，区别只在 `sectname` 为 `__objc_methname`、`flags` 的类型位取 `0x2`。换言之，从"字节布局"角度它和 [[20.Mach-O __cstring节]] 是一模一样的 C 字符串池，工具甚至会把两者并排标成 "C-String Literals"。
- 它与 [[25.Mach-O __objc_classname节]]（类名字符串池）、[[26.Mach-O __objc_methtype节]]（方法类型编码字符串池）是**并列的三大 ObjC 元数据字符串池**，同属 `__TEXT`、同为 `S_CSTRING_LITERALS`，分别存"方法名/类名/方法签名"。
- 它与 [[35.Mach-O __objc_selrefs节]] 是**"名字本身" vs "对名字的引用"**的关系：本节存字符串，`__objc_selrefs` 存指向这些字符串的指针；前者是数据，后者是 runtime 加载期要原地修补（fixup）的"待绑定引用"。本系列把 ObjC 字符串池（24–26）与 ObjC 运行时引用类节（35–42）刻意分开编排，就是为了凸显这层"被指 / 去指"的分工。

一句话定位：**`__objc_methname` = `__TEXT` 段里、类型 `S_CSTRING_LITERALS`、专门存放 Objective-C selector 名字（方法名字符串）、供 runtime 做 SEL 唯一化的只读 C 字符串节**。

> [!note] 它和 `__cstring` 形态相同，为何不合并？
> 纯从"省地方"看，把 selector 名字直接塞进 [[20.Mach-O __cstring节]] 完全可行——它们都是 `\0` 结尾的 ASCII 串。Mach-O 仍把它们单列，是出于**语义/可定位性**而非格式：runtime 与各种工具（`otool -ov`、class-dump、Hopper/IDA 的 ObjC 解析器）需要"凭段名 `__objc_methname` 一把抓到全部 selector 名字"。混进 `__cstring` 后，selector 名字就会和提示文案、URL、格式串等混在一起，既无法批量识别、也破坏了"这一节里全是 selector"的不变量。详见下文第 2 节。

## 核心原理与字段详解

### 1. 内容布局：以 `\0` 分隔/结尾的 selector 名字紧凑排布

`__objc_methname` 的物理内容是**一整块连续字节**，里面是一个接一个、以 `\0`（0x00）分隔并收尾的 selector 名字。和 [[20.Mach-O __cstring节]] 完全一致——没有长度前缀、没有索引表、没有对齐填充（`align` 通常很小），字符串首尾相接、最省空间地塞在一起。

selector 名字的文本就是"方法名 + 每个参数后的冒号"：

- **无参方法**：名字不含冒号，如 `alloc`、`init`、`hash`、`description`、`isJailbroken`。
- **单参方法**：名字以一个冒号结尾，如 `setName:`、`addObject:`、`isEqual:`。
- **多参方法**：每个参数标签后各跟一个冒号，如 `setObject:forKey:`、`initWithFrame:style:`、`tableView:cellForRowAtIndexPath:`。冒号的**个数 = 参数个数**，这是阅读 selector 名字的关键：`a:b:c:` 是一个三参方法的完整名字，而不是三个名字。

举例，若程序里用到 `alloc`、`init`、`setName:` 三个 selector，节内字节可能是这样（首尾相接，各自 `\0` 收尾）：

```text
61 6c 6c 6f 63 00 | 69 6e 69 74 00 | 73 65 74 4e 61 6d 65 3a 00
a  l  l  o  c  \0 | i  n  i  t  \0 | s  e  t  N  a  m  e  :  \0
```

代码侧并不"按下标"访问它。编译器为每个用到的 selector 生成一个内部标号（典型如 `L_OBJC_METH_VAR_NAME_`），并不直接把这个字符串地址交给 `objc_msgSend`，而是**多绕一层**：在 `__objc_selrefs` 里放一个指向该字符串的指针，发消息时从那个指针槽**加载**出 SEL（见第 4 节）。这一层间接正是 SEL 能被"原地唯一化"的关键。

> [!note] 子串/后缀共享同样适用
> 因为 selector 名字也是 `\0` 结尾、紧凑排布，链接器对 `__cstring` 做的**后缀共享（tail merging）**对本节同样可能发生：若 `name` 恰是 `setName` 之外某个串的后缀，理论上可复用同一段尾巴和同一个 `\0`。逆向时若发现两个 selector 名字地址"套娃"重叠，多半就是它。不过对 selector 而言更常见的是**整串去重**（见下一节），因为 ObjC 程序里同一个 selector（如 `init`、`count`）会被海量复用。

### 2. 为什么把 selector 名字单列一节（而非混入 `__cstring`）

这是本节最该讲清的"设计意图"。形态上 `__objc_methname` 和 [[20.Mach-O __cstring节]] 没有任何区别——都是 `S_CSTRING_LITERALS` 的 C 字符串池。把它们分开，根因是 **Objective-C 运行时对 selector 有"全局唯一指针"的强需求，而满足这个需求要求 runtime 能稳定、批量地定位到"所有 selector 名字"**。

展开来看：

1. **SEL 必须全进程唯一**。ObjC 的方法分发、方法缓存（cache）、方法列表排序，全部依赖"同名 selector 在进程内是同一个指针"这一不变量。`objc_msgSend` 的快路是拿 SEL 当 key 去 cache 里做"指针相等"比较（见第 5 节），如果 `"init"` 在不同模块里是不同地址，cache 立刻失效、分发会错乱。所以加载期必须把"内容相同的 selector 名字"统统收敛到**唯一**的一个指针——这就是 **uniquing（唯一化）**。
2. **唯一化需要一个稳定的"全集入口"**。runtime 要唯一化，前提是能枚举出"这个镜像里出现过的全部 selector 引用"。它靠的是按段名取 `__objc_selrefs`（指针表），而这些指针指向的字符串若散落在通用 `__cstring` 里、和成千上万条无关文案混在一起，工具与人都无法"一眼框定 selector 集合"。把名字集中到专名段 `__objc_methname`，runtime/工具就能**凭段名直接处理**，语义清晰、边界明确。
3. **"段名即契约"带来工程便利**。class-dump、`otool -ov`、Hopper/IDA 的 ObjC 插件都默认"`__objc_methname` 里全是 selector 名字"，据此还原方法表。这层约定让生态工具不必去通用字符串池里"猜哪些是方法名"。

> [!note] 名字到底放哪一节，runtime 有多在意？
> 社区里有过实测：有人手工构造 ObjC 元数据时，把 selector 字符串**放错了节**（塞进 `__cstring` 而把指针放进 `__DATA,__const` 而非 `__objc_selrefs`），结果运行即崩——`NSForwarding: warning: selector for message 'hash' does not match selector known to Objective C runtime` 后 `unrecognized selector` 直接 abort；也有人报告"名字不在 `__objc_methname` 节时加载即 segfault"。但也有相反观点认为：**真正被 runtime 读取并据以注册的是 `__objc_selrefs`（指针表），名字字符串具体落在哪一节，runtime 源码里并无强校验**——只要指针在 `__objc_selrefs`、指向的内容是合法 NUL 结尾串即可。两种说法并不矛盾：编译器**约定俗成**把名字放 `__objc_methname`，工具据此识别；而 runtime 的硬依赖在 `__objc_selrefs` 这一侧。逆向时按"名字在 `__objc_methname`、引用在 `__objc_selrefs`"理解最稳妥。

> [!note] 链接器去重在这里收益更大
> 既然是 `S_CSTRING_LITERALS`，链接器 `ld` 跨 `.o` 合并相同字面量的"去重特权"同样作用于本节（机制详见 [[20.Mach-O __cstring节]] 第 3 节）。而 selector 的复用度远高于普通文案——`init`/`alloc`/`count`/`isEqual:`/`description` 这类几乎每个文件都用——所以**编译/链接期的 selector 名字去重收益极高**：最终二进制里每个不同的 selector 名字通常只留一份字符串。这只是"字符串层面去重一份字节"；真正保证"运行期同名 SEL 是同一指针"的是下文第 3 节加载期的 uniquing，二者层次不同、不要混淆。

### 3. SEL 注册：加载期的唯一化流程

这是 `__objc_methname` "活起来"的关键一步。注意：**编译/链接期的字符串去重只能保证"同一份二进制内每个名字存一份字节"，无法保证"运行期跨镜像同名 selector 是同一指针"**——多个动态库各自有自己的 `__objc_methname`，`"init"` 在 libA 和 libB 里是两个不同地址。把它们收敛成一个全局唯一 SEL，发生在**镜像加载期**，由 ObjC runtime 完成。

整体链路（dyld 把 libobjc 拉起后）：`_objc_init` 注册回调 → 每加载一批镜像，dyld 回调 `map_images` → `map_images_nolock` → **`_read_images`**（现代 `__OBJC2__` 运行时的核心读取函数）。`_read_images` 里有一段专门"修 selector 引用"的循环，是理解本节与 [[35.Mach-O __objc_selrefs节]] 协作的核心。现代 objc4 中它大致如下：

```cpp
// Fix up @selector references
// 注意：这一步必须在任何人使用方法列表之前完成，
// 因为「相对方法列表」直接指向 selrefs，并假定其已被唯一化。
static size_t UnfixedSelectors;
{
    mutex_locker_t lock(selLock);
    for (EACH_HEADER) {
        if (hi->hasPreoptimizedSelectors()) continue;   // 已被 dyld 预优化则跳过
        bool isBundle = hi->isBundle();
        SEL *sels = _getObjc2SelectorRefs(hi, &count);   // 取本镜像的 __objc_selrefs
        UnfixedSelectors += count;
        for (i = 0; i < count; i++) {
            const char *name = sel_cname(sels[i]);       // selref 槽里此刻还是「名字字符串地址」
            SEL sel = sel_registerNameNoLock(name, isBundle);  // 唯一化，拿到全局唯一 SEL
            if (sels[i] != sel) {
                sels[i] = sel;                           // 仅在不同才回写（避免弄脏 COW 页）
            }
        }
    }
}
```

逐步拆解：

1. **取引用表**：`_getObjc2SelectorRefs(hi, &count)` 按段名取出本镜像的 `__objc_selrefs`（一个 `SEL[]`）。此刻每个槽位里装的还是"指向 `__objc_methname` 中某个名字字符串的地址"。
2. **取名字**：`sel_cname(sels[i])` 把槽里的指针当 `const char *` 读出名字文本（如 `"setName:"`）——这正是去 `__objc_methname` 里取那段字节。
3. **唯一化注册**：`sel_registerNameNoLock(name, ...)` → `__sel_registerName(name, …)` 执行"查表-否则插入"：先 `search_builtins(name)`（含 dyld 共享缓存的预优化 selector），命中则直接返回；否则在全局集合 `namedSelectors`（现代实现是哈希集 `ExplicitInitDenseSet`，老实现是 `NXMapTable`）里查找，有则返回既有指针、无则插入一份。**这一步保证：任意两个内容相同的名字，最终都解析到同一个 SEL 指针**——这才是 SEL 唯一化的本质。
4. **条件回写**：若 `sels[i] != sel`（即槽里原本的"名字地址"和唯一化后的"规范 SEL"不同），就把槽位**改写**成规范 SEL；若相同（dyld 已预优化过）则**不写**，刻意避免触发 copy-on-write 把只读页弄脏，省内存。回写之后，`__objc_selrefs` 的每个槽里装的就不再是"名字地址"，而是"全局唯一 SEL"了。

```text
        加载前 __objc_selrefs[i]            加载后 __objc_selrefs[i]
   ┌─────────────────────────────┐     ┌─────────────────────────────┐
   │ &("setName:") ─┐            │  →  │  规范 SEL("setName:") ──┐    │
   └────────────────┼────────────┘     └─────────────────────────┼───┘
                    ▼                                              ▼
   __objc_methname: "setName:\0"        全局 selector 表中唯一的那个指针
   （字符串本体，原地不动）              （此后 objc_msgSend 用它当 cache key）
```

> [!note] 为什么这步必须"赶在方法列表之前"
> 源码注释点明：selector fixup 必须先于任何人使用方法列表，因为现代 Mach-O 的**相对方法列表（relative method lists）** 里，方法名不再是绝对指针，而是一个"指向 `__objc_selrefs` 槽位的相对偏移"，并**假定该槽位已被唯一化**。方法列表在 `fixupMethodList` 里被标记为 `uniqued`/`sorted`（其中一步还会**按 SEL 地址排序**以便二分查找）——这一切都建立在"selref 已经回填成规范 SEL"之上。所以 `_read_images` 严格按"先修 selrefs，再处理类与方法列表"的顺序执行。

> [!note] `+load` 在更后面
> 完成 selector 唯一化、类的实现化之后，runtime 才进入 `load_images` 调用各类的 `+load`。也就是说，等你的 `+load` 跑起来时，所有 selector 早已唯一化完毕、可安全发消息。本节字符串、`__objc_selrefs` 引用、SEL 唯一化、`+load` 调用，是"数据 → 引用 → 注册 → 执行"四个递进层次。

### 4. 与 `__objc_selrefs` 的引用关系（被指 vs 去指）

`__objc_methname` 和 [[35.Mach-O __objc_selrefs节]] 是一对必须连起来理解的搭档。编译器为"源码里写了 `@selector(...)` 或发了消息"这件事，会**同时**产出两块数据，二者各在一段：

```asm
    ; 名字本体放 __objc_methname（C 字符串）
    .section __TEXT,__objc_methname,cstring_literals
L_OBJC_METH_VAR_NAME_:
    .asciz "setName:"

    ; 指向名字的指针放 __objc_selrefs（字面量指针, 标 no_dead_strip）
    .section __DATA,__objc_selrefs,literal_pointers,no_dead_strip
    .p2align 3
L_OBJC_SELECTOR_REFERENCES_:
    .quad L_OBJC_METH_VAR_NAME_
```

要点：

- **`__objc_methname` 是"数据/被指方"**：它只是静态的 selector 名字字节，自己不引用任何东西，加载期**原地不动**（除非整页因别的原因被改）。
- **`__objc_selrefs` 是"引用/去指方"**：它的每个 `.quad` 槽位初始指向 `__objc_methname` 的某个名字；加载期被 runtime **就地修补**为规范 SEL（第 3 节）。注意它通常落在 `__DATA`/`__DATA_CONST` 段（可写或加载后变只读），因为它要被 fixup，而 `__objc_methname` 在只读 `__TEXT`、不被改。
- **`objc_msgSend` 取的是 selref，不是 methname**：发消息的指令是从 `__objc_selrefs` 的槽位**加载**出 SEL（`L_OBJC_SELECTOR_REFERENCES_[0]`），再交给 `objc_msgSend`。`__objc_methname` 只是这个 SEL "出生时"的名字来源，发消息热路径并不直接碰它。
- `no_dead_strip` 确保即便静态分析"看不出某 selector 被用到"，链接器也不会把这条引用误删——因为 ObjC 的动态性让"是否被用"无法静态断定。

一句话：**`__objc_methname` 提供"名字字符串"，`__objc_selrefs` 提供"指向名字、且会被唯一化的引用槽"；runtime 顺着 selrefs 找到 methname 里的名字、注册成唯一 SEL、把槽回填，发消息时再从槽里取这个唯一 SEL。**

> [!note] iOS 共享缓存里的演进（了解即可）
> 在 dyld 共享缓存中，selector 早已被 dyld **预优化（preoptimized）**并唯一化好——它把所有 selector 收进一个统一区域、建一张完美哈希表，libobjc 直接拿来当 builtin selector 列表用，省掉一半 ObjC 运行时启动开销、每个 app 省数百 KB 内存。更新的系统（如 iOS 27 的共享缓存）甚至让 ObjC 方法调用桩**直接 `ADRL` 把 selector 指针载入 `x1`**、不再经 `__objc_selrefs` 的 `LDR` 间接。这些都是"把第 3 节的唯一化工作提前到构建缓存时"的极致优化，但单独一个 app 二进制里"`__objc_methname` 存名字、`__objc_selrefs` 存引用"的基本结构不变，理解本节按此即可。

### 5. selector 在 `objc_msgSend` 消息机制中的角色

讲清 SEL 唯一化"为了什么"，就得看消息分发。`objc_msgSend(receiver, sel, ...)` 的工作是：拿 `receiver` 的 `isa` 找到类，再拿 `sel` 当 key 去查"这个类的方法实现 IMP"，找到就跳过去。它处在**几乎每次方法调用的最热路径**上，所以快路用手写汇编实现，核心是**方法缓存（cache）**：

1. 从 `receiver->isa` 取到类，再取类的 `cache`。
2. **用 SEL 算哈希下标**：arm64 上典型是 `index = (sel ^ (sel >> 7)) & mask`——注意它直接拿 **SEL 指针值**参与哈希。
3. 到对应 bucket，**比较 bucket 里存的 SEL 与传入的 `_cmd`（即本次的 sel）是否相等**——这是**指针相等比较**，不是 `strcmp`。
4. **命中（hit）**：直接 `br` 跳到 bucket 里缓存的 IMP（PAC 机型还会先认证指针）。整条快路在现代硬件上可低至 ~3 纳秒，且所有实参寄存器原样不动，被调方法收到的参数和"直接调用"无异。
5. **未命中（miss）**：落入 `__objc_msgSend_uncached` → C++ 的 `lookUpImpOrForward`，做完整的本类+超类方法表搜索、必要时触发 `+initialize`、方法决议（`resolveInstanceMethod:`）、最后才是消息转发；查到后把 `<sel, IMP>` 填进 cache，下次就走快路。

这条链路把第 3 节"为什么非要唯一化"彻底点明了：

- **cache 用 SEL 指针当 key、靠指针相等命中**。若 `"setName:"` 在不同模块是不同地址，第 2 步哈希到的下标、第 3 步的指针比较全部对不上——cache 永远 miss，分发退化到慢路，甚至命中错误条目。**唯一化把同名 selector 收敛成一个指针**，cache 才能稳定命中。
- **相对方法列表按 SEL 地址排序后二分查找**，同样依赖"SEL 是稳定唯一的地址"。
- 这也解释了 `sel_isEqual` 在 Apple runtime 里几乎等价于"指针相等"——因为 SEL 本就被设计成唯一指针。

所以 `__objc_methname` 虽然只是"存了一堆方法名字符串"，却是整套高速消息分发的**地基**：名字 → （selref 引用）→ 唯一 SEL → cache 的 key。没有这一节里稳定可定位的名字，runtime 无从建立"全局唯一 SEL"，`objc_msgSend` 的快路也就无从谈起。

### 6. 与通用 `__cstring` 的区别（对比表）

`__objc_methname` 与 [[20.Mach-O __cstring节]] 字节形态完全相同（都是 `S_CSTRING_LITERALS` 的 NUL 结尾 C 字符串池），差别全在**"装什么 + 谁来消费 + 工具如何识别"**：

| 维度 | `__objc_methname` | `__cstring`（见 [[20.Mach-O __cstring节]]） |
|---|---|---|
| 装什么 | ObjC selector 名字（方法名，含冒号，如 `setObject:forKey:`） | 任意 C 字符串字面量（文案、URL、格式串、路径…） |
| 节类型 `flags & 0xff` | **`S_CSTRING_LITERALS`（0x2）** | **`S_CSTRING_LITERALS`（0x2）**（相同） |
| 所在段 | `__TEXT`（`r-x`，只读） | `__TEXT`（`r-x`，只读）（相同） |
| 链接器去重 | **会**（且 selector 复用度高，收益大） | **会**（相同字面量合并一份） |
| 谁来引用/消费 | **被 `__objc_selrefs` 指向**，由 ObjC runtime 注册成唯一 SEL | 被 `__text` 代码以 `adrp+add`/`lea` 取地址，当 `const char*` 用 |
| 加载期是否参与 fixup | **是**——通过 `__objc_selrefs` 的回填间接参与（名字本身不动） | 否，纯静态数据 |
| 专用工具识别 | `otool -ov`、class-dump 据段名识别为"方法名集合" | 无专用语义，按普通字符串处理 |
| 逆向含义 | 近似一份 **API/方法清单**（用了哪些方法、调了哪些系统 selector） | 硬编码文本/密钥/格式串的富矿 |

要点提炼：

- **形态同、语义异**：两者在二进制里都是"一串 `\0` 分隔的字符串"，肉眼/`strings` 难分；真正的区别是**所属段名与消费者**——`__objc_methname` 的名字会被 `__objc_selrefs` 引用、被 runtime 唯一化成 SEL，而 `__cstring` 只是被代码当只读文本读取。
- **逆向取向不同**：分析 ObjC 程序"做了什么"，先看 `__objc_methname`（方法面貌）与 [[25.Mach-O __objc_classname节]]（类面貌）；找硬编码线索（C2、密钥、文案）则看 `__cstring`。`strings` 会把两者混在一起输出，要精确区分得用 `otool -s __TEXT __objc_methname` 单看本节。

> [!note] 三大 ObjC 字符串池的分工
> `__objc_methname`（方法名）、[[25.Mach-O __objc_classname节]]（类名，如 `NSObject`、`MyViewController`）、[[26.Mach-O __objc_methtype节]]（方法类型编码，如 `v24@0:8@16` 这种 `@encode` 串）三者并列，都是 `__TEXT` 段的 `S_CSTRING_LITERALS`。它们分别回答"方法叫什么名 / 类叫什么名 / 方法的参数与返回类型签名"，配合 `__objc_const`、`__objc_data` 里的类结构，就能拼出近乎完整的类-方法骨架——这正是 class-dump 能"还原头文件"的数据基础。

## 实操：用工具查看

### 示例 1：`otool -s __TEXT __objc_methname` dump 节的原始字节

`otool -s 段名 节名` 以"地址 + 十六进制 + ASCII"逐行 dump 指定节内容，是精确只看 `__objc_methname`（不混入其他字符串）的最直接方式：

```bash
otool -s __TEXT __objc_methname /path/to/ObjCBinary     # dump 本节原始字节（一串 \0 分隔的 selector 名）
otool -V -s __TEXT __objc_methname /path/to/ObjCBinary    # -V 让 otool 尝试解析得更可读
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/字节仅示意 `otool -s` 的逐行格式，实际数值以你机器上的 `otool` 为准。

```text
ObjCBinary:
Contents of (__TEXT,__objc_methname) section
0000000100003a00  61 6c 6c 6f 63 00 69 6e 69 74 00 73 65 74 4e 61  alloc.init.setNa
0000000100003a10  6d 65 3a 00 73 65 74 4f 62 6a 65 63 74 3a 66 6f  me:.setObject:fo
0000000100003a20  72 4b 65 79 3a 00 64 65 73 63 72 69 70 74 69 6f  rKey:.descriptio
0000000100003a30  6e 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  n...............
```

> 说明：左列是该行首字节的**虚拟地址**（从节 `addr` 起算）；中间是十六进制；右列是可打印 ASCII（不可打印字节显示为 `.`）。可见 `alloc\0`、`init\0`、`setName:\0`、`setObject:forKey:\0`、`description\0` 等 selector 名**首尾相接、各自以 `\0` 收尾**——这正是 `S_CSTRING_LITERALS` 的典型布局印证。注意带参方法的冒号个数等于参数个数（`setObject:forKey:` 两个冒号 = 两个参数）。

### 示例 2：`otool -ov` 解析 ObjC 元数据（看 selector 如何被引用）

`otool -ov`（`-o` 解析 ObjC 运行时信息、`-v` 可读化）会把 ObjC 段整体解析出来，能直观看到方法名与 `__objc_selrefs` 引用、方法列表的关联——比逐字节看 `__objc_methname` 更能体现"名字 → 引用 → SEL"的脉络：

```bash
otool -ov /path/to/ObjCBinary | less          # 解析全部 ObjC 元数据（类、方法、selrefs…）
otool -ov /path/to/ObjCBinary | grep -A2 selref   # 聚焦 selector 引用部分
```

> [!warning] 示例输出为示意
> 下列为构造样例，仅示意 `otool -ov` 把 selref 与其指向的 `__objc_methname` 名字关联起来的形式，实际字段/地址以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__objc_selrefs) section
0000000100008000  0x0000000100003a06   ; -> __objc_methname "init"
0000000100008008  0x000000010000xxxx   ; -> __objc_methname "setName:"
0000000100008010  0x000000010000xxxx   ; -> __objc_methname "setObject:forKey:"
...
Meta Class / Method list
   name      0x...  "setName:"          ; 方法名指向 __objc_methname
   types     0x...  "v24@0:8@16"        ; 类型编码指向 __objc_methtype
   imp       0x...  -[Foo setName:]
```

> 说明：`__objc_selrefs` 的每个槽位都标注了它指向的 `__objc_methname` 名字（如 `"setName:"`）——这就是第 4 节"selref 指向 methname"的可视化；方法列表里的 `name` 字段也指回 `__objc_methname`。**注意：在真实样本上，加载后内存里 selref 槽位会是规范 SEL 指针；而对磁盘上的静态文件，otool 解析出的是"指向名字字符串"的初始值。** 这正体现了第 3 节"加载期回填"前后的差异。

### 示例 3：从 selector 名字反查代码（逆向工作流缩影）

逆向 ObjC 程序常见套路是"先在 `__objc_methname` 找到关心的 selector，再回到反汇编找谁向谁发了这条消息"：

```bash
# 1) 先确认目标 selector 在 __objc_methname 里、拿到它的地址
otool -s __TEXT __objc_methname ./target | grep -i "decrypt"
# 2) 找 __objc_selrefs 里指向该名字的槽位地址（发消息时从这个槽加载 SEL）
otool -ov ./target | grep -B1 "decryptData:"
# 3) 反汇编 __text，搜索把该 selref 槽地址载入 x1、再 bl objc_msgSend 的指令
otool -tV ./target | grep -B3 -A1 "objc_msgSend"
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意"selector 名 → selref 引用 → 发消息代码"的关联过程。

```text
; __text 中某处（arm64）：取 receiver、把 "decryptData:" 的 selref 载入 x1，发消息
0000000100002a10  adrp  x8, 0x100008000        ; 定位到 __objc_selrefs 所在页
0000000100002a14  ldr   x1, [x8, #0x18]         ; x1 = selref["decryptData:"] → 唯一 SEL
0000000100002a18  bl    _objc_msgSend           ; [receiver decryptData:...] → 这附近就是解密调用点
```

> 说明：ObjC 里"找调用点"和纯 C 的 `__cstring` xref 略有不同——要找的是**把某个 `__objc_selrefs` 槽地址 `ldr` 进 `x1`、紧接 `bl objc_msgSend`** 的模式（而非直接取字符串地址）。顺着这个模式回到代码，就定位到了"向某对象发某 selector"的具体调用点（如解密、越狱检测、网络请求构造）。这也是 `__objc_methname` 作为 ObjC 逆向"切入点/富矿"的实操含义：它列出了全部"可被调用的方法名面貌"，是顺藤摸瓜的起点。

## FAQ

> [!question] `__objc_methname` 和 `__cstring` 都是 `S_CSTRING_LITERALS` 的只读 C 字符串池，到底差在哪？为什么要分两节？
> 字节形态确实一模一样——都是 `\0` 分隔的 C 字符串、都在 `__TEXT(r-x)`、链接器都能去重。差别全在**语义与消费者**：`__objc_methname` 里装的是 **ObjC selector 名字**，会被 [[35.Mach-O __objc_selrefs节]] 指向、被 runtime 在加载期注册成**全局唯一 SEL**（uniquing），是消息分发 cache 的 key 来源；`__cstring` 里装的是普通文本，只被代码当 `const char*` 读取，runtime 不关心。分两节的根因是**可定位性**：runtime 与工具（`otool -ov`、class-dump）需要"凭段名一把抓到全部 selector 名字"，混进 `__cstring` 会和海量无关文案纠缠、无法批量识别、破坏"本节全是 selector"的不变量。一句话：**`__objc_methname` 是"会被唯一化成 SEL 的方法名专池"，`__cstring` 是"普通只读文本池"。** 详见第 2、6 节。

> [!question] selector 既然就是字符串，运行时怎么保证"同名 selector 是同一个"？这个唯一化在哪一步发生？
> 发生在**镜像加载期**，由 ObjC runtime 完成，编译/链接期的字符串去重做不到这点（不同动态库各有自己的 `__objc_methname`，`"init"` 是不同地址）。流程是：dyld 加载镜像 → 回调 `map_images` → `_read_images` 里那段"fix up @selector references"循环：取本镜像的 `__objc_selrefs`，对每个槽位读出名字（去 `__objc_methname` 取字节）→ `sel_registerNameNoLock` 在全局表 `namedSelectors`（哈希集）里"查表否则插入"，拿到该名字**唯一**的 SEL → 若与槽里原值不同就把槽**回写**成这个唯一 SEL（相同则不写，避免弄脏 COW 页）。从此 `__objc_selrefs` 槽里是规范 SEL，`objc_msgSend` 拿它当 cache key 做指针相等比较。详见第 3 节。

> [!question] `objc_msgSend` 发消息时，到底用的是 `__objc_methname` 里的字符串，还是别的？
> 用的是**唯一化后的 SEL 指针**，不是直接拿 `__objc_methname` 的字符串。发消息的代码是从 [[35.Mach-O __objc_selrefs节]] 的槽位 `ldr` 出一个 SEL 载入 `x1`，再 `bl objc_msgSend`——这个 SEL 在加载期已被回填成全局唯一指针。`objc_msgSend` 的快路是拿这个 SEL **当 key 去类的方法缓存（cache）里做指针相等命中**（arm64 上还先 `sel ^ (sel>>7)` 哈希算下标），命中就直接跳 IMP，全程不做 `strcmp`。`__objc_methname` 里的字符串只是这个 SEL "出生时"的名字来源（加载期 `sel_registerName` 时读过一次），消息热路径并不再碰它。这正是为什么 SEL 必须唯一化——cache 靠指针相等，名字不唯一化则 cache 永远 miss。详见第 5 节。

> [!question] 逆向一个 ObjC 程序，`__objc_methname` 能告诉我什么？怎么从它定位关键逻辑？
> 它近似一份**未脱壳的方法清单**：把它 dump 出来（`otool -s __TEXT __objc_methname`），就能看到目标实现/调用了哪些方法名——`decryptData:`、`isJailbroken`、`validateReceipt:`、`stringWithFormat:` 之类往往直接暴露功能与系统 API 使用面。定位逻辑的套路是"名字 → 引用 → 调用点"：先在本节找到关心的 selector，再用 `otool -ov` 找到 `__objc_selrefs` 里指向它的槽位，最后在 `__text` 里搜"把该 selref 槽 `ldr` 进 `x1` 紧接 `bl objc_msgSend`"的模式，即定位到具体调用点。配合 [[25.Mach-O __objc_classname节]]（类名）与 [[26.Mach-O __objc_methtype节]]（方法签名），class-dump 类工具能据此还原出近乎完整的头文件。详见第 6 节与示例 3。

> [!question] selector 名字必须放在 `__objc_methname` 节里吗？放错节会怎样？
> 编译器**约定俗成**把名字放 `__objc_methname`、把指向它的指针放 `__objc_selrefs`，生态工具（class-dump、`otool -ov`、IDA/Hopper 的 ObjC 解析器）都默认这个布局来识别方法名。从 runtime 角度看，硬依赖其实在 **`__objc_selrefs`（指针表）这一侧**——runtime 遍历的是 selrefs、据此注册 SEL，对名字字符串具体落在哪一节并无强校验，只要指针指向合法 NUL 结尾串即可。社区实测过两种结果：有人把名字放错节导致加载 segfault/`unrecognized selector` abort（多半是连带把指针也没放进 `__objc_selrefs`、或破坏了相对方法列表的假定）；也有人认为"只要指针在 `__objc_selrefs`、名字在哪都行"。结论：**按"名字在 `__objc_methname`、引用在 `__objc_selrefs`"理解与构造最稳妥**，既满足工具识别、也满足 runtime 的引用侧依赖。详见第 2 节备注。

## 与相邻章节的关系

- [[35.Mach-O __objc_selrefs节]]：本节的"引用方"——存指向 `__objc_methname` 名字的指针，加载期被 runtime 唯一化、回填成规范 SEL，是"名字 → SEL"的桥梁；`objc_msgSend` 实际从它取 SEL。理解本节必须连它一起看。
- [[25.Mach-O __objc_classname节]]：并列的 ObjC 字符串池，存**类名**（`NSObject`、`MyViewController`…），同为 `__TEXT` 的 `S_CSTRING_LITERALS`，与方法名配合还原类骨架。
- [[26.Mach-O __objc_methtype节]]：并列的 ObjC 字符串池，存**方法类型编码**（`@encode` 串，如 `v24@0:8@16`），描述方法的参数与返回类型，与方法名一一对应。
- [[20.Mach-O __cstring节]]：通用 C 字符串池，与本节**字节形态相同但语义不同**——它是普通只读文本、不被 runtime 当 selector 处理；判断"某字符串是不是 selector"时必须区分二者。
- [[13.Mach-O __TEXT]]：本节的宿主段——`r-x` 只读属性来自它，selector 名字"运行期不可改"的根因在此。
- [[18.Mach-O section]]：本节是其通用模型的一个实例——`section_64` 结构、`flags` 类型位（这里取 `0x2`）等字段语义在那篇讲透。

## 小结

- `__objc_methname` 是 **Objective-C selector 名字（方法名）的字符串池**：`alloc`、`init`、`setObject:forKey:` 等以 `\0` 分隔、紧凑排布于只读可执行的 `__TEXT` 段，是 [[18.Mach-O section]] 模型里类型为 `S_CSTRING_LITERALS`（`flags & 0xff = 0x2`）的具体节。带参方法名的冒号个数 = 参数个数。
- 它与 [[20.Mach-O __cstring节]] **字节形态相同**（都是 `S_CSTRING_LITERALS` 的 C 字符串），却被**单列一节**——根因是 ObjC runtime 要对 selector 做**全局唯一化**，需要"凭段名稳定、批量定位全部 selector 名字"的入口；混进通用 `__cstring` 会破坏可定位性与"本节全是 selector"的不变量。
- 它的搭档是 [[35.Mach-O __objc_selrefs节]]：后者存**指向本节名字的指针**。加载期 runtime（`map_images` → `_read_images` 的 fixup 循环）遍历 selrefs，对每个名字调 `sel_registerNameNoLock` 在全局表里"查表否则插入"得到**唯一 SEL**，再把 selref 槽**回填**成该 SEL（相同则不写以省 COW 页）。这步必须先于方法列表处理，因为相对方法列表假定 selref 已唯一化。
- selector 在 `objc_msgSend` 中是**方法缓存的 key**：快路拿唯一 SEL 指针哈希算下标、做**指针相等**命中后直跳 IMP（~3ns）。这正是非要唯一化的原因——cache 靠指针相等，名字不唯一则永远 miss。`__objc_methname` 因此是高速消息分发的"地基"。
- **逆向价值**：本节近似一份 **API/方法清单**，dump 出来即见目标用了哪些方法、调了哪些系统 selector；定位逻辑走"名字 → `__objc_selrefs` 引用 → `ldr x1 + bl objc_msgSend` 调用点"，配合 [[25.Mach-O __objc_classname节]]、[[26.Mach-O __objc_methtype节]] 可还原类-方法骨架。
