# 详解Mach-O(三十六)Mach-O __objc_classlist节

> [!abstract] TL;DR
> **`__objc_classlist`（全名 `__DATA,__objc_classlist`，新式二进制里常落在 `__DATA_CONST,__objc_classlist`）列出本镜像「定义」的所有 Objective-C 类**：它是一张**指针数组**，每一项是一个指向类对象 `objc_class` 的指针——准确说指向编译期 emit 的那块类元数据（`isa`/`superclass`/`cache`/`bits`，其中 `bits` 当前指向只读的 `class_ro_t`）。
> 一个 `objc_class` 由**三层结构**刻画：① 编译期写死、放在 clean memory 的 **`class_ro_t`**（`name`/`baseMethods`/`ivars`/`baseProtocols`/`baseProperties`/`instanceStart`/`instanceSize`/`flags`…）；② 运行期可改、放在 dirty memory 的 **`class_rw_t`**（含 `flags`/`firstSubclass`，新式 runtime 用 `PointerUnion` 字段 `ro_or_rw_ext` 指向 ① 或 ③）；③ 惰性分配的 **`class_rw_ext_t`**（`methods`/`properties`/`protocols` 的多维数组，分类、运行期增删方法时才创建）。
> ObjC runtime 在镜像加载（`map_images` → `_read_images`）时调用 `_getObjc2ClassList(hi, &count)` 拿到本表，对每项调 **`readClass`**（读类名 → `addNamedClass` 经 `NXMapInsert` 写进全局命名类表 `gdb_objc_realized_classes` → `addClassTableEntry` 登记进 `allocatedClasses`），随后**惰性 realize**：普通类等首次收到消息才在 `lookUpImpOrForward` 路径上 `realizeClass`，把 `class_ro_t` 升级出 `class_rw_t`、连接父类/方法/属性。
> 它与"引用别处的类"的 [[40.Mach-O __objc_classrefs节]] 相对——一个是**定义清单**（本二进制实现了哪些 `@implementation`），一个是**引用清单**（本二进制代码用到哪些类）；它与 [[37.Mach-O __objc_nlclslist节]] 是"全集与子集"——后者只列实现了 `+load` 的**非惰性类**（须在加载早期就 realize）。逆向 ObjC 程序时，**枚举 `__objc_classlist` 就是列出"这个二进制定义了哪些类"的总入口**。

## 概述与定位

要让 `[MyClass new]`、`objc_getClass("MyClass")`、`[MyClass class]` 这些调用能工作，ObjC runtime 必须先**知道 `MyClass` 的存在、知道它的父类是谁、有哪些方法和成员变量、内存怎么排布**。这些信息编译期就由编译器写进了 `__DATA`（或 `__DATA_CONST`）段的一系列 `__objc_*` 节里，而 **`__objc_classlist` 就是那张"本镜像有哪些类"的总目录**：每个 `@implementation` 都会让编译器在这张表里压入一个指向对应类对象的指针。

把它放进 [[11.Mach-O Segments]] 与 [[18.Mach-O section]] 的框架里看：它本质上就是一个 **`S_REGULAR` 类型的普通指针数组节**（不是字符串节、不是符号桩节，`flags` 低 8 位 = `0x0`），节里没有任何"魔法结构"，就是 `count` 个连续的机器字（64 位每项 8 字节、32 位每项 4 字节），每个机器字是一个 VM 地址，指向同一镜像内某个 `objc_class`。它特殊在**语义**而非格式——runtime 和逆向工具都把它当作"遍历本镜像全部类"的标准入口。

它在一组 `__objc_*` 节里扮演"定义清单"的角色，和另外两张容易混淆的表形成三角关系，先在这里一次讲清，后文再展开：

- **`__objc_classlist`（本篇）= 定义**：本镜像**实现**了哪些类（每个 `@implementation` 一项）。runtime 用 `_getObjc2ClassList` 读它来 `readClass` + realize。
- **[[40.Mach-O __objc_classrefs节]] = 引用**：本镜像代码里**用到**哪些类（`[MyClass foo]` 会 emit 一项），无论该类定义在本镜像还是外部 framework。runtime 用 `_getObjc2ClassRefs` 读它来 `remapClassRef`（把引用槽 fix 成真实类指针）。
- **[[37.Mach-O __objc_nlclslist节]] = 非惰性子集**：`__objc_classlist` 中那些实现了 `+load` 的类的子集，须在加载早期**立即** realize（不能等惰性触发），runtime 用 `_getObjc2NonlazyClassList` 单独读它。

> [!note] 节名总要带段名，且它住在 `__DATA` 还是 `__DATA_CONST` 取决于工具链
> 按 [[18.Mach-O section]] 的约定，节名几乎从不单独出现，而是写作 `段名,节名`。本节经典写法是 `__DATA,__objc_classlist`；但启用链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）的现代 Apple 二进制里，由于表中指针在加载后被 fix 一次就不再变，编译器/链接器倾向把它移进**只读**的 `__DATA_CONST` 段以减少 dirty page，写作 `__DATA_CONST,__objc_classlist`。所以 `otool -s __DATA __objc_classlist` 查不到时，要再试 `__DATA_CONST`。两处的**内容与语义完全一致**，只是所属段的内存保护不同。

## 核心原理与字段详解

### 1. 内容：一张指向类对象的指针数组

`__objc_classlist` 节里**没有自定义结构体**，它就是一段连续的指针：

```c
// 概念上等价于（伪代码）：
struct objc_class * __objc_classlist[count];   // count = 节 size / 指针宽度
```

- **每一项**是一个机器字宽的 VM 地址：64 位 8 字节、32 位 4 字节。
- **条目数 `count`** 不另外存——和 [[18.Mach-O section]] 里符号指针节一样，靠 `节size / 指针宽度` 推算（runtime 里 `_getObjc2ClassList` 通过 `getsectiondata` 拿到节首地址与字节大小，再除以 `sizeof(void*)` 得到 `count`）。
- **每项指向**的是编译器为对应类 emit 的那块元数据，符号名形如 `_OBJC_CLASS_$_MyClass`（注意这是**类对象本身**，不是元类 `_OBJC_METACLASS_$_MyClass`，也不是类名字符串）。

类型上，objc4 把表项声明为 `classref_t`（本质是 `Class` 的别名/可被 fixup 的引用）。每个被指向的 `objc_class` 在现代 runtime（`objc-runtime-new.h`）里定义为：

```c
struct objc_class : objc_object {       // 继承 objc_object，故首字段就是 isa
    // Class ISA;                        // 来自 objc_object：指向"元类"
    Class superclass;                    // 父类；根类此字段为 nil
    cache_t cache;                       // 方法调用缓存（formerly cache pointer and vtable）
    class_data_bits_t bits;              // 低位是标志、& FAST_DATA_MASK 得 class_rw_t*
};
```

64 位下四个字段的偏移与大小是逆向时硬背的常数：

| 偏移 | 字段 | 大小 | 含义 |
|---|---|---|---|
| `0x00` | `isa` | 8 | 指向**元类**（metaclass）；类方法存在元类里 |
| `0x08` | `superclass` | 8 | 指向**父类** `objc_class`；根类为 `nil` |
| `0x10` | `cache` | 16 | `cache_t`：方法缓存（`_buckets` 指针 + `_mask` + `_occupied`） |
| `0x20` | `bits` | 8 | `class_data_bits_t`：`bits & FAST_DATA_MASK` → `class_rw_t*` |

> [!note] 两个数据结构、两个指针就撑起了整张类图
> ObjC 的类图（class graph）结构惊人地简洁：只靠 `objc_object`/`objc_class` 两种结构 + `isa`/`superclass` 两个指针即可构建。`isa` 把"对象→类→元类→根元类"串起来（决定**实例方法 vs 类方法**去哪找），`superclass` 把"类→父类→…→根类(`NSObject`，其 `superclass` 为 `nil`)"串起来（决定**继承链**）。`__objc_classlist` 给出的就是这张图里"本镜像定义的全部节点"的入口指针。

### 2. `class_data_bits_t bits` 与 `FAST_DATA_MASK`：从类对象拿到可读写数据

`bits` 不是一个干净的指针，而是**指针 + 低位标志**的复合字。要拿到真正的 `class_rw_t*`，必须先和掩码做与运算：

```c
struct class_data_bits_t {
    uintptr_t bits;
    class_rw_t* data() const {
        return (class_rw_t *)(bits & FAST_DATA_MASK);  // 抠掉低位标志位
    }
};
// 64 位：#define FAST_DATA_MASK 0x00007ffffffffff8UL
```

`bits` 的低几位被用来存"这个类是否有自定义 retain/release/alloc""是否 Swift 类"等**快路径标志**（FAST flags），这样 runtime 在热路径上一次取字就能同时拿到数据指针和关键标志。逆向时若想从一个类对象手动走到它的方法列表，路径就是：

```text
类对象首地址 + 0x20  →  读出 bits（一个机器字）
bits & 0x00007ffffffffff8  →  class_rw_t*
class_rw_t 里取 ro（或经 class_rw_ext_t 再取 ro）  →  class_ro_t*
class_ro_t.baseMethods / .ivars / .name …
```

> [!note] 为什么是偏移 `0x20`
> `isa(8) + superclass(8) + cache(16) = 32 = 0x20`，所以 `bits` 恒在类对象起始 `+0x20` 处。这是 LLDB / IDA / Hopper 里手动解析类结构时最常用到的一个偏移量。

### 3. 三层结构：`class_ro_t`（编译期/clean）、`class_rw_t`（运行期/dirty）、`class_rw_ext_t`（惰性扩展）

现代 runtime 把一个类的数据**拆成三层**，核心动机是 **clean memory vs dirty memory**——编译期就定死、永不修改的数据放进只读、可被多进程共享、可被系统在内存紧张时丢弃重读的 clean memory（即 `class_ro_t`）；运行期可能被改的数据（加分类方法、`class_addMethod`…）放进每进程私有、必须常驻的 dirty memory（`class_rw_t` / `class_rw_ext_t`）。这样能显著降低系统库那海量类的内存占用。

**① `class_ro_t`（read-only，编译期常量，clean memory）**

`__objc_classlist` 每项最初指向的类对象，其 `bits` 在加载之初指向的就是 `class_ro_t`（realize 前还没有 `class_rw_t`）。它直接 emit 在二进制里，**分类合并进来时也不会改它**：

```c
struct class_ro_t {
    uint32_t flags;              // RO_META(是元类) / RO_ROOT(根类) / RO_HAS_CXX_STRUCTORS …
    uint32_t instanceStart;      // 实例数据起始偏移（父类占完之后）
    uint32_t instanceSize;       // 实例对象总大小
#ifdef __LP64__
    uint32_t reserved;
#endif
    const uint8_t * ivarLayout;  // 强引用 ivar 的 GC/ARC 布局位图
    const char * name;           // 类名（C 字符串，指向 [[25.Mach-O __objc_classname节]]）
    method_list_t * baseMethodList; // 编译期方法列表（新式可为"小/相对"方法列表，故实际类型常为 void*）
    protocol_list_t * baseProtocols;// 编译期遵循的协议
    const ivar_list_t * ivars;      // 实例变量列表
    const uint8_t * weakIvarLayout; // 弱引用 ivar 布局位图
    property_list_t *baseProperties;// 编译期属性
};
```

注意 `class_ro_t` 里的方法/属性/ivar 列表都是 `method_list_t` / `property_list_t` / `ivar_list_t`（**一维**），因为只读表只装编译期内容、运行期不会再往上挂东西。其中 `instanceStart`/`instanceSize` 这对字段是 **ObjC 2.0 非脆弱 ivar（non-fragile ivars）/ ABI 稳定**的关键：父类即便后来增删了 ivar，子类也能在运行期重新计算自己 ivar 的偏移，无需重新编译。

**② `class_rw_t`（read-write，运行期，dirty memory）**

realize 之后 `bits` 改指向 `class_rw_t`。新式 runtime（objc-781+）里它**不再直接内嵌 `ro` 指针 + 三个数组**，而是用一个 `PointerUnion` 单字 `ro_or_rw_ext` 表达"要么直接指 `class_ro_t`、要么指 `class_rw_ext_t`"：

```c
struct class_rw_t {
    // Be warned that Symbolication knows the layout of this structure.
    uint32_t flags;              // RW_REALIZED / RW_REALIZING / RW_META / RW_CONSTRUCTING …
    uint16_t witness;
    explicit_atomic<uintptr_t> ro_or_rw_ext;  // PointerUnion<const class_ro_t, class_rw_ext_t>
    Class firstSubclass;         // 首个子类（构成兄弟链，用于遍历子类）
    Class nextSiblingClass;      // 下一个兄弟类
    // 经 ro()/ext() 访问器从 union 中安全取出 class_ro_t* 或 class_rw_ext_t*
};
```

**③ `class_rw_ext_t`（惰性分配的扩展，dirty memory）**

只有当一个类**真的需要可变的多维列表**时（被 attach 分类、运行期 `class_addMethod`/`class_addProperty` 等），runtime 才通过 `extAlloc` 惰性分配它；绝大多数从不被修改的类省下了这块开销：

```c
struct class_rw_ext_t {
    const class_ro_t *ro;        // 仍保留指向编译期只读表
    method_array_t methods;      // 多维：list_array_tt<method_t, method_list_t>
    property_array_t properties; // 多维
    protocol_array_t protocols;  // 多维
    char *demangledName;
    uint32_t version;
};
```

于是存在**两条取 `ro` 的链**：未被修改的类 → `class_rw_t.ro_or_rw_ext` **直接**指 `class_ro_t`（省内存）；被修改过的类 → `class_rw_t.ro_or_rw_ext` 指 `class_rw_ext_t`，再由它的 `ro` 指 `class_ro_t`。`extAlloc` 分配 `class_rw_ext_t` 时，会把 `ro->baseMethods()`/`baseProperties`/`baseProtocols` 通过 `attachLists` 灌进对应的多维数组里。

> [!note] "Symbolication knows the layout"——这些结构布局是被工具硬编码依赖的
> objc4 源码在 `class_rw_t` 上特意留了注释 `Be warned that Symbolication knows the layout of this structure`：符号化/调试工具（含 Apple 自家 Symbolication.framework、LLDB、第三方 Hopper/IDA）都按这套字段顺序与偏移去读类信息。这意味着这些结构的布局是**事实 ABI**，不能随意改；也意味着逆向时按上面给出的偏移去读是可靠的。

> [!note] `RO_META` / `RW_REALIZED`：怎么判断一个类是否已 realize、是不是元类
> `class_ro_t.flags & RO_META` 表示这是个**元类**（metaclass）的只读表；`class_rw_t.flags & RW_REALIZED` 表示该类**已被 realize**（已经从 `class_ro_t` 升级出 `class_rw_t`）。realize 进行中会同时打 `RW_REALIZING`。逆向静态文件时类都还没 realize，看到的是 `bits→class_ro_t`；在 LLDB 里看运行中进程时，已 realize 的类 `bits→class_rw_t`，可据 `RW_REALIZED` 区分两态。

### 4. 相对/小方法列表（relative method lists）与 `__DATA_CONST`

objc-781+ 引入了 **"小"方法列表（small / relative method lists）**：`class_ro_t.baseMethods` 指向的列表里，每个 `method_t` 不再存 `name`/`types`/`imp` 三个**绝对指针**，而是存**相对偏移**（32 位，相对自身地址）。好处有二：① 偏移是位置无关的，**加载时无需 rebase**，省掉一大批可写指针、缩小 dirty page；② 当类的 `ro` 和方法列表都落在 dyld 共享缓存里时，指针可免 ptrauth 认证，进一步减少签名指针数量。正因为可能是"小列表"也可能是传统"大列表"，新式头文件把 `baseMethodList`/`baseMethods` 的类型标成 `void*`，由 `baseMethods()` 在运行期判别（`isSmallList()` 时按相对列表解码、必要时做 `ptrauth_auth_data`）。

这也是 `__objc_classlist` 越来越多地出现在 **`__DATA_CONST`** 而非 `__DATA` 的根本原因：当表里的类指针与方法列表都不再需要运行期写改（靠链式 fixups 一次性绑定 + 相对偏移免 rebase），整张表就能放进只读段，享受多进程共享、不脏页的好处。逆向新二进制时若按老经验只在 `__DATA` 找而扑空，记得去 `__DATA_CONST`。

### 5. 加载期的类注册：`_read_images` → `readClass` → `addNamedClass` → `addClassTableEntry`

镜像被 dyld 映射后，`_objc_init` 注册的回调 `map_images` 最终进入 **`_read_images`**，这里对每个镜像头 `header_info *hi` 取出类表并逐个 `readClass`：

```c
// _read_images 内，概念流程：
classref_t const *classlist = _getObjc2ClassList(hi, &count);   // 读 __objc_classlist
for (i = 0; i < count; i++) {
    Class cls = (Class)classlist[i];                            // 取出第 i 个类指针
    Class newCls = readClass(cls, headerIsBundle, headerIsPreoptimized);
    // newCls 可能 == cls，可能为 nil（弱链接父类缺失），也可能是未来类预留的空间
}
```

**`readClass` 做了什么**：它把"编译器写出来的类"读进 runtime。核心动作是**读类名**，然后调 `addNamedClass(cls, mangledName, replacing)` 把"类名 → 类指针"登记到**命名类表**，再调 `addClassTableEntry(cls)` 把类登记进**全局类表**。一个直观的说法是：表里读出来本是一个**地址**，经 `readClass` 之后这个地址就和具体类的**符号名**关联起来了。

**`addNamedClass` 与 `NXMapInsert`**：`addNamedClass` 负责把 `name => cls` 插进**命名非元类映射表**。它先用 `getClassExceptSomeSwift(name)` 查是否已有同名类，若有且不同则告警"重复类名"（保留旧映射）；最终对普通类执行 `NXMapInsert(gdb_objc_realized_classes, name, cls)`——把类与类名写进那张**全局命名类表 `gdb_objc_realized_classes`**。这张表在 `_read_images` 首次进入时由 `NXCreateMapTable(...)` 创建一次（受 `doneOnce` 控制），容量按 3/4 装载因子预估。

**`gdb_objc_realized_classes` 这张表**：名字里的 `gdb_` 前缀点明它是**给调试器用的**——LLDB/GDB 可以用 `NXMapGet(gdb_objc_realized_classes, "ClassName")` 按名字捞类。它是 runtime 维护的"已知类名 → 类对象"主索引；`objc_getClass("Foo")` 本质上就是查它（外加 dyld 共享缓存表）。

**`addClassTableEntry`**：在命名登记之后，把类登记进**全部类的表 `allocatedClasses`**（这张表同时含类与元类；`addMeta` 为真时自动把元类也加进去）。`allocatedClasses` 在 `runtime_init`（由 `_objc_init` 调用）里初始化。`objc_getClassList`/`objc_copyClassList` 枚举的就是它。

> [!note] `readClass` 之前的预检：`mustReadClasses`
> `_read_images` 不会无脑遍历每张类表——它先用 `mustReadClasses(hi)` 预检"这个镜像到底需不需要读类"。若镜像已被 dyld 共享缓存预优化（`isPreoptimized()`）、且不含"弱链接父类可能缺失的类"、也没有待决的未来类（future class），就可以**跳过**读取，省掉启动开销。objc4 源码特意强调：`readClass` 的全部工作都被 `mustReadClasses` 预检覆盖，**改一个必须同步改另一个**，否则会漏读或错读。

### 6. 惰性 realize：普通类首次被消息时才完全初始化

登记进类表 ≠ 完全可用。把 `class_ro_t` 升级出 `class_rw_t`、连接父类与元类、（必要时）attach 分类方法、计算 ivar 偏移——这套重活叫 **realize**，由 `realizeClass`（新式委托给 `realizeClassWithoutSwift`）完成：

```c
// realizeClassWithoutSwift 概念流程：
const class_ro_t *ro = (const class_ro_t *)cls->data();   // realize 前 data() 即 ro
bool isMeta = ro->flags & RO_META;
class_rw_t *rw = objc::zalloc<class_rw_t>();               // 分配可写数据
rw->set_ro(ro);                                            // 经 PointerUnion 关联 ro
rw->flags = RW_REALIZED | RW_REALIZING | isMeta;
cls->setData(rw);                                          // bits 改指 class_rw_t
// 递归 realize superclass、metaclass，连接方法/协议/属性，计算 ivar 偏移…
```

关键在于**触发时机**：

- **普通（惰性）类**：加载期**只登记不 realize**。直到它**首次收到消息**，`objc_msgSend` 找不到缓存与方法时进入 `lookUpImpOrForward` → `realizeAndInitializeIfNeeded_locked` → … → `realizeClassWithoutSwift`，此时才真正 realize。"用到才初始化"摊平了启动成本。
- **非惰性类（实现了 `+load`）**：见第 7 节，加载期就被强制 realize。

> [!note] `realizeAllClasses` 默认并不在启动时跑
> runtime 里确实有个 `realizeAllClasses()`（遍历每个镜像、对 `_getObjc2ClassList` 的**全集**逐个 realize），但它**被 debug 开关 `DebugNonFragileIvars` 守着**，正常启动**不会**调用它——否则惰性 realize 的意义就没了。所以"列在 `__objc_classlist` 里" 只保证类被**登记**，不保证它在启动时就被 realize；真正强制 realize 全部类只发生在该调试模式下。

### 7. 与非惰性类 `__objc_nlclslist` 的区别：全集 vs `+load` 子集

`+load` 方法有个硬性语义：**必须在镜像加载早期、`main()` 之前、且早于任何消息发送就被调用**。这就要求其所属类不能等"惰性触发"，而要在加载期**立即 realize**。为此编译器把这些类单独再 emit 一份到 [[37.Mach-O __objc_nlclslist节]]（non-lazy class list），runtime 用 `_getObjc2NonlazyClassList` 读它：

```c
GETSECT(_getObjc2ClassList,        classref_t const, "__objc_classlist");  // 全部类
GETSECT(_getObjc2NonlazyClassList, classref_t const, "__objc_nlclslist");  // +load 子集
```

`_read_images` 里专门有一段"Realize non-lazy classes (for +load methods and static instances)"：遍历 `__objc_nlclslist`，对每项 `remapClass` 后 `addClassTableEntry` 并**立即 realize**。三句话记牢二者关系：

- `__objc_classlist` 是**全集**：本镜像定义的**所有**类都在里面（含实现了 `+load` 的）。
- `__objc_nlclslist` 是**子集**：只含实现了 `+load`（或被标为 non-lazy）的类，须**加载期立即 realize**。
- 不在 `__objc_nlclslist` 里的类 = 惰性类，**首次消息**才 realize。

> [!note] 怎样让一个类变成"非惰性"
> 当前让类进 `__objc_nlclslist` 的标准做法就是**给它实现 `+ (void)load`**。系统库（libdispatch、libtrace、objc、Foundation 等）大量使用非惰性类来保证自身基础设施早早就绪。社区也有提案希望加一个 attribute 直接标记 non-lazy（避免为"只想早 realize"而被迫写一个空 `+load`），但截至主流 runtime 仍以 `+load` 为准。

### 8. 与 `__objc_classrefs` 的区别：定义 vs 引用

这是 ObjC 节里最容易混淆的一对，务必分清（参见 [[40.Mach-O __objc_classrefs节]]）：

| 维度 | `__objc_classlist`（本篇） | `__objc_classrefs` |
|---|---|---|
| 语义 | 本镜像**定义/实现**了哪些类 | 本镜像**代码引用**了哪些类 |
| 何时 emit | 每个 `@implementation` 一项 | 每处 `[MyClass foo]` 之类的类引用一项 |
| 指向 | 本镜像内的 `objc_class` | 任意类（本镜像或外部 framework）的引用槽 |
| runtime 读取 | `_getObjc2ClassList` | `_getObjc2ClassRefs` |
| runtime 处理 | `readClass` + realize（建类） | `remapClassRef`（把引用槽 fix 成真实类指针） |
| 典型用途 | "这个二进制实现了哪些类" | "这个二进制调用了哪些类" |

编译 `[MyClass doStuff]` 时，编译器会从 `__objc_classrefs` 加载类指针、从 `__objc_selrefs`（见 [[35.Mach-O __objc_selrefs节]]）加载 selector，再 `b objc_msgSend`。加载期 runtime 对 `__objc_classrefs`（以及超类引用表 `__objc_superrefs`）的每一项调 `remapClassRef`，把它指向 realize 后的真实类对象——这是**类引用的 fix**，与普通 dyld 惰性绑定是不同的代码路径。

> [!note] 别被符号名 `OBJC_CLASSLIST_REFERENCES_$_` 骗了
> `__objc_classrefs` 节里的引用槽，符号名常长成 `OBJC_CLASSLIST_REFERENCES_$_`——名字里带了"CLASSLIST"，但它**属于 `__objc_classrefs`（引用），不是 `__objc_classlist`（定义）**。判断归属看**节名**，不要看这个有迷惑性的符号名。

### 9. 逆向枚举：为什么说它是"列出本二进制全部类"的总入口

ObjC 的动态派发让"谁调用了谁"在静态层面很难直接看出来（方法不是直接 call，而是经 `objc_msgSend` 发消息），但**"本二进制定义了哪些类"这个问题有确定答案**——就在 `__objc_classlist` 里。逆向工作流通常是：

1. 定位 `__objc_classlist` 节（`__DATA` 或 `__DATA_CONST`），按指针宽度切成 `count` 项。
2. 每项是一个类对象地址 → `+0x20` 取 `bits` → `& FAST_DATA_MASK` 取 `class_rw_t`（静态文件里此时仍是 `class_ro_t`）。
3. 从 `class_ro_t` 读 `name`（→ [[25.Mach-O __objc_classname节]]）、`baseMethods`（方法名/类型/IMP，注意可能是相对方法列表）、`ivars`、`baseProtocols`、`baseProperties`、`superclass`。
4. 据此重建类的声明骨架（类名、父类、方法签名、成员变量），这正是 Hopper/IDA 的 "Objective-C class" 视图、`class-dump`、`otool -ov` 在做的事。

换言之，`__objc_classlist` + 每个类的 `class_ro_t` 链，足以**离线还原出整个二进制的类层次与接口**，不需要运行它。

## 实操：用工具查看

### 示例 1：`otool -ov` 解析全部 ObjC 类元数据

`otool -o`（`-v` 增加可读性）会顺着 `__objc_classlist` 把每个类的名字、父类、方法、协议、属性逐项解析出来——这是最快"看这个二进制定义了哪些类"的方式：

```bash
otool -ov /path/to/ObjCBinary | less        # 解析类/方法/协议/属性
otool -ov /path/to/ObjCBinary | grep -E 'class_(ro|rw)_t|name 0x|baseMethods'
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__objc_classlist) section
00000001000091a0 0x100008338 _OBJC_CLASS_$_AppDelegate
           isa   0x1000083b0 _OBJC_METACLASS_$_AppDelegate
    superclass   0x0  (NSObject 经 fixup 后填入)
         cache   0x0
        vtable   0x0
          data   0x100006120 (struct class_ro_t *)   ; realize 前 bits→class_ro_t
                    flags 0x80                        ; (RO_HAS_CXX_STRUCTORS 之类，示意)
            instanceStart 8
             instanceSize 8
                     name 0x100003f00 AppDelegate     ; 指向 __objc_classname
              baseMethods 0x100006040 (method_list_t *)
                    entsize 24  count 3
                      name  0x... application:didFinishLaunching...
                      types 0x... v@:@@
                      imp   0x100001abc -[AppDelegate application:...]
             baseProtocols 0x...
                    ivars 0x0
           baseProperties 0x...
```

> 说明：`__objc_classlist` 那一行打印出**类指针指向哪个 `_OBJC_CLASS_$_` 符号**；`otool -ov` 接着替你顺 `data → class_ro_t` 把 `name`/`baseMethods`/`ivars` 等解析出来。可见每个 `@implementation` 在这里就是一个表项 + 一套 `class_ro_t` 元数据。`superclass`/`cache` 在静态文件里多为 0，加载期才由 runtime 填。

### 示例 2：`otool -s __DATA __objc_classlist` 直接 dump 原始指针

想看"这张表本身的裸字节"（一串指针），用 `otool -s 段名 节名`；查不到就把段名换成 `__DATA_CONST`：

```bash
otool -s __DATA       __objc_classlist /path/to/ObjCBinary    # 经典位置
otool -s __DATA_CONST __objc_classlist /path/to/ObjCBinary    # 启用链式 fixups 的现代二进制
otool -V -s __DATA __objc_classlist /path/to/ObjCBinary       # -V 尝试把指针解析成符号名
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意"地址 + 指针值"的逐行格式与"指针指向类对象"的事实。

```text
Contents of (__DATA,__objc_classlist) section
00000001000091a0  38 83 00 00 01 00 00 00   → 0x100008338  _OBJC_CLASS_$_AppDelegate
00000001000091a8  90 84 00 00 01 00 00 00   → 0x100008490  _OBJC_CLASS_$_ViewController
00000001000091b0  e8 85 00 00 01 00 00 00   → 0x1000085e8  _OBJC_CLASS_$_Model
```

> 说明：左列是表项在文件/内存里的地址，中间 8 字节小端就是一个指针，右侧是它指向的类对象（`_OBJC_CLASS_$_*`）。节大小 / 8 = 表项数（这里若节是 0x18 字节即 3 个类）。注意指向的是**类对象**而非类名字符串，也非元类。`-V` 能否解析出符号名取决于符号是否被 strip。

### 示例 3：用 LLDB 在运行中进程枚举与解析

在真机/模拟器调试时，可直接问 runtime 要类，或顺着 `bits` 偏移手解：

```text
(lldb) image lookup -rn '_OBJC_CLASS_\$_'      # 列出本镜像定义的类符号
(lldb) po (Class)objc_getClass("ViewController")
(lldb) x/3gx 0x100008490                        # 看类对象前 3 个机器字: isa/superclass/cache...
(lldb) p/x *(uintptr_t*)(0x100008490 + 0x20)    # 读 bits
(lldb) p (class_rw_t*)( *(uintptr_t*)(0x100008490+0x20) & 0x00007ffffffffff8ULL )  # → class_rw_t*
```

> [!warning] 示例输出为示意
> 地址为构造；`gdb_objc_realized_classes` 是 runtime 的命名类主表，已 realize 的类才查得到。

```text
(lldb) p (void*)NXMapGet(gdb_objc_realized_classes, "ViewController")
(void *) $0 = 0x0000000100008490            ; 已 realize → 命中
(lldb) p (void*)NXMapGet(gdb_objc_realized_classes, "DoesNotExist")
(void *) $1 = 0x0000000000000000            ; 不存在 → nil
```

> 说明：`NXMapGet(gdb_objc_realized_classes, name)` 正是 `addNamedClass` 经 `NXMapInsert` 填的那张表的反向查询；惰性类在被消息触发 realize 前可能查不到，这与第 5、6 节的注册/realize 时序一致。

## FAQ

> [!question] `__objc_classlist` 里到底存的是什么——类名？类对象？元类？
> 存的是指向**类对象（`objc_class`）本身**的指针，符号形如 `_OBJC_CLASS_$_MyClass`。它**不是**类名字符串（类名在 `class_ro_t.name`，指向 [[25.Mach-O __objc_classname节]]），也**不是**元类（元类是 `_OBJC_METACLASS_$_MyClass`，由类对象的 `isa` 指向）。每个 `@implementation` 在表里占一项；顺着这一项 `+0x20` 取 `bits`、`& FAST_DATA_MASK` 取数据指针，再到 `class_ro_t` 才能拿到类名、方法、ivar 等。

> [!question] 它和 `__objc_classrefs` 名字这么像，到底差在哪？
> 一字之差，语义相反：**`__objc_classlist` 是"定义"**——本镜像**实现**了哪些类（`@implementation` 驱动），runtime 用 `_getObjc2ClassList` 读它去 `readClass` + realize 建类；**`__objc_classrefs` 是"引用"**——本镜像**代码用到**哪些类（`[Foo bar]` 驱动，被引用的类可能定义在外部 framework），runtime 用 `_getObjc2ClassRefs` 读它去 `remapClassRef` 修引用槽。一个回答"我实现了谁"，一个回答"我调用了谁"。另外别被 `__objc_classrefs` 里 `OBJC_CLASSLIST_REFERENCES_$_` 这个带"CLASSLIST"的符号名误导——看节名，它属于 classrefs。

> [!question] 列在 `__objc_classlist` 里的类，是不是启动时就全部初始化好了？
> 不是。列入此表只保证类被 **`readClass` 登记**（写进命名类表 `gdb_objc_realized_classes` 和全局类表 `allocatedClasses`），**不等于被 realize**。普通类是**惰性 realize**——首次收到消息时才在 `lookUpImpOrForward` 路径上 `realizeClass`（把 `class_ro_t` 升级出 `class_rw_t`、连接父类与方法）。只有实现了 `+load` 的**非惰性类**（单列在 [[37.Mach-O __objc_nlclslist节]]）会在加载期就立即 realize。强制 realize 全集的 `realizeAllClasses()` 仅在 `DebugNonFragileIvars` 调试开关下才跑，正常启动不会。

> [!question] 为什么我在 `__DATA` 段下用 `otool -s` 找不到 `__objc_classlist`？
> 多半因为目标是**启用了链式 fixups 的现代二进制**，编译器把这张表移进了**只读的 `__DATA_CONST` 段**（表里指针加载后 fix 一次即不再变，放只读段可省 dirty page、多进程共享）。改用 `otool -s __DATA_CONST __objc_classlist` 即可。两处内容与语义完全相同，区别只是所属段的内存保护。同理逆向时定位这张表要同时考虑 `__DATA` 与 `__DATA_CONST`。

> [!question] 从一个类对象地址，怎么手动走到它的方法列表？
> 固定路径（64 位）：① 类对象首地址 `+0x20` 读出 `bits`（一个机器字）；② `bits & 0x00007ffffffffff8`（`FAST_DATA_MASK`）得 `class_rw_t*`（静态文件里 realize 前是 `class_ro_t*`）；③ 取 `ro`——若 `ro_or_rw_ext` 直接指 `class_ro_t` 就是它，否则经 `class_rw_ext_t.ro` 再取；④ 从 `class_ro_t.baseMethods` 拿方法列表（注意新式可能是"小/相对"方法列表，每个 `method_t` 是相对偏移而非绝对指针，需按 `entsize` 的小列表格式解码）。`name`、`ivars`、`baseProtocols`、`baseProperties` 同样在 `class_ro_t` 里。

## 与相邻章节的关系

- [[25.Mach-O __objc_classname节]]：每个类的 `class_ro_t.name` 指向那里——存的是类名的 C 字符串。
- [[37.Mach-O __objc_nlclslist节]]：本表（全集）中实现了 `+load` 的**非惰性子集**，须在加载期立即 realize；由 `_getObjc2NonlazyClassList` 单独读取。
- [[40.Mach-O __objc_classrefs节]]：本镜像**引用**的类（含外部），与本表的"**定义**"相对；由 `_getObjc2ClassRefs` 读取、`remapClassRef` 修复。
- [[35.Mach-O __objc_selrefs节]]：`[obj sel]` 调用里 selector 的引用表，与 `__objc_classrefs` 一起喂给 `objc_msgSend`。
- [[18.Mach-O section]]：本节就是一个 `S_REGULAR` 的指针数组节，"条目数 = 节size / 指针宽度"等通用规则出自那篇。

## 小结

- `__objc_classlist`（`__DATA` 或 `__DATA_CONST`，`S_REGULAR`）是本镜像所有 ObjC 类的**指针清单**，每项指向一个 `objc_class`（即 `_OBJC_CLASS_$_*`），条目数 = 节size / 指针宽度。
- `objc_class` 是**三层结构**：编译期只读的 `class_ro_t`（clean，`name`/`baseMethods`/`ivars`/`baseProtocols`/`baseProperties`/`instanceStart`/`instanceSize`/`flags`）、运行期可写的 `class_rw_t`（dirty，用 `PointerUnion` 的 `ro_or_rw_ext` 指向 ro 或 ext）、惰性分配的 `class_rw_ext_t`（多维 `methods`/`properties`/`protocols`）。`bits & FAST_DATA_MASK`（偏移 `0x20`）取数据指针。
- runtime 加载期经 `_read_images` → `_getObjc2ClassList` 遍历本表 → `readClass`（读名）→ `addNamedClass`/`NXMapInsert` 写入命名类表 `gdb_objc_realized_classes` → `addClassTableEntry` 登进 `allocatedClasses`。
- **惰性 realize**：普通类首次被消息时才 `realizeClass`（升级出 `class_rw_t`、连父类/方法）；实现 `+load` 的**非惰性类**单列于 [[37.Mach-O __objc_nlclslist节]]、加载期立即 realize。`realizeAllClasses()` 仅 debug 开关下跑。
- 它是"**定义**"清单，与"**引用**"清单 [[40.Mach-O __objc_classrefs节]] 相对；是逆向**枚举本二进制全部类、离线还原类层次/接口**的总入口。
