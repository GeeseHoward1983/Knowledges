# 详解Mach-O(三十一)Mach-O __nl_symbol_ptr节

> [!abstract] TL;DR
> **`__nl_symbol_ptr`（non-lazy symbol pointer，非惰性符号指针表）是一张"加载即绑定、运行期不变"的外部引用指针表**：每个槽位是一个指针，由 `dyld` 在镜像**加载阶段**就一次性绑定（bind）到目标符号的真实地址，**不等首次使用**——这与惰性的 [[30.Mach-O __la_symbol_ptr节]]（首次调用才绑定）正好相对。
> 它的节类型是 `S_NON_LAZY_SYMBOL_POINTERS`（`flags & SECTION_TYPE == 0x6`，见 [[18.Mach-O section]]），面向**无法惰性化的引用**：外部**数据**符号（全局变量没有"调用"这个触发点）、对函数**取地址**（`&func`，要立刻拿到真值）、以及链接器判定"必须早绑定"的引用。每槽宽度 = 指针宽度（64 位 8 字节 / 32 位 4 字节），条目数 = `size / 指针宽度`；`reserved1` 存它在**间接符号表**里的起始索引（联动 [[06.Mach-O LC_DYSYMTAB]]），用来反查每个槽对应的符号名。
> 与它同类型（`0x6`）的还有**全局偏移表 `__got`**——两者本质都是"加载时绑定的指针表"，差别只是历史习惯（`__got` 偏重函数地址、`__nl_symbol_ptr` 偏重数据）。现代工具链把这类非惰性指针统一组织进 `__got`，并整体搬进 [[15.Mach-O __DATA_CONST]]：加载期临时可写以便 `dyld` 填地址，**绑定完成后整段转为只读**，既满足"早绑定"又获得"运行期不可篡改"的安全收益。一个关键的自举细节：惰性绑定所依赖的 `dyld_stub_binder` 本身，其指针就**非惰性地**存在这里——它必须先被绑定好，才能去解析别人，从而打破"绑定器要靠绑定才能用"的死锁。

## 概述与定位

[[18.Mach-O section]] 把所有节统一抽象成 `section_64`，并指出 `flags` 低 8 位的**类型**决定 `dyld`/链接器的根本处理方式。`__nl_symbol_ptr` 就是类型为 `S_NON_LAZY_SYMBOL_POINTERS`（`0x6`）的那一类节的代表——它和 `__la_symbol_ptr`（`S_LAZY_SYMBOL_POINTERS`，`0x7`）、`__stubs`（`S_SYMBOL_STUBS`，`0x8`）一起，构成 Mach-O **动态符号绑定**机制的三块拼图。

要理解它存在的必要性，先回答一个问题：**为什么不能所有外部引用都惰性绑定？** 惰性绑定的本质是"把符号解析推迟到第一次真正用到时"，而它依赖一个统一的**触发点**——对函数而言就是"第一次调用"，调用会先落到一段桩代码（`__stubs`），桩再去触发 `dyld` 解析、回填指针。但有两类引用**没有这个触发点**：

- **外部数据符号**：引用另一个库里的全局变量（如 `extern int errno;` 的底层、或某个共享的全局对象）。数据没有"被调用"这一动作，编译器拿到它时就是直接读/写内存，无从插入"首次访问才解析"的桩；所以它必须在**加载时**就有真实地址。
- **对函数取地址而非调用**（`void *p = &printf;`）：这里要的是函数的**地址值本身**，要把它存进一个变量、传给别人，而不是立刻跳转执行。既然地址值要立刻参与运算，就不能再延迟解析。

这些"加载后立刻就要用、且无法走惰性桩"的引用，统统放进 `__nl_symbol_ptr`，由 `dyld` 在加载阶段**一次性全部绑定**。它在概念上对应 ELF 里 GOT 的非惰性部分（`-z now` 强制早绑定时的那批槽）。可以一句话定位：

- **`__la_symbol_ptr`（惰性）**：面向"可以等等再说"的外部**函数调用**，省启动时间，把解析成本摊到"真用到时"。
- **`__nl_symbol_ptr`（非惰性）**：面向"必须现在就准备好"的外部**数据/取址**引用，启动时一把绑定，运行期再不变。

> [!note] 节名是约定，类型才是身份
> 和 `__bss`/`__cstring` 一样，`__nl_symbol_ptr` 这个**名字只是惯例**，真正决定它"是非惰性符号指针表"的是节头 `flags` 里的类型位 `S_NON_LAZY_SYMBOL_POINTERS`（`0x6`）。换言之，链接器即便给它改个名，只要类型还是 `0x6`，`dyld` 与工具就照样按"加载时绑定的指针表"处理；反过来，一个名为 `__got` 的节若类型同为 `0x6`，行为与 `__nl_symbol_ptr` 完全一致。解析时**永远以类型为准、别认名字**（这一"以类型为准"的原则贯穿 [[18.Mach-O section]] 全篇）。

## 核心原理与字段详解

### 1. `S_NON_LAZY_SYMBOL_POINTERS`：类型即"加载时绑定"

来自 `<mach-o/loader.h>` 的节类型定义（节选，完整 256 种类型表见 [[18.Mach-O section]] 第 7 节）：

```c
#define S_NON_LAZY_SYMBOL_POINTERS  0x6  /* section with only non-lazy symbol pointers */
#define S_LAZY_SYMBOL_POINTERS      0x7  /* section with only lazy symbol pointers */
#define S_SYMBOL_STUBS              0x8  /* section with only symbol stubs */
```

一个节是否属于 `__nl_symbol_ptr` 这一类，判定方式就是 `flags & SECTION_TYPE == 0x6`（`SECTION_TYPE = 0x000000ff`）。这个类型对 `dyld`/链接器只表达一件事：**本节里全是"非惰性"符号指针，必须在加载时绑定**。`loader.h` 对这两类指针节与桩节的注释明确写道——"对这两类符号指针节和符号桩节，它们在间接符号表里有对应条目；本节每个条目，在间接符号表中按相同顺序排列，起始于节头 `reserved1` 字段记录的索引"。

非惰性的语义还隐含一条"硬约束"：**绑定失败 = 加载失败**。因为这些符号是加载阶段就要确定的，如果某个外部符号找不到（缺库、符号被移除等），`dyld` 无法把对应槽填成真实地址，**整个镜像直接加载失败**（而不是像惰性那样拖到"首次调用"才报错）。这也是"非惰性"在健壮性上与"惰性"的一个实质差异。

### 2. 非惰性指针机制：加载时 dyld 立即 bind，运行期不变

把一个 `__nl_symbol_ptr` 槽从"出厂"到"可用"的生命周期拆开看：

1. **静态链接阶段（`ld`）**：链接器为每个非惰性外部引用在本节里**预留一个指针槽**，并在 `LC_DYLD_INFO_ONLY` 的 bind 信息（或 `LC_DYLD_CHAINED_FIXUPS` 的 fixup 链）里登记一条"绑定指令"——记录"这个槽要绑到哪个库的哪个符号"。此时磁盘文件里这些槽**多为全 0 占位**（真实地址要等运行期才知道）。
2. **加载阶段（`dyld`）**：镜像被映射进内存后，`dyld` 解析 bind 信息（见 [[17.Mach-O LC_DYLD_INFO_ONLY]]），**逐槽计算并写入真实地址**——目标符号在其所属库里的运行期地址（已含该库的 ASLR 滑移 slide）。这一步在**进入 `main` 之前**完成。
3. **运行期**：所有非惰性槽都已是真实地址，**此后不再变化**。代码读这个槽就直接拿到目标地址，没有任何"首次触发解析"的开销，也没有 `dyld` 的参与。

与惰性指针最大的不同就在第 2、3 步：惰性槽的初值指向 `__stub_helper`、要到"首次调用"才由 `dyld_stub_binder` 回填；而非惰性槽在加载阶段就被一把填好，**没有"首次调用触发"机制**——因为它面向的引用（数据/取址）根本没有统一的调用入口可供拦截。

> [!note] 启动 vs 运行期的成本权衡
> 非惰性绑定把符号解析成本**前置到启动**：加载时多花一点时间把所有槽绑好，换取运行期"零解析开销、直接命中"。惰性绑定相反——启动快，但每个符号第一次用时要付一次解析代价。一个有意思的趋势：**当代 `dyld` 已倾向把一切都按非惰性处理**（类似 Linux 默认 `-z now`），惰性路径逐渐退化为历史包袱（详见第 4 节）。

### 3. 面向数据符号 / 取函数地址 / 不可惰性的引用

`__nl_symbol_ptr`（及同类型的 `__got`）承载的，正是那些"无法或不应惰性化"的引用，典型有三类：

- **外部数据符号引用**：引用其他库导出的**全局变量/全局对象**。如 C 运行时的 `environ`、`__stderrp` 之类，或自定义库里的 `extern` 全局量。数据访问是直接的内存读写，没有桩可插，必须加载时就有真值。
- **对函数取地址（`&func`）**：把外部函数的地址当**数据值**使用——存进函数指针变量、塞进回调表、做相等比较等。要的是地址本身，不是"现在跳过去执行"，所以不能延迟。
- **链接器/编译器判定"必须早绑定"的其它引用**：例如某些被 `__attribute__((constructor))` 初始化器在 `main` 之前就要用到的符号、或编译策略/链接选项要求早绑定的引用。这类一旦延迟就可能"用到时还没绑好"，故归入非惰性。

一句话概括判定标准：**凡是"加载后立刻就要用、且没有调用触发点可供惰性化"的外部引用，都走 `__nl_symbol_ptr`/`__got`**。

### 4. 与 `__got` 的关系：同类型，现代统一走 GOT

`__got`（Global Offset Table，全局偏移表）与 `__nl_symbol_ptr` **共享同一个节类型 `S_NON_LAZY_SYMBOL_POINTERS`（`0x6`）**——这是理解两者关系的钥匙：它们本质是**同一种东西**（加载时绑定的指针表），区别只在历史习惯上的"分工命名"：

| 维度 | `__nl_symbol_ptr` | `__got` |
|---|---|---|
| 节类型 `flags & 0xff` | `S_NON_LAZY_SYMBOL_POINTERS (0x6)` | `S_NON_LAZY_SYMBOL_POINTERS (0x6)` |
| 绑定时机 | 加载时（非惰性） | 加载时（非惰性） |
| 传统偏重 | 非惰性**数据**指针 | 导入**函数**地址 |
| 现代归属段 | 多并入 `__got` | `__DATA_CONST`（只读化） |
| `reserved1` | 间接符号表起始索引 | 间接符号表起始索引 |
| 每槽宽度 | 指针宽度（8/4 字节） | 指针宽度（8/4 字节） |

**现代工具链的实际做法是"统一走 `__got`"**：把所有非惰性指针（无论指数据还是指函数）都组织进 `__got`，不再单独保留一个 `__nl_symbol_ptr`。所以你在新的 arm64 二进制里，往往**只看到 `__DATA_CONST,__got`、看不到 `__DATA,__nl_symbol_ptr`**——这不是 `__nl_symbol_ptr` 的机制消失了，而是它的角色被 `__got` 吸收合并了。两者既然类型相同，`dyld` 与 `otool` 对它们的处理也完全一致。

> [!note] 在现代二进制里"找不到 `__nl_symbol_ptr`"是正常的
> 老二进制（i386/armv7、或较旧 SDK 产物）里可能同时有 `__nl_symbol_ptr` 和 `__la_symbol_ptr`；而当代 arm64 链上，非惰性指针都进了 `__got`、惰性路径又大量退化，于是 `__DATA,__nl_symbol_ptr` 常常根本不存在。逆向新目标时，看"加载时绑定的指针"应直接去 `__DATA_CONST,__got` 找。

### 5. 现代归入 `__DATA_CONST` 并绑定后只读：安全加固

把非惰性指针搬进 [[15.Mach-O __DATA_CONST]] 是近年最重要的演进。其动机是一对看似矛盾的需求：

- **加载期必须可写**：`dyld` 要往这些槽里写真实地址，所以绑定那一刻它们得是可写的。
- **运行期最好只读**：这些槽是**函数/数据指针**，一旦被攻击者在运行期改写，就能把控制流/数据流劫持到任意地址（经典的 GOT overwrite 攻击）。

`__DATA_CONST` 用"**先写后封**"解决矛盾：该段在加载/绑定阶段临时可写，**待 `dyld` 把全部非惰性槽绑定完毕后，整段 `mprotect` 改为只读**。绑定后指针恒定不变，正好可以只读化；攻击者再也无法在运行期覆写这些指针。这就是"既要早绑定、又要运行期不可篡改"的解法——也是为什么现代二进制把 `__got` 放进 `__DATA_CONST` 而非可写的 `__DATA`。

> [!note] 这正是 `__nl_symbol_ptr` 能被只读化的前提
> 惰性指针（`__la_symbol_ptr`）天生**运行期要被回填**（首次调用时写真实地址），所以它住在可写的 `__DATA`、无法只读化。而非惰性指针加载后**永不再改**，这"恒定性"才是它能被搬进 `__DATA_CONST` 并封为只读的根本前提。换句话说，"非惰性"与"可只读化"是因果关系：因为绑定后不变，所以可以只读。

### 6. `reserved1`：间接符号表起始索引（反查符号名）

`__nl_symbol_ptr` 的节头 `reserved1` **不是真正保留**，而是按 [[18.Mach-O section]] 第 9 节所述被复用为：本节第一个指针槽在**间接符号表（indirect symbol table）** 中的**起始索引**。完整的"指针槽 → 符号名"反查链如下（这正是 `otool -Iv`、`nm`、fishhook 在做的事）：

1. **定位间接符号表**：由 `LC_DYSYMTAB` 的 `indirectsymoff`/`nindirectsyms` 给出它在 `__LINKEDIT` 里的位置（见 [[06.Mach-O LC_DYSYMTAB]]）。它是一个 `uint32_t` 数组。
2. **算条目数**：本节条目数 `n = size / 指针宽度`（64 位 `/8`、32 位 `/4`）。注意非惰性指针节**不用 `reserved2`**（项大小固定为指针宽度），`reserved2` 通常为 0——这点与 `__stubs`（用 `reserved2` 存 stub 字节大小）不同。
3. **逐槽对位反查**：对第 `i ∈ [0, n)` 个槽：
   - 取间接符号表第 `reserved1 + i` 项 → 得到一个**常规符号表索引** `symIdx`；
   - 查常规符号表 `nlist_64[symIdx]` → 取其 `n_strx`；
   - 以 `n_strx` 为偏移查字符串表 → 得到该槽真正引用的**符号名**（如 `_environ`、`dyld_stub_binder`）。

用一行公式概括：`__nl_symbol_ptr[i] 的符号名 = strtab[ symtab[ indirect[ reserved1 + i ] ].n_strx ]`。

> [!note] 两个特殊间接符号项要跳过
> 间接符号表里有两类哨兵值不指向真实导入符号：`INDIRECT_SYMBOL_LOCAL`（该槽指向本镜像内的局部符号，由 rebase 处理而非 bind）与 `INDIRECT_SYMBOL_ABS`（绝对符号）。健壮的解析器（如 fishhook）在按上式反查前要先判掉这两个标志，否则会拿到无效的符号表索引。

### 7. `dyld_stub_binder` 的指针就放在这里：破自举死锁

这是 `__nl_symbol_ptr`（非惰性）一个极具代表性的角色。回顾惰性绑定的流程（详见 [[30.Mach-O __la_symbol_ptr节]]）：惰性槽首次被调用时，会跳进 `__stub_helper`，由它把"待绑定槽的偏移"压栈，再跳到一个名为 **`dyld_stub_binder`** 的函数——后者才是真正去查符号、回填惰性槽的"绑定器"。

问题来了：`dyld_stub_binder` 自己也是个外部符号（住在 `dyld` 里），**它的地址也要先被绑定，惰性桩才能跳过去**。如果连 `dyld_stub_binder` 都用惰性绑定，就会陷入"要绑定别人得先调它、可调它本身又得先绑定它"的**自举死锁（chicken-and-egg）**。

Mach-O 的解法干净利落：**把 `dyld_stub_binder` 当作非惰性符号，它的指针就存在 `__nl_symbol_ptr`（现代则在 `__got`）里，加载阶段第一批就被 `dyld` 绑好**。于是当任何惰性桩第一次触发、需要调用 `dyld_stub_binder` 时，这个指针早已是真实地址、可直接使用——死锁被打破。这也解释了一个常见观察：在极简的 "Hello World" 程序里，磁盘上的 `__nl_symbol_ptr` 几乎全是 0，但加载后**唯一被非惰性填好的那一项，正是指向 `dyld_stub_binder` 的指针**。

> [!note] 一句话记住它的"自举"地位
> 惰性绑定这套机器要转起来，唯一不能惰性的零件就是绑定器自己——所以 `dyld_stub_binder` 必须非惰性、必须在 `__nl_symbol_ptr`/`__got` 里、必须最先被绑。它是"用来解析别人的人"，自然要先把自己准备好。

### 8. 与 `__la_symbol_ptr` 的系统对比

`__nl_symbol_ptr`（非惰性）与 [[30.Mach-O __la_symbol_ptr节]]（惰性）是同一机制的"立即 / 延迟"两面，逐项对照：

| 维度 | `__nl_symbol_ptr`（非惰性） | `__la_symbol_ptr`（惰性） |
|---|---|---|
| 节类型 `flags & 0xff` | `S_NON_LAZY_SYMBOL_POINTERS (0x6)` | `S_LAZY_SYMBOL_POINTERS (0x7)` |
| 绑定时机 | **加载时**一次性全绑 | **首次调用**时才绑（可被强制改为加载时） |
| 绑定者 | `dyld`（依 bind 信息） | `dyld_stub_binder`（经 `__stub_helper`） |
| 槽初值（磁盘） | 多为 0（待加载填真值） | 指向 `__stub_helper` |
| 运行期是否变 | **不变**（绑定后恒定） | 首次调用后被回填一次 |
| 面向引用 | 外部**数据**、取函数地址、必须早绑定者 | 外部**函数调用**（可延迟者） |
| 典型归属段 | 现代并入 `__DATA_CONST,__got`（只读） | `__DATA`（可写） |
| 能否只读化 | **能**（恒定 → `__DATA_CONST`） | 不能（运行期要回填） |
| `reserved1`/`reserved2` | `reserved1`=间接符号起点；`reserved2` 通常 0 | `reserved1`=间接符号起点；`reserved2` 通常 0 |
| 绑定失败后果 | **加载即失败** | 拖到首次调用才暴露 |

> [!note] 现代趋势：惰性这一侧在收缩
> 当代 `dyld` 倾向"一切非惰性"，加上 `__DATA_CONST` 只读化的安全收益，惰性绑定路径（`__la_symbol_ptr` + `__stub_helper` + `dyld_stub_binder` 回填）在新二进制里越来越像"历史遗存"。理解 `__nl_symbol_ptr` 的非惰性模型，基本就抓住了现代 Mach-O 外部符号绑定的主线。

## 实操：用工具查看

### 示例 1：`otool -s __DATA __nl_symbol_ptr` 看非惰性指针槽

`otool -s 段名 节名` 以"虚拟地址 + 十六进制"逐行 dump 节的原始字节。对 `__nl_symbol_ptr`，看到的就是一串等宽指针：

```bash
otool -s __DATA __nl_symbol_ptr /bin/ls    # 老布局：非惰性指针单独成节
otool -arch arm64 -s __DATA __nl_symbol_ptr /bin/ls   # 指定架构（胖二进制时）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/字节为示意，实际数值以你机器上的 `otool` 为准。

```text
/bin/ls:
Contents of (__DATA,__nl_symbol_ptr) section
0000000100008000  90 3a 5d 80 01 00 00 00   ; 小端 → 0x0000000180 5d 3a90，加载后即真实地址（含 ASLR 滑移）
0000000100008008  e0 12 6c 80 01 00 00 00   ; 另一个非惰性槽，同样已是真值
```

> 说明：与惰性表"初值指向 `__stub_helper`"不同，非惰性表加载后**直接就是目标地址**（小端字节序，需反转后阅读）。每槽 8 字节（64 位），所以条目数 = `size / 8`。在很多现代 arm64 二进制里这个节并不存在——非惰性指针都进了 `__got`（见示例 2）。

### 示例 2：`otool -s __DATA_CONST __got` 看现代只读化的 GOT

现代二进制把非惰性指针统一放进 `__DATA_CONST,__got`，类型同为 `S_NON_LAZY_SYMBOL_POINTERS`，绑定后整段只读：

```bash
otool -s __DATA_CONST __got /bin/ls          # 现代布局：非惰性指针都在这里
otool -l /bin/ls | grep -A 12 "sectname __got"   # 看 __got 节头（flags=0x6、reserved1）
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意 `__got` 节头与非惰性指针的对应关系。

```text
Section
  sectname __got
   segname __DATA_CONST
      addr 0x0000000100008000
      size 0x0000000000000030      ; 48 字节 → 48/8 = 6 个非惰性指针
    offset 16384
     align 2^3 (8)                 ; 指针对齐
    reloff 0
    nreloc 0
     flags 0x00000006              ; 类型 S_NON_LAZY_SYMBOL_POINTERS（与 __nl_symbol_ptr 同型）
 reserved1 6                       ; (index into indirect symbol table) 本节首槽 → 间接符号表第 6 项
 reserved2 0                       ; 指针节不用 reserved2（项大小固定为指针宽度）
 reserved3 0
```

> 说明：`flags & 0xff = 0x6` 表明 `__got` 与 `__nl_symbol_ptr` **是同一类型**；`reserved1=6` 是它在间接符号表里的起点；`reserved2=0`（区别于 `__stubs` 用 `reserved2` 存 stub 大小）；段是 `__DATA_CONST` 而非 `__DATA`，体现"绑定后只读"的加固。

### 示例 3：`otool -Iv` 看间接符号表（把槽反查成符号名）

`otool -I`（`-v` 加详）打印间接符号表，把每个指针槽/桩**对位到它引用的符号名**——这正是第 6 节那条反查链的可视化：

```bash
otool -Iv /bin/ls                              # 打印间接符号表（含 __got/__nl_symbol_ptr/__la_symbol_ptr/__stubs）
otool -l /bin/ls | grep -A 2 indirectsym       # 看 LC_DYSYMTAB 的 indirectsymoff/nindirectsyms
```

> [!warning] 示例输出为示意
> 数值/符号为构造，仅示意 `otool -Iv` 如何把槽地址对位到符号名。

```text
Indirect symbols for (__DATA_CONST,__got) 6 entries
address                     index   name
0x0000000100008000          25      dyld_stub_binder     ; 非惰性！绑定器自身的指针，最先绑好
0x0000000100008008          26      _environ             ; 外部数据符号（全局变量）
0x0000000100008010          27      ___stack_chk_guard   ; 栈保护哨兵（数据）
0x0000000100008018          28      _printf              ; 取址/早绑定的函数指针
...
Indirect symbols for (__TEXT,__stubs) 10 entries
address                     index   name
0x0000000100003a40          0       _printf
...
```

> 说明：`__got` 第 0 项就是 `dyld_stub_binder`，印证第 7 节"绑定器自身非惰性、放在这里破死锁"；`_environ`/`___stack_chk_guard` 是典型的非惰性**数据**符号。每行的 `index` 是该槽在间接符号表里的项号（= `reserved1 + 槽序号`），`otool` 已替你顺着"间接表→符号表→字符串表"查出了 `name`。

## FAQ

> [!question] 非惰性指针 `__nl_symbol_ptr` 和惰性指针 `__la_symbol_ptr` 到底差在哪？
> 差在**绑定时机**与**面向的引用类型**。`__nl_symbol_ptr`（类型 `0x6`）在**镜像加载时**就由 `dyld` 一次性把所有槽绑成真实地址、运行期不变，面向**外部数据符号、取函数地址、必须早绑定**这类"没有调用触发点、加载后立刻要用"的引用；`__la_symbol_ptr`（类型 `0x7`）则把绑定**推迟到外部函数首次被调用**时，由 `dyld_stub_binder` 经 `__stub_helper` 回填，面向"可以延迟"的函数调用。非惰性绑定失败会导致**加载直接失败**，惰性则拖到首次调用才暴露。现代趋势是"一切非惰性"，惰性路径逐渐退化。

> [!question] `__got` 和 `__nl_symbol_ptr` 是不是一回事？为什么我只看到 `__got`？
> 它们**节类型相同**（都是 `S_NON_LAZY_SYMBOL_POINTERS`，`flags & 0xff == 0x6`），本质都是"加载时绑定的指针表"，`dyld`/`otool` 对二者处理一致。历史上习惯用 `__got` 放导入函数地址、`__nl_symbol_ptr` 放非惰性数据指针；但**现代工具链把所有非惰性指针统一并进 `__got`**，并整体放进只读的 `__DATA_CONST`。所以新 arm64 二进制里常常**只有 `__DATA_CONST,__got`、没有 `__DATA,__nl_symbol_ptr`**——这是合并的结果，不是机制消失。逆向时看"加载时绑定的指针"直接去 `__got`。

> [!question] 既然非惰性指针指向函数/数据地址，运行期被改写岂不很危险？现代怎么防？
> 正是为此才把它们搬进 [[15.Mach-O __DATA_CONST]] 并**绑定后只读化**。`dyld` 在加载阶段填完所有非惰性槽后，把整段 `__DATA_CONST` 用 `mprotect` 改为只读；由于非惰性指针**绑定后恒定不变**，只读化不影响功能，却挡住了经典的 GOT/指针覆写攻击。能这么做的前提就是"非惰性"——惰性指针运行期还要被回填，无法只读，只能待在可写的 `__DATA`。

> [!question] `dyld_stub_binder` 为什么偏偏是非惰性、要放在 `__nl_symbol_ptr`/`__got` 里？
> 因为它是惰性绑定机制的**绑定器本身**：惰性槽首次调用时要跳去 `dyld_stub_binder` 解析符号、回填地址。若连它都惰性绑定，就会"要绑别人得先调它、调它又得先绑它"形成**自举死锁**。解法是让它**非惰性**——它的指针存在 `__nl_symbol_ptr`（现代在 `__got`），加载阶段第一批就被 `dyld` 绑好，于是任何惰性桩首次触发时它早已可用。在极简程序里，磁盘上 `__nl_symbol_ptr` 几乎全 0，加载后唯一被填好的那项常常正是它。

> [!question] 怎么知道 `__nl_symbol_ptr`/`__got` 里某个槽指向哪个符号？条目数怎么算？
> 用 `reserved1` 顺着三级表反查：本节第 `i` 槽 → 间接符号表第 `reserved1 + i` 项（一个符号表索引）→ 常规符号表 `nlist_64` 取 `n_strx` → 字符串表取出符号名（间接符号表由 `LC_DYSYMTAB.indirectsymoff` 定位，见 [[06.Mach-O LC_DYSYMTAB]]）。条目数 = `size / 指针宽度`（64 位 `/8`、32 位 `/4`），**指针节不用 `reserved2`**。命令上直接 `otool -Iv` 就能把每槽对位到符号名，省去手工查表。

## 与相邻章节的关系

- [[30.Mach-O __la_symbol_ptr节]]：惰性对照——首次调用才绑定、住可写 `__DATA`、靠 `dyld_stub_binder` 回填；与本篇构成"延迟 vs 立即"的一对。
- [[15.Mach-O __DATA_CONST]]：现代非惰性指针（`__got`）的只读归宿——加载期可写以供绑定、绑定后整段 `mprotect` 转只读。
- [[17.Mach-O LC_DYLD_INFO_ONLY]]：`dyld` 加载时据以绑定本节各槽的 bind 信息来源（新二进制则为 `LC_DYLD_CHAINED_FIXUPS`）。
- [[06.Mach-O LC_DYSYMTAB]]：`reserved1` 索引的**间接符号表**由它的 `indirectsymoff`/`nindirectsyms` 定位，是把指针槽反查成符号名的另一半。
- [[18.Mach-O section]]：本节类型 `S_NON_LAZY_SYMBOL_POINTERS` 与 `reserved1` 复用语义的"公共字段说明书"。
- [[22.Mach-O __stubs节]]：同走间接符号表、但用 `reserved2` 存 stub 大小的桩节，与本篇形成"指针 vs 桩"对照。

## 小结

- `__nl_symbol_ptr` 是**非惰性符号指针表**，节类型 `S_NON_LAZY_SYMBOL_POINTERS`（`flags & 0xff == 0x6`）；每槽是一个指针，由 `dyld` 在**加载时一次性绑定**到真实地址，**运行期不变**——与惰性的 `__la_symbol_ptr`（`0x7`）相对。
- 面向"无法/不应惰性化"的引用：外部**数据**符号、对函数**取地址**、链接器判定必须早绑定者；这些没有"首次调用"触发点，故加载时就得有真值。绑定失败 = 加载失败。
- 与 `__got` **同类型**、本质相同；现代工具链把非惰性指针**统一并入 `__got`** 并整体放进 [[15.Mach-O __DATA_CONST]]，**绑定后只读化**（先写后封），挡住 GOT 覆写攻击——这正以"非惰性 → 绑定后恒定"为前提。
- `reserved1` 存间接符号表起始索引（联动 [[06.Mach-O LC_DYSYMTAB]]），条目数 = `size / 指针宽度`，指针节不用 `reserved2`；顺着"间接表→符号表→字符串表"可把每槽反查成符号名（`otool -Iv` 即做此事）。
- `dyld_stub_binder` 的指针**非惰性地存在这里**：它是惰性绑定的绑定器自身，必须最先被绑好，以打破"绑定器要靠绑定才能用"的自举死锁。
