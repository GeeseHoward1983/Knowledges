# 详解Mach-O(三十八)Mach-O __objc_protolist节

> [!abstract] TL;DR
> **`__objc_protolist`（全称 `__DATA,__objc_protolist` 或现代二进制里的 `__DATA_CONST,__objc_protolist`）登记"本镜像定义的所有 Objective-C 协议"**：它是一张**指针数组**，每项是一个指向 `protocol_t` 结构的指针，对应源码里的一个 `@protocol`。
> 每个 `protocol_t` 完整描述一个协议：协议名（`mangledName`）、它所继承的协议列表（`protocols`）、**四张方法列表**——必选实例方法 / 必选类方法 / 可选实例方法 / 可选类方法（`instanceMethods` / `classMethods` / `optionalInstanceMethods` / `optionalClassMethods`），以及属性列表（`instanceProperties`，新版还有 `_classProperties`）和扩展方法类型（`_extendedMethodTypes`）。
> 镜像加载时，runtime 遍历本表，对每个协议调用 `readProtocol` **注册进全局协议哈希表并做唯一化**（按 `mangledName` 去重，同名协议只保留一个规范实例）。注册之后，`objc_getProtocol("X")`、`@protocol(X)`、`conformsToProtocol:` 等才查得到、比得对。
> 它与"**引用**协议"的 [[42.Mach-O __objc_protorefs节]] 构成一对：`__objc_protolist` 是"**我定义了哪些协议**"（带完整结构体），`__objc_protorefs` 是"**我用到了哪些协议**"（只是绑定到唯一实例的指针槽）。

## 概述与定位

**协议（protocol）是 Objective-C 的"接口契约"**：它声明一组方法（和属性），但不提供实现，谁遵守谁实现。`@protocol UITableViewDataSource ... @end` 就是一个协议定义；`@protocol(UITableViewDataSource)` 取到协议对象；`[obj conformsToProtocol:@protocol(UITableViewDataSource)]` 在运行时判断某对象/类是否遵守它。

这些运行时能力（查询、比较、遵从判定）都要求 runtime **先知道镜像里定义了哪些协议**。编译器把每个 `@protocol` 编成一个 `protocol_t` 结构体放进只读元数据，再把所有这些结构体的地址收集成一张指针数组——**这张数组就是 `__objc_protolist`**。它解决的核心问题是：*让 dyld/objc runtime 在加载镜像时，一次性枚举到本镜像定义的全部协议，逐个登记到进程级的全局协议表里。*

把它放到 ObjC 元数据的全景中看：本系列把 ObjC 元数据节分成两大类——

- **"列表/定义"类节（36/37/38/39）**：`__objc_classlist`（类）、`__objc_nlclslist`（非懒加载类）、**`__objc_protolist`（协议）**、`__objc_catlist`（分类）。它们各自指向"完整结构体"，回答"本镜像**定义/提供**了什么"。
- **"引用"类节（35/40/41/42）**：`__objc_selrefs`（selector）、`__objc_classrefs`（类）、`__objc_supperrefs`（父类）、`__objc_protorefs`（协议）。它们只是"指针槽"，回答"本镜像代码里**用到/引用**了什么"，加载时绑定到唯一实例。

`__objc_protolist` 正是"定义类"里描述协议的那一员，与"引用类"里的 [[42.Mach-O __objc_protorefs节]] 一一对应。本篇把它的数组形态、`protocol_t` 的每个字段、必选/可选方法的四张列表、runtime 的注册与唯一化流程、以及 `conformsToProtocol:`/`objc_getProtocol` 的查表机制讲透。

> [!note] 它住在 `__DATA` 还是 `__DATA_CONST`？
> 早期二进制把 ObjC 元数据列表放在可写的 **`__DATA`** 段（因为加载时 runtime 要回填指针，需要可写）。iOS 9 / 对应 macOS 起新增了 **`__DATA_CONST`** 段，把一批"加载后即固化、之后只读"的 ObjC 节迁了过去——`__objc_protolist`、`__objc_classlist`、`__objc_catlist`、`__objc_const`、`__objc_imageinfo` 等都在其列。所以**同一个节名，在新旧二进制里可能位于不同段**：现代 arm64 设备多数是 `__DATA_CONST,__objc_protolist`，老二进制是 `__DATA,__objc_protolist`。解析工具（如 MachOView）的做法是"先在 `__DATA` 找，找不到再去 `__DATA_CONST` 找"。`otool -s` 要给对段名才 dump 得出来（见下方实操）。段的只读化由链式 fixups + `__DATA_CONST` 在加载完成后重新保护实现，参见 [[15.Mach-O __DATA_CONST]] 与 [[18.Mach-O section]]。

## 核心原理与字段详解

### 1. 节的形态：一张 `protocol_t *` 指针数组

`__objc_protolist` 本身**没有自己的"头结构"**，它就是一段连续的指针：每个指针 = 一个 `protocol_t` 的地址（即一个 `@protocol`）。条目数不显式存储，按"节大小 ÷ 指针宽度"推算（与所有 ObjC 列表节一致，也与 [[18.Mach-O section]] 里讲的"节头不存条目数、靠 `size/单项大小` 推算"同源）：

```text
条目数 n = section.size / sizeof(void*)      // 64 位 → size/8，32 位 → size/4
第 i 个协议 = *(protocol_t **)(节起始 + i * 8) // 64 位
```

数组里的每个指针，**链接期由编译器/链接器填成镜像内的地址，加载期再经 rebase / 链式 fixups 修正**（叠加 ASLR slide）。需要强调：`__objc_protolist` 只收录**本镜像自己定义**的协议；代码里**引用到的**协议（无论本镜像还是别的库定义的）走的是 [[42.Mach-O __objc_protorefs节]]。

### 2. `protocol_t` 完整字段（来自 objc4 `objc-runtime-new.h`）

每个数组项指向的 `protocol_t`，是 ObjC runtime 内部表示协议的结构体。它**继承自 `objc_object`**（所以协议对象自身也有一个 `isa`，类是 `Protocol` 类——这也是为什么 `@protocol(X)` 求得的是一个真正的对象、能当 `id` 传递）：

```cpp
struct protocol_t : objc_object {
    const char *mangledName;                  // 协议名（可能带 Swift mangle 前缀）
    struct protocol_list_t *protocols;        // 本协议所"继承/采纳"的其它协议列表
    method_list_t *instanceMethods;           // @required 实例方法 (-)
    method_list_t *classMethods;              // @required 类方法 (+)
    method_list_t *optionalInstanceMethods;   // @optional 实例方法 (-)
    method_list_t *optionalClassMethods;      // @optional 类方法 (+)
    property_list_t *instanceProperties;      // 协议声明的（实例）属性
    uint32_t size;                            // sizeof(protocol_t)，用于版本兼容
    uint32_t flags;                           // 标志位（含 FIXED_UP，低 16 位留给 Swift）

    // 下面这些字段“在磁盘上不一定都存在”，要先用 size 判断是否落到了该字段
    const char **_extendedMethodTypes;        // 扩展方法类型编码（每个方法一条）
    const char *_demangledName;               // 去 mangle 的可读名（运行时按需填充/缓存）
    property_list_t *_classProperties;        // 协议声明的“类属性”（@property(class)）

    const char *demangledName();              // 取可读协议名的方法
    bool isFixedUp() const;                   // 是否已被 runtime 修整
    void setFixedUp();
};
```

逐字段说明：

| 字段 | 含义 |
|---|---|
| `isa`（来自 `objc_object`） | 协议对象的类指针，固定为 `Protocol` 类。让协议成为一等公民对象 |
| `mangledName` | 协议名。普通 ObjC 协议就是原名（如 `NSCopying`）；与 Swift 互通的协议可能带 mangle 前缀，故查表时 runtime 会做 mangle/demangle 双向尝试 |
| `protocols` | 一个 `protocol_list_t`，列出**本协议继承的协议**（`@protocol A <B, C>` 里的 B、C）。`conformsToProtocol:` 的递归就靠它 |
| `instanceMethods` | `@required` 的**实例**方法（`-` 方法）描述列表 |
| `classMethods` | `@required` 的**类**方法（`+` 方法）描述列表 |
| `optionalInstanceMethods` | `@optional` 的实例方法描述列表 |
| `optionalClassMethods` | `@optional` 的类方法描述列表 |
| `instanceProperties` | 协议里 `@property` 声明的（实例）属性列表——**协议也能带属性** |
| `size` | `sizeof(protocol_t)`。因为后面几个字段"磁盘上不一定有"，runtime 用 `size` 判断某字段是否真实存在，做**向前/向后版本兼容** |
| `flags` | 标志位。最高两位是 runtime 的 fixup 标记，**低 16 位保留给 Swift**（见第 5 节） |
| `_extendedMethodTypes` | **扩展方法类型编码**：比普通 `@encode` 更细，连参数对象的具体类名都带上（如 `@"NSArray"`）。这是**协议方法独有**的信息，且只有私有 API `_protocol_getMethodTypeEncoding()` 能取（见第 7 节） |
| `_demangledName` | 去 mangle 后的人类可读名，运行时按需计算并缓存 |
| `_classProperties` | 协议声明的**类属性**（`@property (class) ...`），较新 runtime 才有 |

> [!note] 为什么方法/属性列表是"指针"而不是内联数组
> `protocol_t` 里这些 `*Methods` / `*Properties` 都是**指向列表的指针**（`method_list_t *` / `property_list_t *`），列表本身另存于 `__objc_const` 等只读节，列表里再放 `method_t` / `property_t` 条目。这样同一份方法描述可被复用、布局也更紧凑。`method_t` 通常含 `name`(SEL/selector 名)、`types`(类型编码) 与 `imp`——但**协议里的方法没有实现**，所以协议方法列表里的 `imp` 为空，只有名字与类型，纯粹是"声明"。selector 名落在 [[24.Mach-O __objc_methname节]]，类型编码落在 [[26.Mach-O __objc_methtype节]]。

### 3. 协议继承（`protocols` 字段）与 `protocol_list_t`

协议可以继承其它协议：`@protocol UITableViewDataSource <NSObject>` 表示它"采纳"了 `NSObject` 协议。这种继承关系存在 `protocols` 字段指向的 `protocol_list_t` 里——一个带计数的协议指针数组：

```cpp
struct protocol_list_t {
    uintptr_t count;                 // 协议个数
    protocol_ref_t list[0];          // 变长数组：count 个协议引用
};
typedef uintptr_t protocol_ref_t;    // 实为 protocol_t*，但“未重映射”（unremapped）
```

注意 `protocol_ref_t` 的注释"**未重映射（unremapped）**"：磁盘上它是一个原始指针，但同名协议唯一化后，真正该用的可能是另一个规范实例，所以 runtime 比较前会先 `remapProtocol` 取到live指针（见第 6 节）。这也是 `conformsToProtocol:` 递归遵从判定的数据基础——沿着 `protocols` 一层层往上查。

### 4. 必选（@required）vs 可选（@optional）方法

ObjC 协议方法分两档，由 `@required`（默认）和 `@optional` 关键字切换：

```objc
@protocol UITableViewDataSource <NSObject>
@required
- (NSInteger)tableView:(UITableView *)t numberOfRowsInSection:(NSInteger)s; // 必选
- (UITableViewCell *)tableView:(UITableView *)t cellForRowAtIndexPath:(NSIndexPath *)i; // 必选
@optional
- (NSInteger)numberOfSectionsInTableView:(UITableView *)t;                  // 可选
- (NSString *)tableView:(UITableView *)t titleForHeaderInSection:(NSInteger)s; // 可选
@end
```

它们在 `protocol_t` 里**物理上分四张表存**，互不混杂——这正是把"必选/可选 × 实例/类"四象限拆成 4 个独立字段的原因：

| 关键字 | 实例方法（`-`） | 类方法（`+`） |
|---|---|---|
| `@required` | `instanceMethods` | `classMethods` |
| `@optional` | `optionalInstanceMethods` | `optionalClassMethods` |

这种"分表"带来两点实际意义：

- **编译期**：编译器知道哪些是必选——若一个类声明遵守该协议却没实现必选方法，编译器会告警（"method in protocol not implemented"）。可选方法不实现则无告警。
- **运行期**：调可选方法前必须先用 `-respondsToSelector:` 判断对方是否实现，否则可能 `unrecognized selector` 崩溃。runtime 也提供 `protocol_getMethodDescription(proto, sel, isRequiredMethod, isInstanceMethod)` / `protocol_copyMethodDescriptionList(proto, isRequiredMethod, isInstanceMethod, &count)` 这两个 API，**靠 `isRequiredMethod`、`isInstanceMethod` 两个布尔参数精确选中四张表中的某一张**来查询。

> [!note] 协议方法没有 `imp`：它是"声明"不是"实现"
> 类的方法列表里 `method_t.imp` 指向真正的函数；但**协议只声明接口、不含实现**，因此协议四张方法列表里每个 `method_t` 的 `imp` 都为空，只有 `name`(selector) 和 `types`(类型编码) 有意义。换句话说，`__objc_protolist` 里能读到"这个协议要求/允许哪些方法、各是什么签名"，但读不到任何机器码——实现永远在遵守该协议的具体类的 `__text` 里。

### 5. `flags`：fixup 标记与 Swift 保留位

`protocol_t.flags` 是 32 位，objc4 只动用了**最高两位**做"是否已被 runtime 修整（fixed up）"的标记，**低 16 位整段保留给 Swift**：

```cpp
#define PROTOCOL_FIXED_UP_2   (1<<31)  // 必须由 runtime 设置，编译器绝不能置位
#define PROTOCOL_FIXED_UP_1   (1<<30)  // 必须由 runtime 设置，编译器绝不能置位
#define PROTOCOL_FIXED_UP_MASK (PROTOCOL_FIXED_UP_1 | PROTOCOL_FIXED_UP_2)
// 注：bits 0..15 reserved for Swift's use
```

runtime 用一个全局目标值 `fixed_up_protocol`（默认 = `PROTOCOL_FIXED_UP_1`）来判断：

```cpp
bool protocol_t::isFixedUp() const {
    return (flags & PROTOCOL_FIXED_UP_MASK) == fixed_up_protocol;
}
void protocol_t::setFixedUp() {
    flags = (flags & ~PROTOCOL_FIXED_UP_MASK) | fixed_up_protocol;
}
```

**为什么要两个 fixup 位？** 这是为 dyld 共享缓存优化留的余地：共享缓存里预先 fixed-up 的协议标 `PROTOCOL_FIXED_UP_1`，正常情况下 `fixed_up_protocol == PROTOCOL_FIXED_UP_1`，于是缓存里的协议通过 `isFixedUp()` 检查、runtime 跳过重复修整；一旦需要禁用共享缓存优化（`disableSharedCacheOptimizations()`），就把目标值改成"两位都要置"（`FIXED_UP_1 | FIXED_UP_2`），缓存里只置了一位的协议便不再算"已修整"，强制 runtime 自己重做。**编译器从不置这两位**，保证刚编出来的协议初始状态恒为"未修整"。逆向时若发现协议 `flags` 高位被置，那是被加载过/共享缓存优化过的痕迹，不是编译产物。

> [!note] `size` + 不定字段：协议结构的"版本兼容"机制
> `protocol_t` 末尾的 `_extendedMethodTypes` / `_demangledName` / `_classProperties` 被源码明确标注"**在磁盘上不一定都存在**"——老编译器编出的协议结构体可能根本没有这几个字段。runtime 靠 `size`（= 编出来时的 `sizeof(protocol_t)`）判断"读到某字段的偏移是否还在结构体范围内"，越界就说明该字段不存在、不去访问。这让新 runtime 能安全读旧二进制、旧 runtime 也不会误读新字段，是一种轻量的前后向兼容设计。

### 6. 加载期：`readProtocol` 注册与唯一化

镜像被加载时（`_read_images` 阶段），runtime 遍历 `__objc_protolist`，对每一项调用 `readProtocol`，把协议登记进**进程级的全局协议哈希表**。这张表是一个以"协议名 → 协议对象"为映射的 `NXMapTable`：

```cpp
// 全局唯一的协议表，惰性初始化；读写需持 runtimeLock
static NXMapTable *protocols(void) { /* INIT_ONCE_PTR(...NXCreateMapTableFromZone...) */ }

static Protocol *getProtocol_impl(const char *name) {
    return (Protocol *)NXMapGet(protocols(), name);   // 按 mangledName 查
}
static Protocol *getProtocol(const char *name) {
    Protocol *result = getProtocol_impl(name);        // 先按原名查
    if (result) return result;
    // 未命中则尝试 Swift mangle 后的名字再查一次
    char *swName = copySwiftV1MangledName(name, true /*isProtocol*/);
    result = getProtocol_impl(swName);
    free(swName);
    return result;
}
```

`readProtocol` 的核心逻辑（结合各版本）：**先用本协议的 `mangledName` 去全局表查**——

- **查不到（首次出现）**：把它作为该名字的**规范实例**插入全局表。插入函数视来源而定：普通镜像用 `NXMapInsert`；若镜像是 bundle（可被卸载），用 `NXMapKeyCopyingInsert`（拷贝键，防 bundle 卸载后键悬空）。随后调 `setFixedUp()` 标记已修整。
- **查得到（同名已存在 `oldproto`）**：说明"已经有另一处定义先赢了"，**本份重复定义被丢弃**，不覆盖已有规范实例（开启 `PrintProtocols` 调试时会打印 `protocol at %p is %s (duplicate of %p)`）。

这就是**唯一化（uniquing）**：无论一个协议被多少个镜像定义、被引用多少次，进程内**每个协议名只有一个规范的 `protocol_t` 实例**。它是后续一切协议比较/查询正确的前提。

> [!note] 共享缓存里的协议：已 fixed-up，但仍要登记进表
> 对来自 dyld 共享缓存的预优化镜像（`headerIsPreoptimized`），协议对象已由缓存初始化好（`isFixedUp()` 为真），runtime 不再重复修整。但为了支持"缓存外的替换定义"（某个 dylib 想覆盖缓存里的协议），runtime **仍会把它加入全局协议表**，让 `getProtocol` 能查到。简言之：fixup 可省，登记不可省。

> [!note] 协议怎么"附"到类/分类上：和全局表是两回事
> 全局协议表回答"这个名字对应哪个协议对象"；而"某个类遵守哪些协议"是另一条线：类做 methodize 时，从 `class_ro_t->baseProtocols` 取出 `protocol_list_t` 并 `rw->protocols.attachLists(...)`（见 [[36.Mach-O __objc_classlist节]] 的 `class_ro_t`）；分类（category）也能声明协议遵从，`attachCategories` 时一并并入（见 [[39.Mach-O __objc_catlist节]]）。所以一个类的"遵从集合"= 自身 baseProtocols + 各分类带来的协议，而这些 `protocol_ref_t` 指向的协议，最终都会被 `remapProtocol` 映射到全局表里的那个唯一实例。

### 7. 扩展方法类型 `_extendedMethodTypes`

普通的方法类型编码（`@encode`）只记到"是个对象（`@`）"这一粒度，如 `barWithArray:` 编成 `@@:@`。但 `protocol_t._extendedMethodTypes` 存的是**扩展类型编码**，连参数/返回值的**具体类名**都带上，例如同一方法可能记成 `@"NSString"12@0:4@"NSArray"8`（`@"NSArray"` 指明这个对象参数期望是 `NSArray`）。

这有两个值得记的特点：

- **协议独有**：只有声明在 Protocol 里的方法才带扩展类型信息，普通类方法不带。
- **私有 API 才能取**：公开的 `protocol_getMethodDescription` 拿到的是普通编码；要拿扩展编码须用私有的 `_protocol_getMethodTypeEncoding()`。JavaScriptCore 的 `JSExport` 正是靠它把 ObjC 方法签名精确桥接到 JS。整体上这是一项"半成品、未公开"的 runtime 特性。

逆向价值：从 `__objc_protolist` 解析协议时，若 `size` 表明 `_extendedMethodTypes` 存在，能据此还原出**比普通类方法更精确的参数类型**（带类名），对理解一个 delegate 协议的真实签名很有帮助。

### 8. 动态创建协议（运行期 API）

除了编译期 `@protocol`，runtime 也允许在**运行期**凭空造协议，这组 API 正是对 `protocol_t` 各字段的写入接口：

```objc
Protocol *p = objc_allocateProtocol("MyDynamicProtocol");          // 分配（尚未注册）
protocol_addProtocol(p, objc_getProtocol("NSObject"));              // 写 protocols（继承）
struct objc_method_description d = { @selector(foo), "v@:" };
protocol_addMethodDescription(p, d.name, d.types,
                              /*isRequired*/ YES, /*isInstance*/ YES);// 写某张方法表
objc_registerProtocol(p);                                           // 注册进全局表（唯一化）
// 之后可 class_addProtocol(cls, p) 让某个类“遵守”它
```

注意 `protocol_addMethodDescription` 的 `isRequired`/`isInstance` 两个布尔参数，恰好对应第 4 节的"四张表"——它决定这条方法落进 `instanceMethods` / `classMethods` / `optionalInstanceMethods` / `optionalClassMethods` 中的哪一张。动态造的协议不来自任何 `__objc_protolist`，而是直接在内存里建 `protocol_t` 并经 `objc_registerProtocol` 登记。

### 9. 协议也可以带属性

容易被忽略：**协议不止能声明方法，还能声明属性**。`@protocol` 里写 `@property` 时，编译器把属性元数据放进 `protocol_t.instanceProperties`（类属性 `@property(class)` 放进新版的 `_classProperties`）。属性本质会展开成 getter/setter 方法声明，所以同时也会体现在方法列表里；属性列表则额外保留 `name`/`attributes`（如 `T@"NSString",C,N` 这种属性特性串）。逆向一个协议时，除了四张方法表，别忘了 `instanceProperties` 里可能还藏着属性声明。

> [!note] 架构与版本差异
> 指针宽度随位宽（64 位 8 字节、32 位 4 字节），故条目数 = `size/8`（或 `/4`）。`protocol_t` 的布局**随 runtime 版本演进**：核心前段（`mangledName`…`flags`）自 objc4-680 到 750+ 都稳定一致，差别主要在尾部"不一定存在"的字段（`_extendedMethodTypes`/`_demangledName`/`_classProperties` 陆续加入），以及 `flags` 低 16 位划给 Swift、更晚版本新增 `isCanonical()` 等。协议**所在的段**则随二进制年代在 `__DATA`（旧）/`__DATA_CONST`（iOS 9+）间变化。协议语义本身与 CPU 架构无关。

## 实操：用工具查看

### 示例 1：定位并 dump `__objc_protolist` 节

先用 `otool -l` 确认它在哪个段（新二进制多在 `__DATA_CONST`），再用 `otool -s` dump 原始指针；`otool -ov` 则把 ObjC 元数据**解析成可读结构**（最有用）：

```bash
otool -l ObjCBinary | grep -B1 -A4 __objc_protolist   # 看它在 __DATA 还是 __DATA_CONST
otool -s __DATA_CONST __objc_protolist ObjCBinary      # 新二进制：dump 指针数组原始字节
otool -s __DATA __objc_protolist ObjCBinary            # 老二进制：段名换成 __DATA
otool -ov ObjCBinary | grep -A 20 'Contents of .*protocol'  # 解析出协议名/方法列表
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值/地址以你机器上的 `otool` 为准。

```text
Contents of (__DATA_CONST,__objc_protolist) section
0000000100009000  0x0000000100008a40   ; → protocol_t* (UITableViewDataSource)
0000000100009008  0x0000000100008b80   ; → protocol_t* (MyDelegate)
```

> 说明：本节就是一串 8 字节指针，每个指向一个 `protocol_t`。条目数 = 节 `size / 8`。左列是该指针的虚拟地址，右列是它存的值（指向某个协议结构体）。`otool -s` 默认只给裸十六进制，不解析协议名——要看名字得用 `-ov`（下例）。

### 示例 2：`otool -ov` 解析单个协议（看四张方法表）

`otool -ov`（或 `-o`）会把 `protocol_t` 展开，列出协议名、继承协议、必选/可选方法等：

> [!warning] 示例输出为示意
> 字段值为构造，仅示意 `protocol_t` 各字段与"必选/可选"分表的呈现方式。

```text
Contents of (__DATA_CONST,__objc_protolist) section
00000001000091e0  0x0000000100008a40
isa                 0x0
name                UITableViewDataSource          ; mangledName
protocols           0x0000000100008c00             ; → 继承的协议列表 (NSObject)
instanceMethods     0x0000000100008d20             ; @required 实例方法
    name  tableView:numberOfRowsInSection:
    types q24@0:8@16
    name  tableView:cellForRowAtIndexPath:
    types @24@0:8@16
classMethods        0x0                            ; 无 @required 类方法
optionalInstanceMethods 0x0000000100008e60         ; @optional 实例方法
    name  numberOfSectionsInTableView:
    types q16@0:8
optionalClassMethods    0x0
instanceProperties      0x0                         ; 本协议未声明属性
    size  96
   flags  0x40000000                                ; 高位被置 = 已 fixed-up（加载后产物）
```

> 说明：可见**必选方法**（`instanceMethods`）与**可选方法**（`optionalInstanceMethods`）落在不同字段——这正是第 4 节"四张表"的实证；`protocols` 指向继承的 `NSObject` 协议；每个方法只有 `name`(selector) 与 `types`(类型编码)、**没有 `imp`**（协议不含实现）。`flags 0x40000000` 的高位被置，说明这份是被加载/优化过的；编译产物里编译器不会置该位。

### 示例 3：用 LLDB 在运行期验证唯一化与查询

把"磁盘上的定义"与"运行期的协议对象"对上，最直观的是在 LLDB 里调 runtime API：

> [!warning] 示例输出为示意
> 地址为构造，仅示意 `objc_getProtocol`/`conformsToProtocol:` 的验证思路。

```text
(lldb) p (Protocol *)objc_getProtocol("UITableViewDataSource")
(Protocol *) $0 = 0x0000000100008a40                 ; 即 __objc_protolist 里那个 protocol_t
(lldb) p (BOOL)[MyDataSource conformsToProtocol:$0]
(BOOL) $1 = YES
(lldb) p (BOOL)(objc_getProtocol("UITableViewDataSource") == @protocol(UITableViewDataSource))
(BOOL) $2 = YES                                       ; 唯一化：同名只有一个规范实例
```

> 说明：`objc_getProtocol("名字")` 走的就是全局协议表的 `NXMapGet`（第 6 节），取回的地址应与 `__objc_protolist` 里登记的 `protocol_t` 一致；`@protocol(X)`（来自 [[42.Mach-O __objc_protorefs节]] 的引用槽）经唯一化后与之 `==` 相等，正是"唯一化"的可观测证据。

## FAQ

> [!question] `__objc_protolist` 和 `__objc_protorefs` 到底差在哪？
> 一个是"**定义**"，一个是"**引用**"。`__objc_protolist`（本篇）登记**本镜像定义了哪些协议**，每项指向**完整的 `protocol_t`**（带名字、继承、四张方法表、属性等全部信息），加载时被 `readProtocol` 注册并唯一化。[[42.Mach-O __objc_protorefs节]] 则记录**代码里每处 `@protocol(X)` 表达式**，每项只是一个**指针槽**，加载时被绑定到全局唯一的协议对象（该对象可能由本镜像定义、也可能来自别的库）。一句话：protolist 提供"协议本体"，protorefs 提供"指向本体的引用"，二者经唯一化在 `==` 意义上对齐。它们和 selector、类、父类的"定义 vs 引用"对照一脉相承（见 [[42.Mach-O __objc_protorefs节]] 的对照表）。

> [!question] runtime 怎么保证 `@protocol(X) == @protocol(X)` 恒成立？
> 靠**唯一化（uniquing）**。加载每个镜像时，`readProtocol` 用协议的 `mangledName` 去**全局协议哈希表**（`NXMapTable protocol_map`）查：没有就把这份作为该名字的**规范实例**插入；已有同名（`oldproto`）就**丢弃这份重复定义**、沿用已登记的那个。于是进程内每个协议名只对应一个 `protocol_t` 实例。之后所有 `@protocol(X)` 引用（[[42.Mach-O __objc_protorefs节]]）经 `remapProtocol` 都被映射到这唯一实例，故指针相等、`conformsToProtocol:` 的比较也可靠。

> [!question] 协议方法的 `@required` 和 `@optional` 在结构里是怎么区分的？
> **物理上分四张独立列表存**：`instanceMethods`（必选实例）、`classMethods`（必选类）、`optionalInstanceMethods`（可选实例）、`optionalClassMethods`（可选类）。`@required`（默认）落前两张，`@optional` 落后两张；`-`/`+` 决定实例还是类。runtime 查询时用 `protocol_getMethodDescription(p, sel, isRequiredMethod, isInstanceMethod)` 的两个布尔参数精确选表。实际意义：必选方法不实现，编译器告警；可选方法调用前要 `-respondsToSelector:` 探测，否则可能崩。

> [!question] 协议里只有方法吗？能不能声明属性？`protocol_t` 里有没有实现代码？
> **协议能声明属性**——`@property` 写在 `@protocol` 里，元数据进 `instanceProperties`（类属性进新版的 `_classProperties`），同时属性会展开成 getter/setter 出现在方法表里。但**协议永远不含实现**：四张方法列表里每个 `method_t` 只有 `name`(selector) 和 `types`(类型编码)，`imp` 为空。所以从 `__objc_protolist` 能读出"要求/允许哪些方法和属性、各是什么签名"，但读不到任何机器码，实现一定在遵守该协议的具体类里。

> [!question] 我用 `otool -s __DATA __objc_protolist` 怎么 dump 不出东西？
> 多半是**段名给错了**。iOS 9 / 对应 macOS 起，`__objc_protolist`（连同 `__objc_classlist`、`__objc_catlist` 等）从 `__DATA` 迁到了**`__DATA_CONST`** 段。现代 arm64 二进制要用 `otool -s __DATA_CONST __objc_protolist`；只有较老的二进制才在 `__DATA`。稳妥做法是先 `otool -l 文件 | grep -A4 __objc_protolist` 看清它实际所属的段名，再对症 dump。想直接看协议名/方法而非裸指针，则用 `otool -ov`。

## 与相邻章节的关系

- [[42.Mach-O __objc_protorefs节]]：协议**引用**表，与本表的"**定义**"严格相对；每个 `@protocol(X)` 引用经唯一化绑定到本表登记的规范 `protocol_t`。
- [[36.Mach-O __objc_classlist节]]：类列表；类的 `class_ro_t->baseProtocols` 会引用它所遵循的协议（指向本表里的协议实例），类 methodize 时 `attachLists` 并入。
- [[39.Mach-O __objc_catlist节]]：分类列表；分类也能声明协议遵从，`attachCategories` 时把协议并入宿主类的遵从集合。
- [[18.Mach-O section]]：节的通用模型——本节"无头、指针数组、条目数靠 `size/指针宽度` 推算"与那篇讲的节通用规律同源。
- [[24.Mach-O __objc_methname节]] / [[26.Mach-O __objc_methtype节]]：协议四张方法表里 `method_t` 的 `name`(selector 名)、`types`(类型编码) 分别落在这两个节。
- [[15.Mach-O __DATA_CONST]]：现代二进制里本节的宿主段，解释了"加载后固化为只读"的由来。

## 小结

- `__objc_protolist`（`__DATA`/新二进制 `__DATA_CONST`）是**本镜像定义的协议清单**：一张 `protocol_t *` 指针数组，条目数 = `size / 指针宽度`，每项指向一个 `@protocol` 对应的 `protocol_t`。
- `protocol_t`（继承 `objc_object`）完整字段：`mangledName`、`protocols`（继承的协议）、**四张方法表** `instanceMethods`/`classMethods`/`optionalInstanceMethods`/`optionalClassMethods`、`instanceProperties`(+ 新版 `_classProperties`)、`size`、`flags`，以及尾部"不一定存在"的 `_extendedMethodTypes`/`_demangledName`/`_classProperties`。
- **必选(@required) vs 可选(@optional)** 物理分四张表存；协议方法**只有声明、`imp` 为空**；协议**也能带属性**。
- 加载期 `readProtocol` 把协议**注册进全局 `NXMapTable` 并按 `mangledName` 唯一化**（同名只留一个规范实例，重复定义被丢弃），保证 `objc_getProtocol`、`@protocol(X)`、`conformsToProtocol:` 查得到、比得对。
- `flags` 高两位是 runtime 的 `FIXED_UP` 标记（编译器绝不置位）、低 16 位留给 Swift；`size` + "不定字段"实现协议结构的版本兼容。
- 与 [[42.Mach-O __objc_protorefs节]] 构成"定义 vs 引用"一对，是 ObjC 元数据"列表类/引用类"对照体系中描述协议的两端。
