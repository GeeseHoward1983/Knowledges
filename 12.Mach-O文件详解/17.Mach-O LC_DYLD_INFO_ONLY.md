# 详解Mach-O(十七)Mach-O LC_DYLD_INFO_ONLY

> [!abstract] TL;DR
> **`LC_DYLD_INFO_ONLY` 是把 `dyld` 在运行时要做的"修补工作"集中编码成五张压缩表的加载命令**：rebase（重定基址）、bind（绑定）、weak_bind（弱绑定）、lazy_bind（惰性绑定）、export（导出）。前四张表是紧凑的**字节码（opcode）流**，第五张 export 是一棵**前缀树（trie）**，全部存放在 [[16.Mach-O __LINKEDIT]] 段里。
> 命令体是**定长 48 字节**的 `dyld_info_command`：一个统一头 `cmd/cmdsize`，外加 **5 对 `(off, size)`** 字段，每对指向 `__LINKEDIT` 内一段数据。五张表分工明确：**rebase** 修正镜像内部因 ASLR slide 而失效的绝对指针；**bind** 把引用的外部符号绑定到依赖库的真实地址；**weak_bind** 处理弱符号去重合并（多个镜像同名弱符号统一指向一份）；**lazy_bind** 把绑定推迟到符号"第一次被调用"时；**export** 用 trie 紧凑表达本镜像导出的所有符号及地址。
> `cmd` 有两个取值：`LC_DYLD_INFO`（`0x22`，不带 `LC_REQ_DYLD`，兼容形式，老 `dyld` 不识别时可忽略回退）与 `LC_DYLD_INFO_ONLY`（`0x80000022`，带 `LC_REQ_DYLD` 位，"信息只在这里、必须处理"，现代默认）。
> **重要时间线**：自 **iOS 15 / macOS 12** 起，以本命令为目标的二进制被新的 **`LC_DYLD_CHAINED_FIXUPS`（链式 fixups）+ `LC_DYLD_EXPORTS_TRIE`（导出 trie 单列）** 组合取代——rebase 与 bind 被"链"在一起按页组织，lazy_bind 彻底消失（连 `__la_symbol_ptr` 都一并去掉）。但兼容旧系统的二进制、以及大量现存样本仍在用 `LC_DYLD_INFO_ONLY`，它依旧是逆向与解析的必修课。

## 概述与定位

早期 Mach-O 用**传统重定位项（relocation entries）+ 间接符号表（indirect symbol table，见 [[06.Mach-O LC_DYSYMTAB]]）**来表达"运行时要改哪些地方、把哪些外部符号填进来"。这套表示方式冗长、解析慢、体积大。自 OS X 10.6 / iOS 起，现代二进制改用 `LC_DYLD_INFO_ONLY`，把这些信息**编码成紧凑字节码**，体积更小、`dyld` 解析更快，并且——关键设计——**全部用字节流（byte stream）编码，无需大小端转换**（解析器不必关心 host 字节序，直接顺序读字节即可）。

它是理解 [[01.Mach-O基础]] 里"`dyld` 如何把磁盘镜像加载、rebase、bind 成一个可运行进程"那一步的核心命令。它本身只是一张**目录（table of contents）**：命令体里没有真正的数据，只有 5 个 `(off, size)` 指针，把 `dyld` 真正要消费的五段数据指向 [[16.Mach-O __LINKEDIT]]。换句话说，本命令与 `__LINKEDIT` 是"目录 ↔ 正文"的关系——命令告诉 `dyld`"去 `__LINKEDIT` 的哪个偏移、读多少字节"，正文（opcode 流 / trie）则住在 `__LINKEDIT` 里。

它之所以重要，原因有三：

1. **它驱动了进程启动时最关键的一步**。段（[[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）只是把字节映射进内存，但映射进来的指针值此刻还是"文件里的理想地址"，是错的；正是 rebase/bind 把它们改成"加载到本次随机基址后的真实地址"，进程才能正确运行。
2. **它是逆向分析的富矿**。bind 表直接列出"本镜像引用了哪些外部符号、来自哪个库"，export 表列出"本镜像对外提供了哪些符号"——这是分析依赖关系、Hook 点、符号可见性的一手信息。
3. **它处在新旧两套机制的交界**。读懂 `LC_DYLD_INFO_ONLY` 的五张表，才能看懂现代 `LC_DYLD_CHAINED_FIXUPS` 是如何把 rebase+bind"链化"、把 lazy_bind 优化掉的——后者是前者的演进。

> [!note] 它修补的"指针"住在哪
> rebase/bind 改写的目标，绝大多数是 [[15.Mach-O __DATA_CONST]] 与 `__DATA` 段里的**指针表**：GOT（`__got`）、非惰性符号指针（`__nl_symbol_ptr`，见 [[31.Mach-O __nl_symbol_ptr节]]）、惰性符号指针（`__la_symbol_ptr`，见 [[30.Mach-O __la_symbol_ptr节]]）、Objective-C 的 `__objc_classlist`/`__objc_classrefs` 等。它们在文件里存的是占位值（rebase 目标常是镜像内偏移、bind 目标在文件里干脆是 `0`），`dyld` 跑完字节码后才把真实地址写进去。所以"哪些字节会被改"由本命令的字节码决定，"改到哪个内存位置"则落在这些数据节上。

## 核心原理与字段详解

### 1. `dyld_info_command` 完整字段定义

来自 `<mach-o/loader.h>`，逐字段注释如下（这是**唯一**的命令结构，32/64 位通用，因为所有字段都是 32 位偏移/大小）：

```c
struct dyld_info_command {
    uint32_t   cmd;             // LC_DYLD_INFO(0x22) 或 LC_DYLD_INFO_ONLY(0x80000022)
    uint32_t   cmdsize;         // 本命令总长，固定 = sizeof(dyld_info_command) = 48

    // ── 表 1：rebase（重定基址）──
    uint32_t   rebase_off;      // rebase 字节码在文件中的偏移（落在 __LINKEDIT 内）
    uint32_t   rebase_size;     // rebase 字节码字节数

    // ── 表 2：bind（非惰性绑定）──
    uint32_t   bind_off;        // bind 字节码文件偏移
    uint32_t   bind_size;       // bind 字节码字节数

    // ── 表 3：weak_bind（弱绑定 / 符号去重）──
    uint32_t   weak_bind_off;   // weak_bind 字节码文件偏移
    uint32_t   weak_bind_size;  // weak_bind 字节码字节数

    // ── 表 4：lazy_bind（惰性绑定）──
    uint32_t   lazy_bind_off;   // lazy_bind 字节码文件偏移
    uint32_t   lazy_bind_size;  // lazy_bind 字节码字节数

    // ── 表 5：export（导出符号 trie）──
    uint32_t   export_off;      // export trie 文件偏移
    uint32_t   export_size;     // export trie 字节数
};
```

字段在文件里的精确偏移（共 48 字节、12 个 `uint32_t`）：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `cmd` | uint32_t | 4 | `0x22` 或 `0x80000022` |
| 4 | `cmdsize` | uint32_t | 4 | 固定 `48` |
| 8 | `rebase_off` | uint32_t | 4 | rebase 字节码偏移 |
| 12 | `rebase_size` | uint32_t | 4 | rebase 字节码大小 |
| 16 | `bind_off` | uint32_t | 4 | bind 字节码偏移 |
| 20 | `bind_size` | uint32_t | 4 | bind 字节码大小 |
| 24 | `weak_bind_off` | uint32_t | 4 | weak_bind 字节码偏移 |
| 28 | `weak_bind_size` | uint32_t | 4 | weak_bind 字节码大小 |
| 32 | `lazy_bind_off` | uint32_t | 4 | lazy_bind 字节码偏移 |
| 36 | `lazy_bind_size` | uint32_t | 4 | lazy_bind 字节码大小 |
| 40 | `export_off` | uint32_t | 4 | export trie 偏移 |
| 44 | `export_size` | uint32_t | 4 | export trie 大小 |

> [!warning] `loader.h` 注释里的著名笔误
> Apple `loader.h` 中 `export_off` / `export_size` 两个字段的注释，被误写成 `"file offset to lazy binding info"` / `"size of lazy binding info"`（与上面 `lazy_bind` 的注释重复）。**这是头文件本身的注释 bug**：这两个字段实际指向的是 **export trie（导出符号前缀树）**，不是惰性绑定。多个解析器作者都踩过这个坑——以字段名 `export_off/export_size` 为准，别信那行注释。

> [!note] 某段 `size` 为 0 = 该表为空
> 任意一对 `(off, size)` 的 `size` 为 `0`，表示该镜像没有这类信息。最常见的是 `weak_bind_size = 0`（纯 C 程序、不涉及 C++ 弱符号去重时）。`dyld` 见到 `size==0` 直接跳过该表。`off` 此时填什么都无所谓（常见填 `0` 或沿用上一段偏移）。

### 2. 五张表的职责（逐表详解）

#### 表 1 — rebase：修正 ASLR slide 导致失效的内部绝对指针

可执行文件 / 动态库被 `dyld` 加载到一个**随机基址**（ASLR slide，见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 关于 slide 的说明）后，镜像内部那些"指向自身"的**绝对指针**（例如一个全局变量里存了另一个全局函数的地址、Objective-C 元数据里的类指针）就全错了——它们记录的是"文件里的理想地址"，必须统一加上这个 slide 才对。

rebase 字节码就是描述"**对哪些位置做这个加法**"的紧凑指令。它在概念上是一张元组表 `<seg-index, seg-offset, type>`（"第几个段、段内偏移、什么类型的重定位"），opcode 只在某一列**发生变化时**才编码，从而把一张大表压成几十字节。注意：rebase **只动镜像内部指针，不涉及任何外部符号**——它不知道符号名，只知道"这个地址需要 +slide"。

#### 表 2 — bind：把外部符号绑定到依赖库的真实地址

当镜像引用了**其他库**里的符号（如 `printf` 来自 libsystem），文件里这些引用位置存的是占位 `0`。bind 负责在**加载时**把它们解析成符号在依赖库中的运行时真实地址并写回。它在概念上是更宽的元组表 `<seg-index, seg-offset, type, symbol-library-ordinal, symbol-name, addend>`——除了位置和类型，还要带上"符号名、来自第几个依赖库（ordinal）、附加偏移 addend"。

`bind` 表里的是**非惰性（non-lazy）绑定**：必须在镜像加载完成、进入 `main` 之前就全部绑好。典型对象是 `__got` / `__nl_symbol_ptr`（[[31.Mach-O __nl_symbol_ptr节]]）里的数据符号引用。

#### 表 3 — weak_bind：弱符号去重 / 合并

C++ 程序（以及带 weak 定义的代码）常出现**多个镜像定义同名弱符号**的情况（如内联函数、模板实例、`operator new`）。语言语义要求"全进程所有镜像必须用同一份"，否则会出现一个对象被一个库 new、被另一个库 delete 却走了不同实现的灾难。

weak_bind 在 **bind 之后**执行，专门处理这种合并：它的字节码格式与 bind 相同，但**按符号名字母序排序**。`dyld` 按序遍历所有带弱绑定信息的镜像，一旦发现同名符号"撞车"（collision），就把它们统一指向同一份定义；若全程无撞车，`dyld` 什么都不用改。排序正是为了让这种"跨镜像找同名"能线性扫描完成。

#### 表 4 — lazy_bind：把绑定推迟到"第一次被调用"时

绝大多数**函数**符号引用其实不必在启动时就绑定——程序可能根本不会调用到它们。lazy_bind 把这些**函数**绑定推迟到符号**第一次被实际调用**的瞬间，显著加快启动。

触发路径是 Mach-O 经典的"三级跳"：调用方先跳到 `__stubs`（[[22.Mach-O __stubs节]]）里的桩 → 桩跳到 `__la_symbol_ptr`（[[30.Mach-O __la_symbol_ptr节]]）当前指向的 `__stub_helper`（[[23.Mach-O __stubs_helper节]]）→ helper 把"该符号在 lazy_bind 区里的偏移"压栈，跳进 `dyld_stub_binder` → `dyld` 用这个偏移定位 lazy_bind 字节码（`lazy_bind_off + 偏移`），解析符号、把真实地址**回填进 `__la_symbol_ptr`** → 此后再调用就直接命中真实地址，不再绕路。所以 `lazy_bind` 的字节码不是顺序整体执行的，而是**按 stub 偏移被零散索引**触发的——这也是它和 `bind` 在使用方式上的根本区别。

> [!note] lazy_bind 与"启动直接绑定"的取舍
> lazy_bind 用启动速度换"首次调用的一点延迟"。但在 arm64e（带指针认证 PAC）等现代场景，dyld 反而倾向**启动时就全部非惰性绑定**（预绑定），因为页级 fixups（链式）让"全绑"也很快，还省掉了 `__stub_helper` 这条易被 Hook 的路径——这正是 iOS 15 起 lazy_bind 消失的伏笔（见第 6 节）。

#### 表 5 — export：用 trie 描述本镜像导出的符号

前四张表是"**我需要别人什么 / 我内部要改什么**"，export 则是"**我对外提供什么**"。它用一棵**前缀树（trie）**紧凑表达本镜像导出的所有符号名及其地址：共享前缀的符号（如 `_malloc` / `_malloc_zone_malloc`）共用树上的公共路径，查找时沿边逐字符下行即可，无需线性扫描整张符号表，**按名查地址非常高效**——这正是别的镜像 bind 你的符号时所查询的数据源。结构细节见第 5 节。

### 3. opcode 字节码机制简介

前四张表共用一套**字节码虚拟机**。理解它的关键是三点：**单字节打包、ULEB128 续接、状态机压缩**。

**(a) 单字节打包**。每个 opcode 占 1 字节，**高 4 位是操作码、低 4 位是立即数（immediate）**：

```
  ┌─7─6─5─4─┬─3─2─1─0─┐
  │ opcode  │   imm   │      opcode = byte & 0xF0,  imm = byte & 0x0F
  └─────────┴─────────┘
```

所以同一个字节既编码"做什么"，又能携带一个 0–15 的小参数。例如把类型设为 1，可以直接写成 `SET_TYPE_IMM | 1`，一个字节搞定。

**(b) ULEB128 续接**。当参数超过 15（地址偏移、段内偏移、库序号、addend 等），opcode 字节后面**紧跟一个 ULEB128 变长整数**（Unsigned Little-Endian Base-128，每字节 7 位有效、最高位为续接标志；这套编码也用于 DWARF）。符号名则是 opcode 后**以 `\0` 结尾的 UTF-8 字符串**。

**(c) 状态机压缩**。解析器维护一组"寄存器"（当前段索引、当前段内偏移、当前类型、当前符号名、当前库序号、当前 addend……）。opcode 流像在**逐列改写这组寄存器**，每凑齐一行就执行一次 `DO_REBASE` / `DO_BIND` 落地一项，并默认继承上一行的列值——**只有变化的列才需要 opcode**。这就是它能把成百上千条重定位压成几十字节的根本。

下面给出 `loader.h` 里**完整的 opcode 常量与十六进制值**。

**REBASE 类型与 opcode：**

| 常量 | 值 | 含义 |
|---|---|---|
| `REBASE_TYPE_POINTER` | `1` | 指针型重定位（最常见） |
| `REBASE_TYPE_TEXT_ABSOLUTE32` | `2` | text 段内 32 位绝对地址 |
| `REBASE_TYPE_TEXT_PCREL32` | `3` | text 段内 32 位 PC 相对地址 |
| `REBASE_OPCODE_MASK` | `0xF0` | 取操作码的掩码 |
| `REBASE_IMMEDIATE_MASK` | `0x0F` | 取立即数的掩码 |
| `REBASE_OPCODE_DONE` | `0x00` | 流结束 |
| `REBASE_OPCODE_SET_TYPE_IMM` | `0x10` | 设置重定位类型（imm 给类型） |
| `REBASE_OPCODE_SET_SEGMENT_AND_OFFSET_ULEB` | `0x20` | 设段索引(imm)+段内偏移(ULEB) |
| `REBASE_OPCODE_ADD_ADDR_ULEB` | `0x30` | 当前偏移 += ULEB |
| `REBASE_OPCODE_ADD_ADDR_IMM_SCALED` | `0x40` | 当前偏移 += imm × 指针大小 |
| `REBASE_OPCODE_DO_REBASE_IMM_TIMES` | `0x50` | rebase 接下来 imm 个指针 |
| `REBASE_OPCODE_DO_REBASE_ULEB_TIMES` | `0x60` | rebase 接下来 ULEB 个指针 |
| `REBASE_OPCODE_DO_REBASE_ADD_ADDR_ULEB` | `0x70` | rebase 1 个，然后偏移 += ULEB |
| `REBASE_OPCODE_DO_REBASE_ULEB_TIMES_SKIPPING_ULEB` | `0x80` | rebase N(ULEB)个，每个之间跳过 ULEB 字节 |

**rebase 字节码示例**（把段 0、偏移 0x1000 起的 3 个连续指针加上 slide）：

```text
0x11                    REBASE_OPCODE_SET_TYPE_IMM (type=1, 指针)
0x20 0x80 0x20          SET_SEGMENT_AND_OFFSET_ULEB (seg=0, offset=0x1000)   ; 0x1000 的 ULEB 编码
0x53                    DO_REBASE_IMM_TIMES (3)   ; 连续 rebase 3 个指针
0x00                    REBASE_OPCODE_DONE
```

**BIND 类型与 opcode：**

| 常量 | 值 | 含义 |
|---|---|---|
| `BIND_TYPE_POINTER` | `1` | 指针型绑定（最常见） |
| `BIND_TYPE_TEXT_ABSOLUTE32` | `2` | text 段 32 位绝对 |
| `BIND_TYPE_TEXT_PCREL32` | `3` | text 段 32 位 PC 相对 |
| `BIND_OPCODE_MASK` | `0xF0` | 取操作码掩码 |
| `BIND_IMMEDIATE_MASK` | `0x0F` | 取立即数掩码 |
| `BIND_OPCODE_DONE` | `0x00` | 流结束（lazy_bind 中是"每条记录结束"） |
| `BIND_OPCODE_SET_DYLIB_ORDINAL_IMM` | `0x10` | 设依赖库序号（imm 给序号 1–15） |
| `BIND_OPCODE_SET_DYLIB_ORDINAL_ULEB` | `0x20` | 设依赖库序号（ULEB，序号 >15） |
| `BIND_OPCODE_SET_DYLIB_SPECIAL_IMM` | `0x30` | 设特殊库序号（self/main/flat 等负值） |
| `BIND_OPCODE_SET_SYMBOL_TRAILING_FLAGS_IMM` | `0x40` | 设符号名(尾随字符串)+标志(imm) |
| `BIND_OPCODE_SET_TYPE_IMM` | `0x50` | 设绑定类型 |
| `BIND_OPCODE_SET_ADDEND_SLEB` | `0x60` | 设 addend（SLEB128，可负） |
| `BIND_OPCODE_SET_SEGMENT_AND_OFFSET_ULEB` | `0x70` | 设段索引(imm)+段内偏移(ULEB) |
| `BIND_OPCODE_ADD_ADDR_ULEB` | `0x80` | 当前偏移 += ULEB |
| `BIND_OPCODE_DO_BIND` | `0x90` | 绑定当前符号到当前地址，偏移 += 指针大小 |
| `BIND_OPCODE_DO_BIND_ADD_ADDR_ULEB` | `0xA0` | 绑定 1 个，然后偏移 += ULEB |
| `BIND_OPCODE_DO_BIND_ADD_ADDR_IMM_SCALED` | `0xB0` | 绑定 1 个，偏移 += imm × 指针大小 |
| `BIND_OPCODE_DO_BIND_ULEB_TIMES_SKIPPING_ULEB` | `0xC0` | 绑定 N(ULEB)个，每个间跳 ULEB 字节 |

特殊库序号（配合 `SET_DYLIB_SPECIAL_IMM`，用低 4 位编码负值）：

| 常量 | 值 | 含义 |
|---|---|---|
| `BIND_SPECIAL_DYLIB_SELF` | `0` | 绑定到本镜像自身 |
| `BIND_SPECIAL_DYLIB_MAIN_EXECUTABLE` | `-1` | 绑定到主可执行文件 |
| `BIND_SPECIAL_DYLIB_FLAT_LOOKUP` | `-2` | 平坦命名空间查找（遍历所有库） |
| `BIND_SPECIAL_DYLIB_WEAK_LOOKUP` | `-3` | 弱查找（找不到不报错，填 0） |

符号尾随标志（`SET_SYMBOL_TRAILING_FLAGS_IMM` 的 imm 位）：`BIND_SYMBOL_FLAGS_WEAK_IMPORT = 0x1`（弱导入，找不到允许为 0）、`BIND_SYMBOL_FLAGS_NON_WEAK_DEFINITION = 0x8`。

**bind 字节码示例**（把来自第 2 个依赖库的 `_foo` 绑定到段 1 的某偏移）：

```text
0x12                       SET_DYLIB_ORDINAL_IMM (dylib #2)
0x40 '_' 'f' 'o' 'o' 0x00  SET_SYMBOL_TRAILING_FLAGS_IMM (flags=0, "_foo\0")
0x51                       SET_TYPE_IMM (type=1, 指针)
0x71 0x10                  SET_SEGMENT_AND_OFFSET_ULEB (seg=1, offset=0x10)
0x90                       DO_BIND
0x00                       BIND_OPCODE_DONE
```

> [!note] 为什么"读 opcode 还得读 dyld 源码"
> `loader.h` 对这些 opcode 只有寥寥注释，很多行为细节（如每次 `DO_BIND` 后偏移会**自动 +1 个指针大小**、lazy_bind 里每条记录以 `DONE` 分隔而非整体一个 `DONE`）只看头文件根本推不出来。要写正确的解析器，权威做法是读 `dyld` 开源实现里 `ImageLoaderMachOCompressed.cpp`（旧）/ `MachOAnalyzer`、`MachOLoaded`（新）中对应的解释循环。

### 4. `LC_DYLD_INFO` vs `LC_DYLD_INFO_ONLY`

两者**命令结构完全相同**（都是上面那 48 字节的 `dyld_info_command`），区别只在 `cmd` 字段的取值，本质是**带不带 `LC_REQ_DYLD` 标志位**：

| 维度 | `LC_DYLD_INFO` | `LC_DYLD_INFO_ONLY` |
|---|---|---|
| `cmd` 值 | `0x22` | `0x80000022` |
| `LC_REQ_DYLD`(`0x80000000`) | 不带 | **带** |
| 语义 | "这里有 dyld 信息"（兼容/可选） | "dyld 信息**只**在这里" |
| 老 dyld 不识别时 | 可**忽略**本命令、回退到传统重定位项 | **必须中止加载**（无法理解就拒绝运行镜像） |
| 现代默认 | 否 | **是** |

`LC_REQ_DYLD`（`0x80000000`）是加载命令通用的"required for dyld"高位标志（见 [[03.Mach-O加载命令]]）：凡 `cmd` 带上这一位，就告诉 `dyld`"这条命令你**必须**看懂并处理，否则不准加载"。`_ONLY` 后缀正是这个意思——动态链接信息**只**编码在这条命令里，没有传统重定位项作后备，所以 `dyld` 没有"忽略它回退"的退路。实践中你在现代二进制里几乎只会看到 `LC_DYLD_INFO_ONLY`。

> [!note] 架构无关，但字节码内容随架构而异
> 命令的 12 个字段都是 32 位偏移/大小，**命令本身与 32/64 位目标无关**（不像段命令有 `LC_SEGMENT`/`LC_SEGMENT_64` 之分）。但它**指向**的 opcode 流里，"指针大小"（`DO_BIND` 后偏移自增多少、`ADD_ADDR_IMM_SCALED` 的缩放因子）会随目标是 32 位还是 64 位而不同——4 字节还是 8 字节——由 `dyld` 按镜像架构解释。export trie 里的地址同理。

### 5. export trie（导出符号前缀树）的结构

export 段是五张表里唯一**不用 opcode** 的：它是一棵 **trie（前缀树 / 字典树）**，整体也是 ULEB128 字节流编码。从根节点到某终端节点沿途各边拼出的字符串，就是一个导出符号名；共享前缀的符号共用公共路径——这是它紧凑且查找快的来源。

**单个节点的布局**（顺序）：

1. **终端信息长度**：一个 ULEB128，表示"本节点的终端导出信息有多少字节"。
   - 若为 `0x00` → 本节点**不是**某个完整符号的终点（只是中间节点），无导出信息，直接跳到第 3 步。
   - 若非 0 → 本节点是一个完整符号的终点，紧跟该长度字节的"终端信息"（第 2 步）。每个节点**至多一个**终端信息。
2. **终端信息**（仅终端节点有）：
   - 先是一个 ULEB128 **flags**（见下表）。
   - 通常 flags 后跟一个 ULEB128 **地址偏移**——符号内容相对镜像 `mach_header` 的偏移（普通符号即此情形）。
   - 若 flags 含 `EXPORT_SYMBOL_FLAGS_REEXPORT(0x08)`：后面是 ULEB128 **库序号** + `\0` 结尾 UTF-8 **原名字符串**（空串表示"在指定库里同名重导出"）。这是**重导出**，常见于 `libsystem_c.dylib` 把 `_strcmp`/`_memcpy` 等转发给底层库。
   - 若 flags 含 `EXPORT_SYMBOL_FLAGS_STUB_AND_RESOLVER(0x10)`：后面是**两个 ULEB128**——stub 偏移 + resolver 偏移（用于 IFUNC 式的运行时择优实现）。
3. **子边数量**：1 字节，表示本节点有几条出边（0–255）。
4. **各条子边**：每条 = `\0` 结尾 UTF-8 **边字符串**（在当前前缀上追加的字符）+ ULEB128 **子节点偏移**（相对 trie 起点，不是真正指针）。

**`EXPORT_SYMBOL_FLAGS_*` 取值**（terminal flags 字节）：

| 常量 | 值 | 含义 |
|---|---|---|
| `EXPORT_SYMBOL_FLAGS_KIND_MASK` | `0x03` | 低 2 位为"种类"掩码 |
| `EXPORT_SYMBOL_FLAGS_KIND_REGULAR` | `0x00` | 普通符号 |
| `EXPORT_SYMBOL_FLAGS_KIND_THREAD_LOCAL` | `0x01` | 线程局部存储（TLS）符号 |
| `EXPORT_SYMBOL_FLAGS_KIND_ABSOLUTE` | `0x02` | 绝对符号 |
| `EXPORT_SYMBOL_FLAGS_WEAK_DEFINITION` | `0x04` | 弱定义 |
| `EXPORT_SYMBOL_FLAGS_REEXPORT` | `0x08` | 重导出（带库序号 + 可选原名） |
| `EXPORT_SYMBOL_FLAGS_STUB_AND_RESOLVER` | `0x10` | 带 stub 偏移 + resolver 偏移 |

```text
        (root)
          │
        "_m"
          │
        ( · )───"alloc"──► [终端: flags=0x00(REGULAR), addr=0x3a40]   → _malloc
          │
        "alloc_zone_malloc"──► [终端: addr=0x3b10]                     → _malloc_zone_malloc
```

> [!note] ULEB128 与 127 的玄机
> trie 里 `≤127`（`0x7f`）的数其 ULEB128 编码就等于单字节本身，所以小偏移看起来"就是普通字节"。dyld 源码有个观察：终端信息长度**唯一**会超过 127 的情形，就是"带名字的重导出"（reexport with name）——因为它要塞下库序号加一整条符号名字符串。这也是解析时区分"普通小节点"和"重导出"的一个旁证。

### 6. 现代取代：链式 fixups（iOS 15 / macOS 12 起）

自 **iOS 15 / macOS 12** 起（以这些版本或更新为部署目标编译的二进制），`LC_DYLD_INFO_ONLY` 被一对新命令取代：

- **`LC_DYLD_CHAINED_FIXUPS`**（`0x80000034`，带 `LC_REQ_DYLD`）——接管 **rebase + bind**。
- **`LC_DYLD_EXPORTS_TRIE`**（`0x80000033`，带 `LC_REQ_DYLD`）——接管 **export**（trie 格式原样不变，只是改由一个 `linkedit_data_command` 指向其首节点）。

数据是这样重新分配的：**export 原样搬到 `LC_DYLD_EXPORTS_TRIE`**（结构不变）；**rebase 和 bind 被"链"在一起、按内存页重组，搬进 `LC_DYLD_CHAINED_FIXUPS`**；而 **lazy_bind 彻底消失**——连带 `__DATA,__la_symbol_ptr`（[[30.Mach-O __la_symbol_ptr节]]）这个惰性指针节也一并去掉了。

**为什么更快、更小**：旧机制里 rebase/bind/lazy_bind 是三张独立的表，启动时要分别遍历。链式 fixups 把"同一内存页内的所有修补"串成一条**链（chain）**——每个待修补的 64 位指针里，**借用高位的若干 bit 存"到下一个待修补点的步距（next，单位 4 字节）"**，`dyld` 顺着链一跳一跳走，一遍扫描就把这一页的 rebase 和 bind **同时**做完。更妙的是，因为按页组织，可以**按缺页（page fault）惰性触发**——某页没被访问就不修补，等于"rebase/bind 也变惰性了"，于是传统 lazy_bind 失去存在意义。

**体积收益**：链式指针里 rebase 目标用 36 位（够 64GB 镜像）、next 步距用 12 位（`2^12 × 4 = 16KB`，正好一页），元数据只需"每页第一个 fixup 的位置"。实测大型 Swift App 的 dyld 数据体积可省 50% 以上（如某 App 减小逾 1MB，Airbnb 实测省 1.4MB）。

**逆向影响**：链式 fixups 让原始二进制里的指针长得很怪（高位塞了链信息，像 `0x0010000101effaa0`），并且一度让 Ghidra 等工具无法识别 `0x80000034`/`0x80000033` 而加载失败。结构定义在 `/usr/include/mach-o/fixup-chains.h`（`dyld_chained_fixups_header` → `dyld_chained_starts_in_image` → 每段 `dyld_chained_starts_in_segment` → 每页 page_starts → 逐个 64 位 fixup，最低位区分 rebase/bind）。

> [!note] 不是"iOS 15 才发明"，而是"iOS 15 才默认开"
> 链式 fixups 的格式其实更早就预置在 dyld 里：用链接器标志 `-fixup_chains` 可以在 iOS 14.6、甚至 iOS 13.4.1 上提前启用。iOS 15 / macOS 12 只是把它设成了**默认部署目标行为**。所以"用不用链式 fixups"取决于编译时的**最低部署目标**，而非运行设备——一个为兼容老系统而把部署目标定低的二进制，今天仍会生成 `LC_DYLD_INFO_ONLY`。

## FAQ

> [!question] `LC_DYLD_INFO` 和 `LC_DYLD_INFO_ONLY` 到底差在哪？为什么现在几乎只见后者？
> 两者**结构完全一样**（同一个 48 字节 `dyld_info_command`），只差 `cmd` 值带不带 `LC_REQ_DYLD`（`0x80000000`）这一位：`LC_DYLD_INFO=0x22`（不带，"信息在这里、但你不认识可以回退到传统重定位项"），`LC_DYLD_INFO_ONLY=0x80000022`（带，"动态链接信息**只**在这里，你必须看懂，否则拒绝加载"）。现代工具链不再生成传统重定位项作后备，所以必须用 `_ONLY` 强制 `dyld` 处理——于是你在现代二进制里几乎只会看到 `LC_DYLD_INFO_ONLY`。

> [!question] rebase 和 bind 有什么区别？为什么需要两张表？
> 它们解决的是**两类不同的"错指针"**。**rebase** 修的是镜像**内部**指针：因为 ASLR 把整个镜像挪了个随机 slide，所有"指向自身"的绝对地址都得统一 +slide——它只做加法，**不涉及符号名**。**bind** 填的是**外部**符号引用：`printf` 在哪、`NSObject` 在哪，得到运行时才从依赖库里查出真实地址写回——它必须带**符号名 + 来自第几个库 + addend**。一个是"我自己内部地址偏移了"，一个是"我要别人的东西"，信息维度不同，自然是两套字节码、两张表。

> [!question] lazy bind 为什么能加快启动？它和 weak bind 各自解决什么？
> **lazy_bind**：函数符号往往大量但未必都会被调用，把它们的绑定推迟到"第一次真正调用"时（经 `__stubs`→`__stub_helper`→`dyld` 触发后回填 `__la_symbol_ptr`），启动时就不必逐个解析，**用首调的一点延迟换启动速度**。**weak_bind**：解决 C++ 等语言"多个镜像定义了同名弱符号（内联函数/模板实例/`operator new`）"时的**去重合并**——必须保证全进程用同一份，否则会 new/delete 错配。它在 bind 之后跑、按符号名排序，让 dyld 能线性扫出跨镜像的同名撞车。一个是"省启动"，一个是"保唯一"，互不相干。

> [!question] 我的二进制里根本没有 `LC_DYLD_INFO_ONLY`，只有 `LC_DYLD_CHAINED_FIXUPS`，是不是这篇过时了？
> 不是——是你的二进制部署目标 ≥ iOS 15 / macOS 12，走了**链式 fixups** 新机制（见第 6 节）。新机制把 rebase+bind"链"成按页组织的链（一遍扫描同时完成、还能按缺页惰性触发），export 单独搬到 `LC_DYLD_EXPORTS_TRIE`（trie 格式不变），lazy_bind 整个取消。但：① 兼容老系统、把部署目标定低的二进制今天仍生成 `LC_DYLD_INFO_ONLY`；② 海量现存二进制是旧格式；③ 读懂五张表才能理解链式 fixups 究竟优化掉了什么。所以它依然是基础必修。判断走哪套，看加载命令里是 `LC_DYLD_INFO_ONLY` 还是 `LC_DYLD_CHAINED_FIXUPS`/`LC_DYLD_EXPORTS_TRIE` 即可。

> [!question] export 表为什么不用 opcode、而要专门搞一棵 trie？
> 因为 export 的诉求和前四张表不同：前四张是"**顺序执行一串修补动作**"，opcode 状态机最省；export 则是"**供别人按符号名快速查地址**"——别的镜像 bind 你的符号时要反复查询它。trie（前缀树）让共享前缀的符号共用路径，按名查找时沿边逐字符下行即可，无需扫描整张符号表，命中快、且天然去重前缀、体积也小。所以它是为"被查询"优化的只读索引，结构上与"被执行"的 opcode 流完全两类。

## 与相邻章节的关系

- [[16.Mach-O __LINKEDIT]]：五张表的**物理归宿**——本命令只是目录，opcode 流与 trie 的字节实体都住在 `__LINKEDIT` 里。
- [[06.Mach-O LC_DYSYMTAB]]：传统的动态符号视图（间接符号表 + 重定位项），与本命令**互补/部分被取代**——`LC_DYLD_INFO_ONLY` 正是它的紧凑替代。
- [[22.Mach-O __stubs节]]、[[30.Mach-O __la_symbol_ptr节]]、[[23.Mach-O __stubs_helper节]]：**lazy_bind 触发路径**上的三个节（桩 → 惰性指针 → 助手），链式 fixups 下已消失。
- [[31.Mach-O __nl_symbol_ptr节]]：**非惰性 bind** 写回的目标节之一。
- [[15.Mach-O __DATA_CONST]]：rebase/bind 改写的指针（`__got` 等）多落在此段，dyld 写完后再 `SG_READ_ONLY` 降为只读。
- [[03.Mach-O加载命令]]：本命令复用统一的 `load_command{cmd,cmdsize}` 头；`LC_REQ_DYLD` 高位标志的语义见该篇。
- [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]：ASLR slide 的来源——rebase 要加的就是这个 slide。

## 小结

- `LC_DYLD_INFO_ONLY` 用 **rebase / bind / weak_bind / lazy_bind / export** 五张压缩表，描述 `dyld` 运行时的全部"修补工作"；命令体是定长 **48 字节**的 `dyld_info_command`（5 对 `(off,size)`），数据全部落在 [[16.Mach-O __LINKEDIT]]。
- **rebase** 修镜像内部 ASLR 指针（只加 slide、不涉符号）；**bind** 绑外部符号（带符号名/库序号/addend）；**weak_bind** 在 bind 后做弱符号去重合并（按名排序）；**lazy_bind** 把函数绑定推迟到首调（经 `__stubs`→`__stub_helper`→`dyld` 回填 `__la_symbol_ptr`）；**export** 用 trie 供他人按名快速查导出地址。
- 前四张表共用一套 **opcode 字节码**（高 4 位操作码 + 低 4 位立即数，超界用 ULEB128 续接，状态机逐列改写、只编码变化列）；`REBASE_OPCODE_*`(0x00–0x80) 与 `BIND_OPCODE_*`(0x00–0xC0) 定义于 `loader.h`。
- export 是 **trie 前缀树**：节点 = 终端信息长度(ULEB) + 可选终端信息(flags + 地址/重导出/stub-resolver) + 子边数 + 各边(`\0`串 + 子节点偏移)；`EXPORT_SYMBOL_FLAGS_*` 区分普通/TLS/绝对/弱/重导出/stub。
- `cmd` 取 `LC_DYLD_INFO(0x22)`（兼容，可忽略回退）或 `LC_DYLD_INFO_ONLY(0x80000022，带 LC_REQ_DYLD)`（必须处理，现代默认）；命令字段与位宽无关，但其 opcode 里的指针大小随 32/64 位而异。
- 自 **iOS 15 / macOS 12** 起被 **`LC_DYLD_CHAINED_FIXUPS`(0x80000034)** + **`LC_DYLD_EXPORTS_TRIE`(0x80000033)** 取代：rebase+bind 链化按页组织（一遍扫描、缺页惰性触发）、export 单列（trie 格式不变）、lazy_bind 与 `__la_symbol_ptr` 一并取消；但兼容旧系统的二进制仍用本命令。

### rebase/bind opcode 与 chained fixups

本节深入字节层面，把 rebase/bind opcode 机制与 iOS15+/macOS12+ 的 `LC_DYLD_CHAINED_FIXUPS` 字节格式全面展开，形成对照。

#### opcode 高 4 位 + 低 4 位的编码规则（穷尽）

每个 opcode 字节的**高 4 位（`byte & 0xF0`）是操作码，低 4 位（`byte & 0x0F`）是立即数**：

```
  ┌─ bit7 bit6 bit5 bit4 ─┬─ bit3 bit2 bit1 bit0 ─┐
  │    opcode（4 位）       │     imm（4 位）         │
  └───────────────────────┴────────────────────────┘
  取操作码：byte & 0xF0      取立即数：byte & 0x0F
```

这种打包使同一字节能同时携带"做什么"和"一个 0–15 的小参数"，是整套字节码体积小的关键。立即数 0–15 够用的就直接用（如类型编号、段索引、重复次数），不够用时紧跟 ULEB128 续接。

**ULEB128 详细格式**：

```
每字节：[ 续接位(bit7) | 有效负载(bit6..bit0) ]
  bit7=1 → 还有后续字节
  bit7=0 → 最后一个字节

示例（编码 300 = 0x12C）：
  第1字节：0xAC = 0b10101100  →  有效负载 0x2C(44)，续接
  第2字节：0x02 = 0b00000010  →  有效负载 0x02，结束
  解码：44 | (2 << 7) = 44 + 256 = 300 ✓

示例（编码 0）：
  一字节：0x00  →  有效负载 0，结束

最大可编码值（n 字节 ULEB128）：2^(7n) - 1
  1字节 → 0 ~ 127
  2字节 → 0 ~ 16383
  3字节 → 0 ~ 2097151（约 2M）
```

**rebase opcode 完整编码表**（高 4 位 → 操作码，低 4 位 → 立即数用途）：

| 字节值（高4|低4）| 操作码常量 | 立即数用途 | 后续参数 | 状态机效果 |
|---|---|---|---|---|
| `0x00` | `DONE` | 无 | 无 | 停止处理 |
| `0x1N` | `SET_TYPE_IMM` | type=N（1=PTR, 2=ABS32, 3=PCREL32）| 无 | `type = N` |
| `0x2N` | `SET_SEGMENT_AND_OFFSET_ULEB` | seg_index=N | ULEB（offset）| `seg=N; off=ULEB` |
| `0x30` | `ADD_ADDR_ULEB` | 0 | ULEB（delta）| `off += ULEB` |
| `0x4N` | `ADD_ADDR_IMM_SCALED` | scale=N | 无 | `off += N*ptr_size` |
| `0x5N` | `DO_REBASE_IMM_TIMES` | count=N | 无 | rebase N次，`off+=ptr_size`×N |
| `0x60` | `DO_REBASE_ULEB_TIMES` | 0 | ULEB（count）| rebase ULEB次 |
| `0x70` | `DO_REBASE_ADD_ADDR_ULEB` | 0 | ULEB（delta）| rebase 1次，`off+=ULEB` |
| `0x80` | `DO_REBASE_ULEB_TIMES_SKIPPING_ULEB` | 0 | ULEB(N)+ULEB(skip) | rebase N次，每次`off+=ptr_size+skip` |

**bind opcode 完整编码表**：

| 字节值（高4|低4）| 操作码常量 | 立即数用途 | 后续参数 | 状态机效果 |
|---|---|---|---|---|
| `0x00` | `DONE` | 0 | 无 | 一条记录结束（lazy_bind 中为单条，非整流结束）|
| `0x1N` | `SET_DYLIB_ORDINAL_IMM` | ordinal=N（1–15）| 无 | `lib=N` |
| `0x20` | `SET_DYLIB_ORDINAL_ULEB` | 0 | ULEB（ordinal）| `lib=ULEB`（ordinal>15 时用）|
| `0x3N` | `SET_DYLIB_SPECIAL_IMM` | N=0,F,E… | 无 | `lib = -(low4)`（负值特殊库；`0xF`→-1=main_exe, `0xE`→-2=flat）|
| `0x4N` | `SET_SYMBOL_TRAILING_FLAGS_IMM` | flags=N | `\0`结尾的符号名字符串 | `name=str; sym_flags=N` |
| `0x5N` | `SET_TYPE_IMM` | type=N | 无 | `type=N` |
| `0x60` | `SET_ADDEND_SLEB` | 0 | SLEB128（有符号）| `addend=SLEB` |
| `0x7N` | `SET_SEGMENT_AND_OFFSET_ULEB` | seg=N | ULEB（offset）| `seg=N; off=ULEB` |
| `0x80` | `ADD_ADDR_ULEB` | 0 | ULEB（delta）| `off += ULEB` |
| `0x90` | `DO_BIND` | 0 | 无 | 绑定当前(lib,sym,seg,off)，`off += ptr_size` |
| `0xA0` | `DO_BIND_ADD_ADDR_ULEB` | 0 | ULEB（delta）| 绑定1次，`off += ULEB` |
| `0xBN` | `DO_BIND_ADD_ADDR_IMM_SCALED` | scale=N | 无 | 绑定1次，`off += N*ptr_size` |
| `0xC0` | `DO_BIND_ULEB_TIMES_SKIPPING_ULEB` | 0 | ULEB(N)+ULEB(skip) | 绑定N次，每次`off+=ptr_size+skip` |

**特殊库序号（`SET_DYLIB_SPECIAL_IMM` 的低 4 位编码负值）**：

```
低4位=0x0 → 特殊值 0（BIND_SPECIAL_DYLIB_SELF = 绑定到自身）
低4位=0xF → 0xF & ~0xF0 = -1（补码）→ BIND_SPECIAL_DYLIB_MAIN_EXECUTABLE
低4位=0xE → -2 → BIND_SPECIAL_DYLIB_FLAT_LOOKUP
低4位=0xD → -3 → BIND_SPECIAL_DYLIB_WEAK_LOOKUP
```

**一段完整 bind 字节码示例**（把来自库2的 `_printf` 绑到段1偏移 0x50，addend=0）：

```
字节流（十六进制）：
12 40 5F 70 72 69 6E 74 66 00 51 71 50 90 00

拆解：
12  → SET_DYLIB_ORDINAL_IMM, lib=2
40  → SET_SYMBOL_TRAILING_FLAGS_IMM, flags=0
5F 70 72 69 6E 74 66 00  → "_printf\0"（符号名字符串）
51  → SET_TYPE_IMM, type=1（POINTER）
71  → SET_SEGMENT_AND_OFFSET_ULEB, seg=1
50  → ULEB128 = 0x50（段内偏移 80）
90  → DO_BIND（绑定，off+=8）
00  → DONE
```

#### `LC_DYLD_CHAINED_FIXUPS` 的 `dyld_chained_ptr_arm64e` 字节级编码

`LC_DYLD_CHAINED_FIXUPS`（`0x80000034`）是 iOS 15+ / macOS 12+ 替代 `LC_DYLD_INFO_ONLY` 的新机制。其数据位于 `__LINKEDIT` 中，由 `linkedit_data_command.dataoff` 指向，从一个 `dyld_chained_fixups_header` 开始级联描述各段的 fixup 链表。

**整体层级结构（`<mach-o/fixup-chains.h>`）**：

```c
[文件级]
dyld_chained_fixups_header {
    uint32_t fixups_version;   // 固定 0
    uint32_t starts_offset;    // 相对本头的 dyld_chained_starts_in_image 偏移
    uint32_t imports_offset;   // imports 表（被绑定符号列表）偏移
    uint32_t symbols_offset;   // 符号名字符串池偏移
    uint32_t imports_count;    // 导入符号数量
    uint32_t imports_format;   // 导入格式（1=32位,2=64位,3=addend64）
    uint32_t symbols_format;   // 符号名格式（0=uncompressed）
}

[镜像级]
dyld_chained_starts_in_image {
    uint32_t seg_count;        // 段数量
    uint32_t seg_info_offset[seg_count];  // 各段的 starts_in_segment 偏移
}

[段级]
dyld_chained_starts_in_segment {
    uint32_t size;             // 本结构总大小
    uint16_t page_size;        // 页大小（0x1000 或 0x4000）
    uint16_t pointer_format;   // 指针格式（见下表）
    uint64_t segment_offset;   // 本段相对文件头的偏移
    uint32_t max_valid_pointer; // 32位非指针最大值（用于区分指针与整数）
    uint16_t page_count;       // 页数
    uint16_t page_start[page_count];  // 各页第一个 fixup 在页内的偏移（字节），0xFFFF=本页无fixup
}
```

**imports 表项格式**（`imports_format` 决定）：

```c
// format=1：dyld_chained_import（32位）
struct dyld_chained_import {
    uint32_t lib_ordinal : 8;   // 库序号
    uint32_t weak_import : 1;   // 弱导入标志
    uint32_t name_offset : 23;  // 符号名在 symbols 池中的偏移
};

// format=2：dyld_chained_import_addend（64位，带 addend）
struct dyld_chained_import_addend {
    uint32_t lib_ordinal : 8;
    uint32_t weak_import : 1;
    uint32_t name_offset : 23;
    int32_t  addend;
};
```

**`pointer_format` 取值与 arm64e 专用格式**：

| 值 | 常量 | 适用架构 | 每个 fixup 指针的位布局 |
|---|---|---|---|
| `1` | `DYLD_CHAINED_PTR_ARM64E` | arm64e | 见下详解 |
| `2` | `DYLD_CHAINED_PTR_64` | arm64/x86_64 | rebase=target(36b)+high8(8b)+next(12b)+bind=0(1b) |
| `3` | `DYLD_CHAINED_PTR_32` | armv7/x86 | 32位小页面格式 |
| `4` | `DYLD_CHAINED_PTR_32_CACHE` | 32位缓存 | - |
| `5` | `DYLD_CHAINED_PTR_32_FIRMWARE` | 固件 | - |
| `6` | `DYLD_CHAINED_PTR_64_OFFSET` | arm64（偏移变体）| target 为镜像内偏移 |
| `7` | `DYLD_CHAINED_PTR_ARM64E_KERNEL` | arm64e 内核 | - |
| `12` | `DYLD_CHAINED_PTR_ARM64E_USERLAND` | arm64e 用户态（主流）| 见下 |
| `13` | `DYLD_CHAINED_PTR_ARM64E_FIRMWARE` | arm64e 固件 | - |

**`DYLD_CHAINED_PTR_ARM64E`（format=1）的 64 位指针位布局**：

```
当 bind=0（rebase 目标，指向镜像内）：
  ┌─ 63 ─┬─ 62..49 ─┬─ 48..37 ─┬─ 36..0 ─┐
  │ bind │  high8   │  next    │ target   │
  │  =0  │ (8 bit)  │ (12 bit) │ (37 bit) │
  └──────┴──────────┴──────────┴──────────┘
  target: 37位，单位字节，相对镜像起点的偏移（最大 128GB）
  high8:  复原指针高8位（用于 tagged pointer / TBI）
  next:   到下一个 fixup 的步距，单位4字节（=0表示链尾）

当 bind=1（导入符号，指向 imports 表）：
  ┌─ 63 ─┬─ 62..53 ─┬─ 52..37 ─┬─ 36..33 ─┬─ 32..16 ─┬─ 15..0 ─┐
  │ bind │ ordinal  │  zero    │  addend  │   next   │ ordinal2 │
  │  =1  │ (10 bit) │ (16 bit) │  (4 bit) │ (17 bit) │(16 bit)  │
  └──────┴──────────┴──────────┴──────────┴──────────┴──────────┘
  （实际布局由版本而异，见下文 arm64e_userland 精确定义）
```

**`DYLD_CHAINED_PTR_ARM64E_USERLAND`（format=12，当前主流 arm64e）的精确位布局**：

```c
// 头文件：<mach-o/fixup-chains.h>

// rebase 变体（bind=0）
struct dyld_chained_ptr_arm64e_rebase {
    uint64_t target   : 43;  // 镜像内 vm offset（0..8TB 范围）
    uint64_t high8    :  8;  // 地址高 8 位
    uint64_t next     : 11;  // 下一个 fixup 步距（单位：8字节）→ 最大跳 16KB（≤ arm64 页）
    uint64_t bind     :  1;  // = 0
    uint64_t auth     :  1;  // = 0（非认证指针）
};

// bind 变体（bind=1）
struct dyld_chained_ptr_arm64e_bind {
    uint64_t ordinal  : 24;  // imports 表索引
    uint64_t addend   :  8;  // 小 addend（有符号，±128）
    uint64_t reserved : 19;
    uint64_t next     : 11;
    uint64_t bind     :  1;  // = 1
    uint64_t auth     :  1;  // = 0
};

// auth_rebase 变体（bind=0, auth=1）— PAC 认证指针
struct dyld_chained_ptr_arm64e_auth_rebase {
    uint64_t target   : 32;  // 镜像内 vm offset（低32位，+sign_extended）
    uint64_t diversity: 16;  // PAC diversity value
    uint64_t addr_div :  1;  // 地址多样性（address diversity）
    uint64_t key      :  2;  // PAC key（0=IA, 1=IB, 2=DA, 3=DB）
    uint64_t next     : 11;
    uint64_t bind     :  1;  // = 0
    uint64_t auth     :  1;  // = 1
};

// auth_bind 变体（bind=1, auth=1）
struct dyld_chained_ptr_arm64e_auth_bind {
    uint64_t ordinal  : 24;
    uint64_t zero     :  8;
    uint64_t diversity: 16;
    uint64_t addr_div :  1;
    uint64_t key      :  2;
    uint64_t next     : 11;
    uint64_t bind     :  1;  // = 1
    uint64_t auth     :  1;  // = 1
};
```

**`next` 字段的步距语义**（arm64e_userland）：

```
next 字段值 → 到下一个 fixup 的字节距离
  值 N → 步距 = N * 8 字节（单位 8B，因 arm64e 指针 8B 对齐）
  next = 0 → 链表末尾（本段/本页最后一个 fixup）

链遍历伪代码：
  uint8_t *page_base = segment + page_start[page_index];
  uint64_t *ptr = (uint64_t*)(page_base + page_starts[i]);
  while (true) {
      process_fixup(ptr);    // 判断 bind/auth 位，分别 rebase 或 bind
      uint64_t next = (*ptr >> 51) & 0x7FF;   // 取 next 字段（示意，实际按结构体字段）
      if (next == 0) break;
      ptr = (uint64_t*)((uint8_t*)ptr + next * 8);
  }
```

**区分四种 arm64e fixup 变体的判别树**：

```
读取 64 位指针 raw_value:
  auth = (raw_value >> 63) & 1
  bind = (raw_value >> 62) & 1
  ┌─ auth=0, bind=0 → dyld_chained_ptr_arm64e_rebase（普通 rebase）
  ├─ auth=0, bind=1 → dyld_chained_ptr_arm64e_bind（普通 bind）
  ├─ auth=1, bind=0 → dyld_chained_ptr_arm64e_auth_rebase（PAC rebase）
  └─ auth=1, bind=1 → dyld_chained_ptr_arm64e_auth_bind（PAC bind）
```

**PAC key 含义**（`key` 字段2位）：

| key 值 | PAC key | 用途 |
|---|---|---|
| `0` | `IA`（Instruction key A）| 函数指针（代码）|
| `1` | `IB`（Instruction key B）| 函数指针（代码，备用）|
| `2` | `DA`（Data key A）| 数据指针（GOT/vtable）|
| `3` | `DB`（Data key B）| 数据指针（备用）|

**`diversity`（16位）与 `addr_div`（1位）组合为 PAC 签名的 context**：

```
PAC 签名计算：
  context = addr_div ? (diversity << 48 | pointer_location) : diversity
  sign:   ptrauth_sign_unauthenticated(target, key, context)
  verify: ptrauth_auth_data(ptr_value, key, context)
    — 验证失败 → 硬件触发 PAC 异常（arm64e exclusive exception）
```

**实际二进制中 arm64e fixup 指针的"奇怪"样子**（未经 dyld 处理时）：

```
原始指针（在 __DATA_CONST/__got 中，未 rebase）：
  0x802C00000001E000

拆解（auth_rebase，auth=1,bind=0）：
  bit63=1 (auth)
  bit62=0 (bind=0 → rebase)
  target(32)  = 0x0001E000 → 镜像内偏移
  diversity   = 0x802C >> ...（根据实际结构体位字段计算）
  next        = ...

dyld 处理后：
  用 ptrauth_sign_unauthenticated(image_base + 0x1E000, key=IA, context=...) 
  得到带 PAC 签名的真实指针，写回原位置
```

# 现代 dyld_info 工具解析（macOS 12+ 系统自带）
