# 详解Mach-O(二)Mach-O文件头

> [!abstract] TL;DR
> Mach-O Header（文件头）是文件偏移 0 处的**固定长度结构**，是内核与 `dyld` 读到的第一段数据，相当于整个文件的"身份证 + 阅读说明"。
> 它由 `mach_header`（32 位，28 字节）或 `mach_header_64`（64 位，32 字节）描述，七到八个字段：`magic`（魔数→位宽/字节序）、`cputype`/`cpusubtype`（目标 CPU）、`filetype`（用途）、`ncmds`/`sizeofcmds`（Load Commands 表的条数与总长）、`flags`（特性开关）、`reserved`（仅 64 位）。
> 解析任何 Mach-O 的第 0 步都是读这 4 字节魔数；随后凭 `cputype` 适配架构、凭 `filetype` 决定处理方式、凭 `ncmds`/`sizeofcmds` 框定命令流边界。本篇把 [[01.Mach-O基础]] 中一笔带过的 Header 放大到**每个字段的每个取值**。

## 概述与定位

在 [[01.Mach-O基础]] 中我们看到 Mach-O 是 **Header → Load Commands → Data** 的三段式结构。本篇聚焦第一段——**Header**。

Header 位于文件偏移 0，长度固定，在系统加载链路里扮演三个角色：

- **识别**：内核（XNU）拿到文件先读魔数，判断是不是 Mach-O、32 还是 64 位、字节序如何。校验不过直接拒绝。
- **适配**：`cputype`/`cpusubtype` 声明目标 CPU，内核据此确认能否在当前设备运行。Fat Binary 会先在外层挑出匹配架构的切片，再读它的 Header（见下文"Fat Binary 外层"与 [[01.Mach-O基础]]）。
- **导航**：`ncmds`/`sizeofcmds` 告诉解析器命令表共几条、总长多少字节，是遍历 [[03.Mach-O加载命令]] 的入口与边界。

Header 不含任何代码或数据，它是一份"如何读懂这个文件"的元说明。

## 结构图示

64 位 Header（`mach_header_64`）的字段按内存顺序排布：

```text
偏移   字段          宽度    含义
+0x00  magic         4B      魔数：位宽 + 字节序
+0x04  cputype       4B      CPU 架构大类（含 ABI64 标志位）
+0x08  cpusubtype    4B      CPU 子类型（低 24 位）+ capability（高 8 位）
+0x0c  filetype      4B      文件类型（MH_EXECUTE / MH_DYLIB …）
+0x10  ncmds         4B      Load Command 条数
+0x14  sizeofcmds    4B      所有 Load Command 总字节数
+0x18  flags         4B      特性标志（MH_PIE / MH_TWOLEVEL …）
+0x1c  reserved      4B      保留（仅 64 位 Header 有）
──────────────────────────────  ← Header 结束（0x20），Load Commands 起始
+0x20  load_command[0] …
```

32 位 `mach_header` 比 64 位少末尾的 `reserved`，其余字段名与顺序完全一致；故命令表起点 = Header 长度（28 / 32 字节）。

## 核心原理与字段详解

### 1. 结构体定义（32 / 64 位）

定义于 `<mach-o/loader.h>`：

```c
struct mach_header {            // 32 位，28 字节
    uint32_t      magic;        // 魔数
    cpu_type_t    cputype;      // CPU 类型
    cpu_subtype_t cpusubtype;   // CPU 子类型
    uint32_t      filetype;     // 文件类型
    uint32_t      ncmds;        // 加载命令数量
    uint32_t      sizeofcmds;   // 所有加载命令总字节数
    uint32_t      flags;        // 标志位
};

struct mach_header_64 {         // 64 位，32 字节（当代主流）
    uint32_t      magic;
    cpu_type_t    cputype;
    cpu_subtype_t cpusubtype;
    uint32_t      filetype;
    uint32_t      ncmds;
    uint32_t      sizeofcmds;
    uint32_t      flags;
    uint32_t      reserved;     // 仅 64 位多出，用于 8 字节对齐
};
```

`cpu_type_t`、`cpu_subtype_t` 实为 `int32_t`，定义在 `<mach/machine.h>`。

### 2. magic（魔数）—— 解析的第 0 步

魔数是开头 4 字节，同时编码**位宽**与**字节序**：

| 常量 | 值 | 含义 |
|---|---|---|
| `MH_MAGIC` | `0xfeedface` | 32 位、主机字节序 |
| `MH_CIGAM` | `0xcefaedfe` | 32 位、相反字节序（`MH_MAGIC` 字节反转） |
| `MH_MAGIC_64` | `0xfeedfacf` | 64 位、主机字节序（当代主流） |
| `MH_CIGAM_64` | `0xcffaedfe` | 64 位、相反字节序 |

`CIGAM` 是 `MAGIC` 倒拼，助记"字节序反转"。读到 `CIGAM*` 即需对后续所有多字节字段做字节交换。注意 Fat Binary 外层用另一套魔数（见第 8 节）。

### 3. cputype（CPU 大类）

`cputype` 高位可叠加 ABI 位宽标志 `CPU_ARCH_ABI64`（`0x01000000`）：

| 常量 | 值 | 架构 |
|---|---|---|
| `CPU_TYPE_X86` / `CPU_TYPE_I386` | `7` | 32 位 x86 |
| `CPU_TYPE_X86_64` | `0x01000007` | 64 位 x86（`7 \| ABI64`） |
| `CPU_TYPE_ARM` | `12` (`0xC`) | 32 位 ARM |
| `CPU_TYPE_ARM64` | `0x0100000C` | 64 位 ARM（`12 \| ABI64`，Apple Silicon / 现代 iOS） |
| `CPU_TYPE_ARM64_32` | `0x0200000C` | ARM64_32（watchOS，`12 \| ABI64_32(0x02000000)`） |
| `CPU_TYPE_POWERPC` | `18` | PowerPC（历史，Rosetta 早期） |

所以从 `cputype` 是否含 `0x01000000` 即可判断 64 位 ABI，与魔数互相印证。

### 4. cpusubtype（CPU 子类型 + capability）

`cpusubtype` 低 24 位是子类型、高 8 位（掩码 `CPU_SUBTYPE_MASK = 0xff000000`）是 capability 位：

| 常量 | 值 | 含义 |
|---|---|---|
| `CPU_SUBTYPE_ARM64_ALL` | `0` | 通用 arm64 |
| `CPU_SUBTYPE_ARM64E` | `2` | arm64e（带指针认证 PAC） |
| `CPU_SUBTYPE_X86_64_ALL` | `3` | 通用 x86_64 |
| `CPU_SUBTYPE_X86_64_H` | `8` | Haswell 及以上优化 |
| `CPU_SUBTYPE_LIB64`（capability 位） | `0x80000000` | 仅 64 位库可用 |

`arm64` 与 `arm64e` 的区别（PAC 指针认证）就体现在子类型上——这也是为什么同一台 Apple Silicon 上同时存在两种切片。

### 5. filetype（文件类型，全 12 种）

| 常量 | 值 | 用途 |
|---|---|---|
| `MH_OBJECT` | `0x1` | 目标文件 `.o`（编译产物，未链接） |
| `MH_EXECUTE` | `0x2` | 可执行文件（App 主程序） |
| `MH_FVMLIB` | `0x3` | 固定 VM 共享库（历史） |
| `MH_CORE` | `0x4` | 核心转储（core dump） |
| `MH_PRELOAD` | `0x5` | 预加载可执行（嵌入式/固件） |
| `MH_DYLIB` | `0x6` | 动态库 `.dylib` / framework |
| `MH_DYLINKER` | `0x7` | 动态链接器自身（`dyld`） |
| `MH_BUNDLE` | `0x8` | 可加载 Bundle（插件，`dlopen` 载入） |
| `MH_DYLIB_STUB` | `0x9` | 仅供静态链接的库桩（无节内容） |
| `MH_DSYM` | `0xa` | 仅含调试符号的伴生文件 `.dSYM` |
| `MH_KEXT_BUNDLE` | `0xb` | 内核扩展 kext |
| `MH_FILESET` | `0xc` | 多个 Mach-O 的集合（如 dyld 共享缓存、内核 cache） |

`MH_EXECUTE` 才会被内核当主程序找入口（[[09.Mach-O LC_MAIN]]）；`MH_DYLIB` 带 [[08.Mach-O LC_ID_DYLIB]]；`MH_FILESET` 是新近用于 kernelcache / dyld cache 的打包形态。

### 6. ncmds / sizeofcmds（命令表边界）

- `ncmds`：紧随 Header 的 Load Command **条数**。
- `sizeofcmds`：所有命令的**总字节数**。

二者共同界定命令区：起点 = Header 末尾，终点 = 起点 + `sizeofcmds`，且循环 `ncmds` 次按各自 `cmdsize` 步进应恰好走完。两者用于交叉校验，对不上即视为损坏。遍历细节见 [[03.Mach-O加载命令]]。

### 7. flags（标志位，常用值）

`flags` 是按位特性开关，常见：

| 标志 | 值 | 含义 |
|---|---|---|
| `MH_NOUNDEFS` | `0x1` | 无未定义符号 |
| `MH_DYLDLINK` | `0x4` | 由 `dyld` 链接（非静态可执行） |
| `MH_BINDATLOAD` | `0x8` | 加载时即绑定全部符号 |
| `MH_PREBOUND` | `0x10` | 已预绑定（旧机制） |
| `MH_SPLIT_SEGS` | `0x20` | 只读段与读写段分离 |
| `MH_TWOLEVEL` | `0x80` | 两级命名空间 |
| `MH_WEAK_DEFINES` | `0x8000` | 含弱符号定义 |
| `MH_BINDS_TO_WEAK` | `0x10000` | 绑定到弱符号 |
| `MH_PIE` | `0x200000` | 位置无关可执行（配合 ASLR） |
| `MH_HAS_TLV_DESCRIPTORS` | `0x800000` | 含线程局部变量描述符 |
| `MH_NO_HEAP_EXECUTION` | `0x1000000` | 堆不可执行 |
| `MH_APP_EXTENSION_SAFE` | `0x02000000` | App Extension 安全 |
| `MH_DYLIB_IN_CACHE` | `0x80000000` | 位于 dyld 共享缓存中 |

`MH_PIE` + `MH_TWOLEVEL` 是现代常态：前者让镜像可被随机加载（rebase 修正内部指针，见 [[17.Mach-O LC_DYLD_INFO_ONLY]]），后者提升符号解析安全性。

### 8. Fat / Universal Binary 外层结构

Fat Binary 在真正的 Mach-O 之前还有一层"包头"，**以大端（big-endian）存储**（与单架构 Mach-O 的主机字节序不同，这是个易错点）：

```c
struct fat_header {
    uint32_t magic;     // FAT_MAGIC 0xcafebabe / FAT_MAGIC_64 0xcafebabf
    uint32_t nfat_arch; // 后随的 fat_arch 条数
};
struct fat_arch {
    cpu_type_t    cputype;
    cpu_subtype_t cpusubtype;
    uint32_t      offset;    // 该架构 Mach-O 在文件中的偏移
    uint32_t      size;      // 该架构 Mach-O 的大小
    uint32_t      align;     // 对齐（2 的幂）
};
```

`FAT_MAGIC_64`（`0xcafebabf`）对应 `fat_arch_64`，`offset`/`size` 扩为 64 位。系统按当前设备的 `cputype`/`cpusubtype` 在 `fat_arch` 数组里挑出匹配切片，再 `offset` 跳到那份单架构 Mach-O 读其 Header。

### 9. 逆向：手工解析 Header 的步骤

1. 读前 4 字节判断魔数：`0xfeedfacf`→64 位小端；`0xcafebabe`→Fat（转大端、按 `nfat_arch` 解析切片，先定位目标架构）。
2. 按位宽套 `mach_header(_64)` 读 `cputype`/`filetype`。
3. 读 `ncmds`/`sizeofcmds`，定位命令区 `[0x20, 0x20+sizeofcmds)`。
4. 进入 [[03.Mach-O加载命令]] 的逐条遍历。

> [!note] 架构差异
> - **位宽**：32 位 `mach_header`（28B，`0xfeedface`），64 位 `mach_header_64`（32B，`0xfeedfacf`，多 `reserved`）。
> - **字节序**：`CIGAM*` 时所有多字段需字节交换；Apple 设备均小端，但 **Fat 外层恒为大端**。
> - **arm64 vs arm64e**：差异在 `cpusubtype`（0 vs 2），arm64e 带指针认证（PAC），对应不同切片。

## 实操：用工具查看

```bash
otool -h /bin/ls          # 打印 Header
file /bin/ls              # 人类可读的位宽/架构
otool -f /usr/lib/libSystem.B.dylib   # 查看 Fat 外层各架构切片
lipo -info /bin/ls        # 列出 Universal 包含哪些架构
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Mach header
      magic cputype cpusubtype  caps    filetype ncmds sizeofcmds      flags
 0xfeedfacf 16777228          0  0x00          2    19       2456 0x00200085
```

逐列解读：

- `magic = 0xfeedfacf` → 64 位小端。
- `cputype = 16777228 = 0x0100000C = CPU_TYPE_ARM64`（`0x0C` ARM 大类 + `0x01000000` ABI64）。
- `cpusubtype = 0`、`caps = 0x00` → 通用 arm64（若 `caps`/subtype 显示 `2` 则为 arm64e）。
- `filetype = 2` → `MH_EXECUTE`。
- `ncmds = 19`、`sizeofcmds = 2456`。
- `flags = 0x00200085` = `MH_NOUNDEFS(0x1) \| MH_DYLDLINK(0x4) \| MH_TWOLEVEL(0x80) \| MH_PIE(0x200000)`。

`otool -f`（Fat 外层）示意：

```text
Fat headers
fat_magic 0xcafebabe
nfat_arch 2
architecture x86_64
    cputype 16777223      cpusubtype 3      offset 16384   size 50000   align 2^14
architecture arm64e
    cputype 16777228      cpusubtype 2      offset 81920   size 60000   align 2^14
```

## FAQ

> [!question] 为什么 `otool -h` 里 cputype 是 16777228 这种大数？
> 那是十进制的 `0x0100000C`。高位 `0x01000000` 是 `CPU_ARCH_ABI64`（64 位标志），低位 `0x0C` 才是 ARM 大类。换算成十六进制就一目了然。

> [!question] `caps` 这一列是什么？
> 它是 `cpusubtype` 高 8 位的 capability 位（`CPU_SUBTYPE_MASK`）。子类型真正的型号信息在低 24 位，capability 位用于 `CPU_SUBTYPE_LIB64` 等标记。

> [!question] arm64 和 arm64e 在 Header 上怎么区分？
> `cputype` 都是 `CPU_TYPE_ARM64`，区别在 `cpusubtype`：arm64 为 `0`（`ARM64_ALL`），arm64e 为 `2`（带指针认证 PAC）。Universal 包里二者是不同切片。

## 小结

- Header 是文件偏移 0 的固定结构，不含代码/数据，承载"如何读懂本文件"的元信息。
- `magic` 是第 0 步（位宽 + 字节序）；`cputype`/`cpusubtype` 定架构（含 ABI64、arm64e 等）；`filetype` 定用途（12 种）；`ncmds`/`sizeofcmds` 划命令区；`flags` 是特性开关。
- Fat Binary 外层 `fat_header`/`fat_arch` **以大端存储**，按架构挑切片。
- 读懂 Header 即可进入 [[03.Mach-O加载命令]]。
