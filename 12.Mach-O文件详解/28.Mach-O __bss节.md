# 详解Mach-O(二十八)Mach-O __bss节

> [!abstract] TL;DR
> **`__bss` 是 `__DATA` 段里专门存放"未初始化（或显式初值为 0）的可写全局/静态变量"的节**，节类型为 `S_ZEROFILL`（值 `0x1`，见 [[18.Mach-O section]] 的完整类型表）。
> 它的核心特性是**只记尺寸、不占文件**：节头里 `addr`/`size` 照常填写，但 `size` 这部分字节**不写进磁盘**（不计入段的 `filesize`），`offset` 字段也**不指向本节专属的初始化数据**。这些内存在加载/首次访问时由内核以"零填充"（zero-fill-on-demand）方式补零。
> 这是"用零换体积"的经典优化——一个 `static char buf[1<<20];` 不会让可执行文件凭空大出 1MB。它也是 [[14.Mach-O __DATA]] 段常见 `vmsize > filesize` 的**首要成因**：内存里要占 1MB（计入 `vmsize`），磁盘上一个字节都不存（不计入 `filesize`）。
> 与它互补的是带非零初值、**老老实实占文件**的 [[27.Mach-O __data节]]；另一类历史上的未初始化数据（"暂定定义"全局符号）归 [[29.Mach-O __common节]]。"bss" 是 1950 年代 IBM 704 汇编器留下的历史术语 *Block Started by Symbol*，与"清零"语义本身无关。

## 概述与定位

C/C++ 语言规定：**具有静态存储期、且没有显式初值（或显式初值为 0）的变量，其初值一律为 0**。文件作用域的 `static int n;`、函数内的 `static char buf[4096];`、未赋初值的全局 `int g;`——它们在程序启动那一刻都该是零。

既然"全是零"是规则保证的，那把成片的零字节真的写进可执行文件就是纯粹的浪费：磁盘空间、加载时的 I/O 都白白消耗。`__bss` 节正是为消除这种浪费而生——它**不存这些零字节，只在节头里记录"我需要多大一块内存"**，把真正的"清零"动作推迟到运行时由内核完成。

可以用一句话概括它在 Mach-O 里的角色：

- **`__data`（见 [[27.Mach-O __data节]]）**：装"有非零初值"的可写数据，初值字节实打实写进文件，占 `filesize`。
- **`__bss`（本篇）**：装"零初值/未初始化"的可写数据，**不占文件**，仅靠 `size` 占 `vmsize`，运行时清零。

二者同住 `rw-` 权限的 [[14.Mach-O __DATA]] 段（继承段的可读可写、不可执行权限），互为补集，共同覆盖"程序的可写全局/静态变量"这一完整空间。

> [!note] 一句话区分三类"可写数据节"
> **`__data` 占文件、`__bss` 不占文件、`__common` 是历史遗留的未初始化"暂定定义"**。三者都在 `__DATA`、都可写，区别在"有没有初值"和"链接器何时给它分配空间"：有初值进 `__data`；本编译单元内确定的零初值/未初始化进 `__bss`；跨编译单元、需链接器合并的"暂定定义"历史上进 `__common`（见 [[29.Mach-O __common节]]）。

本篇是 [[18.Mach-O section]]（节通用模型）中 `S_ZEROFILL` 这一节类型的"具体落地分篇"：[[18.Mach-O section]] 把 `section_64` 的所有字段与全部 `flags` 类型讲了一遍，这里只聚焦 `__bss`——把 `S_ZEROFILL` 的语义、"不占文件"的底层机制、`vmsize > filesize` 的本质、以及与相邻节的边界讲透。

> [!note] `__bss` 节名总写作 `__DATA,__bss`
> 和所有节一样（见 [[18.Mach-O section]]），`__bss` 的节名（`sectname`）从不单独出现，而是与段名组成二元组 `__DATA,__bss`。`section_64` 结构里 `segname` 字段会冗余回填为 `__DATA`，`otool -s __DATA __bss` 这类命令也要求段名 + 节名一起给。

> [!note] 零填充节"总排在段尾"是规范要求
> Apple `loader.h` 明确规定：**零填充节在任何格式里都必须放在所属段的最后**（"The zero fill sections are always last in their segment"）。原因是要让"段尾被零填充的内存"恰好覆盖到零填充节所在的虚拟地址区间——把不占文件的零区放在最后，文件映射结束处之后的内存自然就是该清零的区域，内核映射时无需为它读任何磁盘字节。所以你在 `otool -l` 里几乎总能看到 `__bss` 是 `__DATA` 段排在末尾的节之一。

## 核心原理与字段详解

### 1. 节类型 `S_ZEROFILL`（`flags & SECTION_TYPE == 0x1`）

`__bss` 的身份由 `section_64.flags` 的**低 8 位类型**决定（类型与属性如何拆分，见 [[18.Mach-O section]]）：

```c
#define SECTION_TYPE   0x000000ff   /* flags 低 8 位 = 节类型（互斥）*/
#define S_ZEROFILL     0x1          /* zero fill on demand section */
```

`S_ZEROFILL` 的语义，用 Apple `loader.h` 的原话是 **"zero fill on demand section"（按需零填充节）**：当这段内存**第一次被读或写**时，其中每一页都会被自动填成全零字节。换言之，加载器对这个节的承诺是——"你不用从文件里搬任何字节，我保证这块内存被访问时已经是零"。

因此 `__bss` 节头里：

- `addr`、`size` 照常填写（决定它在内存里**从哪开始、占多大**）；
- `flags` 低 8 位 = `0x1`（`S_ZEROFILL`）；高 24 位属性通常为 0（它既非纯指令、也无重定位）；
- `reloff` / `nreloc` = 0（零数据无需重定位）；
- `reserved1`/`reserved2`/`reserved3` = 0（它不是符号桩/符号指针节，不复用 reserved，见 [[18.Mach-O section]]）；
- `offset`：**关键** —— 见下文第 4 节，它不指向本节专属的初始化字节。

> [!note] 零填充家族：`S_ZEROFILL` / `S_GB_ZEROFILL` / `S_THREAD_LOCAL_ZEROFILL`
> `S_ZEROFILL` 不是孤例，`loader.h` 里共有三种"不占文件"的零填充类型，`__bss` 用的是第一种：
> - **`S_ZEROFILL`（`0x1`）**：常规零填充，`__bss` 即此类。
> - **`S_GB_ZEROFILL`（`0xc`）**："GB 级"零填充，专为超大（可超过 4GB）的零区设计。它**必须独占一个只含零填充节的段**，且这类段排在所有其他段之后。原因是 32 位地址空间下零填充节的尺寸可超过 4GB，若与普通节混在一段，可能使普通节落到 31 位偏移够不着的地方，导致静态链接器无法生成输出文件。
> - **`S_THREAD_LOCAL_ZEROFILL`（`0x12`）**：线程局部存储（TLS）的零填充模板，对应 `__thread_bss` 节——可理解为"每个线程私有的 `__bss`"，新线程创建时按模板零初始化。
>
> 三者机制相同（不占文件、运行时清零），区别只在"用于多大的区""是否线程私有"。判断"一个节是否占文件"的统一标准是**看类型是不是某种 zerofill，而不是看 `offset` 是否为 0**。

### 2. 为什么"全是零"就可以不存进文件

这是 `__bss` 全部价值的根基，本质是一个**信息论层面的观察**：一段内容**完全可预测**的数据（这里是"全 0"），无需逐字节存储，只需记录"它有多长"即可在需要时重建。

- **存 `__data` 的代价**：`int table[256] = {1,2,3,...};` 这 1KB 是**任意值**，不存就丢了，只能逐字节写进文件。
- **存 `__bss` 的代价**：`int table[256];`（未初始化）这 1KB **保证全 0**，"全 0" 这个事实用一个 `size = 1024` 就完整表达了，不必把 1024 个零字节也搬进文件。

于是链接器对 `__bss` 的处理是：**只在节头记 `size`，节数据本身一个字节都不进文件**。操作系统的实现更进一步——用 **zero-fill-on-demand（按需零填充）** 技术：加载时甚至不立刻分配/清零物理内存，而是先映射成"零页"（常映射到同一个只读零页，写时复制），等程序真正写入某页时才分配真实物理页并清零。这样"声明一个 100MB 的 `static` 大数组但只用了前几 KB"既不占磁盘、也不立刻吃满物理内存。

> [!note] 对象文件 vs 最终产物：尺寸都不存，但分配时机不同
> 无论在未链接的 `.o`（`MH_OBJECT`）还是最终可执行/dylib 里，`__bss` 都**只记长度、不存数据**。区别在"谁、何时给它分配并清零"：`.o` 阶段链接器尚未确定最终布局，只携带"需要这么大一块零区"的信息；链接成最终产物后，由 `__DATA` 段的 `vmsize`（大于 `filesize` 的那部分）承载这块零区，最终由内核/`dyld` 在加载镜像时落实零填充。

### 3. 为什么 `vmsize > filesize`：本质成因

[[14.Mach-O __DATA]] 段头（`segment_command_64`）里有两个尺寸字段（详见 [[18.Mach-O section]] 与段命令篇）：

- **`filesize`**：本段在**文件**里占多少字节（磁盘侧）。
- **`vmsize`**：本段加载进**内存**后占多少字节（内存侧）。

`__bss` 的"内存要占、文件不占"直接造成两者不等：它的 `size` **计入** `vmsize`，但**不计入** `filesize`。于是：

```text
__DATA.vmsize  -  __DATA.filesize  ≈  __bss.size  (+ __common.size 等其他零填充节)
```

Apple 官方文档的原话印证了这一点：**"静态链接器常把未初始化数据分配在 `__DATA` 段的末尾；此时 `vmsize` 大于 `filesize`，加载器保证这部分内存被零初始化。"** 这正是 `__bss` 排在段尾（见上文规范要求）+ 不占文件两条性质合起来的结果。

> [!warning] 反过来 `vmsize < filesize` 是非法的（dyld 会拒绝加载）
> `vmsize > filesize` 对 `__DATA` 合法（多出来的就是 `__bss` 等零区）；但**反过来 `vmsize < filesize` 绝不允许**——`dyld` 校验时若发现普通数据段 `vmSize < fileSize`，会直接抛 "malformed mach-o image: segment has vmsize < filesize"。此外，**带可执行权限（`VM_PROT_EXECUTE`）的段不允许 `vmsize != filesize`**，所以"`__bss` 这种 `vmsize>filesize` 的把戏"只能用在可写不可执行的 `__DATA` 段上，`__TEXT`（`r-x`）里不会有零填充节。`__PAGEZERO`（`vmsize=0x1000`、`filesize=0`）是另一个 `vmsize>filesize` 的典型，但它整段都是"无数据占位"，与 `__bss` 的"段尾零区"成因相似而场景不同。

### 4. `offset` 字段：填了值，但不指向真实数据

这是 `__bss` 最容易踩坑的细节。`section_64` 结构有 `offset`（节数据的文件偏移）字段，`__bss` 节头里这个字段**通常填 0，但有时也可能是个非 0 值**——无论填什么，那里都**没有真正属于 `__bss` 的初始化字节**。

原因很直接：`__bss` 根本不占文件，自然没有"本节专属的文件数据"可指。`offset` 在这里要么是 0，要么是某个"恰好等于段尾文件结束位置"的形式上的值，解析器**绝不能**拿它去文件里读 `size` 个字节当作 `__bss` 的初值——读到的会是文件尾部之外的内容或下一段的字节。

> [!warning] 判断"是否占文件"看类型，不看 `offset`
> 解析 Mach-O 时，**"这个节要不要从磁盘读数据"取决于它的类型是不是某种 zerofill（`S_ZEROFILL`/`S_GB_ZEROFILL`/`S_THREAD_LOCAL_ZEROFILL`），而不是看 `offset` 是否为 0**。把零填充节当普通节去 `offset` 处读 `size` 字节，是新手解析器的经典 bug。正确做法：先取 `flags & SECTION_TYPE`，命中零填充类型就只用 `addr`/`size`、跳过文件读取，内存内容视作全 0。

### 5. 谁会被分到 `__bss`：未初始化全局/静态变量的归属

判断一个变量是否进 `__bss`，看它"有没有非零初值"和"作用域/链接性"：

| 源码声明 | 归属节 | 说明 |
|---|---|---|
| `static int n;`（文件作用域，无初值） | `__bss` | 静态存储期 + 零初值 → 零填充 |
| `static int n = 0;`（显式零初值） | `__bss` | 显式 0 等同未初始化，仍是零填充 |
| `static char buf[1<<20];` | `__bss` | 1MB 大数组，**不占文件**，这正是 `__bss` 最划算的场景 |
| 函数内 `static int counter;` | `__bss` | 局部静态变量也是静态存储期、零初值 |
| `int n = 42;`（全局，有非零初值） | `__data`（见 [[27.Mach-O __data节]]） | 有非零初值 → 必须占文件 |
| `static int n = 42;`（有非零初值） | `__data` | 同上，有值就进 `__data` |
| `int n;`（全局、无 `static`，未初始化） | 历史上 `__common`（见 [[29.Mach-O __common节]]） | "暂定定义（tentative definition）"，跨编译单元由链接器合并；现代编译器多数也并入 `__bss` 行为 |

> [!note] "零初值" 与 "未初始化" 在 `__bss` 眼里是一回事
> C 标准下，静态存储期变量"未显式初始化"与"显式初始化为 0"**最终内存表现完全相同**（都是全 0）。所以 `static int a;` 和 `static int a = 0;` 都进 `__bss`，编译器不会因为你多写了 `= 0` 就把它挪去占文件的 `__data`。但**显式非零初值**（哪怕只有一个字节非零，如 `int arr[1000] = {1};`）会让整个对象进 `__data`、占满文件——因为"其余 999 个 0"虽多，但"第一个是 1"这个事实使它不再是"纯零区"。

### 6. `__bss` 与 `__data` / `__common` 的精确边界

把三者放在一起对比，边界最清晰：

| 维度 | `__bss`（本篇） | `__data`（[[27.Mach-O __data节]]） | `__common`（[[29.Mach-O __common节]]） |
|---|---|---|---|
| 节类型 | `S_ZEROFILL`（`0x1`） | `S_REGULAR`（`0x0`） | `S_ZEROFILL`（`0x1`，历史上也用零填充语义） |
| 初值 | 零/未初始化 | 有非零初值 | 未初始化（暂定定义） |
| 是否占文件 | **否**（不计入 `filesize`） | **是**（初值字节进文件） | 否 |
| 计入 `vmsize` | 是 | 是 | 是 |
| `offset` 是否指真实数据 | **否** | **是** | 否 |
| 典型来源 | `static`/全局零初值变量 | `static`/全局非零初值变量 | 老式 C "暂定定义"全局符号 |
| 对 `vmsize>filesize` 的贡献 | **主要成因** | 无（它占文件） | 次要成因 |

> [!note] 架构差异：语义无关、对齐与零页大小相关
> 零填充语义本身**与 CPU 架构无关**——arm64、x86_64、i386 上 `S_ZEROFILL` 的含义完全一致。受架构影响的是两点：① `__bss` 节的对齐（`align`，见 [[18.Mach-O section]]）随其中最大变量的对齐要求变化；② 它所在零页的页大小随平台不同（**arm64 为 16KB、x86_64 为 4KB**），这会影响 `__DATA` 段整体的页对齐与 `vmsize` 的取整。

## 实操：用工具查看

> [!warning] 示例输出为示意
> 本机为 Windows 环境，无法运行 `otool`；以下所有输出均基于 Mach-O 结构知识**构造**，仅用于示意字段格式与判读方法，**实际数值以你在 macOS 上对真实二进制运行的结果为准**。

### 示例 1：`otool -l` 看 `__bss` 节头（重点看 `size` 与 `offset`）

`otool -l` 把每个段命令后的节头逐个打印成 `Section` 块；用 `grep` 过滤到 `__bss`：

```bash
otool -l /bin/ls | grep -A 8 "sectname __bss"   # 看 __bss 节头的关键字段
otool -lv /bin/ls                                 # -v 把 flags 显示成符号名（S_ZEROFILL）
```

```text
Section
  sectname __bss
   segname __DATA
      addr 0x000000010000a000      ; 节虚拟地址（落在 __DATA 段范围内）
      size 0x0000000000100000      ; 1MB —— 内存里要占这么大
    offset 0                       ; ★ 不指向文件数据（即便非 0 也不可当初值读）
     align 2^3 (8)                 ; 存储值 align=3，实际 8 字节对齐（随最大变量而定）
    reloff 0                       ; 零数据，无重定位
    nreloc 0
     flags 0x00000001              ; ★ S_ZEROFILL（flags & 0xff == 0x1）
 reserved1 0                       ; 非符号桩/指针节，reserved 不复用
 reserved2 0
 reserved3 0
```

> 说明：判读 `__bss` 只需盯两处——`flags 0x00000001`（`& 0xff = 0x1` 即 `S_ZEROFILL`，确认这是零填充节）和 `size 0x100000`（1MB，内存占用）。`offset 0` 与"文件里并不存这 1MB"互相印证；`reserved*` 全 0 因为 `__bss` 不像 `__stubs`/`__la_symbol_ptr` 那样复用 reserved 字段（对比见 [[18.Mach-O section]]）。

### 示例 2：用 `size -lm` 看 `__bss` 如何撑大 `vmsize` 却不进 `filesize`

`size -l -m` 按"段套节"列尺寸，最能直观看出 `__bss` 计内存、不计文件：

```bash
size -l -m /bin/ls    # -m: 按段分组列节；-l: 含完整明细
```

```text
Segment __DATA: 1118208 (vmaddr 0x10000a000 fileoff 65536)
    Section __data: 64 (addr 0x10000a000 offset 65536)        ; 占文件
    Section __bss: 1048576 (addr 0x10000a040 offset 0)        ; ★ S_ZEROFILL，不占文件
    total 1048640
```

> 说明：`__DATA` 段 `vmsize` 约 1118208 字节，而真正写进文件的 `__data` 只有 64 字节——巨大的差额几乎全来自 `__bss` 的 1048576（1MB）。这就是 `vmsize > filesize` 的本质：那 1MB 只在内存里存在，磁盘上是零成本的（仅靠节头里一个 `size` 记着）。

### 示例 3：对照看 `filesize` 与 `vmsize`（段头层面）

直接看 `__DATA` 段命令的两个尺寸字段，验证差额：

```bash
otool -l /bin/ls | grep -A 10 "segname __DATA"
```

```text
Load command N
      cmd LC_SEGMENT_64
  cmdsize 232
  segname __DATA
   vmaddr 0x000000010000a000
   vmsize 0x0000000000111000      ; 内存 ≈ 1.06MB（含 __bss 的 1MB 零区）
  fileoff 65536
 filesize 0x0000000000001000      ; 文件仅 4KB（不含 __bss）
   maxprot rw-
  initprot rw-
   nsects 2
    flags 0x0
```

> 说明：`vmsize 0x111000`（≈1.06MB）远大于 `filesize 0x1000`（4KB），差额对应 `__bss`（+ 可能的 `__common`）的零区。注意 `initprot rw-`——`__DATA` 可写不可执行，正因为不可执行，`vmsize != filesize` 才被 `dyld` 允许（见上文 warning）。

## FAQ

> [!question] `__bss` 里的变量是怎么变成 0 的？是编译器写进文件的吗？
> 不是编译器把零字节写进文件，而是**内核在加载/首次访问时清零**。`__bss` 的节类型 `S_ZEROFILL` 是"按需零填充"（zero-fill-on-demand）：文件里根本不存这些字节，加载时这块虚拟内存先被映射成零页，程序首次写入某页时内核才分配真实物理页并保证其内容为 0。所以"`static int n;` 的初值是 0"这个保证由**操作系统/加载器**兑现，而非靠在磁盘上预存一堆零。

> [!question] `__bss` 节头里的 `offset` 不是 0 时，我能去那个位置读它的数据吗？
> **不能**。`__bss` 不占文件，没有"本节专属的初始化字节"。`offset` 即便填了非 0 值（常是个形式上等于段尾文件位置的值），那里的字节也不属于 `__bss`——拿它去读 `size` 个字节会读到无关内容。判断"一个节要不要从磁盘读"的正确依据是**类型是不是某种 zerofill（`flags & SECTION_TYPE` 命中 `S_ZEROFILL`/`S_GB_ZEROFILL`/`S_THREAD_LOCAL_ZEROFILL`）**，命中就只用 `addr`/`size`、内存视作全 0，绝不读文件。

> [!question] 为什么含 `__bss` 的 `__DATA` 段会出现 `vmsize > filesize`？反过来行不行？
> 因为 `__bss` 的 `size` **计入内存大小（`vmsize`）但不计入文件大小（`filesize`）**——内存里要给它留位置（运行时清零），磁盘上却一个字节不存，于是 `vmsize` 比 `filesize` 大出约 `__bss`（+`__common`）的尺寸。**反过来 `vmsize < filesize` 不行**：`dyld` 会判定镜像非法并抛 "segment has vmsize < filesize"；而且可执行段（`VM_PROT_EXECUTE`）要求 `vmsize == filesize`，所以这种"内存比文件大"的优化只适用于可写不可执行的 `__DATA`，`__TEXT` 里不会有 `__bss`。

> [!question] `static int a = 0;` 和 `static int a;` 有区别吗？哪个进 `__bss`？
> **没有区别，两个都进 `__bss`**。C 标准下静态存储期变量"未初始化"与"显式初始化为 0"最终内存表现相同（全 0），编译器把它们一视同仁地放进零填充的 `__bss`，不会因为你多写 `= 0` 就挪去占文件的 `__data`。但只要初值里**有任何一个非零字节**（如 `int arr[1000] = {1};`），整个对象就会进 `__data`、把全部字节（含那 999 个 0）写进文件——因为它不再是"纯零区"，无法用一个 `size` 重建。

> [!question] "bss" 这三个字母到底是什么意思？和"清零"有关系吗？
> "bss" 与"清零"语义**没有直接关系**，它是个历史术语。BSS = **Block Started by Symbol（由符号开始的块）**，源自 1950 年代中期 IBM 704 的汇编器 **UA-SAP**（United Aircraft Symbolic Assembly Program），是其中一条"定义一个符号并预留一块未初始化空间"的伪指令；后来被 FAP、MAP 等 IBM 汇编器沿用，再传入 Unix，一直保留至今。因为原意晦涩，流行一个戏说式的助记 **"Better Save Space（最好省点空间）"**——恰好点出了 `__bss` 不存零字节、节省文件体积的好处。所以记法上：原名描述**机制**（符号标记的预留块），戏说描述**收益**（省空间）。

## 与相邻章节的关系

- [[14.Mach-O __DATA]]：`__bss` 的宿主段，提供 `rw-` 权限；其 `vmsize > filesize` 主要由 `__bss`（+ `__common`）的零区造成。
- [[27.Mach-O __data节]]：带非零初值的可写数据，**占文件**，与 `__bss`（不占文件）互为补集——"有值进 `__data`、零值进 `__bss`"。
- [[29.Mach-O __common节]]：另一类未初始化数据（老式 C 的"暂定定义"全局符号），同样零填充、不占文件，是 `vmsize>filesize` 的次要成因。
- [[18.Mach-O section]]：节通用模型——`S_ZEROFILL`（`0x1`）的类型定义、`flags` 低 8 位/高 24 位拆分、`offset` 对零填充节的特殊含义、零填充家族（含 `S_GB_ZEROFILL`/`S_THREAD_LOCAL_ZEROFILL`）都在那篇详述，本篇是其 `S_ZEROFILL` 的具体落地。

## 小结

- `__bss` 存"未初始化 / 零初值"的可写全局/静态变量，位于 `__DATA` 段（`rw-`），节类型 `S_ZEROFILL`（`flags & SECTION_TYPE == 0x1`）。
- 核心特性"只记尺寸、不占文件"：`size` 计入 `vmsize`、不计入 `filesize`；`offset` 不指向本节专属数据；内容在运行时由内核以 zero-fill-on-demand 方式清零。
- 它是 [[14.Mach-O __DATA]] 段 `vmsize > filesize` 的**首要成因**——内存占、磁盘不占，差额≈`__bss`(+`__common`) 的 `size`；反向 `vmsize < filesize` 非法、可执行段要求 `vmsize==filesize`。
- 归属规则：零初值/未初始化 → `__bss`；有非零初值 → `__data`（[[27.Mach-O __data节]]）；老式"暂定定义" → `__common`（[[29.Mach-O __common节]]）。`static int a;` 与 `static int a = 0;` 都进 `__bss`。
- 解析要点：判断"是否占文件"看**类型是不是 zerofill**，不看 `offset` 是否为 0。
- 命名是历史术语 *Block Started by Symbol*（IBM 704 汇编器），与"清零"无关；流行助记 "Better Save Space"。
