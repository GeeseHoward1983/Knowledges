# 详解Mach-O(三十九)Mach-O __objc_catlist节

> [!abstract] TL;DR
> **`__objc_catlist`（全名 `__DATA,__objc_catlist`，新版工具链多在 `__DATA_CONST` 段）是本镜像所有"分类（category）"的清单**：一张 64 位指针数组，每个 8 字节指针指向一个 `category_t` 结构。`category_t` 完整描述了一个分类——**给哪个类（`cls`）、添加了哪些实例方法（`instanceMethods`）、类方法（`classMethods`）、要遵循哪些协议（`protocols`）、声明了哪些实例属性（`instanceProperties`）以及类属性（`_classProperties`）**。
> 镜像被 `dyld` 加载后，runtime 遍历本表，对每个分类调用 `attachCategories`，把分类的方法 / 属性 / 协议**合并（attach）进目标类**：实例方法进类、类方法进元类。合并用的 `attachLists` 一律**把分类内容插到原列表"最前面"**——于是分类里与原类同名的方法会**先被查找命中**，造成"覆盖"的假象，但**原方法并未被删除或替换**，仍在列表里只是排在后面、再也轮不到它被调用。
> 分类若实现 `+load`，在加载早期被调用，但**严格排在其目标类自己的 `+load` 之后**（先所有类的 `+load`，再所有分类的 `+load`）——这是方法交换（method swizzling）的常用落点。
> 一条铁律：**分类不能添加实例变量（ivar）**。`category_t` 结构里**根本没有 ivars 字段**，且对象的 `instance_size` 在编译期就已写死进 `class_ro_t`，运行时再塞 ivar 会破坏所有既有 ivar 的偏移。要"伪装"实例变量只能用关联对象（`objc_setAssociatedObject`）。本篇把这张表、`category_t` 每个字段、attach 合并与"前插覆盖"机制、`+load` 时序、无 ivar 的根因、多分类顺序的不确定性，以及逆向中的分类 hook 一次讲透。

## 概述与定位

Objective-C 的**分类（Category）** 是"运行时给一个现成的类追加方法"的语言机制。你在源码里写：

```objc
@interface NSString (MyExt)
- (NSString *)mx_trimmed;          // 给系统类 NSString 加方法，无需拿到它的源码
@end
@implementation NSString (MyExt)
- (NSString *)mx_trimmed { /* ... */ }
@end
```

编译器并不会去改 `NSString` 本身（你也没有它的源码），而是把这段"补丁"编译成一个独立的元数据结构 `category_t`，并把指向它的指针登记进本镜像的 **`__objc_catlist`** 节。等镜像被加载、runtime 跑起来，再由 runtime 把这份补丁**动态地缝合（attach）进真正的 `NSString` 类对象**。`__objc_catlist` 就是这批"待缝合补丁"的目录。

可以把 ObjC 的几张元数据"列表节"放在一起对比，理解 `__objc_catlist` 的位置：

- [[36.Mach-O __objc_classlist节]]：本镜像**定义的所有类**的清单（每项指向 `class_t`）。分类要扩展的"目标类"通常就来自类列表（本镜像的类，或其他镜像/系统框架的类）。
- [[37.Mach-O __objc_nlclslist节]]：**Non-Lazy Class** 列表，即实现了 `+load` 的类，需要在加载早期就 realize 并调用 `+load`。分类的 `+load` 早期调用机制与它同源（见下文时序）。
- [[38.Mach-O __objc_protolist节]]：本镜像定义的**协议**清单。分类可以声明"让目标类遵循某协议"，对应 `category_t.protocols`。
- **`__objc_catlist`（本篇）**：本镜像定义的**分类**清单（每项指向 `category_t`）。它和类列表是并列的两张"列表类"节——类列表说"我定义了哪些类"，分类列表说"我给哪些类打了哪些补丁"。

> [!note] 节名总要带段名，且新旧工具链段归属不同
> 和所有节一样，它写作 `段名,节名` 二元组。历史上分类列表在可写的 **`__DATA,__objc_catlist`**；启用只读元数据优化后，现代工具链常把它放进 **`__DATA_CONST,__objc_catlist`**（指针在加载期由 fixups 绑定后即变只读，缩小可写攻击面）。`otool -s` / `otool -ov` 两个段名都可能要试。关于"节如何寄生在段内、`flags`/对齐等通用字段"的完整说明，见 [[18.Mach-O section]]——本篇只聚焦它装的 ObjC 分类内容。

## 核心原理与字段详解

### 1. `__objc_catlist` 的内容：一串 `category_t *`

本节没有自己的头部结构，就是一段紧凑的指针数组：

```c
// 概念上等价于：
struct category_t * __objc_catlist[N];   // N = size / sizeof(void*)
```

- **元素**：每个元素是一个指向 `category_t` 的指针，64 位下 8 字节，32 位下 4 字节。
- **条目数**：节头不显式存个数，由 `节 size ÷ 指针宽度` 推算（与 [[18.Mach-O section]] 里"符号指针节用 `size/8` 算条目数"同理）。
- **指针的值**：编译/链接产物里它是镜像内的"待 rebase/bind"地址；加载期由 `dyld` 的 rebase 或链式 fixups 修正为运行时真实地址后，runtime 才能顺着它读到 `category_t`。
- **runtime 怎么拿到它**：runtime 内部通过 `_getObjc2CategoryList(header_info *)` 从每个已加载镜像里取出这张表来遍历。

### 2. `category_t` 完整字段（来自 objc4 `objc-runtime-new.h`）

这是本篇的核心。Apple 开源的 objc4 里，`category_t` 定义如下（逐字段中文注释）：

```c
struct category_t {
    const char *name;                         // 分类名，如 "MyExt"。仅作记录/调试用，
                                              //   runtime 不靠它定位目标类（靠下面的 cls）
    classref_t cls;                           // 目标类引用：编译期是占位/未绑定，
                                              //   加载期由 runtime 用 remapClass 映射成真正的类对象
    struct method_list_t *instanceMethods;    // 实例方法列表 → attach 进【类】的方法列表
    struct method_list_t *classMethods;       // 类方法列表   → attach 进【元类】的方法列表
    struct protocol_list_t *protocols;        // 协议列表：让目标类"额外遵循"这些协议
    struct property_list_t *instanceProperties;// 实例属性列表（@property 声明，仅元数据；不产生 ivar）
    // ↓↓↓ 此行以下的字段在磁盘上不一定存在（取决于编译器版本/是否有类属性）↓↓↓
    struct property_list_t *_classProperties;  // 类属性列表（class property）

    // 便捷成员函数：按"是否元类"取对应的方法/属性列表
    method_list_t *methodsForMeta(bool isMeta) {
        if (isMeta) return classMethods;       // 元类 → 类方法
        else        return instanceMethods;    // 普通类 → 实例方法
    }
    property_list_t *propertiesForMeta(bool isMeta, struct header_info *hi);
};
```

逐字段说明：

| 字段 | 类型 | 含义与去向 |
|---|---|---|
| `name` | `const char *` | 分类名字符串（如 `MyExt`）。**只用于记录/调试**，runtime 不用它找目标类。 |
| `cls` | `classref_t` | **目标类引用**。编译期目标类（如 `NSString`）可能不在本编译单元，故此处是占位；加载期 runtime 用 `remapClass(cat->cls)` 解析成真正的类对象。若目标类缺失（如被弱链接掉），该分类被整体忽略。 |
| `instanceMethods` | `method_list_t *` | 分类新增的**实例方法**列表，attach 进**类**（instance）的方法列表。 |
| `classMethods` | `method_list_t *` | 分类新增的**类方法**列表，attach 进**元类**（metaclass）的方法列表。 |
| `protocols` | `protocol_list_t *` | 分类声明目标类**额外遵循的协议**，attach 进类的协议列表。 |
| `instanceProperties` | `property_list_t *` | 分类声明的 **`@property`**（实例属性）。**注意：只是属性元数据，不会生成 ivar，也不会自动合成存取方法的存储**。 |
| `_classProperties` | `property_list_t *` | **类属性**列表。**磁盘上不一定有**——老编译器产物没有这一字段；runtime 用 `hasCategoryClassProperties()` 判断当前镜像的 catlist 项是否带这一字段，避免越界读。 |

> [!note] `cls` 为什么是"运行时才绑定"
> 分类最常见的用途是扩展**别的库/系统框架**的类（`NSString`、`UIView`…），这些类在编译本分类时根本不在场。所以 `category_t.cls` 在二进制里不是一个可直接解引用的类指针，而是一个需要 runtime 在加载期"重映射"的引用（经 `remapClass`）。逆向时看到 catlist 项指向的 `category_t`，要顺着 `cls` 字段（结合 `classrefs`/绑定信息，见 [[40.Mach-O __objc_classrefs节]]）才能确定它到底补在哪个类上；只看 `name`（分类名）是不够的，因为不同类可以有同名分类。

> [!note] 新版 runtime 的指针鉴权包装
> 在启用 PAC（Pointer Authentication，arm64e）的新 runtime 里，`instanceMethods`/`classMethods` 不再是裸指针，而是包装成 `WrappedPtr<method_list_t, PtrauthStrip> instanceMethods` 这样的鉴权指针。语义不变（仍指向方法列表），只是解引用前要 strip 掉签名位。逆向 arm64e 二进制时需注意这层包装。

### 3. 加载期合并：`attachCategories` 把分类并入目标类

镜像被 `dyld` 映射后，runtime 在 `_objc_init` 注册的镜像回调（`load_images` / `map_images`）里处理分类。核心链路（以现代 objc4 为例）：

```text
load_images
  → loadAllCategories / load_categories_nolock          // 收集本镜像所有分类
    → 对每个 category_t：remapClass(cat->cls) 解析目标类  // 目标类缺失则跳过
    → attachToClass(cls, ...)（按 ATTACH_CLASS / METACLASS 分别处理）
      → attachCategories(cls, cats, count, flags)         // 真正的合并
        → prepareMethodLists(...)                         // 排序/修整方法列表
        → rwe->methods.attachLists(mlists, mcount)        // 方法：前插
        → rwe->properties.attachLists(...)                // 属性：前插
        → rwe->protocols.attachLists(...)                 // 协议：前插
```

要点：

- **实例方法 vs 类方法分流**：runtime 对**类**调一次 `attachCategories`（取 `instanceMethods`），对**元类**（`cls->ISA()`）再调一次（取 `classMethods`）——靠 `methodsForMeta(isMeta)` 区分。所以"类方法被加进元类"是天然的。
- **dirty memory（`rwe`）**：方法/属性/协议合并会触发 `extAllocIfNeeded` 分配 `class_rw_ext_t`（即 `rwe`）。**只有"用了分类、或运行时 `class_addMethod`/`addProtocol`/`addProperty`"才会产生这块脏内存**；纯净未被分类污染的类直接读只读的 `ro` 数据，省内存。
- **懒加载分类的捷径**：若分类**没有实现 `+load`**，它可以被"懒加载"——此时 runtime 不一定立刻走 `attachCategories`，而是在类首次 realize 时把 `ro` 里"编译期已并好"的方法直接读出（编译器/链接器在某些情况下已把分类方法预并进类数据）。**实现了 `+load` 的分类则必须在加载早期就 attach**（因为 `+load` 要被尽早调用）。

### 4. "覆盖"的真相：`attachLists` 前插 + 反向遍历

这是分类最容易被误解的一点：**分类里与原类同名的方法，看起来"覆盖"了原方法，实则只是"插队到前面、先被查到"，原方法仍在、只是再也轮不到它。**

机制分两层：

**(a) `attachLists` 把新内容插到列表"最前面"**

把分类的 `method_list_t` 并入类的"方法列表的列表"时，runtime 用 `attachLists`，它的语义是**前插（prepend）**：

- 旧实现（如 objc4-756）：`realloc` 扩容后用 `memmove` 把原有各层整体**后移**腾出前排，再 `memcpy` 把新加的列表拷到**前排**（下标 0 起）。
- 新实现：`malloc` 新数组，把旧数组元素从后往前搬到高位（`newArray->lists[i + addedCount] = array()->lists[i]`），新列表从前往后填到低位（`newArray->lists[i] = addedLists[i]`）。

无论哪种写法，结论一致：**新加的（分类的）方法列表落在下标 0（最前），原类的方法列表被挤到后面**。

**(b) 消息查找"从前往后、首个命中即用"**

`objc_msgSend` → `lookUpImpOrForward` 按层从前往后扫方法列表，**遇到第一个匹配的 selector 就返回其 IMP，不再继续**。既然分类方法在最前面，同名时它先被命中——于是**调用原方法名实际执行的是分类的实现**。原类那份实现并没被删，只是排在后面、永远轮不到。

> [!warning] "覆盖"是假象，原实现仍在，且不可靠
> 三个推论务必记牢：① **原方法没被替换/删除**，它仍在类的方法列表里，只是位置靠后；② 因此你**无法用分类"安全地、可逆地"改写一个方法**——这不是替换，是遮蔽；③ 若**同一个类被多个分类都加了同名方法**，谁在最前面（谁最终生效）由加载顺序决定，而加载顺序又由**链接顺序**决定——见第 6 节，这是**未定义行为**。要可靠地改写方法，应使用 `method_exchangeImplementations` / `class_replaceMethod` 做显式 swizzling，而不是靠分类同名"覆盖"。

### 5. 分类的 `+load`：早期调用，但排在目标类之后

分类也可以实现 `+load`：

```objc
@implementation NSString (MyExt)
+ (void)load { /* 常在这里做 method swizzling */ }
@end
```

`+load` 的调用时机由 runtime 的 `call_load_methods` 统一编排，**严格分两批**：

```text
load_images
  → call_load_methods
      → call_class_loads        // 第一批：先调用所有【类】的 +load
      → call_category_loads     // 第二批：再调用所有【分类】的 +load
    （循环直到没有新的 loadable 项）
```

由此得到几条确定的时序：

- **类的 `+load` 一定先于分类的 `+load`**：保证一个类完整加载（`+load` 跑完）后，才轮到它身上的分类 `+load`。所以分类 `+load` 里访问目标类是安全的。
- **`+load` 在 `main()` 之前、镜像加载早期被调用**，且每个 `+load` 只调一次；它走的是"直接取函数地址调用"而非消息发送，所以**不遵循上面第 4 节的"前插覆盖"**（`+load` 不会被分类覆盖，类和各分类各自的 `+load` 都会被调用）。
- 这套早期调用与 [[37.Mach-O __objc_nlclslist节]]（Non-Lazy Class，实现了 `+load` 的类需提前 realize）同源：**实现了 `+load` 的类/分类属于"非懒加载"**，必须在加载早期就被 runtime 处理。

> [!note] 为什么 swizzling 习惯写在分类的 `+load` 里
> `+load` 时机早、且每类/每分类各调一次、线程安全语境明确，非常适合做"启动时一次性的方法交换"。又因为分类 `+load` 严格在目标类 `+load` 之后，交换时目标类的原始方法已就位。注意：不要在 `+load` 里做重活或依赖其他类已初始化——`+initialize`（首次用到类时才调、可能多次因继承）才是放重初始化的地方。

### 6. 多个分类同名方法：顺序"未定义"

当**同一个类被多个分类各加了一个同名方法**时（例如两个库都给 `NSString` 加了 `-base64EncodedString`），到底哪个生效？

- **官方立场：未定义行为（undefined）。** Apple 文档明确：分类方法若与原类、或与同类其他分类、甚至父类的方法同名，**运行时用哪个实现是未定义的**。
- **实际表现：最后加载的那个赢**，而加载顺序由**链接顺序**决定——链接命令行里**靠后的目标文件**对应的分类，其方法最后被 `attachLists` 前插，落在最前面，于是生效。
- **为什么受链接顺序左右**：ObjC **分类不产生链接符号**（只有类名产生符号，方法因动态性不导出符号）。因此哪个 `.o` 先被链接、catlist 里项的先后、runtime 遍历的先后，最终都跟随**链接命令行/Xcode "Compile Sources" 顺序**——调整文件顺序就可能悄悄改变"谁赢"。
- **这只是观测到的实现细节，不是保证**：不同链接器可能不同（如新链接器 `ld_prime` 在分类元数据 flag 合并上已表现出差异）。**绝不要让代码依赖"哪个分类赢"。**

> [!warning] 静态库里的分类要 `-ObjC` 才会被加载
> 因为分类不产生 undefined 符号，链接器**不知道要从静态库里拉取只含分类的 `.o`**——结果运行时报 "selector not recognized"。解决：给 `Other Linker Flags` 加 **`-ObjC`**（强制加载静态库里所有实现了类或分类的成员），必要时配合 `-all_load` / `-force_load`。代价是可执行文件变大。诊断同名冲突可用环境变量 `OBJC_PRINT_REPLACED_METHODS`（打印被分类替换的方法），但要忽略系统框架自身用分类提供实现而产生的"噪声"日志。

### 7. 铁律：分类不能加实例变量（ivar）

分类能加方法、属性声明、协议，**唯独不能加实例变量**。原因有三层，缺一不可：

1. **`category_t` 结构里压根没有 ivars 字段**。对比类的 `class_ro_t` 有 `ivars`（`ivar_list_t *`），`category_t` 从 `name`、`cls`、两张方法列表、协议列表，到两张属性列表为止，**没有任何承载 ivar 的成员**——从数据结构上就放不下。
2. **对象大小 `instance_size` 编译期写死**。一个类实例占多少字节，由其 `class_ro_t.instanceSize` 在编译期固定。`alloc` 按这个大小申请内存。运行期再追加 ivar，意味着对象要变大，但已经 `alloc` 出来的对象不会变大，布局对不上。
3. **会破坏既有 ivar 偏移**。访问 ivar = `对象指针 + 该 ivar 的偏移`。子类 ivar 紧跟父类 ivar 之后排布。若允许给基类中途插 ivar，基类 ivar 区变大，**所有子类的 ivar 偏移都要重算、全部重新编译**（这正是"脆弱基类问题"）。现代 runtime 的非脆弱 ivar 机制（`realizeClassWithoutSwift` 里 `moveIvars` 调整偏移）解决的是**编译期已声明 ivar** 的偏移重定位，**并不允许运行期凭空新增 ivar**。

连带后果：在分类的 `@implementation` 里 `@synthesize` 一个属性会报错 **"@synthesize not allowed in a category implementation"**——因为合成存取方法需要一个同名 ivar 来存值，而分类造不出 ivar。所以**分类里的 `@property` 只生成方法声明、不会有存储**，存取方法得你自己实现。

> [!note] 替代方案：关联对象（Associated Objects）
> 想给分类的属性提供存储，标准做法是**关联对象**：在自己写的 getter/setter 里用 `objc_setAssociatedObject(self, &key, value, policy)` / `objc_getAssociatedObject(self, &key)`，以 `self` 为宿主、用一个静态地址当 key、选与属性内存语义匹配的 policy（`OBJC_ASSOCIATION_RETAIN_NONATOMIC` 等）。它把值挂在 runtime 维护的关联表里，不改对象布局、不新增真正的 ivar，从而"模拟"出实例变量的效果。

### 8. 逆向视角：从 `__objc_catlist` 找 hook 点

对逆向工程，`__objc_catlist` 是定位"补丁逻辑"的入口：

- **枚举本镜像的所有补丁**：从 catlist 顺着每个 `category_t` 读 `cls`（补给哪个类）、`name`（分类名）、`instanceMethods`/`classMethods`（补了哪些方法）。class-dump、Hopper、IDA、`otool -ov` 都会把它解析成 `@interface 目标类 (分类名)` 的可读形式。
- **识别 hook / swizzling**：恶意或插桩代码常借**分类 `+load` + method swizzling** 在启动早期挂钩系统类方法。看到某分类 `+load` 里有 `method_exchangeImplementations`/`class_getInstanceMethod`，基本就是 hook 现场。
- **同名"覆盖"排查**：怀疑某方法被改写时，既要看类自身实现，也要看 catlist 里有没有分类给同名 selector 加了实现（前插后会先生效）。环境变量 `OBJC_PRINT_REPLACED_METHODS` 在动态调试时能直接打印替换关系。
- **运行期插桩**：在 `attachCategories` / `load_categories_nolock` 上下断点，可观察哪些分类在何时被 attach；结合 `cls` 重映射可还原"补丁→目标类"的对应关系。

## 实操：用工具查看

### 示例 1：`otool -ov` 看分类的语义化解析

`otool -ov`（或 `-o` + `-v`）会解析 ObjC 元数据，把 catlist 里的每个 `category_t` 展开成类名、目标类、方法/属性/协议列表：

```bash
otool -ov /path/to/ObjCBinary | grep -A 20 -i 'category\|catlist'   # 看分类块
otool -ov /path/to/ObjCBinary                                       # 完整 ObjC 元数据（含 categories）
```

### 示例 2：`otool -s __DATA __objc_catlist` 看裸指针

直接 dump 节的原始字节（一串指向 `category_t` 的指针）。注意新工具链可能在 `__DATA_CONST`，两个段名都试一下：

```bash
otool -s __DATA __objc_catlist /path/to/ObjCBinary        # 旧布局
otool -s __DATA_CONST __objc_catlist /path/to/ObjCBinary  # 新布局（只读元数据）
```

> [!warning] 示例输出为示意
> 数值 / 地址为构造，仅示意 `otool -s` 的"地址 + 十六进制指针"逐行格式。

```text
Contents of (__DATA_CONST,__objc_catlist) section

00000001000010b0  308f000001000000                      ; 0x100008f30
```

> 说明：左列是该位置的虚拟地址，右列是小端存储的 8 字节指针值（读时按小端翻转）。这里共 3 个指针 ⇒ 本镜像定义了 3 个分类。要"个数"可用 `节 size / 8`。每个指针解引用后才是 `category_t`（用示例 1 的 `-ov` 才能看到语义）。

### 示例 3：用环境变量观察分类替换 / 加载

动态运行时（macOS/iOS）可借 runtime 环境变量观察分类行为：

```bash
OBJC_PRINT_REPLACED_METHODS=YES ./YourApp   # 打印被分类同名方法"替换"（前插覆盖）的情况
OBJC_PRINT_LOAD_METHODS=YES     ./YourApp   # 打印 +load 调用顺序（可见类先于分类）
```

> [!warning] 示例输出为示意
> 仅示意日志格式；忽略系统框架自身用分类提供实现而产生的噪声行。

```text
LOAD: +[NSString load]                 ; 先：类的 +load
LOAD: +[NSString(MyExt) load]          ; 后：分类的 +load（严格在目标类之后）
REPLACE: -[NSString base64EncodedString] by category MyExt   ; 分类前插，同名方法先被命中
```

## FAQ

> [!question] 分类方法"覆盖"了原方法，原方法是被删了还是被替换了？
> **都不是。** 原方法既没被删、也没被替换，它仍在类的方法列表里——只是 runtime 用 `attachLists` 把分类的方法列表**前插**到了"方法列表的列表"最前面（下标 0），而消息查找 `lookUpImpOrForward` 是"从前往后、首个命中即用"。于是同名 selector 先在分类那层被命中、返回分类的 IMP，原类那层再也轮不到。所以这是**遮蔽（先被查到）**，不是替换。推论：你无法靠分类同名"安全可逆地"改写方法，要改写应显式用 `method_exchangeImplementations` 做 swizzling。

> [!question] 同一个类被多个分类加了同名方法，到底哪个生效？能控制吗？
> 官方定义为**未定义行为**。实际表现是**最后加载的分类赢**，而加载顺序跟随**链接顺序**（Xcode "Compile Sources" / 链接命令行里靠后的 `.o` 对应的分类，最后被前插、落在最前、最终生效）。原因是 ObjC **分类不导出链接符号**，一切顺序都由链接器输入顺序决定。但这只是观测到的实现细节、不同链接器可能不同（如 `ld_prime`），**绝不要依赖它**。要避免冲突，给分类方法名加前缀（如 `mx_`）。

> [!question] 为什么分类能加 `@property` 却不能加实例变量？两者不是一回事吗？
> 不是。`@property` 在分类里**只生成方法声明（getter/setter 的签名）和属性元数据**，登记在 `category_t.instanceProperties` 里；它**不会**、也无法生成用于存值的 ivar。而实例变量需要落到对象的内存布局里，`category_t` 结构根本没有 ivars 字段，且对象 `instance_size` 编译期就写死、运行期新增 ivar 会破坏所有既有 ivar 的偏移（脆弱基类问题）。所以在分类 `@implementation` 里 `@synthesize` 会直接报 "@synthesize not allowed in a category implementation"。要给分类属性提供存储，用关联对象 `objc_setAssociatedObject`/`objc_getAssociatedObject` 自己实现存取。

> [!question] 分类的 `+load` 和目标类的 `+load`，谁先调用？会被覆盖吗？
> **目标类的 `+load` 一定先调用，分类的 `+load` 后调用**——runtime 的 `call_load_methods` 先 `call_class_loads`（所有类）、再 `call_category_loads`（所有分类）。而且 `+load` 走"直接取地址调用"不是消息发送，**不参与第 4 节的前插覆盖**：类自己的 `+load` 和它每个分类的 `+load` 都会各被调用一次，互不覆盖。这也是为什么 method swizzling 习惯写在分类的 `+load` 里——时机早、各调一次、且此时目标类已加载完毕。

> [!question] 我从静态库引入的分类方法，运行时报 "unrecognized selector"，为什么？
> 因为**分类不产生 undefined 符号**，链接器看不到"有人用了这个分类"，于是**不会从静态库里把只含分类的目标文件拉进来**，分类方法根本没被链接进可执行文件。解决办法是给 `Other Linker Flags` 加 **`-ObjC`**（强制加载静态库中所有实现了类或分类的成员），冲突更复杂时可用 `-force_load <lib>` 或 `-all_load`。代价是产物体积变大。这与"分类逻辑本身"无关，纯粹是链接阶段没把分类带进来。

## 小结

- `__objc_catlist`（`__DATA` 或新布局的 `__DATA_CONST`）是本镜像**所有分类的清单**：一串指向 `category_t` 的指针，条目数 = `节 size ÷ 指针宽度`。
- `category_t` 字段：`name`（分类名，仅记录）、`cls`（目标类，加载期 `remapClass` 绑定）、`instanceMethods`（进类）、`classMethods`（进元类）、`protocols`、`instanceProperties`、`_classProperties`（磁盘上不一定有）；新 runtime 方法列表字段用 PAC 包装。
- 加载期 runtime 经 `attachCategories` 把分类方法/属性/协议并入目标类（实例方法进类、类方法进元类）；合并用 `attachLists` **一律前插**。
- "同名覆盖"是假象：分类方法被前插到方法列表最前、消息查找"首个命中即用"，故先被调用；**原方法仍在、只是排后面永不被命中**，并非删除或替换。
- 分类 `+load` 在加载早期调用，但**严格在目标类 `+load` 之后**（`call_class_loads` 先于 `call_category_loads`），是 swizzling 常用落点；`+load` 不被覆盖。
- 多个分类同名方法的生效顺序是**未定义行为**（实际"最后链接者赢"，受链接顺序左右，不可依赖）；静态库分类需 `-ObjC` 才会被加载。
- 分类**不能加 ivar**：`category_t` 无 ivars 字段、`instance_size` 编译期写死、新增 ivar 会破坏既有偏移；要"伪装"实例变量用关联对象。
