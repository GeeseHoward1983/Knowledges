# 详解Mach-O(十三)Mach-O __TEXT

> [!abstract] TL;DR
> **`__TEXT` 是 Mach-O 镜像里第一个真正承载文件数据的段，权限为只读可执行（`r-x`），存放机器码与所有"启动后不再变"的只读内容**：核心是 `__text`（机器指令），此外有 `__stubs`/`__stub_helper`（动态符号桩与惰性绑定跳板）、`__cstring`（C 字符串字面量）、`__const`（只读常量）、`__unwind_info`/`__eh_frame`/`__gcc_except_tab`（栈展开与异常处理元数据）、`__objc_methname`/`__objc_classname`/`__objc_methtype`（Objective-C 运行时只读字符串池）等节。
> 它的 `fileoff = 0`，**从文件最开头映射**——因为 Mach-O 的 Header 与 Load Commands 本身就被算进 `__TEXT` 段（它是第一个有数据的段，`__PAGEZERO` 没有任何文件字节），第一个代码节 `__text` 排在这些头部之后。
> 因为只读，`__TEXT` 同时获得两大收益：**防篡改**（运行期代码无法被改写，落实 W^X 原则）与**跨进程共享物理页**（同一可执行/库被多个进程或多次运行时，内核只映射一份 `__TEXT` 物理内存供共享，省内存）。与之相对的可写段是 [[14.Mach-O __DATA]]（`rw-`，写时复制，每进程私有）。

## 概述与定位

`__TEXT` 是程序"能跑起来"的核心：CPU 取指执行的就是这里的 `__text` 节，而程序里所有写死的字符串、只读表、跳板代码、异常处理表也都集中在这里。它继承自 [[11.Mach-O Segments]] 的权限模型——`r-x` 意味着**可读、可执行、但不可写**，从根本上杜绝"运行时改写自身代码"这类攻击与 bug。

把它放在系列里看，`__TEXT` 在地址空间中紧接在 [[12.Mach-O __PAGEZERO]] 之后（典型 arm64 上 `__PAGEZERO` 占低 4GB，`__TEXT` 从 `0x100000000` 起），是第一个把字节真正搬进内存的段；它由一条 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64|LC_SEGMENT_64]] 命令描述，`segname == "__TEXT"`、`initprot == 0x5`（`r-x`）。本篇看**段级全貌**——为什么是 `r-x`、为什么 `fileoff=0`、它装了哪些节、只读带来的安全与共享收益；段内各节的逐字段细节，从 [[19.Mach-O __text节]] 起逐一展开。

> [!note] 段（Segment）与节（Section）在 `__TEXT` 上的体现
> `__TEXT` 是**映射与权限的单位**：整段一套 `r-x` 权限、按页对齐、写给内核/dyld 看。它内部装着多个**节**（`__text`/`__cstring`/`__const`…），节是逻辑内容的单位、写给链接器看，且**共享该段的 `r-x` 权限**。这正是"只读 C 字符串 `__cstring`"要放进 `r-x` 的 `__TEXT`、而"可写全局变量"要放进 `rw-` 的 `__DATA` 的根本原因——权限以段为粒度、整段生效，内容按读写属性分段归位。段头与节头的结构见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 与 [[18.Mach-O section]]。

## 核心原理与字段详解

### 1. 只读可执行（r-x）：权限与含义

`__TEXT` 段对应的 `LC_SEGMENT_64` 命令里，`initprot = 0x5`，按 `VM_PROT_*` 位掩码拆解就是 `VM_PROT_READ(0x1) | VM_PROT_EXECUTE(0x4)`，文本记作 `r-x`：

| 位 | 宏 | 值 | 在 `__TEXT` 上的含义 |
|---|---|---|---|
| 读 | `VM_PROT_READ` | `0x1` | CPU 能读取指令字节，程序也能读取段内只读数据（字符串/常量表） |
| 写 | `VM_PROT_WRITE` | `0x2` | **缺失**——任何写入 `__TEXT` 的页都会触发段错误（`EXC_BAD_ACCESS` / `SIGBUS`） |
| 执行 | `VM_PROT_EXECUTE` | `0x4` | CPU 能从段内取指执行（`__text` 是真正被执行的节） |

- **可执行**使 CPU 能取指：`__text` 节里的机器码就是被执行的对象。
- **不可写**是关键的安全属性：它从内存保护层面杜绝了"运行时修改自身代码""把数据当代码覆盖执行"这类攻击与 bug；需要自修改代码 / JIT 的极少数场景，必须**显式向系统申请一块新的可写可执行内存**（`mmap` + `mprotect`，且在 Hardened Runtime 下需 `com.apple.security.cs.allow-jit` 等授权），而**不是**去改 `__TEXT`。

> [!note] `maxprot` 与现代加固
> 历史上 `__TEXT` 的 `maxprot`（运行时可经 `mprotect` 提升到的权限上限）有时给 `0x7`（`rwx`），为 JIT 留口子，也给攻击者留了"把代码页改可写再篡改"的机会。现代 macOS/iOS 在 Hardened Runtime、代码签名强制等约束下，倾向把 `__TEXT` 的 `maxprot` 收紧到与 `initprot` 一致（`0x5`），禁止运行时把代码页改成可写。逆向时若看到 `__TEXT` 的 `maxprot` 与 `initprot` 不一致，要留意它暗示的运行期权限变更能力。`maxprot`/`initprot` 的完整语义见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]。

### 2. 为什么 `fileoff = 0`：Header + Load Commands 都落在 `__TEXT` 内

你用 `otool -l` 看 `__TEXT` 时，会发现它的 `fileoff` 恒为 **0**——它从文件最开头就开始映射。原因是 Mach-O 的布局里：

> **Mach Header（`mach_header_64`）与紧随其后的全部 Load Commands，本身就被算进第一个有数据的段——也就是 `__TEXT`。**

为什么不是算进 `__PAGEZERO`？因为 [[12.Mach-O __PAGEZERO]] 的 `filesize = 0`、不可读写、**没有任何文件字节**，它纯粹是一段保留的虚拟地址空间；从分页角度看，头部信息必须落在"第一个真正承载文件数据、且可读"的段里，于是落在 `__TEXT`。所以 `__TEXT` 段在文件里的字节排布是：

```text
文件偏移 0 ─┬─ mach_header_64（Mach 头，magic/cputype/ncmds/…）
            ├─ Load Commands（LC_SEGMENT_64 × N、LC_SYMTAB、LC_MAIN …）
            ├─ （页对齐填充 / 节间对齐空隙）
            ├─ __text     节（第一个代码节，真正的机器码）
            ├─ __stubs    节
            ├─ __cstring  节
            └─ …其余 __TEXT 节
```

`__TEXT` 的 `filesize` 把"头部 + 全部节"一并算进去；第一个**代码**节 `__text` 的 `offset`（节文件偏移）通常远大于 0，正好排在 Header + Load Commands + 对齐填充之后。这也解释了一个常见现象：**`__TEXT` 的 `vmaddr` 就是整个镜像的加载基址**（典型 arm64 上 `0x100000000`），因为 Header 落在它开头，镜像基址 = `__TEXT` 基址 = Header 所在地址。dyld 计算 ASLR slide、定位 Load Commands，都以这个基址为锚点。

> [!note] `fileoff=0` 不等于 `vmaddr=0`
> 别把"文件偏移 0"与"虚拟地址 0"混为一谈。`__TEXT` 的 `fileoff=0`（文件里从头开始），但 `vmaddr` 是 `0x100000000`（接在 4GB `__PAGEZERO` 之后）——虚拟地址 0 那一段是 `__PAGEZERO` 的地盘，专门留空拦截空指针。文件侧从 0 开始、内存侧从 `0x100000000` 开始，两者各论各的。

### 3. 完整的 `__TEXT` 常见节一览

`__TEXT` 里到底装了哪些节、各自存什么、对应哪一篇分篇，下表汇总（同一段内所有节**共享 `__TEXT` 的 `r-x` 权限**）。注意：并非每个二进制都包含全部节——最小程序的 `__TEXT` 可能只有 `__text` 与 `__unwind_info` 两个节；带 Objective-C 才会出现 `__objc_*` 系列；用了 C++/ObjC 异常才会出现 `__eh_frame`/`__gcc_except_tab`。

| 节名 | 内容 | 典型节类型/属性 | 详篇 |
|---|---|---|---|
| `__text` | **机器指令**，程序所有函数体，CPU 取指执行的对象 | `S_REGULAR` + `S_ATTR_PURE_INSTRUCTIONS`(`0x80000000`) + `S_ATTR_SOME_INSTRUCTIONS`(`0x400`)，flags 常为 `0x80000400` | [[19.Mach-O __text节]] |
| `__stubs` | 调用外部（动态库）函数的**跳板桩**，每个桩是一条间接跳转，跳向 GOT/符号指针里解析出的真实地址 | `S_SYMBOL_STUBS` + `S_ATTR_PURE_INSTRUCTIONS`；`reserved2` 记单个桩字节数 | [[22.Mach-O __stubs节]] |
| `__stub_helper` | **惰性绑定辅助代码**：首次调用某外部符号时，桩先落到这里，由它带上符号索引调进 dyld 完成绑定，回填 `__la_symbol_ptr` 后续直达 | `S_REGULAR` + 指令属性 | [[23.Mach-O __stubs_helper节]] |
| `__cstring` | **C 字符串字面量**（源码里双引号包起来的零结尾字符串），静态链接器会**跨文件去重**相同字符串 | `S_CSTRING_LITERALS` | [[20.Mach-O __cstring节]] |
| `__const` | **只读常量数据**：`const` 修饰且**不含指针**的常量（含指针的会被拆进 `__DATA_CONST.__const`，因为指针要重定位/叠加 slide） | `S_REGULAR` | [[21.Mach-O __const节]] |
| `__unwind_info` | **紧凑栈展开信息**（compact unwind，Mac OS X 10.6 引入），用两级查找表编码每个函数的展开方式，供异常/崩溃时回溯栈帧 | `S_REGULAR` | （展开见异常处理篇） |
| `__eh_frame` | **DWARF CFI 栈展开信息**（call frame information），C++/x86_64 ObjC 抛异常时遍历它找 catch；正逐渐被 `__unwind_info` 取代，新版 Xcode 多已省略 | `S_REGULAR` + `S_ATTR_LIVE_SUPPORT` | — |
| `__gcc_except_tab` | **异常处理表（LSDA，Language-Specific Data Area）**：与 `__eh_frame` 配合，记录每个函数里 `try` 范围、`catch` 类型、`landing pad` 位置 | `S_REGULAR` | — |
| `__objc_methname` | Objective-C **方法名（selector 名）字符串池**，如 `"doSomething:"` | `S_CSTRING_LITERALS` | [[24.Mach-O __objc_methname节]] |
| `__objc_classname` | Objective-C **类名字符串池**，如 `"NSObject"` | `S_CSTRING_LITERALS` | [[25.Mach-O __objc_classname节]] |
| `__objc_methtype` | Objective-C **方法类型编码字符串池**（type encoding），如 `"v16@0:8"` | `S_CSTRING_LITERALS` | [[26.Mach-O __objc_methtype节]] |

> [!note] 为什么 ObjC 的 selector/类名字符串放 `__TEXT` 而引用表放 `__DATA`
> `__objc_methname`/`__objc_classname`/`__objc_methtype` 存的是**字符串内容本身**——只读、可去重、与进程无关，天然属于 `r-x` 的 `__TEXT`，和 `__cstring` 同类（都打 `S_CSTRING_LITERALS`）。而**指向**这些字符串的引用表（`__objc_selrefs`/`__objc_classrefs` 等，见 [[35.Mach-O __objc_selrefs节]]、[[40.Mach-O __objc_classrefs节]]）存的是**指针**，运行时要被 dyld rebase/bind（叠加 ASLR slide、绑定到运行期 selector 唯一化结果），所以放进可写的 `__DATA`/`__DATA_CONST`。"内容只读放 `__TEXT`、指针可写放 `__DATA`"是 Mach-O 反复出现的分工原则。

> [!note] `__text` 的节属性位 `S_ATTR_*`
> `__text` 的 `flags` 字段常见值 `0x80000400`，是 `S_REGULAR(0x0) | S_ATTR_PURE_INSTRUCTIONS(0x80000000) | S_ATTR_SOME_INSTRUCTIONS(0x00000400)` 的按位或：`PURE_INSTRUCTIONS` 表示"本节只含可执行指令"，`SOME_INSTRUCTIONS` 表示"本节含有指令"。链接器/反汇编器据此识别"这是纯代码节，按指令反汇编而非按数据 dump"。节类型（低 8 位 `S_*`）与属性位（高位 `S_ATTR_*`）的完整定义见 [[18.Mach-O section]]。

### 4. 只读不可写的安全意义：防代码篡改与 W^X

`__TEXT` 不可写不是"碰巧"，而是一道刻意的内存级防线，意义有三层：

1. **代码完整性（防篡改）**。代码页只读，意味着进程在运行期**无法改写自己的机器码**。即便攻击者拿到了某个内存写原语，也写不动 `__TEXT`——想改控制流，只能转而攻击可写区的函数指针（这正是 `__DATA_CONST` 把 GOT 等指针"启动后只读化"要堵的方向，见 [[15.Mach-O __DATA_CONST]]）。
2. **W^X（Write XOR Execute，写与执行互斥）**。现代操作系统的硬性原则是：任一内存页"可写"和"可执行"不应同时成立。`__TEXT` 是 `r-x`（可执行不可写），`__DATA` 是 `rw-`（可写不可执行），两者互补正好满足 W^X——没有任何一个常规段是 `rwx`。这从架构上消灭了"先把 shellcode 写进某页、再跳过去执行"的经典利用链。
3. **配合代码签名**。`__TEXT` 只读使其内容可被代码签名稳定地度量与校验（页哈希写在 `__LINKEDIT` 的签名 blob 里，见 [[16.Mach-O __LINKEDIT]]）。运行期内核按页校验代码哈希，只读保证了"签名时的字节 == 执行时的字节"。

> [!warning] FairPlay 加密是 `__TEXT` 上的特例
> App Store 分发的应用，会被 Apple 用 **FairPlay DRM** 加密——加密的正是 `__TEXT` 段（从 `__text` 节起、到倒数第二个节止的一段代码），由 `LC_ENCRYPTION_INFO_64` 描述（`cryptoff`/`cryptsize`/`cryptid`，FairPlay 下 `cryptsize` 是 4096 的整数倍、`cryptid=1`），并在段 `flags` 上打 `SG_PROTECTED_VERSION_1(0x8)`。运行时由内核按页解密到内存（解密过程需把 `__TEXT` 临时放宽写权限）。所以"砸壳"（dump decrypted）的本质，就是趁 App 运行、`__TEXT` 在内存里已解密时把它 dump 出来。`cryptid=0` 表示未加密（如本地编译产物、越狱砸壳后的包）。`SG_PROTECTED_VERSION_1` 标志的位置与其它 `SG_*` 标志一并见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]。

### 5. 跨进程共享物理页：只读如何省内存

`__TEXT` 只读，还带来一个纯收益的副作用——**多个进程可以共享同一份 `__TEXT` 物理内存**：

- 因为 `__TEXT` 的内容只读、与具体进程状态无关，所以当**同一个可执行文件被运行多次**（开了 N 个同一程序的进程），或**同一个动态库/框架被多个进程加载**时，内核只需把 `__TEXT` 的物理页**映射一份**，让所有相关进程的虚拟地址都指向这同一份物理页即可。N 个进程共享 1 份代码物理内存，省下 (N-1) 份。
- 这对系统库尤其划算：`libSystem`、`Foundation`、`UIKit` 这类几乎人人加载的框架，它们的 `__TEXT` 在全系统只占一份物理内存。
- 在 `vmmap` 里，共享的 `__TEXT` 区域通常标 `SM=COW`（share mode = copy-on-write）或 `SM=SHM`——但因为永不写入，copy 那一步永远不会发生，实际就是纯共享。
- 还有一个连带好处：内存吃紧时，内核可以**直接丢弃** `__TEXT` 的干净（clean）物理页而**无需写回磁盘**（它和文件内容一致、又只读、没有脏数据），需要时再从原文件重新映射读入即可。可写的 `__DATA` 脏页则必须先写回 swap 才能回收，成本高得多。

> [!note] 与 `__DATA` 的对照
> | 维度 | `__TEXT` | `__DATA` |
> |---|---|---|
> | 初始权限 `initprot` | `r-x`（`0x5`） | `rw-`（`0x3`） |
> | 可写？ | 否（写即崩溃） | 是 |
> | 跨进程共享物理页 | **是**（只读，天然共享一份） | 否（写时复制，每进程私有副本） |
> | 内存回收 | 直接丢弃干净页，重映射即可 | 脏页须先写回 swap |
> | 典型节 | `__text`/`__cstring`/`__const`/`__stubs`/`__unwind_info`/`__objc_methname` | `__data`/`__bss`/`__la_symbol_ptr`/`__objc_*` 引用表 |
> | 安全角色 | 代码完整性 + W^X 的"X"侧 | 运行期可变状态 + W^X 的"W"侧；高危指针进一步挪入 `__DATA_CONST` 只读化 |
>
> 一句话：`__TEXT` 是"出厂即固定、只读、可共享"的部分，`__DATA` 是"运行期会变、可写、私有"的部分。详见 [[14.Mach-O __DATA]]。

> [!note] 架构差异
> `__TEXT` 的内部布局与节集合在 arm64 与 x86_64 间高度一致；主要差异在两点：① `__text` 里的指令编码（ARM64 定长 4 字节指令、`__stubs` 桩是固定形态的间接跳转 vs x86_64 变长指令）；② 页对齐粒度（arm64 为 **16KB**/`0x4000`，x86_64 为 **4KB**/`0x1000`）——这影响 `__TEXT` 的 `vmsize` 向哪个边界取整、以及节间对齐空隙的大小。

## 实操：用工具查看

> [!note] 关于本机环境
> 本机为 Windows，无 `otool`/`size` 等 Apple 工具链；以下命令与输出均为**示意**，用于说明字段含义与查看方法，实际数值请在 macOS 上以你机器的工具输出为准。`otool` 在装了 Xcode Command Line Tools 的 macOS 上可用。

### 示例 1：`otool -l` 看 `__TEXT` 段头与节清单

```bash
otool -l /bin/ls | grep -A 6 "segname __TEXT"   # 看 __TEXT 段头
otool -l /bin/ls                                 # 看全部 Load Commands（含每个节描述）
otool -lv /bin/ls                                # -v 把 maxprot/flags 等显示成符号名
```

> [!warning] 示例输出为示意
> 数值基于结构知识构造，仅示意 `__TEXT` 段头的特征字段，实际以你机器上的 `otool` 为准。

```text
Load command 1
      cmd LC_SEGMENT_64
  cmdsize 712                 ; = 72 + 80*8（段头 + 8 个 section_64）
  segname __TEXT
   vmaddr 0x0000000100000000  ; 接在 4GB __PAGEZERO 之后，也是镜像加载基址
   vmsize 0x0000000000008000  ; 32KB（arm64 按 16KB 页取整）
  fileoff 0                   ; __TEXT 从文件开头映射（Header+LC 都在里面）
 filesize 32768               ; 含头部 + 全部节
  maxprot 0x00000005   (r-x)  ; 现代加固：上限即 r-x，不允许运行时改可写
 initprot 0x00000005   (r-x)
   nsects 8                   ; 其后紧跟 8 个 section_64
    flags 0x0                 ; FairPlay 加密包此处会是 0x8 (SG_PROTECTED_VERSION_1)
Section
  sectname __text             ; 第一个代码节
   segname __TEXT
      addr 0x0000000100003a40 ; 远大于 vmaddr，因为前面排着 Header+LC
      size 0x0000000000003210
    offset 14912              ; 节文件偏移 ≠ 0（排在头部之后）
     align 2^2 (4)
     flags 0x80000400         ; S_REGULAR|S_ATTR_PURE_INSTRUCTIONS|S_ATTR_SOME_INSTRUCTIONS
Section
  sectname __stubs
   segname __TEXT
     flags 0x80000408         ; 含 S_SYMBOL_STUBS(0x8) + 纯指令属性
 reserved2 12                 ; 单个桩 12 字节（arm64）
Section
  sectname __cstring
   segname __TEXT
     flags 0x00000002         ; S_CSTRING_LITERALS
...
```

> 说明：`segname __TEXT` + `initprot (r-x)` 标识这是只读可执行代码段；`fileoff 0` 印证"Header+LC 落在 `__TEXT` 内"；`__text` 的 `addr` 远大于段 `vmaddr`、`offset` 远大于 0，正是被头部"顶"下去的；`cmdsize 712 = 72 + 80*8` 与 `nsects 8` 自洽。

### 示例 2：`otool -tV` 反汇编 `__text` 节

```bash
otool -tV /bin/ls        # -t 反汇编 __text 节；-V 把目标地址/桩符号化
```

> [!warning] 示例输出为示意
> 仅示意反汇编形态（arm64），实际指令以你机器为准。

```text
(__TEXT,__text) section
_main:
0000000100003a40  sub  sp, sp, #0x40
0000000100003a44  stp  x29, x30, [sp, #0x30]
0000000100003a48  ...
0000000100003b10  bl   _printf            ; 调用外部函数 → 实际跳到 __stubs 里的桩
...
(__TEXT,__stubs) section
0000000100005e54  ldr  x16, #0x...        ; 从 __got/__la_symbol_ptr 取真实地址
0000000100005e58  br   x16                ; 间接跳转过去（首调时落到 __stub_helper）
```

> 说明：`bl _printf` 表面调 `printf`，实际目标是 `__stubs` 里的桩；桩做一次间接跳转，首次会经 `__stub_helper` 进 dyld 完成惰性绑定，之后直达。这条链路把 `__text`（你的代码）、`__stubs`/`__stub_helper`（`__TEXT` 内的跳板）与 `__DATA` 里的符号指针表串了起来。

### 示例 3：`size -m` 看段/节尺寸汇总

```bash
size -m /bin/ls          # -m: Mach-O 格式按段分组列出各节尺寸
size -l -m /bin/ls       # 再加 -l 含更完整明细
```

> [!warning] 示例输出为示意

```text
Segment __TEXT: 32768
    Section __text: 12816
    Section __stubs: 312
    Section __stub_helper: 336
    Section __cstring: 2439
    Section __const: 1808
    Section __unwind_info: 1480
    Section __objc_methname: 640
    total 19831
Segment __DATA_CONST: 16384
    Section __got: 240
    total 240
Segment __LINKEDIT: 4096
total 53248
```

> 说明：`size -m` 用"段套节"的层级直观呈现 `__TEXT` 的体积构成——`__text` 通常是大头，其后是字符串/常量/展开信息等只读数据。各节 `total` 之和略小于段 `vmsize`，差额是 Header+Load Commands 与节间对齐填充占用的空间。

## FAQ

> [!question] `__TEXT` 为什么 `fileoff = 0`？是不是说它从虚拟地址 0 开始？
> `fileoff = 0` 指**文件侧**从第 0 字节开始映射，原因是 Mach-O 的 Header 与 Load Commands 被算进了 `__TEXT`（它是第一个有文件数据、又可读的段，`__PAGEZERO` 没数据），第一个代码节 `__text` 排在头部之后。但这**不**等于虚拟地址 0——`__TEXT` 的 `vmaddr` 是 `0x100000000`（接在 4GB `__PAGEZERO` 之后），虚拟地址 0 那一段是 `__PAGEZERO` 留空拦空指针的地盘。文件侧从 0、内存侧从 `0x100000000`，互不冲突。

> [!question] `__TEXT` 既然不可写，那字符串常量、`__const` 这些"数据"为什么也塞进来？
> 因为它们都是**只读、运行期不变**的数据，和代码的读写属性一致，正好共享 `__TEXT` 的 `r-x` 权限、并一起享受"防篡改 + 跨进程共享物理页"的红利。判据是"是否需要写"和"是否含指针"：① 纯只读、不含指针的（C 字符串、不含指针的 `const`、ObjC selector/类名字符串）→ `__TEXT`；② 含指针、需运行期 rebase/bind 的（GOT、含指针的 const）→ `__DATA_CONST`（启动后只读化）；③ 运行期会改写的 → `__DATA`。所以 `__cstring`/`__const`/`__objc_methname` 在 `__TEXT`，而指向它们的指针表在 `__DATA*`。

> [!question] 多个进程"共享" `__TEXT`，会不会一个进程改了影响另一个？
> 不会，而且根本改不了。共享的前提正是 `__TEXT` **只读**——没有任何进程能写它（写即段错误）。内核让 N 个进程的虚拟地址映射到同一份物理页，因为这份内容永不改变，共享绝对安全，省下 (N-1) 份物理内存。`vmmap` 里可能标 `SM=COW`，但"写时复制"的写那一步永远不会触发。可写的 `__DATA` 才需要真正的写时复制——某进程一写就分裂出自己的私有副本。

> [!question] 我能不能在运行时修改 `__TEXT` 实现自修改代码 / 热补丁？
> 直接改 `__TEXT` 会立即段错误（它 `r-x` 不可写，现代加固还把 `maxprot` 锁死在 `0x5`，连 `mprotect` 提权都做不到）。正道是**另外申请内存**：`mmap` 一块匿名内存、写入新代码、再 `mprotect` 设为可执行（W^X 要求"写"和"执行"分两步、不可同时），跳过去执行。在 macOS Hardened Runtime / iOS 上还需相应授权（如 JIT entitlement），且签名与平台策略可能进一步限制。换句话说——`__TEXT` 的只读是刻意的护栏，绕过它要走系统给 JIT 留的、受控的专门通道，而非篡改原段。

> [!question] App Store 下载的 App，`__TEXT` 用 `otool` 反汇编为什么是乱码？
> 因为它被 **FairPlay** 加密了（`__TEXT` 段打了 `SG_PROTECTED_VERSION_1`、由 `LC_ENCRYPTION_INFO_64` 描述、`cryptid=1`）。静态文件里 `__text` 是密文，`otool -tV` 自然反汇编不出有意义的指令。运行时内核才会按页解密到内存。要看明文，需在 App 运行、内存中已解密时 dump（即"砸壳"），或使用本地编译/未加密（`cryptid=0`）的产物。

## 小结

- `__TEXT` 是 Mach-O 第一个承载文件数据的段，权限 `r-x`（只读可执行），由一条 `LC_SEGMENT_64` 描述，`segname=="__TEXT"`、`initprot==0x5`。
- `fileoff == 0`：Mach Header 与 Load Commands 本身被算进 `__TEXT`（它是第一个有数据、可读的段），第一个代码节 `__text` 排在头部之后；`__TEXT` 的 `vmaddr` 即镜像加载基址。
- 段内常见节按"只读"属性聚集：`__text`（代码）、`__stubs`/`__stub_helper`（动态符号桩与惰性绑定）、`__cstring`/`__const`（只读字符串与常量）、`__unwind_info`/`__eh_frame`/`__gcc_except_tab`（栈展开与异常表）、`__objc_methname`/`__objc_classname`/`__objc_methtype`（ObjC 只读字符串池）——全部共享段的 `r-x` 权限。
- 不可写带来双重价值：**安全**（代码完整性 + W^X，运行期无法改写代码）与**省内存**（只读使多进程共享同一份 `__TEXT` 物理页，干净页可直接丢弃重映射）。
- 与 `__DATA` 互补：`__TEXT` 是"出厂固定、只读、可共享"，`__DATA` 是"运行期可变、可写、私有"。
- 特例：App Store 包的 `__TEXT` 被 FairPlay 加密（`SG_PROTECTED_VERSION_1` + `LC_ENCRYPTION_INFO_64`，`cryptid=1`），运行时由内核按页解密。
