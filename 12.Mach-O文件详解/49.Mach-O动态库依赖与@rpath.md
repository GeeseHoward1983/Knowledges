# 详解Mach-O(四十九)Mach-O动态库依赖与@rpath

> [!abstract] TL;DR
> **Mach-O 的动态库依赖机制**由三个核心概念构成：`LC_LOAD_DYLIB`（声明"我需要加载哪个库"）、`install_name`（库自己声明"我叫什么名字"）、以及 **`@rpath`/`@executable_path`/`@loader_path` 三个路径占位符**（在运行时展开为实际目录）。
> dyld 在加载可执行文件时，按 `LC_LOAD_DYLIB` 列出的 `install_name` 逐一搜寻 dylib，其中 `@rpath` 引用会依次展开为二进制的 `LC_RPATH` 列表所描述的目录。**两级命名空间**（two-level namespace）则进一步通过在符号引用中编码所属库名，彻底消除了同名符号的冲突。
> 这套机制既是 App Bundle 打包、Framework 嵌入、以及 xcframework 多平台分发的工程基础，也是 **dylib 劫持（dylib hijacking）攻击的作用点**——理解它，才能同时做到"让自己的程序正确找库"和"防止攻击者替换你的库"。作为本系列的**末篇**，本文把动态链接的全貌收归一处，与 [[07.Mach-O LC_LOAD_DYLIB]]、[[17.Mach-O LC_DYLD_INFO_ONLY]] 等篇形成完整闭环。

## 概述与定位

动态库（dylib）是现代操作系统减少代码冗余、实现热修复的核心机制。macOS/iOS 上，一个可执行文件几乎必然依赖数十个系统 dylib（`libSystem.B.dylib`、`libobjc.A.dylib`、`libswiftCore.dylib` 等），外加若干 App 自带的私有 Framework。

这一切的运作，都建立在 Mach-O 加载命令与 dyld 搜索算法的协同上：

1. 链接期：静态链接器（`ld`）把每个依赖库的 `install_name` 写入 `LC_LOAD_DYLIB`；
2. 加载期：`dyld` 读取 `LC_LOAD_DYLIB`，展开路径占位符，定位并加载 dylib；
3. 绑定期：`dyld` 按 `LC_DYLD_INFO_ONLY` / Chained Fixups 中的绑定信息把符号地址填入 GOT。

**为什么逆向工程师要精通这套机制**：

- 分析 App 的 `otool -L` 输出，可以推断其使用的第三方 SDK 与私有框架。
- 理解 `@rpath` 展开顺序，才能还原 App 从哪个路径加载了哪个库版本。
- dylib 劫持（dylib hijacking）是 macOS 权限提升与 iOS 越狱后持久化的常用手段，其原理就是利用 `@rpath` 搜索顺序的漏洞。

## 核心原理与字段详解

### 1. `LC_LOAD_DYLIB` 与 `install_name`

`LC_LOAD_DYLIB`（cmd = `0xC`）是 Mach-O 中声明动态库依赖的主要命令。每条命令对应一个依赖库：

```c
// <mach-o/loader.h>
struct dylib_command {
    uint32_t cmd;        // LC_LOAD_DYLIB = 0xC
                         // LC_LOAD_WEAK_DYLIB = 0x18（弱依赖，缺失不崩溃）
                         // LC_REEXPORT_DYLIB = 0x1F（重新导出）
                         // LC_LAZY_LOAD_DYLIB = 0x20（懒加载）
                         // LC_LOAD_UPWARD_DYLIB = 0x23（上向依赖，循环依赖场景）
    uint32_t cmdsize;
    struct dylib {
        union lc_str name;          // install_name 字符串的偏移（相对本命令起始）
        uint32_t timestamp;         // 链接时 dylib 的修改时间（用于缓存校验）
        uint32_t current_version;   // 编码为 X.Y.Z → (X<<16)|(Y<<8)|Z
        uint32_t compatibility_version; // 最低兼容版本，低于此版本加载失败
    } dylib;
};
```

**`install_name`** 是 dylib **自报家门**的名字——由 dylib 自身的 `LC_ID_DYLIB`（见 [[08.Mach-O LC_ID_DYLIB]]）写入，链接时静态链接器把它原样复制进依赖方的 `LC_LOAD_DYLIB.name` 字段。`dyld` 加载时按此名字定位 dylib，而不是按文件路径搜索。

**`install_name` 的三种典型形式**：

| 形式 | 示例 | 使用场景 |
|---|---|---|
| 绝对路径 | `/usr/lib/libSystem.B.dylib` | 系统库（路径固定） |
| `@executable_path/...` | `@executable_path/../Frameworks/Foo.dylib` | 相对可执行文件的路径（命令行工具）|
| `@rpath/...` | `@rpath/Foo.framework/Foo` | 需要运行时搜索（App/Framework 推荐）|

**版本号解码示例**：

```bash
# current_version = 0x050A0001 → 5.10.1
# compatibility_version = 0x00010000 → 1.0.0
otool -L /usr/lib/libSystem.B.dylib
# /usr/lib/libSystem.B.dylib:
#   /usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1336.0.0)
```

### 2. 三个路径占位符：`@rpath`、`@executable_path`、`@loader_path`

这三个占位符在 `install_name` 和 `LC_RPATH` 中使用，由 dyld 在加载时展开：

#### `@executable_path`

展开为**主可执行文件所在目录**（`argv[0]` 对应路径的目录部分），在整个进程生命周期中固定不变。

```bash
# 典型用法：命令行工具依赖同目录下的 dylib
install_name_tool -change /old/path/libFoo.dylib \
    @executable_path/libFoo.dylib ./mytool

# 结果：mytool 加载时，dyld 展开为 /path/to/mytool/../libFoo.dylib
```

**局限**：当 dylib 被另一个 dylib 间接加载时，`@executable_path` 仍指向**最初的主程序目录**，不指向中间 dylib 的目录。

#### `@loader_path`

展开为**当前正在解析该 `LC_LOAD_DYLIB` 的那个 Mach-O 文件所在目录**。适合 Framework 内部相对引用其他子库：

```bash
# Framework A 内部依赖 Framework B（两者同在一个目录）
# A 的 LC_LOAD_DYLIB 可写：
@loader_path/../B.framework/B
# 无论 A 被放在哪个目录，都能正确找到同级的 B
```

与 `@executable_path` 的关键区别：`@loader_path` 随**调用方**（谁在读取 `LC_LOAD_DYLIB`）变化，`@executable_path` 永远固定于主程序。

#### `@rpath`：运行时搜索路径

`@rpath` 是最灵活的机制。dyld 遇到 `@rpath/Foo.dylib` 时，会**依次**遍历二进制（及其依赖链上所有已加载 Mach-O）的 `LC_RPATH` 列表，将 `@rpath` 替换为每个 rpath 目录，直到找到存在的文件：

```text
搜索顺序示例（LC_RPATH 有三条）：
① @rpath/Foo.dylib → @executable_path/../Frameworks/Foo.dylib → 文件存在 → 加载
   （若不存在，继续）
② @rpath/Foo.dylib → /usr/local/lib/Foo.dylib → 文件存在 → 加载
   （若不存在，继续）
③ @rpath/Foo.dylib → /opt/homebrew/lib/Foo.dylib → 文件不存在 → 搜索失败
```

若所有 rpath 路径都找不到 dylib，行为取决于加载命令类型：
- `LC_LOAD_DYLIB` → `dyld_fatal_error`，进程启动失败（崩溃）
- `LC_LOAD_WEAK_DYLIB` → 忽略（库缺失不致命，代码需用 `dlsym` 检查符号是否存在）

### 3. `LC_RPATH`：声明搜索路径

`LC_RPATH`（cmd = `0x1C`）用于向二进制中追加一个 rpath 搜索目录：

```c
// <mach-o/loader.h>
struct rpath_command {
    uint32_t cmd;      // LC_RPATH = 0x1C
    uint32_t cmdsize;
    union lc_str path; // rpath 目录字符串（相对于本命令起始的偏移）
                       // 可含 @executable_path / @loader_path
};
```

**添加/删除 rpath 的工具命令**：

```bash
# 查看二进制的所有 rpath
otool -l MyApp | grep -A2 LC_RPATH

# 添加 rpath（链接期）
ld ... -rpath @executable_path/../Frameworks

# 添加 rpath（链接后修改）
install_name_tool -add_rpath @executable_path/../Frameworks MyApp

# 删除 rpath
install_name_tool -delete_rpath /old/path MyApp

# 替换 rpath
install_name_tool -rpath /old/path @executable_path/../Frameworks MyApp
```

**`LC_RPATH` 的来源层级**：`dyld` 在展开 `@rpath` 时，搜索的 rpath 列表来自**整个依赖链上所有已加载 Mach-O 的 `LC_RPATH` 汇总**，而不只是主程序的。这意味着：若某个 dylib 带有 `LC_RPATH`，它的 rpath 也会加入搜索池。这一特性既是弹性的来源，也是劫持的风险点（见安全一节）。

### 4. 两级命名空间（Two-Level Namespace）

**两级命名空间**是 macOS 10.1 引入的关键安全与正确性特性，通过在每个符号引用中同时记录"符号名"和"所属库名"，彻底解决了传统 flat namespace（扁平命名空间）下的同名符号冲突问题。

```c
// LC_DYSYMTAB 的 indirect symbol table 中，每条 undefined 符号引用：
//   符号名（如 _malloc）+ 库序号（指向 LC_LOAD_DYLIB 列表的第 N 条）
// 两级命名空间下，_malloc 来自 libSystem，不会与你自己定义的 _malloc 冲突
```

**查看符号所属库**：

```bash
# otool -IV：查看 indirect symbol table（含库名 + 符号名）
otool -IV MyApp | head -40

# nm --defined-in-dylib：
nm -m MyApp | grep "undefined" | head -20
# 输出形如：
#  (undefined) external _objc_msgSend (from libobjc)
#  (undefined) external _malloc (from libSystem)
```

**Flat Namespace 兼容模式**：少数老工具链用 `-flat_namespace` 链接，此时符号查找退化为全局线性搜索，容易发生符号污染。`DYLD_FORCE_FLAT_NAMESPACE=1` 环境变量可以强制开启（逆向调试时偶尔用到）。

### 5. `install_name_tool`：修改依赖关系

`install_name_tool` 是修改已编译 Mach-O 文件中动态库依赖的官方工具：

```bash
# 查看当前依赖（等同 otool -L）
otool -L MyApp

# 修改 install_name（改变 LC_ID_DYLIB，影响依赖方如何引用此库）
install_name_tool -id @rpath/NewFoo.framework/NewFoo NewFoo

# 修改依赖路径（修改 LC_LOAD_DYLIB 中的 name 字段）
install_name_tool -change /absolute/old/path/Foo.dylib \
    @rpath/Foo.framework/Foo MyApp

# 查看 rpath（otool -l 筛 LC_RPATH）
otool -l MyApp | grep -A2 "LC_RPATH"

# 批量修改（常用于 CI/CD 打包脚本）
for dylib in $(otool -L MyApp | awk 'NR>1{print $1}' | grep "^/usr/local"); do
    install_name_tool -change "$dylib" "@rpath/$(basename $dylib)" MyApp
done
```

**`codesign` 联动**：修改 Mach-O 后二进制签名失效，需重签：

```bash
codesign --force --sign - MyApp          # 本地临时签名（开发用）
codesign --force --sign "Developer ID" MyApp  # 发布签名
```

### 6. `otool -L`：查看依赖关系

`otool -L` 是最常用的依赖关系查看命令，直接解析所有 `LC_LOAD_DYLIB`：

```bash
otool -L /Applications/Xcode.app/Contents/MacOS/Xcode
# 典型输出（示意）：
# /Applications/Xcode.app/Contents/MacOS/Xcode:
#   @rpath/DVTFoundation.framework/DVTFoundation
#           (compatibility version 1.0.0, current version 21500.0.0)
#   @rpath/DVTKit.framework/DVTKit
#           (compatibility version 1.0.0, current version 21500.0.0)
#   /usr/lib/libSystem.B.dylib
#           (compatibility version 1.0.0, current version 1336.0.0)
#   /System/Library/Frameworks/Foundation.framework/Versions/C/Foundation
#           (compatibility version 300.0.0, current version 2048.1.0)
```

**解读技巧**：

- 以 `@rpath/` 开头的：App 自带的私有 Framework，通常在 `Contents/Frameworks/` 或 `Plugins/`。
- 以 `/usr/lib/` 或 `/System/Library/` 开头的：系统提供的库，走 dyld 共享缓存。
- 以 `@executable_path/` 开头的：命令行工具常见，库和可执行文件同目录。

**查看弱依赖（`LC_LOAD_WEAK_DYLIB`）**：

```bash
# otool -l 可以区分 LC_LOAD_DYLIB 和 LC_LOAD_WEAK_DYLIB
otool -l MyApp | grep -B1 "LC_LOAD_WEAK_DYLIB" | grep name
```

### 7. 逆向依赖关系图谱

在逆向分析中，建立完整的依赖关系图是理解 App 架构的第一步：

```bash
# 递归分析所有依赖（类似 ldd 的效果）
# 方法一：dyld_info（macOS 12+）
dyld_info -dependents /usr/bin/git

# 方法二：otree（社区工具，递归 otool -L）
# brew install otree
otree MyApp

# 方法三：手写递归脚本
#!/bin/bash
visited=()
function deps() {
    local bin="$1"
    echo "=== $bin ==="
    for dep in $(otool -L "$bin" 2>/dev/null | awk 'NR>1{print $1}'); do
        [[ " ${visited[*]} " =~ " $dep " ]] && continue
        visited+=("$dep")
        [[ -f "$dep" ]] && deps "$dep"
    done
}
deps "$1"
```

**Frameworks 中的子库结构**（xcframework / 嵌套 Framework）：

```text
MyApp.app/
├── Contents/
│   ├── MacOS/MyApp              ← LC_LOAD_DYLIB: @rpath/Foo.framework/Foo
│   │                              LC_RPATH: @executable_path/../Frameworks
│   └── Frameworks/
│       ├── Foo.framework/
│       │   └── Foo              ← LC_ID_DYLIB: @rpath/Foo.framework/Foo
│       │                          LC_LOAD_DYLIB: @rpath/Bar.framework/Bar
│       │                          LC_RPATH: @loader_path/../  ← 找同级的 Bar
│       └── Bar.framework/
│           └── Bar              ← LC_ID_DYLIB: @rpath/Bar.framework/Bar
```

## 安全性与正确使用

### dylib 劫持（dylib hijacking）原理

dylib 劫持利用 `@rpath` 搜索顺序的漏洞，在 dyld 搜索到合法库之前，把恶意 dylib 放置在更靠前的 rpath 目录里：

```text
正常搜索顺序：
① @rpath/Foo.dylib → @executable_path/../Frameworks/Foo.dylib → [文件存在] → 加载正版

攻击后（在 HOME 目录注入）：
LC_RPATH 里插入或利用现有的 ~/Library/... 搜索路径
① @rpath/Foo.dylib → ~/Library/Foo.dylib → [恶意文件存在] → 加载恶意版
```

**利用 `LC_LOAD_WEAK_DYLIB` 的变体**：

如果二进制有 `LC_LOAD_WEAK_DYLIB` 引用了一个在正常安装情况下**不存在**的 dylib 路径（例如某个可选插件路径），攻击者只需在该路径创建恶意 dylib 即可劫持：

```bash
# 检查二进制是否有弱依赖（潜在劫持点）
otool -l /usr/local/bin/mytool | grep -B2 "LC_LOAD_WEAK_DYLIB" -A5
# 若存在指向可写目录的弱依赖路径 → 潜在劫持风险
```

**macOS 上的已知劫持向量**：

1. **`DYLD_INSERT_LIBRARIES` 注入**：不需要修改目标文件，直接在进程启动前注入 dylib；SIP（System Integrity Protection）和 Hardened Runtime 会阻止此技术对系统进程和已签名 App 使用。
2. **`DYLD_LIBRARY_PATH`/`DYLD_FRAMEWORK_PATH`**：覆盖 `@rpath` 搜索；同样被 Hardened Runtime 限制。
3. **弱引用路径植入**：在 `LC_LOAD_WEAK_DYLIB` 指向的可写路径创建恶意 dylib。
4. **rpath 目录可写**：若 `LC_RPATH` 的某个展开目录对攻击者可写，可在其中放置同名 dylib。

### 防御视角

**开发者防御措施**：

```bash
# 1. 开启 Hardened Runtime（hardened-runtime entitlement）
# 在 Xcode 中：Build Settings → Hardened Runtime = YES
# 命令行：codesign --options runtime --sign "Developer ID" MyApp

# 2. 检查所有 LC_RPATH 是否都在 App bundle 内（不引用外部可写目录）
otool -l MyApp | grep -A2 LC_RPATH
# 危险：LC_RPATH path = /usr/local/lib  ← 可能被普通用户写入
# 安全：LC_RPATH path = @executable_path/../Frameworks  ← 仅 bundle 内

# 3. 避免 LC_LOAD_WEAK_DYLIB 引用可写路径
# 用 LC_LOAD_DYLIB（强依赖）+ 运行时 dlopen 检查代替弱依赖

# 4. 使用两级命名空间（默认已开启，勿用 -flat_namespace）
# ld 默认 -twolevel_namespace，无需额外操作

# 5. 代码签名 + 校验 dylib 签名（从 macOS 10.15 起 dyld 会强制校验）
codesign --verify --deep --strict MyApp
```

**系统级防护（Apple 提供，开发者无需额外操作）**：

| 防护机制 | 效果 |
|---|---|
| SIP（System Integrity Protection）| 阻止修改 `/System`、`/usr` 下的二进制和库 |
| Hardened Runtime | 禁止 `DYLD_INSERT_LIBRARIES` 等环境变量注入 |
| Library Validation Entitlement | 只加载与主程序同一证书签名或 Apple 签名的 dylib |
| dyld 签名校验（macOS 10.15+）| 加载 dylib 前校验签名，拒绝未签名库 |
| `__RESTRICT,__restrict` 节 | 二进制内含此节时，dyld 忽略所有 `DYLD_*` 环境变量 |

**`Library Validation` Entitlement** 是对抗 dylib 劫持最有效的手段：

```xml
<!-- MyApp.entitlements -->
<key>com.apple.security.cs.disable-library-validation</key>
<false/>
<!-- 默认即为 false（不禁用），即开启库校验 -->
<!-- 若需加载第三方未签名插件，才设为 true（降低安全性）-->
```

**逆向时绕过防护的常见手段**（仅用于授权测试）：

```bash
# 越狱 iOS 设备上：
# DYLD_INSERT_LIBRARIES 对 App 有效（沙箱限制已绕过）
DYLD_INSERT_LIBRARIES=/usr/lib/substitute.dylib ./myapp

# macOS SIP 关闭状态下：
csrutil disable  # 仅在恢复模式，仅用于开发/研究
# 之后 DYLD_* 环境变量对系统进程也生效
```

## 实操：`otool`/`install_name_tool` 综合演示

### 场景一：将绝对路径依赖改为 `@rpath`（打包修复）

```bash
# 问题：Homebrew 编译的工具依赖 /usr/local/lib/libFoo.2.dylib（绝对路径）
otool -L mytool
# mytool:
#   /usr/local/lib/libFoo.2.dylib (...)
#   ...

# 步骤1：修改 libFoo 的 install_name
install_name_tool -id @rpath/libFoo.2.dylib /usr/local/lib/libFoo.2.dylib

# 步骤2：复制 libFoo 到 App bundle
cp /usr/local/lib/libFoo.2.dylib MyApp.app/Contents/Frameworks/

# 步骤3：修改 mytool 对 libFoo 的引用
install_name_tool -change /usr/local/lib/libFoo.2.dylib \
    @rpath/libFoo.2.dylib mytool

# 步骤4：添加 rpath（指向 bundle 内 Frameworks 目录）
install_name_tool -add_rpath @executable_path/../Frameworks mytool

# 步骤5：验证
otool -L mytool
otool -l mytool | grep -A2 LC_RPATH

# 步骤6：重签名
codesign --force --sign - mytool
codesign --force --sign - MyApp.app/Contents/Frameworks/libFoo.2.dylib
```

### 场景二：逆向分析 App 的私有 Framework 依赖

```bash
# 目标：分析某 App 用了哪些私有 Framework，以及它们的内部依赖
APP="/Applications/WeChat.app"
EXEC="$APP/Contents/MacOS/WeChat"

# 第一层：主程序依赖
echo "=== Main Executable Dependencies ==="
otool -L "$EXEC"

# 找出 @rpath 依赖（私有 Framework）
echo -e "\n=== Private Frameworks (via @rpath) ==="
otool -L "$EXEC" | grep "@rpath" | awk '{print $1}'

# 展开 rpath（查看实际搜索路径）
echo -e "\n=== LC_RPATH entries ==="
otool -l "$EXEC" | grep -A2 LC_RPATH | grep path

# 第二层：某个私有 Framework 的内部依赖
FW="$APP/Contents/Frameworks/MMCommon.framework/MMCommon"
if [ -f "$FW" ]; then
    echo -e "\n=== MMCommon.framework Dependencies ==="
    otool -L "$FW"
fi
```

### 场景三：检测 dylib 劫持风险

```bash
#!/bin/bash
# 扫描二进制的 @rpath 是否包含可写目录（潜在劫持风险）
TARGET="${1:-$(which git)}"

echo "Analyzing: $TARGET"
echo "=== LC_RPATH entries ==="

# 提取 rpath 并展开 @executable_path
EXEC_DIR=$(dirname "$(realpath "$TARGET")")
otool -l "$TARGET" | grep -A2 LC_RPATH | grep "path " | awk '{print $2}' | \
while read rpath; do
    # 展开占位符
    expanded="${rpath/@executable_path/$EXEC_DIR}"
    expanded="${expanded/@loader_path/$EXEC_DIR}"

    # 检查可写性
    if [ -d "$expanded" ] && [ -w "$expanded" ]; then
        echo "[WARN] Writable rpath: $expanded  (original: $rpath)"
    elif [ -d "$expanded" ]; then
        echo "[OK]   $expanded"
    else
        echo "[MISSING] $expanded (not exists, potential hijack if created)"
    fi
done

echo ""
echo "=== LC_LOAD_WEAK_DYLIB (higher risk) ==="
otool -l "$TARGET" | grep -B1 "LC_LOAD_WEAK_DYLIB" | grep -v "LC_LOAD_WEAK" | grep name
```

## 与相邻章节的关系

- [[07.Mach-O LC_LOAD_DYLIB]]：`LC_LOAD_DYLIB` 的详细字段解析（timestamp、version 字段细节、与 `LC_LOAD_WEAK_DYLIB` 的区别），本篇在此基础上讲解 `@rpath` 等路径展开机制。
- [[08.Mach-O LC_ID_DYLIB]]：dylib 自身的 `install_name`（`LC_ID_DYLIB` 命令），是 `LC_LOAD_DYLIB.name` 的"对端"，本篇涉及修改 `install_name` 时需读此篇。
- [[17.Mach-O LC_DYLD_INFO_ONLY]]：符号绑定信息（rebase/bind/lazy bind），是 dyld 找到 dylib 后的下一步——把符号地址填入 GOT；本篇讲"找到哪个库"，17 篇讲"绑定哪些符号"。
- [[15.Mach-O __DATA_CONST]]：`__got`/`__nl_symbol_ptr` 等 dylib 绑定的目标地址所在，与 `@rpath` 机制完成后的符号解析直接关联。

## 小结

- **`LC_LOAD_DYLIB`** 记录依赖库的 `install_name`、兼容版本与当前版本；`install_name` 是库自报家门的名字，由链接期复制进依赖方。
- **三个路径占位符**各司其职：`@executable_path` 固定指向主程序目录；`@loader_path` 随当前解析者的位置变化；`@rpath` 动态遍历 `LC_RPATH` 列表搜索，是 App Bundle 与 Framework 的推荐做法。
- **`LC_RPATH`** 向进程追加 rpath 搜索目录；rpath 列表在整个依赖链上汇总，所有已加载 Mach-O 的 `LC_RPATH` 均参与 `@rpath` 展开。
- **两级命名空间**通过在符号引用中编码库序号，消除了同名符号的冲突，是 macOS 10.1 以后的默认行为。
- **`LC_LOAD_WEAK_DYLIB`** 声明可选依赖——库缺失时进程仍可正常启动，但代码需用 `dlsym` 检查符号可用性；弱依赖是 dylib 劫持的常见目标。
- **`otool -L`** 查看依赖、**`install_name_tool`** 修改依赖和 rpath，是打包、分发和逆向分析的核心工具。
- **dylib 劫持**利用 `@rpath` 搜索顺序，防御关键：开启 Hardened Runtime、Library Validation、避免 `LC_RPATH` 指向可写目录、以强依赖代替不必要的弱依赖。
