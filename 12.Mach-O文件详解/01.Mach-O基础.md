# 详解Mach-O(一)Mach-O基础

> [!abstract] TL;DR
> Mach-O（Mach Object）是 Apple 平台（macOS、iOS、watchOS、tvOS）的原生可执行文件格式，可执行程序、动态库、Bundle、内核扩展、目标文件都用它。
> 一个 Mach-O 文件由 **Header（头部）→ Load Commands（加载命令表）→ Data（段与节）** 三段式构成：Header 声明架构与文件类型，Load Commands 告诉内核与 `dyld` 如何把文件映射进内存、依赖哪些库，Data 区则承载真正的代码与数据。
> 它是理解程序**加载、动态链接与内存布局**的基石——逆向、调试、符号化、性能分析都从读懂 Mach-O 开始。本篇是整个系列的总入口，后续每一篇都在拆解这张结构图里的某个零件。

## 概述与定位

Mach-O 之于 Apple 平台，正如 ELF 之于 Linux、PE 之于 Windows：它是操作系统内核（XNU）与动态链接器 `dyld` 共同认识的"程序长什么样"的契约格式。无论你写的是一个 App、一个 `.dylib` 动态库、一个 `.bundle` 插件，还是编译产生的 `.o` 目标文件，落到磁盘上的都是 Mach-O。

它在系统中的定位可以归纳为三件事：

- **描述布局**：通过 Load Commands 精确声明每个段（Segment）应映射到进程虚拟地址空间的哪个位置、占多大、拥有什么内存权限。
- **声明依赖**：通过 `LC_LOAD_DYLIB` 等命令列出运行时需要的动态库及其版本，`dyld` 据此完成加载与符号绑定。
- **组织数据**：把代码、只读常量、可写数据、链接元信息分门别类放进 `__TEXT` / `__DATA` / `__LINKEDIT` 等段中，既便于按页权限保护，又便于按需映射。

读懂这三段式，是后续所有章节的公共前提。本系列后面会逐个深入 Header 的每个字段（[[02.Mach-O文件头]]）、每一类 Load Command（从 [[03.Mach-O加载命令]] 起）、每一个段（从 [[11.Mach-O Segments]] 起）与每一种节（从 [[18.Mach-O section]] 起）。

## 核心原理与字段详解

### 1. Header（头部）

Header 是文件的"身份证"，内核读它来决定能否、以及如何加载这个文件。64 位下对应内核结构体 `mach_header_64`（定义于 `<mach-o/loader.h>`），关键字段：

| 字段 | 含义 |
|---|---|
| `magic` | 魔数，标识 Mach-O 及字节序/位宽（取值见下方"架构差异"） |
| `cputype` | CPU 架构类型，如 `CPU_TYPE_X86_64`、`CPU_TYPE_ARM64` |
| `cpusubtype` | CPU 子类型，进一步细分（如 arm64e） |
| `filetype` | 文件类型：`MH_EXECUTE`（可执行）、`MH_DYLIB`（动态库）、`MH_OBJECT`（目标文件）、`MH_BUNDLE`（插件）等 |
| `ncmds` | 紧随其后的 Load Command 条数 |
| `sizeofcmds` | 所有 Load Command 的总字节数 |
| `flags` | 标志位，如 `MH_PIE`（地址无关可执行）、`MH_TWOLEVEL`（两级命名空间） |
| `reserved` | 仅 64 位 Header 多出的保留字段 |

`magic` 决定了后续所有字段的解读方式（32/64 位、大小端），因此它是解析的第一步。Header 字段的逐字段拆解见 [[02.Mach-O文件头]]。

### 2. Load Commands（加载命令）

Load Commands 紧跟 Header，是一串变长记录。每条命令都以统一的 `load_command{ uint32_t cmd; uint32_t cmdsize; }` 开头：`cmd` 标识命令类型，`cmdsize` 给出本条命令（含头部与各自附加数据）的总长度——解析时正是靠 `cmdsize` 累加来跳到下一条命令。

它们的作用是"指挥"内核和 `dyld` 搭建进程运行环境，常见命令：

- `LC_SEGMENT` / `LC_SEGMENT_64`：描述一个段如何映射进虚拟内存（地址、大小、文件偏移、权限）。
- `LC_LOAD_DYLIB`：声明一个运行时依赖的动态库及其路径、版本。
- `LC_ID_DYLIB`：动态库声明自身的 install name 与版本。
- `LC_SYMTAB`：指出符号表与字符串表在文件中的位置。
- `LC_DYSYMTAB`：描述动态符号表（本地/外部/未定义符号分区、间接符号表）。
- `LC_MAIN`：声明程序入口点偏移（`entryoff`），取代旧的 `LC_UNIXTHREAD`。
- `LC_DYLD_INFO_ONLY`：指向压缩的动态链接信息（rebase/bind/lazy bind/export 各表）。

命令的通用结构与遍历方式见 [[03.Mach-O加载命令]]。

### 3. Segment（段）与 Section（节）的关系

**段是 Mach-O 中最大的逻辑分组，直接映射到进程地址空间的一段连续虚拟内存**，并带有统一的内存保护权限（读/写/执行）。一个段内部又可细分为零个或多个**节**，节是更细粒度的数据组织单位——同一个段里的所有节共享该段的内存权限。

可以这样理解二者关系：

```
__TEXT 段 (R-X 只读可执行)
 ├─ __text        机器码
 ├─ __cstring     C 字符串常量
 └─ __const       只读常量
__DATA 段 (RW- 可读写)
 ├─ __data        已初始化可写数据
 ├─ __bss         未初始化数据（运行时清零）
 └─ __la_symbol_ptr  惰性符号指针
__LINKEDIT 段 (R-- 只读)
 └─ 符号表 / 字符串表 / 重定位 / dyld info 等链接元数据
```

常见段及职责：

- `__TEXT`：只读可执行，存放代码与只读常量。
- `__DATA`：可读写，存放可变的全局/静态数据。
- `__LINKEDIT`：只读，存放链接器与 `dyld` 用到的元数据（符号表、字符串表、重定位项、绑定信息等），位于文件尾部。

段的整体模型见 [[11.Mach-O Segments]]，节的通用字段（`section_64` 的 `addr`/`size`/`offset`/`flags` 等）见 [[18.Mach-O section]]。

### 4. Fat / Universal Binary（多架构二进制）

一个普通 Mach-O 只含单一架构的代码。为了让同一份文件能在不同 CPU（如 Intel 与 Apple Silicon）上运行，Apple 提供了 **Fat Binary（也叫 Universal Binary）**：在文件最前面加一个 `fat_header`，后跟若干 `fat_arch` 记录，每条记录指向一个内嵌的、完整的单架构 Mach-O 及其在文件中的偏移与大小。系统加载时按当前设备架构挑选对应的那一份。可以把 Fat Binary 理解为"多个 Mach-O 打了个包"。

其外层结构定义于 `<mach-o/fat.h>`，**关键易错点：fat 头与 fat_arch 数组一律以大端（big-endian）存储**，而内嵌的各单架构 Mach-O 仍按各自的主机字节序——所以解析 Fat 外层时永远要做字节序转换：

```c
struct fat_header {
    uint32_t magic;     // FAT_MAGIC 0xcafebabe / FAT_MAGIC_64 0xcafebabf
    uint32_t nfat_arch; // 后随的 fat_arch 条数
};
struct fat_arch {       // FAT_MAGIC_64 时为 fat_arch_64，offset/size 扩为 64 位
    cpu_type_t    cputype;     // 架构大类
    cpu_subtype_t cpusubtype;  // 架构子类型
    uint32_t      offset;      // 该架构 Mach-O 在文件中的偏移
    uint32_t      size;        // 该架构 Mach-O 的大小
    uint32_t      align;       // 对齐（2 的幂，如 2^14）
};
```

布局上是「一个 `fat_header` + `nfat_arch` 个 `fat_arch` 描述符 + 各架构切片」：

```
fat_header        (magic=0xcafebabe, nfat_arch=2)   ← 大端
fat_arch[0]       (x86_64,  offset, size, align)    ← 大端
fat_arch[1]       (arm64e,  offset, size, align)    ← 大端
─────────────────────────────────────────
[offset0] 完整的 x86_64  Mach-O（自带 Header→LC→Data，小端）
[offset1] 完整的 arm64e Mach-O（自带 Header→LC→Data，小端）
```

系统按当前设备的 `cputype`/`cpusubtype` 在 `fat_arch` 数组里挑出匹配切片，再用 `offset` 跳到那份单架构 Mach-O 读其 Header。`fat_arch` 各字段与外层逐字节解析见 [[02.Mach-O文件头]] 第 8 节，本篇只给整体形态。

### 5. 两级命名空间（Two-Level Namespace）

Mach-O 默认采用**两级命名空间**：一个外部符号的引用不仅记录符号名，还记录它来自**哪个动态库**（通过 `LC_LOAD_DYLIB` 的序号定位）。这与传统的扁平命名空间不同——后者只按名字在所有库里查找，容易发生不同库的同名符号互相覆盖。两级命名空间让符号解析更精确、更安全，也是 `MH_TWOLEVEL` 标志的含义。

### 6. dyld 的角色与启动全流程

`dyld`（dynamic linker，动态链接器，路径由 `LC_LOAD_DYLINKER` 指定，通常是 `/usr/lib/dyld`）是用户态程序启动的真正"装配工"。**内核从不直接运行用户二进制——每一次 `exec` 都先落到 `dyld`，哪怕是 `/usr/bin/true`。** 内核把主可执行文件与 `dyld` 映射进内存后，把控制权交给 `dyld`，由它一步步把进程"组装"到能跳进 `main` 为止。

完整启动链路可分为七步：

![[macho-01-fig2.png]]

> [!note]- Mermaid 源码
> ```text
> sequenceDiagram
>     participant K as 内核 (XNU)
>     participant D as dyld
>     participant L as 依赖库 / 共享缓存
>     participant App as 主程序
> 
>     K->>K: 1. execve：校验 Mach-O 头与代码签名<br/>销毁旧 VM、映射段、建栈(argv/envp/auxv)
>     K->>D: 2. 按 LC_LOAD_DYLINKER 映射 dyld 并移交控制权
>     D->>D: 3. 自举：dyld 重定位自身内部指针<br/>(dyldbootstrap::start → dyld::_main)
>     D->>L: 4. 沿 LC_LOAD_DYLIB 递归加载依赖<br/>系统库优先命中 dyld 共享缓存
>     D->>App: 5. 修正(fixup)：rebase 内部指针(ASLR)<br/>+ bind 外部符号（新格式为 chained fixups）
>     D->>App: 6. 自底向上运行初始化器<br/>__mod_init_func / C++ 构造 / ObjC +load
>     D->>App: 7. 跳转 LC_MAIN 指定的入口 → main()
> ```

逐步说明：

1. **内核 `execve`**：校验 Mach-O 头与代码签名/授权，拆掉旧进程的虚拟地址空间，按 Load Commands 映射主程序各段，建好带 `argv`/`envp`/`auxv` 的栈。
2. **移交 dyld**：内核读主程序的 `LC_LOAD_DYLINKER` 找到 `dyld` 路径，把 `dyld` 映射进来并跳过去——入口不是你的 `main`，而是 `dyld`。
3. **dyld 自举**：`dyld` 自己也是动态镜像且无依赖，若未加载到偏好地址，要先 rebase 自身的内部指针，再进入 `dyld::_main`。
4. **加载并映射依赖**：沿 `LC_LOAD_DYLIB` 递归加载所有依赖库；系统库（Foundation、UIKit 等）直接命中 **dyld 共享缓存**（见第 7 节），省去逐个映射与链接。
5. **修正（fixup = rebase + bind）**：**rebase** 修正地址无关代码里的内部指针以适配 ASLR 随机基址；**bind** 把外部符号引用解析成实际地址。旧格式 rebase/bind/lazy bind 各有独立表（`LC_DYLD_INFO_ONLY`，见 [[17.Mach-O LC_DYLD_INFO_ONLY]]）；自 iOS 15 / macOS 12 起改用 **chained fixups**（见第 8 节）。
6. **运行初始化器**：按依赖关系**自底向上**（被依赖者先初始化）执行各镜像的初始化函数——`__DATA,__mod_init_func`（[[32.Mach-O __mod_init_func节]]）里的 C++ 全局构造、`__attribute__((constructor))`、以及 ObjC 的 `+load`。
7. **跳转 `main`**：现代可执行用 `LC_MAIN`（[[09.Mach-O LC_MAIN]]）给出入口偏移 `entryoff`，`dyld` 跳进 `main`；旧二进制用 `LC_UNIXTHREAD`，先经 `crt1.o` 的运行时桩再调 `main`。

因此，Mach-O 的结构本质上是写给 `dyld` 看的一套"装配说明书"。

### 7. dyld 共享缓存（dyld shared cache）

如果每个进程都从磁盘逐个映射、链接几十上百个系统库，启动会非常慢、内存也会大量重复。Apple 的解法是 **dyld 共享缓存**：在系统出厂/更新时（由 `SharedCacheBuilder`）把绝大多数系统 dylib（`/usr/lib/*.dylib`、各 Framework）**预链接、合并成一个大文件**。运行时每个进程都把这同一个缓存文件映射进各自地址空间，底层物理页在所有进程间共享。

要点：

- **省内存 + 提速**：一份缓存服务全系统进程，省去数百 MB 重复内存与重复链接；预先算好的内容让启动从"毫秒级链接"降到"微秒级映射"，还自带预建的 ObjC 运行时哈希表。
- **macOS 11 起的变化**：Big Sur 之后系统不再单独随盘附带这些库的原始文件，磁盘上**唯一的副本就在缓存里**（这也是你在 `/System/Library/Frameworks` 里找不到对应二进制的原因）；旧的 `update_dyld_shared_cache` 被弃用。
- **位置随版本变动**：早期在 `/usr/lib/dyld/` 或 `/System/Library/dyld/`，Ventura 起移到 `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/`（配合 Rapid Security Response）。
- Header 里的 `MH_DYLIB_IN_CACHE`（`0x80000000`）标志即表示该镜像位于共享缓存中。

> [!note] 共享缓存是实现细节
> 缓存的内部布局是 Apple 的内部实现细节，历史上多次大改（dyld 1→4），不应依赖其格式做长期解析。逆向系统库时通常需用工具先把目标 dylib 从缓存中抽取出来。

### 8. Chained Fixups（链式修正，现代格式）

第 6 节提到的 rebase / bind，在 **iOS 15 / macOS 12 及以后**默认改用 **chained fixups（链式修正）**——这是当代二进制最该知道的一个变化。

- **旧格式**（`LC_DYLD_INFO_ONLY`，见 [[17.Mach-O LC_DYLD_INFO_ONLY]]）：rebase、bind、lazy bind、export 各存一张独立的字节码表，`dyld` 要分别遍历。
- **新格式**：rebase 与 bind 信息被编码进 `__DATA` 里指针自身的位域，串成"链"。只在 **每页记录第一个修正点的位置**，后续修正点靠每个指针里的 `next` 字段（步长 ×4）顺着指针往下找；每个 64 位修正项用**最低位**区分是 rebase（0）还是 bind（1)。对应的新加载命令是 `LC_DYLD_CHAINED_FIXUPS`（payload 头为 `dyld_chained_fixups_header`）与 `LC_DYLD_EXPORTS_TRIE`，不再使用 `LC_DYLD_INFO`。

带来的影响：

- **更小更快**：修正信息内联进指针、每页只存一个起点，元数据大幅缩小（大型 Swift 应用可省 1MB+），`dyld` 一遍扫描即可同时完成 rebase 与 bind。
- **没有 lazy bind 了**：所有绑定在加载期一次性完成，旧的惰性绑定机制（`__la_symbol_ptr` + stub helper）随之消失。
- **arm64e 强制使用**：Apple Silicon 的指针认证 ABI 必须配 chained fixups。
- **版本壁垒**：用 chained fixups 的二进制无法在更老的系统上运行/加载。
- **工具差异**：`dyldinfo` 解析不了 chained fixups；可用 `otool -fixup_chains`（仅显示 imports，不含 rebase）。

> [!note] 与本系列的关系
> chained fixups 的字节码细节（`dyld_chained_fixups_header` 各字段、页起点、`dyld_chained_ptr_64_rebase/bind` 联合体）超出总览范畴，本篇只给"它是什么、替代了谁、有何影响"。它与旧 `LC_DYLD_INFO_ONLY` 的关系详见 [[17.Mach-O LC_DYLD_INFO_ONLY]]。

### 9. 与 ELF / PE 的对比

| 维度 | Mach-O (Apple) | ELF (Linux) | PE (Windows) |
|---|---|---|---|
| 顶层组织 | Header + Load Commands + 段/节 | ELF Header + Program/Section Headers | DOS Header + PE Header + Sections |
| 布局描述 | Load Commands 表（可扩展的命令流） | Program Header Table | Section Table |
| 魔数 | `0xfeedfacf`（64 位）| `0x7F 45 4C 46`（`\x7FELF`）| `MZ` + `PE\0\0` |
| 段/节术语 | Segment / Section（段含节）| Segment / Section（程序头 vs 节头两套视图）| Section（无独立段层）|
| 入口点 | `LC_MAIN`（`entryoff`）/ 旧 `LC_UNIXTHREAD` | ELF Header 的 `e_entry` | PE 头的 `AddressOfEntryPoint` |
| 多架构 | Fat/Universal Binary 原生支持 | 单架构（需外部多版本/胖二进制非标准）| 单架构 |
| 命名空间 | 默认两级命名空间（符号带库来源）| 扁平 | 按 DLL 导入表 |
| 动态链接器 | `dyld` | `ld.so` | Windows Loader |
| 重定位/绑定 | rebase + bind（新：chained fixups）| `.rela.*` 重定位 + PLT/GOT 惰性绑定 | 基址重定位表 + IAT |
| 系统库共享 | dyld 共享缓存（预链接合并）| 各 `.so` 独立映射 + 页缓存 | 各 DLL 独立映射（KnownDLLs）|

Mach-O 用"命令流"来描述布局这一设计，使其在扩展性（新增 LC 类型即可表达新特性）与符号访问效率上具有自身特点。三者都是「头 + 描述表 + 数据段」的家族，差异主要在描述表的形态、多架构支持与符号解析策略上。

> [!note] 架构差异
> Mach-O 通过 Header 起始的 4 字节 **magic** 区分位宽与文件形态：
> - **32 位**：`MH_MAGIC` = `0xfeedface`
> - **64 位**：`MH_MAGIC_64` = `0xfeedfacf`（当代 macOS/iOS 主流，对应 `mach_header_64`）
> - **Fat/Universal Binary**：`FAT_MAGIC` = `0xcafebabe`（多架构包的外层魔数）
> 此外还有字节序反转的变体 `MH_CIGAM`/`MH_CIGAM_64`/`FAT_CIGAM`，用于跨端序解析。解析任何 Mach-O 的第一步，都是读这 4 个字节判断该按哪种结构、哪种字节序去读后续内容。

## 实操：用工具查看

在 macOS 上，常用命令行工具有 `otool`（查看 Mach-O 各部分）、`file`（识别文件类型）、`lipo`（操作 Universal 包）、`size`（看各段大小）、`nm`（看符号表）。

```bash
otool -h /bin/ls          # 打印 Header（magic/cputype/filetype/ncmds…）
otool -l /bin/ls          # 列出全部 Load Commands
otool -f /bin/ls          # 查看 Fat/Universal 外层各架构切片
file   /bin/ls            # 人类可读的文件类型与架构
lipo   -info /bin/ls      # 列出 Universal 包含哪些架构
lipo   -thin arm64e /bin/ls -output /tmp/ls.arm64e   # 抽出单一架构切片
size   -m  /bin/ls        # 按段/节统计大小（-m 显示 Mach-O 段节明细）
```

## FAQ

> [!question] Mach-O 和 Fat/Universal Binary 是一回事吗？
> 不是。Mach-O 是单架构的可执行格式；Fat/Universal Binary 是把多个单架构 Mach-O 用一个 `fat_header` + `fat_arch` 数组打成的"包"。系统按设备架构挑出其中一份单架构 Mach-O 来加载。换句话说，Fat 是外壳，里面装着 N 个完整的 Mach-O。

> [!question] 为什么内核不直接运行我的可执行文件，而要先跑 dyld？
> 因为现代可执行依赖动态库、需要 ASLR 重定位与符号绑定，这些活儿都由用户态的 `dyld` 干。内核 `execve` 只负责映射主程序和 `dyld`，随后把控制权交给 `dyld`，由它加载依赖、做 rebase/bind、跑初始化器，最后才跳进你的 `main`。哪怕是 `/usr/bin/true` 也走这条路。

> [!question] rebase、bind、chained fixups 到底什么关系？
> rebase（修内部指针适配 ASLR）和 bind（解析外部符号）是两类"修正"。旧系统它们各存一张表（`LC_DYLD_INFO_ONLY`）；iOS 15 / macOS 12 起合并成 **chained fixups**——把修正信息内联进指针自身并串成链，一遍扫描同时完成 rebase 与 bind，而且不再有 lazy bind。详见本篇第 8 节与 [[17.Mach-O LC_DYLD_INFO_ONLY]]。

> [!question] 为什么 `/System/Library/Frameworks` 里找不到对应的 dylib 文件？
> 因为 macOS 11（Big Sur）起，系统库的唯一副本被预链接合并进了 **dyld 共享缓存**，磁盘上不再单独附带原始二进制。这是为了省内存、加快启动（见第 7 节）。逆向这些系统库需先用工具从共享缓存里抽取。

> [!question] arm64 和 arm64e 有什么区别？为什么一个 Universal 包里两者都有？
> 二者 `cputype` 都是 `CPU_TYPE_ARM64`，区别在 `cpusubtype`：arm64 为 `0`，arm64e 为 `2`，后者带指针认证（PAC）且强制使用 chained fixups。它们在 Universal 包里是两个独立切片，系统按设备能力选用。字段层面见 [[02.Mach-O文件头]]。

## 小结

- Mach-O 是 Apple 平台的原生可执行格式，**Header → Load Commands → Data（段与节）** 三段式是其核心骨架；字段级细节交由分篇展开，本篇负责全局视角与导航。
- Header 用 `magic` 声明位宽与字节序、用 `filetype` 声明用途；Load Commands 是写给内核与 `dyld` 的"装配说明书"；段直接映射到带权限的虚拟内存，节是段内的细粒度分组。
- Fat/Universal Binary 用大端的 `fat_header`/`fat_arch` 把多个单架构 Mach-O 打包；两级命名空间提升符号解析的安全性。
- `dyld` 启动全流程：内核 `execve` → 映射并移交 `dyld` → `dyld` 自举 → 加载依赖（命中**共享缓存**）→ rebase/bind（新格式 **chained fixups**，无 lazy bind）→ 自底向上跑初始化器 → 跳 `LC_MAIN` 进 `main`。
- 与 ELF/PE 相比，Mach-O 以可扩展的"命令流"描述布局、原生支持多架构、用共享缓存预链接系统库，这些是它最鲜明的设计特征。
