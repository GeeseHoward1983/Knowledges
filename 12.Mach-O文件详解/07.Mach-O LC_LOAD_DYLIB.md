# 详解Mach-O(七)Mach-O LC_LOAD_DYLIB

> [!abstract] TL;DR
> **`LC_LOAD_DYLIB` 声明一个运行时强依赖的动态库**：命令体是定长的 `dylib_command`，内嵌一个 `struct dylib`，记录库的**安装名（install name，即路径）**、**构建时间戳**、**当前版本（current_version）** 与 **兼容版本（compatibility_version）**。每依赖一个 `.dylib`，就有一条这样的命令；它与库自身的 `LC_ID_DYLIB`（[[08.Mach-O LC_ID_DYLIB]]）配对——加载方说"我要谁"，被加载方说"我是谁"，两边 install name 必须对得上。
> `name` 是 `union lc_str`，在文件里以"相对命令起点的偏移"存放，真正的字符串紧跟在结构体之后，所以 `cmdsize` 是变长的（随路径长度变化、向指针大小对齐）。`current_version`/`compatibility_version` 把 `X.Y.Z` 打包进 **32 位**：**高 16 位 = X、中 8 位 = Y、低 8 位 = Z**；`dyld` 加载时若运行环境里实际库的 `compatibility_version` **低于**可执行文件记录的值，判定不兼容、加载失败（`current_version` 仅供查询、不参与拒绝）。
> 路径里常见的 `@rpath`、`@executable_path`、`@loader_path` 三种占位符，决定库在运行时被搜索的位置——这是理解"动态库找不到（dyld: Library not loaded / image not found）"类问题的关键。`@rpath` 还要与 `LC_RPATH` 命令提供的运行时搜索路径列表配合。本命令与位宽无关（32/64 位结构一致），并派生出五种变体：`LC_LOAD_DYLIB`（0xc）/ `LC_LOAD_WEAK_DYLIB`（弱依赖）/ `LC_REEXPORT_DYLIB`（再导出）/ `LC_LOAD_UPWARD_DYLIB`（向上依赖、解循环）/ `LC_LAZY_LOAD_DYLIB`（惰性加载），结构都复用 `dylib_command`。

## 概述与定位

一个程序很少独立运行，它依赖 `libSystem`、各种 framework、第三方库等动态库。`LC_LOAD_DYLIB` 就是把这些依赖**写进二进制**的标准方式：链接器（`ld`）在链接期为每个被链接的 `.dylib` 生成一条 `LC_LOAD_DYLIB`，把对方的安装名与版本信息抄进来；运行期 `dyld` 顺着这些命令递归把依赖一并加载、绑定符号、做版本检查。

它之所以重要，原因有三：

1. **它是依赖图的边**。整个进程的动态库依赖关系，就是由一条条 `LC_LOAD_DYLIB`（以及它派生的 WEAK / REEXPORT / UPWARD 变体）连成的有向图；`dyld` 启动时做的第一件大事就是对这张图做递归加载与拓扑处理。
2. **它承载"库去哪找"的全部信息**。`name` 字段里的 install name（绝对路径 / `@rpath/...` / `@loader_path/...` / `@executable_path/...`）直接决定 `dyld` 的搜索行为，绝大多数"库找不到/加载了错误的库"问题都根因在这一个字段。
3. **它决定符号绑定的目标**。在**两级命名空间**（two-level namespace，现代二进制默认）下，每个未定义符号都用一个**库序号（library ordinal）** 指回某一条 `LC_LOAD_DYLIB`，从而精确知道"这个符号该去哪个库里找"——见下文第 6 节。

本命令与库自身的 [[08.Mach-O LC_ID_DYLIB]] 是一对：被依赖的 `.dylib`（`MH_DYLIB` 类型）用一条 `LC_ID_DYLIB` 声明自己的 install name；任何链接它的镜像就把这个 install name 原样抄进一条 `LC_LOAD_DYLIB`。两者**复用同一个 `dylib_command` 结构**，仅 `cmd` 值不同。

> [!note] install name（安装名）到底是什么
> install name 不是"文件当前所在的真实路径"，而是**库在构建时声明、希望别人来找它时使用的路径**——一个嵌进库内部的字符串。链接期 `-install_name <path>` 把它写进库的 `LC_ID_DYLIB`；任何链接该库的镜像把这个字符串**复制**进自己的 `LC_LOAD_DYLIB`。所以"把 dylib 文件挪个位置"并不会自动改变依赖它的程序里记录的路径——程序仍按旧 install name 去找，于是 `dyld` 报 `Library not loaded`。修正手段是 `install_name_tool`（改库自己的 ID 用 `-id`，改依赖方记录的路径用 `-change`，见实操节）。

## 核心原理与字段详解

### 1. `dylib_command` 与 `struct dylib` 完整定义

来自 `<mach-o/loader.h>`，逐字段注释如下。注意 `dylib_command` 是**所有 `LC_*_DYLIB` 命令共用的结构**——`LC_ID_DYLIB`、`LC_LOAD_DYLIB`、`LC_LOAD_WEAK_DYLIB`、`LC_REEXPORT_DYLIB`、`LC_LOAD_UPWARD_DYLIB`、`LC_LAZY_LOAD_DYLIB` 都用它，靠 `cmd` 值区分语义：

```c
/*
 * 一个动态库（filetype == MH_DYLIB）用一条 LC_ID_DYLIB 声明自身；
 * 任何使用该库的镜像，则为它用到的每个库各放一条
 * LC_LOAD_DYLIB / LC_LOAD_WEAK_DYLIB / LC_REEXPORT_DYLIB / ...
 * 这些命令全部复用下面的 dylib_command 结构。
 */
struct dylib_command {
    uint32_t     cmd;        // LC_LOAD_DYLIB(0xc) / LC_ID_DYLIB(0xd) /
                             // LC_LOAD_WEAK_DYLIB(0x18|LC_REQ_DYLD) /
                             // LC_REEXPORT_DYLIB(0x1f|LC_REQ_DYLD) / ...
    uint32_t     cmdsize;    // 命令总长 = sizeof(dylib_command) + 安装名字符串长度，
                             // 向指针大小（8 字节 / 64 位）向上取整
    struct dylib dylib;      // 库标识（路径 + 时间戳 + 两个版本号），见下
};

/*
 * dyld 用 struct dylib 把"链接它的镜像"与"实际找到的库文件"做匹配。
 */
struct dylib {
    union lc_str name;               // 库的安装名/路径（install name），偏移式字符串
    uint32_t timestamp;              // 库的构建时间戳（用于旧式 prebinding 判定）
    uint32_t current_version;        // 库的当前版本号（X.Y.Z 打包成 32 位）
    uint32_t compatibility_version;  // 库的兼容版本号（X.Y.Z 打包成 32 位）
};
```

`dylib_command` 固定头 24 字节（`cmd` 4 + `cmdsize` 4 + `dylib` 16），各字段的精确偏移：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `cmd` | uint32_t | 4 | 命令类型，`LC_LOAD_DYLIB` 为 `0xc` |
| 4 | `cmdsize` | uint32_t | 4 | 含安装名字符串的总长，向指针大小对齐 |
| 8 | `dylib.name` | union lc_str（uint32 offset） | 4 | 安装名字符串**相对命令起点的偏移**，通常为 24 |
| 12 | `dylib.timestamp` | uint32_t | 4 | 构建时间戳 |
| 16 | `dylib.current_version` | uint32_t | 4 | 当前版本，X.Y.Z 打包 |
| 20 | `dylib.compatibility_version` | uint32_t | 4 | 兼容版本，X.Y.Z 打包 |
| 24 | （安装名字符串） | char[] | 变长 | `\0` 结尾，尾部对齐填充 |

> [!note] 四个字段各自的用途（Apple ABI 文档原义）
> - **name**：`dyld` 运行时用它定位库文件。
> - **timestamp**：库的构建时间，`dyld` 用它判断旧式 **prebinding** 信息是否仍可用（现代链式 fixups 时代意义已淡化，常见为 1 或 2）。
> - **current_version**：库的当前版本，可由 `NSVersionOfRunTimeLibrary()` 取回，供程序在运行时查询自己实际用到的库版本；**不参与加载失败判定**。
> - **compatibility_version**：兼容版本，**参与 `dyld` 的兼容性检查**（见第 3 节）。

### 2. `union lc_str`：偏移式字符串

`name` 不是直接内嵌的字符数组，而是一个 `union lc_str`：

```c
union lc_str {
    uint32_t offset;       // 字符串相对“本条命令起点”的字节偏移
#ifndef __LP64__
    char    *ptr;          // 仅 32 位进程内运行时用到的指针视图（文件里不用）
#endif
};
```

文件里**永远使用 `offset` 视图**：它给出安装名字符串相对**本条 load command 起点**（不是文件起点）的偏移。字符串以 `\0` 结尾，**紧跟在 `dylib_command` 固定头之后**，所以 `offset` 几乎总是 `24`（= 头部大小）。解析时取串的方法是 `(char*)cmd + dylib.name.offset`，读到 `\0` 为止；`cmdsize` 则覆盖"头 + 字符串 + 对齐填充"的总长。这种"定长结构 + 尾随变长字符串、用偏移指过去"的设计，在 Mach-O 里被 `LC_RPATH`、`LC_ID_DYLINKER`、`LC_SUB_*` 等所有"带路径"的命令共用。

> [!note] 为什么用偏移而不用指针
> 文件是要被 `mmap` 到任意地址的，存绝对指针没有意义；存"相对命令起点的偏移"则与加载地址无关、自包含。`lc_str` 的 union 形式只是为了让同一份头文件在 32 位运行时能临时复用 `ptr` 视图，落到磁盘上的 Mach-O 里一律是 `offset`。

### 3. 版本号编码：X.Y.Z → 32 位（16.8.8）与兼容性检查

`current_version` 与 `compatibility_version` 都是 `uint32_t`，把点分版本 `X.Y.Z` 打包进 32 位。Apple `loader.h` 的注释写作 **"`X.Y.Z` is encoded in nibbles `xxxx.yy.zz`"**，准确的位划分是 **16 . 8 . 8**：

| 段 | 位区间 | 宽度 | 取值范围 |
|---|---|---|---|
| **X**（major，主版本） | bit 31–16（高 16 位 `xxxx`） | 16 位 | 0–65535 |
| **Y**（minor，次版本） | bit 15–8（中 8 位 `yy`） | 8 位 | 0–255 |
| **Z**（patch，修订） | bit 7–0（低 8 位 `zz`） | 8 位 | 0–255 |

即 `value = (X << 16) | (Y << 8) | Z`；反解 `X = value >> 16`、`Y = (value >> 8) & 0xff`、`Z = value & 0xff`。

举例：`otool -L` 打印的 `current version 1238.60.2`，对应 32 位整数 `(1238<<16)|(60<<8)|2 = 0x04D63C02`；`1.0.0` 即 `0x00010000`。

> [!note] 同一套 16.8.8 编码的"亲戚"
> 这套打包方式还被 `LC_BUILD_VERSION` 的 `minos`/`sdk`、以及 `LC_VERSION_MIN_*` 命令复用。但别和 `LC_SOURCE_VERSION` 混了——后者用的是 **64 位 a24.b10.c10.d10.e10**（`A.B.C.D.E`）的不同打包，位宽完全不同。

**兼容性检查规则（`dyld` 在加载期执行）：**

1. 链接期，`ld` 把被链接库的 `compatibility_version` 与 `current_version` **从对方的 `LC_ID_DYLIB` 抄进**本镜像的 `LC_LOAD_DYLIB`。
2. 运行期，`dyld` 按 `name` 找到磁盘上**实际的**库文件，读出它当前的 `compatibility_version`。
3. **判定**：若"实际库的 `compatibility_version`" **<** "镜像里记录的 `compatibility_version`"，则认为实际库太旧、缺少程序所需的接口，**拒绝加载并报错**（典型 `Incompatible library version: ... requires version X.Y.Z or later, but ... provides version A.B.C`）。否则放行。
4. `current_version` **不参与上述判定**，纯信息性——它告诉程序"你现在用到的库是哪个版本"，供 `NSVersionOfRunTimeLibrary()` 之类查询。

> [!note] compatibility_version 的语义约定
> 直觉记法："`compatibility_version` 是库作者承诺的**最低兼容基线**"。库每次发布**只增不减**地维护这个数：仅当做出**破坏二进制兼容（ABI break）** 的改动时才抬高 `compatibility_version`；纯新增/修 bug 只动 `current_version`。这样老程序（记录了较低的 compat 值）能继续在新库上跑（新库 compat ≥ 老程序要求），而一旦库 ABI 真的断了、compat 抬高，老程序就会被 `dyld` 挡下，避免带病运行。

### 4. 路径占位符：`@rpath` / `@executable_path` / `@loader_path`

install name 常以 `@` 占位符开头，`dyld` 在运行时按规则替换后再去文件系统找库。三者各有适用场景：

| 占位符 | 解析为 | 谁来确定 | 典型用途 |
|---|---|---|---|
| `@executable_path/…` | **主可执行文件**所在目录 | `dyld` 直接替换 | 库始终随**主程序**一起分发、相对主程序固定布局（如 `App.app/Contents/Frameworks`） |
| `@loader_path/…` | **正在加载它的那个镜像**所在目录（可能是某个 dylib，不一定是主程序） | `dyld` 直接替换 | 库可能被**多处复用**、希望相对"引用它的人"定位（插件、可被任意 app 嵌入的 framework） |
| `@rpath/…` | 由 `LC_RPATH` 提供的**一组搜索路径**逐个替换、命中即止 | 需配合 `LC_RPATH`（见下） | **最灵活、最推荐**：库的 install name 固定写 `@rpath/lib.dylib`，把"到底在哪"的决定权留给使用方的 rpath 列表 |

**`@executable_path` vs `@loader_path` 的关键区别**：假设 `libA.dylib` 加载 `libB.dylib`，而 `libB` 又去加载 `libC.dylib`。解析 `libC` 里的 `@loader_path` 时，它指向**加载者 `libB` 所在目录**（不是主程序、也不是 `libA`）；而 `@executable_path` 永远指向**主可执行文件目录**，与是谁加载它无关。所以希望"库挨着引用它的镜像放"用 `@loader_path`，希望"库挨着主程序放"用 `@executable_path`。

**`@rpath` 与 `LC_RPATH` 的配合**：`@rpath` 本身对 `dyld` **没有固定含义**，它是一层间接。`dyld` 加载某镜像时，会扫描该镜像里的所有 `LC_RPATH` 命令，把每条提供的目录依次加进一张**运行时搜索路径列表（run path list）**。当遇到一个 `@rpath/foo.dylib` 形式的依赖时，`dyld` 就用列表里的目录**逐个替换** `@rpath` 去试，第一个存在的即采用。`LC_RPATH` 提供的路径本身也可以再含 `@executable_path`/`@loader_path`（如 `@executable_path/../Frameworks`），形成"先相对主程序、再拼库名"的两段式解析。可以有多条 `LC_RPATH`，`dyld` 按出现顺序尝试。

> [!warning] 受限二进制会忽略 `@` 路径
> 对 SUID/SGID、带 Hardened Runtime 限制、或受 SIP 保护的"受限程序（restricted）"，`dyld` 会**忽略**通过 `@rpath`/`@executable_path`/`@loader_path` 解析的加载，并打印类似 `dyld: warning, LC_RPATH @executable_path/../Frameworks being ignored in restricted program because of @executable_path` 的告警，同时也忽略 `DYLD_*` 环境变量。这是一项安全策略——逆向/部署时若"@ 路径在普通程序里好用、在受限程序里失效"，根因常在此。

> [!note] 调试占位符解析的环境变量
> `DYLD_PRINT_LIBRARIES`（打印实际加载了哪些库及其最终路径）、`DYLD_PRINT_RPATHS`（打印 `@rpath` 的每一步替换尝试）、`DYLD_LIBRARY_PATH` / `DYLD_FALLBACK_LIBRARY_PATH`（覆盖/兜底搜索路径）。注意受限程序会忽略这些变量；`DYLD_FALLBACK_LIBRARY_PATH` 默认含 `/usr/local/lib:/usr/lib`，会让"本不在 rpath 里、却恰好装在 `/usr/local/lib`"的库也能加载，排查"为什么换台机器就找不到"时要留意。

### 5. 五种 dylib 加载命令变体对比

`dylib_command` 这一个结构，被六个 `cmd` 值复用（含库自身的 `LC_ID_DYLIB`）。这里聚焦五种**加载**变体的差异。注意其中四个带 `LC_REQ_DYLD`（`0x80000000`）高位——这是"OS X 10.1 之后新增、且 `dyld` **必须理解**才能正确执行该镜像"的标记；`dyld` 遇到带此位却不认识的命令会直接报错拒载，而不带此位的未知命令会被忽略。

| 命令 | `cmd` 定义 | 解析值 | 带 `LC_REQ_DYLD`? | 语义 |
|---|---|---|---|---|
| `LC_LOAD_DYLIB` | `0xc` | `0x0000000C` | 否 | **强依赖**：库必须在运行时被加载，找不到则启动即崩溃（`dyld: Library not loaded`） |
| `LC_LOAD_WEAK_DYLIB` | `0x18 \| LC_REQ_DYLD` | `0x80000018` | 是 | **弱依赖**：库缺失不报错、不崩溃；其所有导入符号按"弱符号"处理，缺失时取址为 `NULL`，调用前需判空（可选 framework、向后兼容新 API） |
| `LC_REEXPORT_DYLIB` | `0x1f \| LC_REQ_DYLD` | `0x8000001F` | 是 | **再导出**：本库加载目标库，并把目标库的符号**当作自己的对外导出**。用于 umbrella/façade 库（如系统库把子库符号统一对外），让链接方只依赖一个"伞库"即可拿到底层符号 |
| `LC_LOAD_UPWARD_DYLIB` | `0x23 \| LC_REQ_DYLD` | `0x80000023` | 是 | **向上依赖**：标记一条"反方向"的依赖边，用于打破/表达**循环依赖**（A 依赖 B、B 又向上依赖 A），帮助 `dyld` 正确排定初始化顺序 |
| `LC_LAZY_LOAD_DYLIB` | `0x20` | `0x00000020` | **否** | **惰性加载**：把库的加载推迟到**首次使用**时才进行。因为"非必需即可执行"，所以**特意不带** `LC_REQ_DYLD`——旧 `dyld` 不认识它时安全忽略即可 |

> [!note] 为什么唯独 `LC_LAZY_LOAD_DYLIB` 不带 `LC_REQ_DYLD`
> `LC_REQ_DYLD` 的语义是"这条命令对正确执行是**必需**的，不懂就别加载这个镜像"。WEAK / REEXPORT / UPWARD 都改变了 `dyld` 的链接/初始化行为，漏掉会导致错误结果，故必须让 `dyld` 理解（带 REQ 位）。而"惰性加载"按定义就是**可有可无**——退化成普通加载或干脆忽略都不破坏正确性，因此安全地不带 REQ 位，允许老 `dyld` 直接跳过。

### 6. 两级命名空间下的库序号（library ordinal）

现代 Mach-O 默认开启**两级命名空间**（链接器默认行为，Header 里 `MH_TWOLEVEL` 标志置位）。"两级"指：定位一个外部符号时，**第一级是它所属的库、第二级才是符号名**。这要求每个未定义符号都记下"我来自哪个库"——靠的就是**库序号**，它把符号绑回某一条具体的 `LC_LOAD_DYLIB`：

- 所有 `LC_LOAD_DYLIB`（含 WEAK/REEXPORT/UPWARD 变体）**按在文件中出现的先后**构成一个**有序列表**，最早出现的排第 1。
- 每个未定义符号在符号表 `nlist` 项的 **`n_desc` 字段的高 8 位**存一个库序号，用宏 `GET_LIBRARY_ORDINAL(n_desc)` 读、`SET_LIBRARY_ORDINAL` 写。
- 该序号即"上面那个有序列表的 1-based 下标"——`dyld` 据此知道这个符号该去**第几条 `LC_LOAD_DYLIB` 指向的库**里找，从而精确解析、避免不同库里同名符号撞车。

**保留序号值：**

| 序号值 | 名称 | 含义 |
|---|---|---|
| `0x00` | `SELF_LIBRARY_ORDINAL` | 符号在**当前镜像自身**定义 |
| `0x01`–`0xfd`（1–253） | （普通序号） | 按文件中 `LC_LOAD_DYLIB` 出现顺序的库编号（第 1～253 个依赖） |
| `0xfe`（254） | `DYNAMIC_LOOKUP_ORDINAL` | **运行时动态查找**（flat 风格地全局搜，OS X 10.3+ 支持） |
| `0xff`（255） | `EXECUTABLE_ORDINAL` | 符号在**主可执行程序**里定义（插件回链宿主程序符号的场景） |

> [!warning] 改库顺序 = 改符号绑定
> 因为库序号是"按 `LC_LOAD_DYLIB` 文件顺序"的下标，**任何增删/重排 `LC_LOAD_DYLIB` 的操作，都会让既有的库序号集体错位**——除非同步修正所有未定义符号 `n_desc` 里的序号。这就是为什么用 LIEF/手工改 Mach-O 时，"插入一条依赖命令"若不重算序号，会把符号绑到错误的库、产出"看似合法实则坏掉"的二进制。现代链式 fixups（chained fixups）下，库序号则编码在 bind 操作码里（`0x1X` 设置序号、超过 15 用 LEB128），原理一致。详见 [[06.Mach-O LC_DYSYMTAB]] 与 [[17.Mach-O LC_DYLD_INFO_ONLY]]。

### 7. `cmdsize` 与命令遍历

`LC_LOAD_DYLIB` 复用所有加载命令的统一头 `load_command{ cmd, cmdsize }`（见 [[03.Mach-O加载命令]]）。与定长的段命令不同，它的 `cmdsize` **是变长的**：

- `cmdsize = sizeof(dylib_command) + strlen(name) + 1`，再**向指针大小（64 位为 8 字节）向上取整**（尾部补 `\0`）。固定头本身 24 字节，所以 `cmdsize` 总是 ≥ 32 且为 8 的倍数。
- 遍历 Load Commands 时靠累加 `cmdsize` 逐条跳转；安装名字符串的长度已包含在 `cmdsize` 里，所以 `ptr += cmdsize` 会自动跳过这条命令尾随的整串路径，不会把路径字节误当成下一条命令。
- 健壮解析器需校验：`name.offset` 落在 `[8, cmdsize)` 内、字符串在 `cmdsize` 边界内有 `\0` 终止——否则属畸形/构造攻击输入。

## 实操：用工具查看

### 示例 1：`otool -L` 列出所有依赖库

`-L` 把本镜像的依赖（以及它自己的 ID，若是 dylib）连同各自的版本一并列出：

```bash
otool -L /bin/ls          # 列出 /bin/ls 依赖的所有动态库及版本
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
/bin/ls:
	/usr/lib/libutil.dylib (compatibility version 1.0.0, current version 1.0.0)
	/usr/lib/libncurses.5.4.dylib (compatibility version 5.4.0, current version 5.4.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1345.0.0)
```

> 说明：每一行对应一条 `LC_LOAD_DYLIB`；括号里的 `compatibility version` 参与 `dyld` 兼容性判定、`current version` 仅信息性。`libSystem.B.dylib` 用绝对路径作 install name（系统库惯例）。

### 示例 2：`otool -l` 看单条命令原始字段

```bash
otool -l /bin/ls | grep -A 5 LC_LOAD_DYLIB   # 看每条依赖命令的原始字段
otool -l /path/to/lib.dylib | grep -A 4 LC_ID_DYLIB   # 看某库自己的安装名与版本
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意字段形态。

```text
Load command 12
          cmd LC_LOAD_DYLIB
      cmdsize 56                         ; 24 + 路径长 + 对齐填充
         name /usr/lib/libSystem.B.dylib (offset 24)   ; name.offset=24
   time stamp 2 Thu Jan  1 08:00:02 1970 ; timestamp
      current version 1345.0.0           ; 0x05410000
compatibility version 1.0.0              ; 0x00010000
```

```text
Load command 4
          cmd LC_ID_DYLIB                ; 这是“某库声明自己是谁”
      cmdsize 48
         name @rpath/libWaffle.dylib (offset 24)
   time stamp 1 Thu Jan  1 08:00:01 1970
      current version 58.111.101         ; 0x003a6f65
compatibility version 58.0.0             ; 0x003a0000
```

> 说明：`name ... (offset 24)` 印证安装名字符串从命令起点偏移 24（紧跟 24 字节固定头）；`current version 58.111.101` 即 `(58<<16)|(111<<8)|101`。对照看 `LC_ID_DYLIB`（库声明自身）与 `LC_LOAD_DYLIB`（使用方记录依赖）字段一模一样，正是"同一个 `dylib_command` 结构"。

### 示例 3：`otool -l ... | grep LC_RPATH` 看运行时搜索路径

`@rpath` 要靠 `LC_RPATH` 落地，单独查它：

```bash
otool -l /path/to/App | grep -A 2 LC_RPATH
```

> [!warning] 示例输出为示意

```text
          cmd LC_RPATH
      cmdsize 40
         path @executable_path/../Frameworks (offset 12)
          cmd LC_RPATH
      cmdsize 32
         path @loader_path/Libraries (offset 12)
```

> 说明：两条 `LC_RPATH` 给出两个候选目录；遇到 `@rpath/Foo.framework/Foo` 时，`dyld` 先试 `<主程序目录>/../Frameworks/Foo.framework/Foo`，不存在再试 `<加载者目录>/Libraries/...`，命中即止。`LC_RPATH` 也复用"固定头 + 偏移式字符串"布局（`path` 从偏移 12 起）。

### 示例 4：`install_name_tool` 改路径/版本

`install_name_tool` 用来在**编译之后**修改这些内嵌路径——这是解决"dylib 挪了位置/想改用 @rpath/部署时重定位"的标准手段：

```bash
# (1) 改某库自身的 install name（写进它的 LC_ID_DYLIB）
install_name_tool -id @rpath/libfoo.dylib  libfoo.dylib

# (2) 改“使用方”记录的某条依赖路径：把旧路径换成新路径（改对应 LC_LOAD_DYLIB.name）
install_name_tool -change /old/abs/path/libfoo.dylib  @rpath/libfoo.dylib  myExecutable

# (3) 增 / 删 / 改运行时搜索路径（操作 LC_RPATH）
install_name_tool -add_rpath    @executable_path/../Frameworks  myExecutable
install_name_tool -delete_rpath @executable_path/../Frameworks  myExecutable
install_name_tool -rpath        /old/rpath  /new/rpath          myExecutable
```

> [!warning] 示例输出为示意
> 下面演示"改前→改后"用 `otool -L` 观察依赖路径变化，数值为构造。

```text
# 改前：依赖写的是一个写死的绝对路径，换台机器就找不到
% otool -L myExecutable
	/Users/ci/build/libfoo.dylib (compatibility version 1.0.0, current version 1.0.0)

% install_name_tool -change /Users/ci/build/libfoo.dylib @rpath/libfoo.dylib myExecutable
% install_name_tool -add_rpath @executable_path/../Frameworks myExecutable

# 改后：依赖变为 @rpath 形式，配合新增的 LC_RPATH 即可相对主程序定位
% otool -L myExecutable
	@rpath/libfoo.dylib (compatibility version 1.0.0, current version 1.0.0)
```

> 说明：`-change` 改的是**依赖方** `LC_LOAD_DYLIB` 里记录的对方路径；`-id` 改的是**库自己** `LC_ID_DYLIB` 里声明的安装名。要让 `@rpath` 真正生效，"提供方"必须把 install name 设成 `@rpath/...`（macOS 特有的"使用方继承提供方 install name"机制），并由"使用方"用 `LC_RPATH` 给出搜索目录——两边缺一不可。改版本号则用 `ld` 的 `-current_version`/`-compatibility_version`（`install_name_tool` 不改版本字段）。

## FAQ

> [!question] `LC_LOAD_DYLIB` 和 `LC_ID_DYLIB` 到底什么关系？为什么字段长得一模一样？
> 它们**共用同一个 `dylib_command` 结构**，只是 `cmd` 值不同、放置位置和方向相反。`LC_ID_DYLIB`（`0xd`）只出现在动态库（`MH_DYLIB`）里、**每库至多一条**，是库"声明自己的 install name 与版本"——"我是谁、来找我请用这个路径"。`LC_LOAD_DYLIB`（`0xc`）出现在**使用方**（可执行文件或另一个库）里、**每依赖一条**，是"我要加载这个库"。链接期 `ld` 把被链接库 `LC_ID_DYLIB` 里的 `dylib` 字段（路径 + 两个版本号）**整体抄进**使用方的 `LC_LOAD_DYLIB`。所以两边字段相同不是巧合，而是"抄写"的结果；运行时 `dyld` 拿使用方记录的值，去和磁盘上实际库的 `LC_ID_DYLIB` 值比对做兼容性检查。详见 [[08.Mach-O LC_ID_DYLIB]]。

> [!question] `compatibility_version` 和 `current_version` 有什么区别？哪个会导致加载失败？
> 只有 **`compatibility_version` 参与加载失败判定**。规则：运行时实际库的 `compatibility_version` **若低于**程序里记录的值，`dyld` 判定库太旧、拒绝加载（报 `Incompatible library version`）；等于或更高则放行。`current_version` 纯信息性、**永不导致失败**，仅供 `NSVersionOfRunTimeLibrary()` 之类查询"我现在用的是哪个版本"。约定上库作者**只在做 ABI 破坏性改动时才抬高 `compatibility_version`**、平时新增/修 bug 只动 `current_version`——这样老程序能在更新的库上继续跑，库一旦真的不兼容才会被挡下。

> [!question] `@rpath`、`@executable_path`、`@loader_path` 三者怎么选？
> 看"库相对谁固定"。库始终随主程序一起、布局相对**主程序**固定 → `@executable_path`；库希望相对**引用它的那个镜像**（可能是别的 dylib、插件被任意宿主嵌入）→ `@loader_path`；想把"到底在哪"的决定权交给使用方、install name 保持不变最灵活 → `@rpath`（最推荐，但需使用方用 `LC_RPATH` 提供搜索目录配合）。一个口诀：**`@executable_path` 锚主程序、`@loader_path` 锚加载者、`@rpath` 锚一张可配置的搜索表**。注意受限程序（SUID/SIP/Hardened）会忽略这三种 `@` 路径，只认绝对路径。

> [!question] 我把 dylib 文件移到别处，程序就报 `dyld: Library not loaded ... image not found`，怎么回事？
> 因为依赖路径是**链接时就抄死在 `LC_LOAD_DYLIB.name` 里的 install name**，不是"文件现在的真实位置"。挪动文件不会自动更新程序里记录的路径，程序仍按旧路径找、自然找不到。三种修法：①给库一个 `@rpath/...` 的 install name（`install_name_tool -id @rpath/libfoo.dylib libfoo.dylib`），再给程序加 `LC_RPATH`（`-add_rpath`）指向库的新目录；②直接把程序里那条依赖改成新绝对路径（`install_name_tool -change 旧路径 新路径 程序`）；③临时调试可设 `DYLD_LIBRARY_PATH`（但受限程序无效）。用 `DYLD_PRINT_LIBRARIES=1 DYLD_PRINT_RPATHS=1` 跑一遍能看到 `dyld` 实际试了哪些路径，最利于定位。

## 小结

- `LC_LOAD_DYLIB`（`0xc`）用 `dylib_command` + 内嵌 `struct dylib` 记录一个强依赖库的**安装名（install name）**、**时间戳**与**两个版本号**，每依赖一条；与库自身的 `LC_ID_DYLIB`（`0xd`）复用同一结构、配对使用。
- `name` 是 `union lc_str`（偏移式字符串），真正的路径**紧跟固定头之后**、用"相对命令起点的偏移"（通常 24）指过去，故 `cmdsize` 变长且向指针大小对齐。
- 版本号把 `X.Y.Z` 打包进 32 位（**高 16 位 X、中 8 位 Y、低 8 位 Z**）；`dyld` 仅当"实际库 `compatibility_version` < 记录值"时判不兼容、加载失败，`current_version` 仅信息性。
- `@executable_path`（锚主程序）/ `@loader_path`（锚加载者）/ `@rpath`（锚 `LC_RPATH` 提供的搜索表）决定运行时库搜索位置；受限程序忽略这三种 `@` 路径与 `DYLD_*` 环境变量。
- 五种变体复用 `dylib_command`：`LOAD`(0xc) / `WEAK`(0x18|REQ) / `REEXPORT`(0x1f|REQ) / `UPWARD`(0x23|REQ) / `LAZY`(0x20，**唯一不带** `LC_REQ_DYLD`)。
- 两级命名空间下，未定义符号用 `n_desc` 高 8 位的**库序号**（`GET_LIBRARY_ORDINAL`，1–253 为文件序，0/254/255 为 SELF/动态查找/可执行）绑回具体某条 `LC_LOAD_DYLIB`；改命令顺序会破坏绑定。
- 排障用 `otool -L`（列依赖+版本）/ `otool -l`（看原始字段）/ `otool -l | grep LC_RPATH`（看搜索路径）；改路径用 `install_name_tool -id`/`-change`/`-add_rpath`。
