# 详解Mach-O(三十四)Mach-O __cfstring节

> [!abstract] TL;DR
> **`__cfstring` 存放的是编译期就生成好的常量字符串"对象"，不是字符本身**——它装的是源码里每一个 ObjC 字面量 `@"..."`（以及 C 层的 `CFSTR("...")`）对应的常量 `CFString`/`NSString` 对象头。
> 每个对象是一个**四字段定长结构体**：`isa`（指向常量串类 `___CFConstantStringClassReference`）、`flags`（编码标志，ASCII 串常见 `0x7C8`、UTF-16 串常见 `0x7D0`）、`data`（指回 [[20.Mach-O __cstring节]] 里那串真正的字符）、`length`（字符个数，不含结尾 `\0`）。64 位下整体 **32 字节**（4 个机器字，含 `flags` 后的 4 字节填充）。
> 正因为对象头在加载时就已成形、`isa` 已指向字符串类，`@"hello"` 才能**不经运行时 `alloc/init` 分配**就直接当 `NSString *` / `CFStringRef` 用（取 `length`、调方法、做参数）。字符在 `__cstring`（`__TEXT`，只读字节），对象头在 `__cfstring`——一份字符可被一个常量对象引用。
> 因为结构体里有 `isa`/`data` 两个指针需要加载期定位，本节历史上落在可写的 [[14.Mach-O __DATA]]；**现代 arm64 已迁入只读的 [[15.Mach-O __DATA_CONST]]**（arm64e 上更进一步是 `__AUTH_CONST`），指针以链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）形式存放、arm64e 还带指针认证（PAC）签名位。

## 概述与定位

ObjC/Swift 代码里随处可见的 `@"..."` 字面量，要能当**对象**用——调 `[str length]`、`[arr addObject:@"x"]`、`NSLog(@"%@", s)`——就必须有一个符合 `CFString`/`NSString` 内存布局的实例存在。如果每次执行到字面量都去堆上 `alloc/init`，既慢又浪费。Apple 的做法是：**在编译期就把这个对象"预制"好，连同程序一起写进二进制**，加载后直接可用。这个"预制对象的存放处"就是 `__cfstring` 节。

这里有一个常被误解的点，务必先理清楚——**`__cfstring` 里没有字符**：

- **字符本身**（`hello` 这串字节、以 `\0` 结尾）住在 [[20.Mach-O __cstring节]]（属于只读的 `__TEXT` 段，是 `S_CSTRING_LITERALS` 类型的 C 字符串池）。
- **把字符"包装成对象"的那层结构体**（对象头：`isa`/`flags`/`data`/`length`）才住在 `__cfstring`，它的 `data` 字段是一个**指回 `__cstring` 的指针**。

可以这样类比：`__cstring` 是仓库里的原料（裸字节），`__cfstring` 是贴了标签、装了把手、能直接上货架卖的成品包装盒——盒子里并不重新装一份原料，只是用一个指针指向仓库里那份。于是同一份字符既能被 C 代码当 `const char *` 直接用（直接读 `__cstring`），也能被 ObjC 代码当 `NSString *` 用（经由 `__cfstring` 的对象头）。

> [!note] `__cfstring` 与 `__cstring` 是两个节，别混为一谈
> 名字只差一个 `f`，作用却正交：`__cstring`（见 [[20.Mach-O __cstring节]]）= **C 字符串字面量池**，存的是 `"hello\0"` 这种裸字节，类型 `S_CSTRING_LITERALS`，在 `__TEXT`；`__cfstring` = **常量 `CFString`/`NSString` 对象池**，存的是对象头结构体，类型是普通 `S_REGULAR`，历史在 `__DATA`、现代在 `__DATA_CONST`。本篇所有"字符内容"都指向前者，本篇主体讲的是后者。节名总写作 `段名,节名`（如 `__DATA_CONST,__cfstring`），原因见 [[18.Mach-O section]] 里"节名总要带段名"一节。

它的宿主段之所以是 `__DATA` 家族而非 `__TEXT`，根因在于结构体里的 `isa` 与 `data` 是**指针**：`isa` 要在加载时绑定到 CoreFoundation 导出的类符号、`data` 要 rebase 到本镜像内 `__cstring` 的实际地址（开了 ASLR 后地址不固定）。带"加载期要被改写的指针"的数据不能放进纯只读、纯共享的 `__TEXT`，所以它落在 `__DATA`／（现代）`__DATA_CONST`。本节是 [[18.Mach-O section]] 通用模型在"ObjC/CF 常量对象"上的一个具体实例：节类型是普通 `S_REGULAR`，特殊之处全在它承载的那套固定结构体语义。

## 核心原理与字段详解

### 1. 常量字符串对象结构（四字段，64 位约 32 字节）

每个 `@"..."` / `CFSTR("...")` 在 `__cfstring` 里对应**一个定长结构体**。它在 LLVM 内部叫 `__NSConstantString_tag`，IR 类型记作 `{ i32*, i32, i8*, i64 }`，发射到 `section "__DATA,__cfstring", align 8`。概念上的 C 形态：

```c
struct cfstring_object {           // 编译器预制的常量 CFString/NSString 对象头
    uintptr_t isa;     // +0x00  指向 ___CFConstantStringClassReference（常量串类）
    uint32_t  flags;   // +0x08  编码/不可变标志：ASCII 串常见 0x7C8、UTF-16 串常见 0x7D0
                       //        （其后有 4 字节填充，使下一个指针字段 8 字节对齐）
    uintptr_t data;    // +0x10  指向 __cstring 中实际字符的指针（C 字符串首字节）
    uintptr_t length;  // +0x18  字符串长度（字符个数，不含结尾 \0；类型 CFIndex）
};
```

注意 `flags` **本身是 32 位**（一个 `uint32_t`），但因为它后面的 `data` 是 8 字节指针、必须 8 字节对齐，所以 `flags` 与 `data` 之间塞了 **4 字节填充**——这正是"4 个字段却占 32 字节"（而不是 4×4=16 或 4×8=32 里 `flags` 占满 8 字节）的来历：`isa`(8) + `flags`(4) + 填充(4) + `data`(8) + `length`(8) = **32 字节**。

编译器实际发射的汇编（64 位）逐字段印证这一布局：

```asm
        .section __DATA,__cfstring
        .p2align 3                       ; 2^3 = 8 字节对齐
L__unnamed_cfstring_:
        .quad   ___CFConstantStringClassReference   ; isa（指向常量串类）
        .long   1992                                ; flags = 0x7C8（ASCII 8 位串）
        .space  4                                   ; 4 字节填充，对齐到 8
        .quad   L_.str                              ; data → __cstring 里的 "hello"
        .quad   5                                   ; length = 5
```

字段精确偏移（64 位，共 **32 字节**）：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0x00 | `isa` | uintptr_t | 8 | 指向 `___CFConstantStringClassReference` |
| 0x08 | `flags` | uint32_t | 4 | 编码/不可变标志（`0x7C8` / `0x7D0` …） |
| 0x0C | （填充） | — | 4 | 对齐填充，使 `data` 落在 8 字节边界 |
| 0x10 | `data` | uintptr_t | 8 | 指向 `__cstring` 实际字符 |
| 0x18 | `length` | uintptr_t | 8 | 字符个数（不含 `\0`） |

> [!note] `CFSTR("...")` 与 `@"..."` 殊途同归
> ObjC 的 `@"..."` 与 C/CF 的 `CFSTR("...")` 最终都走同一个编译器内建函数生成上面的结构体。开了 `__CONSTANT_CFSTRINGS__` 时，`CFSTR(cStr)` 展开为 `((CFStringRef) __builtin___CFStringMakeConstantString("" cStr ""))`——这个 `__builtin___CFStringMakeConstantString` 就是把字面量"铸成"那 32 字节常量对象、并把字符塞进 `__cstring` 的幕后机器。所以无论你写 ObjC 字面量还是 CF 宏，落到二进制里都是 `__cfstring` 里一个同样布局的对象头。

### 2. 为什么要在字符外面"包一层对象"

C 字符串（`__cstring` 里的裸字节）只是一段 `char`，**它不知道自己有多长（要靠 `strlen` 现算）、更不是任何类的实例**，没法直接 `[str length]` 或丢给收 `id`/`NSString *` 的接口。`__cfstring` 做的事就是把这段裸字节"裱"成一个符合 `CFString`/`NSString` 运行时内存布局的对象：

- **`isa` 让它"有类"**：运行时通过对象首字段（isa）识别其类型。`isa` 指向 `___CFConstantStringClassReference`，于是这个内存块被当作字符串类实例对待，方法派发、`isKindOfClass:`、toll-free bridging（`NSString` ↔ `CFStringRef` 免费桥接）都能正常工作。
- **`flags`/`data`/`length` 描述内容**：`length` 让 `[s length]` 不必扫描即得（O(1)）、`data` 指明字符在哪、`flags` 说明字符怎么编码（8 位还是 UTF-16）。

结果就是：`@"hello"` 在加载完成的那一刻**已经是一个现成、可用、不可变的字符串对象**，引用计数视为"永生"（常量对象不参与真正的 retain/release，release 是 no-op）。这就是为什么 ObjC 字面量看起来"凭空就能当对象用"——它不是凭空，而是编译期预制、加载期定位好指针后摆在那里等你用。

### 3. `isa` 字段与 `___CFConstantStringClassReference`

`isa` 指向的 `___CFConstantStringClassReference` 是 **CoreFoundation.framework 导出的一个符号**，编译器会在每个 ObjC/ObjC++ 翻译单元里隐式声明它。结构体里 `isa` 在编译期被设成"指向该符号"的形态，链接/加载期再把它绑定到 CoreFoundation 中真正的常量串类对象上。

这是一份**稳定 ABI**：你的二进制可能在任意版本的 CoreFoundation 上运行，所以这个结构体布局和 `isa` 的语义必须长期不变。逆向时，反汇编器看到 `__cfstring` 条目首字段是一个指向 `___CFConstantStringClassReference` 的重定位/绑定，就能据此识别"这是一个常量字符串对象"。

> [!warning] 现代系统要求 `isa` 非零（Sonoma 起更严）
> 历史上 CoreFoundation 容忍 `isa` 为 0（一些非 Apple 的 CF 实现如 GNUstep 的 `CONST_STRING_DECL()` 就把 isa 置 NULL），早期系统照样能跑。但**自 macOS Sonoma 起，CF 校验更严：isa 为零会崩溃**，报错形如 `CF objects must have a non-zero isa`（出现在 `CF_IS_OBJC.cold.1`）。这影响的是那些没正确填 isa 的第三方/转译产物；正常 clang ObjC 编译出的 `__cfstring` 一直是填好 `___CFConstantStringClassReference` 的，不受影响。逆向遇到这类崩溃，优先怀疑某个常量串对象的 isa 没被正确绑定。

### 4. `flags` 编码：`0x7C8`（ASCII）与 `0x7D0`（UTF-16）

`flags` 是 `CFString` 运行时信息位（info bits）的编译期快照，**关键看它的低字节**——它决定字符以何种形式存放：

| `flags` 值 | 低字节 | 含义（字符存储形式） | 何时出现 |
|---|---|---|---|
| `0x7C8`（十进制 1992） | `0xC8` | **8 位 / ASCII**：每字符 1 字节，带结尾 `\0`，无长度字节，不可变 | 字面量**全为 7 位 ASCII** 字符时 |
| `0x7D0`（十进制 2000） | `0xD0` | **Unicode / UTF-16**：每字符 16 位 `UniChar`，不可变 | 字面量**含非 ASCII**（码点 > 127）字符时 |

低字节按 Apple CoreFoundation 源码（`CFString.c`）里的位定义拆解，相关位的字母含义是：`I` = 不可变(immutable)、`E` = 内容不内联(not inline，即字符存在别处、靠指针引用)、`U` = 是 Unicode、`N` = 有结尾 `\0`(has NULL byte)、`L` = 有长度字节(has length byte)、`D` = 内容有显式释放器、`C` = 长度字段是 `CFIndex`。两种常量模式都设了 `I`(不可变) 和 `E`(不内联，对应我们 `data` 指向外部 `__cstring`)；区别在于 **ASCII 模式额外设 `N`（有 `\0`）**，而 **UTF-16 模式改设 `U`（是 Unicode）**。

选哪种是**编译期决定**的：编译器扫描字面量，若**每个字符都是 7 位 ASCII**就发紧凑的 8 位形式（`0xC8`），只要**有一个字符需要 7 位以上**就整体转成 UTF-16 并发 `0xD0`。

> [!warning] 不要硬编码 `flags == 0x7C8`
> `0x7C8` 只是"全 ASCII 串"的常见值，含中文/emoji 等的字面量会是 `0x7D0`（UTF-16），且**具体位含义可能随 CoreFoundation 版本微调**。解析 `__cfstring` 时应**读 `flags` 低字节判断编码**（`0xC8`→按 8 位读、`0xD0`→按 UTF-16 读 `length` 个 `UniChar`），而不是写死等于某个常量。Apple 文档亦提醒：`CFSTR`/`@""` 里放非 ASCII（码点 > 127）历史上行为未定义——即便当下能跑，换语言环境/不同工具链可能出问题，工程上常量串尽量保持纯 ASCII。

### 5. `data` 指回 `__cstring`，`length` 给出长度

`data` 是一个指针，指向 [[20.Mach-O __cstring节]] 里这条字符串的首字节（`__TEXT,__cstring` 中那段 `\0` 结尾的裸字节）。`length` 则是这条字符串的**字符个数**（不含结尾 `\0`）。这一对 `data + length` 就是"对象内容"的全部描述：

- 取内容：从 `data` 指向处读 `length` 个单元（ASCII 串每单元 1 字节、UTF-16 串每单元 2 字节，按 `flags` 低字节区分）。
- 这也解释了逆向时常见的"指针 + 长度"配对：反汇编里经常看到先 `lea`/`adrp` 把字符串地址装进寄存器，紧接着一条 `mov` 把**长度立即数**装进另一个寄存器（如 x86-64 上 `lea rdi, [rip+…] ; "invalid licence code"` 后跟 `mov esi, 0x14`，`0x14`=20 正是该串长度）——这两步合起来就是在用 `__cfstring` 对象的 `data` 与 `length`。

`__cstring` 与 `__cfstring` 的分工，一句话：**字符在 `__cstring`、对象头在 `__cfstring`，后者的 `data` 指回前者**。

### 6. 与 `__cstring` 的分工（对照表）

| 维度 | `__cstring`（见 [[20.Mach-O __cstring节]]） | `__cfstring`（本篇） |
|---|---|---|
| 存什么 | C 字符串**裸字节**（`"hello\0"`） | 常量 `CFString`/`NSString` **对象头**结构体 |
| 节类型 | `S_CSTRING_LITERALS`（`0x2`） | 普通 `S_REGULAR`（`0x0`） |
| 宿主段 | `__TEXT`（只读、可共享） | `__DATA` → 现代 `__DATA_CONST` / `__AUTH_CONST` |
| 单元大小 | 不定长（按 `\0` 分隔） | 定长结构体（64 位 32 字节） |
| 含指针否 | 否（纯字节，可去重合并） | **是**（`isa`/`data` 需加载期定位） |
| 谁引用谁 | 被 `__cfstring.data` 指向 | `data` 指回 `__cstring` |
| 对应源码 | C 字面量 `"..."`、ObjC 串的字符部分 | ObjC `@"..."`、`CFSTR("...")` 的对象部分 |

二者配合：**一份字符（`__cstring`）可被一个常量对象（`__cfstring`）引用**；多个相同字面量还能共享同一份字符字节。

### 7. 现代归 `__DATA_CONST`（arm64e 为 `__AUTH_CONST`）与链式 fixups

历史上本节是 `__DATA,__cfstring`（你在老的 / x86_64 二进制里仍会看到它在可写的 `__DATA` 段）。**现代 macOS/iOS 的 arm64 二进制已把它迁出可写段**：

- **普通 arm64**：落在只读的 `__DATA_CONST,__cfstring`（见 [[15.Mach-O __DATA_CONST]]）。
- **arm64e（带指针认证 PAC）**：更进一步落在 `__AUTH_CONST,__cfstring`，与 `__auth_ptr` 等为伍。

之所以能"只读化"，是因为结构体里那两个指针（`isa` 与 `data`）的值在加载期由 **fixups 一次性定下**之后就不再变，故可放进加载后变只读的段，缩小可写数据面、增强安全。但这也带来**逆向/解析上的关键陷阱**：

> [!warning] 现代 arm64 上 `isa`/`data` 在磁盘里不是最终地址
> 现代二进制用**链式 fixups**（`LC_DYLD_CHAINED_FIXUPS`，经 `linkedit_data_command` 引用；macOS 12 以前的旧机制走 `LC_DYLD_INFO`）取代传统重定位。于是 `__cfstring` 磁盘镜像里：`isa` 是一条**绑定（bind）**到 `___CFConstantStringClassReference` 的链式 fixup 项、`data` 是一条**重定位（rebase）**到 `__cstring` 的链式 fixup 项——**都不是可直接解引用的最终虚拟地址**。arm64e 上这些指针还额外携带 **PAC 签名位**。要拿到真实指针，必须**先走一遍 fixup 链**（arm64e 还要剥掉认证位），否则按磁盘里的"裸值"去当地址读 `__cstring` 会读到垃圾。这也是为什么新链接器（ld_prime）对这些常量的 8 字节对齐很严格（曾报 `cfstring constant not pointer aligned`）。

把上面所有要点串起来，**解析 `__cfstring` 的正确流程**是：

1. 定位 `__cfstring` 节（**现代优先查 `__DATA_CONST` / `__AUTH_CONST`，回退查老的 `__DATA`**）。
2. 以 **32 字节步长**逐条遍历，每条是一个 `cfstring_object`。
3. 读 `+0x08` 的 `flags`（低字节定编码）、`+0x18` 的 `length`。
4. 把 `+0x10` 的 `data` 指针**经链式 fixup 解析为真实地址**（arm64e 再剥 PAC），然后按 `flags` 编码从 `__cstring`/`__ustring` 读 `length` 个单元，得到字符串内容。

## 实操：用工具查看

### 示例 1：`otool -s` dump `__cfstring` 节的原始结构体字节

`otool -s 段名 节名` 以十六进制 dump 指定节。注意现代 arm64 二进制要先确认本节落在 `__DATA_CONST`（或 `__AUTH_CONST`）而非 `__DATA`：

```bash
otool -l /path/to/ObjCBinary | grep -A2 cfstring   # 先看 __cfstring 落在哪个段
otool -s __DATA_CONST __cfstring /path/to/ObjCBinary  # 现代 arm64：dump 对象头字节
otool -s __DATA       __cfstring /path/to/ObjCBinary  # 老/ x86_64：在 __DATA
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，地址/数值均为示意，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA_CONST,__cfstring) section
0000000100008000  isa  = &___CFConstantStringClassReference   ; +0x00
0000000100008008  flags= 0x00000000000007c8                   ; +0x08 低字节 0xc8 → 8 位 ASCII 串
0000000100008010  data → 0x0000000100003f00 (__cstring "hello"); +0x10 指回 __cstring
0000000100008018  length= 5                                   ; +0x18 长度 5（不含 \0）
0000000100008020  isa  = &___CFConstantStringClassReference   ; 下一条对象，步长 32 字节
0000000100008028  flags= 0x00000000000007d0                   ; 低字节 0xd0 → UTF-16 串（含非 ASCII）
0000000100008030  data → 0x0000000100003f20 (__ustring …)
0000000100008038  length= 3
```

> 说明：`otool -s` 默认给的是裸十六进制（这里为可读起见把四个机器字标注成了字段含义）。每 **32 字节**一个常量对象；第一条 `flags=0x7C8` 是全 ASCII 串 `hello`、`data` 指回 `__cstring`；第二条 `flags=0x7D0` 表明那是 UTF-16 串（字面量里有非 ASCII 字符）。**现代 arm64 上 `isa`/`data` 在磁盘里其实是链式 fixup 占位，工具已替你解析回符号/目标地址显示**——裸 dump 看到的值未必等于这里的"最终地址"。

### 示例 2：`otool -ov` 看 ObjC/CF 元数据里的常量串

`otool -ov` 打印 64 位 Mach-O 的 ObjC 2.0/CF 元数据（verbose），能把引用到的常量字符串对象与其指向的字符一并解读：

```bash
otool -ov /path/to/ObjCBinary       # 转储 ObjC/CF 元数据（含常量串引用）
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意 `otool -ov` 如何把 `__cfstring` 对象关联到 `___CFConstantStringClassReference` 与 `__cstring` 内容。

```text
Contents of (__DATA_CONST,__cfstring) section
0x100008000
           isa 0x... ___CFConstantStringClassReference
         flags 0x7c8
          data 0x100003f00  "hello"
        length 5
```

> 说明：`-ov` 会把 `isa` 解析成符号名 `___CFConstantStringClassReference`，并顺着 `data` 把 `__cstring` 里的内容 `"hello"` 显示出来，比裸 `-s` 更直观地呈现"对象头 → 字符"的链路。历史上 `otool -ov` 还专门修过"地址 0 处有非零节时把 NULL 指针字段误判为有效数据"的问题，所以遇到 `isa`/`data` 为 0 的异常条目要留神。

### 示例 3：`otool -s __TEXT __cstring` 看 `data` 指向的字符

顺着 `data` 去 `__cstring` 看真正的字符字节（印证"字符在 `__cstring`"）：

```bash
otool -s __TEXT __cstring /path/to/ObjCBinary   # dump 字符池，看到一串以 \0 分隔的 C 串
```

> [!warning] 示例输出为示意
> 地址/字节为构造，仅示意 `__cfstring.data` 指向处的 `__cstring` 内容。

```text
Contents of (__TEXT,__cstring) section
0000000100003f00  68 65 6c 6c 6f 00 25 40 00 6e 61 6d 65 00 00 00   hello.%@.name...
```

> 说明：`0x100003f00` 正是上面示例 1 里第一条 `__cfstring` 对象 `data` 指向的地址，这里就是裸字符 `hello\0`——它本身只是字节、不带类型；是 `__cfstring` 的对象头给它套上了 `isa`/`length`，才让 `@"hello"` 成为可用的 `NSString *`。`__cstring` 的类型是 `S_CSTRING_LITERALS`（详见 [[20.Mach-O __cstring节]]）。

## FAQ

> [!question] `__cfstring` 里到底存的是字符串内容，还是别的东西？
> 存的是**常量字符串"对象头"，不是字符内容**。每个 `@"..."` / `CFSTR("...")` 在这里对应一个 32 字节（64 位）的结构体：`isa`（指向 `___CFConstantStringClassReference`）、`flags`（编码标志）、`data`（指针，指向 [[20.Mach-O __cstring节]] 里那串真正的字符）、`length`（字符个数）。真正的字符字节在 `__cstring`，`__cfstring` 只用 `data` 指过去。换句话说：**字符在 `__cstring`，对象头在 `__cfstring`**。

> [!question] 为什么 `@"hello"` 不用 `alloc/init` 就能当对象用？
> 因为这个对象在**编译期就被预制好、连同程序写进了二进制的 `__cfstring` 节**。加载完成后，它的 `isa` 已绑定到字符串类、`data` 已指向 `__cstring` 的字符、`length` 已填好——它**就是一个现成、不可变、可直接使用的 `NSString`/`CFStringRef` 实例**（视为"永生"对象，retain/release 是 no-op）。所以运行到 `@"hello"` 时不发生任何堆分配，直接拿这个常量对象用即可，`[s length]` 也是 O(1) 直接读 `length` 字段。

> [!question] `flags` 的 `0x7C8` 和 `0x7D0` 是什么意思？能写死判断吗？
> 它们是 `CFString` 信息位的编译期快照，**关键看低字节**：`0x7C8` 低字节 `0xC8` = **8 位/ASCII** 串（每字符 1 字节、带 `\0`、不可变）；`0x7D0` 低字节 `0xD0` = **UTF-16/Unicode** 串（每字符 2 字节、不可变）。编译器按"字面量是否全为 7 位 ASCII"二选一：全 ASCII 发 `0xC8`，含非 ASCII 发 `0xD0`。**不要写死等于 `0x7C8`**——应读低字节判断编码再决定按 1 字节还是 2 字节读 `length` 个字符；具体位义还可能随 CoreFoundation 版本微调。

> [!question] `__cfstring` 在 `__DATA` 还是 `__DATA_CONST`？解析时要注意什么？
> 看时代与架构：**老的 / x86_64 二进制在可写的 `__DATA,__cfstring`；现代 arm64 已迁到只读的 [[15.Mach-O __DATA_CONST]]`,__cfstring`，arm64e 上是 `__AUTH_CONST,__cfstring`**。能只读化是因为 `isa`/`data` 两个指针在加载期由 fixups 定好后就不再变。解析陷阱在于：**现代 arm64 的这两个指针在磁盘里是链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）占位、不是最终地址**，arm64e 还带 PAC 签名位——必须先走 fixup 链解析（arm64e 再剥认证位）才能拿到真实地址去读 `__cstring`，否则会读到垃圾。

> [!question] 它和 `__objc_methname`、`__cstring` 这些字符串相关节是什么关系？
> 都涉及"字符串"，但层次不同：[[20.Mach-O __cstring节]] 是**通用 C 字符串字节池**（`__cfstring` 的 `data` 指向它）；[[24.Mach-O __objc_methname节]] 是 **ObjC 方法选择子名字（SEL 名）的专用字符串池**（供 runtime 注册 selector）；而 `__cfstring` 装的是**带对象头的常量 `CFString`/`NSString`**。一个 ObjC 字面量串会"用到"`__cstring`（存字符）+ `__cfstring`（存对象头）两处；`__objc_methname` 则与方法名有关、不存你写的字面量内容。

## 与相邻章节的关系

- [[20.Mach-O __cstring节]]：本节 `data` 字段指向的目标——真正的字符字节就住在这里；二者是"对象头（`__cfstring`）↔ 字符（`__cstring`）"的引用关系。
- [[14.Mach-O __DATA]]：本节的**历史宿主段**（含 `isa`/`data` 指针，故需可写以便加载期 rebase/bind）。
- [[15.Mach-O __DATA_CONST]]：本节的**现代宿主段**（指针由 fixups 定好后只读化；arm64e 上更进一步是 `__AUTH_CONST`）。
- [[18.Mach-O section]]：通用 `section_64` 模型与 `flags` 类型/属性说明书；`__cfstring` 是其中 `S_REGULAR` 类型的一个实例。
- [[24.Mach-O __objc_methname节]]：ObjC 另一类字符串池（方法名/SEL 名）对照，区分"字面量串对象"与"运行时元数据字符串"。

## 小结

- `__cfstring` 存的是**编译期预制的常量 `CFString`/`NSString` 对象头**（对应源码 `@"..."` / `CFSTR("...")`），**不是字符本身**；字符在 [[20.Mach-O __cstring节]]。
- 每个对象是四字段定长结构体 `isa`/`flags`/`data`/`length`，64 位下 **32 字节**（`flags` 是 32 位、其后有 4 字节对齐填充）。`isa` 指向 CoreFoundation 导出的 `___CFConstantStringClassReference`，是稳定 ABI；Sonoma 起要求 `isa` 非零。
- `flags` 看低字节定编码：`0xC8`（值常见 `0x7C8`）= 8 位/ASCII、`0xD0`（值常见 `0x7D0`）= UTF-16；由编译期"是否全 ASCII"决定，**勿写死**。`data` 指回 `__cstring`、`length` 给字符个数。
- 因为 `isa`/`data` 是指针，本节历史在可写 `__DATA`、**现代 arm64 迁入只读 `__DATA_CONST`（arm64e 为 `__AUTH_CONST`）**；指针以链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）存放、arm64e 带 PAC——解析须先走 fixup 链拿真实地址。
- 预制 + 加载期定位指针，就是 `@"hello"` 无需 `alloc/init` 即可直接当 `NSString *`/`CFStringRef` 用、`[s length]` O(1) 的原因。
