# 详解Mach-O(六)Mach-O LC_DYSYMTAB

> [!abstract] TL;DR
> **`LC_DYSYMTAB`（动态符号表，`cmd = 0xb`）是 [[05.Mach-O LC_SYMTAB]] 的"动态链接增强视图"**：它**不另存一份符号**，而是把 `LC_SYMTAB` 那张 `nlist` 符号表**按 本地（local）/ 外部已定义（external defined）/ 未定义（undefined）三段切片**，并提供动态链接所需的**间接符号表、目录表（table of contents）、模块表（module table）、引用表、外部/本地重定位**等元数据。
> 它的核心是 **8 对 `(offset/index, count)`**：三段分区 `ilocalsym/nlocalsym`、`iextdefsym/nextdefsym`、`iundefsym/nundefsym`，外加 `tocoff/ntoc`、`modtaboff/nmodtab`、`extrefsymoff/nextrefsyms`、`indirectsymoff/nindirectsyms`、`extreloff/nextrel`、`locreloff/nlocrel`。
> `dyld` 与静态链接器 `ld` 正是靠这张表**快速回答三个问题**：哪些符号是私有的、哪些是导出的、哪些要从依赖库绑定进来；而 `__stubs`/`__la_symbol_ptr`/`__got` 的每个槽位"对应哪个符号"，则由**间接符号表**逐一映射。现代二进制中它的绑定职责大半已被 [[17.Mach-O LC_DYLD_INFO_ONLY]] 与链式 fixups 取代，但作为"向后兼容的脚手架"仍普遍存在。

## 概述与定位

[[05.Mach-O LC_SYMTAB]] 给出的是"一整张符号表"（`nlist`/`nlist_64` 数组 + 字符串表）。但**动态链接器关心的不是整张表**，而是三个分门别类的子集：

- 哪些符号是**本模块私有**的（local，给调试器/回溯用，运行期不参与绑定）；
- 哪些是**导出给别人**用的（external defined，本模块定义、供依赖方解析）；
- 哪些是**需要从依赖库绑定进来**的（undefined，本模块引用、待 `dyld` 填地址）。

`LC_DYSYMTAB` 就把同一张符号表**逻辑上切成这三段**（靠三对 `(index, count)`，零拷贝），并补充**间接符号表**来支撑桩（stub）与符号指针的绑定。它描述的全部数据（符号子集 + 各辅助表）都落在 [[16.Mach-O __LINKEDIT]] 段里。

定位上，它与 `LC_SYMTAB` 是"一对搭档"：`LC_SYMTAB` 提供原料（符号 + 字符串），`LC_DYSYMTAB` 提供"如何按动态链接需要去看这堆原料"的索引。二者几乎总是成对出现，且 `LC_DYSYMTAB` 紧跟在 `LC_SYMTAB` 之后。

> [!note] 一句话区分 SYMTAB 与 DYSYMTAB
> `LC_SYMTAB` = "符号本体在哪、有几个、名字串在哪"；`LC_DYSYMTAB` = "这些符号怎么分类、桩/指针怎么映射回符号、静态库的目录/模块/引用/重定位怎么找"。前者是**数据**，后者是**对数据的动态链接索引**。

## 核心原理与字段详解

### 1. 完整 `dysymtab_command` C 结构体（逐字段注释）

定义见 `<mach-o/loader.h>`。**全部 20 个字段都是 `uint32_t`，结构体大小固定 80 字节**（故 `cmdsize` 恒为 `80`），不随 32/64 位变化——它存的全是"文件偏移/索引/计数"，本身与位宽无关：

```c
struct dysymtab_command {
    uint32_t cmd;            /* LC_DYSYMTAB (0xb) */
    uint32_t cmdsize;        /* sizeof(struct dysymtab_command) == 80 */

    /* —— 第一组：把 LC_SYMTAB 符号表切成三段（index 为符号表下标，count 为个数）—— */
    uint32_t ilocalsym;      /* 本地符号的起始下标 index to local symbols */
    uint32_t nlocalsym;      /* 本地符号个数 number of local symbols */
    uint32_t iextdefsym;     /* 外部已定义(导出)符号起始下标 index to externally defined symbols */
    uint32_t nextdefsym;     /* 外部已定义符号个数 number of externally defined symbols */
    uint32_t iundefsym;      /* 未定义符号起始下标 index to undefined symbols */
    uint32_t nundefsym;      /* 未定义符号个数 number of undefined symbols */

    /* —— 第二组：目录表 Table Of Contents（仅动态库 dylib 使用）—— */
    uint32_t tocoff;         /* 目录表的文件偏移 file offset to table of contents */
    uint32_t ntoc;           /* 目录表条目数 number of entries in table of contents */

    /* —— 第三组：模块表 Module Table（仅动态库 dylib 使用）—— */
    uint32_t modtaboff;      /* 模块表的文件偏移 file offset to module table */
    uint32_t nmodtab;        /* 模块表条目数 number of module table entries */

    /* —— 第四组：外部引用符号表 Referenced Symbol Table（仅动态库 dylib 使用）—— */
    uint32_t extrefsymoff;   /* 引用表的文件偏移 offset to referenced symbol table */
    uint32_t nextrefsyms;    /* 引用表条目数 number of referenced symbol table entries */

    /* —— 第五组：间接符号表 Indirect Symbol Table（桩/符号指针绑定的核心）—— */
    uint32_t indirectsymoff; /* 间接符号表文件偏移 file offset to the indirect symbol table */
    uint32_t nindirectsyms;  /* 间接符号表条目数 number of indirect symbol table entries */

    /* —— 第六组：重定位项（主要见于 .o 目标文件与旧式可执行/库）—— */
    uint32_t extreloff;      /* 外部重定位项文件偏移 offset to external relocation entries */
    uint32_t nextrel;        /* 外部重定位项个数 number of external relocation entries */
    uint32_t locreloff;      /* 本地重定位项文件偏移 offset to local relocation entries */
    uint32_t nlocrel;        /* 本地重定位项个数 number of local relocation entries */
};
```

> [!tip] 字段记忆法：`i*` 是"index 起始下标"，`n*` 是"number 个数"，`*off` 是"文件偏移"
> 凡 `i…/n…` 成对的（如 `ilocalsym/nlocalsym`）是**对符号表切片**——值是"符号下标 + 个数"，不是文件偏移；凡 `…off/n…` 成对的（如 `tocoff/ntoc`、`indirectsymoff/nindirectsyms`）是**独立的辅助表**——`…off` 是 `__LINKEDIT` 内的文件偏移、`n…` 是条目数。区分这点就不会把"符号下标"误当成"文件偏移"去 seek。

> [!note] 哪些字段在现代可执行文件里通常是 0
> 现代 macOS/iOS 的**主可执行文件与 dylib**，只有三段分区（`i*/n*sym`）和**间接符号表**（`indirectsymoff/nindirectsyms`）通常非零，挑大梁做动态链接；而 `tocoff/modtaboff/extrefsymoff`（dylib 目录/模块/引用，旧式两级命名空间预绑定时代的产物）与 `extreloff/locreloff`（重定位，主要属于 `.o`）**大多为 0**。看到一堆 0 不要慌，这是正常的——"任何为 0 的文件偏移都表示该部分未使用"。

### 2. 三段分区的前提：符号表必须已排序

`LC_DYSYMTAB` 的"零拷贝切片"能成立，**依赖 `LC_SYMTAB` 符号表已严格按 本地(local) → 外部已定义(external defined) → 未定义(undefined) 的顺序排好**。链接器 `ld` 在生成时就保证了这个布局，于是三对 `(index, count)` 直接在同一张 `nlist` 数组上取区间即可，无需复制任何符号：

```text
LC_SYMTAB 符号表（一维 nlist 数组，下标 0 .. nsyms-1）
┌───────────────────────────┬───────────────────────────┬───────────────────────────┐
│  本地 local               │  外部已定义 ext-defined   │  未定义 undefined         │
│  [ilocalsym, +nlocalsym)  │  [iextdefsym, +nextdefsym)│  [iundefsym, +nundefsym)  │
└───────────────────────────┴───────────────────────────┴───────────────────────────┘
约束（正常文件）：
  ilocalsym  == 0
  iextdefsym == ilocalsym  + nlocalsym
  iundefsym  == iextdefsym + nextdefsym
  nlocalsym + nextdefsym + nundefsym == LC_SYMTAB.nsyms   （三段恰好无缝覆盖整张表）
```

三段的语义与用途：

| 分区 | `nlist` 类型位 | 含义 | 谁来用 |
|---|---|---|---|
| **local 本地** | `N_SECT` 且**不带** `N_EXT` | 仅本模块可见的函数/数据/调试符号、`static`、局部标签 | 调试器、崩溃回溯（符号化），运行期**不参与绑定** |
| **external defined 外部已定义** | 带 `N_EXT`、有定义（`N_SECT`/`N_ABS`） | 本模块**定义并导出**的符号，供依赖方解析 | `dyld` 解析其它镜像对本镜像的引用；`-exported_symbols` |
| **undefined 未定义** | 带 `N_EXT`、`N_UNDF`（`n_sect==NO_SECT`） | 本模块**引用但未定义**，需从依赖库绑定进来 | `dyld` 绑定（找到提供方后回填地址） |

> [!warning] 排序约定一旦破坏，整张动态视图就废了
> 若有人手工编辑符号表打乱了"本地→导出→未定义"的顺序，但没同步修正 `LC_DYSYMTAB` 的三对索引，`dyld`/`otool` 会按错误区间解读，轻则符号显示错乱、重则绑定到错误条目。修改 Mach-O 符号表时，三对 `(index,count)` 必须与实际排序同步维护。

### 3. 间接符号表（Indirect Symbol Table）—— 桩与符号指针的"对应表"

这是 `LC_DYSYMTAB` 在现代二进制里**最实用**的部分。

**要解决的问题**：`__TEXT,__stubs`（跳转桩）、`__DATA,__la_symbol_ptr`（惰性符号指针）、`__DATA_CONST,__got` / `__nl_symbol_ptr`（非惰性/全局偏移表）这些节里，每个**槽位**（一个桩 / 一个指针）都对应某个外部符号（如 `_printf`），但节里只有原始的指令/指针字节，**没有"我是哪个符号"的信息**。间接符号表就是补上这层映射。

**结构**：间接符号表是一段**连续的 `uint32_t` 数组**，位于 `indirectsymoff` 指向的文件偏移、共 `nindirectsyms` 个条目。**每个条目就是一个"符号表下标"**——指向 `LC_SYMTAB` 中对应的 `nlist` 条目（再由 `nlist.n_strx` 找到字符串表里的名字）。整条解析链是：

```text
某节第 n 个槽位 ──► 间接符号表[reserved1 + n] ──► LC_SYMTAB 符号表[idx] ──► 字符串表[n_strx] ──► "_printf"
                    (一个 uint32_t 下标)            (一个 nlist)            (一个 C 字符串)
```

**关键：起始索引藏在节头的 `reserved1`**。每个"符号指针节 / 桩节"的 `section`/`section_64` 头里，`reserved1` 字段记录**本节槽位在间接符号表中的起始下标**；本节槽位个数 = `section.size / 槽位大小`（指针节槽位大小 = 一个指针宽，即 64 位下 8 字节；`__stubs` 的槽位大小记在 `reserved2`）。于是"本节第 n 个槽位 → 符号"的查法是：

```c
// 取 __la_symbol_ptr / __got / __stubs 第 n 个槽位对应的符号
uint32_t base   = section.reserved1;                 // 本节在间接表中的起始下标
uint32_t value  = indirect_symbol_table[base + n];   // 取出该槽位的间接表条目
if (value & (INDIRECT_SYMBOL_LOCAL | INDIRECT_SYMBOL_ABS)) {
    // 特殊条目：local / abs，无具名外部符号（见下）
} else {
    struct nlist_64 *sym = &symtab[value];           // 否则 value 就是符号表下标
    const char *name = &strtab[sym->n_strx];         // 拿到符号名
}
```

**两个特殊高位值**——并非每个条目都是普通下标，最高两位被用作标志（取自 LLVM `MachO.h` 与 Apple 头）：

| 常量 | 值 | 含义 | 解析处理 |
|---|---|---|---|
| `INDIRECT_SYMBOL_LOCAL` | `0x80000000` | 该槽位指向的是**本地（无名）符号**——指针**本身**已直接指向目标、没有对应的具名外部符号 | 不做符号名查找；该指针按"本地常量/本地地址"处理 |
| `INDIRECT_SYMBOL_ABS` | `0x40000000` | 该槽位是**绝对地址**引用——指针精确指向某个绝对地址 | 不做符号名查找；按绝对引用处理 |

二者可按位 OR 出现。解析时应先用掩码 `0xC0000000` 判断这两位：命中 `LOCAL`/`ABS` 就**不要**把剩余值当符号下标去查（否则会把标志位当下标，越界或错位）；都没命中时，整 32 位即为符号表下标。`otool -Iv` 在遇到这两类条目时会分别显示为 `LOCAL` 和 `ABSOLUTE`。

> [!warning] 忽略 `INDIRECT_SYMBOL_LOCAL` 是经典 bug
> LLVM 曾有一处缺陷：在 32 位架构上误以为"间接符号不会有本地链接"，于是当某符号在间接表里的值其实是 `INDIRECT_SYMBOL_LOCAL` 时，被当成下标 `0` 去取，导致符号值取成 0、链接器据此误链接。**任何手写解析器都必须先剥离这两个高位标志再当下标用**。

> [!note] 架构差异
> `dysymtab_command` 20 个字段全是 32 位偏移/计数，结构体本身固定 80 字节、**不随位宽变化**；变化的是它**索引到的**符号项——32 位文件是 `nlist`、64 位是 `nlist_64`（差别在 `n_value` 等字段宽度），这点与 [[05.Mach-O LC_SYMTAB]] 完全一致。间接符号表条目无论 32/64 位都是 `uint32_t`。

### 4. 目录表 / 模块表 / 引用表（静态库 `.a` 与旧式两级命名空间用）

第 2~4 组字段服务于**动态库的"按需加载模块"与旧式预绑定**，在现代单一镜像的可执行文件里几乎总是 0；但理解它们有助于读懂老二进制与静态库归档。它们共同把一个 dylib 描述成"由若干模块（module，对应原来的一个 `.o`）拼成"：

**目录表 Table Of Contents（`tocoff`/`ntoc`）**——一个**已按符号名排序**的数组，让链接器无需扫全表即可二分查到"某导出符号由哪个模块定义"。每条是：

```c
struct dylib_table_of_contents {
    uint32_t symbol_index;  /* 该导出符号在符号表中的下标（指向 external defined 段） */
    uint32_t module_index;  /* 定义该符号的模块在模块表中的下标 */
};
```

**模块表 Module Table（`modtaboff`/`nmodtab`）**——每个模块（≈ 一个原始 `.o`）一条，记录它各自占用的符号/引用/重定位区间，以及 init/term 与 ObjC 模块信息。32 位用 `dylib_module`，64 位用 `dylib_module_64`：

```c
struct dylib_module {            /* 32 位 */
    uint32_t module_name;            /* 模块名（字符串表下标） */
    uint32_t iextdefsym, nextdefsym; /* 本模块提供的"外部已定义符号"区间 */
    uint32_t irefsym,    nrefsym;    /* 本模块在"引用表"中的区间 */
    uint32_t ilocalsym,  nlocalsym;  /* 本模块的"本地符号"区间 */
    uint32_t iextrel,    nextrel;    /* 本模块的"外部重定位"区间 */
    uint32_t iinit_iterm;            /* 低16位=init段起始下标，高16位=term段起始下标 */
    uint32_t ninit_nterm;            /* 低16位=init条目数，高16位=term条目数 */
    uint32_t objc_module_info_addr;  /* (__OBJC,__module_info) 地址 */
    uint32_t objc_module_info_size;  /* (__OBJC,__module_info) 大小 */
};
/* dylib_module_64：末尾两字段顺序/宽度不同——先 uint32_t objc_module_info_size，
   再 uint64_t objc_module_info_addr（地址加宽到 64 位、且位置互换）。 */
```

**引用表 Referenced Symbol Table（`extrefsymoff`/`nextrefsyms`）**——每条用 24 位下标 + 8 位标志，记录"某模块引用/定义了哪个符号"，供模块按需绑定时使用：

```c
struct dylib_reference {
    uint32_t isym  : 24,   /* 符号表下标 */
             flags : 8;    /* 引用类型标志 */
};
```

> [!note] 这三张表为何在新文件里消失
> 它们诞生于**两级命名空间 + 预绑定（prebinding）**的时代，目的是让 dylib 能"按模块"局部绑定、加速启动。随着 `dyld` 改用整镜像的压缩绑定信息（[[17.Mach-O LC_DYLD_INFO_ONLY]]）和共享缓存，这套按模块的机制基本退役，只在**静态库归档 `.a` 的成员**和很老的二进制里还能见到非零值。

### 5. 外部 / 本地重定位项（`.o` 目标文件与旧式镜像）

第 6 组 `extreloff/nextrel`（外部重定位）与 `locreloff/nlocrel`（本地重定位）指向一组 `relocation_info` 条目，告诉链接器"哪些位置在最终确定地址后需要回填修正"：

```c
struct relocation_info {
    int32_t  r_address;     /* 需修正处相对于节起点的偏移 */
    uint32_t r_symbolnum:24,/* 外部重定位=符号表下标；本地重定位=节序号 */
             r_pcrel:1,     /* 是否 PC 相对 */
             r_length:2,    /* 修正宽度：0/1/2/3 → 1/2/4/8 字节 */
             r_extern:1,    /* 1=外部(看符号), 0=本地(看节) */
             r_type:4;      /* 重定位类型（架构相关） */
};
```

- **外部重定位**（`r_extern=1`）：`r_symbolnum` 是符号表下标，修正值取决于该**符号最终地址**（链接到外部定义）。
- **本地重定位**（`r_extern=0`）：`r_symbolnum` 是节序号，修正值取决于**镜像的加载基址滑动**（slide）。

这套**经典重定位**主要存在于**可重定位目标文件 `.o`**；对最终链接好的可执行文件/dylib，地址重定位（rebase）与符号绑定（bind）现代已迁移到 [[17.Mach-O LC_DYLD_INFO_ONLY]] 的压缩字节码或链式 fixups，故 `extreloff/locreloff` 在成品镜像里通常为 0。

```text
            cmd LC_DYSYMTAB
        cmdsize 80
      ilocalsym 0          ; 本地符号：下标 0..41
      nlocalsym 42
     iextdefsym 42         ; 导出符号：下标 42..71
     nextdefsym 30
      iundefsym 72         ; 未定义符号：下标 72..123（待 dyld 绑定）
      nundefsym 52
         tocoff 0          ; 目录表未用（非 dylib 旧式）
           ntoc 0
      modtaboff 0          ; 模块表未用
        nmodtab 0
   extrefsymoff 0          ; 引用表未用
    nextrefsyms 0
 indirectsymoff 30528      ; 间接符号表在 __LINKEDIT 内的文件偏移
  nindirectsyms 40         ; 共 40 个 uint32_t 条目
      extreloff 0          ; 外部重定位未用（成品镜像）
        nextrel 0
      locreloff 0          ; 本地重定位未用
        nlocrel 0
```

> 说明：`cmdsize` 恒为 `80`；索引 0–41 是本地符号、42–71 是导出符号、72–123 是未定义符号——三段恰好覆盖 `LC_SYMTAB` 的 124 个符号（`nsyms=124`）。`tocoff/modtaboff/extrefsymoff/extreloff/locreloff` 全 0 是现代成品文件的典型样貌；真正干活的是三段索引 + `indirectsymoff`。

### 实操 2：看间接符号表（`otool -Iv`）

`-I` 显示间接符号表，`-v` 让它把下标"反查成符号名"显示（verbose）：

```bash
otool -Iv /bin/ls
```

> [!warning] 示例输出为示意
> 数值/符号名为构造示意，实际以你机器为准。

```text
Indirect symbols for (__TEXT,__stubs) 5 entries:
address            index  name
0x0000000100003f44 7      _printf
0x0000000100003f50 8      _malloc
0x0000000100003f5c 9      _free
0x0000000100003f68 4      _strlen
0x0000000100003f74 LOCAL          ; ← INDIRECT_SYMBOL_LOCAL，无具名外部符号
Indirect symbols for (__DATA_CONST,__got) 7 entries:
address            index  name
0x0000000100004000 5      _environ
0x0000000100004008 6      ___stack_chk_guard
0x0000000100004010 ABSOLUTE       ; ← INDIRECT_SYMBOL_ABS，绝对地址引用
0x0000000100004018 8      _malloc
```

> 说明：`__stubs` 第 0 个槽位对应间接表条目（其符号名为 `_printf`），印证"`reserved1 + n` → 间接表 → 符号"的链路；标 `LOCAL`/`ABSOLUTE` 的条目是被 `0x80000000`/`0x40000000` 标志置位、不参与具名符号查找的特殊项。

### 实操 3：对照节头里的 `reserved1` 起始索引

```bash
otool -l /bin/ls | grep -A 12 "sectname __stubs"
otool -l /bin/ls | grep -A 12 "sectname __got"
```

> [!warning] 示例输出为示意

```text
Section
  sectname __stubs
   segname __TEXT
      addr 0x0000000100003f44
      size 0x0000000000000050
   reserved1 0     (index into indirect symbol table)   ; ← __stubs 从间接表下标 0 开始
   reserved2 12    (size of stubs)                       ; ← 每个桩 12 字节
Section
  sectname __got
   segname __DATA_CONST
      addr 0x0000000100004000
      size 0x0000000000000038
   reserved1 5     (index into indirect symbol table)    ; ← __got 从间接表下标 5 开始
```

> 说明：`__stubs.reserved1 = 0` 表示它的 5 个桩占间接表 `[0,5)`；`__got.reserved1 = 5` 表示它的 7 个非惰性指针接着占 `[5,12)`——两节的区间在间接表里首尾相接，正是 `otool -Iv` 两段输出的来历。

### 实操 4：把间接表与符号表对照看（配合 `nm -p`）

```bash
nm -p /bin/ls          # -p 按符号表"原始顺序"列出（而非字母序），下标即可对上间接表的 index 列
```

> [!warning] 示例输出为示意

```text
0000000000000000 U _printf      ; 下标顺序与 otool -Iv 的 index 列一致
0000000000000000 U _malloc
...
```

> 说明：`U` 表示未定义（undefined）——正落在 `LC_DYSYMTAB` 的 `[iundefsym, +nundefsym)` 段；`nm -p` 的顺序与间接表的 `index` 列一一对应，可手工验证整条映射链。

## FAQ

> [!question] `LC_DYSYMTAB` 会重新存一份符号吗？它和 `LC_SYMTAB` 谁离不开谁？
> **不会**。`LC_DYSYMTAB` 一个 `nlist` 都不存，它的三段分区只是**对 `LC_SYMTAB` 那张表取下标区间**，间接符号表也只是一串"指向 `LC_SYMTAB` 的 `uint32_t` 下标"。所以 `LC_DYSYMTAB` **强依赖** `LC_SYMTAB`（没有原料表，分区与间接表都无意义）；反之 `LC_SYMTAB` 可单独存在（纯静态、无动态链接的对象）。二者几乎总是成对出现，`LC_DYSYMTAB` 紧跟其后。

> [!question] 为什么我 dump 出来 `tocoff`/`modtaboff`/`extreloff` 全是 0？文件坏了吗？
> 没坏，**这是现代成品镜像的正常状态**。目录表/模块表/引用表服务于旧式"两级命名空间 + 预绑定 + 按模块绑定"，已基本退役，只在静态库 `.a` 成员里还可能非零；外部/本地重定位主要属于 `.o` 目标文件，成品的 rebase/bind 已迁到 [[17.Mach-O LC_DYLD_INFO_ONLY]]。任何为 0 的 `*off` 都表示"该部分未使用"。真正干活的是三段索引 + 间接符号表。

> [!question] 间接符号表条目里的 `0x80000000` / `0x40000000` 是什么？能直接当下标用吗？
> **不能直接当下标**。`INDIRECT_SYMBOL_LOCAL = 0x80000000` 表示该槽位指向本地无名符号（指针本身已是目标、无具名外部符号）；`INDIRECT_SYMBOL_ABS = 0x40000000` 表示绝对地址引用。解析时必须先用掩码 `0xC0000000` 判这两位：命中就按本地/绝对处理、**不查符号名**；只有都没命中时整 32 位才是符号表下标。忽略它们会把标志位当下标，导致越界或链接到错误符号（LLVM 历史上就栽过这个坑）。

> [!question] 既然有了 `LC_DYLD_INFO_ONLY` / 链式 fixups，`LC_DYSYMTAB` 还有用吗？为什么不删？
> 现代二进制里它的**绑定职责**确实大半被取代：rebase/bind/export 走 [[17.Mach-O LC_DYLD_INFO_ONLY]] 的压缩字节码，更新的 iOS 15 / macOS 12 起改用 `LC_DYLD_CHAINED_FIXUPS` + `LC_DYLD_EXPORTS_TRIE` 链式 fixups。但 `LC_DYSYMTAB` **仍普遍保留**，原因有三：一是**向后兼容**——要在新老系统都能加载的二进制，仍需这张表；二是**工具链与调试器**（`otool`/`nm`/`dsymutil`/反汇编器）依赖三段分区与间接符号表来符号化、给桩调用打标签；三是**间接符号表 + `reserved1`** 仍是把 `__stubs`/`__got` 槽位映射回符号名的标准途径。可以说它从"绑定主力"退居为"符号分类与桩映射的脚手架"，但没退场。

- [[17.Mach-O LC_DYLD_INFO_ONLY]]：现代二进制的 rebase/bind/export 走它（及链式 fixups），取代了 `LC_DYSYMTAB` 的旧式绑定/重定位职责。

## 小结

- `LC_DYSYMTAB`（`0xb`，固定 80 字节）在 `LC_SYMTAB` 之上提供**动态链接视图，零拷贝、不另存符号**。
- **三对 `(index, count)`**（`ilocalsym/nlocalsym`、`iextdefsym/nextdefsym`、`iundefsym/nundefsym`）把**已排序**的符号表切成 本地 / 外部已定义 / 未定义 三段，三段无缝覆盖整张 `LC_SYMTAB`。
- **间接符号表**（`indirectsymoff/nindirectsyms`）是一串 `uint32_t` 下标，配合各节头的 `reserved1` 起始索引，把 `__stubs`/`__la_symbol_ptr`/`__got` 槽位映射回符号；`INDIRECT_SYMBOL_LOCAL(0x80000000)` / `INDIRECT_SYMBOL_ABS(0x40000000)` 为两个特殊标志，须先剥离再当下标。
- **目录表 / 模块表 / 引用表**（`toc*`/`modtab*`/`extref*`）服务旧式两级命名空间预绑定、仅 dylib 与静态库用；**外部/本地重定位**（`extrel*`/`locrel*`）主要属 `.o`——这些在现代成品镜像里通常为 0。
- 现代二进制中其绑定职责多被 [[17.Mach-O LC_DYLD_INFO_ONLY]] 与链式 fixups 取代，但作为符号分类与桩映射的脚手架仍普遍保留。
