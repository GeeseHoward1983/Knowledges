# 详解Mach-O(十二)Mach-O __PAGEZERO

> [!abstract] TL;DR
> **`__PAGEZERO` 是可执行文件（`MH_EXECUTE`）的第一个段，唯一职责是把地址空间最低端整段"圈死"成不可访问区，用来捕获空指针（NULL）解引用**。它从虚拟地址 0 开始，`initprot = maxprot = 0`（`VM_PROT_NONE`，不可读、不可写、不可执行），任何对低地址的访问都会被硬件 MMU 立刻拦下，触发 `EXC_BAD_ACCESS` / `SIGSEGV`，而不是悄悄读到垃圾数据继续跑。
> 它本质上**就是一条普通的 `LC_SEGMENT_64`**（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]），特殊之处全在字段取值：`vmaddr=0`、`vmsize` 巨大（64 位典型 `0x100000000` = 4GB）、`fileoff=0`、`filesize=0`、`nsects=0`、`maxprot=initprot=0`。因为 `filesize=0`，它**不占任何磁盘字节**；因为永远不会被实页支撑，它也**不占物理内存**——纯粹是一段保留的、读写执行皆禁的虚拟地址。
> 64 位下 `vmsize` 取 4GB（而非一页）是有意为之：把整个 32 位低地址区（`0x0`~`0xFFFFFFFF`）全部覆盖，既捕获 `NULL + 大偏移` 的越界访问，又封死"32 位地址截断后落到低区"的攻击面。32 位二进制地址空间紧张，`__PAGEZERO` 一般只占一页（`0x1000` = 4KB）。动态库（`MH_DYLIB`）**不含** `__PAGEZERO`——它被加载进主程序已建好的地址空间，空指针保护由主可执行文件统一提供。

## 概述与定位

几乎所有空指针 bug 都表现为"访问地址 0 附近"：解引用一个未初始化或已置空的指针（`*p` 当 `p == NULL`）、访问 `NULL` 结构体的成员（`p->field`，等价于读 `0 + field_offset`）、调用空函数指针（`(*fp)()` 当 `fp == NULL`）。如果地址 0 附近是一片**可访问**的内存，这些错误会"软着陆"——读到一堆零或垃圾、写坏别人的数据、跳到任意代码，bug 被掩盖、甚至被攻击者利用。`__PAGEZERO` 用一个**无权限的大段**把这片区域变成雷区：程序一旦误用 NULL 指针，MMU 在地址翻译阶段就发现该页无任何访问权限，立刻产生异常（macOS 上表现为 Mach 异常 `EXC_BAD_ACCESS`，BSD 层转换为 `SIGSEGV`/`SIGBUS`），让 bug **当场暴露**而非潜伏。

它是 [[11.Mach-O Segments]] 中"段=权限单位"思想的最极端体现——别的段是 `r-x`/`rw-`/`r--`，`__PAGEZERO` 的权限是**空**（`---`）。换个角度说：`__TEXT`/`__DATA`/`__LINKEDIT` 是"为了放数据而映射内存"，`__PAGEZERO` 恰恰相反，是"为了**不让任何数据**落在这里而占住地址"。它在文件里只有一条 72 字节的段头，没有节、没有数据，却是整个进程内存安全模型的"地基的第 0 块砖"。

本篇是 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]（讲段命令这一**描述结构**）的纵深个案：用 `__PAGEZERO` 这一最简单、又最特殊的段，把"`vmsize` 与 `filesize` 可以不等""`initprot`/`maxprot` 如何决定权限""内核如何按字段识别段类型"几个机制讲透，并延伸到逆向与漏洞视角。

## 核心原理与字段详解

### 1. 它就是一条 `LC_SEGMENT_64`，特殊全在取值

`__PAGEZERO` **没有专属结构**——它复用与 `__TEXT`/`__DATA` 完全相同的 `segment_command_64`（64 位 72 字节定长头，字段布局见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 第 1 节）。把它当作一条 `segname` 为 `"__PAGEZERO"` 的段命令来解析即可。它之所以"特殊"，是因为每个字段都取了极端值：

| 字段 | `__PAGEZERO` 取值 | 含义 / 为何如此 |
|---|---|---|
| `cmd` | `LC_SEGMENT_64`（`0x19`） | 64 位段命令；32 位为 `LC_SEGMENT`（`0x1`） |
| `cmdsize` | `72`（64 位）/ `56`（32 位） | 因 `nsects=0`，命令体**只有段头**，无任何节头跟随 |
| `segname` | `"__PAGEZERO"` | 双下划线 + 大写，Apple 约定；内核也靠这个名 + 字段组合识别它 |
| `vmaddr` | `0x0` | 从地址空间**最低端**开始——正是要圈住的"危险区"起点 |
| `vmsize` | `0x100000000`（4GB，64 位典型）/ `0x1000`（4KB，32 位典型） | 覆盖范围，见第 2 节 |
| `fileoff` | `0` | 占位；因 `filesize=0`，这个偏移**不读任何字节**，填 0 只是形式 |
| `filesize` | `0` | **不映射任何文件内容**，所以这段在磁盘上"不存在"，零体积 |
| `maxprot` | `0x0`（`VM_PROT_NONE`） | 权限**上限**就是 0——运行时也**永远不能**用 `mprotect` 把它提成可读/可写/可执行 |
| `initprot` | `0x0`（`VM_PROT_NONE`） | 初始权限为 0，`---`，读写执行全禁 |
| `nsects` | `0` | **没有任何节**——它不组织数据，自然没有 `__text`/`__data` 之类的小块 |
| `flags` | `0x0` | 无任何 `SG_*` 段标志 |

> [!note] 三个"0"共同定义了"纯保护段"
> `filesize = 0`（不占文件）、`nsects = 0`（无节、无内容）、`initprot = maxprot = 0`（无任何权限）——这三者叠加，就把 `__PAGEZERO` 与所有其他段彻底区分开来。其余每个段都至少满足"要么有文件数据、要么有节、要么有读权限"中的某一项，唯独 `__PAGEZERO` 三项全无。它是 Mach-O 里**唯一**一个"只占地址、不占资源、不给权限"的段。

> [!note] `maxprot=0` 的硬约束意义
> 别的段（如 `__DATA_CONST`）`maxprot` 可能大于 `initprot`，给运行时 `mprotect` 提权留口子。`__PAGEZERO` 的 `maxprot` 也是 0，意味着**进程在整个生命周期内都无法**把这片地址改成可访问——这是比"初始不可访问"更强的保证，从根上杜绝了"先解保护再利用"的可能（对比 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 第 4 节里 `maxprot=0x7` 的安全隐患）。

### 2. 为什么 64 位下 `vmsize` 取 4GB（而非一页）

最朴素的空指针保护只需"封掉地址 0 所在的那一页"（4KB 或 16KB）。但 64 位 `__PAGEZERO` 一律取 **`0x100000000` = 4GB**，把整个 32 位低地址区（`0x00000000`~`0xFFFFFFFF`）全部覆盖。原因有三层：

1. **捕获 `NULL + 大偏移` 的访问**。空指针的危害不止"读地址 0"。当代码做 `p->field`、`array[i]`、`p->big_struct.deep_member` 且 `p == NULL` 时，实际访问的是 `0 + 偏移量`。这个偏移可能很大（大数组下标、深层结构体成员），轻松超出单页 4KB。只封一页时，`NULL->[偏移 > 4KB]` 会落到一页之外的**可访问**区域，保护失效；封满 4GB 后，只要偏移在 32 位范围内（绝大多数情况），访问就一定落在 `__PAGEZERO` 里被拦下。

2. **封死"32 位地址截断"的攻击/错误面**。64 位代码若错误地把指针截断成 32 位（如把 `uint64_t` 指针存进 `int`、或某些 ABI 不匹配），得到的"野地址"必然落在低 4GB。`__PAGEZERO` 占满这 4GB，等于宣告"低 32 位地址范围对用户态永远不可用"，让这类截断错误**确定性地崩溃**而非随机读写。Apple 在 arm64 上甚至把它升级为**强制要求**（见第 5 节)：内核加载 arm64 二进制时会校验它是否真的圈住了完整的低 4GB，否则拒绝加载。

3. **64 位地址空间充裕，圈走 4GB 几乎零成本**。64 位进程有 2⁶⁴（理论）/ 通常 2⁴⁷ 量级的可用地址，拿出最低 4GB 当雷区毫无压力——又因为 `filesize=0`、永不实页化，这 4GB **不占文件、不占物理内存**，只是地址空间里一段"保留不用"的记号。代价几乎为零，收益是堵住一大类空指针/截断漏洞，性价比极高。这也是为什么 `__TEXT` 的 `vmaddr` 恰好从 `0x100000000` 起步——它正好接在 4GB 的 `__PAGEZERO` 之后。

### 3. 空指针解引用如何"落入"并触发异常的完整机制

把"`*p` 当 `p==NULL` 会崩溃"拆成内核/硬件层面的链条：

1. **生成访问地址**。CPU 执行一条访存指令（如 arm64 的 `ldr x0, [x1]`，`x1` 持有指针值 `0`；或 `ldr x0, [x1, #offset]` 访问成员）。目标虚拟地址 = 指针值 + 偏移，落在 `[0, 4GB)` 区间。
2. **MMU 查页表**。CPU 的内存管理单元（MMU）拿这个虚拟地址去查进程页表。`__PAGEZERO` 对应的地址范围在建立进程时被内核登记为"已保留但权限为 `VM_PROT_NONE`"——要么页表项根本没有有效映射，要么映射存在但权限位标记为不可读/写/执行。
3. **MMU 拒绝并产生 fault**。无论哪种情况，MMU 都判定本次访问非法，向 CPU 抛出一个**页错误/访问异常**（arm64 的 Data Abort、x86 的 #PF Page Fault）。
4. **内核接管并转成信号**。XNU 的异常处理路径捕获该 fault，判定该地址不属于任何可访问的 VM 区域（落在 `__PAGEZERO` 这种 `prot=0` 段里），于是生成 Mach 异常 **`EXC_BAD_ACCESS`**（子码通常为 `KERN_INVALID_ADDRESS` 或 `KERN_PROTECTION_FAILURE`）。若进程没有用 Mach 异常端口自行处理，BSD 兼容层把它转换为 POSIX 信号 **`SIGSEGV`**（段错误）或 **`SIGBUS`**（总线错误）投递给进程。
5. **进程崩溃 / 调试器断下**。默认行为是进程终止并由 `ReportCrash` 生成崩溃报告（崩溃日志里 `Exception Type: EXC_BAD_ACCESS (SIGSEGV)`、`Exception Codes: KERN_INVALID_ADDRESS at 0x0000000000000000` 是空指针的典型特征）；若在 LLDB 下运行，则在出错指令处断下，`Fault address` 显示为 0 或一个小偏移。

整条链路的关键是：**保护由硬件 MMU 在地址翻译阶段强制执行**，是页粒度的、确定性的、零运行时开销的——不是靠编译器插桩或运行时检查，而是"地址一旦落进无权限页，硬件必然 fault"。`__PAGEZERO` 做的全部事情，就是确保"地址 0 起、足够大的一段"始终处于这种无权限状态。

### 4. 32 位（4KB）vs 64 位（4GB）的差异

| 维度 | 32 位（`i386` / `armv7`，`LC_SEGMENT`） | 64 位（`x86_64` / `arm64`，`LC_SEGMENT_64`） |
|---|---|---|
| 段命令 | `LC_SEGMENT`（`0x1`），头 56 字节 | `LC_SEGMENT_64`（`0x19`），头 72 字节 |
| `vmaddr` | `0x0` | `0x0` |
| `vmsize` 典型值 | `0x1000`（4KB，**仅一页**） | `0x100000000`（4GB） |
| 覆盖范围 | 仅地址 0 所在的第一页 | 整个低 32 位地址空间 |
| 紧随其后的段起点 | 通常 `0x1000`（或 `0x4000`） | `0x100000000` |
| 设计取舍 | 32 位进程总地址空间仅 4GB，无法奢侈地拿 4GB 当雷区，只能封最关键的第一页 | 64 位空间充裕，圈走 4GB 近乎免费，换取最强保护 |
| 内核强制程度 | 仅"软"要求第一页不可访问（`vm_map_has_hard_pagezero(map, 0x1000)`） | arm64 额外"硬"要求覆盖完整 4GB（`vm_map_has_hard_pagezero(map, 0x100000000)`），否则 `LOAD_BADMACHO` |

> [!note] 别把"`__PAGEZERO` 大小"和"系统页大小"混为一谈
> 系统**页大小**（page size）是 MMU 映射的最小粒度：x86_64 为 **4KB（`0x1000`）**，arm64（Apple Silicon / 现代 iOS 设备）为 **16KB（`0x4000`）**。而 `__PAGEZERO` 的 **`vmsize`** 是它**总共圈了多大地址**，由上表的安全策略决定（32 位约一页、64 位 4GB），与页大小是两个独立概念。唯一的关联是：`vmsize` 必然是页大小的整数倍（4GB 既是 4KB 也是 16KB 的整数倍，天然满足）。`-pagezero_size` 给的值也会被链接器向段对齐（页大小）取整。

### 5. 内核如何识别 `__PAGEZERO` 并强制其存在（XNU `mach_loader.c`）

`__PAGEZERO` 不只是"链接器好心生成的一个段"——XNU 内核在加载二进制时会**主动校验**它，缺失或不够大就直接拒绝运行。识别与校验逻辑在 `bsd/kern/mach_loader.c` 的加载路径里：

**识别**：内核处理每条 `LC_SEGMENT_64` 时，看到一个 `vmaddr == 0 && vmsize > 0 && initprot == 0 && maxprot == 0` 的段，就知道这是 page-zero（保护段），按"映射一段无权限的保留地址"来处理，而非真去读文件（因为 `filesize=0`）。

**强制（两级检查）**：在开启 `enforce_hard_pagezero` 的内核（现代 macOS/iOS 默认开启）上：

1. **通用"软"检查（`0x1000`）**：对所有二进制，调用 `vm_map_has_hard_pagezero(map, 0x1000)`，要求**至少第一页（4KB）**不可访问；返回 `FALSE` 一般就返回 `LOAD_BADMACHO`、拒绝加载。这是 NULL 解引用防护的**最低底线**。其中有一个针对"16KB 系统上跑老 4KB 应用"的狭窄向后兼容例外：若二进制非 64 位地址空间、非 PIE、页大小非 4KB、且只有"软" page zero，为兼容老 4K app 才放行不强制硬 page zero。
2. **arm64 专属"硬"检查（`0x100000000`）**：若二进制是 64 位地址空间且 `cputype == CPU_TYPE_ARM64`，要求它必须有覆盖完整低 32 位（4GB）的"hard page zero"，用 `vm_map_has_hard_pagezero(map, 0x100000000)` 校验；不满足同样返回 `LOAD_BADMACHO`。这是把"封一页"升级为"封满 4GB"的强制，专门关掉"只封 4KB、其余低区可用"的规避手法（见第 7 节）。

两级检查都失败时，内核会释放已建立的 VM map 并以 `LOAD_BADMACHO` 拒绝该二进制。换言之：**在 arm64 上，一个没有 4GB `__PAGEZERO` 的可执行文件根本无法启动**——这把空指针防护从"约定"变成了"内核强制的加载前提"。

### 6. 为什么只存在于 `MH_EXECUTE`，动态库不需要

`__PAGEZERO` 是 **`MH_EXECUTE`（主可执行文件）的标志性段**，而 `MH_DYLIB`（动态库 `.dylib`）、`MH_BUNDLE`（可加载 bundle）、`MH_DYLINKER`（dyld 自身除外的常规组件）等**通常不含**它。道理在于"地址空间归谁建":

- **主可执行文件**是地址空间的"奠基者"。进程启动时，内核 `exec` 它、按它的段命令把内存骨架立起来——`__PAGEZERO` 作为它的第 0 段，**第一个**被映射，负责把整个低端地址区圈成禁区。这是"为整个进程"做的一次性保护。
- **动态库是"客人"**。`.dylib` 在主程序的地址空间**已经建好之后**才被 dyld 加载进来，挂在某个高地址。低端的空指针雷区早已由主可执行文件的 `__PAGEZERO` 铺好，所有共享同一进程地址空间的库**自动**受这同一片保护覆盖。若每个 dylib 都自带一个 `vmaddr=0` 的 `__PAGEZERO`,它们会互相冲突（多个段抢地址 0），且毫无意义——保护是进程级的、只需一份。
- **由此可推**：判断一个 Mach-O 是不是主可执行文件，"有没有 `__PAGEZERO`"是个强信号（虽不绝对——可用 `-pagezero_size 0x0` 去掉，见第 7 节）；反过来，在一个 dylib 里看到 `__PAGEZERO` 是异常的。

> [!note] dyld 自身是个特例
> 动态链接器 `/usr/lib/dyld` 类型为 `MH_DYLINKER`，它被内核当作"第二个可执行映像"加载、也有自己的加载逻辑，情况比普通 dylib 复杂，不在本篇展开。一般结论"库不需要 `__PAGEZERO`"针对的是普通的 `MH_DYLIB`。

### 7. `-pagezero_size` 链接选项

`__PAGEZERO` 由**静态链接器**（`ld`/`ld64`，LLVM 的 `ld.lld` 亦支持）在链接可执行文件时自动生成，其大小可通过 **`-pagezero_size <size>`** 选项控制：

- **语义**：指定 `__PAGEZERO` 段的大小为 `<size>`（十六进制数，会被向**段对齐**（页大小）取整）。链接 `MH_EXECUTE` 时，若没有任何段覆盖"地址 0 到段对齐值"这段范围，链接器就自动造一个无访问权限的段叫 `__PAGEZERO` 把它盖住，以保证 NULL 解引用必然异常。
- **默认值**：不给该选项时，32 位架构默认一页（`0x1000` = 4KB），64 位架构默认 4GB（`0x100000000`）。
- **设为 0 → 删除该段**：`-pagezero_size 0x0` 会让链接器**完全不生成** `__PAGEZERO`。这在**内核开发 / 裸机 / 需要把代码加载到地址 0** 等场景有用——内核镜像往往就要用低地址，标准的 NULL 守护页反而碍事。LLVM `ld.lld` 的实现说明里明确写道："`-pagezero_size` 改变 `__PAGEZERO` 大小，设为 0 时移除该段"，并指出**这一选项常用于内核开发**。
- **设为非默认值**：也可指定一个介于"一页"和"4GB"之间的自定义大小（如某些特殊布局需要更大或更小的保留区），同样向页对齐取整。

> [!warning] 在现代 arm64 上不能随便删 `__PAGEZERO`
> 如第 5 节所述，arm64 内核**强制**要求 64 位 ARM 可执行文件具备覆盖完整 4GB 的 hard page zero。对常规的 arm64 用户态可执行文件用 `-pagezero_size 0x0` 去掉 `__PAGEZERO`（或把它改得小于 4GB），会导致内核加载时 `vm_map_has_hard_pagezero(map, 0x100000000)` 失败、以 `LOAD_BADMACHO` 拒绝启动。`-pagezero_size 0x0` 的有效用武之地主要是内核/特殊镜像，而非普通 app。

### 8. 逆向 / 漏洞视角：mmap NULL 页的攻防史

`__PAGEZERO` 的存在与否，直接关系到"空指针解引用"这类 bug 的**可利用性**。这一点在攻防史上反复上演：

**攻击者想做什么**：当程序（尤其内核）存在 NULL 解引用 bug 时，如果攻击者能在**地址 0 处预先映射一页可控内存**（典型手法 `mmap(NULL, ..., MAP_FIXED, ...)` 或 `mach_vm_allocate` 到地址 0），就能在触发 bug 前把"NULL 指向的内容"布置成精心构造的数据（伪造的函数指针表、vtable 等），让原本会崩溃的解引用**软着陆到攻击者的页**上，进而劫持控制流、提权。Linux 早期（2.6.23 之前）内核态正是因为"什么都不阻止用户 mmap 地址 0",NULL 解引用成了可靠的本地提权原语。

**防御如何层层加码**（用户态 + 内核态）：

1. **`__PAGEZERO`（用户态进程级）**：可执行文件自带的这道无权限大段，让进程**自己的**地址空间最低端被占住——用户态代码无法在地址 0 放数据，自身的 NULL 解引用必崩。
2. **内核最低地址强制（类似 Linux `mmap_min_addr`）**：即便没有 `__PAGEZERO`，macOS 内核也强制一个"用户态不可分配的最低地址"，拒绝把内存映射到 0 附近。`MAP_FIXED` 到地址 0 对非特权用户会被拒（返回错误）——这是专门为降低"内核 NULL 解引用"危害而设的安全特性。
3. **arm64 hard page zero 内核校验**（第 5 节）：内核加载期就强制 64 位 ARM 二进制圈满低 4GB，从加载前提上消灭"低区可被映射"的可能。
4. **硬件辅助（Apple Silicon）**：ARMv8 的 **PXN（Privileged Execute Never）**、以及类比 Intel SMEP/SMAP 的特性，确保内核态不能执行/（在 SMAP 类机制下）随意访问用户态页——即便低区被映射，内核也不会去执行那里的代码。
5. **综合结果**：随 Apple Silicon（arm64）与 macOS 11 Big Sur 之后，Apple 把上述机制叠加，使得用户态 NULL 解引用基本只能崩溃、不能利用；内核态 NULL 解引用也因"无法在低地址布置可控数据 + 硬件不让跨态执行"而被判定为**不可利用**（历史上仍出现过因 SMAP 缺失等条件被重新利用的个案，如 2019 年的相关研究，但门槛已极高）。

> [!note] 逆向时怎么用 `__PAGEZERO` 这条信息
> - 看到一个 Mach-O 的第 0 段是 `vmaddr=0 / vmsize=0x100000000 / prot=---`，基本可断定它是**主可执行文件**（`MH_EXECUTE`），且运行在标准的 NULL 守护下。
> - 若某二进制**异常地缺少** `__PAGEZERO`、或 `__PAGEZERO` 被改得很小，要警惕它可能是内核镜像、特种 loader，或刻意用 `-pagezero_size 0x0` 构造的、试图在低地址做文章的样本——这类布局值得重点分析。
> - 分析崩溃日志时，`EXC_BAD_ACCESS` + `at 0x0`（或一个小偏移地址）几乎可断定是空指针解引用，而能崩在这里，正是 `__PAGEZERO` 在起作用。

## 实操：用工具查看

### 示例 1：`otool -l` 看 `__PAGEZERO` 段头

```bash
otool -l /bin/ls | grep -A 9 __PAGEZERO      # 看 __PAGEZERO 这一条段命令
otool -lv /bin/ls | grep -A 9 __PAGEZERO     # -v 把 maxprot/initprot 显示成 (---) 符号
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Load command 0
      cmd LC_SEGMENT_64
  cmdsize 72                       ; nsects=0，命令体只有 72 字节段头、无节头
  segname __PAGEZERO
   vmaddr 0x0000000000000000       ; 从地址空间最低端起
   vmsize 0x0000000100000000       ; 4GB，圈满整个低 32 位地址区
  fileoff 0                        ; 占位，因 filesize=0 不读任何字节
 filesize 0                        ; 不映射文件内容 → 磁盘零体积
  maxprot 0x00000000   (---)       ; 权限上限=0，运行时也不能提权
 initprot 0x00000000   (---)       ; 初始权限=0，VM_PROT_NONE
   nsects 0                        ; 无节
    flags 0x0                      ; 无 SG_* 标志
```

> 说明：`Load command 0` 表明它是**第一条**加载命令；`cmdsize 72`（= 仅段头，对照 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 的 `cmdsize = 72 + 80*nsects`，此处 `nsects=0`）、`filesize 0`、`nsects 0`、`(---)` 四点共同坐实"纯保护段"的身份。

### 示例 2：32 位 vs 64 位 `__PAGEZERO` 字段对比

> [!warning] 示例输出为示意
> 数值为构造，仅示意 `vmsize` 在 32 位 / 64 位下的策略差异。

```text
# 64 位（arm64 / x86_64，LC_SEGMENT_64）        # 32 位（i386 / armv7，LC_SEGMENT）
      cmd LC_SEGMENT_64                              cmd LC_SEGMENT
  cmdsize 72                                     cmdsize 56
  segname __PAGEZERO                             segname __PAGEZERO
   vmaddr 0x0000000000000000                      vmaddr 0x00000000
   vmsize 0x0000000100000000   ; 4GB              vmsize 0x00001000     ; 4KB（仅一页）
  fileoff 0                                      fileoff 0
 filesize 0                                     filesize 0
  maxprot 0x00000000   (---)                     maxprot 0x00000000   (---)
 initprot 0x00000000   (---)                    initprot 0x00000000   (---)
   nsects 0                                       nsects 0
    flags 0x0                                       flags 0x0
```

> 说明：除 `cmd`（`0x19` vs `0x1`）、`cmdsize`（72 vs 56）、`vmsize`（4GB vs 4KB）外，其余字段两边一致。64 位拿整段低 4GB 当雷区，32 位受地址空间所限只封第一页。

### 示例 3：确认动态库里**没有** `__PAGEZERO`

```bash
otool -l /usr/lib/libSystem.B.dylib | grep -c __PAGEZERO    # 期望输出 0
otool -l /bin/ls                     | grep -c __PAGEZERO    # 期望输出 1（主可执行文件）
```

> [!warning] 示例输出为示意

```text
# 对 .dylib：
0
# 对主可执行文件 /bin/ls：
1
```

> 说明：`grep -c` 数 `__PAGEZERO` 出现次数。动态库（`MH_DYLIB`）输出 0——它不自带空指针守护，依赖主程序的 `__PAGEZERO`；主可执行文件（`MH_EXECUTE`）输出 1。这是从命令行快速区分"主程序 vs 库"的一个旁证。

### 示例 4：`-pagezero_size` 链接选项的效果

```bash
# 默认链接：64 位下自动生成 4GB __PAGEZERO
clang main.c -o app_default

# 显式去掉 __PAGEZERO（内核/特殊镜像场景；常规 arm64 app 这样做会无法加载）
clang main.c -o app_nopz -Wl,-pagezero_size,0x0

# 自定义大小（向页对齐取整）
clang main.c -o app_custom -Wl,-pagezero_size,0x1000
```

> [!warning] 示例输出为示意
> 在 macOS 上用 `otool -l <out> | grep -A2 __PAGEZERO` 验证；以下为预期对照。

```text
app_default :  segname __PAGEZERO  vmsize 0x100000000   ; 默认 4GB
app_nopz    :  (无 __PAGEZERO 段)                        ; 第 0 段直接是 __TEXT
app_custom  :  segname __PAGEZERO  vmsize 0x00001000     ; 被压到一页
```

> 说明：`-Wl,-pagezero_size,<v>` 经由 clang 把选项透传给链接器。`0x0` 移除该段（注意 arm64 内核会因缺 hard page zero 拒绝加载常规可执行文件）；非零值向页对齐取整。该选项最稳妥的用途是内核 / 裸机镜像，而非普通用户态程序。

## FAQ

> [!question] `__PAGEZERO` 占内存吗？占磁盘吗？4GB 不会把内存撑爆？
> 都**不占**。`filesize = 0` 决定它在磁盘上零体积（文件里只有一条 72 字节段头，没有任何数据跟随）。`vmsize = 4GB` 是**虚拟地址**保留量，不是物理内存——这段地址被标记为 `VM_PROT_NONE`、永远不会被任何物理页支撑（没有任何字节会被读写到这里，内核也不会为它分配实页）。所以哪怕写 4GB，进程的实际内存占用（RSS）一分不增。它纯粹是地址空间里一段"圈起来不用、谁碰谁崩"的记号。

> [!question] 为什么不只封地址 0 那**一页**，非要 4GB？
> 因为空指针的危害远不止"读地址 0"。`p->field`、`arr[i]`、`p->a.b.c` 在 `p==NULL` 时访问的是 `0 + 偏移`，偏移可能远超一页（大数组、深层结构体）。只封一页时，`NULL->[大偏移]` 会落到页外的可访问区、保护失效。封满低 4GB 后，只要偏移在 32 位范围内，访问必然落进 `__PAGEZERO` 被拦下；同时还顺带封死了"64 位指针被截断成 32 位"产生的野地址。64 位地址空间充裕、这 4GB 又零成本，所以一步到位封满。32 位进程因为总共才 4GB 地址，奢侈不起，才退而只封第一页。

> [!question] 动态库（`.dylib`）为什么不需要 `__PAGEZERO`？我自己的 framework 也不用加吗？
> 不用，也加不进去。空指针保护是**进程级、只需一份**的：主可执行文件（`MH_EXECUTE`）启动时，它的 `__PAGEZERO` 已经把整个进程地址空间的低端圈死，之后被 dyld 加载进来的所有 dylib / framework 自动共享这同一片保护。库被挂在高地址，根本不该、也不能再去占地址 0（多个段抢地址 0 会冲突）。所以你写 framework 时链接器**不会**给它生成 `__PAGEZERO`，这是对的——保护交给宿主进程的主程序即可。在一个 dylib 里看到 `__PAGEZERO` 反而是异常。

> [!question] 我把 `__PAGEZERO` 用 `-pagezero_size 0x0` 删了，程序还能跑吗？
> 看架构和用途。在**现代 arm64**（Apple Silicon）上，内核**强制**要求 64 位 ARM 可执行文件具备覆盖完整 4GB 的 hard page zero（加载时用 `vm_map_has_hard_pagezero(map, 0x100000000)` 校验），删掉或改小 `__PAGEZERO` 会让常规用户态可执行文件以 `LOAD_BADMACHO` **拒绝启动**。`-pagezero_size 0x0` 的正当用途主要是**内核开发 / 裸机镜像 / 需要把代码放到地址 0** 的特殊场景——这些镜像不走常规用户态加载路径。普通 app 不要动它。

> [!question] 崩溃日志里 `EXC_BAD_ACCESS at 0x0` 和 `__PAGEZERO` 是什么关系？
> 正是 `__PAGEZERO` 在起作用的证据。当代码解引用 NULL（或 NULL + 小偏移）时，访问地址落进 `__PAGEZERO` 这段无权限区，MMU 在地址翻译阶段拒绝，内核生成 Mach 异常 `EXC_BAD_ACCESS`（子码常为 `KERN_INVALID_ADDRESS`），转成 `SIGSEGV` 投给进程，崩溃报告记下 `Exception Type: EXC_BAD_ACCESS (SIGSEGV)` 和 `at 0x0000000000000000`（或一个小偏移地址）。能"干净地崩在地址 0",而不是软着陆读到垃圾继续跑，恰恰是 `__PAGEZERO` 把这片区域圈成雷区的功劳——它让空指针 bug **当场暴露**而非潜伏成更隐蔽的故障或漏洞。

## 小结

- `__PAGEZERO` 是可执行文件（`MH_EXECUTE`）的**首段**，用 `---` 无权限 + 大 `vmsize` 把地址空间最低端圈成雷区，**捕获空指针解引用**，让 bug 当场崩溃（`EXC_BAD_ACCESS`/`SIGSEGV`）而非软着陆。
- 它本质是一条普通 `LC_SEGMENT_64`：`vmaddr=0`、`vmsize`（64 位 4GB / 32 位 4KB）、`fileoff=0`、`filesize=0`、`nsects=0`、`maxprot=initprot=0`。`filesize=0` → 不占磁盘；永不实页化 → 不占物理内存。
- 64 位取 4GB 而非一页，是为了覆盖 `NULL + 大偏移` 与"32 位地址截断"两类危险，且 64 位空间充裕、几乎零成本；32 位受限只封第一页。
- 内核（XNU `mach_loader.c`）**强制**校验：通用"软"检查要求至少第一页（`0x1000`）不可访问，arm64 额外"硬"要求覆盖完整 4GB（`0x100000000`），否则 `LOAD_BADMACHO` 拒绝加载。
- 只存在于主可执行文件；动态库（`MH_DYLIB`）共享主程序的 `__PAGEZERO`，自身不带。`-pagezero_size <size>` 可调大小，`0x0` 删除该段（主要用于内核/特殊镜像，常规 arm64 app 删了会无法加载）。
- 漏洞视角：`__PAGEZERO` + 内核最低地址强制 + arm64 hard page zero + 硬件 PXN/SMAP 类机制，层层封死"在地址 0 映射可控页"的攻击路径，使空指针解引用在现代 macOS/iOS 上基本不可利用。
