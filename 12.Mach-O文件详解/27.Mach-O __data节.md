# 详解Mach-O(二十七)Mach-O __data节

> [!abstract] TL;DR
> **`__data`（全名 `__DATA,__data`）存放"已初始化、且初值非零的可写全局/静态变量"**，住在可读写（`rw-`）的 `__DATA` 段里。它是 [[18.Mach-O section]] 通用模型中最普通的一种节——节类型 `S_REGULAR`（`flags & SECTION_TYPE == 0x0`），没有任何特殊处理标志。
> 因为这些变量"有确定初值"，它们的字节必须**原样写进文件**（计入 `filesize`），加载时按文件内容映射到内存——这一点与"不占文件、运行时才零填充"的 [[28.Mach-O __bss节]] 形成最关键的对照。
> 因为 `__data` 可写，加载后内核把它的页标记为**写时复制（copy-on-write, COW）**：多个进程初始共享同一份只读映射，任一进程一旦写入某页，内核就为它**私有复制**该页。所以你代码里那些"带初值、会被改写"的全局/静态量，运行期每个进程看到的是自己的副本。
> 一句话定位：编译器按"**是否可写 + 是否有非零初值**"两个维度，把全局/静态变量分流到 `__data`（可写+非零初值）、`__bss`（可写+零/未初始化）、`__common`（可写+全局暂定定义）、`__const`（只读）四个去处——`__data` 是其中"可写且带料"的那一类。

## 概述与定位

```c
int          g_count = 5;           // 可写 + 非零初值 → __DATA,__data
static char  buf[16] = "hi";        // 可写 + 非零初值 → __DATA,__data
double       g_ratio = 1.5;         // 可写 + 非零初值 → __DATA,__data
```

上面这类"既要带初值、又允许运行时修改"的变量，编译链接后统统落在 `__data`。要理解它在整张 Mach-O 地图里的位置，得把"段 / 节"两层和"读写权限"一起看：

- **段这一层**：`__data` 的宿主是 [[14.Mach-O __DATA]] 段，权限 `rw-`（可读可写）。[[11.Mach-O Segments]] 把进程地址空间切成若干"一段一套权限"的页对齐区域，`__DATA` 就是那个**可写区**——所有需要运行时改写的数据（可写全局量、指针表、Objective-C 运行时可写元数据等）都装进它。
- **节这一层**：`__data` 是 [[18.Mach-O section]] 描述的通用 `section_64` 模型的一个实例，且是**最朴素的一种**——类型 `S_REGULAR`，不像 `__stubs`（`S_SYMBOL_STUBS`）会复用 `reserved` 字段、也不像 `__bss`（`S_ZEROFILL`）不占文件。它的字节就是变量初值的二进制快照，原样躺在文件里。

可以这样记 `__DATA` 段内"可写数据四兄弟"的分工，它们都继承同一套 `rw-` 权限，区别只在"有没有初值、初值是不是零、是不是暂定定义"：

| 节 | 装什么（C 语言视角） | 有初值? | 占文件? | 节类型 |
|---|---|---|---|---|
| `__data` | `int x = 5;`（带**非零**初值的可写量） | 是（非零） | **是** | `S_REGULAR` |
| `__bss` | `static int i;`（文件内**未初始化/零初值**的可写静态量） | 否（零） | **否** | `S_ZEROFILL` |
| `__common` | `int i;`（全局作用域**暂定定义**，未 `extern`） | 否（零） | **否** | `S_ZEROFILL` |
| `__const` | `const` 数据（只读常量；需重定位的住 `__DATA,__const`） | 是 | 是 | `S_REGULAR`（只读段内） |

> [!note] 节名总要带段名：`__DATA,__data`
> 和所有节一样，`__data` 几乎从不单独出现，而是写作 `段名,节名` 的二元组 `__DATA,__data`。原因有二：① 节名只在 16 字节内唯一，不同段理论上可有同名节（如确实存在 `__TEXT,__const` 与 `__DATA,__const` 两个 `__const`）；② `section_64` 结构本身冗余回填了 `segname`，单看一个节头就能知道它属于哪个段。`otool -s __DATA __data` 这类命令也要求**段名 + 节名一起给**，只给 `__data` 工具不认。

## 核心原理与字段详解

### 1. 内容：带"非零初值"的可写全局/静态变量

`__data` 收容的是同时满足两个条件的变量：**① 可写**（运行时允许修改，所以不能进只读的 `__TEXT`）、**② 有非零初值**（程序员显式写了初始值，且该值不全是 0）。典型来源：

- 带初值的全局变量：`int g_count = 5;`、`long g_flags = 0x1234;`
- 带初值的文件内静态变量：`static double pi = 3.14159;`、`static char buf[16] = "hi";`
- 带初值的可写数组 / 结构体实例：`int table[4] = {1,2,3,4};`、`struct Cfg cfg = { .timeout = 30 };`

为什么这些字节**必须存进文件**？因为初值是"确定且非零"的具体二进制内容，加载器没法凭空"算"出来——它只能从文件里把这串字节原样读出、映射到 `addr` 指定的虚拟地址。于是 `__data` 的 `size` 既计入**内存**占用、也计入**文件**占用（`filesize` 包含它）。这正是它和 `__bss` 的根本差异：`__bss` 的初值"恒为 0"，是个可由内核统一零填充生成的规律值，所以不必在文件里逐字节存一遍。

> [!note] 临界情形：初值恰好为 0 的可写量会去哪？
> 严格说 `__data` 的判据是"**非零**初值"。像 `int z = 0;`、`static int arr[100] = {0};` 这种"显式初始化为 0"的可写量，初值与"未初始化默认 0"无法区分，编译器通常把它们也优化进**零填充**节（`__bss`/`__common`）而非 `__data`，以省下文件空间——毕竟"全 0"的内容内核能零填充生成，没必要在磁盘上存一片 0。所以 `__data` 里真正出现的，是初值**含非零字节**的那些变量。

### 2. 节类型 `S_REGULAR`：最普通、无特殊处理

`__data` 的 `flags` 低 8 位（`flags & SECTION_TYPE`）是 `S_REGULAR`（值 `0x0`），来自 `<mach-o/loader.h>`：

```c
#define SECTION_TYPE   0x000000ff   /* 256 种节类型掩码（低 8 位，互斥）*/
#define S_REGULAR      0x0          /* regular section（普通节，无特殊处理）*/
#define S_ZEROFILL     0x1          /* zero fill on demand section（按需零填充，__bss 用）*/
```

`S_REGULAR` 的语义就是"**普通节，内容原样存文件、加载时直接映射**"，链接器和 `dyld` 不对它做任何类型相关的特殊处理（不像 `S_CSTRING_LITERALS` 会去重、`S_SYMBOL_STUBS` 会按 `reserved2` 算条目、`S_ZEROFILL` 会零填充）。`__text`、`__const` 也都是 `S_REGULAR`——区别不在节类型，而在**所属段的权限**（`__text`/`__const` 在 `r-x`/`r--` 段、`__data` 在 `rw-` 段）和**属性位**（`__text` 还带 `S_ATTR_PURE_INSTRUCTIONS`，`__data` 通常**无任何属性位**，`flags == 0x00000000`）。

> [!note] `__data` 的 `flags` 为何常是 `0x00000000`
> 拆开看：类型 `= flags & 0xff = 0x00`（`S_REGULAR`），属性 `= flags & 0xffffff00 = 0x00000000`（无任何 `S_ATTR_*`）。对比代码节 `__text` 的 `0x80000400`（`S_REGULAR` + `S_ATTR_PURE_INSTRUCTIONS` + `S_ATTR_SOME_INSTRUCTIONS`），`__data` 干干净净——它既不是纯指令、也无需禁死代码消除之类修饰，就是一片"普通可写数据"。`reserved1/2/3` 也全为 0（它不是符号桩/指针节，无需复用 `reserved` 联动间接符号表）。

### 3. 占文件空间：与 `__bss` 零填充的硬对比

这是理解 `__data` 性格的核心。把它和 `__bss` 并排看"内存 vs 文件"两本账：

| 维度 | `__data`（`S_REGULAR`） | `__bss`（`S_ZEROFILL`，见 [[28.Mach-O __bss节]]） |
|---|---|---|
| 内容是否确定 | 确定的非零初值 | 恒为 0（规律值，无需逐字节存） |
| `size` 计入内存? | 是 | 是 |
| **是否占文件（计入 `filesize`）** | **是**，字节原样躺在文件里 | **否**，文件里没有它的真实数据 |
| `offset` 含义 | 指向文件中本节真实的初始化字节 | 字段虽填值，但那里**没有**属于本节的真实字节 |
| 加载方式 | 内核从文件映射该页 | 内核运行时零填充该区 |

链接器布局 `__DATA` 段时，常把零填充节（`__bss`/`__common`）安排在段的**末尾**——这样段的 `filesize`（文件里真实占的字节，到 `__data` 等占文件节为止）会**小于** `vmsize`（内存里要占的字节，含末尾零填充区），二者之差正是零填充节的大小。换句话说，`vmsize > filesize` 这个现象，`__data` 不贡献（它内存=文件等量占用），贡献者是它的邻居 `__bss`/`__common`。判断一个节是否占文件，永远看它的**类型**（是不是某种 zerofill），而不是看 `offset` 是否非零（详见 [[18.Mach-O section]] 与 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。

> [!note] 一个直觉：磁盘省一点，每个进程的内存却要各算各的
> `__bss` 不占文件是"在磁盘上省"——一千个 0 不必存。但 `__data` 占文件是"必要的代价"——非零初值没法压缩成规律。两者都在 `__DATA` 段、都可写，所以加载后两者的页**都按 COW 管理**：磁盘占用是"一份"，运行时内存却可能因为多进程各自写入而"每进程一份私有副本"。

### 4. 写时复制（COW）：每进程私有副本

`__data` 可写，于是它的页享受/受制于**写时复制**机制（与只读 `__TEXT`/`__cstring` 的"跨进程共享一份"恰相反）：

1. **加载初期**：内核把 `__DATA` 段（含 `__data`）按文件内容映射进各进程地址空间，多个加载了同一 dylib 的进程**逻辑上共享**这份映射，页被标记为 COW（写时复制）。
2. **首次写入**：某进程一旦写 `__data` 里的某个变量（例如 `g_count = 6;`），内核**为该进程私有复制**被写的那个物理页（4KB / 16KB），此后该进程改的是自己的副本，不影响其他进程。
3. **结果**：每个进程对 `__data` 的修改互不可见——这正是"全局变量在不同进程里各是各的"的底层实现。

> [!note] `dyld` 的 rebase/bind 也会"弄脏"`__data`
> `__data` 里若存有**指针类初值**（如 `void *p = &g_other;`、函数指针表、含指针的结构体），这些指针在文件里存的是"假设镜像加载到基址 0"时的地址。开启 ASLR 后，`dyld` 必须遍历这些位置、统一叠加 slide（rebase），并把指向外部符号的指针绑定到实际地址（bind / 链式 fixups）。**这个"读改写"动作本身就会弄脏（dirty）相关页**，触发 COW。为减少启动时被弄脏的页数，现代 Apple 工具链把"注定会被 fixup 弄脏"的可写数据进一步聚到 **`__DATA_DIRTY`** 段、把"fixup 后可只读共享"的聚到 **`__DATA_CONST`** 段——本质都是围绕"少脏页、多共享"做的页布局优化（dyld 共享缓存尤其受益）。普通 `__data` 仍是放置常规可写数据的默认去处。

### 5. 与 `__bss` / `__common` / `__const` 的分流规则

编译器对每个全局/静态变量，按"**可写性 + 初值情况**"两个维度路由到下面之一：

```
                       ┌─ 有非零初值 ──────────────→ __DATA,__data      （S_REGULAR，占文件）
        ┌─ 可写 ───────┤
        │              ├─ 零初值/未初始化(文件内静态) → __DATA,__bss     （S_ZEROFILL，不占文件）
变量 ───┤              └─ 全局暂定定义(int i; 未extern) → __DATA,__common  （S_ZEROFILL，不占文件）
        │
        └─ 只读(const) ┬─ 不需重定位的常量 ─────────→ __TEXT,__const     （只读段，可跨进程共享）
                       └─ 需重定位的常量(含指针) ───→ __DATA,__const     （可写段内，fixup 后可转只读）
```

逐条对照：

- **`__data`（可写 + 非零初值）**：`int x = 5;`、`static char b[]="hi";`。本篇主角。
- **`__bss`（可写 + 文件内零/未初始化）**：`static int i;`、`static int arr[100];`。零填充、不占文件，见 [[28.Mach-O __bss节]]。
- **`__common`（可写 + 全局暂定定义）**：`int i;`（写在函数外、未加 `extern`、未给初值）。这是 ANSI C "tentative definition（暂定定义）"概念的落地——多个编译单元若都写 `int i;`，链接器把它们合并成一个，零初始化，见 [[29.Mach-O __common节]]。
- **`__const`（只读常量）**：`const int x = 3;` 进 `__TEXT,__const`（纯只读、可跨进程共享）；而 `const` 但含需重定位引用的（如 `const char *msg = "hi";` 里那个指针）会进 `__DATA,__const`（先在可写段，dyld fixup 完成后可转只读），见 [[21.Mach-O __const节]]。

> [!note] `__bss` 与 `__common` 的细微差别
> 两者都零填充、都不占文件、都在 `__DATA` 段，区别在符号语义：`__bss` 装的是**文件内（static）未初始化静态变量**（`static int i;`，作用域限本文件）；`__common` 装的是**全局作用域的暂定定义**（`int i;`，可被其他文件 `extern` 引用、可由链接器跨单元合并）。一句话：`__bss` 是"我自己的零"，`__common` 是"大家共用、还没人给初值的零"。

### 6. 字节序对多字节变量的影响

`__data` 里多字节变量（`int`/`long`/`double`/指针…）的**字节排布顺序由目标架构的字节序决定**。Apple 现役架构 **arm64 与 x86_64 一律小端（little-endian）**，即"低位字节存在低地址"：

以 `int g = 0x12345678;` 为例，它在 `__data` 文件/内存里的 4 个字节是：

| 地址 | +0 | +1 | +2 | +3 |
|---|---|---|---|---|
| 字节（小端） | `0x78` | `0x56` | `0x34` | `0x12` |

所以你用 `otool -s` / `xxd` dump `__data` 时，多字节量看起来"**像是反着的**"——`int 5`（`0x00000005`）显示为 `05 00 00 00`，`int 0x12345678` 显示为 `78 56 34 12`。读取要点：

- **多字节标量按字节序重排**：解析时要按目标架构的字节序还原（小端就把 dump 出的字节倒序拼回逻辑值）。
- **单字节数据不受影响**：`char`、字符串内容、`uint8_t` 数组按自然顺序排，`"hi\0"` 就是 `68 69 00`，不会"反过来"。
- **变量地址恒为最低字节地址**：无论字节序如何，多字节变量的地址都指向它最低（在内存里最靠前）的那个字节。
- **Mach-O 头有字节序指示**：理论上 Mach-O 可描述大端目标（靠 magic / `cputype` 区分），但当前 Apple 支持的架构全是小端。解析 `__data` 原始字节前，应先看 Header 的 `magic` 判定字节序（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 的架构判定）。

### 7. C 变量到 `__data` 的映射示例（综合演示）

把不同写法的变量放在一起，看编译器如何分流，以及落进 `__data` 的那些在文件里长什么样：

```c
// ① 带非零初值的可写全局     → __DATA,__data
int    g_count = 5;                 // 文件字节: 05 00 00 00            （小端 int）
long   g_mask  = 0x1122334455667788;// 文件字节: 88 77 66 55 44 33 22 11（小端 long）
double g_ratio = 1.5;               // 文件字节: 00 00 00 00 00 00 F8 3F（IEEE754 小端）
char   g_name[8] = "geese";         // 文件字节: 67 65 65 73 65 00 00 00（"geese\0\0\0"，单字节不反转）

// ② 带非零初值的可写静态量     → __DATA,__data
static char buf[16] = "hi";         // 文件字节: 68 69 00 ...（"hi\0" 后补 0 到 16 字节）

// ③ 可写但零/未初始化         → __DATA,__bss（不占文件，见 28 篇）
static int s_cache;                 // 无文件字节，运行时零填充
static int s_zeros[100] = {0};      // 显式置 0，通常也归零填充节，不占文件

// ④ 全局暂定定义（未 extern、未给初值）→ __DATA,__common（不占文件，见 29 篇）
int    g_tentative;                 // 暂定定义，零初始化，链接器跨单元合并

// ⑤ 只读常量                  → __TEXT,__const（可跨进程共享，见 21 篇）
const int  k_limit = 256;           // 纯只读、不可改

// ⑥ extern 声明（仅声明，不产生定义、不占任何节）
extern int g_count;                 // 引用别处的 g_count，本单元不分配存储
```

要点回顾：只有 ① ② 这种"**可写 + 非零初值**"才进 `__data` 并占文件；零/未初始化的去零填充节（`__bss`/`__common`）不占文件；只读的去 `__const`；纯 `extern` 声明不产生存储。

## 实操：用工具查看

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下所有命令输出均基于结构知识构造，**实际数值（地址、偏移、字节）请以你 macOS 机器上的 `otool` 为准**。

### 示例 1：`otool -s __DATA __data` dump 原始字节

`otool -s 段名 节名` 以"虚拟地址 + 十六进制字节"逐行 dump 指定节内容：

```bash
otool -s __DATA __data /bin/ls          # 裸十六进制 dump __DATA,__data
otool -s -v __DATA __data /bin/ls       # -v 附带更友好的显示
```

```text
/bin/ls:
Contents of (__DATA,__data) section
0000000100008000  05 00 00 00 68 69 00 00 88 77 66 55 44 33 22 11   ....hi...wfUD3".
0000000100008010  00 00 00 00 00 00 f8 3f 00 00 00 00 00 00 00 00   .......?........
```

> 说明：左列是该字节的虚拟地址（从节 `addr` 起算）。`05 00 00 00` 是小端的 `int 5`；`68 69 00` 是 `"hi\0"`（单字节不反转）；`88 77 66 55 44 33 22 11` 是小端的 `long 0x1122334455667788`；`00 00 00 00 00 00 f8 3f` 是 `double 1.5`（IEEE754 小端）。这些都带确定非零初值，故原样存进文件——印证 `__data` 的类型 `S_REGULAR` 且占文件。

### 示例 2：`otool -l` 看 `__data` 节头

`otool -l` 把每个段命令后的节头逐个打印成 `Section` 块；用 `grep` 锁定 `__data`：

```bash
otool -l /bin/ls | grep -A 12 "sectname __data"   # 看 __data 完整节头
otool -lv /bin/ls                                  # -v 把 flags 显示成符号名
```

```text
Section
  sectname __data
   segname __DATA
      addr 0x0000000100008000      ; 节虚拟地址（落在 __DATA 段范围内）
      size 0x0000000000000020      ; 32 字节
    offset 32768                   ; 文件偏移（非零，且这里有真实初始化字节）
     align 2^3 (8)                 ; 存储值 align=3，实际 8 字节对齐（指针/double 对齐）
    reloff 0                       ; 已链接产物，无节级重定位
    nreloc 0
     flags 0x00000000              ; 类型 S_REGULAR(0x0) + 无任何属性位
 reserved1 0                       ; 非符号桩/指针节，不复用
 reserved2 0
 reserved3 0
```

> 说明：`flags 0x00000000` 拆开 = 类型 `S_REGULAR`（`&0xff=0`）+ 属性为空——这是普通可写数据节 `__data` 的标准标记，干净无修饰。`offset 32768` 非零且**指向文件里真实的初始化字节**（与 `__bss` 的 `offset` 不指真实数据相反）；`reserved*` 全 0 因为 `__data` 不靠间接符号表联动。

### 示例 3：`size -lm` 看 `__data` 在段里的体积与"占文件 vs 占内存"

```bash
size -l -m /bin/ls    # -m: 按段分组列节；-l: 含完整明细
```

```text
Segment __DATA: 16384 (vmaddr 0x100008000 fileoff 32768)
    Section __data: 32 (addr 0x100008000 offset 32768)     ; S_REGULAR，占文件
    Section __bss:  64 (addr 0x100008020 offset 0)         ; S_ZEROFILL，offset 不指真实数据、不占文件
    Section __common: 8 (addr 0x100008060 offset 0)        ; S_ZEROFILL，同样不占文件
    total 104
```

> 说明：`__data`（32 字节）有真实文件偏移、计入 `filesize`；其后的 `__bss`（64）/`__common`（8）零填充、`offset` 标 0、不占文件——它们让 `__DATA` 段的 `vmsize > filesize`（内存 104，文件实占到 `__data` 末尾约 32+ 字节）。这直观展示了"`__data` 占文件、零填充邻居不占文件"的分工。

## FAQ

> [!question] `__data` 和 `__bss` 都在 `__DATA` 段、都可写，到底差在哪？
> 差在"**初值情况 + 占不占文件**"。`__data` 装"有**非零**初值"的可写量（`int x = 5;`），初值是确定的具体字节，**必须原样存进文件**，加载时按文件映射；`__bss` 装"零初值/文件内未初始化"的可写量（`static int i;`），初值恒为 0、可由内核统一零填充生成，所以**不占文件**，运行时才零填充。判断哪个：看变量有没有非零初值——有就 `__data`、没有（或显式置 0）就归零填充节。两者运行期都按写时复制（COW）管理，每进程私有副本。

> [!question] 为什么 `__data` 里的 `int 5` dump 出来是 `05 00 00 00` 而不是 `00 00 00 05`？
> 因为 Apple 的 arm64 / x86_64 都是**小端（little-endian）**：多字节标量"低位字节存在低地址"。`int 5` 的逻辑值是 `0x00000005`，最低位字节 `0x05` 排在最前（最低地址），于是文件/内存里是 `05 00 00 00`。同理 `0x12345678` 存为 `78 56 34 12`。注意**单字节数据不受影响**——字符串 `"hi\0"` 就是 `68 69 00`，不会反转。逆向解析多字节量时要按小端把字节倒序拼回逻辑值。

> [!question] `__data` 是可写的，那两个进程改同一个全局变量会互相影响吗？
> 不会。`__DATA` 段（含 `__data`）可写，内核加载时把它的页标记为**写时复制（COW）**：初始多进程逻辑共享同一份映射，但**任一进程一旦写入某页，内核就为它私有复制该页**，此后各改各的副本、互不可见。这正是"全局变量在不同进程里各是各的"的底层机制。代价是：被写到的页会从"共享"变成"每进程一份"，增加内存占用——这也是 Apple 引入 `__DATA_DIRTY`/`__DATA_CONST` 做页布局优化、尽量少弄脏页的动机。

> [!question] `int i = 0;`（显式初值 0）会进 `__data` 吗？
> 通常**不会**。`__data` 的判据是"**非零**初值"。显式置 0 的可写量（`int z = 0;`、`int a[100] = {0};`）其初值与"未初始化默认 0"无法区分，编译器一般把它们也优化进**零填充**节（`__bss`/`__common`），以省下文件空间——毕竟"全 0"内核能零填充生成，没必要在磁盘上存一片 0。所以真正出现在 `__data` 里的，是初值**含非零字节**的变量。想强制某个 0 值占文件几乎没有意义，按"非零才进 `__data`"理解即可。

> [!question] `__data`、`__DATA`、`__DATA_CONST`、`__DATA_DIRTY` 这些名字怎么区分？
> `__DATA`（大写、双下划线开头）是**段名**，`__data`（小写）是它里面的**节名**——节名总写作 `__DATA,__data`。`__DATA_CONST` 与 `__DATA_DIRTY` 是另外两个**段**：`__DATA_CONST` 聚"dyld fixup 完成后可转只读、可跨进程共享"的数据（少脏页）；`__DATA_DIRTY` 聚"注定会被 fixup 弄脏"的可写数据（把脏页集中、减少零散弄脏）。它们都是围绕"少脏页、多共享"的页布局优化，dyld 共享缓存尤其受益。普通可写、带非零初值的全局/静态量，默认仍落在 `__DATA,__data`。

## 小结

- `__data`（`__DATA,__data`）存"**已初始化、初值非零的可写全局/静态变量**"，类型 `S_REGULAR`、属性为空（`flags` 常为 `0x00000000`），住在 `rw-` 的 `__DATA` 段。
- **有非零初值 → 必须占文件**：字节原样存进文件（计入 `filesize`）、加载时按文件映射；这与零填充、不占文件的 `__bss`（`vmsize > filesize` 的成因）形成最关键对照。
- **可写 → 写时复制**：加载后页按 COW 管理，每进程一旦写入即获私有副本；dyld 的 rebase/bind 也会弄脏页，故有 `__DATA_DIRTY`/`__DATA_CONST` 的页布局优化。
- **分流规则**：编译器按"可写性 + 初值"路由——可写+非零初值 → `__data`；可写+零/未初始化 → `__bss`；可写+全局暂定定义 → `__common`；只读 → `__const`。
- **字节序**：arm64/x86_64 小端，`__data` 里多字节量按"低位字节在低地址"排布（`int 5` → `05 00 00 00`），单字节/字符串不反转；解析原始字节须按目标架构字节序还原。
