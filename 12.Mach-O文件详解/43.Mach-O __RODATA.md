# 详解Mach-O(四十三)Mach-O __RODATA

> [!abstract] TL;DR
> **`__RODATA`（Read-Only Data，只读数据）在概念上指"专门存放只读数据的段"**，对标 ELF 世界里大名鼎鼎的 **`.rodata`**：字符串字面量、`const` 全局常量、编译期固定不变的常量表，统统映射成只读内存，写入即崩。
> 但要特别强调一点——**`__RODATA` 并不是 Mach-O 的标准必备段**。Mach-O 真正"雷打不动"的三大段是 **`__TEXT` / `__DATA` / `__LINKEDIT`**（再加一个保护性的 `__PAGEZERO`）。在 **Apple 官方工具链（clang + ld64/lld）默认产物**里，只读数据并不会单列成 `__RODATA`，而是落在 **`__TEXT,__const`**（见 [[21.Mach-O __const节]]）、**`__TEXT,__cstring`**（见 [[20.Mach-O __cstring节]]）这类只读节，或者——若是"链接后才固定、需重定位"的指针型常量——落在安全加固的 **`__DATA_CONST`**（见 [[15.Mach-O __DATA_CONST]]）里。
> `__RODATA` 这个**字面段名**真正出现的场合很窄：它是 **LLVM/clang 在 Mach-O 目标上实现 `#pragma clang section rodata="__RODATA,..."` / `__attribute__((section("__RODATA,...")))` 时采用的约定段名**，多见于**嵌入式 / 裸机 / 自定义链接脚本**等需要精确控制内存布局的场景。绝大多数 macOS/iOS 二进制 `otool -l` 里**根本看不到** `__RODATA` 段。
> 不论它叫什么名字，背后的思想都和全系列一脉相承——**用段的内存权限（只读映射）保护"运行期不该变"的数据**：防篡改、可跨进程共享、对 CPU 缓存友好。作为本系列正文的**收官篇**，它正好把"以段为权限单位保护数据"这条主线收回原点。

## 概述与定位

只读数据"到底放哪"，在 Mach-O 里**从来不是唯一答案**——这正是本篇要厘清的核心。同一类"运行期不变的常量",可能出现在四个不同的位置:

- **`__TEXT,__const`**:不含重定位的纯只读常量(见 [[21.Mach-O __const节]]),随只读、可执行的 `__TEXT` 段一起映射,**永远只读、可被所有进程共享**;
- **`__TEXT,__cstring`**:C 字符串字面量(见 [[20.Mach-O __cstring节]]),静态链接器还会做**去重合并**(coalescing);
- **`__DATA_CONST`**:那些"编译期是常量、但内容含**指针**、要等 dyld 在加载期重定位/绑定后才固定"的常量(见 [[15.Mach-O __DATA_CONST]])——**加载期可写、绑定完只读**(SG_READ_ONLY);
- **`__RODATA`**:某些工具链 / 平台约定下,被**显式命名**出来的独立只读数据段。

本篇把 `__RODATA` 当作"**只读数据段**"这一**一般化概念**来讲,同时把它和上面三个"真实去处"的关系彻底讲透——**这恰恰是逆向 / 链接实践里最容易混淆的一处**。作为本系列正文的收官篇,它也呼应了贯穿全系列(从 [[11.Mach-O Segments]] 起)的主题:**用段 / 节的权限模型,保护不同性质的数据**。`__TEXT` 只读且可执行、`__DATA` 可读写、`__DATA_CONST` 先写后只读、`__RODATA` 纯只读——每一种权限组合,都是为某一类数据的安全 / 共享 / 性能需求量身定制。

> [!note] 一句话抓住本质
> **`__RODATA` 是"概念正确、但在 Apple 默认工具链里通常不出现"的段名。** 看到它,基本可断定是 **非 Apple 默认链接配置**(自定义 `#pragma clang section` / `__attribute__((section))` / 嵌入式链接脚本)的产物;在标准 macOS/iOS 二进制里,只读数据请到 **`__TEXT,__const` / `__TEXT,__cstring` / `__DATA_CONST`** 三处去找,而不是 `__RODATA`。

## 核心原理与字段详解

### 1. 基本作用:只读数据段承载什么

无论叫 `.rodata`(ELF)、`__TEXT,__const`(Mach-O 默认)还是 `__RODATA`(自定义),"只读数据"这一**逻辑角色**承载的内容是高度一致的:

1. **字符串字面量**:源码里直接写出的 `"hello"` 这类常量字符串。Mach-O 默认把它们放进 `__TEXT,__cstring`,且**静态链接器会去重**——同一个字符串在多个编译单元出现,最终只留一份(见 [[20.Mach-O __cstring节]])。
2. **`const` 全局 / 静态常量**:用 `const` 修饰、编译期就能定稿的全局或静态变量。**关键细节**:只有**不含重定位**(nonrelocatable)的常量才能进纯只读段;一旦常量里含**指针**(指向其它代码 / 数据,地址受 ASLR 影响),它就**进不了**纯 `.rodata`/`__TEXT,__const`,而要进"可重定位的只读"区(ELF 的 `.data.rel.ro` / Mach-O 的 `__DATA_CONST`)——详见下面第 4 节。
3. **编译期常量数据 / 只读表**:跳转表、查找表、字体 / 资源的内嵌只读数据等,编译期确定、运行期绝不修改。

### 2. 内存保护、共享与缓存:只读映射的三重收益

把这类数据集中映射为**只读**,直接拿到三项好处——这也是"用段权限保护数据"主题的具体兑现:

- **只读 → 防篡改**:操作系统按段头里的 `initprot` 把这片虚拟内存标成不可写,任何写入(无论是程序 bug 还是攻击者拿到写原语后想改常量)都会触发 `EXC_BAD_ACCESS`(保护异常),从而**保护常量完整性**。这与 [[15.Mach-O __DATA_CONST]] 用 `mprotect` 把 GOT 锁只读防 GOT 劫持,是同一类防御思想的不同强度版本。
- **只读 → 可跨进程共享**:正因为这片内存"谁都不会写",内核可以让**同一份物理页**被所有运行该二进制 / 加载该库的进程**共享映射**(copy-on-write 下因从不写而永不分裂)。N 个进程跑同一个程序,只读数据只占一份物理内存——这正是 `__TEXT` 段(只读)能共享、而 `__DATA` 段(可写)每进程各持一份的根本原因。
- **只读 → 缓存友好**:只读数据连续紧凑排布、又不会被写脏,对 CPU 的指令 / 数据缓存和 TLB 都更友好,减少缓存行失效与写回开销。

> [!note] 为什么"含指针的常量"不能进纯只读段
> 一个 `const char *msg = "hi";`,变量 `msg` 本身的值是**另一个对象的地址**。在启用 ASLR / PIE 的世界里,这个地址**编译期并不确定**,要等加载期重定位(rebase,叠加 slide)才能定稿——也就是说**加载期必须能写它一次**。纯只读段从映射起就不可写,放不下这种"需修补一次"的数据。解决办法有二:① 写成 `const char * const msg`(指针**和**它指向的内容都 const),让编译器尽量把数据沉到只读区;② 由链接器把这类"只读但需重定位"的数据放进**加载期可写、修补完再改只读**的特殊区——ELF 叫 `.data.rel.ro`(归 `PT_GNU_RELRO`),Mach-O 就是 **`__DATA_CONST`**(带 `SG_READ_ONLY`,见 [[15.Mach-O __DATA_CONST]])。`__RODATA` 作为**纯只读**段,承载的应是**不含重定位**的那部分常量。

### 3. 与标准段的关系:`__RODATA` 非 Mach-O 必备段(重点)

**这是本篇最需要讲清楚、也最容易被误解的一点。**

Mach-O 的**标准 / 惯例段**是:

- **`__PAGEZERO`**:进程地址空间最低端的不可访问页(64 位下通常 4GB),专门让**空指针 / 野指针解引用**落进来直接触发崩溃,是一道安全护栏;
- **`__TEXT`**:**只读 + 可执行**段,装机器码(`__text`)**和只读常量**(`__const`/`__cstring`/`__literal4`/`__literal8`/`__stubs` 等)。编译器为每个可执行文件**至少**创建一个只读 `__TEXT` 段;因只读,可直接从文件映射一次、被所有进程共享;
- **`__DATA`**:**可读写**段,装可变全局 / 静态变量(`__data`/`__bss`)等,每进程各持一份;
- **`__LINKEDIT`**:**只读**段,装动态链接器要用的原始数据——符号表、字符串表、重定位 / 绑定信息、代码签名等,永远是**最后一个**段。
- (现代加固)**`__DATA_CONST`** / arm64e 的 **`__AUTH_CONST`**:从 `__DATA` 里切出来的"绑定后只读"子集。

**`__RODATA` 不在这份名单里。** Mach-O 的段 / 节命名只是**约定**(`__` 前缀 + 段名大写、节名小写),**并非强制**——格式本身允许任意段名。因此:

- **Apple 默认工具链**(clang 默认配置 + ld64 / 现代 lld)产出的 macOS/iOS 二进制,**通常不会**单列 `__RODATA`,只读数据按上面规则进 `__TEXT,__const` / `__TEXT,__cstring`(纯只读、无重定位)或 `__DATA_CONST`(只读但需重定位)。
- 工具(静态链接器、分析器)判断"一个节该怎么处理",历来更看**节的类型(type)与属性(attributes)**,而非段 / 节的名字字符串——名字主要是给人看的约定。

那 `__RODATA` 到底**什么时候**才会出现?见下一节。

> [!note] Apple 文档对"尽量进 __TEXT"的建议
> Apple 在性能优化指南里反复强调:**把尽可能多的全局变量声明成 `const`,好让它们从可写的 `__DATA` 沉到只读的 `__TEXT,__const`**——只读数据能被多进程共享、不占各进程私有内存,对框架 / 共享库的内存足迹尤其关键。换言之,Apple 的默认导向是"只读数据进 `__TEXT`",而不是"另立 `__RODATA`"。

### 4. `__RODATA` 何时真正出现:`#pragma clang section` 与 `section` 属性

`__RODATA` 这个**字面段名**最权威、最常见的来源,是 **LLVM/clang 对 `#pragma clang section` 指令在 Mach-O 目标上的实现**。当你用该 pragma(或等价的 `__attribute__((section(...)))`)**显式指定**数据该进哪个段 / 节时,clang 对"只读数据(rodata)"采用的**约定段名就是 `__RODATA`**。

LLVM 内部把这些 pragma 翻译成 IR 上的函数 / 全局属性,其 Mach-O 形态形如:

```text
"rodata-section" = "__RODATA,__myrodata1"   ; 只读数据 → __RODATA 段
"data-section"   = "__DATA,__mydata1"       ; 可写数据 → __DATA 段
"bss-section"    = "__BSS,__mybss1"         ; 零填充   → __BSS 段
"relro-section"  = "__RELRO,__myrelro2"     ; 只读但需重定位
; 隐式 text 段:"__TEXT,__mytext1"
```

对应的源码写法(注意 **Mach-O 的 `section` 属性硬性要求 `段名,节名` 逗号分隔**,只给节名会编译报错):

```c
// 写法一:逐个变量指定 section —— 段名,节名 必须成对、逗号分隔
__attribute__((section("__RODATA,__myrodata")))
const int kLookupTable[4] = {1, 2, 3, 4};

// 写法二:pragma 影响一整段声明,再用空串复位
#pragma clang section rodata="__RODATA,__myrodata"
const int a = 1;
const int b = 2;
#pragma clang section rodata=""   // 复位回默认
```

```c
// 反例:Mach-O 上只给裸节名 → 后端致命错误
// "a mach-o section specifier requires a segment and section separated by a comma"
// __attribute__((section("myrodata"))) const int bad = 42;   // ✗ 编不过
```

由此可总结 `__RODATA` 的**出现条件**:

| 场景 | 是否常见 `__RODATA` | 只读数据实际去处 |
|---|---|---|
| 普通 macOS/iOS App、framework(clang 默认) | **几乎不出现** | `__TEXT,__const` / `__TEXT,__cstring` / `__DATA_CONST` |
| 显式 `#pragma clang section rodata="__RODATA,..."` | **出现**(你点名要的) | 你指定的 `__RODATA,<节>` |
| 显式 `__attribute__((section("__RODATA,...")))` | **出现** | 同上 |
| 嵌入式 / 裸机 / 固件 / 自定义链接脚本 | **较常见** | 按链接脚本把只读数据归入独立 `__RODATA`,精确控制布局 |
| 某些非 Apple / 实验性后端、平台移植约定 | 视实现而定 | 可能仿照 ELF `.rodata` 单立 `__RODATA` |

> [!note] 架构差异 / 平台差异
> **是否出现独立 `__RODATA` 段,取决于编译器与链接器的配置(pragma / 属性 / 链接脚本),而非 Mach-O 格式的强制要求。** 多数 macOS/iOS 二进制并不单列此段,而把只读数据并入 `__TEXT`(纯只读)或 `__DATA_CONST`(需重定位的只读)。无论是否单列,页大小仍遵循 **arm64 = 16KB、x86_64 = 4KB** 的对齐规则(只读段必须在页边界结束,才能独立设权限——这点与 [[15.Mach-O __DATA_CONST]] 中"只读段不能与可写数据共享物理页"的约束同源)。

### 5. 概念对标 ELF:`.rodata` 与 `.data.rel.ro`

如果你熟悉 Linux/ELF,`__RODATA` 的概念几乎可以一一对位,但要分清**两种**只读:

| Mach-O | ELF 对应 | 含义 | 权限模型 |
|---|---|---|---|
| `__TEXT,__const` / `__TEXT,__cstring` / `__RODATA`(自定义) | `.rodata` | **不含重定位**的纯只读常量、字符串字面量 | 从映射起即只读,全程不变,可共享 |
| `__DATA_CONST`(`SG_READ_ONLY`) | `.data.rel.ro`(归 `PT_GNU_RELRO`) | **只读但含需重定位的指针**(GOT、指针型常量、ObjC 元数据) | 加载期可写(供链接器修补)→ 修补完改只读 |
| `__DATA,__data` | `.data` | 真正可写的全局 / 静态变量 | 全程可读写,每进程各一份 |

关键差异在于**"谁来把它改只读"以及"分割粒度"**:

- ELF 的 RELRO 区由一个 **`PT_GNU_RELRO` 程序头**描述,运行期由动态链接器(ld.so)在重定位完成后 `mprotect` 成只读;一个可读写区会因此**被切成两半权限**。
- Mach-O 的拆分发生在**段**这一级——`__DATA_CONST` 干脆就是**独立的一个段**,dyld 应用完 chained fixups 后对**整段** `mprotect` 降只读(见 [[15.Mach-O __DATA_CONST]])。
- 而 `.rodata` ↔ `__TEXT,__const`/`__RODATA` 这一档**纯只读、无重定位**的数据,两边都是"从映射起就只读、永不改写",最简单也最适合共享。

> [!note] 一个常被忽视的坑:`const` 不一定进只读段
> 即便你写了 `const`,**含指针的 const 也可能落到可重定位的只读区甚至可写区**,而非纯 `.rodata`/`__TEXT,__const`。推荐写法是 **`const char * const`**(指针自身也 const),让指针和它指向的数据都尽量进只读区。这条 ELF 世界的经验,在 Mach-O 上同样成立——它正是"为什么需要 `__DATA_CONST` 这种'可重定位的只读'档位"的根因。

## 实操：用工具查看

### 示例 1:先确认二进制里**到底有没有** `__RODATA` 段

```bash
# 列出所有段名,看是否存在 __RODATA(多数 Apple 默认产物里没有)
otool -l YourApp | grep -A1 "cmd LC_SEGMENT" | grep segname

# 或者直接筛 __RODATA / __TEXT / __DATA_CONST 一并对照
otool -l YourApp | grep segname
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境,以下输出基于结构知识构造,实际数值(地址、大小、节数量)以你机器上的 `otool` 为准。**特别提醒:绝大多数 Apple 默认工具链产出的 macOS/iOS 二进制并不含独立 `__RODATA` 段**——下面把"典型 Apple 产物"与"自定义出现 `__RODATA`"两种情况都列出,便于对照。

```text
# —— 情况 A:典型 Apple 默认产物(无 __RODATA,只读数据在 __TEXT / __DATA_CONST)——
segname __PAGEZERO
segname __TEXT          ; 只读+可执行:__text / __const / __cstring …(只读数据在这里)
segname __DATA_CONST    ; 只读但需重定位:__got / __const / __objc_classlist …
segname __DATA          ; 可写:__data / __bss …
segname __LINKEDIT
# ↑ 没有 __RODATA —— 这才是大多数情况

# —— 情况 B:用了 #pragma clang section / __attribute__((section("__RODATA,...")))——
segname __PAGEZERO
segname __TEXT
segname __RODATA        ; ★ 因显式指定才出现的独立只读数据段
segname __DATA
segname __LINKEDIT
```

### 示例 2:若 `__RODATA` 存在,看它的段头与节

```bash
# 查看 __RODATA 段头(留意 initprot 是否为 r--、含哪些节)
otool -l YourApp | grep -A 8 "segname __RODATA"

# 查看 __RODATA 段下某个只读节的内容(段名,节名)
otool -s __RODATA __const YourApp
otool -s __RODATA __myrodata YourApp     # 若用 section 属性自定义了节名
```

> [!warning] 示例输出为示意
> 数值为构造,仅示意 `__RODATA` 段"纯只读(`initprot = r--`)"的特征;实际节名 / 大小以你机器上的 `otool` 为准。再次强调:**多数 Apple 二进制并不含独立 `__RODATA` 段,看不到本段属正常现象**。

### 示例 3:验证"写 `__RODATA`(或任何只读段)会崩"

```c
// 伪代码示意:取得某只读段内地址 p 后尝试写入
const int kTable[4] = {1,2,3,4};
*(int *)&kTable[0] = 0x41414141;   // 运行期写只读内存 → EXC_BAD_ACCESS
```

> [!warning] 示例输出为示意
> 实际崩溃信息(地址、库名)随环境不同。

```text
Exception Type:  EXC_BAD_ACCESS (SIGBUS)
Exception Codes: KERN_PROTECTION_FAILURE at 0x0000000100006000
...  写入落在只读映射的常量区 → 保护异常
```

> 说明:这正是"只读映射防篡改"的兑现现场——常量被硬件 + 内核联手锁死,任何写入立刻崩溃。无论这片只读数据叫 `__TEXT,__const` 还是 `__RODATA`,行为一致;区别仅在于 `__DATA_CONST` 多了"加载期那一小段可写窗口"(供 dyld 修补),而纯只读段连这个窗口都没有。

## 与相邻章节的关系

- [[21.Mach-O __const节]]、[[20.Mach-O __cstring节]]:**Apple 工具链里只读数据真正的默认去处**——纯只读、无重定位的常量进 `__TEXT,__const`,C 字符串字面量进 `__TEXT,__cstring`(且会去重)。理解了这两节,就明白为什么大多数二进制"用不着" `__RODATA`。
- [[15.Mach-O __DATA_CONST]]:另一类"只读"数据段,但它是"**加载期可写、绑定后只读**"(`SG_READ_ONLY` + dyld `mprotect`),专门装**含指针、需重定位**的常量(GOT、ObjC 元数据)。它对标 ELF 的 `.data.rel.ro`/RELRO,与 `__RODATA`(纯只读、对标 `.rodata`)恰好构成"只读数据的两个档位"。
- [[11.Mach-O Segments]]:段权限模型总纲。`__RODATA`(纯只读)、`__TEXT`(只读+可执行)、`__DATA_CONST`(先写后只读)、`__DATA`(可写)都是这套"以段为权限单位"思想的不同实例,本篇正是这一主线的收官回扣。

## 小结

- **`__RODATA` 是"只读数据段"的概念化命名**,承载字符串字面量、`const` 常量与编译期只读表,概念上对标 ELF 的 **`.rodata`**;只读映射带来**防篡改、可跨进程共享、缓存友好**三重收益。
- **它并非 Mach-O 标准必备段**。Mach-O 雷打不动的是 **`__TEXT` / `__DATA` / `__LINKEDIT`**(加 `__PAGEZERO`);Apple 默认工具链把只读数据放进 **`__TEXT,__const` / `__TEXT,__cstring`**(纯只读、无重定位)或 **`__DATA_CONST`**(只读但需重定位),**通常不单列 `__RODATA`**。
- **`__RODATA` 这个字面段名真正出现在**:`#pragma clang section rodata="__RODATA,..."`、`__attribute__((section("__RODATA,...")))`,以及嵌入式 / 裸机 / 自定义链接脚本等**需要精确控制布局**的场景——多数 App / framework 的 `otool -l` 里看不到它。
- **两档只读要分清**:纯只读、无重定位 → `.rodata` ↔ `__TEXT,__const`/`__RODATA`(`initprot=r--`,从映射起只读);只读但含需重定位的指针 → `.data.rel.ro` ↔ `__DATA_CONST`(`initprot=rw-` + `SG_READ_ONLY`,先写后锁)。`const` 含指针时**不会**进纯只读段,这是设计 `__DATA_CONST` 的根因。
- **收官呼应**:从 [[11.Mach-O Segments]] 一路到这里,Mach-O 始终在用**段的内存权限**为不同性质的数据"分而治之"——可执行的进 `__TEXT`、可变的进 `__DATA`、绑定后固定的进 `__DATA_CONST`、纯只读的进 `__TEXT,__const`/`__RODATA`。**用段权限保护数据,是贯穿全系列的那条主线。**

### Swift 元数据节

Swift 二进制在 `__TEXT` 段（少数在 `__DATA`）里塞入了一批以 `__swift5_*` 命名的只读节，供 Swift 运行时在启动期完成类型注册、协议一致性检查（conformance）、反射（reflection）等。这些节是逆向 Swift 二进制的核心入口。

#### Swift 元数据节族一览

| 节名 | 段 | 内容 | 运行时用途 |
|---|---|---|---|
| `__swift5_types` | `__TEXT` | 类型描述符指针数组（`TargetContextDescriptor`）| 注册所有 Swift 类型（class/struct/enum/protocol）|
| `__swift5_proto` | `__TEXT` | 协议一致性描述符指针数组（`ConformanceDescriptor`）| 注册 protocol conformance，供 `as?` / 泛型约束查询 |
| `__swift5_fieldmd` | `__TEXT` | 字段描述符（`FieldDescriptor`），描述 struct/class/enum 的存储字段 | 反射（`Mirror`）、`Codable` 自动合成 |
| `__swift5_typeref` | `__TEXT` | 类型引用字符串（Mangled 类型名的 UTF-8 字节池）| 运行时类型查询、反射、`_typeByName()` |
| `__swift5_assocty` | `__TEXT` | 关联类型描述符（associated type witness table）| 协议关联类型的满足声明 |
| `__swift5_replace` | `__TEXT` | 函数替换记录（dynamic function replacement）| `@_dynamicReplacement(for:)` 机制 |
| `__swift5_repl_scope` | `__TEXT` | 函数替换作用域 | 同上 |
| `__swift5_accessible_funcs` | `__TEXT` | 可通过反射访问的函数记录 | 服务于 `@backDeployed` / 分布式 actor |
| `__swift5_captures` | `__TEXT` | 闭包捕获描述符（`CaptureDescriptor`）| 反射闭包所捕获的变量 |

#### 各节字节级格式

**`__swift5_types`**（节类型 `S_REGULAR`，所有项均为 **32 位相对指针**）：

```
节内容：uint32_t[] — 每个元素是一个相对指针，指向 TargetContextDescriptor

相对指针解码：
  uint32_t relptr_at_addr = *(uint32_t*)addr;
  void *target = (void*)((int32_t)relptr_at_addr + (int64_t)addr);
  // 即：target = addr + sign_extend_32(relptr)

TargetContextDescriptor（简化）：
  uint32_t flags;         // 类型类别（低 5 位）+ 版本 + 通用参数数量
                          // flags & 0x1F：0=module, 1=extension, 2=anonymous,
                          //   3=protocol, 4=opaque_type,
                          //   16=class, 17=struct, 18=enum
  int32_t  parent;        // 相对指针，指向父上下文（module/enclosing type）
  int32_t  name;          // 相对指针，指向去混淆的类型名 C 字符串
  ... （后续字段因 flags 种类而异）
```

**`__swift5_proto`**（协议一致性描述符，32 位相对指针数组）：

```
节内容：uint32_t[] → 每个元素 → ConformanceDescriptor

ConformanceDescriptor {
    int32_t  protocolDescriptor;  // 相对指针 → ProtocolDescriptor
    int32_t  typeRef;             // 相对指针 → 类型描述符或类型引用
    int32_t  witnessTablePattern; // 相对指针 → WitnessTable（方法实现表）
    uint32_t flags;               // conformance 类型 + 泛型参数信息
}
```

Swift 运行时 `swift_conformsToProtocol()` 就是在遍历所有镜像的 `__swift5_proto` 节（加 swift runtime 内部缓存）来回答"T 是否符合协议 P"。

**`__swift5_fieldmd`**（字段描述符，可变长度结构体）：

```
FieldDescriptor {
    int32_t  mangledTypeName;   // 相对指针 → Mangled type name 字符串
    int32_t  superclass;        // 相对指针 → superclass 描述（class 特有）
    uint16_t fieldDescriptorKind; // 0=struct, 1=class, 2=enum, 3=multi_payload_enum...
    uint16_t fieldRecordSize;   // 每个 FieldRecord 的字节大小（固定 12B）
    uint32_t numFields;         // 字段数量
    FieldRecord fields[numFields]:   // 各字段描述
      uint32_t flags;           // 字段标志（是 var/let/indirect case 等）
      int32_t  mangledTypeName; // 相对指针 → 字段类型的 mangled name
      int32_t  fieldName;       // 相对指针 → 字段名 C 字符串（\0 结尾）
}
```

**`__swift5_typeref`**（类型引用，字节池）：

```
节内容：连续的 Swift Mangled Type Name 字符串（UTF-8，\0 分隔）
每个字符串格式为：_$s<mangled>  或  $s<mangled>（无下划线前缀）
例如：_$s4main8MyStructVMa\0  → module=main, type=MyStruct（value metatype accessor）
```

Swift mangled name 语法（关键前缀）：

| 前缀 | 含义 |
|---|---|
| `$s` | Swift 5 符号 |
| `So` | Objective-C 类/协议 |
| `Si` | `Swift.Int` |
| `Ss` | `Swift.String` |
| `V` | value type（struct/enum）|
| `C` | class |
| `P` | protocol |
| `G` | generic specialization |

#### Swift 类型元数据布局（运行时结构）

Swift 类在运行时的完整元数据（**FullMetadata<ClassMetadata>**）比 ObjC isa 复杂得多：

```
[内存布局，低地址→高地址]

[ValueWitnessTable]（在元数据前，负偏移处）
  → 描述该类型的值语义（copy/move/destroy/size/stride/alignment）
  → 负偏移 -8（或 -16，由架构决定）处有指向 VWT 的指针

[Metadata Header]（元数据正文起点）
  +0:  isa（类型指针，指向元类，与 ObjC 兼容）
  +8:  superclass Metadata 指针
  +16: cache（ObjC runtime 缓存相关）
  +24: data（低位 flag + 指向 ClassData 的指针）
  +32: ClassFlags（Swift-specific，含 uses_swift_refcounting 等标志）
  +36: InstanceAddressPoint
  +40: InstanceSize
  +44: InstanceAlignMask
  +48: Reserved
  +52: ClassSize（元数据自身大小）
  +56: ClassAddressPoint
  +60: DescriptorPointer（→ ClassDescriptor，即 __swift5_types 里的描述符）
  +64: IVarDestroyer 函数指针（可选）
  [vtable 函数指针数组，从 ClassAddressPoint 后开始]
```

**与 ObjC class 元数据的对比**：

| 维度 | ObjC class（`class_ro_t`）| Swift class Metadata |
|---|---|---|
| isa | objc_class（元类）| 同，兼容 ObjC runtime |
| 方法列表 | `method_t[]`（selector+IMP）| vtable 函数指针 + ObjC 方法表（`@objc` 方法）|
| 属性 | `property_t[]` | FieldDescriptor（`__swift5_fieldmd`）|
| 类型描述 | 无（运行时靠 ObjC 机制）| ClassDescriptor（`__swift5_types`）|
| 反射 | 有限（`class_getInstanceVariable` 等）| 完整（`Mirror`，靠 FieldDescriptor）|
| 协议一致性 | ObjC protocol conformance | SwiftConformanceDescriptor（`__swift5_proto`）|

### method_t small 变体

WWDC 2020（Xcode 12 / iOS 14）引入了 `small method_t`（相对偏移方法列表），用来减少启动时的 rebase 开销和内存占用。它与传统 `big method_t`（绝对指针方法列表）在二进制中**共存**，通过列表头的第 31 位标志区分。

#### big method_t（传统格式，iOS 13 及更早）

```c
// 来自 objc-runtime-new.h，64 位目标
struct method_t_big {
    SEL name;    // uint64_t：指向方法 selector 字符串（__objc_methnames 节）的绝对指针
    char *types; // uint64_t：指向 method type encoding 字符串（__objc_methtype 节）的绝对指针
    IMP imp;     // uint64_t：指向方法实现（__text 节代码）的绝对指针
};
// 每个 method_t_big：3 × 8 = 24 字节（64 位）
// 每个 method_t_big：3 × 4 = 12 字节（32 位）
```

**问题**：三个字段都是绝对指针 → 包含 ASLR 导致的指针，dyld 加载时需对**每个方法做 3 次 rebase**（若程序有 2000 个 ObjC 方法，就要 6000 次 rebase 写操作）。

方法列表头（`method_list_t`，在 `__objc_methnames` 节对应的 `__objc_const` 等节里）：

```c
struct method_list_t {
    uint32_t entsizeAndFlags;  // 低24位=entsize（每项字节数），高8位=flags
                               // 若 entsizeAndFlags & 0x80000000 == 0 → big method_t
    uint32_t count;            // 方法数量
    method_t_big methods[];    // 方法数组（紧跟其后）
};
```

#### small method_t（相对偏移格式，iOS 14+）

`small method_t` 把三个绝对指针替换为**相对于各字段自身地址的 32 位有符号偏移**，彻底消除可写指针，每个方法从 24 字节缩到 12 字节：

```c
struct method_t_small {
    int32_t nameOffset;   // 相对本字段地址的偏移 → 指向 SEL 指针（间接）
    int32_t typesOffset;  // 相对本字段地址的偏移 → 指向 type encoding 字符串
    int32_t impOffset;    // 相对本字段地址的偏移 → 指向方法实现代码（IMP）
};
// 每个 method_t_small：3 × 4 = 12 字节（仅 64 位，小方法表不用于 32 位）
```

**相对指针解码**（与 Swift 元数据相同的规则）：

```c
// 解码 nameOffset
int32_t *nameField = &method->nameOffset;
SEL *namePtr = (SEL*)((uint8_t*)nameField + *nameField);
SEL name = *namePtr;   // 再间接一次（name 字段指向的是 SEL*，不是 SEL 本身）

// 解码 impOffset（IMP 直接可用）
int32_t *impField = &method->impOffset;
IMP imp = (IMP)((uint8_t*)impField + *impField);
```

注意 `nameOffset` 有两层间接：它指向的是 **SEL 指针**（存在于 `__DATA,__objc_selrefs` 节里），而不是 selector 字符串本身。这是 ObjC runtime 确保 selector 唯一性（selector interning）的机制——所有对同一 selector 的引用统一指向 `__objc_selrefs` 里的同一个 SEL 槽。

#### 方法列表头的第 31 位标志

```c
// method_list_t.entsizeAndFlags 的解释
uint32_t entsizeAndFlags = list_header->entsizeAndFlags;
bool uses_small_method = (entsizeAndFlags & 0x80000000) != 0;  // 第 31 位
uint32_t entsize = entsizeAndFlags & 0x0000FFFF;               // 低16位 = 每项大小

// big method_t: entsizeAndFlags = 0x00000018（entsize=24, small=0）
// small method_t: entsizeAndFlags = 0x8000000C（entsize=12, small=1）
```

运行时（`objc_msgSend` 系列）在遍历方法列表时，先检查这一位选择正确的解析路径：

```c
// objc-runtime-new.mm（简化）
template <typename T>
void method_list_t::forEach(T &&callback) {
    if (usesRelativeOffsets()) {   // entsizeAndFlags & 0x80000000
        for (auto &m : smallMethods)
            callback(m.big());     // 运行时按需把 small 转成 big 的视图
    } else {
        for (auto &m : bigMethods)
            callback(m);
    }
}
```

#### big method_t 与 small method_t 详细对比

| 维度 | big method_t | small method_t |
|---|---|---|
| 引入版本 | ObjC 初始 | iOS 14 / macOS 11（WWDC 2020）|
| 每项大小（64位）| **24 字节** | **12 字节**（节省 50%）|
| 字段类型 | 3个绝对指针（uint64_t × 3）| 3个相对偏移（int32_t × 3）|
| 是否含可写指针 | **是**（dyld 需 rebase）| **否**（纯只读，无需 rebase）|
| 启动 rebase 开销 | 每方法 3 次写操作 | **零**（相对偏移编译期固定）|
| 内存共享 | 因 rebase 写脏，进程私有 | 多进程共享（完全只读）|
| 节标志位（`entsizeAndFlags`）| bit31 = 0 | **bit31 = 1**（`0x80000000`）|
| `nameOffset` 间接性 | 直接是 SEL | 指向 `__objc_selrefs` 里的 SEL 槽（两层间接）|
| 最大寻址范围 | 任意 64 位地址 | ±2GB（32 位有符号偏移，实际够用）|
| 适用架构 | 32 位 + 64 位 | **仅 64 位**（32 位 ObjC 继续用 big）|

#### 影响 ObjC 元数据解析（逆向视角）

**识别 small method_t 的特征**：

```bash
# 1. 看方法列表头标志
# 找 __objc_methnames 节相邻的 __objc_const 节，读方法列表头的 entsizeAndFlags
otool -s __TEXT __objc_methnames MyApp | head -5   # 方法名字符串

# 2. 用 class-dump 或 Frida 检测
# class-dump（支持 small method_t）：
class-dump -H MyApp -o /tmp/headers/

# 3. 方法项大小
# __DATA_CONST 节的 __objc_const 中，某个方法列表的每项若为12字节 → small
otool -s __DATA_CONST __objc_const MyApp | grep -A4 "method_list"
```

**解析 small method_t 的伪代码**（逆向工具实现参考）：

```python
def parse_method_list(data, offset, base_addr):
    entsizeAndFlags, count = struct.unpack_from('<II', data, offset)
    is_small = (entsizeAndFlags & 0x80000000) != 0
    entsize = 12 if is_small else 24
    offset += 8   # 跳过列表头
    for i in range(count):
        if is_small:
            nameOff, typesOff, impOff = struct.unpack_from('<iii', data, offset)
            # 解码相对指针
            name_ptr_addr = base_addr + (offset - len(data)) + nameOff
            # name_ptr_addr 处存的是 SEL（还要再读一次）
            # impAddr = base_addr + (offset+8) + impOff
            print(f"  small method #{i}: nameRelOff={nameOff}, impRelOff={impOff}")
        else:
            name, types, imp = struct.unpack_from('<QQQ', data, offset)
            print(f"  big method #{i}: name=0x{name:x}, imp=0x{imp:x}")
        offset += entsize
```

**实测体积收益**：Apple 在 WWDC 2020 Session 10163 中给出数据——某大型 App 启用 small method 后，`__objc_const` 节（存放方法列表）体积减少约 50%，启动期 rebase 时间减少约 80%（因不再需要对每个方法的 3 个指针做 dirty page 写操作）。
