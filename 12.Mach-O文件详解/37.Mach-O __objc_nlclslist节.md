# 详解Mach-O(三十七)Mach-O __objc_nlclslist节

> [!abstract] TL;DR
> **`__objc_nlclslist`（non-lazy class list，非惰性类列表）列出当前镜像里的"非惰性类"——绝大多数情况下就是"实现了 `+load` 方法的类"**。它住在 `__DATA`（或现代加固后的 `__DATA_CONST`）段里，本质是一段**类指针数组**（每项 `classref_t`，64 位 8 字节），数组里每个元素指向 `__objc_data` 里对应类对象的地址。
> 普通 ObjC 类是**惰性（lazy）**初始化的：首次被真正用到（发消息、`objc_getClass` 等）时 runtime 才会 `realize`（实现）它，以省下启动开销。但**实现了 `+load` 的类必须破例**——`+load` 语义要求"镜像一加载就执行"，于是这类被单列进 `__objc_nlclslist`，runtime 在镜像加载早期（`_read_images`）就**强制 `realize`** 它们、并随后**立即调用其 `+load`**。
> 调用顺序由 runtime 严格保证：`prepare_load_methods` → `schedule_class_load` **递归先调度父类再调度子类**（父类 `+load` 先于子类）；`call_load_methods` 先把所有类的 `+load` 调完、再调分类的 `+load`（类先于分类）。整个过程通过 dyld 的 `load_images` 回调触发，**早于本镜像的 `__mod_init_func`（C/C++ 构造器，见 [[32.Mach-O __mod_init_func节]]）、更早于 `main`**——这正是 `+load` 能"最早执行用户代码"的底层来源。
> 它是 [[36.Mach-O __objc_classlist节]]（全部类清单）的一个**子集**，只挑出非惰性类；逆向时它是定位"启动早期 hook（如 method swizzling）"的高价值切入点。

## 概述与定位

`+load` 是 Objective-C 里**执行时机最早的钩子之一**：它常被用于方法交换（method swizzling）、运行时早期注册（如把自身注册到某个父类的工厂表里）、监控埋点、AOP 框架的初始化等"必须先于任何业务代码"的场景。要支持这个"加载即执行"的语义，runtime 必须能在**遍历整个镜像之前**就快速回答两个问题：① 这个镜像到底有没有 `+load` 要调（用来短路、免去无谓加锁）；② 具体是哪些类有 `+load`、需要被优先 `realize`。`__objc_nlclslist` 就是为这两件事服务的索引表。

把它放进整个 ObjC 元数据家族里看，定位非常清晰：

- [[36.Mach-O __objc_classlist节]] 是**全集**——本镜像定义的**所有** ObjC 类（无论惰性与否）都在那里登记，runtime 通过 `_getObjc2ClassList` 读取。
- `__objc_nlclslist` 是其中的**真子集**——只收录"非惰性类"，runtime 通过 `_getObjc2NonlazyClassList` 读取。
- 一个类同时出现在 `__objc_classlist` 与 `__objc_nlclslist` 里，**并不矛盾**：前者负责"它存在、需要被注册进类表"，后者负责"它必须在加载早期就被 `realize` 并调 `+load`"。换句话说，`__objc_classlist` 决定"是否登记"，`__objc_nlclslist` 决定"是否提前实现"。

> [!note] 节名总要带段名：`段名,节名`
> 和所有节一样（见 [[18.Mach-O section]]），`__objc_nlclslist` 在 Mach-O 里写作二元组 `段名,节名`。传统 ObjC 二进制里它是 `__DATA,__objc_nlclslist`；启用链式 fixups 的现代 macOS/iOS 二进制为减小可写脏页、缩小攻击面，常把这类**只读指针表**迁到 `__DATA_CONST,__objc_nlclslist`。runtime 侧的读取函数对此有兜底：先查 `__DATA`，找不到再依次查 `__DATA_CONST`、`__DATA_DIRTY`（见下文第 4 节）。所以 `otool` 命令里务必把段名一起给：`otool -s __DATA __objc_nlclslist ...`，若没输出再试 `__DATA_CONST`。

> [!note] "非惰性类"≈"实现了 +load 的类"，但不完全等价
> 触发一个类成为非惰性的**最经典、也最常见**的方式，就是给它（或它的元类）实现 `+load`。但严格说，"实现 `+load`"是充分条件而非唯一条件：现代 LLVM/Clang 还提供了 `__attribute__((objc_nonlazy_class))` 属性（由 LLVM 提交 `rL353116` 引入），允许**不写 `+load` 也把类标记为非惰性**——这是为了解决一个历史痛点：很多系统库（libdispatch、Foundation 等）当年只为"让某个类提前 `realize`"而被迫写**空 `+load`**，结果在进程启动时把本不该加载的代码页错误地 fault 进来、白白增大启动工作集。有了该属性，就能"只要非惰性、但不要 `+load` 的副作用"。本表收录的是"非惰性类"这一整类，`+load` 只是其最主要来源。

## 核心原理与字段详解

### 1. 惰性类 vs 非惰性类：差在"何时 realize"

ObjC 的类在二进制里以**静态元数据**形式存在（`__objc_classlist` 指向的那些类对象，含 `class_ro_t` 等只读布局信息），但要变成"可用的、能收发消息的"类，runtime 还要做一步 **`realize`（实现）**：分配可读写的 `class_rw_t`、递归实现父类与元类、把方法/属性/协议从 `ro` 整理进 `rw`（`methodizeClass`）、把类挂进全局类表等。`realize` 有成本，所以 runtime 默认**能拖就拖**：

| 维度 | 惰性类（lazy，默认） | 非惰性类（non-lazy） |
|---|---|---|
| 何时 `realize` | **首次被使用时**（发消息走 `lookUpImpOrForward`、`objc_getClass`、作父类被引用等）才 `realize` | **镜像加载早期**（`_read_images`）就**强制** `realize` |
| 触发条件 | 不实现 `+load`、也未标 `objc_nonlazy_class`（占绝大多数） | 实现了 `+load`（最常见），或被标 `__attribute__((objc_nonlazy_class))` |
| 是否进 `__objc_nlclslist` | 否 | **是** |
| 启动开销 | 低（用不到就不实现） | 较高（无论用不用都提前实现+调 `+load`） |
| 典型用途 | 普通业务类 | 需要"加载即生效"的类：swizzling、早期注册、监控 hook |

> [!note] 为什么惰性是默认、提前 realize 是例外
> 一个大型 App 可能定义成千上万个类，但单次运行真正用到的往往只是其中一部分。若启动时把所有类都 `realize` 一遍，既浪费 CPU，又会把大量原本不必访问的元数据页 fault 进内存、推高启动时的内存工作集。所以 runtime 把 `realize` 设计成**按需触发**——惰性类在第一次被消息命中时，于 `lookUpImpOrForward` 路径里顺带完成 `realize`。非惰性类则因为 `+load` 的"加载即执行"语义无法惰性化，只能被单独挑出来提前处理，这"提前"的代价正是 [[#3-与-initialize-的区别本质是-加载即调-vs-惰性消息]] 里讨论的"`+load` 滥用拖慢启动"的根源。

### 2. 表的物理形态：`classref_t` 指针数组

`__objc_nlclslist` 的内容**极其简单**——就是一段连续的**指针数组**，没有任何额外头部或元信息：

```c
// 概念上等价于：
classref_t  nlclslist[N];   // N = section.size / sizeof(classref_t)
```

- 每个元素是一个 `classref_t`（在 64 位下就是一个 8 字节的类对象地址），指向 [[36.Mach-O __objc_classlist节]] 同样会指向的那个类对象（位于 `__objc_data` / `__objc_const` 区域）。
- **条目数不在节里显式存储**，而是用 `节大小 ÷ 单项大小` 推算：`count = section.size / 8`（64 位）。这与 [[18.Mach-O section]] 里"符号指针节用 `size / 指针宽度` 推算条目数"的约定一脉相承。
- 节类型是 `S_REGULAR`（普通节，见 [[18.Mach-O section]] 第 7 节）——它只是"一堆指针"，并不需要 `S_NON_LAZY_SYMBOL_POINTERS` 这种"由 dyld 绑定外部符号"的特殊类型，因为这些指针指向的是**本镜像内部**的类对象，由 dyld 的 rebase / 链式 fixups 统一修正基址即可。

> [!note] 它常带 `S_ATTR_NO_DEAD_STRIP` 属性
> 因为这些类指针在源码层面"看起来没人引用"（没有任何普通代码 `#import` 后直接取它的地址放进这个表——是编译器自动生成的），若不加保护，链接器的死代码消除（dead strip）很可能把它们当垃圾删掉，导致 `+load` 神秘"不被调用"。所以编译器（Clang 的 ObjC codegen）在发射 `__objc_nlclslist` 时会给它打上 `S_ATTR_NO_DEAD_STRIP`（属性值 `0x10000000`，见 [[18.Mach-O section]] 第 8 节），明确告诉链接器"别删"。这也解释了一个常见现象：把含 `+load` 的 `.m` 编进静态库后，若链接时没加 `-ObjC` / `-force_load`，**整个 `.o` 可能不被拉入**，连带 `__objc_nlclslist` 都进不了最终二进制——`NO_DEAD_STRIP` 只保护"已进入链接的节内条目不被剔除"，救不了"整个目标文件没被链接进来"。

### 3. runtime 如何在加载早期处理本表（两阶段·上：realize）

ObjC runtime 启动时，会在 `_objc_init` 里向 dyld **注册回调**（`map_images` 负责镜像映射后的元数据处理、`load_images` 负责触发 `+load`）。当 dyld 把镜像映射好，回调链最终走到 `_read_images`，其中有一段**专门处理非惰性类**的循环，注释明确写着 "Realize non-lazy classes (for +load methods and static instances)"，逻辑大致是：

```objc
// _read_images 内（简化示意，基于 Apple objc4 源码）
for (EACH_HEADER) {
    classref_t *classlist = _getObjc2NonlazyClassList(hi, &count); // ← 读 __objc_nlclslist
    for (i = 0; i < count; i++) {
        Class cls = remapClass(classlist[i]);   // 处理类重映射（如共享缓存）
        if (!cls) continue;
        addClassTableEntry(cls);                 // 登记进全局已分配类表
        realizeClassWithoutSwift(cls, nil);      // ← 立即 realize（普通类是惰性，这里破例）
    }
}
```

`realizeClassWithoutSwift` 会**递归实现父类与元类**——`supercls = realizeClassWithoutSwift(remapClass(cls->getSuperclass()), nil)`、`metacls = realizeClassWithoutSwift(...)`——保证一个类被实现时，它的整条祖先链结构已经就位。这一步只"把类结构建好"，还**没有调 `+load`**。

> [!note] 先做一次"免锁快判"：`hasLoadMethods`
> 在真正进入 `+load` 调度的重活之前，runtime 会先用 `hasLoadMethods` 做一次廉价探测：分别读 `_getObjc2NonlazyClassList`（本表）与 `_getObjc2NonlazyCategoryList`（分类对应的 `__objc_nlcatlist`，见 [[39.Mach-O __objc_catlist节]]），**只要其中任一 `count > 0` 就返回真**，否则直接返回假、跳过后续所有加锁与遍历。这个判断**故意不加锁**——它只是个快速短路，让"根本没有任何 `+load`"的镜像零成本掠过。本表在这里扮演的就是"有没有 `+load`"的索引角色。

### 4. runtime 怎么读到这个 section：`GETSECT` / `getDataSection`

runtime 并不"硬解析 Mach-O"，而是通过系统提供的 `getsectiondata` 按"段名+节名"取数据。objc4 用一个宏 `GETSECT` 批量生成各元数据节的访问函数，其中就有本表的：

```c
// objc-file.mm（简化示意，基于 Apple objc4）
template <typename T>
T* getDataSection(const headerType *mhdr, const char *sectname, size_t *outBytes, size_t *outCount) {
    unsigned long byteCount = 0;
    T* data = (T*)getsectiondata(mhdr, "__DATA", sectname, &byteCount);     // 先查 __DATA
    if (!data) data = (T*)getsectiondata(mhdr, "__DATA_CONST", sectname, &byteCount); // 再查 __DATA_CONST
    if (!data) data = (T*)getsectiondata(mhdr, "__DATA_DIRTY", sectname, &byteCount); // 再查 __DATA_DIRTY
    if (outCount) *outCount = byteCount / sizeof(T);   // ← 条目数 = 字节数 / sizeof(T)
    return data;
}

#define GETSECT(name, type, sectname)                          \
    type *name(const headerType *mhdr, size_t *outCount) {     \
        return getDataSection<type>(mhdr, sectname, nil, outCount); \
    }

// 关键两行：全集与子集，元素类型都是 classref_t
GETSECT(_getObjc2ClassList,        classref_t, "__objc_classlist")    // → 全部类
GETSECT(_getObjc2NonlazyClassList, classref_t, "__objc_nlclslist")   // → 非惰性类（本表）
// 还有 _getObjc2CategoryList / _getObjc2NonlazyCategoryList(__objc_nlcatlist)、
//      _getObjc2ProtocolList、_getObjc2SelectorRefs 等同族成员
```

由此能确认三个事实：① 本表元素类型是 `classref_t`（类指针），所以**条目数 = `section.size / 8`**（64 位）；② 段名查找带兜底，这正是它可能落在 `__DATA_CONST` 的原因；③ 它与 `__objc_classlist` 用的是**同一套读取机制、同一种元素类型**，只是节名不同——再次印证"子集"关系。

### 5. `+load` 的调用顺序：父类先于子类（两阶段·下：schedule + call）

类被 `realize` 之后，`+load` 的**调度与调用**由另一对函数完成，顺序保证全在这里：

```objc
// prepare_load_methods（简化示意）
void prepare_load_methods(const headerType *mhdr) {
    classref_t *classlist = _getObjc2NonlazyClassList(mhdr, &count); // 仍是读本表
    for (i = 0; i < count; i++)
        schedule_class_load(remapClass(classlist[i]));   // 逐个调度

    category_t **categorylist = _getObjc2NonlazyCategoryList(mhdr, &count); // 再处理分类
    for (i = 0; i < count; i++) { ... add_category_to_loadable_list(cat); }
}

// schedule_class_load：靠"先递归父类"保证父类先入队
static void schedule_class_load(Class cls) {
    if (!cls) return;
    ASSERT(cls->isRealized());                 // _read_images 应已 realize
    if (cls->data()->flags & RW_LOADED) return; // 已调度过则跳过
    schedule_class_load(cls->getSuperclass()); // ★ 先调度父类，再加自己
    add_class_to_loadable_list(cls);           // 把自己加进可加载列表（顺序即调用顺序）
    cls->setInfo(RW_LOADED);
}
```

`schedule_class_load` **先递归调度父类、再把自己加入"可加载列表"**，由于"加入列表的顺序就是日后调用的顺序"，于是天然得到"**父类 `+load` 必在子类 `+load` 之前**"。真正发起调用的是 `call_load_methods`：

```objc
// call_load_methods（简化示意）
void call_load_methods(void) {
    do {
        while (loadable_classes_used > 0)  call_class_loads();   // ① 先把"类"的 +load 全部调完
        more_categories = call_category_loads();                // ② 再调"分类"的 +load
    } while (loadable_classes_used > 0 || more_categories);
}
```

它**先把所有类的 `+load` 调完，再调分类的 `+load`**，于是又得到"**类先于分类**"。两条规则合起来，就是大家熟知的 `+load` 调用次序：**父类 → 子类 → （各自的）分类**。

> [!note] 一句话记牢 `+load` 的两条顺序铁律
> ① **父类先于子类**——由 `schedule_class_load` 递归先排父类保证；② **类先于分类**——由 `call_load_methods` 先 `call_class_loads()` 再 `call_category_loads()` 保证。需要特别注意：分类的 `+load` **不会**覆盖宿主类的 `+load`，二者**都会被调用**（一个类自身 `+load` + 它每个实现了 `+load` 的分类各调一次）。这点与 `+initialize` 截然不同（见下节）。

### 6. `+load` 的执行时机：早于 `__mod_init_func`、早于 `main`

`+load` 之所以号称"能跑的最早的用户代码"，关键在它在 dyld 初始化流程里的位置。整体次序（单镜像视角，简化）：

1. **dyld 引导**：映射 dyld 共享缓存、按依赖递归映射本程序依赖的所有 dylib。
2. **`objc_init` 运行**（作为 ObjC runtime 库自身的初始化器），向 dyld **注册 `map_images` / `load_images` 回调**。
3. **dyld 按依赖顺序处理每个镜像的初始化器**，对单个镜像而言：
   - 先经 `map_images` → `_read_images`：`realize` 非惰性类（第 3 节）；
   - 再经 **`load_images` 回调**：`prepare_load_methods` + `call_load_methods` → **执行各 `+load`**（第 5 节）；
   - **然后**才执行该镜像的 **`__mod_init_func`**（`doModInitFunctions`）：即 C++ 全局对象构造函数、C 的 `__attribute__((constructor))` 函数（见 [[32.Mach-O __mod_init_func节]]）。
4. 全部初始化器跑完，dyld 最后调用 **`main()`**。

所以在**同一个镜像内部**，铁定的先后是：**`+load`（经 `load_images`）→ `__mod_init_func`（C/C++ 构造器）→ `main`**。这就是 `+load` 适合"任何业务代码、甚至任何 C++ 全局对象构造之前"做准备的根本原因。

> [!warning] "最早"是有边界的：跨镜像依赖与"同镜像其他类未必就绪"
> 两点容易踩坑：① "早于 `main`、早于本镜像构造器"成立，但**跨镜像**之间，`+load` 的相对顺序取决于 dyld 的**依赖加载顺序**——被依赖的库先初始化。不要假设"我的 `+load` 一定早于另一个无依赖关系的库的 `+load`"。② 在你的 `+load` 里，你可以安全地给**同镜像里其他不相关的类**发消息（它们至少已被 `realize`），但**那些类的 `+load` 未必已经执行过**——所以别在 `+load` 里依赖"另一个类的 `+load` 已经把某些东西准备好了"。

### 3'. 与 `+initialize` 的区别：本质是"加载即调" vs "惰性消息"

`+load` 与 `+initialize` 都是 runtime 自动调用的类方法，但机制天差地别，是面试与逆向高频考点：

| 维度 | `+load` | `+initialize` |
|---|---|---|
| 触发时机 | **加载早期、立即调用**（早于 `main`、早于 `__mod_init_func`） | **惰性**——类（或其子类）**第一次收到消息**前才调用 |
| 类没被用到会调吗 | **会**（只要它在本表里就一定调） | **不会**（用不到就永远不调） |
| 驱动来源 | **本表 `__objc_nlclslist`** 驱动，runtime 直接调用 | **消息发送路径**驱动（`objc_msgSend` 前的检查 → `_class_initialize`），不依赖本表 |
| 分类 | 类自身 + **每个**分类的 `+load` **都调** | **每类仅一次**；分类的 `+initialize` 会**覆盖**宿主类的（只跑一个） |
| 父类未实现时会"继承"吗 | **不会**——只调真正定义了 `+load` 的实现，不走继承 | **会**——按普通消息派发，子类没实现就跑到父类实现（可能被调多次） |
| 线程安全 | 由加载早期的单线程串行执行 | runtime 按类加锁，首个发消息线程执行、其余线程阻塞等待 |
| 推荐用途 | 必须"加载即生效"的注册/swizzling | 绝大多数惰性初始化（更"安全"、用不到不浪费） |

核心差异一句话：**`+load` 是"被一张表点名、加载就强制调"，`+initialize` 是"等你被人搭话、第一次发消息才顺手调"**。因为 `+initialize` 走的是普通消息派发，它有两个"陷阱"：① 子类不实现 `+initialize` 时，父类的实现会被"借用"执行，**父类 `+initialize` 可能被调用多次**（每个未实现的子类各触发一次）——稳妥写法是 `if (self == [ClassName self]) { ... }` 自检；② 它可能**永远不被调**（类没被用到）。所以"必须保证执行"的注册逻辑只能放 `+load`，而"用到才初始化"的大多数场景应优先 `+initialize` 或 `dispatch_once`。

> [!note] 架构差异
> 指针宽度随位宽变化：本表每项在 64 位（arm64 / x86_64）下是 8 字节、在老的 32 位（i386 / armv7）下是 4 字节，故条目数 = `节大小 / 指针宽度`（见 [[18.Mach-O section]]）。除指针宽度外，"非惰性类提前 realize 并调 `+load`"这套机制**与架构无关**，纯粹取决于 runtime 行为。当代 Apple 设备一律 64 位，本表也常因链式 fixups 而落在 `__DATA_CONST`。

> [!warning] `+load` 滥用会显著拖慢启动
> 每一个 `+load`（以及为"提前 realize"而写的空 `+load`）都强制 runtime 在**启动关键路径**上同步执行一次：既要提前 `realize` 整条类层级，又要把相关代码页 fault 进内存。`+load` 越多、做的事越重，启动越慢，且这些开销**无论该类当次运行是否被用到都要付**。Apple 的明确建议是：**能用 `+initialize` 或 `dispatch_once` 就别用 `+load`**；确需非惰性但又不想要 `+load` 副作用时，用 `__attribute__((objc_nonlazy_class))`。也正因为 `+load` 是"最早执行、人人必经"的点，**逆向分析常把本表作为切入口**——攻击/调试代码若想在一切之前 hook，往往把自己注册成一个带 `+load` 的类，于是它的指针就赫然躺在 `__objc_nlclslist` 里。

## 实操：用工具查看

### 示例 1：`otool -s` dump 本表原始字节（裸指针数组）

`otool -s 段名 节名` 以十六进制 dump 节内容。本表是裸指针数组，dump 出来就是一串 8 字节小端地址：

```bash
otool -s __DATA __objc_nlclslist /path/to/ObjCBinary       # 传统位置
otool -s __DATA_CONST __objc_nlclslist /path/to/ObjCBinary # 现代加固二进制常在此
otool -s __DATA __objc_classlist /path/to/ObjCBinary       # 对照看全集，便于确认"子集"关系
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
ObjCBinary:
Contents of (__DATA,__objc_nlclslist) section
00000001000091c0  e0 84 00 00 01 00 00 00                            ; 1 个条目，小端 → 0x00000001000084e0
```

> 说明：左列 `00000001000091c0` 是本节起始虚拟地址；中间 8 字节小端解读为 `0x1000084e0`，正是某个类对象（在 `__objc_data` 里）的地址。本表只存"指针"，不含任何符号名——要知道它指向哪个类，需顺着这个地址去 `__objc_data` 找类对象，再读其 `class_ro_t.name`。节大小 8 字节 ÷ 8 = **1 个非惰性类**。

### 示例 2：`otool -ov` 让 otool 替你解析成"类名 + +load"

裸地址不直观，`otool -ov`（`-o` 解析 ObjC 元数据、`-v` 符号化）会把类指针解析成可读的类信息，便于直接看出"哪些类带 `+load`"：

```bash
otool -ov /path/to/ObjCBinary                      # 完整 dump ObjC 元数据（含 nonlazy class 区块）
otool -ov /path/to/ObjCBinary | grep -i -A2 "non-lazy\|nlcls\|load"  # 粗筛与 +load/非惰性相关行
```

> [!warning] 示例输出为示意
> 数值/类名为构造，仅示意 `otool -ov` 如何把本表指针符号化为类名。

```text
Contents of (__DATA,__objc_nlclslist) section
00000001000091c0 0x1000084e0 _OBJC_CLASS_$_MySwizzler   ; 实现了 +load，故被列入非惰性类表
    isa        0x100008508 _OBJC_METACLASS_$_MySwizzler
    superclass 0x0   (NSObject)
    name       0x100007f3a MySwizzler
    baseMethods 0x100008100 (struct method_list_t *)
        name  0x... load                              ; ← 类方法列表里赫然有 +load
        types 0x... v16@0:8
        imp   0x100002c40 +[MySwizzler load]
```

> 说明：`otool -ov` 顺着本表的类指针走进类对象，打印出类名 `MySwizzler` 及其方法列表——可见其元类方法里有 `load`（即 `+load`），这正是它被收进 `__objc_nlclslist` 的原因。对照 `__objc_classlist`（全集）会发现：那里能列出本镜像所有类，而本表只挑出了带 `+load` 的这一个。

### 示例 3：交叉验证"它是 __objc_classlist 的子集"

```bash
# 看两个表各有几个条目（节大小 ÷ 8 即条目数）
otool -l /path/to/ObjCBinary | grep -A4 "__objc_classlist"    # 看 size，/8 得全部类数
otool -l /path/to/ObjCBinary | grep -A4 "__objc_nlclslist"    # 看 size，/8 得非惰性类数
```

> [!warning] 示例输出为示意

```text
  sectname __objc_classlist
   segname __DATA_CONST
      size 0x0000000000000050      ; 0x50 / 8 = 10 个类（全集）
   ...
  sectname __objc_nlclslist
   segname __DATA_CONST
      size 0x0000000000000008      ; 0x08 / 8 = 1 个非惰性类（子集）⊆ 上面的 10 个
```

> 说明：用 `otool -l` 读两个节的 `size` 再各自 `/8`，能直观验证"非惰性类数 ≤ 全部类数"。本例 10 个类里只有 1 个实现了 `+load`，因此 `__objc_nlclslist` 只有 1 项——它必是那 10 个里的一个。

## FAQ

> [!question] `__objc_nlclslist` 和 `__objc_classlist` 到底什么关系？一个类会同时在两张表里吗？
> `__objc_classlist`（见 [[36.Mach-O __objc_classlist节]]）是**全集**——本镜像定义的所有 ObjC 类都在；`__objc_nlclslist` 是它的**真子集**——只收"非惰性类"（最常见是实现了 `+load` 的类）。一个非惰性类会**同时出现在两张表**，且不矛盾：在 `__objc_classlist` 里它表示"需要被登记进类表"，在 `__objc_nlclslist` 里它表示"必须在加载早期被强制 `realize` 并调 `+load`"。runtime 用同一套 `GETSECT`/`getsectiondata` 机制读两者，元素都是 `classref_t`，仅节名不同。

> [!question] 为什么我的 `+load` 没被调用？
> 最常见有三种原因：① 类被编进**静态库**，链接时**没加 `-ObjC` / `-force_load`**，导致整个 `.o` 没被拉进最终二进制，连 `__objc_nlclslist` 条目都不存在（注意：节属性 `S_ATTR_NO_DEAD_STRIP` 只能保护"已进入链接的条目不被剔除"，救不了"整个目标文件没被链接进来"）。② `+load` 写成了**实例方法 `-load`** 或签名不对——只有类方法 `+ (void)load` 才会被 runtime 当作加载钩子。③ 误以为"分类的 `+load` 会覆盖类的 `+load`"——其实二者都会被调；如果你只在分类里写了 `+load` 却没生效，多半还是该分类所在 `.o` 没被链接进来（同 ①）。排查时先 `otool -s __DATA __objc_nlclslist`（没输出再试 `__DATA_CONST`）确认条目是否存在。

> [!question] `+load` 里能安全做什么、不能做什么？
> **能**：给本镜像里其他不相关的类发消息（它们至少已被 `realize`）、做 method swizzling、注册自己到某父类/系统的表里。**要小心**：① 别依赖"另一个类的 `+load` 已经执行完"——`+load` 之间除父子/类先于分类外没有保证，跨镜像更取决于 dyld 依赖顺序；② 别在 `+load` 里做重活（网络、磁盘、复杂初始化），它在**启动关键路径**上同步执行，直接拖慢冷启动；③ 避免触发大量其他类的 `realize` 或递归 `+load`。需要"稍晚一点、且只在用到时"的初始化，改用 `+initialize` 或 `dispatch_once`。

> [!question] 不写 `+load` 也能让类变成非惰性吗？
> 能。用 `__attribute__((objc_nonlazy_class))`（LLVM 提交 `rL353116` 引入）标记类，即可让它进入 `__objc_nlclslist`、在加载早期被 `realize`，但**不附带 `+load` 的调用**。这正是为了解决历史上"为了提前 `realize` 而被迫写空 `+load`"的副作用——空 `+load` 同样会把代码页 fault 进来、增大启动工作集。换言之：**实现 `+load` ⇒ 非惰性**，但**非惰性 ⇏ 一定实现了 `+load`**；本表收录的是"非惰性类"这一整类。

## 与相邻章节的关系

- [[36.Mach-O __objc_classlist节]]：全部类清单，本表是其"非惰性（含 `+load`）"子集；二者元素类型同为 `classref_t`、读取机制同源。
- [[32.Mach-O __mod_init_func节]]：C/C++ 初始化器（全局构造/`constructor`）。在同一镜像内，`+load`（经 `load_images`）**早于**它执行；二者都早于 `main`。
- [[39.Mach-O __objc_catlist节]]：分类清单。分类的 `+load` 同样在加载早期调用，且由 `call_load_methods` 保证**晚于**所有类的 `+load`（类先于分类）；非惰性分类单列在 `__objc_nlcatlist`。
- [[18.Mach-O section]]：本表作为 `S_REGULAR` 节、靠 `size / 指针宽度` 推算条目数、可带 `S_ATTR_NO_DEAD_STRIP` 属性——这些通用规则的"公共字段说明书"。

## 小结

- `__objc_nlclslist` 列出**非惰性类**（最常见是**实现了 `+load` 的类**，也含被 `__attribute__((objc_nonlazy_class))` 标记者），物理形态是一段 `classref_t` **指针数组**，条目数 = `节大小 / 指针宽度`；常住 `__DATA`，现代加固二进制常迁至 `__DATA_CONST`。
- 它是 [[36.Mach-O __objc_classlist节]]（全集）的**真子集**；普通类**惰性** `realize`（首次用到才实现），非惰性类则在 runtime 加载早期（`_read_images` → `realizeClassWithoutSwift`）被**强制提前 `realize`**。
- `+load` 的调用顺序由 runtime 保证：`schedule_class_load` 递归"先父后子"⇒ **父类先于子类**；`call_load_methods` 先调类再调分类 ⇒ **类先于分类**（分类 `+load` 不覆盖、与类 `+load` 都调）。
- 时机上 `+load`（经 dyld 的 `load_images` 回调）**早于本镜像的 `__mod_init_func`（C/C++ 构造器）、更早于 `main`**——这是 `+load` 能"最早执行"的来源。
- 与 `+initialize` 的本质区别：`+load` 由**本表点名、加载即强制调用**；`+initialize` 是**惰性的、走消息发送路径**（首次发消息前才调，用不到则永不调）。`+load` 滥用会拖慢启动，故 Apple 建议优先 `+initialize`/`dispatch_once`；逆向则常以本表为"早期 hook"的切入点。
