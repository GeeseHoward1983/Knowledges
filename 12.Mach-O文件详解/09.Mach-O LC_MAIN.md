# 详解Mach-O(九)Mach-O LC_MAIN

> [!abstract] TL;DR
> **`LC_MAIN` 回答"进程从哪条指令开始执行"**：命令体是定长 24 字节的 `entry_point_command`，只携带两个 64 位字段——`entryoff` 给出入口相对**文件起点（也即 `__TEXT` 段基址）的偏移**，`stacksize` 可选地指定主线程初始栈大小（`0` 表示用系统默认）。
> 它的 `cmd` 值是 `0x80000028`，其中低位 `0x28`（十进制 40）是命令号、高位 `0x80000000` 是 **`LC_REQ_DYLD`** 标志位——意味着"`dyld` 必须看懂这条命令，看不懂就拒绝加载镜像"。
> 运行期真实入口地址 = **镜像加载基址（含 ASLR slide）+ `entryoff`**。用偏移而非绝对地址，正是为了天然配合地址无关可执行（`MH_PIE`）与 ASLR：无论镜像被随机加载到哪，偏移恒定不变。
> `LC_MAIN` 在 **OS X 10.8 / iOS 6** 起取代了旧的 **`LC_UNIXTHREAD`**：后者直接内嵌一份完整的初始线程寄存器状态（`x86_thread_state64` 的 `rip` / `arm_thread_state64` 的 `pc` 即入口），由内核恢复寄存器后跳转，并需链接器把 `crt1.o` 嵌进每个二进制；前者只给一个偏移，由 `dyld` 在启动末尾负责跳转，省去了 `crt1.o` 重复 `dyld` 已做工作的冗余，也更契合 ASLR。
> 关键认知：**`entryoff` 指向的通常不是你写的 `main`，而是 C 运行时启动桩 `start`**；`dyld` 完成"映射段 → 加载依赖 → rebase/bind → 运行初始化器（`__mod_init_func`）"后，最后一步才跳到 `entryoff`，再由启动桩备好 `argc/argv/envp/apple` 调用你的 `main`。

## 概述与定位

进程"从哪开始执行"这个问题，在现代 Mach-O 可执行文件（`MH_EXECUTE`）里由 **`LC_MAIN`** 回答。它是一条**极简**的加载命令——整个命令体只有 24 字节，比 `LC_SEGMENT_64`（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）那种动辄几百字节、还拖着一长串节头的"重命令"小得多。但它的语义分量极重：**它是 `dyld` 启动流程的终点，是从"加载器世界"交棒给"你的程序代码"的那一跳**。

可以这样理解它在整个加载链里的位置：内核 `execve` 把镜像和 `dyld` 映射进内存、铺好栈，`dyld` 接管后把所有段映射好、把依赖库加载链接好、把全局指针 rebase/bind 好、把 C++ 构造器与 `__attribute__((constructor))` 等初始化器跑完——所有这些"准备工作"做完之后，`dyld` 要回答的最后一个问题就是"现在该跳到哪？"，而 `LC_MAIN.entryoff` 就是这个问题的答案。

它带 **`LC_REQ_DYLD`** 位（`cmd == 0x80000028`），这不是装饰：它在告诉解析器"这条命令是程序能正确运行的**必要条件**，`dyld` 看不懂就必须报 `unknown load command required for execution` 并拒绝加载"。这与那些"看不懂就跳过"的可选命令形成鲜明对比（`LC_REQ_DYLD` 机制详见 [[03.Mach-O加载命令]]）。

现代工具链（clang + 现代 ld）产出的可执行文件几乎一律使用 `LC_MAIN`；只有**非常老**（OS X 10.7 及更早）或**特殊构造**（手工/特定工具链产出）的二进制，以及 **`dyld` 自身**这类需要内核直接拉起、无法依赖 `dyld` 跳转的镜像，才仍用 `LC_UNIXTHREAD`。本篇聚焦 `LC_MAIN` 这条命令的字段语义与运行期行为，并把它与前任 `LC_UNIXTHREAD`、与 `dyld` 全流程、与 C 运行时启动桩一并讲透。

> [!note] `LC_MAIN` 只用于 `MH_EXECUTE`
> `LC_MAIN` 是**可执行文件专属**的命令——它只出现在 `filetype == MH_EXECUTE` 的主可执行文件里。动态库（`MH_DYLIB`）、Bundle（`MH_BUNDLE`）、目标文件（`MH_OBJECT`）都没有"程序入口"这个概念，自然不含 `LC_MAIN`（动态库的初始化走 `__mod_init_func` 等机制，见 [[32.Mach-O __mod_init_func节]]）。文件类型字段见 [[02.Mach-O文件头]]。

## 核心原理与字段详解

### 1. `entry_point_command` 完整字段

来自 `<mach-o/loader.h>`，逐字段注释如下（结构跨架构完全一致，没有 32/64 位两份变体——这点与 `LC_SEGMENT` 不同）：

```c
struct entry_point_command {
    uint32_t  cmd;        /* LC_MAIN, 仅用于 MH_EXECUTE 文件类型；值 0x80000028 */
    uint32_t  cmdsize;    /* 恒为 24（= sizeof(entry_point_command)） */
    uint64_t  entryoff;   /* main() 的文件偏移（相对文件起点，也即 __TEXT 段基址） */
    uint64_t  stacksize;  /* 若非 0，则为主线程初始栈大小（链接时 -stack_size 指定） */
};
```

字段在文件里的精确偏移（共 24 字节）：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `cmd` | uint32_t | 4 | 固定为 `LC_MAIN`（`0x80000028`） |
| 4 | `cmdsize` | uint32_t | 4 | 恒为 `24`，遍历步长 |
| 8 | `entryoff` | uint64_t | 8 | 入口相对文件 / `__TEXT` 起点的偏移 |
| 16 | `stacksize` | uint64_t | 8 | 主线程初始栈大小，`0` 用默认 |

> [!note] `cmdsize` 为什么是固定的 24
> `entry_point_command` 没有任何变长尾巴（不像段命令后面跟 `nsects` 个节头），结构本身就是 `4 + 4 + 8 + 8 = 24` 字节。所以 `LC_MAIN` 的 `cmdsize` **恒为 24**，且天然是 8（指针大小）的整数倍、无需补齐。健壮解析器看到 `cmd == LC_MAIN` 但 `cmdsize != 24` 时，应判定为畸形命令。遍历到下一条命令仍是统一规则 `ptr += cmdsize`（见 [[03.Mach-O加载命令]]）。

### 2. `cmd` 值剖析：`0x80000028` 与 `LC_REQ_DYLD`

`LC_MAIN` 的命令号不是一个"干净"的小整数，而是 `0x80000028`，它由两部分按位或而成：

```
  0x80000028
= 0x00000028   ← 基础命令号（十进制 40）
| 0x80000000   ← LC_REQ_DYLD 标志位（最高位）
```

`LC_REQ_DYLD`（`0x80000000`）是 Mach-O 在 **OS X 10.1 之后**引入的约定：凡是"镜像要正确运行就**必须**被动态链接器理解"的新命令，都把这个最高位或进命令号里。它带来一条强约束——

- **带 `LC_REQ_DYLD` 的命令，`dyld` 看不懂就报错拒载**：`dyld` 会抛出 `unknown load command required for execution` 并拒绝使用该镜像；
- **不带这个位的命令，`dyld` 看不懂就直接忽略**：当作可选信息跳过，不影响加载。

`LC_MAIN` 之所以必须带这个位，是因为入口跳转**只有 `dyld` 会做**（不像旧的 `LC_UNIXTHREAD` 由内核恢复寄存器跳转）——一个不认识 `LC_MAIN` 的旧 `dyld` 根本不知道该跳哪，让它"忽略"这条命令等于让程序无从启动。所以这条命令必须"强制理解"。同样带 `LC_REQ_DYLD` 位的还有 `LC_DYLD_INFO_ONLY`（`0x80000022`）、`LC_LOAD_WEAK_DYLIB`、`LC_DYLD_CHAINED_FIXUPS` 等一票 `dyld` 关键命令。

> [!note] 解析 `cmd` 时的实务
> 遍历加载命令、用 `switch(cmd)` 分派时，要么直接拿 `0x80000028` 整值匹配 `LC_MAIN`，要么先 `cmd & ~LC_REQ_DYLD`（清掉最高位）再比基础号 `0x28`。两种写法都对，但**不能**只比低位却忘了高位的存在——否则容易把 `LC_MAIN`（`0x80000028`）和某条恰好低位也是 `0x28` 的假想命令混淆。`loader.h` 里 `LC_MAIN` 是直接写成 `(0x28 | LC_REQ_DYLD)` 的。

### 3. `entryoff` 的精确语义：文件偏移，不是绝对地址

这是整篇最容易踩坑、也最该讲透的字段。`entryoff` 是一个**偏移量**，而**不是**一个可以直接跳过去的虚拟地址。它的基准是**文件起点**——而由于 `__TEXT` 段恰好从文件偏移 0 开始映射（Mach-O 头与 Load Commands 本身就落在 `__TEXT` 范围内，见 [[13.Mach-O __TEXT]] 与 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]），所以"相对文件起点的偏移"在数值上等同于"相对 `__TEXT` 段基址的偏移"。

运行期把它换算成真实入口地址的公式是：

```
运行期真实入口 = 镜像加载基址(__TEXT 的 vmaddr) + ASLR slide + entryoff
```

`dyld` 的实现就是这么干的：**它把 `entryoff` 直接加到镜像在内存里的基址上，然后跳过去**。拆解三个加数：

- **`__TEXT` 的 `vmaddr`**：文件里写死的"理想加载地址"，64 位可执行文件通常是 `0x100000000`（紧接 4GB `__PAGEZERO` 之后，见 [[12.Mach-O __PAGEZERO]]）；
- **ASLR slide**：内核加载时给所有段统一叠加的随机位移（地址空间布局随机化），每次运行都可能不同；
- **`entryoff`**：文件里写死的、**永不随加载位置变化**的常量偏移。

正因为 `entryoff` 是偏移而非绝对地址，它**天然兼容 `MH_PIE`（地址无关可执行）与 ASLR**：无论这次运行镜像被随机搬到哪个基址，`entryoff` 都不用改、也不需要任何重定位修补。这正是 `LC_MAIN` 相对 `LC_UNIXTHREAD`（内嵌的是含绝对地址 `rip`/`pc` 的完整寄存器状态，PIE 下需要额外处理）的核心优势之一。

> [!note] `entryoff` 与 `__TEXT` 文件偏移的换算
> 若想从 `entryoff` 反推它落在 `__TEXT.__text` 节内的哪个位置：`entryoff` 本身就是文件偏移，可直接拿去和 `__text` 节的 `offset`（节数据文件偏移，见 [[18.Mach-O section]] 与 [[19.Mach-O __text节]]）相减，得到入口在 `__text` 节内的相对位置。在典型可执行文件里，`entryoff` 往往正好等于 `__text` 节的起始文件偏移——因为启动桩 `start` 通常被链接器放在 `__text` 节最前面。

### 4. `entryoff` 指向谁：通常是 `start`，不是 `main`

一个反直觉但极重要的事实：**`entryoff` 指向的入口，通常不是你源码里写的 `main` 函数，而是 C 运行时（CRT）的启动桩 `start`**。`dyld` 跳到 `start`，由 `start` 做完最后一点准备工作后，再 `call` 你的 `main`。

为什么中间要隔一层 `start`？因为从"`dyld` 跳转点"到"符合 C 语义的 `main` 调用"之间，还有几件事要做：

- **按 C/ABI 约定把 `argc/argv/envp/apple` 摆进正确的参数寄存器/栈位置**（x86_64 下 `argc→rdi`、`argv→rsi`、`envp→rdx`、`apple→rcx`）；
- **设置好用于 `main` 返回后收尾的环境**（让 `main` 一 `return`，控制流能正确走到 `exit`）；
- 在更老的路径里，还要做栈/参数的搬运（`LC_UNIXTHREAD` 时代由 `crt1.o` 的 `start` 全包，`LC_MAIN` 时代这部分被 `dyld` + libdyld 的胶水大幅简化）。

所以**"程序入口" ≠ "`main`"**：在 `LC_MAIN` 体系里，`entryoff` 标的是 `start`（链接器默认入口符号），`main` 是被 `start` 调起来的"第二跳"。这也解释了 FAQ 里那个经典问题"为什么 `entryoff` 不是 `main` 的地址"。

> [!note] `-e` 改入口、`-stack_size` 写 `stacksize`
> 默认入口是 `start`（进而调 `main`），但链接时用 **`ld -e <符号>`** 可以把 `LC_MAIN` 的入口改成任意你指定的函数——此时 `entryoff` 就指向那个自定义符号，`main` 甚至可能不被调用。同理，链接时用 **`-stack_size <字节数>`** 会把值写进 `stacksize` 字段；不指定则 `stacksize == 0`，运行期由各平台采用各自默认主线程栈尺寸（macOS 主线程默认通常 8MB 量级，具体以系统为准）。`stacksize` 只管**主线程**初始栈，子线程栈大小由 `pthread` 创建时另行指定，与本字段无关。

### 5. 与 `LC_UNIXTHREAD` 的完整对比

`LC_MAIN` 是 `LC_UNIXTHREAD` 的现代替代品。要真正理解 `LC_MAIN` 的设计取舍，必须把前任拿来对照。`LC_UNIXTHREAD` 走的是 `thread_command` 结构 + **架构相关的线程状态**——它不给偏移，而是**直接内嵌一整套初始寄存器值**，其中程序计数器（x86_64 的 `rip` / arm64 的 `pc`）就是入口地址。

`thread_command` 的结构（`<mach-o/loader.h>`，注意 `flavor`/`count`/`state` 是变长的、被注释在结构外）：

```c
struct thread_command {
    uint32_t  cmd;        /* LC_THREAD 或 LC_UNIXTHREAD（LC_UNIXTHREAD 值 0x5） */
    uint32_t  cmdsize;    /* 总长 = 8 + 每个 flavor 的 (4+4+state 大小) 之和 */
    /* 其后紧跟一个或多个三元组： */
    /* uint32_t flavor;     线程状态的"风味"（架构相关，见 <machine/thread_status.h>） */
    /* uint32_t count;      state 以 uint32_t 计的长度 */
    /* struct XXX_thread_state state;   该 flavor 的寄存器状态结构 */
};
```

x86_64 上 `flavor == x86_THREAD_STATE64`（值 `4`），`state` 是 `x86_thread_state64_t`——21 个 64 位寄存器，`count == 0x2a`（42，按 32 位字计 21×2），整条命令 `cmdsize == 184`（`8 + 4 + 4 + 21×8`）：

```c
struct x86_thread_state64 {   /* x86_THREAD_STATE64, flavor = 4 */
    uint64_t rax, rbx, rcx, rdx, rdi, rsi, rbp, rsp;
    uint64_t r8,  r9,  r10, r11, r12, r13, r14, r15;
    uint64_t rip;             /* ← 入口地址就在这里 */
    uint64_t rflags, cs, fs, gs;
};
```

arm64 上 `flavor == ARM_THREAD_STATE64`，`state` 是 `arm_thread_state64_t`——x0~x28 + fp/lr/sp/pc/cpsr，整条命令 `cmdsize == 288`，入口在 `pc`：

```c
struct arm_thread_state64 {   /* ARM_THREAD_STATE64 */
    uint64_t x[29];           /* x0 ~ x28 */
    uint64_t fp, lr, sp;
    uint64_t pc;              /* ← 入口地址就在这里 */
    uint32_t cpsr;
    /* (含对齐/padding) */
};
```

两者的全面对比：

| 维度 | `LC_MAIN` | `LC_UNIXTHREAD` |
|---|---|---|
| `cmd` 值 | `0x80000028`（带 `LC_REQ_DYLD`） | `0x5`（**不带** `LC_REQ_DYLD`） |
| 命令结构 | `entry_point_command`（定长 24B） | `thread_command` + 变长线程状态 |
| `cmdsize` | 恒 `24` | x86_64=`184`、arm64=`288`（随架构/flavor 变） |
| 入口怎么给 | 一个文件偏移 `entryoff` | 完整初始寄存器状态，PC（`rip`/`pc`）即入口 |
| 还给什么 | `stacksize`（主线程栈大小） | 全套寄存器初值；栈由内核按 shell 栈限制自动建 |
| 跳转执行者 | **`dyld`**（启动末尾跳 `entryoff`） | **内核**直接把寄存器恢复成内嵌状态后跳 |
| ASLR / PIE | 天然友好（偏移与位置无关） | 内嵌绝对地址，PIE 下需额外处理 slide |
| C 运行时 | 入口=`start`，`dyld`+libdyld 胶水极简 | 链接器把 `crt1.o`/`crt0.o` 嵌进每个二进制，`start` 重做大量 `dyld` 已做的活 |
| 引入/取代 | OS X 10.8 / iOS 6 起，现代默认 | 10.8 前的旧式；现仅老/特殊二进制与 `dyld` 自身使用 |
| 解析取入口 | 直接读 `entryoff` | 要解析线程状态、从 `rip`/`pc` 抠出入口 |

> [!note] `LC_THREAD` vs `LC_UNIXTHREAD`
> 同属 `thread_command` 的还有 `LC_THREAD`：两者结构完全一样，区别在于 **`LC_UNIXTHREAD` 会让内核自动创建栈**（按 shell 的栈大小限制），并把命令行参数与环境变量拷到该栈上；`LC_THREAD` 则不自动建栈，多用于 core dump 里记录线程状态、或非 Unix 进程语义的场景。可执行文件的入口用的是 `LC_UNIXTHREAD`。

> [!note] 为什么 `LC_MAIN` 更"快"
> 旧路径里，`crt1.o` 的 `start` 几乎把 `__dyld_start` 刚做过的栈/参数初始化又做了一遍（只是不含 `dyld` 自身的引导），纯属冗余。`LC_MAIN` 体系下，`dyld` 检测到主程序用 `LC_MAIN`，会通过 libdyld 的胶水**更直接地**跳进 `main`，省掉 `crt1.o` 的重复初始化——这正是它被称为"fast path"的由来。

### 6. `dyld` 启动全流程：`LC_MAIN` 是最后一跳

把镜头拉到整条启动链，看清 `LC_MAIN` 在什么时刻、以什么方式被消费。完整链路如下（与本篇第二张图对应）：

1. **内核 `execve`**：校验文件开头的 `mach_header`（`magic`/`cputype` 合法），按 Load Commands 把各段映射进新建的地址空间并施加权限（`__TEXT` 只读可执行等），加载 `LC_LOAD_DYLINKER` 指定的动态链接器（通常 `/usr/lib/dyld`），并**铺设初始栈**——在栈上摆好 `argc`、`argv[]`、`envp[]`（紧跟在 `argv[argc+1]` 之后）、以及 macOS 特有的 `apple[]`（紧跟 `envp` 之后）。
2. **`__dyld_start`**（`dyld` 里第一段跑起来的汇编）：把栈对齐到 ABI 要求、压入终止帧标记，算出 **`dyld` 自身的 slide**（用一个地址恒定的符号与当前 `__dyld_start` 地址相减），把主镜像 `mach_header`、`argc`、`argv`、`dyld` 的 slide 与 `mach_header`、以及 `&startGlue` 等装进寄存器，跳进 `dyldbootstrap::start`。
3. **`dyldbootstrap::start`**：若 `dyld` 自身被 slide，先 `rebaseDyld()` 修正自身的位置敏感数据（之后才能用全局变量）；调 `mach_init()` 让 `dyld` 能用 mach 消息；从栈布局重建 `envp`/`apple` 指针；用 `__guard_setup(apple)` 设好栈金丝雀随机值；最后调用 `dyld::_main`。
4. **`dyld::_main`**（`dyld` 真正的主函数）：先 `configureProcessRestrictions()`（通常限制 `DYLD_*` 环境变量），随后**映射主镜像各段 → 加载并链接所有依赖库（`LC_LOAD_DYLIB` 等，见 [[07.Mach-O LC_LOAD_DYLIB]]）→ 完成 rebase/bind/chained-fixups（`LC_DYLD_INFO_ONLY` 等，见 [[17.Mach-O LC_DYLD_INFO_ONLY]]）→ 运行初始化器**（C++ 构造器、`constructor` 函数，其偏移记在 `__DATA_CONST` 的 `__mod_init_func` 节，见 [[32.Mach-O __mod_init_func节]]）。
5. **入口分派**：`dyld` 调 `getEntryFromLC_MAIN()` 取入口——
   - 若**非零**：主程序用 `LC_MAIN`。`dyld` 把一段 **`startGlue`** 例程的地址**压栈伪装成"返回地址"**（这段胶水负责在程序结束时调 `exit`），然后跳到 `加载基址 + slide + entryoff`。入口处 `start` 跑完、`main` 返回后，那个 `ret` 会"返回"到 `startGlue`，由它调 `exit(返回码)`。
   - 若为零：主程序用 `LC_UNIXTHREAD`（`getEntryFromLC_UNIXTHREAD()`）。`dyld` 把栈恢复原状、跳到 `crt1.o` 的 `start`，由 `start` 自己完成 `main` 前的准备。
6. **`start` → `main(argc, argv, envp, apple)`**：启动桩把四个参数摆进约定寄存器后 `call main`。注意 macOS 的 `main` 比标准 C 多一个第四参数 **`apple`**（一个 key=value 字符串数组，携带可执行路径 `executable_path`、代码签名哈希 `executable_cdhash` 等，供 `dyld`/运行时使用）。
7. **收尾**：`main` 返回其 `int` 退出码，控制流经第 5 步压入的 `startGlue` 走到 `exit`，进程带该退出码终止。

`LC_MAIN` 在这条七步链里**只负责第 5 步那一个数字**——但正因为前四步都是"准备"、第六七步都是"已在你的程序里"，这个数字就是"加载器世界"与"程序世界"的精确分界点。

> [!note] `startGlue` 的"返回地址"小魔术
> `LC_MAIN` 路径有个精巧设计：`dyld` 并不在跳进入口前真的"调用"它（那样还得自己接管返回），而是把 `startGlue` 的地址**压进栈、冒充成入口函数的返回地址**，再直接跳进入口。于是入口里的 `start`/`main` 一路执行，最后那条 `ret` 自然就"返回"到了 `startGlue`，由它统一收尾调 `exit`。这是用一次普通 `ret` 替代"显式调用 + 善后"的常见底层技巧。

### 7. 入口跳转前，初始化器已先跑

一个常被忽略、但对调试与逆向很关键的时序事实：**在 `dyld` 跳到 `entryoff` 之前，主镜像（及其依赖库）的初始化器就已经全部跑完了**（上节第 4 步）。也就是说：

- C++ 全局/静态对象的构造函数、`__attribute__((constructor))` 标注的函数、Objective-C 的 `+load` 等，**都在 `entryoff`（进而 `start`/`main`）之前执行**；
- 这些初始化器的入口偏移登记在 `__DATA_CONST`（旧布局为 `__DATA`）的 **`__mod_init_func`** 节里，由 `dyld` 在第 4 步遍历调用（详见 [[32.Mach-O __mod_init_func节]]）;
- 对应的析构/终止逻辑登记在 `__mod_term_func`（见 [[33.Mach-O __mod_term_func节]]），在 `exit` 路径上反序执行。

所以"程序最先执行的用户代码"严格来说不是 `main`，甚至不是 `start`，而可能是某个全局对象的构造函数或 `constructor`。逆向定位"程序真正起点"时，既要看 `LC_MAIN.entryoff`，也要看 `__mod_init_func` 列表——`entryoff` 是"主流程起点"，`__mod_init_func` 是"更早的初始化起点"。

> [!note] 与 `__DATA_CONST` 的关系
> `__mod_init_func` 现代被放进 `__DATA_CONST`（启动后只读化的段，带 `SG_READ_ONLY` 标志，见 [[15.Mach-O __DATA_CONST]]）——把"启动后不再变"的函数指针表挪进只读区，防止被写原语篡改后劫持初始化流程。这与 `LC_MAIN` 偏移化的设计动机一脉相承：都是为了在 ASLR + 硬化运行时下收紧攻击面。

## 实操：用工具查看

### 示例 1：`otool -l` 看 `LC_MAIN`

```bash
otool -l a.out | grep -A 4 LC_MAIN     # 直接定位 LC_MAIN 命令
otool -l a.out | grep -B 1 -A 3 LC_MAIN
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Load command 12
       cmd LC_MAIN
   cmdsize 24
  entryoff 16064                ; = 0x3ec0，相对 __TEXT(文件起点) 的偏移
 stacksize 0                    ; 用系统默认主线程栈大小
```

> 说明：`cmdsize 24` 自洽（`entry_point_command` 定长）；`entryoff 16064`（0x3EC0）表示入口在 `__TEXT` 内偏移 0x3EC0 处——若 `__TEXT.vmaddr=0x100000000`、本次运行 slide=0x4000，则运行期真实入口 = `0x100000000 + 0x4000 + 0x3EC0 = 0x100007EC0`；`stacksize 0` 表示未用 `-stack_size`，走默认栈。

### 示例 2：对比 `LC_UNIXTHREAD`（老式二进制）

在一个老的或手工构造的二进制上，`otool -l` 看到的入口是另一番模样——直接是寄存器状态，PC 即入口：

```bash
otool -l old_binary | grep -A 40 LC_UNIXTHREAD
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意 `LC_UNIXTHREAD` 用整套寄存器（而非偏移）表达入口。

```text
Load command 10
        cmd LC_UNIXTHREAD
    cmdsize 184                 ; x86_64：8 + 4 + 4 + 21*8
     flavor x86_THREAD_STATE64
      count x86_THREAD_STATE64_COUNT
   rax  0x0   rbx  0x0   rcx  0x0   rdx  0x0
   rdi  0x0   rsi  0x0   rbp  0x0   rsp  0x0
   ... (其余通用寄存器均为 0) ...
   rip  0x0000000100001000      ; ← 入口绝对地址就在 rip
rflags  0x0   cs 0x0  fs 0x0  gs 0x0
```

> 说明：与 `LC_MAIN` 形成对照——这里没有 `entryoff`，入口藏在 `rip`（arm64 则在 `pc`）里，且是**绝对地址**（PIE 下需配合 slide 处理）。`cmdsize 184` 自洽（21 个 64 位寄存器）。要从这种命令取入口，必须解析线程状态、定位 `rip`/`pc`。

### 示例 3：反汇编入口、验证 `entryoff` 指向 `start`

把 `entryoff` 换算成地址后反汇编，验证它落在启动桩而非 `main`：

```bash
# 看入口符号（通常是 start，进而 bl/call _main）
otool -tV a.out | head -40
# 或用 lldb 在入口下断、确认调用栈是 start -> main
lldb a.out -o 'b main' -o 'run' -o 'bt' -o 'quit'
```

> [!warning] 示例输出为示意

```text
_start:                          ; entryoff 指向这里，不是 _main
0000000100003ec0  mov    rdi, ...   ; 整理 argc
0000000100003ec8  mov    rsi, ...   ; 整理 argv
0000000100003ed0  ...               ; 摆放 envp/apple
0000000100003ee0  call   _main      ; ← 第二跳：这里才进你的 main
0000000100003ee5  mov    edi, eax   ; main 返回值 -> 退出码
0000000100003ee7  call   _exit      ; (LC_MAIN 路径多由 dyld 的 startGlue 接管)
```

> 说明：反汇编印证了第 4 节的结论——`entryoff`（这里 0x3EC0）落在 `_start`，`_start` 内部 `call _main` 才进入你的代码。这就是"为什么 `entryoff` 不是 `main` 的地址"最直观的证据。

## FAQ

> [!question] 为什么 `entryoff` 不是 `main` 的地址？
> 因为从"`dyld` 跳转点"到"符合 C 语义的 `main` 调用"之间还隔着一层 C 运行时启动桩 `start`。`dyld` 跳到的是 `start`（链接器默认入口符号），由 `start` 把 `argc/argv/envp/apple` 按 ABI 摆进参数寄存器、布置好返回收尾环境，再 `call main`。所以 `entryoff` 标的是 `start`，`main` 是被 `start` 调起来的第二跳。只有当你用 `ld -e <符号>` 显式改了入口，`entryoff` 才会指向你指定的那个函数（那时 `main` 甚至可能不被调用）。

> [!question] `entryoff` 是文件偏移还是内存地址？运行期怎么变成真实地址？
> 是**文件偏移**——相对文件起点，由于 `__TEXT` 从文件偏移 0 映射，它在数值上也等于相对 `__TEXT` 段基址的偏移，但**不是**可以直接跳的虚拟地址。运行期真实入口 = `__TEXT.vmaddr + ASLR slide + entryoff`：`dyld` 把这个常量偏移直接加到镜像在内存里的基址上再跳。用偏移而非绝对地址，正是为了让 `MH_PIE` + ASLR 下"镜像随机搬到哪都不用改、不用重定位"。

> [!question] `LC_MAIN` 和 `LC_UNIXTHREAD` 能同时出现吗？该信哪个？
> **正常二进制里两者互斥**——一个可执行文件的入口要么由 `LC_MAIN` 给、要么由 `LC_UNIXTHREAD` 给，链接器只会生成其中之一。`dyld` 的取入口逻辑也体现了这点：先试 `getEntryFromLC_MAIN()`，**非零就走 `LC_MAIN` 路径**（libdyld 胶水跳 `main`）；为零才回退到 `getEntryFromLC_UNIXTHREAD()`（恢复寄存器跳 `crt1.o` 的 `start`）。若你在畸形/被篡改样本里同时见到两条，应以 `LC_MAIN` 优先（现代 `dyld` 的判定顺序），并警惕这是人为构造的迹象。

> [!question] `stacksize` 为 0 意味着什么？怎么改？它管子线程吗？
> `stacksize == 0` 表示链接时没用 `-stack_size`，运行期由各平台用**默认主线程栈尺寸**（macOS 主线程通常 8MB 量级，以系统为准）。要改就在链接时加 `ld -stack_size 0x<字节数>`，值会写进该字段、`dyld` 据此为主线程分配初始栈。它**只管主线程**：子线程（`pthread_create`）的栈大小在创建时由 `pthread_attr_setstacksize` 等单独指定，与 `LC_MAIN.stacksize` 无关。

> [!question] `cmd` 为什么是 `0x80000028` 这么个怪值，而不是干净的 `0x28`？
> 因为它把基础命令号 `0x28`（十进制 40）与 **`LC_REQ_DYLD`**（`0x80000000`，最高位）按位或在了一起。`LC_REQ_DYLD` 标记"这条命令是程序正确运行的**必要条件**，`dyld` 看不懂必须报 `unknown load command required for execution` 拒载"，而不是像普通可选命令那样被忽略。`LC_MAIN` 必须带这个位，是因为入口跳转**只有 `dyld` 会做**，一个不认识它的旧 `dyld` 若"忽略"这条命令，程序就无从启动。解析时用整值 `0x80000028` 匹配，或先 `cmd & ~LC_REQ_DYLD` 再比 `0x28`。

## 小结

- `LC_MAIN` 用定长 24 字节的 `entry_point_command` 描述程序入口：`entryoff`（入口相对文件 / `__TEXT` 起点的偏移）+ `stacksize`（主线程初始栈大小，`0` 为默认），`cmdsize` 恒为 24。
- `cmd == 0x80000028` = 命令号 `0x28` | `LC_REQ_DYLD`（`0x80000000`）：`dyld` 必须理解它，否则报错拒载——因为入口跳转只有 `dyld` 会做。
- `entryoff` 是**文件偏移、不是绝对地址**；运行期真实入口 = `__TEXT.vmaddr + ASLR slide + entryoff`，用偏移天然契合 `MH_PIE` 与 ASLR。
- `entryoff` 通常指向 C 运行时启动桩 `start`，**不是** `main`；`start` 备好 `argc/argv/envp/apple` 后再 `call main`（macOS 的 `main` 多一个第四参数 `apple`）。
- 它在 OS X 10.8 / iOS 6 起取代 `LC_UNIXTHREAD`：后者用 `thread_command` + 架构相关线程状态（x86_64 `rip` / arm64 `pc` 即入口）直接给整套寄存器，由内核恢复后跳转、并需嵌 `crt1.o`；前者只给偏移、由 `dyld` 跳转，省冗余且 ASLR 友好。
- 时序上，`dyld` 完成"映射段 → 加载依赖 → rebase/bind → 运行初始化器（`__mod_init_func`）"后，最后一步才跳 `entryoff`；初始化器（C++ 构造器、`constructor`）比 `entryoff` 更早执行。
- `LC_MAIN` 路径用 `startGlue` 压栈伪装返回地址的小技巧，让 `main` 返回后自然走到 `exit`，省掉 `crt1.o` 重复 `dyld` 已做工作的开销（fast path）。
