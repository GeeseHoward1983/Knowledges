# 详解Mach-O(四十二)Mach-O __objc_protorefs节

> [!abstract] TL;DR
> **`__objc_protorefs`（全称 `__DATA,__objc_protorefs`，现代二进制里多为 `__DATA_CONST,__objc_protorefs`）是"协议引用表"（protocol references）**：一张**指针数组**，源码里**每出现一处 `@protocol(SomeProtocol)` 表达式**，编译器就在本表里生成一个槽，初值是一个指向某个 `protocol_t`（协议本体结构）的指针，而 `@protocol(SomeProtocol)` 这处代码被编译成"对本表某槽的读取"。
> **镜像加载时，ObjC runtime 在 `_read_images` 阶段遍历本表**：用 `_getObjc2ProtocolRefs(hi, &count)` 拿到本节，对每个槽调用 `remapProtocolRef(&protoref)`——它按协议的 `mangledName` 去**全局协议哈希表**（`NXMapTable protocol_map`）查到那个**规范（唯一）协议实例**，若与槽里现值不同就**回填**改写槽位。于是 `@protocol(X)` 求得的永远是进程内**唯一的 `protocol_t`**。
> 它与**定义**协议的 [[38.Mach-O __objc_protolist节]] 严格相对：protolist 是"**我定义了哪些协议**"（每项指向带名字/继承/四张方法表/属性的**完整 `protocol_t`**），protorefs 是"**我代码里用到了哪些协议**"（每项只是一个**指针槽**，被绑定到那个唯一实例）。被引用的协议**未必由本镜像定义**，可能来自别的库。
> 唯一化（uniquing）保证 **`@protocol(X) == @protocol(X)` 恒成立**、`conformsToProtocol:` 的比较可靠。它属于 ObjC **四大"引用类"节**（`selrefs`/`classrefs`/`superrefs`/`protorefs`）之一——存的是"对元数据的**引用**"而非元数据本身（协议本体在 protolist 指向的 `protocol_t`），并收尾了 ObjC 元数据"定义 vs 引用"的完整对照体系。

## 概述与定位

要理解 `__objc_protorefs` 为什么存在，先看一句最常见的 Objective-C 代码：`@protocol(NSCopying)`。它是一个**表达式**，求值结果是一个 `Protocol *`（协议对象）——你能把它传给 `[obj conformsToProtocol:@protocol(NSCopying)]` 判断遵从、传给 `class_addProtocol(cls, @protocol(NSCopying))` 给类追加协议、或与另一个协议对象做 `==` 比较。问题是：**编译单个 `.o` 时，编译器并不知道运行时那个"唯一协议对象"的最终地址**——同名协议可能在本镜像定义、也可能在 Foundation 等别的库里定义，到底谁是"规范实例"，要等 runtime 在加载期把所有镜像的协议都登记、唯一化之后才能定。

编译器能做的，只是为每一处 `@protocol(...)` 在 `__objc_protorefs` 里留一个**指针槽**，初值先指向"本编译单元当前能看到的那个 `protocol_t`"（通常是本镜像内的协议本体，或一个对外部协议的占位符号引用），作为"这处代码引用了这个协议"的占位。真正把它**改写成进程内唯一的规范协议指针**的工作，推迟到加载期由 runtime 完成——这个**编译期占位、加载期回填**的两段式设计，与 [[35.Mach-O __objc_selrefs节]] 处理 selector、[[40.Mach-O __objc_classrefs节]] 处理类如出一辙，是整个 ObjC "引用类"四节的共同骨架。

把它放进 [[18.Mach-O section|节（section）的通用模型]] 看：`__objc_protorefs` 是一个无头部、无计数字段的连续指针数组，住在可写段（旧二进制 `__DATA`、现代二进制 `__DATA_CONST`），条目数靠 `节大小 size ÷ 指针宽度` 推算。它与 [[35.Mach-O __objc_selrefs节]]、[[40.Mach-O __objc_classrefs节]]、`__objc_superrefs`（见 [[41.Mach-O __objc_supperrefs节]]）一道构成 ObjC 元数据里的**"引用类"四节**——它们都不存元数据本体，只存"指向本体的、需被加载期修正的指针"。runtime 在 `_read_images` 里注册类/协议本体（"列表类"节）的同期，统一处理这四张引用表。`__objc_protorefs` 是其中**专管协议引用**的一员，也是 ObjC 元数据"定义 vs 引用"对照体系的**收官一节**。

> [!note] "引用 vs 定义"：`__objc_protorefs` 与 `__objc_protolist` 的分工
> 这是本篇最核心、也最容易混的一对概念，务必分清（对照 [[38.Mach-O __objc_protolist节]]）：
> - **`__objc_protolist`（定义方 / 被指方）**：登记"**本镜像定义了哪些协议**"。每项指向一个**完整的 `protocol_t`**——含协议名 `mangledName`、所继承的协议列表 `protocols`、**四张方法表**（必选/可选 × 实例/类）、属性列表等全部信息。加载时由 `readProtocol` **注册进全局协议表并唯一化**（同名只留一个规范实例）。它是"协议本体（数据）"。
> - **`__objc_protorefs`（引用方 / 指向方）**：登记"**本镜像代码里用到了哪些协议**"（即每处 `@protocol(X)` 表达式）。每项只是一个**指针槽**，不含协议的任何描述信息，加载时由 `remapProtocolRef` **绑定到全局表里那个唯一的 `protocol_t`**。它是"指向本体的、可变的引用"。
> 一句话：**protolist 提供"协议长什么样、有哪些方法"，protorefs 提供"代码在哪里用到了这个协议、运行时它对应哪个唯一实例"**。一个协议本体（protolist 一项）可被任意多处 `@protocol(X)`（protorefs 多个槽，甚至跨多个镜像）引用；而被引用的协议**未必**出现在本镜像的 protolist 里（可能定义在 Foundation/UIKit 等外部库）。

## 核心原理与字段详解

### 1. 内容布局：一张"指向协议对象"的指针数组

`__objc_protorefs` 在文件里就是一段**连续的指针数组**，没有头部、没有计数字段——和所有 ObjC 列表/引用节一样，**条目数由 `节大小 size ÷ 指针宽度` 推算**（64 位 `size/8`、32 位 `size/4`，参见 [[18.Mach-O section|节的 size 与条目数推算]]）。每个槽的**编译期初值**是一个指针，指向一个 `protocol_t`（协议本体结构，其字段详见 [[38.Mach-O __objc_protolist节]]）。

编译器为源码里**每一处 `@protocol(...)` 表达式**生成一个槽。被引用的协议**可能在本镜像定义**（这时初值直接指向本镜像 `__objc_protolist` 收录的那个 `protocol_t`），**也可能来自别的库**（这时初值指向一个对外部协议的占位/符号引用，留待加载期绑定）。多处引用**同一个协议**时，protorefs 里会有多个槽——它们最终都会被回填到**同一个**规范 `protocol_t` 上。

> [!note] 它由编译器/链接器协作生成，不是手写
> Clang 处理 `@protocol(X)` 表达式时，由 Apple 运行时代码生成器（`CGObjCMac.cpp`）里的 `GetProtocolRef(const ObjCProtocolDecl *PD)` 发射一个对协议元数据的**引用常量**，落进名为 `__objc_protorefs` 的节，并把这处 `@protocol(X)` 编译成"加载该 protoref 槽的值"。这条"字面量引用 → 加载期 fixup"的路径，与运行期动态查协议的 `objc_getProtocol("X")` 是**两条等价路**：前者读一个已 fixup 的指针槽，后者按名字现查全局表。Clang 的 `objc_non_runtime_protocol` 属性文档也佐证了这一点——被标为"非运行时协议"的协议**不能**用作 `@protocol(X)` 的操作数、`objc_getProtocol` 也找不到它，因为这两条路都依赖协议的 `protocol_t` 元数据真实存在。

### 2. 加载期绑定与唯一化：`_read_images` → `_getObjc2ProtocolRefs` → `remapProtocolRef`

镜像被 `dyld` 映射进来后，ObjC runtime 在 `_objc_init` → `map_images` → **`_read_images`** 里完成协议引用的修正。核心流程（基于 Apple `objc4` 源码 `objc-runtime-new.mm`）分两步——**先有"定义"侧把协议登记唯一化，再有"引用"侧把每个槽重映射到唯一实例**：

**第一步：登记协议本体、建立唯一化表（"定义"侧，处理 `__objc_protolist`）。** runtime 遍历每个镜像的 `__objc_protolist`，对每个协议调用 `readProtocol(...)`，把它按 `mangledName` 注册进**进程级全局协议哈希表** `protocols()`（一个惰性初始化的 `NXMapTable`）：

```cpp
// 全局唯一协议表：名字 → 规范 protocol_t；读写需持 runtimeLock
static NXMapTable *protocols(void) {
    static NXMapTable *protocol_map = nil;
    INIT_ONCE_PTR(protocol_map, NXCreateMapTable(NXStrValueMapPrototype, 16), ...);
    return protocol_map;
}
// 按名字查：先按原名，未命中再试 Swift mangle 后的名字
static Protocol *getProtocol(const char *name) {
    Protocol *result = (Protocol *)NXMapGet(protocols(), name);
    if (result) return result;
    if (char *swName = copySwiftV1MangledName(name, true /*isProtocol*/)) {
        result = (Protocol *)NXMapGet(protocols(), swName);
        free(swName);
        return result;
    }
    return nil;
}
```

`readProtocol` 用 `getProtocol(newproto->mangledName)` 查：**查不到（首次出现）**就把这份作为该名字的**规范实例**插入（普通镜像用 `NXMapInsert`，bundle 用 `NXMapKeyCopyingInsert` 拷贝键防卸载后悬空）；**查得到（同名已存在）**则**丢弃这份重复定义**、沿用已登记的那个。这一步保证**进程内每个协议名只有一个规范 `protocol_t`**——即**唯一化（uniquing）**。

**第二步：重映射每个协议引用槽（"引用"侧，处理 `__objc_protorefs`）。** 唯一化表就绪后，runtime 取出本镜像的 `__objc_protorefs`，逐槽 `remapProtocolRef`：

```cpp
// 取节：GETSECT 宏生成的访问器，读的就是名为 "__objc_protorefs" 的节
// GETSECT(_getObjc2ProtocolRefs, protocol_t *, "__objc_protorefs")
protocol_t **protolist = _getObjc2ProtocolRefs(hi, &count);   // count = size / 指针宽度
for (size_t i = 0; i < count; i++) {
    remapProtocolRef(&protolist[i]);
}

// 把"任意一份同名协议指针"重映射到全局表里的规范实例
static protocol_t *remapProtocol(protocol_ref_t proto) {
    protocol_t *newproto = (protocol_t *)
        getProtocol(((protocol_t *)proto)->mangledName);   // 按 mangledName 查规范实例
    return newproto ? newproto : (protocol_t *)proto;      // 查不到则保留原值
}

// 仅当槽里现值与规范实例不同才回填（避免无谓弄脏内存页）
static size_t UnfixedProtocolReferences;
static void remapProtocolRef(protocol_t **protoref) {
    protocol_t *newproto = remapProtocol((protocol_ref_t)*protoref);
    if (*protoref != newproto) {
        *protoref = newproto;
        UnfixedProtocolReferences++;
    }
}
```

这一遍跑完，runtime 打日志 **"fix up @protocol references"**（可用环境变量 `OBJC_PRINT_IMAGE_TIMES=YES` 在 Xcode scheme 里观察各阶段耗时）。此后代码任何时候读这个槽，拿到的都是**全进程唯一的 `protocol_t` 指针**，可直接用于 `@protocol(X)` 求值、`==` 比较或 `conformsToProtocol:`。

> [!note] `_getObjc2ProtocolRefs` vs `_getObjc2ProtocolList`：别读错节
> runtime 里有两个名字极像的访问器，分别读**两个不同的节**，务必区分：
> - `_getObjc2ProtocolRefs(...)` 由 `GETSECT(_getObjc2ProtocolRefs, protocol_t *, "__objc_protorefs")` 生成，读**引用**节 `__objc_protorefs`（本篇），喂给 `remapProtocolRef`。
> - `_getObjc2ProtocolList(...)` 由 `GETSECT(_getObjc2ProtocolList, protocol_t *, "__objc_protolist")` 生成，读**定义**节 `__objc_protolist`（见 [[38.Mach-O __objc_protolist节]]），喂给 `readProtocol` 做注册唯一化。
> 一个读"引用"、一个读"定义"，节名写错就拿不到对应数据。两者在 `_read_images` 里**先 List（登记唯一化）后 Refs（重映射）**配合工作。

> [!note] 回填的"不等才写"：和 selrefs 同源的省脏页优化
> `remapProtocolRef` 里 `if (*protoref != newproto) *protoref = newproto;` 这个"不等才写"判断是有意为之，与 [[35.Mach-O __objc_selrefs节]] 里 `map_selrefs` 的 `if (sels[i] != sel) ...` 同源：**回填会弄脏（dirty）该内存页**，触发写时复制（COW），把本可多进程共享的干净页变成各进程私有的脏页。对经 **dyld 共享缓存预优化**的系统库，protoref 槽在装载时**就已经指向正确的规范实例**了（`*protoref == newproto`），此时跳过写入就不增加内存压力。源码里的 `UnfixedProtocolReferences` 计数器统计的正是"确实需要改写"的引用数。

### 3. 绑定到全局唯一 `protocol_t`：为何必须唯一化

协议引用的唯一化不是为了好看，而是直接服务于**协议的比较与遵从判定**。考虑这个跨库场景：你的 App 里用 `@protocol(NSCopying)`，Foundation 自己也定义并使用 `NSCopying`。如果每个镜像各自的 protoref 槽都指向"本镜像看到的那份 `protocol_t`"，那么：

- `@protocol(NSCopying) == @protocol(NSCopying)` 可能在跨库时**返回假**（两个不同地址）；
- `[obj conformsToProtocol:@protocol(NSCopying)]` 的内部比较也可能错判——遵从判定要沿协议的 `protocols`（继承）字段递归比对协议指针（`protocol_conformsToProtocol` / `conformsToProtocol:`），指针不统一就比不对。

唯一化把"任意镜像里任意一份同名协议"都归一到**全进程同一个规范 `protocol_t`**（`readProtocol` 登记 + `remapProtocolRef` 重映射），于是所有 protoref 槽都指向这唯一实例。这才是 **`@protocol(X) == @protocol(X)` 恒成立**、`conformsToProtocol:` 比较可靠的前提。可以类比 [[35.Mach-O __objc_selrefs节]]：selector 唯一化让 `objc_msgSend` 敢用 `SEL` 指针相等做缓存键；协议唯一化让协议遵从判定敢用 `protocol_t` 指针相等做比较。

> [!note] 协议的 `mangledName` 是唯一化的"钥匙"
> 唯一化全程以协议的 `mangledName`（`protocol_t` 的首字段）为哈希键。普通 ObjC 协议的 `mangledName` 就是原名（如 `NSCopying`）；与 Swift 互通的协议可能带 mangle 前缀，所以 `getProtocol` 会**先按原名查、未命中再试 Swift mangle 后的名字**。这也解释了为什么 `__objc_protorefs` 的槽**不需要**存协议名——名字信息在它指向的 `protocol_t.mangledName` 里，runtime 顺着指针就能取到，再拿去查表重映射。

### 4. 为什么住在可写段（`__DATA` / `__DATA_CONST`）

理由与其它三张引用表完全一致：**槽要被运行期回填（重映射到规范 `protocol_t`）**，而代码段 `__TEXT` 是 `r-x`（只读可执行）写不了，所以 protorefs 不能放 `__TEXT`，只能放可写的数据段。

- **传统布局**：放在 `__DATA`（`rw-`），加载期 dyld 的 bind/rebase 或 runtime 的 `remapProtocolRef` 直接改写即可。
- **现代布局（链式 fixups）**：iOS 9 / 对应 macOS 起，这批"加载后即固化、之后只读"的 ObjC 节（含 `__objc_protorefs`、`__objc_protolist`、`__objc_classrefs` 等）迁到了 **`__DATA_CONST`**。`__DATA_CONST` 的特点是"**加载期可写、之后只读**"——dyld 先按链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）遍历这些指针完成 rebase/bind 与回填，**回填完再把这些页重新保护为只读**。这样既满足"加载期要回填"的写需求，又能在运行期享受只读页的安全收益（防止协议指针被篡改）。解析工具（如 MachOView）的稳妥做法是"先在 `__DATA` 找，找不到再去 `__DATA_CONST` 找"。

> [!note] 架构差异与 dyld 共享缓存预优化
> ① **指针宽度**：64 位每槽 8 字节、32 位 4 字节，条目数相应用 `size/8` 或 `size/4` 算。
> ② **链式 fixups**：新版 dyld 改变了"回填"的**机制**（指针以链式编码、由 dyld 统一遍历），但"protoref 槽 → 规范 `protocol_t`"的**语义不变**。
> ③ **共享缓存预优化（dyld shared cache）**：对系统库，dyld 在构建共享缓存时就把协议预先唯一化、标记为规范（`hasPreoptimizedProtocols()` / `getPreoptimizedProtocol(name)`），相应的 protoref 槽**装载时就已指向正确的规范实例**，`remapProtocolRef` 因 `*protoref == newproto` 跳过写入。即便如此，runtime 仍会把缓存里的协议**登记进全局表**（以支持"缓存外的替换定义"），所以"fixup 可省，登记不可省"。协议引用的**语义与 CPU 架构无关**。

### 5. ObjC 四大"引用类"节对照（收尾：selrefs / classrefs / superrefs / protorefs）

`__objc_protorefs` 是 ObjC **"引用类"四节**的最后一员。这四张表结构同型（都是"加载期被回填的指针数组"，都住可写段），只是指向的对象不同、由不同的 `GETSECT` 访问器读取、用不同的机制唯一化/重映射。至此整个对照体系闭合：

| 引用节 | 每槽指向（编译期初值） | 回填后是什么 | runtime 访问器 / 修正函数 | 对应的"定义"节（本体） |
|---|---|---|---|---|
| [[35.Mach-O __objc_selrefs节]] | `__objc_methname` 的 selector 名字串 | 全局唯一 `SEL` | `_getObjc2SelectorRefs` / `sel_registerName` | `__objc_methname` |
| [[40.Mach-O __objc_classrefs节]] | 类对象 `objc_class` | 已实现的 `Class` 指针 | `_getObjc2ClassRefs` / `remapClassRef` | [[36.Mach-O __objc_classlist节]] |
| [[41.Mach-O __objc_supperrefs节]] | 父类对象 | 父类 `Class` 指针（`[super …]` 用） | `_getObjc2SuperRefs` / `remapClassRef` | [[36.Mach-O __objc_classlist节]] |
| **`__objc_protorefs`** | 协议对象 `protocol_t` | 唯一化的 `protocol_t` / `Protocol *` | `_getObjc2ProtocolRefs` / `remapProtocolRef` | [[38.Mach-O __objc_protolist节]] |

它们的共性是：**编译期是"指向本体的占位指针"，加载期被 runtime/dyld 修正为"运行时真正可用的唯一对象指针"**。差异只在"被指本体是什么、用什么函数唯一化/重映射"。`__objc_protorefs` 与 `__objc_protolist`（[[38.Mach-O __objc_protolist节]]）配对，恰好为前三对（selector、类、父类）的"引用 vs 定义"补上了**协议**这一对，构成 ObjC 元数据"我用什么 vs 我有什么"的完整对照。

> [!note] 与"列表类"节的区别：我用什么 vs 我有什么
> 别把"引用类"四节和 [[36.Mach-O __objc_classlist节]]、[[38.Mach-O __objc_protolist节]] 这类"**列表/定义类**"节混了：protolist/classlist 列的是"**本镜像定义了哪些协议/类**"（供 runtime 注册"我提供的元数据"），而 protorefs/selrefs/classrefs/superrefs 记的是"**本镜像代码引用了哪些协议/selector/类**"（供 runtime 修正"我要用到的引用"）。一个是"我有什么"，一个是"我用什么"。runtime 在 `_read_images` 里**先处理定义侧（登记、唯一化），再处理引用侧（重映射）**——对协议而言，就是"先 `readProtocol` 后 `remapProtocolRef`"。

## 实操：用工具查看

### 示例 1：`otool -s __DATA __objc_protorefs` dump 原始指针

`otool -s 段名 节名` 以十六进制 dump 指定节的原始字节。注意**段名要按你二进制的实际布局给**——现代二进制多在 `__DATA_CONST`，老二进制在 `__DATA`；稳妥做法是先 `otool -l` 看清它归属哪个段：

```bash
otool -l ObjCBinary | grep -B1 -A4 __objc_protorefs        # 先看它在 __DATA 还是 __DATA_CONST
otool -s __DATA __objc_protorefs /path/to/ObjCBinary        # 老布局/部分二进制
otool -s __DATA_CONST __objc_protorefs /path/to/ObjCBinary  # 现代布局（链式 fixups）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，**地址/字节均为示意**，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__objc_protorefs) section
00000001000092c0  40 8a 00 00 01 00 00 00      ; protoref[0] → 0x100008a40 = protocol_t (NSCopying)
00000001000092c8  80 8b 00 00 01 00 00 00      ; protoref[1] → 0x100008b80 = protocol_t (NSCoding)
00000001000092d0  c0 8c 00 00 01 00 00 00      ; protoref[2] → 0x100008cc0 = protocol_t (MyDelegate, 本镜像定义)
```

> 说明：左列是该槽自身的虚拟地址（从节 `addr` 起算），右列 8 字节是**小端**指针值（`40 8a 00 00 01 00 00 00` → `0x0000000100008a40`），逐个指向一个 `protocol_t`。本节大小 `0x18` → 条目数 `0x18 / 8 = 3` 个。**这是磁盘上的初值；进程加载并经 `remapProtocolRef` fixup 后，这些槽会被重映射到全局表里的规范 `protocol_t`，跨库同名协议最终都指向同一实例。**

### 示例 2：`otool -ov` 把协议引用解析成名字

`otool -ov`（`-o` 解析 ObjC 元数据、`-v` 符号化）会把 protoref 顺着指针解析成它指向的协议名/符号，比裸十六进制直观得多：

```bash
otool -ov /path/to/ObjCBinary                       # 完整 dump ObjC 段（含 protorefs 解析）
otool -ov /path/to/ObjCBinary | grep -i protocol    # 只看协议相关片段（含 protolist/protorefs）
```

> [!warning] 示例输出为示意
> 数值/地址/符号均为构造，仅示意 `otool -ov` 如何把 protoref 槽解析回协议名。

```text
Contents of (__DATA,__objc_protorefs) section
00000001000092c0  0x0000000100008a40 _OBJC_PROTOCOL_$_NSCopying
00000001000092c8  0x0000000100008b80 _OBJC_PROTOCOL_$_NSCoding
00000001000092d0  0x0000000100008cc0 _OBJC_PROTOCOL_$_MyDelegate
```

> 说明：`otool -ov` 替你把每个槽的指针顺藤摸瓜解析到对应的 `protocol_t` 符号（行尾的 `_OBJC_PROTOCOL_$_NSCopying` 等）。这正是逆向时定位"某段代码到底引用了哪些协议"的常用手段——protoref 表几乎就是这个二进制"用到的协议清单"。想进一步看协议**本体**（四张方法表、继承关系），则去解析 [[38.Mach-O __objc_protolist节]]（同样 `otool -ov`，但看 `__objc_protolist` 段落）。

> [!note] 逆向提醒：从共享缓存抽出的 dylib 可能解析不出协议名
> 当一个库被从 **dyld 共享缓存**单独抽取出来时，它的 protoref 指针可能指向**抽取后已不在本文件内**的地址（协议本体还留在共享缓存里）。此时 `otool`/Ghidra 等工具会显示成 `DAT_<address>` 这类裸地址、解析不出协议名。要正确解析，需用**感知共享缓存**的工具或在完整缓存环境下分析——这一点与 [[35.Mach-O __objc_selrefs节]] 的 selref 处境一致。

## FAQ

> [!question] `__objc_protorefs` 和 `__objc_protolist` 到底差在哪？为什么要分两节？
> 一个是"**引用**"，一个是"**定义**"。[[38.Mach-O __objc_protolist节]] 登记**本镜像定义了哪些协议**，每项指向**完整的 `protocol_t`**（带名字、继承、四张方法表、属性等全部信息），加载时由 `readProtocol` 注册进全局表并唯一化。`__objc_protorefs`（本篇）则记录**代码里每处 `@protocol(X)` 表达式**，每项只是一个**指针槽**、不含任何协议描述，加载时由 `remapProtocolRef` 绑定到全局唯一的协议对象。分两节是因为二者职责不同：**定义是"协议本体（数据）"，可被多处引用**；**引用是每处使用一个、需运行期重映射的"指针"**。一个协议本体（protolist 一项）可被任意多处 `@protocol(X)`（protorefs 多个槽，甚至跨多个镜像）引用；且被引用的协议**未必**在本镜像 protolist 里（可能定义在别的库）。简记：protolist 是"协议词典里的词条"，protorefs 是"正文里引用该词条的脚注"。

> [!question] `@protocol(SomeProtocol)` 在二进制里到底变成了什么？
> 变成**对 `__objc_protorefs` 里某个槽的读取**。Clang 的 `GetProtocolRef` 为这处表达式发射一个引用常量放进 `__objc_protorefs`，并把 `@protocol(SomeProtocol)` 编译成"加载该 protoref 槽的值"。**磁盘上**这个槽的初值指向某个 `protocol_t`（本镜像内或外部占位）；**加载后**被 `remapProtocolRef` 重映射成全进程唯一的规范 `protocol_t`，所以运行时 `@protocol(SomeProtocol)` 求值得到的是那个唯一实例，可直接用于 `==` 比较、`conformsToProtocol:`、`class_addProtocol` 等。整个过程对源码透明——你写 `@protocol(X)`，编译期占位、加载期回填替你把它接到唯一协议对象上。它与运行期 `objc_getProtocol("X")` 是两条等价路：前者读已 fixup 的槽，后者按名字现查全局表。

> [!question] runtime 怎么保证 `@protocol(X) == @protocol(X)` 恒成立、`conformsToProtocol:` 比较可靠？
> 靠**唯一化（uniquing）+ 重映射**两步。加载每个镜像时，`readProtocol` 先用协议的 `mangledName` 去**全局协议哈希表**（`NXMapTable protocol_map`）登记：首次出现就作为该名字的**规范实例**插入，已有同名就丢弃重复定义。于是进程内每个协议名只对应一个 `protocol_t`。随后 `remapProtocolRef` 遍历 `__objc_protorefs` 的每个槽，调 `remapProtocol`（按 `mangledName` 查规范实例）把槽**重映射到这唯一实例**（不等才写）。两步做完，所有 `@protocol(X)` 引用——无论在哪个镜像、引用了多少次——都指向同一个 `protocol_t`，故指针 `==` 恒成立；`conformsToProtocol:` 沿协议 `protocols` 继承链递归比较协议指针时，因指针已统一而比较可靠。

> [!question] `__objc_protorefs` 为什么要放在可写段，而不是放只读 `__TEXT`？
> 因为它的槽**必须在加载期被改写**（从"编译期初值"重映射成"全局唯一 `protocol_t`"），而 `__TEXT` 是只读的写不了。传统上它放 `rw-` 的 `__DATA`；现代二进制放 **`__DATA_CONST`**——这是"加载期可写、fixup 完再转只读"的折中：dyld 用链式 fixups 遍历回填完这些指针后，把页重新保护成只读，**既满足回填的写需求，又让运行期享受只读页的防篡改收益**。所以你会看到同一个 protoref 节在老二进制属 `__DATA`、在新二进制属 `__DATA_CONST`，但语义一致——这与 [[35.Mach-O __objc_selrefs节]]、[[40.Mach-O __objc_classrefs节]] 完全同源。

> [!question] 被 `@protocol(X)` 引用的协议，一定在本镜像的 `__objc_protolist` 里吗？
> 不一定。`__objc_protolist` 只收录**本镜像自己定义**的协议；而 `@protocol(X)` 完全可以引用**别的库定义**的协议（比如 App 里 `@protocol(NSCopying)` 引用的是 Foundation 定义的协议）。这种情况下，本镜像 protorefs 里有这个槽，但本镜像 protolist 里**没有**对应的协议本体——槽的初值是一个对外部协议的占位/符号引用，加载期由 `remapProtocolRef` 按名字在**全局表**里查到（由定义它的那个库登记）的规范实例并绑定。这正是"引用"与"定义"可以分处不同镜像的体现，也是唯一化必须做成**进程级全局**的原因。

## 与相邻章节的关系

- [[38.Mach-O __objc_protolist节]]：协议**定义**表，与本表的"**引用**"严格相对；每个 `@protocol(X)` 引用经唯一化绑定到 protolist 登记的规范 `protocol_t`。"引用 vs 定义"的另一半。
- [[35.Mach-O __objc_selrefs节]]：并列的"引用类"节之一，槽指向 selector 名、回填为唯一 `SEL`。结构与回填机制（含"不等才写"省脏页）与本节同源。
- [[40.Mach-O __objc_classrefs节]]：并列的"引用类"节之一，槽指向类、回填为 `Class`。
- [[41.Mach-O __objc_supperrefs节]]：并列的"引用类"节之一，槽指向父类、回填为父类 `Class`（`[super …]` 用）。
- [[36.Mach-O __objc_classlist节]]：runtime 在 `_read_images` 同期处理的"列表/定义类"节（类的定义侧），与引用类四节构成"我有什么 vs 我用什么"。
- [[18.Mach-O section]]：本节"无头、指针数组、条目数靠 `size÷指针宽度` 推算"、可写段与回填的通用模型，都在那篇的字段说明书里。
- [[43.Mach-O __RODATA]]：系列收官篇，只读数据段的一般化讨论。

## 小结

- `__objc_protorefs`（`__DATA`/新二进制 `__DATA_CONST`）是 **协议引用表**：一张指针数组，**每槽对应源码里一处 `@protocol(X)` 表达式**，编译期由 Clang 的 `GetProtocolRef` 生成，初值指向某个 `protocol_t`；条目数 = `size ÷ 指针宽度`。
- **加载期**：runtime 在 `_read_images` 里**先**用 `_getObjc2ProtocolList` + `readProtocol` 把协议本体注册进全局 `NXMapTable` 并按 `mangledName` **唯一化**（同名只留一个规范实例）；**再**用 `_getObjc2ProtocolRefs` 取本节，对每槽 `remapProtocolRef` → `remapProtocol` **重映射到那个唯一实例**（"不等才写"以省脏页），日志为 "fix up @protocol references"。
- **为何唯一化**：让进程内同名协议只有一个 `protocol_t`，从而 **`@protocol(X) == @protocol(X)` 恒成立**、`conformsToProtocol:` 沿继承链的指针比较可靠；被引用的协议**未必在本镜像定义**，故唯一化必须是进程级全局的。
- **为何在可写段**：槽要被运行期重映射，故放可写 `__DATA`；现代二进制放 `__DATA_CONST`（链式 fixups 回填后再只读化），dyld 共享缓存更会预先唯一化好、装载即正确。
- **四大引用节收尾**：`selrefs`/`classrefs`/`superrefs`/`protorefs` 同型（加载期回填的指针数组），区别在被指本体与重映射函数；`__objc_protorefs` 与 [[38.Mach-O __objc_protolist节]] 配对，补全了 ObjC 元数据"定义 vs 引用"对照体系中**协议**的这一端。
