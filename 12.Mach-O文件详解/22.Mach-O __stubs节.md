# 详解Mach-O(二十二)Mach-O __stubs节

> [!abstract] TL;DR
> **`__stubs` 是"调用外部函数的跳板表"**：每个被调用的外部函数（`printf`、`malloc`…）在这里对应一个**符号桩（symbol stub）**——一小段固定的机器码。`__text`（见 [[19.Mach-O __text节]]）里的 `call`/`bl` 永远只跳到桩（地址编译期就定死），桩再去读 `__la_symbol_ptr`（见 [[30.Mach-O __la_symbol_ptr节]]）里那个**可被运行期改写的指针槽**，间接跳到外部函数的真实地址。把"地址要到运行期才知道"这个不确定性，从代码节里隔离进了一个可写指针槽。
> 它的节类型是 **`S_SYMBOL_STUBS`（`0x8`）**，节头里两个 `reserved` 字段被复用：`reserved2` = **每个 stub 的字节大小**（条目数 = `size / reserved2`），`reserved1` = 本节首个桩在**间接符号表**中的**起始索引**（联动 [[06.Mach-O LC_DYSYMTAB]]，据此查出每个桩对应哪个外部符号）。
> 桩的**指令形态随架构而变**：arm64 是固定 3 条 `adrp x16 / ldr x16 / br x16`（12 字节）；x86_64 是 1 条 `jmp *N(%rip)`（6 字节）。这套"桩 + 惰性指针 + `__stub_helper`"机制，正是 ELF 的 **PLT + GOT** 在 Mach-O 里的对应物，实现**惰性绑定（lazy binding）**——程序启动时无需立即解析所有外部符号，首次调用某函数时才解析。
> **现代演进**：启用**链式 fixups（chained fixups）** 的新二进制不再惰性绑定，`__la_symbol_ptr`/`__stub_helper` 路径消失，桩直接打到非惰性 `__got`；arm64e 上更进一步用 `__auth_stubs` + `braa` 指令对指针做 **PAC 认证**后再跳转。

## 概述与定位

外部函数（如 `printf`，定义在 `libsystem_c.dylib` 里）的真实地址，**要到运行期、由 `dyld` 把对应 dylib 映射进地址空间后才知道**。但编译 `main.o` 时，编译器必须给 `call printf` 填一个**当下就确定**的目标。`__stubs` 就是为解决这个矛盾而生的一层**固定的间接跳转**：

- 编译期：`__text` 里的调用点一律跳到**本镜像内**的桩（`_printf$stub`），桩的地址在本镜像里编译期即固定，没有任何"未知地址"。
- 运行期：桩去读 `__la_symbol_ptr` 里属于它的那个**指针槽**。首次调用时该槽还指向绑定逻辑（`__stub_helper` → `dyld_stub_binder`），绑定完成后被**改写为真实地址**；之后每次调用，桩读到的就是真实地址，直达目标函数。

可以这样理解三方的分工——它与 [[23.Mach-O __stubs_helper节]]、[[30.Mach-O __la_symbol_ptr节]] 配合完成惰性绑定：

- **`__stubs`（本篇，在 `__TEXT`，`r-x`）**：固定跳板。是**代码**，只读可执行，编译期定死，运行期不改。
- **`__la_symbol_ptr`（在 `__DATA`，`rw-`）**：可写指针槽。是**数据**，运行期会被 `dyld` 回填真实地址。
- **`__stub_helper`（在 `__TEXT`，`r-x`）**：首次调用时的绑定辅助代码，负责把"要绑哪个符号"的信息压栈并跳进 `dyld_stub_binder`。

> [!note] 为什么"地址会变"的部分必须放进数据段而不是代码段
> 根本约束有二：① **代码节不可写**——`__TEXT` 是 `r-x`，运行期不能改写其中的指令，所以无法"把桩里的跳转目标直接改成真实地址"。② **跳转指令的位宽不够**——x86_64 的 `jmp rel32` 只能编码 ±2GB 的相对偏移，而外部函数可能落在 64 位地址空间的任意位置，一条立即数跳转装不下绝对地址。于是 Mach-O 的解法是：桩里放一条**间接跳转**（"跳到某内存槽里存的地址去"），把那个**可写、可放满 64 位绝对地址**的槽（`__la_symbol_ptr`）放进数据段，让 `dyld` 在运行期往槽里写真实地址。桩本身永远不变。

> [!note] 桩名与节名约定
> `__stubs` 的全称写作 `__TEXT,__stubs`（段名,节名，约定见 [[18.Mach-O section.md|Mach-O section]]）。单个桩在反汇编里常显示为 `_printf$stub` 或 `__stubs` 下的具名条目——`$stub` 后缀是链接器为"某符号的桩"生成的内部符号名。历史上 i386 还有 `__symbol_stub`/`__picsymbol_stub` 等节名变体（PIC = 位置无关代码），现代 arm64/x86_64 统一叫 `__stubs`。

## 核心原理与字段详解

### 1. 桩（stub）是什么：一段"读槽 + 间接跳"的固定代码

每个外部函数对应**一个 stub**，本质是一小段**固定指令**，语义恒为："**跳到该函数在 `__la_symbol_ptr` 里的指针槽所指向的地址去**"。它把两件事彻底解耦：

- **`__text` 只认桩的地址**——这个地址在本镜像内编译期就定死，调用方代码无需关心目标函数最终落在哪。
- **"地址会变"被关进指针槽**——真实地址由 `dyld` 运行期写进 `__la_symbol_ptr`，桩永远读最新值。

所以无论目标函数最终绑定到哪个 dylib 的哪个地址，**桩这段代码本身一字节都不改**，改的只是它去读的那个数据槽。这也是它能放在只读可执行的 `__TEXT` 段里的前提。

### 2. 节类型 `S_SYMBOL_STUBS` 与 `reserved` 字段复用

`__stubs` 的节类型（`flags & SECTION_TYPE`，低 8 位）固定为 **`S_SYMBOL_STUBS`（`0x8`）**。`<mach-o/loader.h>` 对它的原文注释是 *"section with only symbol stubs, byte size of stub in the reserved2 field"*（只含符号桩、stub 字节大小存在 reserved2）。完整的 `flags` 通常是 `0x80000408`：

```c
type = flags & 0x000000ff = 0x08            // S_SYMBOL_STUBS
attr = flags & 0xffffff00 = 0x80000000      // S_ATTR_PURE_INSTRUCTIONS（纯指令，桩里全是代码）
// → 0x80000000 | 0x00000008 = 0x80000408
```

两个 `reserved` 字段被这种节类型**复用**承载关键信息（这套约定的通用说明见 [[18.Mach-O section.md|Mach-O section]] 的 reserved 复用一节）：

- **`reserved2` —— 每个 stub 的字节大小**。普通指针节的条目是固定宽度（一个指针），可桩是**一小段代码**，其字节数**因 CPU 架构而异**（arm64 是 12、x86_64 是 6，见第 4 节），不是固定指针宽度。于是节头**不直接存条目数**，而是把单个 stub 的大小写进 `reserved2`，让解析器用 `条目数 = size / reserved2` 推算，并据此**按下标定位第 i 个桩**（第 i 个桩起始于 `addr + i * reserved2`）。
- **`reserved1` —— 间接符号表起始索引**。本节第一个桩在**间接符号表（indirect symbol table）** 里的起始下标。间接符号表本身由 `LC_DYSYMTAB` 的 `indirectsymoff`/`nindirectsyms` 定位（见 [[06.Mach-O LC_DYSYMTAB]]）。本节第 `i` 个桩 ↔ 间接符号表第 `reserved1 + i` 项；该项是一个 **32 位的符号表索引**，再指向常规符号表里那个真正的符号（`_printf` 之类），从而查出"这个桩到底是哪个外部函数的桩"。
- **`reserved3`**：对桩节不使用，恒 0。

> [!note] 条目数怎么算：`size / reserved2`，不是从节头直接读
> Mach-O 的设计是**节头不显式存条目数**，而是用"总大小 ÷ 单项大小"反推——这样结构更紧凑，代价是解析器必须知道这层约定。对桩节：`stub 个数 = size / reserved2`。例：`size = 0x78 = 120`、`reserved2 = 12` → `120 / 12 = 10` 个桩。这 10 个桩对应间接符号表第 `reserved1 … reserved1+9` 项。**符号指针节**（`__la_symbol_ptr`/`__got`）同理，只是单项是固定指针宽度（64 位 8 字节），故用 `size / 8`、`reserved2` 不用（为 0）。

### 3. 桩 → `__la_symbol_ptr` → 真实地址：一次完整调用的地址路径

把一次 `printf("hi")` 调用拆成"首次"和"之后"两种路径：

**首次调用（要做绑定，绕一大圈）**

1. `__text`：`bl _printf$stub` —— 跳到桩（本镜像内固定地址）。
2. `__stubs`：桩读出自己对应的 `__la_symbol_ptr` 槽里的值，间接跳过去。**此刻槽里存的不是真实地址，而是回指 `__stub_helper` 的地址**。
3. `__stub_helper`：本桩对应的那段 helper **把"桩序号/绑定信息偏移"压栈**，跳到 helper 头部；头部压入 `_dyld_private` 并跳进 `dyld_stub_binder`（其地址由非惰性指针节 `__nl_symbol_ptr` 提供，见 [[31.Mach-O __nl_symbol_ptr节]]）。
4. `dyld_stub_binder`：按压栈的信息在 `LC_DYLD_INFO`/链式 fixups 的绑定表里查到 `_printf` 真实地址，**把它回写进 `__la_symbol_ptr` 槽**，然后跳转到 `printf` 真正执行。

**之后调用（捷径）**

1. `__text`：`bl _printf$stub`。
2. `__stubs`：桩读 `__la_symbol_ptr` 槽 —— **此刻槽里已是 `printf` 真实地址**，间接跳直达目标。`__stub_helper`/`dyld_stub_binder` 不再参与。

这就是"惰性"二字的含义：**只有真正被调用到的外部函数才在首次调用时付出一次解析开销**，从未被调用的函数永不解析，从而加快启动、降低启动期内存触碰。

### 4. arm64 与 x86_64 的桩指令形态对比

桩的**指令序列与字节大小随架构不同**，逆向时务必按 `reserved2` 给的大小切分桩数组：

**arm64（典型 12 字节，3 条指令）**

```asm
; _printf$stub:
adrp   x16, __la_symbol_ptr@PAGE        ; x16 = 指针槽所在 4KB 页的基址（PC 相对）
ldr    x16, [x16, __la_symbol_ptr@PAGEOFF] ; x16 = *(x16 + 页内偏移) —— 取出槽里存的地址
br     x16                              ; 间接跳转到该地址（不是 bl，不压返回地址）
```

机器码形如 `b0000010 / f9400210 / d61f0200`。三条各 4 字节 = **12 字节**，所以 arm64 上 `reserved2` 常为 `12`。用 `x16`（IP0，平台保留的临时寄存器）做中转，不污染参数寄存器。

**x86_64（典型 6 字节，1 条指令）**

```asm
; _printf$stub:
jmp    *0x1234(%rip)                    ; 间接跳转：跳到 RIP 相对寻址的内存槽里存的地址
```

注意这是 **`jmp *mem`（间接跳转）** 而非 `jmp rel32`（相对跳转）：操作数 `0x1234(%rip)` 指出的是 `__la_symbol_ptr` 槽的**内存位置**（用 RIP 相对寻址定位槽），CPU 取出槽里存的**绝对地址**再跳过去。`ff 25` 操作码 + 4 字节位移 = **6 字节**，所以 x86_64 上 `reserved2` 常为 `6`。

| 维度 | arm64 | x86_64 |
|---|---|---|
| 桩指令 | `adrp x16` + `ldr x16,[x16,#off]` + `br x16` | `jmp *off(%rip)` |
| 指令条数 | 3 | 1 |
| 单桩字节（`reserved2`） | **12** | **6** |
| 中转寄存器 | `x16`（IP0，间接 `br`） | 无（直接间接 `jmp`） |
| 寻址方式 | `adrp`/`ldr` 取页基址再加偏移 | RIP 相对取内存操作数 |
| 跳转性质 | 间接 `br`（不压返回地址，靠调用点的 `bl` 已压 `lr`） | 间接 `jmp`（同理，`call` 已压返回地址） |

> [!note] 为什么用"间接跳转"而不是"间接调用"
> 调用方（`__text`）已经用 `bl`（arm64，压 `lr`）/ `call`（x86_64，压返回地址入栈）完成了"保存返回地址"。桩只负责**把控制权转交给真实函数**，无需再压一次返回地址，所以用 `br`/`jmp`（尾跳转）。真实函数 `ret` 时直接返回到**最初的调用点**，桩在调用栈上不留痕迹——它是透明的一跳。

### 5. 与 PLT/GOT 的类比（ELF ↔ Mach-O）

如果你熟悉 ELF 的动态链接，`__stubs` 这套机制几乎是 **PLT + GOT** 的逐一对应：

| ELF（Linux） | Mach-O（Apple） | 角色 |
|---|---|---|
| `.plt`（Procedure Linkage Table） | `__TEXT,__stubs` + `__TEXT,__stub_helper` | 固定跳板代码（Mach-O 把 PLT 拆成"桩"和"helper"两节） |
| `.got.plt`（GOT 的函数部分） | `__DATA,__la_symbol_ptr` | 可被运行期改写的目标指针槽 |
| `.got`（数据 GOT） | `__DATA,__nl_symbol_ptr` / `__DATA_CONST,__got` | 非惰性绑定的指针（含 `dyld_stub_binder` 地址） |
| `_dl_runtime_resolve` | `dyld_stub_binder` | 首次调用时执行解析并回填的运行时例程 |
| PLT 惰性绑定 | 惰性绑定（lazy binding） | 首次调用才解析符号，加快启动 |

核心思想完全一致：**桩是固定跳板，指针槽是可被运行期改写的目标，首次调用触发解析并回填，之后直达**。差异主要在命名与节的切分粒度（Mach-O 把"跳板"和"解析辅助"分成 `__stubs`/`__stub_helper` 两节）。

### 6. 间接符号表如何把桩映射回符号名

桩本身只是代码，**不带符号名**；"第 i 个桩是哪个外部函数"靠**间接符号表**回答（这是解析符号桩绕不开的另一半，详见 [[06.Mach-O LC_DYSYMTAB]]）。流程：

1. 读 `__stubs` 节头的 `reserved1` → 起始索引 `base`。
2. 算桩数 `n = size / reserved2`。
3. 对第 `i ∈ [0, n)` 个桩：取间接符号表第 `base + i` 项（间接符号表是一串 `uint32_t`，文件偏移 = `LC_DYSYMTAB.indirectsymoff`）→ 得一个**符号表索引** `idx`。
4. 查常规符号表 `nlist[idx]`（`LC_SYMTAB`，见 [[05.Mach-O LC_SYMTAB]]）→ 拿到符号名 `_printf`。

> [!note] 间接符号表里的两个哨兵值：`LOCAL` 与 `ABSOLUTE`
> 间接符号表项不总是指向一个真符号。`<mach-o/loader.h>` 定义了两个哨兵位：`INDIRECT_SYMBOL_LOCAL`（`0x80000000`）与 `INDIRECT_SYMBOL_ABS`（`0x40000000`）。当某项是这两个值（或其按位或）时，表示对应槽指向的是**本镜像内的局部符号**或**绝对地址**，而非需要动态绑定的外部符号。`otool -Iv` 遇到它们会直接打印字面 `LOCAL`/`ABSOLUTE`/`LOCAL ABSOLUTE`，而不去解析符号名——看到这些词不要当成 bug。

### 7. 现代演进：链式 fixups 让 `__la_symbol_ptr` 消失，arm64e 用 `__auth_stubs`

上面描述的是**经典惰性绑定**模型。当代 macOS/iOS 二进制正在两个方向上演进，逆向新二进制时要心里有数：

**① 链式 fixups（chained fixups）→ 不再惰性，桩直打 `__got`**

启用 `LC_DYLD_CHAINED_FIXUPS` 后，**惰性绑定被取消**：`dyld` 把所有导入符号当作**非惰性**一次性在加载期绑定。于是 `__la_symbol_ptr` 与 `__stub_helper` 这条惰性路径**整体消失**，`__stubs` 里的桩**直接指向非惰性的 `__DATA_CONST,__got`**（见 [[15.Mach-O __DATA_CONST]]），槽在加载期就被填好真实地址。你在新二进制里**找不到 `__la_symbol_ptr`/`__stub_helper`** 时，去看 `__got` 即可——这不是缺节，而是惰性绑定退场。

**② arm64e：`__auth_stubs` + `braa` 做 PAC 指针认证**

arm64e（带指针认证 PAC 的 ARM64 子架构）上，桩节叫 **`__TEXT,__auth_stubs`**，且把跳转指令换成 **`braa`**（Branch with link to Register, **A**uthenticated, key **A**）——在跳到目标前，用进程内密钥**验证指针的 PAC 签名**，签名不符则触发异常。对应的指针槽是带认证的 `__auth_got`。这把"跳转目标被篡改"这类攻击挡在门外。典型 `__auth_stubs` 桩形如 `adrp x16 / ldr x16,[x16,#off] / braa x16, x17`（用 `braa` 取代 `br`）。

> [!note] 在 dyld 共享缓存里：桩岛（stub islands）
> 在 `dyld_shared_cache` 中，大量 `__auth_stubs`/`__auth_got` 被**聚合进共享的"桩岛"页面**，不再隶属于某个具体 dylib——这是为了在巨大的共享缓存里集中管理跨库跳转。逆向共享缓存里的单个库时，其桩可能指向缓存级的桩岛而非库内本地桩，分析时要顺着桩岛页继续追。

> [!note] 三种"桩世界"速记
> - **经典惰性（老二进制）**：`__stubs` → `__la_symbol_ptr` →（首次）`__stub_helper` → `dyld_stub_binder` 回填。
> - **链式 fixups（现代 x86_64 / arm64）**：`__stubs` → `__got`（加载期已绑定，无 helper、无惰性）。
> - **arm64e（带 PAC）**：`__auth_stubs`（`braa`）→ `__auth_got`（认证后跳转）。
> 看到二进制里没有 `__la_symbol_ptr`、却有 `__got`/`__auth_stubs`，说明它走的是后两种现代路径。

## 实操：用工具查看

### 示例 1：`otool -tV` 反汇编看 `__stubs` 桩

`-t` 专指 `__TEXT,__text`，但反汇编全程会带出 `__stubs`/`__stub_helper` 块；`-V` 把跳转目标符号化（显示 `_printf$stub` 之类）：

```bash
otool -tV /bin/ls            # 反汇编，可看到 __stubs 桩及其间接跳转目标
otool -s __TEXT __stubs /bin/ls   # 直接 dump __stubs 节的原始字节（裸十六进制）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
(__TEXT,__stubs) section
_printf$stub:
0000000100002000  adrp   x16, 2          ; __la_symbol_ptr@PAGE（取指针槽所在页基址）
0000000100002004  ldr    x16, [x16, #0x10] ; x16 = *(x16+0x10)，读出槽里存的地址
0000000100002008  br     x16             ; 间接跳转到该地址
_malloc$stub:
000000010000200c  adrp   x16, 2
0000000100002010  ldr    x16, [x16, #0x18]
0000000100002014  br     x16
```

> 说明：每个桩 3 条指令、共 12 字节（与 `reserved2=12` 一致）；`_printf$stub` 读偏移 `#0x10` 的槽、`_malloc$stub` 读 `#0x18` 的槽——不同桩读 `__la_symbol_ptr` 里不同的指针槽。若是 x86_64，这里会是单行 `jmp *0x....(%rip)`（6 字节）。若是 arm64e，`br x16` 会变成 `braa x16, x17`（节名也变 `__auth_stubs`）。

### 示例 2：`otool -Iv` 看间接符号表（桩 ↔ 符号的对应）

`-I` 显示间接符号表，`-v` 把符号表索引解析成符号名（多出 `name` 列）：

```bash
otool -Iv /bin/ls            # 间接符号表：每个桩/指针槽对应哪个符号
```

> [!warning] 示例输出为示意
> 数值/索引为构造，仅示意 `otool -Iv` 的"address / index / name"三列格式与 LOCAL/ABSOLUTE 哨兵。

```text
Indirect symbols for (__TEXT,__stubs) 3 entries
address                   index  name
0x0000000100002000        5      _printf
0x000000010000200c        6      _malloc
0x0000000100002018        8      _free

Indirect symbols for (__DATA_CONST,__got) 4 entries
address                   index  name
0x0000000100008000        7      _environ
0x0000000100008008        LOCAL          ; 哨兵：指向本镜像内局部符号，不需动态绑定
0x0000000100008010        ABSOLUTE       ; 哨兵：绝对地址项
```

> 说明：`__stubs` 块的第 0、1、2 个桩对应 `index` 5、6、8——正好从节头 `reserved1`（这里假设为 5）起逐项递增（`5 = reserved1+0`、`6 = reserved1+1`…），每个 `index` 再查常规符号表得到 `name`。`__got` 块里出现的 `LOCAL`/`ABSOLUTE` 是间接符号表的哨兵值（`INDIRECT_SYMBOL_LOCAL`/`_ABS`），表示该项不是需要绑定的外部符号。无 `-v` 时 `name` 列会是裸的 `uint32_t` 索引。

### 示例 3：`otool -l` 看 `__stubs` 节头的 `reserved1`/`reserved2`

```bash
otool -l /bin/ls | grep -A 12 "sectname __stubs"
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意符号桩节如何复用 reserved 字段并据此推算条目数。

```text
Section
  sectname __stubs
   segname __TEXT
      addr 0x0000000100002000
      size 0x0000000000000024      ; 36 字节
    offset 8192
     align 2^2 (4)
    reloff 0
    nreloc 0
     flags 0x80000408              ; S_SYMBOL_STUBS(0x8) | S_ATTR_PURE_INSTRUCTIONS(0x80000000)
 reserved1 5                       ; 首桩 → 间接符号表第 5 项
 reserved2 12                      ; 每个 stub 12 字节（arm64）→ 桩数 = 36 / 12 = 3
 reserved3 0
```

> 说明：`flags & 0xff = 0x08` 即 `S_SYMBOL_STUBS`；`size=36`、`reserved2=12` → 本节 `36/12 = 3` 个桩，分别对应间接符号表第 5、6、7 项（联动示例 2 与 [[06.Mach-O LC_DYSYMTAB]]）。x86_64 上这里 `reserved2` 会是 `6`。

## FAQ

> [!question] `__stubs` 和 `__la_symbol_ptr` 到底谁跳谁、谁是代码谁是数据？
> `__stubs` 是**代码**（在 `__TEXT`，`r-x`，编译期定死、运行期不改），`__la_symbol_ptr` 是**数据**（在 `__DATA`，`rw-`，运行期被 `dyld` 回填）。方向是 **`__text` → `__stubs`（桩）→ 读 `__la_symbol_ptr`（指针槽）→ 跳到槽里存的地址**。桩之所以要"间接跳转读槽"，正因为代码节不可写、且跳转指令装不下任意 64 位绝对地址，只能把可写、可放绝对地址的槽放进数据段，让桩去读它。

> [!question] `reserved1` 和 `reserved2` 不是"保留"吗，为什么有值？怎么算桩的个数？
> 对 `S_SYMBOL_STUBS` 节它们被**复用**：`reserved2` = **每个 stub 的字节大小**（arm64=12、x86_64=6），`reserved1` = 本节首桩在**间接符号表**里的**起始索引**。节头**不直接存桩数**，而是用 `桩数 = size / reserved2` 推算（如 `size=120, reserved2=12 → 10` 个）。第 `i` 个桩对应间接符号表第 `reserved1+i` 项，逐项再查常规符号表得到被调函数名。`reserved3` 对桩节不用，恒 0。

> [!question] 为什么 arm64 的桩是 3 条指令、x86_64 只要 1 条？
> 指令集寻址能力不同。x86_64 的 `jmp *mem` 一条就能"跳到某内存槽里存的地址"，且 RIP 相对寻址直接定位到槽，所以 1 条 6 字节搞定。arm64 是定长 4 字节指令、没有"直接 `jmp [内存]`"，必须分三步：`adrp` 取槽所在页的基址、`ldr` 从页内偏移把槽里的地址读进 `x16`、`br x16` 间接跳——3 条共 12 字节。差异直接体现在 `reserved2`（6 vs 12），逆向时按它切分桩数组。

> [!question] 我反汇编新版二进制，根本找不到 `__la_symbol_ptr` 和 `__stub_helper`，是不是缺节了？
> 不是缺节，是**惰性绑定退场了**。启用**链式 fixups**（`LC_DYLD_CHAINED_FIXUPS`）的现代二进制不再惰性绑定，`dyld` 加载期就把导入符号非惰性绑定完，于是 `__la_symbol_ptr`/`__stub_helper` 这条路径消失，`__stubs` 的桩**直接指向 `__DATA_CONST,__got`**（见 [[15.Mach-O __DATA_CONST]]）。去看 `__got` 即可找到目标指针槽。arm64e 上则是 `__auth_stubs`（`braa` 认证跳转）配 `__auth_got`。

> [!question] `__stubs`、`__stub_helper`、`__la_symbol_ptr` 三者各管什么？
> 一句话分工：**`__stubs`** 是固定跳板（代码，`bl`/`call` 的落点）；**`__la_symbol_ptr`** 是可被运行期改写的目标指针槽（数据，桩去读它）；**`__stub_helper`** 是**首次**调用时的绑定辅助（代码，压入桩序号、跳进 `dyld_stub_binder` 做解析并回填槽）。首次调用走"桩 → 槽（指向 helper）→ helper → `dyld_stub_binder` → 回填槽"，之后调用走"桩 → 槽（已是真实地址）→ 直达"。详见 [[23.Mach-O __stubs_helper节]] 与 [[30.Mach-O __la_symbol_ptr节]]。

## 小结

- `__stubs` 是外部函数调用的**固定跳板表**，节类型 `S_SYMBOL_STUBS`（`0x8`），住在 `__TEXT`（`r-x`），`flags` 常为 `0x80000408`（含 `S_ATTR_PURE_INSTRUCTIONS`）。
- `reserved2` = **单个 stub 字节大小**（arm64=12、x86_64=6），`reserved1` = **间接符号表起始索引**；节头不存条目数，**桩数 = `size / reserved2`**，第 `i` 桩 ↔ 间接符号表第 `reserved1+i` 项 → 常规符号表 → 符号名。
- 桩指令形态随架构而变：**arm64** 为 `adrp x16 / ldr x16,[x16,#off] / br x16`（间接 `br`，12 字节）；**x86_64** 为 `jmp *N(%rip)`（间接 `jmp`，6 字节）。机制类比 ELF 的 **PLT+GOT**。
- 调用路径：`__text` → `__stubs`（桩）→ `__la_symbol_ptr`（槽）→ 首次经 `__stub_helper` → `dyld_stub_binder` 回填真实地址，之后直达——即**惰性绑定**，加快启动。
- **现代**：链式 fixups 取消惰性绑定，桩直打非惰性 `__got`、`__la_symbol_ptr`/`__stub_helper` 消失；arm64e 用 `__auth_stubs` + `braa` 对指针做 **PAC 认证**后跳转，共享缓存里聚合成桩岛。
- 实操：`otool -tV` 看 `__stubs` 桩反汇编、`otool -Iv` 看间接符号表（桩↔符号，含 `LOCAL`/`ABSOLUTE` 哨兵）、`otool -l` 看节头的 `reserved1`/`reserved2`。
