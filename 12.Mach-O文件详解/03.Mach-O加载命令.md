# 详解Mach-O(三)Mach-O加载命令

> [!abstract] TL;DR
> **Load Commands（加载命令）是紧跟 Header 之后的一串变长记录，是写给内核与 `dyld` 的"装配说明书"**：声明每个段如何映射、依赖哪些库、符号表/签名/入口在哪。
> 每条命令以统一的 `load_command{ cmd, cmdsize }` 打头——`cmd` 标识类型，`cmdsize` 给出本条总长度，解析器靠累加 `cmdsize` 逐条跳转，共 `ncmds` 条。
> 命令约有 50 种，可归为：段/节、符号与链接信息、动态库、链接器/环境、线程/入口、版本、标识/签名/其他。带 `LC_REQ_DYLD` 位的命令 `dyld` 必须理解，否则拒绝加载。读懂加载命令，就读懂了 Mach-O 如何被"装配"成进程。

## 概述与定位

如果说 [[02.Mach-O文件头]] 是"身份证"，Load Commands 就是"施工图纸"。内核 `exec` 时先读 Header，再逐条解析加载命令搭建进程初始环境（映射段、定位 `dyld`、设置入口）；其余（加载依赖、绑定符号）交给 `dyld` 按这些命令完成。

其设计哲学是**用可扩展的"命令流"描述一切**：表达新特性只需新增一种 `LC_*`，无需改动文件整体格式。这是 Mach-O 区别于 ELF/PE 的鲜明特征。

## 核心原理与字段详解

### 1. 通用头部 `load_command`

所有命令共享前缀（`<mach-o/loader.h>`）：

```c
struct load_command {
    uint32_t cmd;      // 命令类型，如 LC_SEGMENT_64
    uint32_t cmdsize;  // 本条命令总字节数（含头部与各自负载）
};
```

各具体命令是"以 `load_command` 开头、后接各自字段"的更大结构（如 `segment_command_64`、`dylib_command`）。

### 2. cmdsize 与遍历

- `cmdsize` **必须**是指针大小的整数倍（64 位 8 的倍数 / 32 位 4 的倍数），不足处以 0 填充对齐。
- 遍历：从 Header 末尾起，按当前命令 `cmd` 解读，再 `ptr += cmdsize` 跳下一条，循环 `ncmds` 次；累计应恰为 `sizeofcmds`。
- `cmdsize` 是"步长"，一旦错位后续全乱——这也是恶意构造常攻击的点（畸形 `cmdsize` 让解析器越界）。健壮的解析器会校验每条命令不越过命令区边界。

### 3. lc_str —— 命令内嵌字符串机制

像库路径、rpath、dylinker 路径这些变长字符串，不直接定长存储，而用 `lc_str` 联合体记录"相对本命令起点的偏移"，字符串本体紧跟在命令固定字段之后：

```c
union lc_str {
    uint32_t offset;   // 字符串相对该 load command 起点的字节偏移
#ifndef __LP64__
    char    *ptr;      // 仅 32 位在内存中使用
#endif
};
```

这就是为什么 `otool -l` 会显示 `name /usr/lib/libSystem.B.dylib (offset 24)`——`offset 24` 即字符串在该命令内的起始偏移。`cmdsize` 把这段变长字符串也算在内（并对齐）。

### 4. linkedit_data_command —— 多命令复用的通用结构

许多"指向 `__LINKEDIT` 内一段数据"的命令复用同一个极简结构：

```c
struct linkedit_data_command {
    uint32_t cmd;        // 见下表
    uint32_t cmdsize;    // 16
    uint32_t dataoff;    // 数据在文件（__LINKEDIT）中的偏移
    uint32_t datasize;   // 数据字节数
};
```

复用它的命令包括：`LC_CODE_SIGNATURE`、`LC_SEGMENT_SPLIT_INFO`、`LC_FUNCTION_STARTS`、`LC_DATA_IN_CODE`、`LC_DYLIB_CODE_SIGN_DRS`、`LC_LINKER_OPTIMIZATION_HINT`、`LC_DYLD_EXPORTS_TRIE`、`LC_DYLD_CHAINED_FIXUPS`。它们只是"在 `__LINKEDIT` 的哪段字节"，具体语义由 `cmd` 决定。

### 5. LC_REQ_DYLD —— "必须理解"位

`LC_REQ_DYLD = 0x80000000`。某些命令把它按位或进 `cmd`，表示 `dyld` 必须能处理，否则拒绝加载（避免"半懂不懂"地运行）。带此位的常见命令：`LC_LOAD_WEAK_DYLIB`、`LC_RPATH`、`LC_REEXPORT_DYLIB`、`LC_DYLD_INFO_ONLY`、`LC_LOAD_UPWARD_DYLIB`、`LC_MAIN`、`LC_DYLD_EXPORTS_TRIE`、`LC_DYLD_CHAINED_FIXUPS`、`LC_FILESET_ENTRY`。

### 6. 完整命令分类速查

> 下表按功能归类列出主要 `LC_*`（值为 `<mach-o/loader.h>` 定义；标 `\|REQ` 者带 `LC_REQ_DYLD`）。

**段与节**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_SEGMENT` | `0x1` | 32 位段映射 |
| `LC_SEGMENT_64` | `0x19` | 64 位段映射（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]） |

**符号与链接信息**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_SYMTAB` | `0x2` | 符号表 + 字符串表（[[05.Mach-O LC_SYMTAB]]） |
| `LC_DYSYMTAB` | `0xb` | 动态符号表 + 间接符号表（[[06.Mach-O LC_DYSYMTAB]]） |
| `LC_DYLD_INFO` / `LC_DYLD_INFO_ONLY` | `0x22` / `0x22\|REQ` | 压缩 rebase/bind/export（[[17.Mach-O LC_DYLD_INFO_ONLY]]） |
| `LC_DYLD_EXPORTS_TRIE` | `0x33\|REQ` | 导出符号 trie（新式） |
| `LC_DYLD_CHAINED_FIXUPS` | `0x34\|REQ` | 链式 fixups（取代传统 rebase/bind） |
| `LC_FUNCTION_STARTS` | `0x26` | 函数起始地址表 |
| `LC_DATA_IN_CODE` | `0x29` | 代码段内嵌数据标注 |
| `LC_SEGMENT_SPLIT_INFO` | `0x1e` | 段拆分信息（共享缓存用） |

**动态库**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_LOAD_DYLIB` | `0xc` | 依赖库（[[07.Mach-O LC_LOAD_DYLIB]]） |
| `LC_ID_DYLIB` | `0xd` | 库自身 install name（[[08.Mach-O LC_ID_DYLIB]]） |
| `LC_LOAD_WEAK_DYLIB` | `0x18\|REQ` | 弱依赖（缺失不报错） |
| `LC_REEXPORT_DYLIB` | `0x1f\|REQ` | 再导出依赖 |
| `LC_LOAD_UPWARD_DYLIB` | `0x23\|REQ` | 向上依赖（处理循环依赖） |
| `LC_LAZY_LOAD_DYLIB` | `0x20` | 延迟加载依赖 |
| `LC_PREBOUND_DYLIB` | `0x10` | 预绑定库（旧机制） |

**链接器与环境**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_LOAD_DYLINKER` | `0xe` | 动态链接器路径（通常 `/usr/lib/dyld`） |
| `LC_ID_DYLINKER` | `0xf` | dyld 自身标识 |
| `LC_DYLD_ENVIRONMENT` | `0x27` | 给 dyld 的环境变量 |
| `LC_RPATH` | `0x1c\|REQ` | 运行时搜索路径（@rpath 解析依据） |
| `LC_LINKER_OPTION` | `0x2d` | 链接器选项（自动链接） |

**线程与入口**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_UNIXTHREAD` | `0x5` | 初始线程寄存器状态（旧式入口） |
| `LC_THREAD` | `0x4` | 线程状态（无栈分配） |
| `LC_MAIN` | `0x28\|REQ` | 入口偏移 + 栈大小（[[09.Mach-O LC_MAIN]]） |

**版本**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_VERSION_MIN_MACOSX` | `0x24` | 最低 macOS 版本（旧） |
| `LC_VERSION_MIN_IPHONEOS` | `0x25` | 最低 iOS 版本（旧） |
| `LC_VERSION_MIN_TVOS` / `LC_VERSION_MIN_WATCHOS` | `0x2f` / `0x30` | tvOS / watchOS（旧） |
| `LC_BUILD_VERSION` | `0x32` | 统一的平台 + 最低/SDK 版本（新，取代上面四个） |
| `LC_SOURCE_VERSION` | `0x2a` | 源码版本号 |

**标识、签名与其他**

| 命令 | 值 | 作用 |
|---|---|---|
| `LC_UUID` | `0x1b` | 镜像唯一标识（[[10.Mach-O LC_UUID]]） |
| `LC_CODE_SIGNATURE` | `0x1d` | 代码签名数据位置 |
| `LC_ENCRYPTION_INFO` / `_64` | `0x21` / `0x2c` | 加密信息（如 App Store FairPlay 加壳） |
| `LC_NOTE` | `0x31` | 任意附注数据 |
| `LC_SUB_FRAMEWORK` / `_UMBRELLA` / `_CLIENT` / `_LIBRARY` | `0x12`–`0x15` | 伞形框架关系 |
| `LC_FILESET_ENTRY` | `0x35\|REQ` | fileset 中的子镜像入口（kernelcache 等） |

> [!note] 架构差异
> 段命令分 `LC_SEGMENT`（`0x1`，`segment_command`）与 `LC_SEGMENT_64`（`0x19`，`segment_command_64`），当代几乎全用 64 位。版本信息从旧的 `LC_VERSION_MIN_*` 演进到统一的 `LC_BUILD_VERSION`。绑定/重定位从 `LC_DYLD_INFO_ONLY` 演进到 `LC_DYLD_CHAINED_FIXUPS` + `LC_DYLD_EXPORTS_TRIE`（iOS 15 / macOS 12 起的链式 fixups），逆向新二进制时要注意后者。

## 实操：用工具查看

### otool -l 实操与版本命令

#### 逐命令解读 `otool -l`

`otool -l <binary>` 按出现顺序输出所有加载命令，每条命令以 `Load command N` 分隔，字段名与 `<mach-o/loader.h>` 中的 C 结构体字段名完全对应。典型读法：

```bash
otool -l /bin/ls                              # 输出全部加载命令
otool -l /bin/ls | grep -A 2 "cmd "          # 只列命令类型清单（每条的 cmd 行 + 后2行）
otool -l /bin/ls | grep -B1 -A5 LC_BUILD_VERSION   # 只看版本命令
otool -l /bin/ls | grep -A4 LC_MAIN          # 看入口偏移
```

下面逐类给出典型输出示意及字段解读：

**`LC_SEGMENT_64`（最典型的重命令）**

```text
Load command 0
      cmd LC_SEGMENT_64
  cmdsize 552          ← 8(cmd+cmdsize) + 48(segment固定) + nsects*80
  segname __TEXT
   vmaddr 0x0000000100000000   ← 段希望映射到的虚拟地址
   vmsize 0x0000000000004000   ← 段占用的虚拟内存大小（页对齐）
  fileoff 0                    ← 段数据在文件中的起点偏移
 filesize 16384                ← 段在文件中实际占用的字节数
  maxprot 0x00000005   (r-x)   ← 可设置的最高权限
 initprot 0x00000005   (r-x)   ← 初始映射权限
   nsects 6                    ← 本段内含的节数量
    flags 0x0                  ← 段标志（SG_READ_ONLY 等）
```

**`LC_LOAD_DYLIB`**（体现 `lc_str.offset` 机制）

```

```

#### 版本命令详解

版本信息类加载命令经历了两代演进：旧式 `LC_VERSION_MIN_*` 系列，以及统一为所有平台服务的新式 `LC_BUILD_VERSION`。

**旧式（已废弃但仍广泛存在）：`LC_VERSION_MIN_MACOSX` / `LC_VERSION_MIN_IPHONEOS`**

```c
struct version_min_command {
    uint32_t cmd;      /* LC_VERSION_MIN_MACOSX   = 0x24
                          LC_VERSION_MIN_IPHONEOS  = 0x25
                          LC_VERSION_MIN_TVOS      = 0x2f
                          LC_VERSION_MIN_WATCHOS   = 0x30 */
    uint32_t cmdsize;  /* 16 字节固定 */
    uint32_t version;  /* 平台最低版本：X.Y.Z 编码为 (X<<16)|(Y<<8)|Z */
    uint32_t sdk;      /* 编译时所用 SDK 版本，编码方式相同 */
};
```

版本编码规则（适用于 `version` 和 `sdk` 两个字段）：

| 高16位 | 次8位 | 低8位 |
|---|---|---|
| 主版本号 X | 次版本号 Y | 修订号 Z |

示例：macOS 11.3.0 = `(11 << 16) | (3 << 8) | 0 = 0x000B0300`

`otool -l` 示意输出：

```text
Load command 11
      cmd LC_VERSION_MIN_MACOSX
  cmdsize 16
  version 10.15      ← 最低运行系统：macOS 10.15
      sdk 11.3       ← 编译所用 SDK：macOS 11.3 SDK
```

**新式：`LC_BUILD_VERSION`**（macOS 10.14+ / iOS 12+ 工具链默认使用）

`LC_BUILD_VERSION` 统一替代了所有 `LC_VERSION_MIN_*`，在一条命令里同时表达平台、最低 OS 版本、SDK 版本，并可携带多个工具版本记录（`build_tool_version`）：

```c
struct build_version_command {
    uint32_t cmd;       /* LC_BUILD_VERSION = 0x32 */
    uint32_t cmdsize;   /* 24 + ntools * 8 */
    uint32_t platform;  /* 目标平台，见下方 PLATFORM_* 表 */
    uint32_t minos;     /* 最低 OS 版本，编码同 version_min_command */
    uint32_t sdk;       /* SDK 版本，编码同 version_min_command */
    uint32_t ntools;    /* 后随的 build_tool_version 条目数 */
    /* 紧随其后 ntools 个 build_tool_version */
};

struct build_tool_version {
    uint32_t tool;      /* TOOL_CLANG=1, TOOL_SWIFT=2, TOOL_LD=3 */
    uint32_t version;   /* 工具版本，编码同上 */
};
```

**`platform` 常量（`PLATFORM_*`）**：

| 常量 | 值 | 含义 |
|---|---|---|
| `PLATFORM_MACOS` | `1` | macOS |
| `PLATFORM_IOS` | `2` | iOS（设备） |
| `PLATFORM_TVOS` | `3` | tvOS |
| `PLATFORM_WATCHOS` | `4` | watchOS |
| `PLATFORM_BRIDGEOS` | `5` | bridgeOS（Apple Watch 芯片伴侣） |
| `PLATFORM_MACCATALYST` | `6` | Mac Catalyst（iPad App on Mac） |
| `PLATFORM_IOSSIMULATOR` | `7` | iOS Simulator |
| `PLATFORM_TVOSSIMULATOR` | `8` | tvOS Simulator |
| `PLATFORM_WATCHOSSIMULATOR` | `9` | watchOS Simulator |
| `PLATFORM_DRIVERKIT` | `10` | DriverKit（系统扩展） |

`otool -l` 示意输出：

```text
Load command 13
      cmd LC_BUILD_VERSION
  cmdsize 32             ← 24 + 1*8（ntools=1）
 platform 1              ← PLATFORM_MACOS
    minos 14.0           ← 最低 macOS 14.0（Sonoma）
      sdk 14.5           ← 用 macOS 14.5 SDK 编译
   ntools 1
     tool ld             ← TOOL_LD
  version 907.8          ← ld 版本
```

> [!note] 旧式与新式的共存与优先级
> 同一个二进制里不应同时出现 `LC_BUILD_VERSION` 和 `LC_VERSION_MIN_MACOSX`。工具链在 Xcode 10 / LLVM 7 以后默认只生成 `LC_BUILD_VERSION`；旧工具链或指定旧 deployment target 时才产生 `LC_VERSION_MIN_*`。逆向时见到哪种命令，就用哪种命令读版本。

```bash
otool -l /bin/ls                 # 全部加载命令
otool -l /bin/ls | grep "cmd "   # 只看命令类型清单
otool -l /bin/ls | grep -A2 LC_RPATH   # 看某类命令
```

## FAQ

> [!question] 命令到底有多少种？
> `<mach-o/loader.h>` 定义了约 50 个 `LC_*`，但任何单个二进制只会用到其中一部分（典型可执行文件十几到二十几条）。新版本会继续增加（如近年的 `LC_DYLD_CHAINED_FIXUPS`）。

> [!question] 为什么有的命令带 `0x80000000`？
> 那是 `LC_REQ_DYLD` 位，表示"dyld 必须理解此命令"。所以 `LC_MAIN` 的实际 `cmd` 是 `0x28 | 0x80000000 = 0x80000028`。

> [!question] `cmdsize` 可以随便填吗？
> 不可以。它必须按位宽对齐、且把命令的全部负载（含 `lc_str` 字符串）算进去；解析器据它步进。畸形 `cmdsize` 是常见的解析器攻击面，健壮实现会做边界校验。

## 小结

- Load Commands 是紧随 Header 的变长记录串，统一以 `load_command{cmd, cmdsize}` 打头，共 `ncmds` 条、总长 `sizeofcmds`。
- `cmdsize` 是遍历步长，必须对齐；变长字符串用 `lc_str.offset` 内嵌；`linkedit_data_command` 被多命令复用。
- 命令约 50 种，按段/符号/库/链接器/线程/版本/其他归类；`LC_REQ_DYLD` 标记 dyld 必须理解。
- 新式 `LC_BUILD_VERSION`、`LC_DYLD_CHAINED_FIXUPS` 等反映了格式的持续演进。
