# 详解Mach-O(十五)Mach-O __DATA_CONST

> [!abstract] TL;DR
> **`__DATA_CONST` 是现代 Mach-O 的一项内存级安全加固**：把原本混在可写 `__DATA`（见 [[14.Mach-O __DATA]]）里、"由 dyld 绑定一次、此后整个进程生命周期都不该再变"的指针型数据——全局偏移表 `__got`、只读常量 `__const`、模块初始化函数表 `__mod_init_func`、以及 Objective-C 的类列表 `__objc_classlist` / 协议列表 `__objc_protolist` / 分类列表 `__objc_catlist` 等元数据——从 `__DATA` 中**剥离出来单独成段**。
> 这个段带 **`SG_READ_ONLY`（`0x10`）** 段标志，触发 **两阶段权限**机制：① **加载期**内核以 `rw-`（`initprot=0x3`）映射，让 dyld 能写入 rebase / bind / chained-fixups 修补后的真实地址；② **绑定完成后**，dyld 依据 `SG_READ_ONLY` 调用 `mprotect` 把整段降为只读 `r--`，运行期再不可写。
> 这样既保留了"加载期可写以便链接器修补"，又获得了"运行期只读以防篡改"——专门对抗 **GOT 劫持 / 函数指针覆写 / ObjC 元数据篡改**这一大类"获得写原语后改指针劫持控制流"的攻击。它在概念上等价于 Linux/ELF 的 **Full RELRO**。在 **arm64e**（A12 及以后、M 系列）上更进一步，演化出 **`__AUTH_CONST`** 段，对其中的指针叠加 **PAC（指针认证码）**签名，做到"既只读、又签名校验"的双重防护。

## 概述与定位

`__DATA`（见 [[14.Mach-O __DATA]]）的可写属性带来灵活性，也带来风险：它里面历史上塞满了**指针**——导入函数地址表（GOT）、ObjC 类对象指针、C++/ObjC 全局构造器地址……这些指针在 dyld 把镜像加载、把符号绑定到最终地址之后，值就**永久固定**了，正常运行中绝不会再写。但因为它们和真正可变的全局变量同住在 `rw-` 的 `__DATA` 段里，攻击者一旦拿到任意地址写原语（典型如堆溢出、UAF），就能改写这些指针，把对某个库函数的调用悄悄改指到自己的 gadget，从而劫持控制流——这正是经典的 **GOT 劫持 / PLT 劫持**攻击面。

`__DATA_CONST` 是 Apple 给出的应对：**把这些"链接后即固定"的指针隔离进一个独立段，链接一完成就把整段锁成只读。** 它不是 `__DATA` 的子集那么简单，而是 [[11.Mach-O Segments]] 中"以段为权限单位"思想的精细化落地——用**"先可写、后只读"的两阶段权限**，在"加载期必须可写（dyld 要填地址）"与"运行期应当只读（防篡改）"这对矛盾之间取得平衡。

它在系列中的定位：

- 上承 [[11.Mach-O Segments]] 的段/权限总纲与 [[14.Mach-O __DATA]] 的可写数据段——`__DATA_CONST` 正是从 `__DATA` 里"切"出来的那部分只读子集；
- 与 [[17.Mach-O LC_DYLD_INFO_ONLY]]（以及更现代的 `LC_DYLD_CHAINED_FIXUPS`）紧密耦合——dyld 正是依据这些命令里的 rebase/bind/fixup 信息向本段写入指针，**写完才上锁**；
- 向下统辖一组具体节：[[21.Mach-O __const节]]、[[32.Mach-O __mod_init_func节]]、[[36.Mach-O __objc_classlist节]]、[[38.Mach-O __objc_protolist节]]、[[39.Mach-O __objc_catlist节]]、[[40.Mach-O __objc_classrefs节]] 等，它们的"只读性"都由本段的 `SG_READ_ONLY` 统一兜底。

> [!note] 一句话抓住本质
> `__DATA_CONST` ≈ **"只在加载期可写一次、之后永久只读的数据段"**。判断一块数据该不该进 `__DATA_CONST` 的标准只有一条：**它在 dyld 完成 fixups 后是否还会被写？** 不会写的（GOT、const、初始化器表、ObjC 类列表）进 `__DATA_CONST`；还会写的（`__data` 普通可变全局、`__bss`、`__objc_selrefs`、`__objc_ivar` 等）留在 `__DATA`。

## 核心原理与字段详解

### 1. 为什么必须从 `__DATA` 拆出来——攻击面分析

要理解 `__DATA_CONST` 的价值，先要理解 **GOT 劫持**为什么致命。

动态链接的程序在编译期并不知道 `printf`、`objc_msgSend` 这些外部符号的最终地址（它们在系统库里，且库本身受 ASLR 影响每次加载地址都不同）。编译器于是生成一张**全局偏移表 `__got`**（GOT, Global Offset Table，又叫非惰性符号指针表 NonLazySymbolPointers）：代码里对外部函数的调用，实际是"读 GOT 里对应槽位拿到函数指针，再间接跳转"。这些槽位的真实值，要等 dyld 在加载期 **bind** 时才填进去。

问题在于：**填完之后这张表就再也不变了，可它住在可写的 `__DATA` 里。** 于是攻击链变成：

1. 攻击者通过某漏洞获得**任意地址写**原语；
2. 定位到 `__DATA` 里 `__got` 中 `system`（或任意危险函数）的槽位；
3. 把该槽位覆写成自己控制的地址（或干脆把某个常用函数的 GOT 槽改成 `system`）；
4. 程序下一次正常调用该函数时，控制流就被劫持到攻击者代码。

同理还有：覆写 `__mod_init_func` 里的构造器指针、覆写 ObjC 的 `__objc_classlist` / `__objc_classrefs` 让 `objc_msgSend` 派发到伪造的类/方法实现……**凡是"指针 + 可写"的组合，都是这类攻击的温床。**

`__DATA_CONST` 的对策直击要害：**这些指针在 dyld 绑定后本就不需要再写，那就在绑定一结束立刻把它们所在的页改成只读。** 攻击者即便拿到了写原语，写 `__DATA_CONST` 也会直接触发段错误、进程崩溃——把"改 GOT 劫持控制流"这条路彻底堵死。这与 Linux 上 **RELRO（Relocation Read-Only）** 防御 GOT 的思路完全一致：重定位相关的数据页**初始可写**（供动态链接器填址），动态链接器填完后**改成只读**；`__DATA_CONST` 就是 macOS/iOS 版的 **Full RELRO**。

> [!note] 为什么是"整段一起锁"而不是"逐指针锁"
> 内存保护的最小粒度是**页**（arm64 为 16KB，x86_64 为 4KB），`mprotect` 只能按页设权限。所以 Apple 的做法是把所有"加载后只读"的内容**收拢进同一个段**（保证它们落在连续的整页上），dyld 填完后对整段一次性 `mprotect` 降权。这也解释了为什么 `__DATA_CONST` 与 `__DATA` 之间常有页对齐空隙——只读段必须在页边界结束，不能和可写数据共享同一个物理页（否则锁了只读就连旁边的可变全局一起锁死了）。

### 2. `SG_READ_ONLY`（`0x10`）段标志：机制总开关

`__DATA_CONST` 的"启动后只读"不是 dyld 凭段名硬编码猜出来的，而是由段头 `segment_command_64`（见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）里 `flags` 字段的一个比特位**显式声明**的——这个位就是 `SG_READ_ONLY`，定义在 `<mach-o/loader.h>`：

```c
/* <mach-o/loader.h> 段标志（flags 字段，按位或） */
#define SG_HIGHVM               0x1   /* 文件内容对应 VM 高地址部分（core dump 栈段） */
#define SG_FVMLIB               0x2   /* Fixed VM Library 内存（古老，已废弃） */
#define SG_NORELOC              0x4   /* 段内无重定位、也无外部重定位指向它 */
#define SG_PROTECTED_VERSION_1  0x8   /* 段被加密保护（如 FairPlay 对 __TEXT 加密） */
#define SG_READ_ONLY            0x10  /* 段在初始化完成后应被置为只读 ← __DATA_CONST 的标志 */
```

它的语义可以读作一句对 dyld 的指令：

> "**这个段你先按 `initprot` 给的 `rw-` 映射，让我（dyld）能往里写 fixups；等我把这个段所有的 rebase/bind/chained-fixups 都处理完，请你立刻 `mprotect` 把它整段降成只读 `r--`。**"

关键点：

- `SG_READ_ONLY` **不改变 `initprot`/`maxprot` 的静态值**。文件里 `__DATA_CONST` 的 `initprot` 和 `maxprot` 通常都仍是 `0x3`（`rw-`）——`maxprot=0x3` 才允许 dyld 在加载期合法地写。`SG_READ_ONLY` 只是一个"**请在运行期把它降权**"的请求标志。
- 因此用 `otool -l` 看静态文件，`__DATA_CONST` 是 `rw-`、`flags 0x10`；而用 `vmmap` 看运行中的进程，它已是 `r--`。**两套视图都对**，分别是"出厂权限"与"启动后实际权限"。
- 校验趋严：新版 macOS（如 15.4）链接器/dyld 会**强制要求**真正承载只读语义的 `__DATA_CONST` 必须带 `SG_READ_ONLY`，缺这个标志可能导致加载/构建报错——这从侧面说明该机制已成为现代工具链的硬约束，而非可选优化。

### 3. 两阶段权限的完整流程（加载期 rw- → 绑定后 r--）

把整条时间线拆开，逐步看 dyld 到底做了什么：

| 阶段 | 执行者 | 动作 | `__DATA_CONST` 此刻权限 |
|---|---|---|---|
| ① 映射 | 内核 `exec` / dyld | 按段头 `initprot=0x3` 把 `[fileoff, fileoff+filesize)` 映射为 `rw-`（COW 共享） | `rw-`（可写） |
| ② Rebase | dyld | 给段内所有内部指针**叠加 ASLR slide**（文件里存的是"理想地址"，实际地址 = 理想地址 + 本次随机 slide），写回原槽位 | `rw-`（正在写） |
| ③ Bind | dyld | 把对**外部符号**的引用（如 `__got` 里各导入函数）解析为目标库中的最终地址，写入对应槽位 | `rw-`（正在写） |
| ④ 上锁 | dyld | 遍历各段（`forEachSegment`），发现带 `SG_READ_ONLY` 的段，对其整段调用 `mprotect(addr, size, VM_PROT_READ)` 降为 `r--` | **`r--`（只读，锁定）** |
| ⑤ 运行 | 用户代码 | 正常读取已固定的指针；**任何写入触发 `EXC_BAD_ACCESS`(SIGBUS/SIGSEGV)** | `r--`（不可写） |

几个工程细节：

- **现代 dyld 用 chained fixups 统一了 ②③。** `LC_DYLD_CHAINED_FIXUPS` 把 rebase 与 bind 信息编码进一条**指针链**（每个待修补的指针槽，其高位比特里编码了"下一个待修补槽的偏移"以及"这是 rebase 还是 bind、bind 的符号序号/addend"），dyld 顺着链一路走、一路填，效率与体积都优于旧的 `LC_DYLD_INFO_ONLY` 操作码流。无论用哪套，**"填完再 mprotect 上锁"这一步都不变**。
- **连 dyld 自己的 `__DATA_CONST` 也要上锁。** dyld 作为最先加载、自举（self-rebase）的镜像，在给自己做完 chained-fixups 重定位后，`rebaseDyld`/启动序列的最后一步就是把 dyld 自身的 `__DATA_CONST` 从内核给的 `rw-` 改成 `r--`（对应 Apple 内部 `rdar://47805386`）。你可以在调试器里对 dyld 启动序列前后两次 `vmmap`，亲眼看到该段从 `rw-` 翻成 `r--`。
- **崩在 fixups 路径里 ≠ 你写了只读内存。** dyld 应用 fixups 的代码（`Loader::applyFixupsGeneric`、`forEachRebase_Opcodes` 等）位于动态链接极早期，此时 App 自己的代码通常一行都还没跑；这里的崩溃多半是进程被外部异步杀掉，而非"写 `__DATA_CONST`"。真正的"写只读段"崩溃发生在 ⑤ 之后、你的代码运行期。

### 4. `__DATA_CONST` 里到底有哪些节

随着工具链演进，越来越多"加载后只读"的节被默认归入 `__DATA_CONST`。一个现代 arm64 二进制里，本段常见节如下：

| 节 | 内容 | 为何能进 `__DATA_CONST`（绑定后即固定） |
|---|---|---|
| `__got` | 全局偏移表 / 非惰性符号指针（NonLazySymbolPointers） | bind 后各导入符号地址固定，正是 RELRO 要保护的核心目标（见 [[40.Mach-O __objc_classrefs节]] 同类指针） |
| `__const` | 编译期只读常量（含含指针的常量聚合） | rebase 叠加 slide 后即固定；详见 [[21.Mach-O __const节]] |
| `__mod_init_func` | C++/ObjC 全局构造器、`__attribute__((constructor))` 函数指针表（dyld 在 `LC_MAIN` 之前按序调用） | rebase 后地址固定、只被 dyld 读取调用，绝不再写；详见 [[32.Mach-O __mod_init_func节]] |
| `__objc_classlist` | 本镜像定义的所有 ObjC 类对象指针列表（runtime realize 类时遍历） | rebase 后固定；详见 [[36.Mach-O __objc_classlist节]] |
| `__objc_protolist` | ObjC 协议对象指针列表 | rebase 后固定；详见 [[38.Mach-O __objc_protolist节]] |
| `__objc_catlist` | ObjC 分类（category）指针列表 | rebase 后固定；详见 [[39.Mach-O __objc_catlist节]] |
| `__objc_nlclslist` | 非惰性类（实现了 `+load`）列表 | rebase 后固定 |
| `__objc_imageinfo` | ObjC 镜像元信息（版本/标志，runtime 读取） | 加载期写一次，之后只读 |
| `__objc_const` | ObjC 只读元数据（方法/属性/协议表等 `class_ro_t` 数据） | rebase 后固定 |
| `__cfstring` | Core Foundation 常量字符串对象（`CFStringRef`，部分配置下） | 对象骨架 rebase 后固定 |

而**仍然留在可写 `__DATA`** 的典型是：`__data`（已初始化的可变全局/静态变量）、`__bss`/`__common`（未初始化数据，运行时零填充后还会写）、`__objc_selrefs`（selector 引用，runtime 唯一化时会改写）、`__objc_ivar`（实例变量偏移，runtime fix-up 后可能变）、`__la_symbol_ptr`（惰性符号指针，历史上首次调用时才回填——故必须可写）。

> [!note] "拆段"是渐进发生的，不同 Xcode/clang 版本边界不同
> 不要把"某节属于 `__DATA_CONST`"当成铁律——它是**逐版本迁移**的结果。`__objc_classlist` 早期在 `__DATA`，大约到 clang-1100（Xcode 11）才默认改入 `__DATA_CONST`；GOT 与 `__const` 则早在 iOS 9 一带就已迁移。逆向不同年代、不同编译配置的二进制，会看到同名节落在不同段里——**以你手上 `otool -l` 的实际输出为准**，而非死记某张表。

### 5. arm64e 的进化：`__AUTH_CONST` 与 PAC 签名指针

在 **arm64e**（ARMv8.3-A 起，即 A12 Bionic、M1 及以后）上，硬件提供了 **指针认证（Pointer Authentication, PAC）**：64 位指针的高位比特（约 48–63 位，视 VA 配置）里嵌入一段**密码学签名（PAC 码）**，该签名由"指针值 + 进程私有密钥 + 上下文 diversifier（如地址本身/类型）"经硬件运算得出；使用指针前 CPU 用 `AUT*` 指令**校验签名**，签名不符则把指针置为不可解引用的形态，一旦访问即触发"possible pointer authentication failure"类的 `EXC_BAD_ACCESS`。

针对"只读 + 指针"这一最值得保护的组合，arm64e 把 `__DATA_CONST` 中**需要签名**的那部分进一步独立为 **`__AUTH_CONST`** 段。它同样带 `SG_READ_ONLY`（绑定后只读），但段内的指针都是 **PAC 签名指针**，典型含：

| `__AUTH_CONST` 内的节 | 含义 |
|---|---|
| `__auth_got` | **带签名的 GOT**：导入函数指针被签名，间接跳转前先 `AUT` 校验，杜绝"即便能写也写不出合法签名"的篡改 |
| `__auth_ptr` | 其它需要签名的全局指针 |
| `__const` / `__objc_const` | （签名上下文下的）只读常量/ObjC 只读元数据 |
| `__interpose` | interpose 替换表，其中指针用 `BLRAAZ`/`BRAAZ` 配合 diversifier `0` 签名调用 |

于是 arm64e 的防护是**双层**的：

1. **只读（`SG_READ_ONLY` + `mprotect`）**——绑定后写不进去；
2. **签名（PAC）**——即便绕过只读（例如趁加载期可写窗口或物理层攻击）写入了一个指针，没有进程私钥就**伪造不出合法 PAC 码**，CPU 校验时照样拒绝。

chained fixups 在 arm64e 上还**承载签名元数据**：fixup 链中 arm64e 专用的 bind/rebase 项（如 `dyld_chained_ptr_arm64e_auth_*` 格式）会编码"用哪个密钥、diversifier 是多少"，dyld 据此在写入指针的同时**为其生成正确 PAC 签名**——把"只读 + 签名"两件事在加载期一次做完。

> [!note] 看到 `__AUTH_CONST` 就知道是 arm64e
> 普通 arm64（非 e）二进制只有 `__DATA_CONST`；一旦出现 `__AUTH_CONST`（及 `__auth_got`/`__auth_ptr`），基本可断定这是 arm64e 切片、启用了 PAC。Mach-O 头里 `cputype=ARM64`、`cpusubtype=ARM64E`，工具常显示形如 `ARM64e (ARMv8.3) caps: PAC` 的标记（见 [[02.Mach-O文件头]]）。

### 6. 版本演进时间线

| 时间 / 工具链 | 事件 |
|---|---|
| **iOS 9 / macOS 10.11 El Capitan（2015）** | 引入 `__DATA_CONST` 段，开始把 GOT、`__const` 等"加载后只读"数据从 `__DATA` 迁出；`SG_READ_ONLY` 机制铺开。早期 MachOView 等工具为此专门加了对新段的解析支持。 |
| **Xcode 11 / clang-1100（2019 一带）** | ObjC 的 `__objc_classlist` 等类/协议/分类元数据列表默认从 `__DATA` 改入 `__DATA_CONST`，覆盖面进一步扩大。 |
| **A12 / arm64e + 链式 fixups 普及（2018→）** | `LC_DYLD_CHAINED_FIXUPS` 逐步取代 `LC_DYLD_INFO_ONLY`；arm64e 引入 PAC 与 **`__AUTH_CONST`**，对只读段内指针叠加签名，把"只读"升级为"只读 + 签名校验"。 |
| **近年 macOS（如 15.x）** | dyld/链接器对 `__DATA_CONST` 必须携带 `SG_READ_ONLY` 的校验趋严，缺失可能导致构建/加载失败——机制从"加固优化"固化为"硬约束"。 |

> [!note] 与 ELF 世界的对照
> 如果你熟悉 Linux：`__DATA_CONST` ≈ **Full RELRO**（GNU_RELRO 段，链接器填完重定位后 `mprotect` 只读），`__got` ≈ ELF 的 `.got`/`.got.plt`，`__mod_init_func` ≈ `.init_array`。差异在于 macOS 的 `SG_READ_ONLY` 是**段标志驱动、由 dyld 统一执行**，而 ELF 靠 `PT_GNU_RELRO` 程序头；arm64e 的 PAC 则是 ELF 侧暂无的硬件级增强。

## 实操：用工具查看

### 示例 1：`otool -l` 看 `__DATA_CONST` 的 `flags`（确认 SG_READ_ONLY）

```bash
otool -l /bin/ls | grep -A 8 "segname __DATA_CONST"   # 看段头：留意 flags 是否为 0x10
otool -lv /bin/ls                                      # -v 把 maxprot/flags 显示成符号名
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值（地址、大小、节数量）以你机器上的 `otool` 为准。

```text

  fileoff 32768

  maxprot 0x00000003   (rw-)        ; 上限 rw- → 允许加载期写
 initprot 0x00000003   (rw-)        ; 初始 rw- → 内核先按可写映射
   nsects 6
    flags 0x10  (SG_READ_ONLY)      ; ★ 关键：声明"绑定完成后降为只读"

  sectname __got                    ; 全局偏移表（非惰性指针）
```

> 说明：`initprot`/`maxprot` 名义都含写权限（`rw-`，供 dyld 修补），**但 `flags = 0x10 (SG_READ_ONLY)` 才是灵魂**——它告诉 dyld 修补完成后整段降为只读。`cmdsize 552 = 72 + 80*6` 与 `nsects 6` 自洽（段头字段细节见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）。

### 示例 2：arm64e 上多出的 `__AUTH_CONST`

```bash
otool -lv /usr/lib/dyld | grep -A 6 "segname __AUTH_CONST"   # arm64e 切片才有
```

> [!warning] 示例输出为示意
> 仅 arm64e 二进制存在此段；数值为构造。

```text
  segname __AUTH_CONST
   vmaddr 0x000000010000c000
  maxprot 0x00000003   (rw-)
 initprot 0x00000003   (rw-)
    flags 0x10  (SG_READ_ONLY)       ; 同样绑定后只读
   nsects 3
  Section: __auth_got   __AUTH_CONST  ; ★ 带 PAC 签名的 GOT
  Section: __auth_ptr   __AUTH_CONST  ; ★ 其它签名指针
  Section: __const      __AUTH_CONST
```

> 说明：`__AUTH_CONST` 与 `__DATA_CONST` 一样带 `SG_READ_ONLY`（只读），区别在于 `__auth_got`/`__auth_ptr` 里的指针是 **PAC 签名指针**——即便绕过只读写入，伪造不出合法签名也会被 CPU 拒绝。看到此段即可判定为 arm64e + PAC。

### 示例 3：`vmmap` 看运行期实际权限（已被降为 r--）

进程跑起来、dyld 完成 bind 并 `mprotect` 后，`__DATA_CONST` 的**当前**权限已与文件里的 `initprot` 不同——这一步只有运行期视图能看到：

```bash
vmmap <pid> | grep -E "__TEXT|__DATA"     # 对比各段"当前权限/最大权限"
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意 `__DATA_CONST` 运行期的 `r--/rw-` 特征。

```text
__TEXT        100000000-100008000   [   32K] r-x/r-x  SM=COW   /bin/ls
__DATA_CONST  100008000-10000c000   [   16K] r--/rw-  SM=COW            ; ★ 当前 r--，上限 rw-
__DATA        10000c000-100014000   [   32K] rw-/rw-  SM=COW
__LINKEDIT    100014000-100018000   [   16K] r--/r--  SM=COW
```

> 说明：`r--/rw-` 形如"**当前权限 / 最大权限**"——`__DATA_CONST` 当前是 `r--`（dyld 已 `mprotect` 降级），但 `maxprot` 仍是 `rw-`，正好印证 `SG_READ_ONLY` 的"加载期可写、绑定后只读"两阶段机制。**文件静态视图（`otool`）永远看不到这个 `r--`，必须看运行期 `vmmap`。** 想抓现行：对 dyld 启动序列上锁前后各 `vmmap` 一次，能看到该段从 `rw-` 翻成 `r--`。

### 示例 4：验证"写 `__DATA_CONST` 会崩"

可写个小程序，故意往 `__DATA_CONST` 里某个 GOT 槽写值，观察崩溃：

```c
// 伪代码示意：取得某 __DATA_CONST 内地址 p 后尝试写入
*(void **)p = (void *)0x41414141;   // 运行期写只读段 → EXC_BAD_ACCESS (SIGBUS/SIGSEGV)
```

> [!warning] 示例输出为示意
> 实际崩溃信息（地址、库名）随环境不同。

```text
Exception Type:  EXC_BAD_ACCESS (SIGBUS)
Exception Codes: KERN_PROTECTION_FAILURE at 0x0000000100008010
...  写入落在 __DATA_CONST（已 mprotect 为 r--）→ 保护异常
```

> 说明：这正是 `__DATA_CONST` 的防护生效现场——攻击者即便拿到写原语，写本段也会立即崩溃，GOT 劫持被阻断。若崩在 arm64e 的 `__AUTH_CONST`，错误信息里还会出现"pointer authentication failure"字样（PAC 校验失败）。

## FAQ

> [!question] `__DATA_CONST` 和 `__DATA` 到底怎么分？哪些节进哪个段？
> 判据只有一条：**该数据在 dyld 完成 rebase/bind 后是否还会被写？** "绑定后即固定"的指针型数据进 `__DATA_CONST`——`__got`、`__const`、`__mod_init_func`、`__objc_classlist`/`__objc_protolist`/`__objc_catlist`/`__objc_const`、`__objc_imageinfo` 等；"运行期仍会改写"的留在 `__DATA`——`__data`（可变全局）、`__bss`/`__common`（零填充后还写）、`__objc_selrefs`（selector 唯一化会改）、`__objc_ivar`（ivar 偏移 fix-up）、`__la_symbol_ptr`（惰性指针首次调用才回填，必须可写）。注意这条边界**随 Xcode/clang 版本迁移**，逆向时以 `otool -l` 实测为准。

> [!question] 既然要只读，为什么不一开始就把 `__DATA_CONST` 映射成 `r--`？为什么 `initprot` 是 `rw-`？
> 因为**加载期必须可写**。dyld 要往 `__got` 写入符号绑定后的真实地址、往各指针叠加 ASLR slide（rebase）——这些都是写操作。若一开始就只读，dyld 根本没法填址。所以 `initprot` 给 `rw-` 让 dyld 写得进去，写完后再靠 `SG_READ_ONLY` 触发 `mprotect` 降成 `r--`。这就是"两阶段权限"：`rw-`（加载期）→ `r--`（运行期）。静态文件看到 `rw-`、运行期 `vmmap` 看到 `r--`，两者都对。

> [!question] `__DATA_CONST` 和 Linux 的 RELRO 是一回事吗？arm64e 的 `__AUTH_CONST` 又强在哪？
> 思路完全一致——都是"重定位数据初始可写、链接器填完后改只读以防 GOT 劫持"，`__DATA_CONST` 就是 macOS/iOS 版的 **Full RELRO**（`__got`↔`.got`、`__mod_init_func`↔`.init_array`）。差异在执行方式：macOS 用**段标志 `SG_READ_ONLY` + dyld 统一 `mprotect`**，ELF 用 `PT_GNU_RELRO` 程序头。`__AUTH_CONST`（arm64e）则是 ELF 暂无的**硬件级增强**：在"只读"之上再给指针加 **PAC 签名**——即便攻击者绕过只读写入了指针，没有进程私钥伪造不出合法 PAC 码，CPU 校验时照样拒绝，做到"只读 + 签名"双保险。

> [!question] 我能在运行期用 `mprotect` 把 `__DATA_CONST` 改回可写来 hook/patch GOT 吗？
> 理论上若该段 `maxprot` 含 `VM_PROT_WRITE`（多数情况 `maxprot=0x3`），进程**自己**可以 `mprotect` 把它临时改回 `rw-`、改完再改回 `r--`——一些热修复/hook 框架（如 fishhook 思路）正是这么做的。但要注意：① 受 **Hardened Runtime / 代码签名 / SIP** 等策略约束，第三方对系统进程这么干往往被拒；② arm64e 上即使改可写，写进去的指针**没有合法 PAC 签名**，间接跳转时 `AUT*` 校验失败照样崩——所以 arm64e 上单靠 `mprotect` 改写 `__auth_got` 是不够的，必须能正确签名。`__DATA_CONST` 的设计初衷正是**抬高这类运行期改指针的门槛**。

> [!question] 看到 `flags 0x10` 但没看到 `__DATA_CONST` 这个段名，正常吗？
> `SG_READ_ONLY` 是**段标志**而非段名，理论上任何段都可带它；只是约定俗成由名为 `__DATA_CONST`（及 arm64e 的 `__AUTH_CONST`）的段承载。极少数自定义链接场景可能出现别的段名带 `SG_READ_ONLY`，或同一份数据因编译配置/工具链版本不同而落在不同段——判断"是否只读化"看的是 **`flags` 里有没有 `0x10`**，而不是段名字符串。

## 与相邻章节的关系

- [[14.Mach-O __DATA]]：`__DATA_CONST` 是从可写的 `__DATA` 中**拆分出的只读子集**——把"绑定后即固定的指针"迁出去，`__DATA` 只留真正可变的数据。两篇对照看，最能理解"哪些该可写、哪些该只读"。
- [[17.Mach-O LC_DYLD_INFO_ONLY]]：dyld 正是据其（及更现代的 `LC_DYLD_CHAINED_FIXUPS`）里的 rebase/bind 信息向 `__DATA_CONST` 写入真实指针，**写完才对本段上锁**。本段的"可写窗口"恰好就是这条命令被处理的那段时间。
- [[11.Mach-O Segments]]：段权限模型总纲。`__DATA_CONST` 是其"以段为权限单位 + 两阶段权限"思想的精细化落地。
- [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]：承载 `__DATA_CONST` 的段头结构与 `SG_READ_ONLY` 等 `SG_*` 标志的完整定义出处。
- [[40.Mach-O __objc_classrefs节]]：与 `__got` 同类的"绑定后固定的指针表"，同样受益于只读化保护，是理解本段保护对象的好样本。
- 具体节：[[21.Mach-O __const节]]、[[32.Mach-O __mod_init_func节]]、[[36.Mach-O __objc_classlist节]]、[[38.Mach-O __objc_protolist节]]、[[39.Mach-O __objc_catlist节]] 的"只读性"皆由本段统一兜底。

## 小结

- **`__DATA_CONST` 隔离"绑定后即固定"的指针**：GOT `__got`、只读常量 `__const`、初始化器表 `__mod_init_func`、ObjC 的 `__objc_classlist`/`__objc_protolist`/`__objc_catlist`/`__objc_const`/`__objc_imageinfo` 等，从可写 `__DATA` 中迁出单独成段。
- **`SG_READ_ONLY`（`0x10`）驱动两阶段权限**：加载期 `rw-`（`initprot=0x3`，供 dyld 写 rebase/bind/chained-fixups）→ 绑定完成后 dyld `mprotect` 降为 `r--`，运行期再写即 `EXC_BAD_ACCESS`。
- **目的是对抗 GOT 劫持 / 函数指针覆写 / ObjC 元数据篡改**——攻击者即便拿到写原语，写本段也会崩；概念上等价于 Linux 的 **Full RELRO**。
- **静态 vs 运行期两套视图**：`otool -l` 看到 `rw- + flags 0x10`（出厂权限 + 只读声明），`vmmap` 看到 `r--/rw-`（当前已降级 / 上限）——必须用运行期工具才能确认降权已生效。
- **arm64e 进化出 `__AUTH_CONST`**：在只读之上对 `__auth_got`/`__auth_ptr` 等指针叠加 **PAC 签名**，做到"只读 + 签名校验"双重防护；chained fixups 在写入指针时一并生成正确签名。
- **版本时间线**：iOS 9 / macOS 10.11 引入并迁移 GOT/const → Xcode 11/clang-1100 起 ObjC 类列表等默认入段 → arm64e + 链式 fixups 加入 PAC → 近年 dyld 对缺失 `SG_READ_ONLY` 趋于报错。
