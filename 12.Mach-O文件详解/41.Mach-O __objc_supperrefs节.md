# 详解Mach-O(四十一)Mach-O __objc_supperrefs节

> [!note] 命名说明（务必先读）
> 本篇**文件名与原标题沿用了 `__objc_supperrefs`（双写 `p`）的历史拼写**；但 Mach-O 二进制里**实际的节名是 `__objc_superrefs`（单 `p`，super = 父/超）**。这是当年笔记目录建立时的笔误，为保持链接稳定未改文件名。**下文一律使用正确术语 `__objc_superrefs`**；你在 `otool`、`objc4` 源码、LLVM 后端里看到的也都是单 `p` 的 `__objc_superrefs`，请以此为准。

> [!abstract] TL;DR
> **`__objc_superrefs` 是"父类调用引用表"（super references）**：一张**指针数组**，专门服务源码里的 `[super ...]` 调用。`[super foo]` 的语义不是"给 self 发消息"，而是"**跳过当前类、从父类开始查 `foo`**"，所以它**不能**走普通的 `objc_msgSend`，而是被编译器翻译成 `objc_msgSendSuper2(&(struct objc_super){self, 类引用}, @selector(foo), …)`——这个"类引用"就来自 `__objc_superrefs` 的某个槽。
> **关键反直觉点**：本表的槽**初值与回填后存的都是"`[super …]` 所在的那个类（当前类）"，而不是父类本身**。真正"往上走一层取父类"的动作，是 `objc_msgSendSuper2` 在运行期用 `class->superclass` 现算的（见下文汇编）。这样设计是为了**让 super 派发对运行期类层级的改动保持正确**（category/动态改父类后仍指向活的父类）。
> **加载期**：runtime 在 `_read_images` 用 `_getObjc2SuperRefs(hi,&count)` 取到本节，对每个槽调 `remapClassRef(&refs[i])`——把可能已被 runtime **重分配/弱链接忽略**的类指针修正成"活的"类对象（和 [[40.Mach-O __objc_classrefs节]] 走**同一段**重映射循环）；外部父类则由 `dyld` 的 bind / 链式 fixups 绑定到 `_OBJC_CLASS_$_父类` 符号。
> 它属于 ObjC **四大"引用类"节**（`selrefs`/`classrefs`/`superrefs`/`protorefs`）之一——存"对类的**引用**"而非类本体（本体在 [[36.Mach-O __objc_classlist节]]/`__objc_data`）。`flags` 典型值 `0x10000000` = 类型 `S_REGULAR(0x0)` + 属性 `S_ATTR_NO_DEAD_STRIP(0x10000000)`（汇编描述符 `regular,no_dead_strip`）——注意它存的是**类对象指针**，故类型是 `S_REGULAR`，**不是** selrefs 那个 `S_LITERAL_POINTERS`。

## 概述与定位

要理解 `__objc_superrefs` 为什么必须**独立于** [[40.Mach-O __objc_classrefs节]] 存在，得先把 ObjC 两种"带类信息的派发"摆清楚：

- **普通消息 `[obj foo]` / `[NSString new]`**：从**接收者自身的类**开始沿继承链查 `foo`。编译器走 `objc_msgSend`；需要的"类对象"（接收类方法时）来自 `__objc_classrefs`。
- **父类调用 `[super foo]`**：必须**跳过当前类、从父类开始查** `foo`。它解决的是"子类重写了 `foo`，但我想调父类那一版"的需求。这里若仍从当前类查，就会**查回自己、无限递归**。

正因为查找的**起点不同**（自身类 vs 父类），`[super …]` 用的是另一个 messenger：`objc_msgSendSuper2`，且它需要的不是"接收者的类"而是"用于定位父类的类引用"。这个类引用如果和 `__objc_classrefs` 混在一起，语义就糊了——所以编译器为 super 调用单开了一张表：`__objc_superrefs`。

把它放进 [[18.Mach-O section.md|节（section）的通用模型]] 看：`__objc_superrefs` 是一个 `flags` 类型为 `S_REGULAR`、带 `S_ATTR_NO_DEAD_STRIP` 属性的节，住在可写数据段。它和 [[35.Mach-O __objc_selrefs节]]、[[40.Mach-O __objc_classrefs节]]、[[42.Mach-O __objc_protorefs节]] 一道，构成 ObjC 元数据里的**"引用类"四节**——都不存元数据本体，只存"指向本体的、需加载期修正的指针"。runtime 在处理 [[36.Mach-O __objc_classlist节]] 等"列表类"节、注册类的同期，统一修正这四张引用表。

> [!note] 一句话定位
> **`__objc_classrefs` 回答"我代码里用到了哪些类（作为接收者）"；`__objc_superrefs` 回答"我代码里哪些类发起了 `[super …]`，需要据此找它们的父类"**。两表**结构同型**（都是类指针槽、加载期重映射），**语义正交**：一个面向"接收者类引用"，一个面向"父类调用的当前类锚点"。

## 核心原理与字段详解

### 1. 内容布局：一张"指向类对象"的指针数组

`__objc_superrefs` 在文件里就是一段**连续的指针数组**，没有头部、没有计数字段——和所有节一样，**条目数由 `节大小 size ÷ 指针宽度` 推算**（64 位 `size/8`、32 位 `size/4`，参见 [[18.Mach-O section.md|节的 size 与条目数推算]]）。每个槽是一个**类对象指针**：

- 若该类**定义在本镜像**（出现在 [[36.Mach-O __objc_classlist节]] 里），槽就是一个本地 rebase 指针，指向本镜像 `__objc_data` 里那个 `class_t`；
- 若是**外部类**（如系统库的 `UIViewController`），槽是一个待绑定的外部符号引用 `_OBJC_CLASS_$_UIViewController`，由 `dyld` bind / 链式 fixups 解析。

编译器为源码里**每个发起了 `[super …]` 的类**生成（至多）一个槽。注意：**触发点是"哪个类里写了 super 调用"，不是"调了哪个父类方法"**——同一个类里多处 `[super a]`、`[super b]` 通常共用**同一个** superref 槽（都锚定到"当前类"这一个类对象上），因为 messenger 拿到当前类后再按 selector 各查各的。

> [!note] 它由编译器/LLVM 后端发射，不是手写
> Clang 把 `[super foo]` 降级（lower）成对 `objc_msgSendSuper2` 的调用，并在数据段发射当前类的引用，描述符等价于 `.section __DATA,__objc_superrefs,regular,no_dead_strip`，槽里的 `.quad`（64 位）指向**当前类**的 `_OBJC_CLASS_$_当前类`/`L_OBJC_CLASSLIST_…` 标签。`regular` 对应节类型 `S_REGULAR(0x0)`，`no_dead_strip` 对应属性 `S_ATTR_NO_DEAD_STRIP(0x10000000)`——所以本节 `flags` 常见为 `0x10000000`（见下文第 6 节）。

### 2. `[super foo]` 到底编译成了什么：`objc_msgSendSuper2` + `struct objc_super`

这是本篇的核心机制。源码：

```objc
@implementation MyVC : UIViewController
- (void)viewDidLoad {
    [super viewDidLoad];   // ← 关注这一句
}
@end
```

编译器把这句 `[super viewDidLoad]` 翻译成大致如下的等价 C：

```c
struct objc_super sup;
sup.receiver    = self;                       // 真实接收者（还是 self）
sup.super_class = <从 __objc_superrefs 槽读到的『当前类』MyVC>;   // 注意：是当前类，不是父类！
objc_msgSendSuper2(&sup, @selector(viewDidLoad) /*, args… */);
```

其中 `struct objc_super` 是公开结构（`<objc/message.h>`）：

```c
struct objc_super {
    id receiver;            // 真实接收者（self）
    Class super_class;      // 注释原文：super_class is the first class to search
                            // （旧头里此字段名为 class，含义随 runtime 版本演进）
};
```

runtime 内部为新派发实际使用的是一个**字段语义不同**的孪生结构 `objc_super2`：

```c
struct objc_super2 {
    id receiver;            // 真实接收者
    Class current_class;    // 关键：这里放的是『当前类』，messenger 内部再取其 superclass
};
```

**两者内存布局完全一致（两个指针），区别只在第二个字段的"约定语义"**：`objc_msgSendSuper2` 约定第二个字段是**当前搜索类（current class）**，由它自己 `->superclass` 上溯一层；而老的 `objc_msgSendSuper`（"1"版）约定第二字段已经是**要搜索的父类**、直接从那里开查。Apple 在 `objc-abi.h` 的注释写得很直白：*objc_msgSendSuper2() takes the current search class, not its superclass*。

> [!note] 为什么编译器只发 `super2`、却两个都得永久保留
> 实际编译器**只发射 `objc_msgSendSuper2`**；但 `objc_msgSendSuper`（"1"版）作为**永久 ABI** 也必须一直存在（历史代码/手写汇编可能用到）。`super2` 把"取父类"放到运行期做，正是它相对 `super1` 的全部价值（见下条）。

### 3. 反直觉点剖析：槽里为何存"当前类"而非"父类"？看 ARM64 汇编

既然 `[super …]` 是"从父类查"，最朴素的想法是：编译期就把**父类**塞进槽里、`super1` 直接从父类开查不就完了？Apple 偏不——槽里存**当前类**，让 messenger 运行期现算父类。原因看 `objc_msgSendSuper2` 的 arm64 实现就懂了：

```asm
ENTRY _objc_msgSendSuper2
    // x0 = &objc_super{receiver, current_class}
    ldp  p0, p16, [x0]            // p0 = 真实 receiver, p16 = current_class（当前类）
    ldr  p16, [x16, #SUPERCLASS]  // p16 = current_class->superclass ← 运行期才取父类！
    CacheLookup NORMAL            // 从父类开始查缓存/方法列表
END_ENTRY _objc_msgSendSuper2
```

- `ldp p0, p16, [x0]`：一次性把 `objc_super` 的两个字段（receiver、current_class）从 `x0` 指向的结构里加载出来。
- `ldr p16, [x16, #SUPERCLASS]`：把 `current_class->superclass` 取出来——**"上溯一层取父类"这一步发生在运行期、在 messenger 内部**，而不是编译期写死在槽里。
- 然后 `CacheLookup` 从这个**运行期算出的父类**开始查方法。

**这就是为什么槽存当前类**：父类指针**不在编译期固化**，而是每次调用都从"活的"当前类 `->superclass` 现取。好处是 **super 派发对运行期类层级改动天然正确**——比如运行期通过 `class_setSuperclass`（或 KVO 动态子类化等）改了父类，`[super …]` 仍会走到**当时真正的**父类实现，而不会粘在编译期那个旧父类上。若当年把父类写死进槽，这类动态场景就会调错实现。

> [!note] 对照 `objc_msgSendSuper`（"1"版）
> "1"版约定槽/结构里直接给**父类**，省掉 `ldr …#SUPERCLASS` 那一步，从给定类直接开查。若错误地把"当前类"喂给 `super1`，就会**从当前类查起 → 命中自己重写的方法 → 无限递归**。这正是"1/2"两版**起点差一层**的要害，也是编译器统一选 `super2` 的原因。

### 4. 加载期处理：`_read_images` → `_getObjc2SuperRefs` → `remapClassRef`

镜像被 `dyld` 映射进来后，ObjC runtime 在 `_objc_init` → `map_images` → **`_read_images`** 里统一修正类引用。`__objc_superrefs` 与 `__objc_classrefs` **共用同一段重映射逻辑**（基于 Apple `objc4` 源码）：

1. **是否需要重映射**：先判 `if (!noClassesRemapped())`——只有当确实有类被 runtime "重分配/弱链接忽略"时才进这段循环（绝大多数镜像无需重映射，直接跳过）。
2. **取节并逐项重映射**：
   - 先处理 classrefs：`Class *refs = _getObjc2ClassRefs(hi,&count); for(i) remapClassRef(&refs[i]);`
   - 再处理 superrefs：`refs = _getObjc2SuperRefs(hi,&count); for(i) remapClassRef(&refs[i]);`
   - 然后打日志 `ts.log("IMAGE TIMES: remap classes")`。
3. **`_getObjc2SuperRefs` 的来历**：它由 `objc-file.mm` 的 `GETSECT(_getObjc2SuperRefs, Class, "__objc_superrefs")` 宏生成——**读的就是名为 `"__objc_superrefs"` 的节**（单 `p`！），节名写错就拿不到，super 引用修正不上。
4. **`remapClassRef` 做什么**：`Class newcls = remapClass(*ref); if (*ref != newcls) *ref = newcls;`——把槽里的类指针修正成"活的"类对象（`remapClass` 查 `remappedClasses` 表：被重分配的类换成新地址；被弱链接忽略的类返回 `nil`）。**"不等才写"**同样为了**少弄脏内存页**（与 [[35.Mach-O __objc_selrefs节]] 的 `map_selrefs` 同理）。

> [!note] superref 修正的是"类重映射"，外部父类绑定由 dyld 负责
> 这里 `remapClassRef` 解决的是 **runtime 层面的类重分配/弱链接**问题；而"外部父类（如 `UIViewController`）的符号 → 真实地址"这一步，是 **`dyld` 的 bind / 链式 fixups** 在更早阶段完成的（见 [[17.Mach-O LC_DYLD_INFO_ONLY]] 的 bind、或现代的 `LC_DYLD_CHAINED_FIXUPS`）。两步叠加，superref 槽最终指向"活的、正确的当前类对象"，messenger 才能据此 `->superclass` 取到对的父类。

### 5. 与 `__objc_classrefs` 的精确区别（最易混的一对）

`superrefs` 和 `classrefs` 结构同型（都是加载期重映射的类指针数组、走同一循环、同样 `S_REGULAR + no_dead_strip`），**唯一差别在"槽锚定的类是谁、为何而存"**：

| 维度 | `__objc_classrefs`（接收者类引用） | `__objc_superrefs`（父类调用引用） |
|---|---|---|
| **服务的语法** | `[Class msg]`、`[obj msg]`（普通派发） | `[super msg]`（父类调用） |
| **对应 messenger** | `objc_msgSend`（及变体） | `objc_msgSendSuper2` |
| **槽里存哪个类** | **接收者自身的类**（直接拿来当查找起点/类方法接收者） | **`[super …]` 所在的当前类**（messenger 运行期再 `->superclass` 取父类） |
| **查找起点** | 从该类自身开始沿继承链查 | 从该类的**父类**开始查（跳过自己） |
| **触发计数** | 每个被引用的"接收类"一个槽 | 每个"发起 super 调用的类"一个槽 |
| **加载期修正** | `_getObjc2ClassRefs` + `remapClassRef` | `_getObjc2SuperRefs` + `remapClassRef`（**同一段循环**） |
| **runtime 访问器** | `_getObjc2ClassRefs` | `_getObjc2SuperRefs` |

**一句话区分**：classrefs 的槽**就是查找起点**；superrefs 的槽**是查找起点的"下一层基准"**——它存当前类，真正的起点（父类）由 messenger 在运行期 `->superclass` 现算。这"差一层 + 运行期现算"正是 super 语义与动态正确性的来源。

> [!note] 与"列表类"节的区别
> 别把"引用类"四节和 [[36.Mach-O __objc_classlist节]] 这类"**列表类**"节混了：`classlist`/`nlclslist`/`catlist` 列的是"**本镜像定义了哪些类/分类**"（供 runtime 注册"我提供的元数据"，**不参与上面的重映射**——源码注释明确"class list 与 nonlazy class list 保持不重映射，只重映射 class refs / super refs 供派发用"）；而 `superrefs`/`classrefs` 记的是"**本镜像代码要用到哪些类**"（供 runtime 修正"我要用的引用"）。一个是"我有什么"，一个是"我用什么"。

### 6. `flags` 解读：`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`

回到 [[18.Mach-O section.md|节头 flags]] 的视角，`__objc_superrefs` 的 `flags` 典型值是 **`0x10000000`**，按 `SECTION_TYPE(0x000000ff)` / `SECTION_ATTRIBUTES(0xffffff00)` 拆开：

- **类型** `0x10000000 & 0xff = 0x00` = **`S_REGULAR`**（普通节）。注意它**不是** [[35.Mach-O __objc_selrefs节]] 的 `S_LITERAL_POINTERS(0x5)`——selrefs 存的是"指向字面字符串的指针"（链接器可据此做字面量去重），而 superrefs/classrefs 存的是**指向类对象的普通指针**，没有"字面量"语义，故归 `S_REGULAR`。这是两类引用节在 `flags` 上的实质差异。
- **属性** `0x10000000 & 0xffffff00 = 0x10000000` = **`S_ATTR_NO_DEAD_STRIP`**（禁止死代码消除）。链接器即便静态分析觉得某个 superref"看似没人用"，也不得删除——ObjC 的类与 super 调用大量在运行期被动态触达，静态可达性分析不可靠（汇编描述符里 LLVM 后端写的就是 `regular,no_dead_strip`）。

> [!note] `no_dead_strip` 是有意为之
> ObjC 元数据节普遍带 `S_ATTR_NO_DEAD_STRIP`，因为方法/类常被运行期动态使用（消息转发、KVC、`class_setSuperclass` 等），编译期"这个引用没人用"的判断经常是错的。给 superrefs 打上此标记，等于告诉链接器"别用静态分析删我"，保证 super 派发链路完整。

## 实操：用工具查看

### 示例 1：`otool -s __DATA __objc_superrefs` dump 原始指针

`otool -s 段名 节名` 以十六进制 dump 指定节的原始字节。**段名要按你二进制的实际布局给**——老二进制多在 `__DATA`，现代经链式 fixups 只读化的可能并入 `__DATA_CONST`（arm64e 带指针认证的更可能落在 `__AUTH_CONST`）：

```bash
otool -s __DATA __objc_superrefs /path/to/ObjCBinary        # 老布局/部分二进制
otool -s __DATA_CONST __objc_superrefs /path/to/ObjCBinary  # 现代只读化布局
```

```text
Contents of (__DATA,__objc_superrefs) section
0000000100009280  90 41 00 00 01 00 00 00      ; superref[0] → 0x100004190 = class_t(MyVC)，即『当前类』
0000000100009288  b8 41 00 00 01 00 00 00      ; superref[1] → 0x1000041b8 = class_t(MyView)
```

> 说明：左列是该槽自身的虚拟地址（从节 `addr` 起算），右列 8 字节是**小端**指针值（`90 41 00 00 01 00 00 00` → `0x0000000100004190`），指向的是**发起 super 调用的那个类**的 `class_t` 本体（在 `__objc_data`），**不是它的父类**。本节大小 `0x10` → 条目数 `0x10 / 8 = 2`。运行期 `objc_msgSendSuper2` 拿到这个类后再 `->superclass` 上溯一层才得到父类。

### 示例 2：`otool -ov` 解析 ObjC 元数据

`otool -ov`（`-o` 解析 ObjC 元数据、`-v` 符号化）会把引用槽解析成符号名，比裸十六进制直观：

```bash
otool -ov /path/to/ObjCBinary                       # 完整 dump ObjC 段
otool -ov /path/to/ObjCBinary | grep -A2 -i superref # 只看 super 引用片段
```

> [!warning] 示例输出为示意
> 数值/符号为构造，仅示意 `otool -ov` 如何把 superref 槽解析回类符号。注意解析出的是**当前类**符号（如 `MyVC`），父类需结合该类的 `superclass` 字段或 `__objc_classlist` 一起看。

```text
Contents of (__DATA_CONST,__objc_superrefs) section
0x0000000100009280  0x0000000100004190 _OBJC_CLASS_$_MyVC      ; 当前类（发起 [super] 者）
0x0000000100009288  0x00000001000041b8 _OBJC_CLASS_$_MyView    ; 当前类
```

> 说明：逆向时 superrefs 表几乎就是"**本二进制里哪些类用了 `[super …]`**"的清单。要看"调向哪个父类"，再顺着该类 `class_t` 的 `superclass` 字段（或对照 `__objc_classlist` 的继承关系）即可。配合 [[40.Mach-O __objc_classrefs节]] 一起看，能区分"作为接收者被引用的类"与"作为 super 锚点被引用的类"。

> [!note] 逆向提醒：从共享缓存抽出的 dylib 可能解析不全
> 当库被从 **dyld 共享缓存**单独抽取时，superref 指向的类对象可能**已不在本文件内**（本体还在共享缓存里），`otool`/Ghidra 会显示成 `DAT_<address>` 裸地址、解析不出类名。需用**感知共享缓存**的工具或在完整缓存环境下分析。

## FAQ

> [!question] `__objc_superrefs` 和 `__objc_classrefs` 都是类指针表，为什么非要分成两节？合并不行吗？
> 不行，因为二者**查找语义正交**。`__objc_classrefs` 的槽是"接收者的类"，**直接**用作普通派发 `objc_msgSend` 的起点（或类方法接收者）；`__objc_superrefs` 的槽是"`[super …]` 所在的当前类"，要喂给 `objc_msgSendSuper2`、由它 `->superclass` **再上溯一层**才得到查找起点。一处直接用、一处差一层，混在一张表里 runtime 就无法区分"这个类指针该从自身查还是从父类查"。所以编译器按用途分表，runtime 也用两个不同访问器（`_getObjc2ClassRefs` / `_getObjc2SuperRefs`）分别取——尽管它们随后走的是**同一段** `remapClassRef` 重映射循环。

> [!question] 既然 `[super foo]` 是"从父类查"，为什么槽里存的是"当前类"而不是直接存父类？
> 为了**让 super 派发对运行期类层级改动保持正确**。父类指针**不在编译期固化**进槽，而是由 `objc_msgSendSuper2` 每次调用时用 `current_class->superclass` **现算**（汇编里那句 `ldr p16, [x16, #SUPERCLASS]`）。这样，若运行期通过 `class_setSuperclass`、KVO 动态子类化等改了父类，`[super …]` 会走到**当时真正的**父类实现，而不会粘在编译期那个旧父类上。反过来，老的 `objc_msgSendSuper`（"1"版）约定直接给父类、从给定类开查；若错把"当前类"喂给它，就会从当前类查起、命中自己重写的方法、**无限递归**——这正是必须区分 super1/super2、且编译器统一选 super2 的根因。

> [!question] `objc_super` 和 `objc_super2` 是什么关系？编译器到底用哪个？
> 两者**内存布局相同**（`{id receiver; Class …;}` 两个指针），区别只在第二字段的**约定语义**：公开的 `struct objc_super` 第二字段叫 `super_class`（注释称"the first class to search"，配合老的 `objc_msgSendSuper` 时确实直接是要搜索的类）；runtime 内部为 `objc_msgSendSuper2` 用的 `objc_super2` 第二字段叫 `current_class`，是"当前类"，由 messenger 自己上溯取父类。**编译器实际只发射 `objc_msgSendSuper2`**，并把当前类放进结构的第二字段；`objc_super`/`objc_msgSendSuper`（"1"版）作为永久 ABI 保留但编译器一般不生成。简记：你写 `[super …]` → 编译器填 `{self, 当前类}` → 调 `objc_msgSendSuper2` → 它 `->superclass` 取父类开查。

> [!question] `__objc_superrefs` 在加载期具体被谁、怎么修正？
> 两层修正叠加：① **dyld** 在装载/链式 fixups 阶段把**外部父类符号**（如 `_OBJC_CLASS_$_UIViewController`）bind 成真实地址（本镜像内的类则是 rebase）；② ObjC runtime 在 `_read_images` 里，仅当 `!noClassesRemapped()` 时，用 `_getObjc2SuperRefs(hi,&count)` 取本节、对每槽 `remapClassRef(&refs[i])`——把被 runtime **重分配/弱链接忽略**的类指针换成"活的"类对象（与 `__objc_classrefs` **共用同一段循环**，日志 `IMAGE TIMES: remap classes`）。注意源码刻意**不重映射** `__objc_classlist`（类定义本体），只重映射这两张"供派发用"的引用表。

> [!question] 为什么 `__objc_superrefs` 的 `flags` 类型是 `S_REGULAR`，而 `__objc_selrefs` 是 `S_LITERAL_POINTERS`？
> 因为两者槽里指向的东西性质不同。`__objc_selrefs` 存的是"指向**字面字符串**（`__objc_methname` 里的 selector 名）的指针"，`S_LITERAL_POINTERS(0x5)` 这个类型正是为"指向字面量的指针"准备的，便于链接器做字面量去重。而 `__objc_superrefs`（及 `__objc_classrefs`）存的是"指向**类对象**的普通指针"，没有字面量去重语义，所以归 `S_REGULAR(0x0)`。二者共有的属性是 `S_ATTR_NO_DEAD_STRIP(0x10000000)`，故 superrefs 的 `flags` 典型为 `0x10000000`、selrefs 为 `0x10000005`。

## 与相邻章节的关系

- [[40.Mach-O __objc_classrefs节]]：并列的"引用类"节，存**接收者自身的类引用**，与本表的**父类调用锚点**精确相对；二者走**同一段** `remapClassRef` 重映射循环，是本篇最需对照的一篇。
- [[36.Mach-O __objc_classlist节]]：类**定义**列表，父子关系（`superclass`）记录在每个类的 `class_t` 中；superref 拿到当前类后，正是顺着这里的 `superclass` 上溯。"我定义了谁" vs superref 的"我用谁发 super"。
- [[35.Mach-O __objc_selrefs节]]：消息发送的**另一侧**——selector 引用（唯一化为 `SEL`）。`objc_msgSendSuper2` 的第二个参数 `sel` 就来自 selrefs；本篇是详细度与风格的标杆篇。
- [[42.Mach-O __objc_protorefs节]]：并列的"引用类"节之一，槽指向协议、回填为唯一 `Protocol *`。
- [[18.Mach-O section.md|18.Mach-O section]]：本节 `flags`（`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`）、`size÷指针宽度` 推算条目数、可写段与回填/重映射的通用模型，都在那篇的字段说明书里。

## 小结

- `__objc_superrefs`（节名单 `p` `__objc_superrefs`，本篇文件名沿用历史双 `p` `supperrefs`）是 **父类调用引用表**：一张**类指针数组**，每个"发起 `[super …]` 的类"对应一个槽；`flags` 典型 `0x10000000`（`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`），条目数 = `size ÷ 指针宽度`。
- **`[super foo]` 编译为** `objc_msgSendSuper2(&(struct objc_super){self, 当前类}, @selector(foo), …)`；`struct objc_super{receiver, super_class}` 与内部 `objc_super2{receiver, current_class}` 布局同、语义在第二字段差一层。
- **反直觉核心**：槽里存的是**当前类**而非父类；`objc_msgSendSuper2` 运行期 `ldr p16,[x16,#SUPERCLASS]` 现取 `current_class->superclass` 才得父类——这让 super 派发对运行期改父类**保持正确**，也避免错用 super1 导致的自身递归。
- **与 `__objc_classrefs` 的区别**：classrefs 槽是接收者类、直接当查找起点；superrefs 槽是当前类、要 messenger 再上溯一层。两表结构同型、走**同一段** `remapClassRef`，语义正交。
- **加载期**：dyld bind/链式 fixups 解析外部父类符号；runtime 在 `_read_images` 用 `_getObjc2SuperRefs` + `remapClassRef` 修正类重分配/弱链接（`classlist` 本体不重映射，只修引用表）。
