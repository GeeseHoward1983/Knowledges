# 详解Mach-O(三十二)Mach-O __mod_init_func节

> [!abstract] TL;DR
> **`__mod_init_func` 是一张"初始化函数指针数组"**：节里每个条目是一个 8 字节（64 位）/ 4 字节（32 位）的函数指针，指向一个需要在 `main` 之前运行的初始化器——C++ 具有非平凡构造的全局/静态对象的构造函数、`__attribute__((constructor))` 标注的 C 函数等。
> 它的节类型是 **`S_MOD_INIT_FUNC_POINTERS`（`flags & SECTION_TYPE == 0x9`）**，见 [[18.Mach-O section]] 的完整类型表。因为指针指向本镜像内部、受 ASLR 影响需要 rebase（叠加 slide），所以传统上它住在可写的 [[14.Mach-O __DATA]]。
> `dyld` 在完成段映射、依赖库加载、rebase/bind（或链式 fixups）之后，**按数组顺序依次调用**这里的每个函数指针，全部跑完才跳转到 [[09.Mach-O LC_MAIN]] 指定的程序入口。条目数不显式存储，而用 `size ÷ 指针宽度` 推算。
> 它是"程序入口之前还能跑代码"的机制来源之一（另一条路是 ObjC 的 `+load`，见 [[37.Mach-O __objc_nlclslist节]]），既是 C++ 运行时启动的基石，也是注入/反调试/持久化技术常见的藏身处。现代启用链式 fixups 的二进制改用 **`__init_offsets`（`S_INIT_FUNC_OFFSETS == 0x16`）**：存 32 位偏移而非绝对指针，免 rebase、可放只读段。

## 概述与定位

很多语言特性要求"`main` 之前先初始化"：C++ 的全局/静态对象要先调用构造函数、带 `constructor` 属性的函数要先跑、某些框架要在入口前注册回调。这些初始化逻辑不能等到 `main` 里再做——因为 `main` 第一行代码可能就已经在用这些全局对象了。Mach-O 的解法是：让编译器把所有"入口前初始化器"的地址收集进 `__mod_init_func` 这一张指针表，交给 `dyld` 在启动末段统一调用（完整启动流程见 [[09.Mach-O LC_MAIN]] 的启动流程图）。

可以把 `__mod_init_func` 理解为 **C/C++ 世界的"静态初始化清单"**。它和 ObjC 的 `+load` 是"入口前跑代码"的两条不同路径：`+load` 由 ObjC runtime 在 dyld 的镜像加载通知里驱动（数据来自非惰性类列表 [[37.Mach-O __objc_nlclslist节]]），`__mod_init_func` 则由 dyld 直接读节、直接调指针。两者都在 `main` 之前完成，但走的是不同的机制（详见下文第 5 节的先后与区别）。

它在 [[18.Mach-O section]] 的节类型体系里属于 `S_MOD_INIT_FUNC_POINTERS`（`0x9`），与它对称的是终止函数表 `__mod_term_func`（`S_MOD_TERM_FUNC_POINTERS`，`0xa`，见 [[33.Mach-O __mod_term_func节]]）——一个管"入口前初始化"，一个管"退出时清理"。因为表里的指针指向本镜像内部、随 ASLR 滑动需要被 rebase（写回 slide 后的真实地址），所以它天然要求**可写**，因此放在 [[14.Mach-O __DATA]] 段；这也正是现代 `__init_offsets` 诞生的动机（存偏移就不必可写、不必 rebase，可挪到只读段，见第 6 节）。

> [!note] 名字总要带段名：`__DATA,__mod_init_func`
> 和所有节一样（见 [[18.Mach-O section]]），`__mod_init_func` 几乎从不单独出现，而是写作 `段名,节名` 的二元组 `__DATA,__mod_init_func`。`otool -s __DATA __mod_init_func` 这类命令也要求段名 + 节名一起给。少数加固/优化产物里它可能出现在 `__DATA_CONST`（见 [[15.Mach-O __DATA_CONST]]）或被 `__init_offsets` 取代——逆向时别只盯着 `__DATA`。

## 核心原理与字段详解

### 1. 内容：初始化器指针数组

`__mod_init_func` 的节体就是一段**紧密排列的函数指针**，每个指针指向本镜像 `__TEXT,__text`（见 [[19.Mach-O __text节]]）里的一个初始化函数。它的节头是通用的 `section_64` 结构（见 [[18.Mach-O section]]），关键字段取值如下：

- **`flags & SECTION_TYPE == S_MOD_INIT_FUNC_POINTERS (0x9)`**——这是 dyld 识别"本节是初始化器表"的唯一依据。dyld 解析 Load Commands 时只看这个类型位：若某节 `type == S_MOD_INIT_FUNC_POINTERS`，就置 `fHasInitializers = true`，待会儿要回来逐项调用。
- **`size`**——节的字节数。条目数 **不单独存储**，而是 `count = size / sizeof(uintptr_t)`（64 位 `/8`，32 位 `/4`）。所以一个 `size = 0x18 = 24` 字节的 64 位 `__mod_init_func` 含 `24/8 = 3` 个初始化器。
- **`align`**——一般 8 字节对齐（`align = 3`，即 `2^3`），保证指针自然对齐。
- **`reserved1/2/3`**——本节**不复用** reserved（它不是符号桩/符号指针节），三者通常全为 0。这点与 `__stubs`/`__la_symbol_ptr` 不同（那些节靠 `reserved1/2` 联动间接符号表，见 [[18.Mach-O section]] 第 9 节与 [[22.Mach-O __stubs节]]）。

这些指针的**来源**有三类：

1. **C++ 具有非平凡构造的全局/静态对象**。例如文件作用域的 `static std::string g = "hi";` 或 `MyClass g_obj(42);`——编译器为"构造 `g`/`g_obj`"生成一个隐藏的初始化函数（内部通常叫 `__GLOBAL__sub_I_xxx` 之类），并把它的地址放进 `__mod_init_func`。平凡初始化（如 `int g = 5;` 这种编译期常量）不需要运行时构造，不会进表。
2. **`__attribute__((constructor))` 标注的 C 函数**。任何带此属性的函数，其地址都会被编译器收集进 `__mod_init_func`，于是它会在 `main` 之前被自动调用。对称地，`__attribute__((destructor))` 的函数进 `__mod_term_func`（见 [[33.Mach-O __mod_term_func节]]）。
3. **运行时/框架注册的早期初始化逻辑**。一些库用 constructor 属性或全局对象在入口前完成自注册（如把自己挂到某个全局表）。

> [!note] 初始化器的函数签名：和 `main` 收一样的参数
> 在 dyld 内部，`__mod_init_func` 里的指针被当作 **`void (*)(int argc, char** argv, char** envp, char** apple)`** 调用——也就是说初始化器拿到的参数和 `main` 完全一样（macOS 上 `main` 实际收 4 个参数：`argc`、`argv`、环境变量 `envp`、以及 `apple` 数组）。普通 C++ 全局构造器和 `__attribute__((constructor))` 函数通常声明成无参 `void f(void)`，忽略这些参数即可；但你也可以写 `void f(int argc, char** argv, char** envp)` 来读取它们。`__mod_term_func` 里的终止器则无参、无返回（见 [[33.Mach-O __mod_term_func节]]）。

### 2. 调用时机：rebase/bind 之后、跳 LC_MAIN 之前

要理解"为什么这些函数能在 `main` 前跑"，得把 dyld 的启动序列摊开看。`dyld` 是新进程里第一段运行的代码（内核通过主程序的 `LC_LOAD_DYLINKER` 把控制权交给它的 `__dyld_start` 入口），它在跳到你的 `main` 之前，大致按如下顺序做完所有准备：

1. **自举（bootstrap）**：dyld 先把自己 rebase 好。
2. **映射段 + 递归加载依赖库**：把主程序各段映射进地址空间，再顺着 `LC_LOAD_DYLIB`（见 [[07.Mach-O LC_LOAD_DYLIB]]）把所有依赖的 dylib 递归加载进来（系统库多数已在 dyld 共享缓存里预链接）。
3. **rebase / bind（修正/绑定）**：rebase 给本镜像内部指针叠加 ASLR slide；bind 把对外部符号的引用解析到真实地址。现代二进制这一步走链式 fixups（`LC_DYLD_CHAINED_FIXUPS`，见 [[17.Mach-O LC_DYLD_INFO_ONLY]] 的对照），还会做 ObjC/Swift runtime 专属的 fixups。
4. **运行初始化器（本节登场）**：**这一步才轮到 `__mod_init_func`**。dyld 重新扫一遍各镜像，对每个 `S_MOD_INIT_FUNC_POINTERS` 节，从 `addr + slide` 起、按 `size / 指针宽度` 算出的条目数，**逐项调用**函数指针。
5. **跳转入口**：所有初始化器跑完，dyld 才设置好 `argc/argv/...` 并跳到 [[09.Mach-O LC_MAIN]] 指定的程序入口（`main`）。

所以"初始化器运行在 `main` 之前、且外部依赖已就绪之时"这句话有两层含义：① 时间上早于 `main`；② 此时 rebase/bind 已完成，初始化器里可以安全使用本镜像的全局量和依赖库导出的符号。

> [!note] dyld 怎么"找到"并"调用"本节（源码视角）
> dyld 解析 Load Commands 时，对每个 `LC_SEGMENT_64` 里的节查 `flags & SECTION_TYPE`：命中 `S_MOD_INIT_FUNC_POINTERS` 就标记 `fHasInitializers = true`。真正调用发生在初始化阶段：dyld 把节当成 `Initializer* inits = (Initializer*)(sect->addr + fSlide)`，算 `count = sect->size / sizeof(uintptr_t)`，然后 `for (i=0; i<count; i++) inits[i](argc, argv, envp, apple);`。**条目数完全由 `size` 推导**，节头不另存计数——这与 [[18.Mach-O section]] 里"符号桩用 `size/reserved2` 推条目数"是同一种"不显式存计数"的设计哲学，只是这里除数是固定的指针宽度。

### 3. 调用顺序：数组内顺序 + 跨镜像依赖序 + constructor priority

"按什么顺序调用"要分两个层面看：

**(a) 同一镜像内：按指针在数组中出现的顺序。** dyld 对单个 `__mod_init_func` 就是从第 0 项调到第 N-1 项，**严格按出现顺序**。这正是 `__attribute__((constructor(priority)))` 里 priority 起作用的底层机制：priority 本身不被 dyld 理解，而是**链接器在生成节时按 priority 给指针排序**（数字越小越靠前），dyld 再"按出现顺序"调用，于是低 priority 数字的初始化器先跑。priority 取值范围一般 `[101, 65535]`（`0~100` 保留给实现），不写 priority 的 constructor 排在所有带 priority 的之后。

**(b) 跨镜像之间：按依赖关系自底向上（bottom-up）。** dyld 保证**先跑被依赖者、再跑依赖者**：一个库的初始化器，总在它所依赖的全部库的初始化器跑完之后才执行。这样每个初始化器都能放心使用其依赖库——依赖库此刻已初始化完毕。具体地，`DYLD_INSERT_LIBRARIES` 插入的库初始化器最先跑，然后是依赖库，最后才是主程序自己。Apple 文档明确给出这一保证：链接器/加载器在调用某镜像的静态初始化器之前，会先执行其依赖库的静态初始化器。

> [!warning] 循环依赖会破坏"依赖在前"的保证
> "依赖库先初始化"这条保证**对循环依赖无法成立**：若 A 依赖 B、B 又依赖 A，dyld 只能以某种未指定的顺序跑它们的初始化器，无法保证你用到的那一方已经初始化完。工程上应避免初始化期的循环依赖，或把"用到对方"的逻辑推迟到 `main` 之后/首次使用时（惰性初始化）。

### 4. 类型与可写性：为什么住在 __DATA

节类型固定为 **`S_MOD_INIT_FUNC_POINTERS`（`0x9`）**。它住在可写的 [[14.Mach-O __DATA]] 段，根本原因是**指针要被 rebase**：表里存的是绝对函数地址，而 ASLR 会给整个镜像加一个随机 slide，dyld 必须把每个指针改写成 `原值 + slide` 才能用——改写就要求该页可写。

这也带来一个安全副作用：可写的函数指针表 + "在 `main` 前被 dyld 自动调用"，使 `__mod_init_func` 成为**注入/持久化/反调试**的经典目标——往表里塞一个指针，就能让任意代码在程序真正开始前运行。正因如此，现代加固方向是把它换成只读的偏移表 `__init_offsets`（见第 6 节），从结构上消除"可写函数指针"这个攻击面。

> [!note] 架构差异
> 指针宽度随架构不同：64 位（arm64 / x86_64）每条目 8 字节，32 位（armv7 / i386）每条目 4 字节，因此条目数 = `size/8` 或 `size/4`。调用约定（arm64 vs x86_64 的栈/寄存器传参）会影响初始化器内部的参数读取，但"指针数组 + dyld 按序依次调用"的机制在各架构上一致。历史上还有一个**已废弃**的等价机制 `LC_ROUTINES[_64]`（指定单个初始化"例程"），现代工具链一律改用 `S_MOD_INIT_FUNC_POINTERS` 节，`LC_ROUTINES` 基本绝迹。

### 5. 与 ObjC `+load` 的先后与区别

`__mod_init_func` 和 ObjC 的 `+load` 都"在 `main` 之前跑代码"，但走的是**两条不同的路径**，很多人会混淆，这里讲清楚：

| 维度 | `__mod_init_func`（本节） | ObjC `+load` |
|---|---|---|
| 数据来源 | `__DATA,__mod_init_func` 指针表 | 非惰性类/分类列表 `__objc_nlclslist`（见 [[37.Mach-O __objc_nlclslist节]]）/ `__objc_nlcatlist` |
| 谁来调用 | **dyld 直接读节、直接调指针** | **ObjC runtime** 调用（`call_load_methods`） |
| 触发机制 | dyld 初始化阶段遍历 `S_MOD_INIT_FUNC_POINTERS` 节 | ObjC runtime 向 dyld 注册镜像加载回调，dyld 在 `notifySingle` 通知 runtime，runtime 再调 `+load` |
| 典型内容 | C++ 全局对象构造、C `constructor` 函数 | ObjC 类/分类的 `+load` 方法 |
| 函数签名 | `void(int,char**,char**,char**)`（同 `main` 参数） | `+ (void)load`（无参类方法） |

**先后关系**：两者都发生在 dyld 的**同一个初始化阶段**内、都在 `main` 之前。从调用栈看，`+[X load]` → `call_load_methods` → `load_images` → `dyld::notifySingle` → `ImageLoader::recursiveInitialization` → `...runInitializers` → `dyld::_main`——也就是说 `+load` 是在 dyld 跑某镜像初始化器的过程中、由 runtime 回调触发的。同一镜像内，ObjC runtime 通常先处理完该镜像（及其依赖）的 `+load`，C/C++ 的 `__mod_init_func` 在同一初始化流程中被调用；跨镜像同样遵循"依赖在前"的自底向上序。实务上的稳妥心智模型是：**别依赖 `+load` 与 C++ 全局构造器之间的精确相对顺序**（不同 dyld/runtime 版本可能有差异），只确信"两者都在 `main` 之前、且依赖库的都先于依赖者"。

> [!note] 为什么 ObjC 选 `+load` 而非 constructor
> `+load` 由 runtime 在"类已注册进 runtime、但还没人用它"的时刻调用，能保证 ObjC 元数据（类、方法、分类）已就位；而 C++ 全局构造器只保证 C/C++ 运行时就绪。所以需要操作 ObjC 类结构的早期逻辑用 `+load`，纯 C/C++ 的早期逻辑用 constructor 或全局对象。它们落在不同的节、由不同的调用方驱动，但都被 dyld 的同一启动末段统一"夹"在 `main` 之前。

### 6. 现代演进：`__init_offsets`（S_INIT_FUNC_OFFSETS 0x16）

启用**链式 fixups**（`LC_DYLD_CHAINED_FIXUPS`，macOS 11 / iOS 14 起，见 [[17.Mach-O LC_DYLD_INFO_ONLY]]）的现代二进制，链接器会把 `__mod_init_func` **改写成 `__init_offsets`**，节类型从 `S_MOD_INIT_FUNC_POINTERS (0x9)` 变为 **`S_INIT_FUNC_OFFSETS (0x16)`**（这是 [[18.Mach-O section]] 类型表里目前已知编号最高的类型）。两者的差异是结构性的：

| 维度 | `__mod_init_func`（传统） | `__init_offsets`（现代） |
|---|---|---|
| 节类型 | `S_MOD_INIT_FUNC_POINTERS` `0x9` | `S_INIT_FUNC_OFFSETS` `0x16` |
| 条目内容 | **绝对函数指针**（8B/4B） | **32 位相对偏移**（相对镜像基址，恒 4B） |
| 加载处理 | 逐个 **rebase**（+slide）才能用 | 运行时 `基址 + 偏移`，**无需 rebase** |
| 段归属 | 必须可写 → `__DATA` | 可只读 → 可放 `__TEXT` / `__DATA_CONST` |
| 条目数 | `size / 8`（64 位） | `size / 4` |
| 对齐要求 | 8 字节 | **4 字节（dyld 强制要求，否则拒绝执行初始化器）** |

`__init_offsets` 的好处直指链式 fixups 的目标——**减小体积、加快启动**：存相对偏移而非绝对指针，意味着这些初始化器入口**完全不需要 rebase fixup**（省掉一批运行时改写），而且不再有"可写的函数指针表"，从结构上**缩小了攻击面**。代价是 dyld 要按新规则读：把每条 32 位值当偏移、`基址 + 偏移` 得到真实入口再调用。

> [!warning] 逆向新二进制找不到 `__mod_init_func`？去看 `__init_offsets`
> 如果在一个较新的 macOS/iOS 二进制里 `otool -s __DATA __mod_init_func` 什么都没 dump 出来，**初始化器很可能在 `__init_offsets` 里**（`otool -s __TEXT __init_offsets` 或 `__DATA_CONST`）。注意它存的是偏移不是指针，dump 出来的 4 字节要 `镜像基址 + 该偏移` 才是初始化函数地址。另：dyld 对 `__init_offsets` 有 4 字节对齐硬要求，未对齐会直接拒绝跑初始化器。

## 实操：用工具查看

### 示例 1：`otool -s` dump 初始化器指针表

`otool -s 段名 节名` 以十六进制 dump 指定节的原始字节；`otool -l ... | grep` 可定位节头：

```bash
otool -s __DATA __mod_init_func /bin/ls          # dump 初始化器指针数组（裸十六进制）
otool -l /bin/ls | grep -A 6 "sectname __mod_init_func"   # 看该节的节头字段
otool -s __DATA __mod_init_func -V /bin/ls        # 部分版本 -V 可符号化部分内容
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__mod_init_func) section
0000000100008040  10 12 00 00 01 00 00 00    ; 小端 → 0x0000000100001210，第 0 个初始化器入口
0000000100008048  84 13 00 00 01 00 00 00    ; 小端 → 0x0000000100001384，第 1 个初始化器入口
0000000100008050  f0 15 00 00 01 00 00 00    ; 小端 → 0x00000001000015f0，第 2 个初始化器入口
```

> 说明：本节 `size = 0x18 = 24` 字节、64 位指针宽 8 字节，故条目数 = `24 / 8 = 3`，正是上面 3 行。每行 8 字节按**小端**还原成一个虚拟地址（已含 rebase 后效果时还要叠加 slide），即 `__TEXT,__text` 里某初始化函数的入口。dyld 会按 `0x...1210 → 0x...1384 → 0x...15f0` 的**数组顺序**依次调用。

### 示例 2：`otool -l` 看节头确认类型为 `S_MOD_INIT_FUNC_POINTERS`

```bash
otool -l /bin/ls | grep -A 9 "sectname __mod_init_func"
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意节头各字段；重点看 `flags` 的类型位与 `reserved` 全 0。

```text
Section
  sectname __mod_init_func
   segname __DATA
      addr 0x0000000100008040
      size 0x0000000000000018      ; 24 字节 → 24/8 = 3 个初始化器
    offset 32832
     align 2^3 (8)                 ; 8 字节对齐（存储值 align=3）
    reloff 0
    nreloc 0
     flags 0x00000009              ; 类型 = S_MOD_INIT_FUNC_POINTERS(0x9)，无属性位
 reserved1 0                       ; 本节不复用 reserved
 reserved2 0
 reserved3 0
```

> 说明：`flags & 0xff = 0x09` 即 `S_MOD_INIT_FUNC_POINTERS`——dyld 正是靠这个类型位认出"本节是初始化器表"并置 `fHasInitializers = true`（见第 2 节）。`reserved1/2/3` 全 0：本节不是符号桩/指针节，不复用 reserved（对比 [[22.Mach-O __stubs节]]）。`align 2^3 (8)` 里 `2^3` 是存储指数、`(8)` 是工具替你算好的实际字节数（见 [[18.Mach-O section]] 对 `align` 的说明）。

### 示例 3：现代 `__init_offsets`（S_INIT_FUNC_OFFSETS）的样子

启用链式 fixups 的二进制里，初始化器可能在 `__init_offsets`（注意段可能是 `__TEXT` 或 `__DATA_CONST`）：

```bash
otool -s __TEXT __init_offsets /path/to/modern_binary
otool -l /path/to/modern_binary | grep -A 9 "sectname __init_offsets"
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意"偏移而非指针"的差别。

```text
Contents of (__TEXT,__init_offsets) section
0000000100004000  10 32 00 00    ; 小端 → 偏移 0x3210，入口 = 镜像基址 + 0x3210
0000000100004004  a0 35 00 00    ; 小端 → 偏移 0x35a0，入口 = 镜像基址 + 0x35a0
```

> 说明：每条目只有 **4 字节**且是**相对偏移**，需 `镜像基址 + 偏移` 才得真实入口——无需 rebase，这正是它能放进只读段、并省去运行时改写的原因（见第 6 节）。对应节头 `flags & 0xff = 0x16`（`S_INIT_FUNC_OFFSETS`）、`align 2^2 (4)`（dyld 强制 4 字节对齐）。

## FAQ

> [!question] `__mod_init_func` 里到底存的是什么？为什么节头不写有几个初始化器？
> 存的是一串**函数指针**，每个指向 `__TEXT,__text` 里的一个初始化函数（C++ 全局对象构造器、`__attribute__((constructor))` 函数等）。节头**不显式存条目数**，而是约定用 `条目数 = 节 size ÷ 指针宽度` 推算（64 位 `/8`、32 位 `/4`）。这与 Mach-O 一贯"用 `size` 推条目数、保持节头紧凑"的设计一致（见 [[18.Mach-O section]]：符号桩节用 `size/reserved2` 同理）。dyld 读节时就按这个公式算出 N，再从第 0 项调到第 N-1 项。

> [!question] 这些函数确切在什么时刻被调用？能在里面用别的库的函数吗？
> 在 `main` **之前**、dyld 完成"映射段 → 加载依赖 → rebase/bind（或链式 fixups）"**之后**被调用，全部跑完才跳 [[09.Mach-O LC_MAIN]]。因为 rebase/bind 已完成、且 dyld 保证"依赖库的初始化器先于依赖者"（自底向上序），所以**可以**安全使用依赖库导出的符号和本镜像的全局量。唯一的雷区是**循环依赖**——此时"依赖在前"无法保证，对方可能尚未初始化（见第 3 节的 warning）。

> [!question] `__mod_init_func`（C++ 构造 / constructor）和 ObjC 的 `+load`，谁先跑？有何区别？
> 区别在**机制**：`__mod_init_func` 由 **dyld 直接读节、直接调指针**；`+load` 由 **ObjC runtime** 通过向 dyld 注册的镜像加载回调驱动（数据来自 [[37.Mach-O __objc_nlclslist节]]）。两者都在 `main` 之前、同一初始化阶段内完成，且都遵循"依赖库先于依赖者"。**精确的相对先后不应被依赖**（随 dyld/runtime 版本可能不同）：稳妥做法是只确信"都在 `main` 前跑、依赖在前"，需要操作 ObjC 类结构就用 `+load`、纯 C/C++ 早期逻辑就用 constructor 或全局对象。详见第 5 节对照表。

> [!question] 我用 `__attribute__((constructor(priority)))` 指定了优先级，dyld 真的按优先级调吗？
> dyld **不直接理解** priority。priority 的作用发生在**链接期**：链接器按 priority 把指针在 `__mod_init_func` 里**排序**（数字越小越靠前，范围一般 `[101,65535]`，不写 priority 的排最后），dyld 运行时只是"**按指针在数组中出现的顺序**"依次调用——于是低数字 priority 的初始化器先跑。注意 priority 只决定**同一镜像内**的顺序；**跨镜像**之间靠依赖关系（自底向上），priority 不参与跨镜像排序。

> [!question] 为什么有的新二进制里 `otool -s __DATA __mod_init_func` 是空的？
> 多半是该二进制启用了**链式 fixups**，初始化器被换成了现代的 **`__init_offsets`（`S_INIT_FUNC_OFFSETS 0x16`）**——它存 32 位相对偏移而非绝对指针，免 rebase、可放只读段（`__TEXT` 或 `__DATA_CONST`），所以 `__DATA,__mod_init_func` 自然为空或不存在。改去 `otool -s __TEXT __init_offsets` 找，并记得 dump 出来的 4 字节是偏移、要 `镜像基址 + 偏移` 才是入口（见第 6 节与示例 3）。

## 与相邻章节的关系

- [[09.Mach-O LC_MAIN]]：`__mod_init_func` 里的初始化器在 dyld 跳转 `LC_MAIN` 指定入口**之前**被全部调用——它是"入口前代码"的来源，`LC_MAIN` 是入口本身。
- [[33.Mach-O __mod_term_func节]]：对称的**终止函数表**（`S_MOD_TERM_FUNC_POINTERS 0xa`），进程退出时调用、顺序通常与初始化相反；`constructor` ↔ `destructor`、`__mod_init_func` ↔ `__mod_term_func` 一一对应。
- [[37.Mach-O __objc_nlclslist节]]：ObjC `+load` 的非惰性类路径——同样在 `main` 前跑，但由 ObjC runtime 而非 dyld 直接驱动，是与本节并列的另一条"入口前"机制（见第 5 节对照）。
- [[14.Mach-O __DATA]]：本节的宿主段——因为指针要 rebase、需可写，故传统住在 `__DATA`；现代 `__init_offsets` 免 rebase 后可迁出到只读段。
- [[18.Mach-O section]]：`section_64` 通用结构与全部节类型表的"说明书"；本节的 `S_MOD_INIT_FUNC_POINTERS (0x9)` 与 `S_INIT_FUNC_OFFSETS (0x16)` 都出自那张类型表。

## 小结

- `__mod_init_func` 是**初始化器函数指针数组**，节类型 `S_MOD_INIT_FUNC_POINTERS (0x9)`；条目来源是 C++ 非平凡全局/静态对象的构造、`__attribute__((constructor))` 函数、框架早期注册逻辑。
- 条目数不显式存储，用 `size ÷ 指针宽度` 推算；指针被 dyld 当作 `void(int argc, char** argv, char** envp, char** apple)`（同 `main` 参数）调用。
- 调用时机：dyld 完成"映射段 → 加载依赖 → rebase/bind（或链式 fixups）"**之后**、跳 [[09.Mach-O LC_MAIN]] **之前**，识别依据是 `flags` 的类型位（命中即 `fHasInitializers = true`）。
- 调用顺序：**同镜像内**按指针在数组中的出现顺序（`constructor(priority)` 靠链接器排序间接生效）；**跨镜像**自底向上、依赖库先于依赖者（循环依赖除外）。
- 因指针需 rebase 故住可写 [[14.Mach-O __DATA]]；与 ObjC `+load`（runtime 驱动、数据在 [[37.Mach-O __objc_nlclslist节]]）是两条不同的"入口前"路径，精确相对先后不应依赖。
- 现代链式 fixups 二进制改用 `__init_offsets`（`S_INIT_FUNC_OFFSETS 0x16`）：存 32 位相对偏移而非绝对指针，免 rebase、4 字节对齐、可放只读段，缩小攻击面——逆向找不到 `__mod_init_func` 时应转看它。
