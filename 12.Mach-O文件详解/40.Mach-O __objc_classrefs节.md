# 详解Mach-O(四十)Mach-O __objc_classrefs节

> [!abstract] TL;DR
> **`__objc_classrefs` 是"类引用表"（class references）**：一张**指针数组**，每一项（64 位 8 字节 / 32 位 4 字节）对应源码里用到的**一个类**。凡是编译期能确定的"对某个类对象的引用"——`[NSString alloc]`、`[MyClass new]`、`NSString.class`、`@encode` 之外的元类访问等——编译器都会在本表里生成一个槽，并把那处代码编译成"对本表某槽的读取"。
> **磁盘上这些槽的值是占位（外部类引用置零、内部类引用记一个待重定位的相对地址）**；镜像加载时由 `dyld` 完成 **fixup**：引用**本镜像定义的类**走 **rebase**（只加 ASLR 滑动偏移），引用**其它库的类**走 **bind**（按符号名 `_OBJC_CLASS_$_Xxx` 在导出库的符号表里查地址并写回）。回填后，槽里就是**真实的、可直接使用的 `Class` 对象指针**，代码读槽即得类对象，喂给 `objc_msgSend` 发类方法消息。
> 它和定义类的 [[36.Mach-O __objc_classlist节]] 正好相对——**`classlist` 记"我定义了哪些类"，`classrefs` 记"我代码里用到了哪些类"**；被引用的类既可能是本镜像自有的，也可能是外部依赖的。它属于 ObjC **四大"引用类"节**（`selrefs`/`classrefs`/`superrefs`/`protorefs`）之一——存的是"对元数据的**引用**"，而不是元数据本体（类本体在 `__objc_data`/`__objc_const`）。因为槽要被加载期改写，它必须住在**可写**段；现代二进制（Xcode 11 / clang-1100 起）已把它搬到加载后转只读的 [[15.Mach-O __DATA_CONST]]。clang 发射时节标记为 `regular,no_dead_strip`，即类型 `S_REGULAR(0x0)` + 属性 `S_ATTR_NO_DEAD_STRIP(0x10000000)`。

## 概述与定位

要理解 `__objc_classrefs` 为什么存在，先看一句最普通的类方法调用：`[NSString stringWithFormat:@"%d", n]`。它在底层是 `objc_msgSend(NSString_的类对象, @selector(stringWithFormat:), …)`——**第一个参数必须是 `NSString` 这个类对象的真实指针**。可编译器在编译你这个 `.o` 时，**根本不知道 `NSString` 类对象运行时落在哪个地址**：`NSString` 由系统库 Foundation 定义，它的最终地址要等到 dyld 把 Foundation 映射进进程、并经 ASLR 随机化之后才确定。本镜像自己定义的类（如 `ViewController`）同理——磁盘上类对象的地址是"基址相对"的，进程加载滑动（slide）后才知道真值。

编译器能做的，只是在 `__objc_classrefs` 里留一个**指向"那个类对象"的指针槽**，作为"这处代码引用了这个类"的占位，并把对该类的引用编译成"对这个槽的读取"。真正把占位换成"真实 `Class` 指针"的工作，推迟到加载期由 **dyld 的 fixup**（rebase / bind）完成——这个**编译期占位、加载期回填**的两段式设计，就是 `__objc_classrefs` 的全部意义。它和 [[35.Mach-O __objc_selrefs节]] 处理 selector 引用是完全平行的思路，只是被引用的对象从"selector 名字串"换成了"类对象"。

把它放到 [[18.Mach-O section.md|节（section）的通用模型]] 里看：`__objc_classrefs` 是一个住在可写数据段的指针数组节。它和 [[35.Mach-O __objc_selrefs节]]、[[41.Mach-O __objc_supperrefs节]]、[[42.Mach-O __objc_protorefs节]] 一道，构成 ObjC 元数据里的**"引用类"四节**——它们都不存元数据本体，只存"指向本体的、需要被加载期修正的指针"。runtime 在 [[36.Mach-O __objc_classlist节]] 等"列表类"节注册类的同期，统一处理这四张引用表。

> [!note] "引用 vs 定义"：`__objc_classrefs` 与 `__objc_classlist` 的分工
> 这是本篇最该分清的一对概念：
> - **`__objc_classlist`（定义方）**：列的是"**本镜像定义了哪些类**"。runtime 在 `_read_images` 遍历它，对每个类调 `readClass` 把类元数据注册进运行时——这是"我向运行时提供的元数据"。
> - **`__objc_classrefs`（引用方）**：列的是"**本镜像代码用到了哪些类**"。每个槽是一个指向类对象的指针，加载期被 dyld 修正为真实 `Class`——这是"我要用到的引用"。
> 一句话：**`classlist` 管"我有什么类"，`classrefs` 管"我用了什么类"**。一个类被定义一次（在它所属镜像的 classlist 里一项），却可以被任意多个镜像、任意多处代码引用（各自 classrefs 里一个槽）。被引用的类**不一定**由本镜像定义——`NSString`、`UIViewController` 这类外部类，只出现在你的 classrefs 里（作为外部符号），不出现在你的 classlist 里。

## 核心原理与字段详解

### 1. 内容布局：一张"指向类对象"的指针数组

`__objc_classrefs` 在文件里就是一段**连续的指针数组**，没有头部、没有计数字段——和所有节一样，**条目数由 `节大小 size ÷ 指针宽度` 推算**（64 位 `size/8`、32 位 `size/4`，参见 [[18.Mach-O section.md|节的 size 与条目数推算]]）。每个槽对应源码里引用到的**一个不同的类**；编译器为每处类引用生成一个槽，多处引用同一个类时会被链接器合并为指向同一目标的槽（即每个被引用类在本表里通常只占一项）。

哪些代码会触发生成一个 classref 槽？凡是编译期能确定"要拿某个类对象"的地方：

- **类方法调用**：`[NSString alloc]`、`[MyClass new]`、`[NSArray array]`——拿类对象当 `objc_msgSend` 的 receiver。
- **`类名.class` / `[类名 class]`**（字面类名）、`NSStringFromClass` 之外的静态类引用。
- **类作为父类被继承**——这通常落在 [[41.Mach-O __objc_supperrefs节]]（`__objc_superrefs`），与 classrefs 平行但专门服务 `[super …]` 与继承链；本表主要是"普通的类对象引用"。

> [!note] 它由编译器/链接器协作生成，不是手写
> Clang 发射类引用时，会把指向类对象的指针放进一个标记为 `regular,no_dead_strip` 的节：等价汇编是 `.section __DATA,__objc_classrefs,regular,no_dead_strip`，槽里的 `.quad`（64 位）指向类对象符号 `_OBJC_CLASS_$_Xxx`。注意这里是 **`regular`（`S_REGULAR`）而非 selrefs 的 `literal_pointers`**——这是 classrefs 与 [[35.Mach-O __objc_selrefs节]] 在 `flags` 上的关键差异（详见下文第 6 节）。同时，对该类对象符号会生成一条**外部 undefined 符号引用**（若类来自其它库）或**内部定义引用**（若类在本镜像），链接器据此决定该槽走 bind 还是 rebase。

### 2. 加载期回填：外部类走 bind、本镜像类走 rebase

镜像被 `dyld` 映射进来后，`__objc_classrefs` 的每个槽都要被修正成真实的 `Class` 指针。这一步**主要由 dyld 完成**（不是 ObjC runtime——后者只在特殊情况下补一刀，见第 3 节），机制取决于"被引用的类来自哪里"：

1. **本镜像定义的类 → rebase（重定位）**：若引用的类就在本镜像的 [[36.Mach-O __objc_classlist节]] 里定义（如你自己的 `ViewController`），磁盘上槽里存的是一个**基于镜像基址的地址**。由于 ASLR 把镜像整体随机滑动了一个 `slide`，dyld 只需给这个地址**加上 slide 偏移**即可指向真实类对象。rebase 不查符号表、只做加法，所以快。重定位信息记录在 [[17.Mach-O LC_DYLD_INFO_ONLY]] 的 rebase 编码（或现代的链式 fixups）里。
2. **其它库定义的类 → bind（绑定）**：若引用的类由别的 dylib 定义（如 Foundation 的 `NSString`、UIKit 的 `UITableView`），磁盘上这个槽是**置零/占位**的——本镜像根本不知道 `NSString` 类对象的地址。dyld 需要按**符号名 `_OBJC_CLASS_$_NSString`** 去导出它的库的符号表里**字符串匹配查地址**，再把查到的真实地址**写回**这个槽。这就是 bind：因为要查符号表，比 rebase 慢。绑定动作由 [[17.Mach-O LC_DYLD_INFO_ONLY]] 里的 **bind opcodes**（`BIND_OPCODE_SET_SYMBOL_TRAILING_FLAGS_IMM` 携带 `_OBJC_CLASS_$_NSString`、`BIND_OPCODE_SET_SEGMENT_AND_OFFSET_ULEB` 指定写哪个槽等）驱动。

> [!note] 一眼区分 rebase 与 bind
> **rebase = "内部地址 + 滑动偏移"**，解决"同一镜像内的自引用"（ASLR 让基址不定，故需加偏移）；**bind = "按符号名跨库查地址再写回"**，解决"引用别的库的符号"。`__objc_classrefs` 里两种都有：自有类槽走 rebase，外部类槽走 bind。这也正是逆向时区分"自有类 vs 外部依赖类"的底层依据（见第 4 节）。`DYLD_PRINT_BINDINGS=1` 环境变量可在运行时打印每一次 bind，形如 `dyld: bind: app:0x1000010D0 = CoreFoundation:_OBJC_CLASS_$_NSArray, *0x1000010D0 = 0x7FFF...`——左边是被写的 classref 槽地址，右边是绑定到的真实类对象地址。

### 3. runtime 的补刀：`_read_images` → `remapClassRef`

dyld 完成 rebase/bind 后，绝大多数 classref 槽已经指向正确的类对象。但 ObjC runtime 在 `_objc_init` → `map_images` → **`_read_images`** 里还有一段"**重映射（remap）类引用**"的逻辑，作为**特殊情况下的补正**（基于 Apple `objc4` 源码）：

```c
// Fix up remapped classes
// Class list and nonlazy class list remain unremapped.
// Class refs and super refs are remapped for message dispatching.
if (!noClassesRemapped()) {
    for (EACH_HEADER) {
        Class *classrefs = _getObjc2ClassRefs(hi, &count);
        for (i = 0; i < count; i++) remapClassRef(&classrefs[i]);
        classrefs = _getObjc2SuperRefs(hi, &count);
        for (i = 0; i < count; i++) remapClassRef(&classrefs[i]);
    }
}
ts.log("IMAGE TIMES: remap classes");
```

逐项拆解：

- **取节**：runtime 用 `_getObjc2ClassRefs(hi, &count)` 拿到当前镜像的 `__objc_classrefs` 节，类型化为 `Class[]`（`count = size / 指针宽度`）。这个访问器由 `objc-file.mm` 里的宏 **`GETSECT(_getObjc2ClassRefs, Class, "__objc_classrefs")`** 生成——**它读的就是名为 `"__objc_classrefs"` 的节**，节名写错就拿不到。`__objc_superrefs` 用并列的 `_getObjc2SuperRefs` 读，同样在这段里被 remap。
- **`remapClassRef(&classrefs[i])`**：对每个槽，计算 `Class newcls = remapClass(*clsref)`，**仅当 `*clsref != newcls` 时**才把 `*clsref = newcls` 写回。`remapClass` 查的是 `remappedClasses` 全局哈希表：若该类没被重映射过，原样返回；若被重映射过（类对象搬过家），返回新地址。
- **为何需要 remap：未来类（future class）/ 类被重分配**：在更早的"发现类"阶段，`readClass` 解析某个类时，其对象指针**可能改变**——当一个 **future class**（懒加载占位类，先只记名字和占位属性、真正数据后置加载）被一个真实类解析、或类被重分配时，类对象会**搬到新地址**。那么之前 dyld 写进 classrefs/superrefs 的"旧地址"就成了悬垂引用，`remapClassRef` 正是把它们改指到"搬家后的活类指针"，保证消息派发命中真类。
- **这段通常不执行**：注释明确说"类列表与非懒加载类列表保持不重映射，只有 class refs 和 super refs 为消息派发而重映射"。绝大多数情况下 `noClassesRemapped()` 为真（没有类被重映射），整个 `if` 被跳过——所以**日常调试里这段几乎不进**。它是为 future class 等边界场景兜底的。

> [!note] dyld 管"大头"、runtime 管"边角"
> 别把 classrefs 的回填全记在 runtime 头上：**真正把每个槽填成真实类指针的是 dyld 的 rebase/bind**（在 ObjC runtime 介入之前就完成了）。`_read_images` 里的 `remapClassRef` 只处理"类对象在加载过程中又搬了家"这种少数情况，是补正而非主流程。这点和 [[35.Mach-O __objc_selrefs节]] 不同——selrefs 的回填（`sel_registerName` 唯一化）是 runtime 的主动作、每次必跑；classrefs 的回填主力是 dyld、runtime 只兜底。

### 4. 逆向价值：`__objc_classrefs` 是"本镜像用到的类清单"

`__objc_classrefs` 直接暴露"**本镜像代码引用了哪些类**"，是逆向分析勾勒模块边界的利器：

- **配合 `__objc_classlist` 区分自有/外部类**：出现在本镜像 `classlist`（定义）里的，是它**自己实现**的类；只出现在 `classrefs`（引用）而不在 `classlist` 里的，是它**依赖的外部类**（来自 Foundation/UIKit/第三方库）。两表一对照，模块的"对外依赖面"一目了然。
- **bind 信息直接给出"引用了哪个库的哪个类"**：每个外部类槽都对应一条 bind 记录，标明符号 `_OBJC_CLASS_$_Xxx` 来自哪个 dylib（如 `UIKit`）。`xcrun dyldinfo -bind` / `dyld_info -fixups` 能把这张"外部类依赖表"直接打出来（见实操示例 3）。
- **快速回答"这段代码在 new 谁、alloc 谁"**：classrefs 表近似于该二进制"用到的类名清单"，结合 `__objc_selrefs`（用到的方法名清单），能快速还原一段代码"对谁发了什么消息"。

> [!note] 架构差异与现代链式 fixups
> ① **指针宽度**：64 位每槽 8 字节、32 位 4 字节，条目数相应用 `size/8` 或 `size/4` 算。
> ② **链式 fixups（chained fixups）**：新版 dyld（`LC_DYLD_CHAINED_FIXUPS`）改变了 rebase/bind 的**编码与遍历机制**（指针以链式编码、由 dyld 统一遍历回填），但"classref 槽 → 真实类对象"的**语义不变**：自有类仍 rebase、外部类仍 bind。
> ③ **段归属变化（Xcode 11 / clang-1100 起）**：`__objc_classrefs`/`__objc_classlist` 等节的默认段从 `__DATA` 改到了 [[15.Mach-O __DATA_CONST]]（详见第 5 节）。老二进制里你会在 `__DATA` 看到它，新二进制里在 `__DATA_CONST`。

### 5. 为什么住在可写段（`__DATA` / `__DATA_CONST`）

理由和 [[35.Mach-O __objc_selrefs节]] 一致：**槽要被加载期回填（rebase/bind 改写成真实 `Class` 指针）**，而代码段 `__TEXT` 是 `r-x`（只读可执行）写不了，所以 classrefs 不能放 `__TEXT`，只能放可写的数据段。

- **传统布局**：放在 `__DATA`（`rw-`），dyld 的 bind/rebase 直接改写即可。
- **现代布局（`__DATA_CONST`）**：自 **clang-1100.0.33.8（Xcode 11）** 起，编译器默认把 `__objc_classrefs`、`__objc_classlist` 等节从 `__DATA` 搬到了 [[15.Mach-O __DATA_CONST]]。`__DATA_CONST` 的特点是"**加载期可写、之后只读**"——dyld 先按链式 fixups 遍历这些指针、完成 rebase/bind 回填，**回填完再把这些页重新保护为只读**。这样既满足"加载期要回填"的写需求，又能在运行期享受只读页的安全收益（防止类指针被篡改去劫持类方法派发）。部分编译产物里，外部类引用还可能经由 `__got`（全局偏移表）间接，绑定后同样只读化。

> [!note] 同一个节，老/新二进制段属不同
> 你会看到同一个 `__objc_classrefs` 节在**老二进制属 `__DATA`、在新二进制属 `__DATA_CONST`**，但语义完全一致（都是"加载期被 rebase/bind 回填的类引用指针数组"）。所以下文 `otool -s` 实操要按你二进制的**实际段名**给（`__DATA` 还是 `__DATA_CONST`），否则会提示找不到该节。

### 6. `flags` 解读：`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`

回到 [[18.Mach-O section.md|节头 flags]] 的视角，clang 发射 `__objc_classrefs` 用的是 `regular,no_dead_strip`，对应 `flags` 典型值 **`0x10000000`**，按 `SECTION_TYPE(0x000000ff)` / `SECTION_ATTRIBUTES(0xffffff00)` 拆开：

- **类型** `0x10000000 & 0xff = 0x00` = **`S_REGULAR`**（普通节）。**注意这与 [[35.Mach-O __objc_selrefs节]] 不同**：selrefs 是 `S_LITERAL_POINTERS(0x5)`（编译器把它当"指向字面量字符串的指针"，链接器可据此对相同字面量做特殊合并），而 classrefs 指向的是**类对象**（不是字面量），故用普通的 `S_REGULAR`。这是两节最容易被混淆的字段差异——同为"引用类"指针数组，节类型却不一样。
- **属性** `0x10000000 & 0xffffff00 = 0x10000000` = **`S_ATTR_NO_DEAD_STRIP`**（禁止死代码消除）。即便链接器静态分析觉得某个 classref"看似没人引用"，也不应删除——因为 ObjC 类常被运行时动态使用（`NSClassFromString`、KVC、归档/反归档、消息转发等），静态可达性分析不可靠。clang 的 `CGObjCMac.cpp` 对 classrefs/superrefs 等 ObjC 元数据节统一打上此标记。

> [!note] `no_dead_strip` 的现实争议
> LLVM 社区里曾有讨论质疑"为什么 ObjC 这些节都标 `no_dead_strip`"——实测中链接器有时仍会移除确实无用的项，该标记并非在所有场景都决定性生效。但**意图很清楚**：保护 ObjC 元数据不被静态死剥，确保运行期动态用到的类引用都还在。逆向时也因此能在 classrefs 里看到"代码路径上虽未直接调用、但被动态引用"的类。

## 实操：用工具查看

### 示例 1：`otool -s __DATA __objc_classrefs` dump 原始指针

`otool -s 段名 节名` 以十六进制 dump 指定节的原始字节。**段名要按你二进制的实际布局给**——现代二进制多在 `__DATA_CONST`，老二进制在 `__DATA`：

```bash
otool -s __DATA __objc_classrefs /path/to/ObjCBinary        # 老布局/部分二进制
otool -s __DATA_CONST __objc_classrefs /path/to/ObjCBinary  # 现代布局（Xcode 11+）
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，**地址/字节均为示意**，实际数值以你机器上的 `otool` 为准。

```text
Contents of (__DATA,__objc_classrefs) section
0000000100009240  00 00 00 00 00 00 00 00      ; classref[0] 磁盘占位 0（外部类，待 bind → NSString）
0000000100009248  10 80 00 00 01 00 00 00      ; classref[1] → 0x100008010（本镜像类，待 rebase → ViewController）
0000000100009250  00 00 00 00 00 00 00 00      ; classref[2] 磁盘占位 0（外部类，待 bind → UITableView）
```

> 说明：左列是该槽自身的虚拟地址（从节 `addr` 起算），右列 8 字节是**小端**指针值。**外部类引用的槽在磁盘上往往是全 0（占位）**，因为本镜像不知道外部类地址，要等加载期 bind 写入；**本镜像类引用的槽**则是一个基于镜像基址的相对地址（如 `0x100008010`），加载期 rebase 时加上 ASLR 滑动偏移。本节大小 `0x18` → 条目数 `0x18 / 8 = 3` 个。**这是磁盘上的状态；进程加载并 fixup 后，三个槽都会被填成真实 `Class` 指针。**

### 示例 2：`otool -ov` 把类引用解析成类名

`otool -ov`（`-o` 解析 ObjC 元数据、`-v` 符号化）会把 classref 直接显示成它指向的类名，比裸十六进制直观得多：

```bash
otool -ov /path/to/ObjCBinary                       # 完整 dump ObjC 段（含 classrefs 解析）
otool -ov /path/to/ObjCBinary | grep -A 3 -i classref   # 只看类引用片段
```

> [!warning] 示例输出为示意
> 数值/地址为构造，仅示意 `otool -ov` 如何把 classref 槽解析回类名。

```text
Contents of (__DATA_CONST,__objc_classrefs) section
0x0000000100009240  _OBJC_CLASS_$_NSString          (external, bind)
0x0000000100009248  0x0000000100008010 ViewController   (in this image, rebase)
0x0000000100009250  _OBJC_CLASS_$_UITableView       (external, bind)
```

> 说明：`otool -ov` 替你把每个槽解析出来——**外部类**显示为符号名 `_OBJC_CLASS_$_NSString`（它来自别的库，靠 bind），**本镜像类**显示为地址 + 类名 `ViewController`（它在本镜像，靠 rebase）。这正是逆向时区分"自有类 vs 外部依赖类"的直观手段：行尾标了 `external` 的是依赖，标了 `in this image` 的是自有。

### 示例 3：`dyldinfo -bind` 查外部类引用的绑定来源

要专门看"哪些 classref 槽是外部类、各绑定到哪个库"，用 `dyldinfo -bind`（新系统用 `dyld_info -fixups`）按节过滤最直接：

```bash
xcrun dyldinfo -bind /path/to/ObjCBinary | grep __objc_classrefs   # 老工具
xcrun dyld_info -fixups /path/to/ObjCBinary | grep __objc_classrefs # 新工具（链式 fixups）
```

> [!warning] 示例输出为示意
> 地址/库名为构造，仅示意 bind 记录如何把 classref 槽关联到外部库的 `_OBJC_CLASS_$_` 符号。

```text
segment   section            address           type    addend dylib     symbol
__DATA    __objc_classrefs   0x0000000100009240 pointer 0      Foundation _OBJC_CLASS_$_NSString
__DATA    __objc_classrefs   0x0000000100009250 pointer 0      UIKit      _OBJC_CLASS_$_UITableView
```

> 说明：每一行就是一个**外部类引用槽**的绑定记录——`address` 是槽地址、`dylib` 是导出该类的库、`symbol` 是类对象符号。**注意只有外部类（bind）会出现在这里**；本镜像自有类走 rebase，不在 `-bind` 输出里（它们出现在 rebase 信息中）。这是"看本镜像依赖了哪些外部类、来自哪些库"的最权威手段。运行期还可用 `DYLD_PRINT_BINDINGS=1 ./ObjCBinary` 实时观察每次绑定。

> [!note] 逆向提醒：从共享缓存抽出的 dylib 可能解析不出名字
> 当一个库被从 **dyld 共享缓存**单独抽取出来时，它的 classref 指针可能指向**抽取后已不在本文件内**的地址（类对象本体还留在共享缓存里）。此时 `otool`/Ghidra 等工具会显示成 `DAT_<address>` 这类裸地址、解析不出类名。要正确解析，需用**感知共享缓存**的工具或在完整缓存环境下分析。

## FAQ

> [!question] `__objc_classrefs` 和 `__objc_classlist` 到底什么关系？为什么要分两节？
> 一个管"引用"、一个管"定义"。**`__objc_classlist` 列"本镜像定义了哪些类"**：runtime 遍历它、对每个类调 `readClass` 注册进运行时，是"我提供的元数据"。**`__objc_classrefs` 列"本镜像代码用到了哪些类"**：每槽是一个指向类对象的指针，加载期被 dyld 修正为真实 `Class`，是"我要用的引用"。一个类只在它所属镜像的 `classlist` 里出现一次（定义），却能被任意多处代码、任意多个镜像引用（各自 `classrefs` 一个槽）。关键差别：**被引用的类不一定由本镜像定义**——`NSString` 只在你的 `classrefs`（作外部符号），不在你的 `classlist`。简记：classlist 是"我登记的类"，classrefs 是"我用到的类"。

> [!question] `[NSString alloc]` 这种调用，在二进制里到底变成了什么？
> 变成**对 `__objc_classrefs` 里某个槽的读取 + 一次 `objc_msgSend`**。编译器为 `NSString` 在 `__objc_classrefs` 建一个槽，把 `[NSString alloc]` 编译成"先加载该 classref 槽拿到 `NSString` 类对象指针，再 `objc_msgSend(那个指针, @selector(alloc))`"。**磁盘上**这个槽是占位（外部类为 0）；**加载后**被 dyld 经 bind（外部类 `_OBJC_CLASS_$_NSString`）或 rebase（本镜像类）填成真实 `Class`。所以运行时这处代码一读槽就拿到可用的类对象。整个过程对源码透明——你写 `[NSString alloc]`，编译期占位、加载期回填替你把它接到真实类上。

> [!question] 为什么外部类靠 bind、本镜像类靠 rebase？两者差在哪？
> 差在"地址是否本镜像已知"。**本镜像类**的对象就在本镜像内，磁盘上能写一个"基于镜像基址的地址"；运行期 ASLR 把镜像整体滑动了 `slide`，dyld 只需给这个地址**加 slide**——这叫 **rebase**，只做加法、不查符号表，快。**外部类**（如 `NSString`）的对象在**别的库**里，本镜像编译时根本不知其地址，磁盘上只能把槽**置零**、并记一条"我要 `_OBJC_CLASS_$_NSString` 这个符号"的请求；运行期 dyld 按**符号名去导出库的符号表字符串匹配**查到真实地址再写回——这叫 **bind**，要查表，比 rebase 慢。所以 `__objc_classrefs` 里两种槽并存：自有类 rebase、外部类 bind，这也是逆向区分自有/外部类的底层依据。

> [!question] `__objc_classrefs` 为什么放可写段，而不是和代码一样放只读 `__TEXT`？现代怎么兼顾安全？
> 因为它的槽**必须在加载期被改写**（rebase/bind 成真实 `Class` 指针），而 `__TEXT` 只读写不了。传统上放 `rw-` 的 `__DATA`；自 Xcode 11（clang-1100）起，编译器默认把它搬到 [[15.Mach-O __DATA_CONST]]——这是"**加载期可写、fixup 完转只读**"的折中：dyld 用链式 fixups 把这些类指针 rebase/bind 回填完后，把页重新保护成只读，**既满足回填的写需求，又让运行期享受只读页的防篡改收益**（防止有人改写类指针去劫持类方法派发）。所以同一个 classref 节在老二进制属 `__DATA`、新二进制属 `__DATA_CONST`，语义一致。

> [!question] `__objc_classrefs` 和 [[35.Mach-O __objc_selrefs节]] 都是"引用类指针数组"，有什么不同？
> 思路相同（编译期占位、加载期回填的指针数组），但三处关键差异：①**指向对象不同**：selrefs 槽初值指向 `__objc_methname` 的**名字字符串**，classrefs 槽指向**类对象**。②**回填机制不同**：selrefs 由 **runtime 主动 `sel_registerName` 唯一化**并回填（每次必跑）；classrefs 主力是 **dyld 的 rebase/bind**，runtime 的 `remapClassRef` 只在 future class 等边界情况兜底。③**节类型不同**：selrefs 是 `S_LITERAL_POINTERS(0x5)`（指向字面量字符串），classrefs 是 `S_REGULAR(0x0)`（指向类对象，非字面量）；两者都带 `S_ATTR_NO_DEAD_STRIP`。它们和 [[41.Mach-O __objc_supperrefs节]]、[[42.Mach-O __objc_protorefs节]] 共同构成"引用类"四节。

## 与相邻章节的关系

- [[36.Mach-O __objc_classlist节]]：定义的类（"我定义了哪些类"），与本表"引用"（"我用了哪些类"）正好相对。两表对照可区分自有/外部类。
- [[41.Mach-O __objc_supperrefs节]]：并列的"引用类"节，槽指向**父类**、加载期绑定为父类 `Class`，专门服务 `[super …]` 调用与继承链；与本表同样在 `_read_images` 的 `remapClassRef` 里被一并 remap。
- [[35.Mach-O __objc_selrefs节]]：并列的"引用类"节，槽指向 selector 名字串、回填为全局唯一 `SEL`。本篇与它的设计高度平行，差异见上文 FAQ。
- [[42.Mach-O __objc_protorefs节]]：并列的"引用类"节，槽指向协议、回填为唯一 `Protocol *`。
- [[15.Mach-O __DATA_CONST]]：现代（Xcode 11+）类引用槽 fixup 后只读化的归宿——回填的写需求与运行期只读防篡改在这里调和。
- [[17.Mach-O LC_DYLD_INFO_ONLY]]：承载 rebase/bind 信息（或被现代链式 fixups 取代）的加载命令；外部类的 bind opcodes 就编码在这里。
- [[18.Mach-O section.md|18.Mach-O section]]：本节 `flags`（`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`）、`size÷指针宽度` 推算条目数、可写段与回填的通用模型，都在那篇的字段说明书里。

## 小结

- `__objc_classrefs` 是 **类引用表**：一张指针数组，每槽对应代码引用的**一个类**，编译期由 `[Class …]`/类方法调用生成；条目数 = `size ÷ 指针宽度`。clang 发射为 `regular,no_dead_strip`，`flags` 典型 `0x10000000`（`S_REGULAR` + `S_ATTR_NO_DEAD_STRIP`）。
- **加载期回填以 dyld 为主**：引用**本镜像类**走 **rebase**（加 ASLR 滑动偏移），引用**外部类**走 **bind**（按符号 `_OBJC_CLASS_$_Xxx` 跨库查地址写回，磁盘上槽为占位 0）。runtime 的 `_read_images` → `remapClassRef` 只在 future class/类重分配等边界情况补正。
- **引用 vs 定义**：与 [[36.Mach-O __objc_classlist节]]（"我定义了哪些类"）相对，本表是"我用了哪些类"；被引用类不一定由本镜像定义。逆向时两表对照可快速区分自有/外部类、勾勒模块依赖边界。
- **为何在可写段**：槽要被加载期回填，故放可写 `__DATA`；现代二进制（Xcode 11+）放 [[15.Mach-O __DATA_CONST]]（fixup 后转只读），兼顾"加载期可写"与"运行期防篡改"。
- **四大引用节**：`selrefs`/`classrefs`/`superrefs`/`protorefs` 同型（加载期回填的指针数组），区别在被指本体与回填机制；classrefs 与 selrefs 在"回填主力（dyld vs runtime）"和"节类型（`S_REGULAR` vs `S_LITERAL_POINTERS`）"上有别。
