# 详解Mach-O(四)Mach-O LC_SEGMENT / LC_SEGMENT_64

> [!abstract] TL;DR
> **`LC_SEGMENT_64` 是 Mach-O 里最核心的加载命令**：它告诉内核"把文件的哪一段字节，映射到进程虚拟地址空间的哪个位置，占多大、给什么读写执行权限"。每出现一条段命令，进程地址空间里就多出一块带统一权限的连续区域。
> 命令体是定长的 `segment_command_64`（64 字节固定头），其后紧跟 `nsects` 个 `section_64`（每个 80 字节）节描述；`cmdsize = 72 + 80 * nsects`。`vmaddr/vmsize` 描述**内存侧**，`fileoff/filesize` 描述**文件侧**（两者可不等，差额由内核零填充），`maxprot/initprot` 描述**权限**（`VM_PROT_READ=1`/`WRITE=2`/`EXECUTE=4` 的位掩码），`flags` 携带 `SG_*` 段标志。
> 进程地址空间的整体布局（`__PAGEZERO`/`__TEXT`/`__DATA`/`__DATA_CONST`/`__LINKEDIT` 各落在哪、各是什么权限）正是由一组 `LC_SEGMENT_64` 拼出来的。32 位对应 `LC_SEGMENT`（`segment_command`，56 字节头 + 68 字节 `section`），布局同构、仅位宽不同；当代 Apple 设备（arm64、x86_64）一律使用 64 位变体。

## 概述与定位

段（Segment）是 Mach-O 中**直接映射到虚拟内存的最大单位**，而 `LC_SEGMENT_64`（32 位为 `LC_SEGMENT`）就是描述这一映射的加载命令。内核 `exec` 与 `dyld` 把所有段命令处理完，进程的内存骨架就立起来了——可以把每条段命令理解成一行"把磁盘上 `[fileoff, fileoff+filesize)` 这段字节，搬到虚拟地址 `[vmaddr, vmaddr+vmsize)`，权限设为 `initprot`，最高可提到 `maxprot`"的搬运指令。

它之所以是"最核心"的命令，原因有三：

1. **数量最多、占比最大**。一个典型可执行文件里，`LC_SEGMENT_64` 往往是出现次数最多的命令（`__PAGEZERO`/`__TEXT`/`__DATA_CONST`/`__DATA`/`__LINKEDIT` 至少五条），且每条都拖着一串节描述，体量上主导整个 Load Commands 区。
2. **决定进程内存布局**。其余命令大多是"在某段里指一个位置"（符号表在 `__LINKEDIT`、入口在 `__TEXT`），它们的前提是段已经映射好；段命令是这一切的地基。
3. **承载安全语义**。代码与数据分段、`__PAGEZERO` 拦空指针、`__DATA_CONST` 启动后只读化（`SG_READ_ONLY`）、FairPlay 加密段（`SG_PROTECTED_VERSION_1`）——Mach-O 的内存级防护几乎都落在段这一层。

本篇聚焦"段命令"这一**描述结构**（字段、标志、布局、解析）；段的语义模型与各具体段的职责见 [[11.Mach-O Segments]] 及其后续分篇（[[12.Mach-O __PAGEZERO]]、[[13.Mach-O __TEXT]]、[[14.Mach-O __DATA]]、[[15.Mach-O __DATA_CONST]]、[[16.Mach-O __LINKEDIT]]）。

> [!note] 段（Segment）与节（Section）的区别
> 这是初学最易混的一对概念。**段**是映射与权限的单位（页对齐、有 `vmaddr/initprot`），是写给**内核/dyld** 看的；**节**是逻辑内容的单位（`__text`/`__cstring`/`__data` 等），是写给**链接器**看的、用于组织数据。一个段里装多个节，同段内的节共享该段的权限。段命令 = 段头 + 它的节头清单——本篇讲段头，节头见 [[18.Mach-O section]]。

## 核心原理与字段详解

### 1. `segment_command_64` 完整字段（64 位）

来自 `<mach-o/loader.h>`，逐字段注释如下：

```c
struct segment_command_64 {   /* for 64-bit architectures */
    uint32_t  cmd;            // LC_SEGMENT_64 (0x19)
    uint32_t  cmdsize;        // 本命令总长 = sizeof(segment_command_64)
                              //            + nsects * sizeof(section_64)
                              //            = 72 + 80 * nsects
    char      segname[16];    // 段名，定长 16 字节、不足补 \0，如 "__TEXT"
                              // Apple 约定：双下划线 + 全大写
    uint64_t  vmaddr;         // 段映射到的虚拟地址（内存侧起点）
    uint64_t  vmsize;         // 段在内存中占用的大小（内存侧长度）
    uint64_t  fileoff;        // 段数据在文件中的偏移（文件侧起点）
    uint64_t  filesize;       // 从文件映射的字节数（文件侧长度）
    vm_prot_t maxprot;        // 允许的最大内存保护（权限上限）
    vm_prot_t initprot;       // 加载后的初始内存保护
    uint32_t  nsects;         // 段内节（section_64）的数量
    uint32_t  flags;          // 段标志，见下文 SG_* 表
};
```

字段在文件里的精确偏移（共 72 字节）：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `cmd` | uint32_t | 4 | 固定为 `LC_SEGMENT_64`（`0x19`） |
| 4 | `cmdsize` | uint32_t | 4 | `72 + 80*nsects`，遍历步长 |
| 8 | `segname` | char[16] | 16 | 段名，定长、`\0` 补足 |
| 24 | `vmaddr` | uint64_t | 8 | 段虚拟地址 |
| 32 | `vmsize` | uint64_t | 8 | 段内存大小 |
| 40 | `fileoff` | uint64_t | 8 | 段文件偏移 |
| 48 | `filesize` | uint64_t | 8 | 从文件映射大小 |
| 56 | `maxprot` | vm_prot_t(int32) | 4 | 最大保护 |
| 60 | `initprot` | vm_prot_t(int32) | 4 | 初始保护 |
| 64 | `nsects` | uint32_t | 4 | 节数量 |
| 68 | `flags` | uint32_t | 4 | 段标志 |

> [!note] `vm_prot_t` 是什么
> `vm_prot_t` 在 `<mach/vm_prot.h>` 中定义为有符号 32 位整数（`typedef int vm_prot_t;`），所以 `maxprot`/`initprot` 各占 4 字节、布局上等价于 `int32_t`。它是一组位掩码，见第 4 节。

### 2. `segment_command` 完整字段（32 位）

32 位变体结构同构、仅地址/大小字段降为 32 位（固定头 56 字节）：

```c
struct segment_command {      /* for 32-bit architectures */
    uint32_t  cmd;            // LC_SEGMENT (0x1)
    uint32_t  cmdsize;        // = 56 + 68 * nsects（68 = sizeof(section)）
    char      segname[16];    // 段名
    uint32_t  vmaddr;         // 段虚拟地址（32 位）
    uint32_t  vmsize;         // 段内存大小（32 位）
    uint32_t  fileoff;        // 段文件偏移（32 位）
    uint32_t  filesize;       // 从文件映射大小（32 位）
    vm_prot_t maxprot;        // 最大保护
    vm_prot_t initprot;       // 初始保护
    uint32_t  nsects;         // 节数量
    uint32_t  flags;          // 段标志
};
```

| 维度 | `LC_SEGMENT`（32 位） | `LC_SEGMENT_64`（64 位） |
|---|---|---|
| `cmd` 值 | `0x1` | `0x19` |
| 命令结构 | `segment_command` | `segment_command_64` |
| 固定头大小 | **56** 字节 | **72** 字节 |
| 地址/大小字段 | `uint32_t`（4B×4） | `uint64_t`（8B×4） |
| 后跟节结构 | `section`（**68** 字节/个） | `section_64`（**80** 字节/个） |
| `cmdsize` 公式 | `56 + 68 * nsects` | `72 + 80 * nsects` |

> [!note] 架构差异速记
> 两者布局**同构**，差别仅在四个地址/大小字段的位宽（32→64）以及由此带来的固定头/节头尺寸。当代 Apple 设备（arm64、x86_64）一律使用 64 位变体；`LC_SEGMENT`（32 位）只在老的 i386 / armv7 二进制里出现。一个 FAT（universal）二进制里可能 i386 切片用 `LC_SEGMENT`、x86_64 切片用 `LC_SEGMENT_64`，解析时要先看 Header 的 `magic`/`cputype` 决定按哪套读（见 [[02.Mach-O文件头]]）。

### 3. 内存侧 vs 文件侧：四个核心字段

段命令用两对字段分别描述"内存里长什么样"和"文件里存了多少"：

- `vmaddr` / `vmsize`：段在**进程虚拟内存**中的起点与大小（内存侧）。
- `fileoff` / `filesize`：段数据在**磁盘文件**中的起点与大小（文件侧）。

映射规则：内核把文件 `[fileoff, fileoff+filesize)` 这段字节，`mmap` 到内存 `[vmaddr, vmaddr+vmsize)` 的开头。**`vmsize` 必须 ≥ `filesize`**；当 `vmsize > filesize` 时，多出来的内存由内核以零页"按需填充"（zero-fill on demand），不占文件空间。这是 Mach-O 节省体积的关键机制。

**`vmsize` 与 `filesize` 不等的几种典型情形：**

| 情形 | 关系 | 原因 |
|---|---|---|
| `__PAGEZERO` | `filesize = 0`，`vmsize` 巨大（4GB） | 纯占位的不可访问区，无任何文件数据，仅为拦截空指针保留地址空间（见 [[12.Mach-O __PAGEZERO]]） |
| 含 `__bss`/`__common` 的 `__DATA` | `vmsize > filesize` | 未初始化数据（`__bss`）只记大小、不存内容，运行时零填充（见 [[28.Mach-O __bss节]]） |
| 页对齐填充 | `vmsize ≥ filesize`（向页大小取整） | 段必须按页对齐，末尾不足一页的部分被对齐填充撑大 |
| `__LINKEDIT` | `vmsize ≈ filesize`（都向页取整） | 链接器元数据是实打实的文件数据，内存/文件大小基本相等 |

> [!note] `fileoff = 0` 的 `__TEXT`
> 你会发现 `__TEXT`（甚至 `__PAGEZERO`）的 `fileoff` 常为 0。这是因为 `__TEXT` 段从文件最开头映射，**Mach-O 的 Header 和 Load Commands 本身就落在 `__TEXT` 段范围内**——它们也要被一起映射进内存，所以 `__TEXT` 的 `filesize` 把头部一并算进去了。`__PAGEZERO` 因为 `filesize=0`，`fileoff` 填 0 只是占位、不读任何字节。

### 4. 内存保护 `maxprot` / `initprot` 与 `VM_PROT_*`

`vm_prot_t` 是位掩码（`<mach/vm_prot.h>`）：

| 宏 | 值 | 含义 |
|---|---|---|
| `VM_PROT_NONE` | `0x0` | 无任何权限 |
| `VM_PROT_READ` | `0x1` | 可读 |
| `VM_PROT_WRITE` | `0x2` | 可写 |
| `VM_PROT_EXECUTE` | `0x4` | 可执行 |

按位组合就得到常见取值：`0x1` = `r--`、`0x3` = `rw-`、`0x5` = `r-x`、`0x7` = `rwx`、`0x0` = `---`。

- `initprot`：段加载后的**初始**权限。例如 `__TEXT` 为 `r-x`（5）、`__DATA` 为 `rw-`（3）。
- `maxprot`：该段允许被 `mprotect` 提升到的**最高**权限上限。运行时只能在 `maxprot` 范围内调整，越界会失败。

权限以**页**为粒度施加（一段一套权限、整页生效），这正是 Mach-O 把代码、只读数据、可写数据**分段存放**的根本原因——便于按页保护、缩小可写∩可执行的攻击面（W^X 原则）。

**常见段的权限取值（数值可能随架构/链接器版本略有差异）：**

| 段 | `initprot` | `maxprot` | 文本 | 说明 |
|---|---|---|---|---|
| `__PAGEZERO` | `0x0` | `0x0` | `---` | 不可访问，拦截 NULL 解引用 |
| `__TEXT` | `0x5` | `0x5` 或 `0x7` | `r-x` | 代码 + 只读常量；现代加固倾向 `maxprot=0x5` 禁止运行时改可写 |
| `__DATA_CONST` | `0x3` | `0x3` | `rw-` | 初始可写以便 dyld 写 fixups，启动后经 `SG_READ_ONLY` 降为只读 |
| `__DATA` | `0x3` | `0x3` 或 `0x7` | `rw-` | 可变数据（COW 共享） |
| `__LINKEDIT` | `0x1` | `0x1` | `r--` | 链接器元数据，纯只读 |

> [!warning] `maxprot=0x7`（rwx）的安全含义
> 历史上 `__TEXT`/`__DATA` 的 `maxprot` 常给 `0x7`（允许运行时把页改成 rwx），这给 JIT 也给攻击者留了口子。现代 macOS/iOS 在 Hardened Runtime、`__TEXT` 强制只读等加固下，倾向把 `maxprot` 收紧到与 `initprot` 一致，并通过专门的 `__DATA_CONST` 段把"启动后不再变"的指针挪出可写区。逆向看到 `maxprot` 与 `initprot` 不一致时，留意它暗示的运行时权限变更能力。

### 5. 段标志 `flags`（`SG_*`）完整表

`flags` 字段携带段级标志（按位或），均定义于 `<mach-o/loader.h>`：

| 标志 | 值 | 含义 |
|---|---|---|
| `SG_HIGHVM` | `0x1` | 该段文件内容对应 VM 空间的**高地址**部分，低地址部分零填充（仅用于 core dump 里的栈段） |
| `SG_FVMLIB` | `0x2` | 该段是固定地址 VM 库（Fixed VM Library）分配的内存，供链接器做重叠检查（古老机制，已基本废弃） |
| `SG_NORELOC` | `0x4` | 该段内**没有任何东西被重定位、也没有任何东西重定位到它**，因此可被安全替换而无需重定位 |
| `SG_PROTECTED_VERSION_1` | `0x8` | 该段被**加密保护**（version 1 加密格式）。典型如 App Store 分发时 FairPlay 对 `__TEXT` 的加密；运行时由内核解密页 |
| `SG_READ_ONLY` | `0x10` | 该段在**初始化完成后应被置为只读**。`mmap` 时可读写，dyld 处理完 fixups 后用 `mprotect` 把它降为只读——这正是 `__DATA_CONST` 的实现机制 |

> [!note] 历史值陷阱
> 极老的 NeXTStep 时代头文件曾把 `SG_NORELOC` 定义为 `0x3`，与现代 `loader.h` 的 `0x4` 不同。当代工作一律以现行 `loader.h`（`SG_NORELOC=0x4`、`SG_PROTECTED_VERSION_1=0x8`、`SG_READ_ONLY=0x10`）为准。绝大多数普通段的 `flags` 为 `0x0`，段标志在实践中用得不多，但 `SG_READ_ONLY` 与 `SG_PROTECTED_VERSION_1` 在分析现代二进制与加壳样本时很关键。

### 6. 段头之后的 `nsects` 个 `section_64`

段头紧接着排布 `nsects` 个 `section_64`（64 位，每个 80 字节），描述段内每个节。它们**物理上连续跟在段头后面**，并且其总大小已计入段头的 `cmdsize`——所以解析器读完一个段命令时，自然就把它的全部节头一起读完了。

```c
struct section_64 {          /* for 64-bit architectures */
    char     sectname[16];   // 节名，如 "__text"、"__cstring"
    char     segname[16];    // 所属段名，冗余回填，如 "__TEXT"
    uint64_t addr;           // 节的虚拟地址
    uint64_t size;           // 节大小（字节）
    uint32_t offset;         // 节数据在文件中的偏移
    uint32_t align;          // 对齐（2 的幂的指数，如 4 表示 16 字节对齐）
    uint32_t reloff;         // 重定位项在文件中的偏移
    uint32_t nreloc;         // 重定位项数量
    uint32_t flags;          // 节类型与属性（S_* / S_ATTR_*）
    uint32_t reserved1;      // 保留（间接符号索引等）
    uint32_t reserved2;      // 保留（计数或项大小等）
    uint32_t reserved3;      // 保留（仅 section_64 有，对齐用）
};
```

32 位 `section`（68 字节）少一个 `reserved3`，其余同构。

- `__TEXT` 段里典型有 `__text`（代码）、`__stubs`、`__cstring`、`__const` 等节。
- `__DATA` 段里典型有 `__data`、`__bss`、`__la_symbol_ptr`、`__objc_*` 等节。
- 同一段内的所有节**共享该段的内存保护**——这也是为什么"只读字符串"`__cstring` 要放进 `r-x` 的 `__TEXT`、而"可写指针表"要放进 `rw-` 的 `__DATA`。

节头的逐字段含义、`flags` 里的节类型（`S_REGULAR`/`S_ZEROFILL`/`S_CSTRING_LITERALS` 等）与属性位详见 [[18.Mach-O section]]；各具体节（[[19.Mach-O __text节]]、[[20.Mach-O __cstring节]]、[[27.Mach-O __data节]]、[[28.Mach-O __bss节]] 等）在系列后续分篇展开。

### 7. `cmdsize` 与命令遍历

`LC_SEGMENT_64` 复用所有加载命令的统一头 `load_command{ cmd, cmdsize }`（见 [[03.Mach-O加载命令]]）。遍历 Load Commands 时靠累加 `cmdsize` 逐条跳转，对段命令而言：

- **`cmdsize` 必须等于 `72 + 80 * nsects`**（32 位为 `56 + 68 * nsects`），且为指针大小整数倍。两者对不上，要么 `nsects` 被篡改、要么命令越界——健壮解析器会据此校验。
- 段命令把它的节头清单"算进自己的 `cmdsize`"，所以遍历到下一条命令时是 `ptr += cmdsize`，会自动跳过本段的全部节头，不会把节头误当成下一条命令。

### 8. 页对齐与地址空间布局

段必须按**页**对齐映射，页大小取决于架构：

- **x86_64**：4KB 页（`0x1000`）。
- **arm64（Apple Silicon / 现代 iOS 设备）**：**16KB 页（`0x4000`）**。这意味着 arm64 上每个段的 `vmaddr` 与 `fileoff`（对需要映射的段）按 16KB 对齐，段尾不足 16KB 的部分被填充——这是 arm64 二进制段间常出现较大空隙的原因。

典型 arm64 可执行文件的地址布局（自低向高）：`__PAGEZERO`（`vmaddr=0`，`vmsize=0x100000000` 即 4GB）→ `__TEXT`（`vmaddr=0x100000000`，`r-x`）→ `__DATA_CONST` → `__DATA`（`rw-`）→ `__LINKEDIT`（`r--`，文件末尾、高地址）。`__TEXT` 从 `0x100000000` 起，正好接在 4GB 的 `__PAGEZERO` 之后。

> [!note] ASLR slide 与 `vmaddr`
> 文件里的 `vmaddr` 是"理想加载地址"。开启 ASLR（地址空间布局随机化）后，内核会给所有段统一加上一个随机的 **slide**，实际加载地址 = `vmaddr + slide`。内核在加载时按段的 `initprot` 识别段类型（`initprot==0 && maxprot==0 && vmaddr==0` → `__PAGEZERO`；含 `VM_PROT_EXECUTE` → `__TEXT`；含 `VM_PROT_WRITE` → `__DATA`），并校验 `vmaddr + vmsize + slide` 不溢出。`__DATA_CONST` 里之所以需要 fixups（启动时由 dyld 写回真实地址），正是因为指针值要叠加这个 slide。

### 9. 版本演进：`__DATA_CONST` 与 `SG_READ_ONLY` 只读化

早期 Mach-O 只有可写的 `__DATA`，里面混着"启动后就不再改"的指针（如 GOT、非惰性符号指针 `__got`/`__nl_symbol_ptr`、`__const`、Objective-C 的 `__objc_classlist` 等）。这些指针在 dyld 完成 rebase/bind 后值就固定了，但因为住在可写段里，攻击者一旦获得写原语就能改写它们劫持控制流。

现代工具链把这类"启动后只读"的数据拆进独立的 **`__DATA_CONST`** 段，并给它打上 **`SG_READ_ONLY`（0x10）** 标志：

1. `mmap` 时 `__DATA_CONST` 以 `rw-`（`initprot=0x3`）映射，让 dyld 能写入 fixups；
2. dyld 处理完该段所有 rebase/bind/chained-fixups 后，依据 `SG_READ_ONLY` 调用 `mprotect` 把整段降为只读 `r--`；
3. 此后任何写入都会触发段错误，GOT 劫持等攻击被堵死。

这是 macOS 10.15 / iOS 13 一带引入、并随链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）普及的硬化措施。详见 [[15.Mach-O __DATA_CONST]] 与 [[21.Mach-O __const节]]。另一个相关标志 `SG_PROTECTED_VERSION_1（0x8）` 则用于 App Store FairPlay 对 `__TEXT` 的加密保护，运行时由内核按页解密。

### 示例 1：`otool -l` 看单个段命令

```bash
otool -l /bin/ls | grep -A 12 LC_SEGMENT_64   # 看所有段命令的头
otool -lv /bin/ls                              # -v 把 maxprot 等显示成符号名
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text

      cmd LC_SEGMENT_64
  cmdsize 552                 ; = 72 + 80*6
  segname __TEXT
   vmaddr 0x0000000100000000  ; 接在 4GB __PAGEZERO 之后
   vmsize 0x0000000000004000  ; 16KB（arm64 一页）
  fileoff 0                   ; __TEXT 从文件开头映射（含 Header）
 filesize 16384
  maxprot 0x00000005   (r-x)  ; 现代加固：上限即 r-x，不允许改可写
 initprot 0x00000005   (r-x)
   nsects 6                   ; 其后跟 6 个 section_64
    flags 0x0
```

> 说明：`segname __TEXT`、`initprot (r-x)` 表明这是只读可执行的代码段；`nsects 6` 说明其后还跟着 6 个节描述；`cmdsize 552 = 72 + 80*6` 自洽。

   vmaddr 0x0                vmaddr 0x100008000
   vmsize 0x100000000        vmsize 0x4000

   vmaddr 0x10000c000        vmaddr 0x100010000
   vmsize 0x8000             vmsize 0x1000
  fileoff 49152             fileoff 49152

### 示例 4：`vmmap` 看运行时实际权限

进程跑起来后，`__DATA_CONST` 已被 dyld 降为只读——用 `vmmap` 能看到与文件里 `initprot` 不同的**当前**权限：

```bash
vmmap <pid> | grep -E "__TEXT|__DATA"
```

> [!warning] 示例输出为示意

```text
__TEXT        100000000-100004000   [   16K] r-x/r-x  SM=COW  /bin/ls
__DATA_CONST  100008000-10000c000   [   16K] r--/rw-  SM=COW  ; 当前 r--，上限 rw-
__DATA        10000c000-100014000   [   32K] rw-/rw-  SM=COW
```

> 说明：`r--/rw-` 形如"当前权限/最大权限"——`__DATA_CONST` 当前是 `r--`（dyld 已 `mprotect` 降级），但 `maxprot` 仍是 `rw-`，正好印证 `SG_READ_ONLY` 的"启动后只读"机制。文件静态视图（`otool`）看不到这一步，必须看运行时的 `vmmap`。

## FAQ

> [!question] `vmsize` 为什么能比 `filesize` 大？反过来可以吗？
> 可以大、不可以小。`vmsize ≥ filesize` 是硬约束。大出来的部分（未初始化数据 `__bss`、页对齐填充、`__PAGEZERO` 的纯占位）由内核**零填充、按需分页**，不占文件字节，从而显著缩小文件体积。若 `vmsize < filesize`，多出的文件数据无处映射，属于畸形文件，解析器应拒绝。

> [!question] `maxprot` 和 `initprot` 有什么区别？为什么 `__DATA_CONST` 的 `initprot` 是 rw- 却最终只读？
> `initprot` 是加载后的**初始**权限，`maxprot` 是运行时可经 `mprotect` 提升到的**上限**。`__DATA_CONST` 初始给 `rw-` 是为了让 dyld 能写入 rebase/bind 后的真实指针；写完后 dyld 依据段的 `SG_READ_ONLY` 标志调用 `mprotect` 把它降成 `r--`。所以静态文件里看到的是 `rw-`，运行时 `vmmap` 看到的是 `r--`——两套视图都对，分别是"出厂设置"与"启动后实际"。

> [!question] 一条段命令的 `cmdsize` 怎么算？为什么不能随便填？
> `cmdsize = 72 + 80 * nsects`（64 位）或 `56 + 68 * nsects`（32 位），即段头加上全部节头的总长，且须为指针大小整数倍。它是遍历 Load Commands 的"步长"：解析器读完一条就 `ptr += cmdsize` 跳下一条。`cmdsize` 与 `nsects` 对不上，会让解析器要么把节头误读成下一条命令、要么越界——这是常见的解析器攻击面，健壮实现必须校验 `cmdsize == 72 + 80*nsects` 且不越过命令区边界。

> [!question] `__PAGEZERO` 的 `vmsize` 为什么是 4GB？它占内存吗？
> 64 位可执行文件的 `__PAGEZERO` 通常 `vmaddr=0`、`vmsize=0x100000000`（4GB）、`filesize=0`、`prot=---`。它把低 4GB 整段地址空间标成"不可读写执行"，这样任何对 NULL 或小整数指针的解引用都会立刻段错误，挡住一大类空指针漏洞；同时把 32 位地址范围整体"圈走"，避免 64 位代码误用 32 位地址。它**不占物理内存、也不占文件**——只是一段保留的、永远不会被实页支撑的虚拟地址。详见 [[12.Mach-O __PAGEZERO]]。

## 小结

- `LC_SEGMENT_64`（32 位 `LC_SEGMENT`）描述一个段从文件到虚拟内存的映射，是搭建进程内存布局的**核心命令**，复用统一的 `load_command` 头。
- 命令体是定长段头（64 位 72 字节 / 32 位 56 字节），其后紧跟 `nsects` 个节头（`section_64` 80 字节 / `section` 68 字节），`cmdsize = 头 + 全部节头`。
- `vmaddr/vmsize`（内存侧）与 `fileoff/filesize`（文件侧）可不相等，约束是 `vmsize ≥ filesize`，差额由内核零填充（`__PAGEZERO`/`__bss`/页对齐）。
- `initprot/maxprot` 是 `VM_PROT_*`（R=1/W=2/X=4）位掩码，以页为粒度施加，是代码/数据分段存放的根本动因；`maxprot` 给运行时权限调整留上限。
- `flags` 携带 `SG_*` 段标志：`SG_READ_ONLY(0x10)` 实现 `__DATA_CONST` 启动后只读、`SG_PROTECTED_VERSION_1(0x8)` 用于 FairPlay 加密、`SG_NORELOC(0x4)` 标记无重定位。
- arm64 用 16KB 页对齐、x86_64 用 4KB；ASLR 给所有段统一加 slide，`__DATA_CONST` 的 fixups 即为叠加该 slide。
