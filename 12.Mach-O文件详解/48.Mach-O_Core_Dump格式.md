# 详解Mach-O(四十八)Mach-O Core Dump格式

> [!abstract] TL;DR
> **Core Dump（核心转储）是进程崩溃瞬间的内存快照**：操作系统把进程的全部虚拟内存段、所有线程的寄存器状态、崩溃时的信号信息打包成一个文件，供事后（post-mortem）调试。
> 在 Apple 平台上，Core Dump 同样采用 **Mach-O 格式**，文件类型为 **`MH_CORE`（magic = `0xFEEDFACF`/`0xFEEDFACE`，filetype = `4`）**。它的加载命令区别于可执行文件：没有 `LC_LOAD_DYLIB`、没有 `LC_MAIN`，取而代之的是大量 **`LC_SEGMENT`/`LC_SEGMENT_64`**（转储每个内存区间）、**`LC_THREAD`**（保存线程寄存器/浮点/向量状态）以及可选的 **`LC_NOTE`**（附加元数据，如崩溃原因、内核版本）。
> 掌握 `MH_CORE` 的内部结构，能让你在没有符号服务器的离线环境、内核崩溃现场或法证分析场景中，用 `lldb`/`otool` 直接从原始字节中提取崩溃时的调用栈、寄存器值与内存内容——这是 macOS/iOS 逆向与取证的核心技能。

## 概述与定位

Core Dump 在软件开发与取证分析中扮演"时间胶囊"角色：进程崩溃的那一刻，操作系统将其冻结并以文件形式保存下来，让调试者事后穿越回崩溃现场。macOS/iOS 并未引入专有格式，而是复用了 Mach-O 容器，仅改变文件类型字段与加载命令集合。

这一设计的优势在于：

- **工具链统一**：`otool`、`nm`、`lldb`、`dwarfdump` 等现有工具无须修改即可解析 Core 文件。
- **格式自描述**：加载命令携带了段大小、地址、线程数量等全部布局信息，解析器只需按序读取即可重建进程地址空间视图。
- **与 ELF Core 对称**：功能上几乎一一对应，但结构细节差异显著（详见 ELF 对比一节）。

> [!note] 与普通 Mach-O 的关键区别
> 普通可执行文件的 `LC_SEGMENT` 描述"文件里的数据如何映射到虚拟地址"；而 `MH_CORE` 的 `LC_SEGMENT` 描述的是"进程运行期某个虚拟内存区间的内容"，数据直接附于文件中。因此 Core 文件通常**体积巨大**（等于进程驻留内存的大小），且**不可执行**（没有任何代码段权限需求，仅供读取）。

## 核心原理与字段详解

### 1. 文件头：`MH_CORE` 类型

`MH_CORE` 的文件头与普通 Mach-O 完全一致，差异只在 `filetype` 字段：

```c
// <mach-o/loader.h>
struct mach_header_64 {
    uint32_t magic;       // 0xFEEDFACF（64位）或 0xFEEDFACE（32位）
    cpu_type_t cputype;   // CPU_TYPE_ARM64 / CPU_TYPE_X86_64 …
    cpu_subtype_t cpusubtype;
    uint32_t filetype;    // MH_CORE = 4  ← 关键区分字段
    uint32_t ncmds;       // 加载命令总数
    uint32_t sizeofcmds;  // 加载命令区总字节数
    uint32_t flags;       // MH_CORE 通常为 0
    uint32_t reserved;    // 64位专有保留字段
};
```

`filetype` 的其他常见值对比：

| filetype | 十进制 | 含义 |
|---|---|---|
| `MH_EXECUTE` | 2 | 可执行文件 |
| `MH_DYLIB` | 6 | 动态库 |
| `MH_CORE` | 4 | Core Dump |
| `MH_KEXT_BUNDLE` | 11 | 内核扩展 |

### 2. `LC_SEGMENT_64`：内存段转储

Core 文件里的 `LC_SEGMENT_64` 与普通 Mach-O 共用同一结构体，但语义有本质不同：

```c
// <mach-o/loader.h>
struct segment_command_64 {
    uint32_t cmd;           // LC_SEGMENT_64 = 0x19
    uint32_t cmdsize;
    char     segname[16];   // Core 里通常为空字符串，或填进程原始段名
    uint64_t vmaddr;        // ★ 进程运行时该段的虚拟起始地址
    uint64_t vmsize;        // ★ 该段的虚拟大小（含 BSS 零页）
    uint64_t fileoff;       // Core 文件内的数据偏移（0 表示该段没有实际数据）
    uint64_t filesize;      // Core 文件中实际存储的字节数（≤ vmsize）
    vm_prot_t maxprot;      // 最大内存保护（原始权限）
    vm_prot_t initprot;     // 初始内存保护
    uint32_t nsects;        // Core 里通常为 0（段内无节结构）
    uint32_t flags;         // SG_READ_ONLY 等
};
```

关键细节：

- **`segname` 通常为空**：Core 文件里转储的段不再携带语义名称，调试器通过 `vmaddr` 与原始二进制的段地址对应来重建符号。
- **`filesize < vmsize` 的情形**：BSS 段（全零初始化的数据）、未访问的匿名内存映射可能被省略（`filesize = 0`），节省空间；调试器遇到 `filesize = 0` 的段时会用零填充该地址范围。
- **`maxprot`/`initprot`**：保留了崩溃时的内存权限，帮助调试器判断哪些区域是代码（`rx`）、哪些是可写数据（`rw`）。

**典型段布局示意**：

```text

Load command 0
      cmd LC_SEGMENT_64
```

### 3. `LC_THREAD`：线程状态快照

`LC_THREAD` 是 Core Dump 中最关键的加载命令，它保存了崩溃瞬间每个线程的完整 CPU 寄存器状态：

```c
// <mach-o/loader.h>
struct thread_command {
    uint32_t cmd;        // LC_THREAD = 0x4
    uint32_t cmdsize;
    // 后接可变长度的 (flavor, count, state) 三元组数组
    // uint32_t flavor;
    // uint32_t count;
    // <arch_thread_state> state;  // 大小 = count × sizeof(uint32_t)
};
```

**ARM64 线程状态（`ARM_THREAD_STATE64`，flavor = 6）**：

```c
// <mach/arm/thread_status.h>
struct arm_thread_state64_t {
    uint64_t x[29];   // x0–x28 通用寄存器
    uint64_t fp;      // x29 帧指针
    uint64_t lr;      // x30 链接寄存器（返回地址）
    uint64_t sp;      // x31 栈指针
    uint64_t pc;      // 程序计数器（崩溃时的指令地址）
    uint32_t cpsr;    // 处理器状态寄存器
    uint32_t __pad;
};
// count = ARM_THREAD_STATE64_COUNT = sizeof(arm_thread_state64_t)/sizeof(uint32_t)
```

**x86_64 线程状态（`x86_THREAD_STATE64`，flavor = 4）**：

```c
// <mach/i386/thread_status.h>
struct x86_thread_state64_t {
    uint64_t rax, rbx, rcx, rdx;
    uint64_t rdi, rsi, rbp, rsp;
    uint64_t r8, r9, r10, r11, r12, r13, r14, r15;
    uint64_t rip;     // 崩溃时的指令指针
    uint64_t rflags;
    uint64_t cs, fs, gs;
};
```

一个 `LC_THREAD` 命令可携带**多个** `(flavor, count, state)` 三元组，例如同时包含通用寄存器状态 + 浮点/向量寄存器状态（`ARM_NEON_STATE64` / `x86_FLOAT_STATE64`）。多线程进程的 Core 文件会有多条 `LC_THREAD`，每条对应一个线程。

**`LC_UNIXTHREAD` 与 `LC_THREAD` 的区别**：

| 命令 | cmd 值 | 历史用途 |
|---|---|---|
| `LC_THREAD` | `0x4` | Core Dump 中使用；不暗示任何入口点 |
| `LC_UNIXTHREAD` | `0x5` | 早期可执行文件中用于指定程序入口（已被 `LC_MAIN` 取代）|

在 Core 文件里，`LC_THREAD` 纯粹是"状态快照"容器，不涉及执行语义。

### 4. `LC_NOTE`：可扩展元数据

`LC_NOTE`（cmd = `0x31`）是 Mach-O 2013 年后引入的通用扩展槽，在 Core Dump 中用于附加崩溃上下文信息：

```c
// <mach-o/loader.h>
struct note_command {
    uint32_t cmd;           // LC_NOTE = 0x31
    uint32_t cmdsize;       // 通常 = sizeof(note_command) = 24
    char     data_owner[16]; // 所有者标识字符串（空字符补全）
    uint64_t offset;        // 注记数据在 Core 文件中的偏移
    uint64_t size;          // 注记数据的字节大小
};
```

**常见 `data_owner` 值**：

| `data_owner` | 内容格式 | 用途 |
|---|---|---|
| `"addrable bits"` | 结构体（版本 + 地址位数）| ARM64 有效地址位数（39/48/52位 TBI/PAC/LA57 等）|
| `"all image infos"` | dyld `dyld_all_image_infos` 副本 | 加载的所有 dylib 路径与 load address |
| `"build version"` | 版本号结构 | OS/平台版本，辅助 dsym 匹配 |
| `"kern ver str"` | 内核版本 C 字符串 | 取证时记录系统版本 |
| `"crash info"` | 崩溃描述结构 | 信号号、崩溃地址、进程名 |
| `"xpc bootstrap"` | XPC 引导信息 | 沙箱容器路径等 |

`LC_NOTE` 的内容格式不在 POSIX 或 Mach-O 标准中规定，属于 Apple 私有扩展；`lldb` 内置了对上述 `data_owner` 的解析支持。

### 5. 进程地址空间的完整性

一个典型的 Core Dump 包含进程所有**驻留**（resident）内存区间的段记录：

- **代码段**（原始可执行文件 + 所有已加载 dylib 的 `__TEXT`）
- **数据段**（`__DATA`、`__DATA_CONST`、堆、BSS）
- **栈区**（每个线程一个独立的匿名映射区间）
- **特殊映射**（`__PAGEZERO`、dyld 共享缓存区域、`mmap` 文件映射）

**被省略的区域**（`filesize = 0`）：

- 只读且可从原始文件重建的代码页（`__TEXT` 段在某些内核版本下会省略以减小 Core 体积）
- 全零的匿名页（BSS、从未访问的栈末尾）
- dyld 共享缓存的只读部分（可从 `/System/Library/dyld/` 恢复）

调试器（`lldb`）处理 `filesize = 0` 的段时，优先从原始二进制文件补充内容（需要 `target.exec-search-paths` 或手动 `target symbols add`）。

## 实操：`otool` 与 `lldb` 分析 Core

### 步骤1：生成测试 Core（macOS）

```bash
# 方法一：系统生成（需开启 core dump 功能）
ulimit -c unlimited               # 允许生成 core
./crash_me                        # 运行会崩溃的程序
ls /cores/                        # macOS 把 core 放在 /cores/ 目录

# 方法二：对运行中进程强制生成（不终止进程）
gcore -o /tmp/myapp.core <PID>

# 方法三：lldb 内生成
lldb ./myapp
(lldb) run
# 等待崩溃，或手动 Ctrl+C
(lldb) process save-core /tmp/myapp.core
```

### 步骤2：`otool` 查看 Core 结构

```bash
# 查看文件头（确认 filetype = MH_CORE）
otool -h /cores/core.12345
# 期望输出：
# Mach header
# magic      cputype  cpusubtype  ...  filetype  ncmds  sizeofcmds  flags
# 0xfeedfacf 16777228 0           ...  4         102    10704       0x00000000
#                                      ↑ MH_CORE

# 列出所有加载命令（段 + 线程 + note）
otool -l /cores/core.12345 | head -200

# 只看 LC_THREAD（线程状态）
otool -l /cores/core.12345 | grep -A 5 "LC_THREAD"

# 只看 LC_NOTE（元数据）
otool -l /cores/core.12345 | grep -A 6 "LC_NOTE"

# 统计各类加载命令数量
otool -l /cores/core.12345 | grep "      cmd " | sort | uniq -c | sort -rn
```

> [!warning] 输出为示意
> 实际地址、ncmds 数量以你环境为准。典型 Core 文件可能有 80~200 条 `LC_SEGMENT_64`，对应进程加载的所有 dylib 与匿名映射。

### 步骤3：`lldb` 加载 Core 分析崩溃现场

```bash
# 加载可执行文件 + Core（lldb 自动匹配 UUID）
lldb ./myapp -c /cores/core.12345

# 或先启动 lldb 再加载
lldb
(lldb) target create --core /cores/core.12345

# 若二进制不在原路径，手动指定
(lldb) target create /path/to/myapp
(lldb) target core /cores/core.12345
```

**lldb 核心分析命令**：

```bash
# 查看崩溃时的线程列表（每条 LC_THREAD 对应一个条目）
(lldb) thread list

# 查看崩溃线程的调用栈
(lldb) thread backtrace
# 或缩写
(lldb) bt

# 查看所有线程的栈（取证时很有用）
(lldb) bt all

# 查看崩溃时的寄存器（对应 LC_THREAD 里的 arm_thread_state64_t）
(lldb) register read
(lldb) register read --all   # 含浮点/向量寄存器

# 查看崩溃时某个内存地址（从 Core 文件的对应段读取）
(lldb) memory read 0x16b3f0000
(lldb) x/32xb 0x16b3f0000    # 十六进制 32 字节

# 查看崩溃时的本地变量（需调试符号）
(lldb) frame variable

# 查看崩溃信号信息（从 LC_NOTE "crash info" 提取）
(lldb) process status
```

### 步骤4：从 `LC_NOTE` 提取 dylib 加载信息

`LC_NOTE "all image infos"` 记录了崩溃瞬间所有已加载 dylib 的路径和 slide，在没有系统符号的情况下非常关键：

```bash
# lldb 自动解析 all image infos
(lldb) image list
# 输出：[  0] 8A3F... 0x100000000 /usr/bin/myapp
#        [  1] 2B1C... 0x1979e0000 /usr/lib/libc++.dylib
#        ...（所有已加载 dylib，含 slide 后的基地址）

# 手动计算 ASLR slide
(lldb) target modules dump sections
# 找到 __TEXT vmaddr 对比 LC_NOTE 里记录的加载地址，差值即 slide
```

### 步骤5：提取崩溃现场的关键信息（取证脚本示意）

```python
#!/usr/bin/env python3
# 用 lief 或 macholib 解析 Core 文件，提取线程 PC 值
import struct, sys

CORE_PATH = sys.argv[1]

MH_CORE         = 4
LC_THREAD       = 0x4
ARM_THREAD_STATE64 = 6
ARM_THREAD_STATE64_COUNT = 68  # sizeof(arm_thread_state64_t)/4

with open(CORE_PATH, 'rb') as f:
    data = f.read()

# 解析文件头（64位大端按需调整）
magic, cputype, cpusubtype, filetype, ncmds, sizeofcmds, flags, _ = \
    struct.unpack_from('<IIIIIIII', data, 0)

assert filetype == MH_CORE, f"Not a core dump! filetype={filetype}"
assert magic == 0xFEEDFACF, "Only 64-bit little-endian supported"

offset = 32  # sizeof(mach_header_64)
thread_id = 0

for _ in range(ncmds):
    cmd, cmdsize = struct.unpack_from('<II', data, offset)
    if cmd == LC_THREAD:
        pos = offset + 8
        while pos < offset + cmdsize:
            flavor, count = struct.unpack_from('<II', data, pos)
            pos += 8
            if flavor == ARM_THREAD_STATE64:
                # x0-x28(29个), fp, lr, sp, pc, cpsr
                regs = struct.unpack_from(f'<{count}I', data, pos)
                x = [struct.unpack_from('<Q', data, pos + i*8)[0] for i in range(29)]
                fp  = struct.unpack_from('<Q', data, pos + 29*8)[0]
                lr  = struct.unpack_from('<Q', data, pos + 30*8)[0]
                sp  = struct.unpack_from('<Q', data, pos + 31*8)[0]
                pc  = struct.unpack_from('<Q', data, pos + 32*8)[0]
                cpsr= struct.unpack_from('<I', data, pos + 33*8)[0]
                print(f"Thread {thread_id}: PC=0x{pc:016x} SP=0x{sp:016x} "
                      f"LR=0x{lr:016x} FP=0x{fp:016x}")
            pos += count * 4
        thread_id += 1
    offset += cmdsize

print(f"\nTotal threads: {thread_id}")
```

## 与 ELF Core 格式对比

ELF 和 Mach-O 的 Core Dump 在设计目标上完全相同，但结构上有若干实质差异：

| 维度 | Mach-O `MH_CORE` | ELF Core（Linux）|
|---|---|---|
| **格式容器** | Mach-O（复用 `mach_header`/`load_command`）| ELF（`Elf64_Ehdr` + `PT_NOTE` + `PT_LOAD`）|
| **内存段记录** | `LC_SEGMENT_64`（每段一条加载命令）| `PT_LOAD` 程序头（类似，但无段名）|
| **线程状态** | `LC_THREAD`（flavor + count + state 三元组）| `PT_NOTE` 中的 `NT_PRSTATUS`/`NT_PRPSINFO` |
| **元数据附加** | `LC_NOTE`（data_owner 命名空间）| `PT_NOTE`（`NT_FILE`/`NT_SIGINFO` 等）|
| **dylib 信息** | `LC_NOTE "all image infos"` | `/proc/<pid>/maps` 的快照（`NT_FILE`）|
| **信号信息** | `LC_NOTE "crash info"`（私有格式）| `NT_SIGINFO`（`siginfo_t` 结构体）|
| **内核版本** | `LC_NOTE "kern ver str"`（字符串）| `NT_UTSNAME`（`struct utsname`）|
| **节结构** | `LC_SEGMENT` 内 `nsects=0`（无节）| 无对应概念（ELF Core 只有段）|
| **文件大小优化** | `filesize=0` 省略只读/零页 | 同，`PT_LOAD` 的 `p_filesz=0` |
| **工具支持** | `lldb`、`otool`、`dwarfdump`、`vmmap` | `gdb`、`eu-readelf`、`crash`、`lldb` |
| **压缩支持** | 无原生压缩（macOS 用 `compresscore`）| 部分 Linux 发行版支持压缩（`zstd`）|

**关键设计哲学差异**：

- ELF Core 把所有元数据塞进一个 `PT_NOTE` 段，内部用 "note" 条目分类；Mach-O 则用顶层加载命令分层（`LC_THREAD`、`LC_NOTE` 各司其职），更符合 Mach-O 的"加载命令即意图"设计哲学。
- Mach-O 的 `LC_THREAD` 明确区分 flavor（通用寄存器 vs 浮点 vs 向量），对多指令集扩展（PAC、SVE/SME）有更好的可扩展性；ELF 则依赖 `NT_PRFPREG`/`NT_ARM_VFP` 等扩展 note 类型。
- ELF Core 是 POSIX 标准规范的一部分（部分），理论上跨 OS 可移植；Mach-O Core 是 Apple 私有格式，`LC_NOTE` 的内容全部是私有结构体。

## 安全性与正确使用

### Core Dump 的信息泄露风险

Core Dump 是进程内存的完整副本，意味着：

- **堆上的明文密钥、密码、令牌**都会被转储进文件。
- **加密内存区域**（如 `mlock` 保护的内存）在某些内核配置下仍会被 dump。
- **Keychain 内容**若被解密后放入堆，同样会出现在 Core 中。

**生产环境防护措施**：

```bash
# 禁止进程生成 core（setrlimit）
ulimit -c 0

# 或在代码中设置
#include <sys/resource.h>
struct rlimit rl = { .rlim_cur = 0, .rlim_max = 0 };
setrlimit(RLIMIT_CORE, &rl);

# macOS 额外：com.apple.security.cs.allow-dyld-environment-variables
# 开启代码签名的 Hardened Runtime 后，未授权进程无法 attach/core-dump
```

**iOS 平台差异**：iOS 设备上的 App 无法生成标准 Core Dump（沙箱限制）；崩溃由系统捕获，以 `.ips`（JSON 格式）存储在 `/var/mobile/Library/Logs/CrashReporter/`，可通过 `plutil` 和 `atos` 手动符号化，也可由 Xcode Organizer 自动处理。

### 逆向分析的合法边界

- 分析**自己开发的程序**的 Core Dump：无限制，是正常调试手段。
- 分析**第三方 App** 的 Core Dump：在越狱设备上可行，但受 App 的用户协议约束。
- 在**法证取证**场景（司法授权下）分析 Core：合法，Core Dump 是重要数字证据形式。
- **转储他人进程**（无 `task_for_pid` 授权）：违反 macOS 安全策略，系统会拒绝（`kern_return_t = KERN_PROTECTION_FAILURE`）；macOS 的 Hardened Runtime + SIP 阻止未授权进程 attach。

### 调试符号匹配

Core 文件与二进制通过 **UUID**（`LC_UUID`）匹配：

```bash
# 查看 Core 中记录的主程序 UUID（从 LC_NOTE "all image infos" 解析）
lldb ./myapp -c /cores/core.12345
(lldb) image list -u     # 列出各镜像的 UUID

# 用 dwarfdump 查 dSYM 的 UUID（确保版本匹配）
dwarfdump --uuid MyApp.dSYM/Contents/Resources/DWARF/MyApp

# 手动添加符号文件
(lldb) target symbols add /path/to/MyApp.dSYM
```

UUID 不匹配时，`lldb` 能读取内存，但无法符号化地址；此时可用 `atos` 手动偏移计算：

```bash
# 从 image list 找到 myapp 的 load address（含 slide）
# 设 slide = 0x10000000
atos -o MyApp.dSYM/Contents/Resources/DWARF/MyApp \
     -l 0x10000000 \
     0x10000000 + <PC 减去 slide>
```

## 小结

- **`MH_CORE`（filetype = 4）** 是 Core Dump 在 Mach-O 格式中的身份标识，共享所有 Mach-O 工具链的支持。
- **`LC_SEGMENT_64`** 转储进程每个虚拟内存区间的字节内容；`filesize = 0` 表示该区间被省略（节省空间），调试器会用原始二进制补充。
- **`LC_THREAD`** 以 `(flavor, count, state)` 三元组保存每个线程的完整寄存器快照（ARM64 的 `arm_thread_state64_t` 或 x86_64 的 `x86_thread_state64_t`），是 `bt`/`register read` 命令的数据来源。
- **`LC_NOTE`** 提供可扩展的元数据插槽，`data_owner` 字段标识内容类型（`"all image infos"`、`"crash info"`、`"kern ver str"` 等），`lldb` 内置解析。
- **与 ELF Core 的关键差异**：Mach-O 用顶层加载命令分类（语义明确），ELF 用 `PT_NOTE` 内部条目（更紧凑）；功能等价，结构不同。
- **安全**：Core 文件是进程内存的全量副本，包含明文密钥等敏感信息，生产环境应通过 `setrlimit(RLIMIT_CORE, 0)` 或 Hardened Runtime 禁止生成；分析他人进程需合法授权。
