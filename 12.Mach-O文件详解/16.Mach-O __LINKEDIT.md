# 详解Mach-O(十六)Mach-O __LINKEDIT

> [!abstract] TL;DR
> **`__LINKEDIT` 是 Mach-O 里一个特殊的"被指向的容器段"**：它只读（`r--`）、位于文件最尾部、**自身不含任何节**（`nsects == 0`），命令体就只有那 72 字节的段头。它存放链接器与 `dyld` 运行所需的**全部元数据**：符号表（`nlist_64`）、字符串表、间接符号表，dyld 的 rebase/bind/export 字节码或链式 fixups，函数起始表、Data-in-Code 标注、代码签名 blob 等。
> 这些数据不由 `__LINKEDIT` 自己描述，而是由一组加载命令（`LC_SYMTAB`/`LC_DYSYMTAB`/`LC_DYLD_INFO_ONLY`/`LC_FUNCTION_STARTS`/`LC_DATA_IN_CODE`/`LC_CODE_SIGNATURE`/`LC_DYLD_CHAINED_FIXUPS`/`LC_DYLD_EXPORTS_TRIE`…）**以"文件偏移 + 大小"（`symoff`/`stroff`、`dataoff`/`datasize`、`*_off`/`*_size`）直接指入**，把分散的元数据集中在文件尾部、统一以只读映射。可以把 `__LINKEDIT` 理解成一块"公共数据池"，各 LC 像一张张"门牌"，每张门牌写着"我的数据从文件第 X 字节起、长 Y 字节"。
> 三条硬性约束贯穿全篇：① 它**必须是最后一个段**（`dyld` 会拒绝在 `__LINKEDIT` 之后还有段数据的二进制）；② 内部各块**必须连续、有序**（`dyld` 有 underrun/overrun 校验）；③ **代码签名覆盖它前面的所有内容、并把签名本身放在 `__LINKEDIT` 的最末端**。`strip` 主要削减的就是这里的符号表与字符串表——去掉调试与多余符号能显著减小体积，且不影响 `__TEXT`/`__DATA` 的运行逻辑。

## 概述与定位

如果说 `__TEXT`/`__DATA` 是"程序本体"，`__LINKEDIT` 就是"装配与维护手册"：它不参与任何运行期计算逻辑（CPU 永远不会跳进 `__LINKEDIT` 取指令、也不会把它当业务数据读写），却是**链接、加载、符号化、签名校验**的唯一依据。`dyld` 启动一个镜像时，做的第一批工作——rebase（按 ASLR slide 平移指针）、bind（把外部符号解析成真实地址）、应用链式 fixups、校验代码签名——所读的全部输入数据都躺在 `__LINKEDIT` 里。

它在整个文件里的角色非常独特，和前面讲过的 `__PAGEZERO`/`__TEXT`/`__DATA`/`__DATA_CONST`（见 [[11.Mach-O Segments]]）有一个本质区别：

- `__TEXT`/`__DATA` 这类段是**自描述**的——段头之下挂着 `nsects` 个 `section_64` 节头，每个节头自带 `addr`/`size`/`offset`，段自己就把内部结构讲清楚了（节头通用字段见 [[18.Mach-O section]]）。
- `__LINKEDIT` 是**被描述**的——它 `nsects == 0`，段头之下**没有任何节头**。它内部装了什么、每块从哪开始、有多长，**完全由别的加载命令说了算**。段头只负责圈出"文件 `[fileoff, fileoff+filesize)`、内存 `[vmaddr, vmaddr+vmsize)`、权限 `r--`"这一整块地皮，地皮内部怎么划分由各 LC 的偏移字段决定。

因此本篇的主线不是"讲一个段头"（段头字段已在 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 讲透），而是讲清楚一件事：**`__LINKEDIT` 是众多加载命令（见 [[03.Mach-O加载命令]]）数据的物理归宿，它如何被这些 LC 用文件偏移"瓜分"，以及围绕它的三条铁律（最后一个段、内部连续有序、签名覆盖在前置于末）从何而来、为何如此**。

> [!note] "段"与"容器"的双重身份
> `__LINKEDIT` 仍然是一个标准的 `LC_SEGMENT_64`（或 32 位 `LC_SEGMENT`）描述的段，拥有完整的 `segname`/`vmaddr`/`vmsize`/`fileoff`/`filesize`/`maxprot`/`initprot`/`flags` 字段，只是 `nsects` 恒为 0、`initprot`/`maxprot` 恒为 `0x1`（`r--`）。它的"容器"身份不来自段结构本身，而来自"被一堆 LC 用偏移指入"这一**约定**。换句话说，把哪些字节算作 `__LINKEDIT`，是段头说了算；这些字节内部是符号表还是签名，是各 LC 说了算。两套视图叠在同一块文件区域上。

## 核心原理与字段详解

### 1. 一个"被指向"的容器段：`nsects == 0` 的本质

`__LINKEDIT` 的特别之处在于：它没有自己的节，而是被一组加载命令用文件偏移"瓜分"。回顾段头结构（完整字段见 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]）：

```c
struct segment_command_64 {
    uint32_t  cmd;            // LC_SEGMENT_64 (0x19)
    uint32_t  cmdsize;        // 因 nsects=0，cmdsize 恰好 = 72（仅段头，无节头）
    char      segname[16];    // "__LINKEDIT"
    uint64_t  vmaddr;         // 映射到的虚拟地址（接在 __DATA 之后的高地址）
    uint64_t  vmsize;         // 内存占用（向页大小取整）
    uint64_t  fileoff;        // 在文件中的起始偏移（靠近文件末尾）
    uint64_t  filesize;       // 从文件映射的字节数（= 内部所有元数据块之和，再页对齐）
    vm_prot_t maxprot;        // 0x1（r--）
    vm_prot_t initprot;       // 0x1（r--）
    uint32_t  nsects;         // 0 ← 关键：无任何 section_64 节头
    uint32_t  flags;          // 通常 0x0
};
```

`nsects == 0` 带来两个直接结论：

1. **`cmdsize == 72`**（32 位为 56）。一般段的 `cmdsize = 72 + 80*nsects`，`__LINKEDIT` 因 `nsects=0`，命令体就只剩那 72 字节段头，后面不跟任何 `section_64`。解析器读到这条命令、`ptr += 72` 就直接跳到下一条 LC 了。
2. **段内结构对段头不可见**。`__TEXT` 能告诉你"我里面有 `__text` 在偏移 A、`__cstring` 在偏移 B"，因为它有节头；`__LINKEDIT` 的段头只说"我从文件 `fileoff` 起、长 `filesize`"，至于这 `filesize` 字节里前 200 字节是 rebase 字节码、接着是符号表、最后是签名——**段头一无所知，全靠下面这张对照表里的各个 LC 用各自的偏移字段去指**。

可以打个比方：`__TEXT` 是一栋"有楼层平面图的写字楼"（节头就是平面图），`__LINKEDIT` 是一块"空地皮"，段头只圈了地界，地皮上盖了哪些房子、各占多大，要去问持有各自地契（偏移字段）的租户（各 LC）。

### 2. 完整的"哪个 LC 在 `__LINKEDIT` 放什么"对照表

这是本篇的核心。下表把"指入 `__LINKEDIT` 的所有常见加载命令"与"它放进去的数据"逐一对应，并标出它**用哪个偏移字段**去指。注意两类偏移字段：

- **专用结构**（`LC_SYMTAB`/`LC_DYSYMTAB`/`LC_DYLD_INFO_ONLY`）有自己定制的多对 `off`/`size` 字段；
- **通用结构 `linkedit_data_command`**（`LC_FUNCTION_STARTS`/`LC_DATA_IN_CODE`/`LC_CODE_SIGNATURE`/`LC_DYLD_CHAINED_FIXUPS`/`LC_DYLD_EXPORTS_TRIE` 等一大批）统一只有一对 `dataoff`/`datasize`。

| 加载命令 | 在 `__LINKEDIT` 中存放的数据 | 指入用的偏移字段 | 结构类型 |
|---|---|---|---|
| [[05.Mach-O LC_SYMTAB]] | **符号表**（`nlist`/`nlist_64` 数组）+ **字符串表**（符号名，NUL 结尾） | `symoff`/`nsyms`（符号表）、`stroff`/`strsize`（字符串表） | `symtab_command`（专用） |
| [[06.Mach-O LC_DYSYMTAB]] | **间接符号表**（指向符号表的索引数组，供 `__got`/`__la_symbol_ptr`/`__nl_symbol_ptr` 用），以及历史的目录表/模块表/重定位项 | `indirectsymoff`/`nindirectsyms`、`tocoff`、`modtaboff`、`extreloff`、`locreloff`… | `dysymtab_command`（专用） |
| [[17.Mach-O LC_DYLD_INFO_ONLY]] | **rebase / bind / weak-bind / lazy-bind / export** 五段字节码（dyld 的压缩重定位与绑定信息） | `rebase_off`/`rebase_size`、`bind_off`/`bind_size`、`weak_bind_off`/`weak_bind_size`、`lazy_bind_off`/`lazy_bind_size`、`export_off`/`export_size` | `dyld_info_command`（专用） |
| `LC_DYLD_CHAINED_FIXUPS` | **链式 fixups** 数据（`dyld_chained_fixups_header` 起头，含 rebase+bind 的链表式编码；macOS 12 / iOS 15+ 取代 `LC_DYLD_INFO_ONLY` 的 rebase/bind） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_DYLD_EXPORTS_TRIE` | **导出符号 trie**（与旧 `export` 同款 trie 编码，链式 fixups 时代把导出信息搬到此独立命令） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_FUNCTION_STARTS` | **函数起始地址表**（ULEB128 增量压缩的函数入口偏移列表，供回溯/符号化/崩溃解析） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_DATA_IN_CODE` | **Data-in-Code 标注**（代码段中内嵌的数据区间，如 ARM 跳转表/字面量池，反汇编器据此跳过这些"伪指令"字节） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_CODE_SIGNATURE` | **代码签名 blob**（CMS 签名 + Code Directory 哈希；置于 `__LINKEDIT` 最末端，覆盖它前面的一切，见第 6 节） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_SEGMENT_SPLIT_INFO` | 共享缓存拆分信息（dyld shared cache 构建用） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_DYLIB_CODE_SIGN_DRS` | 依赖库的代码签名 Designated Requirements | `dataoff`/`datasize` | `linkedit_data_command`（通用） |
| `LC_LINKER_OPTIMIZATION_HINT` | 链接器优化提示（LOH，供 ld 做指令级优化） | `dataoff`/`datasize` | `linkedit_data_command`（通用） |

> [!note] `linkedit_data_command`：一个结构，十几条命令共用
> 上表里大半命令共享同一个极简结构（`<mach-o/loader.h>`）：
> ```c
> struct linkedit_data_command {
>     uint32_t cmd;       // LC_CODE_SIGNATURE / LC_FUNCTION_STARTS / LC_DATA_IN_CODE /
>                         // LC_DYLD_CHAINED_FIXUPS / LC_DYLD_EXPORTS_TRIE / LC_SEGMENT_SPLIT_INFO …
>     uint32_t cmdsize;   // 固定 16（四个 uint32）
>     uint32_t dataoff;   // 数据在 __LINKEDIT 中的文件偏移（相对当前 slice 起点）
>     uint32_t datasize;  // 数据字节数
> };
> ```
> 它的语义非常直白：**这块 blob 从文件第 `dataoff` 字节开始、占 `datasize` 字节**，且这段区间必然落在 `__LINKEDIT` 的 `[fileoff, fileoff+filesize)` 之内。这种"一个通用门牌结构 + `cmd` 区分用途"的设计，让 Apple 后续新增元数据（如链式 fixups、导出 trie）时无需发明新结构，复用 `linkedit_data_command` 即可，命令解析器也只需认得这一个 16 字节布局。

> [!note] 专用结构 vs 通用结构，偏移都相对谁？
> 无论 `symoff`/`stroff`、`indirectsymoff`，还是 `dataoff`，它们都是**相对当前架构 slice（Mach-O Header）起点**的文件偏移，不是相对 `__LINKEDIT.fileoff` 的局部偏移。所以解析时直接 `slice_base + symoff` 就能定位符号表；并且这些偏移一定 ≥ `__LINKEDIT.fileoff`、其末端 ≤ `__LINKEDIT.fileoff + __LINKEDIT.filesize`，否则就是越界（见第 5 节 dyld 的 underrun/overrun 校验）。

### 3. 为什么位于文件尾部、且只读（`r--`）

`__LINKEDIT` 通常是最后一个段，紧贴文件末尾；其 `initprot`/`maxprot` 恒为 `0x1`（`r--`），运行期不被修改。两点都不是偶然，而是格式与安全设计的必然：

**为什么 `r--` 只读：** `__LINKEDIT` 里装的全是"给 dyld/链接器读的输入数据"——符号表用来符号化、字符串表用来查名字、rebase/bind 字节码用来驱动 dyld 改 `__DATA`/`__DATA_CONST` 里的指针、签名用来校验完整性。这些数据**只被读、从不被运行期业务逻辑写**。dyld 处理 fixups 时写的是 `__DATA_CONST`/`__DATA` 段（那里才需要可写、用完再 `mprotect` 降只读），而 `__LINKEDIT` 自己自始至终只读。给它 `r--` 一来符合最小权限原则、缩小可写面，二来它的内容被代码签名哈希覆盖、本就不该改——若可写，签名校验的意义就被破坏了。

**为什么在文件尾部：** 这与代码签名和"可增删性"强绑定。其一，代码签名 blob 由 `codesign` 在事后**追加到文件末尾**（也就是追加到 `__LINKEDIT` 末端），签名覆盖它之前的所有字节；把 `__LINKEDIT` 放最后，签名才能"盖住前面的一切"且自己干净地落在最后（详见第 6 节）。其二，因为 `__LINKEDIT` 在文件最末，**对它扩容或缩容只需在文件尾部追加/截断**，不必挪动前面 `__TEXT`/`__DATA` 的任何字节、不必重排其它段的 `fileoff`——`strip` 缩小符号表、`codesign` 追加签名、各种二进制改写工具增删元数据，都因此变得相对容易。如果 `__LINKEDIT` 在中间，任何尺寸变化都会引发后续段的偏移雪崩。

### 4. 为什么必须是最后一个段（dyld 的硬性校验）

这是 `__LINKEDIT` 最重要的一条铁律：**它必须是 Mach-O（每个架构 slice）里物理位置最末的段，`dyld` 会拒绝任何在 `__LINKEDIT` 之后还有段数据的二进制。**

原因层层递进：

1. **代码签名的覆盖范围依赖它在最后。** 签名的设计是"覆盖文件里它之前的所有内容"。签名数据自己住在 `__LINKEDIT` 末端，如果 `__LINKEDIT` 后面还有别的段数据，那部分就落在签名覆盖范围之外——等于留了一块"签名管不到"的区域，攻击者可往那里塞东西而不破坏签名。为杜绝此漏洞，`dyld` 直接规定 `__LINKEDIT` 必须最后，其后不得有任何段字节。
2. **`vmsize` 不得小于 `filesize`。** 这是所有段的通则，但在 `__LINKEDIT` 上尤其容易被改写工具踩坑：手工增大 `__LINKEDIT` 的 `filesize`（比如塞进更大的签名）却忘了同步调大 `vmsize`，`dyld` 会因 "`vmsize < filesize`" 直接报错拒绝加载。
3. **这也解释了"为何不能往签名后的二进制随便追加数据"。** 一旦在已签名二进制末尾（`__LINKEDIT` 之后）追加字节，要么签名失效（追加内容不在签名内、但文件哈希变了），要么直接违反"最后一个段"约束被 dyld 拒。正确做法是：**新段数据要插在 `__LINKEDIT` 之前**，再重新签名（让新签名覆盖含新段的全部内容）。专业改写工具（如 LIEF、`insert_dylib`、`macho_edit`）正是这么做的——它们要么把新段塞进 `__LINKEDIT` 前并整体下移 `__LINKEDIT`、修正所有偏移，要么先截断旧签名、改写后再 `codesign --force` 重签。

> [!warning] 改写 `__LINKEDIT` 的两个经典翻车点
> ① **忘了同步 `vmsize`**：增大 `filesize` 不增大 `vmsize` → dyld 报 `vmsize` 小于 `filesize`。
> ② **签名残留 padding**：移除旧签名后，`__LINKEDIT` 末端常留有为对齐签名（按 `0x10` 对齐）而填的 padding，若不一并截掉，`codesign_allocate` 会报 "link edit information does not fill the __LINKEDIT segment"（链接信息没填满段），重签失败。处理这类二进制要用能正确"截断 slice + 改 `__LINKEDIT` 的 `filesize`/`vmsize` + 重对齐"的工具。

### 5. 内部必须连续、有序（dyld 的 underrun / overrun 校验）

不仅"`__LINKEDIT` 整体要最后"，其**内部各块也必须连续、有序、互不重叠，且全部落在 `__LINKEDIT` 范围内**。`dyld` 对此有明确的越界检查：对每一个指入 `__LINKEDIT` 的 LC，校验其数据区间 `[off, off+size)` 满足 `off ≥ linkeditFileOffsetStart` 且 `off+size ≤ linkeditFileOffsetEnd`，否则抛错拒绝加载。以链式 fixups 为例，dyld 源码会抛：

- 若 `dataoff < linkeditFileOffsetStart` → `"dyld chained fixups info underruns __LINKEDIT"`（数据起点在 `__LINKEDIT` 之前，**下溢**）；
- 若 `dataoff + datasize > linkeditFileOffsetEnd` → `"dyld chained fixups info overruns __LINKEDIT"`（数据末端超出 `__LINKEDIT`，**上溢**）。

符号表同理会报 `"symbol table underruns __LINKEDIT"` 这类错误（社区里常因二进制被不当改写、偏移没修对而遇到）。

各块的典型排布顺序（同一个 `__LINKEDIT` 内、从低偏移到高偏移）大致为：

```text
低偏移 ┌─────────────────────────────────────────────┐
       │ dyld info 字节码 / 链式 fixups (rebase+bind)  │ ← LC_DYLD_INFO_ONLY / LC_DYLD_CHAINED_FIXUPS
       │ export trie 导出符号树                        │ ← (随 export_off) / LC_DYLD_EXPORTS_TRIE
       │ function starts 函数起始表                    │ ← LC_FUNCTION_STARTS
       │ data-in-code 标注                            │ ← LC_DATA_IN_CODE
       │ 符号表 nlist_64[]：locals → extdef → undef    │ ← LC_SYMTAB.symoff（顺序受 LC_DYSYMTAB 索引约束）
       │ 间接符号表 indirect symbols                   │ ← LC_DYSYMTAB.indirectsymoff
       │ (外部/局部重定位项，旧式)                      │ ← LC_DYSYMTAB.extreloff/locreloff
       │ 字符串表 string table                        │ ← LC_SYMTAB.stroff（符号数据里通常排最后）
       │ 代码签名 Code Signature                      │ ← LC_CODE_SIGNATURE.dataoff（永远在最末端）
高偏移 └─────────────────────────────────────────────┘
```

> [!note] 符号表内部也有强制分组
> `LC_SYMTAB` 的符号表（`nlist_64` 数组）本身必须按类型**分三段连续排列**：① 局部符号（local，调试用）→ ② 外部定义符号（external defined）→ ③ 未定义符号（undefined，待 dyld 绑定）。`LC_DYSYMTAB` 的 `ilocalsym`/`nlocalsym`、`iextdefsym`/`nextdefsym`、`iundefsym`/`nundefsym` 三对"起始索引 + 数量"正是指向这三段连续区间。所以 `LC_DYSYMTAB` 不另存一份符号，而是"复用 `LC_SYMTAB` 的符号表、再用索引把它切成三类 + 定位间接符号表"。这也是为什么 `LC_DYSYMTAB` 存在则 `LC_SYMTAB` 必然存在（详见 [[05.Mach-O LC_SYMTAB]] 与 [[06.Mach-O LC_DYSYMTAB]]）。

### 6. 代码签名：覆盖前面所有内容，并置于 `__LINKEDIT` 末端

`LC_CODE_SIGNATURE` 通过 `linkedit_data_command` 的 `dataoff`/`datasize` 指向代码签名 blob，这个 blob **总是放在 `__LINKEDIT` 的最末端**（也就是整个文件的最末端，因为 `__LINKEDIT` 是最后一个段）。它的工作方式是：

1. **签名内容覆盖它之前的一切。** Code Directory 把文件按页切块、逐页算哈希，覆盖范围是"文件开头直到代码签名 blob 之前"的所有字节——包含 Mach-O Header、全部 Load Commands、`__TEXT`、`__DATA`/`__DATA_CONST`，以及 `__LINKEDIT` 里签名之前的所有元数据（符号表、字符串表、fixups…）。换句话说，**除了签名自己，文件里其它每一个字节都被签名哈希罩住**。
2. **签名自己不能签自己**，所以它必须在最末端：盖住前面所有内容、自己干净地收在最后。这与"`__LINKEDIT` 必须是最后一个段"互为因果——只有 `__LINKEDIT` 在最后、签名在 `__LINKEDIT` 最末，"覆盖前面全部、自己在最后"才能成立。
3. **`codesign_allocate` 的预期布局：** 工具默认"`LC_CODE_SIGNATURE` 指向的签名在 `__LINKEDIT` 末端、且 `__LINKEDIT` 在 slice 末端"。移除签名时，它截断 slice 去掉签名部分、并同步更新 `__LINKEDIT` 段命令的 `filesize`（fat 二进制还要更新各 slice 的大小/偏移）。移除签名后，`__LINKEDIT` 里最后的内容通常就是字符串表。

正因签名覆盖范围如此之广，**任何对前面内容的改动都会使签名失效**：改一条 Load Command、动一个字节的 `__TEXT`、`strip` 掉若干符号——都会让重新计算的页哈希对不上原签名，必须 `codesign --force --sign ...` 重签（`--force` 用来覆盖已失效的旧签名，否则 codesign 拒绝改写已签名二进制）。

### 7. 为什么 `strip` 主要削减此段

`strip` 删除调试符号、局部符号等，主要缩减的正是 `__LINKEDIT` 里的**符号表（`nlist_64` 数组）与字符串表（符号名字符串）**，而 `__TEXT`/`__DATA` 基本不动——所以 strip 后代码照常运行，仅符号信息变少（崩溃栈、`nm` 输出里能看到的名字减少）。

不同级别的削减：

- **`strip -x`**：去掉**局部符号**（local），只保留全局符号。常用于发布前瘦身、又不破坏动态导出。
- **`strip`（默认 / `-S`）**：去掉**调试符号**等。
- **最激进（设 `STRIP_NLISTS` 环境变量，或对应选项）**：对走动态链接的二进制，可移除几乎所有 `nlist` 符号与字符串表（dyld 真正必需的最小集除外）。

为什么效果集中在这里：`__LINKEDIT` 是符号表/字符串表的物理归宿，且它在文件最末、便于"缩容后直接截断尾部"。删掉局部符号后，符号表条目变少 → 字符串表里对应的名字也可去掉 → `__LINKEDIT.filesize` 减小 → 文件随之变小。`__TEXT`/`__DATA` 的字节不受影响，故功能不变。

> [!warning] strip 之后必须重签
> `strip` 改动了 `__LINKEDIT`（符号表/字符串表变了、段尺寸变了），而代码签名覆盖 `__LINKEDIT`，所以**对已签名二进制执行 strip 会使其签名立即失效**，必须 `codesign --force` 重新签名。常见翻车："codesign_allocate: file not in an order that can be processed (link edit information does not fill the __LINKEDIT segment)"——多因原签名留下的对齐 padding 没被正确截掉、`__LINKEDIT` 出现"空洞"，需要能正确重排/截断 `__LINKEDIT` 的工具来处理。

> [!note] 架构差异
> `__LINKEDIT` 内的符号项随位宽为 `nlist`（32 位，12 字节）或 `nlist_64`（64 位，16 字节）；其余偏移表（rebase/bind 字节码、export trie、function starts、链式 fixups、签名 blob）的结构与位宽无关，靠字节流/ULEB128 编码，天然免于大小端与位宽差异。`arm64e` 还会包含指针认证（PAC）相关的额外 fixup 信息（链式 fixups 的 `pointer_format` 会用专门的 PAC 变体）。另外，**macOS 12 / iOS 15 起，工具链用 `LC_DYLD_CHAINED_FIXUPS` + `LC_DYLD_EXPORTS_TRIE` 取代了 `LC_DYLD_INFO_ONLY`**：rebase 与 bind 被"链"在一起搬进 `__DATA`/`__DATA_CONST` 的指针自身（`__LINKEDIT` 只放链表头与 imports 表），导出符号 trie 搬到独立命令，且**不再有 lazy bind**（连带 `__DATA,__la_symbol_ptr` 节也随之消失）。详见 [[17.Mach-O LC_DYLD_INFO_ONLY]]。


```text
      cmd LC_DYLD_CHAINED_FIXUPS

      cmd LC_DYLD_EXPORTS_TRIE
```

## FAQ

> [!question] `__LINKEDIT` 既然 `nsects == 0`，那它内部的结构到底由谁决定？
> 由**指入它的各条加载命令**决定，不由段头决定。段头（`segment_command_64`）只圈定"文件 `[fileoff, fileoff+filesize)`、内存 `[vmaddr, vmaddr+vmsize)`、权限 `r--`"这一整块地皮；地皮内部哪段是符号表、哪段是字符串表、哪段是签名，全靠 `LC_SYMTAB` 的 `symoff`/`stroff`、`LC_DYSYMTAB` 的 `indirectsymoff`、`linkedit_data_command` 的 `dataoff` 等偏移字段去指。要弄清某个 `__LINKEDIT` 装了什么，**不能看节头（它没有），要逐条看指向它的 LC 的偏移字段**（见示例 2）。

> [!question] 为什么 `__LINKEDIT` 必须是最后一个段？放中间会怎样？
> 因为**代码签名住在 `__LINKEDIT` 末端、且设计为覆盖文件里它之前的所有内容**。只有 `__LINKEDIT` 在最后，签名才能"盖住前面一切、自己干净地收在文件最末"；若 `__LINKEDIT` 之后还有别的段数据，那部分就逃出签名覆盖范围，留下可被篡改的盲区。为堵死这个洞，`dyld` 直接拒绝任何"`__LINKEDIT` 之后还有段数据"的二进制。这也是为什么不能往已签名二进制尾部随意追加数据——正确做法是把新段插到 `__LINKEDIT` 之前、再 `codesign --force` 重签（让新签名覆盖含新段的全部内容）。

> [!question] 为什么 `strip` 只动 `__LINKEDIT`、却能让整个文件变小，且不影响程序运行？
> 因为**符号信息（符号表 + 字符串表）物理上只存在于 `__LINKEDIT`**，而它们对"代码能不能跑"不是必需的——CPU 执行 `__TEXT` 的指令、读写 `__DATA` 的数据，全程不需要符号名（符号名只在链接期、符号化/调试期有用）。`strip` 删掉局部/调试符号后，`__LINKEDIT` 里的符号表条目和对应字符串变少，段尺寸缩小，又因 `__LINKEDIT` 在文件最末、可直接截断尾部，文件随之变小；`__TEXT`/`__DATA` 一个字节没动，所以程序照常运行，只是 `nm`、崩溃栈里能看到的名字变少了。代价：对已签名二进制 strip 后签名失效，须重签（见下一问）。

> [!question] 改写或 strip 之后，为什么常遇到 "link edit information does not fill the __LINKEDIT segment"？怎么办？
> 这是 `codesign_allocate` 在重签时报的"`__LINKEDIT` 没被填满（有空洞）"错误。根因：原签名 blob 按 `0x10` 对齐，移除签名时若只删了 blob 本体、却漏删了它前面为对齐而填的 padding，`__LINKEDIT` 末端就留下一段"没有任何 LC 指向"的空隙，破坏了"内部连续、填满段"的约束。解决办法是用能**正确截断 slice + 同步更新 `__LINKEDIT` 的 `filesize`/`vmsize` + 重新对齐**的工具（如 `macho_edit`、LIEF）来移除旧签名，再 `codesign --force --sign ...` 重签。同时切记同步 `vmsize ≥ filesize`，否则 dyld 会另报"`vmsize` 小于 `filesize`"而拒绝加载。

## 小结

- `__LINKEDIT` 是**只读（`r--`）、位于文件最尾部、无节（`nsects=0`、`cmdsize=72`）的元数据容器段**——段头只圈地皮，内部结构由别的 LC 决定。
- 它是一块"公共数据池"：符号表/字符串表（`LC_SYMTAB`）、间接符号表（`LC_DYSYMTAB`）、rebase/bind/export（`LC_DYLD_INFO_ONLY`）、链式 fixups（`LC_DYLD_CHAINED_FIXUPS`）、导出 trie（`LC_DYLD_EXPORTS_TRIE`）、函数起始（`LC_FUNCTION_STARTS`）、Data-in-Code（`LC_DATA_IN_CODE`）、代码签名（`LC_CODE_SIGNATURE`）等，全由各 LC 以 `symoff`/`stroff`/`dataoff` 等**文件偏移直接指入**；大半命令共用极简的 `linkedit_data_command{dataoff,datasize}`。
- 它**必须是最后一个段**（dyld 拒绝其后还有段数据），内部各块**必须连续、有序、不越界**（dyld 有 underrun/overrun 校验），这两条都为代码签名服务。
- **代码签名置于 `__LINKEDIT` 最末端、覆盖它之前的所有字节**；任何对前面内容的改动（含 strip）都使签名失效，须 `codesign --force` 重签。
- **`strip` 主要削减此段的符号表/字符串表**，文件随之变小而代码照常运行；改写/重签时当心 padding 空洞与 `vmsize < filesize` 两类翻车。

### __LINKEDIT 各块字节格式

本节从字节层面剖析 `__LINKEDIT` 内各主要数据块的实际编码，包括 rebase/bind opcode、export trie 节点、代码签名 blob，以及 dyld 共享缓存对 `__LINKEDIT` 的特殊处理。

#### rebase/bind opcode 字节级格式

rebase 与 bind 字节码（由 `LC_DYLD_INFO_ONLY` 指入 `__LINKEDIT`）共用同一套**单字节打包**规则：每字节高 4 位是操作码、低 4 位是立即数（immediate）：

```
  ┌─ b7 b6 b5 b4 ─┬─ b3 b2 b1 b0 ─┐
  │   opcode(4)   │    imm(4)     │     opcode = byte & 0xF0
  └───────────────┴───────────────┘     imm    = byte & 0x0F
```

当参数超过 15 时，opcode 字节后紧跟 **ULEB128**（Unsigned Little-Endian Base-128）变长整数：每字节低 7 位是有效负载，最高位（`0x80`）为**续接标志**——置 1 表示后面还有字节，置 0 表示结束。解码示例：

```
ULEB128 字节流       十六进制   解码方式
0xE5 0x8E 0x26       [0xe5,0x8e,0x26]   = 0x65 | (0x0e<<7) | (0x26<<14)
                                         = 0x65 + 0x700 + 0x98000 = 0x98765 = 624485
```

编码 `624485` 的 ULEB128：

```c
do {
    uint8_t byte = value & 0x7f;
    value >>= 7;
    if (value != 0) byte |= 0x80;   // 续接标志
    emit(byte);
} while (value != 0);
// 产出: 0xe5 0x8e 0x26
```

**rebase 状态机寄存器**（解析器维护）：

| 寄存器 | 初始值 | 用途 |
|---|---|---|
| `seg_index` | 0 | 当前目标段的索引 |
| `seg_offset` | 0 | 当前目标在段内的字节偏移 |
| `type` | 0 | 重定位类型（`REBASE_TYPE_POINTER=1`） |

**rebase 完整 opcode 字节表**：

| opcode 高 4 位 | 完整字节（高 4 位 | 低 4 位）| 操作 | 参数 |
|---|---|---|---|
| `0x00` | `REBASE_OPCODE_DONE` | 流结束，停止处理 | 无 |
| `0x10` | `REBASE_OPCODE_SET_TYPE_IMM` | `type = imm`（重定位类型） | imm（0–15）|
| `0x20` | `REBASE_OPCODE_SET_SEGMENT_AND_OFFSET_ULEB` | `seg_index = imm; seg_offset = ULEB` | imm + ULEB128 |
| `0x30` | `REBASE_OPCODE_ADD_ADDR_ULEB` | `seg_offset += ULEB` | ULEB128 |
| `0x40` | `REBASE_OPCODE_ADD_ADDR_IMM_SCALED` | `seg_offset += imm * ptr_size` | imm（0–15）|
| `0x50` | `REBASE_OPCODE_DO_REBASE_IMM_TIMES` | 执行 `imm` 次 rebase，每次 `seg_offset += ptr_size` | imm（1–15）|
| `0x60` | `REBASE_OPCODE_DO_REBASE_ULEB_TIMES` | 执行 ULEB 次 rebase | ULEB128 |
| `0x70` | `REBASE_OPCODE_DO_REBASE_ADD_ADDR_ULEB` | rebase 1 次，然后 `seg_offset += ULEB` | ULEB128 |
| `0x80` | `REBASE_OPCODE_DO_REBASE_ULEB_TIMES_SKIPPING_ULEB` | rebase N(ULEB) 次，每次间隔 ULEB 字节 | ULEB1 (N) + ULEB2 (skip) |

**一段完整 rebase 字节码示例**（段 2 偏移 0x100 处连续 4 个指针）：

```text
字节:  0x21 0x80 0x02 0x54 0x00
解码:
  0x21 → opcode=0x20(SET_SEGMENT_AND_OFFSET_ULEB), imm=1  → seg_index=1
  0x80 0x02 → ULEB128 = 0x100                              → seg_offset=0x100
  0x54 → opcode=0x50(DO_REBASE_IMM_TIMES), imm=4          → rebase 4次，每次偏移+8（ptr_size）
  0x00 → DONE
```

**bind 独有字段**（在 rebase 基础上增加）：符号名通过 `SET_SYMBOL_TRAILING_FLAGS_IMM`（`0x40`）编码——opcode 字节之后紧跟以 `\0` 结尾的 UTF-8 符号名字符串，字节序列形如：

```text
0x40 '_' 'p' 'r' 'i' 'n' 't' 'f' 0x00
    │    └────────────────────────────── 符号名 _printf\0
    └─ SET_SYMBOL_TRAILING_FLAGS_IMM, flags(imm)=0
```

`addend` 用 **SLEB128**（Signed LEB128，最高位为符号扩展标志）编码，允许负值。

#### export trie 节点字节格式

export trie 存储本镜像对外导出的所有符号名及地址，用前缀树（trie）紧凑编码。**每个节点在字节流中的精确布局**如下（顺序不可颠倒）：

```text
[节点布局]
  ULEB128   terminalSize    — 本节点的"终端信息"字节数（0 = 非终端节点）
  [若 terminalSize > 0]:
    ULEB128   flags          — EXPORT_SYMBOL_FLAGS_* 组合
    [普通符号]:
      ULEB128 vmoffset      — 符号地址相对镜像 mach_header 的偏移
    [若 flags & REEXPORT(0x08)]:
      ULEB128 libOrdinal    — 来源库序号
      cstring origName      — 原符号名（\0 结尾，空串=同名）
    [若 flags & STUB_AND_RESOLVER(0x10)]:
      ULEB128 stubOffset    — stub 函数偏移
      ULEB128 resolverOffset— resolver 函数偏移
  uint8_t   childCount      — 子边数量（0–255）
  [每条子边（childCount 个）]:
    cstring   label         — 边字符串（\0 结尾的部分符号名片段）
    ULEB128   nodeOffset    — 子节点相对 trie 起点的字节偏移
```

**具体示例**（导出 `_malloc` 和 `_malloc_zone_malloc`）：

```text
root 节点 (terminalSize=0, childCount=1):
  子边: "_malloc\0"  → 偏移 12

偏移 12: 中间节点 "_malloc"(terminalSize=2, flags=0,vmoffset=0x3a40, childCount=1):
  终端: flags=0x00  vmoffset ULEB=0xe880 0x03  (= 0x3a40)
  子边: "_zone_malloc\0" → 偏移 35

偏移 35: 终端节点 "_malloc_zone_malloc"(terminalSize=2, flags=0, vmoffset=0x3b10, childCount=0)
```

ULEB128 解码 `0xe880 0x03`：`0x68 | (0x00<<7) | (0x03<<14) = 0x68 + 0 + 0xC000 = 0xC068`（此为示意，实际值因二进制而异）。

**`EXPORT_SYMBOL_FLAGS_*` 取值速查**：

| 常量 | 值 | 含义 |
|---|---|---|
| `EXPORT_SYMBOL_FLAGS_KIND_REGULAR` | `0x00` | 普通符号（kind 掩码 `0x03` 的值 0）|
| `EXPORT_SYMBOL_FLAGS_KIND_THREAD_LOCAL` | `0x01` | TLS 符号 |
| `EXPORT_SYMBOL_FLAGS_KIND_ABSOLUTE` | `0x02` | 绝对地址符号 |
| `EXPORT_SYMBOL_FLAGS_WEAK_DEFINITION` | `0x04` | 弱定义 |
| `EXPORT_SYMBOL_FLAGS_REEXPORT` | `0x08` | 重导出（附带库序号+原名）|
| `EXPORT_SYMBOL_FLAGS_STUB_AND_RESOLVER` | `0x10` | IFUNC 式双入口（stub+resolver）|

**解析 trie 的伪代码**：

```c
void parseTrie(uint8_t *start, uint32_t offset, const char *prefix) {
    uint8_t *p = start + offset;
    uint64_t termSize = readULEB128(&p);
    if (termSize) {
        uint64_t flags   = readULEB128(&p);
        uint64_t vmaddr  = readULEB128(&p);   // 普通符号
        printf("export: %s flags=0x%llx addr=0x%llx\n", prefix, flags, vmaddr);
        p += (termSize - alreadyRead);        // 跳过剩余终端信息
    }
    uint8_t childCount = *p++;
    for (int i = 0; i < childCount; i++) {
        char label[256];
        strcpy(label, (char*)p); p += strlen(label)+1;  // 读边字符串
        uint64_t childOff = readULEB128(&p);
        char newPrefix[256]; strcpy(newPrefix, prefix); strcat(newPrefix, label);
        parseTrie(start, childOff, newPrefix);            // 递归
    }
}
```

#### CS（Code Signature）blob 字节结构

代码签名 blob 由 `LC_CODE_SIGNATURE` 指向，位于 `__LINKEDIT` 的最末端。它是一个**SuperBlob**，内嵌多个子 blob，整体结构如下（所有字段**大端序**，与 Mach-O 主体的小端序相反）：

```
[CS_SuperBlob]  偏移 0（相对 dataoff）
  uint32_t magic       = 0xFADE0CC0   — SuperBlob 魔数
  uint32_t length      — 整个 blob 总字节数（= datasize）
  uint32_t count       — 子 blob 数量
  [CS_BlobIndex × count]:
    uint32_t type      — 子 blob 类型（见下表）
    uint32_t offset    — 子 blob 相对 SuperBlob 起点的偏移

[子 blob 1：CS_CodeDirectory]  最重要的子 blob
  uint32_t magic       = 0xFADE0C02
  uint32_t length
  uint32_t version     — CD 版本（0x20400 = v2.4，主流）
  uint32_t flags
  uint32_t hashOffset  — hash 槽数组相对本 CD 起点的偏移
  uint32_t identOffset — 标识符字符串偏移（bundle ID）
  uint32_t nSpecialSlots  — 特殊槽数量（< 0，负索引）
  uint32_t nCodeSlots     — 代码槽数量（= ceil(codeLimit / pageSize)）
  uint32_t codeLimit      — 被签名的文件字节数（= dataoff，不含签名 blob 本身）
  uint8_t  hashSize    — 每个哈希的字节数（SHA256 = 32）
  uint8_t  hashType    — 哈希算法（1=SHA1, 2=SHA256, 5=SHA256-TRUNC）
  uint8_t  platform    — 平台（0=macOS, 1=iOS…）
  uint8_t  pageSize    — log2(页大小)（12 = 4KB, 14 = 16KB）
  uint32_t spare2
  // v2.0+
  uint32_t scatterOffset
  // v2.1+
  uint32_t teamOffset  — 团队 ID 字符串偏移
  // v2.4+
  uint32_t spare3
  uint64_t codeLimit64
  uint64_t execSegBase
  uint64_t execSegLimit
  uint64_t execSegFlags  — 可执行段标志（决定 entitlement 授权）
  // hash 槽数组（hashOffset 处）:
  // 负索引 [-nSpecialSlots, -1]：特殊槽（bound info hash、requirements hash 等）
  // 正索引 [0, nCodeSlots-1]：对文件每页内容的 SHA256 哈希（32 字节 × nCodeSlots）
```

**子 blob 类型常量**：

| type 值 | 含义 |
|---|---|
| `0x00000000` | `CSSLOT_CODEDIRECTORY`（主 Code Directory）|
| `0x00000001` | `CSSLOT_INFOSLOT`（Info.plist 哈希）|
| `0x00000002` | `CSSLOT_REQUIREMENTS`（code requirements blob）|
| `0x00000003` | `CSSLOT_RESOURCEDIR`（资源目录哈希）|
| `0x00000004` | `CSSLOT_APPLICATION`（应用特定数据）|
| `0x00000005` | `CSSLOT_ENTITLEMENTS`（entitlements plist，XML 明文）|
| `0x10000100` | `CSSLOT_ALTERNATE_CODEDIRECTORIES`（备用 CD，如 SHA1+SHA256 并存）|
| `0xFADE0B01` | `CSSLOT_SIGNATURESLOT`（CMS 签名 blob，含证书链）|

**CMS 签名子 blob**（magic `0xFADE0B01`）包含完整的 DER 编码 CMS（Cryptographic Message Syntax）结构：SignedData → SignerInfo → 对 Code Directory 的签名（ECDSA/RSA），以及证书链（开发者证书 → 中间 CA → Apple Root CA）。

**codesign 工具读取路径**：`codesign -dvvv` → 解析 SuperBlob → 读 CodeDirectory → 验证每页哈希 → 读 CMS blob → 验证签名链。

**字节级查看命令**：

```bash
# 用 xxd 查看 blob 魔数（大端 0xFADE0CC0）
xxd -s $((0x$(otool -l /bin/ls | awk '/LC_CODE_SIGNATURE/{getline; getline; print $2}'))) \
    -l 16 /bin/ls

# macOS 内核源码：security/codesigning/CodeSigning.h（魔数）
# XNU：bsd/kern/ubc_info.c（每页哈希校验流程）
```

#### dyld 共享缓存中的 `__LINKEDIT` 合并与去重

在 `dyld_shared_cache`（iOS/macOS 启动后由 dyld 预构建的系统库快照）中，`__LINKEDIT` 经历了大规模的**合并去重**优化：

**1. `__LINKEDIT` 跨库合并（Merged LINKEDIT）**

dyld 构建共享缓存时，把所有入缓存的 dylib（`libSystem`、`libobjc`、`Foundation`…）的 `__LINKEDIT` **合并进缓存的一个全局 LINKEDIT 区域**，各库的段头 `LC_SEGMENT_64 __LINKEDIT` 的 `vmaddr`/`fileoff` 被**重写**，指向缓存内各自对应的偏移，原始 `.dylib` 文件里各 `__LINKEDIT` 的副本被丢弃。效果：

```text
原始：
  libSystem.dylib   __LINKEDIT [符号表 A | 字符串表 A | trie A | ...]
  libobjc.dylib     __LINKEDIT [符号表 B | 字符串表 B | trie B | ...]
  ...

缓存后（简化）：
  dyld_shared_cache:
    全局 LINKEDIT 区域:
      [符号表 A | 符号表 B | ... (去重后)]
      [字符串表 A+B+... (合并，重复字符串去重)]
      [trie A | trie B | ...]
      [代码签名（各库 CD 合并成缓存级签名）]
    各库的 LC_SEGMENT __LINKEDIT 的 fileoff/vmaddr 被改写为全局区域内各自的子区间
```

**2. 字符串表去重（String Table Deduplication）**

多个库的符号字符串表往往含大量相同字符串（如 `_malloc`、`_free` 在多库出现）。缓存构建工具（`update_dyld_shared_cache`/`dyld-cache-builder`）把字符串做**全局去重**：相同字符串只存一份，各库的 `nlist::n_strx`（字符串表索引）被**更新为全局偏移**。这能把字符串表总大小减少 20%–40%。

**3. 代码签名的缓存级处理**

单个 dylib 的代码签名 blob（`CS_SuperBlob`）在被加入共享缓存后**被替换**：缓存本身有一个全局的代码签名结构，逐页覆盖缓存文件的所有内容。原始 dylib 的签名 CS blob 不再独立存在于缓存 `__LINKEDIT` 中。

**4. 逆向共享缓存中的 LINKEDIT**

从共享缓存中提取单个 dylib 时（如用 `dyld_cache_extract`/`dsc_extractor`），工具需要**反向重建**各库的 `__LINKEDIT`：

```bash
# macOS 12+ 系统内置的 dsc_extractor：
/usr/lib/dsc_extractor /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e \
    /tmp/extracted_dylibs

# 提取后各库的 __LINKEDIT 是重建的，LC_CODE_SIGNATURE 指向重建签名
# 可用 otool -l 看 __LINKEDIT 段头以验证偏移是否合理
otool -l /tmp/extracted_dylibs/usr/lib/libSystem.B.dylib | grep -A8 "__LINKEDIT"
```

**5. 链式 fixups 与共享缓存的 fixup 优化**

启用链式 fixups 后，共享缓存进一步优化：各 dylib 的 `LC_DYLD_CHAINED_FIXUPS` 数据（链表头信息）被合并，缓存在**构建时**就直接把 rebase/bind 应用（slide=0 时），加载共享缓存时只需对整个缓存加一次 slide，而不必逐库逐 fixup 处理。这使系统库的启动 fixup 时间趋近于 0。

```text
提示：逆向者常见困惑——
  "共享缓存里的 dylib 为何 __LINKEDIT 的 fileoff 很大、甚至超出 dylib 本身大小？"
  答：因为 __LINKEDIT 段头被重写为全局合并 LINKEDIT 区域内的偏移（相对缓存文件头），
  而不再是相对原始 dylib 头的本地偏移。使用 dsc_extractor 提取后的 dylib 才有正常的本地偏移。
```
