# 详解Mach-O(八)Mach-O LC_ID_DYLIB

> [!abstract] TL;DR
> **`LC_ID_DYLIB`（`cmd = 0xd`）是动态库用来声明"我是谁"的加载命令**：它给出本库的 **install name（安装路径名）** 与两个版本号（`current_version` / `compatibility_version`），**只出现在 `MH_DYLIB` 类型的文件（`.dylib`/framework/bundle 形式的库）中**，可执行文件（`MH_EXECUTE`）没有它。一个库**有且通常只有一条** `LC_ID_DYLIB`。
> 命令体复用 `dylib_command`（`load_command` 统一头 + 一个 `struct dylib`），与下游使用方的 [[07.Mach-O LC_LOAD_DYLIB]] **结构完全同构、语义恰好相反**——一个声明"自身身份"，一个声明"依赖谁"。`dylib.name` 是 `lc_str` 偏移式字符串，真正的路径字节排在命令尾部、计入 `cmdsize`。
> **install name 是动态链接的"锚点"**：链接时，下游会把被链接库的 `LC_ID_DYLIB.name` **原样抄进自己的 `LC_LOAD_DYLIB`**；运行时 `dyld` 就按这个字符串去定位库。所以改库的 install name（`install_name_tool -id`）会直接决定下游能否找到它；写成绝对路径 vs `@rpath` 决定了库可不可重定位、能不能打进 App 包。
> 两个版本号都按 **`(X<<16)|(Y<<8)|Z`** 把 `X.Y.Z` 打包进 32 位（16/8/8 位宽）。历史上 `dyld` 加载时会校验"实际库提供的版本 < 可执行文件要求的 `compatibility_version` ⇒ `Incompatible library version` 失败"；但**这一强制校验在 macOS 12 起已从 dyld 中移除**——理解其语义对维护老系统、读 `otool -L` 输出仍然必要。

## 概述与定位

每个动态库都需要一个"身份证"。当别的程序（或别的库）链接它时，链接器要把它的路径写进调用方自己的 [[07.Mach-O LC_LOAD_DYLIB]]——而这个被抄写的路径，正来自库自身的 `LC_ID_DYLIB`。因此 `LC_ID_DYLIB` 是**动态库分发与定位的"源头"**：它一处定义，下游处处引用。

可以把这对命令理解成一组"名片交换"协议：

- 库这边出 `LC_ID_DYLIB`，写明"我叫 `@rpath/MyLib.dylib`，当前版本 3.2.0，对外承诺兼容到 1.0.0"。
- 链接它的程序那边收下这张名片，把"`@rpath/MyLib.dylib`、要求兼容版本 ≥ 1.0.0"刻进自己的 `LC_LOAD_DYLIB`。
- 运行时 `dyld` 拿着程序里的这条记录，按 install name 去找库、加载它、（历史上）核对版本是否达标。

它在加载命令体系里的特殊之处有三：

1. **它是文件类型的"标志性命令"**。`LC_ID_DYLIB` 的有无，几乎等价于"这个 Mach-O 是不是一个动态库"。链接器只在产物是 `MH_DYLIB` 时才发射它；`MH_EXECUTE`（可执行）、`MH_OBJECT`（`.o` 目标文件）、`MH_BUNDLE`（`dlopen` 加载的插件 bundle，严格说 `MH_BUNDLE` 也不带 `LC_ID_DYLIB`）都没有。
2. **它是"被引用"而非"主动驱动"的命令**。多数加载命令（如 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]]、[[09.Mach-O LC_MAIN]]）会让 `dyld`/内核在加载本镜像时**主动做点什么**；`LC_ID_DYLIB` 在自身被加载时几乎不触发动作——它的价值发生在**链接期**（被抄写）和**下游加载期**（被核对）。
3. **它是 install name 的"权威定义点"**。同一条 install name 会出现在两个地方：库的 `LC_ID_DYLIB`（定义）、所有下游的 `LC_LOAD_DYLIB`（引用）。二者必须对得上，否则 `dyld` 找不到库。

本篇聚焦 `LC_ID_DYLIB` 这一**描述结构**（字段、版本编码、install name 语义、与下游的耦合、改名工作流）；`LC_LOAD_DYLIB` 与各类 `@path` 占位符的运行时搜索细节见 [[07.Mach-O LC_LOAD_DYLIB]]，`dyld` 的整体加载流程见 [[01.Mach-O基础]]。

> [!note] "install name" 这个名字的由来
> `install name` 直译是"安装名"。它来自 NeXTSTEP/早期 macOS 的思路：库被"安装"到系统某个固定位置（如 `/usr/lib`），库的身份就用它**被安装后的绝对路径**来表示。后来 App 沙盒化、库要随 `.app` 一起分发，固定绝对路径不再现实，于是引入了 `@rpath`/`@loader_path`/`@executable_path` 这些"可重定位"前缀（见第 4 节）。但字段名 `install name` 与构建设置名 `Dynamic Library Install Name`（Xcode）/`-install_name`（`ld`）都沿用至今。

## 核心原理与字段详解

### 1. `dylib_command` 与 `struct dylib` 完整定义

`LC_ID_DYLIB` 复用 `dylib_command`，定义于 `<mach-o/loader.h>`，与 [[07.Mach-O LC_LOAD_DYLIB]] **同一个结构**，逐字段注释如下：

```c
struct dylib_command {
    uint32_t     cmd;        // 此处为 LC_ID_DYLIB (0xd)
                             //   （下游使用方则是 LC_LOAD_DYLIB 0xc，结构完全相同）
    uint32_t     cmdsize;    // 本命令总长 = sizeof(dylib_command)
                             //   + install name 字符串长度（含 \0），再向指针大小取整
    struct dylib dylib;      // 库描述（见下），定长部分
};

// 描述"动态库与链接它的文件如何匹配"的数据，仅用于 dylib_command
struct dylib {
    union lc_str name;             // 库路径 = install name，偏移式字符串（见第 2 节）
    uint32_t     timestamp;        // 构建时间戳（prebinding 时代用于判定缓存是否可用）
    uint32_t     current_version;  // 当前版本，X.Y.Z 打包成 32 位（见第 3 节）
    uint32_t     compatibility_version; // 兼容版本，X.Y.Z 打包成 32 位
};
```

`struct dylib` 是**定长 16 字节**（`union lc_str` 4 字节 + 三个 `uint32_t` 各 4 字节），加上 `load_command` 头 8 字节，`dylib_command` 的**定长部分共 20 字节**；其后再拖一段变长字符串。

`LC_ID_DYLIB` 命令体在文件里的精确布局：

| 偏移 | 字段 | 类型 | 字节 | 含义 |
|---|---|---|---|---|
| 0 | `cmd` | uint32_t | 4 | 固定为 `LC_ID_DYLIB`（`0xd`，十进制 13） |
| 4 | `cmdsize` | uint32_t | 4 | 定长 20 + 字符串长度，向指针大小取整；遍历步长 |
| 8 | `dylib.name`（`lc_str.offset`） | uint32_t | 4 | install name 字符串相对**命令起点**的偏移（常为 24） |
| 12 | `dylib.timestamp` | uint32_t | 4 | 构建时间戳，多数现代库填很小的占位值 |
| 16 | `dylib.current_version` | uint32_t | 4 | 当前版本，`(X<<16)\|(Y<<8)\|Z` |
| 20 | `dylib.compatibility_version` | uint32_t | 4 | 兼容版本，同样打包格式 |
| 24 | `name` 字符串 | char[] | 变长 | install name 文本，`\0` 结尾 + 对齐补 `\0` |

> [!note] 为什么 `name` 偏移常是 24
> `union lc_str` 在文件里以 `offset`（`uint32_t`）形式出现，表示"字符串首字节距本命令第 0 字节的偏移"。由于 `cmd`+`cmdsize`+`struct dylib` 这 24 字节是定长且字符串紧随其后，所以 `LC_ID_DYLIB`/`LC_LOAD_DYLIB` 里 `name` 的偏移几乎总是 **24**。这就是 `otool -l` 输出里 `name @rpath/MyLib.dylib (offset 24)` 那个 `(offset 24)` 的来历。

### 2. `union lc_str`：偏移式变长字符串

`name` 不是内联的定长 `char[16]`（那是 `segname` 的玩法），而是 `lc_str`——一个"长度可变、内容外置"的字符串机制，专为存放 install name 这种**长度不定的路径**而设：

```c
union lc_str {
    uint32_t offset;     // 字符串相对命令起点的字节偏移（文件中实际使用这个）
#ifndef __LP64__
    char    *ptr;        // 仅 32 位进程内存态用；文件里不使用
#endif
};
```

规则要点：

- **文件里只用 `offset`**：解析时取 `命令起点 + offset` 得到字符串首地址，按 C 字符串（`\0` 结尾）读取。
- **字符串数据排在结构体之后**：路径字节物理上跟在 `dylib_command` 定长部分后面，并把这段长度**计入 `cmdsize`**。所以 `cmdsize` = 20（定长）+ `strlen(name)+1`，再向指针大小（64 位为 8）**向上取整**，尾部用 `\0` 补齐。
- **越界即畸形**：健壮解析器须校验 `offset < cmdsize` 且字符串在命令边界内有 `\0` 终止，否则按损坏文件拒绝（这是常见的解析器攻击面）。

> [!note] `lc_str` 不止 `name` 一处用
> 凡是"加载命令里要塞一段变长字符串"的场景都用 `lc_str`：`LC_LOAD_DYLIB`/`LC_ID_DYLIB` 的 install name、`LC_RPATH` 的搜索路径、`LC_SUB_FRAMEWORK`/`LC_SUB_CLIENT` 的名字、`LC_DYLINKER`（动态链接器路径）等。理解了这里的"偏移 + 尾随字节 + 计入 cmdsize"模式，这些命令的字符串字段都同理。

### 3. `current_version` / `compatibility_version`：编码、语义与 dyld 校验

#### 3.1 32 位打包：`(X<<16) | (Y<<8) | Z`

两个版本号都把人类可读的 `X.Y.Z` 三段式编码进一个 `uint32_t`，**位宽分配 16 / 8 / 8**：

| 组件 | 位段 | 位宽 | 取值范围 |
|---|---|---|---|
| `X`（major，主版本） | bit 31–16（高 16 位） | 16 bit | 1 ~ 65535（须为正非零） |
| `Y`（minor，次版本） | bit 15–8 | 8 bit | 0 ~ 255 |
| `Z`（patch，修订） | bit 7–0（低 8 位） | 8 bit | 0 ~ 255 |

`ld64`（Apple 链接器）里 `parseVersionNumber32` 的实现就是：校验 `X ≤ 0xffff`、`Y ≤ 0xff`、`Z ≤ 0xff` 后返回 **`(X << 16) | (Y << 8) | Z`**。超出位宽（如 `minor = 300`）会直接报链接错误。反向解码：`X = v >> 16`、`Y = (v >> 8) & 0xff`、`Z = v & 0xff`。

几个换算实例，便于对照 `otool` 输出与十六进制原始值：

| `X.Y.Z` | 计算 | 十六进制原始值 |
|---|---|---|
| `1.0.0` | `(1<<16)` | `0x00010000` |
| `3.2.0` | `(3<<16)\|(2<<8)` | `0x00030200` |
| `1345.0.0` | `(1345<<16)` | `0x05410000` |
| `16.7.8` | `(16<<16)\|(7<<8)\|8` | `0x00100708` |
| `0`（未设置） | `0` | `0x00000000` |

> [!note] 版本号永远三段显示；不足补零
> Mach-O 的版本号是定死的三段式 `X.Y.Z`。你给链接器只写 `1`，入库后 `otool -L` 也会显示成 `1.0.0`——短版本号靠补零扩成三段。`compatibility_version`/`current_version` 在 `otool -L` 里成对出现，正是 `(compatibility version 1.0.0, current version 3.2.0)` 这种格式。

#### 3.2 两者语义的分工

- **`current_version`（当前版本）**：纯**信息性**字段，描述"这个库现在是第几版"。运行时可由 `NSVersionOfRunTimeLibrary()` 取回，供程序判断"我实际加载到的库是哪一版"。它**不参与** dyld 的加载放行/拒绝决策。
- **`compatibility_version`（兼容版本）**：库对外的**向后兼容承诺**——"凡是当初针对 `compatibility_version ≤ 本值` 编译的下游，我都保证 ABI 兼容"。它是历史上 dyld **真正用于加载校验**的字段。约定：只在发生**破坏二进制兼容**的改动（删/改导出符号、改结构体布局）时才抬高 `compatibility_version`；纯新增、纯修 bug 只抬 `current_version`，`compatibility_version` 不动——这样老下游仍能加载新库。
- 若 `compatibility_version` **保持为 0**（不指定），则**完全不做版本检查**，任意版本都放行。

#### 3.3 dyld 的兼容性校验逻辑（及其在 macOS 12 的移除）

历史上的检查发生在 `dyld` 加载某依赖库、把下游 `LC_LOAD_DYLIB` 里记录的"要求兼容版本"与库实际 `LC_ID_DYLIB.compatibility_version` 比对时。判定条件（综合 dyld 源码 `MachOFile::enforceCompatVersion` 一带逻辑）大致是：

1. 下游要求的 `minVersion`（即链接时抄下来的 `compatibility_version`）**不是通配符 `0xFFFFFFFF`**（`0xFFFFFFFF` 表示"匹配任意版本"）；
2. **库实际提供的 `compatibility_version` < 下游要求的 `minVersion`**；
3. 该 Mach-O **要求强制校验兼容版本**。

三者同时成立，就抛出经典错误：

```text
Incompatible library version: <下游> requires version A.B.C or later,
but <库> provides version a.b.c
```

也就是说，**"库提供的兼容版本，低于可执行文件要求的兼容版本"才失败**；反之（库更高/相等）放行。注意比较的是 `compatibility_version`，不是 `current_version`。

> [!warning] 这项强制校验在 macOS 12（Monterey）起已被移除
> Apple 在 macOS 12 一带的 dyld 重写中**删除了上述校验代码路径**：`MachOFile::enforceCompatVersion` 虽仍有定义，但已**完全不再被调用**。这意味着在现代 macOS 上，即使下游要求的兼容版本高于库实际提供的版本，**也不会再触发 `Incompatible library version` 而拒绝加载**。因此：
> - 在 **macOS 12+** 上调试"库找不到/加载失败"，先排查 **install name 对不上、`@rpath` 没解析到、签名失效**，而**不是**版本不兼容——后者已不再是失败原因。
> - 该校验在**老系统（macOS 11 及更早、对应历史 iOS）** 仍可能生效；维护老版本兼容、读历史报错时仍需理解它。
> - `compatibility_version` 至今仍**写进文件、仍由 `otool -L` 显示**，并可能被第三方/链接期工具用作一致性提示——只是 dyld 运行时不再据此拒绝加载。

#### 3.4 `timestamp`

`timestamp` 是构建时间戳，源自 **prebinding（预绑定）** 时代：早期 dyld 用它判定某库的预绑定信息是否仍然有效（库被重建后时间戳变化即作废缓存）。prebinding 早已被 dyld shared cache 取代，现代库的 `timestamp` 多填一个很小的占位值（常见为 `1` 或 `2`），分析时一般可忽略。

### 4. install name 决定下游"怎么找到你"

这是 `LC_ID_DYLIB` 最核心的实践语义。链接期，当 A 链接库 B 时，链接器把 **B 的 `LC_ID_DYLIB.name` 原样写进 A 的 `LC_LOAD_DYLIB`**；运行期 `dyld` 就拿着这个字符串去定位 B。**B 的 install name 长什么样，A 运行时就去哪找 B**——install name 的写法因此直接决定了库可不可重定位。

常见三类写法及取舍：

| install name 写法 | 运行时解析 | 适用 | 风险/限制 |
|---|---|---|---|
| 绝对路径 `/usr/local/lib/B.dylib` | 直接当成磁盘绝对路径 | 系统库、固定安装位置的库 | **不可重定位**：库或 App 一旦换目录就失效；不适合随 `.app` 分发 |
| `@rpath/B.dylib` | 在下游的一组 `LC_RPATH` 运行时搜索路径里**依次查找** | **分发型库、打进 App 包的 framework**（最灵活、最推荐） | 下游必须配好至少一条能命中库的 `LC_RPATH`（如 `@executable_path/../Frameworks`），否则找不到 |
| `@loader_path/B.dylib` | 相对"**引用它的那个镜像**"所在目录 | 嵌套 framework、可被多个不同可执行体复用的插件 | 路径相对"加载者"，被不同宿主加载时基准目录不同，需理解清楚 |
| `@executable_path/B.dylib` | 相对**主可执行文件**所在目录 | 一切都在单个 `.app` 包内、结构固定 | 库被非主程序（如另一个库）间接加载时，基准仍是主程序目录，灵活性弱于 `@rpath` |

> [!note] `@rpath` 与库自身 install name 的配合
> `@rpath` 的精髓是**解耦**：库只在自己的 `LC_ID_DYLIB` 里声明 `@rpath/B.dylib`（"到运行时搜索路径里找我"），**具体去哪找由下游的 `LC_RPATH` 决定**。于是同一个库 B，可以被装进 App 包（下游 rpath 指 `@executable_path/../Frameworks`）、也可以被装进系统目录（下游 rpath 指 `/usr/local/lib`），库自身一字不改。`@executable_path`/`@loader_path`/`@rpath` 三者的运行时搜索细节见 [[07.Mach-O LC_LOAD_DYLIB]]。

### 5. 只属于库：为什么 `LC_ID_DYLIB` 只出现在 `MH_DYLIB`

`LC_ID_DYLIB` 是 `MH_DYLIB` 文件类型的**标志性命令**：

- **可执行文件（`MH_EXECUTE`）没有它**：可执行文件不会"被别人当库链接"，无需对外声明 install name；它有的是 [[09.Mach-O LC_MAIN]]（入口）和一堆 `LC_LOAD_DYLIB`（依赖）。
- **目标文件（`MH_OBJECT`，`.o`）没有它**：`.o` 是中间产物，install name 由最终链接成库时才确定。
- **`dlopen` 加载的 bundle（`MH_BUNDLE`）通常也没有它**：bundle 一般靠运行时 `dlopen` 路径定位，不走 install name 抄写那套。

链接器只在产物类型为 `MH_DYLIB` 时才发射 `LC_ID_DYLIB`，且**一个库通常只有一条**。所以"有没有 `LC_ID_DYLIB`"几乎是判定"这个 Mach-O 是不是动态库"的速判依据。文件类型字段见 [[02.Mach-O文件头]] 的 `filetype`。

> [!note] 架构差异
> `LC_ID_DYLIB` 与位宽无关，**32/64 位结构完全一致**（`dylib_command` 不含任何随位宽变化的地址/大小字段，三个版本/时间戳字段恒为 32 位，`lc_str` 文件态恒用 32 位 `offset`）。这与 [[04.Mach-O LC_SEGMENT - LC_SEGMENT_64]] 那种"32/64 位分两套结构"截然不同——dylib 系命令只有一套。

### 6. 与 `LC_LOAD_DYLIB` 同构、与一族 dylib 命令的关系

`dylib_command` 这一个结构被一整族"与动态库相关"的加载命令复用，全靠 `cmd` 值区分语义：

| 命令 | `cmd` 值 | 语义 |
|---|---|---|
| `LC_ID_DYLIB` | `0xd` | **声明自身身份**（install name + 版本），只在 `MH_DYLIB`。本篇主角 |
| `LC_LOAD_DYLIB` | `0xc` | 声明一个**必需依赖**（见 [[07.Mach-O LC_LOAD_DYLIB]]） |
| `LC_LOAD_WEAK_DYLIB` | `0x18`（`\| LC_REQ_DYLD`） | **弱依赖**：库缺失不报错，符号解析为 NULL（`weak_import`） |
| `LC_REEXPORT_DYLIB` | `0x1f`（`\| LC_REQ_DYLD`） | **再导出**：把依赖库的符号当作本库自己的导出（umbrella framework 常用） |
| `LC_LOAD_UPWARD_DYLIB` | `0x23`（`\| LC_REQ_DYLD`） | **向上依赖**：用于打破库间循环依赖 |
| `LC_LAZY_LOAD_DYLIB` | `0x20` | **惰性加载**库（首次用到时才加载，较少见） |

它们**结构体完全相同**（都是 `dylib_command`），解析代码可共用一套；区别只在 `cmd` 决定"这是身份声明还是某种依赖、以及依赖的强弱"。`LC_ID_DYLIB` 与 `LC_LOAD_DYLIB` 这对尤其特殊——**同构且语义互为镜像**：库用前者说"我是 `@rpath/B.dylib`"，下游用后者说"我要 `@rpath/B.dylib`"，两个字符串必须逐字节相等，`dyld` 才能把"要求"对接到"提供"。

### 7. `cmdsize` 与命令遍历

`LC_ID_DYLIB` 复用所有加载命令的统一头 `load_command{ cmd, cmdsize }`（见 [[03.Mach-O加载命令]]）。遍历 Load Commands 时靠累加 `cmdsize` 逐条跳转，对本命令而言：

- **`cmdsize` = 20（定长部分）+ install name 字符串长度（含结尾 `\0`），再向指针大小（64 位为 8）向上取整**，尾部用 `\0` 补齐对齐。所以同样一个库，install name 越长，`cmdsize` 越大；改名后 `cmdsize` 往往随之变化。
- 字符串既然计入 `cmdsize`，遍历到下一条命令就是 `ptr += cmdsize`，会**自动跳过尾随的 install name 字节**，不会把路径文本误当成下一条命令的头。
- 健壮解析器须校验 `dylib.name`（即 `lc_str.offset`）落在 `[sizeof(dylib_command), cmdsize)` 内、且字符串在 `cmdsize` 边界前有 `\0` 终止——否则按畸形文件处理。

> [!note] 改 install name 为何要 `install_name_tool`、而不能直接改字节
> 因为 install name 是**变长且计入 `cmdsize`** 的：把 `@rpath/A.dylib` 改成更长的 `@rpath/SubDir/A.dylib`，会撑大 `cmdsize`，进而挤动其后所有加载命令的偏移、影响 `mach_header.sizeofcmds`。`install_name_tool` 会正确地重排命令、更新 `cmdsize`/`sizeofcmds`、在 `__LINKEDIT`（见 [[16.Mach-O __LINKEDIT]]）里维持一致性；手抠字节几乎必然把文件改坏。若预计后续要改长，链接时可用 `ld -headerpad_max_install_names` 预留命令区空间。

## 实操：用工具查看

### 示例 1：`otool -D` 只看库自身的 ID（install name）

`otool -D` 是最直接的"读 `LC_ID_DYLIB.name`"命令，只打印库 ID 一行：

```bash
otool -D /usr/lib/libSystem.B.dylib    # 只输出该库的 install name
```

> [!warning] 示例输出为示意
> 本机为 Windows 环境，以下输出基于结构知识构造，实际数值以你机器上的 `otool` 为准。

```text
/usr/lib/libSystem.B.dylib:
/usr/lib/libSystem.B.dylib
```

> 说明：第一行是被查文件路径，第二行就是它的 install name（这里二者恰好一致，因为系统库用绝对路径当 ID）。对一个用 `@rpath` 的库，第二行会是 `@rpath/MyLib.dylib`。

### 示例 2：`otool -l` 看完整的 `LC_ID_DYLIB` 命令体

```bash
otool -l /usr/lib/libSystem.B.dylib | grep -A 5 LC_ID_DYLIB
```

> [!warning] 示例输出为示意
> 数值为构造，仅示意各字段形态。

```text
Load command 4
          cmd LC_ID_DYLIB
      cmdsize 56                    ; 20 定长 + "/usr/lib/libSystem.B.dylib\0" 补齐
         name /usr/lib/libSystem.B.dylib (offset 24)   ; install name + lc_str 偏移
   time stamp 2 Wed Dec 31 ...      ; prebinding 时代遗留，占位
      current version 1345.0.0      ; 0x05410000
compatibility version 1.0.0         ; 0x00010000
```

> 说明：`name ... (offset 24)` 印证第 1 节"`lc_str` 偏移恒为 24"；`current 1345.0.0` 与 `compatibility 1.0.0` 体现"当前版本一路上涨、兼容版本长期不动"的典型策略；`cmdsize 56` = 20 定长 + 路径字符串补齐。

### 示例 3：`otool -L` 看版本号成对显示（下游视角）

`otool -L` 列依赖时，每个库后面括号里成对显示 `compatibility version` 与 `current version`——这两个数正是各库 `LC_ID_DYLIB` 里写的（被抄到下游后回显）：

```bash
otool -L /bin/ls
```

> [!warning] 示例输出为示意

```text
/bin/ls:
	/usr/lib/libutil.dylib (compatibility version 1.0.0, current version 1.0.0)
	/usr/lib/libncurses.5.4.dylib (compatibility version 5.4.0, current version 5.4.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1345.0.0)
```

> 说明：`otool -L` 看的是**下游 `LC_LOAD_DYLIB` 里抄来的版本**，而 `otool -D`/`otool -l ...LC_ID_DYLIB` 看的是**库自身 `LC_ID_DYLIB` 里定义的版本**——正常情况下两者应一致。对比这两条命令的输出，正是排查"版本/路径对不上"的常用手法。

### 示例 4：`install_name_tool -id` 改库 ID、`-change` 改下游引用

这是把库从"绝对路径 ID"改造成"可重定位 `@rpath`"、再让下游跟上的标准工作流：

```bash
# 1) 把库自身的 install name（LC_ID_DYLIB.name）改成 @rpath 形式
install_name_tool -id @rpath/libfoo.dylib libfoo.dylib

# 2) 把使用方里对老绝对路径的引用（LC_LOAD_DYLIB.name）改成同一个 @rpath
install_name_tool -change /old/abs/path/libfoo.dylib @rpath/libfoo.dylib myapp

# 3) 给使用方加一条能命中库的运行时搜索路径（LC_RPATH），@rpath 才解析得到
install_name_tool -add_rpath @executable_path/../Frameworks myapp

# 4) 核对结果
otool -D libfoo.dylib        # 库 ID 是否已是 @rpath/libfoo.dylib
otool -L myapp               # 使用方对 libfoo 的引用是否已改为 @rpath/libfoo.dylib
otool -l myapp | grep -A 2 LC_RPATH   # rpath 是否已加上
```

> [!warning] 示例输出为示意
> 命令本身在 macOS 上可直接运行；此处不附回显，实际以你机器为准。

> [!warning] 改完二进制会使代码签名失效，需重新签名
> 在现代 macOS（尤其 Apple Silicon）上，`install_name_tool` 修改了二进制就会**让原有代码签名失效**，直接运行会被拒。改完通常要重新签名（临时签名示例：`codesign --force --sign - <binary>`）。另外 `-add_rpath` 添加的路径若已存在会报错——改一条用 `install_name_tool -rpath <old> <new>`、删一条用 `-delete_rpath <path>`。

## FAQ

> [!question] `LC_ID_DYLIB` 和 `LC_LOAD_DYLIB` 是什么关系？为什么结构一模一样？
> 二者**共用同一个 `dylib_command` 结构**，只是 `cmd` 不同（`0xd` vs `0xc`）、**语义恰好相反**：`LC_ID_DYLIB` 出现在库里、声明"我是谁"（install name + 版本）；`LC_LOAD_DYLIB` 出现在使用方里、声明"我依赖谁"。链接时，链接器把**被链接库的 `LC_ID_DYLIB.name` 原样抄进使用方的 `LC_LOAD_DYLIB.name`**，所以两个字符串必须逐字节相等，运行时 `dyld` 才能把"依赖要求"对接到"库的身份"。可以理解为：一张名片（`LC_ID_DYLIB`）被对方收进了通讯录（`LC_LOAD_DYLIB`）。

> [!question] `current_version` 和 `compatibility_version` 有什么区别？dyld 用哪个判失败？
> `current_version` 是**信息性**的"当前第几版"，可由 `NSVersionOfRunTimeLibrary()` 读回，**不参与**加载放行决策；`compatibility_version` 是库的**向后兼容承诺**，历史上**正是 dyld 用于加载校验的字段**。规则：当"库实际提供的 `compatibility_version` < 下游要求的兼容版本"且未用 `0xFFFFFFFF` 通配、且文件要求强制校验时，dyld 抛 `Incompatible library version` 拒绝加载。约定上只在破坏 ABI 时才抬 `compatibility_version`，纯新增/修 bug 只抬 `current_version`。**但注意：这套强制校验已在 macOS 12 起从 dyld 移除**——现代 macOS 上版本不匹配不再因此拒载，排错应优先看 install name / `@rpath` / 签名。

> [!question] install name 写绝对路径好还是 `@rpath` 好？
> 取决于分发方式。**系统库、装在固定位置**（如 `/usr/lib`）的库用**绝对路径**最省事——dyld 直接按路径找。**要随 `.app` 分发、或希望库可任意搬动**的，用 **`@rpath/B.dylib`** 最灵活：库只声明"到运行时搜索路径里找我"，具体目录交给下游的 `LC_RPATH`（如 `@executable_path/../Frameworks`）决定，库自身一字不改就能适配不同部署位置。`@loader_path` 适合"无论被谁加载都要找到同目录兄弟库"的嵌套 framework/插件，`@executable_path` 适合一切都在单个 App 包内的简单场景。

> [!question] 改了库的 install name，下游为什么突然找不到它了？怎么修？
> 因为下游 `LC_LOAD_DYLIB` 里记的还是**老的** install name，而你只改了库的 `LC_ID_DYLIB`——两边对不上，dyld 按老字符串去找新库（或新路径）自然失败。修法：用 `install_name_tool -change <旧install name> <新install name> <下游二进制>` 把**每一个**下游的引用同步成新值；若新 ID 是 `@rpath` 形式，还要确保下游有一条能命中库的 `LC_RPATH`。改完用 `otool -L <下游>` 核对引用、`otool -D <库>` 核对库 ID 两者一致。别忘了改完二进制要重新签名。

> [!question] 为什么只有动态库才有 `LC_ID_DYLIB`，可执行文件没有？
> 因为 `LC_ID_DYLIB` 的用途是"对外声明身份，供别人链接时抄写"。**可执行文件（`MH_EXECUTE`）不会被当作库去链接**，没有对外声明 install name 的需要，所以不带它（它有的是 `LC_MAIN` 入口和若干 `LC_LOAD_DYLIB` 依赖）。链接器只在产物是 `MH_DYLIB` 时才发射 `LC_ID_DYLIB`，且通常只有一条。因此"有没有 `LC_ID_DYLIB`"几乎可以直接判定"这是不是一个动态库"，配合 [[02.Mach-O文件头]] 的 `filetype` 字段更稳妥。

## 小结

- `LC_ID_DYLIB`（`cmd=0xd`）是**动态库声明自身 install name 与版本**的命令，**仅存在于 `MH_DYLIB`**（库），可执行文件没有，一个库通常只有一条；它是判定"是不是动态库"的标志性命令。
- 命令体复用 `dylib_command`（`load_command` 头 + 定长 `struct dylib` 16 字节 + 变长 install name），与下游的 [[07.Mach-O LC_LOAD_DYLIB]] **完全同构、语义相反**；`name` 是 `lc_str` 偏移式字符串（偏移恒 24），计入 `cmdsize`。
- **install name 是动态链接的锚点**：链接时被下游 `LC_LOAD_DYLIB` 原样抄写，运行时 `dyld` 据此定位库。绝对路径不可重定位、`@rpath` 最灵活（配合下游 `LC_RPATH`）、`@loader_path`/`@executable_path` 各有适用。
- `current_version`（信息性）与 `compatibility_version`（兼容承诺）均按 **`(X<<16)|(Y<<8)|Z`**（16/8/8 位）打包；历史上 dyld 校验"库提供的兼容版本 < 下游要求 ⇒ `Incompatible library version` 失败"，但**该强制校验自 macOS 12 起已移除**，现代排错优先看 install name/`@rpath`/签名。
- 改库 ID 用 `install_name_tool -id`、改下游引用用 `-change`、配 `@rpath` 要 `-add_rpath`；改完二进制会使代码签名失效，需重新签名。验证用 `otool -D`（库 ID）/`-L`（下游引用与版本）/`-l`（原始命令）。
