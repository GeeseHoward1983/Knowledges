# Windows 堆内部结构：NT Heap、LFH 与 Segment Heap

> [!abstract] TL;DR
> Windows 堆体系在 Windows 10 前以 **NT Heap** 为核心，由前端（Front-End，即 LFH）与后端（Back-End，FreeList + VirtualAlloc）两级组成；Windows 10 1809 起为 UWP 与系统进程引入 **Segment Heap**，将后端拆分为 VS/LFH/Large/Backend 四层。理解 `_HEAP`、`_HEAP_ENTRY`（8 字节 XOR 编码头）、`_HEAP_BUCKET`/`_HEAP_SUBSEGMENT`/UserBlocks（LFH）、`_SEGMENT_HEAP` 及其四层路由，是 Windows 平台逆向分析、堆调试与漏洞研究的核心前提。本章横向对比 glibc ptmalloc，并给出完整的 WinDbg 实战命令图谱。

## 概述与定位

### Windows 堆的历史演进

Windows 自 NT 3.5 起就提供 `HeapCreate`/`HeapAlloc`/`HeapFree` 这套 Win32 堆 API。其底层实现经历了三次重大架构迭代：

1. **NT Heap（传统后端，Windows NT 3.5 – XP）**：以双向链表 FreeList 组织空闲块，分配时首次拟合（first-fit）或最佳拟合（best-fit），碎片问题在长时间运行的服务进程中非常突出。

2. **NT Heap + LFH（Low Fragmentation Heap，Windows Vista – 8.1/10）**：针对频繁分配同一 size class 的场景，在前端引入 LFH，以桶（bucket）+子段（subsegment）的位图分配替代链表搜索，将平均分配复杂度从 O(n) 降至 O(1) 并大幅减少碎片。

3. **Segment Heap（Windows 10 1809+）**：为 UWP 进程与部分系统进程（`svchost.exe` 中的某些服务）启用，完全重写后端，引入 Backend（VirtualAlloc 大块）→ VS（Variable Size，中等）→ LFH 前端三级缓存，外加 Large block 独立路径，兼顾性能、安全与碎片控制。

> 普通桌面 Win32 程序默认仍使用 NT Heap + LFH；是否启用 Segment Heap 由进程清单（manifest）中的 `<heapType>SegmentHeap</heapType>` 或 IFEO/Image File Execution Options 注册表键控制。

### 与 Linux ptmalloc 的定位对比

| 维度 | Windows NT Heap + LFH | Linux ptmalloc2 |
|------|----------------------|-----------------|
| 主分配单元 | HeapAlloc，返回堆内指针 | malloc，返回 sbrk/mmap 指针 |
| 元数据位置 | 每个块紧前 8 字节（in-line） | 每个 chunk 紧前 8/16 字节 |
| 元数据保护 | XOR cookie 编码 | 无原生保护（tcache key 除外） |
| 小块前端 | LFH（激活后） | tcache + fastbin |
| 中块链表 | FreeList[128] + ListHint | unsorted bin + small bin + large bin |
| 大块路径 | 直接 VirtualAlloc | mmap（> mmap_threshold） |
| 多线程 | 每个 HEAP 对象独立锁 | 多 arena（per-thread arena） |
| 安全强化 | cookie、encode pointer（Vista+） | safe-linking（2.32+）、tcache key |

## 原理与机制

### NT Heap 整体架构

NT Heap 的两级架构如下：

```
┌──────────────────────────────────────────────────────────────┐
│  进程默认堆 (RtlGetProcessHeap) / 自建堆 (RtlCreateHeap)       │
│                       _HEAP 结构                              │
│                                                              │
│  ┌─────────────────────────────────────┐                     │
│  │       前端（Front-End）               │                     │
│  │  LFH（_HEAP_LOOKASIDE / _LFH_HEAP） │  ← 小块 <= 0x3F8B  │
│  └─────────────────────────────────────┘                     │
│                        ↕  miss → 后端                         │
│  ┌─────────────────────────────────────┐                     │
│  │       后端（Back-End）                │                     │
│  │  FreeList[128] + ListHint/BlocksIndex│ ← 中块             │
│  │  VirtualAlloc 大块链表              │  ← > 0x7F000 字节  │
│  └─────────────────────────────────────┘                     │
└──────────────────────────────────────────────────────────────┘
```

**分配决策链**：
1. 若 LFH 已激活且请求 size 落入 LFH 覆盖范围（≤ `0x3F8B` 字节），走 LFH 前端。
2. 否则查 FreeList 后端（首次拟合，从 FreeList[index] 开始）。
3. 若后端也无合适块，则扩展 heap segment（`VirtualAlloc` 新页）或直接用 VirtualAlloc 分配大块。

### `_HEAP` 结构解析

`_HEAP` 是整个堆的控制中心，ntdll!RtlAllocateHeap 每次都从此结构出发。关键字段（Win10 x64，偏移仅供参考，版本间有变动）：

| 偏移 | 字段 | 说明 |
|------|------|------|
| +0x000 | `Entry` (_HEAP_ENTRY) | 头部（第一个空闲块占位符） |
| +0x010 | `SegmentSignature` | 0xFFEEFF00，用于区分 Segment Heap（0xDDEEDDEE）|
| +0x018 | `SegmentFlags` | 堆标志（GROWABLE/EXECUTABLE 等） |
| +0x020 | `SegmentListEntry` | 所有 segment 的双向链表 |
| +0x058 | `TotalFreeSize` | 当前总空闲字节数（以粒度为单位） |
| +0x070 | `FreeListBitmapLength` | BlocksIndex 活跃位图长度 |
| +0x078 | `FreeHints[]` / `ListHints` | 每个 FreeList 桶的首个合适块提示指针 |
| +0x100 | `FreeLists[128]` | 128 条双向链表，索引 = size/8（小块） |
| +0x7D0 | `LargeBlocksIndex` | 超大块 AVL 树根节点 |
| +0x7E0 | `FrontEndHeap` | 指向 _LFH_HEAP 结构（LFH 激活后） |
| +0x7E8 | `FrontEndHeapType` | 0=关闭, 1=Lookaside(XP), 2=LFH(Vista+) |

WinDbg 查看：
```
dt ntdll!_HEAP @$peb+0x30   ; 默认堆地址在 PEB.ProcessHeap
dt ntdll!_HEAP <heap_addr>
```

### `_HEAP_ENTRY`：8 字节块头与 XOR 编码

每个 NT Heap 分配块（无论空闲还是已分配）的**正前方**紧跟 8 字节的 `_HEAP_ENTRY`：

```c
struct _HEAP_ENTRY {
    union {
        struct {
            USHORT Size;        // 块大小（以 8 字节粒度计）
            UCHAR  Flags;       // BUSY(0x01) | EXTRA_PRESENT(0x02) | FILL_PATTERN(0x04) | ...
            UCHAR  SmallTagIndex; // 小块 cookie
            USHORT PreviousSize; // 前一块大小（以粒度计）
            UCHAR  SegmentOffset;
            UCHAR  ExtendedBlockSignature;
        };
        struct {
            PVOID  SubSegmentCode; // LFH 模式下指向 _HEAP_SUBSEGMENT
            USHORT PreviousSize;
            UCHAR  SegmentOffset;
            UCHAR  UnusedBytes;   // = 分配粒度 - 用户请求字节数
        };
    };
};
```

**XOR 编码防护（Vista+ 引入）**：

为防止线性堆溢出直接覆盖并伪造 `_HEAP_ENTRY`，Vista 起引入了对 `_HEAP_ENTRY` 前 4 字节（Size/Flags/SmallTagIndex/PreviousSize）的 XOR 编码：

```
编码值 = 原始4字节 XOR _HEAP.Encoding.Code
```

`_HEAP.Encoding.Code` 在堆初始化时由 `RtlpGetRandomHeapCookie()` 随机生成，存放在 `_HEAP+0x50`（x64 大约位置，版本相关）。每次 HeapAlloc/HeapFree 时 ntdll 都会校验头部，若 XOR 解码后的 Flags 与实际不符则触发 `RtlpHeapReportCorruption`，默认导致进程终止。

**逆向解码流程**（WinDbg 手工）：
```
// 1. 读取 _HEAP 的编码 cookie
dt ntdll!_HEAP <heap> Encoding
// 2. 读取 _HEAP_ENTRY 原始值
dq <entry_addr> L1
// 3. XOR 解码
? <raw_value> ^ <encoding_code>
```

### FreeList 与 ListHints/BlocksIndex

NT Heap 后端维护 128 条双向 FreeList（FreeList[0..127]），其中：
- FreeList[0]：保留，实际不用于固定尺寸块
- FreeList[1]：8 字节块（1×8）
- FreeList[n]：n×8 字节块（n ≤ 127）
- FreeList[128] 之外的"大桶"（size > 127×8）通过 `LargeBlocksIndex`（AVL 树）管理

**ListHints**（Vista 起引入，又称 BlocksIndex）：为每条 FreeList 记录一个"提示"指针，直接指向最近释放或分配的块，避免每次都从链表头遍历。命中 ListHint 时分配为 O(1)；未命中时退化为链表搜索。

```mermaid
graph TD
    A[HeapAlloc 请求 n 字节] --> B{size <= 0x3F8B<br/>且 LFH 已激活?}
    B -- 是 --> C[LFH 前端分配<br/>_HEAP_BUCKET → _HEAP_SUBSEGMENT]
    B -- 否 --> D{size <= 127×8?}
    D -- 是 --> E[查 FreeList[n/8]<br/>及 ListHint]
    D -- 否 --> F{size < 0x7F000?}
    F -- 是 --> G[LargeBlocksIndex<br/>AVL 树搜索]
    F -- 否 --> H[VirtualAlloc 直接分配<br/>挂入 VirtualAllocdBlocks 链]
    E -- 命中 --> I[返回块，更新 ListHint]
    E -- 未命中 --> J[扩展 Segment 或<br/>VirtualAlloc 新页]
    G --> I
```

## 结构/算法/伪代码详解

### LFH 激活机制

LFH 不是一开始就启用的，它有一个**渐进激活**过程：

**激活条件**：对某个 size class，在 **0x11（17）次**分配后，堆管理器判断该 size 分配频繁，将其升级到 LFH 管理。具体阈值：Windows XP/Vista 时为 18 次（`0x12`），Windows 7+ 调整为 17 次（`0x11`），源码注释和部分逆向文献写 "16 次" 或 "18 次" 均指同一区间的不同计数方式。

```
// ntdll 内部（伪代码简化）
if (++bucket->AllocationCount >= HEAP_LFH_ENABLE_THRESHOLD) {
    RtlpLowFragHeapActivateBucket(heap, bucket);
}
```

激活后，`_HEAP.FrontEndHeap` 指向 `_LFH_HEAP`，`FrontEndHeapType = 2`。

### `_HEAP_BUCKET`

LFH 将 size space 切分为若干"桶"，每个桶管理一个固定 size class 的所有分配。

```c
struct _HEAP_BUCKET {
    USHORT BlockUnits;     // 每块大小（以粒度为单位）
    UCHAR  SizeIndex;      // size class 索引
    union {
        UCHAR UseAffinity;
        struct {
            UCHAR AffinityIndex : 7;
            UCHAR ActiveSubsegmentPresent : 1;
        };
    };
};
```

`_LFH_HEAP` 中有 `_HEAP_BUCKET Buckets[128]`，覆盖 size class 0–127（对应 1–128 个粒度单位，即最大 128×8=1024 字节的 LFH 范围，Vista；Win7+ 扩展到 0x3F8B 即 ~16KB）。

### `_HEAP_SUBSEGMENT` 与 UserBlocks

每个活跃的 `_HEAP_BUCKET` 绑定一个或多个 `_HEAP_SUBSEGMENT`，后者管理一整个连续的"用户块区域"（UserBlocks）：

```c
struct _HEAP_SUBSEGMENT {
    volatile LONG       LocalInfo;       // 原子操作控制字（ABA 保护）
    volatile LONG       LocalData;       // 当前可用位图状态
    _INTERLOCK_SEQ      AggregateExchg; // 无锁分配的交换序列号
    USHORT              BlockSize;       // 此 subsegment 管理的块大小
    USHORT              Flags;
    USHORT              BlockCount;      // UserBlocks 中的块总数
    UCHAR               SizeIndex;
    UCHAR               AffinityIndex;
    _HEAP_SUBSEGMENT*   SFreeListEntry;  // 指向下一个空闲 subsegment
    volatile LONG       Lock;
    _HEAP_USERDATA_HEADER* UserBlocks;  // 指向实际存放数据的连续区域
};
```

**UserBlocks** 是一段连续内存，以位图（bitmap）方式追踪每个 slot 的空闲/占用状态。分配时找到第一个 0 位（空闲 slot），置 1，返回对应地址；释放时将位清 0。由于 bitmap 操作可以用 `BSF`（bit scan forward）指令 O(1) 完成，LFH 分配性能极好。

LFH subsegment 的关键安全属性：**LFH 块的 `_HEAP_ENTRY` 头部布局与普通 NT Heap 块不同**，`SubSegmentCode` 字段经过 XOR 编码（与块地址自身 XOR），防止通过伪造 `_HEAP_ENTRY` 来操控 LFH 内部指针。

### NT Heap 分配伪代码（简化）

```c
void* RtlpAllocateHeap(HEAP* heap, size_t size, ULONG flags) {
    size_t granSize = ROUND_UP(size + sizeof(HEAP_ENTRY), HEAP_GRANULARITY);
    
    // 1. 尝试 LFH 前端
    if (heap->FrontEndHeapType == 2 && LFH_COVERS(granSize)) {
        HEAP_BUCKET* bucket = &heap->FrontEndHeap->Buckets[SIZE_TO_INDEX(granSize)];
        if (bucket->ActiveSubsegmentPresent) {
            void* block = LfhpAllocateFromSubsegment(bucket->ActiveSubsegment);
            if (block) return (HEAP_ENTRY*)block + 1;
        }
    }
    
    // 2. 后端 FreeList 搜索
    size_t idx = granSize / HEAP_GRANULARITY;
    if (idx < 128) {
        LIST_ENTRY* hint = heap->ListHints[idx];
        if (hint && DecodeEntry(hint).Size == idx) {
            RemoveEntryList(hint);
            UpdateListHint(heap, idx);
            return EncodeAndReturn(hint);
        }
        // 扫描更大的 FreeList 并切割
        for (size_t i = idx; i < 128; i++) {
            if (!IsListEmpty(&heap->FreeLists[i])) {
                // ... 取出并切割
            }
        }
    }
    
    // 3. VirtualAlloc 大块
    if (granSize > HEAP_LARGE_BLOCK_THRESHOLD) {
        void* mem = VirtualAlloc(NULL, size, MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE);
        InsertVirtualAllocBlock(heap, mem, size);
        return (HEAP_ENTRY*)mem + 1;
    }
    
    // 4. 扩展 segment
    return RtlpExtendHeap(heap, granSize);
}
```

### NT Heap 释放伪代码（简化）

```c
void RtlpFreeHeap(HEAP* heap, void* ptr) {
    HEAP_ENTRY* entry = (HEAP_ENTRY*)ptr - 1;
    
    // 1. 校验编码头
    HEAP_ENTRY decoded = DecodeEntry(entry, heap->Encoding);
    if (!ValidateEntry(decoded))
        RtlpHeapReportCorruption(heap, entry); // 终止进程
    
    // 2. LFH 块？
    if (decoded.Flags & HEAP_ENTRY_LFH_FLAG) {
        LfhpFreeBlock(heap->FrontEndHeap, entry, decoded);
        return;
    }
    
    // 3. 尝试向后合并（coalescing）
    if (!(next->Flags & HEAP_ENTRY_BUSY)) {
        CoalesceWithNext(entry, next);
    }
    // 向前合并
    if (!(decoded.Flags & HEAP_ENTRY_LAST_ENTRY)) {
        HEAP_ENTRY* prev = entry - decoded.PreviousSize;
        if (!(DecodeEntry(prev).Flags & HEAP_ENTRY_BUSY))
            CoalesceWithPrev(prev, entry);
    }
    
    // 4. 插回 FreeList
    size_t idx = entry->Size;
    InsertTailList(&heap->FreeLists[min(idx, 128)], &entry->FreeList);
    UpdateListHint(heap, idx);
}
```

### Segment Heap 四层架构（Win10 1809+）

Segment Heap 的 `_SEGMENT_HEAP` 结构是完全独立的新实现，与 NT Heap 的 `_HEAP` 在逻辑上平行但代码路径分离。进入条件：`_HEAP.SegmentSignature == 0xDDEEDDEE`。

```
_SEGMENT_HEAP
├── Backend（VirtualAlloc 大块管理层）
│     _HEAP_SEG_CONTEXT × 2（偶数/奇数 segment）
│     每个 segment = VirtualAlloc 的 2MB 对齐区域
│
├── LFH（前端，小块 ≤ 16KB，与 NT Heap LFH 概念类似但实现独立）
│     _HEAP_LFH_CONTEXT
│       → _HEAP_LFH_BUCKET[128]
│         → _HEAP_LFH_SUBSEGMENT
│           → slots bitmap
│
├── VS（Variable Size，中等块 ≤ 128KB）
│     _HEAP_VS_CONTEXT
│       → _HEAP_VS_CHUNK_HEADER（每块 16 字节头）
│       → 红黑树（大小 + 地址排序）空闲管理
│
└── Large（> 128KB）
      直接 VirtualAlloc，元数据在 _HEAP_LARGE_ALLOC_DATA
      按地址排序的 AVL 树管理
```

**路由逻辑**（Segment Heap）：

```
size ≤ 16KB      → LFH 前端（优先）
16KB < size ≤ 128KB → VS 层（Variable Size）
size > 128KB     → Large 直接 VirtualAlloc
任何层 miss       → Backend（从 segment 补充页给 LFH/VS）
```

### `_SEGMENT_HEAP` 关键字段

```c
// 简化布局，Win10 x64
struct _SEGMENT_HEAP {
    _HEAP_LOCK            Lock;
    RTL_HP_SEG_ALLOC_POLICY SegAllocPolicy;
    ULONG                 GlobalFlags;        // 可选全局 PageHeap 标志
    _HEAP_LFH_CONTEXT     LfhContext;
    _HEAP_VS_CONTEXT      VsContext;
    _RTL_HP_ENV_HANDLE    EnvHandle;
    PVOID                 Callbacks;          // HeapDestroyCallback 等
    _HEAP_SEG_CONTEXT     SegContexts[2];    // 两个 segment 管理区
    _HEAP_VS_CONTEXT      LargeAllocMetadata;
    volatile ULONGLONG    LargeReservedPages;
    volatile ULONGLONG    LargeCommittedPages;
    RTL_RUN_ONCE          StackTraceInitVar;
};
```

### VS 层的 chunk 头部

VS 层（Variable Size）不使用传统的 8 字节 `_HEAP_ENTRY`，改用 16 字节的 `_HEAP_VS_CHUNK_HEADER`：

```c
struct _HEAP_VS_CHUNK_HEADER {
    union {
        struct {
            ULONG MemoryCost  : 16; // 内存代价（页 pin 数）
            ULONG UnsafeSize  : 16; // 未 XOR 保护的大小字段
        };
        ULONG EncodedSegmentPageOffset; // XOR 编码：offset XOR cookie XOR addr>>4
    };
    union {
        struct {
            ULONGLONG Allocated : 1;
            ULONGLONG UnsafePrevSize : 15;
            ULONGLONG Padding : 48;
        };
        ULONGLONG HeaderBits;
    };
};
```

VS 层的编码 cookie 存放在 `_HEAP_VS_CONTEXT.EncodedCommitPageCount` 附近，实际校验由 `RtlpHpVsChunkHeaderEncode`/`Decode` 完成。

### WinDbg 堆分析命令大全

#### 基础信息

```windbg
!heap                           ; 列出所有堆（地址、类型、标志）
!heap -s                        ; 每个堆的摘要统计（块数、总大小）
!heap <heap_addr>               ; 指定堆的详细信息
!heap -v <heap_addr>            ; 验证堆完整性（遍历所有块校验 cookie）
```

#### 查找特定地址属于哪个堆块

```windbg
!heap -x <address>              ; 反向查找：address 属于哪个堆的哪个块
!heap -x -v <address>           ; 同上，并显示块详情（大小、标志、前后块）
```

示例输出解读：
```
HEAP_ENTRY  Size  Prev  Flags    UserPtr  UserSize  state
0x1234ff8   0008  0000  [07]     0x123500 0x3c      busy
```
- `0x1234ff8`：`_HEAP_ENTRY` 地址（用户数据在 `0x1234ff8 + 8 = 0x123500`）
- `Size = 0x008`：块大小 = 8 × 8 = 64 字节（粒度单位）
- `[07]`：Flags = 0x07（BUSY | EXTRA_PRESENT | FILL_PATTERN）
- `UserSize = 0x3c`：用户请求的 60 字节（总 64 字节 - 8 字节头 = 56 字节可用，UnusedBytes=4）

#### LFH 专项

```windbg
!heap -l                        ; 列出所有堆的 LFH 状态
!heap -i <heap_addr>            ; 堆内部结构，包括 LFH bucket 详情
dt ntdll!_LFH_HEAP @poi(<heap>+0x7e0)
dt ntdll!_HEAP_SUBSEGMENT <subseg_addr>
dt ntdll!_HEAP_USERDATA_HEADER <userblocks_addr>
```

#### Segment Heap 专项

```windbg
dt ntdll!_SEGMENT_HEAP <heap_addr>
dt ntdll!_HEAP_LFH_CONTEXT <heap_addr+offset>
dt ntdll!_HEAP_VS_CONTEXT <heap_addr+offset>
!heap -c <address>              ; VS chunk 信息（Win10 Segment Heap）
```

#### 手工解码 `_HEAP_ENTRY`

设堆地址为 `heap`，块头地址为 `entry`：
```windbg
; 读取编码 cookie（_HEAP.Encoding 偏移约 0x50，版本相关）
dq <heap>+0x50 L2               ; 显示 Encoding.Code（两个 ULONG_PTR）

; 读取原始块头
dq <entry> L1                   ; 8 字节原始值

; 在 WinDbg 中计算解码

```

更便捷的方式用 `!heap -x <entry_or_userptr>`，WinDbg 自动解码并展示。

### 调试实战：定位堆损坏

**场景**：程序随机崩溃，调用栈在 `ntdll!RtlpHeapReportCorruption`。

1. 设置堆调试标志（需在进程启动前设置，或用 GFlags）：
```windbg
!gflag +htc +hpa       ; 开启 Heap Tail Check 和 Full Page Heap
```

2. 运行程序，等待崩溃：
```windbg
bp ntdll!RtlpHeapReportCorruption
g
; 触发后查看第一个参数（损坏的块地址）
; 在 x64 中第一个参数在 rcx，第二个在 rdx
.echo 损坏块地址
r rcx
!heap -x @rcx
!heap -v <heap_base>
```

3. 用 `!heap -x -v <corrupt_addr>` 查看前后块，判断是 write-beyond-end（尾部 tag 被覆盖）还是 use-after-free（已释放块的 FreeList 指针被污染）。

### GFlags / PageHeap

**GFlags（Global Flags）** 是 Windows 内建的堆调试工具，可通过以下方式启用：

```cmd
; 命令行（需要 Debugging Tools for Windows）
gflags.exe /p /enable myapp.exe /full   ; 开启 Full PageHeap（每次分配一页 guard page）
gflags.exe /p /enable myapp.exe         ; 普通 PageHeap（末尾追加 guard pattern）
gflags.exe /p /query myapp.exe          ; 查询当前设置
gflags.exe /p /disable myapp.exe        ; 关闭
```

**PageHeap 原理**：
- **普通 PageHeap**（`/enable` 不加 `/full`）：在每个块尾追加 `0xDC` 填充字节和 `0xAB` guard pattern，HeapFree 时校验是否被覆盖，捕获 write-beyond-end。
- **Full PageHeap**（`/full`）：每次分配都用一个完整内存页对齐，紧接一个 `MEM_NOACCESS` 保护页，写越界立即触发 access violation，精确定位越界位置，但内存消耗极大。

GFlags 相关注册表路径：
```
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\<appname.exe>
  GlobalFlag = 0x02000000 (NtGlobalFlag: FLG_HEAP_PAGE_ALLOCS)
  PageHeapFlags = ...
```

### 堆喷射与堆风水基础

理解堆结构对于逆向分析和漏洞研究同样重要。以下是两个基础概念（不涉及具体利用，仅作原理说明）：

**堆喷射（Heap Spray）**：通过大量分配相同大小的对象，使堆中某个地址范围以极大概率被我们的数据填充，配合其他漏洞（如 Use-After-Free）来控制执行流。理解 LFH 的 UserBlocks 布局有助于分析喷射是否有效（LFH 中同 size class 的分配是连续的，非常利于喷射）。

**堆风水（Heap Grooming / Feng Shui）**：通过精心控制分配/释放顺序，使目标对象紧邻可控数据，从而使溢出或 UAF 的影响可预测。理解 FreeList 的首次拟合行为和 LFH 的桶分配机制，是设计堆风水的前提。

在逆向分析中，可以用 WinDbg 的 `!heap -t` 追踪特定 size class 的分配历史：
```windbg
; 追踪 0x40 字节的分配/释放
!heap -t 0x40
```

## 安全性与正确使用

### 正确使用 Windows 堆 API

Windows 堆 API 虽然有 XOR cookie 保护，但这不是让开发者放松的理由。以下是正确使用的核心原则：

**1. 配对使用，禁止混用**

`HeapAlloc` 分配的内存必须用 `HeapFree` 释放，且必须使用**同一个堆句柄**：
```c
HANDLE hHeap = HeapCreate(0, 0, 0);
PVOID  ptr   = HeapAlloc(hHeap, HEAP_ZERO_MEMORY, 256);
// ... 使用 ptr
HeapFree(hHeap, 0, ptr);  // ← 必须用 hHeap，不能用 GetProcessHeap()
HeapDestroy(hHeap);
```

混用 `malloc`/`HeapFree` 或 `new`/`HeapFree` 是未定义行为，在某些 CRT 版本中会立即崩溃。

**2. 检查返回值**

`HeapAlloc` 在分配失败时默认返回 `NULL`（若未设置 `HEAP_GENERATE_EXCEPTIONS` 标志），必须检查：
```c
PVOID buf = HeapAlloc(GetProcessHeap(), 0, size);
if (!buf) {
    // 处理 OOM
    SetLastError(ERROR_NOT_ENOUGH_MEMORY);
    return FALSE;
}
```

若设置了 `HEAP_GENERATE_EXCEPTIONS`，失败时会抛出 `STATUS_NO_MEMORY` 结构化异常（SEH），需用 `__try/__except` 捕获。

**3. 使用 `HEAP_ZERO_MEMORY` 避免信息泄漏**

不要假设分配的内存已清零；若结构中含有指针或敏感字段，应使用 `HEAP_ZERO_MEMORY` 标志：
```c
PVOID buf = HeapAlloc(heap, HEAP_ZERO_MEMORY, sizeof(MY_STRUCT));
```

这等价于 `calloc`，性能略差于普通分配但避免未初始化读（Uninit-read）导致的信息泄漏。

**4. 防止 Double-Free**

释放后立即将指针置 NULL，并在释放前检查：
```c
HeapFree(heap, 0, ptr);
ptr = NULL;
// 后续代码检查 if (ptr) 即可避免 double-free
```

NT Heap 的 LFH 对 Double-Free 有部分检测（位图状态校验），但传统 FreeList 路径的 Double-Free 检测能力有限，可能导致静默损坏。

**5. 用 App Verifier 做常规堆检查**

Application Verifier（`appverif.exe`）是 Windows 内建的动态分析工具，开启 Heaps 检查选项后相当于自动启用 PageHeap，并对以下情形报告：
- Use-After-Free
- Buffer Overrun（尾部 guard 被覆盖）
- Double-Free
- HeapHandle 不匹配

使用方式：
```cmd
appverif.exe -enable Heaps -for myapp.exe
myapp.exe          ; 运行，异常将在 Debugger 中断
appverif.exe -disable * -for myapp.exe   ; 清理
```

**6. 线程安全**

默认 `HeapCreate` 创建的堆带锁（`HEAP_NO_SERIALIZE` 未设置），多线程并发 `HeapAlloc`/`HeapFree` 是安全的。若用 `HEAP_NO_SERIALIZE` 创建"无锁堆"，则调用方必须自行同步。

### XOR Cookie 的局限性

虽然 Vista+ 的 XOR 编码防护能检测出对 `_HEAP_ENTRY` 的覆盖，但它有两个局限：
1. **仅在 HeapAlloc/HeapFree 时校验**：若程序先修改元数据，再调用一系列无关的堆操作，损坏可能在远处触发崩溃，增加调试难度（此时 PageHeap 可精确定位）。
2. **仅保护 entry 头部，不保护用户数据内的指针/函数指针**：攻击者可通过越界写覆盖对象内的虚函数表指针，绕过堆 cookie 检测。

## 小结

Windows 堆体系的核心要点：

| 组件 | 位置 | 关键结构 | 分配算法 | 保护机制 |
|------|------|----------|----------|----------|
| NT Heap 后端 | ntdll.dll | `_HEAP`, `_HEAP_ENTRY` | FreeList 首次拟合 + ListHint | XOR cookie（Vista+） |
| NT Heap LFH | ntdll.dll | `_LFH_HEAP`, `_HEAP_BUCKET`, `_HEAP_SUBSEGMENT` | 位图 O(1)，17次激活 | SubSegmentCode XOR + 地址 |
| Segment Heap VS | ntdll.dll | `_SEGMENT_HEAP`, `_HEAP_VS_CONTEXT` | 红黑树 best-fit | EncodedSegmentPageOffset |
| Segment Heap LFH | ntdll.dll | `_HEAP_LFH_CONTEXT` | 同 NT Heap LFH 概念 | Slot bitmap 校验 |
| Large blocks | ntdll.dll | VirtualAlloc direct | N/A（OS 页管理） | MEM_NOACCESS guard（PageHeap）|

理解这套体系的价值：
- **性能调优**：知道何时触发 LFH（同 size 17次），何时退化到 FreeList，才能设计出分配友好的数据结构。
- **调试效率**：用 `!heap -x <addr>`、PageHeap、App Verifier 能将"随机崩溃"精确定位到损坏点。
- **逆向分析**：解码 `_HEAP_ENTRY` 的 XOR 头，理解 LFH 的 UserBlocks 布局，是分析 Windows 堆相关漏洞的必要基础。
- **平台对比**：Windows 的 XOR cookie 对应 glibc 的 safe-linking；LFH 对应 tcache + fastbin；Segment Heap Backend 对应 ptmalloc 的 mmap 路径——两套体系解决相同问题，但机制细节差异显著。

Windows 11 和最新的 Segment Heap 还在持续演进，例如引入了 Guard Page 机制和更细粒度的 VS chunk 保护，逆向研究者需以每个 ntdll 版本为单位验证结构偏移，不可完全依赖静态文档。
