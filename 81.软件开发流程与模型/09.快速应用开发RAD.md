# 软件开发流程与模型(九)快速应用开发RAD

> [!abstract] 速览
> **快速应用开发（RAD, Rapid Application Development）** 由 James Martin 于 **1991 年**系统化，主张用 **构件复用 + 强力工具 + 用户深度参与 + 时间盒** 大幅压缩开发周期，靠一系列原型快速逼近成品。
> 它反对"长周期、重文档"的 [[03.瀑布模型|瀑布]]，信奉"**够用就好、快速见效**"。
> 一句话：**少写、多拼、快交付**——能复用就不重写，能用工具生成就不手敲。RAD 是今天 **低代码 / 无代码** 浪潮的思想先祖。本篇深入其阶段、四要素、时间盒/JAD，以及它在低代码时代的复活。

## 1. RAD 是什么

RAD 认为：只要**复用构件 + 工具加速 + 用户全程参与**，就能在**数周到数月**内交付业务系统，而非动辄一年。它把"快速"刻进基因。

## 2. RAD 的阶段

```mermaid
graph LR
    A[需求规划<br/>Requirements Planning] --> B[用户设计<br/>原型迭代+JAD] --> C[快速构造<br/>构件复用+工具生成] --> D[切换交付<br/>Cutover]
    B -. 用户持续参与 .- C
```

| 阶段 | 重点 |
| --- | --- |
| 需求规划 | 快速锁定范围与目标 |
| 用户设计 | 与用户一起做原型、反复确认（JAD） |
| 快速构造 | 用工具 / 构件快速实现 |
| 切换交付 | 数据迁移、培训、上线 |

## 3. RAD 的四大要素

| 要素 | 作用 |
| --- | --- |
| **原型 Prototyping** | 快速可见、与用户对齐（见 [[05.原型模型]]） |
| **构件复用 Reuse** | 不重复造轮子，拼装已有构件 |
| **强力工具** | CASE 工具 / 代码生成器 / 低代码平台 |
| **SWAT 小团队** | "Skilled With Advanced Tools"，精干、高效、用户在内 |

## 4. 时间盒（Timeboxing）

RAD 用**固定时间盒**约束范围：时间到就交付当前可用版本，**砍功能不砍工期**——这与敏捷的"固定迭代"一脉相承，也是控制范围蔓延的利器。

## 5. JAD：联合应用设计

**JAD（Joint Application Design）** 是 RAD 的关键实践：把用户、开发、决策者**关进同一个工作坊**，集中、密集地一起设计，而非来回拉锯。它大幅缩短了需求沟通周期。

## 6. 优点

| 优点 | 说明 |
| --- | --- |
| 交付快、见效快 | 周期以周计 |
| 用户满意度高 | 全程参与、所见即所得 |
| 适合业务可视化系统 | 表单 / 流程 / 管理类 |
| 降低后期返工 | 原型早对齐 |

## 7. 缺点

| 缺点 | 说明 |
| --- | --- |
| 强依赖**可复用构件**与**成熟工具** | 没有则优势消失 |
| 不适合大型 / 高复杂 / 强算法系统 | 拼装搞不定核心算法 |
| 性能 / 架构可能被牺牲 | 求快易留隐患 |
| 需用户高度投入 | 用户没空则难落地 |

## 8. 适用与不适用

| ✅ 适合 | ❌ 不适合 |
| --- | --- |
| 表单 / 流程 / 管理类业务系统 | 高性能 / 强算法 / 底层系统 |
| 工期紧、有成熟构件 / 低代码 | 无可复用资产 |
| 规模中小、用户能深度参与 | 超大规模、用户难参与 |

## 9. RAD vs 瀑布 vs 敏捷

| 维度 | RAD | [[03.瀑布模型\|瀑布]] | [[13.Scrum框架\|敏捷]] |
| --- | --- | --- | --- |
| 速度 | **极快** | 慢 | 快 |
| 依赖 | 工具 + 构件 | 文档 | 团队 + 纪律 |
| 文档 | 轻 | 重 | 中 |
| 用户参与 | **极高** | 低 | 高 |

## 10. 真实案例：低代码搭内部系统

某公司要在 3 周内上线"设备报修系统"：用低代码平台拖拽表单、配置审批流、复用通知 / 权限构件，与需求方边搭边改——**第 2 周就给出可用版本**，第 3 周上线。换成瀑布，光需求与设计文档就不止 3 周。

## 11. RAD 的现代化身：低代码 / 无代码

| 平台 | 定位 |
| --- | --- |
| OutSystems / Mendix | 企业级低代码 |
| Microsoft Power Apps | 微软生态 |
| 宜搭 / 简道云 / 钉钉 & 飞书低代码 | 国内办公生态 |
| Retool | 内部工具快速搭建 |

> [!note]
> 低代码 = RAD 理念的现代实现：**构件复用(组件库) + 强力工具(可视化编辑器) + 用户参与(业务人员自助) + 时间盒(快速交付)**——四要素一个不少。变的是工具，不变的是"少写多拼"的思想。

## 12. RAD 与构件化 / 微服务

RAD 的"构件复用"思想，在今天体现为**组件库、SDK、API 经济、微服务**——能调用现成服务就不自己造。[[28.平台工程与内部开发者平台|平台工程]]的"黄金路径 + 自助平台"也是 RAD 精神的延续：让开发者快速拼装、自助交付。

## 13. 工具链

低代码平台（OutSystems、Mendix、Power Apps、宜搭）、表单 / 流程引擎、构件库、代码生成器、API 网关。

## 14. 常见误区与面试要点

> [!warning] 易错点
> - **RAD = 敏捷？** 不。RAD 早于敏捷，**更依赖工具与构件复用**；敏捷更强调团队协作与迭代纪律。
> - **RAD 适合所有项目？** 不。复杂算法、超大规模、强性能要求不适合。
> - **RAD 不需要设计？** 仍需，但**轻量**且与构造高度交织（JAD）。
> - **低代码 = RAD？** 低代码是 RAD 的现代实现，RAD 是更广的方法论。
> - **时间盒里做不完怎么办？** 砍功能、保工期，而非延期。

## 15. 对常见说法的修正

> [!note] 修正清单
> 1. **"RAD 已经过时"**——它的内核（复用 + 工具 + 用户参与 + 时间盒）在**低代码 / 无代码**浪潮中强势复活。
> 2. **"RAD = 糙快猛、必然低质"**——若有成熟构件与工具，RAD 既快又稳；低质往往源于滥用而非方法本身。

## 16. 一句话记忆

> **RAD** = 少写、多拼、快交付：靠**构件复用 + 强力工具 + 用户全程参与(JAD) + 时间盒**把周期压到最短——今天的低代码平台，就是 RAD 的转世。
