# 软件开发流程与模型（50）· C4 架构模型

> [!abstract] TL;DR
> **C4 模型**是由 Simon Brown 创建的轻量级架构可视化框架，用"地图缩放"隐喻将软件系统拆分为 **System Context（系统上下文）→ Container（容器）→ Component（组件）→ Code（代码）** 四层抽象，不同层面向不同受众，按需展开细节。它不强制记号法（UML 非必须），可与 Structurizr DSL、PlantUML C4、Mermaid C4、draw.io 等工具结合，实现**架构即代码**。C4 解决的核心问题是：团队用同一张图说不清楚"大图"与"细节"的受众错配困境。

## 概述与定位

### 架构可视化的困境

软件架构文档长期存在一个两难困境：要么图太粗（一张方框箭头图涵盖所有层次，技术细节和业务意图混在一起），要么图太细（直接跳到类图或 UML 组件图，非技术干系人无从理解）。团队在白板上画的"架构图"往往既无统一语义，也无受众意识——同一张图试图同时满足 CTO、开发者和运维工程师，结果谁都看得一头雾水。

### Simon Brown 与 C4 的诞生

**C4 模型**由英国软件架构师 **Simon Brown** 在 2010 年代逐步提炼并公开，核心思想受 **地图缩放（Map Zoom）** 启发：就像 Google Maps 可以从世界地图逐步缩放到街道级别，架构图也应当分层表达，每一层有自己的粒度、受众和目的。"C4"得名于四层抽象的英文首字母：**C**ontext、**C**ontainer、**C**omponent、**C**ode。

C4 在 2010 年代末迅速成为架构沟通领域的事实标准，原因在于：

- **门槛极低**：不需要掌握完整 UML，开发者只用学四个核心概念就能上手。
- **受众驱动**：明确规定每层图的目标读者，避免"一图服众"的无效沟通。
- **工具友好**：与多种文本化工具集成，支持架构即代码，版本可追溯。
- **可扩展**：除四层核心图外，还提供 System Landscape、Dynamic、Deployment 等补充视角。

C4 不是 UML 的替代品，而是 UML 的**使用指南**——它告诉你"在哪一层该画什么"，具体记号可以用 UML，也可以用自定义图形，只要语义清晰、图例完备即可。

## 原理与机制

### "地图缩放"隐喻的核心认知

理解 C4 的关键是接受"**不同层级对应不同问题**"这一前提：

| 缩放层级 | 核心问题 | 类比 |
| --- | --- | --- |
| Level 1：Context | 这个系统做什么？谁用它？它与哪些外部系统交互？ | 国家地图：只看边界与相邻国家 |
| Level 2：Container | 系统内部由哪些可独立部署/运行的单元组成？它们如何通信？ | 城市地图：看区域划分与主干道 |
| Level 3：Component | 每个容器内部有哪些模块/服务？模块之间如何协作？ | 街道地图：看具体道路与建筑 |
| Level 4：Code | 每个组件内部的类/接口是什么？ | 建筑平面图：看每个房间布局 |

### 四层抽象详解

**Level 1：系统上下文图（System Context Diagram）**

这是最高层级的图，目的是回答"**这个系统在更大的生态中处于什么位置**"。图中包含：
- 你正在构建/描述的**软件系统**（通常是一个方框，中心）
- 与该系统交互的**用户（Person）**：内部用户、外部客户、管理员等
- 与该系统通信的**外部系统（External System）**：第三方服务、遗留系统、合作伙伴 API 等
- 各元素之间的**关系/交互**（箭头 + 简短描述）

这张图**不展示技术细节**，受众是**所有干系人**——包括业务方、产品经理、架构师和开发者。它回答的是"这个系统的边界在哪里"这个最基础的问题，是一切后续讨论的共同语言基础。

**Level 2：容器图（Container Diagram）**

"容器"在 C4 中是个特定术语，指**可以独立部署或运行的技术单元**，例如：
- Web 应用（React SPA、服务器端渲染应用）
- API 服务（REST API、GraphQL 服务）
- 数据库（PostgreSQL 实例、Redis 集群）
- 消息队列（Kafka、RabbitMQ）
- 移动端应用（iOS App、Android App）
- 微服务中的每个独立服务

注意 C4 的"容器"与 Docker 容器不是同一概念，虽然 Docker 容器往往对应 C4 的一个容器。C4 容器的判断标准是"**能否独立部署、独立运行**"。

容器图展示系统内部的容器构成，以及容器之间、容器与外部系统之间的通信方式（HTTP、gRPC、消息队列、数据库连接等）。受众主要是**技术团队成员**——开发者、架构师、DevOps 工程师。

**Level 3：组件图（Component Diagram）**

组件图进一步放大某一个容器的内部结构，展示容器内的**逻辑模块、服务、层次结构**。一个"组件"大致对应代码中的一个**包、模块、命名空间或一组协同工作的类**（如"用户认证组件"、"订单处理服务"、"通知发送器"）。

组件图是四层中**最容易失控的一层**——如果团队为系统中每个容器都维护详细的组件图，维护成本会急剧上升。实践建议：只为**核心的、频繁讨论的容器**维护组件图，其他按需生成。

受众是**开发者**，特别是需要理解某个服务内部结构的新成员或跨团队协作者。

**Level 4：代码图（Code Diagram）**

最细粒度，展示类、接口、继承、依赖关系——本质上是 UML 类图。Simon Brown 明确建议：**Level 4 通常不需要手动维护**，因为大多数 IDE 和工具能自动从代码生成。对于某些特别复杂的算法逻辑或关键的领域模型，可以按需绘制。

### 元素与关系的语义约定

C4 对图中的元素定义了明确的语义（尽管不强制特定的视觉记号）：

| 元素类型 | 语义 | 出现层级 |
| --- | --- | --- |
| Person | 人类用户或角色 | L1、L2 |
| Software System | 整个软件系统 | L1 |
| Container | 可独立部署的技术单元 | L2、L3 |
| Component | 容器内的逻辑模块 | L3 |
| Relationship | 元素间的交互，需标注协议/技术 | 所有层 |

**图例（Legend）是必须的**：每张 C4 图都应附图例，说明方框/颜色/形状的含义。这是 C4 非正式但重要的约定——"如果你用颜色区分系统内外，图例必须说明颜色的语义"。

## 结构/算法/伪代码详解

### 四层缩放关系的可视化

```mermaid
flowchart TD
    subgraph L1["Level 1：System Context（系统上下文）"]
        direction LR
        User["👤 用户<br/>Person"]
        Sys["📦 目标系统<br/>Software System"]
        ExtSys["🌐 外部系统<br/>External System"]
        User -->|"使用"| Sys
        Sys -->|"调用 API"| ExtSys
    end

    subgraph L2["Level 2：Container（容器）"]
        direction LR
        WebApp["🖥 Web App<br/>React SPA"]
        API["⚙️ API 服务<br/>Node.js REST"]
        DB["🗄 数据库<br/>PostgreSQL"]
        MQ["📨 消息队列<br/>Kafka"]
        WebApp -->|"HTTPS / JSON"| API
        API -->|"SQL"| DB
        API -->|"publish event"| MQ
    end

    subgraph L3["Level 3：Component（组件）"]
        direction LR
        AuthComp["🔐 认证组件<br/>AuthService"]
        OrderComp["📋 订单组件<br/>OrderService"]
        NotifyComp["🔔 通知组件<br/>NotificationService"]
        AuthComp -->|"验证 token"| OrderComp
        OrderComp -->|"触发通知"| NotifyComp
    end

    subgraph L4["Level 4：Code（代码）"]
        direction LR
        IOrder["«interface»<br/>IOrderRepository"]
        OrderRepo["OrderRepositoryImpl"]
        OrderSvc["OrderService"]
        OrderSvc --> IOrder
        IOrder <|.. OrderRepo
    end

    L1 -->|"放大目标系统"| L2
    L2 -->|"放大 API 服务容器"| L3
    L3 -->|"放大订单组件"| L4
```

### 补充图类型

除四层核心图外，C4 还定义了三种补充视角：

**系统全景图（System Landscape Diagram）**

本质上是"多个系统的 Level 1 展开"——在组织层面展示所有软件系统及其相互关系，适合向企业架构师或 CTO 说明"我们整个技术生态是怎样的"。它不聚焦于某一个系统的内部，而是展示**系统间的依赖网络**。

**动态图（Dynamic Diagram）**

描述特定**业务场景或用例**下，元素之间的交互序列（类似 UML 时序图，但不限于类级别）。例如"用户登录"这个用例涉及哪些容器/组件的协作，按时间顺序展示消息流转。动态图可以在任意层级绘制（容器间的动态交互、组件间的动态交互）。

**部署图（Deployment Diagram）**

将容器图"映射"到实际的基础设施上——展示哪些容器运行在哪些节点（VM、Kubernetes Pod、云服务区域）上，节点之间如何通信，适合 DevOps 工程师和运维团队理解系统的物理拓扑。

### 符号与图例约定

C4 **没有强制的视觉记号法**，但推荐以下约定（尤其使用 Structurizr 时的默认风格）：

- **方框**代表软件元素（系统、容器、组件），**椭圆**代表人
- 外部系统/人员通常用**灰色填充**，本系统元素用**彩色填充**
- 箭头从调用方指向被调用方，标注**通信协议/技术**（如 "HTTPS"、"gRPC"、"消息"）
- 每个元素框内应包含：**名称**（粗体）、**类型标注**（如 `[Container: Java/Spring Boot]`）、**简短描述**
- 每张图应有**标题**和**图例**

Structurizr 的渲染风格已成为业界参考，但完全允许团队用 UML 记号（方框 + 构造型）、draw.io 自定义图形、甚至 Mermaid 的 flowchart 语法来绘制 C4 图，只要语义一致即可。

## 工具视角与实战

### Structurizr 与 C4 DSL（架构即代码的核心工具）

**Structurizr** 是 Simon Brown 本人开发的官方工具，提供 **DSL（领域专用语言）** 来文本化描述架构模型，然后自动生成各层图：

```
workspace {
    model {
        user = person "用户"
        system = softwareSystem "电商系统" {
            webapp = container "Web App" "React SPA" "JavaScript"
            api = container "API 服务" "处理业务逻辑" "Node.js"
            db = container "数据库" "持久化存储" "PostgreSQL"
        }
        extPayment = softwareSystem "支付网关" "外部" {
            tags "External System"
        }

        user -> webapp "浏览/下单"
        webapp -> api "HTTPS/JSON"
        api -> db "SQL"
        api -> extPayment "HTTPS"
    }

    views {
        systemContext system "SystemContext" {
            include *
            autoLayout
        }
        container system "Containers" {
            include *
            autoLayout
        }
    }
}
```

DSL 文件与代码放在同一仓库（如 `docs/architecture/workspace.dsl`），通过 Git 进行版本管理——这正是"架构即代码"理念的体现：架构模型的变更有 commit 记录、可 diff、可 review。

Structurizr 提供云端渲染服务（structurizr.com）和本地 Docker 镜像，团队可以选择自托管。

### PlantUML C4 扩展

PlantUML 社区提供了 `C4-PlantUML` 宏库，允许在 PlantUML 语法中使用 C4 语义：

```plantuml
@startuml
!include C4_Context.puml

Person(user, "用户", "普通消费者")
System(ecommerce, "电商系统", "处理订单和支付")
System_Ext(payment, "支付网关", "第三方支付服务")

Rel(user, ecommerce, "浏览/下单", "HTTPS")
Rel(ecommerce, payment, "发起支付", "HTTPS/REST")
@enduml
```

PlantUML C4 的优势是可以嵌入大多数文档系统（Confluence、GitLab Wiki、AsciiDoc）中直接渲染，适合已有 PlantUML 基础设施的团队。

### Mermaid C4 支持

Mermaid 从 v10 起支持 C4 语法（`C4Context`、`C4Container` 等类型），可直接在 Markdown 文件、GitHub、Obsidian 等支持 Mermaid 的平台中渲染，无需额外工具。

### draw.io 与手绘风格

对于不需要"架构即代码"的场景（如快速白板讨论），draw.io（diagrams.net）提供了 C4 形状库，可以拖拽绘制符合 C4 语义的图表，然后导出为 SVG/PNG 嵌入文档。

### 工具选型建议

| 场景 | 推荐工具 |
| --- | --- |
| 需要版本管理、与代码同仓库 | Structurizr DSL |
| 已有 PlantUML 基础设施 | C4-PlantUML |
| Markdown 文档（GitHub/Obsidian） | Mermaid C4 |
| 临时白板讨论、非技术受众 | draw.io / Lucidchart |
| 大型组织、多团队协作 | Structurizr Cloud |

## 安全性与正确使用

### 正确落地：受众优先原则

C4 最容易被误用的方式是**忽视受众**——把 Level 3 的组件图拿去给业务方演示，或者在架构评审会上只展示 Level 1 而让开发者看不到技术细节。

**正确做法**：在每次架构沟通前，先明确受众，然后选择对应层级：
- 向业务方/产品经理解释系统边界 → Level 1 Context 图
- 向开发团队说明技术选型与服务划分 → Level 2 Container 图
- 向模块负责人解释内部结构 → Level 3 Component 图
- 向代码 reviewer 解释关键设计 → Level 4 Code 图（按需）

### 误区：过度维护所有层级

一个常见的反模式是"**为每个容器都画完整的组件图，并保持实时更新**"。这会造成巨大的文档维护负担，最终导致图与代码脱节（"架构图撒谎"问题）。

Simon Brown 的建议是：Level 4 通常由工具自动生成；Level 3 只在关键容器上维护；Level 1 和 Level 2 是必须的，也是最值得投入维护的层级。如果使用 Structurizr DSL，由于模型是代码化的，维护成本显著降低。

### 误区：把 C4 与具体技术强绑定

C4 是**技术中立**的——同一张 Container 图可以描述单体应用，也可以描述微服务架构。不要因为"我们用的是微服务，所以每个服务就是一个容器"而机械地等号，也不要认为容器必须对应 Docker 容器。判断标准始终是：**能否独立部署？能否独立运行？**

### 反模式：无图例的 C4 图

没有图例的 C4 图比没有 C4 的图更危险——读者会对方框的含义产生自己的假设，引发误解。每张图都必须包含图例，说明颜色、形状、标注的语义。

### 与 CI/CD 集成（架构即代码的完整闭环）

将 Structurizr DSL 文件纳入代码仓库后，可以在 CI 流水线中：
1. 验证 DSL 语法正确性（Structurizr CLI 的 `validate` 命令）
2. 自动导出 SVG/PNG 图片
3. 将图片更新到文档系统（Confluence、GitBook、静态网站）

这样架构图的更新与代码变更的 PR 绑定，架构评审和代码评审可以同时进行。

### 与 ADR 的配合

C4 图展示的是架构的**当前状态**，但不解释**为什么是这个状态**——为什么选择这个技术栈？为什么是微服务而不是单体？这些"为什么"的问题由**架构决策记录（ADR）** 来回答（见 [[51.架构决策记录ADR]]）。C4 与 ADR 是互补的：C4 是地图，ADR 是地图背后的决策日志。

## 小结

C4 模型用四层抽象（Context / Container / Component / Code）和"地图缩放"隐喻，解决了架构可视化中受众错配和粒度混乱的核心问题。它不强制记号法，与 Structurizr DSL、PlantUML、Mermaid、draw.io 均有良好集成，支持架构即代码。实践要点：优先维护 L1 与 L2，L3 按需维护，L4 交由工具生成；每张图必须有图例；以受众决定展示层级。C4 与 ADR 配合使用，前者描述架构现状，后者记录决策理由，共同构成完整的架构文档体系。

在团队拓扑演进（见 [[44.TeamTopologies团队拓扑]]）中，C4 的 Container 图往往直接映射到团队边界——每个流对齐团队拥有一组容器，Container 图成为团队间接口契约的可视化表达，是架构与组织设计对齐的重要工具。
