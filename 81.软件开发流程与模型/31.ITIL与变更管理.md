# 软件开发流程与模型(三十一)ITIL与变更管理

> [!abstract] 速览
> **ITIL（IT Infrastructure Library）** 是 **IT 服务管理(ITSM)** 的事实标准框架，关注"如何稳定、可靠地交付与运营 IT 服务"。其中**变更管理(Change Enablement)** 最受关注——它管控"对生产的每一次改动"，传统上靠 **CAB(变更咨询委员会)** 审批。
> 一句话：**ITIL 站在"稳定运营"的立场管变更，DevOps 站在"快速交付"的立场推变更**——二者曾对立，ITIL 4 已转向拥抱敏捷/DevOps。本篇讲清 ITIL 4、变更类型与流程，及其与 DevOps 的张力与融合。

## 1. ITIL 是什么

ITIL 起源于英国政府，是一套 **IT 服务管理最佳实践**：把 IT 当"服务"来运营，覆盖事件、问题、变更、服务级别等。最新是 **ITIL 4**(2019)，从"流程"转向"价值"。

## 2. ITIL 4 概览

| 组成 | 说明 |
| --- | --- |
| **服务价值系统(SVS)** | 从需求到价值的整体框架 |
| **四个维度** | 组织与人、信息与技术、合作伙伴、价值流与流程 |
| **七条指导原则** | 如"聚焦价值""从现状开始""迭代推进""协作可见" |
| **34 项实践** | 含事件 / 问题 / 变更 / 服务请求管理等 |

> ITIL 4 的指导原则("迭代推进""协作""保持简单")已明显**向敏捷/DevOps 靠拢**。

## 3. 核心实践

| 实践 | 管什么 |
| --- | --- |
| **事件管理 Incident** | 快速恢复中断的服务 |
| **问题管理 Problem** | 找根因、防复发 |
| **变更赋能 Change Enablement** | 管控对生产的改动 |
| **服务请求管理** | 处理标准请求(如开账号) |
| **服务级别管理** | 维护 SLA(见 [[29.SRE与错误预算]]) |

## 4. 变更类型

| 类型 | 特征 | 审批 |
| --- | --- | --- |
| **标准变更 Standard** | 低风险、预批准、流程化 | 免审(预授权) |
| **常规变更 Normal** | 需评估与审批 | CAB 评审 |
| **紧急变更 Emergency** | 救火、需尽快 | 紧急审批(ECAB) |

## 5. 变更管理流程

```mermaid
graph LR
    RFC[变更请求 RFC] --> ASSESS[评估风险 / 影响] --> APPROVE[审批<br/>CAB / 预授权] --> IMPL[实施] --> REVIEW[实施后复盘 PIR]
```

> **CAB(Change Advisory Board，变更咨询委员会)** 评估常规变更——这是传统 ITIL 最被 DevOps 诟病"慢"的环节。

## 6. ITIL vs DevOps：张力与融合

| 维度 | 传统 ITIL | DevOps |
| --- | --- | --- |
| 变更 | CAB 审批、谨慎 | 自动化、频繁 |
| 节奏 | 慢而稳 | 快而频 |
| 风险观 | 减少变更 | 小批量降风险 |

> [!note] 融合趋势
> DevOps 研究(DORA)发现：**重量级变更审批(CAB)与高绩效负相关**——它拖慢却未必更安全。现代做法是用**标准变更(预授权) + 自动化门禁([[21.持续集成与持续交付CICD|CI/CD]]) + 同行评审**替代人工 CAB，让"频繁小变更"既快又可控。ITIL 4 也已接纳这一思路。

## 7. 现代变更管理

| 传统 | 现代(DevOps 化) |
| --- | --- |
| CAB 周会审批 | 标准变更预授权、自动放行 |
| 人工评估 | 自动化测试 + 安全门禁 |
| 大批量变更 | 小批量、高频(降单次风险) |
| 文档审批留痕 | [[23.GitOps\|Git 提交即留痕]] |

## 8. 优点与挑战

| 优点 | 挑战 |
| --- | --- |
| 规范、可审计、可追溯 | 重流程易拖慢交付 |
| 适合强合规 / 大型运维 | CAB 可能成瓶颈 |
| 与 SLA / 合规对接 | 需与 DevOps 平衡 |

## 9. 真实案例：用标准变更替代 CAB

某企业所有上线都要走周会 CAB，发布被卡到每两周一次。改革：把"经 CI/CD 全自动测试 + 同行评审"的发布定义为**标准变更(预授权)**，免去 CAB；只有架构级/高风险变更才走 CAB。结果发布频率大增、事故率未上升——**自动化门禁取代了人工审批**。

## 10. 工具链

ServiceNow、Jira Service Management、BMC Helix(ITSM 平台)；与 [[21.持续集成与持续交付CICD|CI/CD]] 集成实现变更自动登记与审计。

## 11. 常见误区与面试要点

> [!warning] 易错点
> - **ITIL = 官僚拖慢？** 传统重 CAB 确有此弊，但 ITIL 4 已拥抱敏捷/DevOps。
> - **变更管理 = 阻止变更？** 不。是**管控风险地促成变更**(Change Enablement 之名)。
> - **CAB 越严越安全？** DORA 数据显示重量级审批与高绩效**负相关**。
> - **三种变更类型？** 标准(预授权)、常规(CAB)、紧急(ECAB)。
> - **DevOps 怎么对接变更管理？** 用标准变更 + 自动化门禁 + 评审替代人工 CAB。
> - **ITIL 与 SRE 冲突吗？** 互补：SRE 管可靠性工程，ITIL 管服务流程，可融合。

## 12. 对常见说法的修正

> [!note] 修正清单
> 1. **"ITIL 与 DevOps 水火不容"**——ITIL 4 已转向价值与敏捷；现代变更管理与 DevOps 可融合(自动化门禁=轻量变更控制)。
> 2. **"严格审批=更安全"**——研究表明重量级 CAB 拖慢且未必更安全，小批量+自动化更优。

## 13. 一句话记忆

> **ITIL** 从"稳定运营"立场提供 IT 服务管理(事件/问题/变更)；其**变更管理**传统靠 **CAB 审批**，但重审批被 DORA 证明拖慢且未必更安全——现代做法用**标准变更预授权 + CI/CD 自动门禁 + 评审**替代，让 ITIL 与 DevOps 融合。
