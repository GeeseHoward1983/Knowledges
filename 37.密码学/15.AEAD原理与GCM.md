# 密码学（15）· AEAD原理与GCM

> [!abstract] TL;DR
> - **AEAD（Authenticated Encryption with Associated Data）**在一次调用里同时提供**机密性 + 完整性 + 真实性**，彻底封堵"加密不认证"的经典漏洞。
> - **AES-GCM** 是最常见的 AEAD：CTR 模式加密明文（见 [[13.CTR模式]]），GHASH 在 **GF(2¹²⁸)** 上对 AAD 与密文做多项式求值，生成认证标签 tag。
> - **命门**：nonce（初始化向量 IV）**绝不能对同一密钥重用**——nonce 重用导致认证密钥 H 泄露，可实施 Forbidden Attack 伪造任意消息。
> - AAD（附加认证数据）认证但不加密，适合包头、关联元数据。
> - 生产环境：96 位 nonce（随机或计数器）、128 位 tag 全长校验、优先使用 AES-NI + PCLMULQDQ 硬件加速。

本篇是「AEAD」专题的开篇与核心。前置知识：[[10.分组密码工作模式总论]] 对模式体系的整体鸟瞰，[[13.CTR模式]] 的密钥流加密原理，[[04.AES详解]] 的分组密码基础。GHASH 的兄弟算法 Poly1305 及其与 ChaCha20 的搭配见 [[37.Poly1305与GMAC]]，另一 AEAD 变体见 [[16.ChaCha20-Poly1305]]。

## 概述与定位

### "加密不认证"的代价

在 GCM 出现之前，使用分组密码的常见模式（CBC、CTR、CFB……）**只提供机密性**，不内建完整性校验。工程师往往有两种错误做法：

1. **只加密，不加 MAC**：攻击者可以对密文任意翻转、截断、重放，接收方无从察觉。CBC 的 Padding Oracle 攻击正是利用这一点——没有 MAC，解密边界成了攻击者的预言机。
2. **MAC-then-Encrypt（先 MAC 再加密）**：把 MAC 和明文一起加密，看似安全，实则仍可能引发 padding oracle，因为接收方需要先解密才能验 MAC，而解密时已经给了错误反馈的机会。

密码学界对"正确组合"的研究结论是：**Encrypt-then-MAC（先加密再 MAC）在语义安全 + 密文完整性两方面均可证明最优**。AEAD 算法将这个"正确组合"封装成单一原语，API 级别强制执行，消除工程实现的选择空间。

### AEAD 的三重保证

| 保证       | 含义                                            | 缺失时的风险                     |
|------------|------------------------------------------------|----------------------------------|
| 机密性     | 攻击者无法从密文推断明文                        | 明文泄露                         |
| 完整性     | 密文任何改动（含位翻转、截断、拼接）均被检出    | Padding Oracle、明文注入         |
| 真实性     | 只有持有密钥者才能生成合法密文                  | 消息伪造、重放攻击（需结合 nonce）|

### AAD——认证但不加密的附加数据

**AAD（Associated Data，附加认证数据）**是 AEAD 的第四个输入（除密钥、nonce、明文外）：

- **不加密**：AAD 以明文传输，接收方可直接读取（如 IP 头、数据包序号、协议版本）。
- **参与认证**：AAD 被纳入 tag 计算——若 AAD 被篡改，tag 校验失败，消息被拒绝。

典型场景：TLS 记录层协议用版本号、序列号、长度作 AAD，加密的是 payload；数据库加密用行 ID 作 AAD，防止密文行被跨行复制重用。

```
AEAD 接口：
  Encrypt(K, nonce, plaintext, AAD)  → (ciphertext, tag)
  Decrypt(K, nonce, ciphertext, AAD, tag)  → plaintext 或 ⊥
```

`⊥` 表示认证失败（tag 不匹配），此时**不返回任何明文**——这是"先认证再解密"的关键性质。

## 原理与机制

### Encrypt-then-MAC 为何最优

设加密方案 E 满足语义安全（IND-CPA），MAC 方案 M 满足消息不可伪造（EUF-CMA）。三种组合的安全性：

```
方案                   IND-CPA  密文不可伪造  备注
----------------------------------------------------------
Encrypt-then-MAC       ✓        ✓            最优，可证明 IND-CCA2
MAC-then-Encrypt       ✓        ✗（通常）    先解密再验MAC，存在泄漏
Encrypt-and-MAC        ✗（潜在）不确定       MAC 可能泄露明文信息
```

Encrypt-then-MAC 的核心优势：接收方先验 MAC，验证失败直接拒绝，**解密函数从不被调用**，攻击者无法从解密过程获取任何反馈。AES-GCM 在内部实现的就是 Encrypt-then-MAC 的精神：CTR 加密在前，GHASH 计算 tag 在后（但 tag 同时覆盖 AAD 与密文）。

### GF(2¹²⁸) 速览

GHASH 在 **GF(2¹²⁸)**（二元扩域，128 位）上进行多项式乘法。理解其运算：

```
元素：128 位比特串，视为 GF(2)[x] 中次数 ≤ 127 的多项式
加法：按位 XOR（无进位）
乘法：多项式乘法后模不可约多项式
      GCM 使用：p(x) = x^128 + x^7 + x^2 + x + 1
```

乘法硬件加速：x86/x64 的 `PCLMULQDQ` 指令直接实现无进位多项式乘法（carryless multiply），配合 AES-NI，GCM 可达到近线速。

### AES-GCM 整体结构

AES-GCM 的输入：密钥 K（128/192/256 位）、96 位 nonce IV、明文 P、附加数据 A。

**步骤一：生成认证子密钥 H**

```
H = AES_K(0^128)
```

H 是将全零块用密钥 K 加密的结果，是 GHASH 的"哈希密钥"。H **随密钥固定**，与 nonce 无关——这是 nonce 重用致命的根源。

**步骤二：生成初始计数器块 J₀**

```
若 len(IV) == 96 位：
    J₀ = IV ‖ 0^31 ‖ 1       // 高 96 位 nonce，低 32 位置 1
否则：
    J₀ = GHASH_H(IV 填充后)   // 其他长度 IV 经 GHASH 处理
```

96 位 nonce 是推荐规格，避免额外 GHASH 运算。

**步骤三：CTR 加密明文**

计数器从 `J₀ + 1` 开始（`inc32` 只递增低 32 位）：

```
对第 i 块（i = 1, 2, …, n）：
    CTR_i = inc32(J₀, i)      // J₀ 的低32位加 i
    S_i   = AES_K(CTR_i)      // 密钥流块
    C_i   = P_i XOR S_i       // 密文块
末尾不足一块：取 S_n 的高位字节做 XOR
```

这正是 [[13.CTR模式]] 描述的密钥流加密；GCM 将 J₀+1 作为起始计数器，J₀ 本身留给 tag 加密使用（见步骤五）。

**步骤四：GHASH 计算认证值**

GHASH 对"AAD ‖ padding ‖ 密文 ‖ padding ‖ len(A) ‖ len(C)"做多项式求值：

```
// 所有输入均按 128 位分块，不足补零
blocks = pad128(A) ‖ pad128(C) ‖ [len(A)]₆₄ ‖ [len(C)]₆₄

// 多项式 Horner 求值（H 是评估点）
X = 0
for each block m_i in blocks:
    X = (X XOR m_i) · H     // 乘法在 GF(2^128) 上
// 最终 X 即 GHASH 输出 S
```

本质是以 H 为变量的多项式：

```
GHASH = A₁·H^(m+n+1) + A₂·H^(m+n) + … + C₁·H^(n+1) + … + Cₙ·H^2 + [len]·H
```

（m 块 AAD，n 块密文，系数均为 GF(2¹²⁸) 元素）。

**步骤五：生成认证标签**

```
S   = GHASH_H(A, C)
T   = AES_K(J₀) XOR S       // 用 J₀（非 J₁）加密 GHASH 输出
tag = T[0 .. tag_len - 1]    // 截取，默认 128 位
```

用 `AES_K(J₀)` 做一次性掩码，防止 GHASH 的输出（纯 MAC 值）被直接攻击。

### 解密与认证验证

解密时，先重算 GHASH → 重算 tag → **比对 tag**（常量时间比较），比对通过才解密。任何顺序错误（先解密再验 tag）都可能引入 oracle。

```
Decrypt(K, IV, C, A, tag_recv):
    H   = AES_K(0)
    J₀  = IV ‖ 0x00000001
    S   = GHASH_H(A, C)
    T   = AES_K(J₀) XOR S
    if NOT constant_time_equal(T[0..tag_len-1], tag_recv):
        return ⊥                // 认证失败，拒绝
    // 通过后才解密
    P   = CTR_decrypt(K, J₀+1, C)
    return P
```

## 算法流程 / 结构详解

### 参数规范

| 参数      | 推荐值            | 备注                                    |
|-----------|------------------|-----------------------------------------|
| 密钥长度  | 128 位（256 位）  | AES-128-GCM 常见，高敏感用 AES-256-GCM  |
| nonce     | 96 位             | 其他长度需额外 GHASH，性能差且复杂       |
| tag 长度  | 128 位            | 不应截短；128 位提供 64 位安全边界       |
| AAD       | 任意长度          | 可为空，但不能省略接口参数               |

### 硬件加速

AES-GCM 有两条硬件加速路径（x86）：

- **AES-NI**（`AESENC`/`AESENCLAST`）：加速 AES 轮函数，消除旁路攻击。
- **PCLMULQDQ**：无进位多项式乘法，直接加速 GF(2¹²⁸) 乘法（GHASH 核心）。

两者组合使 AES-GCM 吞吐量可达数 GB/s（单核），远超软件实现的几十 MB/s。ARM 对应 `PMULL`/`PMULL2` 指令。

### 与 CTR 模式的关系

GCM 的加密路径即 CTR 模式（起点从 J₀+1 开始），继承 CTR 的全部特性：

- 加密解密均只需 AES **正向**函数
- 密文块可**完全并行**计算
- 支持**随机访问**（跳转到任意块计算其计数器）
- 末尾不足块不需填充

详细 CTR 原理见 [[13.CTR模式]]；AES 底层见 [[04.AES详解]]。

### 伪代码：完整 AES-GCM 加密

```python
def aes_gcm_encrypt(K, IV, P, A, tag_len=16):
    # 1. 认证子密钥
    H = AES_encrypt(K, bytes(16))           # E_K(0^128)

    # 2. 初始计数器（96位 IV）
    assert len(IV) == 12
    J0 = IV + b'\x00\x00\x00\x01'          # IV ‖ 0^31 ‖ 1

    # 3. CTR 加密
    C = b''
    counter = int.from_bytes(J0, 'big') + 1  # 从 J0+1 开始
    for i in range(0, len(P), 16):
        ctr_block = counter.to_bytes(16, 'big')
        keystream = AES_encrypt(K, ctr_block)
        chunk = P[i:i+16]
        C += xor_bytes(keystream[:len(chunk)], chunk)
        # 仅递增低32位（inc32）
        lo32 = (counter & 0xFFFFFFFF) + 1
        counter = (counter & ~0xFFFFFFFF) | (lo32 & 0xFFFFFFFF)

    # 4. GHASH：对 pad(A) ‖ pad(C) ‖ [len(A)]64 ‖ [len(C)]64
    ghash_input = (
        pad_to_128(A) +
        pad_to_128(C) +
        (len(A) * 8).to_bytes(8, 'big') +
        (len(C) * 8).to_bytes(8, 'big')
    )
    S = ghash(H, ghash_input)               # GF(2^128) 多项式求值

    # 5. Tag
    T = xor_bytes(AES_encrypt(K, J0), S)
    tag = T[:tag_len]

    return C, tag
```

## 安全性与正确使用

### nonce 唯一性是命门

> [!danger] GCM nonce 重用 → 灾难性失败
> 若对相同密钥 K 使用相同 nonce 加密两条不同消息：
> 1. 两段密文用**同一密钥流**，XOR 消去密钥流，直接得到 `C₁ XOR C₂ = P₁ XOR P₂`（Two-Time Pad）。
> 2. 更严重：攻击者可由此恢复 **GHASH 认证子密钥 H**（Forbidden Attack）——有了 H，可**伪造任意消息的合法 tag**，彻底破坏认证。

Forbidden Attack 的数学原理：两次加密的 tag 方程相减，可建立关于 H 的多项式方程，结合 CTR 密钥流重用恢复明文差异，进而解出 H。

**正确的 nonce 生成策略**：

| 策略           | 适用场景                          | 注意事项                        |
|----------------|----------------------------------|---------------------------------|
| 随机 96 位     | 单密钥消息数 < 2³²（~40 亿）      | 生日悖论：超此数量 nonce 碰撞概率不可忽略 |
| 确定性计数器   | 有状态连接（TLS、有序通信）       | 计数器绝不回绕；重启需换密钥    |
| 密钥派生 + 随机| 混合方案                          | KDF 生成子密钥，随机 nonce 配合  |

TLS 1.3 使用序列号作计数器（确定性，不回绕），最大记录数 2⁶⁴ 条即要求重新握手。

### tag 截断风险

tag 截短会成比例地降低伪造成功率的难度：

```
tag 长度   伪造成功概率（单次尝试）
-------------------------------
128 位     1/2^128 ≈ 3×10^-39
96  位     1/2^96  ≈ 1×10^-29
64  位     1/2^64  ≈ 5×10^-20   （不推荐）
32  位     1/2^32  ≈ 2×10^-10   （危险）
```

**NIST SP 800-38D** 允许最短 32 位 tag，但要求附加的密钥使用次数限制。生产环境始终使用 **128 位 tag**。

### tag 比较必须常量时间

```python
# 错误：早退出给攻击者时序 oracle
if computed_tag == received_tag:   # Python bytes 比较早退出
    ...

# 正确：常量时间比较
import hmac
if hmac.compare_digest(computed_tag, received_tag):
    ...
```

时序攻击可逐字节试探 tag，将伪造复杂度从 2¹²⁸ 降至 128×2⁸ = 32768 次。

### 消息数量限制

同一密钥加密消息总量有上限：

```
随机 nonce：建议 < 2^32 条（防生日碰撞）
密文总长度：< 2^39 - 256 位（≈64 GiB）每次调用
```

超出限制需**密钥轮换**。

### 推荐做法清单

> [!tip] 正确使用 AES-GCM
> 1. **nonce 绝不重用**：随机 96 位或有状态计数器（绝不回绕）。
> 2. **tag 用全 128 位**：不截断，不截短。
> 3. **先验 tag 再解密**：认证失败立即返回 ⊥，不返回任何解密数据。
> 4. **常量时间比较 tag**：`hmac.compare_digest` 或等价函数。
> 5. **密钥轮换**：随机 nonce 下消息量不超过 2³² 条；超出立即换密钥。
> 6. **优先 AES-256-GCM**：高敏感数据；通用场景 AES-128-GCM 可接受。
> 7. **不要自己实现 GCM**：使用经过审计的库（OpenSSL、libsodium、BoringSSL、cryptography.io）。
> 8. **AAD 包含关联上下文**：序列号、请求 ID、版本号，防止密文跨上下文复用。

### 对比其他 AEAD

| 方案                  | 加密核心         | MAC 核心         | 硬件依赖         | nonce 重用代价     |
|-----------------------|-----------------|-----------------|------------------|--------------------|
| AES-128-GCM           | AES-CTR         | GHASH / GF(2¹²⁸) | AES-NI + PCLMUL  | 灾难性（泄露 H）    |
| ChaCha20-Poly1305     | ChaCha20 流密码 | Poly1305        | 无（软件友好）    | 严重（泄露密钥流）  |
| AES-CCM               | AES-CTR         | AES-CBC-MAC     | AES-NI           | 严重               |
| AES-SIV               | AES-CTR         | S2V             | AES-NI           | 只泄露相同明文      |

ChaCha20-Poly1305 见 [[16.ChaCha20-Poly1305]]；Poly1305 MAC 详细见 [[37.Poly1305与GMAC]]。AES-SIV（nonce misuse resistance）适用于无法保证 nonce 唯一性的场景。

## 实战示例

### Python（cryptography 库）

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

key   = AESGCM.generate_key(bit_length=128)   # 128位密钥
aesgcm = AESGCM(key)

nonce = os.urandom(12)                         # 96位随机 nonce
aad   = b"v1;seq=42;dst=10.0.0.1"            # 附加数据（明文传输，参与认证）
pt    = b"secret message"

ct_with_tag = aesgcm.encrypt(nonce, pt, aad)  # 密文 + 128位 tag
recovered   = aesgcm.decrypt(nonce, ct_with_tag, aad)
assert recovered == pt
```

> [!warning] 示例输出为示意
> 实际 nonce、密文、tag 均为随机字节，上述代码仅演示接口调用。

### OpenSSL 命令行

```bash
# 加密（-aes-128-gcm，nonce 用 -iv，AAD 用 -aad）
openssl enc -aes-128-gcm -K <hex_key> -iv <hex_nonce_96bit> \
    -in plain.txt -out cipher.bin -e

# 注意：openssl enc 对 GCM 支持有限，生产环境建议用 EVP API 或专用库
```

> [!warning] 示例输出为示意
> `openssl enc` 对 GCM AAD 支持因版本而异，完整 GCM API 建议用 C 语言 EVP_AEAD 接口或 Python/Go/Rust 的成熟绑定。

## 小结

AEAD 以单一接口封装了"加密 + 认证"的正确组合，AES-GCM 是其中最广泛部署的方案：

- **机密性**来自 CTR 模式加密（[[13.CTR模式]]）。
- **完整性 + 真实性**来自 GHASH 在 GF(2¹²⁸) 上的多项式 MAC，及 `AES_K(J₀)` 掩码。
- **AAD** 将关联上下文纳入认证，防止密文跨场景复用。
- **性能**由 AES-NI + PCLMULQDQ 保障，近线速。
- **命门**是 nonce 唯一性——重用则认证密钥 H 泄露，整个方案崩塌（Forbidden Attack）。

正确使用 AES-GCM 的三条铁律：**nonce 不重用、tag 不截断、先验证再解密**。
