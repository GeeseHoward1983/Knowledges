# Hook 技术全景指南

> 本系列文档系统地讲解软件工程中各类 **Hook（钩子）** 技术的原理、实现机制、API、可运行示例、典型场景和常见陷阱。
> 目标读者：希望深入理解 hook 而不仅仅"会调用"的中高级开发者、逆向工程师、平台工具开发者。

---

## 0. 什么是 Hook？

**Hook（钩子）**，本质上是**在程序的某个既定执行点上，插入一段自定义代码、改变或扩展原行为的机制**。它的核心抽象只有三件事：

1. **挂载点（Hook point）**：原程序中"可以被打断"的位置。可以是函数入口、事件分发循环、系统调用、消息泵、生命周期回调、import/require 语句、CPU 指令边界。
2. **替换或附加的逻辑（Hook handler）**：你的代码。它可以**完全替换**原逻辑、**前置/后置**于原逻辑、或**包装（wrap）**原逻辑。
3. **派发机制（Dispatch）**：把控制权从原程序转交给你的 handler，以及（可选地）再交还给原程序的机制。这部分的实现差异最大——它可能是：
   - 一次函数指针赋值（C 回调、Vue/React Hook 注册）
   - 一次符号解析重定向（`LD_PRELOAD`、IAT/GOT）
   - 一次机器指令改写（Inline Hook、Detours）
   - 一次内核数据结构替换（kprobe、eBPF）
   - 一次解释器内部结构注入（Python `sys.settrace`、Node `Module._load`）
   - 一次 OS 提供的注册接口（`SetWindowsHookEx`、`installEventFilter`）

理解上述三件事的具体形态，比记住任何具体 API 都重要。任何看似新颖的 hook 技术，都可以拆解成"挂载点 + handler + 派发"这三件事的某种组合。

## 1. Hook 的分类维度

不同语境下"hook"指的东西差别很大。下表用 6 个正交维度来对所有 hook 技术做统一分类：

| 维度 | 取值 | 说明 |
|---|---|---|
| **抽象层** | 应用层 / 框架层 / 语言运行时层 / 操作系统层 / 内核层 / CPU 指令层 | 越靠下越通用、越强大，但风险和复杂度越高 |
| **侵入方式** | 显式注册 / 替换符号 / 改写指令 / 子类化 / 配置驱动 | 决定是否需要源码访问权、是否需要重启进程 |
| **粒度** | 全局（process-wide）/ 线程 / 对象实例 / 单次调用 | 决定隔离性和性能开销 |
| **时机** | 进入前（pre）/ 返回后（post）/ 包装（around）/ 替换（replace）/ 异常时 | 决定 handler 能拿到/改变什么数据 |
| **生效范围** | 进程内（in-process）/ 跨进程（out-of-process，需要注入或 ptrace）/ 全系统 | 决定部署方式 |
| **持久性** | 进程生命周期内 / 一次性 / 持久（写入二进制或系统配置） | 决定卸载策略 |

举例：
- React `useEffect` = 应用层 + 显式注册 + 组件实例粒度 + pre/post/cleanup + 进程内 + 组件生命周期。
- Windows Detours Inline Hook = 操作系统层 + 改写指令 + 进程全局 + 包装 + 进程内 + 进程生命周期内（或持久化到 DLL 注入）。
- eBPF kprobe = 内核层 + 配置驱动（验证器+JIT）+ 全系统 + 入前/返回后 + 全系统 + 通常一次会话。

## 3. 怎么挑选合适的 Hook 技术？

下面这张决策表把"目标 → 推荐技术"映射到具体方案：

| 你想干的事 | 推荐技术 | 备选 | 不要用 |
|---|---|---|---|
| 在 React 组件挂载/更新/卸载时跑代码 | `useEffect` | 类组件 `componentDid*`（已过时） | monkey patch React 内部 |
| 在用户每次按键时记录（自己进程内） | Qt: `installEventFilter`<br>Win32: `SetWindowsHookEx(WH_KEYBOARD)` | 直接绑控件 `keyPressEvent` | Inline Hook |
| 监控**全系统**所有进程的某个 API 调用 | eBPF uprobe（Linux）<br>ETW（Windows） | DLL 注入 + Inline Hook | LD_PRELOAD（只对自己启动的进程生效） |
| 给已运行进程的某函数加一段日志 | uprobe / GDB python / Frida | ptrace 注入 | 重启进程 |
| 替换 `malloc` 做内存检测 | `LD_PRELOAD` + `dlsym(RTLD_NEXT, "malloc")` | jemalloc/tcmalloc 替换 | Inline Hook（malloc 在 hot path，性能差） |
| 给 Python 测试 mock 一个第三方函数 | `unittest.mock.patch` | `sys.settrace` | monkey patch（污染全局） |
| 拦截 Node.js 的所有 `require()` | Module._load wrapper / ESM loader hook | proxy NodeJS internals | 改源代码 |
| 在 Qt 应用收到原生窗口消息前拦截 | `QAbstractNativeEventFilter` | `winEventHook` | Qt 内部修改 |
| 性能分析（采样 CPU） | perf / eBPF profile | Linux: gprof, Windows: WPA | 自己 inline hook 每个函数 |
| 限制某个程序不能调用 `connect()` | seccomp-bpf / eBPF LSM | `LD_PRELOAD` 替换 | hook 但不阻止（绕过容易） |

**通用原则：能用应用层就别用框架层；能用框架层就别用语言层；能用语言层就别用 OS 层；能用 OS 层就别用内核层；能用内核层就别改 CPU 指令。每下沉一层，能力涨一截，但调试难度、平台耦合、稳定性风险都涨一截。**

**工程流程类 hook（Claude Code / Git）和上面所有"运行时 hook"是正交的两个维度**——前者在"操作发生时"（commit、tool call、push）触发外部脚本，后者在"代码运行时"插入逻辑。前者用 settings.json / `.git/hooks/` 等配置文件管理，无需理解机器码、ABI、内核数据结构，但同样能极大改变工作流程。详见 [06-claude-code-hooks.md](./06-claude-code-hooks.md) 和 [07-git-hooks.md](./07-git-hooks.md)。

## 4. 共通的陷阱清单（在所有 hook 技术里都会踩）

1. **重入（Reentrancy）**：你的 hook 在 handler 里又触发了被 hook 的目标。典型：在 `malloc` hook 里 `printf`，而 `printf` 内部又 `malloc`。对策：thread-local 标志位 / 直接调用 syscall 绕过 libc / 用环形缓冲区延后 IO。
2. **线程安全**：handler 可能被多线程并发进入。共享数据要原子化或加锁；锁要避免和被 hook 的目标抢同一把锁（容易死锁）。
3. **栈/寄存器约定**：低层 hook（Inline Hook、Detours）必须保证 trampoline 严格遵守 ABI（caller-saved/callee-saved 寄存器、栈对齐、shadow space），否则崩溃位置很难定位。
4. **多版本兼容**：内核结构体、glibc 内部符号、React/Qt 内部 API 都在变。eBPF 的 CO-RE 就是为解决这个发明的；其他层只能多版本测试。
5. **卸载（uninstall）**：很多 hook 容易装、难卸。Inline Hook 卸载时要保证没有线程正在 trampoline 里执行（quiesce）。LD_PRELOAD 进程退出就消失，但 ptrace 注入不 detach 干净会杀目标。
6. **隐藏性 vs 可观测性**：恶意软件常用 hook 隐藏自己（rootkit），同样的技术正当用途下要反过来——要让你的 hook 在崩溃栈、日志、`/proc` 里清晰可辨，方便排错。
7. **签名/完整性校验**：现代系统大量用 Code Integrity / KPP（PatchGuard）/ macOS SIP / Android verified boot 来阻止内核或系统库被 hook。设计方案前要先确认目标系统允不允许。
8. **性能**：每次 hook 都是一次额外的间接跳转 + 寄存器保存。对 hot path（每秒上百万次调用的函数）做 hook，单次额外几十 ns 都会变成显著开销。要先 profile。

## 7. 法律 / 道德边界

- 用户态 hook 自己进程：自由。
- DLL 注入 / `LD_PRELOAD` 到第三方进程：取决于平台政策（Windows EULA、macOS notarization、Android Play Protect）。
- 内核 hook：商业产品必须有数字签名（Windows）/ 通过 Apple 公证 / Linux 模块签名。
- 反作弊、外挂、监听、隐私采集：受当地法律约束。技术中立，使用要合规。
