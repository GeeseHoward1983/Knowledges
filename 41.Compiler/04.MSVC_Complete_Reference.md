# MSVC 编译器与链接器完整参数详解

> MSVC（Microsoft Visual C++）是微软的 C/C++ 工具链，编译器主程序为 `cl.exe`，链接器为 `link.exe`。它与 GCC/Clang 风格迥异：选项以 **`/`**（也接受 `-`）引导，且**与 Unix 工具链不通用**。
>
> ⚠️ **关键特性：MSVC 的编译器选项严格区分大小写**。这意味着 **`/Gz`（`__stdcall` 调用约定）与 `/GZ`（已弃用的运行时检查）是两个完全不同的选项**——本文多处辨析正源于此，阅读时务必看清字母大小写。
>
> **版本基准**：以 **Visual Studio 2022（MSVC v143 / 工具集 17.x）** 及以上为参考；标注"已弃用"者以官方 [MSVC 编译器选项](https://learn.microsoft.com/cpp/build/reference/compiler-options) 为准。
>
> **另见**：[[03.GCC_G++_Complete_Reference|GCC/G++ 参考]] · [[01.Clang_Clang++_Complete_Reference|Clang/Clang++ 参考]] · [[02.Compiler_Comparison|GCC vs Clang vs MSVC 对比]]

## MSVC 编译流程

`cl.exe` 把源码变成可执行程序，概念上分 4 步：

1. **预处理（Preprocessing）**：处理 `#include`、`#define`、`#ifdef` 等，生成 `.i`/`.ii` 中间文件。
2. **编译（Compilation）**：将预处理结果翻译为汇编。
3. **汇编（Assembly）**：将汇编翻译为机器码，生成 `.obj` 目标文件（COFF 格式）。
4. **链接（Linking）**：由 `link.exe` 合并 `.obj` 与库，生成 `.exe` 或 `.dll`。

> 💡 `cl.exe` 只能在 **"Developer Command Prompt / x64 Native Tools 命令提示符"** 中启动（依赖一系列环境变量），不能直接在普通 cmd 或资源管理器里运行。

## 一、编译器参数（cl.exe）

## 1. 优化选项

- **/Od**：禁用优化（调试默认）
- **/O1**：**最小化体积**（= `/Og /Os /Oy /Ob2 /GF /Gy` 等组合）
- **/O2**：**最大化速度**（发布推荐；= `/Og /Oi /Ot /Oy /Ob2 /GF /Gy` 等组合）
- **/Os**：优先代码体积
- **/Ot**：优先代码速度
- **/Og**：启用全局优化
- **/Oi**：把部分库函数作为内部函数（intrinsic）内联展开
- **/Oy**：省略帧指针（x86）
- **/Ob\<n>**：内联展开级别（`0` 禁用、`1` 仅 `__inline`/`inline` 标记、`2`/`3` 让编译器自行决定）
- **/Ox**：启用大多数速度优化（= `/Ob2 /Oi /Ot /Oy`），但**不含** `/O1`/`/O2` 才有的 `/GF`、`/Gy`。官方建议发布构建直接用 `/O2` 而非 `/Ox`

### 1.1 PGO——按配置优化（Profile-Guided Optimization）

MSVC 的 PGO 与 GCC 逻辑相似但工具链不同，分三阶段完成。

**阶段一：全程序优化 + 插桩构建**

```bat
cl /O2 /GL app.cpp /link /LTCG:PGINSTRUMENT /OUT:app_instr.exe
```

- `/GL`（Whole Program Optimization）：让编译器延迟代码生成到链接期，跨模块做分析——PGO 的前提条件
- `/LTCG:PGINSTRUMENT`：链接时插入 profile 计数器，生成 `app_instr.exe` 及配套的 `.pgd`（profile database）文件

**阶段二：收集 profile**

```bat
rem 用代表性 workload 运行插桩版本
app_instr.exe < representative_input.txt
rem 运行后自动生成 app_instr!N.pgc（profile count 文件）
```

多次运行可以累积多个 `.pgc`，用 `pgomgr` 合并：

```bat
pgomgr /merge app_instr!1.pgc app_instr!2.pgc app.pgd
```

`pgomgr`（Profile Guided Optimization Manager）是 MSVC 专属工具，用于合并、查看、过滤 `.pgc`/`.pgd` 文件。

**阶段三：利用 profile 优化构建**

```bat
cl /O2 /GL app.cpp /link /LTCG:PGO /OUT:app_pgo.exe
```

- `/LTCG:PGO`（也写作 `/LTCG:PGOPTIMIZE`）：读取 `.pgd` 文件，按热度重新优化：热路径内联、冷代码移出 icache、函数排序（基于 `/ORDER`）、分支预测提示等

**MSVC PGO 选项速查**

| 选项 | 作用 |
|---|---|
| `/GL` | 启用全程序优化，PGO 的前置条件 |
| `/LTCG:PGINSTRUMENT` | 链接器：生成插桩版本 + `.pgd` |
| `/LTCG:PGO` | 链接器：读取 `.pgd` 做 profile 引导优化 |
| `/LTCG:PGUPDATE` | 增量更新：新增 `.pgc` 后无需完整重建 |
| `/PROFILE`（link.exe）| 生成可与性能分析工具配合的映像 |
| `pgomgr /merge` | 合并多个 `.pgc` 到 `.pgd` |
| `pgomgr /summary` | 显示 profile 热度统计 |

**与 GCC PGO 的关键差异**

| 维度 | MSVC | GCC |
|---|---|---|
| profile 文件格式 | `.pgd` + `.pgc`（私有格式）| `.gcda`（gcov 格式）|
| 合并工具 | `pgomgr` | `gcov` / `lcov` |
| 与 LTO 绑定 | 必须同时开 `/GL`/`/LTCG` | 可独立，但配合 `-flto` 效果更好 |
| 并行收集 | 多进程写 `.pgc` 编号自动递增，安全 | 多进程写 `.gcda` 需注意竞争 |

> 深度原理与 GCC/Clang PGO 横向对比见 [[05.PGO_Profile_Guided_Optimization|PGO 专题]]。

## 2. 代码生成 `/G` 选项

> 🔎 本节是 MSVC 最易混淆处。下面按"调用约定 / 安全 / 链接优化 / 钩子"分组，并标注大小写。

**调用约定（均仅 x86，x64 统一用一种 ABI）**
- **/Gd**：`__cdecl` 调用约定（x86 **默认**）
- **/Gr**：`__fastcall` 调用约定
- **/Gz**：`__stdcall` 调用约定 ← 注意是**小写 z**
- **/Gv**：`__vectorcall` 调用约定（x86 与 x64）

**安全与运行时检查**
- **/GS**：缓冲区安全检查（栈 cookie，默认开）；**/GS-** 关闭
- **/guard:cf**：控制流保护（Control Flow Guard）
- **/Gs[n]**：控制栈探测（stack probe）阈值
- **/GZ**：**（已弃用，VS2005 起）** 等同于 **/RTC1**，启用栈帧运行时错误检查，**仅用于 `/Od` 非优化构建**。现应改用 `/RTC`。← 注意是**大写 Z**，与 `/Gz` 毫无关系
- **/RTC1**：运行时检查（= `/RTCs` 栈帧检查 + `/RTCu` 未初始化变量检查）

**链接期优化相关**
- **/GL**：**全程序优化（Whole Program Optimization）**——让编译器跨所有模块做内联与全局分析，需配合链接器 **/LTCG**；同时使按概要引导优化（PGO）成为可能。`/GL-` 关闭
- **/Gy**：**函数级链接（function-level linking）**——为每个函数生成独立 COMDAT，便于链接器剔除未引用函数与折叠相同函数（`/OPT:REF,ICF`）
- **/Gw**：对全局数据也做类似 `/Gy` 的"按需保留"优化
- **/GF**：启用只读字符串池（相同字符串字面量合并且置于只读段）

**其他代码生成**
- **/GR**：启用 RTTI（默认）；**/GR-** 禁用
- **/GA**：为 Windows 应用程序优化（TLS 访问）
- **/GT**：支持基于静态 TLS 的纤程（fiber）安全
- **/Gm**：**（已弃用）** 启用最小重新生成（minimal rebuild）
- **/GX**：**（已弃用）** 同步异常处理，**请改用 /EH**
- **/Gh** / **/GH**：分别在每个函数**入口**调用 `_penter`、**出口**调用 `_pexit` 钩子函数（性能插桩用，需自行提供这两个函数实现）
- **/arch:**：指定指令集架构基线（如 `/arch:AVX2`、`/arch:AVX512`）

## 3. 预处理器选项

- **/D \<name>** / **/D \<name>=\<value>**：定义（带值）预处理器宏
- **/U \<name>**：取消某宏定义；**/u**：取消所有预定义宏
- **/I \<path>**：添加头文件包含路径
- **/FI \<file>**：强制（隐式）预包含某头文件
- **/FU \<file>**：强制 `#using` 某托管程序集
- **/C**：预处理时保留注释
- **/P**：预处理到 `.i` 文件
- **/showIncludes**：编译时打印所有被包含头文件（排查包含关系/编译慢）

## 4. 语言（一致性）选项

- **/std:c++14** / **/std:c++17** / **/std:c++20** / **/std:c++latest**：指定 C++ 标准（**`/std:c++14` 为下限，MSVC 没有 `/std:c++11`/`c++03` 开关**）
- **/std:c11** / **/std:c17**：指定 C 标准（VS2019 16.8+）
- **/permissive-**：**标准一致性模式**——关闭一批 MSVC 历史宽松行为，更贴近 ISO（强烈推荐新项目开启；在 `/std:c++20` 及以上**默认启用**）
- **/permissive**：关闭一致性模式（恢复宽松行为）
- **/Zc:\<feature>**：逐项一致性开关（如 `/Zc:__cplusplus` 让 `__cplusplus` 宏取正确值、`/Zc:preprocessor` 启用符合标准的预处理器）
- **/Za**：禁用语言扩展（C；C++ 下不推荐）
- **/openmp**：启用 OpenMP 支持

## 5. 调试选项

- **/Z7**：调试信息直接放进 `.obj`（CodeView/C7 格式，无独立 PDB）
- **/Zi**：生成独立程序数据库（PDB）调试信息
- **/ZI**：生成支持"编辑并继续"（Edit & Continue）的调试信息（仅 x86/调试）
- **/Fd\<file>**：指定 PDB 文件名
- **/FS**：强制串行化对 PDB 的写入（多进程编译时必需）
- **/Zo**：为优化代码生成增强调试信息
- **/Zp[n]**：设置结构体成员对齐

## 6. 异常处理

- **/EHsc**：标准 C++ 异常处理，并假定 `extern "C"` 函数不抛 C++ 异常（**最常用**）
- **/EHs**：同步异常处理（不做上面的 `extern "C"` 假定）
- **/EHa**：异步异常处理（可捕获结构化异常 SEH）
- **/GX**：**（已弃用）** 旧的异常处理开关，等价 `/EHsc`，请改用 `/EH`

## 7. 输出文件选项

- **/Fo\<file>**：指定 `.obj` 目标文件名
- **/Fe\<file>**：指定可执行文件名
- **/Fa\<file>** / **/FA**：生成汇编列表文件
- **/Fi\<file>**：指定预处理输出文件名
- **/Fm\<file>**：生成映射（map）文件
- **/Fp\<file>**：指定预编译头 `.pch` 文件名
- **/Fd\<file>**：指定 PDB 文件名

## 8. 预编译头选项

- **/Yc[file]**：**创建**预编译头
- **/Yu[file]**：**使用**预编译头
- **/Y-**：忽略其他所有预编译头选项
- **/Fp\<file>**：指定 `.pch` 文件名

## 9. 警告选项

> 🔧 本节区分**全局等级**（大写 `/W`）与**针对单条警告号**（小写 `/w` 后接编号）。原始资料常把二者混淆。

- **/W0 /W1 /W2 /W3 /W4**：设置警告**等级**（`0` 关闭全部 → `4` 最严格；工程推荐 `/W4`）
- **/Wall**：启用**所有**警告（包含大量默认关闭的、通常很嘈杂，仅排查时用）
- **/WX**：**将警告视为错误**（相当于 GCC/Clang 的 `-Werror`）；**/WX-** 取消
- **/wd\<n>**：禁用指定编号的警告（如 `/wd4996` 关闭"已弃用 API"警告）
- **/we\<n>**：把指定编号的警告**视为错误**（如 `/we4101`）
- **/wo\<n>**：指定编号的警告**只报告一次**
- **/w\<L>\<n>**：为指定编号警告设置等级 L（如 `/w34996` = 把 4996 设为等级 3 警告）
- **/external:W\<n>** / **/external:I\<path>**：对"外部头文件"单独设较低警告等级（避免第三方头刷屏）

## 10. 运行时库选项

- **/MD**：多线程 **DLL** 版运行时（`MSVCRT.lib`，发布常用）
- **/MDd**：多线程 DLL 调试版（`MSVCRTD.lib`）
- **/MT**：多线程**静态**运行时（`LIBCMT.lib`）
- **/MTd**：多线程静态调试版（`LIBCMTD.lib`）

> 📌 同一程序及其所有库必须使用**一致**的运行时库选项，否则会出现重复符号或堆跨边界释放等问题。

## 11. Sanitizer 与代码分析

- **/fsanitize=address**：启用 **AddressSanitizer（ASan）**——VS2019 **16.9+** 起支持，兼容所有优化级别（`/Od`~`/O2 /GL`）与静态/动态 CRT，可生成 EXE 或 DLL；建议配合 `/Zi`。命中即定位越界、use-after-free 等
- **/fsanitize=fuzzer**：启用 LibFuzzer 覆盖率引导模糊测试（VS2022 17.0+，实验性）
- **/fsanitize-coverage=...**：插入覆盖率插桩（供 fuzzer 等使用）
- **/analyze**：启用静态代码分析（C++ Core Guidelines / SAL 检查）

> ⚠️ `/fsanitize` 不支持逗号合并写法（不能 `/fsanitize=address,fuzzer`），需分别指定；且不支持配合 PGO。

## 12. 编译控制与杂项

- **/c**：只编译不链接
- **/link**：其后的参数透传给链接器 `link.exe`
- **/LD** / **/LDd**：创建（调试版）DLL
- **/nologo**：取消版权横幅输出
- **/TC** / **/TP**：把**所有**输入文件强制按 C / C++ 处理
- **/MP[n]**：多进程并行编译（充分利用多核）
- **/utf-8**：将源文件与执行字符集都设为 UTF-8（处理中文等非 ASCII 源码强烈推荐）

### 12.1 编译诊断与排查编译慢

MSVC 提供一批"诊断内部计时"隐藏选项，用于定位编译瓶颈（模板实例化/PCH 失效/头文件递归展开等）：

**`/d1reportTime`——编译器前端计时**

```bat
cl /d1reportTime /O2 app.cpp 2>&1 | head -60
```

输出每个翻译单元的：
- 顶级宏展开时间
- 模板实例化时间（按实例化点排序）
- 各阶段（解析/语义分析/代码生成）耗时

> 适合定位"某 `.cpp` 特别慢"——往往是某个递归模板或无节制的 `#include` 链。

**`/d2cgsummary`——编译器后端（代码生成）计时**

```bat
cl /O2 /d2cgsummary app.cpp
```

输出代码生成阶段各 pass 的耗时摘要（内联/向量化/寄存器分配等），结合 `/GL` 下的 LTO 耗时分析尤为有用。

**`/Bt`——子进程计时**

```bat
cl /Bt app.cpp
```

`/Bt`（Build Timing）打印 `cl.exe` 内部各子进程（`c1.dll` 前端、`c2.dll` 后端）的运行时间，格式如：

```
time(C:\...\c1.dll)=0.34s
time(C:\...\c2.dll)=1.12s
```

前端慢 → 模板/头文件问题；后端慢 → 代码生成/优化问题。

**排查编译慢的典型流程**

1. `cl /Bt` 快速定位是前端（`c1.dll`）还是后端（`c2.dll`）
2. 前端慢 → `cl /d1reportTime` 找模板实例化热点；检查 `/showIncludes` 输出确认 PCH 是否命中
3. 后端慢 → `cl /d2cgsummary` 查代码生成各 pass；考虑降低 `/Ob` 内联级别或减少 `/O2` 范围

### 12.2 C++20 Modules（模块）支持

MSVC 从 **VS 2019 16.8** 起试验性、**VS 2022 17.x** 起稳定支持 C++20 Modules（`/std:c++20` 或 `/std:c++latest` 下开启）。

**关键编译器选项**

| 选项 | 含义 |
|---|---|
| **/interface** | 将当前翻译单元编译为**模块接口单元**（Module Interface Unit），生成 `.ifc` 文件 |
| **/internalPartition** | 编译模块分区实现单元（不导出的内部实现）|
| **/exportHeader \<header>** | 将传统头文件（如 `<vector>`）封装成头单元（Header Unit），生成 `.ifc` |
| **/reference \<name>=\<ifc>** | 指定被 `import` 的模块名到 `.ifc` 路径的映射 |
| **/translateInclude** | 将 `#include <header>` 自动替换为对应头单元的 `import`（需配合 `/exportHeader`）|
| **/headerName:quote** / **/headerName:angle** | 指定头单元名称查找规则 |

**`.ifc` 文件（Interface Compilation artifact）**

`.ifc` 是 MSVC 的**二进制模块接口格式**（Binary Module Interface，BMI），类似 GCC/Clang 的 `.pcm`。它包含编译器所需的所有类型、模板定义等信息，但**不是目标文件**——仍需同时编译出 `.obj`。

**典型构建流程示例**

```bat
rem 1. 编译模块接口单元，生成 math.ifc + math.obj
cl /std:c++20 /c /interface /TP math.ixx /Fo:math.obj

rem 2. 编译消费者，引用 math.ifc
cl /std:c++20 /c /reference math=math.ifc main.cpp /Fo:main.obj

rem 3. 链接
link math.obj main.obj /OUT:app.exe
```

**与传统头文件/PCH 的对比**

| 维度 | 传统 `#include` + PCH | C++20 Modules |
|---|---|---|
| 文本还是二进制 | 文本展开（PCH 是二进制缓存）| 全程二进制（`.ifc`）|
| 宏泄漏 | 头文件宏对所有包含者可见 | 模块**不导出宏**，彻底隔离 |
| 重新编译 | 头文件改动触发所有包含者重编 | `.ifc` 接口不变则消费者无需重编 |
| 构建系统支持 | 成熟 | 需要构建系统显式管理 `.ifc` 依赖（CMake 3.28+ 支持）|
| 与旧代码互操作 | 天然兼容 | `import <header>` 或 `#include` 内全局模块片段（GMF）|

**陷阱**

- **顺序依赖**：`.ifc` 必须在消费者之前生成，构建系统需正确处理依赖顺序（`cl.exe` 不自动扫描依赖）
- **跨模块宏**：模块不导出宏，若第三方库依赖宏传递（如 `BOOST_*` 配置宏），需在全局模块片段中先 `#include`
- **`/translateInclude` 注意事项**：自动将 `#include` 转为头单元 import 可能打破依赖宏的头文件顺序

### 12.3 `/Brepro` 可复现构建

```bat
cl /Brepro app.cpp
```

`/Brepro` 让 MSVC 在生成 `.obj` 时，将 PDB 的 GUID 替换为**从源文件内容派生的确定性哈希**，而非随机 UUID——从而消除因随机 GUID 导致的"内容相同但二进制不同"问题。

**为什么默认构建不可复现？**

MSVC 默认在每次编译时为每个 `.obj` 生成随机 GUID（用于 PDB 匹配），即便源码未变、编译选项未变，两次构建产物二进制也不同。这影响：
- 增量构建判断（构建系统误认为文件变化）
- 分发/缓存（无法用内容哈希去重）
- 供应链安全审计（无法校验产物来源）

**配合使用**：`/Brepro` 只处理 `.obj` 的 GUID，要做到完全可复现构建还需消除其他时间戳来源（链接器 `/Brepro` 选项同样存在，用于处理 PE 映像时间戳）。

> 可复现构建的完整实践（工具链配置、CI 验证、与 Clang/GCC 对比）见 [[09.Reproducible_Builds_and_Cross_Compile|可复现构建与交叉编译专题]]。

### 12.4 `__asm`（x86 内联汇编）与 Intrinsics

#### `__asm`——仅限 x86 的内联汇编

MSVC 支持在 **x86（32位）** 代码中使用 `__asm` 关键字嵌入 Intel 语法汇编（与 GCC AT&T 语法相反，使用 `目标, 源` 操作数顺序）：

```c
// 仅 x86（32位），x64 下编译报错
int add_asm(int a, int b) {
    __asm {
        mov eax, a
        add eax, b
        // 返回值通过 eax 传递
    }
}
```

**x64 下无 `__asm`**：MSVC **x64 编译器不支持内联汇编**。原因是 x64 ABI（特别是异常处理和栈展开）需要编译器完全控制帧结构，内联汇编会破坏展开元数据的生成。x64 下唯一的选择是：
1. **Intrinsics**（推荐）：用 `<intrin.h>` 或 `<immintrin.h>` 中的 C 内联函数
2. **独立 `.asm` 文件**（MASM）：通过 `ml64.exe` 汇编，在链接期合并

#### Intrinsics——平台相关内置函数

MSVC 提供两套头文件：

**`<intrin.h>`——MSVC 专有内置函数**

```c
#include <intrin.h>

// CPU 特性检测
int info[4];
__cpuid(info, 0);             // 执行 CPUID 指令

// 原子操作（x86/x64 均可）
long val = _InterlockedIncrement(&counter);
long old = _InterlockedCompareExchange(&target, new_val, expected);

// 位操作
unsigned char _BitScanForward(unsigned long *index, unsigned long mask);  // BSF
unsigned char _BitScanReverse(unsigned long *index, unsigned long mask);  // BSR
unsigned int __popcnt(unsigned int value);   // POPCNT（需 /arch:SSE4.2 或以上）

// 内存屏障
_ReadWriteBarrier();          // 编译器屏障（不生成 MFENCE）
__faststorefence();           // x64: sfence
_mm_mfence();                 // 需要 SSE2
```

**`<immintrin.h>`——Intel SIMD Intrinsics（SSE/AVX）**

```c
#include <immintrin.h>

// 需要 /arch:AVX2
__m256i a = _mm256_loadu_si256((__m256i*)src);
__m256i b = _mm256_loadu_si256((__m256i*)src2);
__m256i c = _mm256_add_epi32(a, b);             // 8 x int32 并行加法
_mm256_storeu_si256((__m256i*)dst, c);

// 需要 /arch:SSE4.1
__m128i x = _mm_blendv_epi8(a, b, mask);
```

**`/arch:` 选项与 Intrinsics 的对应关系**

| `/arch:` | 可用 Intrinsics |
|---|---|
| 默认（x64）| SSE、SSE2 |
| `/arch:SSE4.2` | + SSE3/SSSE3/SSE4.1/SSE4.2/POPCNT |
| `/arch:AVX` | + AVX（256位浮点）|
| `/arch:AVX2` | + AVX2（256位整数）+ FMA3 |
| `/arch:AVX512` | + AVX-512 系列 |

**与 GCC `__builtin_*` 的对比**

| 功能 | MSVC | GCC |
|---|---|---|
| 位计数 | `__popcnt()` | `__builtin_popcount()` |
| 前导零 | `_BitScanReverse()` | `__builtin_clz()` |
| 预取 | `_mm_prefetch()` | `__builtin_prefetch()` |
| 分支预测 | 无直接等价（用 `__assume()`）| `__builtin_expect()` |
| CPUID | `__cpuid()` | `__builtin_cpu_supports()` |

> 内联汇编进阶（x64 MASM 集成、AVX-512 Intrinsics 实战）与 GCC `asm volatile` 详见 [[08.Inline_Asm_and_Intrinsics|内联汇编与 Intrinsics 专题]]。

## 二、链接器参数（link.exe）

## 1. 基础选项

- **/OUT:\<file>**：指定输出文件名
- **/ENTRY:\<symbol>**：指定入口点函数
- **/SUBSYSTEM:\<type>**：指定子系统（`CONSOLE` / `WINDOWS` 等）
- **/DLL**：生成动态链接库
- **/MAP[:file]**：生成映射文件
- **/DEBUG**：生成调试信息（PDB）
- **/MACHINE:\<arch>**：指定目标平台（`X64`/`X86`/`ARM64`）
- **/BASE:\<addr>** / **/ALIGN**：设置基址 / 段对齐

## 2. 优化选项

- **/LTCG**：**链接时代码生成**——与编译器 `/GL` 配套，完成跨模块优化
- **/OPT:REF**：剔除未被引用的函数/数据；**/OPT:ICF**：折叠内容相同的 COMDAT（配合 `/Gy` 效果最佳）
- **/INCREMENTAL[:NO]**：启用/关闭增量链接（调试快、发布建议关）
- **/ORDER** / **/SECTION** / **/MERGE**：函数排序 / 段属性 / 合并段

## 3. 符号与库选项

- **/LIBPATH:\<dir>**：附加库搜索路径
- **/DEFAULTLIB:\<lib>** / **/NODEFAULTLIB**：添加 / 忽略默认库
- **/DEF:\<file>**：模块定义文件
- **/EXPORT:\<symbol>**：导出函数
- **/IMPLIB:\<file>**：指定生成的导入库名
- **/DELAYLOAD:\<dll>**：延迟加载某 DLL
- **/MANIFEST[:...]** / **/MANIFESTINPUT**：生成 / 输入清单

## 4. 安全与加固选项

- **/DYNAMICBASE**：启用地址空间布局随机化（ASLR，默认开）
- **/HIGHENTROPYVA**：启用 64 位高熵 ASLR
- **/NXCOMPAT**：兼容数据执行保护（DEP）
- **/GUARD:CF**：在映像中启用控制流保护
- **/CETCOMPAT**：标记为 CET（影子栈）兼容
- **/SAFESEH**：生成安全异常处理表（x86）

## 5. 其他常用

- **/STACK:\<n>** / **/HEAP:\<n>**：设置栈 / 堆大小
- **/VERSION:\<n>**：设置映像版本号
- **/PROFILE**：为性能分析/PGO 生成可用映像
- **/VERBOSE**：打印链接过程详细进度
- **/NOLOGO**：取消版权横幅
- **/IGNORE:\<n>** / **/ERRORREPORT**：忽略指定警告 / 错误报告行为

---

正确使用这些选项可以在性能、体积与安全之间取得平衡。MSVC 的两个高频"现代化"建议：**新项目开启 `/permissive-` 与 `/std:c++20`** 提升标准一致性，**用 `/W4 /WX` 把缺陷拦在编译期**，调试构建再加 `/fsanitize=address` 暴露内存问题。
