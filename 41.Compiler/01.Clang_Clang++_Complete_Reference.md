# Clang/Clang++ 编译器完整参数详解

> Clang 是 LLVM 项目的 C / C++ / Objective-C 前端，以**编译速度快、诊断信息友好、模块化易集成**著称。它在命令行上**高度兼容 GCC**（绝大多数 `-W`、`-O`、`-f`、`-m` 选项同名同义），因此本文重点放在 Clang 的**特有项**与**与 GCC 的差异**上。
>
> **版本基准**：以现代 Clang（**17 及以上**）为参考，涉及版本差异处会显式标注。
>
> **另见**：[[03.GCC_G++_Complete_Reference|GCC/G++ 参考]] · [[04.MSVC_Complete_Reference|MSVC 参考]] · [[02.Compiler_Comparison|GCC vs Clang vs MSVC 对比]]

## Clang 编译流程

Clang 高度集成，概念上同样经历 4 个阶段，但中间表示是 **LLVM IR**：

1. **预处理（Preprocessing）**：处理 `#include`、`#define`、`#ifdef` 等指令，生成 `.i`/`.ii` 中间文件。
2. **解析与语义分析（Parsing & Semantic Analysis）**：把源码解析为抽象语法树（AST）并做类型检查。
3. **代码生成与优化（CodeGen & Optimization）**：把 AST 降级为 **LLVM IR**，在 IR 上做优化。
4. **汇编与链接（Assembly & Linking）**：由后端把 IR 编译为机器码生成目标文件，再链接成可执行文件。

> 💡 Clang 内置集成汇编器，默认不调用外部 `as`；可用 `-emit-llvm`、`-S` 在各阶段间观察产物。

## 1. 阶段选择选项（Stage Selection Options）

- **-E**：仅运行预处理器，输出预处理后的源码
- **-fsyntax-only**：只做预处理、解析与类型检查，不生成代码（最快的"语法体检"）
- **-S**：生成汇编文件（`.s`），不汇编、不链接
- **-c**：生成目标文件（`.o`），不链接
- **（不指定）**：执行全部阶段并链接成可执行文件

## 2. 输出与诊断观察选项（Output Options）

- **-o \<file>**：指定输出文件名
- **-v**：显示编译过程的详细命令与路径
- **-###**：只打印将要执行的命令而不执行
- **--help** / **--version**：帮助 / 版本信息

## 3. 语言选择与模式选项（Language Selection）

- **-x \<language>**：指定源文件语言（`c`、`c++`、`objective-c`、`objective-c++`）
- **-std=\<standard>**：指定语言标准
  - C：`c99`、`c11`、`c17`、`c23`，及 `gnu99`/`gnu11`/`gnu17`/`gnu23`
  - C++：`c++11`、`c++14`、`c++17`、`c++20`、`c++23`（早期临时名 `c++2b`）、`c++26`（实验，`c++2c`），及对应 `gnu++*`
  - **`c++NN` vs `gnu++NN`**：前者严格遵循 ISO 标准、禁用扩展；后者额外允许 GNU 扩展。Clang 默认采用 `gnu++NN`
- **-ansi**：等价于 `-std=c89`（C）或 `-std=c++98`（C++）
- **-ObjC / -ObjC++**：把输入按 Objective-C / Objective-C++ 处理

## 4. 预处理器选项（Preprocessor Options）

- **-D \<macro>[=\<value>]** / **-U \<macro>**：定义 / 取消宏
- **-I \<dir>**：添加头文件搜索目录
- **-iquote \<dir>**：仅为 `#include "file"` 添加搜索目录
- **-isystem \<dir>**：添加系统头文件目录（抑制其中告警）
- **-idirafter \<dir>**：添加次级（最后搜索）目录
- **-include \<header>**：在所有源文件开头隐式包含某头文件
- **-imacros \<header>**：仅读取某文件的宏定义
- **-nostdinc**：不搜索标准系统头文件目录
- **-MD** / **-MMD** / **-MF** / **-MP**：依赖关系文件生成（语义同 GCC）

## 5. 诊断选项（Diagnostic Options）

- **-Wall** / **-Wextra**：启用常用 / 额外警告
- **-Werror** / **-Werror=\<warning>**：（指定）警告视为错误
- **-Wpedantic** / **-pedantic-errors**：（强制）ISO 标准符合性
- **-Weverything**：启用**所有**警告（**Clang 特有**，仅适合排查，不建议常开）
- **-w**：禁用所有警告
- **-Wno-\<warning>**：禁用某条具体警告
- **-fdiagnostics-show-option**：在诊断里显示触发它的 `-W` 选项名（默认开）
- **-fcaret-diagnostics**：用 `^` 标注出错的具体位置（Clang 招牌诊断体验，默认开）
- **-fcolor-diagnostics** / **-fno-color-diagnostics**：启用 / 禁用彩色诊断
- **-fmessage-length=n**：设置诊断换行宽度

> 🎯 Clang 的诊断质量是其核心卖点：默认带源码片段、`^~~~` 区间标注与修复建议（fix-it）。

## 6. 优化选项（Optimization Options）

- **-O0**：不优化（默认）
- **-O1**：介于 `-O0` 与 `-O2` 的基础优化
- **-O2**：开启大部分优化（典型发布级别）
- **-O3**：在 `-O2` 之上启用更耗时、可能增大体积的优化
- **-Os**：类似 `-O2` 但额外控制代码体积
- **-Oz**：比 `-Os` 更激进地压缩体积
- **-Ofast**：在 `-O3` 上叠加可能违反标准的激进优化；**自 Clang 19 起已弃用**，推荐改用 `-O3 -ffast-math -fstrict-aliasing`
- **-Og**：偏调试友好的优化（接近 `-O1`）
- **-O4**：**当前等价于 `-O3`**。历史上曾用于触发链接时优化（LTO），现已不再，如需 LTO 请显式使用 `-flto`（见 §11）

## 7. 调试选项（Debugging Options）

- **-g**：生成调试信息
- **-g0**：不生成调试信息
- **-gline-tables-only**：仅生成行号表（崩溃栈回溯够用、体积小）
- **-gdwarf-4 / -gdwarf-5**：生成指定版本 DWARF
- **-glldb** / **-ggdb**：为 LLDB / GDB 调优调试信息
- **-fstandalone-debug** / **-fno-standalone-debug**：是否生成独立（更完整）的调试类型信息

## 8. 代码生成选项（Code Generation Options）

- **-fPIC** / **-fpic**：生成位置无关代码（用于共享库）
- **-fPIE** / **-fpie**：生成位置无关可执行代码
- **-fdata-sections** / **-ffunction-sections**：把每个数据/函数放入独立 section（配合链接器 `--gc-sections` 去除未引用部分）
- **-fcommon** / **-fno-common**：是否允许未初始化全局变量的暂定定义（现代默认 `-fno-common`）
- **-fexceptions** / **-fno-exceptions**：启用 / 禁用 C++ 异常
- **-frtti** / **-fno-rtti**：启用 / 禁用 RTTI
- **-fvisibility=hidden|default|protected|internal**：设置符号默认可见性
- **-fstack-protector** / **-fstack-protector-strong** / **-fstack-protector-all**：栈保护（强度递增）

## 9. 目标选择选项（Target Selection Options）

- **-target \<triple>** / **--target=\<triple>**：指定交叉编译目标三元组（如 `aarch64-linux-gnu`）。**Clang 原生支持交叉编译**，无需为每个目标单独构建一套编译器
- **-m32 / -m64**：生成 32 / 64 位代码
- **-march=\<arch>**：指定目标架构（`x86-64-v3`、`armv8-a`、`native` 等）
- **-mtune=\<tune>**：按指定微架构调优
- **-mcpu=\<cpu>**：指定目标 CPU
- **-mfpu=\<unit>** / **-mfloat-abi=hard|soft|softfp**：ARM 浮点单元与 ABI

## 10. 链接器选项（Linker Options）

- **-L \<dir>** / **-l \<library>**：库搜索目录 / 链接指定库
- **-static** / **-shared**：仅静态库 / 生成共享库
- **-Wl,\<flag>**：透传选项给链接器
- **-fuse-ld=lld|gold|bfd|mold**：选择链接器（**`lld` 是 LLVM 自带链接器，速度很快**）
- **-rdynamic**：把所有符号加入动态符号表
- **-nostdlib** / **-nodefaultlibs**：不使用标准库

## 11. 链接时优化（LTO）

- **-flto** / **-flto=full**：完整 LTO，跨翻译单元做全局优化
- **-flto=thin**：**ThinLTO**（Clang 特色）——并行、增量友好，体积/时间开销远小于 full LTO，效果接近
- **-fwhole-program-vtables**：配合 LTO 做虚表全程序优化（去虚拟化）
- **-fembed-bitcode**：在目标文件中嵌入 bitcode（iOS/macOS 历史用途）

## 12. 程序插桩与 Sanitizer（Sanitizers）

**Sanitizer 系列正是在 Clang/LLVM 中诞生**，是其招牌能力。**编译与链接都需加同一选项**，建议配合 `-g -fno-omit-frame-pointer`：

- **-fsanitize=address**（ASan）：越界、use-after-free、栈/全局溢出等内存错误
- **-fsanitize=undefined**（UBSan）：整数溢出、空指针解引用、非法移位等未定义行为
- **-fsanitize=thread**（TSan）：数据竞争检测（会强制 PIE/PIC）
- **-fsanitize=memory**（MSan）：未初始化内存读取（**Clang 特有**，GCC 无）
- **-fsanitize=leak**（LSan）：内存泄漏
- **-fsanitize=cfi**：控制流完整性（需配合 `-flto -fvisibility=hidden`，**Clang 特有**）
- **-fsanitize=address,undefined**：ASan 与 UBSan **可组合**；**TSan/MSan 不能与 ASan 同时使用**
- **-fno-sanitize-recover=all**：命中即终止（默认部分检查可恢复继续）

## 13. 静态分析与其他（Static Analyzer & Misc）

- **--analyze**：运行 Clang **静态**分析器（编译期发现部分缺陷，区别于上面的运行期 Sanitizer）
- **-Xanalyzer \<arg>**：透传参数给静态分析器
- **-ftime-trace**：生成可在 `chrome://tracing` 查看的编译耗时火焰图（排查编译慢的利器）
- **-emit-llvm**：输出 **LLVM IR**（配合 `-S` 得 `.ll` 文本，配合 `-c` 得 `.bc` 字节码）而非机器码
- **-Xclang \<arg>**：把参数直接透传给 Clang 前端（cc1）
- **-fno-discard-value-names**：保留 LLVM IR 中的值名（调试 IR 时更可读）
- **-fno-integrated-as**：改用外部汇编器，而非内置集成汇编器

---

Clang 与 GCC 在命令行上高度兼容，迁移成本低；选择 Clang 的典型理由是**更友好的诊断、更快的编译、ThinLTO、丰富的 Sanitizer，以及对交叉编译与工具链集成的天然支持**。

## 14. PGO（IR-PGO，Instrumentation-based Profile-Guided Optimization）

PGO 是一套"先插桩采集运行时热点，再利用 profile 数据重新编译"的两阶段优化方案。Clang 的 IR-PGO 在 **LLVM IR 层**插桩，比旧式前端插桩噪声更少、精度更高。

### 工作流程

```bash
# 第一步：用插桩构建生成带 profraw 的可执行文件
clang++ -O2 -fprofile-instr-generate -o app_instr app.cpp

# 第二步：用代表性负载运行，生成 .profraw
./app_instr <typical-workload>
# 产出：default.profraw（或 LLVM_PROFILE_FILE 环境变量指定路径）

# 第三步：合并多次运行的 profraw → profdata
llvm-profdata merge -sparse default.profraw -o app.profdata

# 第四步：利用 profdata 做 PGO 优化重编译
clang++ -O2 -fprofile-instr-use=app.profdata -o app_pgo app.cpp
```

### 关键选项

| 选项 | 作用 |
|------|------|
| `-fprofile-instr-generate` | 插桩编译，统计每个计数器执行次数 |
| `-fprofile-instr-generate=<path>` | 指定 profraw 输出路径模式 |
| `-fprofile-instr-use=<file>` | 使用 profdata 进行 PGO 重编译 |
| `LLVM_PROFILE_FILE=out%p.profraw` | 运行时控制输出路径，`%p` 展开为 PID |
| `llvm-profdata merge -sparse` | 合并、去噪、转换 profraw → profdata |

### 边界陷阱

- **profdata 与可执行文件须来自同一次插桩编译**：源码或优化级别变动后 profdata 的哈希失配会触发 `-Wprofile-instr-out-of-date` 警告，旧数据仍会被采用但可能造成反优化。
- **fork/多进程**：使用 `%p`（PID）或 `%m`（模块 ID）模式避免多进程覆盖同一文件。
- **PGO + LTO 叠加**：`-flto=thin -fprofile-instr-use` 可组合，效果叠加；但 full LTO 下插桩编译需同时加 `-flto`。
- **CI 中的 profdata 缓存**：profdata 依赖代码热点结构，在大版本改动后建议重新采集，不要无限期复用。

> 详细 PGO 工作流、Context-Sensitive PGO（CS-PGO）及 perf-to-profdata 转换方案见 [[05.PGO_Profile_Guided_Optimization]]。

## 15. AutoFDO / Sample PGO

AutoFDO（Automatic Feedback-Directed Optimization）是 PGO 的**无插桩变体**：用系统采样工具（Linux `perf`、macOS `instruments`）在**生产环境**对已发布二进制采集硬件性能计数器，再将其转换为 Clang 可用的 profile，无需插桩编译与重新部署插桩二进制。

### 工作流程

```bash
# 第一步：以调试信息构建生产二进制
clang++ -O2 -g1 -o app app.cpp          # -g1 仅生成行号表，开销极小

# 第二步：Linux perf 采样（在生产机或压测环境）
perf record -b -e br_inst_retired:near_taken -o perf.data ./app <workload>

# 第三步：转换 perf.data → AutoFDO profile（需 google/autofdo 工具）
create_llvm_prof --binary=app --profile=perf.data --out=app.afdo

# 第四步：Sample PGO 重编译
clang++ -O2 -fprofile-sample-use=app.afdo -o app_afdo app.cpp
```

### 与 IR-PGO 的对比

| 维度 | IR-PGO（插桩） | AutoFDO（采样） |
|------|--------------|----------------|
| 插桩开销 | 运行时约 5–30% 性能损失 | 近乎零开销（硬件计数器） |
| profile 精度 | 高（软件计数器，精确计数） | 较低（采样率依赖频率设置） |
| 需要重新部署 | 需要插桩二进制 | 直接对已有生产二进制采样 |
| 冷路径覆盖 | 均匀（只要执行到） | 依赖采样频率，低频路径可能被忽略 |

### 关键选项

- **`-fprofile-sample-use=<file>`**：使用 AutoFDO/Sample PGO profile 进行编译。
- **`-fprofile-sample-accurate`**：告知编译器 profile 数据全面可信，对 profile 未覆盖的代码路径做更激进的去优化（反向暗示冷代码）。
- **`-fcs-profile-generate`**：Context-Sensitive Sample PGO，在执行到采样热点时动态插桩，进一步提升精度。

### BOLT 后链接优化

对于 AutoFDO 无法显著优化的**布局**与**指令缓存**问题，可叠加 BOLT（Binary Optimization and Layout Tool）对最终二进制做后链接重排。BOLT 同样基于 `perf` profile，与 AutoFDO 流程自然衔接。

> BOLT 的完整工作流程、适用场景与限制见 [[06.BOLT_Post_Link_Optimization]]。

## 16. `-Xclang` 常用调试开关

`-Xclang <arg>` 把参数直接透传给 **Clang 前端（cc1）**，可访问正常驱动层不暴露的内部调试接口。这些选项**不保证跨版本稳定**，仅用于开发调试与原理探究，不应出现在生产构建脚本中。

### AST 观察

```bash
# 打印 AST（类树状文本，适合理解类型与节点结构）
clang++ -Xclang -ast-dump -fsyntax-only foo.cpp

# 按 JSON 格式输出 AST（便于程序解析）
clang++ -Xclang -ast-dump=json -fsyntax-only foo.cpp

# 仅打印某个函数的 AST（结合 -ast-dump-filter）
clang++ -Xclang -ast-dump -Xclang -ast-dump-filter -Xclang myFunc -fsyntax-only foo.cpp
```

### LLVM IR 输出

```bash
# 输出优化前 IR（文本 .ll 格式）
clang++ -O2 -emit-llvm -S -o out.ll foo.cpp

# 输出优化后 IR（字节码 .bc 格式，可用 llvm-dis 反汇编）
clang++ -O2 -emit-llvm -c -o out.bc foo.cpp

# 用 opt 对 .bc 手动跑某个优化 pass
opt -O2 out.bc -o out_opt.bc
llvm-dis out_opt.bc -o out_opt.ll
```

> 关于 LLVM IR 的结构、SSA 形式与 pass 体系，详见 [[07.Compiler_IR_GIMPLE_RTL_LLVM]]。

### 编译统计与 Pass 计时

```bash
# 打印各 LLVM IR Pass 执行次数与统计（需 assert build 或 release+stats）
clang++ -O2 -Xclang -print-stats foo.cpp

# 输出每个 Pass 耗时（更细粒度，适合排查优化瓶颈）
clang++ -O2 -ftime-report foo.cpp

# 火焰图（可在 chrome://tracing 打开）
clang++ -O2 -ftime-trace foo.cpp
# 生成 foo.json，Chrome Tracing 格式
```

### 其他常用 cc1 开关

| 开关 | 效果 |
|------|------|
| `-Xclang -disable-llvm-passes` | 跳过所有 LLVM 优化 pass，仅做前端 → IR 降级（观察"原始"IR） |
| `-Xclang -disable-O0-optnone` | 在 `-O0` 下去掉 `optnone` 属性，使后续 `opt` 可正常优化（调试插桩场景常用） |
| `-Xclang -verify` | 启用注释驱动的诊断验证（编写编译器测试时使用） |
| `-Xclang -fconstexpr-depth=N` | 设置 `constexpr` 求值深度上限（调试模板元编程超深递归） |

### 边界陷阱

- `-Xclang` 选项仅在**单一翻译单元**的 cc1 调用中生效；使用 LTO 时部分选项不适用。
- 不同 Clang 版本的 cc1 参数可能改名或废弃，`clang -cc1 --help` 可查当前版本支持的完整列表。

## 17. Clang 工具链生态

Clang 的模块化架构使其天然适合作为**工具链底座**。以下工具均基于 libclang / LibTooling，共享同一份编译数据库（`compile_commands.json`）。

### compile_commands.json（编译数据库）

`compile_commands.json` 是工具链生态的**枢纽文件**，记录每个翻译单元的确切编译命令（包含 `-I`、`-D`、`-std` 等）。

```bash
# CMake 生成（最常见方式）
cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON ..

# Ninja + Bear（针对非 CMake 项目）
bear -- make

# 手动生成（compiledb 工具）
pip install compiledb
compiledb make
```

> 没有 `compile_commands.json`，clangd / clang-tidy 只能做**单文件推断**，跨文件的头文件路径与宏定义会丢失，导致大量假阳性错误。

### clang-tidy（静态分析与 lint）

clang-tidy 是基于 AST 的**规则化 lint 工具**，提供 500+ 内置检查，涵盖性能、可读性、现代化改写、bug-prone 模式等。

```bash
# 检查单文件（需 compile_commands.json 在父目录或 -p 指定）
clang-tidy src/foo.cpp -- -std=c++17

# 指定规则（modernize 系列自动改写旧风格为现代 C++）
clang-tidy -checks='modernize-*,readability-*' src/foo.cpp

# 自动修复（-fix，修改源文件，建议先 git commit 再执行）
clang-tidy -checks='modernize-use-nullptr' -fix src/foo.cpp

# 批量运行整个项目（借助 run-clang-tidy.py）
run-clang-tidy -p build/ -checks='clang-analyzer-*,performance-*'
```

常用检查族：

| 检查族 | 典型用途 |
|--------|---------|
| `clang-analyzer-*` | 路径敏感静态分析（对应 `--analyze`） |
| `modernize-*` | 改写 C++98 代码为 C++11/14/17 风格 |
| `performance-*` | 检测不必要拷贝、低效 API 使用等 |
| `readability-*` | 命名、括号、const 放置等可读性规则 |
| `bugprone-*` | 已知 bug-prone 模式（移动后使用、整数截断等） |
| `cppcoreguidelines-*` | C++ Core Guidelines 对应检查 |

### clang-format（代码格式化）

clang-format 是基于词法/AST 的**格式化工具**，支持 LLVM、Google、Mozilla、WebKit、Microsoft 等内置风格，也可通过 `.clang-format` 文件细粒度定制。

```bash
# 原地格式化（-i）
clang-format -i src/foo.cpp

# 指定风格
clang-format -style=Google src/foo.cpp

# 仅格式化 diff 中改动的行（CI 中常用，避免全文件噪声）
git diff -U0 HEAD | clang-format-diff -p1 -i

# 导出当前风格为 .clang-format 配置文件
clang-format -style=LLVM -dump-config > .clang-format
```

### clangd（语言服务器，LSP）

clangd 是 LLVM 官方的 **Language Server Protocol** 实现，为编辑器（VS Code、Vim/Neovim、Emacs 等）提供代码补全、跳转定义、悬停文档、重构和实时诊断。

```bash
# VS Code：安装 clangd 扩展，它会自动发现 compile_commands.json
# Neovim（nvim-lspconfig）：
#   require('lspconfig').clangd.setup{}
# 手动启动（调试）：
clangd --compile-commands-dir=./build --log=verbose
```

关键配置选项（`.clangd` 文件或命令行）：

| 选项 | 作用 |
|------|------|
| `--background-index` | 后台建立全项目索引（跳转更准确） |
| `--clang-tidy` | 在编辑器中实时显示 clang-tidy 诊断 |
| `--header-insertion=never` | 禁止自动插入头文件（可能插错时用） |
| `--compile-commands-dir=<dir>` | 手动指定 compile_commands.json 目录 |

### 边界陷阱

- **clang-tidy `-fix` 与宏**：宏展开内的代码修复容易出错，建议对含复杂宏的文件仔细审查修复结果。
- **clangd 与 precompiled headers（PCH）**：部分构建系统生成的 PCH 路径在 `compile_commands.json` 中记录有误，导致 clangd 无法使用 PCH，回退为全量解析（速度变慢）。
- **多构建目录**：当项目有 debug/release 两套 build 时，`compile_commands.json` 只有一份，需手动选择或用软链接指向。

> 完整的 clang-tidy 规则库、clangd 配置方案与 CMake 集成见 [[10.Clang_Tooling_Ecosystem]]。
