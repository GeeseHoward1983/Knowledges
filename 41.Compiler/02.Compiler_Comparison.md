# GCC、Clang 和 MSVC 编译器对比

> 本文从平台、流程、选项、特色、性能、生态等维度，横向对比三大主流 C/C++ 编译器，帮助按场景选型。每款编译器的逐项参数详解见对应参考页。
>
> **逐项参数详解**：[[03.GCC_G++_Complete_Reference|GCC/G++ 参考]] · [[01.Clang_Clang++_Complete_Reference|Clang/Clang++ 参考]] · [[04.MSVC_Complete_Reference|MSVC 参考]]

---

## 基本信息

| 编译器 | 开发方 | 支持平台 | 许可证 | 命令行风格 |
|--------|--------|----------|--------|------------|
| **GCC** | GNU 项目 | Linux、macOS、Windows(MinGW) 等 | GPLv3 | `-` 选项 |
| **Clang** | LLVM 项目 | Linux、macOS、Windows 等 | Apache 2.0 with LLVM Exception | `-` 选项（兼容 GCC） |
| **MSVC** | Microsoft | 仅 Windows | 商业（随 VS） | `/` 选项（区分大小写） |

> 📝 Clang 早期采用 NCSA/BSD 风格许可，自 LLVM 8（2019）起统一为 **Apache 2.0 with LLVM Exception**。

## 编译流程

三者都经历"预处理 → 编译 → 汇编 → 链接"，差异在中间表示：

| 阶段 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 中间产物 | `.i`→`.s`→`.o` | `.i`→**LLVM IR**→`.o` | `.i`→`.asm`→`.obj` |
| 关键工具 | `cpp`/`cc1`/`as`/`ld` | 集成式（内置汇编器） | `cl.exe`/`link.exe` |
| 输出 | 可执行 / `.so` | 可执行 / `.so`/`.dylib` | `.exe` / `.dll` |

详细阶段说明见各自参考页的"编译流程"一节。

## 主要选项对比

### 1. 阶段控制

| 用途 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 只预处理 | `-E` | `-E` | `/E`（或 `/P` 输出到文件） |
| 生成汇编 | `-S` | `-S` | `/FA` |
| 生成目标文件 | `-c` | `-c` | `/c` |
| 指定输出 | `-o file` | `-o file` | `/Fo<file>`（目标）/ `/Fe<file>`（exe） |

### 2. 优化级别

| 用途 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 无优化（调试） | `-O0` | `-O0` | `/Od` |
| 基本优化 | `-O1` | `-O1` | — |
| 速度优化（发布） | `-O2` | `-O2` | `/O2` |
| 更激进 | `-O3` | `-O3` | `/Ox`（子集） |
| 体积优化 | `-Os` | `-Os` / `-Oz` | `/O1` |
| 调试友好优化 | `-Og` | `-Og` | — |
| 链接时优化 | `-flto` | `-flto` / `-flto=thin` | `/GL` + 链接器 `/LTCG` |

### 3. 调试信息

| 用途 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 生成调试信息 | `-g` | `-g` | `/Zi`（独立 PDB） |
| 嵌入式调试信息 | — | — | `/Z7` |
| 编辑并继续 | — | — | `/ZI`（x86） |
| 调试时优化 | `-Og` | `-Og` | `/Od` |

### 4. 警告

| 用途 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 常用警告 | `-Wall` | `-Wall` | `/W3` |
| 额外警告 | `-Wextra` | `-Wextra` | `/W4` |
| 警告视为错误 | `-Werror` | `-Werror` | `/WX` |
| 启用（几乎）所有 | `-Wall -Wextra` | `-Weverything` | `/Wall` |
| 禁用单条警告 | `-Wno-<name>` | `-Wno-<name>` | `/wd<编号>` |

### 5. C++ 语言标准

| 标准 | GCC | Clang | MSVC |
|------|-----|-------|------|
| C++11 | `-std=c++11` / `gnu++11` | `-std=c++11` / `gnu++11` | **无专用开关**（下限即 `/std:c++14`） |
| C++14 | `-std=c++14` | `-std=c++14` | `/std:c++14`（默认） |
| C++17 | `-std=c++17` | `-std=c++17` | `/std:c++17` |
| C++20 | `-std=c++20` | `-std=c++20` | `/std:c++20` |
| C++23 | `-std=c++23`（旧名 `c++2b`） | `-std=c++23` / `c++2b` | `/std:c++latest` |
| C++26（实验） | `-std=c++2c` | `-std=c++2c` | `/std:c++latest` |

### 6. C 语言标准

| 标准 | GCC | Clang | MSVC |
|------|-----|-------|------|
| C90 | `-std=c90`（或 `-ansi`） | `-std=c90` | 默认支持 |
| C99 | `-std=c99` / `gnu99` | `-std=c99` / `gnu99` | 部分支持（长期不完整） |
| C11 | `-std=c11` | `-std=c11` | `/std:c11`（VS2019 16.8+） |
| C17/C18 | `-std=c17` | `-std=c17` | `/std:c17`（VS2019 16.8+） |
| C23 | `-std=c23`（旧名 `c2x`） | `-std=c23` / `c2x` | 有限支持 |

> 注：MSVC 默认的 C++ 标准为 `/std:c++14`，且对 C 标准（尤其 C99）的完整支持长期滞后于 GCC/Clang，直到较新版本才补齐。

### 7. Sanitizer（运行期缺陷检测）

| Sanitizer | GCC | Clang | MSVC |
|-----------|-----|-------|------|
| AddressSanitizer（内存错误） | `-fsanitize=address` | `-fsanitize=address` | `/fsanitize=address`（VS2019 16.9+） |
| UndefinedBehaviorSanitizer | `-fsanitize=undefined` | `-fsanitize=undefined` | — |
| ThreadSanitizer（数据竞争） | `-fsanitize=thread` | `-fsanitize=thread` | — |
| MemorySanitizer（未初始化读） | — | `-fsanitize=memory` | — |
| LeakSanitizer（内存泄漏） | `-fsanitize=leak` | `-fsanitize=leak` | — |

> Sanitizer 系列源自 Clang/LLVM，GCC 4.8+ 跟进；MSVC 目前主要支持 ASan。三者的 ASan 在 Windows 上还能互相协作调试。

## 特色功能对比

### [[03.GCC_G++_Complete_Reference|GCC]] 特色
- **标准支持全面**：C90→C23、C++98→C++23/26 持续跟进
- **丰富的 GNU 扩展**与海量内置函数
- **多语言**：除 C/C++ 外还支持 Fortran、Go、Ada、D 等前端
- **最广的目标架构覆盖**，是 Linux 发行版与众多嵌入式平台的事实标准编译器
- 与 **GDB** 深度配合

### [[01.Clang_Clang++_Complete_Reference|Clang]] 特色
- **诊断信息最友好**：带源码片段、`^~~~` 区间标注与 fix-it 修复建议
- **编译速度快**、内存占用适中
- **模块化（基于 LLVM）**：易作为库嵌入 IDE、静态分析、代码补全工具
- **ThinLTO**、丰富的 **Sanitizer**、原生**交叉编译**（`-target`）
- 是 **macOS/iOS 的官方编译器**、**Android NDK 推荐编译器**

### [[04.MSVC_Complete_Reference|MSVC]] 特色
- 与 **Visual Studio / Windows SDK / Win32 / COM / .NET** 深度集成
- 一流的 **Windows 调试体验**与"编辑并继续"
- 近年标准一致性大幅改善（`/permissive-`、`/std:c++20`），但 C 标准支持仍偏滞后
- Windows 桌面/服务器开发的默认选择

## 性能对比（经验性，依工程而异）

| 方面 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 编译速度 | 中等 | 较快 | 较快 |
| 生成代码性能 | 优秀 | 优秀 | 优秀（Windows 上常最优） |
| 内存占用 | 较高 | 中等 | 中等 |
| 诊断信息质量 | 良好（近年大幅改善） | 优秀 | 良好 |

> ⚠️ 三者生成代码的性能在不同基准上各有胜负，**不存在普遍意义上的"最快编译器"**，应针对自己的工作负载实测。

## 生态系统

- **GCC**：Linux 发行版与嵌入式领域的标准；与 GDB、Autotools/CMake 等深度协作。
- **Clang**：苹果生态官方工具链；与 LLVM 全家桶（lld、lldb、clang-tidy、clang-format）紧密结合；现代 C++ 工具的首选底座。
- **MSVC**：Windows 原生开发标准；与 MSBuild、Visual Studio、Windows SDK、DirectX 一体化。

## PGO 三家工作流对比

PGO（Profile-Guided Optimization）是编译器利用运行时热点数据重编译、提升生成代码质量的两阶段优化技术。三家编译器均提供 PGO 支持，但插桩方式、工具链与 profile 格式互不通用。

### 工作流对比表

| 阶段 | GCC | Clang（IR-PGO） | MSVC |
|------|-----|----------------|------|
| 插桩编译 | `-fprofile-generate` | `-fprofile-instr-generate` | `/GL`（全程序优化，LTCG 模式） |
| 运行采集 | 直接运行，生成 `.gcda` | 直接运行，生成 `.profraw` | 使用 `pgosweep.exe` 或 `.pgc` |
| 合并 profile | `gcov-tool merge` 或无需显式合并 | `llvm-profdata merge -sparse *.profraw -o out.profdata` | `pgomgr /merge *.pgc app.pgd` |
| 重编译 | `-fprofile-use=<dir>` | `-fprofile-instr-use=<file>` | `/LTCG:PGO`（链接器选项） |
| profile 格式 | `.gcda` / `.gcno`（GCov 格式） | `.profdata`（LLVM 私有格式） | `.pgd` / `.pgc`（MSVC 私有格式） |
| 采样 PGO | `-fauto-profile=<file>`（AutoFDO） | `-fprofile-sample-use=<file>` | — |
| 增量兼容性 | profile 哈希校验，不匹配则警告并降级 | 同左；`-Wprofile-instr-out-of-date` | profile 与 IL 强绑定，版本不符报错 |

### 关键差异

- **GCC** 的 profile 以**源文件路径**为键，多目录构建时需注意路径一致性（`-fprofile-prefix-path` 可重映射）。
- **Clang** 使用内部函数哈希，只要函数体不变则哈希稳定，不受文件重命名影响；`-sparse` 选项大幅减小 profdata 体积。
- **MSVC** 的 PGO 与 `/LTCG` 紧密耦合，不能单独使用；profile 文件（`.pgd`）与 IL（中间语言）同版本强绑定，升级编译器后必须重新收集。

> 详细的三平台 PGO 实战配置、CS-PGO 和 AutoFDO 进阶用法见 [[05.PGO_Profile_Guided_Optimization]]。

## LTO / LTCG 深度对比

链接时优化（LTO）允许编译器跨翻译单元做全局分析与优化，是解决模块边界内联不足、死代码残留等问题的关键手段。

### 三家实现对比

| 维度 | GCC Full LTO | Clang ThinLTO | MSVC `/LTCG` |
|------|-------------|---------------|--------------|
| 启用方式 | `-flto`（编译+链接均需） | `-flto=thin`（同） | 编译 `/GL`，链接 `/LTCG` |
| 中间表示 | GIMPLE（序列化到 `.o` 节） | LLVM Bitcode（精简摘要 + 懒加载模块） | MSVC IL（`.obj` 内嵌） |
| 并行性 | 链接时单进程分析（`-flto=jobserver` 可部分并行） | **原生并行**，每模块独立优化，只共享摘要 | 链接器控制，部分并行 |
| 增量构建 | **差**：任意 `.o` 变化可能触发全量重链 | **好**：未变化模块复用缓存（`.thinlto_cache/`） | 中等：PDB 信息可增量，IL 变化仍需重分析 |
| 内存峰值 | 高（全部 IR 同时载入内存） | 低（摘要索引 + 按需加载） | 中等 |
| ABI 兼容性 | 仅限 GCC 编译的 `.o`；不同 GCC 版本间 GIMPLE 不互通 | 仅限 Clang/LLVM；但可与非 LTO `.o` 混链 | 仅限 MSVC；不能与 GCC/Clang `.obj` 混 LTO |
| 调试信息 | LTO 下 DWARF 生成有限制 | LTO 下支持完整 DWARF，`-g` 可正常工作 | PDB 可正常生成，调试体验完整 |
| 推荐场景 | 不特别强调增量的 release 构建 | **大型项目首选**（增量快、内存省） | Windows 原生项目 release 构建 |

### ThinLTO 缓存

Clang ThinLTO 提供持久化模块缓存，显著加速二次全量构建：

```bash
clang++ -O2 -flto=thin \
  -Wl,--thinlto-cache-dir=/tmp/thinlto_cache \
  -Wl,--thinlto-cache-policy=cache_size_bytes=500m \
  -o app *.cpp
```

### 与 PGO 叠加

三家均支持 LTO + PGO 叠加，叠加效果通常优于单独使用。典型顺序：收集 profile（插桩或采样）→ 开启 LTO 的 PGO 重编译。MSVC 的叠加方式是 `/GL /LTCG:PGO`，Clang 是 `-flto=thin -fprofile-instr-use=app.profdata`。

## 中间表示可观测性对比

编译器中间表示（IR）是理解优化行为、调试代码生成问题的核心工具。三家编译器在 IR 的可观测性上差异显著。

| 维度 | GCC（GIMPLE/RTL） | Clang（LLVM IR） | MSVC（IL） |
|------|-----------------|-----------------|-----------|
| IR 类型 | GIMPLE（高层）→ RTL（低层）两层 | LLVM IR（SSA 形式，单层） | MSVC IL（私有，无文档） |
| 导出命令 | `-fdump-tree-all`（GIMPLE）`-fdump-rtl-all`（RTL） | `-emit-llvm -S -o out.ll`（文本 IR）`-emit-llvm -c -o out.bc`（字节码） | **无标准导出方式** |
| 可读性 | GIMPLE 文本可读；RTL 需熟悉 GCC 内部 | **LLVM IR 设计即面向可读性**，类型完整、注释友好 | 不可导出，闭源 |
| Pass 查看 | `-fdump-tree-<passname>`（如 `-fdump-tree-optimized`） | `opt -print-after-all`、`-Xclang -print-stats` | — |
| 可操作性 | `gccplugin` API 可插入自定义 Pass | `opt`、`llvm-pass-manager` 标准接口，生态丰富 | 无 |
| 反汇编 | `objdump -d` 看最终机器码 | `llvm-objdump -d`（支持 LLVM 反汇编格式） | `dumpbin /DISASM` |

### GIMPLE 观察示例

```bash
# 输出所有 GIMPLE tree dump（每个 pass 一个文件，如 foo.cpp.003t.original）
g++ -O2 -fdump-tree-all foo.cpp

# 仅看最终优化后的 GIMPLE
g++ -O2 -fdump-tree-optimized foo.cpp

# 查看 RTL（汇编选择前的低层 IR）
g++ -O2 -fdump-rtl-expand foo.cpp
```

### LLVM IR 观察示例

```bash
# 优化前 IR
clang++ -O0 -emit-llvm -S -o before.ll foo.cpp

# 优化后 IR
clang++ -O2 -emit-llvm -S -o after.ll foo.cpp

# 用 opt 对 IR 应用指定 pass 并观察变化
opt -O2 --print-after-all before.ll -o /dev/null 2>&1 | less
```

> GIMPLE/RTL 与 LLVM IR 的结构原理、SSA 形式与 Pass 体系的深度解析见 [[07.Compiler_IR_GIMPLE_RTL_LLVM]]。

## 诊断精度对比

诊断质量直接影响开发效率，尤其在大型代码库与严格 C++ 场景下差异明显。

### 综合对比

| 维度 | GCC | Clang | MSVC |
|------|-----|-------|------|
| 错误定位精度 | 良好（近年大幅改善，列号精确） | **优秀**（区间标注 `^~~~`，精确到 token） | 良好（行号准确，列号部分场景不精确） |
| Fix-it 修复建议 | 部分警告带修复建议 | **广泛支持 fix-it**，clang-tidy 可自动应用 | 部分错误带"智能感知"修复（IDE 内） |
| 模板错误可读性 | 历史上较差，GCC 12+ 有专项改善 | **优秀**（concept 约束错误尤为清晰） | 中等，VS IDE 有折叠功能辅助 |
| 彩色输出 | `-fdiagnostics-color=always` | `-fcolor-diagnostics`（终端默认开） | VS 控制台彩色（IDE 内原生彩色） |
| 诊断列宽控制 | `-fmessage-length=n` | `-fmessage-length=n` | — |
| `-Wsuggest-override` | 有（检测未加 `override` 的虚函数覆盖） | `-Wsuggest-override`（同） | 无对应选项（IDE 有代码建议） |
| 未使用变量/参数 | `-Wunused`、`-Wunused-parameter` | 同 GCC；`-Wunused-but-set-variable` 等细粒度更多 | `/W4` 覆盖部分，无等价 `-Wunused-*` 体系 |
| 诊断抑制粒度 | `#pragma GCC diagnostic push/pop` | `#pragma clang diagnostic push/pop`（不互通） | `#pragma warning(push/pop)` |

### `-fdiagnostics-*` 系列（GCC/Clang 共有）

| 选项 | 效果 |
|------|------|
| `-fdiagnostics-show-option` | 诊断后附上触发它的 `-W` 选项名（便于精准 `-Wno-xxx`） |
| `-fdiagnostics-show-caret` | 用 `^` 标注出错位置（Clang 默认开，GCC 同） |
| `-fdiagnostics-column-unit=byte` | 列号以字节计（而非字符，影响含多字节 UTF-8 的中文源码） |
| `-fdiagnostics-format=json` | 以 JSON 输出诊断（IDE 集成用） |

### 边界陷阱

- **`#pragma` 抑制不互通**：GCC 的 `#pragma GCC diagnostic` 在 Clang 下无效（反之亦然），跨平台项目需分别用 `__GNUC__` / `__clang__` 宏判断。
- **MSVC `/Wall` 与 GCC/Clang `-Wall` 含义不同**：MSVC `/Wall` 相当于开启几乎所有警告（包含大量"informational"级别），实际项目常用 `/W3` 或 `/W4`；而 GCC/Clang `-Wall` 只是"常用警告子集"。

## 内联汇编差异

C/C++ 内联汇编在三家编译器间差异显著，是平台移植的主要障碍之一。

### 语法风格对比

| 维度 | GCC / Clang（GNU 风格） | MSVC（Intel 风格） |
|------|------------------------|-------------------|
| 汇编语法 | **AT&T**（默认）：`op src, dst`，寄存器前缀 `%` | **Intel**：`op dst, src`，无前缀 |
| 关键字 | `asm` / `__asm__` | `__asm` / `__asm__` |
| 操作数绑定 | **约束字符串**（`"r"`、`"m"`、`"=r"` 等）+ 占位符（`%0`、`%1`） | 直接使用 C 变量名（MSVC 自动分配寄存器） |
| 输入/输出声明 | 显式分 `:`（输出）、`:`（输入）、`:`（破坏） | 隐式（编译器分析） |
| 可移植性 | 跨平台（GCC/Clang 共用同一语法） | 仅 MSVC；x64 下 MSVC **不支持内联汇编**（需外部 `.asm`） |
| Intel 语法切换 | `-masm=intel` 或 `__asm__(".intel_syntax noprefix\n")` | 默认即 Intel 语法 |

### GCC/Clang 内联汇编示例

```c
// AT&T 语法（默认）：64 位加法，输出约束 "=r"，输入约束 "r"
uint64_t add(uint64_t a, uint64_t b) {
    uint64_t result;
    __asm__ volatile (
        "addq %2, %1\n\t"
        "movq %1, %0"
        : "=r"(result)       // 输出
        : "r"(a), "r"(b)     // 输入
        : "cc"               // 破坏：条件码寄存器
    );
    return result;
}
```

### `asm goto`（GCC/Clang 特有）

`asm goto` 允许内联汇编直接跳转到 C 标签，是 Linux 内核`unlikely`/`likely` 分支与静态跳转表的核心机制：

```c
// asm goto 示例（Linux 内核风格）
int check(int x) {
    asm goto (
        "testl %0, %0\n\t"
        "jz %l[zero]"       // 条件跳转到 C 标签 "zero"
        :
        : "r"(x)
        :
        : zero              // 标签列表
    );
    return 1;
zero:
    return 0;
}
```

> **MSVC 无等价的 `asm goto`**；x64 MSVC 完全不支持内联汇编，需改用 intrinsics 或独立 `.asm` 文件（MASM）。

### MSVC 内联汇编（仅 x86 32 位）

```c
// MSVC __asm：仅在 /arch:IA32（x86-32）下支持
int add(int a, int b) {
    __asm {
        mov eax, a
        add eax, b
        // 返回值在 eax，MSVC 约定
    }
}
```

### 边界陷阱

- **x64 MSVC 无内联汇编**：64 位 Windows 项目需改用 `<intrin.h>` 中的 intrinsics（如 `_mm_*`、`__rdtsc`）或独立汇编文件配合 MASM（`ml64.exe`）。
- **GCC/Clang 约束字符串错误**是最常见的内联汇编 bug：输出约束忘写 `=` 导致编译器不写回，或忘记声明破坏寄存器导致优化器错误复用。
- **`volatile` 关键字**：内联汇编若有副作用（I/O 端口、内存屏障），必须加 `volatile` 防止编译器删除或重排。

> 内联汇编约束语法完整参考、SIMD intrinsics 与平台抽象方案见 [[08.Inline_Asm_and_Intrinsics]]。

## clang-cl 的特殊地位

`clang-cl` 是 Clang 的**MSVC 兼容命令行驱动**，使 Clang 能作为 MSVC 的直接替代品，接受 `/` 风格的 MSVC 选项并生成与 MSVC ABI 兼容的目标文件。

### 定位与核心价值

```
源码 → clang-cl（MSVC 兼容前端） → LLVM 优化器 → MSVC ABI 目标文件
```

- **前端**：理解 MSVC 选项（`/O2`、`/W4`、`/EHsc`、`/std:c++20` 等），解析 MSVC 扩展语法（`__declspec`、`__forceinline`、SAL 注解）。
- **后端**：LLVM 优化管线（享受 ThinLTO、Sanitizer、更好的诊断）。
- **输出**：与 MSVC 完全兼容的 `.obj`，可与 `link.exe` / `lld-link` 混合链接，无需修改 `.def` 文件或导出符号策略。

### 典型用途

| 场景 | 说明 |
|------|------|
| 在 Windows 上享受 Clang 的诊断与 Sanitizer | 用 clang-cl 替代 `cl.exe`，ASan/UBSan 可在 Windows 上运行 |
| CMake + Ninja + clang-cl | `cmake -T ClangCL` 或 `cmake -DCMAKE_C_COMPILER=clang-cl` |
| 渐进式迁移 | 同一 Visual Studio 解决方案中，部分项目用 clang-cl、部分用 MSVC |
| 跨平台代码验证 | 在 Windows 构建环境下用 Clang 前端检查跨平台兼容性 |

### 与 MSVC 的主要差异（已知不兼容点）

| 方面 | clang-cl 状态 |
|------|--------------|
| `__declspec(uuid(...))` / COM 支持 | 支持，但部分 ATL/WTL 模板可能有兼容问题 |
| `/MP`（多进程编译） | clang-cl 自身已多线程，无需 `/MP` |
| MSVC 特定 STL 内部实现细节 | 使用 MSVC STL（不替换），兼容性良好 |
| 编译速度 | 与 MSVC 相当，部分场景更快 |
| `__assume` / SAL | 部分支持（`__assume` 映射为 `__builtin_assume`） |

### 启用方式

```bash
# CMake 指定 clang-cl（Visual Studio 生成器）
cmake -G "Visual Studio 17 2022" -T ClangCL ..

# CMake 指定 clang-cl（Ninja 生成器，需 MSVC 环境变量）
cmake -G Ninja -DCMAKE_C_COMPILER=clang-cl -DCMAKE_CXX_COMPILER=clang-cl ..

# 直接调用（需在 Developer Command Prompt 中，以便 include/lib 路径正确）
clang-cl /O2 /std:c++20 /EHsc foo.cpp /link /OUT:foo.exe
```

### 边界陷阱

- **必须在 MSVC 开发者提示符（Developer Command Prompt）中运行**，或手动设置 `INCLUDE`、`LIB`、`PATH` 等 MSVC 环境变量，否则找不到 Windows SDK 和 MSVC CRT 头文件。
- **clang-cl 默认目标是宿主机架构**（通常 x64），交叉编译到 ARM64 需显式 `--target=arm64-pc-windows-msvc`。
- **`/clang:<arg>`**：clang-cl 提供 `/clang:` 前缀透传 Clang 原生选项（如 `/clang:-fsanitize=address`），这是在 MSVC 模式下访问 Clang 特有功能的标准方式。

## 总结与选型建议

- **[[03.GCC_G++_Complete_Reference|GCC]]**：历史悠久、平台与语言覆盖最广，开源世界的基石 —— Linux/嵌入式首选。
- **[[01.Clang_Clang++_Complete_Reference|Clang]]**：现代化设计、体验友好、工具链强大 —— 跨平台、苹果生态、需要静态分析/Sanitizer 的项目首选。
- **[[04.MSVC_Complete_Reference|MSVC]]**：与微软生态深度整合 —— Windows 平台开发的最佳选择。

> 实务中，跨平台项目常**同时用三者做 CI**：让不同编译器的诊断互相补盲、暴露不可移植写法，是提升代码质量的高性价比手段。
