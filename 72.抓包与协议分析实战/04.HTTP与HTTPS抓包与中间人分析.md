# HTTP 与 HTTPS 抓包与中间人分析

> [!abstract] TL;DR
> HTTP 明文流量用 tcpdump/Wireshark 直接抓即可；HTTPS 需要在 TLS 终止处介入。三条路径：①MITM 代理（mitmproxy/Burp/Charles）颁发伪造证书并将其加入系统信任；②通过 SSLKEYLOGFILE 导出会话密钥后解密；③在受控设备上安装 CA 证书（Android/iOS 测试）。代理方式最直观，但 Android 7+ 应用不再信任用户 CA，需借助 `network_security_config.xml` 或 root 绕过。

## 概述与定位

HTTP/1.1、HTTP/2、HTTP/3 的抓包挑战各有不同：

| 协议版本 | 传输层 | 抓包难点 |
|----------|--------|----------|
| HTTP/1.1 | TCP（明文） | 无，直接 Wireshark |
| HTTP/1.1 over TLS | TCP+TLS | 需解密 |
| HTTP/2 (h2) | TCP+TLS | 需解密+HPACK头部解压 |
| HTTP/2 (h2c) | TCP（明文） | 无 TLS，Wireshark 可解 |
| HTTP/3 (QUIC) | UDP+TLS 1.3 | QUIC 加密，需 SSLKEYLOGFILE |

**HTTPS 抓包的三种方式：**
1. **MITM 代理**（最常用）：在客户端和服务器之间插入代理，各自建立独立 TLS 连接
2. **SSLKEYLOGFILE 密钥导出**：从客户端导出会话密钥，Wireshark 离线解密（需控制客户端）
3. **CA 证书安装**：在受控设备上安装自签 CA，配合透明代理（适合移动端测试）

## 原理与机制

### CONNECT 隧道建立过程

在 HTTP/HTTPS 流量中，代理（无论是显式代理还是 MITM 代理）与客户端之间的通信始于一个 `CONNECT` 方法请求。这个机制是 HTTP/1.1 规范（RFC 7231）的一部分，最初用于在代理上建立到目标服务器的 TCP 隧道。

当浏览器要访问 `https://example.com/` 时（假设已配置代理 `127.0.0.1:8080`），实际发生的步骤：

```
步骤 1：建立到代理的 TCP 连接（3次握手）
步骤 2：客户端发送 CONNECT 请求：
  CONNECT example.com:443 HTTP/1.1
  Host: example.com:443
  Proxy-Authorization: Basic ...（若代理要认证）
  
步骤 3：代理建立到 example.com:443 的 TCP 连接
步骤 4：代理回应 200：
  HTTP/1.1 200 Connection Established
  
步骤 5：客户端在已建立的隧道上发起 TLS 握手
  [TLS ClientHello]  → 对于 MITM 代理，此时代理"冒充"服务器
```

代理如何区分明文 HTTP 与 HTTPS（TLS）：对于显式代理，这很直接——HTTP 请求直接发到代理（`GET http://example.com/ HTTP/1.1`），HTTPS 通过 CONNECT 方法建立隧道再在隧道上做 TLS。对于**透明代理**（客户端不知道代理存在），代理在 CONNECT 阶段无法利用上层协议，必须依赖其他手段区分，最常用的是**SNI（Server Name Indication）**——TLS ClientHello 中包含的服务器名称是明文的，透明代理可以读取 SNI 决定如何路由。

### TLS 拦截的证书链重建原理

MITM 代理拦截 TLS 的关键技术是**动态证书颁发（Dynamic Certificate Generation）**。代理持有一个自签的 CA 证书和对应私钥，当客户端发起 TLS 握手时，代理会：

1. 读取 ClientHello 中的 SNI（或等待 CONNECT 请求中的目标域名）
2. 实时生成一张叶证书（leaf certificate），其 CN（Common Name）和 SAN（Subject Alternative Name）设为目标域名（如 `example.com`）
3. 用自签 CA 的私钥对叶证书签名，使叶证书的 issuer 指向自签 CA
4. 把这张动态生成的叶证书呈现给客户端

客户端验证证书时，沿信任链向上追溯：叶证书 → 自签 CA。只要客户端已把自签 CA 加入信任存储（操作系统证书库或浏览器证书库），验证就通过，不会出现证书警告。同时，代理与真实服务器之间建立第二段 TLS 连接，代理以普通客户端身份与真实服务器握手，验证服务器的真实证书。

代理内部维护一个证书缓存，第一次遇到某域名时生成并缓存该域名的叶证书，后续请求复用，避免重复签名开销。

### 透明代理：iptables REDIRECT + SO_ORIGINAL_DST

透明代理的核心问题是：客户端把数据包发往真实服务器（如 `93.184.216.34:443`），而不是代理。要在网关/路由器上拦截，需要借助 Linux netfilter 的 NAT 机制：

```bash
# 将目标 80/443 端口的流量重定向到 mitmproxy 的 8080 端口
iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 80 \
  -j REDIRECT --to-port 8080
iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 443 \
  -j REDIRECT --to-port 8080

# 启动 mitmproxy 透明模式
mitmproxy --mode transparent --listen-port 8080
```

`REDIRECT` 目标把数据包的目的 IP 改写为 127.0.0.1，目的端口改为 8080，数据包被投递给本机的 mitmproxy 进程。但 mitmproxy 收到连接后，如何知道客户端原本想连接的是哪个 IP 和端口？这就是 **`SO_ORIGINAL_DST` socket 选项**的作用：`getsockopt(fd, SOL_IP, SO_ORIGINAL_DST, &orig_addr)` 让进程查询内核 conntrack 表，取回 NAT 重写前的原始目标地址（`93.184.216.34:443`）。mitmproxy 用这个原始地址与真实服务器建立出站连接，完成 MITM 拦截。

对于 HTTPS 流量，mitmproxy 还需要从 TLS ClientHello 的 SNI 扩展中读取目标域名，才能动态生成对应的叶证书。若客户端不发送 SNI（旧应用或某些特殊场景），透明代理只能看到目的 IP，无法获取域名，动态证书生成会使用 IP 地址作为 CN，这在现代浏览器中可能触发证书警告。

### HSTS 与证书固定为何阻碍拦截

两个机制可以使 MITM 拦截失效，即使客户端已安装自定义 CA：

**HSTS（HTTP Strict Transport Security）** 通过响应头 `Strict-Transport-Security: max-age=31536000; includeSubDomains` 告知浏览器：该域名未来一年内必须用 HTTPS，且不接受 HTTPS 降级。浏览器会把这条记录存入 HSTS 缓存，后续如果遇到证书错误（即使是用户手动确认），直接拒绝连接，不给用户绕过的机会。更强的形式是 **HSTS Preloading**——域名被预先嵌入浏览器二进制文件，不需要用户先访问过该域名就生效，Chromium 的 preload list 有数万条记录。MITM 工具遇到 preload 域名时，无法通过替换 CA 的方式绕过。

**证书固定（Certificate Pinning）** 则更激进：应用硬编码了服务器证书的公钥哈希（或证书指纹），即使系统信任了 MITM 的 CA，应用自己做哈希对比后发现公钥不匹配，会主动拒绝连接。绕过证书固定通常需要：在运行时 hook TLS 库的验证函数（如用 Frida 注入），或反编译应用修改固定逻辑后重新打包。

**合规边界**：HSTS/证书固定是防御机制，绕过它们分析第三方应用时，必须确保在 Bug Bounty 或授权渗透测试范围内，且不得将分析结果用于恶意目的。

### HTTP/1.1 keep-alive/pipelining 对抓包的影响

HTTP/1.1 默认启用 keep-alive（持久连接），同一 TCP 连接上会发送多个 HTTP 请求/响应，请求按顺序进行（非并行）。这对抓包有两方面影响：

- **Wireshark 的 HTTP 重组**：Wireshark 能识别 keep-alive 连接，把同一 TCP stream 上的多个 HTTP 事务分别解析展示。但如果 snaplen 截断了 Content-Length 指定的响应体，Wireshark 可能无法确定下一个请求的起始位置，导致后续 HTTP 消息解析失败。
- **pipelining**：HTTP/1.1 pipelining 允许客户端不等上一个响应就发送下一个请求，但响应必须按请求顺序返回。这在实践中很少使用（浏览器几乎都禁用），但在 Wireshark 中会看到多个请求"叠放"在同一 TCP 帧里，显示过滤器 `http.request` 会把它们都匹配出来。HTTP/2 的多路复用（stream）从根本上取代了 pipelining，允许响应乱序返回。

### 显式代理 vs 透明代理

| 类型 | 客户端感知 | 配置方式 | 适用场景 |
|------|-----------|----------|----------|
| 显式代理（Explicit） | 需手动配置代理 IP:Port | 浏览器/系统代理设置 | 桌面浏览器测试 |
| 透明代理（Transparent）| 无感知，流量被重定向 | iptables/路由重定向 | 移动设备/IoT 测试 |

### mitmproxy 完整示例

**安装与基本启动：**

```bash
pip install mitmproxy

# 交互式 TUI（最常用）
mitmproxy --listen-port 8080

# 命令行无交互（mitmdump，类似 tcpdump）
mitmdump --listen-port 8080 -w /tmp/capture.mitm

# Web UI（需浏览器）
mitmweb --listen-port 8080
```

**mitmproxy Addon（内联脚本）示例：**

```python
# addon_example.py
from mitmproxy import http
import json
import logging

class RequestLogger:
    """记录所有 HTTP 请求，修改特定响应"""

    def request(self, flow: http.HTTPFlow) -> None:
        """每个请求到达时调用"""
        logging.info(f"[REQ] {flow.request.method} {flow.request.pretty_url}")
        
        # 修改请求头（注入自定义头）
        flow.request.headers["X-Debug-Proxy"] = "mitmproxy"
        
        # 拦截并直接返回响应（不转发给服务器）
        if flow.request.pretty_url == "https://example.com/flag":
            flow.response = http.Response.make(
                200,
                b'{"flag": "intercepted"}',
                {"Content-Type": "application/json"}
            )

    def response(self, flow: http.HTTPFlow) -> None:
        """每个响应返回时调用"""
        logging.info(
            f"[RSP] {flow.response.status_code} "
            f"{flow.request.pretty_url} "
            f"({len(flow.response.content)} bytes)"
        )
        
        # 修改 JSON 响应内容
        if "application/json" in flow.response.headers.get("content-type", ""):
            try:
                data = json.loads(flow.response.content)
                data["_injected"] = True
                flow.response.content = json.dumps(data).encode()
            except json.JSONDecodeError:
                pass

addons = [RequestLogger()]
```

```bash
# 加载 addon 运行
mitmdump -s addon_example.py --listen-port 8080

# 过滤特定域名
mitmdump --listen-port 8080 -f '~d example.com'
```

**mitmproxy 过滤语法速查：**

```
~d example.com          # 按域名过滤
~m GET                  # 按 HTTP 方法

```

### Burp Suite 配置

**CA 证书导入（浏览器/设备）：**

```
1. 启动 Burp Suite，默认监听 127.0.0.1:8080
2. 浏览器访问 http://burp（或 http://127.0.0.1:8080）
3. 下载 "CA Certificate"（DER 格式）
4. 浏览器/操作系统 → 证书管理 → 导入为受信任根 CA
5. 设置系统代理：127.0.0.1:8080
```

**上游代理配置（Burp → 企业代理）：**

```
Project options → Connections → Upstream Proxy Servers
→ Add: Destination host: *, Proxy host: corp-proxy.internal, Port: 3128
```

**Intruder Sniper 模式：**

```
1. 在 Proxy → HTTP history 中找到目标请求
2. 右键 → Send to Intruder
3. Positions → Attack type: Sniper
4. 在请求体中用 § 标记注入点：
   username=admin&password=§test123§
5. Payloads → 从字典文件加载密码列表
6. Start attack → 按状态码/响应长度排序异常项
```

### Charles Map Remote 规则

Charles 常用于移动端 API 调试，`Map Remote` 可将请求重定向到测试服务器：

```
Tools → Map Remote → Add

  Protocol: https

  Protocol: https

```

### mitmproxy Addon 进阶：修改响应

```python
# patch_response.py：将生产 API 响应中的特定字段替换
from mitmproxy import http
import json, re

class ResponsePatcher:
    def response(self, flow: http.HTTPFlow) -> None:
        # 只处理特定 API 端点
        if not re.search(r'/api/user/\d+', flow.request.path):
            return
        
        ct = flow.response.headers.get("content-type", "")
        if "application/json" not in ct:
            return
        
        try:
            body = json.loads(flow.response.text)
            # 将 isPremium 强制为 true（绕过付费墙测试）
            if "isPremium" in body:
                body["isPremium"] = True
            flow.response.text = json.dumps(body)
        except Exception as e:
            pass

addons = [ResponsePatcher()]
```

## 安全性与正确使用

### Android 7+ 证书信任链

Android 7.0（API 24）之后，应用默认**不再信任用户安装的 CA**（只信任系统 CA），导致安装 mitmproxy/Burp CA 到用户证书存储后，大多数应用仍然拒绝连接。

**解决方案一：`network_security_config.xml`（需重打包或控制应用）**

```xml
<!-- res/xml/network_security_config.xml -->
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <!-- 允许明文 HTTP（仅调试） -->
    <base-config cleartextTrafficPermitted="true">
        <trust-anchors>
            <!-- 信任系统 CA -->
            <certificates src="system" />
            <!-- 信任用户安装的 CA（关键！） -->
            <certificates src="user" />
        </trust-anchors>
    </base-config>
    
    <!-- 针对特定域名的精细配置 -->
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <trust-anchors>
            <!-- 仅信任内嵌的特定证书（证书固定）-->
            <certificates src="@raw/my_ca_cert" />
        </trust-anchors>
    </domain-config>
</network-security-config>
```

在 `AndroidManifest.xml` 的 `<application>` 标签中引用：

```xml
<application
    android:networkSecurityConfig="@xml/network_security_config"
    ...>
```

**解决方案二：将 mitmproxy CA 推入系统证书存储（需 root）**

```bash
# 转换 mitmproxy CA 为系统信任格式
openssl x509 -inform PEM -subject_hash_old \
  -in ~/.mitmproxy/mitmproxy-ca-cert.pem | head -1
# 输出: e5c3944b（哈希值）

# 重命名并推入系统目录
cp ~/.mitmproxy/mitmproxy-ca-cert.pem e5c3944b.0
adb root
adb remount
adb push e5c3944b.0 /system/etc/security/cacerts/
adb shell chmod 644 /system/etc/security/cacerts/e5c3944b.0
adb reboot
```

### HTTPS 抓包的合规边界

本章描述的所有技术——MITM 代理、证书替换、透明代理、证书固定绕过——必须严格限定在**自有或明确书面授权**的应用和网络范围内使用。具体要求：

- 仅对**自己拥有**或**有书面授权**的应用进行安全测试
- 在企业 Bug Bounty 范围内操作，遵守各计划的条款
- 不得对第三方服务（银行 App、支付应用等）进行未授权的 MITM 测试
- 企业网络中对员工 HTTPS 流量进行监控，必须有明确法律授权和员工知情同意
- 捕获到的包含认证凭据、个人信息的流量数据，须在分析完成后立即销毁，不得留存或泄露

## 小结

- HTTP 明文抓包无需特殊处理，HTTPS 需要 MITM 代理或密钥导出
- CONNECT 隧道是 HTTP 代理拦截 HTTPS 的基础协议；透明代理通过 iptables REDIRECT + SO_ORIGINAL_DST 实现无感知拦截，SNI 是透明场景下识别目标域名的关键
- MITM 代理通过动态签发叶证书实现 TLS 拦截，前提是客户端信任代理的 CA
- HSTS Preloading 和证书固定是对抗 MITM 的强力防御机制，绕过需要运行时 hook 或重打包
- mitmproxy 的 Addon 机制提供了强大的 Python 脚本化能力，可实现请求修改、响应注入、自动化测试
- Burp Suite 是 Web 安全测试的行业标准工具，Intruder 和 Repeater 是最高频的两个模块
- Android 7+ 应用不信任用户 CA，需通过 `network_security_config.xml` 或 root 安装系统 CA 解决
- 所有 MITM 操作必须在授权范围内，对自有/授权流量才能抓包，生产用户的 HTTPS 流量严禁拦截
