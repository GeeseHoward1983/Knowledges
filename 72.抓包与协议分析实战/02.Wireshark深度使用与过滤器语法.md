# Wireshark 深度使用与过滤器语法

> [!abstract] TL;DR
> Wireshark 的核心是两套独立过滤系统：BPF **捕获过滤器**（决定什么帧进文件）和 **显示过滤器**（决定已捕获的帧中显示哪些）。两者语法完全不同，混淆是新手最常见的错误。tshark 将 Wireshark 的解析能力带到命令行，可输出任意协议字段的结构化数据。

## 概述与定位

Wireshark 是目前最主流的图形化协议分析工具，底层依赖 libpcap/Npcap 捕获，通过数百个内置 **dissector** 解析协议层，最终以树状结构展示每个字段的含义。

**架构层次：**

```
┌──────────────────────────────┐
│     Qt GUI / GTK GUI         │  ← 用户交互层
├──────────────────────────────┤
│   Display Filter Engine      │  ← 显示过滤（用户态）
│   Dissector Layer            │  ← 协议解析（数百个 .so 插件）
│   Frame Reader / Assembler   │  ← TCP 流重组、片段合并
├──────────────────────────────┤
│   libpcap / Npcap            │  ← 捕获抽象层
│   BPF Capture Filter         │  ← 内核级过滤
└──────────────────────────────┘
```

tshark 是 Wireshark 的命令行前端，共享同一套 dissector 和过滤引擎，适合批量分析、CI 集成和自动化脚本。

## 原理与机制

### 两种过滤器对比

| 维度 | 捕获过滤器（BPF） | 显示过滤器 |
|------|------|------|
| 作用时机 | 捕获时，内核层 | 已捕获后，用户态 |
| 语法体系 | libpcap/BPF 语法 | Wireshark 专有语法 |
| 性能影响 | 减少写入磁盘的数据量 | 仅影响显示，不改变文件 |
| 精确度 | 只能访问固定偏移字段 | 可访问任意解析后的命名字段 |
| 可修改性 | 修改需重新开始捕获 | 随时修改，即时生效 |
| 示例 | `tcp port 80` | `tcp.port == 80` |
| 出错影响 | 可能丢失需要的包 | 仅改变显示，数据不丢失 |

这两套过滤体系在编译路径上完全不同。捕获过滤器由 `libpcap` 的 `pcap_compile()` 函数编译成 cBPF 字节码，通过 `setsockopt(SO_ATTACH_FILTER)` 注入内核，过滤在**帧进入用户态之前**完成，不匹配的帧根本不进入 pcap 文件，因此能显著降低磁盘 I/O 和文件大小。显示过滤器则由 Wireshark 自己的 **epan（Ethereal Packet ANalyzer）** 引擎编译成一棵求值树（expression tree），在用户态对已解析的协议字段做谓词求值，匹配结果只影响"显示"，所有帧的原始数据始终保留在 pcap 文件中。

这两种时机差异带来一个重要实践原则：**新手应优先用宽泛的捕获过滤器（甚至不过滤）抓取原始数据，再用显示过滤器做精细分析**。错误使用捕获过滤器可能导致关键帧被遗漏（例如只抓了 TCP 数据帧而遗漏了 SYN/ACK，导致无法分析连接建立延迟）。有经验的分析人员只有在流量速率过高、磁盘空间紧张的场景才依赖捕获过滤器做硬过滤。

### Dissector 解析树——逐层解析协议的工作方式

Wireshark 的 dissector 架构是一个**链式调用**体系：每一层 dissector 解析完自己负责的头部后，根据特定字段的值（EtherType、IP proto、TCP/UDP 端口等）调用下一层的 dissector，形成一棵解析树（Packet Details 面板看到的展开树就是这棵树的可视化）。

dissector 注册时会声明自己感兴趣的协议标识符。例如 HTTP dissector 注册到端口 80 和 8080，当 TCP dissector 把 TCP 段的 payload 交出去时，会查询 `tcp.port` 表找到合适的 dissector 处理。整个过程大致如下：

1. Frame dissector 读取原始字节，提取帧元数据（时间戳、接口、帧号）
2. 根据 pcap 文件记录的 DLT（数据链路类型，如 `DLT_EN10MB`=以太网）选择链路层 dissector
3. Ethernet dissector 解析 MAC 头，根据 EtherType（0x0800=IPv4、0x86DD=IPv6、0x0806=ARP）调用下一层
4. IP dissector 解析 IP 头，根据 proto 字段（6=TCP、17=UDP、1=ICMP）调用传输层 dissector
5. TCP dissector 解析 TCP 头，根据 dport/sport 查找应用层 dissector（如 HTTP、TLS、DNS）
6. 应用层 dissector 解析应用协议，字段被标注为命名字段（field ID，如 `http.request.method`）

**启发式 dissector（Heuristic Dissector）** 是 Wireshark 的"猜测"机制：当端口映射找不到已知 dissector 时（如 HTTP 运行在非标准的 9090 端口），启发式 dissector 会尝试分析 payload 的特征模式（HTTP 请求以 `GET/POST/PUT` 等动词开头、TLS 以 `\x16\x03` 开头），如果匹配度足够高则强行用对应 dissector 解析。用户也可以手动覆盖：`Analyze → Decode As`，强制指定某个端口的 dissector。

### TCP 流重组机制——乱序与重传的处理

TCP 是字节流协议，应用层数据可能被分割到多个 TCP 段，还可能因为网络乱序或重传导致到达顺序与发送顺序不同。Wireshark 的 Frame Reader / Assembler 层在 dissector 之前做**流重组**：

- 维护每条 TCP 流（4 元组：src IP、dst IP、src port、dst port）的重组状态
- 按序列号将 TCP 段排序，检测并标注重传（`tcp.analysis.retransmission`）
- 对乱序段（`tcp.analysis.out_of_order`）暂存，等待缺失段到达后一起交给上层 dissector
- 当一个 HTTP 响应体跨越多个 TCP 段时，只有最后一个段到达时 HTTP dissector 才能看到完整的 HTTP 消息

这套机制使 Wireshark 能以"应用视角"展示数据：用 Follow TCP Stream 看到的是按正确顺序排列的完整应用数据，而不是分散的 TCP 段。重传段会被标注但不会被重复送给应用层 dissector。`tcp.analysis.bytes_in_flight` 字段记录了还在传输中（未被 ACK）的字节数，对分析 TCP 性能问题非常有用。

### 专家信息（Expert Info）工作原理

Wireshark 的 Expert Info（`Analyze → Expert Information`）是一套基于规则的自动诊断系统，在 dissector 解析每个帧时同步运行，把观察到的异常加入全局诊断列表。规则来源包括内置规则（如检测 TCP 重传、零窗口、RST 等）和 dissector 自定义规则（如 TLS 警告、DNS 解析失败等）。严重程度分 Chat/Note/Warn/Error 四级。分析人员通常先打开 Expert Info 做一次全局扫描，然后按 Error/Warn 优先级排序，快速定位异常帧。

着色规则（Coloring Rules）和专家信息有所不同：着色规则是基于显示过滤器表达式对帧进行着色，目的是辅助人眼快速区分帧类型；专家信息是 dissector 在解析过程中主动写入的诊断信息，更接近"自动化分析结果"。

## 结构/算法/伪代码详解

### 显示过滤器完整语法

**比较运算符：**

```
==  eq    等于
!=  ne    不等于
>   gt    大于
<   lt    小于
>=  ge    大于等于
<=  le    小于等于
~=  matches  正则匹配（POSIX ERE）
contains  包含子串
```

**逻辑运算符：**

```
&&  and   逻辑与
||  or    逻辑或
!   not   逻辑非
```

**成员运算符与范围：**

```
# 检查字段是否在集合中
tcp.port in {80 443 8080}

# 字节范围切片（偏移:长度）
tcp[0:2]  # TCP 头前两个字节（源端口）

# 字段存在性检查
http.request  # 等价于 http.request exists
```

显示过滤器的一个重要行为是**无字段自动失配**：如果某个字段在当前帧中不存在（比如对 UDP 帧评估 `tcp.port`），该表达式默认返回 false，而不是报错。这意味着 `!http.request` 会同时隐藏 HTTP 请求帧**和**所有不包含 `http.request` 字段的帧（如 DNS、ICMP）——这往往不是用户的本意。正确做法是 `http && !http.request`（已是 HTTP 流量但不是请求）。

### 常用显示过滤器速查表

**HTTP 系列：**

```
http                                    # 所有 HTTP 流量
http.request                            # 仅请求
http.response                           # 仅响应
http.request.method == "GET"            # GET 请求
http.request.method == "POST"           # POST 请求
http.response.code == 200               # 200 OK
http.response.code >= 400               # 错误响应
http.host contains "example.com"        # 特定主机
http.request.uri matches "/api/.*"      # URI 正则匹配
```

**TLS/SSL 系列：**

```
tls                                     # 所有 TLS 流量
tls.handshake                           # TLS 握手帧
tls.handshake.type == 1                 # ClientHello
tls.handshake.type == 2                 # ServerHello
tls.handshake.extensions.server_name contains "example.com"  # SNI
ssl.record.content_type == 21           # Alert 记录
```

**DNS 系列：**

```
dns                                     # 所有 DNS
dns.qry.name == "example.com"           # 特定域名查询
dns.flags.response == 0                 # 仅请求
dns.flags.response == 1                 # 仅响应
dns.qry.type == 1                       # A 记录查询
dns.qry.type == 28                      # AAAA 记录查询
dns.flags.rcode != 0                    # DNS 错误（非 NOERROR）
```

**TCP 系列：**

```
tcp.flags.syn == 1 && tcp.flags.ack == 0   # SYN（连接建立）
tcp.flags.rst == 1                          # RST（连接重置）
tcp.flags.fin == 1                          # FIN（正常关闭）
tcp.analysis.retransmission                 # TCP 重传
tcp.analysis.duplicate_ack                  # 重复 ACK
tcp.analysis.zero_window                    # 零窗口（接收方缓冲满）
tcp.port == 443                             # 目标或源端口 443
tcp.dstport == 80                           # 目标端口 80
ip.addr == 192.168.1.100                    # 任意方向 IP
ip.src == 10.0.0.1 && ip.dst == 10.0.0.2   # 特定方向
```

**ICMP 系列：**

```
icmp                                    # 所有 ICMP
icmp.type == 8                          # Echo Request（ping 发出）
icmp.type == 0                          # Echo Reply（ping 回复）
icmp.type == 3                          # Destination Unreachable
```

### tshark 字段提取示例

```bash
# 提取所有 HTTP 请求的主机名和 URI
tshark -r capture.pcapng \
  -Y 'http.request' \
  -T fields \
  -e frame.number \
  -e ip.src \
  -e http.host \
  -e http.request.method \
  -e http.request.uri \
  -E header=y \
  -E separator=,

# 统计各响应码数量
tshark -r capture.pcapng \
  -Y 'http.response' \
  -T fields \
  -e http.response.code \
  | sort | uniq -c | sort -rn

# 提取 DNS 查询域名（去重）
tshark -r capture.pcapng \
  -Y 'dns.flags.response == 0' \
  -T fields \
  -e dns.qry.name \
  | sort -u

# 实时捕获并输出 TLS SNI
tshark -i eth0 \
  -Y 'tls.handshake.type == 1' \
  -T fields \
  -e ip.src \
  -e tls.handshake.extensions.server_name

# 统计每分钟 HTTP 请求数（-z io,stat）
tshark -r capture.pcapng \
  -z io,stat,60,'http.request' \
  -q
```

tshark 的 `-T fields -e` 模式本质上是把 Wireshark 的 dissector 解析树中指定字段的值提取出来打印——任何在 Wireshark 的字段名引用工具（`View → Internals → Supported Protocols`）中列出的字段都可以用 `-e` 提取。对于大型 pcap 文件，tshark 的管道处理通常比打开 Wireshark GUI 快得多，是自动化分析流水线的核心工具。

## 工具视角与实战

### Follow Stream（流追踪）

Follow Stream 是 Wireshark 最实用的功能之一，可以重组 TCP/UDP/HTTP 流并以可读格式展示完整会话内容。

**操作步骤：**
1. 右键点击任意属于目标会话的帧
2. 选择 `Follow → TCP Stream`（或 UDP/HTTP/TLS）
3. 弹窗显示双向数据，客户端→服务器用红色，服务器→客户端用蓝色
4. 可切换显示格式：ASCII / C arrays / Raw（hex） / UTF-8

**自动生成的显示过滤器：**`tcp.stream eq 5`（流编号从 0 开始）

### 着色规则（Coloring Rules）

`View → Coloring Rules` 可为匹配特定过滤器的帧设置背景/前景色：

| 默认颜色 | 匹配条件 |
|----------|----------|
| 黑底红字 | `tcp.analysis.flags && !tcp.analysis.window_update` |
| 黄底黑字 | `arp` |
| 绿背景 | `http` |
| 紫背景 | `dns` |

自定义规则示例：高亮所有 POST 请求：
- 名称：`HTTP POST`
- 过滤器：`http.request.method == "POST"`
- 背景色：橙色

### IO Graph 绘制

`Statistics → IO Graph` 可绘制流量随时间变化的折线图：

- X 轴：时间（可调精度：秒/毫秒）
- Y 轴：数据包数/字节数/bit rate
- 支持叠加多条过滤器曲线，便于对比 TCP 重传率与总流量

**实用场景**：定位流量突增时刻，结合时间戳找到问题帧。一个常用技巧是同时绘制"所有流量"和"tcp.analysis.retransmission"两条曲线，若重传率在某个时间点骤升，往往对应网络拥塞或链路故障。

### Conversations 矩阵

`Statistics → Conversations` 显示所有通信对之间的统计：

| 列 | 含义 |
|----|------|
| Address A / Address B | 通信双方 IP |
| Packets A→B / B→A | 各方向包数 |
| Bytes A→B / B→A | 各方向字节数 |
| Rel Start | 相对开始时间 |
| Duration | 会话持续时间 |

支持按 Ethernet / IPv4 / IPv6 / TCP / UDP 分级过滤，可右键选择 `Apply as Filter`。

### 统计命令（tshark -z）

```bash
# 协议层级统计
tshark -r capture.pcapng -z io,phs -q

# TCP/UDP 会话统计
tshark -r capture.pcapng -z conv,tcp -q

# HTTP 请求-响应时间统计
tshark -r capture.pcapng -z http,tree -q

# DNS 统计
tshark -r capture.pcapng -z dns,tree -q

# IO 按秒统计字节数
tshark -r capture.pcapng -z io,stat,1 -q
```

### tshark 管道化分析实战

tshark 的真正威力在于与标准 Unix 工具组合：

```bash
# 找出访问最频繁的域名（DNS 请求）
tshark -r capture.pcapng -Y 'dns.flags.response==0' \
  -T fields -e dns.qry.name 2>/dev/null \
  | sort | uniq -c | sort -rn | head -20

# 按字节量排序的 TCP 会话（找最大流量源）
tshark -r capture.pcapng -z conv,tcp -q 2>/dev/null \
  | grep -v '^=' | sort -k3 -rn | head -10

# 提取 HTTP Basic Auth 用户名（Base64 解码）
tshark -r capture.pcapng -Y 'http.authorization' \
  -T fields -e http.authorization 2>/dev/null \
  | grep -oP 'Basic \K[A-Za-z0-9+/=]+' \
  | while read b64; do echo "$b64" | base64 -d; echo; done

# 生成每个 IP 的请求次数 CSV
tshark -r capture.pcapng -Y 'http.request' \
  -T fields -e ip.src -E separator=, 2>/dev/null \
  | sort | uniq -c | awk '{print $2","$1}' > http_per_ip.csv
```

## 安全性与正确使用

### Lua Dissector 安全边界

Wireshark 支持用 Lua 编写自定义 dissector（`~/.config/wireshark/plugins/*.lua`），但需注意：

- **代码执行风险**：`.pcapng` 文件可内嵌触发 Lua dissector 的自定义数据，理论上存在载荷注入风险。不要用生产环境 Wireshark 打开来源不明的 pcap 文件
- **权限隔离**：Wireshark 以普通用户权限运行（通过 dumpcap 子进程获取 CAP_NET_RAW），Lua 代码在同等权限下执行
- **来源验证**：只加载来自可信源的 Lua 插件，`.lua` 文件不要从公共论坛直接复制粘贴

### 大文件性能

- 超过 1 GB 的 pcap 文件，Wireshark 加载时全量建立帧索引，可能耗时数分钟且内存占用高
- **建议**：先用 `editcap` 切割，或用 `tshark -Y` 过滤后写出子集再打开
- 显示过滤器对大文件进行二次过滤时，Wireshark 需要线性扫描，可配合 `Statistics → Expert Information` 快速定位异常

### 合规边界——仅对自有/授权流量使用

Wireshark 和 tshark 的所有分析功能，前提是分析人员对捕获文件拥有合法权利。对他人流量进行抓包、对非自有网络使用 ARP 欺骗等主动中间人手段，在绝大多数司法管辖区属于违法行为。企业 SOC 分析师在对内网流量进行监控分析时，也需要确保有明确的法律授权和员工知情同意政策。

## 小结

- Wireshark 的架构由 GUI、Display Filter Engine、Dissector Layer 和 libpcap 四层组成
- 捕获过滤器（BPF）由 libpcap 编译成 cBPF 字节码注入内核，显示过滤器由 epan 引擎在用户态求值——两套语法、两种时机、两条编译路径，不可混用
- Dissector 链式调用实现逐层协议解析，启发式 dissector 可识别非标准端口上的协议
- TCP 流重组让 Follow Stream 能够展示正确排序的应用层完整数据，乱序/重传被自动处理
- 显示过滤器支持比较、逻辑、成员、正则等丰富运算，可直接访问解析后的命名字段
- tshark 通过 `-T fields -e` 可提取任意字段为结构化输出，与 sort/awk/grep 管道组合是自动化分析的基石
- Follow Stream、IO Graph、Conversations 是日常分析最高频的三个功能
