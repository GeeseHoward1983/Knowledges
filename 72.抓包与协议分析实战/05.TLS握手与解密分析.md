# TLS 握手与解密分析

> [!abstract] TL;DR
> TLS 1.3 将握手压缩为 1-RTT（ClientHello 直接携带 key_share），握手消息在 Finished 后即加密，无法从网络层观察证书。TLS 1.2 四步握手明文可见证书但支持 RSA 静态密钥解密。实战解密首选 SSLKEYLOGFILE：NSS 格式日志导出客户端侧会话密钥，Wireshark 导入即可解密，且不依赖服务器私钥，兼容 PFS（前向保密）。

## 概述与定位

TLS（Transport Layer Security）是 HTTPS、SMTPS、DoT 等协议的安全层。从抓包分析角度，TLS 带来了三个核心挑战：

1. **加密**：载荷不可见，需密钥才能解密
2. **握手复杂性**：TLS 1.2 和 1.3 握手流程差异显著
3. **前向保密（PFS）**：TLS 1.3 强制使用 ECDHE，服务器私钥泄露不能解密历史流量

**Wireshark TLS 解密的两种方式：**

| 方法 | 适用 TLS 版本 | 需要条件 | 缺点 |
|------|-------------|----------|------|
| 服务器 RSA 私钥 | TLS 1.2（无 PFS）| 持有服务器私钥 | 不支持 ECDHE/DHE（PFS）|
| SSLKEYLOGFILE | TLS 1.2 + 1.3 | 控制客户端进程 | 需在客户端配置环境变量 |

## 原理与机制

### TLS 1.2 vs TLS 1.3 握手逐消息对比

理解两个版本的握手差异，是读懂抓包结果的前提。

**TLS 1.2 握手详解（2-RTT，4个飞行批次）：**

TLS 1.2 握手需要 2-RTT（不含 TCP 握手）：

```
客户端                            服务器
   │                                │
   │──── ClientHello ──────────────▶│  版本/随机数/密码套件列表/扩展
   │◀─── ServerHello ───────────────│  选定版本/随机数/选定密码套件
   │◀─── Certificate ───────────────│  服务器证书链（明文可见！）
   │◀─── ServerKeyExchange ─────────│  DHE/ECDHE 参数（若使用 PFS）
   │◀─── ServerHelloDone ───────────│
   │                                │
   │──── ClientKeyExchange ────────▶│  加密的 Pre-Master Secret（RSA）
   │                                │  或 ECDHE 客户端公钥
   │──── ChangeCipherSpec ─────────▶│  通知：后续启用加密
   │──── Finished ─────────────────▶│  首个加密消息（验证握手完整性）
   │◀─── ChangeCipherSpec ───────────│
   │◀─── Finished ───────────────────│
   │                                │
   │══════ 应用数据（加密） ════════│
```

TLS 1.2 的证书和 ServerKeyExchange 是**明文传输**的，在 Wireshark 中可以直接看到服务器证书的 CN、有效期、公钥等信息。这对于排查证书问题（过期、域名不匹配、证书链不完整）非常方便。

**TLS 1.3 握手详解（1-RTT，加密更早开始）：**

TLS 1.3 的核心改进是把密钥协商提前到 Hello 阶段：

```
客户端                            服务器
   │                                │
   │──── ClientHello ──────────────▶│  
   │     supported_versions: [1.3]  │
   │     key_share: X25519 公钥     │  ← 直接携带 ECDHE 公钥
   │     supported_groups: [x25519, │
   │       secp256r1, secp384r1]    │
   │     signature_algorithms: ...  │
   │     server_name: example.com   │  ← SNI 扩展（明文！）
   │     ....（其他扩展）           │
   │                                │
   │◀─── ServerHello ───────────────│  
   │     key_share: 服务器 X25519   │  ← 双方现在可导出握手密钥
   │◀─── {EncryptedExtensions} ─────│  ← 后续握手消息全部加密！
   │◀─── {Certificate} ─────────────│  证书在加密中，抓包不可见
   │◀─── {CertificateVerify} ───────│
   │◀─── {Finished} ────────────────│
   │                                │
   │──── {Finished} ───────────────▶│
   │══════ 应用数据（加密） ════════│
```

**为何 TLS 1.3 是 1-RTT**：ClientHello 直接携带了 ECDHE 公钥（`key_share` 扩展），服务器收到后立即可以计算共享密钥，回复 ServerHello 时也携带自己的 ECDHE 公钥，双方在第一轮消息交换后就拥有了握手密钥，无需再等一轮。TLS 1.2 之所以需要 2-RTT，是因为密码套件协商（ServerHello）和密钥参数交换（ServerKeyExchange）是分开的消息，客户端拿到服务器的 ECDHE 参数后才能生成自己的 ClientKeyExchange。

**加密范围差异**：TLS 1.2 中 ChangeCipherSpec 之前的所有消息（包括证书）都是明文；TLS 1.3 中从 ServerHello 之后的所有握手消息就已加密（EncryptedExtensions、Certificate、CertificateVerify、Finished），只有 ClientHello 和 ServerHello 是明文。这使得 TLS 1.3 的流量对监控设备更加不透明。

### 密钥派生：master secret → HKDF → traffic keys

TLS 1.2 和 1.3 在密钥派生上有根本性差异。

**TLS 1.2 密钥派生（PRF）**：
1. 密钥交换后双方拥有 `pre_master_secret`
2. `master_secret = PRF(pre_master_secret, "master secret", ClientRandom + ServerRandom)`（48字节）
3. `key_block = PRF(master_secret, "key expansion", ServerRandom + ClientRandom)`（扩展到各个密钥所需长度）
4. 从 key_block 中切分出 client_write_MAC_key、server_write_MAC_key、client_write_key、server_write_key、client_write_IV、server_write_IV
5. SSLKEYLOGFILE 中 `CLIENT_RANDOM <client_random> <master_secret>` 提供的就是第二步的输出，Wireshark 从 master_secret 重推 key_block

**TLS 1.3 密钥派生（HKDF）**：

```
ECDHE 共享密钥（或 0 若无 PSK）
    │
    ▼ HKDF-Extract（盐=0）
Early Secret（影响 0-RTT 早数据密钥）
    │
    ▼ HKDF-Derive-Secret（"derived"）再 HKDF-Extract（IKM=ECDHE 共享密钥）
Handshake Secret
    ├── client_handshake_traffic_secret → 客户端握手加密密钥
    └── server_handshake_traffic_secret → 服务器握手加密密钥
    │
    ▼ HKDF-Derive-Secret（"derived"）再 HKDF-Extract（IKM=0）
Master Secret
    ├── client_application_traffic_secret_0 → 客户端应用数据密钥（初始）
    └── server_application_traffic_secret_0 → 服务器应用数据密钥（初始）
    └── exporter_master_secret（供扩展使用）
    └── resumption_master_secret（用于 session resumption）
```

HKDF（HMAC-based Key Derivation Function，RFC 5869）相比 TLS 1.2 的 PRF 有更好的密钥分离特性——每个用途都有独立的密钥，compromising 一个密钥不会影响其他。密钥轮换（Key Update）通过 `KeyUpdate` 消息触发，对 `_0` 后缀的 secret 做一次 HKDF-Expand-Label 得到 `_1`，依此类推，SSLKEYLOGFILE 中对应的标签是 `CLIENT_TRAFFIC_SECRET_1` 等。

### 前向保密（PFS）的意义——为何有私钥也无法解密 ECDHE 流量

**前向保密（Perfect Forward Secrecy / Forward Secrecy）** 的核心思想：即使长期私钥（服务器的 RSA 或 ECDSA 私钥）将来被泄露，也无法解密**过去**录制的流量。

这在密码学上是通过**临时密钥对**实现的：在 ECDHE（Elliptic Curve Diffie-Hellman Ephemeral）密钥交换中，服务器在每次握手时生成一个全新的临时 ECDH 密钥对，用服务器长期签名私钥对临时公钥签名（防止冒充），完成密钥交换后立即丢弃临时私钥。

所以即使攻击者：
1. 录制了所有 TLS 加密流量（存入磁盘，等待未来能解密）
2. 数年后通过漏洞或法律手段获取了服务器的 RSA 私钥

也无法解密历史流量，因为服务器 RSA 私钥只能验证临时密钥对的签名，而实际加密流量数据的 session key 是从已被丢弃的临时 ECDH 私钥派生的——它根本不存在于任何持久化存储上。

**对抓包分析的影响**：使用 PFS（ECDHE）的 TLS 连接，**不能通过服务器私钥解密**，Wireshark 的 RSA Keys 功能对它无效。唯一的解密路径是在连接建立期间从客户端进程中导出 session key（即 SSLKEYLOGFILE），或者在握手阶段就拦截（MITM 代理）。这就是为什么 SSLKEYLOGFILE 成为了解密自有 TLS 流量的黄金标准。

TLS 1.2 的不支持 PFS 的套件（如 `TLS_RSA_WITH_AES_128_CBC_SHA`）允许用服务器私钥解密，但 TLS 1.3 已完全移除了所有静态 RSA 密钥交换套件，所有 TLS 1.3 连接强制 PFS。

### Session Resumption 与 0-RTT 的重放风险

**Session Resumption（会话恢复）** 是 TLS 的性能优化机制，允许客户端和服务器跳过完整握手，用之前协商好的会话状态恢复连接：

- **TLS 1.2 Session ID**：服务器在 ServerHello 中包含 Session ID，客户端保存；下次连接时在 ClientHello 中提交 Session ID，服务器查找缓存并恢复
- **TLS 1.2 Session Ticket**：服务器把加密后的会话状态发给客户端保存（不在服务器存储），客户端下次连接时在 `session_ticket` 扩展中提交；服务器用 ticket 加密密钥解密后恢复会话
- **TLS 1.3 PSK（Pre-Shared Key）**：结合前两种优点，会话恢复时客户端在 ClientHello 的 `pre_shared_key` 扩展中提交 PSK 标识符，服务器验证后用 PSK 推导新密钥

**0-RTT Early Data（TLS 1.3 特有）**：TLS 1.3 允许客户端在第一个 ClientHello 中就携带应用数据（Early Data），无需等待握手完成。服务器在收到 ClientHello 后就能解密 Early Data，实现零往返延迟。代价是：0-RTT 数据**不提供前向保密**（PSK 来自上次会话，若 PSK 泄露则 Early Data 可解密），且存在**重放攻击**风险——攻击者可以录制 0-RTT 数据包并重发给服务器。安全的服务器实现应对 0-RTT 请求的幂等性有严格要求（如只允许安全 HTTP 方法 GET/HEAD，不允许 POST），并部署重放窗口检测。

在 SSLKEYLOGFILE 中，0-RTT 数据对应的密钥标签是 `EARLY_TRAFFIC_SECRET`。

## 结构/算法/伪代码详解

### SSLKEYLOGFILE 格式说明与 Wireshark 对应关系

NSS Key Log 格式（Chrome、Firefox、curl 等支持）每行记录一个密钥材料：

```
# TLS 1.2
CLIENT_RANDOM <client_random_hex> <master_secret_hex>

# TLS 1.3（每个流量方向各一行）
CLIENT_HANDSHAKE_TRAFFIC_SECRET <client_random_hex> <secret_hex>
SERVER_HANDSHAKE_TRAFFIC_SECRET <client_random_hex> <secret_hex>
CLIENT_TRAFFIC_SECRET_0 <client_random_hex> <secret_hex>
SERVER_TRAFFIC_SECRET_0 <client_random_hex> <secret_hex>

# TLS 1.3 密钥更新（0-RTT 或密钥轮换）
CLIENT_TRAFFIC_SECRET_1 <client_random_hex> <secret_hex>
```

各标签说明及 Wireshark 解密用途：

| 标签 | 用途 |
|------|------|
| `CLIENT_RANDOM` | TLS 1.2 主密钥（master secret），Wireshark 从此派生所有对称密钥 |
| `CLIENT_HANDSHAKE_TRAFFIC_SECRET` | TLS 1.3 客户端握手流量密钥，用于解密握手阶段客户端消息（Finished 等）|
| `SERVER_HANDSHAKE_TRAFFIC_SECRET` | TLS 1.3 服务器握手流量密钥，用于解密 EncryptedExtensions/Certificate/Finished |
| `CLIENT_TRAFFIC_SECRET_0` | TLS 1.3 客户端应用数据密钥（初始），解密实际 HTTP 请求 |
| `SERVER_TRAFFIC_SECRET_0` | TLS 1.3 服务器应用数据密钥（初始），解密实际 HTTP 响应 |
| `EARLY_TRAFFIC_SECRET` | TLS 1.3 0-RTT Early Data 密钥 |

`<client_random_hex>` 是 ClientHello 中 32 字节随机数的十六进制表示，Wireshark 用它把密钥行与对应的 TLS 连接匹配（因为同时可能有多个 TLS 连接，每个都有不同的 client_random）。

### TLS 报文字段逐层解析

以 ClientHello 为例（TLS Record 层 → Handshake 层）：

```
TLS Record Layer:
  Content Type: 22 (Handshake)          ← 1 字节
  Version: 0x0301 (TLS 1.0)             ← 2 字节（历史兼容，实际版本在扩展中）
  Length: xxxx                           ← 2 字节

Handshake:
  Handshake Type: 1 (ClientHello)       ← 1 字节
  Length: xxxxxx                         ← 3 字节

ClientHello:
  Legacy Version: 0x0303 (TLS 1.2)     ← 2 字节（固定，实际版本在 supported_versions）
  Random: [32 bytes]                    ← 32 字节（client_random，SSLKEYLOGFILE 的索引键）
  Session ID Length: xx                 ← 1 字节
  Session ID: [variable]               ← 0-32 字节
  Cipher Suites Length: xxxx           ← 2 字节
  Cipher Suites: [list]                ← 每个 2 字节
  Compression Methods: 0x00            ← 1 字节（TLS 1.3 禁用压缩）
  Extensions Length: xxxx              ← 2 字节
  Extensions: [...]                    ← 各扩展
```

### TLS 扩展表

| 扩展类型 | 类型值 | 说明 |
|----------|--------|------|
| server_name (SNI) | 0x0000 | 目标域名，明文！抓包可见 |
| max_fragment_length | 0x0001 | 最大片段长度 |
| status_request (OCSP) | 0x0005 | 在线证书状态请求 |
| supported_groups | 0x000a | 支持的椭圆曲线组（x25519/P-256/P-384）|
| signature_algorithms | 0x000d | 支持的签名算法 |
| alpn | 0x0010 | 应用层协议协商（h2/http/1.1）|
| signed_cert_timestamp | 0x0012 | CT 签名时间戳 |
| extended_master_secret | 0x0017 | 增强主密钥派生 |
| session_ticket | 0x0023 | TLS 1.2 会话恢复票据 |
| supported_versions | 0x002b | 支持的 TLS 版本（TLS 1.3 核心扩展）|
| psk_key_exchange_modes | 0x002d | PSK 模式（TLS 1.3）|
| key_share | 0x0033 | ECDHE 密钥共享（TLS 1.3 核心）|
| pre_shared_key | 0x0029 | PSK 标识（TLS 1.3 0-RTT）|

从抓包分析视角来看，最重要的是 `server_name`（SNI，明文域名）和 `alpn`（协议协商，告诉我们实际用了 h2 还是 http/1.1）。TLS 1.3 中还有 `Encrypted Client Hello（ECH）` 扩展（前身是 ESNI），把整个 ClientHello 加密，连 SNI 也隐藏——未来这将让基于 SNI 的 DPI（深度包检测）失效。

## 工具视角与实战

### 配置 SSLKEYLOGFILE

**Chrome / Edge：**

```bash
# Linux/macOS
SSLKEYLOGFILE=/tmp/ssl_keys.log google-chrome --ssl-key-log-file=/tmp/ssl_keys.log

# Windows（PowerShell）
$env:SSLKEYLOGFILE = "C:\tmp\ssl_keys.log"
Start-Process "chrome.exe"

# 或者通过系统环境变量（持久化，所有支持 NSS 的程序均生效）
# Windows: 系统属性 → 高级 → 环境变量 → 新建 SSLKEYLOGFILE
```

**Firefox：**

```
about:config → 搜索 security.tls.loglevel
# 或者设置同名环境变量后重启 Firefox
SSLKEYLOGFILE=/tmp/ssl_keys.log firefox
```

**curl：**

```bash
curl --tls-max 1.3 \
     --tlsv1.3 \
     -v \
     https://example.com \
     --ssl-key-log-file /tmp/curl_keys.log
```

**Python（ssl 模块钩子）：**

```python
import ssl
import socket

def setup_keylog(keylog_file="/tmp/python_ssl.log"):
    """为 Python ssl 连接配置 SSLKEYLOGFILE"""
    ctx = ssl.create_default_context()
    
    # Python 3.8+ 支持 keylog_filename
    ctx.keylog_filename = keylog_file
    return ctx

# 使用示例
ctx = setup_keylog()
with socket.create_connection(("example.com", 443)) as sock:
    with ctx.wrap_socket(sock, server_hostname="example.com") as ssock:
        ssock.send(b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n")
        print(ssock.recv(4096))

# 对于 requests 库，通过 urllib3 注入
import urllib3
urllib3.util.ssl_.DEFAULT_CIPHERS = "..."
# 注：requests 不直接支持 keylog，推荐用 mitmproxy 替代
```

### Wireshark 配置 TLS 解密步骤

```
1. 打开捕获文件（或已有实时抓包）

2. 菜单：Edit → Preferences → Protocols → TLS
   （或在 TLS 帧上右键 → Protocol Preferences → TLS）

3. (Pre)-Master-Secret log filename → 浏览选择 ssl_keys.log

4. 若用 RSA 私钥（仅 TLS 1.2 无 PFS）：
   Edit → Preferences → Protocols → TLS → RSA keys list → Add
   填写: IP地址, 端口, 协议(http), 私钥文件路径, 密码

5. 点击 OK，Wireshark 自动尝试用密钥解密已捕获的包

6. 显示过滤器：http（若成功解密，HTTPS 流量现在显示为 HTTP）
```

验证是否解密成功的方法：在 TLS 数据包的 Packet Details 中，若看到 "Decrypted TLS" 层，说明解密成功。

### 将 SSLKEYLOGFILE 嵌入 pcapng（DSB 块）

Wireshark 4.0+ 支持把 SSLKEYLOGFILE 内容嵌入 pcapng 的 Decryption Secrets Block（DSB），方便分发：

```bash
# 用 editcap 把密钥文件嵌入现有 pcapng
editcap --inject-secrets tls,ssl_keys.log \
  input.pcapng output_with_keys.pcapng

# 嵌入后，接收者打开 pcapng 无需单独提供密钥文件
```

## 安全性与正确使用

### 私钥泄露风险

SSLKEYLOGFILE 包含所有 TLS 会话的密钥材料，一旦泄露，对应时间段内的所有加密流量均可被解密：

- **文件权限**：`chmod 600 /tmp/ssl_keys.log`，仅当前用户可读
- **生命周期**：使用完毕立即删除，不要提交到代码仓库（`.gitignore` 中添加 `*.log`）
- **生产禁用**：绝对不在生产服务器上设置 `SSLKEYLOGFILE`，仅在本地开发/测试环境使用
- **隔离**：建议在虚拟机或容器中进行 TLS 调试，避免影响其他应用的密钥安全

### SSLKEYLOGFILE 的合规边界

- 只对**自己控制**的客户端进程设置密钥日志
- 不对第三方应用注入 NSS hook 导出其密钥（可能违反相关法律）
- 企业环境中，若需监控员工 HTTPS 流量，必须有明确的法律授权和员工知情同意
- SSLKEYLOGFILE 与 pcapng 组合是强大的合规审计工具，也是潜在的隐私泄露载体，需严格控制访问权限和数据保留期限

### CT（Certificate Transparency）与 HSTS/HPKP

- **CT（证书透明度）**：所有 CA 签发的证书必须提交到公开日志（CT Log），可用于检测未经授权的证书颁发。工具：https://crt.sh
- **HSTS（HTTP Strict Transport Security）**：通过响应头 `Strict-Transport-Security: max-age=31536000` 要求浏览器永远使用 HTTPS，防止 SSL strip 攻击
- **HPKP（HTTP Public Key Pinning，已废弃）**：固定证书公钥哈希，Chromium 已于 2018 年移除支持，但概念在移动端 App 中仍广泛使用

## 小结

- TLS 1.3 强制 1-RTT + ECDHE + 握手加密，抓包只能看到 SNI 和握手类型，证书不可见；TLS 1.2 的证书和握手参数明文传输，抓包可观察
- TLS 1.3 使用 HKDF 进行层级化密钥派生，密钥分离更彻底；TLS 1.2 基于 PRF 从 master_secret 展开所有密钥
- PFS（前向保密）通过临时 ECDHE 密钥对实现：临时私钥握手后立即丢弃，历史流量不可用服务器长期私钥解密——必须用 SSLKEYLOGFILE
- SSLKEYLOGFILE 是解密自有 TLS 流量的黄金方案，兼容 TLS 1.2/1.3 和 PFS，Chrome/Firefox/curl/Python 均支持
- 0-RTT Early Data 提供零往返延迟，但不具备前向保密且有重放风险，应用服务器须实现重放防护
- Wireshark 通过 `Preferences → TLS → (Pre)-Master-Secret log` 导入密钥文件，DSB 块可将密钥嵌入 pcapng 文件
- 密钥日志文件属于高度敏感信息，需严格控制权限和生命周期，禁止在生产环境使用
