# 移动端抓包：Android与iOS

> [!abstract] TL;DR
> 移动端抓包面临三重挑战：SSL Pinning 拒绝用户安装的 CA 证书、VPN 检测绕过代理、Root 检测阻止调试工具注入。Android 通过 PCAPdroid（VPN Service API，无需 Root）或 mitmproxy 透明代理实现抓包；iOS 通过 rvictl 创建虚拟网络接口配合 Wireshark 捕获原始流量。绕过 SSL Pinning 需要 Frida/objection 或修改 network_security_config.xml。

## 概述与定位

移动端 App 的网络流量分析是安全审计、漏洞挖掘和逆向工程的关键环节，但与 PC 端抓包相比，存在独特的技术障碍：

**Android 特殊挑战：**
- Android 7.0（API 24）起，用户安装的 CA 证书默认不受应用信任（须明确在 `network_security_config.xml` 中声明）
- 部分 App 内置 SSL Pinning（公钥/证书 Hash 白名单），拒绝非预期证书
- Root 检测（SafetyNet/Play Integrity）阻止 Frida 注入

**iOS 特殊挑战：**
- iOS 应用沙盒隔离，无法在设备上直接安装 tcpdump（非越狱）
- ATS（App Transport Security）强制 HTTPS
- SSL Pinning 通过 `NSURLSessionDelegate` 或第三方库（如 TrustKit）实现

正确理解这些机制，才能选择最合适的抓包方案。从防御侧看，了解 SSL Pinning 的各种绕过路径也是设计更健壮的 Pinning 实现的前提——知道哪里会被 hook，才能把验证逻辑迁移到更难被动态注入的位置。

## 原理与机制

### Android VPN Service API（PCAPdroid 原理）

Android 提供 `VpnService` API，允许普通 App（无需 Root）创建一个用户空间 VPN，将设备所有网络流量路由到该 App 处理。PCAPdroid 正是利用这一 API：

1. App 调用 `VpnService.Builder` 建立 TUN（虚拟网络接口）设备，分配一个私有虚拟子网（如 `10.215.173.0/24`）
2. Android 内核将所有出站流量路由到 `/dev/tun` 字符设备，而非物理网卡
3. PCAPdroid 的用户空间进程从 tun fd 读取 IP 数据包，解析 IP/TCP/UDP 报头，将原始帧写入 pcap 格式
4. PCAPdroid 同时作为"透传层"，将数据包转发到真实的目标（不拦截，只复制记录）
5. 无需 Root，无需证书安装，适合捕获**明文流量**

这与 Wireguard/OpenVPN 等 VPN 客户端使用的机制完全相同——只不过 PCAPdroid 不做加密，只做抓包。

**限制**：对于加密 TLS 流量，PCAPdroid 只能记录密文，无法解密（除非配合 mitmproxy 透明代理模式）。tun 接口处理的是 IP 层报文，TLS 数据在 IP payload 内，PCAPdroid 无法在没有私钥的情况下解密。

**与 Root 方案的对比**：Root 后可直接在 tcpdump 挂接物理网卡（如 `wlan0`），但 VpnService 方案不依赖 Root，能在出厂设备上运行，代价是额外的用户空间转发层增加了轻微延迟。

### iOS rvictl 的 RemoteVirtualInterface 机制

Apple 的 `rvictl`（Remote Virtual Interface）工具使用 Apple 内部的 `com.apple.mobile.remote_interface` 私有框架，通过 USB 在 Mac 上创建与 iOS 设备绑定的虚拟网络接口：

```
Mac                          iOS 设备
┌──────────────────┐   USB   ┌──────────────────┐
│  rvi0 虚拟接口   │ ←────── │  所有网络流量    │
│  Wireshark 捕获  │         │  (Wi-Fi + 蜂窝)  │
└──────────────────┘         └──────────────────┘
```

iOS 内部的网络栈（XNU 内核的 `if_veth` 驱动）将设备的所有网络接口流量镜像到 USB 通道，Mac 侧生成一个 `rvi0`（Remote Virtual Interface 0）接口，该接口对 Wireshark/tcpdump 表现为标准网络接口。这个方案的优势在于：

- **非越狱**：完全官方支持，Apple 开发者工具内置
- **全流量**：同时捕获 Wi-Fi 和蜂窝网络流量（其他方案往往只能捕获 Wi-Fi）
- **时间戳准确**：iOS 设备侧打上时间戳，避免 Mac 侧 USB 延迟影响
- **无需安装证书**：只是流量镜像，不做任何中间人操作

但 rvictl 无法解密 TLS 流量，只能看到加密的 IP/TCP 层，是取证分析（"这个 App 连接了哪些 IP"）而非协议内容分析（"这个 App 发送了什么数据"）的工具。

### TLS 证书验证链与 SSL Pinning

标准 TLS 验证流程：客户端 → 接收服务器证书 → 验证证书链（中间 CA → 根 CA）→ 根 CA 在系统信任存储中 → 信任。MITM 代理（mitmproxy/Burp）插入自签 CA 证书，只要该 CA 被安装到系统/用户信任存储，就能完成中间人解密。

SSL Pinning 通过额外验证打破这一流程：

- **证书 Pinning**：在 App 代码中硬编码服务器证书的 DER 内容或 SHA-256 哈希，与运行时收到的证书进行比较，不一致则拒绝连接。最严格但证书轮换代价高——服务端更新证书必须同步发版 App。
- **公钥 Pinning**（SubjectPublicKeyInfo Pinning）：只固定证书中的公钥哈希，而非整个证书。证书可以轮换（签发新证书但保持同一公钥），App 不需要同步更新。这是目前移动 App 最常见的 Pinning 形式。
- **CA 固定**：只接受特定 CA 签发的证书（如企业自建 PKI 的内部 CA），是企业 MDM 场景的常见选择。

绕过途径：
1. **系统级**：将代理 CA 安装到系统存储（需 Root）——绕过大多数 Pinning，但 App 可以跳过系统信任存储直接自行验证
2. **编译时**：修改 APK 中的 `network_security_config.xml`（需重新签名）——绕过 Android 框架层的 CA 信任配置，但 App 在代码中直接实现的 Pinning 不受影响
3. **运行时**：Frida hook TLS 验证函数，跳过 Pinning 检查——最灵活，能对抗几乎所有 Java 层的 Pinning 实现

### network_security_config.xml 与 Android 7+ 的信任层级变化

Android 7.0（Nougat，API 24）是移动端安全的一个重要分水岭。在此之前，用户安装的 CA 证书（通过"设置→安全→安装证书"）默认受所有 App 信任，mitmproxy 的证书安装后即可对所有 App 抓包。

从 Android 7.0 起，Android 引入了分层信任机制：
- **System CA**（`/system/etc/security/cacerts/`）：系统内置根 CA，无条件信任
- **User CA**（`/data/misc/user/0/cacerts-added/`）：用户安装的 CA，默认**仅受 `targetSdkVersion < 24` 的 App 信任**

如果一个 App 的 `targetSdkVersion >= 24`（现代 App 几乎全部如此），用户安装 mitmproxy 证书也没有效果，App 完全忽略 User CA 存储。要让 App 信任用户 CA，开发者需要在 `AndroidManifest.xml` 中声明 `android:networkSecurityConfig` 属性，并在 XML 文件中明确列出 User CA 信任。安全审计时常用的方法是将目标 App 反编译后修改此文件再重打包，或使用 Frida 动态绕过。

### Android：adb + mitmproxy 透明代理配置

```bash
# 1. 启动 mitmproxy（透明模式，监听 8080）
mitmproxy --mode transparent --listen-port 8080

# 2. adb 反向端口映射（设备 8080 → 宿主机 8080）
adb reverse tcp:8080 tcp:8080

# 3. 在设备上配置 Wi-Fi 代理为 127.0.0.1:8080
# 或通过 adb shell 设置全局代理（需 Root 或 ADB over USB）
adb shell settings put global http_proxy 127.0.0.1:8080

# 4. 安装 mitmproxy CA 证书（Android 7 以下）
# 访问 http://mitm.it 下载 CA 证书
# 在设置 > 安全 > 安装证书中安装

# 5. 查看实时流量
# mitmproxy 交互界面中直接浏览所有请求/响应
```

### Android：network_security_config.xml 修改（APK 重打包）

```xml
<!-- res/xml/network_security_config.xml -->
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <!-- 信任用户安装的 CA（Android 7+ 的关键配置）-->
    <base-config cleartextTrafficPermitted="true">
        <trust-anchors>
            <!-- 信任系统 CA -->
            <certificates src="system" />
            <!-- 信任用户安装的 CA（mitmproxy/Burp 证书）-->
            <certificates src="user" />
        </trust-anchors>
    </base-config>

    <!-- 针对特定域名禁用 Pinning（调试专用）-->
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
        <!-- 注释掉或删除原有的 <pin-set> 节点 -->
    </domain-config>
</network-security-config>
```

```bash
# APK 重打包流程（需 apktool + apksigner）
apktool d target.apk -o target_decompiled/
# 编辑 res/xml/network_security_config.xml
# 确保 AndroidManifest.xml 中引用了该文件：
# android:networkSecurityConfig="@xml/network_security_config"
apktool b target_decompiled/ -o target_patched.apk
# 重新签名
keytool -genkey -v -keystore debug.keystore -alias androiddebugkey \
  -keyalg RSA -keysize 2048 -validity 10000 -storepass android -keypass android
apksigner sign --ks debug.keystore --ks-key-alias androiddebugkey \
  --ks-pass pass:android --key-pass pass:android target_patched.apk
adb install target_patched.apk
```

### Frida hook 注入点原理与 SSL Pinning 绕过

Frida 通过 ptrace 系统调用（Linux）或 task_for_pid（iOS）附加到目标进程，注入一个动态链接库，然后通过 V8/QuickJS JavaScript 引擎在目标进程内存空间执行 hook 脚本。对于 Android Java 应用，Frida 使用 ART（Android Runtime）的 instrumentation API，可以在 Java 方法调用链的任意点插入代码，实现方法替换（`overload.implementation`）。

SSL Pinning 绕过的关键 hook 目标：
- **`okhttp3.CertificatePinner.check`**：OkHttp3（绝大多数现代 Android App 使用）的 Pinning 检查方法
- **`javax.net.ssl.X509TrustManager.checkServerTrusted`**：Java 标准 TLS 信任管理器的服务器证书验证方法
- **`javax.net.ssl.SSLContext.init`**：TLS 上下文初始化，替换为全信任的 TrustManager
- **`com.android.org.conscrypt.TrustManagerImpl.checkTrustedRecursive`**：Android 内置 TLS 实现的底层验证方法

```bash
# 1. 安装 frida-server 到 Android 设备（需 Root 或模拟器）
# 从 https://github.com/frida/frida/releases 下载对应架构的 frida-server
adb push frida-server-16.x.x-android-arm64 /data/local/tmp/frida-server
adb shell chmod 755 /data/local/tmp/frida-server
adb shell /data/local/tmp/frida-server &

# 2. 安装 objection
pip install objection

# 3. 列出设备上运行的进程
frida-ps -U

# 4. 附加到目标 App 并禁用 SSL Pinning
objection -g com.target.app explore

# 在 objection shell 中执行：
# android sslpinning disable
# 效果：hook 所有常见 SSL Pinning 实现（OkHttp3/Retrofit/原生 X509TrustManager）

# 5. Frida 脚本方式（更精细控制）
frida -U -f com.target.app --no-pause -l ssl_bypass.js
```

```javascript
// ssl_bypass.js — 绕过 Android SSL Pinning 的通用 Frida 脚本
Java.perform(function() {
    // 绕过 OkHttp3 CertificatePinner
    try {
        var CertificatePinner = Java.use('okhttp3.CertificatePinner');
        CertificatePinner.check.overload('java.lang.String', 'java.util.List')
            .implementation = function(hostname, peerCertificates) {
                console.log('[+] OkHttp3 CertificatePinner.check bypassed for: ' + hostname);
                return;  // 直接返回，不执行 Pinning 检查
            };
    } catch(e) { console.log('OkHttp3 not found'); }

    // 绕过系统 TrustManager
    try {
        var TrustManager = Java.use('javax.net.ssl.X509TrustManager');
        var SSLContext = Java.use('javax.net.ssl.SSLContext');
        var TrustManagerImpl = Java.registerClass({
            name: 'com.custom.TrustManagerImpl',
            implements: [TrustManager],
            methods: {
                checkClientTrusted: function(chain, authType) {},
                checkServerTrusted: function(chain, authType) {},
                getAcceptedIssuers: function() { return []; }
            }
        });
        var ctx = SSLContext.getInstance('TLS');
        ctx.init(null, [TrustManagerImpl.$new()], null);
        SSLContext.getDefault.implementation = function() { return ctx; };
        console.log('[+] TrustManager bypassed');
    } catch(e) { console.log('TrustManager bypass failed: ' + e); }
});
```

> [!caution] 授权边界：SSL Pinning 绕过的合规范围
> SSL Pinning 绕过技术**仅适用于以下场景**：
> - **自有 App 开发调试**：开发者对自己开发的应用进行接口联调和问题排查
> - **授权安全审计**：已获书面授权的渗透测试或安全评估项目
> - **自有设备上的自有 App**：用户对自己账号下的 App 进行个人研究
>
> **严禁以下行为**：
> - 绕过第三方 App 的 SSL Pinning 以截获其他用户数据
> - 利用抓包结果破解 App 的 API 协议进行商业竞争
> - 在未获授权的情况下对 App 服务器发起请求或进行自动化攻击
> - 使用 Frida/objection 等工具对不拥有的 App 进行运行时分析
>
> 在大多数国家/地区，未授权的网络截获属于违法行为（中国《网络安全法》第 27 条，美国 CFAA 等）。安全研究必须在授权边界内进行，且所发现的漏洞应通过负责任披露途径报告给厂商。

## 安全性与正确使用

### 合规测试清单

在进行移动端抓包分析前，确认以下事项：

- [ ] 测试对象是自己开发/拥有的 App，或已获得书面授权
- [ ] 测试设备是专用测试设备，不包含真实用户数据
- [ ] 若为企业安全审计，已签署 NDA 和授权协议
- [ ] 抓包数据在项目结束后按约定销毁
- [ ] 不将 SSL Pinning 绕过工具（frida-server）留在生产设备上

### 防御侧：加固 SSL Pinning 实现

了解攻击路径有助于构建更强壮的防御。Frida hook 在 Java 层（ART bytecode 层面）工作，如果将证书验证逻辑迁移到 native 层（通过 JNI 调用 C/C++ 代码），hook 的难度会大幅提升——逆向工程师必须在二进制层面 patch 或 hook，而非简单替换 Java 方法实现。进一步的加固手段包括：

- **代码混淆（ProGuard/R8）**：使 Frida 脚本中的类名/方法名查找失效（`Java.use('okhttp3.CertificatePinner')` 会因混淆后的名称变化而失败）
- **完整性检测**：在运行时检测自身代码是否被 hook（检查方法指针是否被重定向）
- **Root/模拟器检测**：通过 Play Integrity API 或自定义检测逻辑拒绝在 Root/模拟器环境下运行
- **Native 层证书验证**：在 JNI 层调用 OpenSSL/BoringSSL 直接验证证书，绕过 Java TrustManager 机制

```java
// 更难被 Frida Hook 绕过的 Pinning 实现（使用 native 层）
// 在 JNI 层实现证书验证，增加逆向难度
// 使用 OkHttp CertificatePinner 配合代码混淆
OkHttpClient client = new OkHttpClient.Builder()
    .certificatePinner(new CertificatePinner.Builder()
        .add("api.example.com",
             "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
        .build())
    .build();
```

需要注意的是，SSL Pinning 只是深度防御的一环，不能作为唯一的安全保障。结合接口请求签名（防重放）、服务端异常行为检测（频率限制、User-Agent 指纹）等机制，才能构成有效的纵深防御体系。

## 小结

移动端抓包是安全研究的核心技能，需要根据平台（Android/iOS）、Root 状态和 SSL Pinning 实现选择合适的工具链。Android 的 VPN Service API 使得 PCAPdroid 成为无侵入性的明文流量捕获方案，其背后的 tun 虚拟接口机制与 VPN 客户端完全相同；Android 7.0 引入的分层 CA 信任变化（User CA 默认不受 targetSdkVersion≥24 的 App 信任）是现代移动端抓包的核心障碍，修改 `network_security_config.xml` 是最低侵入的绕过路径；`adb reverse` + mitmproxy 是 HTTPS 调试的黄金组合；iOS 的 rvictl 利用 RemoteVirtualInterface 机制提供官方的非越狱全流量捕获路径；SSL Pinning 的各类绕过（证书固定/公钥固定/CA 固定）对应不同的 Frida hook 目标，理解原理才能选择正确的工具。所有这些技术必须在明确授权范围内使用，仅用于自有 App 调试、授权安全审计或 CTF 靶场环境。
