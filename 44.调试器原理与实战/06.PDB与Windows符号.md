# 调试器原理与实战（6）· PDB与Windows符号

> [!abstract] TL;DR
> - **PDB 是什么**：微软私有的调试信息数据库（Program Database），由 MSVC/Clang-cl 生成，独立于 PE 以 `.pdb` 文件形式存在。与 DWARF 嵌入二进制不同，PDB **完全外置**——PE 里只留一枚"指针"（RSDS 记录），调试器凭 GUID + Age 去匹配并加载对应 PDB。
> - **PE 指向 PDB 的路径**：`DataDirectory[6]` → `IMAGE_DEBUG_DIRECTORY[]` → `Type == IMAGE_DEBUG_TYPE_CODEVIEW (2)` 条目 → RSDS 块（含 GUID + Age + 路径字符串）。详见 [[13.PE文件详解/14-详解PE文件(十四)：调试数据.md]]。
> - **符号服务器**：微软提供 `https://msdl.microsoft.com/download/symbols`，`_NT_SYMBOL_PATH` 控制搜索链；调试器先查本地缓存再按哈希路径下载。
> - **两类符号**：公开符号（函数名 + 全局地址，strip 后的 stripped PDB）vs 私有符号（完整类型 + 局部变量 + 行号，内部使用的完整 PDB）。
> - **读取 API**：Windows 上两种途径——`dbghelp.dll`（高层，调试器快速接入）和 DIA SDK（COM，完整语义查询）。
> - **三平台对照**：Linux/macOS 用 DWARF + `.debug_*` 节，Windows 用 PDB + 符号服务器，是完全独立的两套体系——但目标相同：把地址翻译回源码。

本篇紧接 [[05.调试信息DWARF]]，将视角从 ELF/DWARF 世界切换到 Windows/PDB 世界。两篇合读，可以在脑中建立"同一个调试需求在两套生态里如何实现"的完整对照图。

## 概述与定位

### 为什么 Windows 有独立的 PDB 体系

DWARF 把调试信息**嵌入**目标文件（`.o`/`.so`/ELF 可执行），一个文件"全量自包含"。这让发布带调试信息的二进制变得简单——但代价是：调试节体积巨大（大型 C++ 项目 debug build 的 `.debug_info` 可达数百 MB），而且一旦发布就很难"事后补充类型信息"。

微软的 PDB 设计走了另一条路：

1. **物理分离**：PDB 与 PE 完全是两个文件，通过 PE 内嵌的 GUID + Age 在运行时动态匹配。
2. **增量构建友好**：PDB 是一个 MSF（Multi-Stream File）容器，内部以流（stream）为单位组织，增量编译只追加/替换变化的流，不重写整体。
3. **符号服务器**：微软为 Windows 系统模块（`ntdll.dll`、`kernel32.dll`…）维护公开符号服务器，任何调试器都可在线下载——这在 DWARF 体系里没有对等的生态。

这也意味着：调试一个 Windows 程序，**仅靠 PE 本体看不到变量名**；调试器必须额外加载配套 PDB。

## 原理与机制

### 全局解析链：从 PE 到 PDB 到变量

```mermaid
graph TD
  PE["PE 可执行文件<br/>(myapp.exe)"] -->|DataDirectory[6]| DD["IMAGE_DEBUG_DIRECTORY[]<br/>（调试目录数组）"]
  DD -->|Type == 2 (CODEVIEW)| RSDS["RSDS 数据块<br/>GUID: {xxxxxxxx-...}<br/>Age: 3<br/>Path: C:\\build\\myapp.pdb"]
  RSDS -->|GUID + Age 匹配| SYM["符号搜索链<br/>_NT_SYMBOL_PATH"]
  SYM -->|本地缓存命中| LOCAL["本地 PDB 缓存<br/>C:\\Symbols\\myapp.pdb\\<br/>&lt;GUID&gt;&lt;Age&gt;\\myapp.pdb"]
  SYM -->|未命中则请求| SERVER["符号服务器<br/>msdl.microsoft.com"]
  SERVER -->|下载| LOCAL
  LOCAL -->|DIA SDK / dbghelp| PDB["PDB 内容<br/>类型 · 符号 · 行号 · 模块"]
  PDB -->|地址查询| SRC["源码位置<br/>myapp.cpp:42 · 变量 x @ rbp-8"]
```

整条链的核心是**两次匹配**：

1. **PE → PDB 文件**：RSDS 里的 GUID（16 字节）+ Age（递增整数）与 PDB 文件头里的 GUID + Age 必须完全一致，差一位都不匹配。这防止了"用错版本的 PDB 调试"导致的地址错位。
2. **PDB 文件 → 调试器内存视图**：调试器（或 `dbghelp.dll`）通过 DIA SDK 读取 PDB 各流，建立地址→名称、行号、类型的索引。

## PE 的调试目录与 RSDS 记录

这一节是本篇与 [[13.PE文件详解/14-详解PE文件(十四)：调试数据.md]] 的交叉点，从调试器消费视角再过一遍关键路径。

### IMAGE_DEBUG_DIRECTORY 与 CODEVIEW 条目

PE 的可选头 `DataDirectory[6]`（`IMAGE_DIRECTORY_ENTRY_DEBUG`）指向 `IMAGE_DEBUG_DIRECTORY` 结构**数组**，每条目 28 字节：

```c
typedef struct _IMAGE_DEBUG_DIRECTORY {
    DWORD  Characteristics;    // 保留，0
    DWORD  TimeDateStamp;      // 构建时间戳
    WORD   MajorVersion;
    WORD   MinorVersion;
    DWORD  Type;               // ← 关键：类型枚举
    DWORD  SizeOfData;
    DWORD  AddressOfRawData;   // RVA
    DWORD  PointerToRawData;   // 文件偏移（静态解析用这个）
} IMAGE_DEBUG_DIRECTORY;
```

`Type` 为 `IMAGE_DEBUG_TYPE_CODEVIEW`（值 `2`）的条目，其数据块就是 CodeView 调试信息。现代 MSVC 生成的 CodeView 块几乎全是 **RSDS** 格式（VS 2005+，PDB 7.0），以 4 字节签名 `RSDS`（`0x53445352`）开头：

```c
// RSDS 数据块（紧跟 IMAGE_DEBUG_DIRECTORY.PointerToRawData）
struct RSDS_RECORD {
    DWORD  Signature;       // 'RSDS' = 0x53445352
    GUID   Guid;            // 16 字节，PE 与 PDB 配对标识
    DWORD  Age;             // 增量版本号（每次链接 +1）
    char   PdbFileName[1];  // 以 '\0' 结尾的 PDB 完整路径
};
```

`GUID` 是真正的"身份证"：编译器每次链接都生成新 GUID 写入 PE 和 PDB，保证它们是同一次构建产物。`Age` 用于后续增量更新（如 `/INCREMENTAL` 链接或 `/EDITANDCONTINUE`）——每次修改 PDB 内容但不重新生成 PE 时，Age 递增；调试器需要 GUID 相同且 Age 小于等于 PDB 的 Age 才认为匹配。

> [!warning] 安全提醒：PDB 路径泄露
> RSDS 里的 `PdbFileName` 常包含开发者机器用户名和内部路径（如 `C:\Users\alice\src\SecretProject\x64\Release\SecretProject.pdb`）。逆向分析时这是第一个要读的字段——它直接泄露项目名称、构建机器信息。正式发布前应用 `/PDBALTPATH` 链接选项替换为无意义路径，或彻底去除调试目录。

## PDB 文件格式：MSF 容器与内部流

PDB 文件是一个 **MSF（Multi-Stream File）** 容器，类似 FAT 文件系统的页面化结构——文件分为等大小的页面（page），流（stream）由若干不连续页面组成，通过流目录（Stream Directory）索引。

### MSF 结构概览

```text
PDB 文件（MSF 容器）
┌──────────────────────────────────────────┐
│  SuperBlock（第0页）                      │
│    Magic: "Microsoft C/C++ MSF 7.00\r\n\032DS\0\0\0"
│    PageSize / FreePageMap / PageCount     │
│    RootStreamSize / RootPageMap           │
├──────────────────────────────────────────┤
│  Stream 0：Old MSF Directory（保留）      │
│  Stream 1：PDB Info Stream                │
│    GUID / Age / 具名流名→流号映射         │
│  Stream 2：TPI（Type Info）               │
│    所有类型记录（结构体/枚举/函数签名…） │
│  Stream 3：DBI（Debug Info）              │
│    模块列表（.obj 文件）/ 节贡献表        │
│    全局符号索引 / 公开符号索引            │
│  Stream 4：Global Symbol（GS）            │
│  Stream 5：Public Symbol（PS）            │
│  Stream N…：各模块符号流（每个 .obj 一条）│
│  Named Stream "/names"：字符串池          │
│  Named Stream "/src/headerblock"：…       │
└──────────────────────────────────────────┘
```

### 关键流的职责

| 流 | 名称 | 存放内容 | 调试器用途 |
|---|---|---|---|
| 1 | PDB Info | GUID · Age · 具名流映射 | 匹配验证、版本检查 |
| 2 | TPI（Type Info） | 所有 CodeView 类型记录 | `print struct Foo` 展开成员 |
| 3 | DBI（Debug Info） | 模块列表、节贡献、公开/全局符号流号 | 地址→模块→符号 |
| GS | Global Symbol | 全局符号散列表（名字→地址） | 按名查全局变量/函数 |
| PS | Public Symbol | 公开符号（export 级别，含 decorated name） | 反汇编中的函数标签 |
| 模块流 | Module Symbol | 每个 .obj 的局部符号 + 行号 | 源码行 · 局部变量 |

### CodeView 记录类型概览

PDB 内的符号和类型以 **CodeView 记录**（CV record）格式编码，每条记录由 2 字节长度 + 2 字节类型码（`S_*`/`LF_*`）+ 载荷组成：

**符号记录（`S_*`，存于符号流）：**

| 类型码 | 名称 | 含义 |
|---|---|---|
| `S_PUB32` | Public symbol | 公开符号（装饰名 + 地址） |
| `S_GPROC32` | Global procedure | 全局函数（含类型索引 + 偏移） |
| `S_LPROC32` | Local procedure | 静态/文件域函数 |
| `S_GDATA32` | Global data | 全局变量 |
| `S_LDATA32` | Local data | 静态局部变量 |
| `S_REGREL32` | Register-relative | 寄存器相对局部变量（如 `rbp-8`） |
| `S_BLOCK32` | Block | 词法作用域块 |
| `S_INLINESITE` | Inline site | 内联函数实例 |

**类型记录（`LF_*`，存于 TPI 流）：**

| 类型码 | 名称 | 含义 |
|---|---|---|
| `LF_STRUCTURE` | Struct | 结构体定义（含字段列表引用） |
| `LF_ENUM` | Enum | 枚举类型 |
| `LF_POINTER` | Pointer | 指针类型 |
| `LF_PROCEDURE` | Procedure | 函数签名（参数类型 + 返回类型） |
| `LF_ARRAY` | Array | 数组类型 |
| `LF_FIELDLIST` | Field list | 结构体字段列表 |

这些记录类型与 DWARF 的 `DW_TAG_*` / `DW_AT_*` 体系平行，服务于相同目的（描述程序的类型和符号系统），但编码格式完全不同。

## 符号服务器

符号服务器（Symbol Server）是 Windows 调试生态里独有的机制，允许调试器在运行时**按需下载**系统模块的 PDB——这解决了一个实际痛点：你无法在自己的开发机上预先安装每个 `ntdll.dll` 版本对应的 PDB。

### _NT_SYMBOL_PATH

调试器（WinDbg / Visual Studio）读取环境变量 `_NT_SYMBOL_PATH` 来确定符号搜索策略。标准格式：

```
srv*<本地缓存路径>*<符号服务器URL>
```

典型设置：

```cmd
set _NT_SYMBOL_PATH=srv*C:\Symbols*https://msdl.microsoft.com/download/symbols
```

可以串联多个源（用 `;` 分隔），调试器按顺序查找：

```
srv*C:\Symbols*https://msdl.microsoft.com/download/symbols;C:\myproject\symbols
```

### 符号服务器的哈希路径约定

微软符号服务器使用固定的目录层级来组织文件：

```
<缓存根>\<PDB文件名>\<GUID(无连字符,大写)><Age>\<PDB文件名>
```

例如：

```
C:\Symbols\ntdll.pdb\B2614B6B5CEDB98AC6BEFE2F09EB26EE1\ntdll.pdb
```

HTTP 下载 URL 同构：

```
https://msdl.microsoft.com/download/symbols/ntdll.pdb/B2614B6B5CEDB98AC6BEFE2F09EB26EE1/ntdll.pdb
```

调试器拿到 PE 里的 GUID + Age，直接拼出这个路径做 GET 请求，若 HTTP 200 则下载并缓存；若 404 则该符号不公开。

### WinDbg 实操：符号路径与重新加载

```windbg
; 查看当前符号路径
.sympath

; 设置符号路径（加入微软公开服务器）
.sympath srv*C:\Symbols*https://msdl.microsoft.com/download/symbols

; 重新加载所有模块符号
.reload /f

; 仅重载指定模块
.reload /f ntdll.dll

; 检查模块符号加载状态
lm v m ntdll
```

> [!warning] 示例输出为示意
> WinDbg 命令及输出为代表性示意，非本机实跑。实际结果依 WinDbg 版本、网络状态和目标进程而异。


## DIA SDK 与 dbghelp.dll：读取 PDB 的两条路

Windows 提供两套 API 来消费 PDB，面向不同的使用场景。

### dbghelp.dll：高层调试辅助库

`dbghelp.dll` 是 Windows 随附的调试辅助库，封装了符号加载、栈回溯、符号查找等高层操作，调试器和崩溃处理程序的首选：

```c
#include <windows.h>
#include <dbghelp.h>
#pragma comment(lib, "dbghelp.lib")

// 初始化符号引擎
SymInitialize(GetCurrentProcess(), "srv*C:\\Symbols*https://msdl.microsoft.com/download/symbols", TRUE);

// 按地址查符号
SYMBOL_INFO_PACKAGE sym = {};
sym.si.SizeOfStruct = sizeof(SYMBOL_INFO);
sym.si.MaxNameLen   = MAX_SYM_NAME;
DWORD64 displacement = 0;
SymFromAddr(GetCurrentProcess(), address, &displacement, &sym.si);
printf("符号名: %s  偏移: +0x%llx\n", sym.si.Name, displacement);

// 按地址查源文件行号
IMAGEHLP_LINE64 line = { sizeof(IMAGEHLP_LINE64) };
DWORD lineDisp = 0;
SymGetLineFromAddr64(GetCurrentProcess(), address, &lineDisp, &line);
printf("源文件: %s:%lu\n", line.FileName, line.LineNumber);
```

`dbghelp` 内部调用 DIA SDK 完成实际 PDB 解析，对调用方屏蔽了 MSF/CodeView 细节。

### DIA SDK：完整语义查询

DIA（Debug Interface Access）SDK 是微软提供的 COM 库（`msdia140.dll` 等），提供对 PDB 内容的完整访问，适合静态分析工具、反汇编器等需要深度查询类型系统的场景：

```cpp
#include <dia2.h>

CComPtr<IDiaDataSource> pSource;
CoCreateInstance(CLSID_DiaSource, nullptr, CLSCTX_INPROC_SERVER,
                 IID_IDiaDataSource, (void**)&pSource);

// 加载 PDB
pSource->loadDataFromPdb(L"C:\\build\\myapp.pdb");

CComPtr<IDiaSession> pSession;
pSource->openSession(&pSession);

CComPtr<IDiaSymbol> pGlobal;
pSession->get_globalScope(&pGlobal);

// 枚举所有函数
CComPtr<IDiaEnumSymbols> pFuncs;
pGlobal->findChildren(SymTagFunction, nullptr, nsNone, &pFuncs);

IDiaSymbol* pFunc = nullptr;
ULONG fetched = 0;
while (SUCCEEDED(pFuncs->Next(1, &pFunc, &fetched)) && fetched) {
    BSTR name;
    pFunc->get_name(&name);
    DWORD rva;
    pFunc->get_relativeVirtualAddress(&rva);
    wprintf(L"函数: %s  RVA: 0x%08X\n", name, rva);
    SysFreeString(name);
    pFunc->Release();
}
```

DIA SDK 的 `IDiaSymbol` 接口可以查询任意 CodeView 记录的所有属性——类型、行号、父作用域、子符号——等同于对 PDB 做完整的语义遍历。

### 两条路对比

| 维度 | dbghelp.dll | DIA SDK |
|---|---|---|
| 接口风格 | 过程式 C API | COM/C++ |
| 部署要求 | 系统自带 | 需 `msdia*.dll` |
| 功能范围 | 符号解析 + 栈回溯 + 模块管理 | PDB 完整内容访问 |
| 典型用途 | 调试器、崩溃处理 | 静态分析工具、反汇编器 |
| 线程安全 | 单进程单句柄（需加锁） | 会话级隔离 |

## 公开符号 vs 私有符号

微软向公众发布 Windows 系统模块的 PDB，但不发布完整版本——这里存在**公开符号（public symbols）**与**私有符号（private symbols）**的重要区分。

### 私有符号（Private / Full PDB）

内部开发时产出的完整 PDB，包含：

- 所有函数（含 `static` 函数、lambda）的名称和地址范围
- 所有局部变量、参数的名称 + 类型 + 栈/寄存器位置
- 完整的类型系统（TPI 流）：结构体字段、虚函数表布局
- 源文件行号映射（精确到语句级）
- 内联函数展开信息（`S_INLINESITE`）

私有符号让调试器可以做 `print x.member`、`break MyClass::method`，是完整调试体验的基础。

### 公开符号（Stripped / Public PDB）

通过 `pdbcopy.exe` 或链接器 `/PDBSTRIPPED` 选项生成，仅保留：

- 公开函数的装饰名（decorated/mangled name）与地址
- 导出符号的名称

**不包含**：局部变量、类型定义、源码行号、内联信息。

微软公开服务器上的 PDB 均为 stripped 版本，足以让调试器在调用栈里显示函数名，但无法展开结构体成员或查看局部变量。

### strip 操作

```cmd
; 链接时同时生成完整 PDB 和 stripped PDB
link /DEBUG /PDB:full.pdb /PDBSTRIPPED:public.pdb myapp.obj

; 事后用 pdbcopy 剥离
pdbcopy full.pdb public.pdb -p
```

> [!warning] 示例输出为示意
> 命令行为代表性示意，`pdbcopy.exe` 在 Windows SDK 中随附。

## PDB vs DWARF：完整对照

| 维度 | PDB（Windows） | DWARF（Linux/macOS） |
|---|---|---|
| **存储位置** | 独立 `.pdb` 文件，PE 内只留 GUID 指针 | 嵌入 ELF/Mach-O 的 `.debug_*` 节（或 Split DWARF `.dwo`） |
| **格式类型** | 微软私有 MSF 容器 + CodeView 记录 | 公开标准（DWARF 2/3/4/5），LLVM/GCC 均实现 |
| **类型信息** | TPI 流中的 `LF_*` 记录 | `.debug_info` 中的 `DW_TAG_structure_type` 等 DIE |
| **符号信息** | GS/PS/模块流中的 `S_*` 记录 | `.debug_info` 中的 `DW_TAG_subprogram` / `DW_TAG_variable` |
| **行号映射** | 模块流中的行号子流（偏移 + 行号对） | `.debug_line` 行号状态机字节码 |
| **位置表达式** | `S_REGREL32`（简单寄存器相对） | `DW_OP_*` 表达式（图灵完备，可描述复杂位置） |
| **栈展开** | `.pdata`/`.xdata` 节（SEH unwind codes）| `.debug_frame` / `.eh_frame` CFI 表 |
| **符号分发** | 符号服务器（`_NT_SYMBOL_PATH` + HTTP） | 无标准生态，靠发行版 debuginfo 包或 debuginfod |
| **增量更新** | Age 字段 + MSF 增量写 | 无，重新编译生成新文件 |
| **读取 API** | `dbghelp.dll` / DIA SDK (COM) | `libdwarf` / `libelf` / LLVM `DWARFContext` |
| **公开 vs 私有** | stripped PDB（公开）vs full PDB（内部）| 无正式 strip 机制（`strip --only-keep-debug` 属工具层） |

---

## 三平台对照

### Linux：DWARF + debuginfod

Linux 没有符号服务器生态，但 **debuginfod**（由 elfutils 提供）正在填补这个空缺——发行版（Fedora、Ubuntu 等）部署 debuginfod 服务端，本地 GDB/LLDB 通过 HTTP 按 Build ID 下载对应的 debuginfo 包：

```bash
# 配置 debuginfod 服务端地址
export DEBUGINFOD_URLS="https://debuginfod.fedoraproject.org"

# GDB 自动从 debuginfod 下载符号
$ gdb /usr/bin/python3
(gdb) run
# GDB 输出：Downloading separate debug info for /usr/lib/...
```

> [!warning] 示例输出为示意
> 命令行及 GDB 输出为代表性示意，非本机实跑。

Linux 上不存在"公开符号 vs 私有符号"的正式机制，通常靠发行版分别打包 `<package>-debuginfo` RPM/DEB 提供完整 DWARF，应用程序开发者自行决定是否 strip。

### macOS：Mach-O + dSYM

macOS/iOS 采用不同于 Windows 的外置方案——**dSYM（DWARF Symbol Map）** bundle：

- 编译器生成 DWARF 嵌入目标文件；
- `dsymutil` 把散落在各 `.o` 里的 DWARF 聚合为独立的 `.dSYM/Contents/Resources/DWARF/<binary>` 文件；
- 通过 **Build UUID**（类似 GUID）匹配，Xcode/LLDB 自动关联。

```bash
# 生成 dSYM bundle
dsymutil myapp -o myapp.dSYM

# LLDB 加载（通常自动，也可手动）
(lldb) add-dsym myapp.dSYM

# 查看 Build UUID（与 dSYM 内 UUID 匹配）
dwarfdump --uuid myapp
```

> [!warning] 示例输出为示意
> macOS 工具命令为代表性示意，非本机实跑（本机为 Windows 环境）。

macOS 没有 Windows 那样的公开符号服务器——Apple 系统框架的调试信息随 Xcode 安装，不走 HTTP 下载。

### 三平台快速对比

| 维度 | Linux | macOS | Windows |
|---|---|---|---|
| 调试信息格式 | DWARF（嵌入 ELF） | DWARF（聚合进 dSYM） | PDB（独立文件） |
| 外置机制 | Split DWARF `.dwo` / debuginfod | dSYM bundle | PDB + 符号服务器 |
| 匹配标识 | Build ID（ELF note） | Build UUID（Mach-O LC_UUID） | GUID + Age（RSDS） |
| 符号下载 | debuginfod（HTTP） | Xcode 本地随附 | msdl.microsoft.com（HTTP） |
| 类型系统读取 | libdwarf / lldb / gdb | lldb / dwarfdump | DIA SDK / dbghelp |

## 数据结构详解

### RSDS 记录的字节布局

```text
偏移    大小    字段           说明
0x00    4       Signature      'R','S','D','S'（0x53445352，小端）
0x04   16       Guid           标准 GUID（DWORD + WORD + WORD + 8 BYTE）
0x14    4       Age            链接时递增；PDB 内 Age 须 >= PE 内 Age
0x18    ?       PdbFileName    '\0' 结尾的 ANSI 字符串（完整路径）
```

### GUID 字节序注意事项

`GUID` 在 PE 和 PDB 中的存储字节序遵循 Windows 的 `GUID` 结构约定：

```c
typedef struct _GUID {
    DWORD Data1;   // 4 字节，小端
    WORD  Data2;   // 2 字节，小端
    WORD  Data3;   // 2 字节，小端
    BYTE  Data4[8];// 8 字节，大端（网络序）
} GUID;
```

符号服务器路径里的 GUID 字符串将 `Data1/2/3` 按小端解读后以大写十六进制输出（无连字符），再追加 Age：`{AABBCCDD-EEFF-0011-2233-445566778899}` + Age `1` → 路径 `DDCCBBAAFFEE11003344556677889901`（注意 Data1/2/3 反序）。

实际工具（WinDbg、`symchk`）会处理这个细节；手动拼路径时需注意字节序。

## 实操

### 用 dumpbin 验证 RSDS

```cmd
dumpbin /headers C:\Windows\System32\ntdll.dll | findstr /i "pdb"
```

> [!warning] 示例输出为示意

```text
C:\Symbols\ntdll.pdb\B2614B6B5CEDB98AC6BEFE2F09EB26EE1\ntdll.pdb
```

`dumpbin /headers` 的 `Debug Directories` 节会显示完整 RSDS 信息，包括路径和 GUID。

### WinDbg 调试流程示例

```windbg
; 1. 启动 WinDbg 并打开可执行文件
; windbg.exe -z myapp.exe   （分析 dump）
; windbg.exe myapp.exe       （实时调试）

; 2. 配置符号路径
.sympath srv*C:\Symbols*https://msdl.microsoft.com/download/symbols;C:\build\myapp.pdb

; 3. 强制重新加载符号
.reload /f

; 4. 验证符号是否成功加载
lm v m myapp

; 5. 按名称解析地址
x myapp!main
x myapp!MyClass::*

; 6. 查看符号 + 原始地址的双向映射
ln 0x00401000    ; 地址 → 最近符号
u myapp!main     ; 反汇编函数（带符号标注）
```

> [!warning] 示例输出为示意
> WinDbg 命令及输出为代表性示意，非本机实跑（本机无目标进程）。

### symchk 验证符号匹配

`symchk.exe`（Windows SDK 工具）可批量检查 PE 与 PDB 的 GUID 匹配状态：

```cmd
symchk /r C:\Windows\System32 /s srv*C:\Symbols*https://msdl.microsoft.com/download/symbols
```

> [!warning] 示例输出为示意

```text
SYMCHK: myapp.exe          PASSED - C:\build\myapp.pdb
SYMCHK: helper.dll         FAILED  - No symbols found
```

`PASSED` 表示 GUID + Age 匹配，`FAILED` 表示无 PDB 或 GUID 不一致。

## 陷阱与常见问题

### 陷阱 1：GUID 匹配失败 —— "wrong PDB"

调试器报 `PDB not found` 或 `Symbols not loaded`，最常见原因是 PE 与 PDB 的 GUID 不一致（拷错了 PDB，或 PDB 是其他构建版本）。

诊断步骤：
1. `dumpbin /headers myapp.exe` 看 PE 里的 GUID。
2. 用 `pdbutil.exe` 或 DIA SDK 读 PDB 的 GUID（PDB Info 流）。
3. 两者逐字节对比。

### 陷阱 2：符号路径优先级

`_NT_SYMBOL_PATH` 按分号分隔从左到右搜索，第一个命中就停止。如果本地缓存有旧版 PDB 且 GUID 不一致，会被跳过而不报错。用 `.sympath+` 追加而不是覆盖，再用 `.reload /f` 强制重试。

### 陷阱 3：/INCREMENTAL 导致 Age 递增

Visual Studio 默认开启增量链接（`/INCREMENTAL`）。每次增量链接 PDB 的 Age +1 但 GUID 不变；PE 里的 Age 也同步更新。调试器要求 `PE.Age <= PDB.Age` 且 GUID 相同——如果把旧 PE 配新 PDB（Age 更大）通常能加载，但反过来（旧 PDB、新 PE）则失败。

### 陷阱 4：公开符号不含局部变量

用微软符号服务器下载的 stripped PDB 无法显示局部变量和结构体成员。调试 Windows 内核/系统 DLL 时，`dt`（display type）命令在 stripped PDB 下只能显示有限信息；需要完整私有 PDB 才能展开结构体（通常需要 Microsoft 内部访问权限或第三方逆向研究）。

---

## 小结

PDB 是 Windows 调试生态的基石——PE 通过 RSDS 记录（GUID + Age）指向外部 `.pdb` 文件，调试器借符号服务器按需下载并缓存，最终通过 DIA SDK 或 `dbghelp.dll` 消费 MSF 容器内的 CodeView 类型/符号/行号记录。

与 DWARF（嵌入二进制、公开标准、图灵完备的位置表达式）相比，PDB 走的是"外置 + 符号服务器分发"路线，在大规模 Windows 生态下极其实用——特别是系统模块的公开符号服务器，让任何人都能在没有源码的情况下得到体面的调用栈。两套体系的核心目标完全相同：把运行时地址翻译回源码层的名字。
