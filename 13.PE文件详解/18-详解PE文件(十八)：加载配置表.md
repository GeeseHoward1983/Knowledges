# 详解PE文件(十八)：加载配置表

> 来源：[CSDN 原文](https://blog.csdn.net/geesehoward20000/article/details/154744537)　｜　发布：2025-12-02　｜　合集《PE文件详解》第 18/26 篇

> [!tip] 一句话核心
> 加载配置表（Load Configuration Directory）是 [[07-详解PE文件(七)：数据目录|数据目录]] 第 11 项（索引 10）。它的核心价值不在于描述文件格式，而在于**向操作系统加载器声明该 PE 文件启用了哪些运行时安全加固机制**——从最早的 `/GS` 安全 Cookie 到 Windows 10 引入的 CFG 控制流防护，所有加固特性的地址和参数都集中在这张表里。

> [!info] 速查
> - **结构体**：`IMAGE_LOAD_CONFIG_DIRECTORY32` / `IMAGE_LOAD_CONFIG_DIRECTORY64`
> - **数据目录索引**：10（第 11 条目）
> - **位置**：[[06-详解PE文件(六)：可选头|可选头]] → DataDirectory[10].VirtualAddress 指向
> - **关键字段**：`SecurityCookie`（/GS）、`SEHandlerTable/Count`（SafeSEH）、`GuardCF*`（CFG）、`GuardFlags`
> - **大小**：随 Windows 版本持续扩展，由首字段 `Size` 声明实际长度
> - **编译选项**：`/GS`（安全 Cookie）、`/SafeSEH`、`/Guard:CF`（CFG）

加载配置表是 PE 文件里一张"随时代生长"的结构——早期它只有寥寥几个内存管理字段，随着 Windows 安全机制的演进，每隔几个版本就会在结构末尾追加新的加固字段。理解它，就是理解 Windows 平台几十年来漏洞缓解技术的演进史。

本篇涉及的数据目录概念详见 [[07-详解PE文件(七)：数据目录]]，数据目录在 [[06-详解PE文件(六)：可选头|可选头]] 末尾给出 RVA 与大小。上一篇 [[17-详解PE文件(十七)：TLS表]] 介绍了线程局部存储表，同样位于数据目录中。

## 数据结构定义

### 32 位版本（IMAGE_LOAD_CONFIG_DIRECTORY32）

```c
typedef struct _IMAGE_LOAD_CONFIG_DIRECTORY32 {

    DWORD   TimeDateStamp;                  // 时间戳
    WORD    MajorVersion;                   // 主版本号
    WORD    MinorVersion;                   // 次版本号

    DWORD   GlobalFlagsSet;                 // 全局标志设置
    DWORD   CriticalSectionDefaultTimeout;  // 临界区默认超时
    DWORD   DeCommitFreeBlockThreshold;     // 释放块阈值
    DWORD   DeCommitTotalFreeThreshold;     // 总释放阈值
    DWORD   LockPrefixTable;                // 锁前缀表地址
    DWORD   MaximumAllocationSize;          // 最大分配大小
    DWORD   VirtualMemoryThreshold;         // 虚拟内存阈值
    DWORD   ProcessHeapFlags;               // 进程堆标志
    DWORD   ProcessAffinityMask;            // 进程亲和性掩码
    WORD    CSDVersion;                     // CSD版本
    WORD    DependentLoadFlags;             // 依赖加载标志
    DWORD   EditList;                       // 编辑列表地址
    DWORD   SecurityCookie;                 // 安全Cookie地址
    DWORD   SEHandlerTable;                 // SE异常处理表地址
    DWORD   SEHandlerCount;                 // SE异常处理程序数量

    DWORD   GuardCFCheckFunctionPointer;

    DWORD   GuardCFFunctionCount;
    DWORD   GuardFlags;

    IMAGE_LOAD_CONFIG_CODE_INTEGRITY CodeIntegrity;

    DWORD   GuardAddressTakenIatEntryTable;
    DWORD   GuardAddressTakenIatEntryCount;
    DWORD   GuardLongJumpTargetTable;
    DWORD   GuardLongJumpTargetCount;

    DWORD   DynamicValueRelocTable;
    DWORD   CHPEMetadataPointer;

    DWORD   GuardRFFailureRoutine;

```

### PE32 vs PE32+ 字段宽度对比

| 字段类别 | PE32（32位） | PE32+（64位） |
|----------|-------------|--------------|
| 大小/版本/标志等非地址字段 | `DWORD` / `WORD` | 不变，保持 `DWORD` / `WORD` |
| 地址/指针类字段（如 `SecurityCookie`、`LockPrefixTable`） | `DWORD`（4 字节） | `ULONGLONG`（8 字节） |
| 阈值类字段（`DeCommitFreeBlockThreshold` 等） | `DWORD` | `ULONGLONG` |
| 结构体总基础大小（不含扩展字段） | `0x48`（约） | `0x70`（约） |

> [!note] Size 字段是版本控制的关键
> 结构体首字段 `Size` 并不是固定值，而是**当前二进制实际使用的字节数**。加载器读到这个值后，只解析 `[0, Size)` 范围内的字段，超出部分视为不存在。这是微软在不破坏向后兼容性的前提下持续扩展结构体的惯用手法——老程序在新系统上运行时，加载器能识别它的结构版本，不会越界读取不存在的字段。

## 各字段详解

### 基本信息字段

| 字段 | 偏移（32位） | 大小 | 说明 |
|------|-------------|------|------|
| `Size` | `0x00` | 4 | 结构体实际大小，加载器据此判断版本 |
| `TimeDateStamp` | `0x04` | 4 | 结构体时间戳（通常为 0） |
| `MajorVersion` | `0x08` | 2 | 主版本号 |
| `MinorVersion` | `0x0A` | 2 | 次版本号 |
| `GlobalFlagsClear` | `0x0C` | 4 | 进程启动时要清除的全局调试标志位 |
| `GlobalFlagsSet` | `0x10` | 4 | 进程启动时要设置的全局调试标志位 |
| `CriticalSectionDefaultTimeout` | `0x14` | 4 | 临界区等待默认超时（毫秒，0 = 无限） |

### 内存管理字段

这组字段是加载配置表最早期的功能——允许编译器向加载器提示该进程的堆内存管理偏好。在现代系统中，这些字段通常保持为 0（使用系统默认值）。

| 字段 | 说明 |
|------|------|
| `DeCommitFreeBlockThreshold` | 单块连续空闲内存超过此阈值时归还物理页 |
| `DeCommitTotalFreeThreshold` | 堆总空闲量超过此阈值时触发 decommit |
| `MaximumAllocationSize` | 单次分配上限（0 = 无限制） |
| `VirtualMemoryThreshold` | 超过此大小的分配走大块路径 |
| `ProcessHeapFlags` | 传递给 `HeapCreate` 的标志 |
| `ProcessAffinityMask` | CPU 亲和性掩码（0 = 不限制） |
| `LockPrefixTable` | x86 LOCK 前缀指令地址表（多处理器优化） |

### 安全加固字段

这是加载配置表最核心的部分，也是它随 Windows 版本不断扩展的主要驱动力。

```text
安全字段在结构体中的分布（以 32 位为例，示意偏移）

[0x00] Size ─────── 版本控制锚点
[0x40] SecurityCookie ─── /GS 安全 Cookie 变量地址
[0x44] SEHandlerTable ─── SafeSEH 处理器函数表 RVA 列表
[0x48] SEHandlerCount ─── SafeSEH 处理器数量
      （以上为早期 Windows 引入）
      ─────────── Windows 10 1607 后追加 ───────────
[0x4C] GuardCFCheckFunctionPointer ─── CFG 检查函数指针地址
[0x50] GuardCFDispatchFunctionPointer ── CFG 分发函数指针地址
[0x54] GuardCFFunctionTable ─── CFG 合法目标函数列表 RVA
[0x58] GuardCFFunctionCount ── CFG 合法目标函数数量
[0x5C] GuardFlags ─────────── 各加固特性的开关位图
```

## 安全特性详解

### /GS — 安全 Cookie（缓冲区溢出保护）

`/GS` 是 Visual C++ 编译器的"栈守护"选项（默认开启）。其原理：在函数入口将一个随机值（Cookie）压入栈，函数返回前验证 Cookie 未被篡改——若被改写，说明发生了栈溢出，立即调用 `__report_gsfailure` 终止进程。

```text
栈帧布局（启用 /GS 后）
┌──────────────────────────────┐  高地址（调用方栈）
│  返回地址（Return Address）   │  ← 攻击者想覆盖的目标
├──────────────────────────────┤
│  Security Cookie（随机值）    │  ← 攻击者必须先覆盖这里
├──────────────────────────────┤     函数返回前验证此值
│  局部变量 / 缓冲区            │  ← 溢出从这里开始
└──────────────────────────────┘  低地址（当前帧）
```

- `SecurityCookie` 字段：指向进程 `.data` 段中存放 Cookie 实际值的**变量地址**（VA，非 RVA）。加载器在进程启动时用随机值初始化它。
- 每个启用 `/GS` 的函数，编译器会在入口插入 `xor eax, [__security_cookie]; push eax`，返回前执行 `__security_check_cookie`。

> [!warning] 逆向与安全提醒
> 在逆向分析时，`SecurityCookie` 的值就是进程中 Cookie 随机化的基准地址。对该地址的读写访问往往是 exploit 开发的重要目标；IDA/Ghidra 可通过此 VA 定位 Cookie 变量，从而跟踪溢出检测代码路径。

### SafeSEH — 结构化异常处理保护

`SEHandlerTable` 和 `SEHandlerCount` 一起构成了 **SafeSEH** 机制的 PE 侧数据：

- `SEHandlerTable`：合法 SEH 处理程序的 **RVA 列表**（已排序，方便二分查找）。
- `SEHandlerCount`：列表中的处理程序数量。

Windows 加载器（以及内核的异常分发路径）在调用 SEH 处理程序前会验证：目标处理程序地址是否在该表中。不在表中的处理程序不会被执行，从而阻断了经典的 **SEH 覆盖攻击**（将 `EXCEPTION_REGISTRATION` 的 `Handler` 字段覆写为 shellcode）。

> [!note] SafeSEH 仅对 32 位 PE 有意义
> 64 位 Windows 使用 **基于表的异常处理**（通过 [[11-详解PE文件(十一)：异常表|异常表]] 中的 `RUNTIME_FUNCTION` 记录），彻底抛弃了栈上链式 SEH 结构，不再需要 SafeSEH。`SEHandlerTable/Count` 在 64 位结构体中虽然字段仍在，但实际为 0。

### CFG — 控制流防护（Control Flow Guard）

CFG 是 Windows 8.1/10 引入的硬件辅助 **间接调用白名单**机制，用于对抗 ROP（Return-Oriented Programming）和 JOP（Jump-Oriented Programming）攻击。

```text
CFG 工作流程

编译阶段（/Guard:CF）
  ─────────────────────────────────────────
  编译器扫描所有间接调用点（call [reg]、call [mem]）
  将合法跳转目标函数加入 GuardCFFunctionTable
  ↓
  生成 __guard_check_icall_ptr / __guard_dispatch_icall_fptr
  插入到每个间接调用前
  ─────────────────────────────────────────

运行时（Windows 加载器 + 内核）
  ─────────────────────────────────────────
  加载器读取 GuardCFFunctionTable，
  构建"合法目标位图"（每 16 字节 1 bit）
  ↓
  每次间接 call/jmp 触发前，
  __guard_check_icall 查位图 → 地址合法则放行，否则终止进程
  ─────────────────────────────────────────
```

相关字段一览：

| 字段 | 说明 |
|------|------|
| `GuardCFCheckFunctionPointer` | 指向 `__guard_check_icall_fptr` 变量的地址（VA），加载器填入实际检查函数 |
| `GuardCFDispatchFunctionPointer` | 指向 `__guard_dispatch_icall_fptr` 变量的地址（VA） |
| `GuardCFFunctionTable` | 合法间接调用目标函数的 RVA 列表起始地址（RVA） |
| `GuardCFFunctionCount` | 列表中函数条目数量 |
| `GuardFlags` | 各加固特性的能力位图（见下表） |

`GuardFlags` 常见标志位：

| 标志位 | 含义 |
|--------|------|
| `0x00000100` | `IMAGE_GUARD_CF_INSTRUMENTED`：程序已插入 CFG 检查代码 |
| `0x00000200` | `IMAGE_GUARD_CFW_INSTRUMENTED`：写入目标也受保护 |
| `0x00000400` | `IMAGE_GUARD_CF_FUNCTION_TABLE_PRESENT`：GuardCFFunctionTable 有效 |
| `0x00000800` | `IMAGE_GUARD_SECURITY_COOKIE_UNUSED`：/GS Cookie 未使用 |
| `0x00001000` | `IMAGE_GUARD_PROTECT_DELAYLOAD_IAT`：延迟导入表只读保护 |
| `0x00004000` | `IMAGE_GUARD_RF_INSTRUMENTED`：栈指针完整性检查（RetpolineFlow） |
| `0x00010000` | `IMAGE_GUARD_CF_LONGJUMP_TABLE_PRESENT`：longjmp 目标表有效 |

## 安全加固特性一览表

| 特性 | 编译选项 | 相关字段 | 防护目标 | 引入时机 |
|------|----------|----------|----------|----------|
| 栈 Cookie（/GS） | `/GS` | `SecurityCookie` | 栈缓冲区溢出 → 返回地址覆写 | Windows XP SP2 |
| SafeSEH | `/SafeSEH` | `SEHandlerTable`, `SEHandlerCount` | SEH 链覆写（32位） | Windows XP SP2 |
| 控制流防护 CFG | `/Guard:CF` | `GuardCF*`, `GuardFlags` | 间接调用劫持（ROP/JOP） | Windows 8.1 Update 3 |
| 代码完整性 | 链接器自动 | `CodeIntegrity` | 代码段哈希校验 | Windows 10 1703 |
| 地址取用 IAT 保护 | `/Guard:CF` | `GuardAddressTaken*` | IAT 地址泄露缓解 | Windows 10 1903 |
| Long Jump 表 | `/Guard:CF` | `GuardLongJumpTarget*` | longjmp 目标合法性 | Windows 10 1903 |
| 栈指针完整性（RF） | `/Guard:ehcont` | `GuardRF*` | 异常展开时 RSP 篡改 | Windows 10 20H1 |
| Enclave 配置 | SDK 相关 | `EnclaveConfigurationPointer` | VBS Enclave 元数据 | Windows 11 |

> [!important] 加固特性叠加原则
> 上表中的特性并非互斥，现代安全编译的 PE 通常**同时启用多项**。`GuardFlags` 字段就是这些特性的"开关位图"，逆向分析时检查这个字段能快速了解目标程序启用了哪些防护层，从而评估绕过难度。

## 版本演进：结构随 Windows 扩展的历程

```text
加载配置表 Size 值随 Windows 版本的增长（32 位，示意）

Windows XP   ──────────── 0x40 ─── 基本内存管理字段
Windows Vista ──────────── 0x48 ─── + SecurityCookie
Windows 7    ──────────── 0x48 ─── + SEHandlerTable/Count
Windows 8.1  ──────────── 0x5C ─── + GuardCF 基础字段
Windows 10 RS1 (1607) ─── 0x70 ─── + GuardFlags、CodeIntegrity 前导
Windows 10 RS3 (1703) ─── 0x78 ─── + CodeIntegrity（完整）
Windows 10 19H1 (1903) ── 0x88 ─── + GuardAddressTaken*、GuardLongJump*
Windows 10 20H1 ────────── 0xA0 ─── + GuardRF*、DynamicValueReloc*
Windows 10 21H1 ────────── 0xA8 ─── + GuardRFVerifyStackPointer*
Windows 11      ────────── 0xB0 ─── + EnclaveConfigurationPointer
```

> [!note] 向后兼容的诀窍
> 老程序（小 `Size`）运行在新 Windows 上：加载器只读取 `[0, Size)` 范围，超出部分当作"该特性未启用"；新程序（大 `Size`）运行在老 Windows 上：加载器读完自己能识别的范围后停止，不越界——双向兼容通过首字段一个 `DWORD` 优雅实现。

## 实战：dumpbin 查看加载配置表

`dumpbin /loadconfig` 是查看加载配置表最直接的工具。典型输出：

> [!example] dumpbin /loadconfig 输出示例
> ```
> Load Configuration Directory:
>   Size:                           00000048
>   TimeDateStamp:                  00000000
>   MajorVersion:                   0000
>   MinorVersion:                   0000
>   GlobalFlagsClear:               00000000
>   GlobalFlagsSet:                 00000000
>   CriticalSectionDefaultTimeout:  00000000
>   DeCommitFreeBlockThreshold:     00000000
>   DeCommitTotalFreeThreshold:     00000000
>   LockPrefixTable:                00000000
>   MaximumAllocationSize:          00000000
>   VirtualMemoryThreshold:         00000000
>   ProcessHeapFlags:               00000000
>   ProcessAffinityMask:            00000000
>   CSDVersion:                     0000
>   DependentLoadFlags:             0000
>   EditList:                       00000000
>   SecurityCookie:                 00401000
>   SEHandlerTable:                 00000000
>   SEHandlerCount:                 00000000
> ```

关注点：
- `Size = 0x48`：说明这是一个早期结构，仅包含基础字段，没有 CFG 支持。
- `SecurityCookie = 0x00401000`：`/GS` 已启用，Cookie 变量在 VA `0x401000`。
- `SEHandlerTable = 0x00000000`：SafeSEH 未启用（或为 64 位二进制）。

如需查看启用了完整 CFG 的现代二进制，`GuardCFFunctionTable` 会包含非零地址，且 `GuardFlags` 会有 `CF_INSTRUMENTED | CF_FUNCTION_TABLE_PRESENT` 等位被置位。

## 编译器选项与加载配置表的关系

在 Visual Studio 中，以下选项直接影响加载配置表的生成内容：

| 编译/链接选项 | 效果 |
|---------------|------|
| `/GS`（默认开启） | 生成 `__security_cookie` 变量，填写 `SecurityCookie` 字段 |
| `/SafeSEH` | 生成 SEH 处理器列表，填写 `SEHandlerTable/Count` |
| `/Guard:CF` | 扫描间接调用，生成 `GuardCFFunctionTable`，填写所有 `GuardCF*` 字段 |
| `/Guard:ehcont` | 生成异常连续处理目标表，填写 `GuardRF*` 字段 |
| 无任何选项 | 加载配置表可能仍存在（链接器默认生成最小结构），但安全字段全零 |

> [!warning] 逆向分析注意事项
> 1. **无加载配置表 ≠ 无安全机制**：系统 DLL 本身可能在运行时通过其他机制（如 ASLR、DEP/NX）提供防护，不能仅凭加载配置表缺失就判定无保护。
> 2. **CFG 白名单可被枚举**：`GuardCFFunctionTable` 是明文的 RVA 列表。逆向时可以转储它，了解程序中所有合法间接调用目标——这对漏洞研究也有参考价值。
> 3. **`SecurityCookie` 地址固定**：Cookie 值虽然随机，但存放它的**变量地址**在加载配置表中是明文。配合 ASLR 的基址随机化，攻击者需要先泄露模块基址才能定位 Cookie 地址。

> [!summary] 小结
> 加载配置表（Load Configuration Directory，[[07-详解PE文件(七)：数据目录|数据目录]] 索引 10）是 PE 文件中**唯一专门承载运行时安全加固元数据**的结构。它的三大核心职能：
> - **`SecurityCookie`**：宣告 `/GS` 安全 Cookie 变量位置，供加载器初始化随机值。
> - **`SEHandlerTable/Count`**：为 32 位 PE 提供合法 SEH 处理器白名单（SafeSEH）。
> - **`GuardCF*` + `GuardFlags`**：声明 CFG 合法间接调用目标表，供内核构建位图。
>
> 结构体通过首字段 `Size` 实现优雅的版本控制，随 Windows 版本持续追加字段而不破坏兼容性。对逆向工程师而言，检查 `GuardFlags` 和 `SecurityCookie` 是评估目标程序防护强度的第一步。
>
