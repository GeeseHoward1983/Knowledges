# 详解PE文件(十九)：绑定配置表

> 来源：[CSDN 原文](https://blog.csdn.net/geesehoward20000/article/details/154744605)　｜　发布：2025-12-02　｜　合集《PE文件详解》第 19/26 篇

> [!tip] 一句话核心
> 绑定导入表的本质是**空间换时间**：在构建期把每个导入函数的绝对地址预先写入 [[20-详解PE文件(二十)：导入地址表|IAT]]，加载时先对比 DLL 时间戳——戳对了就"零解析"直接用，戳不对（DLL 被升级/ASLR 重新布局）就回退到正常导入流程。简单却高效，在 ASLR 出现之前是 Windows 加速启动的重要手段。

> [!info] 速查
> - **结构体**：`IMAGE_BOUND_IMPORT_DESCRIPTOR` + `IMAGE_BOUND_FORWARDER_REF`
> - **大小**：`IMAGE_BOUND_IMPORT_DESCRIPTOR` = 8 字节；`IMAGE_BOUND_FORWARDER_REF` = 8 字节
> - **数据目录索引**：11（第 12 项，从 0 计数）
> - **位置**：[[07-详解PE文件(七)：数据目录|可选头数据目录]] 第 11 项指向，通常位于文件头区域而非节区
> - **关键字段**：`TimeDateStamp`（时间戳校验）、`OffsetModuleName`（模块名偏移）、`NumberOfModuleForwarderRefs`（转发引用数）
> - **关联篇目**：[[08-详解PE文件(八)：导入表]]、[[20-详解PE文件(二十)：导入地址表]]、[[21-详解PE文件(二十一)：延迟导入表]]

绑定导入表（Bound Import Table）是 PE 文件导入家族中最容易被忽视、却又暗藏玄机的一员。它本身不描述"要导入哪些函数"，而是记录"我在构建期已经把地址写好了——如果还有效，就跳过解析"。理解它，需要先明白 PE 加载器在 [[08-详解PE文件(八)：导入表|导入表]] 解析阶段究竟做了哪些工作，绑定优化才有意义。

## 绑定导入表在 PE 文件中的位置

绑定导入表是 [[06-详解PE文件(六)：可选头|可选头]] 末尾的 [[07-详解PE文件(七)：数据目录|数据目录]] 数组中的第 12 个条目（索引 11）。下面是数据目录全貌，绑定导入表在其中的位置一目了然：

```text
数据目录数组（共16个条目）：
0.  导出表 (Export Table)
1.  导入表 (Import Table)
2.  资源表 (Resource Table)
3.  异常表 (Exception Table)
4.  证书表 (Certificate Table)
5.  基址重定位表 (Base Relocation Table)
6.  调试数据 (Debug Data)
7.  版权信息 (Architecture Specific Data)
8.  全局指针 (Global Pointer)
9.  TLS表 (Thread Local Storage Table)
10. 加载配置表 (Load Configuration Table)
11. 绑定导入表 (Bound Import Table)       ← 本篇
12. 导入地址表 (Import Address Table)
13. 延迟导入表 (Delay Import Descriptor)
14. CLR运行时头 (CLR Runtime Header)
15. 保留 (Reserved)
```

与大多数数据目录项不同，绑定导入表的数据通常位于**文件头区域**（`e_lfanew` 之前或紧随节表之后），而不存放在某个具名节（如 `.rdata`）中。这是因为绑定信息需要在加载器处理节之前就能访问。

```text
文件偏移
0x00  ┌─────────────────────────────────┐
      │  DOS 头 + DOS Stub              │
      ├─────────────────────────────────┤
      │  PE 签名 "PE\0\0"               │
      ├─────────────────────────────────┤
      │  COFF 文件头                    │
      ├─────────────────────────────────┤
      │  可选头（含数据目录[11]）        │
      │   DataDirectory[11].VirtualAddress ──────────┐
      ├─────────────────────────────────┤            │
      │  节表                           │            │
      ├─────────────────────────────────┤            │
      │  ◄── 绑定导入表（文件头区域）◄──┘            │
      │  IMAGE_BOUND_IMPORT_DESCRIPTOR[]│
      │  + 模块名称字符串池             │
      ├─────────────────────────────────┤
      │  节数据（.text/.rdata/...）     │
      └─────────────────────────────────┘
```

> [!note] RVA 还是文件偏移？
> 绑定导入表的 `DataDirectory[11].VirtualAddress` 字段记录的是 **RVA**，但由于该结构通常位于文件头区域（PE 头之前已映射），加载器在处理它时往往直接按文件偏移读取，而非靠节区映射计算。这与位于节区内的导入表、导出表不同，需要特别留意。

## 数据结构定义

绑定导入表由两个互相嵌套的结构组成，外加一个紧随其后的**模块名称字符串池**。

### IMAGE_BOUND_IMPORT_DESCRIPTOR

```c
typedef struct _IMAGE_BOUND_IMPORT_DESCRIPTOR {
    DWORD   TimeDateStamp;               // 时间戳
    WORD    OffsetModuleName;            // 模块名称偏移量
    WORD    NumberOfModuleForwarderRefs; // 转发引用的数量
// Array of zero or more IMAGE_BOUND_FORWARDER_REF follows
} IMAGE_BOUND_IMPORT_DESCRIPTOR, *PIMAGE_BOUND_IMPORT_DESCRIPTOR;
```

### IMAGE_BOUND_FORWARDER_REF

```c
typedef struct _IMAGE_BOUND_FORWARDER_REF {
    DWORD   TimeDateStamp;      // 时间戳
    WORD    OffsetModuleName;   // 转发模块名称偏移量
    WORD    Reserved;           // 保留字段
} IMAGE_BOUND_FORWARDER_REF, *PIMAGE_BOUND_FORWARDER_REF;
```

两个结构**大小均为 8 字节**，布局完全相同（`IMAGE_BOUND_FORWARDER_REF` 仅把 `NumberOfModuleForwarderRefs` 换成了 `Reserved`）。

| 偏移 | 字段 | 大小 | 说明 |
|---|---|---|---|
| `+0x00` ⭐ | `TimeDateStamp` | 4 | **DLL 的时间戳快照**，用于校验绑定是否仍有效 |
| `+0x04` | `OffsetModuleName` | 2 | 相对于**绑定导入表自身起始**的名称字符串偏移 |
| `+0x06` | `NumberOfModuleForwarderRefs` | 2 | 紧随本描述符之后的 `IMAGE_BOUND_FORWARDER_REF` 条目数 |

## 各字段详解

### TimeDateStamp — 时间戳校验核心

`TimeDateStamp` 是绑定优化的**灵魂字段**。它记录的是绑定工具（如 `bind.exe`）运行时，目标 DLL 的 `IMAGE_FILE_HEADER.TimeDateStamp` 的快照值。

加载时，PE 加载器会把这个存档值与实际加载到内存中的 DLL 的时间戳做比较：

- **一致** → 说明 DLL 没有被替换或更新，预写的地址仍然有效，跳过 [[08-详解PE文件(八)：导入表|正常导入解析]]，直接用 IAT 里的预填地址。
- **不一致** → 绑定失效，加载器回退到对 [[08-详解PE文件(八)：导入表|导入表]] 的全量解析流程，重新填写 [[20-详解PE文件(二十)：导入地址表|IAT]]。

> [!warning] 时间戳不是真正的时间
> `TimeDateStamp` 的值是 POSIX 时间戳格式（自 1970-01-01 起的秒数），但链接器通常会把它固定为一个"确定性构建"标记值（如 `0`、`1`），或是构建时的实际时间——具体取决于工具链配置。逆向时见到全零时间戳，通常意味着该 PE 使用了"可复现构建"模式，而不是"没有绑定"。

### OffsetModuleName — 模块名偏移

`OffsetModuleName` 是一个 16 位的相对偏移，指向**绑定导入表起始位置**偏移该值处的 NULL 结尾字符串，即被绑定 DLL 的文件名（如 `KERNEL32.dll`）。

所有模块名称字符串紧密排列在描述符数组末尾（全零结束符之后），形成一个字符串池：

```text
绑定导入表起始地址
│
│  ← IMAGE_BOUND_IMPORT_DESCRIPTOR[0]（8 字节）
│  ← IMAGE_BOUND_FORWARDER_REF[...]  （若有，每条 8 字节）
│  ← IMAGE_BOUND_IMPORT_DESCRIPTOR[1]（8 字节）
│  ← ...
│  ← IMAGE_BOUND_IMPORT_DESCRIPTOR 结束符（8 字节全零）
│  ← "KERNEL32.dll\0"      ← OffsetModuleName 指向此处
│  ← "USER32.dll\0"
│  ← ...（字符串池）
```

### NumberOfModuleForwarderRefs — 转发引用计数

当一个 DLL（例如 `USER32.dll`）的某些导出函数实际上**转发**（forward）给另一个 DLL（如 `ntdll.dll`）时，对被转发 DLL 的绑定信息也需要记录。`NumberOfModuleForwarderRefs` 指明了紧随当前 `IMAGE_BOUND_IMPORT_DESCRIPTOR` 之后有多少个 `IMAGE_BOUND_FORWARDER_REF` 条目。

> [!note] DLL 转发（Forwarding）是什么？
> 当一个 DLL 的某个导出入口点不是真正的函数实现，而是一个指向另一个 DLL 中函数的字符串（如 `NTDLL.RtlAllocateHeap`）时，就发生了函数转发。`HeapAlloc` 在 `KERNEL32.dll` 里就是典型案例——它实际上转发给 `NTDLL.dll` 的 `RtlAllocateHeap`。绑定工具需要同时为转发链上的每个 DLL 记录时间戳，才能完整验证绑定有效性。

## 工作原理：绑定优化与回退流程

理解绑定导入表，最重要的是理解它的**两阶段流程**：构建期绑定 + 加载期校验。

### 绑定优化：预先写入地址

```text
                    【构建期：bind.exe 工作流程】
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
   解析 PE 的导入表（ImportTable）     加载各 DLL，获取基址
              │                               │
              └───────────────┬───────────────┘
                              │
              ┌───────────────▼───────────────┐
              │  计算每个导入函数的绝对地址    │
              │  = DLL基址 + 函数RVA          │
              └───────────────┬───────────────┘
                              │
         ┌────────────────────┼────────────────────┐
         ▼                                         ▼
  将绝对地址写入 IAT                  将 DLL 时间戳写入
  （导入地址表，见第 20 篇）           绑定导入表（本篇）
```

### 加载期校验：成功则跳过，失败则回退

```text
                    【加载期：PE 加载器工作流程】
                              │
              ┌───────────────▼───────────────┐
              │  检查 DataDirectory[11] 是否存在│
              └───────────────┬───────────────┘
                              │ 存在
              ┌───────────────▼───────────────┐
              │  读取绑定导入表               │
              │  对每个描述符：               │
              │  ① 找到对应已加载 DLL         │
              │  ② 比对 TimeDateStamp         │
              └────────────┬──────────────────┘
                           │
          ┌────────────────┴────────────────┐
          │ 时间戳匹配？                    │
          ▼                                 ▼
         是                                否
          │                                 │
          ▼                                 ▼
  ✓ 绑定有效                       ✗ 绑定失效
  直接使用 IAT 中的预填地址         回退：按正常导入表
  跳过导入表全量解析                全量解析并重新填写 IAT
  （零解析，最快路径）              （见第 08、20 篇）
```

> [!important] ASLR 与绑定的冲突
> Windows Vista 引入的 ASLR（地址空间布局随机化）会在每次系统启动时随机化 DLL 的基址，导致预先写入 IAT 的绝对地址**几乎永远无效**。即使时间戳匹配，地址也会因 ASLR 而不同，加载器仍需回退到正常流程。这是绑定导入表在现代 Windows 中逐渐退出历史舞台的根本原因。

## 内存布局详解

绑定导入表在文件中的完整布局如下（以两个 DLL、第一个有一条转发引用为例）：

```text
+--------------------------------+ ← 绑定导入表起始（DataDirectory[11] 指向）
| IMAGE_BOUND_IMPORT_DESCRIPTOR  |   第一个导入模块（8 字节）
|   TimeDateStamp = 0x12345678   |
|   OffsetModuleName = 0x0030    |   → 指向 "KERNEL32.dll"
|   NumberOfModuleForwarderRefs  |
|     = 1                        |
+--------------------------------+
| IMAGE_BOUND_FORWARDER_REF      |   KERNEL32 的转发引用（8 字节）
|   TimeDateStamp = 0xAABBCCDD   |
|   OffsetModuleName = 0x003E    |   → 指向 "NTDLL.dll"
|   Reserved = 0                 |
+--------------------------------+
| IMAGE_BOUND_IMPORT_DESCRIPTOR  |   第二个导入模块（8 字节）
|   TimeDateStamp = 0x87654321   |
|   OffsetModuleName = 0x0047    |   → 指向 "USER32.dll"
|   NumberOfModuleForwarderRefs  |
|     = 0                        |
+--------------------------------+
| IMAGE_BOUND_IMPORT_DESCRIPTOR  |   结束标记（8 字节全零）
|   TimeDateStamp = 0            |
|   OffsetModuleName = 0         |
|   NumberOfModuleForwarderRefs  |
|     = 0                        |
+--------------------------------+ ← 偏移 0x0030（名称字符串池起点）
| "KERNEL32.dll\0"               |   模块名 1
+--------------------------------+ ← 偏移 0x003E
| "NTDLL.dll\0"                  |   模块名 2（转发目标）
+--------------------------------+ ← 偏移 0x0047
| "USER32.dll\0"                 |   模块名 3
+--------------------------------+
```

| 区段 | 大小规律 | 说明 |
|---|---|---|
| 主描述符数组 | `(1 + ForwarderRefs) × 8` 字节/模块 | 以全零 8 字节结尾 |
| 字符串池 | 各模块名长度 + 1（`\0`）之和 | 无对齐要求 |
| `OffsetModuleName` 基准 | **绑定导入表自身起始** | 注意：不是节起点，不是文件起点 |

## 实际应用

### 创建绑定导入表

使用 Microsoft 的 `bind.exe` 工具可以创建绑定导入表：

```
bind.exe [-u] dllname.exe
```

`-u` 参数表示解除绑定（unbind），将 IAT 恢复为符号名占位状态并清空绑定导入表。

> [!example] 用 dumpbin 查看绑定导入表
> ```
> BOUND IMPORT TABLE
>     偏移量 时间戳        模块名称
>         48 0x12345678   KERNEL32.dll
>         96 0x87654321   USER32.dll
> ```
> 使用命令：`dumpbin /imports <文件名>` 即可查看，绑定信息通常与导入表并列显示。

### 与导入家族的关系

绑定导入表与 PE 文件中另外三个导入相关结构形成完整的"导入家族"：

| 结构 | 篇目 | 角色 |
|---|---|---|
| 导入表（Import Table） | [[08-详解PE文件(八)：导入表]] | 描述"需要导入哪些函数"，是解析的权威来源 |
| **绑定导入表（Bound Import Table）** | **本篇（19）** | **记录预填地址的 DLL 时间戳，用于校验快速路径** |
| 导入地址表（IAT） | [[20-详解PE文件(二十)：导入地址表]] | 存放实际函数地址，绑定时预填，回退时重写 |
| 延迟导入表（Delay Import） | [[21-详解PE文件(二十一)：延迟导入表]] | 按需延迟加载 DLL，现代替代方案之一 |

> [!warning] 逆向与安全提醒
> 1. **绑定信息可以伪造**：攻击者可修改 `TimeDateStamp` 使校验永远通过，从而让恶意地址预先写入 IAT，而加载器不会重新验证。
> 2. **双重解析陷阱**：部分解析工具只看导入表，忽略绑定导入表；实际加载时走的却是绑定路径。逆向时如果发现 IAT 中的地址与导入表解析结果不符，应优先检查绑定导入表。
> 3. **已停用不等于不存在**：即使在 Windows 10/11 上，仍有大量老旧 PE 带有绑定导入表。加载器仍会处理它（并因 ASLR 而回退），弄清楚这一流程有助于分析启动性能与加载器行为。

## 现代使用情况

### 在现代 Windows 中的衰落

| 因素 | 影响 |
|---|---|
| ASLR（Vista+） | 基址随机化，预填地址几乎永远失效，必须回退 |
| Secure Boot / 代码签名 | DLL 更新更频繁，时间戳更容易不匹配 |
| 延迟导入表（DelayLoad） | 提供了更灵活的按需加载替代方案 |
| APIset（Windows 7+） | 将 API 调用路由到虚拟 DLL，绕过地址绑定 |

Windows Vista 及以后版本的微软官方二进制文件已基本不再使用绑定导入表。但了解它仍然重要：一方面大量遗留程序依然携带它，另一方面它完整揭示了 PE 加载器设计中"乐观预填 + 失败回退"的工程思维。

> [!summary] 小结
> 绑定导入表是 PE 加载优化的历史产物，核心思路是**构建期预填地址、加载期时间戳校验**：命中则零成本跳过导入解析，未命中则无缝回退。结构上由 `IMAGE_BOUND_IMPORT_DESCRIPTOR` + `IMAGE_BOUND_FORWARDER_REF` + 字符串池三部分组成，全部以全零描述符结尾。ASLR 出现后，预填地址几乎永远失效，绑定导入表逐渐退出现代 PE 构建实践。理解它是深入掌握 [[08-详解PE文件(八)：导入表|导入表]]、[[20-详解PE文件(二十)：导入地址表|IAT]]、[[21-详解PE文件(二十一)：延迟导入表|延迟导入表]]以及 Windows 加载器行为的必要一步。本篇属于 [[07-详解PE文件(七)：数据目录|数据目录]] 第 11 项，由 [[06-详解PE文件(六)：可选头|可选头]] 末尾的数据目录数组索引。
