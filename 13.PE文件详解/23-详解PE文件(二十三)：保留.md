# 详解PE文件(二十三)：保留

> 来源：[CSDN 原文](https://blog.csdn.net/geesehoward20000/article/details/154745212)　｜　发布：2025-11-28　｜　合集《PE文件详解》第 23/26 篇

> [!tip] 一句话核心
> 数据目录共 16 项，最后一项（索引 15）由 Microsoft PE 规范显式标记为 **"保留"**：`VirtualAddress` 和 `Size` 必须全部为 `0`，Windows 加载器不会读取或解释它。它既是 16 项数组的终止符，也是格式为未来扩展预留的空槽。

> [!info] 速查
> - **所属结构**：`IMAGE_OPTIONAL_HEADER.DataDirectory[15]`
> - **条目类型**：`IMAGE_DATA_DIRECTORY`（8 字节：VirtualAddress 4 B + Size 4 B）
> - **宏定义**：无（规范未为此项定义宏常量）
> - **规范要求**：`VirtualAddress == 0` 且 `Size == 0`
> - **加载器行为**：忽略（不解析、不映射）
> - **位置**：[[06-详解PE文件(六)：可选头]] 末尾 → [[07-详解PE文件(七)：数据目录]] 的第 16 个槽

从 [[08-详解PE文件(八)：导入表|导入表]] 到 [[22-详解PE文件(二十二)：CLR运行时头|CLR 运行时头]]，[[07-详解PE文件(七)：数据目录|数据目录]] 的前 15 项各自指向 PE 文件的一块具名数据区域。到了第 16 项（索引 15），PE 规范划下了句号：这一项是保留项，不指向任何实际数据，也没有配套的宏常量。它的全部意义就是"静静地占据那 8 个字节，内容必须是零"。

## 数据目录结构回顾

在正式讨论保留项之前，先把它所在的容器结构明确一下。[[06-详解PE文件(六)：可选头|可选头（Optional Header）]] 末尾有一个固定 16 项的数组：

```c
// 数据目录结构
typedef struct _IMAGE_DATA_DIRECTORY {
    DWORD VirtualAddress;  // 数据的相对虚拟地址（RVA）
    DWORD Size;            // 数据的大小
} IMAGE_DATA_DIRECTORY, *PIMAGE_DATA_DIRECTORY;

// 数据目录数组在可选头中的定义
#define IMAGE_NUMBEROF_DIRECTORY_ENTRIES 16

typedef struct _IMAGE_OPTIONAL_HEADER {
    // ... 其他字段 ...

    // 数据目录数组
    IMAGE_DATA_DIRECTORY DataDirectory[IMAGE_NUMBEROF_DIRECTORY_ENTRIES];

} IMAGE_OPTIONAL_HEADER, *PIMAGE_OPTIONAL_HEADER;
```

每个 `IMAGE_DATA_DIRECTORY` 固定 8 字节（4 字节 RVA + 4 字节 Size），16 项合计 **128 字节**，紧贴在可选头其余字段的后面。

> [!note] 为什么没有宏常量？
> 前 15 项（索引 0～14）都在 `winnt.h` 中定义了对应的 `IMAGE_DIRECTORY_ENTRY_*` 宏，方便代码按名称索引。而索引 15 既无实际用途，Microsoft 就未为它提供宏名。若需手动引用，直接写字面量 `15` 或 `IMAGE_NUMBEROF_DIRECTORY_ENTRIES - 1` 即可。

## 保留项的规范要求

Microsoft PE/COFF 规范对索引 15 的要求只有一句话：**必须被设置为全零**（both `VirtualAddress` and `Size` must be zero）。这意味着：

- 链接器输出时直接填 `00 00 00 00 00 00 00 00`（8 字节零）；
- Windows 加载器不会去解释这 8 字节；
- PE 文件解析工具通常会验证它是否为零，非零视为格式异常。

> [!important] 规范约束
> **VirtualAddress 和 Size 缺一不可，都必须是 0。** 若只有一个字段为零而另一个不为零，同样不符合 PE 规范，部分严格解析器会将整个文件视为可疑。

## 为什么要保留这一项？

PE 格式自 1990 年代设计以来，为了兼顾"现在够用"与"未来可扩展"两个目标，刻意把数据目录定为 16 项而非恰好用满：

1. **为未来扩展预留空槽**：若 Microsoft 日后引入新的数据区域类型，可以直接启用这一项而无需更改 `IMAGE_NUMBEROF_DIRECTORY_ENTRIES` 或现有结构布局，从而保持二进制兼容。
2. **固定数组长度、简化解析**：16 是 2 的幂次，让解析器能以 `16 × 8 = 128` 字节为定长跳过整个数据目录，不必动态感知条目数量。
3. **标准化对齐**：固定数量使所有合规 PE 文件的可选头末尾布局一致，工具链可以不加判断地计算偏移。

> [!note] 历史小知识
> 数据目录最初设计时，PE 规范就预留了"将来可能增加的条目"。随着 Windows 不断演化，陆续新增了 TLS、加载配置、CLR、延迟导入等项目，到达 15 项后正好凑满 16——最后一个槽始终没有被分配实际用途，就此成为永久保留项。

## 实际应用：验证保留字段

在编写 PE 解析器或做安全审计时，检查该字段是否合规是一个轻量但有意义的验证步骤：

```c
#include <windows.h>
#include <stdio.h>

BOOL CheckReservedDataDirectory(PIMAGE_NT_HEADERS pNTHeaders) {
    PIMAGE_DATA_DIRECTORY pDataDir = &pNTHeaders->OptionalHeader.DataDirectory[15];

    // 检查保留字段是否为零
    if (pDataDir->VirtualAddress == 0 && pDataDir->Size == 0) {
        printf("保留字段符合规范：VirtualAddress=0, Size=0\n");
        return TRUE;
    } else {
        printf("警告：保留字段不为零！VirtualAddress=0x%X, Size=0x%X\n",
               pDataDir->VirtualAddress, pDataDir->Size);
        return FALSE;
    }
}
```

> [!warning] 逆向 / 安全提醒
> 若在野 PE 样本的 `DataDirectory[15]` 不为零，有两种可能：
> 1. **格式破坏**：链接器或 Packer 写错，文件本身可能已损坏或被篡改。
> 2. **主动利用**：部分 Packer / 免杀工具会在保留项里藏额外数据或指针，利用大多数解析器"跳过索引 15"的行为来隐藏信息。遇到非零的保留项，应重点关注。

## 在 PE 布局中的位置

理解保留项的意义，不妨把视角拉开，看它在整个 PE 文件中所处的"方位"：

```text
PE 文件整体结构（简化）

  ┌──────────────────────────────────┐  ← 文件起点
  │  DOS 头 (IMAGE_DOS_HEADER, 64B)  │
  ├──────────────────────────────────┤
  │  DOS Stub 程序                   │
  ├──────────────────────────────────┤  ← e_lfanew 指向
  │  PE 签名 "PE\0\0" (4B)           │
  ├──────────────────────────────────┤
  │  COFF 文件头 (20B)               │
  ├──────────────────────────────────┤
  │  可选头 (96B / 112B)             │
  │    ├─ 标准字段                   │
  │    ├─ Windows 特有字段           │
  │    └─ DataDirectory[0..15]       │  ← 本篇：DataDirectory[15] 保留 ≡ 0
  ├──────────────────────────────────┤  ← 数据目录结束，PE 头部完毕
  │  节表 (Section Table)            │  → 见 [[24-详解PE文件(二十四)：节表]]
  ├──────────────────────────────────┤
  │  节数据 (.text / .data / ...)    │
  └──────────────────────────────────┘
```

保留项是数据目录的最后一个条目，它之后紧接的就是 [[24-详解PE文件(二十四)：节表|节表]]——PE 文件的结构从此由"头部描述"切换到"节数据"阶段。

> [!summary] 小结
> 数据目录第 16 项（`DataDirectory[15]`）是 PE 格式里最"静默"的存在：没有宏名、没有实际数据、两个字段永远为零。它的意义在于：**以一个占位的空槽收尾 16 项数组，既保持了结构的固定长度与解析简便性，又为格式未来演化留下了扩展余地**。它标志着整个 [[07-详解PE文件(七)：数据目录|数据目录]] 描述的终结，PE 文件的解析重心随即从头部转向 [[24-详解PE文件(二十四)：节表|节表]] 与节数据。
