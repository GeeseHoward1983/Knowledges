# 详解PE文件(十二)：证书表

> 来源：[CSDN 原文](https://blog.csdn.net/geesehoward20000/article/details/154743223)　｜　发布：2025-11-21　｜　合集《PE文件详解》第 12/26 篇

> [!tip] 一句话核心
> 证书表（Certificate Table / Security Directory）是 PE 文件中唯一使用**文件偏移**而非 RVA 的数据目录项——加载器不会把它映射进内存，验签工具直接按文件偏移读取 `WIN_CERTIFICATE` 结构，里面存的是 **PKCS#7 格式的 Authenticode 签名数据**。

> [!info] 速查
> - **数据目录索引**：`IMAGE_DIRECTORY_ENTRY_SECURITY`（值为 **4**）
> - **核心结构体**：`WIN_CERTIFICATE`（头部 8 字节 + 变长证书数据）
> - **地址类型**：`VirtualAddress` 字段存放的是**文件偏移**，不是 RVA（唯一例外）
> - **对齐方式**：每个证书条目按 **8 字节**对齐
> - **常用证书类型**：`WIN_CERT_TYPE_PKCS_SIGNED_DATA`（`0x0002`），即 PKCS#7
> - **所属位置**：追加在 PE 文件尾部，不属于任何节
> - **相关篇目**：[[07-详解PE文件(七)：数据目录]] · [[06-详解PE文件(六)：可选头]]

PE 文件的**证书表**（Certificate Table），在 Microsoft 文档中又称**安全目录**（Security Directory），是 Windows 可执行文件数字签名的存储载体。它使得操作系统能够在加载或运行一个程序之前，用 Authenticode 机制核验文件是否被篡改、是否来自可信发布者。对于内核驱动，Windows 甚至强制要求有效签名，否则拒绝加载。

> [!warning] 关键区别：文件偏移 vs. RVA
> 在 [[07-详解PE文件(七)：数据目录]] 的 16 个条目中，证书表是**唯一一个** `VirtualAddress` 字段存放**文件偏移（File Offset）**而非**相对虚拟地址（RVA）**的项。这是因为证书表数据并不映射进进程的虚拟内存，验签工具直接在磁盘文件层面读取它。解析时切勿对该字段做 RVA→文件偏移转换，否则会读到错误位置。

## 证书表在 PE 文件中的位置

证书表数据通常**追加在 PE 文件的末尾**，不属于任何 Section，也不会被加载器映射到进程地址空间。它由 [[06-详解PE文件(六)：可选头]] 中数据目录数组的第 5 项（索引 4）指向：

```text
文件（磁盘）布局
┌─────────────────────────────────────────────┐
│  DOS 头（64 字节）                           │
├─────────────────────────────────────────────┤
│  PE 签名 "PE\0\0"                            │
│  COFF 文件头                                 │
│  可选头（含 DataDirectory[4]）               │
│    ├─ VirtualAddress = <文件偏移 FOA>        │  ← 注意：文件偏移，非 RVA
│    └─ Size           = <证书表总字节数>       │
├─────────────────────────────────────────────┤
│  节表                                        │
├─────────────────────────────────────────────┤
│  .text  节数据                               │
│  .rdata 节数据                               │
│  ... 其余各节 ...                            │
├─────────────────────────────────────────────┤
│  证书表数据（FOA 处）                         │  ← DataDirectory[4].VirtualAddress 直接指这里
│    WIN_CERTIFICATE #0                        │
│    WIN_CERTIFICATE #1（若有多个）            │
└─────────────────────────────────────────────┘
```

> [!note] 证书表不映射入内存
> 绝大多数数据目录项（导入表、资源表、重定位表等）都会随节数据一起被映射进进程虚拟内存。证书表则不然——它仅存在于磁盘文件，Windows 加载器**不会**把它映射进来。WinVerifyTrust 等 API 内部会另行以文件方式打开、校验。

## 数据目录入口

证书表通过 [[06-详解PE文件(六)：可选头]] 末尾的数据目录表寻址，索引固定为 4：

```c
// 数据目录中的证书表项
DataDirectory[IMAGE_DIRECTORY_ENTRY_SECURITY]
```

| 字段 | 含义 | 备注 |
|---|---|---|
| `VirtualAddress` | 证书表在文件中的**文件偏移**（FOA） | 唯一用 FOA 而非 RVA 的目录项 |
| `Size` | 证书表区域的总字节数 | 包含所有 WIN_CERTIFICATE 条目 |

若 `VirtualAddress == 0`，则该 PE 文件没有数字签名。

## WIN_CERTIFICATE 结构详解

证书表区域由一个或多个 `WIN_CERTIFICATE` 结构紧密排列而成，每个条目按 8 字节对齐。

```c
typedef struct _WIN_CERTIFICATE {
    DWORD dwLength;             // 证书结构的总长度
    WORD  wRevision;            // 结构版本
    WORD  wCertificateType;     // 证书类型
    BYTE  bCertificate[ANYSIZE_ARRAY]; // 证书数据
} WIN_CERTIFICATE, *LPWIN_CERTIFICATE;
```

### 字段一览

| 偏移 | 字段 | 大小 | 说明 |
|---|---|---|---|
| `+0x00` | `dwLength` | 4 字节 | 整个条目的总字节数（含头部 8 字节 + 证书数据），按 8 字节对齐 |
| `+0x04` | `wRevision` | 2 字节 | 结构版本号，常见值 `0x0200`（WIN_CERT_REVISION_2_0） |
| `+0x06` | `wCertificateType` | 2 字节 | 证书数据格式，见下表 |
| `+0x08` | `bCertificate[]` | 变长 | 实际证书数据，长度 = `dwLength - 8` |

头部固定 **8 字节**，之后跟变长的证书二进制数据：

```text
WIN_CERTIFICATE 内存布局
┌──────────────────────────────────────────────┐
│ dwLength      (4 字节)  整个条目总长          │
│ wRevision     (2 字节)  版本，通常 0x0200     │
│ wCertificateType (2 字节) 类型               │
├──────────────────────────────────────────────┤
│ bCertificate[]           变长证书数据         │
│  （PKCS#7 / X.509 / ...）                    │
│                                              │
│  [填充 0 至 8 字节对齐]                       │
└──────────────────────────────────────────────┘
```

### wRevision 取值

| 常量 | 值 | 说明 |
|---|---|---|
| `WIN_CERT_REVISION_1_0` | `0x0100` | 版本 1.0（较旧，已少见） |
| `WIN_CERT_REVISION_2_0` | `0x0200` | 版本 2.0，当前主流 |

### wCertificateType 取值

```c
// 证书类型定义
#define WIN_CERT_REVISION_1_0 0x0100
#define WIN_CERT_REVISION_2_0 0x0200

#define WIN_CERT_TYPE_X509             0x0001
#define WIN_CERT_TYPE_PKCS_SIGNED_DATA 0x0002
#define WIN_CERT_TYPE_RESERVED_1       0x0003
```

| 常量 | 值 | 说明 |
|---|---|---|
| `WIN_CERT_TYPE_X509` | `0x0001` | X.509 证书格式（较少使用） |
| `WIN_CERT_TYPE_PKCS_SIGNED_DATA` | `0x0002` | PKCS#7 签名数据，**最常见** |
| `WIN_CERT_TYPE_RESERVED_1` | `0x0003` | 保留，不用于实际签名 |

> [!important] PKCS#7 是实际标准
> 现代 Windows 可执行文件几乎全部使用 `WIN_CERT_TYPE_PKCS_SIGNED_DATA`（`0x0002`），即 PKCS#7 格式。`bCertificate` 字段中存放的是一个完整的 **PKCS#7 SignedData** 对象（DER 编码），内嵌了文件哈希、签名者证书链、时间戳等完整 Authenticode 信息。

## Authenticode 签名流程

Authenticode 是 Microsoft 为 PE 文件设计的代码签名体系，签名过程涉及对文件特定部分计算哈希，再用私钥签名后附加到证书表。

```text
Authenticode 签名流程

  原始 PE 文件
       │
       ▼
  ┌─────────────────────────────────────────────┐
  │  计算文件哈希（排除以下三部分）              │
  │  1. OptionalHeader.CheckSum                 │
  │  2. DataDirectory[4]（证书表目录项本身）     │
  │  3. 证书表数据区（文件末尾）                 │
  └─────────────────────────────────────────────┘
       │  哈希值（SHA-256 等）
       ▼
  ┌─────────────────────────────────────────────┐
  │  构建 PKCS#7 SignedData                      │
  │  ├─ 文件哈希（SpcPeImageData）               │
  │  ├─ 签名者证书（含公钥）                     │
  │  ├─ 用私钥对哈希做 RSA/ECDSA 签名            │
  │  └─ 时间戳（可选，防私钥过期失效）           │
  └─────────────────────────────────────────────┘
       │  DER 编码的 PKCS#7 blob
       ▼
  ┌─────────────────────────────────────────────┐
  │  追加到 PE 文件尾部                          │
  │  ├─ 封装进 WIN_CERTIFICATE 结构              │
  │  └─ 更新 DataDirectory[4] 的偏移和大小       │
  └─────────────────────────────────────────────┘
       │
       ▼
  已签名的 PE 文件
```

> [!note] 为什么要排除这三部分再算哈希？
> - **CheckSum**：签名工具在写入证书后会更新校验和，若签名前把它也纳入哈希，写入后校验和必然变化，导致哈希对不上。
> - **DataDirectory[4]**：证书表目录项记录的是证书数据的位置和大小，这些值在证书写入之前无法确定，因此同样排除。
> - **证书表数据本身**：不能用它来验证自己，否则形成循环依赖。

## 签名验证流程

Windows 在运行/加载已签名的 PE 文件时，通过 WinVerifyTrust API 做如下校验：

```text
签名验证流程

  打开 PE 文件（文件方式，非内存映射）
       │
       ▼
  读 DataDirectory[4].VirtualAddress（文件偏移）
       │
       ▼
  跳到该偏移，读取 WIN_CERTIFICATE 结构
       │
       ▼
  解析 PKCS#7 SignedData，取出：
  ├─ 声明的文件哈希
  ├─ 签名者证书链
  └─ 数字签名值
       │
       ▼
  按同样规则重新计算文件哈希（排除 CheckSum/目录项/证书数据）
       │
       ├─ 哈希不匹配 ──▶  文件已被篡改，验证失败
       │
       ▼
  用证书公钥验证签名值
       │
       ├─ 签名无效 ──▶  证书与内容不匹配，验证失败
       │
       ▼
  验证证书链是否可信（根 CA 是否在信任库中）
       │
       ├─ 不可信 ──▶  来源不可信，验证失败
       │
       ▼
  验证通过 ──▶  文件完整，来源可信
```

## 多证书条目的布局

一个 PE 文件的证书表可以包含多个 `WIN_CERTIFICATE` 条目（如同时存放主签名和反签名时间戳），它们在文件中**顺序排列**，每条按 8 字节对齐：

```text
证书表区域（文件偏移 FOA 处）
┌─────────────────────────────────────────────┐
│  WIN_CERTIFICATE #0                          │
│    dwLength = N0（含 8 字节头）              │
│    bCertificate[N0-8]                        │
│    [填充至 8 字节对齐]                        │
├─────────────────────────────────────────────┤
│  WIN_CERTIFICATE #1（若有）                  │
│    dwLength = N1                             │
│    bCertificate[N1-8]                        │
│    [填充至 8 字节对齐]                        │
├─────────────────────────────────────────────┤
│    ...                                       │
└─────────────────────────────────────────────┘
   ↑
   DataDirectory[4].Size 覆盖整个区域
```

遍历时，每次按 `((dwLength + 7) / 8) * 8` 推进偏移，直到超过 `DataDirectory[4].Size` 为止。

## 实战：读取与验证证书表

以下是完整的 C 代码示例，演示如何解析证书表并调用 Windows API 验证签名。

```c
#include <windows.h>
#include <stdio.h>
#include <wintrust.h>
#include <softpub.h>

// 证书类型定义
#define WIN_CERT_REVISION_1_0 0x0100
#define WIN_CERT_REVISION_2_0 0x0200

#define WIN_CERT_TYPE_X509             0x0001
#define WIN_CERT_TYPE_PKCS_SIGNED_DATA 0x0002
#define WIN_CERT_TYPE_RESERVED_1       0x0003

void PrintCertificateInfo(PWIN_CERTIFICATE cert) {
    printf("=== 证书信息 ===\n");
    printf("证书长度: %lu 字节\n", cert->dwLength);
    printf("版本: 0x%04X\n", cert->wRevision);
    printf("证书类型: 0x%04X ", cert->wCertificateType);

    switch (cert->wCertificateType) {
        case WIN_CERT_TYPE_X509:
            printf("(X.509 证书)\n");
            break;
        case WIN_CERT_TYPE_PKCS_SIGNED_DATA:
            printf("(PKCS#7 签名数据)\n");
            break;
        case WIN_CERT_TYPE_RESERVED_1:
            printf("(保留类型)\n");
            break;
        default:
            printf("(未知类型)\n");
            break;
    }

    printf("证书数据大小: %lu 字节\n", cert->dwLength - sizeof(WIN_CERTIFICATE));
}

void PrintCertificateTable(const char* filename) {
    HANDLE hFile = CreateFile(filename, GENERIC_READ, FILE_SHARE_READ,
                              NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);

    if (hFile == INVALID_HANDLE_VALUE) {
        printf("无法打开文件: %s\n", filename);
        return;
    }

    HANDLE hMapping = CreateFileMapping(hFile, NULL, PAGE_READONLY, 0, 0, NULL);
    if (!hMapping) {
        printf("创建文件映射失败\n");
        CloseHandle(hFile);
        return;
    }

    LPVOID lpBase = MapViewOfFile(hMapping, FILE_MAP_READ, 0, 0, 0);
    if (!lpBase) {
        printf("映射文件失败\n");
        CloseHandle(hMapping);
        CloseHandle(hFile);
        return;
    }

    // 获取DOS头
    PIMAGE_DOS_HEADER dosHeader = (PIMAGE_DOS_HEADER)lpBase;

    // 验证DOS签名
    if (dosHeader->e_magic != IMAGE_DOS_SIGNATURE) {
        printf("不是有效的PE文件\n");
        UnmapViewOfFile(lpBase);
        CloseHandle(hMapping);
        CloseHandle(hFile);
        return;
    }

    // 获取NT头
    PIMAGE_NT_HEADERS ntHeaders = (PIMAGE_NT_HEADERS)((LPBYTE)lpBase + dosHeader->e_lfanew);

    // 验证PE签名
    if (ntHeaders->Signature != IMAGE_NT_SIGNATURE) {
        printf("不是有效的PE文件\n");
        UnmapViewOfFile(lpBase);
        CloseHandle(hMapping);
        CloseHandle(hFile);
        return;
    }

    // 获取证书表信息
    PIMAGE_DATA_DIRECTORY certDir =
        &ntHeaders->OptionalHeader.DataDirectory[IMAGE_DIRECTORY_ENTRY_SECURITY];

    if (certDir->VirtualAddress == 0) {
        printf("该文件没有数字签名\n");
        UnmapViewOfFile(lpBase);
        CloseHandle(hMapping);
        CloseHandle(hFile);
        return;
    }

    // 注意：证书表使用文件偏移而不是RVA
    PWIN_CERTIFICATE cert = (PWIN_CERTIFICATE)((LPBYTE)lpBase + certDir->VirtualAddress);

    printf("=== 证书表信息 ===\n");
    printf("证书表文件偏移: 0x%08X\n", certDir->VirtualAddress);
    printf("证书表大小: %d 字节\n", certDir->Size);

    // 遍历证书表中的所有证书
    DWORD offset = 0;
    int certIndex = 0;

    while (offset < certDir->Size) {
        PWIN_CERTIFICATE currentCert = (PWIN_CERTIFICATE)((LPBYTE)cert + offset);

        if (currentCert->dwLength == 0) {
            break;
        }

        printf("\n证书 %d:\n", certIndex++);
        PrintCertificateInfo(currentCert);

        // 按8字节对齐
        offset += ((currentCert->dwLength + 7) / 8) * 8;
    }

    UnmapViewOfFile(lpBase);
    CloseHandle(hMapping);
    CloseHandle(hFile);
}

// 使用Windows API验证文件签名
BOOL VerifyFileSignature(const char* filename) {
    WINTRUST_FILE_INFO fileInfo = { 0 };
    fileInfo.cbStruct = sizeof(WINTRUST_FILE_INFO);
    fileInfo.pcwszFilePath = (LPCWSTR)filename;
    fileInfo.hFile = NULL;
    fileInfo.pgKnownSubject = NULL;

    WINTRUST_DATA trustData = { 0 };
    trustData.cbStruct = sizeof(WINTRUST_DATA);
    trustData.pPolicyCallbackData = NULL;
    trustData.pSIPClientData = NULL;
    trustData.dwUIChoice = WTD_UI_NONE;
    trustData.fdwRevocationChecks = WTD_REVOKE_NONE;
    trustData.dwUnionChoice = WTD_CHOICE_FILE;
    trustData.dwStateAction = WTD_STATEACTION_VERIFY;
    trustData.hWVTStateData = NULL;
    trustData.pwszURLReference = NULL;
    trustData.dwProvFlags = WTD_SAFER_FLAG;
    trustData.dwUIContext = 0;
    trustData.pFile = &fileInfo;

    GUID actionId = WINTRUST_ACTION_GENERIC_VERIFY_V2;

    LONG result = WinVerifyTrust(NULL, &actionId, &trustData);

    switch (result) {
        case ERROR_SUCCESS:
            printf("文件签名验证成功\n");
            return TRUE;
        case TRUST_E_NOSIGNATURE:
            printf("文件没有数字签名\n");
            return FALSE;
        case TRUST_E_EXPLICIT_DISTRUST:
            printf("文件签名被明确拒绝\n");
            return FALSE;
        case TRUST_E_SUBJECT_NOT_TRUSTED:
            printf("文件签名不被信任\n");
            return FALSE;
        default:
            printf("文件签名验证失败，错误码: 0x%08X\n", result);
            return FALSE;
    }
}
```

> [!example] 代码解析要点
> - `DataDirectory[IMAGE_DIRECTORY_ENTRY_SECURITY].VirtualAddress` 是**文件偏移**，代码中直接用 `(LPBYTE)lpBase + certDir->VirtualAddress` 定位，没有做 RVA→FOA 转换——这是正确的。
> - 遍历时用 `((currentCert->dwLength + 7) / 8) * 8` 计算对齐后步长，确保跳过每个条目的末尾填充字节。
> - `WinVerifyTrust` 内部会自己打开文件做校验，不依赖内存映射中的证书数据。

## 证书表的安全意义

证书表在 Windows 安全体系中具有多层意义：

| 应用场景 | 作用 |
|---|---|
| 文件完整性验证 | 防止二进制文件被篡改，签名哈希不匹配即告警 |
| 来源验证 | 确认文件由持有受信代码签名证书的发布者签发 |
| 内核驱动加载 | Windows 64 位强制要求驱动具备有效 EV 签名，否则拒绝加载 |
| 企业安全策略（WDAC） | 仅允许运行满足签名策略的可执行文件 |
| 恶意软件防护 | SmartScreen 等机制基于签名决定信任级别 |

> [!warning] 逆向 / 安全提醒
> 1. **签名剥离**：直接将 `DataDirectory[4]` 置零并截断证书表数据，可以"去签名"但不改变文件其余字节，文件哈希不受影响。某些安全产品仅检查有无签名字段而不验证其有效性，此操作可绕过它们。
> 2. **签名覆盖**：将未签名内容追加到 PE 文件末尾（证书表之后），有时被用于隐藏 payload，因为签名校验仅覆盖证书表之前的内容（具体行为取决于 Windows 版本）。
> 3. **双重签名**：部分恶意样本在证书表中嵌入多个 WIN_CERTIFICATE 条目，利用某些工具只检查第一个的缺陷。解析时应遍历所有条目。
> 4. **`VirtualAddress` 字段特殊性**：与其他数据目录项不同，此字段若被误当 RVA 处理，将导致解析错误或越界访问。

## 时间戳与 Countersignature

### 问题起源：证书过期后签名失效

标准 Authenticode 签名的有效性与**签名证书的有效期**绑定：当签名者的代码签名证书到期后，即便文件签名在证书有效期内完成，Windows 的严格验证模式也会认为签名"无效"（因为验签时需要验证证书链当前是否可信）。这对长期分发的驱动和软件是严重问题。

RFC 3161 可信时间戳与 Countersignature 正是解决这一问题的机制。

---

### RFC 3161 可信时间戳

**RFC 3161**（Internet X.509 PKI Time-Stamp Protocol, TSP）定义了一种由**时间戳权威机构（TSA, Time Stamping Authority）** 颁发时间戳令牌（Timestamp Token, TST）的协议：

```text
时间戳申请流程：

签名工具（signtool / osslsigncode）
    │
    │ 1. 计算 SignerInfo 的 signature 字段的哈希（MessageImprint）
    │
    ▼
TSA 服务器（如 http://timestamp.digicert.com）
    │
    │ 2. TSA 用自己的私钥对 {hash, 时间} 签名，生成 TimeStampToken（PKCS#7 格式）
    │
    ▼
signtool
    │ 3. 把 TST 作为 "未认证属性" 嵌入 SignerInfo，
    │    属性 OID = 1.2.840.113549.1.9.16.2.14（id-smime-aa-timeStampToken）
    ▼
写入 WIN_CERTIFICATE.bCertificate（PKCS#7 SignedData）
```

时间戳令牌（TST）包含：
- `MessageImprint`：对原始签名值的哈希（绑定到具体签名，不可伪造替换）
- `GenTime`：TSA 认证的签名时间（UTC）
- TSA 自身的签名（RSA/ECDSA）

---

### Countersignature（反签名）

Countersignature 是 RFC 3161 时间戳在 Authenticode 上的具体实现形式。在 PKCS#7 `SignedData` 的 `signerInfos` 结构中：

```text
PKCS#7 SignedData
└─ signerInfos[0]  (主签名者，代码发布者)
    └─ unauthenticatedAttributes
        └─ countersignature (OID 1.2.840.113549.1.9.6)  [传统 RFC 2459 模式]
           或
        └─ id-smime-aa-timeStampToken (OID 1.2.840.113549.1.9.16.2.14) [RFC 3161 TST]
```

**两种 Countersig 模式对比：**

| 维度 | 传统 Countersignature | RFC 3161 TST |
|---|---|---|
| 标准 | PKCS#9 | RFC 3161 |
| 内容 | CA 对主签名值的签名 | TSA 对主签名哈希+时间的签名 |
| 含时间 | 是（但非权威） | 是（TSA 权威时间） |
| Windows 支持 | XP 起 | Vista 起（推荐） |
| 工具 | 已逐渐被 RFC 3161 取代 | 当前主流 |

### "证书过期后签名仍有效"的原理

有了有效的 RFC 3161 时间戳后，Windows（通过 `WinVerifyTrust`）在验签时：

```text
验签逻辑（简化）：

1. 解析 WIN_CERTIFICATE → PKCS#7 SignedData
2. 验证主签名（代码发布者证书 + 哈希）
3. 在 unauthenticatedAttributes 中找到 RFC 3161 TST
4. 验证 TST 本身（TSA 证书链 + TSA 签名）
5. 从 TST 取出 GenTime（签名时间戳）
6. 检查：在 GenTime 时，主签名者证书是否有效（未过期、未吊销）？
          └─ YES → 签名视为在证书有效期内完成 → 继续信任，即使证书现已过期
          └─ NO  → 签名无效
```

关键：验签只要求证书在**签名时间点**有效，而非验签的当前时间点。这是"使用时间戳后，证书过期不影响历史签名"的根本原因。

> [!note] 吊销（Revocation）与时间戳
> 若签名者私钥在签名后被泄露，CA 吊销该证书，则**时间戳无法救回**此场景——因为吊销表示密钥从发布即不可信，与有效期无关。吊销检查（CRL/OCSP）在验签时会实时进行。

### Authenticode 完整验证链

```text
signtool verify /v /pa target.exe

验证层次：

① 文件哈希层
   重新计算文件哈希（排除 CheckSum / DataDirectory[4] / 证书数据）
   vs PKCS#7 SignedData.encapContentInfo 中的 SpcPeImageData

② 主签名层
   签名者公钥（证书内） 验证 SignerInfo.signature

③ 证书链层
   叶证书 → 中间 CA → 根 CA → Windows 受信根存储

④ 时间戳层
   RFC 3161 TST 内的 TSA 证书链 → TSA 根 CA
   GenTime 时，主签名者证书有效期 ✓

⑤ 吊销检查层（需联网）
   CRL / OCSP 查询各证书吊销状态
```

**`signtool verify` 命令参数：**

```cmd
:: 基本验证（仅 Authenticode 策略）
signtool verify /pa target.exe

:: 详细输出（含证书链、时间戳信息）
signtool verify /v /pa target.exe

:: 验证驱动签名（WHQL 策略）
signtool verify /kp target.sys

:: 指定根证书存储（企业内网 CA）
signtool verify /pa /r "LocalMachine\Root" target.exe

:: 查看所有签名（含 Countersignature 时间戳）
signtool verify /v /all target.exe
```

输出关键字段解读：

```text
Verified: C:\target.exe
Number of files successfully Verified: 1

Hash of file (sha256): ABCDEF...

Signing Certificate Chain:
    DigiCert SHA2 Assured ID Code Signing CA
        Issued to:   ExampleCorp Inc.
        Expires:     2025-06-01 00:00:00
        SHA1 hash:   ...

The signature is timestamped: 2024-03-15 10:23:45
Timestamp Verified by:
    DigiCert Timestamp 2023
        ...

Successfully verified: target.exe
```

若签名证书已过期但时间戳合法，输出会显示：

```text
WARNING: The signing certificate has expired.
The signature is timestamped: <date within cert validity>
Successfully verified: target.exe   ← 仍然通过，因为时间戳有效
```

### 双重签名（Dual Signature）与嵌套 SignedData

Windows 8.1 起支持**双重签名**：在同一 `WIN_CERTIFICATE` 条目中同时包含 SHA-1 和 SHA-256 算法的签名，以同时兼容老旧系统和新系统的安全要求。实现方式是在 `unauthenticatedAttributes` 中以 OID `1.3.6.1.4.1.311.2.4.1`（`SPC_NESTED_SIGNATURE`）嵌套第二个完整的 `PKCS#7 SignedData`：

```text
WIN_CERTIFICATE.bCertificate
└─ PKCS#7 SignedData  (SHA-1，主签名)
    └─ signerInfos[0].unauthenticatedAttributes
        ├─ countersignature (RFC 3161 TST，SHA-1 时间戳)
        └─ SPC_NESTED_SIGNATURE (OID 1.3.6.1.4.1.311.2.4.1)
            └─ PKCS#7 SignedData (SHA-256，嵌套签名)
                └─ signerInfos[0].unauthenticatedAttributes
                    └─ countersignature (RFC 3161 TST，SHA-256 时间戳)
```

```cmd
:: signtool 添加第二个签名（不替换第一个）
signtool sign /as /fd sha256 /tr http://timestamp.digicert.com /td sha256 target.exe
:: /as = append signature（追加，而非替换）
```

> [!warning] 逆向/安全分析提醒
> 某些恶意软件利用第二个嵌套 `SignedData` 藏匿非标准内容（超大证书链、隐写数据），因为安全产品有时只解析第一层 PKCS#7 而忽略嵌套结构。完整分析时应递归解析所有嵌套签名块。

### 实战：用 osslsigncode 查看时间戳

```bash
# Linux 上分析 Windows PE 签名
osslsigncode verify -in target.exe

# 输出示例：
# Signature verification: ok
# Number of signers: 1
#   Signer #0:
#     Subject: CN=ExampleCorp Inc., O=ExampleCorp Inc.
#     Signing time: Mar 15 10:23:45 2024 GMT  ← Countersignature 时间戳
#     PKCS9 signing time: Mar 15 10:23:45 2024 GMT

# 提取嵌入的 PKCS#7 blob 做进一步分析
osslsigncode extract-signature -in target.exe -out sig.p7b
openssl pkcs7 -inform DER -in sig.p7b -print_certs -text | head -100
```：它用**文件偏移**寻址（非 RVA），数据位于文件末尾不被映射进内存，核心结构 `WIN_CERTIFICATE` 承载 **PKCS#7 Authenticode 签名**。签名计算时需排除 `CheckSum`、目录项自身和证书数据三部分，以避免循环依赖。理解这一结构，是分析 Windows 代码完整性机制、反恶意软件手法和驱动签名校验的重要基础。
