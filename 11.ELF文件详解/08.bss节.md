# 详解ELF文件(八).bss节

.bss节（Block Started by Symbol）是ELF（Executable and Linkable Format）文件中一个特殊的节区，用于存储未初始化的全局变量和静态变量。它是一个重要的优化机制，通过不占用实际文件空间来节省磁盘空间。

## .bss节基本概念

.bss节是ELF文件中专门用于存储未初始化全局变量和静态变量的节区。它的名称来源于早期汇编语言中的助记符"Block Started by Symbol"，最早出现在 1956 年 FAP（Fortran Assembly Program）汇编器中，用于声明一块以某符号为起始的内存区域。

与 [[07.data节|.data节]] 不同，.bss节在可执行文件中**不占用实际的磁盘空间**——节头表中只有元数据（地址、大小、标志），没有对应的文件字节。这是 `SHT_NOBITS` 类型的核心含义。

## 节头属性

.bss 的 `sh_type = SHT_NOBITS` 是它与其它数据节最本质的差异——`NOBITS` 表示"该节在文件中不占字节"（高亮为本节）：

| 节 | sh_type | sh_flags | 占文件空间 |
|---|---|---|---|
| .text | SHT_PROGBITS | SHF_ALLOC \| SHF_EXECINSTR (AX) | 是 |
| .rodata | SHT_PROGBITS | SHF_ALLOC (A) | 是 |
| .data | SHT_PROGBITS | SHF_ALLOC \| SHF_WRITE (WA) | 是 |
| **.bss** | **SHT_NOBITS** | **SHF_ALLOC \| SHF_WRITE (WA)** | **否** |

注意：.bss 与 .data 共享相同的 `sh_flags`（`SHF_ALLOC | SHF_WRITE`），因此两者在加载后都落入可读写的 `PT_LOAD` 段。区别只在于 `sh_type`——`SHT_NOBITS` vs `SHT_PROGBITS`。

`sh_size` 字段记录了 .bss 节在**内存**中应占用的字节数，加载器依此在内存中分配空间并清零，但这个大小不对应任何文件字节。

## .bss节存储的内容

### 1. 未初始化的全局变量

```c
int global_uninitialized;        // 存储在.bss节
char buffer[1024];               // 存储在.bss节
double large_array[10000];       // 存储在.bss节
```

### 2. 显式初始化为0的全局变量

```c
int global_zero = 0;             // 存储在.bss节（优化）
static int static_zero = 0;      // 存储在.bss节（优化）
```

C 标准规定所有未初始化的全局/静态变量初始值为 0，因此显式写 `= 0` 与不写等价，编译器将两者统一放入 .bss。

### 3. 未初始化的静态变量

```c
static int static_uninitialized; // 存储在.bss节
void function() {
    static int local_static;     // 存储在.bss节
}
```

## .bss节的重要特性

### 1. 零初始化（C 标准保证）

C 标准（ISO/IEC 9899）第 6.7.9 节规定：具有静态存储期（global、static 关键字）的变量如果没有显式初始值，其值被初始化为 0（数值类型）或空指针（指针类型）或每个成员为 0 的结构体。这一行为由运行时环境（操作系统内核或启动代码）保证，实现上依赖 .bss 的零清。

### 2. 不占用文件空间

.bss节在可执行文件中只占用元数据空间，不存储实际的数据内容。这使得包含大量未初始化数组或缓冲区的程序文件保持较小的体积。

### 3. 运行时分配

当程序加载时，操作系统根据.bss节的大小信息为其分配内存，并将所有内容清零。

## SHT_NOBITS 原理：为什么不占文件空间

`SHT_NOBITS` 的语义在 ELF 规范中明确定义：该节区**在文件中不占用任何字节**。尽管节头表中记录了 `sh_size`（内存大小）和 `sh_offset`（形式上的文件偏移），但实际上在 `sh_offset` 处读取的字节属于文件中的其他内容（或超出文件范围）。

从 `PT_LOAD` 段的角度理解更直观：

```text
# 可读写段程序头（代表性示例，非本机实跑）
$ readelf -l a.out
  LOAD  0x002e10  0x0000000000003e10  0x0000000000003e10
        FileSiz=0x000220  MemSiz=0x000228  Flags=RW
        
# .data 节大小 = 0x220，.bss 节大小 = 0x8
# FileSiz = 0x220（只有 .data 的字节在文件里）
# MemSiz  = 0x228（.data + .bss 的内存合计）
```

加载器读取这个段时：
1. `mmap` 文件的 `[p_offset, p_offset + p_filesz)` 字节到 `[p_vaddr, p_vaddr + p_filesz)`
2. 对 `[p_vaddr + p_filesz, p_vaddr + p_memsz)` 这段额外内存**清零**
3. 这段额外内存就是 .bss 节所在区域

## COMMON 符号与 .bss

### COMMON 符号的定义

在目标文件（`.o`）中，未初始化的全局变量（非 `static`）并不直接放入 .bss 节，而是作为 `COMMON` 符号（符号表中 `st_shndx = SHN_COMMON`）存在。

COMMON 符号允许**多个编译单元各自声明同名全局变量，链接器负责合并**——取所有声明中最大的 `st_size` 作为最终大小，确保任何声明都能访问到足够大的存储空间。这与 C 语言传统的"强弱定义"语义对应：

```c
// file1.c
int global_buf[100];    // COMMON 符号，大小 400 字节

// file2.c
int global_buf[200];    // COMMON 符号，大小 800 字节
// 链接器合并：取 max(400, 800) = 800 字节，放入 .bss
```

### COMMON 与 .bss 的区别

| 属性 | COMMON（目标文件中）| .bss（可执行文件中）|
|---|---|---|
| 所在阶段 | 编译后目标文件 | 链接后可执行文件/共享库 |
| 符号 sh_shndx | SHN_COMMON | 指向 .bss 节的节索引 |
| 允许重复定义 | 是（链接器合并）| 否（已合并为唯一符号）|
| 大小确定 | 编译时已知 | 链接后确定 |

```bash
# 在目标文件中看到 COMMON 符号（大写 C）
nm foo.o | grep ' C '

# 在最终可执行文件中已转为 .bss 符号（大写 B）
nm a.out | grep ' B '
```

### -fno-common 选项

GCC 从 GCC 10 开始，**默认启用 `-fno-common`**，将未初始化全局变量直接放入 .bss（而非 COMMON）。这意味着多次定义同名全局变量会报链接错误，符合 C++ 语义。

```bash
gcc -fcommon -o a.out foo.c     # 旧行为：使用 COMMON 符号
gcc -fno-common -o a.out foo.c  # 新默认：直接放 .bss，重复定义报错
```

## 边界符号：__bss_start、__bss_end、_end

链接器（GNU ld）在链接脚本中为 .bss 节的边界自动生成符号，供运行时代码使用：

### 标准边界符号

| 符号名 | 含义 |
|---|---|
| `__bss_start` 或 `__bss_start__` | .bss 节在内存中的起始地址 |
| `__bss_end` 或 `__bss_end__` 或 `_ebss` | .bss 节在内存中的结束地址 |
| `_end` 或 `end` | 整个数据段（含 .bss）的结束地址，也是堆的初始起点 |

### 链接脚本定义

```ld
/* 典型嵌入式/裸机链接脚本片段 */
.bss :
{
    __bss_start__ = .;
    *(.bss)
    *(.bss.*)
    *(COMMON)
    . = ALIGN(4);
    __bss_end__ = .;
} > RAM

_end = .;   /* 堆的起点 */
```

### 在 C 代码中使用

```c
extern char __bss_start__;
extern char __bss_end__;

// 裸机启动代码：手动清零 .bss
void bss_init(void) {
    char *p = &__bss_start__;
    while (p < &__bss_end__) {
        *p++ = 0;
    }
}
```

### 在 Linux 用户态程序中的意义

Linux 程序不需要手动清零 .bss，内核在加载时已完成此操作。但 `_end` 符号仍有用途：`brk()`/`sbrk()` 系统调用用于扩展堆空间，堆的初始地址即 `_end`。

## 零初始化的底层机制

### Linux 内核的实现方式

Linux 内核在 `execve()` 加载 ELF 时，对 .bss 区域使用 `mmap(MAP_ANONYMOUS | MAP_PRIVATE)` 分配匿名映射：

```c
/* 内核伪代码（简化） */
// 映射 .data 部分（有文件内容）
mmap(p_vaddr, p_filesz, PROT_READ|PROT_WRITE,
     MAP_PRIVATE|MAP_FIXED, fd, p_offset);

// 扩展映射以覆盖 .bss（无文件内容，清零）
mmap(p_vaddr + p_filesz, p_memsz - p_filesz, PROT_READ|PROT_WRITE,
     MAP_ANONYMOUS|MAP_PRIVATE|MAP_FIXED, -1, 0);
```

`MAP_ANONYMOUS` 匿名映射页由内核的"零页"（zero page）提供写时复制：
- 初始时所有匿名页的页表项指向同一个全零物理页（内核维护的"零页"），页表权限为只读（COW）
- 第一次写入 .bss 中任一变量时，触发 COW 缺页，内核分配新物理页并复制零内容，修改页表指向新页并设为可写
- 对于**从未写入的 .bss 页**，零页始终共享，不占任何物理内存

这一"惰性清零"机制使即使声明了 1MB 的未初始化全局数组，如果程序从未访问它，也**不占用任何物理内存**。

### 嵌入式裸机的实现方式

在没有操作系统的裸机环境（如 ARM Cortex-M 微控制器），.bss 的零初始化由启动代码（`startup.s` 或 `Reset_Handler`）负责，在 `main()` 被调用之前执行：

```c
/* ARM Cortex-M 典型启动代码（C 版本） */
void Reset_Handler(void) {
    /* 1. 初始化 .data：从 Flash 复制初始值到 RAM */
    uint32_t *src = &_etext;        /* Flash 中 .data 的 LMA */
    uint32_t *dst = &_sdata;        /* RAM 中 .data 的 VMA */
    while (dst < &_edata) {
        *dst++ = *src++;
    }
    
    /* 2. 清零 .bss */
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }
    
    /* 3. 调用 main */
    main();
}
```

## .bss节与.data节的区别

### 1. 存储内容差异

- .bss节：存储未初始化或初始化为0的变量
- [[07.data节|.data节]]：存储已初始化且初始值非0的变量

### 2. 文件空间占用

- .bss节：在可执行文件中不占用实际磁盘空间
- .data节：在可执行文件中占用实际磁盘空间，存储初始值

### 3. 加载过程

- .bss节：加载时只需要分配内存并清零
- .data节：加载时需要从文件中读取初始值到内存

## .bss节在执行视图中的位置

在可执行文件的执行视图中，.bss节通常与 [[07.data节|.data节]] 一起被合并到一个可读写段中。这是因为它们都具有可读写的属性。

典型的内存布局：

```
低地址
+------------------+
|     .text        |  只读可执行
+------------------+
|     .rodata      |  只读
+------------------+
|     .data        |  可读写（已初始化）
+------------------+
|     .bss         |  可读写（初始为0）
+------------------+
高地址
```

## .bss节的内存管理

### 1. 内存分配

在程序加载时，操作系统会为.bss节分配足够的内存空间，并将所有内容初始化为零。Linux 上通过 `mmap(MAP_ANONYMOUS)` 实现惰性分配，嵌入式系统通过启动代码主动清零。

### 2. 访问权限

.bss节具有读写权限（`PROT_READ | PROT_WRITE`），程序可以随时读取和修改其中的数据。

### 3. 生命周期

.bss节中的变量具有与程序相同的生命周期，从程序启动到程序结束一直存在。

## .bss节的优化优势

### 1. 节省磁盘空间

通过不存储实际数据，.bss节显著减少了可执行文件的大小。

```c
// 下面这个声明只增加节头表中 sh_size 字段的值，不增加文件字节
double huge_matrix[1024][1024];  // 8 MB，但文件体积不增加
```

这对嵌入式系统意义重大：固件烧录到 Flash 时，.bss 不占用 Flash 空间，节省了宝贵的只读存储器。

### 2. 提高加载效率

由于不需要从磁盘读取数据，程序加载.bss节的速度更快（不产生文件 I/O）。惰性清零机制进一步优化：只有被实际访问的内存页才会被物理分配和清零。

### 3. 物理内存节省

得益于惰性清零 + 零页 COW，程序中的 .bss 变量直到首次读写前不占用任何物理 RAM。这对内存受限系统至关重要。

### 4. 简化程序初始化

操作系统自动将.bss节清零，简化了程序的初始化过程。

## 大数组的影响：.bss vs 动态分配

| 分配方式 | .bss 全局数组 | malloc/new 动态分配 |
|---|---|---|
| 文件大小 | 不增加 | 不增加 |
| 内存占用（未访问）| 极小（零页共享）| 0（未分配）|
| 内存占用（已访问）| 约等于数组大小 | 约等于数组大小 + 堆元数据 |
| 生命周期 | 程序全生命期 | 手动管理（malloc/free）|
| 线程安全 | 无保护，需同步 | 取决于分配器实现 |
| 初始值 | 保证为 0 | 未初始化（malloc）或 0（calloc）|

结论：对于生命周期等同于程序的大缓冲区，全局 .bss 数组在简洁性上有优势；对于动态大小或按需分配的场景，应使用堆分配。

## 实战：分析.bss节

### 1. readelf：NOBITS 节的特殊表现

```bash
readelf -S a.out                # 注意 .bss 的 Type 是 NOBITS
```

```text
# 示例输出（代表性，非本机实跑）
$ readelf -S a.out
  [Nr] Name   Type     Address          Off    Size   ES Flg Lk Inf Al
  [25] .bss   NOBITS   0000000000004010 003010 000008 00  WA  0   0  4
```

注意：`.bss` 的 `Off`（文件偏移）后**没有对应的真实字节**——`Size` 记录的是要在内存中分配的字节数。

### 2. 尝试 dump .bss 会失败（正说明它不占文件空间）

```bash
readelf -x .bss a.out
```

```text
# 示例输出（代表性）
readelf: Section '.bss' has no data to dump.
```

这条报错恰恰印证了 .bss 的本质：文件里根本没有它的数据内容。

### 3. size：bss 列计入内存但不计入文件

```bash
size a.out
```

```text
# 示例输出（代表性）
   text    data     bss     dec     hex filename
   1591     600    1056    2647     a57 a.out
```

### 4. nm：查看 .bss 中的符号

```bash
nm a.out | grep ' [bB] '   # B = 全局 .bss 变量，b = 静态/局部 .bss 变量
```

```text
# 示例输出（代表性，非本机实跑）
0000000000004010 B global_uninitialized
0000000000404020 B big_buffer
0000000000004018 b static_uninitialized
```

### 5. 对比有无大数组时的文件大小

```bash
# 全局 .bss 数组：文件几乎不变
echo 'char buf[1048576];' > big_bss.c && gcc big_bss.c -o big_bss.out
ls -lh big_bss.out       # 几 KB

# 全局 .data 数组（已初始化）：文件增大 1MB
echo 'char buf[1048576] = {1};' > big_data.c && gcc big_data.c -o big_data.out
ls -lh big_data.out      # 超过 1MB

# 对比 bss 列
size big_bss.out big_data.out
```

```bash
readelf -l a.out | grep -A3 'LOAD.*RW'
```

```text

  LOAD  0x002e10  0x0000000000003e10  0x0000000000003e10
        0x000220  0x000228  RW  0x1000
  # p_filesz = 0x220 (.data 大小)
  # p_memsz  = 0x228 (.data + .bss 大小)
  # .bss 大小 = 0x228 - 0x220 = 0x8 字节
```

## .bss节在不同阶段的作用

### 1. 编译阶段

- 编译器识别程序中未初始化的全局变量和静态变量
- 将这些变量的信息（地址、大小、对齐）记录在符号表中，符号的 `st_shndx` 指向 .bss 节（或设置为 `SHN_COMMON`）
- 非 `static` 的未初始化全局变量在 `-fcommon` 模式下生成 COMMON 符号

### 2. 链接阶段

- 链接器将所有目标文件的 .bss 节合并，累加大小
- 将 COMMON 符号分配到 .bss 节（取最大 `st_size`）
- 计算 .bss 节的总 `sh_size`，但**不写入任何文件字节**
- 在输出的 `PT_LOAD` 段头中，`p_memsz = p_filesz + bss_size`

### 3. 加载阶段

- 加载器为.bss节分配内存空间（Linux：`mmap(MAP_ANONYMOUS)`；裸机：启动代码循环清零）
- 操作系统将.bss节的所有内容初始化为零

### 4. 执行阶段

- 程序可以读取和修改.bss节中的数据
- 变量在整个程序执行期间保持有效

## .bss节的历史背景

.bss节的概念来源于早期的汇编语言和链接器设计。在计算机发展的早期阶段，内存和存储空间都非常宝贵，因此设计一种机制来优化未初始化数据的存储是非常重要的。.bss节的设计体现了早期计算机科学家对资源优化的深刻思考。

最早的 .bss 实现中，名称代表"Block Started by Symbol"，指以符号名标记起始地址的一块内存区域。在磁带存储时代，省去未初始化数据的存储意味着显著减少程序加载时间。

## .bss节的安全考虑

### 1. 数据安全性

由于.bss节在程序启动时被自动清零，确保了未初始化变量不会包含随机的"垃圾值"，提高了程序的安全性和可预测性。这是防止"使用未初始化内存"漏洞（CWE-457）的重要机制。

### 2. 信息泄露防护

通过初始化为零，.bss 节避免了可能存在的敏感信息泄露：若操作系统重用物理内存页（来自其他进程），零初始化可防止新进程读取旧内容（内核在分配匿名页时始终清零）。

### 3. 内存保护

.bss 所在 `PT_LOAD` 段的 `p_flags` 不含 `PF_X`，保证了 .bss 变量所在内存页不可执行（NX 保护），防止攻击者在 .bss 缓冲区写入 shellcode 并执行。

### 4. 栈 Canary 与 .bss 的关系

全局变量（.bss 和 .data）不受栈 canary 保护，但因为有 NX 保护（不可执行），溢出攻击需要通过其他手段（ROP、GOT 覆写等）才能获得控制流。

## 实际示例

考虑以下C代码：

```c
#include <stdio.h>
#include <stdlib.h>

// 未初始化的全局变量 - 存储在.bss节
int global_uninit;
char big_buffer[1024*1024];  // 1MB的缓冲区

// 显式初始化为0的全局变量 - 通常也存储在.bss节
int global_zero = 0;

// 已初始化的全局变量 - 存储在.data节
int global_init = 42;

// 未初始化的静态变量 - 存储在.bss节
static int static_uninit;

void function() {
    // 未初始化的局部静态变量 - 存储在.bss节
    static int local_static_uninit;

    // 已初始化的局部静态变量 - 存储在.data节
    static int local_static_init = 100;

    // 普通局部变量 - 存储在栈上，不在.bss节
    int local_var = 200;

    printf("bss variables: %d, %d, %d\n",
           global_uninit, static_uninit, local_static_uninit);
}

int main() {
    printf("Global uninitialized: %d\n", global_uninit);
    printf("Global zero: %d\n", global_zero);
    printf("Big buffer address: %p\n", (void*)big_buffer);

    // 动态分配的内存 - 不在.bss节，而在堆上
    char *heap_memory = malloc(1024);
    printf("Heap memory address: %p\n", (void*)heap_memory);

    free(heap_memory);
    return 0;
}
```

在这个例子中：

- `global_uninit`、`big_buffer`、`global_zero`、`static_uninit`和`local_static_uninit`存储在.bss节
- `global_init`和`local_static_init`存储在 [[07.data节|.data节]]
- `local_var`存储在栈上
- `heap_memory`指向的内存存储在堆上

## 32位与64位差异

| 特性 | 32位（i386）| 64位（x86-64）|
|---|---|---|
| 指针大小 | 4 字节（NULL = 0x00000000）| 8 字节（NULL = 0x0000000000000000）|
| 典型 .bss 起始地址 | `0x0804b000` 附近（非PIE）| `0x601040` 附近（非PIE）|
| 大型数组影响 | 相同（.bss 不占文件，只占内存）| 相同 |
| 零页共享 | 4 KB 页 | 4 KB 页（huge page 2MB 也支持）|

## 总结

.bss节是ELF文件中一个重要的优化机制，专门用于存储未初始化的全局变量和静态变量。它通过不占用实际文件空间的方式显著减小了可执行文件的大小，并通过操作系统自动清零的机制确保了数据的安全性和可预测性。

核心机制三要点：（1）`SHT_NOBITS` 使节在文件中无字节，只在节头表记录内存大小；（2）加载时通过 `mmap(MAP_ANONYMOUS)` + 零页 COW 惰性分配物理内存；（3）COMMON 符号机制允许多编译单元共享同名未初始化全局变量（GCC 10 后默认禁用）。理解 .bss 的工作原理对于内存优化、嵌入式启动代码设计和安全分析均有重要意义。
