# 详解ELF文件(五十三).ELF加载器内核实现

> [!abstract] TL;DR
> 当用户执行 `execve` 系统调用时，Linux 内核通过 `fs/binfmt_elf.c` 中的 `load_elf_binary` 函数解析 ELF 文件，将 `PT_LOAD` 段用 `mmap` 映射到虚拟地址空间，构造包含运行时元数据的辅助向量（auxv），在 `randomize_va_space` 控制下应用 ASLR，最终通过 `start_thread` 跳转到动态链接器或 ELF 入口点，完成从内核态到用户态的过渡。理解这条路径是逆向分析、漏洞挖掘和容器安全研究的核心基础。

## 概述与定位

ELF 可执行文件并不能自己运行起来——必须有人"读懂"它的结构、把代码和数据搬进内存、建好栈和寄存器，再把控制权交出去。这个"人"就是操作系统内核中的 **ELF 二进制加载器（ELF binary loader）**。

在 Linux 内核源码树中，加载器的核心实现位于 `fs/binfmt_elf.c`。它通过内核的 **binfmt 框架**（binary format framework）注册，在 `execve` 系统调用内被分派。整条链路从用户调用 `execve` 开始，到 `_start`（用户态入口，通常是 `ld.so` 的 `_start` 或静态可执行文件的 `_start`）开始执行结束，中间穿越十几个内核函数和数百行核心代码。

理解内核加载器的意义在于：

- **逆向分析**：知道哪些信息由内核填入（环境变量指针、auxv、argv 等），哪些由动态链接器填入，才能正确解读进程内存布局。
- **漏洞挖掘**：`execve` 处理路径上有多处历史 CVE（如 `vDSO` 映射、`AT_EXECFN` 字符串拷贝等），理解路径才能审计。
- **沙箱/容器安全**：seccomp 规则对 `execve` 的过滤、namespace 隔离与 ELF 加载的交互都在这条路径上发生。
- **调试工具原理**：`strace`、GDB 的 `exec` 事件、`ptrace(PTRACE_TRACEME)` 都在加载路径的特定点被触发。

本篇完整还原从 `execve` 系统调用入口到第一条用户态指令的全过程，聚焦内核代码路径，辅以数据结构和 ASLR 实现细节。

## 原理与机制

### execve 系统调用入口

用户程序执行：
```c
execve("/usr/bin/ls", argv, envp);
```
内核侧的系统调用入口是 `sys_execve`（x86-64 上实际为 `__x64_sys_execve`），最终收敛到 `do_execve` → `do_execveat_common`：

```c
// fs/exec.c（概要，非完整代码）
int do_execveat_common(int fd, struct filename *filename,
                       struct user_arg_ptr argv,
                       struct user_arg_ptr envp,
                       int flags)
{
    struct linux_binprm *bprm;
    // 1. 分配 bprm 结构（binary parameters）
    bprm = alloc_bprm(fd, filename);
    // 2. 读取文件头部（前 BINPRM_BUF_SIZE = 256 字节）到 bprm->buf
    retval = bprm_execve(bprm, fd, filename, flags);
    // ... 错误路径清理 ...
}
```

`linux_binprm`（简称 `bprm`）是贯穿整个 `execve` 路径的核心数据结构，记录可执行文件的所有运行时信息：文件对象、文件头缓冲区、credential、argv/envp 字符串、目标入口点等。

### binfmt 分派机制

`bprm_execve` 调用 `search_binary_handler`，遍历内核注册的所有二进制格式处理器（`formats` 链表），尝试识别并加载：

```c
// 注册的格式处理器（按优先级排列的常见子集）
- binfmt_script   // #! shebang 脚本
- binfmt_misc     // /proc/sys/fs/binfmt_misc 用户自定义格式
- binfmt_elf      // ELF 文件（我们关注的）
- binfmt_elf_fdpic // MMU-less 系统的 FDPIC ELF
```

`binfmt_elf` 的识别方式：检查 `bprm->buf` 前 4 字节是否为 `\x7fELF`（ELF magic number）。识别成功后，调用其 `.load_binary` 回调，即 `load_elf_binary`。

### load_elf_binary 主流程

`load_elf_binary`（`fs/binfmt_elf.c`）是加载过程的核心，逻辑可分为以下阶段：

**阶段一：解析和验证 ELF 头**

```c
// 读取完整 ELF 头（Elf64_Ehdr）
loc->elf_ex = *((struct elfhdr *)bprm->buf);
if (loc->elf_ex.e_ident[EI_MAG0] != ELFMAG0) { /* ... */ }
// 验证 e_type 必须是 ET_EXEC 或 ET_DYN
if (loc->elf_ex.e_type != ET_EXEC && loc->elf_ex.e_type != ET_DYN)
    goto out;
// 验证架构匹配（e_machine）
if (!elf_check_arch(&loc->elf_ex))
    goto out;
```

**阶段二：读取程序头表（Program Header Table）**

```c
elf_phdata = load_elf_phdrs(&loc->elf_ex, bprm->file);
// elf_phdata 是 Elf64_Phdr 数组，包含所有程序头条目
```

**阶段三：处理解释器（动态链接器）**

遍历程序头，寻找 `PT_INTERP` 条目：
```c
for (i = 0; i < loc->elf_ex.e_phnum; i++) {
    if (elf_ppnt->p_type == PT_INTERP) {
        // 读取解释器路径（如 /lib64/ld-linux-x86-64.so.2）
        // 打开解释器文件，读取其 ELF 头
        // 验证解释器本身是合法的 ELF（ET_DYN 或 ET_EXEC）
        interpreter = open_exec(elf_interpreter);
        // 读取解释器的程序头表
        interp_elf_phdata = load_elf_phdrs(&interp_elf_ex, interpreter);
    }
}
```

若不存在 `PT_INTERP`，则为**静态链接可执行文件**，跳过解释器加载。

**阶段四：准备新进程的地址空间**

```c
// 清空当前进程的旧地址空间，准备新地址空间
retval = begin_new_exec(bprm);
// 设置进程名、信号处理为默认值、关闭 O_CLOEXEC 文件描述符等
setup_new_exec(bprm);
```

`begin_new_exec` 是"不归点"（point of no return）——一旦调用成功，内核就开始销毁旧进程的地址空间，不能再回退到旧程序。这解释了为什么 `execve` 失败在参数验证阶段返回（旧程序继续运行），而深入执行后的错误会导致进程崩溃（SIGSEGV/SIGKILL），而非返回错误码。

**阶段五：映射 ELF 段（核心）**

详见下一节"结构/算法/伪代码详解"中的 PT_LOAD 处理。

**阶段六：构建用户栈和辅助向量**

```c
retval = setup_arg_pages(bprm, randomize_stack_top(STACK_TOP), executable_stack);
// 将 argv、envp 字符串推入栈顶
// 构建辅助向量（AT_* 条目）
create_elf_tables(bprm, &loc->elf_ex,
                  load_addr, interp_load_addr,
                  e_entry);
```

**阶段七：设置入口点，跳转用户态**

```c
// 确定入口点：有解释器则跳解释器，否则跳 ELF 的 e_entry
if (elf_interpreter)
    elf_entry = load_elf_interp(&interp_elf_ex, interpreter,
                                 &interp_load_addr, interp_elf_phdata);
else
    elf_entry = loc->elf_ex.e_entry;

// 设置寄存器（x86-64）：rip = elf_entry，rsp = 栈顶
start_thread(regs, elf_entry, bprm->p);
```

`start_thread` 将 `pt_regs` 中的指令指针设置为 `elf_entry`，将栈指针设置为栈顶（`bprm->p` 是栈顶指针）。内核从系统调用返回后，CPU 跳转到 `elf_entry` 开始执行——用户态的第一条指令。

## 结构/算法/伪代码详解

### PT_LOAD 段的 mmap 映射策略

PT_LOAD 是 ELF 中的可加载段，每个 PT_LOAD 段最终通过一次或两次 `mmap` 映射到进程地址空间。

**关键字段**：
- `p_offset`：段在文件中的偏移
- `p_vaddr`：期望的虚拟地址（对 ET_EXEC 是固定地址，对 ET_DYN 是相对偏移）
- `p_filesz`：文件中的字节数
- `p_memsz`：内存中的字节数（`p_memsz >= p_filesz`，差值为 BSS 零填充区域）
- `p_flags`：权限标志（PF_R/PF_W/PF_X）
- `p_align`：对齐要求（通常为页大小 0x1000 或大页 0x200000）

**ET_EXEC（固定地址可执行文件）的映射**：

```c
// 伪代码：ET_EXEC PT_LOAD 映射
for each PT_LOAD phdr in elf_phdata:
    vaddr = phdr.p_vaddr  // 固定虚拟地址，不加任何偏移
    
    // mmap 文件内容（p_filesz 对应的部分）
    // 地址对齐到页边界
    addr = ELF_PAGESTART(vaddr)          // 向下对齐到页
    off  = phdr.p_offset - ELF_PAGEOFFSET(vaddr)  // 文件偏移对齐
    len  = ELF_PAGEALIGN(phdr.p_filesz + ELF_PAGEOFFSET(vaddr))
    
    prot = PROT_NONE
    if phdr.p_flags & PF_R: prot |= PROT_READ
    if phdr.p_flags & PF_W: prot |= PROT_WRITE
    if phdr.p_flags & PF_X: prot |= PROT_EXEC
    
    mmap(addr, len, prot, MAP_PRIVATE|MAP_FIXED, fd, off)
    
    // 如果 p_memsz > p_filesz，BSS 区域需要零填充
    if phdr.p_memsz > phdr.p_filesz:
        // 文件映射尾部到下一页的区域：memset 清零
        // 剩余纯 BSS 页：mmap(MAP_ANONYMOUS) 匿名映射（内核保证零填充）
        bss_start = vaddr + phdr.p_filesz
        bss_end   = vaddr + phdr.p_memsz
        padzero(bss_start)  // 清零页内尾部
        if PAGE_ALIGN(bss_start) < PAGE_ALIGN(bss_end):
            mmap(PAGE_ALIGN(bss_start),
                 PAGE_ALIGN(bss_end) - PAGE_ALIGN(bss_start),
                 prot, MAP_ANONYMOUS|MAP_FIXED|MAP_PRIVATE, -1, 0)
```

**ET_DYN（位置无关可执行文件/共享库）的映射**：

ET_DYN 文件的 `p_vaddr` 是相对偏移，内核需要先确定**加载基址**（load address），再加上每个段的相对偏移：

```c
// 伪代码：ET_DYN 基址选择
if e_type == ET_DYN:
    if ASLR 启用 (randomize_va_space >= 1):
        // 通过 mmap 探测找一块足够大的空闲区域
        // 具体地址由内核的 mmap 地址分配器决定（受 ASLR 随机化）
        load_addr = mmap(0, total_size, PROT_NONE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)
        // 解除这次探测映射，后面再按 p_vaddr 偏移重映射
        munmap(load_addr, total_size)
        // load_bias = load_addr - min(p_vaddr across all PT_LOAD)
    else:
        load_bias = 0  // ASLR 关闭时，加载到链接时的地址
    
    for each PT_LOAD:
        actual_vaddr = phdr.p_vaddr + load_bias
        // 其余与 ET_EXEC 相同
```

实际内核实现（`load_elf_binary` 中的 `ELF_ET_DYN_BASE` 和 `mmap_base`）更复杂，涉及 `mm->mmap_base` 的随机化（见 ASLR 节）。

### MAP_FIXED 与映射合并

内核使用 `MAP_FIXED` 标志，强制将段映射到指定地址——即使该地址已有映射，`MAP_FIXED` 会静默覆盖（这是一个历史遗留的危险行为，Linux 5.17 引入 `MAP_FIXED_NOREPLACE` 用于更安全的场景）。

链接器通常将相邻的 `PT_LOAD` 段（如 `.text` 和 `.rodata` 合并为一个 `R|X` 段，`.data` 和 `.bss` 合并为一个 `RW` 段）以减少段数量和页对齐浪费。典型的现代 ELF 只有 2-3 个 PT_LOAD 段。

### 辅助向量（auxv）完整构建

辅助向量（Auxiliary Vector）是内核传递给用户态的运行时元数据，以 `{type, value}` 对的形式放在栈上（位于 envp 字符串之上）。类型定义在 `include/uapi/linux/auxvec.h`：

| AT 类型 | 数值 | 内容 | 用途 |
|---------|------|------|------|
| `AT_PHDR` | 3 | 程序头表在内存中的地址 | 动态链接器找程序头 |
| `AT_PHENT` | 4 | 程序头表条目大小（`sizeof(Elf64_Phdr)`） | 遍历程序头 |
| `AT_PHNUM` | 5 | 程序头表条目数量 | 遍历程序头 |
| `AT_PAGESZ` | 6 | 页大小（通常 4096） | 内存对齐 |
| `AT_BASE` | 7 | 解释器（ld.so）的加载基址 | 动态链接器自身重定位 |
| `AT_FLAGS` | 8 | 标志（通常为 0） | 保留 |
| `AT_ENTRY` | 9 | ELF 程序的真正入口点 | ld.so 完成后跳转 |
| `AT_UID` | 11 | 实际用户 ID | 安全决策 |
| `AT_EUID` | 12 | 有效用户 ID | 安全决策 |
| `AT_GID` | 13 | 实际组 ID | 安全决策 |
| `AT_EGID` | 14 | 有效组 ID | 安全决策 |
| `AT_PLATFORM` | 15 | 平台字符串（如 "x86_64"） | 编译时特性检测 |
| `AT_HWCAP` | 16 | CPU 能力位掩码（SSE/AVX 等） | glibc 选择优化实现 |
| `AT_CLKTCK` | 17 | `times()` 的时钟频率 | 时间换算 |
| `AT_SECURE` | 23 | 是否 suid/sgid（1=安全模式） | ld.so 安全限制 |
| `AT_RANDOM` | 25 | 指向 16 字节随机数的指针 | 栈 cookie、PIE 基址种子 |
| `AT_HWCAP2` | 26 | CPU 能力位掩码扩展 | 更新特性检测 |
| `AT_EXECFN` | 31 | 可执行文件路径字符串 | 进程自查 |
| `AT_SYSINFO_EHDR` | 33 | vDSO 的 ELF 头地址 | 快速系统调用 |
| `AT_NULL` | 0 | 列表终止符 | 标识 auxv 结束 |

`create_elf_tables` 函数的栈布局构建顺序（从高地址到低地址）：

```
高地址
├── envp 字符串（null terminated）
├── argv 字符串（null terminated）  
├── AT_EXECFN 字符串（可执行文件路径）
├── AT_PLATFORM 字符串（"x86_64"）
├── AT_RANDOM 的 16 字节随机数
├── ... (padding 至对齐)
├── AT_NULL {0, 0}       ← auxv 末尾哨兵
├── {AT_*, value} 对     ← 各辅助向量条目（从上往下逆序压入）
├── {AT_SYSINFO_EHDR, vdso_addr}
├── NULL                  ← envp 终止
├── envp[n]              ← 指向上方字符串的指针数组
├── envp[0]
├── NULL                  ← argv 终止
├── argv[argc-1]         ← 指向上方字符串的指针数组
├── argv[0]
├── argc                  ← 参数个数
低地址 ← rsp 指向此处
```

### ASLR 实现点：randomize_va_space

`/proc/sys/kernel/randomize_va_space` 控制 ASLR 级别：

- `0`：完全关闭，所有地址确定性
- `1`：随机化栈、mmap 基址、vDSO；不随机化堆
- `2`（默认）：随机化栈、mmap 基址、vDSO、堆

内核的随机化实现分散在多处：

**mmap 基址随机化**（`arch/x86/mm/mmap.c`）：
```c
// mmap_base 计算（简化）
unsigned long arch_mmap_rnd(void)
{
    unsigned long rnd;
    // x86-64: 28 位随机量，左移 12 位（页对齐）= 最多 2^28 * 4096 = 1TB 的随机范围
    rnd = get_random_long() & ((1UL << mmap_rnd_bits) - 1);
    return rnd << PAGE_SHIFT;
}

unsigned long arch_get_mmap_base(unsigned long addr, unsigned long base)
{
    if (current->flags & PF_RANDOMIZE)
        return base + arch_mmap_rnd();  // mmap_base + 随机偏移
    return base;
}
```

**栈随机化**：
```c
// setup_arg_pages 中：
if (current->flags & PF_RANDOMIZE)
    stack_top -= arch_align_stack(stack_top);
// arch_align_stack 引入最多 8MB 的随机偏移
```

**ET_DYN 基址随机化**（PIE 可执行文件）：
```c
// load_elf_binary 中，ET_DYN 类型：
if (!(current->personality & ADDR_NO_RANDOMIZE) &&
    randomize_va_space)
    load_bias = ELF_ET_DYN_BASE;
// ELF_ET_DYN_BASE 在 x86-64 上 = (2/3 * TASK_SIZE)
// 实际基址由首次 mmap 调用的返回值决定（受 mmap_base 随机化影响）
```

**堆随机化**（`brk` 随机化）：
```c
// mm->brk 的初始值在 load_elf_binary 中设置
// set_brk 之后再加随机偏移（randomize_va_space >= 2 时）
if (current->flags & PF_RANDOMIZE)
    mm->brk = mm->start_brk = arch_randomize_brk(mm);
```

**vDSO 随机化**：
vDSO 是一个内核映射的小型共享库（包含 `gettimeofday`、`clock_gettime` 等快速系统调用实现）。其地址通过独立的随机化机制确定，最终通过 `AT_SYSINFO_EHDR` 告知用户态。

### 静态与动态可执行文件的分叉点

```
load_elf_binary
    │
    ├─ 有 PT_INTERP？
    │       │
    │      Yes ──► 加载 ld.so（load_elf_interp）
    │               ─► elf_entry = ld.so 的入口点
    │               ─► AT_BASE = ld.so 加载基址
    │               ─► AT_ENTRY = 原程序 e_entry
    │               ─► 跳转到 ld.so._start
    │
    └─ No（静态链接）
            ─► elf_entry = 程序自身 e_entry（通常是 _start）
            ─► AT_BASE = 0
            ─► 直接跳转到程序 _start
```

动态链接的情况下，第一个运行的用户态代码是 **ld.so 的 `_start`**，而非程序自身的 `_start`。`ld.so` 从 auxv 读取必要信息（`AT_PHDR`、`AT_BASE`、`AT_ENTRY` 等），完成所有共享库的加载和符号解析，最后跳转到 `AT_ENTRY` 指向的程序真正入口。

```bash
# 运行进程后立刻查看（或在 GDB 中）
cat /proc/$(pgrep ls)/maps
# 或
pmap -x $(pgrep ls)
```

**4. GDB 调试加载过程**

```bash
gdb /usr/bin/ls
(gdb) catch exec              # 在 execve 完成时停止
(gdb) run
(gdb) info proc mappings      # 查看内存映射
(gdb) info auxv               # 查看辅助向量
(gdb) x/20xg $rsp             # 查看栈顶，寻找 argc/argv/envp/auxv 布局
```

**5. 验证 ASLR 效果**

```bash
# 运行两次同一程序，比较地址
for i in 1 2; do
    LD_SHOW_AUXV=1 ls 2>&1 | grep AT_ENTRY
done
# 若 ASLR 启用，两次 AT_ENTRY 地址不同（PIE 可执行文件）

# 临时关闭 ASLR（需 root）
echo 0 > /proc/sys/kernel/randomize_va_space
# 或针对单个进程：
setarch x86_64 -R ./prog  # -R = --addr-no-randomize
```

**6. 逆向分析时定位 auxv**

```python
# 在 GDB Python / pwndbg 中寻找 auxv 位置
# auxv 在 envp 数组末尾的 NULL 之后
# 栈布局：argc | argv[] | NULL | envp[] | NULL | auxv[] | AT_NULL
import gdb
sp = int(gdb.parse_and_eval("$rsp"))
argc = int(gdb.parse_and_eval(f"*(long*){sp}"))
# argv 从 sp+8 开始，envp 从 sp+8+(argc+1)*8 开始
# auxv 从 envp 的 NULL 结尾之后开始
```

## 安全性与正确使用

### 历史漏洞与加载路径安全

**CVE-2021-4034（pkexec / PwnKit）**：`execve` 传入空 argv 时，内核代码允许 `argv[0]` 实际上指向 `envp[0]`，导致 `pkexec` 将环境变量误当成程序路径，结合路径处理漏洞实现本地提权。根因在 `argv` 解析路径的边界检查缺失。

**CVE-2017-1000253**：加载 PIE 可执行文件时，若程序头指定的加载地址与内核选定的栈地址重叠，`MAP_FIXED` 会静默覆盖栈区域，导致本地提权。修复方案：内核检测并拒绝 PT_LOAD 段与栈的重叠。

**ASLR 绕过的信息泄漏**：
- `AT_RANDOM`（16 字节随机数）本身就在栈上，任何栈读取泄漏都会暴露随机种子
- `AT_SYSINFO_EHDR` 暴露 vDSO 地址，可用于计算内核镜像基址（在某些配置下）
- `argv[0]` 中的路径信息泄漏程序在 `AT_EXECFN` 处的地址

**`MAP_FIXED` 的危险性**：内核使用 `MAP_FIXED` 映射 ELF 段，会静默覆盖已有映射。恶意构造的 ELF 文件若能让内核执行加载（如通过 `binfmt_misc` 注册的自定义加载器），可以利用此行为覆盖敏感内存区域。

### 正确使用 execve 的注意事项

**环境变量继承的安全含义**：

`execve` 不自动清理 `envp`——调用者传什么，子进程就收到什么。对于 suid 程序，ld.so 会在 `AT_SECURE=1` 时忽略 `LD_PRELOAD`、`LD_LIBRARY_PATH` 等敏感环境变量。应用程序在 `execve` setuid 程序前应手动清理环境：

```c
// 安全的 execve：只传必要的环境变量
char *safe_envp[] = {
    "PATH=/usr/bin:/bin",
    "HOME=/tmp",
    NULL
};
execve("/usr/sbin/target", argv, safe_envp);
```

**argv[0] 约定**：按 POSIX 约定，`argv[0]` 应该是程序名（通常是路径或 basename）。内核不强制此约定，但 `ps`、`top` 等工具和程序自身（通过 `argv[0]` 打印错误信息）依赖它。伪装进程名的技术（如僵尸进程伪装）正是利用了内核不验证 `argv[0]` 的特性。

**文件描述符继承**：`execve` 不关闭文件描述符（除非设置了 `O_CLOEXEC` 标志）。子进程会继承父进程的所有 fd，包括 socket、pipe 等。安全编程要求在 `execve` 之前对所有非必要 fd 设置 `FD_CLOEXEC`，或使用 `close_range`（Linux 5.9+）批量关闭。

**`begin_new_exec` 之后不能失败**：内核代码注释中明确标注，`begin_new_exec` 之后的错误只能导致进程被 `SIGKILL` 终止，无法返回 `execve` 的错误码。因此所有可能失败的检查（参数验证、权限检查、文件打开）都在此之前完成。

## 小结

ELF 内核加载器的路径虽然横跨数千行内核代码，但逻辑结构清晰：

1. **识别**：binfmt 框架通过 magic number 分派给 `load_elf_binary`
2. **解析**：读取 ELF 头和程序头表，定位 `PT_INTERP`（解释器）
3. **映射**：用 `mmap` 将所有 `PT_LOAD` 段映射到地址空间，ET_DYN 需先确定加载基址（受 ASLR 影响）
4. **构建**：`create_elf_tables` 将 argc/argv/envp/auxv 推入新栈
5. **ASLR**：`randomize_va_space` 控制各区域随机化，分散在 mmap 基址、栈、堆、vDSO 的独立随机化机制中
6. **跳转**：`start_thread` 设置 rip/rsp，内核返回用户态，执行 ld.so._start 或程序 _start

辅助向量（auxv）是内核留给用户态的"信息地图"，动态链接器完全依赖它才能正确初始化进程。逆向分析时，从 GDB 的 `info auxv` 出发，结合 `/proc/PID/maps`，可以精确还原内核加载决策。
