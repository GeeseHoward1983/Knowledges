# ELF的SHT_GROUP与链接器去重

> [!abstract] TL;DR
> C++ 模板实例化、内联函数、虚表等会在多个翻译单元中生成相同的节区副本。ELF 通过 `SHT_GROUP`（COMDAT 组）机制让链接器识别并折叠这些重复体，仅保留一份。本篇深度解析 COMDAT 组的二进制结构、链接器去重算法、与 `--gc-sections` 的交互、ICF（Identical Code Folding）技术，以及逆向时识别 COMDAT 残留的实战技巧。

---

## 一、问题根源：C++ 的"一式多份"难题

### 1.1 翻译单元模型与重复代码

C++ 标准规定，每个 `.cpp` 文件是一个独立的翻译单元（Translation Unit，TU），独立编译为目标文件（`.o`）。当多个 TU 包含同一头文件并实例化同一模板时，编译器会在每个 `.o` 中生成该实例的完整代码。

典型场景：

```cpp
// vector.h（被多个 .cpp 包含）
template<typename T>
class std::vector<int> { ... };

// a.cpp → a.o 中含 std::vector<int>::push_back
// b.cpp → b.o 中含 std::vector<int>::push_back（完全相同的机器码）
// c.cpp → c.o 中含 std::vector<int>::push_back（同上）
```

链接时若不去重，最终二进制中 `push_back` 的机器码将出现三份，导致：

- **代码膨胀**：大型项目可让二进制增大数十 MB
- **符号冲突**：若标记为强符号（`STB_GLOBAL`），链接器报 `multiple definition` 错误

### 1.2 传统解决方案的局限

| 方法 | 原理 | 缺陷 |
|---|---|---|
| `weak` 符号（`__attribute__((weak))`）| 多个 weak 定义，链接器任选一个 | 语义上保留任意副本，不保证选最优 |
| `inline` 关键字 | 语言层面允许多定义，编译器标记 `STB_WEAK` | 同 weak，且内联失败时仍重复 |
| `extern template` | 抑制特定实例化，声明仅在一个 TU 实例化 | 需手动维护，易遗漏 |

COMDAT 组机制从 ELF 层面解决了这个问题，语义更精确：**一组节要么全部保留，要么全部丢弃，且相同签名的组只保留一个**。

## 二、SHT_GROUP：ELF 节组机制

### 2.1 节头类型 `SHT_GROUP = 17`

ELF 规范在节头 `sh_type` 中定义了 `SHT_GROUP`（值 `0x11` / 17）。一个 group 节本身是一张表，列出属于该组的其他节的索引。

节头字段语义（对 SHT_GROUP 节而言）：

| 字段 | 含义 |
|---|---|
| `sh_name` | 通常为空字符串（`""`）或 `.group` |
| `sh_type` | `SHT_GROUP = 17` |
| `sh_flags` | 通常为 0 |
| `sh_link` | 指向符号表节（通常 `.symtab`）的索引 |
| `sh_info` | 组签名符号在符号表中的索引（`Elf64_Sym`） |
| `sh_entsize` | `sizeof(Elf32_Word) = 4` |
| `sh_size` | 整个节大小，含 4 字节 flags + N*4 字节成员索引 |

### 2.2 节数据布局

```
SHT_GROUP 节内容（小端，32位字数组）：
┌──────────────────────┐
│  flags  (4 bytes)    │  ← 0x1 = GRP_COMDAT
├──────────────────────┤
│  section_index[0]    │  ← 第一个成员节的节头索引
├──────────────────────┤
│  section_index[1]    │
├──────────────────────┤
│  ...                 │
└──────────────────────┘
```

**`flags` 字段**：目前仅定义了一个标志位：

- `GRP_COMDAT = 0x1`：标记为 COMDAT 组，触发链接器去重语义

### 2.3 组签名符号

`sh_info` 指向 `.symtab` 中的一个符号，该符号的名称（`st_name` → 字符串表）作为**组签名（group signature）**。链接器通过比较签名来判断哪些组是"相同的"。

对于 C++ 模板实例，GCC/Clang 生成的签名是经过名称修饰（name mangling）的符号名，例如：

```
_ZN9std__cxx117__debug3vecIiSaIiEE9push_backERKi
（std::__debug::vec<int, std::allocator<int>>::push_back(int const&)）
```

签名符号的绑定通常是 `STB_LOCAL`，节索引是 `SHN_ABS` 或该组内某成员节的索引（各编译器实现略有差异）。

### 2.4 成员节的标记

属于某个 COMDAT 组的节，其节头中 `sh_flags` 包含 `SHF_GROUP = 0x200`，且 `sh_group` 字段（等同于 `sh_info`）指回对应的 SHT_GROUP 节。

```c
/* elf.h 摘录 */
#define SHF_GROUP    0x200  /* Section is member of a group */
#define SHT_GROUP    17     /* Section group */
#define GRP_COMDAT   0x1    /* Mark group as COMDAT */
```

### 2.5 用 readelf 观察

```bash
$ readelf -g foo.o          # 显示所有 section groups
$ readelf -S foo.o          # 查看节头，注意 SHF_GROUP 标志 (G)

# 示例输出（简化）：
COMDAT group section [   1] `.group' [_ZN3foo3barEv] contains 2 sections:
   [   2]   .text._ZN3foo3barEv
   [   3]   .rela.text._ZN3foo3barEv
```

### 2.6 Mermaid：SHT_GROUP 与成员节的引用关系

```mermaid
graph TD
    GRP["SHT_GROUP 节<br/>.group<br/>flags=GRP_COMDAT<br/>sh_info→SYM"]
    SYM["符号表条目<br/>name='_ZN3foo3barEv'<br/>（组签名）"]
    TEXT["成员节<br/>.text._ZN3foo3barEv<br/>SHF_GROUP"]
    RELA["成员节<br/>.rela.text._ZN3foo3barEv<br/>SHF_GROUP"]
    GRP -->|sh_info| SYM
    GRP -->|成员索引[0]| TEXT
    GRP -->|成员索引[1]| RELA
    TEXT -->|sh_group| GRP
    RELA -->|sh_group| GRP
```

## 三、链接器去重算法

### 3.1 整体流程

链接器（GNU ld、gold、lld）处理 COMDAT 组的算法本质是：**同一签名只保留第一个遇到的组，丢弃后续所有同名组**。

```
阶段一：收集阶段（Pass 1）
  for each input .o file:
    for each SHT_GROUP section:
      sig = symbol_name(sh_info)
      if sig not in comdat_table:
        comdat_table[sig] = this_group   # 第一个：保留
        mark all member sections as KEEP
      else:
        mark all member sections as DISCARD   # 后续：丢弃

阶段二：布局阶段（Pass 2）
  只将 KEEP 状态的节放入输出文件布局
  所有 DISCARD 节的重定位条目也一并丢弃
```

### 3.2 签名比较的精确语义

ELF 规范规定：签名比较是**字节级字符串比较**，不涉及任何解码或语言语义。这意味着：

- 同一模板实例在不同编译器选项下可能产生不同的修饰名（如 `-fabi-version` 差异），导致不被视为同一组
- 故意在两个 TU 中定义不同内容但相同签名，会导致链接器选择"错误"的版本——这是一种攻击面

### 3.3 GNU ld 实现细节

GNU ld 在 `bfd/elflink.c` 的 `_bfd_elf_check_kept_section` 函数中实现了 COMDAT 保留逻辑。关键数据结构：

```c
/* 简化版，源自 bfd/elf-bfd.h */
struct bfd_elf_section_data {
  ...
  struct bfd_link_order *link_order; /* 输出节链接顺序 */
  /* COMDAT 相关 */
  asection *kept_section;  /* 若该节被丢弃，指向保留的那个对应节 */
};
```

当一个节被 COMDAT 丢弃时，链接器将其 `kept_section` 指向实际保留的副本。这对于 debug 节的处理至关重要：`.debug_info` 中引用的 DIE 偏移需要重定位到保留的节。

### 3.4 lld 的实现

LLVM lld 在 `lld/ELF/InputFiles.cpp` 的 `ObjFile<ELFT>::initializeGroups()` 中初始化 COMDAT 处理。lld 使用一个全局的 `ConcurrentMap<StringRef, InputSection *>` 实现无锁并发去重（在多线程链接场景中）：

```cpp
// lld 源码伪代码
for (auto &group : obj.groups) {
  StringRef sig = obj.getSymbolName(group.signature);
  if (comdat.try_emplace(sig, &group.members[0]).second) {
    // 首次见到，保留
    for (auto *sec : group.members) sec->live = true;
  } else {
    // 重复，丢弃
    for (auto *sec : group.members) sec->live = false;
  }
}
```

### 3.5 处理重定位到丢弃节的引用

当节 A（保留）引用节 B（被 COMDAT 丢弃），但 B 的保留副本 B' 已经被选择时，链接器需要将重定位目标从 B 的地址修改为 B' 的对应偏移。这通过 `kept_section` 指针加 `r_addend` 调整完成。

若没有对应的保留副本（如 B 根本没有出现在任何输入文件中），则这是一个链接错误（`undefined reference`）——但 COMDAT 机制保证了如果组被选中，组内所有成员都随之保留，故正确使用时不会出现孤立引用。

## 四、`--gc-sections` 与 COMDAT 的交互

### 4.1 `--gc-sections` 基本原理

`--gc-sections`（GCC/ld）或等效的 `-dead-strip`（Apple ld）对链接器输出进行**死代码消除**（Dead Code Elimination）：

1. 从根节点集合（entry point、`KEEP()` 指令标记的节、`__attribute__((used))` 符号）出发
2. 通过重定位条目追踪引用关系，构建节的可达图
3. 不可达的节标记为 dead，不写入输出

前提：编译时需启用 `-ffunction-sections -fdata-sections`，让每个函数/变量占据独立节区（否则同一节内的死代码无法单独删除）。

### 4.2 COMDAT 与 gc-sections 的顺序关系

关键规则：**COMDAT 去重先于 gc-sections**。链接器的处理顺序是：

```
Input files
    │
    ▼
COMDAT 去重（选出每组的保留副本）
    │
    ▼
--gc-sections 可达性分析（在已去重的节上运行）
    │
    ▼
输出文件布局
```

因此：

- 即使某个 COMDAT 组被选为"保留"，若后续 gc-sections 发现无任何根节点可达到组内成员，该组仍会被消除
- 被 COMDAT 丢弃的节不参与 gc-sections 分析（已标记 dead）

### 4.3 `KEEP()` 链接脚本指令

若需强制保留某个节（即使 gc-sections 判定其不可达），可在链接脚本中使用：

```ld
SECTIONS {
  .text : {
    KEEP(*(.text.startup))    /* 强制保留 startup 节 */
    *(.text .text.*)
  }
}
```

`KEEP()` 将匹配的节加入 gc-sections 的根集合，但它**不影响** COMDAT 去重——若有多个同签名 COMDAT 组，KEEP 只能确保保留的那个副本不被 gc-sections 消除，无法阻止非第一个副本被 COMDAT 丢弃。

### 4.4 调试 gc-sections 行为

```bash
# 查看哪些节被 gc-sections 消除
$ ld --gc-sections --print-gc-sections -o out a.o b.o 2>&1 | head -50

# 查看最终保留了哪些节（输出文件的节列表）
$ readelf -S out | grep -v NOBITS
```

## 五、ICF（Identical Code Folding）

### 5.1 ICF 的本质

COMDAT 去重基于**签名**——两个节签名相同就合并，但可能内容并不完全一样（如不同的编译选项产生不同代码）。ICF 则更激进：比较**节内容的字节序列**，把内容完全相同的节（即使签名不同、来自不同模板）合并为同一物理地址。

ICF 由 gold 链接器引入，lld 也支持（`--icf=all` 或 `--icf=safe`）：

```bash
$ lld-link --icf=all ...     # MSVC 风格
$ ld.lld --icf=safe -o out a.o b.o   # ELF
$ gold --icf=all -o out a.o b.o
```

### 5.2 ICF 的算法

lld 的 ICF 使用**迭代哈希图**算法（受 LLVM 论文 "Gold's ICF" 启发）：

```
初始化：
  for each section s:
    s.hash = hash(s.content || s.reloctype_list)
    // 不含重定位目标值，只含重定位类型

迭代：
  repeat until convergence:
    for each section s:
      target_hashes = [target(r).hash for r in s.relocs]
      s.new_hash = hash(s.hash || target_hashes)
    update all s.hash

折叠：
  sections with equal hash → 合并为同一输出节
  后续引用到旧节地址的重定位 → 修正为保留节地址
```

### 5.3 ICF 的安全模式 vs 激进模式

| 模式 | 行为 | 风险 |
|---|---|---|
| `--icf=safe` | 只折叠 `const` 标记的数据节和函数节（不折叠有指针比较语义的内容） | 低 |
| `--icf=all` | 折叠所有内容相同的节，包括函数指针 | 函数指针比较可能失效（`&f1 == &f2` 本应为 false 但变为 true） |

C++ 标准 [basic.types] 规定，相同类型的两个不同函数对象的指针不相等。激进 ICF 可能违反此语义，通常只在不做函数指针比较的场合使用。

### 5.4 ICF 在逆向中的表现

当目标二进制使用了 ICF，逆向工程师会观察到：

- 多个外部符号（通过 `plt` 条目）跳转到**同一地址**
- `nm --print-map` 显示多个符号名绑定到同一偏移
- IDA Pro 或 Ghidra 将同一函数体标注多个名称（alias）
- 函数指针比较测试在调试时返回意外的 `true`

识别 ICF 折叠的方法：用 `readelf -s` 检查符号表，若多个符号 `st_value` 相同（且 `st_size` 相同），大概率是 ICF 折叠结果。

## 六、逆向场景：识别与分析 COMDAT

### 6.1 目标文件中的 COMDAT 残留

链接后的可执行文件/共享库中，SHT_GROUP 节通常不再存在（链接器已完成去重，不需要保留 group 元数据）。但在分析**未链接的目标文件**（`.o`、`.a` 静态库成员）时，COMDAT 信息完整保留。

```bash
# 分析静态库中的目标文件
$ ar x libfoo.a foo.o
$ readelf -g foo.o          # 列出所有 group
$ readelf -S foo.o | grep -i group   # 查找带 G 标志的节
```

### 6.2 还原模板实例化关系

当逆向 C++ 目标文件时，COMDAT 签名可以帮助还原模板层次：

```
.group 签名：_ZN3std6vectorIiSaIiEE9push_backERKi
→ 解码：std::vector<int, std::allocator<int>>::push_back(int const&)
→ 推断：代码是 std::vector<int> 的 push_back 实例
```

可用 `c++filt` 解码修饰名：

```bash
$ echo '_ZN3std6vectorIiSaIiEE9push_backERKi' | c++filt
std::vector<int, std::allocator<int>>::push_back(int const&)
```

### 6.3 虚表与 COMDAT

多继承和虚函数的虚表（vtable）也是 COMDAT 组的典型成员。GCC 为每个含虚函数的类生成以下 COMDAT 组（若类在头文件中定义）：

| 节 | 内容 |
|---|---|
| `.text._ZTV3Foo` | Foo 的虚表（函数指针数组） |
| `.rodata._ZTS3Foo` | Foo 的 type-info 字符串 |
| `.rodata._ZTI3Foo` | Foo 的 type-info 结构体 |

逆向时见到 `_ZTV` 前缀节名，即可确认这是虚表 COMDAT 组。`_ZTI` 是 RTTI（运行时类型信息），`_ZTS` 是类型名字符串。

### 6.4 COMDAT 相关的链接错误分析

在逆向分析中常见的 COMDAT 引发错误：

**错误一：COMDAT 组冲突（签名相同但内容不同）**
```
warning: COMDAT group 'foo' in a.o and b.o have different contents
```
这通常意味着两个 TU 用了不同的编译宏或 ABI 版本定义了同名函数。

**错误二：孤立 COMDAT 引用**
```
error: undefined reference to '_ZN3FooC1Ev'
```
若 Foo 的构造函数在某个 COMDAT 组中，而该组的所有副本都被 gc-sections 消除，就会出现此错误。解决方法：检查是否遗漏了 `-ffunction-sections` 或 `KEEP()` 标记。

## 七、安全性与正确使用

### 7.1 COMDAT 的潜在攻击面

COMDAT 机制中，签名比较是字符串级别的，不验证内容一致性。攻击者可以：

1. **构造同签名不同内容的 COMDAT 组**，在链接时替换合法实现。这在供应链攻击（修改第三方 `.o` 文件）中是可行的攻击向量。
2. **通过 COMDAT 组注入后门代码**，让链接器"自然地"选择恶意版本（若恶意文件在命令行中排在前面）。

**防御建议**：

- 使用可重现构建（Reproducible Builds），对 `.o` 和最终链接结果做哈希校验
- 启用 `--warn-comdat-group-mismatch`（gold 选项），对签名相同但内容不同的组产生警告
- 在 CI/CD 中对静态库文件进行完整性检查

### 7.2 ICF 与安全性

ICF 折叠函数后，函数地址可能被修改。若代码中存在函数指针地址验证（如白名单检查），ICF 可能导致两个本不相等的函数地址变为相同，绕过检查。

**安全建议**：

- 在安全敏感代码中避免使用 `--icf=all`
- 若必须使用，确保代码中无基于函数指针地址的安全决策
- ASLR 与 ICF 共存：ICF 不影响 ASLR，因为 ASLR 是对加载基地址的随机化，ICF 只影响节在文件内的相对偏移

### 7.3 调试与正确使用建议

| 场景 | 推荐做法 |
|---|---|
| 发布版本减小体积 | `-ffunction-sections -fdata-sections --gc-sections` + `--icf=safe` |
| 调试版本 | 不用 ICF，不用 gc-sections，保留完整符号 |
| 静态分析 `.o` | `readelf -g` 查看 COMDAT 组，`c++filt` 解码签名 |
| 链接错误排查 | `--verbose` + `--print-gc-sections` 追踪节被消除的原因 |
