# 详解ELF文件(五十五).ELF符号版本化全流程

> [!abstract] TL;DR
> ELF 符号版本化（Symbol Versioning）是 GNU 扩展，允许共享库在不破坏现有 ABI 的前提下演进接口。版本控制通过 `--version-script` 在链接时嵌入，由 `.gnu.version`（符号版本索引）、`.gnu.version_d`（版本定义）、`.gnu.version_r`（版本需求）三张表在运行时由 ld.so 验证。`@@` 标记默认版本，`@` 标记旧版本；`.symver` 汇编指令允许在同一共享库中提供同名函数的多个版本实现。glibc 将此机制用于在保持向后兼容的同时修复函数行为（如 `memcpy@GLIBC_2.14` 修复缺失后缀处理）。

## 概述与定位

共享库（`.so`）是代码复用的基础设施。当一个共享库升级版本时，它面临一个两难困境：

- 如果修改了某个函数的行为或签名，链接旧版本共享库的程序可能行为改变或崩溃
- 如果完全保持旧接口不变，又无法修复 bug 或引入更好的实现

**ELF 符号版本化**（GNU Symbol Versioning）正是解决这一问题的机制。它允许：

1. 一个共享库中**同时存在同名函数的多个版本实现**
2. 每个可执行文件在链接时记录它**依赖的是哪个版本**的符号
3. 运行时链接器（ld.so）确保程序始终绑定到**正确版本的符号**，即使系统上安装了更新版本的共享库

这套机制由 Ulrich Drepper 为 glibc 设计，现已成为 GNU/Linux 共享库生态的标准实践。理解它对于：
- **共享库开发者**：如何正确声明和维护 ABI 版本
- **逆向工程师**：如何识别二进制文件的 glibc 版本依赖和符号绑定关系
- **安全研究者**：如何利用版本不匹配或版本降级漏洞

本篇从链接时的 `--version-script` 语法出发，串联三个 ELF 节区的内部结构，最后以 glibc 真实案例（`memcpy@GLIBC_2.14`）收尾。

## 原理与机制

### 问题背景：没有符号版本化时的困境

假设 libfoo.so.1 导出函数 `foo_process`，若该函数在 1.1 版本中修改了行为（修复了一个 bug）：

- 链接了 libfoo.so.1.0 的旧程序，可能依赖旧的（有 bug 的）行为
- 如果系统升级了 libfoo 到 1.1，旧程序可能意外"被修复"，行为改变

无版本化的共享库通过**库版本号**（SONAME，如 `libfoo.so.2`）区分不兼容的 ABI，但这意味着每次破坏兼容性就必须升 SONAME，并且**旧版本的库文件必须保留**在系统上，导致系统同时安装多个版本的同一库。

**符号版本化的优势**：在同一个 `.so` 文件中同时提供旧版本和新版本的实现，消除了保留多个 `.so` 文件的需要。

### --version-script 语法全貌

版本脚本（Version Script）是传递给链接器的文本文件，控制符号的版本标签和可见性：

```
# 基本结构：版本节点定义
VERSION_TAG_NAME {
    global:         # 公开导出的符号列表
        symbol1;
        symbol2;
        symbol3;    # 支持 glob 通配：symbol_*;
    local:          # 隐藏的符号（不导出）
        *;          # 通配：所有其他符号默认隐藏
} PARENT_VERSION;   # 可选：继承父版本（建立依赖链）
```

**实际示例（libfoo 的版本脚本）**：

```
# libfoo.map

# 初始版本
LIBFOO_1.0 {
    global:
        foo_init;
        foo_process;
        foo_cleanup;
    local:
        *;          # 所有内部实现符号默认隐藏
};

# 1.1 版本：新增符号，修改 foo_process 行为
LIBFOO_1.1 {
    global:
        foo_process;    # 覆盖：提供新实现（旧实现通过 .symver 保留）
        foo_extra;      # 新增：1.1 才有的函数
} LIBFOO_1.0;           # 继承：LIBFOO_1.0 中的符号在 1.1 中仍然可用

# 2.0 版本：不兼容变更（通常应该改 SONAME）
LIBFOO_2.0 {
    global:
        foo_process;    # 接口签名变了
        foo_init_v2;
} LIBFOO_1.1;           # 继承链延续
```

链接库时传入：
```bash
gcc -shared -Wl,--version-script,libfoo.map -o libfoo.so.1 libfoo.o
```

### @@ 默认版本与 @ 旧版本的语义

符号的版本标注有两种形式：

| 形式 | 含义 | 使用场景 |
|------|------|---------|
| `symbol@@VERSION` | **默认版本**：链接时未指定版本的程序绑定到此实现 | 最新的、推荐的实现 |
| `symbol@VERSION` | **旧版本**：只有明确依赖此版本的旧程序才绑定到此实现 | 保留的向后兼容实现 |

从使用者的角度（编译新程序时）：
- `dlsym(handle, "symbol")` 或 `-lfoo` 自动绑定到 `symbol@@LATEST_VERSION`（默认版本）
- 旧程序（编译时链接了旧版本 libfoo）会在 `.gnu.version_r` 中记录 `symbol@OLD_VERSION`，ld.so 运行时绑定到旧实现

**在符号表中的体现**（`readelf -sW` 输出）：

```
Num:    Value          Size Type    Bind   Vis      Ndx Name
 42: 0000000000001234   100 FUNC    GLOBAL DEFAULT   12 foo_process@@LIBFOO_1.1
 43: 0000000000001100    98 FUNC    GLOBAL DEFAULT   12 foo_process@LIBFOO_1.0
```

两个 `foo_process`：一个带 `@@`（新，默认），一个带 `@`（旧，向后兼容）。

### .symver 汇编指令：在同一源文件中提供多版本实现

`.symver` 是 GNU 汇编器的伪指令，允许在 C 源代码中为同名函数绑定不同的版本标签：

```c
// libfoo.c

// 旧版本实现（LIBFOO_1.0 的 foo_process）
// 函数名内部叫 foo_process_old，外部导出为 foo_process@LIBFOO_1.0
__asm__(".symver foo_process_old, foo_process@LIBFOO_1.0");
int foo_process_old(const char *input) {
    // 旧实现（有 bug：不处理 NULL 输入）
    return strlen(input) + 1;
}

// 新版本实现（LIBFOO_1.1 的 foo_process，默认版本）
// 内部名 foo_process_new，外部导出为 foo_process@@LIBFOO_1.1
__asm__(".symver foo_process_new, foo_process@@LIBFOO_1.1");
int foo_process_new(const char *input) {
    // 新实现：修复 NULL 检查
    if (!input) return -1;
    return strlen(input) + 1;
}
```

`.symver` 指令格式：
```
.symver 内部函数名, 外部符号名[@或@@版本标签]
```

- `@@`：声明为默认版本（链接新程序时自动绑定）
- `@`：声明为旧版本（只有旧程序才会绑定）

链接后，符号表中同时存在两个条目，但对外提供的都叫 `foo_process`——区别仅在版本标签。

## 结构/算法/伪代码详解

### 三张关键 ELF 节区

符号版本化在 ELF 中由三个配套节区共同实现：

```
.gnu.version      符号版本索引表（Symbol Version Index Table）
.gnu.version_d    版本定义表（Version Definition Table，由库方维护）
.gnu.version_r    版本需求表（Version Need Table，由使用方维护）
```

### .gnu.version：符号版本索引表

节头属性：`sh_type = SHT_GNU_versym`，条目大小 = 2 字节（`Elf64_Half`），与 `.dynsym`（动态符号表）一一对应。

每个条目是一个 16 位整数，值含义：
- `0`：`VER_NDX_LOCAL`——局部符号，不导出
- `1`：`VER_NDX_GLOBAL`——全局符号，无版本标签
- `2+`：版本索引——对应 `.gnu.version_d` 或 `.gnu.version_r` 中的版本定义

```
readelf --syms --wide prog | head -20
readelf -V prog  # 显示版本符号信息

# 示例输出（代表性）：
Symbol table '.dynsym' contains 8 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     0: ...                 0 NOTYPE  LOCAL  DEFAULT  UND 
     1: ...                 0 FUNC    GLOBAL DEFAULT  UND memcpy@GLIBC_2.14 (2)
     2: ...                 0 FUNC    GLOBAL DEFAULT  UND printf@GLIBC_2.2.5 (3)
# 括号中的数字就是 .gnu.version 中该符号的版本索引
```

### .gnu.version_d：版本定义表

节头属性：`sh_type = SHT_GNU_verdef`。只存在于**提供符号**的共享库中（.so 文件）。

结构定义（可多条，链表结构）：

```c
typedef struct {
    Elf64_Half  vd_version;  // 版本格式版本号（始终为 1）
    Elf64_Half  vd_flags;    // VER_FLG_BASE（基础版本）或 0
    Elf64_Half  vd_ndx;      // 版本索引（从 1 开始，与 .gnu.version 对应）
    Elf64_Half  vd_cnt;      // 紧跟的 Verdaux 条目数（通常 1 个名称 + n 个依赖）
    Elf64_Word  vd_hash;     // 版本名称的哈希值（DJB2 类似算法）
    Elf64_Word  vd_aux;      // 到第一个 Verdaux 条目的字节偏移
    Elf64_Word  vd_next;     // 到下一个 Verdef 条目的字节偏移（0 = 最后一条）
} Elf64_Verdef;

typedef struct {
    Elf64_Word  vda_name;    // 版本名称在 .dynstr 中的偏移
    Elf64_Word  vda_next;    // 到下一个 Verdaux 的偏移（0 = 最后）
} Elf64_Verdaux;
```

一个典型的 `.gnu.version_d` 包含多条 Verdef：

```
版本索引 1: LIBFOO_1.0 (VER_FLG_BASE，基础版本)
版本索引 2: LIBFOO_1.1 (依赖 LIBFOO_1.0)
版本索引 3: LIBFOO_2.0 (依赖 LIBFOO_1.1)
```

### .gnu.version_r：版本需求表

节头属性：`sh_type = SHT_GNU_verneed`。只存在于**使用符号**的可执行文件或共享库中，记录该文件依赖哪些版本的哪些符号。

```c
typedef struct {
    Elf64_Half  vn_version;  // 格式版本（始终为 1）
    Elf64_Half  vn_cnt;      // 紧跟的 Vernaux 条目数（该文件对此共享库的所有版本需求）
    Elf64_Word  vn_file;     // 共享库名称在 .dynstr 中的偏移（如 "libc.so.6"）
    Elf64_Word  vn_aux;      // 到第一个 Vernaux 条目的偏移
    Elf64_Word  vn_next;     // 到下一个 Verneed 条目的偏移（0 = 最后）
} Elf64_Verneed;

typedef struct {
    Elf64_Word  vna_hash;    // 版本名称哈希（与 Verdef 中的 vd_hash 匹配）
    Elf64_Half  vna_flags;   // 通常为 0
    Elf64_Half  vna_other;   // 版本索引（在此文件的 .gnu.version 中使用）
    Elf64_Word  vna_name;    // 版本名称在 .dynstr 中的偏移（如 "GLIBC_2.14"）
    Elf64_Word  vna_next;    // 到下一个 Vernaux 的偏移
} Elf64_Vernaux;
```

### 三张表的串联查找流程

```
ld.so 绑定 memcpy 符号的过程：

1. 读取可执行文件的 .dynsym，找到 memcpy 的符号条目
   ─► 通过 .gnu.version 获取其版本索引，例如 idx = 5

2. 查找 .gnu.version_r（版本需求表）
   ─► 找到版本索引 5 对应的 Vernaux 条目
   ─► 得到版本名称 "GLIBC_2.14" 和库名 "libc.so.6"
   
3. 打开 libc.so.6，读取其 .gnu.version_d（版本定义表）
   ─► 查找版本名称 "GLIBC_2.14"（用 vd_hash 快速比对）
   ─► 找到对应的 Verdef 条目，确认 libc.so.6 确实提供 GLIBC_2.14 版本

4. 在 libc.so.6 的 .dynsym 中查找 memcpy
   ─► 通过 .gnu.version 确认该条目的版本索引对应 GLIBC_2.14（@@GLIBC_2.14）
   ─► 将 memcpy 的 GOT 条目填写为该实现的地址
   
5. 若 libc.so.6 版本过旧，不包含 GLIBC_2.14 的版本定义
   ─► ld.so 报错：symbol memcpy version GLIBC_2.14 not found（致命错误）
```

### 版本查找的 Mermaid 流程图

```mermaid
flowchart LR
    A[可执行文件.dynsym<br/>sym: memcpy, idx=5] --> B[.gnu.version<br/>entry[5] = 5]
    B --> C[.gnu.version_r<br/>idx 5: GLIBC_2.14<br/>from libc.so.6]
    C --> D[打开 libc.so.6]
    D --> E[libc.so.6<br/>.gnu.version_d<br/>查找 GLIBC_2.14]
    E -->|找到| F[libc.so.6<br/>.dynsym 找 memcpy<br/>版本 @@GLIBC_2.14]
    F --> G[写入 GOT<br/>绑定成功]
    E -->|未找到| H[ld.so 报错<br/>version not found<br/>进程终止]
```

### 向后兼容符号别名（.symver）完整实现模式

```c
// 在共享库中同时维护多个版本的标准模板

// ============ foo_compat.c（向后兼容实现）============
// 旧实现：维持历史行为，仅供老程序使用
#include "libfoo_internal.h"

// 告诉汇编器：函数 foo_v10_impl 对外导出为 foo_func@LIBFOO_1.0
// @ 单个 at 号 = 旧版本，不会被新链接选中
__asm__(".symver foo_v10_impl, foo_func@LIBFOO_1.0");
int foo_v10_impl(int x) {
    return x * 2;  // 旧行为
}

// ============ foo_current.c（当前实现）============
// 新实现：修复了旧实现的问题
// @@ 双 at 号 = 默认版本，新链接的程序自动使用此版本
__asm__(".symver foo_v11_impl, foo_func@@LIBFOO_1.1");
int foo_v11_impl(int x) {
    if (x < 0) return 0;  // 新行为：负数返回 0
    return x * 2;
}

// ============ libfoo.map（版本脚本）============
/*
LIBFOO_1.0 {
    global:
        foo_func;
    local:
        *;
};

LIBFOO_1.1 {
    global:
        foo_func;
} LIBFOO_1.0;
*/

// ============ 编译命令 ============
// gcc -shared -fPIC \
//     -Wl,--version-script,libfoo.map \
//     -o libfoo.so.1 foo_compat.c foo_current.c
```

### 识别程序依赖的 glibc 最低版本

```bash
# 方法一：直接查看版本需求
readelf -V ./prog | grep "Name:" | sort -t_ -k2 -V | tail -5
# 找出最新的 GLIBC_x.y，即程序需要的最低 glibc 版本

# 方法二：用 objdump
objdump -p ./prog | grep GLIBC | sort -V | tail -5

# 方法三：自动化脚本
python3 << 'EOF'
import subprocess, re
out = subprocess.check_output(['readelf', '-V', './prog'], text=True, stderr=None)
versions = re.findall(r'Name: (GLIBC_[\d.]+)', out)
if versions:
    print("最低 glibc 版本:", sorted(versions, key=lambda v: [int(x) for x in v.split('_')[1].split('.')])[-1])
EOF
```

### glibc memcpy@GLIBC_2.14 案例详解

这是 GNU 符号版本化最著名的真实案例：

**背景**：在 x86-64 SSE4.2 优化版本的 glibc 2.13 及以前，`memcpy` 的实现有一个向后拷贝优化，导致**源和目标重叠时**（overlapping memory copy）行为不正确（某些情况下相当于 `memmove` 的语义，但有时方向相反）。这实际上是许多程序错误地将 `memcpy` 用于重叠拷贝时"碰巧"工作，glibc 2.14 修复了 `memcpy` 使其严格按标准（不处理重叠），导致这些程序在 glibc 2.14 上崩溃。

**解决方案**：glibc 2.14 引入了符号版本化：
```
memcpy@@GLIBC_2.14  ─► 新实现（严格，不处理重叠）
memcpy@GLIBC_2.2.5 ─► 旧实现（实际上是 memmove 语义，向后拷贝）
```

- 在 glibc 2.14 之后**编译**的程序：绑定到 `memcpy@@GLIBC_2.14`（使用新实现）
- 在 glibc 2.14 之前**编译**的程序：`.gnu.version_r` 中记录 `memcpy@GLIBC_2.2.5`，运行时仍绑定到旧实现

**验证命令**：
```bash
# 查看 ls 依赖的 memcpy 版本
objdump -T /usr/bin/ls | grep memcpy
# 输出（代表性）：
# 0000000000000000      DF *UND*  0000000000000000  GLIBC_2.14  memcpy

# 查看 libc.so.6 提供的 memcpy 版本
objdump -T /lib/x86_64-linux-gnu/libc.so.6 | grep "memcpy"
# 0000000000097fd0 g    DF .text  0000000000000029  GLIBC_2.14  memcpy
# 0000000000097fc0 g    DF .text  000000000000000f  GLIBC_2.2.5 memcpy
```

### 逆向分析时识别版本符号

```bash
# 快速检查一个二进制使用的 glibc 版本
strings ./target | grep "GLIBC_"
# 注意：strings 可能误报，以 readelf -V 为准

# 用 nm 列出所有外部符号及版本
nm -u -D ./target
# 输出格式：地址 类型 符号名@@版本
# U __libc_start_main@@GLIBC_2.34  ← 使用 2.34 的新接口

# 检查是否使用了 GLIBC_2.34（新的 __libc_start_main 签名）
# vs GLIBC_2.2.5（旧签名，不接受 init/fini/argc/argv）
objdump -T ./target | grep __libc_start_main
```

```bash
# 常见错误：./prog: /lib/x86_64-linux-gnu/libc.so.6: version 'GLIBC_2.33' not found
# 诊断：

```

## 安全性与正确使用

### 版本脚本的访问控制：隐藏内部符号

版本脚本的 `local: *;` 是隐藏内部实现符号的正确方式，而非安全机制。被 `local` 隐藏的符号：

- 不出现在 `.dynsym`（动态符号表）中
- 不能被外部 `dlsym` 按名字查找
- 减小了共享库的符号表大小，降低了名称冲突风险
- **不是安全边界**：逆向工程师通过直接内存扫描仍可找到这些函数

正确实践：
```
LIBFOO_PRIVATE {
    local: *;  # 所有符号默认隐藏
};

LIBFOO_1.0 {
    global:
        /* 仅列出公开 API */
        foo_init;
        foo_process;
};
```

等价于编译时使用 `-fvisibility=hidden` + `__attribute__((visibility("default")))` 注释公开符号。

### 版本降级攻击（Version Downgrade）

攻击场景：如果攻击者能修改程序的 `.gnu.version_r` 节（或修改 ld.so 的搜索路径），将程序的版本需求从 `GLIBC_2.14`（安全版本）降级到 `GLIBC_2.2.5`（有 bug 的版本），可以复活已修复的漏洞。

防御：
- 启用只读 RELRO（`-Wl,-z,relro,-z,now`）：`PT_GNU_RELRO` 段包含 `.gnu.version_r`，使其在运行时只读，防止内存中修改
- 文件系统完整性校验（dm-verity、IMA）：防止磁盘上的 ELF 被篡改

### 正确的版本脚本维护实践

**不应该做**：
- 每次更新都引入新版本节点（版本碎片化，维护负担重）
- 在版本节点中使用通配符 `global: *;`（泄漏所有内部符号）
- 删除旧版本节点（破坏向后兼容性）

**应该做**：
```
# 只有在 ABI 发生不兼容变更时才引入新版本节点
# 新增符号可以加到最新版本节点，不需要新建节点

# 好的版本脚本结构示例：
LIBFOO_1 {
    global:
        foo_init;
        foo_process_v1;  # 旧实现，通过 .symver 保留
        foo_cleanup;
    local:
        *;
};

LIBFOO_2 {
    global:
        foo_process_v2;  # 新实现
        foo_batch;       # 新增功能
} LIBFOO_1;              # 继承 LIBFOO_1 的所有符号
```

**测试兼容性**：
```bash
# 确认所有旧版本符号仍然存在
nm -D libfoo.so.1 | grep @  # 列出所有带版本标签的符号
# 用 abi-compliance-checker 工具自动检查 ABI 兼容性
abi-compliance-checker -lib foo -old old_libfoo.xml -new new_libfoo.xml
```

## 小结

ELF 符号版本化是 GNU 共享库生态实现 ABI 稳定性的核心机制，其全流程可概括为：

1. **链接时**：`--version-script` 为每个导出符号附加版本标签，写入 `.gnu.version_d`（库的声明）
2. **使用方链接时**：链接器记录程序依赖的具体版本到 `.gnu.version_r`，动态符号表 `.gnu.version` 为每个符号存储版本索引
3. **运行时**：ld.so 通过三张表的串联查找，确保每个符号绑定到正确版本的实现
4. **多版本共存**：`.symver` 指令允许在同一 .so 中同时提供 `symbol@@NEW`（默认）和 `symbol@OLD`（向后兼容）两套实现

glibc 的 `memcpy@GLIBC_2.14` 是此机制的标志性案例，展示了如何在修复 bug 的同时保持对旧程序的二进制兼容性。逆向分析时，`readelf -V` 和 `objdump -T` 是获取版本信息的首选工具，所得版本标签能直接揭示程序的 glibc 最低版本要求和 ABI 依赖历史。
