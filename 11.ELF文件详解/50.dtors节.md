# 详解ELF文件(五十).dtors节

`.dtors` 节（Destructors Section）是 ELF 文件格式中用于存储程序析构函数指针数组的节区。它是 [[44.fini_array节|.fini_array]] 的前身，与 [[45.ctors节|.ctors]] 成对出现。

## 1. 基本概念

`.dtors` 节全称是 "Destructors Section"，用于存储程序退出时需要调用的析构函数指针列表。它与 [[45.ctors节|.ctors]] 节相对应——后者存储构造函数指针列表。

在 C++ 程序中，文件作用域的全局对象（`Global Objects`）和静态对象（`Static Objects`）需要在程序退出时按**构造逆序**被销毁，这些析构函数的地址就存储在 `.dtors` 节里，由 GCC 运行时支持库在退出阶段遍历调用。

## 2. 主要功能

- 存储程序全局对象的析构函数指针数组
- 在程序正常退出时（`main` 函数返回后，`exit()` 执行期间）调用这些析构函数
- 确保程序资源的正确释放和清理
- 通过 `__attribute__((destructor))` 属性显式注册任意清理函数

## 3. 节头属性

| 字段 | 值 | 说明 |
|------|----|------|
| `sh_type` | `SHT_PROGBITS` (1) | 普通程序数据 |
| `sh_flags` | `SHF_ALLOC \| SHF_WRITE` | 可执行期写（函数指针） |
| `sh_addralign` | 4（32 位）/ 8（64 位） | 指针对齐 |
| `sh_entsize` | 0 | 无固定条目大小 |

## 4. 结构布局与哨兵值

`.dtors` 节带有与 `.ctors` 一致的**哨兵（sentinel）布局**，由 `crtbegin.o` 和 `crtend.o` 分别贡献首尾两个哨兵：

```
.dtors（链接后合并结果）：
  [来自 crtbegin.o]  0xffffffff         ← __DTOR_LIST__ 起始哨兵，-1
  [来自各 .o 文件]   <析构函数地址1>
                     <析构函数地址2>
                     ...
  [来自 crtend.o]    0x00000000         ← __DTOR_END__ / NULL 终止符
```

### 4.1 哨兵值的含义

| 位置 | 值 | 来源 | 含义 |
|------|----|------|------|
| 首元素 | `0xffffffff`（32位）/ `0xffffffffffffffff`（64位） | `crtbegin.o` | 起始哨兵；部分实现解读为"列表开始"，有些文档称其为计数器占位，但均被跳过 |
| 末元素 | `0x00000000` | `crtend.o` | NULL 终止符，遍历时用于检测列表结束 |

> 哨兵首元素的值 `-1`（`0xffffffff`）并非计数——它是固定的魔法值，被 `__do_global_dtors_aux` 识别后直接跳过，永远不会被当作函数地址调用。

### 4.2 crtbegin.o / crtend.o 中的定义

链接顺序为：`crti.o → crtbegin.o → [用户目标文件] → crtend.o → crtn.o`

```c
/* crtbegin.o 提供 .dtors 节中的首个条目（-1 哨兵） */
static func_ptr __DTOR_LIST__[]
  __attribute__ ((section(".dtors"), aligned(sizeof(func_ptr))))
  = { (func_ptr) -1 };

/* crtend.o 提供 .dtors 节中的末尾条目（NULL 终止） */
static func_ptr __DTOR_END__[]
  __attribute__ ((section(".dtors"), aligned(sizeof(func_ptr))))
  = { (func_ptr) 0 };
```

链接器把所有输入文件的 `.dtors` 贡献片段按链接顺序拼接，最终得到以 `-1` 开头、`0` 结尾的完整 `__DTOR_LIST__`。

## 5. 逆序执行机制

### 5.1 .ctors 的执行顺序（对照基准）

`.ctors` 由 `__do_global_ctors_aux` 从尾部向头部**逆序**遍历，即：后链接的目标文件先执行构造函数。这是有意为之的——遵循"后链接、先构造"的依赖语义。

### 5.2 .dtors 的正向遍历 = 构造逆序

C++ 标准要求析构顺序与构造顺序相反。`.dtors` 数组的存储顺序与链接顺序一致（先链接的在前），`__do_global_dtors_aux` **正向遍历**（从索引 1 开始，跳过哨兵 `-1`，直至遇到 `NULL`）：

```c
/* crtstuff.c 中 __do_global_dtors_aux 的核心逻辑 */
static func_ptr *p = __DTOR_LIST__ + 1;  /* 跳过 -1 哨兵 */
while (*p)
{
    p++;
    (*(p-1))();   /* 调用析构函数 */
}
```

由于 `.ctors` 是逆序执行（后进先出），对应的 `.dtors` 正向执行（先进先出），恰好实现了 **LIFO（Last In First Out）** 的析构语义。

例如，链接顺序为 `a.o b.o c.o`：
- `.ctors` 执行顺序：`c → b → a`（构造）
- `.dtors` 存储顺序：`a, b, c`（与链接一致）
- `.dtors` 执行顺序：`a → b → c`（析构）—— 恰好是构造逆序

```mermaid
graph LR
  A["链接顺序: a.o, b.o, c.o"] -->|.ctors 执行| B["构造: c → b → a"]
  B -->|.dtors 执行| C["析构: a → b → c (逆序)"]
```

## 7. 与 C++ 的关系

### 7.1 全局对象析构

在 C++ 程序中，`.dtors` 节特别重要：

- 文件作用域的全局变量（如 `static MyClass obj;`）在编译时会自动生成析构注册代码
- 编译器将析构函数指针写入对应编译单元的 `.dtors` 输入节
- 链接器合并所有 `.dtors` 输入节，形成最终的 `__DTOR_LIST__` 数组
- 程序退出时（`exit()` / `main` return），运行时遍历这个列表调用每个析构函数

### 7.2 `__attribute__((destructor))` 与 `.dtors`

GCC 扩展属性 `__attribute__((destructor))` 可将任意函数注册为程序退出时的清理函数，其实现方式正是将函数地址写入 `.dtors` 节（在旧工具链中）或 `.fini_array` 节（在现代工具链中）。

```c
/* 示例：使用 __attribute__((destructor)) */
__attribute__((destructor))
static void my_cleanup(void) {
    printf("程序退出清理\n");  /* 在 main 返回后被调用 */
}

/* 带优先级版本（优先级范围：101–65535；0–100 保留给实现） */
__attribute__((destructor(200)))
static void high_priority_cleanup(void) {
    /* 优先级越低，越先执行（先析构） */
}
```

> **优先级语义**：优先级数字**越小越先执行**（因为 `.fini_array` 正序执行中数字小的在前），与 `__attribute__((constructor(N)))` 的数字小先执行一致。0–100 由实现保留（如 gcov 使用 `destructor(100)`）；应用代码应使用 101 及以上。

### 7.3 `atexit()` 的关系

`atexit()` 注册的函数与 `.dtors` 是两套独立机制。`exit()` 执行顺序为：
1. 调用 `atexit()` 注册的函数（LIFO 顺序）
2. 刷新并关闭所有打开的 `FILE*` 流
3. 调用 `.dtors`/`.fini_array` 中的析构函数

## 10. 安全相关考虑

### 10.1 .dtors overwrite 攻击

`.dtors` 节历史上是一个重要的**漏洞利用目标**，最早被 Juan M. Bello Rivas 在 2000 年 12 月 Bugtraq 邮件列表中系统记录（"Overwriting the .dtors section"）。

**攻击原理**：

1. `.dtors` 节的 `SHF_WRITE` 标志使其在运行时可写（在 RELRO 出现之前）；
2. 若程序存在可溢出到 `.dtors` 地址范围的缓冲区（通常 `.data` 节紧邻 `.dtors`），攻击者可覆盖 `__DTOR_LIST__[1]`（即哨兵之后的第一个槽位）；
3. 将该槽位改写为 shellcode 地址；
4. `main` 返回后，`__do_global_dtors_aux` 遍历 `.dtors`，将 shellcode 地址当作函数指针调用，执行任意代码。

```
.data 节（含可溢出缓冲区）
  [buf: 0..N]

.dtors 节（紧随 .data）
  [0xffffffff]      ← 哨兵，不被调用
  [dtor_addr]       ← 被攻击者覆盖为 shellcode 地址
  [0x00000000]      ← NULL 终止符
```

即使程序本身没有显式的析构函数（`__DTOR_LIST__[1]` 原本为 NULL），攻击者只要将 NULL 改写为 shellcode 地址即可触发执行。

### 10.2 现代防御机制

| 防御手段 | 效果 | 说明 |
|----------|------|------|
| Partial RELRO | 将 `.dtors`、`.ctors`、`.jcr`、`.dynamic`、`.got`（非 `.got.plt`）标记为只读 | GCC 默认启用 `-Wl,-z,relro` |
| Full RELRO | 同时将 `.got.plt` 标记为只读；`.fini_array` 也受保护 | 需 `-Wl,-z,relro,-z,now` |
| NX 位 / W^X | 数据页不可执行，shellcode 直接运行失效 | 现代 CPU/OS 默认开启 |
| ASLR | 随机化 `.dtors` 地址，增加定向覆写难度 | Linux 内核默认开启 |

> 在启用 Partial RELRO 后，`.dtors` 节在运行时即为只读，`.dtors` overwrite 攻击在现代环境中已无法直接奏效。

## 11. 现代发展：被 .fini_array 取代

### 11.1 .fini_array 的优势

随着 ELF 的发展，`.dtors` 节逐渐被 [[44.fini_array节|.fini_array]] 取代：

| 特性 | .dtors（旧） | .fini_array（新） |
|------|-------------|------------------|
| 节类型 | `SHT_PROGBITS` | `SHT_FINI_ARRAY` |
| 动态标签 | 无（依赖 `_fini` 间接调用） | `DT_FINI_ARRAY` + `DT_FINI_ARRAYSZ` |
| 哨兵值 | 需要（`-1` 和 `0`） | 不需要（`sh_size / sizeof(ptr)` 即元素数） |
| 遍历方式 | 手动解析哨兵 | 动态链接器直接使用大小信息 |
| 优先级排序 | 靠链接顺序间接控制 | 可通过 `.fini_array.N` 子节精确排序 |

GCC 4.7 引入 `--enable-initfini-array` 配置选项；现代 GCC（5+）在支持的目标上**默认生成 `.fini_array` 而非 `.dtors`**，`__attribute__((destructor))` 直接写入 `.fini_array`。

### 11.2 共存场景

在 GCC 过渡时期，`.dtors` 和 `.fini_array` 可能共存于同一链接输出中（例如 `crtbegin.o` 来自旧版，用户目标文件使用新工具链）。GNU ld 链接脚本通常包含如下合并规则，确保两者均被处理：

```ld
.fini_array     :
{
  PROVIDE_HIDDEN (__fini_array_start = .);
  KEEP (*(SORT_BY_INIT_PRIORITY(.fini_array.*) SORT_BY_INIT_PRIORITY(.dtors.*)))
  KEEP (*(.fini_array) KEEP (*(.dtors)))
  PROVIDE_HIDDEN (__fini_array_end = .);
}
```
