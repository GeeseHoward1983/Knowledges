# 详解ELF文件(三十五).interp节

.interp节是ELF（Executable and Linkable Format）文件中的一个重要节区，全称是"interpreter"（解释器）。它包含了程序解释器（通常是动态链接器）的路径名，在动态链接的可执行文件中起着关键作用。

## 1. 基本概念和作用

.interp节的主要作用是指定程序运行时需要使用的程序解释器（也称为动态链接器）。对于动态链接的可执行文件，这个解释器负责在程序运行时将程序链接到所需的共享库。

在Linux系统中，最常见的.interp节内容是：

```
/lib64/ld-linux-x86-64.so.2
```

这是64位Linux系统的标准动态链接器路径。

**三条核心事实**：
1. `.interp` 仅存在于**动态可执行文件**中，不出现在共享库（.so）和静态可执行文件中
2. 内核在 `execve()` 时读取此路径，**不做任何假设**，路径完全由 ELF 文件自身决定
3. 解释器路径是 **ABI 的一部分**，与 libc 版本紧密绑定，随意修改会导致可执行文件无法运行

## 2. 数据结构

.interp节的数据结构非常简单，它只包含一个以NULL结尾的字符串，即程序解释器的路径名。

```
.interp节内容示例：
/lib64/ld-linux-x86-64.so.2\0
```

节头属性：
- `sh_type = SHT_PROGBITS`（程序数据，由链接器填写）
- `sh_flags = SHF_ALLOC`（需要映射到进程地址空间）
- `sh_size`：路径字符串长度 + 1（含末尾 `\0`）
- 通常是文件中偏移最小的节之一（排在节头表之前），便于内核快速定位

## 3. 与程序头表的关系

.interp节通常对应一个特殊的程序段（Segment），其类型为 PT_INTERP（见 [[03.程序头表]]）。这意味着在程序加载过程中，操作系统会识别这个段并使用其中指定的解释器来加载程序。

```
Program Headers:
Type           Offset   VirtAddr   PhysAddr   FileSiz MemSiz  Flg Align
INTERP         0x000238 0x00400238 0x00400238 0x0001c 0x0001c R   0x1
    [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

PT_INTERP 段通常是程序头表中 `p_filesz` 最小的段，权限为只读（`PF_R`，无执行权限）。其 `p_offset`、`p_filesz`、`p_memsz` 与 .interp 节的 `sh_offset`、`sh_size` 完全对应。

## 4. 结构图示

.interp 是内核加载动态可执行文件时的"第一跳"——内核据此先把控制权交给动态链接器：

```mermaid
graph LR
  EXEC["动态可执行文件"] -->|PT_INTERP 段| INTERP[".interp\n/lib64/ld-linux-x86-64.so.2"]
  INTERP -->|内核读取并加载| LDSO["动态链接器 ld.so"]
  LDSO -->|加载依赖库 + 重定位| ENTRY["跳转到程序入口 e_entry"]
```

工作流程：

1. 当操作系统加载动态链接的可执行文件时，会检查程序头表中的 PT_INTERP 段
2. 找到.interp节中指定的程序解释器路径
3. 加载并运行该解释器（动态链接器）
4. 动态链接器负责解析和链接程序所需的共享库
5. 最终将控制权转交给程序的入口点

## 5. 内核处理 PT_INTERP 的详细流程

内核在 `execve()` 系统调用中处理 ELF 可执行文件时，PT_INTERP 的处理过程如下：

### 5.1 内核执行步骤（Linux 内核 `fs/binfmt_elf.c`）

```
execve(path, argv, envp)
 ├─ 读取 ELF 魔数，验证 e_ident
 ├─ 读取程序头表（Phdr[]）
 ├─ 找到 PT_INTERP 段
 │   └─ 读取 .interp 字符串（路径长度 < PATH_MAX）
 ├─ 打开解释器文件，验证其也是有效 ELF
 ├─ 映射可执行文件的 PT_LOAD 段到进程地址空间
 ├─ 映射解释器（ld.so）的 PT_LOAD 段
 ├─ 构建辅助向量（auxv），包含：
 │   ├─ AT_PHDR：可执行文件程序头表地址
 │   ├─ AT_PHNUM：程序头数量
 │   ├─ AT_ENTRY：可执行文件真实入口（e_entry）
 │   ├─ AT_BASE：解释器加载基址
 │   └─ AT_EXECFN：可执行文件路径名
 └─ 跳转到解释器入口点（ld.so 的 e_entry）
```

内核**不假设**解释器路径的格式，只要是有效路径即可。唯一的约束是路径长度不超过 `PATH_MAX`（通常 4096 字节）。

### 5.2 辅助向量（auxv）传递的信息

ld.so 启动后，从栈上读取辅助向量获取以下信息（无需重新解析 ELF 文件）：

| auxv 类型 | 说明 |
|---|---|
| AT_PHDR | 可执行文件程序头表的内存地址（用于定位 PT_DYNAMIC） |
| AT_PHENT | 程序头条目大小 |
| AT_PHNUM | 程序头条目数 |
| AT_BASE | ld.so 自身的加载基址（用于自举重定位） |
| AT_ENTRY | 可执行文件入口地址（ld.so 最后跳转到此） |
| AT_FLAGS | 处理器特定标志 |
| AT_PAGESZ | 系统页大小 |
| AT_RANDOM | 16 字节随机种子（用于 canary 等安全机制） |

```bash
# 查看辅助向量内容
LD_SHOW_AUXV=1 /bin/true
```

## 6. 各架构与发行版的动态链接器路径

不同架构和 C 库实现有不同的解释器路径，路径是 ABI 约定的一部分：

### 6.1 glibc（GNU C Library）各架构路径

| 架构 | 位宽 | 解释器路径 |
|---|---|---|
| x86 | 32位 | `/lib/ld-linux.so.2` |
| x86-64 | 64位 | `/lib64/ld-linux-x86-64.so.2` |
| x86-64 | 32位（x32 ABI） | `/libx32/ld-linux-x32.so.2` |
| ARM (EABI) | 32位软浮点 | `/lib/ld-linux.so.3` |
| ARM (EABI) | 32位硬浮点 | `/lib/arm-linux-gnueabihf/ld-linux.so.3` |
| AArch64 | 64位 | `/lib/ld-linux-aarch64.so.1` |
| RISC-V | 64位 | `/lib/ld-linux-riscv64-lp64d.so.1` |
| MIPS | 32位大端 | `/lib/ld.so.1` |
| MIPS | 64位 | `/lib64/ld.so.1` |
| PowerPC | 32位 | `/lib/ld.so.1` |
| PowerPC64 (ELFv2) | 64位 | `/lib64/ld64.so.2` |
| s390x | 64位 | `/lib/ld64.so.1` |
| LoongArch64 | 64位 | `/lib64/ld-linux-loongarch-lp64d.so.1` |

### 6.2 musl libc 各架构路径

musl 使用统一风格的路径命名，且动态链接器直接内嵌在 libc 中（即 `ld-musl-<arch>.so.1` 就是 libc）：

| 架构 | musl 解释器路径 |
|---|---|
| x86-64 | `/lib/ld-musl-x86_64.so.1` |
| x86 | `/lib/ld-musl-i386.so.1` |
| AArch64 | `/lib/ld-musl-aarch64.so.1` |
| ARM 硬浮点 | `/lib/ld-musl-armhf.so.1` |
| RISC-V 64 | `/lib/ld-musl-riscv64.so.1` |
| MIPS 64 | `/lib/ld-musl-mips64.so.1` |

musl 的动态链接器不支持 `LD_PRELOAD` 与 `LD_LIBRARY_PATH` 所有 glibc 语义；它的 lazy binding 行为也与 glibc 有差异（musl 默认 eager binding）。

### 6.3 多架构（Multiarch）Debian/Ubuntu 路径

Debian/Ubuntu 的 multiarch 方案将架构特定库放入对应子目录，解释器路径也随之变化：

| 目标三元组 | 解释器路径 |
|---|---|
| `x86_64-linux-gnu` | `/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2`（符号链接） |
| `i386-linux-gnu` | `/lib/i386-linux-gnu/ld-linux.so.2` |
| `aarch64-linux-gnu` | `/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1` |

通常 `/lib64/ld-linux-x86-64.so.2` 是指向 multiarch 路径的符号链接，保持向后兼容。

## 7. 实战：查看 .interp

```bash
readelf -p .interp /bin/ls       # 直接打印解释器路径
objdump -s -j .interp /bin/ls    # 十六进制查看
file /bin/ls                     # 也会输出解释器信息
```

```text
# 示例输出（代表性，非本机实跑）
$ readelf -p .interp /bin/ls
String dump of section '.interp':
  [     0]  /lib64/ld-linux-x86-64.so.2

$ file /bin/ls
/bin/ls: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), \
  dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, ...
```

## 8. 特殊情况

### 8.1 静态链接程序

静态链接的可执行文件通常不包含.interp节，因为它们不需要动态链接器。

```bash
gcc -static hello.c -o hello_static
file hello_static           # 输出 "statically linked"，无 interpreter 字样
readelf -l hello_static | grep INTERP    # 无输出
```

### 8.2 静态 PIE（Static PIE）

静态 PIE 是一种特殊情况：使用 PIE 编译，但**不依赖任何动态库**（静态链接 libc），也**没有 .interp 节**。内核直接将其映射到随机地址（利用 PIE + ASLR），然后跳转到 `e_entry` 执行自举重定位（如果有 `PT_DYNAMIC` 和 `DT_RELR` 的话）。

```bash
gcc -static-pie hello.c -o hello_spie
readelf -l hello_spie | grep -E 'INTERP|DYNAMIC'  # 无 INTERP，可能有 DYNAMIC
```

静态 PIE 常见于容器基础镜像（如 Alpine 使用 musl）和安全强化环境。

### 8.3 直接执行动态链接器

ld.so 自身可作为程序直接运行：

```bash
/lib64/ld-linux-x86-64.so.2 /bin/ls       # 通过 ld.so 运行 /bin/ls
/lib64/ld-linux-x86-64.so.2 --help        # 查看 ld.so 命令行选项
```

这在调试和沙箱场景中非常有用，无需修改 .interp 即可测试不同 ld.so 版本。

### 8.4 不同架构的系统

不同架构的系统使用不同的动态链接器：

- 32位x86系统：/lib/ld-linux.so.2
- 64位x86系统：/lib64/ld-linux-x86-64.so.2
- ARM系统：/lib/ld-linux-armhf.so.3

## 9. patchelf --set-interpreter 详解

`patchelf` 是修改 ELF 文件 .interp（以及 RPATH/SONAME 等）的工具，常用于：

- 将编译好的二进制移植到不同 Linux 发行版（glibc 路径不同）
- 使用特定版本的 ld.so（如 glibc 2.35 的 ld.so 运行针对 2.31 编译的程序）
- 容器/沙箱场景使用自定义动态链接器

### 9.1 基本用法

```bash
# 查看当前解释器路径
patchelf --print-interpreter /path/to/binary

# 修改解释器路径
patchelf --set-interpreter /custom/path/ld.so /path/to/binary

# 组合修改（同时设置 RPATH）
patchelf \
  --set-interpreter /nix/store/.../lib/ld-linux-x86-64.so.2 \
  --set-rpath /nix/store/.../lib \
  /path/to/binary
```

### 9.2 patchelf 的实现原理

当新路径比原路径长时，patchelf 无法原地修改（因为文件中紧跟 .interp 后的内容不可随意移动）。此时 patchelf 采用"重写节"策略：

1. 解析原始 ELF，记录所有节和程序头
2. 在文件末尾追加新的 .interp 内容
3. 更新 `PT_INTERP` 的 `p_offset`、`p_vaddr`、`p_filesz`、`p_memsz` 字段
4. 更新 `.interp` 的 `sh_offset`、`sh_size` 字段
5. 重写 ELF 文件

注意：patchelf 修改后的二进制在 checksum 校验（如 RPM/dpkg 完整性检查）中会失效，使用前需评估影响。

### 9.3 编译时指定解释器路径

无需 patchelf，也可在编译/链接时直接指定：

```bash
# GCC/Clang 通过 -Wl 传递链接器选项
gcc -Wl,--dynamic-linker=/custom/ld.so -o output input.c

# 直接调用 ld
ld --dynamic-linker=/custom/ld.so -o output input.o
```

## 10. glibc vs musl 动态链接器核心差异

| 特性 | glibc ld-linux.so | musl ld-musl-*.so.1 |
|---|---|---|
| 实现分离 | ld.so 与 libc.so.6 分离 | ld.so 即 libc（同一文件） |
| 延迟绑定 | 默认启用（除非 BIND_NOW） | 默认**立即绑定**（无延迟） |
| LD_PRELOAD | 完整支持 | 支持（语义略有差异） |
| `$ORIGIN` | 支持 | 支持 |
| dlopen 相容性 | 完整 | 基本支持（行为更严格） |
| RPATH/RUNPATH | 完整支持 | 基本支持 |
| GNU 符号版本控制 | 支持 | 不支持 |
| 调试（LD_DEBUG） | 丰富（all/libs/symbols 等） | 不支持（需 strace 替代） |
| 启动开销 | 稍高（延迟绑定基础设施） | 更低（立即绑定，无 PLT 状态机） |

## 11. 与其他节和段的关系

- **与PT_INTERP段**：.interp节通常对应 PT_INTERP 类型的程序段
- **与 [[18.dynamic节|.dynamic]] 节**：两者都与动态链接相关，但 .interp 指定"由谁来链接"，.dynamic 提供"链接所需的数据"
- **与链接器**：链接器在创建可执行文件时决定使用哪个动态链接器

## 12. 安全考虑

1. **程序解释器劫持**：恶意修改.interp节可能导致程序加载恶意的动态链接器——攻击者用自定义 ld.so 执行初始化代码，完全控制程序的加载过程
2. **二进制完整性验证**：安全扫描工具应检查 .interp 路径是否符合系统预期，偏离标准路径的可执行文件值得审查
3. **沙箱环境**：在某些沙箱或容器环境中，可能需要修改.interp节指向定制的动态链接器（如 `patchelf --set-interpreter`）
4. **NixOS/Guix 等函数式包管理**：这些发行版将 ld.so 放在哈希路径下（如 `/nix/store/xxx-glibc-2.37/lib/ld-linux-x86-64.so.2`），所有打包的二进制都通过 patchelf 修改了 .interp，保证使用对应版本的 libc

## 13. 实际意义

1. **动态链接支持**：使得程序能够使用共享库，减小可执行文件大小
2. **系统兼容性**：确保程序使用正确的动态链接器
3. **加载过程控制**：为操作系统提供加载程序所需的解释器信息

.interp节虽然内容简单，但它是动态链接可执行文件能够正常运行的关键组成部分。通过指定正确的程序解释器，它确保了程序在运行时能够正确地链接和加载所需的共享库。
