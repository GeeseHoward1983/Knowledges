# 详解ELF文件(十).shstrtab节

.shstrtab节（Section Header String Table）是ELF（Executable and Linkable Format）文件中的一个特殊字符串表节，用于存储所有节区名称的字符串。它是理解和解析ELF文件结构的关键组成部分。

## .shstrtab节基本概念

.shstrtab节是ELF文件中的节区头部字符串表节，它专门用于存储所有节区名称的字符串。在ELF文件中，每个节区都有一个名称，这些名称以字符串形式存储在.shstrtab节中，而节区头表中的sh_name字段则存储对应名称在.shstrtab节中的索引（即字节偏移）。

ELF 文件头（`Elf64_Ehdr`）中的 `e_shstrndx` 字段记录了 .shstrtab 节在节头表中的编号，工具和加载器首先读取该字段，才能定位并解析所有节名。若节数超过 65279（`SHN_LORESERVE - 1`），`e_shstrndx` 会被置为 `SHN_XINDEX`（0xffff），实际编号存于节头表第 0 项的 `sh_link` 字段。

## .shstrtab节的结构和组织方式

.shstrtab节本质上是一个字符串表，采用特殊的方式组织字符串：

### 1. 字符串存储格式

- 所有字符串连续存储在一个数据块中
- 每个字符串以空字符（`\0`）结尾
- 字符串之间直接相连，没有额外分隔符
- **首字节（偏移 0）固定为 `\0`**，代表空字符串；节头 sh_name = 0 表示无名节

### 2. 索引机制

- 索引值即字符串在 .shstrtab 字节数组中的**起始偏移量**，而非"第几个字符串"
- 通过偏移可以从任意位置开始读取，直到遇到 `\0` 为止
- 这种设计允许**后缀共享**：短字符串若是长字符串的后缀，可直接指向长字符串的中间位置，节省空间（详见下文）

### 3. 示例结构

```
偏移量  内容              说明
0x00    \0                空字符串（索引0，约定保留）
0x01    .symtab\0         ".symtab" 字符串（索引1）
0x09    .strtab\0         ".strtab" 字符串（索引9）
0x11    .shstrtab\0       ".shstrtab" 字符串（索引17，= 0x11）
0x1b    .text\0           ".text" 字符串（索引27，= 0x1b）
0x21    .rodata\0         ".rodata" 字符串（索引33）
0x29    .data\0           ".data" 字符串（索引41）
0x2f    .bss\0            ".bss" 字符串（索引47）
```

节头表中每个节头的 `sh_name` 字段存储的正是上面的偏移值，例如 `.text` 节头的 `sh_name = 0x1b`。

## 结构图示

节头表里每个节头的 `sh_name` 不是字符串本身，而是一个指向 .shstrtab 内偏移的"指针"：

```mermaid
graph LR
  SH["节头[i].sh_name = 0x07"] -->|偏移| STR[".shstrtab: \0.text\0.data\0.bss\0…"]
  STR -->|0x07 处读到| NAME["\".data\""]
  EH["ELF Header.e_shstrndx"] -.指出哪个节是 .shstrtab.-> SH
```

## .shstrtab节与ELF文件其他部分的关系

### 1. 与ELF头部的关系

ELF头部中的e_shstrndx字段指明了.shstrtab节在节区头表中的索引位置。这个信息对于解析节区名称至关重要（见 [[02.ELF文件头部]]）。

### 2. 与节区头表的关系

[[34.节头表|节区头表]]中的每个节区头都有一个sh_name字段，该字段是对应节区名称在.shstrtab节中的索引。通过这个索引，可以找到具体的节区名称字符串。

### 3. .shstrtab 自身的节头

.shstrtab 也在节头表中占有一个条目，因此 .shstrtab 节的 `sh_name` 也指向 .shstrtab 内的某个偏移，该偏移处存储的正是字符串 `".shstrtab\0"` 本身——它自我描述。

## 三种字符串表的区别

ELF文件中存在多个字符串表，它们用途不同、互不混淆：

| 字符串表 | 类型 | 存储内容 | 被谁索引 | SHF_ALLOC（运行时在内存） |
|---|---|---|---|---|
| **.shstrtab** | SHT_STRTAB | 节区名称 | 节头 sh_name（由 e_shstrndx 定位） | 否（通常） |
| .strtab | SHT_STRTAB | 符号名称（静态） | [[09.symtab节\|.symtab]] 的 st_name | 否 |
| .dynstr | SHT_STRTAB | 动态符号名/库名/版本名 | [[15.dynsym节\|.dynsym]] 的 st_name、[[18.dynamic节\|.dynamic]] 的 DT_* | 是 |

> 详见 [[16.dynstr节]]。三者结构完全相同（连续的 `\0` 结尾字符串），区别只在"服务对象"与"是否 ALLOC"。

## 字符串去重与后缀共享（SHF_STRINGS / SHF_MERGE）

### SHT_STRTAB 类节的内建去重

对于 `.shstrtab`、`.strtab`、`.dynstr` 等 `SHT_STRTAB` 类型的节，链接器在合并多个目标文件的字符串表时会自动进行**去重**和**后缀共享（tail/suffix merging）**优化：

- **完全重复**：两个目标文件中均有字符串 `"printf"` → 合并后只保留一份。
- **后缀共享**：若已有字符串 `"_IO_printf"`，则 `"printf"` 可直接指向前者偏移 4 处，无需额外存储。

### SHF_MERGE | SHF_STRINGS 机制（用于常量字符串节）

对于存放字符串常量的 `.rodata` 节，链接器支持用 `SHF_MERGE | SHF_STRINGS` 标志触发跨目标文件的字符串合并：

```c
// 编译器可生成带有 SHF_MERGE|SHF_STRINGS 的 .rodata.str1.1 节
// 链接器据此合并不同 .o 中相同的字符串常量
```

`SHF_MERGE` 的约束：
- 节必须是只读的（程序运行时不可修改）
- 每个元素必须有独立的重定位记录
- `sh_entsize` 须为 0 或 1（字节粒度的字符串）

此优化可显著减小含大量重复字符串常量的程序体积。

### .shstrtab 本身通常不标 SHF_STRINGS

`.shstrtab` 的 `sh_type = SHT_STRTAB`，`sh_flags` 通常为 0（无 SHF_ALLOC，无 SHF_MERGE），因为它只在链接/分析阶段需要，不需要合并优化，且工具已知其格式无需额外标志。

## .shstrtab节的作用

### 1. 节区名称解析

.shstrtab节使得工具和系统能够将节区索引转换为可读的节区名称，例如：

- 将索引1转换为".text"
- 将索引7转换为".data"
- 将索引13转换为".bss"

### 2. 工具支持

各种分析工具（如readelf、objdump等）依赖.shstrtab节来显示节区的名称，提高可读性。

### 3. 系统处理

操作系统和链接器使用.shstrtab节来识别和处理不同类型的节区。链接器按节名决定如何合并（如将多个输入文件的 `.text` 合并到输出文件的 `.text`）；内核加载器通过节名识别 `.interp`、`.dynamic` 等特殊节；调试器通过节名定位 `.debug_*` 系列节。

## 实战：查看 .shstrtab

```bash
readelf -x .shstrtab a.out      # 十六进制+ASCII 查看
readelf -p .shstrtab a.out      # 按字符串逐条打印（更直观）
readelf -S a.out                # 查看节头表，包括 sh_name 字段的偏移值
```

```text
# 示例输出（代表性，非本机实跑）
$ readelf -p .shstrtab a.out
String dump of section '.shstrtab':
  [     1]  .symtab
  [     9]  .strtab
  [    11]  .shstrtab
  [    1b]  .text
  [    21]  .rodata
  [    29]  .data
  [    2f]  .bss
```

左侧 `[ 偏移 ]` 正是某个节头 `sh_name` 会引用的值（十六进制）。

查看 ELF 文件头中的 e_shstrndx 字段，确定 .shstrtab 位于哪个节：

```bash
readelf -h a.out | grep "Section header string"
# Section header string table index: 30    ← .shstrtab 是第 30 个节
```

```text
# 示例输出（代表性，非本机实跑）
$ readelf -S a.out | head -5
There are 31 section headers, starting at offset 0x3978:

Section Headers:
  [Nr] Name              Type             Address           Offset
  [ 0]                   NULL             0000000000000000  00000000
  [ 1] .interp           PROGBITS         0000000000000318  00000318
  ...
  [30] .shstrtab         STRTAB           0000000000000000  000033a0
```

`.shstrtab` 的 `Address = 0`，印证了它没有 SHF_ALLOC，不映射到进程地址空间。

## .shstrtab节在不同文件类型中的存在

### 1. 目标文件（.o文件）

- 包含完整的.shstrtab节
- 用于后续链接过程中的节区识别

### 2. 可执行文件

- 通常包含.shstrtab节
- 主要用于调试和分析目的

### 3. 共享库文件

- 包含.shstrtab节用于调试
- 可以通过strip命令移除以减小文件大小
- 但极端情况下（如被 `strip --strip-section-headers` 或直接修改 ELF 头把 e_shstrndx 置零），.shstrtab 被删除或"假隐藏"后，readelf/objdump 仍可运行，只是节名显示为空或数字索引

### 4. 特殊情况：e_shstrndx = SHN_XINDEX

当 ELF 文件节数 >= 65280（SHN_LORESERVE）时，e_shstrndx 无法存放真实的节编号：

```
e_shstrndx = 0xffff（SHN_XINDEX）
→ 真实编号存于节头表第 0 项的 sh_link 字段
```

## .shstrtab节的生成过程

### 1. 编译阶段

- 编译器为每个节区生成名称
- 将节区名称存储在目标文件的.shstrtab节中

### 2. 链接阶段

- 链接器合并多个目标文件的.shstrtab节
- 重新组织字符串表以消除重复（后缀共享优化）
- 更新ELF头部中的e_shstrndx字段，指向最终的 .shstrtab 节编号

## 实际示例

考虑一个典型的ELF文件，其.shstrtab节可能包含以下字符串：

```
\0.text\0.data\0.bss\0.shstrtab\0.strtab\0.symtab\0.rodata\0
```

对应的索引关系：

- 索引0：""（空字符串）
- 索引1：".text"
- 索引7：".data"
- 索引13：".bss"
- 索引18：".shstrtab"
- 索引28：".strtab"
- 索引36：".symtab"
- 索引44：".rodata"

在节区头表中，每个节区的sh_name字段将包含相应的索引值。

### 后缀共享实例

现代链接器会对 .shstrtab 进行后缀共享优化。例如，节名 `.rela.text` 和 `.text` 共存时：

```
偏移  内容
0x00  \0
0x01  .rela.text\0       ← 长字符串
0x0c  .text\0            ← 如无后缀共享则独立存放
```

开启后缀共享后，`.text` 可直接指向 `.rela.text` 内偏移 6 处（`0x01 + 5 = 0x06`），节省 6 字节。对于有数十个 `.rela.*` 节的大型项目，节省效果相当可观。

## .shstrtab节的安全考虑

### 1. 信息泄露

- .shstrtab节包含程序的节区结构信息
- 可能被攻击者用于分析程序结构
- 发布版本通常会保留.shstrtab节，因为它对执行不是必需的

### 2. 节区保护

- 可以使用strip命令移除.shstrtab节
- 有助于减小文件大小并增加逆向工程难度
- 某些混淆工具会故意破坏 .shstrtab（如将节名替换为乱码），使 readelf -S 输出显示为乱码，干扰静态分析，但不影响程序执行

## 总结

.shstrtab节是ELF文件中存储节区名称字符串的关键节区，它通过索引机制与节区头表紧密关联。通过.shstrtab节，各种工具能够将节区索引转换为可读的节区名称，大大提高了ELF文件的可读性和可分析性。

理解.shstrtab节的结构和作用对于程序分析、调试和安全研究都具有重要意义。它是连接机器可读的索引和人类可读的名称的重要桥梁，使得ELF文件的结构更加清晰和易于理解。
