# 第 15 章 · 生成器与构建系统

> 基准版本：CMake 4.3.4

到这里为止，前面所有章节讲的都是"怎么写 `CMakeLists.txt`"——也就是怎么描述你的项目。但 CMake 本身**不编译任何代码**：它是一个"构建系统生成器（build system generator）"，它读你的 `CMakeLists.txt`，然后产出一套**原生构建文件**（`Makefile`、`build.ninja`、`.sln`/`.vcxproj`、`.xcodeproj` 等），真正的编译动作交给底层的 `make` / `ninja` / `MSBuild` / `xcodebuild` 去干。**生成器（generator）就是决定"产出哪一种原生构建文件"的那个旋钮。**

选错生成器或不理解生成器的脾气，是新手最常踩的坑：在 Visual Studio 生成器下设了 `CMAKE_BUILD_TYPE` 却发现毫无效果、在 Ninja 下想切 Debug/Release 却要重新跑一遍 `cmake`、在 macOS 上 `cmake ..` 默认出来的是 Makefile 而不是 Xcode 工程……这些现象背后都是**单配置 / 多配置生成器**这条核心分界线。本章会把生成器的分类、单 vs 多配置的本质差异、各主流生成器（VS / Ninja / Xcode）的专属选项，以及统一的"驱动构建"命令 `cmake --build`，一次讲透。

阅读前置：建议先读完[[42.Cmake/03 - 第一个项目与构建流程.md|第 3 章（第一个项目与构建流程）]]（理解"配置 → 生成 → 构建"三段式）与[[42.Cmake/07 - 生成器表达式.md|第 7 章（生成器表达式）]]（本章用 `$<CONFIG>` 写跨配置逻辑）。Presets 中的 `generator` 字段在[[42.Cmake/16 - CMake Presets.md|第 16 章]]详述。

## 15.1 生成器是什么

### 15.1.1 三段式里的"生成"那一段

回顾 CMake 的工作流：

```bash
# 第 1 段：配置（Configure）—— 读 CMakeLists.txt，跑探测、求值变量
# 第 2 段：生成（Generate）—— 把内部模型翻译成原生构建文件   ← 生成器在这里登场
# 第 3 段：构建（Build）   —— 调用原生构建工具真正编译链接
cmake -S . -B build -G "Ninja"      # 第 1、2 段一起跑，-G 指定生成器
cmake --build build                 # 第 3 段
```

`-G <generator-name>` 就是告诉 CMake："第 2 段请产出 Ninja 文件"。一个 build 目录（build tree）**在第一次配置时就和某个生成器绑死了**——`CMakeCache.txt` 里会记下 `CMAKE_GENERATOR`。想换生成器，不能在原目录上 `-G` 改，必须**删掉整个 build 目录**重新配置（或者用一个全新的 build 目录）。这是初学者第二常踩的坑：

```bash
# ❌ 这样改不了生成器，CMake 会报 "does not match the generator used previously"
cmake -S . -B build -G "Unix Makefiles"
cmake -S . -B build -G "Ninja"          # 报错！build 已绑定 Unix Makefiles

# ✅ 正确做法：换目录，或先清空
cmake -S . -B build-ninja -G "Ninja"    # 用新目录
# 或
rm -rf build && cmake -S . -B build -G "Ninja"
```

### 15.1.2 查看本机可用的生成器

`cmake --help` 的**末尾**会列出当前平台上 CMake 知道的所有生成器，默认生成器用 `*` 标注：

```bash
cmake --help
```

输出尾部形如（Windows 上装了 VS 2022 的典型结果）：

```text
Generators

The following generators are available on this platform (* marks default):
* Visual Studio 17 2022        = Generates Visual Studio 2022 project files.
                                 Use -A option to specify architecture.
  Visual Studio 16 2019        = Generates Visual Studio 2019 project files.
  Ninja                        = Generates build.ninja files.
  Ninja Multi-Config           = Generates build-<Config>.ninja files.
  NMake Makefiles              = Generates NMake makefiles.
  NMake Makefiles JOM          = Generates JOM makefiles.
  MinGW Makefiles              = Generates a make file for use with mingw32-make.
  MSYS Makefiles               = Generates MSYS makefiles.
  Unix Makefiles               = Generates standard UNIX makefiles.
  ...
```

> 注意：列表内容**因平台、因机器而异**。Linux/macOS 上不会出现 Visual Studio 生成器；`Ninja` 是否出现取决于 `ninja` 是否在 PATH 上（CMake 自带 Ninja 文件生成能力，但运行 `ninja` 需要本机装了 ninja 可执行）。生成器名字**大小写敏感、空格敏感**，必须和 `--help` 里的写法完全一致，建议永远用引号包起来：`-G "Unix Makefiles"`。

要查某个具体生成器支持哪些选项（平台、toolset 等），可以读官方手册页 `cmake-generators.7`，或针对单个生成器：

```bash
cmake --help-manual cmake-generators.7   # 全量生成器手册
```

## 15.2 生成器分类总表

CMake 4.3.4 的生成器大致分四类：**Makefile 系**（单配置）、**Ninja 系**、**IDE 系**（多配置）、**其他/历史**。下表汇总：

| 类别 | 生成器名（`-G` 用） | 原生工具 | 单/多配置 | 主要平台 | 备注 |
|---|---|---|---|---|---|
| **Makefile** | `Unix Makefiles` | `make` | 单配置 | Linux/macOS/Unix | Unix 类系统默认 |
| | `MinGW Makefiles` | `mingw32-make` | 单配置 | Windows | MinGW 工具链，**不需要 sh.exe 在 PATH** |
| | `MSYS Makefiles` | `make`（MSYS） | 单配置 | Windows | MSYS 环境，POSIX 风格 |
| | `NMake Makefiles` | `nmake` | 单配置 | Windows | MSVC 自带 nmake，需在 VS 命令行环境 |
| | `NMake Makefiles JOM` | `jom` | 单配置 | Windows | JOM = 并行版 nmake |
| **Ninja** | `Ninja` | `ninja` | **单配置** | 全平台 | 速度最快、最推荐的命令行生成器 |
| | `Ninja Multi-Config` | `ninja` | **多配置** | 全平台 | 3.17+ 引入，命令行下的多配置方案 |
| **IDE（多配置）** | `Visual Studio 17 2022` | `MSBuild` | **多配置** | Windows | 当前主流 VS |
| | `Visual Studio 16 2019` | `MSBuild` | **多配置** | Windows | 上一代 VS |
| | `Visual Studio 18 2026` | `MSBuild` | **多配置** | Windows | 最新 VS（4.3 已支持） |
| | `Xcode` | `xcodebuild` | **多配置** | macOS | Apple 平台官方 IDE |
| **其他/历史** | `Watcom WMake` | `wmake` | 单配置 | Windows/DOS | Open Watcom |
| | `Green Hills MULTI` | GHS MULTI | 多配置 | 嵌入式 | 嵌入式 RTOS 工具链 |
| | `Borland Makefiles` | `make`（Borland） | 单配置 | Windows | **历史遗留**，新项目勿用 |

几条选型建议：

- **命令行 / CI / 跨平台**：首选 `Ninja`（要切多配置就用 `Ninja Multi-Config`）。它最快、依赖追踪最准、各平台行为最一致。
- **Windows 上要在 VS IDE 里点按钮调试**：用 `Visual Studio 17 2022`，产出 `.sln` 双击即开。
- **macOS 上要在 Xcode 里调试**：用 `Xcode`。
- **只想最朴素地在 Linux 上编译**：`Unix Makefiles` 也完全够用，但 `Ninja` 通常更快。

> 关于 IDE 生成器还有一种"用 IDE 的编辑器、但底层走 Ninja"的现代姿势：VS / VS Code / CLion 都可以打开一个 `Ninja` 配置的 build 目录或基于 Presets 工作，从而既享受 Ninja 的速度，又有 IDE 的智能感知。是否一定要用 VS 生成器，取决于你是否需要原生 `.sln` 工程文件本身。

## 15.3 单配置 vs 多配置（核心概念）

这是整章最重要的一节，理解它能让你少踩一大半坑。

### 15.3.1 两种构建模型的本质区别

所谓"配置（configuration）"指的是 `Debug` / `Release` / `RelWithDebInfo` / `MinSizeRel` 这四个标准构建类型之一（也可自定义）。它们的差别在编译/链接 flag：`Debug` 带调试符号、不优化、定义 `_DEBUG`；`Release` 开 `-O3`/`/O2`、定义 `NDEBUG`；`RelWithDebInfo` 优化的同时保留符号；`MinSizeRel` 优化体积。

**关键问题是：这个"用哪个配置"的决定，在什么时候做？**

- **单配置生成器（single-config）**：一个 build 目录**只对应一个配置**。配置类型在**配置期（跑 `cmake` 时）**就钉死，由缓存变量 `CMAKE_BUILD_TYPE` 决定。想要 Debug 又要 Release，得开**两个 build 目录**分别配置。代表：所有 Makefile 生成器、`Ninja`。
- **多配置生成器（multi-config）**：一个 build 目录**同时容纳所有配置**。配置类型在**构建期（跑 `cmake --build` 时）**才用 `--config <cfg>` 选，同一套工程文件可反复构建出 Debug、Release……此时 `CMAKE_BUILD_TYPE` **完全无效**，改用 `CMAKE_CONFIGURATION_TYPES` 列出可选配置。代表：所有 Visual Studio 生成器、`Xcode`、`Ninja Multi-Config`。

### 15.3.2 单配置的用法

```bash
# 单配置：配置期定类型，每个类型一个目录
cmake -S . -B build-debug   -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release

cmake --build build-debug      # 出来的是 Debug 产物
cmake --build build-release    # 出来的是 Release 产物
```

`CMakeLists.txt` 里给 `CMAKE_BUILD_TYPE` 一个合理默认值，是单配置项目的标准做法（用户没指定时不要让它空着，空 `CMAKE_BUILD_TYPE` 意味着既不带优化也不带 `-g`，往往不是想要的）：

```cmake
# 仅对单配置生成器设默认 Build Type
get_property(_is_multi_config GLOBAL PROPERTY GENERATOR_IS_MULTI_CONFIG)
if(NOT _is_multi_config AND NOT CMAKE_BUILD_TYPE)
  set(CMAKE_BUILD_TYPE "RelWithDebInfo" CACHE STRING
      "Build type (Debug/Release/RelWithDebInfo/MinSizeRel)" FORCE)
  # 让 GUI / ccmake 的下拉框有候选项
  set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
               Debug Release RelWithDebInfo MinSizeRel)
endif()
```

### 15.3.3 多配置的用法

```bash
# 多配置：配置一次，构建期反复选类型
cmake -S . -B build -G "Ninja Multi-Config"   # 或 VS / Xcode，不传 CMAKE_BUILD_TYPE
cmake --build build --config Debug            # 构建 Debug
cmake --build build --config Release          # 同一目录再构建 Release
```

想限定可用配置（例如只要 Debug + Release，去掉另外两个），用 `CMAKE_CONFIGURATION_TYPES`：

```cmake
# 多配置生成器下裁剪可用配置
if(CMAKE_CONFIGURATION_TYPES)
  set(CMAKE_CONFIGURATION_TYPES "Debug;Release" CACHE STRING "" FORCE)
endif()
```

> ⚠️ **最经典的坑**：在 VS / Xcode / Ninja Multi-Config 下传 `-DCMAKE_BUILD_TYPE=Release` —— **它会被忽略**，你以为在编 Release，构建时不加 `--config` 默认却编了 Debug。反过来，在 `Unix Makefiles` / `Ninja` 下传 `--config Release` 给 `cmake --build` —— 单配置生成器会**忽略 `--config`**（除非你配置期就设了对应的 `CMAKE_BUILD_TYPE`）。**配置期 `CMAKE_BUILD_TYPE` ↔ 单配置；构建期 `--config` ↔ 多配置**，两者不要混用。

### 15.3.4 写跨配置的可移植代码

要写一段"无论单配置还是多配置都正确"的逻辑，**不要读 `CMAKE_BUILD_TYPE`**（它在多配置下是空的），而要用生成器表达式 `$<CONFIG>` 与全局属性 `GENERATOR_IS_MULTI_CONFIG`：

```cmake
# $<CONFIG> 在生成期按"当前正在构建的配置"求值，单/多配置都对
target_compile_definitions(app PRIVATE
  $<$<CONFIG:Debug>:APP_DEBUG=1>
  $<$<CONFIG:Release>:APP_FAST=1>
)

# 不同配置链接不同的库版本
target_link_libraries(app PRIVATE
  $<$<CONFIG:Debug>:foo_d>
  $<$<NOT:$<CONFIG:Debug>>:foo>
)

# 判定当前生成器是否多配置（注意：这是只读全局属性，不是变量）
get_property(_multi GLOBAL PROPERTY GENERATOR_IS_MULTI_CONFIG)
message(STATUS "Multi-config generator: ${_multi}")
```

多配置下输出目录通常按配置分子目录（如 `Debug/`、`Release/`），跨配置写路径时也应配合 `$<CONFIG>`：

```cmake
set_target_properties(app PROPERTIES
  RUNTIME_OUTPUT_DIRECTORY "${CMAKE_BINARY_DIR}/bin/$<CONFIG>")
```

### 15.3.5 单 vs 多配置对比总表

| 维度 | 单配置生成器 | 多配置生成器 |
|---|---|---|
| 代表生成器 | `Unix Makefiles`、`Ninja`、各 Makefile 系 | Visual Studio、`Xcode`、`Ninja Multi-Config` |
| 配置类型何时决定 | **配置期**（跑 `cmake`） | **构建期**（跑 `cmake --build`） |
| 控制变量 | `CMAKE_BUILD_TYPE`（缓存变量） | `CMAKE_CONFIGURATION_TYPES`（列出候选） |
| 切换配置的代价 | 需另开 build 目录重新配置 | 同一目录加 `--config` 即可 |
| 构建命令 | `cmake --build build` | `cmake --build build --config Release` |
| `CMAKE_BUILD_TYPE` 是否有效 | ✅ 有效 | ❌ **被忽略** |
| `--config` 是否有效 | ❌ 基本被忽略 | ✅ 有效（不传则取默认） |
| `GENERATOR_IS_MULTI_CONFIG` | `FALSE` | `TRUE` |
| 跨配置写逻辑 | `$<CONFIG>` 或读 `CMAKE_BUILD_TYPE` | **必须用 `$<CONFIG>`** |
| 默认输出目录 | 直接在 build 下 | 常带 `Debug/`、`Release/` 子目录 |

## 15.4 Visual Studio 生成器细节

VS 生成器产出 `.sln` 解决方案与 `.vcxproj` 工程，底层由 `MSBuild` 构建。它是多配置生成器，有两个 VS 专属的命令行旋钮：`-A`（平台/架构）和 `-T`（toolset）。

### 15.4.1 选择平台架构：`-A`

新式 VS 生成器（VS 2019/2022/2026）的目标架构通过 `-A` 指定，**不再**像老式那样把架构写进生成器名（旧的 `Visual Studio 16 2019 Win64` 写法已废弃）：

**`-A <platform>`**：指定目标平台架构。

- `-A Win32`：32 位 x86。
- `-A x64`：64 位 x64（VS 2019/2022 在 64 位主机上的**默认**）。
- `-A ARM64`：64 位 ARM。
- `-A ARM64EC`：ARM64EC（与 x64 兼容的 ARM64）。

```bash
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake -S . -B build -G "Visual Studio 17 2022" -A ARM64
```

该值会写入缓存变量 `CMAKE_GENERATOR_PLATFORM`，也可通过 `-DCMAKE_GENERATOR_PLATFORM=x64` 设置（等价于 `-A`）。

### 15.4.2 选择 toolset：`-T`

**`-T <toolset-spec>`**：指定 MSBuild 平台工具集（PlatformToolset），并可附带子选项。常用形态：

- `-T v143`：用 VS 2022 的工具集（VS 2019 默认 `v142`，VS 2026 为 `v145`）。可借此用新 IDE 编译旧工具集。
- `-T ClangCL`：用 Visual Studio 内置的 **clang-cl** 工具集（MSVC 兼容的 Clang 前端）。
- `-T v143,host=x64`：选 toolset 的同时，指定**主机工具**用 64 位版（避免 32 位 `cl.exe` 在大项目上爆内存）。`host=x86` 则反之。
- `-T v143,version=14.40`：固定到某个具体的 MSVC 工具集次版本（多版本并存时锁定）。
- `-T v141_xp`：带 XP 子工具集（历史用途，针对 Windows XP）。

```bash
# 用 clang-cl + 64 位主机工具构建 x64
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T "ClangCL,host=x64"

# 锁定 MSVC 工具集次版本
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T "v143,version=14.40"
```

该值写入缓存变量 `CMAKE_GENERATOR_TOOLSET`（等价于 `-DCMAKE_GENERATOR_TOOLSET=...`）。

### 15.4.3 与 `MSVC` / `MSVC_VERSION` 的关系

当编译器是 MSVC（或 clang-cl 走 MSVC 兼容前端）时，CMake 会设置一组识别变量，供 `CMakeLists.txt` 做条件判断：

- **`MSVC`**：布尔，编译器为 MSVC ABI 时为真（VS 生成器 + MSVC、或 Ninja + cl.exe、甚至 clang-cl 都会为真）。注意 `MSVC` 反映的是**编译器**，而非生成器——用 Ninja 调 `cl.exe` 时 `MSVC` 同样为真。
- **`MSVC_VERSION`**：MSVC 编译器内部版本号（如 VS 2022 17.10 对应 `1940` 一带）。用于精细的版本门控。
- **`MSVC_TOOLSET_VERSION`**：工具集版本（如 `143`）。
- **`CMAKE_VS_PLATFORM_NAME`**：当前 VS 平台名（`x64`/`Win32`/`ARM64`），VS 生成器专属。

```cmake
if(MSVC)
  target_compile_options(app PRIVATE /W4 /permissive-)
  if(MSVC_VERSION GREATER_EQUAL 1930)        # VS 2022+
    target_compile_options(app PRIVATE /Zc:preprocessor)
  endif()
endif()
```

更系统的编译器识别（`CMAKE_<LANG>_COMPILER_ID` 等）见[[42.Cmake/14 - 编译器、语言标准与特性.md|第 14 章]]。

### 15.4.4 解决方案/工程结构与文件夹分组

VS 生成器为整个 build 生成一个 `.sln`，每个 target 一个 `.vcxproj`。CMake 还会自动加几个"伪工程"：

- **`ALL_BUILD`**：构建全部 target（相当于默认 target）。
- **`ZERO_CHECK`**：检测 `CMakeLists.txt` 是否变化，变了就自动重跑 CMake（这就是你在 VS 里改了 `CMakeLists.txt` 一编译它会先重新生成的原因）。
- **`INSTALL`** / **`PACKAGE`** / **`RUN_TESTS`**：对应 `cmake --install`、CPack、CTest。

target 多了，VS 解决方案资源管理器会很乱。用全局属性 `USE_FOLDERS` + target 属性 `FOLDER` 把工程按虚拟文件夹归类：

```cmake
set_property(GLOBAL PROPERTY USE_FOLDERS ON)   # 4.x 默认即为 ON，显式写更稳妥

set_target_properties(core util PROPERTIES FOLDER "Libraries")
set_target_properties(app_gui app_cli PROPERTIES FOLDER "Apps")
set_target_properties(unit_tests PROPERTIES FOLDER "Tests")
# FOLDER 支持斜杠表示层级
set_target_properties(third_party_foo PROPERTIES FOLDER "ThirdParty/foo")
```

> `ZERO_CHECK`、`ALL_BUILD` 等预定义工程也可塞进文件夹：用全局属性 `PREDEFINED_TARGETS_FOLDER`（默认 `CMakePredefinedTargets`）调整它们的归属名。

源文件在工程内的分组（Filters）用 `source_group()`，与 IDE 折叠展示有关，此处不展开。

## 15.5 Ninja 与 Ninja Multi-Config

### 15.5.1 为什么 Ninja 快且一致

Ninja 是一个刻意"做得很小"的构建工具：它不像 `make` 那样有复杂的内置规则和宏展开，而是消费一份由生成器（CMake）写好的、扁平化的 `build.ninja`。这带来几个实打实的好处：

- **增量构建判断极快**：Ninja 的依赖图和文件时间戳检查经过专门优化，几千个目标的 no-op 构建（什么都没改）通常在亚秒级返回；`make` 在同等规模下慢得多。
- **依赖追踪更准**：CMake + Ninja 用编译器生成的 `.d` depfile 精确追踪头文件依赖，改一个头只重编真正受影响的 TU。
- **默认全并行**：Ninja 默认按 CPU 核数并行，不用像 `make` 那样手动记得加 `-j`。
- **跨平台一致**：同一份 `CMakeLists.txt` 在 Linux/macOS/Windows 上用 Ninja 生成，构建行为高度一致，特别适合 CI。

代价是：Ninja 是**单配置**生成器，切 Debug/Release 要么开两个 build 目录，要么改用下面的 Multi-Config 版本。

```bash
# 前提：本机 PATH 里有 ninja 可执行；Windows 上需在 VS 开发者命令行里跑（让 cl.exe 可见）
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build            # Ninja 默认全核并行
```

### 15.5.2 Ninja Multi-Config（3.17+）

`Ninja Multi-Config` 是 CMake 3.17 引入的多配置版 Ninja——**命令行环境下想要"一个目录多配置"的最佳选择**，无需 VS/Xcode 这类 IDE。它与普通 Ninja 的差别：不再只生成一个 `build.ninja`，而是给每个配置各生成一个 `build-<Config>.ninja`（如 `build-Debug.ninja`、`build-Release.ninja`），外加一个默认入口 `build.ninja`。

```bash
cmake -S . -B build -G "Ninja Multi-Config"
cmake --build build --config Debug      # 走 build-Debug.ninja
cmake --build build --config Release    # 走 build-Release.ninja
```

四个专属变量（都在配置期设）：

**`CMAKE_CONFIGURATION_TYPES`**：列出要生成的配置集合，默认 `Debug;Release;RelWithDebInfo`。

**`CMAKE_DEFAULT_BUILD_TYPE`**：指定默认入口 `build.ninja` 对应哪个配置——即 `cmake --build build` **不带 `--config`** 时构建的配置。不设则取 `CMAKE_CONFIGURATION_TYPES` 的第一个。

**`CMAKE_DEFAULT_CONFIGS`**：在默认 `build.ninja` 里，"无配置后缀的目标"实际构建哪些配置（可设多个，或 `all`）。

**`CMAKE_CROSS_CONFIGS`**：开启**跨配置（cross-config）模式**——允许从任意一个 `build-<Config>.ninja` 里构建**别的**配置的目标（生成形如 `<target>:<OtherConfig>`、`<target>:all` 的目标）。值必须是 `CMAKE_CONFIGURATION_TYPES` 的子集，设 `all` 表示全部互通。这对"先编 Release 库再用 Debug 工具跑它"这类跨配置依赖很有用。

```cmake
set(CMAKE_CONFIGURATION_TYPES "Debug;Release;RelWithDebInfo" CACHE STRING "" FORCE)
set(CMAKE_CROSS_CONFIGS "all" CACHE STRING "" FORCE)        # 任意配置间可互相构建
set(CMAKE_DEFAULT_BUILD_TYPE "Release" CACHE STRING "" FORCE)
set(CMAKE_DEFAULT_CONFIGS "all" CACHE STRING "" FORCE)
```

跨配置模式下可以直接对 ninja 点名跨配置目标：

```bash
cd build
ninja -f build-Debug.ninja app:Release    # 在 Debug 文件里构建 Release 的 app
ninja -f build-Debug.ninja app:all        # 构建 app 的所有 cross-config 配置
```

## 15.6 Xcode 生成器

`Xcode` 是 macOS 上的多配置生成器，产出 `.xcodeproj`（多 target 时还有 workspace），底层由 `xcodebuild` 构建。

```bash
cmake -S . -B build -G Xcode
cmake --build build --config Release          # 等价于在 Xcode 里选 Release scheme
open build/MyProject.xcodeproj                # 直接在 Xcode IDE 里打开调试
```

- **scheme / configuration**：Xcode 工程的 configuration 即 CMake 的配置（默认 `CMAKE_CONFIGURATION_TYPES` = `Debug;Release;...`），构建期用 `--config` 选，与 VS 同理。
- **`CMAKE_XCODE_*` 系列变量**：用于把任意 Xcode build setting 透传给工程。最常用的是通配形式 **`CMAKE_XCODE_ATTRIBUTE_<name>`**，会被翻译成对应的 Xcode build setting。例如：

```cmake
# 把 Xcode build settings 透传进工程
set(CMAKE_XCODE_ATTRIBUTE_CLANG_ENABLE_OBJC_ARC YES)
set(CMAKE_XCODE_ATTRIBUTE_GCC_WARN_64_TO_32_BIT_CONVERSION NO)
set(CMAKE_XCODE_GENERATE_SCHEME ON)   # 为每个 target 生成 scheme，方便命令行/CI 调度
```

- **代码签名（简述）**：iOS/macOS 打包绕不开签名，常用三个透传属性：

```cmake
set(CMAKE_XCODE_ATTRIBUTE_DEVELOPMENT_TEAM "ABCDE12345")            # 开发者团队 ID
set(CMAKE_XCODE_ATTRIBUTE_CODE_SIGN_IDENTITY "Apple Development")   # 签名身份
set(CMAKE_XCODE_ATTRIBUTE_CODE_SIGN_STYLE "Automatic")             # 自动/手动签名
```

更完整的签名/打包细节属于 Apple 平台专题，本教程不深入；交叉编译到 iOS 见[[42.Cmake/13 - 工具链与交叉编译.md|第 13 章]]。

## 15.7 选择与默认生成器

### 15.7.1 各平台的默认生成器

不带 `-G` 时，CMake 按平台挑默认：

| 平台 | 默认生成器 |
|---|---|
| Linux / 类 Unix | `Unix Makefiles` |
| macOS | `Unix Makefiles`（**不是** Xcode！要 Xcode 须显式 `-G Xcode`） |
| Windows（装了 VS） | 最新已安装的 `Visual Studio NN YYYY` |
| Windows（无 VS，仅 MinGW 等） | 视环境而定，可能无默认、需显式指定 |

> macOS 用户常误以为 `cmake ..` 会出 Xcode 工程——其实默认是 Makefile。要 Xcode 必须 `-G Xcode`。

### 15.7.2 用 `CMAKE_GENERATOR` 改默认

**`CMAKE_GENERATOR`（环境变量，3.15+）**：当命令行没给 `-G` 时，CMake 读这个环境变量作为默认生成器；若它的值不是合法生成器名，则退回内置默认。适合在 CI 或个人开发机上"一次设定，全局生效"：

```bash
# Linux/macOS：让默认生成器变成 Ninja
export CMAKE_GENERATOR=Ninja
cmake -S . -B build        # 没写 -G，但会用 Ninja
```

```powershell
# Windows PowerShell
$env:CMAKE_GENERATOR = "Ninja"
cmake -S . -B build
```

相关的还有环境变量 `CMAKE_GENERATOR_PLATFORM`、`CMAKE_GENERATOR_TOOLSET`，作用同 `-A` / `-T` 的默认值。最终实际采用的生成器会落到缓存变量 `CMAKE_GENERATOR` 里（注意区分：同名的环境变量是"输入默认"，缓存变量是"已锁定结果"）。

### 15.7.3 与 Presets 的关系（→第 16 章）

手敲 `-G "Ninja Multi-Config" -A ...` 既冗长又难记，团队协作时还容易写错。现代做法是把生成器、平台、toolset、缓存变量统统写进 `CMakePresets.json` 的 `configurePresets[].generator` 字段，然后 `cmake --preset <name>` 一键复现：

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "ninja-release",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/ninja-release",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Release" }
    }
  ]
}
```

```bash
cmake --preset ninja-release        # 生成器、目录、缓存变量全由 preset 决定
```

Presets 的完整语法、`buildPresets`、继承与条件，见[[42.Cmake/16 - CMake Presets.md|第 16 章]]。

## 15.8 驱动构建：`cmake --build`

无论用哪种生成器，都**不必**直接记 `make` / `ninja` / `MSBuild` / `xcodebuild` 各自的命令行——CMake 提供统一的"构建工具模式（Build Tool Mode）"包装器 `cmake --build`，把参数翻译给底层工具。这让 CI 脚本可以"生成器无关"。

基本形态：

```bash
cmake --build <dir> [options] [-- <native-args>...]
```

`<dir>` 是 build 目录。`--` 之后的内容会**原样透传**给底层构建工具（如给 ninja 传特殊参数）。常用选项逐个讲：

**`--config <cfg>`**：指定构建配置（`Debug`/`Release`/`RelWithDebInfo`/`MinSizeRel` 等）。**仅对多配置生成器有意义**；单配置生成器忽略它（其配置在 `cmake` 配置期由 `CMAKE_BUILD_TYPE` 定）。

```bash
cmake --build build --config Release
```

**`--target <t> [<t>...]`（简写 `-t`）**：只构建指定 target，而非默认的全部。可一次给多个。特殊目标如 `clean`（清理）、`install`、`help` 也可作为 target 传入。

```bash
cmake --build build --target app
cmake --build build -t app tests           # 同时构建两个
cmake --build build --target clean         # 清理（等价于底层的 make/ninja clean）
```

**`--parallel [<N>]`（简写 `-j [<N>]`）**：并行构建的最大作业数。不给 `<N>` 则用工具默认（Ninja 本就默认全核；`make` 不加这个则串行）。

```bash
cmake --build build --parallel 8           # 最多 8 个并行作业
cmake --build build -j                      # 用底层工具的默认并行度
```

> 并行度也可由环境变量 **`CMAKE_BUILD_PARALLEL_LEVEL`** 设定：当 `cmake --build` 没显式带 `--parallel` 时，CMake 读它作为并行作业数（设为 8 等价于 `--parallel 8`；设为空字符串则用底层工具默认）。适合在 CI 里全局配一次。

```bash
export CMAKE_BUILD_PARALLEL_LEVEL=16
cmake --build build         # 自动按 16 并行，无需每条命令都加 -j
```

**`--clean-first`**：构建前先执行一次 clean，相当于"先清后建"的一次性全量重建（比手动 `--target clean` 再构建省一步）。注意它不等于删 build 目录重配，只清构建产物。

```bash
cmake --build build --clean-first --config Release
```

**`-v` / `--verbose`**：打印底层实际执行的编译/链接命令行（看真实传给编译器的 flag、include 路径时极有用，排查"为什么我的宏没生效""头文件路径对不对"的首选）。

```bash
cmake --build build -v
```

> 对 **Makefile 生成器**，还可以在配置期设缓存变量 **`CMAKE_VERBOSE_MAKEFILE=ON`** 让生成的 Makefile**永久**输出完整命令行（无需每次 `-v`）；Ninja 则一般用 `-v` 即可。二者目的相同，作用范围不同：`CMAKE_VERBOSE_MAKEFILE` 是"配置期写进构建文件"，`-v` 是"本次构建临时打开"。

**`--`（透传分隔符）**：之后的参数直接给底层工具。例如给 ninja 传 `-k`（出错后尽量继续构建其余目标）：

```bash
cmake --build build -- -k 0                 # ninja: keep going, 不因首个错误停下
cmake --build build --config Release -- -m  # MSBuild: 启用多进程构建
```

一条覆盖常见组合的"全家桶"命令：

```bash
# 多配置、Release、只编 app、8 并行、先清后建、打印命令行
cmake --build build --config Release --target app --parallel 8 --clean-first -v
```

### 15.8.1 与之配套的安装/测试驱动（顺带一提）

同属"工具模式"的还有两个常配合使用的包装器，细节分别在第 11、12 章，这里给出与 `--config` 的呼应关系：

```bash
cmake --install build --config Release --prefix /opt/myapp    # 多配置下安装也要 --config
ctest --test-dir build -C Release                             # CTest 用 -C 选配置
```

## 15.9 各平台生成器选择实例

前面把生成器逐个讲透了，这一节从"我在某个平台上该用哪个、怎么敲"的角度，给出可直接照抄的命令。

### 15.9.1 Windows

Windows 上有三条主线，按"是否需要 VS IDE、用哪条工具链"来选：

- **Visual Studio 17 2022**（多配置，首选）：产出 `.sln`，双击即在 IDE 里调试；架构用 `-A`、工具集用 `-T`。无需 Developer 命令行，VS 生成器会自己定位工具链。
- **Ninja Multi-Config**（多配置，命令行/CI 首选）：一个目录多配置又快，但用 MSVC 时**必须在 "x64 Native Tools Command Prompt for VS" 之类的 Developer 命令行里跑**（或先执行 `vcvarsall.bat`），否则 `cl.exe` / `rc.exe` 不在 PATH，配置期就会报找不到编译器。
- **MinGW Makefiles**（单配置）：走 GCC 工具链（mingw32-make），与 MSVC 无关；不需要 `sh.exe` 在 PATH。

```bash
# VS 2022：x64 + v143 工具集 + 64 位主机工具
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T v143,host=x64
cmake --build build --config Release

# VS 2022：交叉到 ARM64，或改用内置 clang-cl
cmake -S . -B build -G "Visual Studio 17 2022" -A ARM64 -T ClangCL
cmake --build build --config Release

# Ninja Multi-Config（务必在 VS Developer 命令行里执行，cl.exe 才可见）
cmake -S . -B build -G "Ninja Multi-Config"
cmake --build build --config Debug

# MinGW（GCC 工具链，单配置）
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

### 15.9.2 macOS

- **Xcode**（多配置）：要在 Xcode IDE 里调试、做代码签名 / 打 `.app`·`.framework`、或针对 iOS 设备/模拟器时用它（签名透传见 15.6）。
- **Ninja**（单配置）：纯命令行编译、CI 构建最快，首选。
- **Unix Makefiles**（单配置）：macOS 不带 `-G` 时的默认（**不是 Xcode**），够用但通常比 Ninja 慢。

```bash
# Xcode：要 IDE 调试 / 签名 / iOS 时用
cmake -S . -B build -G Xcode
cmake --build build --config Release
open build/MyProject.xcodeproj          # 在 Xcode 里打开

# Ninja：命令行 / CI 首选
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

### 15.9.3 Linux

- **Ninja**（单配置，首选）：最快、依赖最准、默认全核并行。
- **Unix Makefiles**（单配置）：不带 `-G` 时的默认，无 Ninja 时的稳妥退路。

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release   # 首选
cmake --build build

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release            # 退而求其次：默认 Unix Makefiles
cmake --build build -j
```

### 15.9.4 平台 × 推荐生成器 对照表

| 平台 | 推荐生成器 | 单/多配置 | 典型命令 |
|---|---|---|---|
| **Windows** | `Visual Studio 17 2022` | 多配置 | `cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T v143,host=x64` → `cmake --build build --config Release` |
| Windows（命令行/CI） | `Ninja Multi-Config`（须 Developer 命令行） | 多配置 | `cmake -S . -B build -G "Ninja Multi-Config"` → `cmake --build build --config Release` |
| Windows（GCC 工具链） | `MinGW Makefiles` | 单配置 | `cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release` → `cmake --build build` |
| **macOS**（IDE/签名/iOS） | `Xcode` | 多配置 | `cmake -S . -B build -G Xcode` → `cmake --build build --config Release` |
| macOS（命令行/CI） | `Ninja` | 单配置 | `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release` → `cmake --build build` |
| **Linux** | `Ninja` | 单配置 | `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release` → `cmake --build build` |
| Linux（退路） | `Unix Makefiles` | 单配置 | `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` → `cmake --build build -j` |

### 15.9.5 跨平台统一命令

Ninja 是唯一在三大平台上写法完全一致的生成器，最适合跨平台脚本与 CI：

```bash
# 这一行在 Windows（Developer 命令行内）/ macOS / Linux 上一字不差
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

若要"一份脚本既覆盖单配置又覆盖多配置"，统一改用 `Ninja Multi-Config` 并在构建期带 `--config`——单配置生成器会忽略 `--config`，多配置生成器才认它（区别见 15.3）：

```bash
cmake -S . -B build -G "Ninja Multi-Config"
cmake --build build --config Release        # 多配置：--config 生效；切别的配置不必重配
```

完整的跨平台工程（连同各平台条件分支、依赖与 CI 矩阵）见[[42.Cmake/19 - 跨平台实战与平台差异大全.md|第 19 章]]。

## 本章小结

本章把"CMake 生成什么、底层用什么编译、怎么统一驱动"这条链路讲清楚了：

- **生成器决定产出哪种原生构建文件**，在配置期由 `-G` 选定，并和 build 目录**绑死**——换生成器要换/清目录。`cmake --help` 末尾列本机可用生成器（`*` 为默认）。
- **四大类生成器**：Makefile 系（单配置）、`Ninja` / `Ninja Multi-Config`、IDE 系（VS / Xcode，多配置）、其他历史。命令行/CI 首选 Ninja，要 IDE 调试用 VS/Xcode。
- **单 vs 多配置是核心分界**：单配置在**配置期**用 `CMAKE_BUILD_TYPE` 定类型（一目录一配置）；多配置在**构建期**用 `--config` 选（一目录多配置），此时 `CMAKE_BUILD_TYPE` 失效、改用 `CMAKE_CONFIGURATION_TYPES`。跨配置逻辑一律用 `$<CONFIG>`，用全局属性 `GENERATOR_IS_MULTI_CONFIG` 判定。
- **VS 生成器**：`-A` 选平台（`x64`/`Win32`/`ARM64`），`-T` 选 toolset（`v143`/`ClangCL`/`host=x64`/`version=...`）；`MSVC`/`MSVC_VERSION` 反映编译器；`USE_FOLDERS` + `FOLDER` 整理解决方案结构。
- **Ninja 因扁平规则 + 精确依赖 + 默认并行而又快又一致**；`Ninja Multi-Config`（3.17+）用 `build-<Config>.ninja` 实现命令行多配置，配套 `CMAKE_DEFAULT_BUILD_TYPE` / `CMAKE_DEFAULT_CONFIGS` / `CMAKE_CROSS_CONFIGS`。
- **Xcode 生成器**用 `--config` 选 configuration，`CMAKE_XCODE_ATTRIBUTE_<name>` 透传 build setting 与代码签名。
- **默认生成器**因平台而异（macOS 默认竟是 Makefile 而非 Xcode）；用环境变量 `CMAKE_GENERATOR`（3.15+）改默认，或交给 Presets 的 `generator` 字段管理。
- **`cmake --build`** 统一驱动构建，与生成器无关：`--config` 选配置、`--target` 选目标、`--parallel`/`CMAKE_BUILD_PARALLEL_LEVEL` 控并行、`--clean-first` 先清后建、`-v`/`CMAKE_VERBOSE_MAKEFILE` 看真实命令行、`--` 透传底层工具参数。

掌握了生成器与 `cmake --build`，你就能在任意平台、任意 IDE/命令行环境间自由切换构建后端。下一章把这些零散的 `-G` / `-A` / `-T` / `-D` 命令行收敛进可复现、可共享的配置文件——CMake Presets。
