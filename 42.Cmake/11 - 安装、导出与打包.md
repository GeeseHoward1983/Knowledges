# 第 11 章 · 安装、导出与打包

> 基准版本：CMake 4.3.4

构建产物如果只躺在 `build/` 目录里，它就只属于「你」和「这台机器」。要让别人能 `find_package(MyLib)` 直接拿来用，要让运维能 `apt install`、用户能双击安装包，就必须把**安装规则（install）**、**导出信息（export）**、**打包配置（CPack）**这三件事做对。

本章按「先放对位置 → 再让别人能 import → 最后封装成分发物」的顺序展开：

1. `install()` 的全部形式（这是地基，必须逐参数吃透）；
2. `GNUInstallDirs` 规范安装路径；
3. 安装组件（COMPONENT）；
4. **导出目标供他人 `find_package`**（本章核心，给完整端到端可复现示例）；
5. RPATH 让安装后的可执行文件能找到动态库；
6. **CPS（CMake 4.x 新增）**——跨构建系统的包描述；
7. CPack 打包成 `.zip` / `.deb` / `.rpm` / 安装程序。

---

## 11.1 `install()` 全形式

`install()` 不会在配置或构建阶段拷贝任何文件，它只是**生成安装脚本**（`cmake_install.cmake`）。真正执行安装的是：

```bash
cmake --install <build-dir> [--prefix <p>] [--config <cfg>] [--component <c>]
# 旧式等价：cmake --build <build-dir> --target install
# 或在 build 目录里：cpack 之前先 make install / ninja install
```

`install()` 的每个签名对应一种「安装什么」。按出现频率，最重要的是 `TARGETS`、`FILES`、`DIRECTORY`、`EXPORT`，其余按需使用。

> ⚠️ 安装规则的**执行顺序 = 声明顺序**（同一目录内）。跨目录时父目录的规则先于由 `add_subdirectory()` 引入的子目录规则——除非子目录在父目录之前被 `add_subdirectory()`。这一点在装脚本（SCRIPT/CODE）依赖文件已就位时很关键。

### 11.1.1 `install(TARGETS ...)` —— 安装构建目标

这是最常用的形式，用来安装由 `add_library()` / `add_executable()` 产生的产物。完整签名：

```cmake
install(TARGETS <target>... [EXPORT <export-name>]
        [RUNTIME_DEPENDENCY_SET <set-name>]
        [<artifact-kind>
         [DESTINATION <dir>]
         [PERMISSIONS <permission>...]
         [CONFIGURATIONS <config>...]
         [COMPONENT <component>]
         [NAMELINK_COMPONENT <component>]
         [OPTIONAL] [EXCLUDE_FROM_ALL]
         [NAMELINK_ONLY | NAMELINK_SKIP]
        ]...
        [FILE_SET <set-name> [DESTINATION <dir>] ...]...     # 3.23+
        [CXX_MODULES_BMI [DESTINATION <dir>] ...]            # 3.28+
        [INCLUDES DESTINATION [<dir>...]]
        )
```

#### artifact-kind（产物种类）

一个目标可能同时产出多种文件（例如 Windows 的 DLL = `RUNTIME` 的 `.dll` + `ARCHIVE` 的导入库 `.lib`）。CMake 把它们分门别类，你为每一类指定独立的 `DESTINATION`。

| artifact-kind | 装的是什么 | 典型来源 |
|---|---|---|
| **ARCHIVE** | 静态库 `.a`/`.lib`；DLL 平台上共享库的**导入库** `.lib`；MinGW 的 `.dll.a` | `STATIC` 库、`SHARED` 库（DLL 侧） |
| **LIBRARY** | 非 DLL 平台的共享库 `.so`/`.dylib`；`MODULE` 库 | `SHARED` / `MODULE` 库 |
| **RUNTIME** | 可执行文件；DLL 平台上的 `.dll` 本体 | `add_executable()`、`SHARED` 库（Windows 侧） |
| **OBJECTS** | 对象库的 `.o`/`.obj` 文件 | `OBJECT` 库 |
| **FRAMEWORK** | macOS framework 整包（替代 ARCHIVE/LIBRARY/RUNTIME） | 设了 `FRAMEWORK TRUE` 的库 |
| **BUNDLE** | macOS application bundle（替代 RUNTIME） | 设了 `MACOSX_BUNDLE TRUE` 的可执行 |
| **PUBLIC_HEADER** | 目标的 `PUBLIC_HEADER` 属性列出的头文件 | 设过 `PUBLIC_HEADER` 属性 |
| **PRIVATE_HEADER** | 目标的 `PRIVATE_HEADER` 属性列出的头文件 | 同上 |
| **RESOURCE** | 目标的 `RESOURCE` 属性列出的资源文件 | 同上 |
| **FILE_SET `<name>`**（3.23+） | 文件集（推荐用于头文件） | `target_sources(... FILE_SET ...)` |
| **CXX_MODULES_BMI**（3.28+） | C++ 模块的 BMI（二进制模块接口） | `CXX_MODULES` 文件集 |

> 💡 **省略 artifact-kind 的简写**：若不写任何种类关键字，直接 `install(TARGETS foo DESTINATION bin)`，CMake 会把**所有种类**都装到该 `DESTINATION`。但更推荐配合 `GNUInstallDirs` 显式分类——见下文。
>
> 💡 **不写 DESTINATION 也行**：自 3.14 起，`install(TARGETS)` 对各 artifact-kind 有默认目标（`ARCHIVE/LIBRARY`→`${CMAKE_INSTALL_LIBDIR}`，`RUNTIME`→`${CMAKE_INSTALL_BINDIR}`，头文件→`${CMAKE_INSTALL_INCLUDEDIR}` 等），前提是你 `include(GNUInstallDirs)`。

#### 逐参数详解

- **EXPORT** `<export-name>`：把这些目标登记到一个导出集，供后续 `install(EXPORT ...)`/`export(EXPORT ...)` 生成 `*Targets.cmake`。**这是「让别人 `find_package`」的起点**（11.4 详述）。
- **DESTINATION** `<dir>`：安装相对 `CMAKE_INSTALL_PREFIX` 的目录（绝对路径会忽略 prefix，不推荐）。每个 artifact-kind 各自一个。
- **COMPONENT** `<component>`：把该规则归入命名组件，支持「只装某一部分」（11.3）。
- **PERMISSIONS** `<perm>...`：覆盖默认权限。取值如 `OWNER_READ OWNER_WRITE OWNER_EXECUTE GROUP_READ GROUP_EXECUTE WORLD_READ WORLD_EXECUTE SETUID SETGID`。
- **CONFIGURATIONS** `<config>...`：仅当以该配置（`Debug`/`Release` …）安装时生效。常用于给 Debug 库装到不同位置或加后缀。
- **OPTIONAL**：若产物不存在（例如该配置没构建），不报错跳过。
- **EXCLUDE_FROM_ALL**：默认不随「全量安装」装，只有显式 `--component` 指定它时才装。
- **NAMELINK_ONLY** / **NAMELINK_SKIP** / **NAMELINK_COMPONENT**：处理共享库的版本符号链接。`libfoo.so.1.2.3`（实体）、`libfoo.so.1`（soname 链接，运行期需要）、`libfoo.so`（namelink，开发期链接需要）。把 namelink 单独划到 `-dev` 组件即用这组选项。
- **FILE_SET** `<name>`（3.23+）：安装由 `target_sources(... FILE_SET <name> TYPE HEADERS ...)` 声明的文件集，自动保留 `BASE_DIRS` 计算出的相对目录结构——**这是现代安装头文件的首选方式**，取代手写 `install(DIRECTORY include/)`。
- **INCLUDES DESTINATION** `<dir>...`：不拷贝文件，而是把这些目录追加进导出目标的 `INTERFACE_INCLUDE_DIRECTORIES`（自动包进 `$<INSTALL_INTERFACE:>`）。

示例（一个共享库，含现代 FILE_SET 头文件安装）：

```cmake
include(GNUInstallDirs)

add_library(mylib SHARED src/mylib.cpp)
target_sources(mylib
  PUBLIC
    FILE_SET HEADERS
      BASE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/include
      FILES     include/mylib/mylib.h)

install(TARGETS mylib
        EXPORT  MyLibTargets
        RUNTIME       DESTINATION ${CMAKE_INSTALL_BINDIR}      COMPONENT runtime
        LIBRARY       DESTINATION ${CMAKE_INSTALL_LIBDIR}      COMPONENT runtime
                      NAMELINK_COMPONENT dev
        ARCHIVE       DESTINATION ${CMAKE_INSTALL_LIBDIR}      COMPONENT dev
        FILE_SET HEADERS DESTINATION ${CMAKE_INSTALL_INCLUDEDIR} COMPONENT dev)
```

### 11.1.2 `install(FILES ...)` 与 `install(PROGRAMS ...)`

安装任意文件。两者唯一区别：`PROGRAMS` 默认带可执行权限（`OWNER_EXECUTE GROUP_EXECUTE WORLD_EXECUTE`，适合脚本），`FILES` 默认仅读写。

```cmake
install(<FILES|PROGRAMS> <file>...
        TYPE <type> | DESTINATION <dir>
        [PERMISSIONS <permission>...]
        [CONFIGURATIONS <config>...]
        [COMPONENT <component>] [RENAME <name>]
        [OPTIONAL] [EXCLUDE_FROM_ALL])
```

- **DESTINATION** `<dir>`：目标目录。
- **TYPE** `<type>`：用 `GNUInstallDirs` 已知类型（`BIN`/`LIB`/`INCLUDE`/`DATA`/`DOC`/`SYSCONF` …）代替 DESTINATION，CMake 自动取对应路径，二选一。
- **RENAME** `<name>`：安装时改名（仅当只装单个文件时有效）。
- **PERMISSIONS** / **CONFIGURATIONS** / **COMPONENT** / **OPTIONAL** / **EXCLUDE_FROM_ALL**：同 `TARGETS`。

```cmake
install(FILES    LICENSE README.md DESTINATION ${CMAKE_INSTALL_DOCDIR})
install(FILES    config/default.conf
        DESTINATION ${CMAKE_INSTALL_SYSCONFDIR}/myapp RENAME myapp.conf)
install(PROGRAMS scripts/run.sh DESTINATION ${CMAKE_INSTALL_BINDIR} RENAME myapp-run)
```

### 11.1.3 `install(DIRECTORY ...)` —— 安装整个目录

把目录连同结构一起装过去，支持精细过滤。

```cmake
install(DIRECTORY <dir>... TYPE <type> | DESTINATION <dir>
        [FILE_PERMISSIONS <permission>...]
        [DIRECTORY_PERMISSIONS <permission>...]
        [USE_SOURCE_PERMISSIONS] [OPTIONAL] [MESSAGE_NEVER]
        [CONFIGURATIONS <config>...] [COMPONENT <component>] [EXCLUDE_FROM_ALL]
        [FILES_MATCHING]
        [[PATTERN <pattern> | REGEX <regex>] [EXCLUDE]
         [PERMISSIONS <permission>...]]...)
```

关键点：

- **源目录尾斜杠语义**：`DIRECTORY include/`（**带** `/`）装的是 include 里的**内容**；`DIRECTORY include`（**不带** `/`）会把 `include` 这层目录本身也装进去。极易踩坑。
- **PATTERN** `<glob>` / **REGEX** `<re>`：匹配文件/目录名。后接 `EXCLUDE` 表示排除，后接 `PERMISSIONS` 表示给匹配项单独设权限。
- **FILES_MATCHING**：开启后，只有匹配了某个 `PATTERN`/`REGEX` 的**文件**才会被装（目录结构仍保留以容纳它们）。常用于「只装 .h，不装 .cpp」。
- **USE_SOURCE_PERMISSIONS**：沿用源文件权限。**MESSAGE_NEVER**：安装时不打印每个文件。

```cmake
# 只安装头文件，跳过内部目录与 .in 模板
install(DIRECTORY include/          # 注意尾斜杠：装内容
        DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
        FILES_MATCHING
          PATTERN "*.h"
          PATTERN "*.hpp"
          PATTERN "internal" EXCLUDE
          PATTERN "*.in"     EXCLUDE)
```

### 11.1.4 `install(EXPORT ...)` —— 导出目标描述文件

把 `install(TARGETS ... EXPORT <name>)` 登记的目标，生成一个可被 `find_package`/`include()` 消费的 `*.cmake`。详见 11.4，签名先列于此：

```cmake
install(EXPORT <export-name> DESTINATION <dir>
        [NAMESPACE <namespace>] [FILE <name>.cmake]
        [PERMISSIONS <permission>...]
        [CONFIGURATIONS <config>...]
        [EXPORT_LINK_INTERFACE_LIBRARIES]
        [COMPONENT <component>] [CXX_MODULES_DIRECTORY <dir>])
# 或导出为 Android.mk：install(EXPORT_ANDROID_MK <export-name> DESTINATION <dir> ...)
```

- **NAMESPACE** `<ns>::`：给导入目标加前缀（约定写成 `MyLib::`），避免与下游目标重名，也清晰标明「这是外来的」。
- **FILE** `<name>.cmake`：输出文件名，默认 `<export-name>.cmake`。
- **CONFIGURATIONS**：把不同配置拆到不同 `*-debug.cmake`/`*-release.cmake`（CMake 自动按配置切分，一般无需手动）。

### 11.1.5 `install(SCRIPT ...)` 与 `install(CODE ...)`

在安装阶段执行自定义逻辑。`SCRIPT` 跑一个 `.cmake` 文件，`CODE` 内联一段 CMake 代码。

```cmake
install([[SCRIPT <file>] | [CODE <code>]]
        [ALL_COMPONENTS | COMPONENT <component>]
        [EXCLUDE_FROM_ALL])
```

它们在该规则所处位置「按声明顺序」执行。脚本里可用 `$ENV{DESTDIR}` 与 `CMAKE_INSTALL_PREFIX`。3.21+ 起支持 `$<...>` 生成器表达式（让脚本能感知配置）。

```cmake
install(CODE [[
  message(STATUS "Running post-install for ${CMAKE_INSTALL_PREFIX}")
  execute_process(COMMAND ${CMAKE_COMMAND} -E create_symlink
                  myapp-1.0 "$ENV{DESTDIR}${CMAKE_INSTALL_PREFIX}/bin/myapp")
]])
```

### 11.1.6 运行期依赖：`RUNTIME_DEPENDENCY_SET` 与 `IMPORTED_RUNTIME_ARTIFACTS`

发布时常需把目标**依赖的第三方动态库**一并打包（典型如 Windows 上把所需 DLL 拷到 bin）。

**`install(RUNTIME_DEPENDENCY_SET)`**（3.21+）：安装由 `install(TARGETS ... RUNTIME_DEPENDENCY_SET <set>)` 收集的运行期依赖集合。底层调用 `file(GET_RUNTIME_DEPENDENCIES)` 解析，仅支持 Windows/Linux/macOS。

```cmake
install(RUNTIME_DEPENDENCY_SET <set-name>
        [[LIBRARY|RUNTIME|FRAMEWORK]
         [DESTINATION <dir>] [PERMISSIONS <permission>...]
         [CONFIGURATIONS <config>...] [COMPONENT <component>]
         [NAMELINK_COMPONENT <component>] [OPTIONAL] [EXCLUDE_FROM_ALL]]...
        [PRE_INCLUDE_REGEXES <regex>...] [PRE_EXCLUDE_REGEXES <regex>...]
        [POST_INCLUDE_REGEXES <regex>...] [POST_EXCLUDE_REGEXES <regex>...]
        [POST_INCLUDE_FILES <file>...]   [POST_EXCLUDE_FILES <file>...]
        [DIRECTORIES <dir>...])
```

`PRE_*`/`POST_*` 正则用于在解析前/后筛掉系统库（如 `/lib`、`api-ms-win-*`），避免把操作系统自带库也打进包。

**`install(IMPORTED_RUNTIME_ARTIFACTS)`**：安装**导入目标**（`add_library(foo SHARED IMPORTED)`）的运行期产物——例如你 `find_package` 来的第三方库的 `.dll`/`.so`，想随你自己的程序一起分发。

```cmake
install(IMPORTED_RUNTIME_ARTIFACTS <target>...
        [RUNTIME_DEPENDENCY_SET <set-name>]
        [[LIBRARY|RUNTIME|FRAMEWORK|BUNDLE]
         [DESTINATION <dir>] [PERMISSIONS <permission>...]
         [CONFIGURATIONS <config>...] [COMPONENT <component>]
         [OPTIONAL] [EXCLUDE_FROM_ALL]]...)
```

## 11.2 `GNUInstallDirs`：别再硬编码路径

不要写 `DESTINATION lib`、`DESTINATION bin`——不同发行版的惯例不同（64 位库在 Debian 是 `lib/x86_64-linux-gnu`，在 Fedora 是 `lib64`），硬编码会破坏系统集成。正确做法是 `include(GNUInstallDirs)`，用它提供的标准变量：

```cmake
include(GNUInstallDirs)
```

| 变量 | 默认值 | 含义 |
|---|---|---|
| `CMAKE_INSTALL_BINDIR` | `bin` | 可执行文件 |
| `CMAKE_INSTALL_SBINDIR` | `sbin` | 系统管理可执行 |
| `CMAKE_INSTALL_LIBDIR` | `lib` / `lib64` / `lib/<triplet>`（自动判定） | 库文件 |
| `CMAKE_INSTALL_INCLUDEDIR` | `include` | 头文件 |
| `CMAKE_INSTALL_DATADIR` | `share` 下（`DATAROOTDIR`） | 架构无关数据 |
| `CMAKE_INSTALL_DATAROOTDIR` | `share` | 只读数据根 |
| `CMAKE_INSTALL_DOCDIR` | `share/doc/<PROJECT_NAME>` | 文档 |
| `CMAKE_INSTALL_MANDIR` | `share/man` | man 手册 |
| `CMAKE_INSTALL_SYSCONFDIR` | `etc` | 配置文件 |
| `CMAKE_INSTALL_LIBEXECDIR` | `libexec` | 程序专用辅助可执行 |
| `CMAKE_INSTALL_LOCALSTATEDIR` | `var` | 可变状态数据 |

每个 `*DIR` 还有一个 `CMAKE_INSTALL_FULL_*DIR`（拼上 prefix 的绝对路径），在需要写进配置文件、生成绝对路径时用。

> ⚠️ `LIBDIR` 的自动判定依赖 `include(GNUInstallDirs)` 的时机：要在确定目标架构之后（即 `project()`/启用语言之后）`include`，否则可能判错。

### 安装前缀与覆盖

- **`CMAKE_INSTALL_PREFIX`**：安装根，所有相对 `DESTINATION` 以它为基。Unix 默认 `/usr/local`，Windows 默认 `C:/Program Files/<ProjectName>`。可在配置时设：`-DCMAKE_INSTALL_PREFIX=/opt/myapp`。
- **`cmake --install <build> --prefix <p>`**：在**安装时**覆盖 prefix，无需重新配置——比配置期的 `CMAKE_INSTALL_PREFIX` 更灵活（适合打包脚本）。
- **`DESTDIR` 环境变量**（Unix）：安装时给所有路径再加一层前缀，**不影响**写进文件里的路径。专为发行版打包设计：
  ```bash
  DESTDIR=/tmp/pkgroot cmake --install build
  # 文件落到 /tmp/pkgroot/usr/local/...，但内部记录的仍是 /usr/local/...
  ```
  Windows 上 `DESTDIR` 仅在路径无盘符时有意义，一般不用。

## 11.3 安装组件（COMPONENT）

把安装规则按用途分组，使用者就能选择性安装。常见划分：`runtime`（最终用户跑程序所需）、`dev`（开发者头文件 + 导入库 + 配置文件）、`doc`。

为每条 `install()` 加 `COMPONENT <name>`（见前文示例），然后：

```bash
# 只装运行时部分（部署到生产服务器）
cmake --install build --component runtime

# 只装开发部分（提供 SDK）
cmake --install build --component dev

# 不带 --component：装所有未标 EXCLUDE_FROM_ALL 的规则
cmake --install build
```

组件化的好处：
- 制作分离的 `-runtime` / `-dev` 安装包（与 CPack 组件打包天然对接，见 11.7）；
- 让最终产物更小（用户不需要头文件和 `.a`）；
- `EXCLUDE_FROM_ALL` 让某些组件（如调试符号）默认不装、按需获取。

## 11.4 导出目标供他人 `find_package`（核心）

目标是：你发布库 `MyLib` 后，**下游项目**只需写

```cmake
find_package(MyLib 1.2 REQUIRED)
target_link_libraries(app PRIVATE MyLib::mylib)
```

就能拿到头文件路径、编译选项、链接库、依赖传递——全部自动。要做到这点，发布方需要生成三类文件并装到 `<prefix>/lib/cmake/MyLib/`：

1. **`MyLibTargets.cmake`**——由 `install(EXPORT)` 生成，记录每个导入目标（`IMPORTED`）及其属性。
2. **`MyLibConfig.cmake`**——`find_package` 的入口，负责 `include` 上面那个 Targets 文件，并处理本包的依赖。
3. **`MyLibConfigVersion.cmake`**——版本与兼容性检查。

### 11.4.1 第一步：登记目标 + 生成 Targets 文件

```cmake
include(GNUInstallDirs)

add_library(mylib SHARED src/mylib.cpp)
add_library(MyLib::mylib ALIAS mylib)        # 让自家构建树内也用带命名空间的名字
set_target_properties(mylib PROPERTIES
  VERSION   ${PROJECT_VERSION}               # 例 1.2.3 → libmylib.so.1.2.3
  SOVERSION ${PROJECT_VERSION_MAJOR})        # → libmylib.so.1

# 关键：用 BUILD_INTERFACE / INSTALL_INTERFACE 处理「构建时」与「安装后」两套头文件路径
target_include_directories(mylib PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>   # 自家构建时用源码树
  $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>)        # 别人安装后用安装树

# 1) 安装目标本体，并登记到导出集 MyLibTargets
install(TARGETS mylib
        EXPORT  MyLibTargets
        RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}
        LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}
        ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR}
        INCLUDES DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})

# 2) 安装头文件（此处用传统 DIRECTORY 形式；也可改用 11.1.1 的 FILE_SET）
install(DIRECTORY include/ DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})

# 3) 由导出集生成 MyLibTargets.cmake，带命名空间
install(EXPORT MyLibTargets
        FILE        MyLibTargets.cmake
        NAMESPACE   MyLib::
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyLib)
```

> 🔑 **`$<BUILD_INTERFACE:>` 与 `$<INSTALL_INTERFACE:>` 的双路径**：同一个 `target_include_directories(PUBLIC ...)`，源码树构建时（含 `export()` 构建树导出）走 `BUILD_INTERFACE`，安装后被下游消费时走 `INSTALL_INTERFACE`。`INSTALL_INTERFACE` 的路径是**相对 prefix** 的，不能写绝对路径。漏掉它，下游会拿到指向你机器源码目录的失效路径。

### 11.4.2 第二步：写 `MyLibConfig.cmake.in` 模板

`Config.cmake` 不要手写普通 `configure_file`，要用 `CMakePackageConfigHelpers` 的 `configure_package_config_file()`——它提供 `@PACKAGE_*@` 占位与 `set_and_check()`，能让安装包**可重定位**（用户把整个安装目录挪到别处也能用）。

模板文件 `cmake/MyLibConfig.cmake.in`：

```cmake
@PACKAGE_INIT@

include(CMakeFindDependencyMacro)
# 若 MyLib 依赖其他包，在这里声明，让下游 find_package(MyLib) 时连带找到
# find_dependency(Threads REQUIRED)
# find_dependency(fmt 9 REQUIRED)

# 引入由 install(EXPORT) 生成的导入目标
include("${CMAKE_CURRENT_LIST_DIR}/MyLibTargets.cmake")

check_required_components(MyLib)
```

- `@PACKAGE_INIT@`：被展开成可重定位的初始化样板（计算 `PACKAGE_PREFIX_DIR` 等）。
- `find_dependency(...)`（来自 `CMakeFindDependencyMacro`）：转发 `REQUIRED`/`QUIET`/版本，保证传递依赖被解析。**必须在这里声明你的公开依赖**，否则下游链接时缺库。
- `check_required_components(MyLib)`：校验用户 `find_package(MyLib COMPONENTS ...)` 请求的组件都已满足。

### 11.4.3 第三步：生成并安装 Config + 版本文件

```cmake
include(CMakePackageConfigHelpers)

# 由模板生成可重定位的 MyLibConfig.cmake
configure_package_config_file(
  ${CMAKE_CURRENT_SOURCE_DIR}/cmake/MyLibConfig.cmake.in
  ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfig.cmake
  INSTALL_DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyLib
  # PATH_VARS 用于把安装路径变量转成可重定位形式，供模板里的 @PACKAGE_xxx@ 引用
  # PATH_VARS CMAKE_INSTALL_INCLUDEDIR
)

# 生成版本文件，指定兼容策略
write_basic_package_version_file(
  ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfigVersion.cmake
  VERSION       ${PROJECT_VERSION}
  COMPATIBILITY SameMajorVersion)

# 安装这两个文件，与 Targets 同目录
install(FILES
        ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfig.cmake
        ${CMAKE_CURRENT_BINARY_DIR}/MyLibConfigVersion.cmake
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyLib)
```

**`write_basic_package_version_file()` 的 `COMPATIBILITY`**（决定 `find_package(MyLib 1.2)` 何时判为兼容）：

| COMPATIBILITY | 含义 |
|---|---|
| **AnyNewerVersion** | 安装版 ≥ 请求版即兼容（最宽松，适合严格向后兼容的库） |
| **SameMajorVersion** | 主版本号相同才兼容（语义化版本常用：major 变更 = 破坏性） |
| **SameMinorVersion** | major+minor 都需相同 |
| **SamePatchVersion** | major+minor+patch 都需相同 |
| **SameFullVersion** / **ExactVersion** | 完全一致才兼容 |
| **SemanticVersion** | 按 SemVer 规则（含 1.0 之前 0.x 的特殊处理） |

附加 `ARCH_INDEPENDENT`：若包不含与架构绑定的二进制（纯头文件库、纯脚本），加它可跳过 32/64 位匹配检查，让 32 位项目也能用 64 位机器上装的包。

### 11.4.4 构建树导出：`export()`（不安装也能被找到）

有时希望**不执行安装**就让另一个项目从你的**构建目录**直接消费（如 monorepo 内联开发、CI 缓存）。用 `export()`：

```cmake
# 形式一：从导出集生成构建树版 Targets 文件
export(EXPORT MyLibTargets
       NAMESPACE MyLib::
       FILE      ${CMAKE_CURRENT_BINARY_DIR}/MyLibTargets.cmake)

# 形式二：直接列目标（无需先 install(... EXPORT ...)）
export(TARGETS mylib NAMESPACE MyLib::
       FILE ${CMAKE_CURRENT_BINARY_DIR}/MyLibTargets.cmake)

# 可选：把本构建树注册进用户级包注册表，使裸 find_package(MyLib) 也能定位（4.x 默认关闭，需显式开启策略/变量）
# export(PACKAGE MyLib)
```

构建树导出的目标走 `$<BUILD_INTERFACE:>` 路径，因此下游拿到的头文件指向你的源码树——适合开发，不适合分发。

### 11.4.5 端到端：下游如何使用

发布方安装后，下游项目的 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.23)
project(app LANGUAGES CXX)

find_package(MyLib 1.2 REQUIRED)          # 触发 MyLibConfig.cmake → ConfigVersion 校验
add_executable(app main.cpp)
target_link_libraries(app PRIVATE MyLib::mylib)
# 头文件路径、编译特性、传递依赖全部经 INTERFACE 属性自动带入，无需手写 include 目录
```

配置时若 MyLib 装在非默认前缀，指给它：

```bash
cmake -B build -DCMAKE_PREFIX_PATH=/opt/mylib
# CMake 会在 <prefix>/lib/cmake/MyLib/ 下找到 MyLibConfig.cmake
```

> 📌 完整目录布局（安装后）：
> ```
> <prefix>/
> ├── include/mylib/mylib.h
> ├── lib/libmylib.so.1.2.3 (+ soname/namelink)
> └── lib/cmake/MyLib/
>     ├── MyLibConfig.cmake
>     ├── MyLibConfigVersion.cmake
>     ├── MyLibTargets.cmake
>     └── MyLibTargets-release.cmake   # 按配置自动生成
> ```

## 11.5 RPATH：让安装后的程序找到动态库

可执行文件运行时要定位它链接的 `.so`。RPATH（写进 ELF/Mach-O 的搜索路径）控制这件事。CMake 默认在**构建树**里设置 RPATH 指向构建产物（让你能直接跑），但**安装时会清除**这些（因为构建路径在目标机器不存在）——于是安装后可能 `error while loading shared libraries`。相关属性/变量：

- **`CMAKE_SKIP_BUILD_RPATH`**（默认 OFF）：是否不为构建树设 RPATH。一般保持 OFF，方便直接运行构建产物。
- **`CMAKE_BUILD_WITH_INSTALL_RPATH`**（默认 OFF）：构建时就用「安装后的 RPATH」，从而安装阶段无需改写二进制（更快，但构建树里直接跑可能找不到库）。
- **`CMAKE_INSTALL_RPATH`**（目标属性 `INSTALL_RPATH`）：安装后写入的 RPATH，字符串列表。Linux 常设为相对自身的 `$ORIGIN`：
  ```cmake
  set(CMAKE_INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")  # macOS 用 @loader_path
  ```
- **`CMAKE_INSTALL_RPATH_USE_LINK_PATH`**（默认 OFF）：自动把链接时用到的、位于安装树之外的库目录追加进 install RPATH。装了依赖第三方库时常开启。
- **`BUILD_RPATH`**（目标属性）/ **`CMAKE_BUILD_RPATH`**：往构建树 RPATH 追加额外目录。

典型「安装后即可运行」配方（库与可执行同前缀）：

```cmake
set(CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE)
if(APPLE)
  set(CMAKE_INSTALL_RPATH "@loader_path/../${CMAKE_INSTALL_LIBDIR}")
elseif(UNIX)
  set(CMAKE_INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")
endif()
```

> 💡 Windows 没有 RPATH 概念，靠 DLL 与 exe 同目录或 `PATH`——这也是 `install(RUNTIME_DEPENDENCY_SET)` 在 Windows 上重要的原因。
> 💡 发行版打包（DEB/RPM）通常要求**不带 RPATH**（库装进标准系统路径，由 ld.so 缓存解析）。可在打包构建中清空 `CMAKE_INSTALL_RPATH` 或用 chrpath 剥离。

## 11.6 CPS：跨构建系统的包描述（CMake 4.x 新增）

CMake 4.x 引入对 **Common Package Specification（CPS）** 的支持，用一种**非 CMake 语言**的、表达力更强的 JSON 格式描述包。意义在于**互操作**：用 Meson、Bazel、手写 Makefile 的项目也能消费你的包，而不必看懂 `*Config.cmake`。

- `find_package` 现在能搜索并导入 CPS 包；
- `install` 和 `export` 新增 **`PACKAGE_INFO`** 子命令生成 CPS 描述（写入 `cps/<package-name>` 子目录）；
- 导入的目标隐式带 `<package-name>::` 前缀；
- `project()` 新增 `COMPAT_VERSION` 和 `SPDX_LICENSE`，可被 CPS 包继承。

> ⚠️ 截至 4.3.4，CPS 支持仍在演进，规范本身也在迭代。生产中若只面向 CMake 下游，`install(EXPORT)` + `Config.cmake` 仍是成熟主路；CPS 适合需要被异构构建系统消费的场景。

**`install(PACKAGE_INFO ...)`** 签名：

```cmake
install(PACKAGE_INFO <package-name> EXPORT <export-name>
        [PROJECT <project-name> | NO_PROJECT_METADATA]
        [APPENDIX <appendix-name>]
        [DESTINATION <dir>] [LOWER_CASE_FILE]
        [VERSION <version> [COMPAT_VERSION <version>] [VERSION_SCHEMA <string>]]
        [DEFAULT_TARGETS <target>...] [DEFAULT_CONFIGURATIONS <config>...]
        [LICENSE <license-string>] [DEFAULT_LICENSE <license-string>]
        [DESCRIPTION <description-string>] [HOMEPAGE_URL <url-string>]
        [PERMISSIONS <permission>...] [CONFIGURATIONS <config>...]
        [CXX_MODULES_DIRECTORY <directory>]
        [COMPONENT <component>] [EXCLUDE_FROM_ALL])
```

`export(PACKAGE_INFO ...)` 形式相同（少了安装相关的 `DESTINATION`/`COMPONENT` 等），用于构建树。

示例：在已有 `install(TARGETS ... EXPORT MyLibTargets)` 基础上，再额外生成 CPS 描述：

```cmake
install(PACKAGE_INFO MyLib EXPORT MyLibTargets
        VERSION       ${PROJECT_VERSION}
        COMPAT_VERSION ${PROJECT_VERSION_MAJOR}.0.0
        DESCRIPTION   "A sample modern CMake library"
        HOMEPAGE_URL  "https://example.org/mylib"
        LICENSE       "MIT"
        DEFAULT_TARGETS mylib)
```

下游（CMake 侧）消费方式与普通包一致——`find_package(MyLib)` 会自动识别 CPS 描述；非 CMake 工具则直接解析生成的 `.cps` JSON。

## 11.7 CPack：打包成可分发物

`install()` 解决「放对位置」，CPack 解决「封装成 `.zip`/`.deb`/`.rpm`/安装程序」。CPack **复用你已写好的 `install()` 规则**——这是它的核心设计：装到哪、装哪些，CPack 全照搬。

### 11.7.1 最小配置

在顶层 `CMakeLists.txt` **末尾**（要在所有 `install()` 之后）：

```cmake
set(CPACK_PACKAGE_NAME    "MyApp")
set(CPACK_PACKAGE_VENDOR  "Acme Inc.")
set(CPACK_PACKAGE_VERSION "${PROJECT_VERSION}")          # 或拆成 MAJOR/MINOR/PATCH
set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "A great application")
set(CPACK_PACKAGE_CONTACT "maintainer@example.org")      # DEB 等生成器必需
set(CPACK_RESOURCE_FILE_LICENSE "${CMAKE_CURRENT_SOURCE_DIR}/LICENSE")
set(CPACK_GENERATOR "TGZ;ZIP")                           # 默认生成的格式

include(CPack)   # 必须在所有 CPACK_* 变量设置之后 include
```

`include(CPack)` 会生成 `CPackConfig.cmake` 与 `CPackSourceConfig.cmake`，之后在 build 目录运行：

```bash
cpack                       # 用 CPACK_GENERATOR 指定的所有生成器打包
cpack -G DEB                # 临时指定单一生成器
cpack -G "ZIP;TGZ"          # 多个
cpack -C Release            # 指定打包的配置（多配置生成器如 VS/Ninja Multi-Config 需要）
cpack --config CPackConfig.cmake -B out   # 指定配置文件与输出目录
cpack -G TGZ --source-package             # 源码包（走 CPackSourceConfig）
```

### 11.7.2 核心 `CPACK_*` 变量

| 变量 | 作用 |
|---|---|
| `CPACK_PACKAGE_NAME` | 包名（默认取 `PROJECT_NAME`） |
| `CPACK_PACKAGE_VERSION` | 版本；或 `CPACK_PACKAGE_VERSION_{MAJOR,MINOR,PATCH}` |
| `CPACK_PACKAGE_VENDOR` | 供应商 |
| `CPACK_PACKAGE_CONTACT` | 维护者邮箱（DEB/RPM 等需要） |
| `CPACK_PACKAGE_DESCRIPTION_SUMMARY` | 一行简介 |
| `CPACK_PACKAGE_DESCRIPTION_FILE` | 详细描述文件路径 |
| `CPACK_GENERATOR` | 二进制包生成器列表 |
| `CPACK_SOURCE_GENERATOR` | 源码包生成器列表 |
| `CPACK_PACKAGE_FILE_NAME` | 输出文件名（默认 `名-版本-系统`） |
| `CPACK_PACKAGE_INSTALL_DIRECTORY` | 安装程序的默认安装目录（NSIS/WIX） |
| `CPACK_RESOURCE_FILE_LICENSE` | 许可证文件（安装程序中展示） |
| `CPACK_RESOURCE_FILE_README` / `_WELCOME` | README / 欢迎页 |
| `CPACK_PACKAGE_INSTALL_REGISTRY_KEY` | Windows 注册表键 |
| `CPACK_STRIP_FILES` | 打包时剥离调试符号 |
| `CPACK_THREADS` | 压缩线程数 |

各生成器还有自己的 `CPACK_<GEN>_*` 变量族，例如：
- DEB：`CPACK_DEBIAN_PACKAGE_DEPENDS`、`CPACK_DEBIAN_PACKAGE_SECTION`、`CPACK_DEBIAN_FILE_NAME`、`CPACK_DEBIAN_PACKAGE_SHLIBDEPS`（自动算依赖）；
- RPM：`CPACK_RPM_PACKAGE_REQUIRES`、`CPACK_RPM_PACKAGE_GROUP`、`CPACK_RPM_FILE_NAME`；
- NSIS：`CPACK_NSIS_MUI_ICON`、`CPACK_NSIS_MODIFY_PATH`；
- WIX：`CPACK_WIX_UPGRADE_GUID`（**必填**，用于升级识别）、`CPACK_WIX_INSTALL_SCOPE`。

### 11.7.3 常见生成器

| 生成器 | 产物 | 平台 | 备注 |
|---|---|---|---|
| **ZIP** | `.zip` | 全平台 | 免安装绿色包 |
| **TGZ** / **TBZ2** / **TXZ** | `.tar.gz` 等 | Unix | 归档分发 |
| **STGZ** | 自解压 `.sh` | Unix | shell 自解压脚本 |
| **DEB** | `.deb` | Debian/Ubuntu | 需 `CPACK_PACKAGE_CONTACT`；建议开 `SHLIBDEPS` |
| **RPM** | `.rpm` | RHEL/Fedora/SUSE | 需 `rpmbuild` |
| **NSIS** / **NSIS64** | `.exe` 安装程序 | Windows | 需 NSIS；经典向导式安装 |
| **WIX** | `.msi` | Windows | 需 WiX Toolset；企业部署/组策略友好；`UPGRADE_GUID` 必填 |
| **INNOSETUP** | `.exe` | Windows | 需 Inno Setup |
| **NuGet** | `.nupkg` | Windows | NuGet 包 |
| **DragNDrop** | `.dmg` | macOS | 拖拽安装磁盘映像 |
| **productbuild** / **PackageMaker** | `.pkg` | macOS | 向导式安装，支持签名/公证 |
| **Bundle** | `.app`/`.dmg` | macOS | 应用程序包 |
| **IFW** | 跨平台安装程序 | 全平台 | Qt Installer Framework |
| **External** | 自定义 | 全平台 | 输出 JSON，交给外部工具 |
| **FreeBSD** | `.pkg` | FreeBSD | pkg 包 |

查看本机可用生成器：`cpack --help`。

### 11.7.4 组件化打包

把 11.3 定义的 `COMPONENT` 直接变成多个包或安装程序里的可选勾选项。

```cmake
set(CPACK_PACKAGE_NAME "MyApp")

# 选择打包模式
set(CPACK_DEB_COMPONENT_INSTALL ON)        # DEB：每个组件一个 .deb
set(CPACK_RPM_COMPONENT_INSTALL ON)        # RPM 同理
# 归档类按组件拆分 / 合并：
set(CPACK_ARCHIVE_COMPONENT_INSTALL ON)    # ZIP/TGZ 每组件一包；不设则合并成一个
# set(CPACK_COMPONENTS_GROUPING ALL_COMPONENTS_IN_ONE)  # 强制合并

# 只打包列出的组件（不写则打包全部）
set(CPACK_COMPONENTS_ALL runtime dev)

include(CPack)        # 必须先 include(CPack)，cpack_add_component 才可用

# 为组件加元信息（显示名、说明、依赖、是否默认勾选）
cpack_add_component(runtime
  DISPLAY_NAME "Runtime"
  DESCRIPTION  "Executables and shared libraries"
  REQUIRED)
cpack_add_component(dev
  DISPLAY_NAME "Development Files"
  DESCRIPTION  "Headers and CMake package files"
  DEPENDS runtime)                          # dev 依赖 runtime
# 可选：把多个组件归到一个安装组
cpack_add_component_group(sdk DISPLAY_NAME "SDK")
```

效果：
- 归档/DEB/RPM 组件模式下，`cpack` 会产出 `MyApp-1.0-Linux-runtime.deb`、`MyApp-1.0-Linux-dev.deb` 等多个文件；
- NSIS/WIX/IFW 等图形安装程序会把组件渲染成可勾选的安装选项，并尊重 `DEPENDS`/`REQUIRED`。

> 💡 `cpack_add_component()` / `cpack_add_component_group()` 来自 `CPackComponent` 模块，`include(CPack)` 会自动引入，无需单独 `include(CPackComponent)`。

## 11.8 安装与打包的平台差异

前面各节的 `install()` / CPack 规则在三大平台**写法相同、产物却不同**。下面把最容易出错的三处差异收拢成对照，便于一次性看清；完整工程见第 19 章。

### 11.8.1 动态库安装产物差异

同一句 `install(TARGETS mylib RUNTIME ... LIBRARY ... ARCHIVE ...)`，各 artifact-kind 在三平台落到的文件完全不同：

| 平台 | 共享库本体 | 去向（artifact-kind） | 伴生文件 | 链接定位机制 |
|---|---|---|---|---|
| **Windows** | `mylib.dll` | **RUNTIME** → `bin` | 导入库 `mylib.lib` 走 **ARCHIVE** → `lib` | 加载器按文件名在 `bin`/`PATH` 找 DLL |
| **macOS** | `libmylib.dylib` | **LIBRARY** → `lib` | 无单独导入库；内嵌 **install_name**（`@rpath/libmylib.dylib`） | `@rpath` + 可执行文件的 RPATH 解析 |
| **Linux** | `libmylib.so.1.2.3` | **LIBRARY** → `lib` | **SONAME 软链** `libmylib.so.1`（运行期）+ namelink `libmylib.so`（开发期） | `SONAME` + RPATH/`ld.so` 缓存 |

要点：Windows 的「DLL 进 `bin`、导入库 `.lib` 进 `lib`」是唯一需要把同一个 `SHARED` 目标拆到两个 `DESTINATION` 的平台；macOS/Linux 的 `.dylib`/`.so` 都归 `LIBRARY`。因此规范写法对三平台**同时**给全 RUNTIME/LIBRARY/ARCHIVE：

```cmake
include(GNUInstallDirs)
install(TARGETS mylib EXPORT MyLibTargets
        RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}    # Windows .dll
        LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}    # .so / .dylib（+ namelink）
        ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR})   # 静态库 / Windows 导入库 .lib
```

> 💡 Linux 的 `VERSION`/`SOVERSION`（见 11.4.1）决定 `.so.1.2.3` 实体名与 `.so.1` 软链；CMake 安装时会自动建好这些符号链接。Windows 无此机制，macOS 用 install_name 而非软链。

### 11.8.2 运行时依赖部署差异

把目标依赖的第三方动态库随包分发，三平台机制不同：

| 平台 | 部署手段 | 定位机制 |
|---|---|---|
| **Windows** | `$<TARGET_RUNTIME_DLLS:tgt>` 拷 DLL，或 `install(RUNTIME_DEPENDENCY_SET)` | DLL 与 exe 同目录 / `PATH` |
| **macOS** | `fixup_bundle()` 改写 install_name，或 `install(RUNTIME_DEPENDENCY_SET)` | `@rpath` / `@loader_path` |
| **Linux** | `install(RUNTIME_DEPENDENCY_SET)` + `$ORIGIN` RPATH | RPATH / `ld.so` |

Windows——构建后把所需 DLL 拷到 exe 旁（CMake 3.21+）：

```cmake
if(WIN32)
  add_custom_command(TARGET app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy_if_different
            $<TARGET_RUNTIME_DLLS:app> $<TARGET_FILE_DIR:app>
    COMMAND_EXPAND_LISTS)
endif()
```

跨平台——用运行期依赖集合统一收集（详见 11.1.6），靠 `PRE_EXCLUDE_REGEXES` 滤掉系统库：

```cmake
install(TARGETS app RUNTIME_DEPENDENCY_SET appDeps DESTINATION ${CMAKE_INSTALL_BINDIR})
install(RUNTIME_DEPENDENCY_SET appDeps
        PRE_EXCLUDE_REGEXES "api-ms-win-.*" "ext-ms-.*"   # Windows 系统 DLL
        POST_EXCLUDE_REGEXES ".*/system32/.*" "^/lib.*" "^/usr/lib.*")  # macOS/Linux 系统库
```

macOS/Linux 让安装后可执行文件自己找到同包里的库，用相对 RPATH（见 11.5）：

```cmake
if(APPLE)
  set(CMAKE_INSTALL_RPATH "@loader_path/../${CMAKE_INSTALL_LIBDIR}")
elseif(UNIX)
  set(CMAKE_INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")
endif()  # Windows 无 RPATH，靠 11.8.2 的 DLL 同目录部署
```

### 11.8.3 打包格式差异

`CPACK_GENERATOR` 应按平台选择——同一份 `install()` 规则喂给不同生成器：

| 平台 | 常用 `CPACK_GENERATOR` | 产物 |
|---|---|---|
| **Windows** | `NSIS` / `WIX` / `ZIP` | 向导安装程序 `.exe` / `.msi` / 绿色包 |
| **macOS** | `DragNDrop` / `productbuild` | 拖拽 `.dmg` / 向导 `.pkg`（可签名公证） |
| **Linux** | `DEB` / `RPM` / `TGZ` | `.deb` / `.rpm` / 归档 |

```cmake
if(WIN32)
  set(CPACK_GENERATOR "NSIS;ZIP")
elseif(APPLE)
  set(CPACK_GENERATOR "DragNDrop;productbuild")
elseif(UNIX)
  set(CPACK_GENERATOR "DEB;RPM;TGZ")
endif()
include(CPack)   # 必须在所有 CPACK_* 之后
```

> 💡 各生成器仍需各自的平台变量：WIX 的 `CPACK_WIX_UPGRADE_GUID` 必填、DEB 建议开 `CPACK_DEBIAN_PACKAGE_SHLIBDEPS` 自动算依赖、RPM 需本机有 `rpmbuild`（详见 11.7.2 / 11.7.3）。`cpack --help` 查本机实际可用的生成器。

完整跨平台工程与差异对照大全见 [[42.Cmake/19 - 跨平台实战与平台差异大全.md|第 19 章]]。

## 本章小结

- `install()` 只生成安装脚本，真正执行是 `cmake --install <build>`；它的形式分别对应「装什么」：`TARGETS`（构建产物，含各 artifact-kind 与 3.23+ 的 `FILE_SET`）、`FILES`/`PROGRAMS`（任意文件）、`DIRECTORY`（带 `PATTERN`/`FILES_MATCHING` 过滤的目录）、`EXPORT`（导出描述）、`SCRIPT`/`CODE`（安装期逻辑）、以及 3.21+ 的 `RUNTIME_DEPENDENCY_SET` / `IMPORTED_RUNTIME_ARTIFACTS`（运行期依赖）。
- 路径一律走 `GNUInstallDirs`（`CMAKE_INSTALL_BINDIR`/`LIBDIR`/`INCLUDEDIR` …），不要硬编码；prefix 可在配置期（`CMAKE_INSTALL_PREFIX`）、安装期（`--prefix`）或打包期（`DESTDIR`）覆盖。
- `COMPONENT` + `cmake --install --component` 实现选择性安装，并与 CPack 组件打包无缝对接。
- **让别人 `find_package` 的标准三件套**：`install(TARGETS ... EXPORT)` + `install(EXPORT ... NAMESPACE MyLib::)` 生成 Targets；`configure_package_config_file()` 由 `*.cmake.in` 生成可重定位的 Config；`write_basic_package_version_file(... COMPATIBILITY ...)` 生成版本文件。`target_include_directories` 必须用 `$<BUILD_INTERFACE:>`/`$<INSTALL_INTERFACE:>` 区分构建树与安装树路径。构建树直连用 `export(EXPORT|TARGETS)`。
- RPATH 决定安装后能否找到动态库：`CMAKE_INSTALL_RPATH`（设 `$ORIGIN`/`@loader_path`）、`CMAKE_INSTALL_RPATH_USE_LINK_PATH`、`CMAKE_BUILD_WITH_INSTALL_RPATH`。
- CMake 4.x 的 **CPS**（`install/export(PACKAGE_INFO ...)`）生成跨构建系统可消费的包描述，面向异构生态。
- **CPack** 复用 `install()` 规则打包：设 `CPACK_PACKAGE_*` 与 `CPACK_GENERATOR` 后 `include(CPack)`，用 `cpack -G <gen> -C <cfg>` 产出 `ZIP`/`TGZ`/`DEB`/`RPM`/`NSIS`/`WIX`/`DragNDrop`/`productbuild` 等；组件化打包用 `CPACK_<GEN>_COMPONENT_INSTALL` + `CPACK_COMPONENTS_ALL` + `cpack_add_component()`。
