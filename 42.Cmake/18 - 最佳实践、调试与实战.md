# 第 18 章 · 最佳实践、调试与实战

> 基准版本：CMake 4.3.4

这是全教程的压轴章，也是收官章。前面十七章我们逐块拆解了现代 CMake 的全部基础设施：从语言语法、target 模型、属性与生成器表达式，到查找依赖、安装导出、测试、工具链、模块工具集。每一章都像是在打磨一块零件。本章要做两件事——**把零件拧成一台完整的机器**，以及**告诉你机器卡住时怎么修**。

具体而言，本章分三大块。第一块是"道"：现代 CMake 的最佳实践清单与反模式剖析，把散落在各章的"应该这样写""不要那样写"系统地收拢成一份可以贴在显示器旁边的检查表。第二块是"术"：调试技巧大全，CMake 的配置过程长期被诟病为"黑盒"，但实际上它提供了极其丰富的内省（introspection）能力——`--trace`、`--debug-find`、`variable_watch`、`CMakeConfigureLog.yaml` 等等，会用这些工具，配置脚本就不再是黑盒。第三块是"器"：一个从零搭起、完整可复现的实战工程——一个库、一个可执行、GoogleTest 单元测试、`install()` 导出让别人 `find_package` 复用、`CPack` 打包、`CMakePresets.json` 一键固化——把前面所有知识点在一个真实项目里跑通一遍。

## 18.1 现代 CMake 最佳实践清单

"现代 CMake"不是一个版本号，而是一套思维方式。它的核心可以浓缩成一句话：**以 target 为中心，用依赖关系描述需求，让需求自动传播，而不是靠全局状态硬塞。** 下面这份清单是这套思维方式的具体落地，每一条都给出"为什么"和"怎么做"。建议把它当成一份 code review 的检查表。

### 18.1.1 一图流：现代 CMake 十二条军规

| # | 军规 | 一句话理由 |
|---|------|-----------|
| 1 | 用 `target_*` 命令，不用全局命令 | 全局命令污染所有 target，无法表达"谁需要什么" |
| 2 | 每个 `target_*` 显式标注 `PUBLIC`/`PRIVATE`/`INTERFACE` | 控制需求是否沿依赖链传播，这是现代 CMake 的灵魂 |
| 3 | 导出的 target 加命名空间 `Foo::` | 命名空间 target 不存在时立即报错，避免被当成裸库名 |
| 4 | 安装路径用 `GNUInstallDirs` | 不要硬编码 `lib`/`bin`/`include`，跨发行版可移植 |
| 5 | `cmake_minimum_required` 用区间 `<min>...<max>` | 同时声明"最低能跑"和"按哪个版本的策略行为" |
| 6 | 显式列源文件，不用 `file(GLOB)` | GLOB 不参与依赖追踪，新增文件不触发重新配置 |
| 7 | 用 `target_compile_features` / `CXX_STANDARD`，不手写 `-std=` | 声明式、可传播、跨编译器；手写 flag 不可移植又污染 |
| 8 | 不往 `CMAKE_CXX_FLAGS` 里塞东西 | 全局 flag 影响每个 target 和每个依赖，难以局部覆盖 |
| 9 | 永远 out-of-source 构建 | 保持源码树干净，`rm -rf build` 即可彻底清理 |
| 10 | 用 Presets 固化配置 | 把一长串 `-D` 命令行参数沉淀成可版本控制的 JSON |
| 11 | 顶层用 `PROJECT_IS_TOP_LEVEL` 守卫测试/安装 | 项目被 `add_subdirectory` 嵌入时自动收敛 |
| 12 | 用 `BUILD_TESTING` + `CTest` 模块开关测试 | 标准化测试开关，下游可一键关掉你的测试 |

下面逐条展开讲透。

### 18.1.2 用 target_* 而非全局命令

这是现代 CMake 与"古典 CMake"最根本的分水岭。古典写法用一组全局命令——`include_directories()`、`add_definitions()`、`link_libraries()`、`add_compile_options()`——这些命令的作用范围是"当前目录及其子目录中之后定义的所有 target"。问题在于：它表达的是"位置"，而不是"依赖"。一个 target 拿到了哪些头文件路径、哪些宏、哪些链接库，取决于它在哪个目录、写在哪一行之后，而不是取决于它实际依赖了什么。这种隐式的、基于文本顺序的耦合，是大型 CMake 工程难以维护的头号原因。

现代写法用 `target_*` 系列命令，把每一项需求**绑定到具体的 target 上**：

```cmake
# ❌ 古典：作用于"此后所有 target"，无法表达归属
include_directories(${CMAKE_CURRENT_SOURCE_DIR}/include)
add_definitions(-DUSE_FOO)
link_libraries(foo)
add_executable(app main.cpp)   # app 被动继承了上面三项，但代码里看不出关系

# ✅ 现代：每项需求显式绑定到 app
add_executable(app main.cpp)
target_include_directories(app PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_compile_definitions(app PRIVATE USE_FOO)
target_link_libraries(app PRIVATE foo)
```

记忆口诀：**凡是不带 `target_` 前缀、又能影响编译/链接的全局命令，现代工程里基本都不该出现。** 对照表：

| 古典全局命令 | 现代 target 命令 |
|--------------|------------------|
| `include_directories()` | `target_include_directories()` |
| `add_definitions()` / `add_compile_definitions()` | `target_compile_definitions()` |
| `add_compile_options()` | `target_compile_options()` |
| `link_libraries()` | `target_link_libraries()` |
| `link_directories()` | `target_link_directories()`（少用，优先用 import target） |
| `include(...)` 设全局标准 | `target_compile_features()` |

### 18.1.3 明确 PUBLIC / PRIVATE / INTERFACE

`target_*` 命令的第一个关键字（`PUBLIC`/`PRIVATE`/`INTERFACE`）决定了这项需求是"自己用"还是"传给依赖我的人用"，这是现代 CMake 的核心机制（第 4 章详述）。三句话区分：

- **`PRIVATE`**：仅本 target 编译时需要，不传播。典型：实现细节用到的内部头、内部依赖库。
- **`INTERFACE`**：本 target 不需要，但链接我的人需要。典型：header-only 库的头目录。
- **`PUBLIC`** = `PRIVATE` + `INTERFACE`：本 target 需要，链接我的人也需要。典型：出现在公共头文件里的依赖。

判断标准非常机械：**这个东西出现在我的公共头文件（会被安装、被别人 `#include` 的头）里吗？** 出现了就是 `PUBLIC`（或 header-only 时 `INTERFACE`），只在 `.cpp` 里用就是 `PRIVATE`。

```cmake
add_library(mathx src/mathx.cpp)

# 公共头 include/ 目录：别人也要能 #include <mathx/mathx.h> → PUBLIC（用 BUILD/INSTALL 双接口）
target_include_directories(mathx
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>)

# fmt 出现在公共头的函数签名里 → PUBLIC，依赖会传播
target_link_libraries(mathx PUBLIC fmt::fmt)

# spdlog 只在 mathx.cpp 内部用于打日志 → PRIVATE，不传播
target_link_libraries(mathx PRIVATE spdlog::spdlog)
```

写错的代价很实际：该 `PUBLIC` 写成 `PRIVATE`，下游链接你的库时会报"找不到符号 / 找不到头"；该 `PRIVATE` 写成 `PUBLIC`，会把本该隐藏的内部依赖泄漏给下游，造成不必要的传递依赖和版本冲突。

### 18.1.4 导出加命名空间 Foo::

当你用 `install(EXPORT ...)` 导出 target 供别人 `find_package()` 使用时，务必给导出集加上命名空间（见第 11 章）：

```cmake
install(EXPORT mathxTargets
    FILE mathxTargets.cmake
    NAMESPACE mathx::            # 关键：导出为 mathx::mathx 而非裸 mathx
    DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/mathx)
```

为什么重要？因为带 `::` 的名字 CMake 强制当作 **import target** 解析——如果拼错或包没找到，`target_link_libraries(app PRIVATE mathx::mathx)` 会在配置阶段**立即报错**。而裸名字 `mathx` 一旦找不到 target，CMake 会把它当成一个普通的库文件名传给链接器，错误推迟到链接阶段，报一句晦涩的 `cannot find -lmathx`，排查成本陡增。命名空间把"早失败、清晰失败"变成默认行为。

### 18.1.5 用 GNUInstallDirs

不要硬编码安装子目录。不同平台、不同发行版的约定不一样：64 位库在某些发行版叫 `lib64`，在 Debian 系叫 `lib/x86_64-linux-gnu`，Windows 习惯把可执行和 DLL 都放 `bin`。`GNUInstallDirs` 模块帮你抹平这些差异：

```cmake
include(GNUInstallDirs)

install(TARGETS mathx
    RUNTIME  DESTINATION ${CMAKE_INSTALL_BINDIR}       # 通常 bin
    LIBRARY  DESTINATION ${CMAKE_INSTALL_LIBDIR}       # 通常 lib / lib64
    ARCHIVE  DESTINATION ${CMAKE_INSTALL_LIBDIR}
    INCLUDES DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})  # 通常 include
```

它提供 `CMAKE_INSTALL_BINDIR`、`CMAKE_INSTALL_LIBDIR`、`CMAKE_INSTALL_INCLUDEDIR`、`CMAKE_INSTALL_DATADIR`、`CMAKE_INSTALL_DOCDIR` 等一整套变量，且用户可以通过 `-DCMAKE_INSTALL_LIBDIR=...` 覆盖。

### 18.1.6 cmake_minimum_required 用区间

`cmake_minimum_required` 的版本号其实承担两个职责：**最低可运行版本**，以及**策略（policy）行为的基线**。老写法只给一个版本号 `VERSION 3.20`，意思是"最低 3.20，且按 3.20 的策略行为运行"。但如果用户装的是 4.3.4，你其实希望享受 3.20 之后引入的所有新策略的现代行为，又不想把最低版本抬到 4.3.4（那会把还在用 3.20 的用户挡在门外）。区间语法正好解决这个矛盾：

```cmake
# ❌ 单版本：最低 3.20，且策略行为也锁死在 3.20，新策略全不启用
cmake_minimum_required(VERSION 3.20)

# ✅ 区间：最低仍是 3.20，但策略行为按 4.3 的现代默认（截至 4.3 的策略都启用 NEW 行为）
cmake_minimum_required(VERSION 3.20...4.3)
```

含义：运行的 CMake 至少要 3.20；策略上，所有在 `<= 4.3` 区间内引入的策略都采用 NEW（现代）行为，不会因为你声明了一个低 `min` 而退回老行为、刷一堆 deprecation 警告。这是现代工程的标准写法。

### 18.1.7 显式列源文件，而非 file(GLOB)

这是一条争议常被提起、但官方立场非常明确的规则：**不要用 `file(GLOB)` 收集源文件。**

```cmake
# ❌ 反模式：通配收集，新增 .cpp 后构建不会自动感知
file(GLOB SOURCES "src/*.cpp")
add_library(mathx ${SOURCES})

# ✅ 显式列出，新增/删除文件 = 改 CMakeLists.txt = 自动触发重新配置
add_library(mathx
    src/mathx.cpp
    src/internal/helper.cpp
    src/internal/tables.cpp)
```

根因在 CMake 的构建模型：CMake 在**配置阶段**展开 `GLOB`，把匹配到的文件列表"烧"进生成的构建系统。之后你新建了一个 `src/new.cpp`，文件系统变了，但 `CMakeLists.txt` 没变——增量构建（`cmake --build .` 或 `make`/`ninja`）不会重新跑配置，于是新文件被完全忽略，编译时也不报错，调试时百思不得其解。而显式列源文件，新增文件必然意味着修改 `CMakeLists.txt`，CMake 检测到 `CMakeLists.txt` 时间戳变化会自动重新配置。

CMake 3.12 引入了 `CONFIGURE_DEPENDS` 选项试图缓解：`file(GLOB SRC CONFIGURE_DEPENDS "src/*.cpp")` 会让构建工具在每次构建前重新检查目录。但官方文档明确警告：它**不保证在所有生成器上可靠**，且每次构建都要扫目录、有性能开销，**不推荐作为常规手段**。结论不变：显式列出。

### 18.1.8 用 compile_features / CXX_STANDARD，而非手写 -std=

语言标准应该用声明式机制表达，而不是手塞编译器 flag（第 14 章详述）：

```cmake
# ❌ 反模式：硬编码 flag，不可移植（MSVC 不认 -std），会污染所有语言连 C 文件都被塞
add_compile_options(-std=c++20)

# ✅ 方式一：target 级元特性，能沿依赖传播
target_compile_features(mathx PUBLIC cxx_std_20)

# ✅ 方式二：标准属性三件套（设在 target 之前的全局变量，或直接设 target 属性）
set_target_properties(mathx PROPERTIES
    CXX_STANDARD 20
    CXX_STANDARD_REQUIRED ON     # 编译器不支持就报错，不静默降级
    CXX_EXTENSIONS OFF)          # 用 -std=c++20 而非 -std=gnu++20
```

`target_compile_features(... PUBLIC cxx_std_20)` 的妙处：它声明"我至少需要 C++20"，并且这个要求会沿 `PUBLIC` 传播给所有链接 `mathx` 的 target——下游自动也被要求至少 C++20，无需重复声明。CMake 会自动翻译成当前编译器认识的正确 flag（GCC/Clang 的 `-std=c++20`、MSVC 的 `/std:c++20`）。

### 18.1.9 不污染 CMAKE_CXX_FLAGS

`CMAKE_CXX_FLAGS`（以及 `CMAKE_C_FLAGS`、`CMAKE_EXE_LINKER_FLAGS` 等）是全局 flag 变量，会被附加到**每一个** C++ target 的编译命令上，包括你 `FetchContent` 进来的第三方依赖。往里塞东西是典型反模式：

```cmake
# ❌ 反模式：全局 flag，连第三方依赖都被强加 -Werror，依赖里一个警告就让你构建失败
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall -Wextra -Werror")

# ✅ 只给自己的 target 加，且用生成器表达式按编译器区分
target_compile_options(mathx PRIVATE
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra;-Werror>
    $<$<CXX_COMPILER_ID:MSVC>:/W4;/WX>)
```

如果确实想给"自己的所有 target"统一加警告 flag，正确做法是建一个 `INTERFACE` 库当"warning 载体"，让自己的 target 显式链接它（下面 18.4.4 给完整范式），而不是污染全局变量。

### 18.1.10 永远 out-of-source 构建

In-source build（直接在源码目录里 `cmake .`）会把 `CMakeCache.txt`、`CMakeFiles/`、Makefile 等一大堆生成物和你的源码混在一起，污染版本控制、难以清理、还可能让 `file(GLOB)` 误收集到生成文件。永远用独立的构建目录：

```bash
# ✅ out-of-source：构建产物全在 build/，rm -rf build 即彻底清理
cmake -S . -B build
cmake --build build
```

可以在顶层加一道防呆，禁止 in-source：

```cmake
if(CMAKE_SOURCE_DIR STREQUAL CMAKE_BINARY_DIR)
    message(FATAL_ERROR
        "禁止在源码目录内构建。请用：cmake -S . -B build")
endif()
```

### 18.1.11 用 Presets 固化配置

当你的项目有多套配置（debug/release、不同编译器、不同选项组合），与其每次手敲一长串 `-D` 参数，不如用 `CMakePresets.json` 把它们固化下来（第 16 章详述）。Presets 是 JSON、可版本控制、可被 IDE 识别、可组合继承：

```bash
# 没有 presets：每次都要记住这一长串
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON -DCMAKE_INSTALL_PREFIX=/opt/mathx ...

# 有 presets：一句话
cmake --preset release
```

本章 18.5 会给出一份覆盖 debug/release + test + workflow 的完整 `CMakePresets.json`。

## 18.2 反模式逐条剖析

上一节的清单偏"应该怎么做"，这一节聚焦"绝对不要怎么做"——把最常见的反模式拎出来，给"❌ 错误写法 → ✅ 正确写法"的逐条对照。这些反模式在历史悠久的 CMake 工程里随处可见，识别并铲除它们，是迁移到现代 CMake 的第一步。

### 18.2.1 反模式：file(GLOB) 收集源文件

**❌ 错误写法**

```cmake
file(GLOB SOURCES "src/*.cpp")
file(GLOB_RECURSE HEADERS "include/*.h")
add_library(mathx ${SOURCES} ${HEADERS})
```

**问题**：增量构建失效。`GLOB` 在配置时一次性展开，新增 `src/foo.cpp` 后，`CMakeLists.txt` 时间戳没变 → 不重新配置 → 新文件被忽略，编译期甚至不报错，表现为"明明写了代码却没生效"。`GLOB_RECURSE` 还可能误抓到 `build/` 里的生成文件。

**✅ 正确写法**

```cmake
add_library(mathx
    src/mathx.cpp
    src/internal/helper.cpp)
# 头文件不必列进源文件列表，除非要用 FILE_SET HEADERS 管理安装（见 18.4）
```

显式列出虽然多敲几行，但换来的是"改文件清单 = 改 `CMakeLists.txt` = 自动重配置"的确定性。

### 18.2.2 反模式：全局 include_directories / add_definitions

**❌ 错误写法**

```cmake
include_directories(${CMAKE_SOURCE_DIR}/include)
add_definitions(-DMATHX_DEBUG)
add_library(mathx src/mathx.cpp)
add_executable(app main.cpp)   # app 也莫名其妙拿到了 include 路径和宏
```

**问题**：作用域是"此后所有 target"。`app` 被动继承了 `mathx` 的头路径和宏，但代码里完全看不出这层关系；当工程变大、目录变多，谁拿到了什么变得无法追溯。

**✅ 正确写法**

```cmake
add_library(mathx src/mathx.cpp)
target_include_directories(mathx PUBLIC include)
target_compile_definitions(mathx PRIVATE MATHX_DEBUG)

add_executable(app main.cpp)
target_link_libraries(app PRIVATE mathx)   # app 通过链接 mathx 自动获得其 PUBLIC 头路径
```

### 18.2.3 反模式：手拼 CMAKE_CXX_FLAGS

**❌ 错误写法**

```cmake
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -O3 -march=native -Wall")
```

**问题**：（1）全局污染，连第三方依赖都被强加；（2）`-O3` 和 CMake 自己根据 `CMAKE_BUILD_TYPE` 设置的优化级别（如 Release 的 `-O3`、RelWithDebInfo 的 `-O2`）打架，可能互相覆盖出意外结果；（3）`-march=native` 让二进制不可移植，在别的机器上跑可能非法指令崩溃；（4）`-Wall` 等警告 flag 不该作用于依赖。

**✅ 正确写法**

```cmake
# 优化级别交给 CMAKE_BUILD_TYPE / 生成器表达式，不手设 -O
target_compile_options(mathx PRIVATE
    $<$<CONFIG:Release>:$<$<CXX_COMPILER_ID:GNU,Clang>:-march=native>>
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra>)
```

### 18.2.4 反模式：link_libraries

**❌ 错误写法**

```cmake
link_libraries(pthread fmt)
add_executable(app main.cpp)   # 全局生效，所有后续 target 都链 pthread/fmt
```

**问题**：和 `include_directories` 同病——全局、无归属、无法表达谁真的需要这些库。

**✅ 正确写法**

```cmake
add_executable(app main.cpp)
target_link_libraries(app PRIVATE Threads::Threads fmt::fmt)
```

（线程库优先用 `find_package(Threads)` 提供的 import target `Threads::Threads`，而非裸 `pthread`。）

### 18.2.5 反模式：in-source build

**❌ 错误写法**

```bash
cd myproject
cmake .            # 在源码目录里配置
make
```

**问题**：`CMakeCache.txt`、`CMakeFiles/`、`Makefile` 等生成物散落源码树，污染 Git、难清理、易被通配命令误收集。

**✅ 正确写法**

```bash
cmake -S . -B build
cmake --build build
```

并在顶层 `CMakeLists.txt` 加 18.1.10 的 `FATAL_ERROR` 防呆。

### 18.2.6 反模式：滥用 macro

**❌ 错误写法**

```cmake
macro(add_my_lib name)
    add_library(${name} ${ARGN})
    set(result ${name})          # macro 里"设变量"实际是改调用者作用域，且无局部隔离
endmacro()
```

**问题**：`macro` 不创建新作用域，参数 `${name}`/`${ARGN}` 是文本替换而非真正的变量，里面 `set()` 会泄漏污染调用者，`return()` 行为也反直觉（直接从调用者返回）。

**✅ 正确写法**：除非你确实需要"在调用者作用域里设变量"，否则**一律用 `function`**。`function` 有独立作用域，参数是真变量，需要回传值时用 `set(... PARENT_SCOPE)` 或新版的 `return(PROPAGATE ...)`：

```cmake
function(add_my_lib name)
    add_library(${name} ${ARGN})
    # 需要回传时显式 PARENT_SCOPE，意图清晰、无意外泄漏
    set(result ${name} PARENT_SCOPE)
endfunction()
```

### 18.2.7 反模式：硬编码绝对路径 / 安装路径

**❌ 错误写法**

```cmake
target_include_directories(app PRIVATE /home/alice/libs/foo/include)
install(TARGETS app RUNTIME DESTINATION /usr/local/bin)
```

**问题**：`/home/alice/...` 在别人机器、CI、容器里都不存在；硬编码 `/usr/local/bin` 无视 `CMAKE_INSTALL_PREFIX`、无视平台差异。

**✅ 正确写法**

```cmake
find_package(foo REQUIRED)                  # 让 CMake 去找，而非写死路径
target_link_libraries(app PRIVATE foo::foo)

include(GNUInstallDirs)
install(TARGETS app RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR})  # 相对前缀、跨平台
```

### 18.2.8 反模式：target_link_libraries 不写关键字

**❌ 错误写法**

```cmake
target_link_libraries(mathx fmt::fmt)   # 没写 PUBLIC/PRIVATE/INTERFACE
```

**问题**：不写关键字是"古典签名"，CMake 为兼容老代码会接受，但传播语义变得隐晦（取决于历史规则），且**同一个 target 不能混用"带关键字"和"不带关键字"两种调用**，否则直接报错。这是新手最常踩的配置错误之一。

**✅ 正确写法**：永远写关键字。

```cmake
target_link_libraries(mathx PUBLIC fmt::fmt)
```

## 18.3 调试技巧大全

CMake 配置失败时，初学者往往束手无策——脚本不像普通程序能下断点单步。但其实 CMake 提供了一整套强大的内省与调试工具，覆盖"打印变量、追踪执行、调试 find、查看缓存、监视变量变化、看真实编译命令、读配置日志"全链路。本节逐条给出**命令 / 用途 / 示例**。掌握这些，配置过程对你就是透明的。

### 18.3.1 message：分级日志

`message()` 是最基础的调试手段，但它有**日志级别**，配合命令行可以精细控制输出量（第 8 章详述）。

**`message(<LEVEL> "...")`：按级别打印**。级别从高到低：`FATAL_ERROR`（致命，停止）、`SEND_ERROR`（错误，继续配置但不生成）、`WARNING`、`AUTHOR_WARNING`、`DEPRECATION`、`NOTICE`（默认级别，输出到 stderr）、`STATUS`（常规进度，带 `--` 前缀）、`VERBOSE`、`DEBUG`、`TRACE`（最详细）。

```cmake
message(STATUS  "常规进度，默认可见")
message(VERBOSE "更啰嗦的细节，默认不显示")
message(DEBUG   "调试信息，默认不显示")
message(TRACE   "最细粒度，默认不显示")
```

**`--log-level=<LEVEL>`：控制显示哪些级别**。默认只显示 `STATUS` 及以上。想看 `DEBUG`/`TRACE` 必须调高：

```bash
cmake -S . -B build --log-level=DEBUG     # 显示 DEBUG 及以上的 message
cmake -S . -B build --log-level=VERBOSE   # 显示 VERBOSE 及以上
```

**`CMAKE_MESSAGE_LOG_LEVEL`：用变量持久化日志级别**。等价于命令行 `--log-level`，但写进缓存后后续构建复用，无需每次敲：

```bash
cmake -S . -B build -DCMAKE_MESSAGE_LOG_LEVEL=DEBUG
```

**`CMAKE_MESSAGE_CONTEXT`：给日志加上下文标签**。在嵌套的子目录/函数里，可以把当前"上下文名"压栈，配合 `--log-context` 命令行，所有 `message` 会自动带上 `[ctx.subctx]` 前缀，迅速定位输出来自哪一层：

```cmake
function(configure_module)
    list(APPEND CMAKE_MESSAGE_CONTEXT "mymod")   # 压栈上下文
    message(STATUS "配置中")   # 启用 --log-context 时输出：[mymod] 配置中
endfunction()
```

```bash
cmake -S . -B build --log-context   # 启用上下文前缀显示
```

### 18.3.2 trace：逐行追踪执行

当你想知道"配置脚本到底一行行执行了什么、变量在每一步是什么值"时，`--trace` 系列是终极武器。

**`--trace`：打印每一条被执行的命令**。输出格式为 `<文件>(<行号>):  <命令>(<参数>)`，把整个配置过程的执行流摊开。输出量巨大，通常配合 `--trace-redirect` 落盘后再搜。

```bash
cmake -S . -B build --trace
```

**`--trace-expand`：在 trace 基础上展开所有变量**。这是 `--trace` 最有用的变体——它把命令参数里的 `${VAR}` 全部替换成实际值再打印，让你直接看到"这一行命令拿到的真实参数是什么"。排查"变量值不对"类问题首选：

```bash
cmake -S . -B build --trace-expand
```

例如脚本里写 `target_link_libraries(app PRIVATE ${MY_LIBS})`，普通 `--trace` 打印的还是 `${MY_LIBS}`，而 `--trace-expand` 会打印成 `target_link_libraries(app PRIVATE fmt::fmt;spdlog::spdlog )`，一眼看出这个变量实际展开成了什么。

**`--trace-source=<file>`：只追踪指定文件**。全量 trace 噪声太大时，把追踪范围限定到你怀疑的某个 `.cmake` 或 `CMakeLists.txt`，只打印来自该文件的命令：

```bash
cmake -S . -B build --trace-source=cmake/Helpers.cmake --trace-expand
```

可以多次指定 `--trace-source` 追踪多个文件。

**`--trace-redirect=<file>`：把 trace 输出写到文件**。trace 输出动辄上万行，直接刷屏不可读。重定向到文件后用编辑器/grep 慢慢看：

```bash
cmake -S . -B build --trace-expand --trace-redirect=trace.log
```

四者关系：`--trace` 是开关，`--trace-expand` 是"展开变量版"的开关，`--trace-source` 缩小追踪范围，`--trace-redirect` 决定输出去向。常用组合是 `--trace-expand --trace-source=<可疑文件> --trace-redirect=trace.log`。

### 18.3.3 debug-output 与 debug-find 家族

**`--debug-output`：显示更详细的内部调试信息**。会打印 `message(SEND_ERROR)`/`message(FATAL_ERROR)` 触发处的调用栈等额外信息，定位"是谁调用的这条链路"很有用。

```bash
cmake -S . -B build --debug-output
```

**`--debug-find`：调试所有 find_* 命令**。这是排查"`find_package`/`find_library` 找不到东西"的核心工具。它会把每个 `find_program`/`find_library`/`find_file`/`find_path`/`find_package` 的**搜索过程**全打印出来——查了哪些目录、试了哪些文件名、为什么没命中：

```bash
cmake -S . -B build --debug-find
```

输出会告诉你类似"在 `/usr/lib`、`/usr/local/lib` 找 `libfoo.so`、`libfoo.a`……均未找到"，让你立刻明白是路径不对、库名不对、还是根本没装。等价的脚本内开关是变量 `CMAKE_FIND_DEBUG_MODE`（可在 `find_*` 调用前后 `set(... TRUE/FALSE)` 只对局部开启）。

**`--debug-find-pkg=<pkg>`：只调试指定包的 find_package**（3.23+）。全量 `--debug-find` 噪声太大时，把调试范围缩小到你关心的那个包：

```bash
cmake -S . -B build --debug-find-pkg=fmt        # 只打印 fmt 相关的查找过程
```

**`--debug-find-var=<var>`：只调试结果存入指定变量的 find_* 调用**（3.23+）。当你知道某个 `find_library(FOO_LIB ...)` 失败、`FOO_LIB-NOTFOUND`，可以精准追踪它：

```bash
cmake -S . -B build --debug-find-var=FOO_LIB    # 只打印结果变量为 FOO_LIB 的查找
```

### 18.3.4 -L / -LA / -LAH：查看缓存

配置出问题，常常是缓存变量的值不对。`cmake -L` 系列把缓存变量列出来检视，无需打开 `CMakeCache.txt` 翻：

**`cmake -L <builddir>`：列出非高级（non-advanced）缓存变量**，即用户通常关心的那些。

**`cmake -LA <builddir>`：列出全部缓存变量**，包括标记为 advanced 的（编译器路径、内部细节等）。

**`cmake -LAH <builddir>`：在 `-LA` 基础上附带每个变量的帮助说明（help string）**，看不懂某个变量是干嘛的时用它：

```bash
cmake -L  build       # 用户级缓存变量
cmake -LA build       # 全部缓存变量
cmake -LAH build      # 全部 + 说明文字
```

注意它读的是已存在的 build 目录里的缓存，所以要先配置过一次。

**`cmake --system-information [file]`：dump 整个系统/CMake 环境信息**。把当前平台、编译器、所有系统变量、模块路径等一次性导出，提交 bug 报告或排查"环境怎么和别人不一样"时很有用：

```bash
cmake --system-information sysinfo.txt
```

### 18.3.5 CMakePrintHelpers：优雅地打印变量与属性

每次都手写 `message(STATUS "FOO = ${FOO}")` 很啰嗦。`CMakePrintHelpers` 模块提供两个便捷宏：

**`cmake_print_variables(<var>...)`：一行打印多个变量的名字与值**：

```cmake
include(CMakePrintHelpers)
cmake_print_variables(CMAKE_CXX_COMPILER CMAKE_BUILD_TYPE PROJECT_VERSION)
# 输出：-- CMAKE_CXX_COMPILER="/usr/bin/g++" ; CMAKE_BUILD_TYPE="Release" ; PROJECT_VERSION="1.0.0"
```

**`cmake_print_properties(TARGETS <t>... PROPERTIES <prop>...)`：打印 target/源文件/目录等的属性**。调试"这个 target 的 include 目录到底有哪些""链了哪些库"时极方便：

```cmake
cmake_print_properties(
    TARGETS mathx
    PROPERTIES INTERFACE_INCLUDE_DIRECTORIES INTERFACE_LINK_LIBRARIES TYPE)
```

### 18.3.6 variable_watch：监视变量何时被改

当一个变量莫名其妙变成了你不期望的值，你想知道"到底是哪一行代码改了它"，`variable_watch()` 就是为此而生——它给变量挂一个监视器，每当该变量被**读或写**，就打印一条记录（在哪个文件、哪一行、读还是写、新值是什么）：

```cmake
variable_watch(CMAKE_CXX_FLAGS)            # 每次读写 CMAKE_CXX_FLAGS 都打印
# 也可指定回调函数做自定义处理：
variable_watch(MY_VAR my_watch_callback)
```

这是排查"全局变量被某个不知名的子目录/模块偷偷修改"类问题的杀手锏。

### 18.3.7 看真实编译命令：VERBOSE_MAKEFILE 与 --build -v

配置看起来没问题，但编译报错，你想看**实际传给编译器的完整命令行**（到底加了哪些 flag、include 路径对不对）。两种方式：

**`CMAKE_VERBOSE_MAKEFILE`：让生成的构建系统打印每条编译/链接命令**：

```bash
cmake -S . -B build -DCMAKE_VERBOSE_MAKEFILE=ON
cmake --build build           # 此后每条命令都会回显完整命令行
```

**`cmake --build . -v`（或 `--verbose`）：构建时临时开启 verbose**，无需改缓存，更轻便，对 Make 和 Ninja 都有效：

```bash
cmake --build build -v        # 一次性看完整编译/链接命令
```

看到真实命令后，"为什么没加 `-DFOO`""为什么 include 路径不对""链接顺序为什么是这样"之类问题往往一目了然。

### 18.3.8 配置日志：CMakeConfigureLog.yaml 与 message(CONFIGURE_LOG ...)

CMake 3.26 引入了一个常被忽视但极其有用的特性——**结构化配置日志**。每次配置时，CMake 会把诸如 `try_compile`/`try_run`/`check_*` 的详细过程（用的什么编译命令、输出是什么、为什么判定成功/失败）写进构建目录下的 `CMakeFiles/CMakeConfigureLog.yaml`。当某个 `check_cxx_source_compiles()` 莫名失败时，去这个 YAML 里翻对应条目，能看到完整的试编译命令和编译器报错原文，远比"检测失败"这一句话有用：

```bash
# 配置后查看（路径相对于 build 目录）
cat build/CMakeFiles/CMakeConfigureLog.yaml
```

**`message(CONFIGURE_LOG "...")`：把自己的诊断信息也写进配置日志**。你在自定义的探测逻辑里，可以用这个特殊级别把详细信息记进 `CMakeConfigureLog.yaml`，而不刷屏到终端——既保留了排查所需的细节，又保持控制台输出干净：

```cmake
message(CONFIGURE_LOG "探测 SIMD 支持：尝试编译 AVX2 测试代码……结果见上下文")
```

### 18.3.10 `cmake --fresh`（3.24+）：清除缓存重新配置

**问题背景**：有时候你想"完全从零开始配置"——缓存里有旧值干扰、换了工具链但不想手动删除构建目录、或只是想确认"干净配置是否也能成功"。通常的做法是 `rm -rf build && cmake ...`，但这会连已编译的产物也一起删掉，下次还要全量重编。

**`cmake --fresh`** 是 CMake 3.24 引入的更精准替代方案：**只清除配置缓存**（`CMakeCache.txt` 和 `CMakeFiles/`），保留已编译的 `.o`/`.a`/可执行文件，然后重新运行完整的配置流程。

```bash
# 等价于：删 CMakeCache.txt + CMakeFiles/ → 重新 cmake -S . -B build
cmake --fresh -S . -B build

# 也可在已存在的 build 目录上直接用，不需要先 cd 进去
cmake --fresh -S . -B build -DCMAKE_BUILD_TYPE=Release

# 配合 preset 使用（清除该 preset 对应 build 目录的缓存）
cmake --preset release --fresh
```

**与删 build 目录的对比**：

| 方式 | 清除内容 | 保留内容 | 适用场景 |
|---|---|---|---|
| `rm -rf build && cmake ...` | 所有文件（缓存 + 编译产物） | 无 | 怀疑编译产物本身损坏；换工具链（编译器） |
| `cmake --fresh` | 配置缓存（`CMakeCache.txt`、`CMakeFiles/cmake.check_cache`、CMake 内部元数据） | 已编译的 `.o`/`.a`/可执行；`_deps/`（FetchContent 下载的源码） | 只想重跑配置逻辑；换了非编译器类选项（`CMAKE_BUILD_TYPE`、`CPACK_*` 等） |

> **注意**：`--fresh` 不删除 FetchContent 已下载的依赖（`${CMAKE_BINARY_DIR}/_deps`），所以重配后不需要重新下载第三方源码——这比全删 build 目录快得多。换编译器时，由于编译器检测结果写在缓存里，`--fresh` 能正确触发重新检测；但编译产物（由旧编译器生成）仍然留在 build 目录，可能与新编译器产物混用，此时还是建议删目录。

### 18.3.11 cmake-file-api：IDE 与工具查询构建图的现代接口

**为什么需要**：IDE（CLion、VS Code 的 CMake Tools 扩展、Qt Creator 等）、代码补全工具（clangd、ccls）、静态分析器在"感知" CMake 项目时，过去只能解析 `compile_commands.json`（仅包含编译命令，不含目标关系、安装规则等），或者"插入"到 CMake 里硬读内部状态——这既脆弱又与 CMake 版本强耦合。

**cmake-file-api** 是 CMake 3.14 引入的**官方机器可读查询接口**：工具在构建目录下写入"查询文件"，CMake 配置时读取并在同目录生成结构化的 JSON 响应，包含目标列表、依赖关系、编译选项、安装规则、测试用例等完整构建图信息。

**工作流程**：

```
1. 工具在 <build>/.cmake/api/v1/query/ 写查询文件
                     ↓
2. cmake -B <build> 执行配置
                     ↓
3. CMake 在 <build>/.cmake/api/v1/reply/ 生成 JSON 响应
                     ↓
4. 工具读取 JSON，不需要解析 CMakeLists.txt 或 CMakeCache.txt
```

**查询文件写法**（工具或脚本创建空文件即触发响应）：

```bash
# 查询所有目标的代码模型（codemodel v2 是最完整的目标/目录/依赖信息）
mkdir -p build/.cmake/api/v1/query
touch build/.cmake/api/v1/query/codemodel-v2

# 查询 CMake 文件列表（哪些 CMakeLists.txt / .cmake 参与了此次配置）
touch build/.cmake/api/v1/query/cmakeFiles-v1

# 查询配置日志（等同于 CMakeConfigureLog.yaml 内容）
touch build/.cmake/api/v1/query/configureLog-v1
```

```bash
# 配置后，响应文件出现在：
ls build/.cmake/api/v1/reply/
# index-<hash>.json          ← 入口索引，列出所有响应文件
# codemodel-v2-<hash>.json   ← 目标列表与目录树
# target-<name>-<hash>.json  ← 每个目标的详细信息（源文件、编译选项、链接库）
# cmakeFiles-v1-<hash>.json  ← 参与配置的所有 .cmake 文件
```

**JSON 响应包含的信息（`codemodel-v2` 节选）**：

- 所有目标（可执行/库/自定义）的名称、类型、源文件清单
- 每个源文件的编译命令片段（include 路径、宏定义、语言标准）
- 目标间依赖关系（`PRIVATE`/`PUBLIC`/`INTERFACE` 链接）
- 安装规则（每个目标装到哪、哪些文件集、哪个组件）
- `CMAKE_BUILD_TYPE` / 生成器 / 工具链信息

**对开发者的意义**：

1. **IDE 集成**：CLion、VS Code cmake-tools 扩展内部都用 file-api 来了解项目结构，而不是硬解析 `CMakeLists.txt`。你在 IDE 里 reload cmake 时，它就是在触发上述流程。
2. **自定义脚本**：可以写脚本在 CI 里解析 file-api 响应，自动生成目标依赖图、检查安装规则完整性、验证特定目标链接了特定库。
3. **clangd / ccls**：只看 `compile_commands.json` 的工具得到的是扁平的编译命令；用 file-api 的工具还能理解目标层次和依赖传播，补全更精准。

> cmake-file-api 的完整 JSON schema 与各 object kind 详见 [[42.Cmake/21 - cmake-file-api.md|第 21 章（cmake-file-api）]]。

## 18.4 组织大型项目

小项目一个 `CMakeLists.txt` 就够，但工程一旦变大——多个库、多个可执行、自定义模块、可选第三方依赖——就需要一套清晰的目录与文件组织约定。本节讲大型项目的标准骨架。

### 18.4.1 标准目录骨架

一个组织良好的中大型 CMake 项目，典型结构如下：

```
myproject/
├── CMakeLists.txt              # 顶层：project()、全局开关、add_subdirectory
├── CMakePresets.json           # 配置预设
├── cmake/                      # 自定义 CMake 模块与配置模板
│   ├── FindXXX.cmake           # 自写的查找模块（若需要）
│   ├── CompilerWarnings.cmake  # 公共 warning 设置
│   └── ProjectConfig.cmake.in  # find_package 配置文件模板
├── include/                    # 公共头（也可下沉到各子库目录里）
├── src/                        # 各库/可执行的子目录
│   ├── mathx/
│   │   └── CMakeLists.txt
│   └── app/
│       └── CMakeLists.txt
├── tests/                      # 测试
│   └── CMakeLists.txt
└── docs/
```

**顶层 `CMakeLists.txt` 的职责**：声明 `cmake_minimum_required` + `project()`、设置全局策略与开关、把 `cmake/` 加入 `CMAKE_MODULE_PATH`、用 `add_subdirectory()` 拉入各子目录。它本身**不直接定义 target**，只做编排：

```cmake
cmake_minimum_required(VERSION 3.21...4.3)
project(myproject VERSION 1.0.0 LANGUAGES CXX)

# 把自定义模块目录加入搜索路径
list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/cmake")

# 全局基线（仅顶层时生效，见下）
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_subdirectory(src/mathx)
add_subdirectory(src/app)
```

### 18.4.2 PROJECT_IS_TOP_LEVEL：仅顶层才启用测试/安装

一个良好的库应该能两种方式被使用：（1）作为独立项目单独构建；（2）被别的项目用 `add_subdirectory()` 或 `FetchContent` 嵌入。这两种场景下，"是否启用测试""是否生成安装规则"的期望不同——独立构建时希望测试开着，被嵌入时下游通常不想跑你的测试、也不想被你的 `install()` 规则污染。

CMake 3.21 引入了 `PROJECT_IS_TOP_LEVEL` 变量（由 `project()` 自动设置），完美解决这个问题：它在"本项目是顶层项目"时为真，被嵌入时为假。用它来守卫测试与安装：

```cmake
# 只有当本项目是顶层构建时，才默认启用测试
if(PROJECT_IS_TOP_LEVEL)
    include(CTest)              # 提供 BUILD_TESTING 选项，默认 ON
    if(BUILD_TESTING)
        add_subdirectory(tests)
    endif()
endif()

# 安装规则同理，可只在顶层启用，避免嵌入时污染下游的安装
if(PROJECT_IS_TOP_LEVEL)
    install(...)
endif()
```

### 18.4.3 BUILD_TESTING：标准化测试开关

不要自己发明测试开关（如 `MYPROJECT_ENABLE_TESTS`）。CMake 有约定俗成的标准开关 `BUILD_TESTING`，由 `include(CTest)` 模块引入（默认 `ON`）。用它的好处是统一：任何熟悉 CMake 的人都知道 `-DBUILD_TESTING=OFF` 能关掉测试，下游也能用同一个开关关掉你的测试。

```cmake
include(CTest)                 # 引入 BUILD_TESTING 选项（默认 ON）并 enable_testing()
if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

```bash
cmake -S . -B build -DBUILD_TESTING=OFF   # 一键关闭所有测试构建
```

### 18.4.4 公共 warning 载体：INTERFACE 库范式

18.1.9 提到"想给自己所有 target 统一加 warning，又不污染全局"。标准范式是建一个 `INTERFACE` 库当载体，把 warning flag 挂在它的 `INTERFACE` 上，然后让自己的每个 target 链接它：

```cmake
# cmake/CompilerWarnings.cmake
add_library(project_warnings INTERFACE)
target_compile_options(project_warnings INTERFACE
    $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra;-Wpedantic>
    $<$<CXX_COMPILER_ID:MSVC>:/W4>)

# 各 target 显式"链接"它来获得 warning（INTERFACE 库不产出二进制，只传播需求）
target_link_libraries(mathx PRIVATE project_warnings)
target_link_libraries(app   PRIVATE project_warnings)
```

这样 warning 只作用于显式链接它的自家 target，第三方依赖完全不受影响，且开关集中可控。

### 18.4.5 super-build：可选的"先拉依赖再建主体"模式

对于依赖关系复杂、需要把第三方依赖也纳入统一构建的项目，可以采用 super-build（超级构建）模式：用一个外层项目，先通过 `ExternalProject_Add()` 把各个依赖（甚至主项目自身）作为独立的"外部项目"下载、配置、构建、安装到一个公共前缀，再让主项目从那个前缀里 `find_package`。它和 `FetchContent`（把依赖源码直接并入同一次构建）是两条路线：

- **FetchContent**：依赖与主项目同一个 CMake 配置/构建过程，简单、IDE 友好，适合中小依赖。
- **super-build / ExternalProject**：每个依赖独立配置构建，隔离性强、能处理"依赖需要不同工具链/不同 CMake 版本"的复杂场景，但更重、调试更绕。

中小项目用 FetchContent 即可（本章实战就用它）；只有当依赖图复杂到 FetchContent 力不从心时，才上 super-build。两者细节见第 10 章。

## 18.5 加速构建

工程一大，构建变慢就成了切肤之痛。CMake 生态提供了一整套正交的加速手段，可以叠加使用。本节逐一介绍。

### 18.5.1 换生成器：用 Ninja

最立竿见影的一步：把默认的 Makefiles 换成 **Ninja**。Ninja 是专为速度设计的构建工具，依赖检查、增量构建、并行调度都比 Make 快得多，几乎没有理由不用：

```bash
cmake -S . -B build -G Ninja
cmake --build build
```

对多配置需求，还有 `Ninja Multi-Config` 生成器，一个构建目录支持 Debug/Release 同时存在（第 15 章详述）。

### 18.5.2 编译缓存：ccache / sccache

`ccache`（及其支持分布式/云缓存的同类 `sccache`）缓存编译结果，第二次编译同样的源文件直接命中缓存、跳过实际编译。CMake 通过 `CMAKE_<LANG>_COMPILER_LAUNCHER` 变量在编译器前面"包"一层启动器来接入它，无需改任何源码：

```bash
cmake -S . -B build \
    -DCMAKE_C_COMPILER_LAUNCHER=ccache \
    -DCMAKE_CXX_COMPILER_LAUNCHER=ccache
```

之后正常构建即可。clean build 后再 build，ccache 命中率高时能快几倍到十几倍。`sccache` 同理，把 `ccache` 换成 `sccache`。

### 18.5.3 Unity build：合并编译单元

Unity build（也叫 jumbo build）把多个 `.cpp` 拼进一个翻译单元一起编译，大幅减少头文件重复解析和编译进程启动开销，对头文件密集的项目提速明显。CMake 内置支持：

```bash
# 全局开启（给所有 target 启用）
cmake -S . -B build -DCMAKE_UNITY_BUILD=ON
```

或对单个 target 精细控制：

```cmake
set_target_properties(mathx PROPERTIES
    UNITY_BUILD ON
    UNITY_BUILD_BATCH_SIZE 8)   # 每 8 个源文件合并成一个 unity 文件
```

注意 Unity build 偶尔会暴露代码里的"坏味道"（如不同 `.cpp` 里有同名的匿名命名空间符号、`using namespace` 冲突），需要时可对个别文件用 `set_source_files_properties(... PROPERTIES SKIP_UNITY_BUILD_INCLUSION ON)` 排除。

### 18.5.4 预编译头：PCH

预编译头（PCH）把一组稳定、被大量包含的头（标准库、第三方大头如 `<vector>`、`fmt/fmt.h`）预先编译一次，后续编译单元直接复用，省掉重复解析。用 `target_precompile_headers()`：

```cmake
target_precompile_headers(mathx PRIVATE
    <vector>
    <string>
    <unordered_map>)
```

多个 target 可以用 `REUSE_FROM` 复用同一份 PCH，避免每个 target 各编一遍（第 14 章详述）：

```cmake
target_precompile_headers(app REUSE_FROM mathx)
```

### 18.5.5 并行构建：--parallel

最后，别忘了让构建本身跑满 CPU。`cmake --build` 加 `--parallel`（或 `-j`）开多任务并行：

```bash
cmake --build build --parallel              # 用所有可用核心
cmake --build build --parallel 8            # 指定 8 路并行
cmake --build build -j$(nproc)              # Linux 下按核心数
```

Ninja 默认就并行（无需 `-j`），但显式指定也无妨。这些加速手段彼此正交，实践中常一起上：**Ninja + ccache + PCH + `--parallel`**，组合拳下来大型项目的迭代构建时间往往能砍掉一大半。

## 18.6 压轴实战：完整工程

理论讲完，现在把前面所有知识点在一个**完整、可复现**的真实项目里跑通。我们要做的项目 `mathx` 包含：

- 一个库 `mathx`：有 `PUBLIC` 公共头、`PRIVATE` 内部实现、自动生成的导出头（控制符号可见性）。
- 一个可执行 `app`：链接 `mathx`。
- 用 **GoogleTest**（通过 `FetchContent` 拉取）写的单元测试，接入 **CTest**。
- 完整的 `install()` + 导出 `mathxConfig.cmake`，让别人 `find_package(mathx)` 后用 `mathx::mathx` 链接。
- **CPack** 打包成可分发的安装包。
- `CMakePresets.json`（debug/release + test + workflow）一键驱动。
- 从配置 → 构建 → 测试 → 安装 → 打包的完整命令序列与预期输出。

### 18.6.1 完整文件树

```
mathx/
├── CMakeLists.txt                      # 顶层
├── CMakePresets.json                   # 预设
├── cmake/
│   └── mathxConfig.cmake.in            # find_package 配置模板
├── include/
│   └── mathx/
│       └── mathx.h                     # 公共头
├── src/
│   ├── mathx.cpp                       # 库实现
│   └── internal/
│       └── detail.cpp                  # 内部实现（PRIVATE）
├── app/
│   └── main.cpp                        # 可执行入口
└── tests/
    ├── CMakeLists.txt
    └── test_mathx.cpp                  # GoogleTest 用例
```

### 18.6.2 源代码

先把 C++ 源码摆出来（极简，重点在 CMake）。

`include/mathx/mathx.h`（公共头，注意它要 `#include` 生成的导出头）：

```cpp
#pragma once
#include "mathx/mathx_export.h"   // 由 generate_export_header 生成

namespace mathx {
// MATHX_EXPORT 控制此符号在动态库中导出/导入
MATHX_EXPORT int add(int a, int b);
MATHX_EXPORT int mul(int a, int b);
}  // namespace mathx
```

`src/mathx.cpp`：

```cpp
#include "mathx/mathx.h"

namespace mathx {
int add(int a, int b) { return a + b; }
int mul(int a, int b) {
    int r = 0;
    for (int i = 0; i < b; ++i) r = add(r, a);  // 调用内部实现做演示
    return r;
}
}  // namespace mathx
```

`src/internal/detail.cpp`（内部翻译单元，不对外暴露）：

```cpp
// 内部实现细节，可放仅库内使用的辅助函数；此处留空演示 PRIVATE 源文件归属
namespace mathx::detail {}
```

`app/main.cpp`：

```cpp
#include <iostream>
#include "mathx/mathx.h"

int main() {
    std::cout << "3 + 4 = " << mathx::add(3, 4) << "\n";
    std::cout << "3 * 4 = " << mathx::mul(3, 4) << "\n";
    return 0;
}
```

`tests/test_mathx.cpp`：

```cpp
#include <gtest/gtest.h>
#include "mathx/mathx.h"

TEST(MathxTest, Add) {
    EXPECT_EQ(mathx::add(2, 3), 5);
    EXPECT_EQ(mathx::add(-1, 1), 0);
}

TEST(MathxTest, Mul) {
    EXPECT_EQ(mathx::mul(3, 4), 12);
    EXPECT_EQ(mathx::mul(0, 99), 0);
}
```

### 18.6.3 顶层 CMakeLists.txt（全文）

这是工程的核心，逐段都有注释。它综合了本章几乎所有要点：区间 `cmake_minimum_required`、`PROJECT_IS_TOP_LEVEL` 守卫、`GenerateExportHeader`、`FILE_SET HEADERS` 管理公共头安装、`GNUInstallDirs`、命名空间导出、生成 `mathxConfig.cmake`、`FetchContent` + GoogleTest、`CTest`、`CPack`。

```cmake
cmake_minimum_required(VERSION 3.26...4.3)
project(mathx
    VERSION 1.0.0
    DESCRIPTION "A tiny modern-CMake demo math library"
    LANGUAGES CXX)

# ── 全局基线：仅顶层构建时设置，避免被嵌入时覆盖下游 ──────────────
if(PROJECT_IS_TOP_LEVEL)
    set(CMAKE_CXX_STANDARD 20)
    set(CMAKE_CXX_STANDARD_REQUIRED ON)
    set(CMAKE_CXX_EXTENSIONS OFF)
    # 默认隐藏符号，由导出头按需放出（配合 generate_export_header）
    set(CMAKE_CXX_VISIBILITY_PRESET hidden)
    set(CMAKE_VISIBILITY_INLINES_HIDDEN ON)
endif()

include(GNUInstallDirs)            # CMAKE_INSTALL_BINDIR / LIBDIR / INCLUDEDIR ...
include(GenerateExportHeader)      # generate_export_header()
include(CMakePackageConfigHelpers) # configure_package_config_file() 等

# ── 库 mathx ──────────────────────────────────────────────────
add_library(mathx
    src/mathx.cpp
    src/internal/detail.cpp)       # 显式列源文件，不用 file(GLOB)

add_library(mathx::mathx ALIAS mathx)  # 构建树内也能用命名空间名引用，写法与下游一致

# 生成导出头：定义 MATHX_EXPORT 宏，写到构建目录
generate_export_header(mathx
    EXPORT_FILE_NAME ${CMAKE_CURRENT_BINARY_DIR}/include/mathx/mathx_export.h)

# 公共头用 FILE_SET HEADERS 管理：编译时可见、安装时自动装到 INCLUDEDIR
target_sources(mathx
    PUBLIC
        FILE_SET HEADERS
            BASE_DIRS ${CMAKE_CURRENT_SOURCE_DIR}/include
            FILES ${CMAKE_CURRENT_SOURCE_DIR}/include/mathx/mathx.h
        FILE_SET gen_headers TYPE HEADERS
            BASE_DIRS ${CMAKE_CURRENT_BINARY_DIR}/include
            FILES ${CMAKE_CURRENT_BINARY_DIR}/include/mathx/mathx_export.h)

# 标准要求：用元特性，沿 PUBLIC 传播给下游
target_compile_features(mathx PUBLIC cxx_std_20)

# ── 可执行 app ────────────────────────────────────────────────
add_executable(app app/main.cpp)
target_link_libraries(app PRIVATE mathx::mathx)  # 带命名空间，写法与下游一致

# ── 安装与导出（仅顶层）──────────────────────────────────────
if(PROJECT_IS_TOP_LEVEL)
    # 1) 安装 target，并把它收进导出集 mathxTargets
    install(TARGETS mathx app
        EXPORT mathxTargets
        RUNTIME  DESTINATION ${CMAKE_INSTALL_BINDIR}
        LIBRARY  DESTINATION ${CMAKE_INSTALL_LIBDIR}
        ARCHIVE  DESTINATION ${CMAKE_INSTALL_LIBDIR}
        FILE_SET HEADERS                              # 装公共头
        FILE_SET gen_headers)                         # 装生成的导出头

    # 2) 安装导出集为 mathxTargets.cmake，带命名空间 mathx::
    install(EXPORT mathxTargets
        FILE mathxTargets.cmake
        NAMESPACE mathx::
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/mathx)

    # 3) 由模板生成 mathxConfig.cmake（供 find_package(mathx) 使用）
    configure_package_config_file(
        ${CMAKE_CURRENT_SOURCE_DIR}/cmake/mathxConfig.cmake.in
        ${CMAKE_CURRENT_BINARY_DIR}/mathxConfig.cmake
        INSTALL_DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/mathx)

    # 4) 生成版本文件，支持 find_package(mathx 1.0 ...) 的版本检查
    write_basic_package_version_file(
        ${CMAKE_CURRENT_BINARY_DIR}/mathxConfigVersion.cmake
        VERSION ${PROJECT_VERSION}
        COMPATIBILITY SameMajorVersion)

    # 5) 安装这两个 config 文件
    install(FILES
        ${CMAKE_CURRENT_BINARY_DIR}/mathxConfig.cmake
        ${CMAKE_CURRENT_BINARY_DIR}/mathxConfigVersion.cmake
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/mathx)
endif()

# ── 测试（仅顶层 + BUILD_TESTING）─────────────────────────────
if(PROJECT_IS_TOP_LEVEL)
    include(CTest)                 # 引入 BUILD_TESTING（默认 ON）并 enable_testing()
    if(BUILD_TESTING)
        add_subdirectory(tests)
    endif()
endif()

# ── CPack 打包（仅顶层）──────────────────────────────────────
if(PROJECT_IS_TOP_LEVEL)
    set(CPACK_PACKAGE_NAME "mathx")
    set(CPACK_PACKAGE_VENDOR "Example")
    set(CPACK_PACKAGE_VERSION ${PROJECT_VERSION})
    set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "${PROJECT_DESCRIPTION}")
    # 生成器：跨平台压缩包；Linux 上也可加 DEB/RPM，Windows 上加 NSIS/ZIP
    set(CPACK_GENERATOR "TGZ;ZIP")
    include(CPack)                 # 必须放在所有 CPACK_* 设置之后
endif()
```

### 18.6.4 tests/CMakeLists.txt（全文，FetchContent + GoogleTest）

```cmake
include(FetchContent)

# 声明依赖：从官方仓库拉取指定 tag 的 GoogleTest
FetchContent_Declare(
    googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG v1.15.2                 # 固定到具体版本，保证可复现
    GIT_SHALLOW TRUE)

# Windows 上让 gtest 用动态运行时，避免与主项目运行时不一致
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)

FetchContent_MakeAvailable(googletest)   # 下载并 add_subdirectory 进当前构建

# 定义测试可执行
add_executable(test_mathx test_mathx.cpp)
target_link_libraries(test_mathx
    PRIVATE
        mathx::mathx
        GTest::gtest_main)          # gtest_main 自带 main()

# 用 GoogleTest 模块自动发现每个 TEST() 并注册成独立的 CTest 用例
include(GoogleTest)
gtest_discover_tests(test_mathx)
```

### 18.6.5 cmake/mathxConfig.cmake.in（全文）

这个模板被 `configure_package_config_file()` 处理后生成 `mathxConfig.cmake`，是下游 `find_package(mathx)` 时实际加载的入口文件。它负责把导出的 target 文件 `include` 进来：

```cmake
@PACKAGE_INIT@

# 加载导出的 target 定义（提供 mathx::mathx）
include("${CMAKE_CURRENT_LIST_DIR}/mathxTargets.cmake")

check_required_components(mathx)
```

`@PACKAGE_INIT@` 是 `configure_package_config_file()` 注入的样板，负责设置相对路径解析等。下游使用时只需：

```cmake
find_package(mathx 1.0 REQUIRED)
target_link_libraries(myapp PRIVATE mathx::mathx)   # 直接拿到带命名空间的 import target
```

### 18.6.6 CMakePresets.json（全文，schema v11）

> 注意：CMake **4.3.4** 支持 presets **schema 版本 11**。这里用相对保守的 version 11，可享受最新能力；如需兼容更老的 CMake，可调低 version 并相应裁剪字段。

```json
{
  "version": 11,
  "cmakeMinimumRequired": { "major": 3, "minor": 26, "patch": 0 },
  "configurePresets": [
    {
      "name": "base",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": {
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
    {
      "name": "debug",
      "displayName": "Debug",
      "inherits": "base",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "BUILD_TESTING": "ON"
      }
    },
    {
      "name": "release",
      "displayName": "Release",
      "inherits": "base",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release",
```

### 18.6.7 完整命令序列与预期结果

万事俱备。下面是从零跑通整条流水线的命令，每步附预期输出。

**第 1 步：配置（Release）**

```bash
cmake --preset release
```

预期：CMake 配置成功，期间 `FetchContent` 会克隆 GoogleTest（首次较慢），末尾出现：

```
-- Configuring done
-- Generating done
-- Build files have been written to: .../mathx/build/release
```

**第 2 步：构建**

```bash
cmake --build --preset release
```

预期：编译 `mathx` 库、`app` 可执行、`test_mathx` 测试可执行以及 GoogleTest，全部成功，无警告（隐藏可见性 + 标准设置都已就绪）。

**第 3 步：运行测试**

```bash
ctest --preset release
```

预期：`gtest_discover_tests` 把 `MathxTest.Add`、`MathxTest.Mul` 注册成了独立用例，CTest 全绿：

```
    Start 1: MathxTest.Add
1/2 Test #1: MathxTest.Add ....................   Passed    0.01 sec
    Start 2: MathxTest.Mul
2/2 Test #2: MathxTest.Mul ....................   Passed    0.01 sec

100% tests passed, 0 tests failed out of 2
```

也可以直接跑 `app` 验证：

```bash
./build/release/app
# 3 + 4 = 7
# 3 * 4 = 12
```

**第 4 步：安装**

```bash
cmake --install build/release
```

预期：把库、可执行、公共头（含生成的 `mathx_export.h`）、`mathxConfig.cmake`/`mathxConfigVersion.cmake`/`mathxTargets.cmake` 安装到 `stage/`（即 preset 里设的 `CMAKE_INSTALL_PREFIX`）：

```
-- Installing: .../stage/lib/libmathx.a
-- Installing: .../stage/bin/app
-- Installing: .../stage/include/mathx/mathx.h
-- Installing: .../stage/include/mathx/mathx_export.h
-- Installing: .../stage/lib/cmake/mathx/mathxConfig.cmake
-- Installing: .../stage/lib/cmake/mathx/mathxTargets.cmake
...
```

此时别的项目就能 `find_package(mathx 1.0 REQUIRED PATHS .../stage)` 并 `target_link_libraries(... mathx::mathx)` 复用它了。

**第 5 步：打包**

```bash
cpack --preset release
# 或不用 preset： cd build/release && cpack
```

预期：在构建目录生成可分发的安装包：

```
CPack: - package: .../mathx-1.0.0-Linux.tar.gz generated.
CPack: - package: .../mathx-1.0.0-Linux.zip generated.
```

**一键全流程：workflow**

上面 5 步里"配置→构建→测试→打包"可以用一条 workflow 命令串起来，这是 Presets 工作流的精髓：

```bash
cmake --workflow --preset release
```

预期：CMake 依次执行 workflow preset 里定义的 configure → build → test → package 四步，任何一步失败则中止。一条命令完成从源码到安装包的全过程——这正是现代 CMake "把复杂构建流程固化成可复现一键操作"的终极体现。

## 本章小结

本章是全教程的收官章，做了三件事：把现代 CMake 的最佳实践收拢成清单、把调试能力系统化、把全部知识点在一个完整工程里跑通。

**最佳实践（道）**：现代 CMake 的核心是"以 target 为中心、用依赖描述需求、让需求传播"。十二条军规归纳为——用 `target_*` 不用全局命令；显式标注 `PUBLIC`/`PRIVATE`/`INTERFACE`；导出加命名空间 `Foo::`；安装用 `GNUInstallDirs`；`cmake_minimum_required` 用区间 `<min>...<max>`；显式列源文件不用 `file(GLOB)`；用 `target_compile_features`/`CXX_STANDARD` 不手写 `-std=`；不污染 `CMAKE_CXX_FLAGS`；永远 out-of-source；用 Presets 固化配置；用 `PROJECT_IS_TOP_LEVEL` 守卫测试/安装；用 `BUILD_TESTING` 标准化开关。每条都有对应的反模式，识别并铲除 `file(GLOB)`、全局 `include_directories`、手拼 flag、`link_libraries`、in-source、滥用 `macro`、硬编码路径、`target_link_libraries` 不写关键字，是迁移到现代 CMake 的第一步。

**调试（术）**：CMake 配置不是黑盒。`message` 分级 + `--log-level`/`CMAKE_MESSAGE_CONTEXT` 控制输出；`--trace-expand`/`--trace-source`/`--trace-redirect` 逐行追踪并展开变量；`--debug-find`/`--debug-find-pkg`/`--debug-find-var` 专治 `find_package` 找不到；`cmake -LAH` 看缓存、`--system-information` dump 环境；`CMakePrintHelpers` 优雅打印变量与属性；`variable_watch` 揪出谁改了变量；`--build -v`/`CMAKE_VERBOSE_MAKEFILE` 看真实编译命令；`CMakeConfigureLog.yaml`（3.26+）与 `message(CONFIGURE_LOG ...)` 记录 try_compile/check_* 的全部细节。

**实战（器）**：一个完整工程把库 + 可执行 + GoogleTest 测试 + 安装导出 + CPack 打包 + Presets 工作流全部串通，给出了每个 `CMakeLists.txt` 全文和从配置到打包的完整命令序列。其中 `generate_export_header` + `FILE_SET HEADERS` 管理公共头与符号可见性、命名空间导出让下游 `find_package` 后用 `mathx::mathx`、`FetchContent` 拉 GoogleTest + `gtest_discover_tests` 自动注册用例、`cmake --workflow --preset release` 一键跑完全流程——这些正是现代 CMake 在真实项目中的标准姿势。

**现代 CMake 心法**，最后再凝练一次：

1. **一切皆 target，需求随依赖传播。** 不要用全局状态，用 `target_*` + 三种可见性关键字。
2. **声明意图，而非堆砌命令。** 用 `target_compile_features` 声明"我要 C++20"，让 CMake 翻译成正确 flag；用 import target 表达依赖，让 CMake 处理路径与传递。
3. **早失败、清晰失败。** 命名空间 target、`STANDARD_REQUIRED ON`、`cmake_minimum_required` 区间、in-source 防呆——都在把错误尽量提前、说清楚。
4. **可复现高于一切。** 显式列源文件、固定依赖版本、用 Presets 固化配置、out-of-source——让任何人在任何机器上跑出同样结果。
5. **配置过程是可观测的。** 卡住了就开 trace、开 debug-find、看 ConfigureLog，不要靠猜。

**进一步学习资源**：

- **官方文档**：<https://cmake.org/cmake/help/latest/> 是最权威、最及时的参考，按 `cmake-commands(7)`、`cmake-variables(7)`、`cmake-properties(7)`、`cmake-generator-expressions(7)` 等手册分类查阅。
- **内置帮助**：`cmake --help`、`cmake --help-command <cmd>`、`cmake --help-variable <var>`、`cmake --help-module <mod>`、`cmake --help-property <prop>` 可在命令行直接查任意命令/变量/模块/属性的文档，无需联网。
- **官方教程**：官方 *CMake Tutorial*（文档站内）从零搭一个项目，循序渐进。
- **《Professional CMake: A Practical Guide》**（Craig Scott 著，持续更新）：公认最全面、最现代的 CMake 进阶书籍，由 CMake 核心维护者撰写，覆盖本教程未及的大量工程细节。
