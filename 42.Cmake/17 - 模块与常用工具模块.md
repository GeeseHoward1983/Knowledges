# 第 17 章 · 模块与常用工具模块

> 基准版本：CMake 4.3.4

CMake 自带了上百个 **模块（modules）**——它们是后缀为 `.cmake` 的脚本片段，用 `include()` 加载后，会向当前作用域注入一批可复用的命令、宏与变量。前面章节里反复出现的 `GNUInstallDirs`、`FetchContent`、`CMakePackageConfigHelpers` 都是模块。本章把"模块机制"本身讲透：模块如何被查找与加载，`cmake -P` 脚本模式和 `cmake -E` 跨平台工具如何脱离构建系统独立运行，以及最常用的一批内置工具模块（特性探测、导出头生成、特性汇总、调试打印……）逐个用法。最后讲如何把你自己的可复用逻辑封装成模块，并简要介绍 `cmake_language(DEFER)` 延迟调用。

> 阅读提示：本章是"工具箱总览"。其中与安装、依赖、测试、打包强相关的模块（`GNUInstallDirs`、`FetchContent`、`GoogleTest` 等）在本章只给"是什么 + 一句话用法"，深入用法见对应章节的交叉引用。

## 17.1 模块机制：`include()` 与 `CMAKE_MODULE_PATH`

### 17.1.1 模块是什么

一个 CMake 模块就是一个 `.cmake` 文件，里面通常定义 `function()` / `macro()`、设置变量、或执行一段探测逻辑。模块**不会自动生效**，必须显式加载：

```cmake
include(<module>)            # 按模块名加载（不带 .cmake 后缀，不带路径）
include(<file>.cmake)        # 也可以直接给一个文件路径
```

两种调用形式由参数里有没有 `/` 或 `.cmake` 后缀来区分：

- `include(GNUInstallDirs)`——**按模块名**加载。CMake 在「模块搜索路径」里查找名为 `GNUInstallDirs.cmake` 的文件。
- `include(${CMAKE_CURRENT_LIST_DIR}/cmake/MyHelpers.cmake)`——**按文件路径**加载，直接指向某个文件。

`include()` 的完整签名：

```cmake
include(<file|module>
        [OPTIONAL]              # 找不到也不报错（默认找不到会 FATAL_ERROR）
        [RESULT_VARIABLE <var>] # 把实际加载到的完整路径写入 <var>，未找到则为 NOTFOUND
        [NO_POLICY_SCOPE])      # 不为被包含文件开启独立的策略作用域
```

> ⚠️ `include()` **不**建立新的变量作用域：被包含文件里 `set()` 的普通变量，会直接落在调用处的作用域里。这点和 `add_subdirectory()` 截然不同——后者会进入子目录作用域。正因如此，模块里定义的 `function`/`macro` 加载后即可在当前文件直接调用。

### 17.1.2 模块搜索路径

`include(<模块名>)` 与 `find_package(<Pkg> MODULE)` 查找 `.cmake` 文件时，**搜索顺序**为：

1. **`CMAKE_MODULE_PATH`** 列出的目录（按列表顺序，先列的优先）——这是你放置自定义模块、或覆盖内置模块的地方。
2. CMake 安装目录下的 **内置模块目录**（见下）。

```cmake
# 把项目的 cmake/ 目录加进模块搜索路径（追加而非覆盖，避免破坏父项目的设置）
list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/cmake")

include(MyHelpers)   # 现在能找到 cmake/MyHelpers.cmake 了
```

> 实践建议：用 `list(APPEND ...)` 而不是 `set(CMAKE_MODULE_PATH ...)`，因为你的项目可能作为子项目被 `add_subdirectory`，直接覆盖会丢掉上层已设的路径。

### 17.1.3 内置模块在哪里

CMake 内置模块随发行版一起安装在 `<CMake 安装前缀>/share/cmake-<主.次>/Modules/` 目录下，例如：

```bash
# Linux 典型
/usr/share/cmake-4.3/Modules/GNUInstallDirs.cmake
# Windows 典型
C:/Program Files/CMake/share/cmake-4.3/Modules/GenerateExportHeader.cmake
```

想知道当前 CMake 自带了哪些模块、各自做什么，**最权威的清单是官方手册 `cmake-modules(7)`**：

```bash
cmake --help-module-list          # 列出所有内置模块名
cmake --help-module GenerateExportHeader   # 查看单个模块的完整文档
man cmake-modules                 # Unix 上的离线手册页
```

> 直接阅读 `Modules/` 目录下的 `.cmake` 源码，也是理解模块行为最可靠的方式——内置模块本身就是用 CMake 语言写的。

### 17.1.4 两类模块：utility modules vs find modules

CMake 把内置模块分成两大类，命名与用途都不同：

| 类别 | 命名规律 | 加载方式 | 作用 |
| --- | --- | --- | --- |
| **工具模块（utility modules）** | 任意名字，如 `GNUInstallDirs`、`CheckTypeSize`、`GenerateExportHeader` | `include(<名字>)` | 提供可复用的命令/宏/变量，封装通用功能 |
| **查找模块（find modules）** | 必须叫 `Find<PackageName>.cmake` | 由 `find_package(<Pkg> MODULE)` 间接加载（也可手动 `include`，但不推荐） | 定位某个第三方依赖，导出 `<Pkg>_FOUND`、导入目标等 |

本章聚焦 **工具模块**；查找模块的编写与 `find_package` 的 MODULE/CONFIG 两种模式见 **第 10 章**。

## 17.2 `cmake -P`：脚本模式

`cmake -P <script>.cmake` 让 CMake **像解释器一样直接运行一个 `.cmake` 脚本**——没有项目、没有 `CMakeLists.txt`、不生成构建系统、不写缓存。它非常适合把跨平台的"小自动化"用 CMake 语言写出来，从而在任何装了 CMake 的机器上一致运行（无需依赖 bash 或 PowerShell）。

```bash
cmake -P do_something.cmake                 # 运行脚本
cmake -P do_something.cmake arg1 arg2 ...    # 还可以传参
```

### 17.2.1 脚本模式下的专用变量

在 `-P` 模式中，CMake 设置了几个普通配置时不存在的变量，用来读取命令行：

| 变量 | 含义 |
| --- | --- |
| `CMAKE_ARGC` | 命令行参数的**总个数**（含 `cmake` 本身及其后的全部 token） |
| `CMAKE_ARGV0`, `CMAKE_ARGV1`, ... | 各个参数的值，`ARGV0` 是 `cmake` 可执行文件本身 |
| `CMAKE_SCRIPT_MODE_FILE` | 当前正在执行的脚本文件的**完整路径**；配置 `CMakeLists.txt` 时此变量**不会被设置**——可据此判断"我是否运行在脚本模式" |

> ⚠️ 参数的下标有一段"固定前缀"。`cmake -P script.cmake foo bar` 实际被解析为：`ARGV0=cmake`、`ARGV1=-P`、`ARGV2=script.cmake`、`ARGV3=foo`、`ARGV4=bar`。也就是说**用户传的第一个参数从 `CMAKE_ARGV3` 开始**。稳妥的做法是从 `CMAKE_ARGC` 倒推或循环遍历。

一个读取并打印用户参数的脚本：

```cmake
# args.cmake —— 用 cmake -P args.cmake a b c 运行
message(STATUS "脚本路径: ${CMAKE_SCRIPT_MODE_FILE}")
message(STATUS "参数总数 CMAKE_ARGC = ${CMAKE_ARGC}")

# 用户参数从 ARGV3 起；这里把它们收集成列表
set(user_args "")
math(EXPR last "${CMAKE_ARGC} - 1")
foreach(i RANGE 3 ${last})
  list(APPEND user_args "${CMAKE_ARGV${i}}")
endforeach()
message(STATUS "用户参数: ${user_args}")
```

```bash
$ cmake -P args.cmake hello world 42
-- 脚本路径: /home/me/args.cmake
-- 参数总数 CMAKE_ARGC = 6
-- 用户参数: hello;world;42
```

> 提示：从 CMake 3.30+ 起，命令行还支持 `cmake -P <script> -- <args...>`，用 `--` 显式分隔脚本参数。`--` 之后的参数也会原样进入 `CMAKE_ARGV*` 序列。

### 17.2.2 脚本模式能用什么、不能用什么

- **能用**：所有"脚本类"命令——`file()`、`string()`、`list()`、`execute_process()`、`message()`、`configure_file()`、`math()`、`include()` 等，以及大多数工具模块（凡是不依赖目标/构建系统的）。
- **不能用**：任何"项目/构建"语义命令——`project()`、`add_executable()`、`add_library()`、`target_*()`、`install()` 在脚本模式下要么报错要么无意义；`find_package()` 部分可用但行为受限。

### 17.2.3 典型用途

- 构建过程中的**自定义步骤**：在 `add_custom_command`/`add_custom_target` 里 `COMMAND ${CMAKE_COMMAND} -P generate_version.cmake` 生成版本头、时间戳、清单文件。
- **跨平台脚手架**：替代写两套（`.sh` + `.bat`）的清理/打包/部署脚本。
- **配置时计算**：复杂的字符串处理、文件批量改名，封装成脚本反复调用。

```cmake
# CMakeLists.txt 里在构建时调用一个生成脚本，平台无关
add_custom_command(
  OUTPUT  ${CMAKE_CURRENT_BINARY_DIR}/version.h
  COMMAND ${CMAKE_COMMAND}
          -DOUT=${CMAKE_CURRENT_BINARY_DIR}/version.h
          -DVER=${PROJECT_VERSION}
          -P ${CMAKE_CURRENT_SOURCE_DIR}/cmake/gen_version.cmake
  COMMENT "生成 version.h"
)
```

> 注意上例用 `-D<var>=<value>` 给脚本"传参"：在 `-P` 之前用 `-D` 定义的缓存变量，在脚本里可以直接读到。这是比 `CMAKE_ARGV*` 更可读的传参方式。

## 17.3 `cmake -E`：命令行工具模式

`cmake -E <command> [args]` 提供一组**与平台无关的基础命令**，主要用于在 `add_custom_command`/`add_custom_target` 里写出"在 Windows / Linux / macOS 上行为一致"的构建步骤——因为不能假设目标机上有 `cp`、`rm`、`tar` 等 Unix 工具。

查看完整子命令清单：

```bash
cmake -E help        # 列出当前版本支持的所有 -E 子命令
```

### 17.3.1 常用子命令一览

| 子命令 | 作用 | 备注 / 版本 |
| --- | --- | --- |
| `copy <f>... <dest>` | 复制一个或多个文件到目标 | 多文件时 `<dest>` 必须是已存在的目录 |
| `copy_if_different <f>... <dest>` | 仅当内容不同才复制 | 减少无谓的重新构建触发 |
| `copy_directory <dir>... <dest>` | 递归复制目录内容 | 复制的是"内容"，不含顶层目录名本身 |
| `copy_if_newer <f>... <dest>` | 按时间戳决定是否复制（比比对内容更快） | **3.31+ / 4.x** |
| `copy_directory_if_newer <dir>... <dest>` | 目录版的按时间戳复制 | **3.31+ / 4.x** |
| `make_directory <dir>...` | 创建目录（含中间层级，已存在不报错） | 等价 `mkdir -p` |
| `rm [-rRf] <path>...` | 删除文件/目录；`-r` 递归、`-f` 忽略不存在 | **3.17+**，取代旧的 `remove`/`remove_directory` |
| `remove [-f] <file>...` | 删除文件（旧命令，仅文件） | 已弃用，新代码用 `rm` |
| `remove_directory <dir>...` | 删除目录（旧命令） | 已弃用，新代码用 `rm -r` |
| `rename <old> <new>` | 重命名/移动文件或目录 | |
| `echo [<string>...]` | 打印参数并换行 | |
| `echo_append [<string>...]` | 打印参数但**不**换行 | |
| `env [选项] <cmd> [args...]` | 在修改后的环境变量下运行子命令 | 见下 |
| `tar [cxt][zjJv][f] <archive> [files]...` | 创建/解压/列出归档（tar、zip 等） | `--format=<gnutar\|pax\|paxr\|zip>` |
| `cat [--] <file>...` | 把多个文件内容拼接输出到 stdout | **3.18+**；`-` 表示读 stdin（3.24+） |
| `compare_files [--ignore-eol] <f1> <f2>` | 比较两文件是否相同；不同则返回非 0 | `--ignore-eol` 忽略行尾差异 |
| `create_symlink <old> <new>` | 创建符号链接 | Windows 需要相应权限 |
| `create_hardlink <old> <new>` | 创建硬链接 | **3.19+** |
| `true` | 什么都不做，返回退出码 0 | |
| `false` | 什么都不做，返回退出码 1 | |
| `sleep <秒数>...` | 睡眠指定秒数 | |
| `chdir <dir> <cmd> [args]...` | 切到 `<dir>` 后运行命令 | |
| `time <cmd> [args]...` | 运行命令并计时（打印耗时） | |
| `touch <file>...` / `touch_nocreate <file>...` | 更新时间戳 / 仅当文件存在时更新 | |
| `md5sum`/`sha1sum`/`sha256sum`/... `<file>...` | 计算并打印校验和 | |
| `capabilities` | 以 JSON 输出本 cmake 的能力（生成器等） | 供工具集成用 |

> `copy` 与 `copy_if_different` 都支持**多源文件**（CMake 3.5+），此时末参数必须是一个**已存在的目录**。若目标目录可能不存在，先 `cmake -E make_directory`。

### 17.3.2 `cmake -E env`：可控环境下运行命令

```bash
# 语法
cmake -E env [--unset=NAME]... [--modify ENVIRONMENT_MODIFICATION]... [NAME=VALUE]... <command> [args]...
```

- `NAME=VALUE`：为子命令设置环境变量。
- `--unset=NAME`：删除某个环境变量。
- `--modify PATH=path_list_append:/opt/bin`：对**列表型**环境变量做追加/前置等操作（`path_list_append` / `path_list_prepend` 等，3.25+）。

```bash
cmake -E env CC=clang CXX=clang++ cmake -S . -B build
cmake -E env --unset=LD_LIBRARY_PATH ./my_test
```

### 17.3.3 在自定义命令里使用 `-E`

`-E` 模式最大的价值是配合 `${CMAKE_COMMAND}` 写跨平台构建步骤：

```cmake
# 构建后把产物和资源拷到 dist/，全程不依赖系统 shell
add_custom_command(TARGET app POST_BUILD
  COMMAND ${CMAKE_COMMAND} -E make_directory   $<TARGET_FILE_DIR:app>/dist
  COMMAND ${CMAKE_COMMAND} -E copy_if_different $<TARGET_FILE:app>
                                                $<TARGET_FILE_DIR:app>/dist
  COMMAND ${CMAKE_COMMAND} -E copy_directory    ${CMAKE_SOURCE_DIR}/assets
                                                $<TARGET_FILE_DIR:app>/dist/assets
  COMMENT "组装 dist 目录"
  VERBATIM)
```

> 始终用 `${CMAKE_COMMAND}` 而不是字面量 `cmake`，确保用的是当前正在运行的那一个 CMake。

## 17.4 特性探测模块（Check\* 系列）

这是工具模块里最大的一族：在配置阶段**真正编译/链接/运行一小段探针代码**，据此判断"当前编译器/系统是否支持某语言特性、某头文件、某符号、某函数、某类型、某编译选项"，结果写入一个缓存变量，供 `configure_file`/`target_compile_definitions` 使用。它们是写可移植 C/C++ 项目的基石。

### 17.4.1 Check\* 模块速查表

| 模块 | 核心命令 | 探测内容 |
| --- | --- | --- |
| `CheckCXXSourceCompiles` | `check_cxx_source_compiles(<code> <var>)` | 一段 C++ 源码能否**编译**通过 |
| `CheckCSourceCompiles` | `check_c_source_compiles(<code> <var>)` | 一段 C 源码能否编译通过 |
| `CheckCXXSourceRuns` | `check_cxx_source_runs(<code> <var>)` | C++ 源码能否编译、链接并**成功运行**（退出码 0） |
| `CheckCSourceRuns` | `check_c_source_runs(<code> <var>)` | C 源码能否编译链接并运行 |
| `CheckIncludeFile` | `check_include_file(<header> <var> [flags])` | 某 **C** 头文件是否存在且可包含 |
| `CheckIncludeFileCXX` | `check_include_file_cxx(<header> <var> [flags])` | 某 **C++** 头文件是否可包含 |
| `CheckIncludeFiles` | `check_include_files("<h1>;<h2>" <var> [LANGUAGE <C\|CXX>])` | 一组头文件**按顺序一起**是否可包含 |
| `CheckSymbolExists` | `check_symbol_exists(<symbol> "<headers>" <var>)` | 某符号（宏/函数/全局量）在给定头文件中是否可见（**C** 语境） |
| `CheckCXXSymbolExists` | `check_cxx_symbol_exists(<symbol> "<headers>" <var>)` | 同上，但用 **C++** 编译器，可查 C++ 重载/模板符号 |
| `CheckFunctionExists` | `check_function_exists(<func> <var>)` | 某函数能否被**链接**到（不查头文件声明） |
| `CheckLibraryExists` | `check_library_exists(<lib> <func> <location> <var>)` | 链接 `<lib>` 后某函数是否可用 |
| `CheckCXXCompilerFlag` | `check_cxx_compiler_flag(<flag> <var>)` | C++ 编译器是否接受某编译选项 |
| `CheckCCompilerFlag` | `check_c_compiler_flag(<flag> <var>)` | C 编译器是否接受某编译选项 |
| `CheckLinkerFlag` | `check_linker_flag(<lang> <flag> <var>)` | 链接器是否接受某选项（3.18+） |
| `CheckTypeSize` | `check_type_size(<type> <var> [LANGUAGE <C\|CXX>])` | 某类型是否存在及其 `sizeof` 字节数 |
| `CheckStructHasMember` | `check_struct_has_member(<struct> <member> "<headers>" <var>)` | 结构体是否含某成员 |
| `CheckPrototypeDefinition` | `check_prototype_definition(...)` | 函数原型是否与给定签名一致 |

> 命名约定：`check_*` 命令把结果写到一个**缓存布尔/字符串变量**里。该变量是带缓存的，意味着**只探测一次**；改了探测条件却复用了旧缓存，会得到陈旧结果——这正是下一节 `CMakePushCheckState` 与"换名/清缓存"重要的原因。

### 17.4.2 影响探测的 `CMAKE_REQUIRED_*` 变量

几乎所有 Check\* 命令都会读取下面这组变量，用来给探针编译/链接配置环境。**它们不会自动清理，会"污染"后续探测**：

| 变量 | 作用 |
| --- | --- |
| `CMAKE_REQUIRED_FLAGS` | 附加给探针的编译选项（字符串，空格分隔） |
| `CMAKE_REQUIRED_DEFINITIONS` | 附加的预处理宏定义，形如 `-DFOO=1`（列表） |
| `CMAKE_REQUIRED_INCLUDES` | 附加的头文件搜索路径（列表） |
| `CMAKE_REQUIRED_LINK_OPTIONS` | 附加的链接选项（列表，3.14+） |
| `CMAKE_REQUIRED_LIBRARIES` | 探针链接时附加的库（列表，可填导入目标名） |
| `CMAKE_REQUIRED_LINK_DIRECTORIES` | 附加的库搜索路径（列表，3.31+） |
| `CMAKE_REQUIRED_QUIET` | 设为真则不打印探测过程的 `--` 状态行 |

### 17.4.3 例子：探测源码编译

```cmake
include(CheckCXXSourceCompiles)

check_cxx_source_compiles("
  #include <version>
  int main() {
  #if __cpp_lib_format >= 201907L
    return 0;
  #else
    #error no <format>
  #endif
  }
" HAVE_STD_FORMAT)

if(HAVE_STD_FORMAT)
  target_compile_definitions(app PRIVATE USE_STD_FORMAT)
endif()
```

### 17.4.4 例子：头文件 / 符号 / 函数 / 库

```cmake
include(CheckIncludeFiles)
include(CheckSymbolExists)
include(CheckFunctionExists)
include(CheckLibraryExists)

# 一组头文件（按顺序，前者可能是后者的前置依赖）
check_include_files("sys/types.h;sys/stat.h" HAVE_SYS_STAT_H)

# 符号：宏 SEEK_SET 与函数 fopen 是否在 stdio.h 中可见
check_symbol_exists(SEEK_SET "stdio.h" HAVE_SEEK_SET)
check_symbol_exists(fopen    "stdio.h" HAVE_FOPEN)

# 函数能否被链接（不查头文件）
check_function_exists(strdup HAVE_STRDUP)

# 链接 m 库后 pow 是否可用，结果存入 HAVE_LIBM
check_library_exists(m pow "" HAVE_LIBM)
```

> **`check_symbol_exists` vs `check_function_exists`**：前者既检查"符号是否在指定头文件中声明"又检查"是否可链接"，因此对**宏**和被宏实现的函数也适用，是更推荐的方式；后者只检查"能否链接到该符号"，对那些只以宏形式存在、没有真实函数体的"函数"会误判。

### 17.4.5 例子：编译器选项探测

```cmake
include(CheckCXXCompilerFlag)

check_cxx_compiler_flag("-Wall" HAVE_WALL)
if(HAVE_WALL)
  target_compile_options(app PRIVATE -Wall)
endif()

# 用法陷阱：探测告警类选项时，最好先把 -Werror 加进 REQUIRED_FLAGS，
# 否则不支持的选项可能只是"警告未知选项"而非报错，导致探测假阳性。
```

### 17.4.6 例子：`CheckTypeSize`

```cmake
include(CheckTypeSize)

check_type_size("void*"      SIZEOF_VOID_P)   # 指针宽度 → 判断 32/64 位
check_type_size("long long"  SIZEOF_LONG_LONG)
check_type_size("struct timespec" HAVE_TIMESPEC LANGUAGE C)

# 结果：
#   SIZEOF_VOID_P        → 数字（如 8），同时定义 HAVE_SIZEOF_VOID_P
#   类型不存在时变量为空字符串 / false
message(STATUS "指针 ${SIZEOF_VOID_P} 字节")
```

`check_type_size` 还会设置 `HAVE_<var>` 形式的存在性布尔变量，常配合 `configure_file` 生成 `config.h`：

```c
/* config.h.in */
#cmakedefine HAVE_SIZEOF_VOID_P 1
#define SIZEOF_VOID_P @SIZEOF_VOID_P@
```

### 17.4.7 **CMakePushCheckState**：详解

连续做多项探测时，常常需要"临时给某次探测设置 `CMAKE_REQUIRED_LIBRARIES` 等，做完恢复原状"。手动 `set`/还原既啰嗦又易错——`CMakePushCheckState` 提供成对的栈式保存/恢复命令：

```cmake
include(CMakePushCheckState)

cmake_push_check_state([RESET])   # 把当前所有 CMAKE_REQUIRED_* 压栈保存
cmake_pop_check_state()           # 弹栈恢复到上次 push 时的状态
cmake_reset_check_state()         # 直接清空所有 CMAKE_REQUIRED_*（不压栈）
```

- `cmake_push_check_state(RESET)`：压栈的同时把当前 `CMAKE_REQUIRED_*` **清空**，让接下来的设置从干净状态开始（最常用）。

典型范式——"开一个隔离的探测块"：

```cmake
include(CheckSymbolExists)
include(CMakePushCheckState)

cmake_push_check_state(RESET)
  set(CMAKE_REQUIRED_LIBRARIES ${CMAKE_DL_LIBS})  # 只在本块内链接 dl 库
  check_symbol_exists(dlopen "dlfcn.h" HAVE_DLOPEN)
cmake_pop_check_state()   # dlopen 探完，REQUIRED_LIBRARIES 自动还原，不污染后续
```

> 把每一组"需要特殊环境的探测"都包在 `push(RESET) ... pop` 之间，是大型项目里保证探测结果互不干扰的标准做法。

## 17.5 选项与系统信息模块

### 17.5.1 **CMakeDependentOption**：详解

普通 `option()` 是无条件的。当一个开关"只有在另外的开关满足时才有意义"，用 `cmake_dependent_option` 表达这种依赖关系：

```cmake
include(CMakeDependentOption)

cmake_dependent_option(<option> "<help>" <default> "<conditions>" <force_value>)
```

- `<conditions>`：一个**分号分隔的条件列表**（每个条件是一个 `if` 表达式）。**全部为真**时，该选项才向用户暴露，并以 `<default>` 作为默认值。
- `<force_value>`：当条件**不满足**时，选项被隐藏，并被强制设为此值（通常是 `OFF`）。

```cmake
option(USE_BAR "启用 Bar" ON)
option(USE_ZOT "启用 Zot" OFF)

# 仅当 USE_BAR 为 ON 且 USE_ZOT 为 OFF 时，USE_FOO 才可见且默认 ON；
# 否则 USE_FOO 被强制为 OFF 且不出现在 cache 编辑界面
cmake_dependent_option(USE_FOO "使用 Foo" ON "USE_BAR;NOT USE_ZOT" OFF)
```

> 效果：用户在 `ccmake`/`cmake-gui` 里只会在"前置条件满足"时看到 `USE_FOO`，避免出现"勾了但实际无效"的矛盾配置。

### 17.5.2 **ProcessorCount**：详解

获取当前机器的逻辑核心数，常用于给测试/外部构建设置并行度：

```cmake
include(ProcessorCount)

ProcessorCount(N)         # 把核心数写入变量 N；无法判定时 N 为 0
if(N EQUAL 0)
  set(N 1)
endif()
message(STATUS "可用处理器: ${N}")

# 用法举例：让 ctest 默认并行
set(CTEST_BUILD_FLAGS -j${N})
set_property(GLOBAL PROPERTY CTEST_PARALLEL_LEVEL ${N})
```

## 17.6 **GenerateExportHeader**：符号可见性导出宏

这是写**跨平台共享库**绕不开的模块。不同平台导出符号的机制不同：

- **Windows（MSVC）**：动态库默认**不导出**任何符号，需要在声明上加 `__declspec(dllexport)`（构建该 DLL 时）或 `__declspec(dllimport)`（使用该 DLL 时）。
- **类 Unix（GCC/Clang）**：默认**全部导出**；为了得到干净的 ABI，通常用 `-fvisibility=hidden` 把默认改成隐藏，再用 `__attribute__((visibility("default")))` 显式导出公开符号。

手写这套条件宏既冗长又易错。`generate_export_header()` 自动生成一个**统一的导出头**，里面定义了一组可移植的宏，你只需在公开声明上标注它们即可。

### 17.6.1 基本用法

```cmake
add_library(example SHARED example.cxx)

include(GenerateExportHeader)
generate_export_header(example)
#   ↑ 生成 ${CMAKE_CURRENT_BINARY_DIR}/example_export.h
#     并自动定义宏：EXAMPLE_EXPORT / EXAMPLE_NO_EXPORT / EXAMPLE_DEPRECATED ...

target_include_directories(example PUBLIC ${CMAKE_CURRENT_BINARY_DIR})
```

生成的头文件里包含（以目标名 `example` 为例）这些宏：

| 宏 | 含义 |
| --- | --- |
| `EXAMPLE_EXPORT` | 标注**公开**符号：构建库时展开为 dllexport / visibility default，使用库时展开为 dllimport |
| `EXAMPLE_NO_EXPORT` | 标注**内部**符号（即便整体默认导出，也强制隐藏） |
| `EXAMPLE_DEPRECATED` | 标注**已弃用**符号（展开为编译器的 deprecated 属性） |
| `EXAMPLE_DEPRECATED_EXPORT` / `EXAMPLE_DEPRECATED_NO_EXPORT` | 弃用 + 导出/不导出的组合 |

在头文件里这样用：

```cpp
// example.h
#include "example_export.h"

class EXAMPLE_EXPORT Widget {        // 整个类对外导出
public:
  void doStuff();
  EXAMPLE_DEPRECATED void oldApi();  // 仍导出，但标记弃用
private:
  EXAMPLE_NO_EXPORT void helper();   // 内部细节，不导出
};
```

### 17.6.2 与可见性预设配合（推荐）

`generate_export_header` 生成的宏要发挥作用，需要把**默认可见性设为隐藏**，否则 Unix 下"全导出"会让 `EXPORT/NO_EXPORT` 的区分失去意义。标准做法是设置目标级（或全局）可见性属性：

```cmake
set(CMAKE_CXX_VISIBILITY_PRESET hidden)       # 默认隐藏（等价 -fvisibility=hidden）
set(CMAKE_VISIBILITY_INLINES_HIDDEN TRUE)     # 内联函数也隐藏，进一步收紧 ABI

add_library(example SHARED example.cxx)

include(GenerateExportHeader)
generate_export_header(example)
```

> 关键点：CMake 会为该目标自动定义一个名为 `<target>_EXPORTS` 的预处理宏（这里是 `example_EXPORTS`）——**仅在编译该库自身时**有定义。生成的导出头正是靠它来区分"我在构建库"（用 dllexport）还是"我在使用库"（用 dllimport）。你**不需要**手动定义它。

### 17.6.3 定制宏名

把一个已有库迁过来时，常需要让宏名匹配既有代码：

```cmake
generate_export_header(example
  BASE_NAME        MYLIB          # 宏前缀与文件名基名
  EXPORT_FILE_NAME mylib_export.h
  EXPORT_MACRO_NAME      MYLIB_API     # 公开宏改名
  NO_EXPORT_MACRO_NAME   MYLIB_LOCAL
  DEPRECATED_MACRO_NAME  MYLIB_DEPRECATED
)
```

> 安装时别忘了把生成的 `*_export.h` 也一并安装（它位于构建目录），否则下游用户拿不到。配合 `FILE_SET HEADERS`（见第 11 章）可以优雅地把它纳入安装集合。

## 17.7 报告与调试模块

### 17.7.1 **FeatureSummary**：详解

在大型项目里，配置结束时打印一份"哪些可选功能开了/关了、哪些依赖找到了/没找到"的汇总，对用户极其友好。`FeatureSummary` 模块提供三个命令和一个打印入口，协同完成这件事。

#### 三个核心命令

**`set_package_properties(<name> PROPERTIES ...)`**——为 `find_package` 找到（或未找到）的包附加元信息：

```cmake
include(FeatureSummary)

find_package(ZLIB)
set_package_properties(ZLIB PROPERTIES
  TYPE        RECOMMENDED          # 依赖重要程度（见下表）
  URL         "https://zlib.net"   # 项目主页
  DESCRIPTION "通用压缩库"         # 一句话描述
  PURPOSE     "用于打包模块的 gzip 压缩输出"  # 本项目用它做什么
)
```

`TYPE` 取值语义：

| `TYPE` | 含义 | 对 `FATAL_ON_MISSING_REQUIRED_PACKAGES` 的影响 |
| --- | --- | --- |
| `RUNTIME` | 运行时依赖（最高：缺少将导致运行失败） | 视为 `REQUIRED`，缺失时致命 |
| `REQUIRED` | 必须依赖（同上，语义更直接） | 缺失时 `feature_summary` 报致命错误 |
| `RECOMMENDED` | 强烈推荐但非强制 | 缺失时仅打印警告摘要 |
| `OPTIONAL` | 可选，有更好没有也行 | 缺失时仅打印信息摘要 |

`DESCRIPTION` 与 `PURPOSE` 都是可选字符串，`URL` 可选字符串。多次调用 `set_package_properties` 对同一包可累加（后设的不覆盖先设的，各字段独立）。

**`add_feature_info(<name> <enabled_var> <description>)`**——登记一条"项目自定义功能"进汇总，不依赖 `find_package`：

```cmake
option(WITH_PNG "启用 PNG 导出" ON)
find_package(ZLIB)

add_feature_info("PNG export" WITH_PNG "需要 ZLIB；启用后可导出 .png 文件")
add_feature_info("ZLIB compression" ZLIB_FOUND "gzip 压缩支持（来自系统 ZLIB）")
```

- `<name>`：特性名字（字符串，显示在摘要里）。
- `<enabled_var>`：布尔变量或表达式，为真则该特性显示为"已启用"，为假则"已禁用"。
- `<description>`：说明文字，显示在该特性条目下。

**`feature_summary(WHAT <what> ...)`**——在 `CMakeLists.txt` 末尾调用，打印汇总：

```cmake
feature_summary(
  WHAT ALL
  INCLUDE_QUIET_PACKAGES
  FATAL_ON_MISSING_REQUIRED_PACKAGES
)
```

`WHAT` 可取单值或列表（多个用分号或空格分隔）：

| `WHAT` 取值 | 打印内容 |
| --- | --- |
| `ALL` | 等价于下面所有有意义选项的组合 |
| `ENABLED_FEATURES` | 已启用的功能（`add_feature_info` 中为真的） |
| `DISABLED_FEATURES` | 已禁用的功能 |
| `PACKAGES_FOUND` | `find_package` 找到的包 |
| `PACKAGES_NOT_FOUND` | `find_package` 未找到的包 |
| `OPTIONAL_PACKAGES_FOUND` / `OPTIONAL_PACKAGES_NOT_FOUND` | 仅 `TYPE OPTIONAL` 的包 |
| `RECOMMENDED_PACKAGES_FOUND` / `RECOMMENDED_PACKAGES_NOT_FOUND` | 仅 `TYPE RECOMMENDED` 的包 |
| `REQUIRED_PACKAGES_FOUND` / `REQUIRED_PACKAGES_NOT_FOUND` | 仅 `TYPE REQUIRED/RUNTIME` 的包 |
| `RUNTIME_PACKAGES_FOUND` / `RUNTIME_PACKAGES_NOT_FOUND` | 仅 `TYPE RUNTIME` 的包 |

其余常用选项：

- **`INCLUDE_QUIET_PACKAGES`**：也包含 `find_package(... QUIET)` 调用时找到/未找到的包（默认 QUIET 包被排除）。
- **`FATAL_ON_MISSING_REQUIRED_PACKAGES`**：若有 `TYPE REQUIRED` 或 `TYPE RUNTIME` 的包未找到，`feature_summary` 执行后立即 `FATAL_ERROR`（代替在每个 `find_package` 后手动 `if(NOT Foo_FOUND) message(FATAL_ERROR ...)`)。
- **`DESCRIPTION "<text>"`**：给本次 `feature_summary` 调用输出前加一行标题。
- **`VAR <var>`**：把汇总字符串存入变量（不打印），供进一步处理（写文件、传给 CPack 等）。
- **`FILENAME <file>`** / **`APPEND`**：写入文件（`APPEND` 模式则追加，否则覆盖）。

#### 完整工程实例

```cmake
cmake_minimum_required(VERSION 3.14)
project(MyApp VERSION 1.0 LANGUAGES CXX)

include(FeatureSummary)

# --- 依赖查找 ---
find_package(ZLIB)
set_package_properties(ZLIB PROPERTIES
  TYPE        RECOMMENDED
  URL         "https://zlib.net"
  DESCRIPTION "通用压缩库"
  PURPOSE     "gzip 格式的导入/导出")

find_package(OpenSSL)
set_package_properties(OpenSSL PROPERTIES
  TYPE        OPTIONAL
  DESCRIPTION "TLS 库"
  PURPOSE     "HTTPS 传输支持")

find_package(Threads REQUIRED)
set_package_properties(Threads PROPERTIES
  TYPE        REQUIRED
  DESCRIPTION "系统线程库")

# --- 自定义功能开关 ---
option(ENABLE_GUI "启用图形界面（依赖 Qt）" OFF)
find_package(Qt6 QUIET COMPONENTS Widgets)
add_feature_info("GUI (Qt6)"    Qt6_FOUND  "图形界面支持，需要 Qt6::Widgets")
add_feature_info("GUI enabled"  ENABLE_GUI "已通过 -DENABLE_GUI=ON 启用")

option(WITH_TESTS "构建单元测试" ON)
add_feature_info("Unit tests" WITH_TESTS "CTest 测试套件")

# --- 目标定义 ...（省略）--- #

# --- 末尾汇总 ---
feature_summary(
  WHAT           ALL
  INCLUDE_QUIET_PACKAGES
  FATAL_ON_MISSING_REQUIRED_PACKAGES
  DESCRIPTION    "=== MyApp 配置汇总 ==="
)
```

**典型输出**（配置后打印）：

```text
=== MyApp 配置汇总 ===
-- The following RECOMMENDED packages have been found:
 * ZLIB (required version >= 1.2.3), 通用压缩库, <https://zlib.net>
   gzip 格式的导入/导出
-- The following OPTIONAL packages have NOT been found:
 * OpenSSL, TLS 库
   HTTPS 传输支持
-- The following REQUIRED packages have been found:
 * Threads, 系统线程库
-- The following features have been enabled:
 * Unit tests, CTest 测试套件
-- The following features have been DISABLED:
 * GUI enabled, 已通过 -DENABLE_GUI=ON 启用
 * GUI (Qt6), 图形界面支持，需要 Qt6::Widgets
```

> 📌 最佳实践：把 `feature_summary(WHAT ALL FATAL_ON_MISSING_REQUIRED_PACKAGES)` 固定放在顶层 `CMakeLists.txt` 的最末尾（所有 `find_package`、`add_feature_info`、`set_package_properties` 都在它之前），一行代替若干个"找不到就 FATAL_ERROR"的手动检查，同时给用户清晰的配置概览。

### 17.7.2 **CMakePrintHelpers**：详解

调试 CMake 脚本时，逐个 `message(STATUS "x=${x}")` 很繁琐。本模块提供两个便捷打印命令：

```cmake
include(CMakePrintHelpers)
```

**`cmake_print_variables(<var>...)`**——一次打印多个变量名与值（变量不存在也安全）：

```cmake
cmake_print_variables(CMAKE_C_COMPILER CMAKE_MAJOR_VERSION PROJECT_NAME NOT_EXISTS)
# -- CMAKE_C_COMPILER="/usr/bin/cc" ; CMAKE_MAJOR_VERSION="4" ; PROJECT_NAME="demo" ; NOT_EXISTS=""
```

**`cmake_print_properties(...)`**——打印目标/源文件/目录等的属性值：

```cmake
cmake_print_properties(
  TARGETS   app mylib
  PROPERTIES TYPE INTERFACE_INCLUDE_DIRECTORIES COMPILE_DEFINITIONS)
```

支持的对象类别：`TARGETS` / `SOURCES` / `DIRECTORIES` / `TESTS` / `CACHE_ENTRIES`，搭配 `PROPERTIES` 列出要查看的属性名。这是排查"目标的某个属性到底被设成了什么"的利器。

## 17.9 编写自定义模块

把项目里反复出现的逻辑（统一的编译告警、产物布局、辅助函数）抽成一个模块，是保持 `CMakeLists.txt` 简洁、可维护的关键手段。

### 17.9.1 步骤

1. 在项目里建一个目录，约定俗成叫 `cmake/`。
2. 写一个 `cmake/MyHelpers.cmake`，里面 `function()`/`macro()` 定义可复用逻辑。
3. 把 `cmake/` 追加进 `CMAKE_MODULE_PATH`。
4. 用 `include(MyHelpers)` 加载，然后调用其中的函数。

```cmake
# 顶层 CMakeLists.txt
list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/cmake")
include(MyHelpers)

add_executable(app main.cpp)
enable_project_warnings(app)   # 来自 MyHelpers.cmake
```

```cmake
# cmake/MyHelpers.cmake
include_guard(GLOBAL)          # 防止被重复 include（见下）

# 给目标统一开一组编译告警（跨编译器）
function(enable_project_warnings target)
  if(MSVC)
    target_compile_options(${target} PRIVATE /W4 /permissive-)
  else()
    target_compile_options(${target} PRIVATE -Wall -Wextra -Wpedantic)
  endif()
endfunction()
```

### 17.9.2 **`include_guard()`**：防重复包含

一个模块可能被多个文件 `include`。若它在全局作用域里定义了缓存变量、调用了 `add_*`、或做了昂贵探测，重复加载会出问题或拖慢配置。`include_guard()` 是 CMake 版的"头文件 include guard / `#pragma once`"：

```cmake
include_guard()          # DIRECTORY 级：当前目录作用域内只加载一次
include_guard(DIRECTORY) # 同上，显式写法
include_guard(GLOBAL)    # 全局：整个 cmake 运行期间只加载一次（模块最常用）
```

把它放在自定义模块的**第一行**：第二次 `include` 该文件时会直接返回，不再执行后续内容。

> `function`/`macro` 的区别提醒：`function` 有独立作用域，内部 `set` 默认不外泄（需 `PARENT_SCOPE` 或 `set(... PARENT_SCOPE)` 才回传）；`macro` 是文本展开、共享调用者作用域。封装可复用逻辑时**优先 `function`**，仅在确实需要修改调用者变量、或需要展开多条 `target_*` 时才考虑 `macro`。

## 17.10 延迟调用与动态执行：`cmake_language(DEFER / CALL / EVAL)`

`cmake_language()` 是 CMake 3.18 引入的元命令，提供三种独立但常配合使用的能力：延迟调用（`DEFER`）、动态调用（`CALL`）、代码求值（`EVAL CODE`）。前面章节"模块简介"里提及了 `DEFER`，本节展开三者的完整语义、用途与陷阱。

### 17.10.1 `cmake_language(DEFER ...)`：延迟到目录末尾执行

把一次命令调用**推迟到当前目录 `CMakeLists.txt` 处理完毕时**再执行：

```cmake
# 把一次 message 调用推迟到当前目录处理结束时执行
cmake_language(DEFER CALL message "目录处理收尾")

message("这行先打印")
# —— 目录末尾 —— 才打印 "目录处理收尾"
```

常用形式：

| 形式 | 作用 |
| --- | --- |
| `cmake_language(DEFER CALL <command> [args...])` | 登记一个延迟调用，在当前目录作用域结束时执行 |
| `cmake_language(DEFER DIRECTORY <dir> CALL ...)` | 指定在**某个目录**作用域结束时执行 |
| `cmake_language(DEFER ID_VAR <var> CALL ...)` | 登记并把本次调用的 ID 存入 `<var>`，便于后续取消 |
| `cmake_language(DEFER CANCEL_CALL <id>...)` | 取消之前登记的延迟调用（未知 ID 被忽略） |
| `cmake_language(DEFER GET_CALL_IDS <var>)` | 获取当前作用域内所有已登记延迟调用的 ID 列表 |

**求值时机**：延迟调用里的变量引用在**执行时**才展开（届时变量值可能已改变）。若需要按"登记时的快照"固定参数值，应提前把值算好存进一个临时变量，再把那个变量传进 `DEFER CALL`，或改用下面的 `EVAL CODE` 方式提前展开。

**典型用途**：在写"框架型"模块（被用户 `CMakeLists.txt` 使用，但需要在用户定义完所有 target 之后才能后处理）时，用 `DEFER` 把收尾逻辑延迟到用户代码处理完毕后再跑：

```cmake
# cmake/CompileWarnings.cmake
include_guard(GLOBAL)

# 用户 CMakeLists.txt 处理完后，自动给所有 EXECUTABLE 目标加告警
cmake_language(DEFER CALL _apply_warnings_to_all_executables)

function(_apply_warnings_to_all_executables)
  get_property(all_targets DIRECTORY PROPERTY BUILDSYSTEM_TARGETS)
  foreach(t IN LISTS all_targets)
    get_target_property(type ${t} TYPE)
    if(type STREQUAL "EXECUTABLE")
      target_compile_options(${t} PRIVATE
        $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:-Wall;-Wextra>
        $<$<CXX_COMPILER_ID:MSVC>:/W4>)
    endif()
  endforeach()
endfunction()
```

> ⚠️ **陷阱**：`DEFER CALL` 在**当前 `CMakeLists.txt` 目录作用域**末尾执行，而非整个 configure 结束后——若目录结构有多层 `add_subdirectory`，各目录的延迟调用**分别**在各自目录末尾触发，不一定是全局最后阶段。如需在整个 configure 真正结束时执行，把 `DEFER` 放在顶层 `CMakeLists.txt` 的末尾，或配合 `DIRECTORY ${CMAKE_SOURCE_DIR}` 指定顶层。

### 17.10.2 `cmake_language(CALL ...)`：动态调用命令

`CALL` 允许通过**变量保存的命令名**来调用 CMake 命令，实现类似"函数指针"的分发：

```cmake
cmake_language(CALL <command> [<arg>...])
```

与直接写命令名的区别在于，`<command>` 可以是一个**变量展开后的字符串**，从而在运行时决定调用哪个命令：

```cmake
# 工厂模式：根据变量动态调用不同的日志函数
set(log_cmd "message")

cmake_language(CALL ${log_cmd} STATUS "动态调用了 message")
# 等价于：message(STATUS "动态调用了 message")
```

更实用的场景——在一个循环里批量分发到不同命令：

```cmake
function(dispatch_action action target)
  # action 可为 "compile" / "link" / "check"，对应不同的处理函数
  cmake_language(CALL "handle_${action}" "${target}")
endfunction()

function(handle_compile target)
  target_compile_options(${target} PRIVATE -O2)
endfunction()

function(handle_link target)
  target_link_options(${target} PRIVATE -Wl,--as-needed)
endfunction()

dispatch_action(compile mylib)
dispatch_action(link    mylib)
```

> **限制与陷阱**：
> - `CALL` 只能调用**已定义的 `function`/`macro`**，或内置命令——不能调用未定义的名字（会 FATAL_ERROR）。
> - 命令名在调用时才决定，IDE/静态分析工具看不到这层调用，可维护性下降；仅在"分发表"型场景才值得用。
> - CMake 内置命令（如 `message`、`add_executable` 等）也可被 `CALL` 调用。但不可借此规避 `if_policy` 等控制流——`cmake_language(CALL if "...")` 不合法。

### 17.10.3 `cmake_language(EVAL CODE ...)`：把字符串当代码执行

`EVAL CODE` 把一段**字符串当作 CMake 代码**在当前作用域内立即执行，相当于 `eval` 语义：

```cmake
cmake_language(EVAL CODE "<cmake代码字符串>")
```

**基本示例**：

```cmake
set(var_name "MY_FLAG")
set(var_value "-O3")

# 动态构造并执行一条 set() 语句
cmake_language(EVAL CODE "set(${var_name} \"${var_value}\" CACHE STRING \"\" FORCE)")
message(STATUS "MY_FLAG = ${MY_FLAG}")   # 输出：-O3
```

**与 `DEFER` 配合——"登记时展开变量，延迟时执行"**：

```cmake
set(my_target "app")

# 直接用 DEFER CALL：变量 my_target 在执行时才求值（如果那时已被改，会出错）
cmake_language(DEFER CALL message STATUS "延迟目标：${my_target}")

# 安全做法：用 EVAL CODE 立即展开 my_target，把结果字符串再传给 DEFER
cmake_language(EVAL CODE "
  cmake_language(DEFER CALL message STATUS \"延迟目标快照：${my_target}\")
")
# 现在 DEFER 里存的是展开后的字符串 "app"，即便后来 my_target 变了也无影响
```

**生成批量命令（元编程）**：

```cmake
# 根据列表动态生成多个 option() 定义
set(features Foo Bar Baz)
foreach(feat IN LISTS features)
  cmake_language(EVAL CODE "
    option(WITH_${feat} \"启用 ${feat} 功能\" OFF)
    add_feature_info(\"${feat}\" WITH_${feat} \"可选功能 ${feat}\")
  ")
endforeach()
```

> ⚠️ **陷阱与最佳实践**：
> - `EVAL CODE` 里的变量**在代码被构造时展开**（字符串插值阶段），而非执行时——这与普通命令调用不同，容易混淆（双引号里的 `${var}` 在 `EVAL CODE "..."` 的引号里就已被展开）。
> - 执行出错时报错信息会指向 `cmake_language(EVAL CODE ...)` 这一行，而非动态生成的"虚拟文件名"，调试体验差。大量使用 `EVAL CODE` 会让逻辑难以追踪，**优先考虑 `function`/`macro` + `cmake_language(CALL ...)` 组合**；仅在确实需要动态生成 CMake 语法（如 `if`/`foreach`/`option` 关键字本身需要变化）时才用 `EVAL CODE`。
> - `EVAL CODE` 在当前作用域内执行，`set()` 的结果对调用方可见（与 `include()` 行为一致，不建立新作用域）。

## 本章小结

- **模块机制**：模块是 `.cmake` 脚本，用 `include(<名字>)`（按模块名，走 `CMAKE_MODULE_PATH` → 内置 `Modules/` 目录查找）或 `include(<路径>)`（按文件）加载；`include` 不开新作用域。内置模块分**工具模块**与**查找模块（`Find*`）**两类，权威清单见 `cmake-modules(7)` / `cmake --help-module-list`。
- **`cmake -P`** 脚本模式独立运行 `.cmake`，专用变量 `CMAKE_ARGC`/`CMAKE_ARGV*`（用户参数从 `ARGV3` 起）/`CMAKE_SCRIPT_MODE_FILE`；适合跨平台自动化与构建时生成步骤，常配 `-D` 传参。
- **`cmake -E`** 提供跨平台基础命令（`copy`/`copy_if_different`/`copy_directory`、`make_directory`、`rm`、`echo`、`env`、`tar`、`cat`、`compare_files`、`create_symlink`、`true`/`false`、`sleep`、`chdir`、`time` 等），用 `${CMAKE_COMMAND} -E` 写 shell 无关的自定义命令。
- **特性探测 Check\* 系列**：编译/链接/运行探针判断头文件、符号、函数、库、编译选项、类型大小等是否可用，结果入缓存；用 `CMAKE_REQUIRED_*` 配置探测环境，并用 **`CMakePushCheckState`**（`push(RESET)...pop`）隔离避免污染。
- **选项/信息模块**：`CMakeDependentOption`（条件依赖型开关）、`ProcessorCount`（核心数）。
- **`GenerateExportHeader`** 生成可移植的符号导出宏（`<T>_EXPORT`/`_NO_EXPORT`/`_DEPRECATED`），配合 `CMAKE_CXX_VISIBILITY_PRESET hidden`、`CMAKE_VISIBILITY_INLINES_HIDDEN` 与自动定义的 `<target>_EXPORTS` 宏，干净地控制共享库 ABI。
- **报告/调试**：`FeatureSummary`（三命令：`set_package_properties` 标注 TYPE/URL/DESCRIPTION/PURPOSE、`add_feature_info` 登记自定义功能、`feature_summary(WHAT ALL FATAL_ON_MISSING_REQUIRED_PACKAGES)` 末尾一键汇总并在缺 REQUIRED 包时致命报错）、`CMakePrintHelpers`（`cmake_print_variables`/`cmake_print_properties` 调试打印）。
- **自定义模块**：放进 `cmake/`、加入 `CMAKE_MODULE_PATH`、首行 `include_guard(GLOBAL)` 防重复，优先用 `function` 封装。
- **`cmake_language` 三子命令**：`DEFER CALL`（把调用推迟到目录作用域末尾，适合"全部目标定义完后"的统一后处理，注意变量在执行时才展开）；`CALL <command>`（以变量名动态分发到不同命令，实现工厂模式，命令名在运行时决定）；`EVAL CODE`（把字符串当 CMake 代码立即执行，适合批量生成 `option`/`set` 等语句的元编程，字符串里的变量在构造时展开）。三者常配合：用 `EVAL CODE` 预先展开变量快照、再传给 `DEFER`，解决"登记时值 vs 执行时值"的时序问题。
