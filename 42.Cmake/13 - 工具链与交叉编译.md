# 第 13 章 · 工具链与交叉编译

> 基准版本：CMake 4.3.4

> 本章面向「目标机不是构建机」的全部场景：在 x86_64 Linux/Windows 工作站上，为 ARM 嵌入式板、Android 手机、裸机 MCU、浏览器（WebAssembly）等异构目标生成可执行文件与库。核心抽象只有一个——**工具链文件（toolchain file）**。读完本章你应当能：独立编写一个可复用的 toolchain file；理解 `CMAKE_SYSTEM_NAME` 为何是"交叉编译的总开关"；用 `CMAKE_FIND_ROOT_PATH` 系列变量把 `find_package`/`find_library` 牢牢钉在目标 sysroot 内；并能针对 ARM Linux、Android NDK、裸机、Emscripten 四类典型目标各自落地一份完整的工具链配置。

---

## 13.1 什么是工具链文件

### 13.1.1 概念：把"目标平台描述"从项目里剥离

CMake 默认假设**构建机（host）就是目标机（target）**——即你在哪台机器上跑 `cmake`，生成的二进制就跑在哪台机器上。这叫**本机编译（native build）**。一旦目标机与构建机不同（不同 CPU 架构、不同操作系统、甚至没有操作系统），就进入**交叉编译（cross compiling）**。

交叉编译需要回答一组问题：用哪个交叉编译器？目标 CPU 是什么架构？目标系统是 Linux 还是裸机？目标的头文件和库放在哪个根目录（sysroot）里？这些信息**与你的项目源码无关，只与"目标平台 + 工具链"有关**。如果把它们写进 `CMakeLists.txt`，那么同一份代码想换一个目标就得改项目文件，灾难性地破坏了可移植性。

CMake 的解法是把这组"目标平台描述"集中写进一个独立的 `.cmake` 脚本——这就是**工具链文件**。它本质上是一段在 CMake 配置极早期被 `include()` 进来的普通 CMake 脚本，里面只做一件事：`set()` 一堆描述目标平台的变量。

```cmake
# my-toolchain.cmake —— 一个最小可用的工具链文件骨架
set(CMAKE_SYSTEM_NAME      Linux)          # 触发交叉编译：目标系统是 Linux
set(CMAKE_SYSTEM_PROCESSOR arm)            # 目标 CPU 架构
set(CMAKE_C_COMPILER       arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER     arm-linux-gnueabihf-g++)
```

### 13.1.2 为什么要用工具链文件

| 维度 | 不用 toolchain file（写死在项目里） | 用 toolchain file |
| --- | --- | --- |
| 可移植性 | 换目标平台要改 `CMakeLists.txt` | 项目文件零改动，换一个 `--toolchain` 即可 |
| 关注点分离 | 平台信息与构建逻辑混在一起 | 平台描述独立成文件，可单独维护、复用、版本化 |
| 多目标并存 | 难以同时维护多个目标 | 每个目标一份 toolchain，多个 build 目录并行 |
| 团队协作 | 每个人的路径写死，无法共享 | toolchain 用变量参数化，可入库共享 |
| CI/CD | 难以在流水线里切换目标 | 流水线传不同 `-DCMAKE_TOOLCHAIN_FILE` 即可 |

经验法则：**只要做交叉编译，就一定用工具链文件**；即便是本机编译，当你需要固定某个特定编译器、特定 sysroot 时，toolchain file 也是比一堆零散 `-D` 更整洁的载体。

### 13.1.3 如何传入工具链文件

有两种等价的命令行写法，外加一个环境变量：

```bash
# 写法一：直接设置 CMAKE_TOOLCHAIN_FILE 缓存变量（所有版本通用）
cmake -DCMAKE_TOOLCHAIN_FILE=/abs/path/to/my-toolchain.cmake -S . -B build

# 写法二：--toolchain 选项（CMake 3.21+ 提供，等价于上面，更简洁）
cmake --toolchain /abs/path/to/my-toolchain.cmake -S . -B build
```

- **`--toolchain <path-to-file>`** 是 3.21 引入的便捷选项，与设置 `CMAKE_TOOLCHAIN_FILE` 变量完全等价。在 4.3.4 中两者可任选。
- **相对路径解析规则**：toolchain file 的相对路径先相对于**构建目录**解释，找不到再相对于**源码目录**解释。生产环境强烈建议写**绝对路径**以免歧义。
- **环境变量 `CMAKE_TOOLCHAIN_FILE`**：当**新建**一个构建树时，可用同名环境变量初始化该缓存变量。但仅在首次创建 build 目录时生效。

```bash
# 写法三：环境变量（仅在首次创建 build 树时生效）
export CMAKE_TOOLCHAIN_FILE=/abs/path/to/my-toolchain.cmake
cmake -S . -B build
```

### 13.1.4 关键约束：只在首次配置生效

这是初学者最容易踩的坑，务必牢记：

> **工具链文件只在某个构建目录"首次配置"时被读取一次，其结果固化进 `CMakeCache.txt`。一旦 build 目录已存在缓存，再传 `--toolchain` 或修改 toolchain file 内容，CMake 都不会重新应用它。**

原因是 toolchain file 里设置的 `CMAKE_C_COMPILER` 等变量会写入缓存，而编译器一旦确定就不允许中途更换（更换编译器等于推翻所有已检测的能力）。

因此正确的工作流是：**改了 toolchain file 或要换目标平台，就删掉整个 build 目录重新配置**。

```bash
# 错误：在已配置的 build 目录上换 toolchain，新 toolchain 被忽略
cmake --toolchain other.cmake -S . -B build      # ⚠️ 不生效

# 正确：删除缓存后重新配置
rm -rf build
cmake --toolchain other.cmake -S . -B build      # ✅ 干净的全新配置
```

> 提示：toolchain file 本身会被 CMake 列为配置依赖，正常情况下"改 toolchain 内容 → 重新生成"对**非编译器类**变量是会触发重配的；但对编译器这种"一锤定音"的变量，删 build 目录永远是最稳妥的做法。本章后续所有"换目标"的操作，默认都意味着用一个干净的新 build 目录。

## 13.2 核心系统变量

交叉编译的"平台身份"由一组 `CMAKE_SYSTEM_*` 变量描述。它们必须在工具链文件里设置（因为要在编译器检测之前就生效）。

### 13.2.1 目标系统三件套

**CMAKE_SYSTEM_NAME**：目标操作系统的名字，**它是整个交叉编译机制的总开关**。
- 这是最重要的一个变量。**只要在工具链文件里 `set(CMAKE_SYSTEM_NAME ...)`，CMake 就立刻认为"这是交叉编译"**，并把 `CMAKE_CROSSCOMPILING` 置为 `TRUE`。
- 取值是目标系统名，如 `Linux`、`Windows`、`Darwin`、`Android`、`QNX`、`WindowsCE`，以及表示"裸机/无操作系统"的特殊值 `Generic`。
- 反过来：本机编译时**绝不要**手动设置它——CMake 会自动把它初始化为 `CMAKE_HOST_SYSTEM_NAME`，此时 `CMAKE_CROSSCOMPILING` 为 `FALSE`。手动设置（哪怕设成与 host 相同的值）也会强制开启交叉编译模式。

```cmake
# 设置这一行，本身就等于声明"开始交叉编译"
set(CMAKE_SYSTEM_NAME Linux)
```

**CMAKE_SYSTEM_PROCESSOR**：目标 CPU 架构的名字。
- 自由形式的字符串，CMake 本身不强制取值，但许多模块/查找逻辑会读它来分支。常见值：`arm`、`aarch64`、`x86_64`、`riscv64`、`mips`、`cortex-m4`（裸机常用具体型号）等。
- 交叉编译时**应当显式设置**，否则它会沿用 host 的处理器名，误导依赖它的逻辑。
- 特例：为 **Android** 编译时不要手动设它，CMake 会根据 `CMAKE_ANDROID_ARCH_ABI` 自动推导。

**CMAKE_SYSTEM_VERSION**：目标系统的版本号。
- 含义随目标系统而变：对 Android 是 **API level**（如 `21`）；对 Windows 是 SDK/系统版本；对裸机通常不需要。
- 若不设，多数平台会有合理默认值。

### 13.2.2 构建机信息：CMAKE_HOST_SYSTEM_*

与目标侧对应，CMake 自动提供一组描述**构建机本身**的只读变量，便于工具链脚本或项目里做"宿主判断"：

**CMAKE_HOST_SYSTEM_NAME**：构建机的操作系统名（如 `Linux`、`Windows`、`Darwin`）。
**CMAKE_HOST_SYSTEM_PROCESSOR**：构建机的 CPU 架构。
**CMAKE_HOST_SYSTEM_VERSION**：构建机的系统版本。
**CMAKE_HOST_SYSTEM**：综合形式 `name-version`。

此外还有一组布尔便捷量描述宿主：**CMAKE_HOST_UNIX**、**CMAKE_HOST_WIN32**、**CMAKE_HOST_APPLE**。注意区分：不带 `HOST` 的 `UNIX`/`WIN32`/`APPLE` 描述的是**目标**平台，带 `HOST` 的才描述构建机。交叉编译里这两者经常不一致——例如在 Windows 上为 Linux 交叉编译时，`CMAKE_HOST_WIN32` 为真而 `UNIX` 为真、`WIN32` 为假。

```cmake
# 工具链或项目里按宿主选择工具路径
if(CMAKE_HOST_WIN32)
  set(MY_NDK_HOST_TAG "windows-x86_64")
elseif(CMAKE_HOST_APPLE)
  set(MY_NDK_HOST_TAG "darwin-x86_64")
else()
  set(MY_NDK_HOST_TAG "linux-x86_64")
endif()
```

### 13.2.3 CMAKE_CROSSCOMPILING：判定当前是否在交叉

**CMAKE_CROSSCOMPILING**：当 `CMAKE_SYSTEM_NAME` 被工具链显式设置（即开启交叉编译）时为 `TRUE`，本机编译时为 `FALSE`。
- 它是项目代码里判断"现在是不是交叉环境"的标准开关。最典型的用途：**在交叉环境里跳过那些需要运行目标二进制才能完成的步骤**（如运行期特性探测、运行刚编出来的代码生成器等）。

```cmake
if(CMAKE_CROSSCOMPILING)
  # 交叉时：用预先准备好的、能在 host 上跑的工具，或读取预设结果
  find_program(CODEGEN_EXE codegen)         # 用宿主上已装好的同名工具
else()
  # 本机时：可以直接构建并运行刚编出来的工具
  add_executable(codegen tools/codegen.c)
  set(CODEGEN_EXE $<TARGET_FILE:codegen>)
endif()
```

> 注意：`CMAKE_CROSSCOMPILING` 为真**不代表目标二进制完全无法在 host 运行**。例如在 x86_64 上为 i386 交叉，二进制其实能跑。"能否运行目标程序"由 13.5/13.7 讨论的 `CMAKE_CROSSCOMPILING_EMULATOR` 与 `try_run` 行为决定，而非简单看这个布尔量。

## 13.3 指定编译器与目标

平台身份定好后，下一步是告诉 CMake**用哪个编译器、它该产出什么目标**。

### 13.3.1 直接指定编译器路径

**CMAKE_C_COMPILER** / **CMAKE_CXX_COMPILER**：C / C++ 编译器的可执行文件（其他语言同理，如 `CMAKE_ASM_COMPILER`、`CMAKE_Fortran_COMPILER`）。
- 可以是绝对路径（推荐，最稳），也可以是能在 `PATH` 里找到的命令名（如 `arm-linux-gnueabihf-gcc`）。
- 对 GNU 风格的交叉工具链，编译器名通常自带"目标三元组前缀"（`arm-linux-gnueabihf-`），用前缀名即可隐式带出整套 binutils（`ar`、`ranlib`、`ld` 等通常被 CMake 据此自动找到）。

```cmake
# 方式 A：用工具链根目录拼路径，最清晰可控
set(TOOLCHAIN_ROOT /opt/gcc-arm-linux-gnueabihf)
set(CMAKE_C_COMPILER   ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-g++)

# 方式 B：仅给命令名（依赖 PATH），简洁但可移植性稍弱
set(CMAKE_C_COMPILER   arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER arm-linux-gnueabihf-g++)
```

### 13.3.2 用 target 三元组指定目标：Clang 风格

对于 **Clang、QNX qcc** 这类"单一编译器、靠命令行参数切换目标"的编译器，不需要每个目标各装一份编译器，而是用一个变量告诉它"为谁编译"：

**CMAKE_\<LANG\>_COMPILER_TARGET**：传给编译器驱动的目标三元组（即 clang 的 `--target=<triple>`）。
- 仅应在工具链文件中设置。
- 仅对支持该机制的编译器有效（clang、qcc）；GCC 这类"每目标一份编译器"的工具链用不到它（GCC 通过编译器名前缀区分目标）。

```cmake
set(CMAKE_SYSTEM_NAME      Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(triple arm-linux-gnueabihf)

set(CMAKE_C_COMPILER          clang)
set(CMAKE_C_COMPILER_TARGET   ${triple})    # 等价于给 clang 传 --target=arm-linux-gnueabihf
set(CMAKE_CXX_COMPILER        clang++)
set(CMAKE_CXX_COMPILER_TARGET ${triple})
```

### 13.3.3 外部工具链：CMAKE_\<LANG\>_COMPILER_EXTERNAL_TOOLCHAIN

**CMAKE_\<LANG\>_COMPILER_EXTERNAL_TOOLCHAIN**：当用 Clang 编译，但希望它借用某套 **GCC 工具链**的头文件、库与 binutils 时，用此变量指向那套 GCC 工具链的安装根。
- 对应 clang 的 `--gcc-toolchain=<path>`。典型场景：embedded Linux 厂商只提供了一套 GCC sysroot/工具链，而你想用 clang 当前端去复用它。
- 仅应在工具链文件中设置。

```cmake
set(CMAKE_C_COMPILER          clang)
set(CMAKE_C_COMPILER_TARGET   armv7-linux-gnueabihf)
# 让 clang 使用这套 GCC 工具链里的 crt 文件、libstdc++、ld 等
set(CMAKE_C_COMPILER_EXTERNAL_TOOLCHAIN   /opt/gcc-arm-linux-gnueabihf)
set(CMAKE_CXX_COMPILER        clang++)
set(CMAKE_CXX_COMPILER_TARGET armv7-linux-gnueabihf)
set(CMAKE_CXX_COMPILER_EXTERNAL_TOOLCHAIN /opt/gcc-arm-linux-gnueabihf)
```

### 13.3.4 汇编器、链接器与其他工具

- **汇编器**：`set(CMAKE_ASM_COMPILER ...)` 并在 `project()`/`enable_language(ASM)` 中启用 `ASM` 语言。GNU 前缀工具链下，CMake 通常能从编译器名自动推断 binutils；只有当工具不在常规位置或命名不规范时才需手动指定。
- **链接器**：一般通过编译器驱动间接调用，不单独指定 `ld`。如需换链接器（如用 `lld`、`gold`），现代写法是设置链接器类型：

```cmake
# 选择链接器（CMake 3.29+ 提供的标准入口，替代手写 -fuse-ld 链接标志）
set(CMAKE_LINKER_TYPE LLD)        # 取值如 LLD / GOLD / BFD / MOLD ...
```

- **archiver / ranlib**：静态库工具，对应 `CMAKE_AR`、`CMAKE_RANLIB`。GNU 前缀工具链通常自动带出；裸机/特殊工具链可能需要手动设。

```cmake
set(CMAKE_AR     ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-ar)
set(CMAKE_RANLIB ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-ranlib)
```

## 13.4 sysroot 与查找根

交叉编译最隐蔽的难题是 **`find_*` 系列命令（`find_library`/`find_path`/`find_program`/`find_package`）默认会搜宿主机的 `/usr` 等系统目录，从而误把宿主库当成目标库**。这一节的变量就是为了把查找牢牢限制在目标根目录内。

### 13.4.1 CMAKE_SYSROOT：目标根文件系统

**CMAKE_SYSROOT**：目标系统的根文件系统路径（sysroot），即"假装这就是目标机的 `/`"。
- 它会作为 `--sysroot=<dir>` 传给编译器和链接器，使编译器去 `<sysroot>/usr/include` 找头、`<sysroot>/usr/lib` 找库，而不是宿主的 `/usr`。
- 它**只能在工具链文件中设置**（编译器一旦带上 sysroot 检测就定型了）。
- 它同时会被加入 `find_*` 的隐式查找前缀（见下文模式变量）。

```cmake
set(CMAKE_SYSROOT /opt/rpi-sysroot)   # 树莓派根文件系统的本地副本
```

> 相关变量 **CMAKE_SYSROOT_COMPILE** / **CMAKE_SYSROOT_LINK**：当编译期与链接期需要不同 sysroot 时分别覆盖，绝大多数情况无需关心。

### 13.4.2 CMAKE_STAGING_PREFIX：安装到哪、又从哪找

**CMAKE_STAGING_PREFIX**：交叉编译时的"暂存安装前缀"。
- 在交叉编译里，`CMAKE_INSTALL_PREFIX` 表达的是"将来在**目标机**上安装到哪个路径"（如 `/usr/local`），但你显然不能真的把文件装进目标机。`CMAKE_STAGING_PREFIX` 指定一个**宿主机上的目录**，`make install` 实际把文件放到这里（一个"目标根的暂存副本"）。
- 设置它后，这个 staging 目录也会被加入 `find_*` 的查找根——这样你交叉编译的多个项目可以互相找到彼此装到 staging 里的产物。

```cmake
set(CMAKE_SYSROOT        /home/dev/rpi-rootfs)   # 只读：厂商根文件系统
set(CMAKE_STAGING_PREFIX /home/dev/stage)        # 可写：你自己产物的暂存安装地
```

### 13.4.3 CMAKE_FIND_ROOT_PATH：附加查找根列表

**CMAKE_FIND_ROOT_PATH**：一个目录列表，`find_*` 命令在受限模式下会把每个候选根作为前缀去拼接搜索（即在 `<root>/usr/lib` 等位置找，而不是真实的 `/usr/lib`）。
- `CMAKE_SYSROOT` 与 `CMAKE_STAGING_PREFIX` 会被**自动**纳入查找根，无需重复列出；`CMAKE_FIND_ROOT_PATH` 用于**追加**额外的目标侧根目录（比如几个独立放置的第三方目标库前缀）。

```cmake
set(CMAKE_FIND_ROOT_PATH
    /opt/extra-arm-libs            # 额外的目标侧依赖前缀
    /opt/vendor-sdk/aarch64)
```

### 13.4.3.1 `CMAKE_SYSROOT` vs `CMAKE_FIND_ROOT_PATH`：两条不同的查找路径

这两个变量都与"查找根"有关，但作用机制**截然不同**，混淆是交叉编译中最常见的错误之一：

| 维度 | `CMAKE_SYSROOT` | `CMAKE_FIND_ROOT_PATH` |
|---|---|---|
| **传给编译器** | **是**：以 `--sysroot=<dir>` 传给编译器和链接器，编译器据此修改**内建头文件/库的搜索路径** | **否**：纯粹是 CMake 层面的 `find_*` 查找前缀，编译器完全不感知 |
| **影响范围** | 影响编译器的**内建搜索路径**（即 `#include <stdio.h>` 这类系统头，以及链接器找 crt 启动文件的路径） | 只影响 CMake 的 `find_library`/`find_path`/`find_program`/`find_package` 行为 |
| **自动并入 find 根** | **是**：`CMAKE_SYSROOT` 会自动作为 `find_*` 的一个查找根（在模式为 `ONLY` 或 `BOTH` 时生效） | 本身就是查找根列表，`CMAKE_SYSROOT` 会被追加进来 |
| **典型来源** | 厂商提供的根文件系统镜像（如树莓派 rootfs、Android NDK sysroot） | 你自己追加的额外依赖前缀，如独立装在宿主机某目录下的目标侧第三方库 |
| **只能在 toolchain file 里设** | **是**（编译器 sysroot 必须在编译器检测前确定） | 也推荐在 toolchain file 里设，但 CMakeLists.txt 里设也有效 |

**一句话区分**：`CMAKE_SYSROOT` 是"告诉**编译器**：把 `/` 当成 `<sysroot>`"；`CMAKE_FIND_ROOT_PATH` 是"告诉 **CMake 的 find_* 命令**：去这些根目录下找"。前者影响编译期内建路径解析，后者影响配置期的查找逻辑。

**典型组合使用**：

```cmake
# toolchain.cmake

# 1) 告诉编译器把 /opt/rpi-rootfs 当成根（编译器内建 #include / crt 路径）
set(CMAKE_SYSROOT /opt/rpi-rootfs)

# 2) 额外告诉 CMake find_*：还要去这两个独立目录查找目标侧库
#    （它们不在 /opt/rpi-rootfs 下，是你单独放的第三方 ARM 库）
set(CMAKE_FIND_ROOT_PATH
    /opt/extra-arm-qt6            # Qt6 for ARM 的安装前缀
    /opt/extra-arm-openssl)       # OpenSSL for ARM 的安装前缀
# 注意：CMAKE_SYSROOT 也会被自动加进 find 根，不必手动列出

# 3) 模式：库/头/包只在上述根下找，程序在宿主找
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

**`CMAKE_FIND_ROOT_PATH_MODE_*` 与 `CMAKE_SYSROOT` 的交互**：

- 当模式为 `ONLY` 时，`find_library` 等只在 `CMAKE_SYSROOT`（自动加入）+ `CMAKE_FIND_ROOT_PATH`（手动加入）拼出的路径下找，**完全不碰宿主的真实路径**。
- 当模式为 `BOTH` 时，先在上述根下找，再在宿主真实路径下找。
- 当模式为 `NEVER` 时，忽略所有 find 根（包括 sysroot），直接在宿主真实路径找——这是 `CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER` 的语义：确保构建期工具（编译器、代码生成器）取自宿主机而不是 sysroot 里的 ARM 二进制。

### 13.4.3.2 `CMAKE_STAGING_PREFIX`：交叉编译的暂存安装前缀

**场景背景**：交叉编译时，`CMAKE_INSTALL_PREFIX` 表示"最终在**目标机**上的安装路径"（如 `/usr/local`），但你不能真的把文件写到目标机的文件系统里。`CMAKE_STAGING_PREFIX` 解决了这个矛盾——它指定宿主机上的一个**暂存目录**，`cmake --install` 把文件实际写到这里，而文件内容（如 CMake Config 文件里记录的路径、库的 RPATH）仍然写的是 `CMAKE_INSTALL_PREFIX`（即目标机路径）。

```cmake
# toolchain.cmake 中的典型配置
set(CMAKE_SYSROOT        /home/dev/rpi-rootfs)   # 只读：厂商提供的目标根文件系统
set(CMAKE_STAGING_PREFIX /home/dev/stage)        # 可写：你自己产物的暂存安装地
# CMAKE_INSTALL_PREFIX 在命令行设置为 /usr/local（目标机路径，不需要在 toolchain 里设）
```

**`CMAKE_STAGING_PREFIX` 的双重作用**：

1. **作为安装目标**：`cmake --install build` 把文件写到 `${CMAKE_STAGING_PREFIX}/...` 而非真实的 `CMAKE_INSTALL_PREFIX`（不存在于宿主机）。
2. **作为 `find_*` 查找根**：staging 目录被**自动加入** `find_*` 的查找根（与 `CMAKE_SYSROOT` 类似），这样当你有多个交叉编译的子项目时，后编译的项目能 `find_package` 到前面已经 stage 好的产物——这是 staging 机制的核心价值。

**与 `CMAKE_SYSROOT` 的区分**：

| | `CMAKE_SYSROOT` | `CMAKE_STAGING_PREFIX` |
|---|---|---|
| **内容来源** | 厂商/发行版提供的根文件系统（只读或不由你写） | 你自己的构建产物的暂存区（可写） |
| **传给编译器** | 是（`--sysroot`） | 否 |
| **用于 `find_*`** | 是（自动加入查找根） | 是（自动加入查找根） |
| **文件内记录的路径** | N/A | 文件内路径仍写 `CMAKE_INSTALL_PREFIX`（目标机路径） |

**多项目 staging 工作流**：

```bash
# 项目 A：交叉编译并 stage
cmake --toolchain toolchain.cmake -S projectA -B buildA \
    -DCMAKE_INSTALL_PREFIX=/usr/local \
    -DCMAKE_STAGING_PREFIX=/home/dev/stage
cmake --build buildA
cmake --install buildA   # 实际写到 /home/dev/stage/usr/local/...

# 项目 B：依赖项目 A，find_package 能找到 stage 里的产物
cmake --toolchain toolchain.cmake -S projectB -B buildB \
    -DCMAKE_INSTALL_PREFIX=/usr/local \
    -DCMAKE_STAGING_PREFIX=/home/dev/stage
# CMake 配置时 find_package(ProjectA) 会在 /home/dev/stage/... 下找到它
cmake --build buildB
```

### 13.4.4 四个模式变量：精确控制"按哪个根去找"

CMake 把"查找"分成四类，每类用一个模式变量决定**是只在查找根里找、只在宿主真实路径里找、还是两者都找**。这是交叉编译里最需要精雕细琢的开关。

取值含义：

| 取值 | 含义 |
| --- | --- |
| `NEVER` | **不使用** `CMAKE_FIND_ROOT_PATH`/sysroot 前缀，只在宿主机真实根（`/`）下查找 |
| `ONLY` | **只在** 查找根（sysroot / staging / `CMAKE_FIND_ROOT_PATH`）下查找，忽略宿主真实路径 |
| `BOTH` | 先在查找根下找，再在宿主真实路径下找（两者都搜） |

四个模式变量及其典型设置：

| 模式变量 | 控制对象 | 典型交叉设置 | 为什么 |
| --- | --- | --- | --- |
| **CMAKE_FIND_ROOT_PATH_MODE_PROGRAM** | `find_program` 找可执行工具 | `NEVER` | 构建期要运行的工具（编译器、代码生成器、`pkg-config` 等）必须是**能在宿主机上跑**的，不能从目标 sysroot 里捞一个 ARM 二进制来执行 |
| **CMAKE_FIND_ROOT_PATH_MODE_LIBRARY** | `find_library` 找链接库 | `ONLY` | 链接进目标程序的库必须是**目标架构**的，绝不能误链宿主库 |
| **CMAKE_FIND_ROOT_PATH_MODE_INCLUDE** | `find_path` 找头文件 | `ONLY` | 头文件应取目标 sysroot 的版本（含目标特定宏/ABI） |
| **CMAKE_FIND_ROOT_PATH_MODE_PACKAGE** | `find_package` 找包配置 | `ONLY` | 包的 `*Config.cmake` 应来自目标侧，避免找到宿主上同名包 |

最常见、最稳妥的一组交叉编译配置（记住这四行几乎是模板）：

```cmake
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)   # 工具在 host 上找
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)    # 库只在 sysroot 里找
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)    # 头只在 sysroot 里找
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)    # 包只在 sysroot 里找
```

> 微调建议：如果某些 header-only 第三方库装在宿主机而非 sysroot，可临时把 `INCLUDE` 放宽为 `BOTH`；但 `LIBRARY` 一般不要放成 `BOTH`，否则极易误链宿主 `.so`。`PROGRAM` 几乎总是 `NEVER`，因为构建用的工具必须能在 host 跑。

## 13.5 try_compile / try_run 在交叉环境

CMake 在配置期会做大量"探测"：编译一小段代码看某特性是否支持（`check_*` 系列、`try_compile`），甚至编译后**运行**它读结果（`try_run`）。这些机制在交叉环境会出问题。

### 13.5.1 问题：默认探测要"编出并运行可执行文件"

- `try_compile` 默认编译一个**可执行文件**。在某些交叉目标（尤其裸机、特殊嵌入式工具链）上，"链接成可执行文件"这步本身就需要完整的启动文件、链接脚本、`_start` 入口等，配置期还没准备好这些时会直接失败——哪怕你真正想编的只是个静态库。
- `try_run` 更进一步要**运行**编出的二进制。交叉目标的二进制在宿主机上根本跑不起来（架构不符），于是 `try_run` 无法得到运行结果。

### 13.5.2 解法一：CMAKE_TRY_COMPILE_TARGET_TYPE

**CMAKE_TRY_COMPILE_TARGET_TYPE**：控制 `try_compile`（以及内部用到它的所有 `check_*`）生成何种产物。
- 默认 `EXECUTABLE`（编可执行文件）。
- 设为 **`STATIC_LIBRARY`** 后，探测只把测试代码**编译并归档成静态库**，**跳过链接成可执行文件**那一步——从而避免"无法链接/无法运行"导致的探测失败。这是裸机与"目标二进制无法在 host 运行"场景的标准做法。

```cmake
# 裸机/无法运行目标时，让所有配置期探测只编译不链接可执行
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
```

> 代价：设为 `STATIC_LIBRARY` 后，依赖"链接是否成功"的探测（例如检查某符号能否被链接到）会失去意义——因为根本不链接。这是为了让配置在受限交叉环境里走得通而做的取舍。

### 13.5.3 解法二：CMAKE_CROSSCOMPILING_EMULATOR（让目标二进制能"跑"）

**CMAKE_CROSSCOMPILING_EMULATOR**：指定一个**模拟器/包装器命令**，CMake 在需要运行目标二进制时（`try_run`、`add_custom_command` 里运行刚构建的工具、CTest 运行测试用例等）会用它来执行。
- 例如用 QEMU 用户态模拟运行 ARM 程序，或 Emscripten 场景下用 Node.js 运行 `.js`/`.wasm`。
- 它也会成为可执行目标的 `CROSSCOMPILING_EMULATOR` 属性默认值，于是 `add_test(... COMMAND <target>)` 注册的测试会自动变成 `<emulator> <target>` 来运行（详见第 12 章 CTest）。

```cmake
# 用 QEMU 用户态模拟器运行 ARM 二进制（注意：分号分隔的列表，第一个是程序，后面是参数）
set(CMAKE_CROSSCOMPILING_EMULATOR /usr/bin/qemu-arm-static)

# 带参数的写法（例如 qemu 需要 -L 指定 sysroot 以加载动态库）
set(CMAKE_CROSSCOMPILING_EMULATOR /usr/bin/qemu-arm-static;-L;/opt/rpi-sysroot)
```

设置了模拟器后，`try_run` 才有可能在交叉环境得到真实的运行结果；否则 `try_run` 会保留运行结果变量为"未知"，需要你在工具链里**预先缓存**这些探测结果（见下文）。

### 13.5.4 解法三：预置探测结果

当既不想 `STATIC_LIBRARY`、又没有模拟器时，可以在工具链文件里**直接把探测结果预先 `set(... CACHE ...)` 进缓存**，让 CMake 跳过实际探测。`try_run` 对此尤其重要——它会查找形如 `<VAR>` 与 `<VAR>__TRYRUN_OUTPUT` 的缓存变量。

```cmake
# 预置某个 check_c_source_runs / try_run 的结果，避免在交叉环境真正运行
set(HAVE_WORKING_FOO 1 CACHE INTERNAL "预置：目标平台支持 FOO")
```

## 13.6 完整实例

下面给出五类目标的**可直接复用**工具链文件与构建命令。请把路径替换成你机器上的实际安装位置；每份开头都建议用变量参数化根目录以便共享。

### 13.6.1 ARM Linux 交叉编译（arm-linux-gnueabihf-gcc）

场景：在 x86_64 Linux 工作站上，为运行 32 位 ARM 硬浮点 Linux（如树莓派 2/3 的 armhf 用户态）编译。

```cmake
# toolchains/arm-linux-gnueabihf.cmake
# 用法：cmake --toolchain $PWD/toolchains/arm-linux-gnueabihf.cmake -S . -B build-arm

# 1) 目标平台身份（设置 SYSTEM_NAME 即开启交叉编译）
set(CMAKE_SYSTEM_NAME      Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

# 2) 交叉工具链根目录（按需改成你的安装路径）
set(TOOLCHAIN_ROOT /opt/gcc-arm-linux-gnueabihf)

# 3) 指定编译器（GNU 前缀名会自动带出 ar/ranlib/ld 等 binutils）
set(CMAKE_C_COMPILER   ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER ${TOOLCHAIN_ROOT}/bin/arm-linux-gnueabihf-g++)

# 4) 目标根文件系统（树莓派 rootfs 的本地副本）与暂存安装前缀
set(CMAKE_SYSROOT        /opt/rpi-sysroot)
set(CMAKE_STAGING_PREFIX /home/dev/stage-arm)

# 5) 查找根模式：工具在 host 找；库/头/包只在 sysroot 找
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

# 6) （可选）若要在配置期/CTest 里运行 ARM 二进制，启用 QEMU 模拟
# set(CMAKE_CROSSCOMPILING_EMULATOR /usr/bin/qemu-arm-static;-L;${CMAKE_SYSROOT})
```

构建：

```bash
cmake --toolchain "$PWD/toolchains/arm-linux-gnueabihf.cmake" -S . -B build-arm
cmake --build build-arm -j
# 验证产物架构（应显示 ARM）
file build-arm/your_executable      # -> ELF 32-bit LSB ... ARM, EABI5 ...
```

对 64 位 ARM（aarch64），把三元组换成 `aarch64-linux-gnu-`、`CMAKE_SYSTEM_PROCESSOR` 改 `aarch64` 即可，其余结构不变。

### 13.6.2 Android（NDK 自带工具链）

Android 的交叉编译由 NDK 深度支持，CMake 内置了对应平台模块。**首选用 NDK 自带的 `android.toolchain.cmake`**（与 Android Studio/Gradle 一致），也可只用 CMake 原生的 `CMAKE_ANDROID_*` 变量。

方式 A：直接用 NDK 自带工具链文件（最贴近官方、最省心）

```bash
# ANDROID_ABI / ANDROID_PLATFORM 是 NDK 工具链识别的选项
cmake -S . -B build-android \
  -DCMAKE_TOOLCHAIN_FILE=$ANDROID_NDK/build/cmake/android.toolchain.cmake \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-21 \
  -G Ninja
cmake --build build-android -j
```

- `ANDROID_ABI`：目标 ABI，常见 `arm64-v8a`、`armeabi-v7a`、`x86_64`、`x86`。
- `ANDROID_PLATFORM`：最低 Android API level，如 `android-21`（等价于直接写 `21`）。

方式 B：用 CMake 原生 Android 支持（自己写 toolchain，或全用命令行 `-D`）

CMake 看到 `CMAKE_SYSTEM_NAME=Android` 会自动搜索并使用 NDK；关键变量如下：

```cmake
# toolchains/android-arm64.cmake
set(CMAKE_SYSTEM_NAME      Android)
set(CMAKE_SYSTEM_VERSION   21)              # = Android API level（21）
set(CMAKE_ANDROID_ARCH_ABI arm64-v8a)       # 目标 ABI（不要手动设 SYSTEM_PROCESSOR）
set(CMAKE_ANDROID_NDK      /opt/android-ndk) # NDK 根目录
set(CMAKE_ANDROID_STL_TYPE c++_shared)       # C++ 运行库：LLVM libc++ 共享版
```

```bash
cmake --toolchain "$PWD/toolchains/android-arm64.cmake" -S . -B build-android -G Ninja
cmake --build build-android -j
```

关键 `CMAKE_ANDROID_*` 变量说明：

- **CMAKE_ANDROID_NDK**：NDK 安装根目录。也可用 `CMAKE_ANDROID_STANDALONE_TOOLCHAIN` 指向独立工具链。
- **CMAKE_SYSTEM_VERSION**：Android API level；不设时按 `CMAKE_ANDROID_API` / sysroot / NDK 最新可用值推导。
- **CMAKE_ANDROID_ARCH_ABI**：目标 ABI（`arm64-v8a` 等），CMake 据此自动设处理器与编译目标。
- **CMAKE_ANDROID_STL_TYPE**：C++ STL 变体。NDK r18+ 实际只剩 libc++ 两种有效值——`c++_shared` 与 `c++_static`；4.3.4 文档列出的历史取值（`gnustl_*`、`stlport_*`、`gabi++_*` 等）在新 NDK 上已不可用。默认值在提供 `gnustl` 的旧 NDK 上为 `gnustl_static`，否则为 `c++_static`。**新项目请显式选 `c++_shared` 或 `c++_static`**。

> 提醒：方式 A 的 `ANDROID_ABI`/`ANDROID_PLATFORM` 是 **NDK 工具链脚本**定义的选项名；方式 B 的 `CMAKE_ANDROID_ARCH_ABI`/`CMAKE_SYSTEM_VERSION` 是 **CMake 原生**变量名。两套不要混用。日常以方式 A 为主，与 Android 生态最一致。

### 13.6.3 嵌入式裸机（CMAKE_SYSTEM_NAME = Generic）

场景：为没有操作系统的 MCU（如 Cortex-M4 单片机）编译固件。关键点：用 `Generic` 表示"无操作系统"，并用 `STATIC_LIBRARY` 绕开"配置期探测要链接可执行文件"的障碍。

```cmake
# toolchains/arm-none-eabi.cmake  (Cortex-M4F 裸机示例)
# 1) Generic 表示目标无操作系统（裸机）；显式给出具体处理器
set(CMAKE_SYSTEM_NAME      Generic)
set(CMAKE_SYSTEM_PROCESSOR cortex-m4)

# 2) 关键：避免配置期探测去链接/运行可执行文件，只编静态库即可
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)

# 3) 裸机交叉工具链（arm-none-eabi 系列，none = 无 OS，eabi = 无系统调用约定）
set(TOOLCHAIN_ROOT /opt/gcc-arm-none-eabi)
set(CMAKE_C_COMPILER   ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-gcc)
set(CMAKE_CXX_COMPILER ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-g++)
set(CMAKE_ASM_COMPILER ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-gcc)  # 汇编也用 gcc 驱动

# 4) 显式指定 binutils（裸机工具链有时需要）
set(CMAKE_AR     ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-ar)
set(CMAKE_RANLIB ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-ranlib)
set(CMAKE_OBJCOPY ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-objcopy CACHE FILEPATH "")
set(CMAKE_SIZE    ${TOOLCHAIN_ROOT}/bin/arm-none-eabi-size    CACHE FILEPATH "")

# 5) 目标 CPU/浮点等编译选项（按你的 MCU 调整）
set(CPU_FLAGS "-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard")
set(CMAKE_C_FLAGS_INIT   "${CPU_FLAGS} -ffunction-sections -fdata-sections")
set(CMAKE_CXX_FLAGS_INIT "${CPU_FLAGS} -ffunction-sections -fdata-sections")
# 链接：丢弃未用段，指定你的链接脚本
set(CMAKE_EXE_LINKER_FLAGS_INIT "${CPU_FLAGS} -Wl,--gc-sections -T${CMAKE_CURRENT_LIST_DIR}/STM32F4.ld")

# 6) 裸机无 host 程序可找；库/头不走宿主
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```

```bash
cmake --toolchain "$PWD/toolchains/arm-none-eabi.cmake" -S . -B build-mcu -G Ninja
cmake --build build-mcu -j
# 生成可烧录的 .bin / .hex 通常用 objcopy（可在 CMakeLists 里加 POST_BUILD 自定义命令）
arm-none-eabi-objcopy -O binary build-mcu/firmware.elf build-mcu/firmware.bin
```

> 为什么 `STATIC_LIBRARY` 在裸机几乎是必需的：CMake 启用语言时会试编一个小程序。裸机下"链接成可执行"需要 `crt0`、链接脚本、`_start` 等，配置期往往尚未就绪，导致编译器检测失败、`project()` 直接报错。把探测降级为静态库即可让检测顺利通过。官方 Renesas CC-RL 示例也用了同样手法（`set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)`）。

### 13.6.4 WebAssembly / Emscripten

场景：把 C/C++ 编译到 WebAssembly，在浏览器或 Node.js 里运行。Emscripten 充当"交叉编译器"，它自带一个 `Emscripten.cmake` 工具链文件，并提供 `emcmake` 包装器自动注入它。

方式 A：用 `emcmake` 包装器（推荐，最省事）

`emcmake` 本质上就是在你的 `cmake` 调用前自动加上 `-DCMAKE_TOOLCHAIN_FILE=<emscripten>/cmake/Modules/Platform/Emscripten.cmake`，并设置好 `CMAKE_CROSSCOMPILING_EMULATOR` 为 Node.js（这样 CTest/`try_run` 可用 Node 运行 wasm）。

```bash
# 先激活 emsdk 环境
source /path/to/emsdk/emsdk_env.sh

# 用 emcmake 包装 configure；后续 build 用普通命令即可
emcmake cmake -S . -B build-wasm -G Ninja
cmake --build build-wasm -j
# 产物：.js（胶水/启动器）、.wasm（字节码），按目标设置可附带 .html
```

方式 B：手动指定 Emscripten 工具链文件（适合 CI / IDE kit，不便用包装器时）

```bash
cmake -S . -B build-wasm -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE="$EMSDK/upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake"
cmake --build build-wasm -j
```

- `Emscripten.cmake` 内部会设置 `CMAKE_SYSTEM_NAME` 为 `Emscripten`、定位 `emcc`/`em++`、并为"不感知 wasm 的老项目"模拟好一系列平台变量，使其能顺利通过 CMake 的平台检测。
- **务必把工具链文件放在命令行**，不要在 `CMakeLists.txt` 里用 `option()` 决定是否 include 它——那会陷入"先有鸡还是先有蛋"（toolchain 必须在工程被处理之前就确定）。
- 注意 A 与 B 的一个差异：`emcmake` 会额外把 `CMAKE_CROSSCOMPILING_EMULATOR` 指向 Node.js，而单用工具链文件**不会**。若用方式 B 又想让测试能跑 wasm，需自行设置该模拟器变量指向 `node`。

项目侧常用设置（在 `CMakeLists.txt` 里按 Emscripten 分支）：

```cmake
if(EMSCRIPTEN)
  # 例如生成 .html 便于直接在浏览器打开，或暴露导出函数
  set_target_properties(app PROPERTIES SUFFIX ".html")
  target_link_options(app PRIVATE
    "-sALLOW_MEMORY_GROWTH=1"
    "-sEXPORTED_RUNTIME_METHODS=['ccall','cwrap']")
endif()
```

### 13.6.5 Windows 上的交叉：MinGW 与 MSVC（简述）

**在 Windows 上为 Windows 编译**通常不算"交叉"——直接用对应生成器即可：

```bash
# 用 MinGW-w64 的 GCC（生成原生 Windows PE，无需 toolchain file）
cmake -S . -B build-mingw -G "MinGW Makefiles"
cmake --build build-mingw -j

# 用 MSVC（Visual Studio 生成器，按需选架构）
cmake -S . -B build-msvc -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc --config Release
```

真正的"交叉"出现在两类情况：

1) **在 Linux 上为 Windows 编译（MinGW-w64 交叉工具链）**——这是经典交叉，需要 toolchain file：

```cmake
# toolchains/linux-to-mingw64.cmake  (Linux 主机 -> Windows x64 目标)
set(CMAKE_SYSTEM_NAME      Windows)            # 目标是 Windows -> 开启交叉
set(CMAKE_SYSTEM_PROCESSOR x86_64)

set(TOOLPREFIX x86_64-w64-mingw32)
set(CMAKE_C_COMPILER   ${TOOLPREFIX}-gcc)
set(CMAKE_CXX_COMPILER ${TOOLPREFIX}-g++)
set(CMAKE_RC_COMPILER  ${TOOLPREFIX}-windres)   # Windows 资源编译器

# 把查找根钉到 MinGW 的目标前缀，避免误用 Linux 主机库
set(CMAKE_FIND_ROOT_PATH /usr/${TOOLPREFIX})
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

```bash
cmake --toolchain "$PWD/toolchains/linux-to-mingw64.cmake" -S . -B build-win -G Ninja
cmake --build build-win -j        # 产物为 .exe / .dll（PE 格式）
```

2) **同一台 Windows 上跨架构 MSVC**（如 x64 主机产出 ARM64 目标）——通常无需手写 toolchain，用生成器选项即可：

```bash
# Visual Studio 生成器：-A 指定目标架构
cmake -S . -B build-arm64 -G "Visual Studio 17 2022" -A ARM64
cmake --build build-arm64 --config Release
```

> 小结：Windows 目标的"交叉"主要是 **Linux→Windows（MinGW）** 用 toolchain file，以及 **MSVC 跨架构** 用 `-A`。在 Windows 本机用 MinGW/MSVC 编 Windows 程序属于本机编译，无需工具链文件。

## 13.7 常见坑

交叉编译的疑难，九成集中在"运行期检测"和"查找根"两类。逐一对照排查。

### 13.7.1 运行期检测在交叉环境失效

**症状**：`try_run`、`check_c_source_runs`、`check_cxx_symbol_exists`（其内部可能运行）等返回奇怪结果，或配置直接卡住/失败，提示无法运行刚编出来的程序。

**根因**：交叉编出来的二进制是目标架构，在宿主机上跑不起来，CMake 拿不到运行结果。

**对策（按优先级）**：
1. 能改用"只编译不运行"的检测就改（`check_*_compiles` 替代 `check_*_runs`）。
2. 在工具链里设 `CMAKE_CROSSCOMPILING_EMULATOR`（如 QEMU、Node），让 `try_run` 能真正运行。
3. 在工具链里**预置**这些探测的缓存结果（`set(VAR ... CACHE INTERNAL ...)` 及 `VAR__TRYRUN_OUTPUT`）。
4. 裸机/无法链接可执行的目标，配合 `CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY`。
5. 用 `if(CMAKE_CROSSCOMPILING)` 包住"需要运行目标"的逻辑，交叉时走替代分支。

### 13.7.2 find_package / find_library 找到宿主库

**症状**：链接报 ABI/架构不匹配（如 `incompatible ... skipping`、`wrong file format`），或运行时崩溃；细查发现链接到了宿主 `/usr/lib` 的 `.so`，而不是 sysroot 里的目标库。

**根因**：`CMAKE_FIND_ROOT_PATH_MODE_LIBRARY`/`PACKAGE`/`INCLUDE` 没设成 `ONLY`，于是 `find_*` 落到了宿主真实路径。

**对策**：
- 确保四个模式变量按 13.4.4 的模板设置（`PROGRAM=NEVER`，`LIBRARY/INCLUDE/PACKAGE=ONLY`）。
- 确认目标库确实在 `CMAKE_SYSROOT` / `CMAKE_STAGING_PREFIX` / `CMAKE_FIND_ROOT_PATH` 覆盖的前缀下。
- 用 `--debug-find`（或 `--debug-find-pkg=<name>`）打印查找过程，看 CMake 实际搜了哪些目录、为什么选中了某个文件。
- `pkg-config` 是重灾区：它默认读宿主的 `.pc`。交叉时设 `PKG_CONFIG_LIBDIR`/`PKG_CONFIG_SYSROOT_DIR` 指向目标 sysroot，或用交叉版 `arm-...-pkg-config`。

### 13.7.3 CMAKE_FIND_ROOT_PATH_MODE_* 配置不当

这是个"两头堵"的坑，配松配紧都会出问题：

- **配得太紧（全 `ONLY`）**：构建期需要的**宿主工具**（代码生成器、`protoc`、`pkg-config` 等）会找不到——因为它们装在宿主 `/usr/bin`，却被 `ONLY` 排除。**对策**：`CMAKE_FIND_ROOT_PATH_MODE_PROGRAM` 必须是 `NEVER`（让程序在宿主真实路径找）。
- **配得太松（用 `BOTH` 或漏设）**：库/头会回退到宿主路径，重新引发 13.7.2 的误链。
- **`PROGRAM` 误设为 `ONLY`**：典型错误。会导致"找不到宿主工具"，常表现为某个 `find_program` 失败进而整个配置失败。记住：**要被执行的东西在 host 找（NEVER/BOTH），要被链接/包含的东西在 sysroot 找（ONLY）**。

经验口诀：

> **PROGRAM 给 NEVER，LIBRARY/INCLUDE/PACKAGE 给 ONLY**——这是交叉编译查找根的默认安全配置；只有遇到"宿主上的 header-only 库"等特例，才把对应那一项放宽成 `BOTH`，并且**永远不要轻易放宽 LIBRARY**。

### 13.7.4 其他高频小坑

- **改了 toolchain 却不生效**：忘了删 build 目录（见 13.1.4）。任何对编译器/sysroot 的修改都应在干净 build 目录上重配。
- **相对路径 toolchain 找不到**：相对路径相对 build/源目录解释，跨目录调用易失配——一律用绝对路径或 `--toolchain "$PWD/..."`。
- **`CMAKE_SYSROOT` 写进了 `CMakeLists.txt`**：无效。它（连同 `CMAKE_C_COMPILER` 等）**只能在工具链文件里设**，因为要在编译器检测前生效。
- **Android 手动设了 `CMAKE_SYSTEM_PROCESSOR`**：会干扰 NDK 推导，应交给 `CMAKE_ANDROID_ARCH_ABI`/`ANDROID_ABI`。
- **Emscripten 方式 B 下测试跑不起来**：单用工具链文件不会设 `CMAKE_CROSSCOMPILING_EMULATOR`，需自行指向 `node`，或干脆改用 `emcmake`。

## 13.8 以 Windows 为宿主的交叉编译实例

前面 13.6 的实例多以 Linux 工作站为宿主。但 Windows 本身就是一台合格的交叉构建机：VS 自带跨架构后端、NDK/Emscripten/LLVM 都有官方 Windows 发行版。本节专讲「**构建机是 Windows、目标各异**」的落地配方，每个目标给 toolchain file 或命令 + 要点，力求精炼可复现。与第 19 章的全平台/反向交叉矩阵互补——这里只覆盖「Windows 出发」这一行。

> 通用前提（与目标无关，先记住）：
> - **`CMAKE_SYSTEM_NAME` 是交叉总开关**——一旦在 toolchain file 里 `set()` 它（哪怕值还是 `Windows`），即进入交叉模式、`CMAKE_CROSSCOMPILING=TRUE`。同平台异架构（如 x64→ARM64 用 VS 生成器）则靠 `-A` 选架构，**无需**设它、不算严格意义的交叉。
> - **目标二进制大多无法在 Windows 宿主直接运行**，配置期探测要按 13.5 处理：裸机/无法链接可执行时设 `CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY`；需要 `try_run`/CTest 跑目标程序时设 `CMAKE_CROSSCOMPILING_EMULATOR`（如 Node 跑 wasm）。
> - **查找根模式照旧用 13.4.4 的模板**：`CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER`（构建工具在 Windows 宿主上找），`LIBRARY/INCLUDE/PACKAGE ONLY`（库/头/包只在目标 sysroot 找），避免误用宿主 MSVC/MinGW 的库。

### 13.8.1 Windows(x64) → Windows ARM64（VS 生成器，同平台异架构）

最简单的一类：宿主与目标同为 Windows，只是 CPU 架构从 x64 变 ARM64。Visual Studio 自带 ARM64 交叉后端，**用生成器的 `-A` 选目标架构即可，完全不需要 toolchain file，也不必设 `CMAKE_SYSTEM_NAME`**。

```bash
# -A 指定目标架构；需已安装 VS 的「ARM64 生成工具」组件
cmake -S . -B build -G "Visual Studio 17 2022" -A ARM64
cmake --build build --config Release
# 产物为 ARM64 的 .exe/.dll；可用 dumpbin /headers 看 machine 字段确认为 ARM64
```

- `-A` 可取 `x64` / `Win32` / `ARM64` / `ARM64EC`。这属于「同 OS 跨架构」，CMake 仍视为本机式构建（`CMAKE_CROSSCOMPILING` 为 `FALSE`），但产出的二进制确为 ARM64。
- 若用 Ninja 而非 VS 生成器，则需先进入对应架构的「ARM64 Native/Cross Tools 命令提示符」让 `cl.exe` 指向 ARM64 后端，再 `-G Ninja` 配置。

### 13.8.2 Windows → Android（NDK 自带工具链）

与 13.6.2 同一套 NDK 工具链，只是宿主换成 Windows——NDK 的 Windows 发行版会自动选用 `windows-x86_64` 这套宿主侧可执行（回顾 13.2.2 的 `CMAKE_HOST_WIN32` 分支即此理）。命令形态不变，注意 Windows 下用 `%NDK%` 环境变量与反斜杠/正斜杠均可（CMake 接受正斜杠最稳）：

```bat
cmake -S . -B build ^
  -DCMAKE_TOOLCHAIN_FILE=%NDK%/build/cmake/android.toolchain.cmake ^
  -DANDROID_ABI=arm64-v8a ^
  -DANDROID_PLATFORM=android-24 ^
  -G Ninja
cmake --build build -j
```

- `%NDK%` 指向 NDK 安装根（如 `C:/Android/Sdk/ndk/26.3.11579264`）；`^` 是 cmd 的续行符（PowerShell 用反引号 `` ` ``）。
- `ANDROID_ABI`=`arm64-v8a`（亦可 `armeabi-v7a`/`x86_64` 等），`ANDROID_PLATFORM`=`android-24`（最低 API level，等价于写 `24`）。其余 `CMAKE_ANDROID_*` 原生变量见 13.6.2，两套选项不要混用。
- 建议配 Ninja 生成器（NDK 官方推荐）；用 NDK 自带的 `prebuilt/windows-x86_64/bin/ninja.exe` 或自行安装均可。

### 13.8.3 Windows → WebAssembly（Emscripten）

与 13.6.4 一致，Emscripten 有完整 Windows 发行版，**首选 `emcmake` 包装器**自动注入 `Emscripten.cmake` 并把 `CMAKE_CROSSCOMPILING_EMULATOR` 指向 Node（于是 CTest/`try_run` 能用 Node 跑 wasm）：

```bat
:: 先激活 emsdk 环境（Windows 用 .bat，非 .sh）
emsdk_env.bat

:: emcmake 包装 configure；build 用普通命令
emcmake cmake -S . -B build -G Ninja
cmake --build build
:: 产物：.wasm（字节码）+ .js（胶水/启动器），按目标设置可附带 .html
```

- Windows 上激活环境用 `emsdk_env.bat`（对应 Linux 的 `emsdk_env.sh`）。
- 若不便用包装器（CI/IDE kit），可手动 `-DCMAKE_TOOLCHAIN_FILE=%EMSDK%/upstream/emscripten/cmake/Modules/Platform/Emscripten.cmake`；但此法**不会**自动设模拟器，要跑 wasm 测试需自行把 `CMAKE_CROSSCOMPILING_EMULATOR` 指向 `node`。
- 务必把 wasm 用 Ninja/Makefile 类单配置生成器构建，不要用 VS 生成器。

### 13.8.4 Windows → Linux（两条路：LLVM 原生交叉 / 经 WSL）

在 Windows 上产出 Linux ELF，有两条主流路径，按是否愿意装 WSL 二选一。

**路线一（详写）：LLVM/clang + lld 原生交叉。** clang 是「单编译器靠 `--target` 切目标」的典型（回顾 13.3.2），配合 `lld` 链接器与一份 Linux sysroot，即可在纯 Windows 上直接产出 ELF，无需 WSL。关键是用 `CMAKE_<LANG>_COMPILER_TARGET` 给三元组、`CMAKE_SYSROOT` 指向 Linux 根：

```cmake
# toolchains/win-to-linux-clang.cmake  (Windows 宿主 -> Linux x86_64 目标)
set(CMAKE_SYSTEM_NAME      Linux)              # 目标是 Linux -> 开启交叉
set(CMAKE_SYSTEM_PROCESSOR x86_64)

set(triple x86_64-linux-gnu)
set(CMAKE_C_COMPILER          clang)
set(CMAKE_C_COMPILER_TARGET   ${triple})       # = 给 clang 传 --target=x86_64-linux-gnu
set(CMAKE_CXX_COMPILER        clang++)
set(CMAKE_CXX_COMPILER_TARGET ${triple})
set(CMAKE_LINKER_TYPE         LLD)             # 用 lld（跨平台链接器，免装 GNU ld）

# 一份 Linux 根文件系统（含目标的 libc/头文件），从目标机或镜像拷到本地
set(CMAKE_SYSROOT "C:/sysroots/ubuntu-x86_64")

# 查找根模板：工具在 Windows 宿主找，库/头/包只在 sysroot 找
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

```bat
cmake --toolchain "%CD%/toolchains/win-to-linux-clang.cmake" -S . -B build -G Ninja
cmake --build build -j
:: 产物为 Linux ELF；拷到目标机或用 WSL/QEMU 验证运行
```

要点：sysroot 必须备齐目标的 `libc`/头文件（最易缺失的一环）；`CMAKE_SYSROOT` 同 13.4.1 只能写在 toolchain file 里；若要在配置期/CTest 真跑 ELF，可把 `CMAKE_CROSSCOMPILING_EMULATOR` 指向 QEMU 用户态或 `wsl`。

**路线二（一句话）：** 直接在 **WSL** 内当作一台 Linux 主机做本机编译（装好 gcc/clang 后按 13.6 的本机流程走），对 Windows 而言这是最省心的「伪交叉」，代价是依赖 WSL 环境。

末尾提示：完整的各平台矩阵与**反向交叉**（如 Linux→Windows MinGW、macOS 通用二进制等）及横向对照见 [[42.Cmake/19 - 跨平台实战与平台差异大全.md|第 19 章]]。

## 本章小结

- **工具链文件**是交叉编译的核心抽象：把"目标平台 + 工具链"的描述从项目里剥离成独立 `.cmake`，用 `-DCMAKE_TOOLCHAIN_FILE=...` 或 `--toolchain`（3.21+）传入，**只在某 build 目录首次配置时生效**——改它必须删 build 目录重配。
- **`CMAKE_SYSTEM_NAME` 是总开关**：一旦设置即开启交叉编译并令 `CMAKE_CROSSCOMPILING=TRUE`；配合 `CMAKE_SYSTEM_PROCESSOR`/`CMAKE_SYSTEM_VERSION` 描述目标，`CMAKE_HOST_SYSTEM_*` 描述构建机。
- **指定编译器**：GCC 用带三元组前缀的编译器名（自动带出 binutils）；Clang/qcc 用 `CMAKE_<LANG>_COMPILER_TARGET` 设目标三元组，必要时用 `CMAKE_<LANG>_COMPILER_EXTERNAL_TOOLCHAIN` 借用 GCC 工具链。
- **sysroot 与查找根**：`CMAKE_SYSROOT` 指目标根文件系统，`CMAKE_STAGING_PREFIX` 指宿主暂存安装地，二者自动并入查找根；四个 `CMAKE_FIND_ROOT_PATH_MODE_*` 用 `NEVER/ONLY/BOTH` 精确控制查找——**PROGRAM=NEVER，LIBRARY/INCLUDE/PACKAGE=ONLY** 是安全模板。
- **配置期探测**：交叉环境无法运行目标二进制，用 `CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY` 跳过链接可执行（裸机必备），用 `CMAKE_CROSSCOMPILING_EMULATOR` 让 `try_run`/CTest 经模拟器运行，或预置探测缓存结果。
- **五类实例**：ARM Linux（`arm-linux-gnueabihf-gcc` + sysroot）、Android（首选 NDK 自带 `android.toolchain.cmake` + `ANDROID_ABI`/`ANDROID_PLATFORM`，或原生 `CMAKE_ANDROID_*`）、裸机（`Generic` + `STATIC_LIBRARY` + `arm-none-eabi`）、Emscripten（`emcmake` 或 `Emscripten.cmake`）、Windows 交叉（Linux→MinGW 用 toolchain，MSVC 跨架构用 `-A`）。
- **常见坑**集中在"运行期检测失效"与"find 找到宿主库"两类，核对查找根模式与运行模拟器即可解决绝大多数问题。
