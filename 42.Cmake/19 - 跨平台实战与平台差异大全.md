## 19.1 跨平台核心理念：让 CMake 抽象差异，而不是你

写跨平台 CMake 的第一性原理只有一句话：**把"平台差异"交给 CMake 的抽象层，你只描述"意图"。** 凡是你在 `CMakeLists.txt` 里硬编码的平台细节，都是未来在另一个平台上爆炸的雷。

### 19.1.1 五条铁律

**铁律一：不硬编码编译器、不硬编码编译/链接 flag。**
用 target 级命令 + 编译器抽象，而不是直接往 `CMAKE_CXX_FLAGS` 里塞 `-std=c++20`、`/MD`、`-fPIC`。

```cmake
# ❌ 反面：把 GCC 的写法钉死，MSVC/Clang-cl 立刻挂
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -std=c++20 -Wall -fPIC")

# ✅ 正面：描述意图，CMake 翻译成每个编译器的方言
target_compile_features(app PRIVATE cxx_std_20)        # 选标准 → 各编译器自己映射 /std:c++20 或 -std=c++20
set_target_properties(app PROPERTIES POSITION_INDEPENDENT_CODE ON)  # -fPIC，MSVC 上自动忽略
target_compile_options(app PRIVATE
  $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall -Wextra>
  $<$<CXX_COMPILER_ID:MSVC>:/W4>)
```

**铁律二：不硬编码文件扩展名。** `.exe`/`.dll`/`.dylib`/`.so`/`.lib` 全部由 CMake 根据平台决定，你引用产物时用**生成器表达式**而非字面量。

```cmake
# ❌  copy ${CMAKE_BINARY_DIR}/mylib.dll  → 换平台即错
# ✅  用生成器表达式拿到"当前平台下这个 target 的真实文件"
add_custom_command(TARGET app POST_BUILD
  COMMAND ${CMAKE_COMMAND} -E copy $<TARGET_FILE:mylib> $<TARGET_FILE_DIR:app>)
```

**铁律三：不硬编码安装路径。** 不要写 `DESTINATION lib` 或 `DESTINATION C:/Program Files/...`，统一用 **`GNUInstallDirs`** 提供的 `CMAKE_INSTALL_BINDIR` / `CMAKE_INSTALL_LIBDIR` / `CMAKE_INSTALL_INCLUDEDIR`，它会在 64 位 Linux 上自动给出 `lib64`、在 Debian 上给出 `lib/x86_64-linux-gnu` 等正确值。

**铁律四：平台分支用生成器表达式 > `if()`。** 生成器表达式在**生成阶段**对每个配置/平台分别求值，天然支持多配置生成器（Xcode / Visual Studio）；`if(WIN32)` 在配置阶段只跑一次。能用 `$<PLATFORM_ID:>`、`$<CXX_COMPILER_ID:>` 解决的，优先用它们。

**铁律五：差异集中在一处。** 把所有"if 平台 then …"收拢进少数几个 `cmake/Platform*.cmake` 模块或一段集中的 block，不要让平台判断散落在每个子目录。后面第 9 节的真·跨平台工程就是这么组织的。

### 19.1.2 现代 target-based 的跨平台优势

target-based 写法（`target_link_libraries` / `target_include_directories` / `target_compile_definitions` 携带 `PUBLIC|PRIVATE|INTERFACE`）本身就是最强的跨平台武器：依赖的传递、头文件路径、宏定义都随 target 流动，换平台时**绝大多数 target 描述一字不改**，只在少数平台相关 target 上挂条件属性即可。本章所有示例一律 target-based，不再出现 `include_directories()` / `link_directories()` 这类全局污染命令。

## 19.2 平台判定与条件分支

### 19.2.1 平台判定变量速查表

CMake 在 `project()` 之后自动设置一批平台布尔量与字符串量。下表是"如何判定每个平台"的权威速查：

| 想判定的平台/环境 | 推荐条件 | 说明 |
|---|---|---|
| Windows（任意工具链） | `if(WIN32)` | MSVC、MinGW、Clang-cl、Cygwin 之外的 Win 均为真；Cygwin 下 `WIN32` 为假 |
| 类 Unix（含 macOS/Linux） | `if(UNIX)` | macOS 上 `UNIX` 和 `APPLE` **同时为真** |
| macOS / iOS / 任意 Apple | `if(APPLE)` | 仅表示"Apple 平台"，不区分桌面与移动 |
| Linux（4.0+ 内置） | `if(LINUX)` | CMake ≥ 3.25 提供；老版本用 `CMAKE_SYSTEM_NAME STREQUAL "Linux"` |
| 仅 macOS（排除 iOS） | `if(APPLE AND NOT IOS)` 或 `CMAKE_SYSTEM_NAME STREQUAL "Darwin"` | `Darwin` 专指 macOS |
| iOS | `if(IOS)` 或 `CMAKE_SYSTEM_NAME STREQUAL "iOS"` | 交叉编译时由 toolchain/`-DCMAKE_SYSTEM_NAME=iOS` 触发 |
| Android | `if(ANDROID)` 或 `CMAKE_SYSTEM_NAME STREQUAL "Android"` | NDK 工具链设置 |
| MSVC 编译器 | `if(MSVC)` | Clang-cl 模拟 MSVC 时 `MSVC` 也为真（`MSVC` 描述"前端是否 cl 兼容"） |
| MinGW | `if(MINGW)` | GCC for Windows |
| Cygwin | `if(CYGWIN)` | |
| Emscripten / WASM | `if(EMSCRIPTEN)` 或 `CMAKE_SYSTEM_NAME STREQUAL "Emscripten"` | `emcmake` 设置 |
| 裸机/无 OS | `CMAKE_SYSTEM_NAME STREQUAL "Generic"` | ARM Cortex-M 等交叉编译目标 |
| 是否在交叉编译 | `if(CMAKE_CROSSCOMPILING)` | toolchain 设置了 `CMAKE_SYSTEM_NAME` 且与宿主不同则为真 |

**`CMAKE_SYSTEM_NAME`：详解。** 这是**目标系统**名（不是宿主），原生构建时等于宿主，交叉编译时由 toolchain 文件设定。常见取值：`Windows` / `Darwin`（macOS）/ `Linux` / `Android` / `iOS` / `Generic`（裸机）/ `Emscripten` / `QNX` 等。它是所有平台判定的"真相之源"——上面那些布尔量大多由它推导。

> ⚠️ **宿主 vs 目标，别搞混。** `CMAKE_SYSTEM_NAME` = 目标；`CMAKE_HOST_SYSTEM_NAME` = 你正在敲命令的机器。交叉编译里这两者不同。同理还有 `CMAKE_SYSTEM_PROCESSOR`（目标 CPU）与 `CMAKE_HOST_SYSTEM_PROCESSOR`（宿主 CPU）。

**`MSVC` vs `WIN32`：常见坑。** `WIN32` 表示"目标是 Windows"，`MSVC` 表示"前端是否 cl 兼容"。在 Windows 上用 MinGW 时 `WIN32` 真、`MSVC` 假；用 Clang-cl 时两者皆真。要区分运行时库/链接器行为时判 `MSVC`，要区分系统 API 时判 `WIN32`。

### 19.2.2 生成器表达式平台分支

`$<PLATFORM_ID:...>` 和 `$<CXX_COMPILER_ID:...>` 是 `if()` 的"生成阶段"对应物，可逐目标、逐配置精确投放：

```cmake
target_compile_definitions(app PRIVATE
  $<$<PLATFORM_ID:Windows>:MYAPP_WINDOWS>
  $<$<PLATFORM_ID:Darwin>:MYAPP_MACOS>
  $<$<PLATFORM_ID:Linux>:MYAPP_LINUX>)

# 可一次匹配多个平台（逗号分隔 = OR）
target_link_libraries(app PRIVATE
  $<$<PLATFORM_ID:Linux,Darwin>:pthread>)

# 按编译器投放警告 flag
target_compile_options(lib PRIVATE
  $<$<CXX_COMPILER_ID:MSVC>:/permissive- /W4>
  $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:-Wall -Wextra -Wpedantic>)
```

> `PLATFORM_ID` 取的就是 `CMAKE_SYSTEM_NAME`（`Windows`/`Darwin`/`Linux`/…）。`CXX_COMPILER_ID` 常见值：`MSVC` / `GNU` / `Clang` / `AppleClang`（macOS 自带的 Clang，**与上游 `Clang` 是两个 ID**，别只判 `Clang` 漏掉 macOS）/ `Intel` / `IntelLLVM`。

### 19.2.3 选 `if()` 还是生成器表达式？

| 场景 | 选择 | 原因 |
|---|---|---|
| 决定**是否定义某个 target**、是否进入子目录 | `if()` | 配置阶段决策，target 还不存在 |
| 给已存在 target 加编译/链接/宏，且想支持多配置生成器 | 生成器表达式 | 逐配置/逐平台精确求值，Xcode/VS 多配置下正确 |
| 只为单配置生成器（Ninja/Makefiles）且逻辑简单 | 两者均可 | `if()` 更直观 |
| `find_package` 等只能在配置期做的事 | `if()` | 没有生成期等价物 |

## 19.3 Windows 平台实战（完整工程）

Windows 是差异最大、坑最多的平台：三套主流工具链、DLL 显式导出、运行时 DLL 部署、多种打包格式。

### 19.3.1 三套工具链对比

| 维度 | **MSVC**（cl.exe） | **MinGW-w64**（gcc/g++） | **Clang-cl** |
|---|---|---|---|
| 来源 | Visual Studio / Build Tools | MSYS2 / 独立发行 | LLVM，模拟 cl 命令行 |
| `CMAKE_CXX_COMPILER_ID` | `MSVC` | `GNU` | `MSVC`（前端兼容）/ 也可 `Clang` 取决于驱动 |
| `MSVC` 变量 | 真 | 假 | 真 |
| ABI / 运行时库 | MSVC CRT（`/MD` `/MT`） | MinGW 运行时（libstdc++ + 自带 DLL） | MSVC CRT |
| 默认生成器 | Visual Studio 17 2022 | Ninja / MinGW Makefiles | Ninja |
| 符号导出 | 必须显式 `__declspec` 或 `WINDOWS_EXPORT_ALL_SYMBOLS` | 默认全导出（可显式收紧） | 同 MSVC |
| 与 MSVC 库链接 | 原生兼容 | **不兼容**（不同 ABI） | 原生兼容 |
| 适用 | 主流 Windows 开发、与 VS 生态/vcpkg 集成 | 想用 GCC、纯开源工具链 | 想要 Clang 诊断 + MSVC ABI 兼容 |

**生成器与架构选择（MSVC / VS 生成器专属）：**

**`-A <平台>`：详解。** 指定 VS 生成器的目标架构，取值 `Win32` | `x64` | `ARM64` | `ARM64EC`。**只对 Visual Studio 生成器有效**，Ninja 不认（Ninja 下架构由所选 cl 的环境决定，需在 "x64 Native Tools" 命令行里跑）。

**`-T <工具集>`：详解。** 指定 VS 平台工具集 / 主机工具链，如 `-T v143`（VS2022 工具集）、`-T host=x64`（用 64 位 cl，避免 32 位 cl 内存不足）、`-T ClangCL`（在 VS 生成器里切到 Clang-cl）、`-T fortran=ifx` 等。

```bash
# MSVC + VS 生成器，显式 64 位、64 位主机工具链
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -T host=x64
cmake --build build --config Release

# 同源码生成 ARM64
cmake -S . -B build-arm64 -G "Visual Studio 17 2022" -A ARM64
cmake --build build-arm64 --config Release

# 在 VS 生成器内切换到 Clang-cl 工具集
cmake -S . -B build-clangcl -G "Visual Studio 17 2022" -A x64 -T ClangCL

# Ninja + MSVC（须在 "x64 Native Tools Command Prompt for VS 2022" 中执行）
cmake -S . -B build-ninja -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-ninja

# Ninja + MinGW-w64（MSYS2 的 mingw64 环境）
cmake -S . -B build-mingw -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-mingw
```

### 19.3.2 DLL 符号导出：三种方式

Windows DLL **默认不导出任何符号**（与 ELF 默认全可见相反）。你必须告诉链接器哪些符号对外可见。

**方式一（推荐）：`GenerateExportHeader` 自动生成导出宏。** CMake 模块根据 target 自动生成一个 `<target>_export.h`，里面定义形如 `MYLIB_EXPORT` 的宏：编译该库时展开为 `__declspec(dllexport)`，被别人 `#include` 使用时展开为 `__declspec(dllimport)`，在 GCC/Clang 上展开为 `__attribute__((visibility("default")))`。**一套头文件三平台通用**，这是现代标准做法。

```cmake
# CMakeLists.txt 片段
include(GenerateExportHeader)

add_library(mylib SHARED src/mylib.cpp)
add_library(mylib::mylib ALIAS mylib)

# 全局默认隐藏，仅显式标注者导出（与 Windows 行为对齐，跨平台一致）
set_target_properties(mylib PROPERTIES
  CXX_VISIBILITY_PRESET hidden
  VISIBILITY_INLINES_HIDDEN ON)

# 生成 ${CMAKE_CURRENT_BINARY_DIR}/mylib_export.h，含 MYLIB_EXPORT 宏
generate_export_header(mylib)

target_include_directories(mylib PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}>   # 让使用者能 #include "mylib_export.h"
  $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>)
```

```cpp
// include/mylib.hpp —— 业务头，统一用生成的宏
#pragma once
#include "mylib_export.h"      // 由 generate_export_header 生成

MYLIB_EXPORT int add(int a, int b);   // 跨平台导出
class MYLIB_EXPORT Calculator {        // 整类导出
public:
  int square(int x) const;
};
```

> 进阶：`generate_export_header(mylib BASE_NAME myapi EXPORT_MACRO_NAME MY_API EXPORT_FILE_NAME myapi_export.h)` 可自定义宏名与文件名；它还会生成 `MYLIB_NO_EXPORT`、`MYLIB_DEPRECATED` 等配套宏。

**方式二：手写 `__declspec`。** 不依赖模块时的原始写法，理解原理用：

```cpp
#if defined(_WIN32)
#  if defined(MYLIB_BUILD)        // 编译 DLL 时由 CMake 定义
#    define MYLIB_API __declspec(dllexport)
#  else
#    define MYLIB_API __declspec(dllimport)
#  endif
#else
#  define MYLIB_API __attribute__((visibility("default")))
#endif
```
```cmake
target_compile_definitions(mylib PRIVATE MYLIB_BUILD)   # 只在构建库自身时定义
```

**方式三（偷懒应急）：`WINDOWS_EXPORT_ALL_SYMBOLS`。** 让 CMake 自动导出 DLL 的**所有非数据**符号，免写任何宏。适合快速移植大型旧代码库，但导出面失控、二进制更大、**不导出数据符号**（全局变量仍需手动 `__declspec(dllexport)`）。

```cmake
add_library(legacy SHARED ${LEGACY_SOURCES})
set_target_properties(legacy PROPERTIES WINDOWS_EXPORT_ALL_SYMBOLS ON)
```

### 19.3.3 运行时 DLL 依赖拷贝

Windows 没有 RPATH，可执行文件运行时靠 `PATH` 和**同目录**找 DLL。开发/测试时最干净的办法：用 `$<TARGET_RUNTIME_DLLS>` 把所有依赖 DLL 拷到 exe 旁边。

**`$<TARGET_RUNTIME_DLLS:tgt>`：详解。** 生成器表达式，展开为 `tgt` 运行时依赖的所有 DLL 的完整路径列表（递归解析 target 间依赖）。要求 `tgt` 是可执行文件、`SHARED` 库或 `MODULE` 库。配合 `add_custom_command(POST_BUILD)` + `COMMAND_EXPAND_LISTS`（让分号列表展开成多参数）使用：

```cmake
add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE mylib::mylib foo::foo)   # 这些库的 DLL 都会被收集

if(WIN32)
  add_custom_command(TARGET app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy -t $<TARGET_FILE_DIR:app> $<TARGET_RUNTIME_DLLS:app>
    COMMAND_EXPAND_LISTS                      # 关键：把 DLL 列表展开为多个参数
    COMMENT "Copying runtime DLLs next to app.exe")
endif()
```

> 注意：`$<TARGET_RUNTIME_DLLS>` 解析的是**已知 target**（含 imported target，如 `find_package` 来的）依赖的 DLL；系统 DLL（kernel32 等）不会被拷。若 imported target 没正确设置 `IMPORTED_LOCATION`，可能收集不全。安装阶段则用 `install(RUNTIME_DEPENDENCY_SET ...)` 或 `file(GET_RUNTIME_DEPENDENCIES ...)` 做更严谨的部署。

### 19.3.4 vcpkg 集成

[vcpkg](https://github.com/microsoft/vcpkg) 是 Windows 上事实标准的 C++ 包管理器（也支持 macOS/Linux）。集成靠它提供的 toolchain 文件 + manifest（`vcpkg.json`）。

`vcpkg.json`（与顶层 `CMakeLists.txt` 同目录）：
```json
{
  "name": "myapp",
  "version": "1.0.0",
  "dependencies": ["fmt", "spdlog", "zlib"]
}
```

配置时挂上 vcpkg toolchain（推荐用环境变量 `VCPKG_ROOT` 或写进 preset）：
```bash
cmake -S . -B build \
  -DCMAKE_TOOLCHAIN_FILE="%VCPKG_ROOT%/scripts/buildsystems/vcpkg.cmake" \
  -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

`CMakeLists.txt` 里照常 `find_package`，无需关心 vcpkg 安装路径：
```cmake
find_package(fmt CONFIG REQUIRED)
find_package(spdlog CONFIG REQUIRED)
target_link_libraries(app PRIVATE fmt::fmt spdlog::spdlog)
```

> 用 manifest 模式时，配置阶段 vcpkg 会自动按 `vcpkg.json` 安装依赖。`VCPKG_TARGET_TRIPLET`（如 `x64-windows`、`x64-windows-static`）控制动/静态链接与架构；写进 cache 变量或 preset 里。

### 19.3.5 NSIS / WIX 安装包

Windows 安装程序两大 CPack 生成器：**NSIS**（脚本化、轻量、最常见）与 **WIX**（生成 MSI，企业部署/组策略友好，需 WiX Toolset）。

```cmake
# 安装规则（GNUInstallDirs 提供跨平台目录）
include(GNUInstallDirs)
install(TARGETS app mylib
  RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}      # app.exe + DLL
  LIBRARY DESTINATION ${CMAKE_INSTALL_BINDIR}      # Windows 上 DLL 归 RUNTIME，但显式写无妨
  ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR})     # 导入库 .lib

# CPack 公共元数据
set(CPACK_PACKAGE_NAME "MyApp")
set(CPACK_PACKAGE_VENDOR "Acme")
set(CPACK_PACKAGE_VERSION "1.0.0")
set(CPACK_PACKAGE_INSTALL_DIRECTORY "MyApp")

if(WIN32)
  set(CPACK_GENERATOR "NSIS")              # 或 "WIX"，或两者 "NSIS;WIX"
  # NSIS 专属
  set(CPACK_NSIS_MODIFY_PATH ON)                       # 允许把安装目录加入 PATH
  set(CPACK_NSIS_ENABLE_UNINSTALL_BEFORE_INSTALL ON)
  set(CPACK_PACKAGE_EXECUTABLES "app" "MyApp")         # 开始菜单快捷方式
  # WIX 专属（启用 WIX 时）
  set(CPACK_WIX_UPGRADE_GUID "PUT-A-FIXED-GUID-HERE")  # 升级用，必须固定不变
endif()

include(CPack)   # 必须最后 include
```

```bash
# 构建后打包
cmake --build build --config Release
cpack --config build/CPackConfig.cmake -C Release    # 生成 MyApp-1.0.0-win64.exe (NSIS) 或 .msi (WIX)
# 或：  cd build && cpack -C Release
```

**预期产物**：`build/_CPack_Packages/...` 下生成 `MyApp-1.0.0-win64.exe`（NSIS 安装器）或 `MyApp-1.0.0-win64.msi`（WIX）。NSIS 需机器装有 NSIS；WIX 需装 WiX Toolset 且 `candle`/`light` 在 PATH。

## 19.4 macOS 平台实战（完整工程）

macOS 的特色：Apple Clang + Xcode 生成器、Universal Binary（一份二进制装两种架构）、基于 `@rpath` 的动态库定位、`.app`/`.framework` Bundle、代码签名。

### 19.4.1 编译器与生成器

macOS 默认编译器是 **Apple Clang**（`CMAKE_CXX_COMPILER_ID` = `AppleClang`，注意不是 `Clang`）。生成器二选一：

```bash
# Ninja（命令行 CI 首选，单配置）
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build

# Xcode（多配置，调试/签名/打包体验最好）
cmake -S . -B build -G Xcode
cmake --build build --config Release
```

### 19.4.2 Universal Binary（arm64 + x86_64）

**`CMAKE_OSX_ARCHITECTURES`：详解。** 分号分隔的目标架构列表。设为 `"arm64;x86_64"` 即生成同时含 Apple Silicon 与 Intel 的**胖二进制（Universal 2）**。**必须在 `project()` 之前**（通常经命令行/toolchain/preset 传入），因为它影响编译器探测。

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_OSX_ARCHITECTURES="arm64;x86_64" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build
# 验证：
lipo -info build/app        # → Architectures in the fat file: app are: x86_64 arm64
```

> Xcode 生成器下若想强制每种架构都构建（而非只构建活动架构），设 `-DCMAKE_XCODE_ATTRIBUTE_ONLY_ACTIVE_ARCH=NO`。

### 19.4.3 部署目标与 SDK

**`CMAKE_OSX_DEPLOYMENT_TARGET`：详解。** 最低支持的 macOS 版本（如 `12.0`）。低于此版本的 API 调用会告警/链接失败；它写进二进制的 `LC_BUILD_VERSION`。**`project()` 之前设置。**

**`CMAKE_OSX_SYSROOT`：详解。** 使用的 SDK，可为 `macosx`（默认，当前 Xcode 的 macOS SDK）、`iphoneos`、`iphonesimulator`，或绝对 SDK 路径。交叉到 iOS 时常配合 `CMAKE_SYSTEM_NAME=iOS` 由 CMake 自动选。

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=12.0 \
  -DCMAKE_OSX_SYSROOT=macosx \
  -DCMAKE_OSX_ARCHITECTURES="arm64;x86_64"
```

### 19.4.4 @rpath / install_name / RPATH

macOS 动态库（`.dylib`）内嵌一个 **install_name**——它告诉链接它的程序"运行时去哪找我"。现代做法是把 install_name 设为 `@rpath/libfoo.dylib`，再由可执行文件提供一组 **rpath** 去解析 `@rpath`。

**`MACOSX_RPATH`：详解。** target 属性，为 `TRUE`（CMake 默认即开）时该 `.dylib` 的 install_name 目录部分设为 `@rpath`。由变量 `CMAKE_MACOSX_RPATH` 初始化。这是让库可重定位的前提。

**`CMAKE_INSTALL_RPATH`：详解。** 安装后二进制里写入的 rpath 列表，用于解析 `@rpath`。macOS 上常设 `@loader_path/../lib`（相对可执行文件自身定位，类似 Linux 的 `$ORIGIN`）。

**`CMAKE_BUILD_RPATH`：详解。** **构建树**里的额外 rpath，让你不安装就能直接跑 build 目录里的可执行文件。

**`INSTALL_NAME_DIR` / `CMAKE_INSTALL_NAME_DIR`：详解。** 显式覆盖 install_name 的目录部分（替代 `@rpath`）。一般不需要，除非要装到固定绝对路径。

```cmake
# 让安装后的 app 能在 ../lib 找到自带 dylib（macOS）
if(APPLE)
  set_target_properties(app PROPERTIES
    INSTALL_RPATH "@loader_path/../lib"
    BUILD_WITH_INSTALL_RPATH OFF)   # 构建期用构建 rpath，安装期重写为 INSTALL_RPATH
endif()
# 库自身保持 @rpath（默认行为，无需额外设置 MACOSX_RPATH）
```

> 验证：`otool -L build/app`（看依赖的 install_name）、`otool -l build/app | grep -A2 LC_RPATH`（看 rpath 列表）。

### 19.4.5 .app Bundle 与 Framework

**`MACOSX_BUNDLE`：详解。** 可执行 target 属性，为真时产物是 `App.app/` 目录结构（GUI 应用标准形态），CMake 自动生成 `Info.plist`。

**`FRAMEWORK`：详解。** 库 target 属性，为真时产物是 `Foo.framework/` Bundle（含头文件、资源、版本符号链接）。

```cmake
# GUI 应用打成 .app
add_executable(MyApp MACOSX_BUNDLE src/main.mm)
set_target_properties(MyApp PROPERTIES
  MACOSX_BUNDLE_BUNDLE_NAME "MyApp"
  MACOSX_BUNDLE_GUI_IDENTIFIER "com.acme.myapp"
  MACOSX_BUNDLE_BUNDLE_VERSION "1.0.0"
  MACOSX_BUNDLE_SHORT_VERSION_STRING "1.0")

# 动态库打成 .framework
add_library(MyKit SHARED src/kit.cpp include/kit.h)
set_target_properties(MyKit PROPERTIES
  FRAMEWORK TRUE
  FRAMEWORK_VERSION A
  MACOSX_FRAMEWORK_IDENTIFIER com.acme.mykit
  VERSION 1.0.0          # → Mach-O "current version"
  SOVERSION 1            # → Mach-O "compatibility version"
  PUBLIC_HEADER include/kit.h)
```

### 19.4.6 代码签名

**`XCODE_ATTRIBUTE_CODE_SIGN_IDENTITY`：详解。** Xcode 生成器下设置签名身份（如 `"Developer ID Application"`、`"Apple Development"`，或 `"-"` 表示 ad-hoc 临时签名）。配套常用 `XCODE_ATTRIBUTE_DEVELOPMENT_TEAM`（Team ID）、`XCODE_ATTRIBUTE_CODE_SIGN_STYLE`（`Automatic`/`Manual`）。

```cmake
if(APPLE AND CMAKE_GENERATOR STREQUAL "Xcode")
  set_target_properties(MyApp PROPERTIES
    XCODE_ATTRIBUTE_CODE_SIGN_IDENTITY "Apple Development"
    XCODE_ATTRIBUTE_DEVELOPMENT_TEAM "ABCDE12345"
    XCODE_ATTRIBUTE_CODE_SIGN_STYLE "Automatic")
endif()
```

非 Xcode 生成器（Ninja）下用安装后 `codesign` 命令补签：
```bash
codesign --force --deep --sign "Developer ID Application: Acme (ABCDE12345)" build/MyApp.app
codesign --verify --verbose build/MyApp.app
```

### 19.4.7 DragNDrop / productbuild 打包

```cmake
if(APPLE)
  install(TARGETS MyApp BUNDLE DESTINATION .)        # .app 直接装到 DMG 根
  set(CPACK_GENERATOR "DragNDrop")                   # 生成 .dmg；或 "productbuild" 生成 .pkg 安装器
  set(CPACK_DMG_VOLUME_NAME "MyApp")
  set(CPACK_DMG_FORMAT "UDZO")                        # 压缩 DMG
  include(CPack)
endif()
```
```bash
cmake --build build --config Release
cpack -C Release          # → MyApp-1.0.0-Darwin.dmg
```

**预期产物**：`MyApp-1.0.0-Darwin.dmg`（拖拽安装）或 `.pkg`（productbuild，向导式安装、可签名分发）。

## 19.5 Linux 平台实战（完整工程）

Linux 的核心议题：共享库的 `SOVERSION` 版本化、RPATH/RUNPATH 与 `$ORIGIN`、pkg-config `.pc` 生成、`GNUInstallDirs` 目录规范、DEB/RPM 打包。

### 19.5.1 编译器

GCC（`GNU`）与 Clang 二选一，靠 `CC`/`CXX` 环境变量或 cache 变量选择：
```bash
# GCC（通常默认）
cmake -S . -B build-gcc -G Ninja -DCMAKE_BUILD_TYPE=Release
# Clang
cmake -S . -B build-clang -G Ninja -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_BUILD_TYPE=Release
```

### 19.5.2 共享库版本化（VERSION / SOVERSION / SONAME）

**`VERSION`：详解。** 共享库的完整版本（如 `1.2.3`），决定真实文件名 `libfoo.so.1.2.3`。
**`SOVERSION`：详解。** ABI 版本（如 `1`），决定 **SONAME**（`libfoo.so.1`）——链接器记录进依赖者、运行时据此匹配。只要 ABI 兼容就保持 `SOVERSION` 不变，仅升 `VERSION`。

```cmake
add_library(foo SHARED src/foo.cpp)
set_target_properties(foo PROPERTIES VERSION 1.2.3 SOVERSION 1)
```
CMake 在安装时自动建好符号链接三连：
```
libfoo.so          -> libfoo.so.1.2.3   (开发链接用，-lfoo 命中)
libfoo.so.1        -> libfoo.so.1.2.3   (SONAME，运行时用)
libfoo.so.1.2.3                          (真实文件)
```
> 验证 SONAME：`readelf -d build/libfoo.so.1.2.3 | grep SONAME` → `Library soname: [libfoo.so.1]`。

### 19.5.3 RPATH / RUNPATH / $ORIGIN

Linux 运行时由动态加载器（ld.so）按顺序找库：`DT_RPATH`（旧）→ `LD_LIBRARY_PATH` → `DT_RUNPATH`（新）→ `ld.so.cache` → 默认 `/lib`、`/usr/lib`。让自带库可被找到的可移植做法是嵌入相对 rpath `$ORIGIN`。

**`$ORIGIN`：详解。** ld.so 的特殊记号，运行时展开为"可执行文件/库**所在目录**"。`$ORIGIN/../lib` 即"我旁边的 ../lib"，使整个安装目录可整体搬动。注意在 CMake 字符串里要写成 `\$ORIGIN`（转义 `$`）或用括号包裹避免被 CMake 当变量。

**`CMAKE_INSTALL_RPATH`：详解。** 安装后写入二进制的 rpath。
**`CMAKE_INSTALL_RPATH_USE_LINK_PATH`：详解。** 设为 `ON` 时，CMake 自动把链接期用到的外部库目录追加进安装 rpath，省得手写。

```cmake
if(UNIX AND NOT APPLE)   # 纯 Linux
  set_target_properties(app PROPERTIES
    INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")
  set(CMAKE_INSTALL_RPATH_USE_LINK_PATH ON)
endif()
```
> 验证：`readelf -d build/app | grep -E 'RPATH|RUNPATH'`。现代 ld 默认生成 `RUNPATH`；若需旧式 `RPATH`，链接时加 `-Wl,--disable-new-dtags`。

### 19.5.4 生成 pkg-config `.pc` 文件

为了让纯 Makefile/Autotools 项目也能 `pkg-config --cflags --libs foo` 用上你的库，手写模板 + `configure_file`：

`foo.pc.in`：
```ini
prefix=@CMAKE_INSTALL_PREFIX@
exec_prefix=${prefix}
libdir=${prefix}/@CMAKE_INSTALL_LIBDIR@
includedir=${prefix}/@CMAKE_INSTALL_INCLUDEDIR@

Name: foo
Description: Foo library
Version: @PROJECT_VERSION@
Libs: -L${libdir} -lfoo
Cflags: -I${includedir}
```
```cmake
include(GNUInstallDirs)
configure_file(foo.pc.in ${CMAKE_CURRENT_BINARY_DIR}/foo.pc @ONLY)
install(FILES ${CMAKE_CURRENT_BINARY_DIR}/foo.pc
        DESTINATION ${CMAKE_INSTALL_LIBDIR}/pkgconfig)
```

### 19.5.5 GNUInstallDirs 与 DEB / RPM 打包

```cmake
include(GNUInstallDirs)
install(TARGETS app foo
  RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}      # 可执行
  LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}      # .so
  ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR})     # .a
install(DIRECTORY include/ DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})

set(CPACK_PACKAGE_NAME "myapp")
set(CPACK_PACKAGE_VERSION "1.0.0")
set(CPACK_PACKAGE_CONTACT "maintainer@acme.com")    # DEB 必需
if(UNIX AND NOT APPLE)
  set(CPACK_GENERATOR "DEB;RPM")                     # 同时出 .deb 和 .rpm
  # DEB 专属
  set(CPACK_DEBIAN_PACKAGE_DEPENDS "libc6 (>= 2.31)")
  set(CPACK_DEBIAN_PACKAGE_SHLIBDEPS ON)             # 自动推断共享库依赖（需 dpkg-shlibdeps）
  set(CPACK_DEBIAN_FILE_NAME DEB-DEFAULT)            # 规范命名 myapp_1.0.0_amd64.deb
  # RPM 专属
  set(CPACK_RPM_PACKAGE_LICENSE "MIT")
  set(CPACK_RPM_PACKAGE_REQUIRES "glibc >= 2.31")
  set(CPACK_RPM_FILE_NAME RPM-DEFAULT)
endif()
include(CPack)
```
```bash
cmake --build build
cpack -C Release        # → myapp_1.0.0_amd64.deb  和  myapp-1.0.0-1.x86_64.rpm
```
> DEB 需 `dpkg`；RPM 需 `rpmbuild`。`CPACK_DEBIAN_PACKAGE_SHLIBDEPS ON` 能自动算出 `Depends:`，强烈推荐。

## 19.6 移动 / 嵌入式 / WASM

这些都是**交叉编译**（宿主 ≠ 目标），共同套路：传一个 toolchain 文件设定 `CMAKE_SYSTEM_NAME` + 交叉编译器 + sysroot。下面给各平台最小可用命令。

### 19.6.1 Android（NDK）

NDK 自带 toolchain 文件，无需手写。

**`ANDROID_ABI`：详解。** 目标 CPU ABI：`arm64-v8a`（主流 64 位）/ `armeabi-v7a`（旧 32 位 ARM）/ `x86_64`（模拟器）/ `x86`。
**`ANDROID_PLATFORM`：详解。** 最低 API level，如 `android-24`（= API 24 / Android 7.0）。

```bash
cmake -S . -B build-android -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=$ANDROID_NDK_HOME/build/cmake/android.toolchain.cmake \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-24 \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build-android
# 产物：libxxx.so（arm64-v8a），供 APK/AAR 打包或 JNI 加载
```

### 19.6.2 iOS

CMake 内置 iOS 支持，用 Xcode 生成器最顺：

```bash
cmake -S . -B build-ios -G Xcode \
  -DCMAKE_SYSTEM_NAME=iOS \
  -DCMAKE_OSX_ARCHITECTURES=arm64 \
  -DCMAKE_OSX_DEPLOYMENT_TARGET=15.0 \
  -DCMAKE_XCODE_ATTRIBUTE_DEVELOPMENT_TEAM=ABCDE12345 \
  -DCMAKE_XCODE_ATTRIBUTE_CODE_SIGN_IDENTITY="Apple Development"
cmake --build build-ios --config Release -- -sdk iphoneos
```
> 模拟器目标：`-DCMAKE_OSX_SYSROOT=iphonesimulator -DCMAKE_OSX_ARCHITECTURES=arm64`（Apple Silicon Mac 上的模拟器）。

### 19.6.3 ARM 裸机（无 OS）

无操作系统 → `CMAKE_SYSTEM_NAME=Generic`，并务必告诉 CMake 用静态库做编译器探测（见 19.7.7）。`cmake/arm-none-eabi.cmake`：
```cmake
set(CMAKE_SYSTEM_NAME Generic)             # 裸机，无 OS
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_C_COMPILER   arm-none-eabi-gcc)
set(CMAKE_CXX_COMPILER arm-none-eabi-g++)
set(CMAKE_ASM_COMPILER arm-none-eabi-gcc)

# 裸机没法链接出可执行做探测，改用静态库探测
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)

set(MCU_FLAGS "-mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16")
set(CMAKE_C_FLAGS_INIT   "${MCU_FLAGS}")
set(CMAKE_CXX_FLAGS_INIT "${MCU_FLAGS}")
```
```bash
cmake -S . -B build-mcu -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake
cmake --build build-mcu     # 产物：.elf / .bin / .hex（配合 objcopy 自定义命令）
```

### 19.6.4 树莓派（交叉编译）

经典 Linux 交叉 toolchain（官方文档同款，呼应第 13 章）。`cmake/rpi.cmake`：
```cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_SYSROOT /home/dev/rasp-pi-rootfs)              # 从树莓派拷回的根文件系统
set(CMAKE_STAGING_PREFIX /home/dev/stage)               # 宿主上的安装暂存区

set(tools /home/dev/gcc-linaro-arm-linux-gnueabihf)
set(CMAKE_C_COMPILER   ${tools}/bin/arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER ${tools}/bin/arm-linux-gnueabihf-g++)

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)            # 程序在宿主找
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)             # 库/头只在 sysroot 找
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

### 19.6.5 Emscripten / WebAssembly

Emscripten 提供 `emcmake` 包装器，自动注入 `Emscripten.cmake` toolchain。

```bash
# 先 source 过 emsdk 环境（emsdk_env）后：
emcmake cmake -S . -B build-wasm -G Ninja -DCMAKE_BUILD_TYPE=Release
emmake make -C build-wasm        # 或 cmake --build build-wasm
```
让可执行 target 产出 `.html` 外壳（默认产出 `.js` + `.wasm`）：
```cmake
if(EMSCRIPTEN)
  set_target_properties(app PROPERTIES SUFFIX ".html")     # → app.html + app.js + app.wasm
  target_link_options(app PRIVATE
    "-sALLOW_MEMORY_GROWTH=1"
    "--shell-file=${CMAKE_CURRENT_SOURCE_DIR}/shell.html")
endif()
```
**预期产物**：`app.html`（页面外壳）、`app.js`（胶水）、`app.wasm`（字节码）。用 `emrun build-wasm/app.html` 本地起服务预览。

## 19.7 交叉编译实战 —— 以 Windows 为宿主（重点）

交叉编译统一心法（详见 [[42.Cmake/13 - 工具链与交叉编译.md|第 13 章]]）：**一个 toolchain 文件**告诉 CMake 三件事——目标系统是什么（`CMAKE_SYSTEM_NAME` + `CMAKE_SYSTEM_PROCESSOR`）、用哪个交叉编译器、到哪去找目标的库/头（`CMAKE_SYSROOT` + `CMAKE_FIND_ROOT_PATH*`）。下面以 **Windows 为开发宿主**逐场景给出。

### 19.7.1 Windows(x64) → Windows(ARM64)（同平台异架构）

最简单：同一套 MSVC，VS 生成器加 `-A ARM64` 即可，**无需 toolchain 文件**。

```bash
cmake -S . -B build-arm64 -G "Visual Studio 17 2022" -A ARM64
cmake --build build-arm64 --config Release
# 产物：ARM64 的 app.exe / .dll，可在 Windows on ARM 设备运行
```
> 需安装 VS 的"ARM64 生成工具"组件。若用 Ninja，则要在 "ARM64 Native/Cross Tools Command Prompt" 里跑，由该 shell 的环境决定架构。

### 19.7.2 Windows → Linux（LLVM/clang + lld，或经 WSL）

**路线 A（推荐入门）：WSL2。** 在 WSL 里就是一次普通的原生 Linux 构建，最省心：
```bash
# 在 WSL 的 Ubuntu 里：
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build
```

**路线 B：原生 Windows 上用 clang + lld 交叉到 Linux。** 需要一份 Linux sysroot（从目标机/容器拷回）。`cmake/win-to-linux.cmake`：
```cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR x86_64)

set(triple x86_64-linux-gnu)
set(CMAKE_C_COMPILER   clang)
set(CMAKE_CXX_COMPILER clang++)
set(CMAKE_C_COMPILER_TARGET   ${triple})
set(CMAKE_CXX_COMPILER_TARGET ${triple})

set(CMAKE_SYSROOT "C:/sysroots/ubuntu-22.04")        # 目标 Linux 的根文件系统
set(CMAKE_LINKER_TYPE LLD)                            # 用 lld 链接（CMake 3.29+ 抽象；旧版用 -fuse-ld=lld）

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```
```bash
cmake -S . -B build-linux -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/win-to-linux.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build-linux
```
> 路线 B 维护成本高（sysroot 同步、glibc 版本匹配），仅在不能用 WSL/容器时考虑。日常优先 WSL2 或 Docker。

### 19.7.3 Windows → Android（NDK on Windows）

与 19.6.1 完全一致，NDK 的 toolchain 是平台无关的，Windows 上路径用正斜杠或转义反斜杠：
```bash
cmake -S . -B build-android -G Ninja ^
  -DCMAKE_TOOLCHAIN_FILE=%ANDROID_NDK_HOME%/build/cmake/android.toolchain.cmake ^
  -DANDROID_ABI=arm64-v8a -DANDROID_PLATFORM=android-24 -DCMAKE_BUILD_TYPE=Release
cmake --build build-android
```
> Windows 上务必用 **Ninja**（NDK 自带 `ninja.exe` 与 `make` 可在 `$NDK/prebuilt/windows-x86_64/bin` 找到）。`^` 是 cmd 续行符；PowerShell 用反引号 `` ` ``。

### 19.7.4 Windows → WebAssembly（Emscripten on Windows）

Emscripten 在 Windows 上一等支持，`emcmake` 同样可用：
```bash
emcmake cmake -S . -B build-wasm -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-wasm
# 产物：app.js + app.wasm（如 19.6.5 设了 SUFFIX 则加 app.html）
```

### 19.7.5 反向参考：Linux → Windows（MinGW-w64 交叉）

在 Linux 上用 MinGW-w64 交叉出 Windows 的 `.exe`/`.dll`，CI 里很常见。`cmake/linux-to-win.cmake`：
```cmake
set(CMAKE_SYSTEM_NAME Windows)
set(CMAKE_SYSTEM_PROCESSOR x86_64)

set(CMAKE_C_COMPILER   x86_64-w64-mingw32-gcc)
set(CMAKE_CXX_COMPILER x86_64-w64-mingw32-g++)
set(CMAKE_RC_COMPILER  x86_64-w64-mingw32-windres)

set(CMAKE_FIND_ROOT_PATH /usr/x86_64-w64-mingw32)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```
```bash
sudo apt install mingw-w64                # Debian/Ubuntu
cmake -S . -B build-win -G Ninja -DCMAKE_TOOLCHAIN_FILE=cmake/linux-to-win.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build-win                   # 产物：app.exe（需随附 MinGW 运行时 DLL）
```

### 19.7.6 macOS → iOS

见 19.6.2。要点：宿主必须是 macOS（iOS SDK 与签名工具仅 macOS 提供），`-DCMAKE_SYSTEM_NAME=iOS` + Xcode 生成器 + 签名属性。

### 19.7.7 交叉编译三个必记要点

**`CMAKE_TRY_COMPILE_TARGET_TYPE`：详解（最常踩的坑）。** CMake 探测编译器时默认尝试**链接一个可执行文件**；交叉到裸机/无标准启动文件的目标时这一步会失败，导致 `project()` 直接报错。设为 `STATIC_LIBRARY` 让探测只编译不链接，绕过该问题：
```cmake
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)   # 写在 toolchain 文件里
```

**`CMAKE_FIND_ROOT_PATH_MODE_*`：详解。** 控制 `find_program/find_library/find_path/find_package` 在交叉编译时去**宿主**还是**目标 sysroot** 里找：
- `..._PROGRAM NEVER`：可执行工具（如 protoc 代码生成器）要用**宿主**的 → 不进 sysroot 找。
- `..._LIBRARY ONLY` / `..._INCLUDE ONLY` / `..._PACKAGE ONLY`：库、头、包配置**只**在目标 sysroot（`CMAKE_FIND_ROOT_PATH` / `CMAKE_SYSROOT`）里找，绝不误用宿主的。

**`CMAKE_SYSROOT` / `CMAKE_STAGING_PREFIX`：详解。** 前者是目标 SDK 的根（编译/链接搜索基准）；后者是交叉编译时**宿主上的安装暂存目录**（`install` 装到这里而非真往目标系统写），与目标的 `CMAKE_INSTALL_PREFIX` 分离。

## 19.8 跨平台差异对照大表（核心）

下表是本章的"压缩档案"——每行一个跨平台任务，三列对比。建议打印。

| 任务 / 维度 | **Windows** | **macOS** | **Linux** |
|---|---|---|---|
| 动态库扩展名 | `.dll` | `.dylib` | `.so` |
| 导入库（链接期需要） | `.lib`（DLL 的导入库）/ `.lib`（静态库） | 无（直接链 `.dylib`/`.framework`） | 无（直接链 `.so`/`.a`） |
| 静态库扩展名 | `.lib` | `.a` | `.a` |
| 可执行扩展名 | `.exe` | 无 | 无 |

| CMake 默认生成器 | `Visual Studio 17 2022`（装了 VS 时） | `Unix Makefiles`（命令行）/ 常用 Xcode | `Unix Makefiles`（常切 Ninja） |
| 依赖管理常用方案 | vcpkg / Conan / FetchContent | Homebrew / vcpkg / Conan / FetchContent | 系统包管理(apt/dnf) + pkg-config / Conan / vcpkg / FetchContent |

| 路径分隔符（环境变量列表） | `;` | `:` | `:` |

## 19.9 真·跨平台完整工程（压轴）

下面这一份工程在 **Windows / macOS / Linux** 上都能跑通 `configure → build → test → install → package`。它示范了：平台条件集中处理、`GenerateExportHeader` 跨平台导出、RPATH / install_name / `TARGET_RUNTIME_DLLS` 三平台部署、各平台 CPack 生成器自动选择，并配一份用 `condition` 区分平台的 `CMakePresets.json`。

### 19.9.1 目录结构

```
xplat-demo/
├── CMakeLists.txt
├── CMakePresets.json
├── cmake/
│   └── packaging.cmake          # CPack 平台分支集中处
├── include/
│   └── greet/greet.hpp
├── src/
│   ├── greet.cpp                # → libgreet（SHARED）
│   └── main.cpp                 # → greet_app（可执行）
└── tests/
    └── test_greet.cpp
```

### 19.9.2 顶层 `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.28)
project(XPlatDemo VERSION 1.0.0 LANGUAGES CXX)

include(GNUInstallDirs)
include(GenerateExportHeader)
include(CTest)                       # 提供 BUILD_TESTING 选项 + enable_testing()

# ---- 跨平台默认（集中处理）----
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_VISIBILITY_PRESET hidden)        # 三平台统一：默认隐藏，显式导出
set(CMAKE_VISIBILITY_INLINES_HIDDEN ON)
set(CMAKE_POSITION_INDEPENDENT_CODE ON)

# 单配置生成器给个默认构建类型
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
  set(CMAKE_BUILD_TYPE Release CACHE STRING "" FORCE)
endif()

# 把产物集中到 bin/lib，方便运行（尤其 Windows 找 DLL）
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)
set(CMAKE_LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)
set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)

# ---- 共享库 ----
add_library(greet SHARED src/greet.cpp)
add_library(greet::greet ALIAS greet)
target_include_directories(greet PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}>          # 生成的导出头
  $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>)
generate_export_header(greet EXPORT_FILE_NAME ${CMAKE_CURRENT_BINARY_DIR}/greet_export.h)

# 版本化：Linux→SONAME，macOS→Mach-O 版本，Windows→PE 镜像版本
set_target_properties(greet PROPERTIES
  VERSION ${PROJECT_VERSION}
  SOVERSION ${PROJECT_VERSION_MAJOR})

# ---- 可执行 ----
add_executable(greet_app src/main.cpp)
target_link_libraries(greet_app PRIVATE greet::greet)

# ---- 平台相关的 RPATH / install_name / DLL 部署（集中分支）----
if(APPLE)
  set_target_properties(greet_app PROPERTIES
    INSTALL_RPATH "@loader_path/../${CMAKE_INSTALL_LIBDIR}")
elseif(UNIX)   # Linux 及其它 *nix
  set_target_properties(greet_app PROPERTIES
    INSTALL_RPATH "$ORIGIN/../${CMAKE_INSTALL_LIBDIR}")
  set(CMAKE_INSTALL_RPATH_USE_LINK_PATH ON)
elseif(WIN32)
  # 开发期：把依赖 DLL 拷到 exe 旁，双击即可运行
  add_custom_command(TARGET greet_app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy -t $<TARGET_FILE_DIR:greet_app> $<TARGET_RUNTIME_DLLS:greet_app>
    COMMAND_EXPAND_LISTS)
endif()

# ---- 测试 ----
if(BUILD_TESTING)
  add_executable(test_greet tests/test_greet.cpp)
  target_link_libraries(test_greet PRIVATE greet::greet)
  add_test(NAME greet_smoke COMMAND test_greet)
  # Windows 上让 ctest 能找到 greet.dll
  if(WIN32)
    set_tests_properties(greet_smoke PROPERTIES
      ENVIRONMENT "PATH=$<TARGET_FILE_DIR:greet>;$ENV{PATH}")
  endif()
endif()

# ---- 安装 ----
install(TARGETS greet greet_app
  RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}        # exe + Windows DLL
  LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}        # .so/.dylib
  ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR})       # .lib(导入库)/.a
install(FILES include/greet/greet.hpp ${CMAKE_CURRENT_BINARY_DIR}/greet_export.h
  DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}/greet)
# Windows 安装期顺带带上运行时依赖 DLL
if(WIN32)
  install(FILES $<TARGET_RUNTIME_DLLS:greet_app>
    DESTINATION ${CMAKE_INSTALL_BINDIR})
endif()

# ---- 打包（平台分支抽到单独模块）----
include(cmake/packaging.cmake)
```

### 19.9.3 `cmake/packaging.cmake`

```cmake
set(CPACK_PACKAGE_NAME "XPlatDemo")
set(CPACK_PACKAGE_VENDOR "Acme")
set(CPACK_PACKAGE_VERSION ${PROJECT_VERSION})
set(CPACK_PACKAGE_CONTACT "maintainer@acme.com")
set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "A cross-platform demo")

if(WIN32)
  set(CPACK_GENERATOR "NSIS;ZIP")
  set(CPACK_NSIS_MODIFY_PATH ON)
  set(CPACK_PACKAGE_EXECUTABLES "greet_app" "Greet App")
elseif(APPLE)
  set(CPACK_GENERATOR "DragNDrop;TGZ")
  set(CPACK_DMG_VOLUME_NAME "XPlatDemo")
else()  # Linux
  set(CPACK_GENERATOR "DEB;RPM;TGZ")
  set(CPACK_DEBIAN_PACKAGE_SHLIBDEPS ON)
  set(CPACK_DEBIAN_FILE_NAME DEB-DEFAULT)
  set(CPACK_RPM_PACKAGE_LICENSE "MIT")
  set(CPACK_RPM_FILE_NAME RPM-DEFAULT)
endif()

include(CPack)   # 必须在所有 CPACK_* 设定之后
```

### 19.9.4 源码（最小可复现）

`include/greet/greet.hpp`：
```cpp
#pragma once
#include "greet_export.h"          // generate_export_header 生成
#include <string>
GREET_EXPORT std::string greet(const std::string& who);
```
`src/greet.cpp`：
```cpp
#include "greet/greet.hpp"
std::string greet(const std::string& who) { return "Hello, " + who + "!"; }
```
`src/main.cpp`：
```cpp
#include "greet/greet.hpp"
#include <iostream>
int main() { std::cout << greet("CMake 4.3.4") << '\n'; }
```
`tests/test_greet.cpp`：
```cpp
#include "greet/greet.hpp"
#include <cassert>
int main() { assert(greet("x") == "Hello, x!"); return 0; }
```

### 19.9.5 `CMakePresets.json`（用 condition 区分平台）

> `condition` + `${hostSystemName}` 让**同一个 preset 文件**在三平台各自只暴露匹配的 preset；CI 里无脑跑 `--preset <平台名>` 即可。`packagePresets` 需 preset 版本 ≥ 6（CMake 3.25+）。

### 19.9.6 各平台命令与预期产物

**Windows：**
```bash
cmake --preset windows
cmake --build --preset windows
ctest --preset windows
cmake --install build/windows --config Release
cpack --preset windows
```
产物：`build/windows/bin/greet_app.exe` + `greet.dll`（已拷到旁）；安装到 `out/windows/{bin,lib,include}`；`XPlatDemo-1.0.0-win64.exe`（NSIS）+ `.zip`。

**macOS：**
```bash
cmake --preset macos
cmake --build --preset macos
ctest --preset macos
cmake --install build/macos
cpack --preset macos
```
产物：`build/macos/bin/greet_app`（Universal，`lipo -info` 可见 arm64+x86_64）+ `libgreet.1.0.0.dylib`（install_name = `@rpath/...`）；`XPlatDemo-1.0.0-Darwin.dmg` + `.tar.gz`。

**Linux：**
```bash
cmake --preset linux
cmake --build --preset linux
ctest --preset linux
cmake --install build/linux
cpack --preset linux
```
产物：`build/linux/bin/greet_app`（rpath = `$ORIGIN/../lib`）+ `libgreet.so.1.0.0`（SONAME `libgreet.so.1` + 符号链接）；`xplatdemo_1.0.0_amd64.deb` + `xplatdemo-1.0.0-1.x86_64.rpm` + `.tar.gz`。

> **跨平台验证一条龙**：三平台跑同样五步、`greet_app` 输出同一句 `Hello, CMake 4.3.4!`、`ctest` 全绿——这就是"一次编写、三处构建"落地的标志。CMakeLists 里平台相关代码全部收拢在 `if(APPLE)/elseif(UNIX)/elseif(WIN32)` 一个 block 和 `packaging.cmake` 一个文件中，正是第 1 节"差异集中在一处"的体现。

## 本章小结

- **核心理念**：让 CMake 抽象平台差异——不硬编码编译器/flag/扩展名/路径，用 `target_*`、生成器表达式、`GNUInstallDirs`，把差异集中在少数几处。
- **平台判定**：`WIN32`/`APPLE`/`UNIX`/`LINUX`/`MSVC`/`MINGW`/`ANDROID`/`IOS`/`EMSCRIPTEN` 等布尔量源自 `CMAKE_SYSTEM_NAME`（目标系统，区别于 `CMAKE_HOST_SYSTEM_NAME`）；逐目标/逐配置投放用 `$<PLATFORM_ID:>`/`$<CXX_COMPILER_ID:>`。
- **三大桌面平台**：Windows 重点是显式符号导出（`GenerateExportHeader`）+ DLL 部署（`$<TARGET_RUNTIME_DLLS>`）+ NSIS/WIX；macOS 重点是 Universal Binary（`CMAKE_OSX_ARCHITECTURES`）+ `@rpath`/install_name + .app/.framework + 签名 + DMG/pkg；Linux 重点是 `SOVERSION` 版本化 + `$ORIGIN` RPATH + pkg-config + DEB/RPM。
- **移动/嵌入式/WASM 与交叉编译**：统一靠 toolchain 文件设定 `CMAKE_SYSTEM_NAME` + 交叉编译器 + sysroot；以 Windows 为宿主可直达 ARM64（`-A ARM64`）、Android（NDK）、WASM（`emcmake`），到 Linux 优先 WSL2；牢记 `CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY` 与 `CMAKE_FIND_ROOT_PATH_MODE_*` 两大交叉要点（详见 [[42.Cmake/13 - 工具链与交叉编译.md|第 13 章]]）。
- **对照大表 + 真·跨平台工程**：把扩展名、可见性、版本化、运行时查找、部署、打包、安装路径的三平台差异一表打尽；最后一份 `CMakeLists.txt` + `CMakePresets.json`（`condition` 区分平台）在三平台都能 configure/build/test/install/package，是全部理念的落地范本。
