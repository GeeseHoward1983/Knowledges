# 第 14 章 · 编译器、语言标准与特性

> 基准版本：CMake 4.3.4

本章聚焦"如何告诉编译器用哪个语言标准、加哪些 flag、走哪条优化路径"。这是 CMake 工程里最高频也最容易写错的一块：很多项目至今还在用 `add_compile_options(-std=c++17)` 这种硬塞 flag 的老写法，既不可移植、又会污染所有语言（连 C 源文件都被塞了 `-std=c++17`），还和 CMake 自己管理标准的机制打架。本章会系统讲清楚现代写法：用 `CMAKE_<LANG>_STANDARD` / `target_compile_features` 声明标准、用 `target_compile_options` + 生成器表达式按编译器/配置加 flag、用 `CMAKE_<LANG>_COMPILER_ID` 做编译器识别，以及 PCH、Unity build、IPO/LTO、PIC、`compile_commands.json` 等一系列编译期能力开关。

阅读前置：建议先读完[[42.Cmake/04 - Target 与现代 CMake.md|第 4 章（Target 与现代 CMake）]]（理解 target 与属性、`PUBLIC`/`PRIVATE`/`INTERFACE` 传播）和[[42.Cmake/07 - 生成器表达式.md|第 7 章（生成器表达式）]]（本章大量使用 `$<...>`）。

## 14.1 语言标准设置

### 14.1.1 三个全局变量：STANDARD / STANDARD_REQUIRED / EXTENSIONS

CMake 通过三个一组的变量/属性来描述"某语言要用哪个标准"。以 C++ 为例：

**`CMAKE_CXX_STANDARD`**：设置目标默认使用的 C++ 标准版本（数字，不带 `c++` 前缀），例如 `20` 表示 C++20。它在 CMake 3.1 引入。这是一个**变量**（不是属性），其作用是：当一个 target 被 `add_library()`/`add_executable()` 创建时，用它的当前值去初始化该 target 的 `CXX_STANDARD` 属性。因此它必须在创建 target **之前**设置才会生效。

**`CMAKE_CXX_STANDARD_REQUIRED`**：布尔值，控制"标准是硬性要求还是尽力而为"。默认（或设为 `OFF`）时，CMake 采用**降级（decay）**行为——如果编译器不支持请求的标准 flag（例如不认识 `-std=gnu++20`），CMake 不会报错，而是悄悄退回到它支持的较低标准（如 `-std=gnu++17` 甚至 `-std=gnu++98`），你的代码可能因此用错标准编译而出现莫名其妙的报错。设为 `ON` 后，若编译器不支持指定标准，配置阶段直接失败。**强烈建议恒为 `ON`**，避免降级带来的隐蔽问题。

**`CMAKE_CXX_EXTENSIONS`**：布尔值，控制是否启用编译器的 GNU 扩展。默认 `ON`，CMake 会传 `-std=gnu++20`（带 GNU 扩展，如 `typeof`、变长数组、内联汇编的某些宽松写法）；设为 `OFF` 则传 `-std=c++20`（严格标准）。追求可移植性、希望代码在 GCC/Clang/MSVC 行为一致时，应设为 `OFF`。

最常见、最推荐的全局设置写法是在 `project()` 调用之后、定义任何 target 之前写：

```cmake
cmake_minimum_required(VERSION 3.20)
project(MyApp LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)            # 全工程默认 C++20
set(CMAKE_CXX_STANDARD_REQUIRED ON)   # 不允许降级，不支持就报错
set(CMAKE_CXX_EXTENSIONS OFF)         # 用 -std=c++20 而非 -std=gnu++20
```

> ⚠️ 顺序很关键：这三个变量是在 target **创建时**被读取并固化进 target 属性的。如果你在 `add_executable(app ...)` 之后才 `set(CMAKE_CXX_STANDARD 20)`，对 `app` **无效**。要么放在所有 target 之前，要么改用下面的 target 级属性 / `target_compile_features`。

### 14.1.2 target 级属性：CXX_STANDARD / CXX_STANDARD_REQUIRED / CXX_EXTENSIONS

上面三个 `CMAKE_*` 变量分别对应三个**目标属性**，可用 `set_target_properties` 精确控制单个 target，而不影响全局：

```cmake
add_executable(app main.cpp)

set_target_properties(app PROPERTIES
    CXX_STANDARD 20
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
)
```

**`CXX_STANDARD`（属性）**：该 target 编译时使用的 C++ 标准。若未显式设置，则初始化为创建 target 时 `CMAKE_CXX_STANDARD` 变量的值。

**`CXX_STANDARD_REQUIRED`（属性）**：是否禁止标准降级，语义同上。

**`CXX_EXTENSIONS`（属性）**：是否启用 GNU 扩展，语义同上。

target 级属性的优先级高于全局变量，适合"工程整体 C++17，但某个用到协程的库单独提到 C++20"这类场景。

### 14.1.3 支持的标准值一览

C++ 标准值（用于 `CMAKE_CXX_STANDARD` / `CXX_STANDARD`）：

| 值 | 对应标准 | 引入此值的 CMake 版本 |
| --- | --- | --- |
| `98` | C++98 | 3.1 |
| `11` | C++11 | 3.1 |
| `14` | C++14 | 3.1 |
| `17` | C++17 | 3.8 |
| `20` | C++20 | 3.12 |
| `23` | C++23 | 3.20 |
| `26` | C++26 | 3.25 |

C 标准值（用于 `CMAKE_C_STANDARD` / `C_STANDARD`）：

| 值 | 对应标准 | 引入此值的 CMake 版本 |
| --- | --- | --- |
| `90` | C90（即 C89/ANSI C） | 3.1 |
| `99` | C99 | 3.1 |
| `11` | C11 | 3.1 |
| `17` | C17 | 3.21 |
| `23` | C23 | 3.21 |

> 💡 **"CMake 认这个值" ≠ "你的编译器支持它"**。CMake 从 3.25 起就认 `26`，但实际能否编译出 C++26 取决于具体编译器版本（GCC/Clang/MSVC 各自支持进度不同）。把 `CXX_STANDARD_REQUIRED` 设为 `ON`，CMake 会在配置阶段帮你检测并在不支持时报错，否则会发生 14.1.1 说的降级。

其他语言也有对应的一组变量/属性，命名规律完全一致（把 `CXX` 换成对应语言名）：

- C：`CMAKE_C_STANDARD` / `C_STANDARD`、`..._STANDARD_REQUIRED`、`..._EXTENSIONS`
- CUDA：`CMAKE_CUDA_STANDARD` / `CUDA_STANDARD`（值同 C++：`03/11/14/17/20/23/26`）
- OBJC（Objective-C）：`CMAKE_OBJC_STANDARD` / `OBJC_STANDARD`
- OBJCXX（Objective-C++）：`CMAKE_OBJCXX_STANDARD` / `OBJCXX_STANDARD`
- HIP：`CMAKE_HIP_STANDARD` / `HIP_STANDARD`

（Fortran/Swift/ASM 等没有"语言标准号"的概念，不走这套机制。）

## 14.2 compile features 与 target_compile_features

### 14.2.1 命令语义

`target_compile_features` 用来声明"编译这个 target 需要哪些编译器特性"，CMake 会自动加上满足这些特性所需的最低标准 flag，并把要求按可见性传播给依赖者。

```cmake
target_compile_features(<target> <PRIVATE|PUBLIC|INTERFACE> <feature>... [...])
```

- `PRIVATE`：特性只用于该 target 自身编译，不传播。
- `INTERFACE`：特性只施加给链接此 target 的下游，自身不用。
- `PUBLIC`：两者皆是（既影响自身，也传播给下游）。

可见性关键字是**强制**的。`PRIVATE`/`PUBLIC` 填充 target 的 `COMPILE_FEATURES` 属性，`PUBLIC`/`INTERFACE` 填充 `INTERFACE_COMPILE_FEATURES` 属性。对同一 target 重复调用会**追加**。若请求的特性不在 `CMAKE_CXX_COMPILE_FEATURES`（或 `CMAKE_C_COMPILE_FEATURES` / `CMAKE_CUDA_COMPILE_FEATURES`）列出的可用特性里，CMake 会直接报错。

### 14.2.2 元特性 cxx_std_NN（推荐）

最常用、也最推荐的是**元特性（meta-feature）** `cxx_std_<NN>`，它表示"编译器模式至少为 C++NN"：

```cmake
target_compile_features(mylib PUBLIC cxx_std_20)
```

这一行的含义是：`mylib` 自身按至少 C++20 编译；并且**任何链接 `mylib` 的 target 也会被要求至少 C++20**——这正是它相对于直接设 `CXX_STANDARD` 的最大优势：标准要求可以像头文件依赖一样沿 target 图传播。例如一个公开头文件里用了 C++20 概念（concepts）的库，用 `PUBLIC cxx_std_20` 声明后，使用者无需手动再设标准。

C++ 元特性及其引入版本：

| 元特性 | 含义 | 引入版本 |
| --- | --- | --- |
| `cxx_std_98` | 编译器模式 ≥ C++98 | 3.1 |
| `cxx_std_11` | 编译器模式 ≥ C++11 | 3.1 |
| `cxx_std_14` | 编译器模式 ≥ C++14 | 3.1 |
| `cxx_std_17` | 编译器模式 ≥ C++17 | 3.8 |
| `cxx_std_20` | 编译器模式 ≥ C++20 | 3.12 |
| `cxx_std_23` | 编译器模式 ≥ C++23 | 3.20 |
| `cxx_std_26` | 编译器模式 ≥ C++26 | 3.30 |

CUDA 有对应的 `cuda_std_<NN>`，C 有 `c_std_90/99/11/17/23`。

### 14.2.3 具体特性与 CMAKE_CXX_KNOWN_FEATURES

除元特性外，还有一批**具体（细粒度）特性**，主要是 C++11/C++14 时代用来探测"编译器是否支持某个语言点"的，例如：

- `cxx_constexpr`：常量表达式
- `cxx_auto_type`：`auto` 类型推导
- `cxx_lambdas`：lambda
- `cxx_nullptr`：`nullptr`
- `cxx_override`：`override` 关键字
- `cxx_range_for`：范围 for
- `cxx_variadic_templates`：变参模板
- `cxx_alias_templates`、`cxx_decltype`、`cxx_static_assert` …

完整清单见全局只读属性 **`CMAKE_CXX_KNOWN_FEATURES`**（"此 CMake 版本知道的所有 C++ 特性名"）；其中在当前编译器上**实际可用**的子集，则体现在 **`CMAKE_CXX_COMPILE_FEATURES`** 变量里。

```cmake
# 打印当前编译器实际支持的所有特性
get_property(features GLOBAL PROPERTY CMAKE_CXX_KNOWN_FEATURES)
message(STATUS "Known: ${features}")
message(STATUS "Available on this compiler: ${CMAKE_CXX_COMPILE_FEATURES}")
```

> 📌 **重要现状**：CMake 官方明确，C++17 及以后**不再提供具体特性**——也就是说没有 `cxx_if_constexpr`、`cxx_concepts` 这类细粒度名字。原因是现代编译器对一个标准的特性支持基本是"全有或全无"，逐特性探测意义不大。**因此对于现代工程（C++17/20/23），请直接用元特性 `cxx_std_NN`，不要再依赖具体特性。**

### 14.2.4 三种写法的取舍

到这里我们有三种声明标准的方式，推荐优先级如下：

| 写法 | 是否传播给下游 | 推荐度 | 适用 |
| --- | --- | --- | --- |
| `target_compile_features(t PUBLIC cxx_std_20)` | ✅ 是 | ⭐⭐⭐ 首选 | 库的公开 API 需要某标准；现代工程默认 |
| `set_target_properties(t PROPERTIES CXX_STANDARD 20 ...)` | ❌ 否 | ⭐⭐ | 仅约束本 target，不想影响使用者；可执行文件 |
| `set(CMAKE_CXX_STANDARD 20)`（全局变量） | ❌ 否（但影响后续所有 target） | ⭐ | 小工程图省事统一设定 |

一句话经验：**库优先 `target_compile_features(... PUBLIC cxx_std_NN)`**（让标准要求随依赖传播）；**可执行程序用 target 属性或全局变量**即可。三者可以混用，CMake 取其中要求最高的标准。绝对不要用 `add_compile_options(-std=...)` 手动塞标准 flag（见 14.3）。

## 14.3 编译与链接选项

### 14.3.1 target_compile_options

`target_compile_options` 给指定 target 添加**编译**阶段的命令行选项（warning 开关、优化级别、宏开关等）：

```cmake
target_compile_options(<target> [BEFORE] <PRIVATE|PUBLIC|INTERFACE> <option>... [...])
```

- 可见性语义同前：`PRIVATE` 填充 `COMPILE_OPTIONS`，`INTERFACE` 填充 `INTERFACE_COMPILE_OPTIONS`，`PUBLIC` 两者皆填。
- `BEFORE`（可选）：把选项插到现有选项**之前**（默认追加在后）。
- 选项里出现 `-D`/`-I` 是允许的，但**不推荐**——加宏请用 `target_compile_definitions`、加头文件目录请用 `target_include_directories`，语义更清晰、更可移植。

```cmake
target_compile_options(app PRIVATE -Wall -Wextra -Wpedantic)
```

### 14.3.2 target_link_options（3.13+）

`target_link_options` 给 target 的**链接**阶段添加选项（链接器 flag，如 `-fsanitize=address` 的链接侧、`/SUBSYSTEM`、`-Wl,...` 等）。在 CMake **3.13** 引入：

```cmake
target_link_options(<target> [BEFORE] <PRIVATE|PUBLIC|INTERFACE> <option>... [...])
```

它填充 `LINK_OPTIONS` / `INTERFACE_LINK_OPTIONS` 属性。注意它针对的是"链接成可执行文件/动态库"这一步的选项，而**链接哪些库**仍用 `target_link_libraries`。典型用法是和 sanitizer 配合，编译和链接两侧都要加 flag：

```cmake
target_compile_options(app PRIVATE -fsanitize=address)
target_link_options(app    PRIVATE -fsanitize=address)
```

### 14.3.3 配合生成器表达式按编译器/配置加 flag

由于不同编译器的 flag 互不兼容（GCC/Clang 用 `-Wall`，MSVC 用 `/W4`），加 flag 几乎总要配合**生成器表达式**做条件判断。常用判断条件：

- `$<CXX_COMPILER_ID:GNU>`：当前 C++ 编译器是否为 GNU（GCC）。
- `$<CXX_COMPILER_ID:Clang,AppleClang>`：可一次列多个 ID。
- `$<CONFIG:Debug>`：当前构建配置是否为 Debug。
- `$<COMPILE_LANGUAGE:CXX>`：仅对 C++ 源文件生效（多语言 target 里隔离 flag 的关键）。

把"条件"和"内容"拼在一起的惯用模式是 `$<$<条件>:内容>`：

```cmake
# 按编译器加不同的警告 flag
target_compile_options(app PRIVATE
    $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:-Wall;-Wextra;-Wpedantic>
    $<$<CXX_COMPILER_ID:MSVC>:/W4;/permissive->
)

# 仅 Debug 配置加调试相关 flag
target_compile_options(app PRIVATE
    $<$<CONFIG:Debug>:-g3;-O0>
)

# 多语言 target：-Wno-deprecated 只加到 C++ 源文件
target_compile_options(mixed PRIVATE
    $<$<COMPILE_LANGUAGE:CXX>:-Wno-deprecated-declarations>
)
```

> 关于生成器表达式的完整语法、所有可用条件与列表展开规则，见[[42.Cmake/07 - 生成器表达式.md|第 7 章]]。这里只需记住：**编译器/配置相关的 flag，几乎都要用 `$<...>` 包起来**，否则就会出现"给 MSVC 传了 `-Wall`"之类的错误。

### 14.3.4 老式 add_compile_options / add_link_options 对比

CMake 还有目录级（directory-scoped）的命令：

- `add_compile_options(<option>...)`：给**当前目录及其子目录**中之后定义的所有 target 加编译选项。
- `add_link_options(<option>...)`（3.13+）：同理，加链接选项。
- `add_definitions(-DXXX)`：老式加宏（已被 `target_compile_definitions` 取代）。

它们的问题在于**作用域是目录而非 target**，会"撒胡椒面"式地影响范围内的一切，包括第三方子目录里的 target，且不区分语言（连 C 文件都会被塞 C++ flag）。

| 维度 | `target_compile_options`（现代） | `add_compile_options`（老式） |
| --- | --- | --- |
| 作用域 | 单个 target，精确 | 当前目录+子目录的所有后续 target |
| 可见性传播 | 支持 PUBLIC/INTERFACE 沿依赖传播 | 不支持 |
| 隔离性 | 好，不会误伤别的 target | 差，易污染第三方/其他语言 |
| 推荐 | ✅ 默认使用 | ⚠️ 仅用于真正的全工程统一基线 |

**结论：优先 `target_compile_options` / `target_link_options`。** `add_compile_options` 只在你确实想给"本工程所有 target"设一条统一基线、且能接受其副作用时才用。

## 14.4 多语言支持

### 14.4.1 在 project() 中声明语言

CMake 工程的语言在 `project()` 的 `LANGUAGES` 子句里声明（也可省略，默认启用 `C` 和 `CXX`）：

```cmake
project(MyApp VERSION 1.0 LANGUAGES C CXX CUDA)
```

声明语言会触发 CMake 探测并配置对应的编译器（找编译器、测试编译、设置一堆 `CMAKE_<LANG>_*` 变量）。若要"先不启用任何语言"（例如纯脚本/纯打包工程），用 `LANGUAGES NONE` 或空列表。

### 14.4.2 enable_language 延迟启用

`enable_language(<lang> [OPTIONAL])` 可以在 `project()` 之后**按需**启用某语言，常用于"只有在满足条件时才编 CUDA/Fortran"的场景：

```cmake
project(MyApp LANGUAGES CXX)
# ... 一些条件判断 ...
if(USE_CUDA)
    enable_language(CUDA)
endif()
```

`OPTIONAL` 关键字目前保留备用。若想在启用前**先探测**某语言编译器是否存在（避免直接 `enable_language` 失败导致配置报错），用 `CheckLanguage` 模块：

```cmake
include(CheckLanguage)
check_language(CUDA)        # 设置 CMAKE_CUDA_COMPILER（找到则为路径，否则为 NOTFOUND）
if(CMAKE_CUDA_COMPILER)
    enable_language(CUDA)
    message(STATUS "CUDA enabled: ${CMAKE_CUDA_COMPILER}")
else()
    message(STATUS "No CUDA support")
endif()
```

### 14.4.3 支持的语言一览

`project()` 的 `LANGUAGES` 和 `enable_language()` 支持的语言：

| 语言标识 | 说明 |
| --- | --- |
| `C` | C 语言 |
| `CXX` | C++ |
| `CUDA` | NVIDIA CUDA C++（first-class，CMake 直接驱动 nvcc/clang-cuda） |
| `OBJC` | Objective-C |
| `OBJCXX` | Objective-C++ |
| `Fortran` | Fortran |
| `HIP` | AMD HIP（GPU，类 CUDA） |
| `ISPC` | Intel SPMD Program Compiler |
| `Swift` | Swift |
| `CSharp` | C#（仅 Visual Studio / MSBuild 生成器） |
| `ASM` | 通用汇编（编译器驱动） |
| `ASM_NASM` | NASM 汇编 |
| `ASM_MASM` | Microsoft MASM |
| `ASM_MARMASM` | ARM MASM（armasm） |
| `ASM_POASM` | 兼容 ASM（POASM） |
| `ASM-ATT` | AT&T 语法汇编 |

> 注：`CSharp` 与 `Swift` 等对生成器有要求（C# 基本只能在 VS 生成器下用，Swift 推荐 Ninja/Xcode）。汇编方言的可用性取决于平台与工具链。

### 14.4.4 各语言专用变量（命名规律）

启用语言后，CMake 会为每种语言生成一组以 `CMAKE_<LANG>_` 为前缀的变量，命名规律高度一致，把 `<LANG>` 换成 `C`/`CXX`/`CUDA`/`Fortran`/`Swift` 等即可。常用的有：

| 变量模式 | 含义 |
| --- | --- |
| `CMAKE_<LANG>_COMPILER` | 该语言编译器的完整路径 |
| `CMAKE_<LANG>_COMPILER_ID` | 编译器厂商标识（见 14.5） |
| `CMAKE_<LANG>_COMPILER_VERSION` | 编译器版本号 |
| `CMAKE_<LANG>_FLAGS` | 该语言全配置通用的 flag（慎改，建议用 target 命令） |
| `CMAKE_<LANG>_FLAGS_<CONFIG>` | 特定配置的 flag，如 `CMAKE_CXX_FLAGS_DEBUG` |
| `CMAKE_<LANG>_STANDARD` | 默认语言标准（仅 C/CXX/CUDA/OBJC/OBJCXX/HIP 有意义） |
| `CMAKE_<LANG>_COMPILE_FEATURES` | 当前编译器实际可用的特性列表 |
| `CMAKE_<LANG>_EXTENSIONS` | 是否启用该语言的编译器扩展 |

CUDA 还有一批专属变量，最重要的是 **`CMAKE_CUDA_ARCHITECTURES`**（指定目标 GPU 架构，如 `75;86;native`）以及对应 target 属性 `CUDA_ARCHITECTURES`、`CUDA_SEPARABLE_COMPILATION`（分离编译/设备链接）。HIP 有 `CMAKE_HIP_ARCHITECTURES`。

## 14.4.5 `CMAKE_<LANG>_FLAGS_INIT`：工具链文件中设置初始 flag 的正确方式

> 本小节讲清楚"用工具链文件预置 flag"的正确变量，与直接修改 `CMAKE_CXX_FLAGS` 的区别及其陷阱。

### 为什么不能在工具链文件里直接改 `CMAKE_CXX_FLAGS`

`CMAKE_CXX_FLAGS` 是**用户可覆盖的缓存变量**。它的完整初始化链是这样的：

1. CMake 读取工具链文件（`--toolchain` / `CMAKE_TOOLCHAIN_FILE`）。
2. 读完工具链文件后，CMake 用 **`CMAKE_CXX_FLAGS_INIT`** 的值来初始化 `CMAKE_CXX_FLAGS` 的**首次缓存写入默认值**。
3. 若用户（或 preset 的 `cacheVariables`）已在缓存里设了 `CMAKE_CXX_FLAGS`，则缓存值生效、不被覆盖。

如果工具链文件写：

```cmake
# 错误：工具链文件里直接赋值 CMAKE_CXX_FLAGS
set(CMAKE_CXX_FLAGS "-march=armv8-a -mfpu=neon")
```

那么每次**重新配置**（`cmake .`，不清缓存），工具链文件都会强行覆盖用户在缓存里改好的值，而且语义与"用户传 `-DCMAKE_CXX_FLAGS=...`"产生冲突——究竟谁的优先级更高，行为依赖 `set()` 的位置，极难预测。

### 正确做法：`CMAKE_<LANG>_FLAGS_INIT`

**`CMAKE_<LANG>_FLAGS_INIT`** 是专门设计给工具链文件（和初始化阶段）使用的**初始值占位变量**。语义：

> 若缓存里还**没有** `CMAKE_<LANG>_FLAGS` 的值，就用 `CMAKE_<LANG>_FLAGS_INIT` 来初始化它；若缓存已有值，`FLAGS_INIT` 的内容会被**附加**到缓存值后面（注意：自 CMake 3.7+ 起的精确行为），不会覆盖用户已有的设置。

因此，在工具链文件里正确的写法是：

```cmake
# cmake/toolchains/aarch64-linux-gnueabihf.cmake

set(CMAKE_SYSTEM_NAME      Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

set(CMAKE_C_COMPILER   aarch64-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnueabihf-g++)

# ✅ 正确：用 _INIT 变量预置初始 flag，不会覆盖用户缓存
set(CMAKE_C_FLAGS_INIT   "-march=armv8-a")
set(CMAKE_CXX_FLAGS_INIT "-march=armv8-a")

# ✅ 也有 EXE / SHARED / MODULE / STATIC 对应的链接器 flag INIT 变量
set(CMAKE_EXE_LINKER_FLAGS_INIT    "-Wl,--gc-sections")
set(CMAKE_SHARED_LINKER_FLAGS_INIT "-Wl,--gc-sections")
```

对应的 INIT 变量族：

| INIT 变量 | 初始化的缓存变量 |
| --- | --- |
| `CMAKE_C_FLAGS_INIT` | `CMAKE_C_FLAGS` |
| `CMAKE_CXX_FLAGS_INIT` | `CMAKE_CXX_FLAGS` |
| `CMAKE_<LANG>_FLAGS_INIT` | `CMAKE_<LANG>_FLAGS` |
| `CMAKE_EXE_LINKER_FLAGS_INIT` | `CMAKE_EXE_LINKER_FLAGS` |
| `CMAKE_SHARED_LINKER_FLAGS_INIT` | `CMAKE_SHARED_LINKER_FLAGS` |
| `CMAKE_MODULE_LINKER_FLAGS_INIT` | `CMAKE_MODULE_LINKER_FLAGS` |
| `CMAKE_STATIC_LINKER_FLAGS_INIT` | `CMAKE_STATIC_LINKER_FLAGS` |
| `CMAKE_<LANG>_FLAGS_<CONFIG>_INIT` | `CMAKE_<LANG>_FLAGS_<CONFIG>`（如 `_DEBUG_INIT`） |

> 📌 **使用场合总结**：
> - 工具链文件里——用 `CMAKE_<LANG>_FLAGS_INIT`，向目标平台/ABI 传递无法缺省的基础 flag（架构、FPU、ABI 选项等）。
> - 项目 `CMakeLists.txt` 里——不要动 `CMAKE_CXX_FLAGS` 全局变量，改用 `target_compile_options(... PRIVATE ...)` / `target_compile_features(...)`，精确、可移植。
> - 用户或 CI——通过 `-DCMAKE_CXX_FLAGS="..."` 命令行 / preset 的 `cacheVariables` 追加，不污染工具链层。

## 14.4.6 `CMAKE_CXX_SCAN_FOR_MODULES`：C++20 模块依赖扫描

**`CMAKE_CXX_SCAN_FOR_MODULES`**（CMake 3.28 引入）是一个布尔变量，控制 CMake 是否对 C++ 源文件执行**模块依赖扫描（module dependency scanning）**——即分析 `.cpp`/`.ixx` 里的 `import`/`export module` 语句，自动推导 C++20 命名模块的编译顺序依赖。

```cmake
# 全工程启用模块依赖扫描（默认在支持 C++20 模块的编译器下为 ON）
set(CMAKE_CXX_SCAN_FOR_MODULES ON)
```

**默认行为**：CMake 在检测到编译器具备模块支持能力（GCC 14+/Clang 16+/MSVC 19.34+）且 `CXX_STANDARD` ≥ 20 时，自动将此变量置 `ON`；其他情况为 `OFF`。

**何时需要手动设置**：

- 将 `OFF` 可临时禁用扫描（加速仅含传统头文件的项目的配置时间，避免扫描开销）。
- 当工程已完全迁移到 C++20 模块但编译器版本边缘情况未被自动检测到时，可强制置 `ON`。
- 对应的 target 级属性是 **`CXX_SCAN_FOR_MODULES`**（可 `set_target_properties(mylib PROPERTIES CXX_SCAN_FOR_MODULES OFF)` 对单个目标关闭）。

> 📖 **C++20 模块的完整用法**（`import std;`、BMI 生成与复用、`FILE_SET CXX_MODULES`、跨目标导入等）见 [[42.Cmake/20 - C++20 模块支持.md|第 20 章（C++20 模块支持）]]。本节仅说明这一开关变量的含义。

## 14.5 编译器识别

CMake 在启用语言时会自动探测编译器身份，结果存进只读变量，供生成器表达式和 `if()` 判断使用。

### 14.5.1 CMAKE_<LANG>_COMPILER_ID

**`CMAKE_<LANG>_COMPILER_ID`**：编译器厂商/家族的标识字符串。这是判断"是哪家编译器"的**唯一正确手段**（不要去解析编译器路径名）。常见取值：

| COMPILER_ID | 对应编译器 |
| --- | --- |
| `GNU` | GCC / g++ |
| `Clang` | 上游 LLVM Clang |
| `AppleClang` | Apple 自带的 Clang（与上游 `Clang` 分开） |
| `MSVC` | 微软 Visual C++（cl.exe） |
| `Intel` | 经典 Intel 编译器（icc/icpc，已停更） |
| `IntelLLVM` | 基于 LLVM 的新 Intel 编译器（icx/icpx，oneAPI） |
| `NVIDIA` | NVIDIA CUDA 编译器（nvcc） |
| `NVHPC` | NVIDIA HPC SDK 编译器（nvc/nvc++） |
| `ARMClang` | Arm Compiler 6（基于 Clang） |
| `ARMCC` | Arm Compiler 5（老的 armcc） |
| `TI` | 德州仪器编译器 |
| `XL` / `XLClang` | IBM XL（经典 / 基于 Clang） |
| `Fujitsu` | 富士通编译器 |
| `Cray` | Cray 编译器 |

> ⚠️ 两个高频坑：(1) `AppleClang` 不等于 `Clang`，在 macOS 上若想同时覆盖两者要写 `$<CXX_COMPILER_ID:Clang,AppleClang>`；(2) 新版 Intel `icx` 是 `IntelLLVM` 而非 `Intel`。

判断用法（脚本里）：

```cmake
if(CMAKE_CXX_COMPILER_ID STREQUAL "GNU")
    message(STATUS "Using GCC")
elseif(CMAKE_CXX_COMPILER_ID MATCHES "Clang")   # 同时匹配 Clang / AppleClang
    message(STATUS "Using some Clang")
endif()
```

生成器表达式里更简洁（推荐用于加 flag，见 14.3.3）：`$<CXX_COMPILER_ID:GNU,Clang,AppleClang>`。

### 14.5.2 CMAKE_<LANG>_COMPILER_VERSION

**`CMAKE_<LANG>_COMPILER_VERSION`**：编译器版本号字符串（如 `13.2.0`、`19.40.33811`）。常配合 `VERSION_GREATER_EQUAL` 等版本比较运算符做最低版本门槛：

```cmake
if(CMAKE_CXX_COMPILER_ID STREQUAL "GNU"
   AND CMAKE_CXX_COMPILER_VERSION VERSION_LESS 11)
    message(FATAL_ERROR "需要 GCC 11 或更高版本以支持 C++20")
endif()
```

### 14.5.3 CMAKE_<LANG>_COMPILER_FRONTEND_VARIANT

**`CMAKE_<LANG>_COMPILER_FRONTEND_VARIANT`**：编译器的**命令行前端风格**，取值通常为 `GNU` 或 `MSVC`。它解决的是 `clang-cl` 这类"内核是 Clang、但命令行参数学 MSVC（用 `/W4` 而非 `-Wall`）"的混血情况：

- 用 `clang-cl` 时：`CMAKE_CXX_COMPILER_ID` = `Clang`，但 `CMAKE_CXX_COMPILER_FRONTEND_VARIANT` = `MSVC`。
- 用普通 `clang` 时：两者都偏 `GNU` 风格。

所以"决定加 `-Wall` 还是 `/W4`"更稳妥的依据其实是 FRONTEND_VARIANT 而非 COMPILER_ID。生成器表达式有对应的 `$<CXX_COMPILER_FRONTEND_VARIANT:MSVC>`：

```cmake
target_compile_options(app PRIVATE
    $<$<CXX_COMPILER_FRONTEND_VARIANT:GNU>:-Wall;-Wextra>
    $<$<CXX_COMPILER_FRONTEND_VARIANT:MSVC>:/W4>
)
```

### 14.5.4 MSVC / MSVC_VERSION 等便捷变量

针对 Windows/MSVC，CMake 提供一组便捷布尔/数值变量（注意它们是**平台/编译器级**判断，对 `clang-cl` 这种"MSVC 前端"通常也为真）：

- **`MSVC`**：当编译器使用 MSVC ABI / 命令行时为真（含 `cl.exe` 和 `clang-cl`）。
- **`MSVC_VERSION`**：MSVC 编译器版本的数值编码，如 `1940`（对应 VS 2022 17.10 一带）。便于按 VS 版本设门槛。
- **`MSVC_TOOLSET_VERSION`**：工具集版本，如 `143`。
- **`MSVC_IDE`**：是否在 Visual Studio IDE 生成器下。
- **`WIN32`** / **`UNIX`** / **`APPLE`**：目标平台判断（平台维度，不是编译器维度，但常一起用）。

```cmake
if(MSVC)
    target_compile_options(app PRIVATE /utf-8 /W4)
    if(MSVC_VERSION GREATER_EQUAL 1930)   # VS 2022+
        target_compile_options(app PRIVATE /Zc:preprocessor)
    endif()
endif()
```

## 14.6 预编译头 PCH

### 14.6.1 target_precompile_headers（3.16+）

预编译头（Precompiled Header）把一批稳定、重量级的头文件（标准库、第三方大头、Windows.h 等）预先编译成中间产物，后续每个源文件复用，可显著缩短编译时间。CMake **3.16** 起内建支持，跨编译器（GCC/Clang/MSVC）统一：

```cmake
target_precompile_headers(<target> <PRIVATE|PUBLIC|INTERFACE> <header>... [...])
```

```cmake
target_precompile_headers(app PRIVATE
    <vector>
    <string>
    <unordered_map>
    "mylib/bigheader.hpp"
)
```

规则要点：

- 尖括号 `<vector>` 表示系统头，引号 `"foo.hpp"` 表示项目头（写法与 `#include` 一致）。
- CMake 自动生成一个聚合头并强制注入到该 target 的每个源文件最前面，无需你改源码的 `#include`。
- 可见性照旧：`PUBLIC`/`INTERFACE` 会把 PCH 要求传播给下游 target（下游也会用同一套 PCH 头）。
- 还可以用生成器表达式按语言隔离，避免把 C++ 头塞进 C 源文件：
  ```cmake
  target_precompile_headers(app PRIVATE
      "$<$<COMPILE_LANGUAGE:CXX>:<vector>>"
  )
  ```

### 14.6.2 REUSE_FROM：多 target 复用同一份 PCH

`REUSE_FROM` 让一个 target 直接复用另一个 target 已经编好的 PCH，避免每个 target 各编一份、省时间省磁盘：

```cmake
target_precompile_headers(lib_a PRIVATE <vector> <string>)
target_precompile_headers(lib_b REUSE_FROM lib_a)   # 复用 lib_a 的 PCH
```

使用 `REUSE_FROM` 的前提是两个 target 的编译环境**兼容**（相同编译器、相同语言标准、相同会影响 PCH 的关键 flag/宏定义），否则会编译失败。被复用方（`lib_a`）需要先用普通形式定义好自己的 PCH。

### 14.6.3 注意事项与坑

- **不是越多越好**：放进 PCH 的应是"几乎所有源文件都用、且很少改动"的重头。把会频繁修改的项目自有头放进去，反而会因 PCH 失效而频繁重编、得不偿失。
- **可能掩盖缺失的 include**：因为 PCH 头被注入每个源文件，某个 `.cpp` 即使忘了 `#include <vector>` 也能编过——这会破坏头文件自包含性，关掉 PCH 后构建立刻崩。可用 `CMAKE_PCH_WARN_INVALID`、并在 CI 里偶尔关 PCH（`-DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`）做自检。
- **全局开关**：`CMAKE_DISABLE_PRECOMPILE_HEADERS=ON` 可一键禁用整个工程的 PCH，便于排查上一条问题。
- 对外发布的库谨慎用 `PUBLIC`/`INTERFACE` PCH，以免把你的 PCH 选择强加给使用者。

## 14.7 Unity / Jumbo build

### 14.7.1 开关

Unity build（又称 jumbo build）把同一 target 的多个 `.cpp` 拼进少数几个"巨型翻译单元"再编译，借此大幅减少重复解析头文件和模板实例化的开销，常能显著缩短全量构建时间。CMake 3.16 起内建。

- **`CMAKE_UNITY_BUILD`**：变量，设为 `ON` 后，之后创建的 target 默认启用 Unity build（用它初始化 target 的 `UNITY_BUILD` 属性）。
- **`UNITY_BUILD`**：target 属性，单独控制某 target 是否走 Unity build。
- **`UNITY_BUILD_BATCH_SIZE`**：target 属性，每个 jumbo 文件最多合并多少个源文件（默认值为 8）。设为 `0` 表示"全部源文件合并进一个"。

```cmake
set(CMAKE_UNITY_BUILD ON)              # 全工程默认开启

add_library(fastlib ...)
set_target_properties(fastlib PROPERTIES
    UNITY_BUILD ON
    UNITY_BUILD_BATCH_SIZE 16          # 每 16 个源文件合一组
)

# 对某个不兼容 Unity 的 target 单独关闭
set_target_properties(legacy PROPERTIES UNITY_BUILD OFF)
```

还有 `UNITY_BUILD_MODE`（`BATCH` 按批 / `GROUP` 按显式分组）以及源文件级属性 `UNITY_GROUP`，用于手动把相关源文件分到同一组。

### 14.7.2 收益与坑

收益：编译墙钟时间常能降低数成，对模板/头文件密集的 C++ 工程尤其明显。

坑（都是因为"多个 .cpp 被塞进同一个翻译单元"导致符号互相可见）：

- **匿名命名空间冲突**：两个文件各自的 `namespace { int g = 1; }` 合并后变成重定义。
- **`static` 全局符号冲突**：不同文件里同名的 `static` 函数/变量撞名。
- **宏污染**：某文件 `#define` 的宏会泄漏到同批后续文件。
- **`using namespace` 泄漏**：文件顶部的 `using namespace foo;` 影响到同批其他文件。
- **包含顺序敏感**：依赖特定 include 先后顺序的代码可能行为改变。

应对：把改动频繁或不兼容的源文件用 `set_source_files_properties(foo.cpp PROPERTIES SKIP_UNITY_BUILD_INCLUSION ON)` 单独排除；或对该 target `UNITY_BUILD OFF`。建议 Unity build 只在 CI/Release 全量构建时开，本地增量开发可关（增量改一个文件会触发整批重编，反而变慢）。

## 14.8 IPO / LTO

### 14.8.1 概念与变量

过程间优化（IPO，Interprocedural Optimization），在 GCC/Clang 上即链接时优化（LTO，Link-Time Optimization），让优化器跨翻译单元做内联与优化，通常能进一步提升运行时性能、缩小体积，代价是链接更慢。

- **`CMAKE_INTERPROCEDURAL_OPTIMIZATION`**：变量，设为 `ON` 后，之后创建的 target 默认启用 IPO（用它初始化 target 的 `INTERPROCEDURAL_OPTIMIZATION` 属性）。也有按配置的变体 `CMAKE_INTERPROCEDURAL_OPTIMIZATION_<CONFIG>`，例如只在 Release 开。
- **`INTERPROCEDURAL_OPTIMIZATION`**：target 属性，单独控制某 target；同样有 `INTERPROCEDURAL_OPTIMIZATION_<CONFIG>`。

### 14.8.2 用 CheckIPOSupported 先检测

并非所有编译器/平台/配置都支持 IPO，直接开可能在链接阶段才报错。**正确做法是用 `CheckIPOSupported` 模块的 `check_ipo_supported()` 先探测**：

```cmake
include(CheckIPOSupported)
check_ipo_supported(RESULT ipo_ok OUTPUT ipo_msg)

if(ipo_ok)
    message(STATUS "IPO/LTO 已启用")
    set(CMAKE_INTERPROCEDURAL_OPTIMIZATION ON)     # 全工程
else()
    message(WARNING "IPO/LTO 不受支持：${ipo_msg}")
endif()
```

`check_ipo_supported()` 的常用形参：

- `RESULT <var>`：写入布尔结果（支持为真）。**不写 `RESULT` 时，不支持会直接 `FATAL_ERROR`**——这在"我确定要用 IPO，不支持就该报错"时反而方便。
- `OUTPUT <var>`：写入不支持时的诊断信息。
- `LANGUAGES <langs>`：限定要检查的语言（如 `CXX`、`C CXX`）。

只给单个 target 开（推荐更细粒度）：

```cmake
include(CheckIPOSupported)
check_ipo_supported(RESULT ok)
if(ok)
    set_property(TARGET app PROPERTY INTERPROCEDURAL_OPTIMIZATION TRUE)
    # 或仅 Release：
    set_property(TARGET app PROPERTY INTERPROCEDURAL_OPTIMIZATION_RELEASE TRUE)
endif()
```

> 历史提示：IPO 的现代行为由策略 `CMP0069` 控制（CMake 3.9 引入）。把 `cmake_minimum_required(VERSION 3.9)` 或更高写好即取 `NEW` 行为——CMake 会真正传递 IPO flag，并在不支持时按上述规则处理，而不是早期那种静默忽略。CMake 4.x 下只要正常声明最低版本即可，无需手动设策略。

## 14.9 位置无关代码 PIC

位置无关代码（PIC，Position-Independent Code）让生成的目标码可被加载到任意地址，是构建共享库（`.so`/`.dll` 的 Unix 侧）的前提；把要进共享库的静态库/对象也编成 PIC，能避免链接报错（如经典的 `recompile with -fPIC`）。

- **`CMAKE_POSITION_INDEPENDENT_CODE`**：变量，设为 `ON` 后初始化之后 target 的同名属性。
- **`POSITION_INDEPENDENT_CODE`**：target 属性，单独控制某 target。对 `SHARED`/`MODULE` 库，CMake 默认即为 PIC；对 `STATIC` 库和可执行文件默认非 PIC，需要时显式开。

```cmake
# 全工程统一 PIC（最省心，尤其当静态库会被链进共享库时）
set(CMAKE_POSITION_INDEPENDENT_CODE ON)

# 或只给某静态库开，因为它要被某个 .so 链接
add_library(util STATIC ...)
set_target_properties(util PROPERTIES POSITION_INDEPENDENT_CODE ON)
```

> 与可执行文件 PIE 的关系：CMake 还有策略 `CMP0083` 控制是否给可执行文件加 PIE（位置无关可执行文件）flag。需要可移植地控制 PIE 时，配合 `check_pie_supported()`（来自 `CheckPIESupported` 模块）使用，思路与 14.8 的 IPO 检测一致。

## 14.10 编译命令数据库 compile_commands.json

**`CMAKE_EXPORT_COMPILE_COMMANDS`**：设为 `ON` 后，CMake 在构建目录生成 `compile_commands.json`——一份"每个源文件用什么完整命令行编译"的清单（JSON Compilation Database）。它是 clangd、clang-tidy、ccls、各类 IDE/编辑器做精准跳转、补全和静态分析的标准输入。

```bash
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

也可以在 `CMakeLists.txt` 顶部（`project()` 之前）设：

```cmake
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
```

要点：

- **仅 Makefile 与 Ninja 生成器支持**导出该文件；Visual Studio、Xcode 等 IDE 生成器**不生成**（这两者有各自的 IDE 内索引机制）。
- 文件生成在构建目录（如 `build/compile_commands.json`）。clangd 默认会向上层目录查找它；常见做法是在项目根放一个软链接/拷贝指向 build 下的文件：
  ```bash
  ln -s build/compile_commands.json compile_commands.json   # Unix
  ```
- 用 `CMAKE_EXPORT_COMPILE_COMMANDS` 这个名字时，也可以通过环境变量 `CMAKE_EXPORT_COMPILE_COMMANDS` 影响默认值。
- 它记录的是配置时确定的命令，生成器表达式会被展开成实际 flag。

## 14.11 编译特性检测模块（速查）

工程里经常需要"在配置阶段试编一段代码 / 试加一个 flag / 查一个头或符号是否存在"，再据此决定要不要定义某个宏。CMake 提供一组 `Check*` 模块完成这类**编译期能力探测**。这里只给一句话用途，**完整用法、参数、`CMAKE_REQUIRED_*` 变量族与避坑见[[42.Cmake/17 - 模块与常用工具模块.md|第 17 章（模块与常用工具模块）]]**。

| 模块 / 命令 | 一句话用途 |
| --- | --- |
| `include(CheckCXXSourceCompiles)` → `check_cxx_source_compiles(<code> <var>)` | 试编一段 C++ 源码，能编过则 `<var>` 为真（探测语言特性/平台行为）。 |
| `include(CheckCXXSourceRuns)` → `check_cxx_source_runs(...)` | 不仅编过还能成功运行才为真（探测运行期行为，交叉编译时慎用）。 |
| `include(CheckIncludeFileCXX)` → `check_include_file_cxx(<header> <var>)` | 检查某 C++ 头文件是否存在且可包含（C 版为 `CheckIncludeFile`）。 |
| `include(CheckSymbolExists)` → `check_symbol_exists(<symbol> <headers> <var>)` | 检查某符号（函数/宏）在给定头文件下是否存在（C++ 版 `CheckCXXSymbolExists`）。 |
| `include(CheckCXXCompilerFlag)` → `check_cxx_compiler_flag(<flag> <var>)` | 检查当前编译器是否接受某个 flag（如 `-march=native`），接受才加。 |
| `include(CheckTypeSize)` → `check_type_size(<type> <var>)` | 获取某类型的字节大小（兼顾存在性）。 |
| `include(CheckLanguage)` → `check_language(<lang>)` | 探测某语言编译器是否可用（见 14.4.2）。 |

典型组合用法（配合 `target_compile_options` 仅在编译器接受时加 flag）：

```cmake
include(CheckCXXCompilerFlag)
check_cxx_compiler_flag("-march=native" HAS_MARCH_NATIVE)
if(HAS_MARCH_NATIVE)
    target_compile_options(app PRIVATE -march=native)
endif()
```

## 本章小结

本章梳理了 CMake 4.3.4 下管理编译器、语言标准与编译期能力的现代方式：

- **语言标准**：用 `CMAKE_<LANG>_STANDARD` + `..._STANDARD_REQUIRED ON` + `..._EXTENSIONS OFF` 三件套设全局基线，或用 target 级同名属性精确控制；C++ 取值 `98/11/14/17/20/23/26`，C 取值 `90/99/11/17/23`。务必把 `STANDARD_REQUIRED` 设为 `ON` 以杜绝静默降级。
- **compile features**：现代工程首选 `target_compile_features(t PUBLIC cxx_std_NN)` 元特性——能让标准要求沿依赖**传播**，优于直接设 STANDARD；C++17 起不再有细粒度具体特性，统一用 `cxx_std_NN`。
- **编译/链接选项**：用 `target_compile_options` / `target_link_options`（3.13+）替代老式 `add_compile_options`，并几乎总是配合生成器表达式 `$<$<CXX_COMPILER_ID:...>:...>` 按编译器/配置/语言加 flag，避免污染。
- **多语言**：`project(... LANGUAGES ...)` 或 `enable_language()` 启用 C/CXX/CUDA/OBJC/Fortran/Swift/HIP/ISPC/CSharp/ASM 等；用 `CheckLanguage` 先探测再启用。
- **编译器识别**：靠 `CMAKE_<LANG>_COMPILER_ID`（区分 `GNU`/`Clang`/`AppleClang`/`MSVC`/`IntelLLVM` 等）、`..._VERSION`、`..._COMPILER_FRONTEND_VARIANT`（识别 `clang-cl`）及 `MSVC`/`MSVC_VERSION`，绝不要靠解析路径名。
- **编译期加速与优化**：PCH（`target_precompile_headers` + `REUSE_FROM`，3.16+）、Unity build（`CMAKE_UNITY_BUILD` / `UNITY_BUILD_BATCH_SIZE`）、IPO/LTO（`CMAKE_INTERPROCEDURAL_OPTIMIZATION` + `check_ipo_supported()` 先检测）、PIC（`CMAKE_POSITION_INDEPENDENT_CODE`）——每一项都有对应的"先检测/可单独关闭"的稳妥用法。
- **工具链集成**：`CMAKE_EXPORT_COMPILE_COMMANDS=ON` 生成 `compile_commands.json` 供 clangd/IDE（仅 Makefile/Ninja 生成器）。
- **能力探测**：`Check*` 系列模块做"试编/试 flag/查头查符号"，详解见第 17 章。

一句话原则贯穿全章：**优先 target 级、优先声明式（features/属性）、优先用生成器表达式做条件、优先"先检测后启用"**——这是写出可移植、可维护、可被工具消费的现代 CMake 工程的关键。
