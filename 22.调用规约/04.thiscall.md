# `__thiscall` 详解（This Call / C++ 成员函数调用规约）

> 关键词：`__thiscall` ｜ **`this` 走 `ECX`** ｜ callee 清栈 `ret N` ｜ C++ 非静态成员函数默认 ｜ 可变参数成员函数例外
> 上级：[[22.调用规约/00.总览|x86 三种调用规约总览]]

`thiscall` 是 **C++ 非静态成员函数**在 32 位 x86（MSVC）上的**默认**调用规约。它专为解决一个 C 里不存在的问题而生：成员函数除了显式参数，还有一个隐藏的 `this` 指针要传。

它的做法可以一句话概括：**`this` 单独塞进 `ECX`，其余参数完全照 stdcall 办**（压栈、从右往左、callee 用 `ret N` 清栈）。因此可把它理解成「只用 `ECX` 传 `this`、不用 `EDX` 传参的半个 [[22.调用规约/03.fastcall.md|fastcall]]」。

> ⚠️ 本页以 **MSVC `__thiscall`** 为准。`thiscall` 在不同编译器/ABI 下差异极大（GCC/Clang 的 Itanium ABI 根本没有这个概念），见下文「跨编译器视角」。

---

## 核心规则（MSVC）

| 项目 | 规定 |
|------|------|
| **适用对象** | C++ **非静态成员函数**（参数个数固定时）；编译器默认套用，无需手写 `__thiscall` |
| **`this` 传递** | 隐藏的 `this` 指针 → **`ECX`**（不压栈、不占用显式参数位） |
| **显式参数传递** | 全部经**栈**传递（与 stdcall 相同），无其他寄存器参数 |
| **压栈顺序** | **从右往左**（与 cdecl/stdcall 相同） |
| **栈清理** | **被调用者（callee）清** —— `ret N`，`N` **只算压在栈上的显式参数**，**不含 `this`**（`this` 在 `ECX`） |
| **返回值** | 整型/指针 → `EAX`；64 位 → `EDX:EAX`；浮点 → x87 栈顶 `ST(0)` |
| **callee-saved** | `EBX`、`ESI`、`EDI`、`EBP`（同前三者；`ECX` 被征用传 `this`，属易失） |
| **名称修饰** | **C++ name mangling**（非 C 链接的 `@N` 体系）；公有成员形如 `?func@Class@@QAE...@Z`，其中 `E` 即 thiscall 标记 |
| **可变参数成员函数** | **例外！** 退化为 `__cdecl`：`this` 改为**压栈**（作为隐藏的最左参数），caller 清栈 |

> 关键细节：`ret N` 的 `N` **不包含 `this`**。两个 `int` 参数的成员函数 → `ret 8`（不是 12），因为 `this` 在 `ECX` 里、没占栈。这是 thiscall 逆向时最容易数错的地方。

## 汇编示例

C++ 源码：

```cpp
struct Point {
    int x, y;
    int sum(int bias);          // 非静态成员函数 → 默认 __thiscall
};
int Point::sum(int bias) { return x + y + bias; }

Point p;                        // 假设 p 地址已知
int r = p.sum(10);
```

调用方（caller）：

```asm
push 10            ; bias → 压栈（普通显式参数，从右往左）
lea  ecx, [p]      ; ★ this → ECX（对象地址，不压栈）
call ?sum@Point@@QAEHH@Z
mov  [r], eax      ; 取返回值，调用后无 add esp（callee 已清）
```

被调用方（callee）：

```asm
?sum@Point@@QAEHH@Z:
    push ebp
    mov  ebp, esp
    ; this 在 ECX；x 在偏移 0，y 在偏移 4
    mov  eax, [ecx]      ; this->x
    add  eax, [ecx+4]    ; + this->y
    add  eax, [ebp+8]    ; + bias（栈上唯一的显式参数）
    pop  ebp
    ret  4               ; ★ callee 清栈：只清 bias=4 字节；this 在 ECX 不占栈
```

> 指纹组合：**`call` 前往 `ECX` 装「对象指针」+ 显式参数压栈 + callee `ret N`（N 不含 this）**。函数体内大量 `[ecx+偏移]` 形式的成员访问是另一记强信号。
>
> （MSVC Debug 版常先 `mov [ebp-4], ecx` 把 `this` 存进局部变量再用；Release 版多半全程留在 `ECX`。本例按 Release 风格简化。）

## 设计动机：为什么 `this` 单独走 `ECX`

成员函数体内**几乎每一次**字段访问都要用到 `this`（`this->x`、`this->y`……）。若像普通参数那样把 `this` 压栈，则每次访问都得先从栈里把它读进寄存器，内存往返频繁。

把 `this` 常驻一个寄存器（`ECX`）后：

- 字段访问直接 `[ecx+偏移]`，**省去反复读栈**；
- `ECX` 是 caller-saved（易失）寄存器，被征用不影响 callee-saved 的保存契约；
- 其余参数仍走栈、callee 清栈，**沿用 stdcall 的小体积优势**（成员函数同样被大量调用）。

可见 thiscall 是「fastcall 的省栈思路」+「stdcall 的清栈方式」针对 `this` 的特化组合。

---

## 与 fastcall 的区别（最易混淆）

两者都在 `call` 前往 `ECX` 装值、都 callee 清栈，反汇编初看很像。**决定性差异：`EDX` 用不用来传参**。

| 维度 | `__thiscall` | `__fastcall` |
|------|--------------|--------------|
| `ECX` 装的是 | **`this` 对象指针** | 第 1 个显式参数 |
| `EDX` | **不用于传参** | 第 2 个显式参数 |
| 寄存器传参个数 | 仅 `this` 一个（且非显式参数） | 最多两个显式参数 |
| `ret N` 的 N | 显式栈参数（**不含 this**） | 全部栈参数（寄存器那两个不计） |
| 适用 | C++ 非静态成员函数（默认） | 任意函数（需显式 `__fastcall`） |
| 名称修饰 | C++ mangling，含 `QAE`/`E` | C 链接 `@func@N` |

> 一句话判别：**只见 `ECX`、不见 `EDX` 参与传参 → thiscall；`ECX` 和 `EDX` 都装了实参 → fastcall。**

---

## 可变参数成员函数：唯一的例外

成员函数若带 `...`（如 `void Log(const char* fmt, ...)`），callee 无法在编译期算出 `N`，于是 **thiscall 失效，整体退化为 `__cdecl`**：

- `this` **不再走 `ECX`**，而是和普通参数一样**压栈**——作为隐藏的**最左参数**（最后压、地址最低，紧邻返回地址）；
- **caller 清栈**（`add esp, N`），因为只有调用方知道这次传了几个变参。

这与 [[22.调用规约/01.cdecl.md|cdecl 支持可变参数]] 的原理完全一致：可变参数 ⇔ caller 清栈 ⇔ `this` 也只能压栈。逆向时如果一个 C++ 成员函数把 `this` 压栈而非装 `ECX`，第一反应就该是「它是个变参成员函数」。

---

## 名称修饰与静态成员

成员函数是 **C++ 链接**，套用完整 name mangling，**没有** cdecl/stdcall/fastcall 那种简洁的 `_func` / `_func@N` / `@func@N`：

```
int Point::sum(int)   →   ?sum@Point@@QAEHH@Z
```

拆解 `?sum@Point@@QAEHH@Z`：

- `?sum@Point@@` —— 类 `Point` 的成员函数 `sum`；
- `Q` —— 访问级别 **public**（`I`=protected、`A`=private）；
- `A` —— `this` 的 cv 限定为**无**（`B`=const → 常量成员函数为 `QBE`）；
- `E` —— **`__thiscall` 标记**（对照：`A`=cdecl、`G`=stdcall、`I`=fastcall）；
- `HH` —— 返回 `int` + 一个 `int` 参数（`H` 即 `int`）；`@Z` —— 参数表结束。

> 因此在一堆修饰名里看到 `QAE` / `IAE` / `AAE`（访问级 + `E`）开头的签名，基本就是某个 thiscall 成员函数。

**静态成员函数不是 thiscall**：它没有 `this`，按 `__cdecl` 编译，修饰名里是 `SA`（`S`=static、`A`=cdecl）。这是「成员函数 ≠ 一定 thiscall」的常见误区。

---

## 跨编译器视角：thiscall 是 MSVC x86 的概念

`thiscall` 作为一种**独立**调用规约，主要是 **MSVC + 32 位 x86** 的产物：

- **GCC / Clang（Itanium C++ ABI，Linux x86）**：**没有**单独的 thiscall。`this` 只是被当作**隐式的第一个参数**，按平台通行的 C 规约传递——32 位下即压栈（最左、caller 清，等价 cdecl 形态），无 `ECX` 特权。
- **GCC 针对 i386 的 `thiscall` 属性**：为兼容 Windows，GCC 提供 `__attribute__((thiscall))`，模拟 MSVC 的「`this` 走 `ECX` + callee 清栈」。
- **显式关键字**：MSVC 从 VS2005 起允许显式书写 `__thiscall`（例如声明与成员函数指针匹配的函数指针类型），但日常几乎用不到——编译器对成员函数**隐式**采用即可。

> 与 [[22.调用规约/03.fastcall.md|fastcall 的可移植性警告]] 同理：thiscall 的二进制形态高度依赖编译器，**不适合作为跨编译器的公开 ABI**；要跨边界暴露功能，用 `extern "C"` 包一层 cdecl/stdcall 自由函数。

---

## 64 位下的归宿

进入 **x86-64**，thiscall 和其它三种规约一样「合流」、关键字被接受但忽略：`this` 退化为**普通的第一个整型参数**，并入平台唯一约定——

- **Windows x64**：`this` → **`RCX`**（第一个整型参数寄存器），后续显式参数依次走 `RDX, R8, R9`；
- **System V（Linux/macOS）x64**：`this` → **`RDI`**。

即 64 位下不再有「`this` 专属规约」，但 `this` 落在首个参数寄存器这一点，恰是它 32 位 `ECX` 待遇的自然延续。

## 逆向识别

- `call` 之前把一个**对象指针**（常来自 `new` 的返回值、`lea ecx, [局部对象]`、或先前保存的指针）装入 **`ECX`**，且 **`EDX` 未参与传参**，函数 `ret N` 收尾 → **thiscall**。
- 函数体内频繁出现 **`[ecx+偏移]`** 形式的成员字段访问（或先 `mov [ebp-4], ecx` 存档再用）。
- **虚函数调用**：先 `mov ecx, 对象指针` 设好 `this`，再 `mov eax, [ecx]`（取 vtable 指针）、`call [eax+偏移]`（按槽位间接调用）——「`ECX=this` + 间接 `call`」是 C++ 虚调用的典型画面。
- 修饰名形如 `?name@Class@@QAE...@Z`（含 `QAE`/`IAE`/`AAE` 等 `E` 结尾的访问段）。

> 对照排除：`ECX` **和** `EDX` 都装了实参 → [[22.调用规约/03.fastcall.md|fastcall]]；参数全压栈、无 `ECX` 传指针、`ret N` → [[22.调用规约/02.stdcall.md|stdcall]]；`this` 反常地压了栈（成员函数却 caller 清栈）→ **变参成员函数**（已退化为 cdecl）。

---

## 虚函数调用的汇编展开

虚函数调用是 thiscall 在逆向中最常见的完整画面：通过对象的 vtable 指针做**两次间接寻址**，再发起 thiscall 风格的 `call`。

### 场景：基类指针调用虚函数

C++ 源码：

```cpp
struct Animal {
    virtual void speak();     // vtable[0]（第 0 个虚函数槽）
    virtual void move();      // vtable[1]
    int id;
};
void call_speak(Animal* p) {
    p->speak();               // 虚调用
}
```

生成的汇编（MSVC x86 Release）：

```asm
; p 在 [ebp+8]（或 ECX 寄存器，视内联情况）
mov  ecx, [ebp+8]        ; ★ ECX = this = p（对象指针）
mov  eax, [ecx]          ; ★ EAX = *this = vtable 指针（对象首地址处存放 vptr）
call [eax + 0]           ; ★ 调用 vtable[0] = Animal::speak（或其覆写版本）
```

三行汇编拆解：

| 指令 | 含义 |
|------|------|
| `mov ecx, [ebp+8]` | 把参数 `p`（对象地址）装入 `ECX` = 设置 `this` |
| `mov eax, [ecx]` | 取对象首 4 字节 = **vptr**（指向虚函数表的指针） |
| `call [eax+0]` | 通过 vptr 跳入 vtable 第 0 槽 = 运行时多态分派 |

若调用 `move()`（vtable 第 1 槽）则偏移改为 `[eax+4]`（每槽 4 字节，32 位指针）。

### 含数据成员的完整内存布局

```
对象 p 的内存布局（Animal 对象）：
  +0x00  [vptr]    → Animal::vtable
  +0x04  int id

Animal::vtable：
  [0]  → Animal::speak（或子类覆写）
  [4]  → Animal::move（或子类覆写）
```

逆向展开示意（含调用后流程）：

```asm
; 虚调用 p->speak() 的完整序列
mov  ecx, dword ptr [p]         ; ECX = 对象指针 this
mov  eax, dword ptr [ecx]       ; EAX = vptr（对象偏移 0 处）
call dword ptr [eax]            ; 调用 vtable[0]，callee 接收 ECX=this
; callee 返回后 ECX 可能已被覆盖（ECX 是 caller-saved）
```

> 逆向识别口诀：**`mov ecx, <obj>` → `mov eax, [ecx]` → `call [eax+N]`** = 虚调用三段式；N/4 即虚函数在 vtable 中的槽号（0-based）。

### 调试版的额外噪声

MSVC Debug 版会把 `this`（`ECX`）先存进局部变量 `[ebp-4]`，再从那里读，导致反汇编看起来更长：

```asm
; Debug 版序言（在函数体内见到这段，说明这是 Debug thiscall 成员函数）
mov  [ebp-4], ecx         ; this 存档到局部变量（MSVC debug 用于栈帧分析）
...
mov  ecx, [ebp-4]         ; 读回 this
mov  eax, [ecx]           ; 取 vptr
call [eax+N]              ; 虚调用
```

Release 版通常全程 `ECX` 常驻，不存不读。

## 多重继承下 this 指针调整

多重继承是 thiscall 最复杂的逆向场景：当一个对象**同时继承多个基类**时，不同基类子对象在内存中位于不同偏移，调用继承自不同基类的虚函数时 `this` 指针必须相应**偏移调整**。这种调整由编译器生成的 **this-adjusting thunk（调整块）** 完成，是 MSVC C++ ABI 特有的机制。

### 多重继承内存布局回顾

```cpp
struct A { virtual void fa(); int a; };    // A 子对象，偏移 0
struct B { virtual void fb(); int b; };    // B 子对象，偏移 N
struct C : A, B { void fa() override; void fb() override; };
```

`C` 对象的内存布局（MSVC x86）：

```
+0x00  [A::vptr] → C 的 A-slot vtable
+0x04  int A::a
+0x08  [B::vptr] → C 的 B-slot vtable
+0x0C  int B::b
```

`C` 从 `A`（偏移 0）和 `B`（偏移 8）各继承一个子对象。

### this 指针调整的必要性

```cpp
C obj;
B* bp = &obj;    // bp 指向 obj 内 B 子对象的起始地址，即 &obj + 8
bp->fb();        // 调用 C::fb，但 this 传入的是 bp（指向 B 子对象）
```

`C::fb` 的实现体需要访问 `C` 的完整成员（包括 `A::a`），因此它期望 `this` 指向 **`C` 对象的起始地址**（偏移 0），而不是 `B` 子对象的地址（偏移 8）。必须在进入 `C::fb` 之前把 `this` 从 `bp`（`&obj+8`）调整回 `&obj`（减去 8）。

### this-adjusting thunk 汇编示例

MSVC 为 `B` 的 vtable 槽生成一个「调整块」：

```asm
; C 的 B-slot vtable 中 fb 槽指向此 thunk，而非直接指向 C::fb
?fb_thunk_adjust@C@@:
    sub   ecx, 8        ; ★ this 调整：从 B 子对象地址 → C 对象起始地址
    jmp   ?fb@C@@UAEXXZ ; 跳转到真正的 C::fb 实现体（ECX 已经是正确的 this）
```

完整调用链：

```asm
; bp->fb() 的汇编（bp 指向 B 子对象）
mov  ecx, dword ptr [bp]         ; ECX = B 子对象地址（= &obj + 8）
mov  eax, dword ptr [ecx]        ; EAX = B-slot vptr
call dword ptr [eax + 0]         ; 进入 thunk：sub ecx,8 → jmp C::fb
                                 ; 此时 C::fb 收到的 ECX = &obj（已调整）
```

### 逆向识别 this 调整块

| 模式 | 含义 |
|------|------|
| vtable 槽指向的函数体只有 `sub ecx, N` + `jmp <真实函数>` | this-adjusting thunk，`N` 是基类子对象相对 C 完整对象的偏移 |
| vtable 槽指向的函数体有 `add ecx, N` + `jmp ...` | 反向调整（较少见，多为虚继承场景） |
| 函数符号名含 `_thunk`、`$thunk`，或 MSVC 内部标记 | 同上，编译器生成的调整块 |

> 调整量 `N` 即为该基类子对象在派生类对象中的字节偏移量；逆向多重继承类布局时，汇编里的 thunk 调整量是还原类层次结构的重要线索。

详见 [[23.C_C++运行时与ABI/08.多重继承与虚继承布局]] 中关于完整对象布局与 vtable 构造的深度分析。
