# x86 三种经典调用规约详解（cdecl / stdcall / fastcall）

> 本目录是**独立成册**的 x86 调用规约专题，纵深拆解 **32 位 x86** 上最经典的三种调用规约（calling convention / 调用约定）：
> `__cdecl`、`__stdcall`、`__fastcall`。
> 它是手写汇编、逆向工程、跨语言/跨编译器互操作（DLL 导出、P/Invoke、`extern "C"`）的命脉。

---

## 一、调用规约到底「约定」了什么

函数调用是 caller（调用者）与 callee（被调用者）之间的一纸契约。规约必须把下面五件事钉死，否则双方对不上账，栈就会被写花：

1. **参数怎么传** —— 走栈，还是走寄存器？走栈的话**压栈顺序**（从右往左 / 从左往右）？
2. **谁来清理参数占的栈空间** —— caller 清（caller-clean）还是 callee 清（callee-clean）？这是三者最核心的分水岭。
3. **返回值放哪** —— 整数/指针放 `EAX`（64 位用 `EDX:EAX`），浮点放 x87 栈顶 `ST(0)`。
4. **寄存器谁负责保护** —— `EAX/ECX/EDX` 是 **caller-saved（易失，volatile）**；`EBX/ESI/EDI/EBP` 是 **callee-saved（非易失）**，被调用者用了就得先存后恢复。这条**三种规约一致**。
5. **名称修饰（name decoration / mangling）** —— 编译器给符号加的前后缀，正是「编译期的规约指纹」，链接期靠它对齐。

> 第 3、4 条三者相同；**真正区分三种规约的，是第 1、2 条（参数走哪、谁清栈）和第 5 条（名字长什么样）**。

## 二、三者速览对比

| 维度 | `__cdecl` | `__stdcall` | `__fastcall` |
|------|-----------|-------------|--------------|
| **寄存器传参** | 无，全走栈 | 无，全走栈 | **前两个 ≤32 位整型/指针走 `ECX`、`EDX`** |
| **压栈顺序** | 从右往左 | 从右往左 | 余下参数从右往左 |
| **谁清栈** | **caller 清** | **callee 清** | **callee 清** |
| **清栈指令** | `call` 后 `add esp, N` | 函数内 `ret N` | 函数内 `ret N`（仅清栈上那部分） |
| **返回值** | `EAX` / `EDX:EAX` / `ST(0)` | 同左 | 同左 |
| **名称修饰（MSVC，C 链接）** | `_func` | `_func@N` | `@func@N` |
| **可变参数（`...`）** | ✅ 天然支持 | ❌ 不支持（MSVC 下退化为 cdecl） | ❌ 不支持 |
| **代码体积** | 略大（每个调用点都有清栈） | 小（清栈只在函数内一处） | 小 |
| **典型用途** | C/C++ **默认**、CRT、`printf` | **Win32 API**（`WINAPI`/`CALLBACK`） | 性能敏感的内部小函数 |

> `N` = 参数总字节数。例如两个 `int` 参数 → `N = 8`，stdcall 修饰为 `_add@8`，fastcall 修饰为 `@add@8`。

## 三、核心分水岭：谁清栈（caller-clean vs callee-clean）

参数压栈后，这段栈空间总得有人 `add esp` 收回。**由谁收，决定了一切派生差异**：

- **caller-clean（cdecl）**：每个调用点自己收尾。
  - 优点：caller 永远知道自己压了几个参数 → **天然支持可变参数**（`printf(fmt, ...)`）。
  - 代价：N 个调用点 = N 段清栈代码，**体积偏大**。

- **callee-clean（stdcall / fastcall）**：函数自己用 `ret N` 一次性收回。
  - 优点：清栈代码只在函数体内**一处**，调用点更干净，**体积更小**。
  - 代价：函数签名一旦固定，**参数个数不能变** → 不支持真正的 `...` 可变参数。

> ⚠️ **规约不匹配 = 栈失衡（stack imbalance）**：声明用 cdecl、实际函数是 stdcall（或反之），两边都清或都不清，`ESP` 在多次调用后逐渐漂移，最终崩在一个与现场无关的地方——这是 DLL/回调/P-Invoke 的经典疑难杂症。

## 四、逆向识别速查（看反汇编判规约）

| 反汇编现象 | 判定 |
|------------|------|
| `call` 之后紧跟 `add esp, N`（N>0） | **caller 清栈** → `cdecl`（或可变参数函数） |
| 函数以 `ret N`（N>0）结尾 | **callee 清栈** → `stdcall` / `fastcall` / `thiscall` |
| `call` 前把实参装入 `ECX`、`EDX`，且 `ret N` 收尾 | **`fastcall`**（两个寄存器参数） |
| `call` 前只往 `ECX` 装一个「对象指针」，其余压栈，`ret N` | **`thiscall`**（C++ 成员函数，`ECX = this`） |
| 参数全压栈、`ret`（无操作数）、调用点有 `add esp` | **`cdecl`** |
| 符号名形如 `_f` / `_f@8` / `@f@8` | 依次对应 **cdecl / stdcall / fastcall** |

## 五、64 位时代：三种规约的「合流」

进入 **x86-64**，OS 各自只保留**一种**调用规约，上面三个关键字在 64 位下**被接受但忽略**（全部塌缩为该平台唯一约定）：

- **Windows x64**：前四个整型走 `RCX, RDX, R8, R9`，调用者预留 **32 字节 shadow space**，callee 清栈靠展开表。
- **System V（Linux/macOS）x64**：前六个整型走 `RDI, RSI, RDX, RCX, R8, R9`，有 **128 字节 red zone**。

唯一仍有意义的扩展是 **`__vectorcall`**（VS2013+）：把向量/浮点参数塞进 `XMM/YMM`，32 位与 64 位下都有效。

> 结论：`cdecl/stdcall/fastcall` 的「三国演义」是 **32 位 x86 专属剧情**；写 64 位代码时不必纠结，但**读老二进制、做逆向、维护 Win32 遗留代码**时它仍是必修课。

### 5.1 64 位时代的调用规约合流

32 位的「三国演义」进入 64 位后收敛为两条主干，并衍生出向量扩展与 ARM 分支：

**Windows x64（Microsoft x64 ABI）** — 详见 [[05.Windows_x64调用规约]]
- 整型/指针前四个走 `RCX, RDX, R8, R9`；XMM0–XMM3 负责对应位置的浮点/向量参数。
- 调用者必须在栈上预留 **32 字节 home space（shadow space）**，即使参数全在寄存器里；被调用方可将寄存器参数溢出（spill）到这里。
- 清栈靠 **UNWIND_INFO 展开表**，而非 `ret N`；栈须 16 字节对齐（`call` 前）。
- `__cdecl`/`__stdcall`/`__fastcall` 关键字在 64 位下被编译器**静默忽略**，全部收敛为此规约。

**System V AMD64 ABI** — 详见 [[06.SystemV_AMD64调用规约]]
- 整型/指针前六个走 `RDI, RSI, RDX, RCX, R8, R9`；XMM0–XMM7 传浮点/向量。
- **128 字节 red zone**：`RSP` 以下 128 字节是已分配的「静默区」，叶函数（leaf function）可直接用，无需移动 RSP。
- 无 shadow space；调用者与被调用方严格遵循寄存器使用表，分 caller-saved / callee-saved 两组。

**`__vectorcall`（VS2013+）** — 详见 [[07.vectorcall]]
- fastcall 的超集；在 Windows x64 或 x86 下均有效。
- 整型参数规则与基础规约相同（Windows x64 下走 RCX/RDX/R8/R9），但**浮点/向量参数**走 `XMM0–XMM5`（x86 下也是 XMM0–XMM5），避免 SSE/AVX 数据在浮点寄存器与通用寄存器之间来回搬运。
- 是 64 位下**唯一仍有意义**的显式规约关键字，其余关键字 64 位下全被忽略。

**AAPCS64（ARM64 / AArch64）** — 详见 [[10.AAPCS64_ARM64调用规约]]
- ARM 架构统一规约（Procedure Call Standard for AArch64），适用于 Windows on ARM64、Linux ARM64、macOS Apple Silicon。
- 整型/指针前八个走 `X0–X7`；浮点/SIMD 前八个走 `V0–V7`（`S/D/Q` 别名）。
- 栈须 16 字节对齐；`X0–X18` 为 caller-saved，`X19–X28` 为 callee-saved，`X29=FP`，`X30=LR`（链接寄存器）。
- 无 shadow space，无 red zone（系统相关，内核有自己的 Red Zone 策略）。

**系统调用规约** — 详见 [[08.系统调用规约]]
- 与用户态调用规约独立：Linux x64 系统调用号走 `RAX`，参数走 `RDI/RSI/RDX/R10/R8/R9`（注意第四个是 `R10` 而非 `RCX`）；Windows 系统调用（syscall）由 `ntdll` 封装，用户层通常不直接使用。

### 5.2 返回值传递规则概览

不同类型的返回值走不同通道，详见 [[09.聚合体与返回值传递]]：

| 返回类型 | x86（三种规约共同） | Windows x64 | System V AMD64 |
|----------|---------------------|-------------|----------------|
| 整型/指针（≤32位） | `EAX` | `RAX` | `RAX` |
| 64位整型 | `EDX:EAX`（高:低） | `RAX` | `RAX` |
| 浮点（`float`/`double`） | x87 栈顶 `ST(0)` | `XMM0` | `XMM0` |
| **小结构体/聚合体** | 隐式指针（见下） | ≤8 字节→`RAX`；≤16 字节→`RAX:RDX` | 按类别分类（INTEGER/SSE/MEMORY） |
| **大结构体** | **隐式首参指针（RVO）** | 同 x86 隐式指针 | 同，由调用者分配缓冲区传入 |

**大结构体的隐式指针机制（x86 重点）**：
- 返回类型为结构体且**超过能直接塞进寄存器的大小**时，调用者在栈上（或堆上）分配足够的缓冲区，并将该缓冲区地址作为**隐藏的第一个参数**（最先压栈）传给被调用方。
- 被调用方把结构体写入该地址，并在 `EAX`（或 `RAX`）返回该指针本身。
- 这正是 **RVO（Return Value Optimization）** 的 ABI 基础：编译器将命名返回对象直接构造在调用者提供的缓冲区里，省去一次拷贝。
- 逆向识别：函数参数比源码声明多一个、`EAX` 返回值与第一个「指针类型参数」相同 → 通常即为大结构体返回的隐式指针。

## 六、扩展规约（旁系，了解即可）

| 规约 | 关键词 | 要点 |
|------|--------|------|
| **thiscall** | `__thiscall` | C++ 非静态成员函数默认；`this` 走 `ECX`，其余压栈，callee 清栈（可变参数成员函数除外）→ [[22.调用规约/04.thiscall.md\|详解]] |
| **vectorcall** | `__vectorcall` | fastcall 的超集；前若干向量/浮点参数走 `XMM0–XMM5`；32/64 位通用 |
| **naked** | `__declspec(naked)` | 不生成序言/尾声，栈帧全手写，写中断/钩子用 |
