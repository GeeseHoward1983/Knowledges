# `__fastcall` 详解（Fast Call / 寄存器传参调用规约）

> 关键词：`__fastcall` ｜ **前两个参数走 `ECX`、`EDX`** ｜ callee 清栈 ｜ 性能向
> 上级：[[22.调用规约/00.总览|x86 三种调用规约总览]]

`fastcall` 把**前两个**适合的参数塞进寄存器 `ECX`、`EDX`，省去压栈/读栈的内存往返，因此「fast」。剩余参数仍走栈，并由 **callee 清栈**（同 stdcall）。

> ⚠️ fastcall 在历史上**各编译器实现不一**（MSVC、Borland、GCC 的 `regparm` 各有差异）。本页以 **MSVC `__fastcall`** 为准。

---

## 核心规则（MSVC）

| 项目 | 规定 |
|------|------|
| **寄存器参数** | **从左往右**前两个 **≤32 位的整型/指针**参数 → `ECX`（第 1 个）、`EDX`（第 2 个） |
| **走栈的参数** | 其余参数、以及**浮点/`double`/`__int64`/结构体**等放不进寄存器的 → 仍压栈，**从右往左** |
| **栈清理** | **被调用者（callee）清** —— `ret N`，`N` 只算**压在栈上那部分**字节 |
| **返回值** | 整型/指针 → `EAX`；64 位 → `EDX:EAX`；浮点 → `ST(0)` |
| **callee-saved** | `EBX`、`ESI`、`EDI`、`EBP`（同前两者；但注意 `ECX/EDX` 已被征用为传参） |
| **名称修饰（MSVC，C 链接）** | `@func@N`，`N` = **所有参数**总字节数（含寄存器里那两个）。`int add(int,int)` → `@add@8` |

> 关键细节：**只有 ≤32 位的整型/指针**才进 `ECX/EDX`。`float`/`double`、`__int64`、大于 4 字节的结构体一律走栈——很多人误以为「前两个参数无论类型都进寄存器」，这是常见错误。

---

## 汇编示例（含第三个走栈的参数）

C 源码：

```c
int __fastcall add3(int a, int b, int c) { return a + b + c; }
int r = add3(1, 2, 3);
```

调用方（caller）：

```asm
push 3            ; c → 压栈（第 3 个，放不进寄存器）
mov  edx, 2       ; b → EDX（第 2 个）
mov  ecx, 1       ; a → ECX（第 1 个）
call @add3@12     ; N=12：3 个 int 的总字节数
mov  [r], eax
```

被调用方（callee）：

```asm
@add3@12:
    push ebp
    mov  ebp, esp
    ; a 在 ECX，b 在 EDX，c 在 [ebp+8]
    mov  eax, ecx
    add  eax, edx
    add  eax, [ebp+8]   ; c
    pop  ebp
    ret  4              ; ★ 只清栈上的 1 个参数(c)=4 字节，寄存器参数无需清
```

> 注意两个「12 vs 4」的反差：**名称修饰 `@12`** 按全部参数算，**`ret 4`** 只按压栈参数算。这是 fastcall 逆向时最易绕晕的点。

---

## 优缺点

✅ **优点**
- 前两个参数免去内存读写，**调用开销更低**，适合高频小函数（如内联辅助、热路径工具函数）。
- 兼具 callee 清栈的**小体积**优势。

❌ **缺点**
- `ECX/EDX` 被占用，函数内部少了两个自由的易失寄存器，复杂函数可能反而**增加溢出（spill）**，未必更快。
- **跨编译器不可移植**：MSVC 与 Borland/GCC 的 fastcall 语义不同，不适合做**公开 ABI**。
- 同样**不支持可变参数**（callee 清栈）。

---

## 逆向识别

- `call` 之前把实参装入 **`ECX`、`EDX`**，函数 `ret N` 收尾 → **fastcall**。
- 符号名形如 `@funcname@N`（前后都是 `@`）。
- 对照：若 `call` 前**只**往 `ECX` 装了一个看起来是「对象指针」的值、其余压栈、`ret N` → 多半是 **thiscall**（C++ 成员函数，`ECX = this`），见下。

---

## 旁系：thiscall 与 vectorcall

- **`__thiscall`**：C++ 非静态成员函数的默认规约。`this` → `ECX`，其余参数压栈（从右往左），callee 清栈。可视为「只用 `ECX` 传 `this` 的半个 fastcall」。可变参数成员函数例外（改为 caller 清栈、`this` 也压栈）。详见 [[22.调用规约/04.thiscall.md|__thiscall 详解]]。
- **`__vectorcall`**（VS2013+）：fastcall 的超集，额外用 `XMM0–XMM5` 传向量/浮点参数，整型仍走 `ECX/EDX`（x64 下走 `RCX/RDX/R8/R9`）。32 位、64 位均有效，是 64 位下**唯一仍有意义**的显式规约关键字。

详见 [[22.调用规约/00.总览|总览]] 的「扩展规约」一节。

## Borland/Delphi fastcall 与 MSVC __fastcall 的差异

历史上有多个编译器用「fastcall」命名自己的寄存器传参规约，但**寄存器选择和顺序各不相同**，形成了跨编译器不兼容的格局：

### 寄存器使用顺序对比

| 编译器 | 参数 1 | 参数 2 | 参数 3 | 其余参数 | 清栈方 |
|--------|--------|--------|--------|----------|--------|
| **MSVC `__fastcall`** | `ECX` | `EDX` | 压栈（从右往左） | 压栈 | callee（`ret N`） |
| **Borland C++ / Delphi `fastcall`（`register`）** | `EAX` | `EDX` | `ECX` | 压栈（从左往右） | callee |
| **Watcom C++（`__register`/`__fastcall`）** | `EAX` | `EDX` | `EBX` | `ECX` 或栈 | callee |

Borland/Delphi 的 `fastcall`（Delphi 中称 `register` 调用规约）用 **EAX/EDX/ECX** 前三个参数，且压栈顺序是**从左往右**（与 MSVC 从右往左相反）；Watcom 则另起一套。

### 跨编译器不兼容的具体表现

假设有如下声明和调用：

```c
// 函数签名
int __fastcall add3(int a, int b, int c);

// 调用方（MSVC 编译的 caller）
int r = add3(1, 2, 3);
```

**MSVC caller 生成的汇编**（a→ECX，b→EDX，c→栈）：

```asm
push 3           ; c 压栈
mov  edx, 2      ; b → EDX
mov  ecx, 1      ; a → ECX
call @add3@12
```

**Borland 编译的 callee `add3` 期待的参数布局**（a→EAX，b→EDX，c→ECX）：

```
Borland 视角：EAX=?（未赋值）, EDX=2, ECX=1, 栈顶=3
```

MSVC 把 `a=1` 塞入 `ECX`，Borland callee 却从 `EAX` 读第一个参数；`ECX` 被 Borland 当作第三个参数 `c`，而 MSVC 已经把 `c=3` 压栈了——双方对三个参数的落点理解完全不同，结果是**数据读错、计算结果错误**，甚至因栈错位而崩溃。

> 根本原因：两套 fastcall 用了不同的「前三 vs 前两」参数数量与不同的寄存器顺序，互相没有协商过协议。**凡涉及跨编译器二进制互操作，绝不能用 fastcall 做公开 ABI**；改用 `__stdcall`（或 64 位下的平台统一规约）。

### Delphi `register` vs MSVC `__fastcall` 名称映射

Delphi/Object Pascal 的 `register` 调用规约就是 Borland fastcall，**不是** MSVC fastcall：

```delphi
function Add3(a, b, c: Integer): Integer; register;  // Delphi: EAX/EDX/ECX
```

逆向 Delphi 二进制时，看到 EAX/EDX/ECX 三寄存器传参就是这套规约；看到 ECX/EDX 两寄存器才是 MSVC fastcall。

## GCC `__attribute__((regparm(N)))` 

GCC 在 32 位 x86 上提供了 `regparm` 属性，允许函数声明使用前 N 个整型参数走寄存器传递，是 GCC 自己的「fastcall 家族」成员。

### 基本语法与语义

```c
int __attribute__((regparm(3))) add3(int a, int b, int c);
// N 可以是 1、2 或 3（超过 3 无意义，x86 只有 EAX/EDX/ECX 三个 caller-saved 整型寄存器）
```

| `regparm(N)` | 参数 1 | 参数 2 | 参数 3 | 其余参数 |
|--------------|--------|--------|--------|----------|
| `regparm(1)` | `EAX`  | 栈     | 栈     | 栈       |
| `regparm(2)` | `EAX`  | `EDX`  | 栈     | 栈       |
| `regparm(3)` | `EAX`  | `EDX`  | `ECX`  | 栈       |

- 寄存器顺序是 **EAX → EDX → ECX**（与 Borland fastcall 相同，与 MSVC fastcall 的 ECX/EDX 不同）。
- 只有 **≤32 位整型/指针**进寄存器；浮点、`long long`、结构体仍走栈。
- 清栈方：默认跟随基础调用规约（cdecl → caller 清，stdcall → callee 清）。

### 汇编示例（regparm(3)）

```c
int __attribute__((regparm(3), cdecl)) add3(int a, int b, int c) {
    return a + b + c;
}
int r = add3(1, 2, 3);
```

调用方（caller）：

```asm
mov  eax, 1      ; a → EAX（第 1 个）
mov  edx, 2      ; b → EDX（第 2 个）
mov  ecx, 3      ; c → ECX（第 3 个）
call add3
; caller 清栈（cdecl 基础），但无参数在栈上，add esp 省略
```

被调用方（callee）：

```asm
add3:
    ; a 在 EAX，b 在 EDX，c 在 ECX
    add  eax, edx
    add  eax, ecx
    ret              ; 无操作数（caller 清；但栈上无参数，等效 ret 0）
```

### 与 MSVC `__fastcall` 的对比

| 维度 | MSVC `__fastcall` | GCC `regparm(2)` | GCC `regparm(3)` |
|------|-------------------|------------------|------------------|
| 参数 1 寄存器 | `ECX` | `EAX` | `EAX` |
| 参数 2 寄存器 | `EDX` | `EDX` | `EDX` |
| 参数 3 寄存器 | 压栈 | 压栈 | `ECX` |
| 名称修饰 | `@func@N` | 无（遵循基础规约） | 无 |
| 跨编译器兼容 | ❌ 不兼容 | ❌ 不兼容 | ❌ 不兼容 |
| 可用平台 | 32/64 位 Windows | Linux x86（32 位） | Linux x86（32 位） |

> GCC `regparm(2)` 与 MSVC `__fastcall` 虽然都用两个寄存器传参，但寄存器是 EAX/EDX vs ECX/EDX——**参数 1 的寄存器不同**，二进制不兼容。Linux 内核曾大量使用 `regparm(3)` 优化系统调用路径（在 `fastcall` 宏定义中），现代内核已改为统一使用平台调用规约。
