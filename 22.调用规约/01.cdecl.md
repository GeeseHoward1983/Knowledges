# `__cdecl` 详解（C Declaration / C 默认调用规约）

> 关键词：`__cdecl` ｜ caller 清栈 ｜ 全栈传参 ｜ **唯一支持可变参数** ｜ C/C++ 默认
> 上级：[[22.调用规约/00.总览|x86 三种调用规约总览]]

`cdecl`（C declaration）是 C/C++ 在 x86 上的**默认调用规约**，名字源于「这就是 C 语言声明函数时的标准约定」。CRT、`printf` 这类函数都是它。

---

## 核心规则

| 项目 | 规定 |
|------|------|
| **参数传递** | 全部经**栈**传递，无寄存器参数 |
| **压栈顺序** | **从右往左**（最后一个参数先压，第一个参数最后压 → 第一个参数在最低地址，紧邻返回地址） |
| **栈清理** | **调用者（caller）清** —— `call` 返回后由调用方 `add esp, N` 收回 |
| **返回值** | 整型/指针 → `EAX`；64 位（`long long`）→ `EDX:EAX`；浮点 → x87 栈顶 `ST(0)` |
| **caller-saved** | `EAX`、`ECX`、`EDX`（被调用者可随意覆盖） |
| **callee-saved** | `EBX`、`ESI`、`EDI`、`EBP`（被调用者动用前须保存、返回前须恢复） |
| **名称修饰（MSVC，C 链接）** | 前导下划线：`int add(int,int)` → `_add` |

> **为什么从右往左压栈？** 这样第一个参数永远在**最靠近返回地址**的固定位置（`[ebp+8]`），与后面有几个参数无关。可变参数函数（`printf`）正是靠这一点：先读到的 `fmt` 位置固定，再按格式串推断后续参数。

---

## 汇编示例

C 源码：

```c
int __cdecl add(int a, int b) { return a + b; }
int r = add(1, 2);
```

调用方（caller）：

```asm
push 2            ; 先压 b（最右）
push 1            ; 再压 a
call _add
add  esp, 8       ; ★ caller 清栈：收回 2 个参数 = 8 字节
mov  [r], eax     ; 取返回值
```

被调用方（callee）：

```asm
_add:
    push ebp
    mov  ebp, esp
    mov  eax, [ebp+8]    ; a（第一个参数，紧邻返回地址）
    add  eax, [ebp+12]   ; b
    pop  ebp
    ret                  ; ★ 无操作数：自己不清参数，留给 caller
```

> 记忆点：**callee `ret`（裸返回）+ caller `add esp, N`** 是 cdecl 的指纹组合。

## 可变参数：cdecl 的独门绝技

```c
int printf(const char* fmt, ...);   // 必然是 cdecl
```

只有 caller 清栈，才能支持参数个数不定的函数：

- callee（`printf`）**不知道**这次到底传了几个参数，自然没法 `ret N`；
- caller 在每个调用点**明确知道**自己压了多少，调用后用对应的 `add esp, N` 收回。

因此 **C 标准要求可变参数函数必须是 cdecl**；MSVC 下即便你给可变参数函数标了 `__stdcall`，编译器也会**静默改回 cdecl**。

---

## 优缺点

✅ **优点**
- 唯一支持可变参数（`printf`/`scanf` 全家）。
- 兼容性最好，是 C ABI 的「最大公约数」；跨编译器互操作首选。
- 调用约定简单、心智负担低。

❌ **缺点**
- 每个调用点都要带一段 `add esp, N`，**总代码体积偏大**。
- 全栈传参，无寄存器加速，**比 fastcall 慢一点**。

---

## 逆向识别

- 看到 `call` 之后紧跟 `add esp, N`（N>0）→ **基本就是 cdecl**（或可变参数函数）。
- 函数体以裸 `ret`（无操作数）结束，而参数确实压在栈上。
- 符号名形如 `_funcname`（单下划线前缀，无 `@N` 后缀）。

> 反例：若 `call` 后**没有** `add esp`、函数却以 `ret N` 收尾，那是 callee 清栈 → 看 [[22.调用规约/02.stdcall.md|stdcall]] / [[22.调用规约/03.fastcall.md|fastcall]]。

---

## 浮点参数与返回

cdecl 对浮点的处理在 x86 上**完全走栈 + x87**，与整型路径截然不同：

### 浮点参数：全部压栈，无寄存器传参

浮点参数（`float`、`double`）与整型参数一样**从右往左压栈**，没有任何寄存器快捷通道（XMM 在 32 位 x86 cdecl 下**不参与**参数传递）。

```c
double __cdecl scale(double x, float k);
// 调用：double r = scale(3.14, 2.0f);
```

调用方（caller）汇编示意：

```asm
; 从右往左：先压 k（float, 4 字节），再压 x（double, 8 字节）
push  40000000h        ; k = 2.0f（IEEE 754 单精度，4 字节，直接压 4 字节）
push  51EB851Fh        ; x = 3.14 的低 32 位（double 占 8 字节，分两次 push）
push  4008F5C2h        ; x = 3.14 的高 32 位
call  _scale
add   esp, 12          ; ★ caller 清栈：4+8=12 字节
```

> 实战中编译器可能先把浮点常量加载到 x87 寄存器，再用 `fst [esp]` 写入栈，但调用方与被调用方之间的边界始终是**栈上字节**，而非寄存器。

### 浮点返回值：x87 栈顶 ST(0)

x86 cdecl（及 stdcall、fastcall）统一约定：浮点返回值放在 **x87 浮点栈顶 `ST(0)`**（对应 `st0` 寄存器）。

```c
double __cdecl average(double a, double b) { return (a + b) / 2.0; }
```

被调用方（callee）汇编示意：

```asm
_average:
    push  ebp
    mov   ebp, esp
    fldl  [ebp+8]      ; 把 a（double，[ebp+8..+15]）压入 x87 栈 → ST(0)=a
    faddl [ebp+16]     ; ST(0) = a + b
    fldl  _two         ; ST(0) = 2.0，ST(1) = a+b
    fdivrp             ; ST(0) = (a+b)/2.0，弹出 ST(1)
    ; ★ 返回值就留在 ST(0)，caller 读时用 fstp [dest] 或 fstpl 取走
    pop   ebp
    ret                ; 裸 ret，caller 清栈；ST(0) 持有返回值
```

调用方取返回值：

```asm
call  _average
add   esp, 16          ; 清栈
fstp  qword ptr [r]    ; ★ 把 ST(0) 弹出并写入 double 变量 r
```

> **逆向识别**：函数出口前 `ST(0)` 持有有效值而无后续 `fstp` 弹出；调用方在 `add esp` 之后紧跟 `fstpl [dest]` 或 `fstp qword ptr [var]` → 返回的是 `double/float`。

### SSE 路径（编译器优化扩展，非标准 cdecl）

GCC/Clang 在 32 位 x86 下开启 `-mfpmath=sse`（或隐含于 `-O2` + `-msse2`）时，会用 **XMM 寄存器**存放浮点运算中间值，但仍遵守「调用边界用 x87 `ST(0)` 返回」的 ABI 约定——参数进函数体后可能立即 `movsd xmm0, [ebp+8]` 搬到 XMM，运算完再 `movsd [ebp-8], xmm0` + `fldl [ebp-8]` 搬回 x87 以满足返回规约。这是**函数内部优化**，不改变调用边界的浮点语义。

## cdecl 在 Linux x86 (GCC) 与 MSVC 下的细节差异

两者都叫「cdecl」，压栈顺序、caller 清栈、整型返回值放 EAX 这几条一致，但以下细节存在差异，跨编译器互操作时需要逐条核对：

### 默认栈对齐

| 编译器 | 调用前 ESP 对齐要求 |
|--------|---------------------|
| **GCC (Linux x86，gcc ≥ 4.5)** | **16 字节对齐**（ABI 要求，SSE 指令需要） |
| **MSVC（32 位）** | **4 字节对齐**（历史遗留，仅保证 DWORD 对齐） |

GCC 在函数序言里会执行 `and esp, -16`（或等价操作）把栈对齐到 16 字节，以满足 `movaps`/`movapd` 等 SSE 指令的对齐要求。MSVC 默认不做这一步，混用时如果 GCC 编译的函数内有 SSE 对齐读写，而调用方是 MSVC 代码，可能引发对齐异常（#GP）。

### 结构体返回（隐式指针）的实现细节

| 编译器 | 隐式指针传递方式 |
|--------|-----------------|
| **GCC** | 隐式指针作为**第一个隐藏参数**（即最后压栈，在最高地址），caller 负责分配缓冲区并压栈，`EAX` 返回该指针 |
| **MSVC** | 行为类似，但对于**单一 POD 结构体**（如 `struct { int x; int y; }`），MSVC 有时会直接把它拆成 `EDX:EAX` 返回（编译器扩展行为，非标准 cdecl）；非 POD 或较大结构体同样走隐式指针 |

> 这是 GCC 与 MSVC 混用时**最常见的 ABI 不兼容点**之一：如果返回结构体的函数在一侧编译器用了 `EDX:EAX` 优化、另一侧期待隐式指针，调用方会读到垃圾数据或崩溃。

### 名称修饰（Name Decoration）

| 编译器 | C 链接（`extern "C"` 或纯 C） | C++ 链接 |
|--------|-------------------------------|----------|
| **MSVC** | **前导下划线** `_funcname`（32 位；64 位下**无下划线**） | MSVC mangling（`?func@@...`） |
| **GCC (Linux)** | **无前导下划线** `funcname`（Linux ELF 惯例） | Itanium C++ ABI mangling（`_Z...`） |
| **GCC (MinGW on Windows)** | 视目标格式：生成 PE 时沿用 **`_funcname`** 前导下划线，与 MSVC 兼容；Linux ELF 目标无下划线 |

> 逆向或链接时：在 Linux 上 `nm` 看到 `add`（无下划线）是 GCC cdecl；在 Windows PE 里 `_add` 是 MSVC/MinGW cdecl；符号 `?add@@YAHHH@Z` 才是 MSVC C++ cdecl。

### 浮点返回值的平台偏好

| 编译器 + 选项 | `double` 返回通道 |
|---------------|-------------------|
| MSVC 32 位（默认） | x87 `ST(0)` |
| GCC 32 位（`-mfpmath=387`，默认） | x87 `ST(0)` |
| GCC 32 位（`-mfpmath=sse -msse2`） | 函数内部用 XMM，但**返回边界仍用 ST(0)**（遵守 ABI） |

两者在调用边界上一致（`ST(0)`），不存在互操作问题；差异在函数体内部的运算路径。
