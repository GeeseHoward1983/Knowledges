# 内联汇编（GCC/Clang extended asm 与 MSVC __asm）

> [!abstract] TL;DR
> 内联汇编让 C/C++ 代码在不跳出编译单元的前提下嵌入精确控制的汇编片段。GCC/Clang 的 extended asm 通过**约束字符串**把寄存器分配和操作数绑定交给编译器，既能利用寄存器分配器又能保留逐条指令的精度控制。MSVC 的 `__asm{}` 仅支持 x86-32，x64 完全移除，需改用 intrinsics 或独立 `.asm` 文件。`__attribute__((naked))` 裸函数省去编译器生成的序言/尾声，是中断处理、hook 桩和 shellcode 的利器。多架构项目务必了解各平台约束字符串的差异，否则同一段代码在 ARM/AArch64 或 RISC-V 上会产生截然不同的分配结果甚至编译报错。

## 概述与定位

内联汇编（inline assembly）是 C/C++ 源文件中嵌入汇编指令的机制，它处于三种"汇编-C 交互"方式的中间位置：

```mermaid
graph LR
    A["纯 C/intrinsics<br/>（编译器全权）"] --> B["内联汇编<br/>（共享寄存器分配）"] --> C["外部 .s 文件<br/>（手写栈帧/ABI）"]
```

**选内联汇编的典型场景**：

- 需要某条 C 语言无法直接表达的特权/系统指令（`cpuid`、`rdtsc`、`csrr`、`mrs`）。
- 对单个热点循环体做精确优化，但不想为它单独维护一个 `.s` 文件。
- 写 CPUID 特性检测、原子原语、I/O 端口读写等平台相关的基础设施代码。
- 中断处理入口（配合 `naked` 属性，手写全部寄存器保存/恢复）。

**不应内联汇编的场景**：调用约定复杂的整个函数体、需要精细控制代码布局的大段逻辑、需要跨平台移植的通用库——此时拆成独立 `.s` 文件更清晰，也更容易被汇编器/连接器单独处理。

GCC extended asm 自 GCC 2.x 起存在，Clang 完全兼容其语法（含 `asm goto` 从 GCC 4.5/Clang 3.4 起）。两者在约束字符串上基本一致，但对某些极端约束的处理细节不同，后文会指出。

## 原理与机制

### basic asm 与 extended asm 的区别

**basic asm** 语法最简：

```c
asm("nop");
asm("cli");  // 仅在内核/特权代码中合法
```

它没有操作数绑定，编译器把这段文本原样嵌入输出，**不与寄存器分配器交互**。basic asm 不声明 clobber，因此编译器无法知道它是否破坏寄存器，在函数体中（非全局作用域）使用 basic asm 有未定义行为风险（它可能修改了编译器认为仍有效的寄存器）。GCC 文档建议：除非是单纯的无副作用指令（`nop`），函数体内一律用 extended asm。

**extended asm** 格式：

```
asm [volatile] ("模板字符串"
    : 输出操作数列表
    : 输入操作数列表
    : clobber 列表);
```

四部分之间用 `:` 分隔；若某部分为空可省略（但 `:` 保留）。

### volatile 的语义

`asm volatile(...)` 告诉编译器：**不要移动、合并或删除这条 asm**。若没有 `volatile`，编译器可以：

- 判断输出未被使用而删除整条 asm（dead code elimination）。
- 将 asm 移出循环（CSE / hoisting）。
- 将两次相同的 asm 合并为一次。

访问硬件寄存器、执行有副作用的指令（`cpuid`、`rdtsc`、`rdmsr`、`fence`）、写内存屏障等，都必须加 `volatile`。

### 操作数约束字符串

约束字符串决定了操作数如何与机器资源绑定：

| 约束 | 含义 |
|------|------|
| `"r"` | 任意通用寄存器 |
| `"m"` | 内存操作数（编译器生成有效地址） |
| `"i"` | 立即数（编译期常量） |
| `"n"` | 整数立即数（精确常量，比 `"i"` 严格） |
| `"g"` | 通用：寄存器、内存或立即数（编译器自由选） |
| `"0"`~`"9"` | 与第 N 个操作数使用同一寄存器（用于 read-write 的 output=input） |

**修饰符前缀**（加在约束字符串最前面）：

| 修饰符 | 含义 |
|--------|------|
| `"="` | 输出操作数（write-only，旧值不保留） |
| `"+"` | 读写操作数（编译器分配同一寄存器给 input 和 output） |
| `"&"` | early-clobber：该输出寄存器在指令执行**前**就已被写，编译器不会把它分配给任何输入操作数 |

`"&"` 是避免 output/input 别名冲突的关键。例如字节拷贝循环中，若输出指针与某个输入共享寄存器，指令还没读完输入就已经破坏了它。加 `"&"` 强制分配独立寄存器。

### 操作数引用

在模板字符串里用 `%0`、`%1`、… 按声明顺序（输出在前、输入在后）引用操作数：

```c
int a = 10, b = 20, result;
asm("add %2, %1, %0"   // ARM64 语法：add result, a, b
    : "=r"(result)     // %0：输出
    : "r"(a), "r"(b)); // %1：a，%2：b
```

也支持**命名引用**（GCC 扩展，更可读）：

```c
asm("add %[res], %[x], %[y]"
    : [res] "=r"(result)
    : [x] "r"(a), [y] "r"(b));
```

`%%` 转义为字面的 `%`（x86 AT&T 语法中 `%%eax` 才是寄存器名）。

### clobber 列表

clobber 告诉编译器哪些资源被隐式修改：

- `"cc"`：标志寄存器（x86 EFLAGS、ARM CPSR/NZCV 等）被修改。
- `"memory"`：内存被修改，相当于内存屏障——编译器必须在 asm 前将所有已缓存于寄存器的内存值刷回，asm 后重新从内存加载。这是用内联汇编写内存屏障的标准手法。
- 具体寄存器名（`"eax"`、`"x0"` 等）：这些寄存器被 asm 使用，编译器不应用它们存放活跃变量。

### asm goto：跳转到 C 标签

GCC 4.5+ 引入 `asm goto`，允许 asm 模板里的跳转指令跳到 C 代码中的标签：

```c
asm goto("test %0, %0; jz %l[zero_label]"
         :
         : "r"(x)
         : "cc"
         : zero_label);
// 正常路径
return 1;
zero_label:
return 0;
```

`%l[标签名]` 生成标签的汇编地址。`asm goto` 的输出操作数不支持 `"+"` 修饰，且必须把所有可达的 C 标签列在第五个 `:` 段。Linux 内核广泛用 `asm goto` 实现静态分支（static branch / jump label），以避免每次执行都进行条件判断。

## 结构/算法/伪代码详解

### x86/x86-64 的约束特殊性

x86 AT&T 语法里寄存器名前加 `%`，因此在 asm 模板中引用操作数用 `%%` 才是字面 `%`：

```c
// x86-64：用 rdtsc 读时间戳计数器
static inline uint64_t rdtsc(void) {
    uint32_t lo, hi;
    asm volatile("rdtsc"
                 : "=a"(lo), "=d"(hi));  // "a"=eax, "d"=edx
    return ((uint64_t)hi << 32) | lo;
}
```

x86 特有的约束字母（寄存器类）：

| 约束 | x86 含义 |
|------|---------|
| `"a"` | `eax`/`rax` |
| `"b"` | `ebx`/`rbx` |
| `"c"` | `ecx`/`rcx` |
| `"d"` | `edx`/`rdx` |
| `"S"` | `esi`/`rsi` |
| `"D"` | `edi`/`rdi` |
| `"A"` | `edx:eax`（64 位值分布于两个 32 位寄存器，用于 `div`/`mul`） |
| `"q"` | 任意可做字节寻址的寄存器（`eax`/`ebx`/`ecx`/`edx`，32 位模式限制） |

x86 还支持内存+寄存器的复合约束 `"rm"`（可选内存或寄存器），以及 `"0"`~`"9"` 的"匹配约束"来表达 read-write 操作数：

```c
// 原子自增（lock xadd）
int atomic_fetch_add(int *ptr, int val) {
    asm volatile("lock; xadd %0, %1"
                 : "+r"(val), "+m"(*ptr)  // val 是 read-write
                 :
                 : "cc", "memory");
    return val;  // 返回旧值（xadd 语义）
}
```

### ARM/AArch64 的约束

ARM/AArch64 使用 **Intel 语法的寄存器名**（不带 `%`），约束字母与 x86 不同：

```c
// AArch64：读系统寄存器 MPIDR_EL1（多处理器 Affinity）
static inline uint64_t read_mpidr(void) {
    uint64_t val;
    asm volatile("mrs %0, mpidr_el1"
                 : "=r"(val));
    return val;
}
```

AArch64 特有约束：

| 约束 | AArch64 含义 |
|------|-------------|
| `"r"` | 通用整数寄存器（x0–x30，按操作数宽度选 w/x 前缀） |
| `"w"` | SIMD/浮点向量寄存器（v0–v31，含 b/h/s/d/q 视图） |
| `"x"` | 仅 64 位通用寄存器（不含 wzr/wsp） |
| `"Q"` | 内存操作数（适合 `ldxr`/`stxr` 等要求基地址+零偏移的指令） |

向量寄存器约束示例（NEON 内积）：

```c
// AArch64 NEON：4×float 内积
float dot4_neon(const float *a, const float *b) {
    float result;
    asm("ld1  {v0.4s}, [%1]  \n"
        "ld1  {v1.4s}, [%2]  \n"
        "fmul v2.4s, v0.4s, v1.4s \n"
        "faddp v2.4s, v2.4s, v2.4s \n"
        "faddp s0, v2.2s      \n"
        "str  s0, [%0]        \n"
        :
        : "r"(&result), "r"(a), "r"(b)
        : "v0", "v1", "v2", "memory");
    return result;
}
```

注意：直接将向量寄存器放入 clobber 列表（`"v0"` 等）是告诉编译器这些 SIMD 寄存器被使用，避免与 ABI callee-saved NEON 寄存器冲突。更惯用的写法是用 `"w"` 约束把向量操作数通过输入/输出传递，而非硬编码寄存器名。

### RISC-V 的约束

RISC-V GCC 的内联汇编约束相对简洁（指令集正交，寄存器用途区分少）：

| 约束 | RISC-V 含义 |
|------|------------|
| `"r"` | 整数寄存器（x1–x31） |
| `"f"` | 浮点寄存器（f0–f31，需 F 扩展） |
| `"A"` | 内存操作数，要求仅基地址（适合 AMO 原子指令） |
| `"I"` | 12 位有符号立即数（`addi` 的立即数范围） |
| `"J"` | 0 立即数（零值常量优化） |
| `"K"` | 5 位无符号立即数（`csri` 系列的立即数范围） |

读写 CSR（控制状态寄存器）的示例：

```c
// RISC-V：读 cycle 计数器（需 Zicsr 扩展）
static inline uint64_t riscv_rdcycle(void) {
    uint64_t val;
    asm volatile("rdcycle %0" : "=r"(val));
    return val;
}

// RISC-V：原子加（AMO）——注意 "A" 约束
int riscv_atomic_add(int *ptr, int inc) {
    int old;
    asm volatile("amoadd.w.aqrl %0, %2, %1"
                 : "=r"(old), "+A"(*ptr)
                 : "r"(inc)
                 : "memory");
    return old;
}
```

`"A"` 约束指示操作数是仅含基地址的内存引用（不含偏移），这与 AMO 指令的编码限制一致——`amoadd`、`lr`、`sc` 均不支持地址偏移字段（编码中偏移固定为 0）。

### 多架构约束对比代码

```c
// 跨架构内存屏障（全序，等效 C11 atomic_thread_fence(memory_order_seq_cst)）

static inline void full_barrier(void) {
#if defined(__x86_64__) || defined(__i386__)
    asm volatile("mfence" ::: "memory");

#elif defined(__aarch64__)
    asm volatile("dmb ish" ::: "memory");
    // ish = inner shareable domain；更强用 "dsb sy"

#elif defined(__arm__)
    asm volatile("dmb sy" ::: "memory");

#elif defined(__riscv)
    asm volatile("fence iorw, iorw" ::: "memory");
    // iorw = I/O + 读 + 写，全序屏障

#elif defined(__loongarch64)
    asm volatile("dbar 0" ::: "memory");
    // dbar 0 = 完整数据屏障，LoongArch 手册 §7.3

#else
#error "unsupported architecture for full_barrier"
#endif
}
```

### MSVC `__asm{}`：仅限 x86-32

MSVC 的内联汇编与 GCC 完全不同，不使用约束字符串，而是类似"内嵌的小型汇编器"：

```c
// MSVC x86-32 内联汇编（仅 /arch:IA32，x64 编译器已移除此语法）
int add_msvc(int a, int b) {
    int result;
    __asm {
        mov eax, a      // 直接用 C 变量名引用（MSVC 自动映射到栈地址）
        add eax, b
        mov result, eax
    }
    return result;
}
```

MSVC 内联汇编的特点与限制：

- 可直接在 asm 块中用 C 变量名（`a`、`b`）引用变量，MSVC 自动解析为栈偏移。
- 不需要声明 clobber，MSVC 保守地假设 asm 块可能改动任何寄存器（EAX/ECX/EDX 视为 caller-saved 且 asm 可修改；EBX/ESI/EDI/EBP 被保护）。
- **x64 版本的 MSVC 编译器完全不支持 `__asm{}`**，微软官方理由是 x64 的调用约定和 SEH（结构化异常处理）不允许编译器在复杂的 asm 块内维护栈展开元数据。
- x64 下的替代方案：1) 使用 intrinsics（`_mm_*`、`_InterlockedExchange` 等）；2) 写独立 `.asm` 文件，用 MASM（`ml64.exe`）编译后链接；3) 切换到 GCC/Clang（MinGW 或 Clang-cl）。

### `__attribute__((naked))` 裸函数

裸函数（naked function）让编译器**不生成函数序言（push rbp; mov rbp, rsp 等）和尾声（pop rbp; ret）**，函数体必须完全由程序员用内联汇编手写：

```c
// AArch64 裸函数：中断服务例程入口
__attribute__((naked)) void irq_handler_entry(void) {
    asm volatile(
        "stp x29, x30, [sp, #-16]!  \n"  // 保存帧指针和链接寄存器
        "stp x0,  x1,  [sp, #-16]!  \n"  // 保存 x0/x1
        "stp x2,  x3,  [sp, #-16]!  \n"
        "bl  do_irq_handler           \n"  // 调用 C 处理函数
        "ldp x2,  x3,  [sp], #16     \n"  // 恢复寄存器
        "ldp x0,  x1,  [sp], #16     \n"
        "ldp x29, x30, [sp], #16     \n"
        "eret                         \n"  // 从异常返回
    );
}
```

裸函数的注意事项：

1. **禁止使用任何局部变量和 C 参数引用**——编译器不建立栈帧，`a`、`b` 等参数名在 asm 里无效。
2. **不能有返回值**（返回值依赖编译器生成的 epilog 代码）。
3. GCC 在裸函数中只允许 basic asm（不允许 extended asm，因为约束解析依赖栈帧信息）——这是 GCC 的文档限制，Clang 对此稍宽松但也不保证。
4. ARM GCC 用 `naked` 的另一常见场景是 **hook 桩**（detour/trampoline）：在目标函数头部放跳转，跳到裸函数保存全部寄存器后调用 hook 逻辑，最后恢复并继续原函数。

## 工具视角与实战

### 查看编译器如何展开约束

用 `gcc -S` 或 `clang -S` 生成汇编，然后搜索 asm 模板中的指令名，直接看编译器选了什么寄存器：

```bash
gcc -O2 -S -o out.s foo.c
grep -A3 "rdtsc\|mfence\|cpuid" out.s
```

更方便的方式是用 [Compiler Explorer (godbolt.org)](https://godbolt.org)，可以侧面对比 GCC/Clang 对同一 asm 的不同处理。

### 常见陷阱

1. **忘记 `"memory"` clobber 导致重排**：写了内存但没声明 clobber，编译器在 asm 前后按旧缓存值优化，读到的是旧数据。
2. **约束太宽（`"g"`）导致生成低效代码**：若指令只接受寄存器，用 `"g"` 可能生成内存操作数版本，指令无效引发 illegal instruction。
3. **early-clobber 缺失**：输出与某个输入寄存器冲突，指令先写输出再读输入，导致输入被提前破坏。
4. **x86-32 和 x64 的 `"A"` 约束含义不同**：32 位下 `"A"` 是 `edx:eax` 组合；64 位下 `"A"` 是 `rax` 或 `rdx`（任意一个 64 位寄存器，不是组合），不可混用。
5. **Clang 的 tied-operand 差异**：Clang 对匹配约束（`"0"` 等）与 `"="` 的组合有时产生与 GCC 不同的寄存器选择，建议用 `"+"` 代替 `"="+匹配约束` 写 read-write。

### 与独立 `.s` 文件的选型边界

| 维度 | 内联汇编 | 独立 `.s` 文件 |
|------|---------|--------------|
| 调用约定 | 编译器处理（共享寄存器分配） | 完全手写（需符合平台 ABI） |
| 调试信息 | 行号可关联到 C 源码 | 需单独维护 DWARF |
| 移植性 | 约束字符串可多架构 `#ifdef` | 每架构独立文件 |
| 代码体积 | 适合数条到十数条指令 | 适合整个函数/模块 |
| 可读性 | 中（约束字符串难读） | 好（纯汇编格式自由） |
| 适合场景 | 单条指令、原子操作、屏障 | 整个函数体、复杂栈操作 |

经验法则：**超过 20 行汇编、需要手写序言/尾声、需要精确控制代码布局**的场合，直接上独立 `.s` 文件；其余大多数场合内联汇编足够，也更方便被编译器优化前后的代码所内联。

## 安全性与正确使用

### 避免约束错误导致的未定义行为

扩展 asm 的约束声明是一种**契约**：程序员承诺"我只用声明的输入、只修改声明的输出和 clobber"。违反契约的结果是**未定义行为**，不是运行时崩溃（有时正常运行，有时在 `-O2` 时神秘出错）。

几个正确性原则：

- 每条被修改的寄存器要么作为输出操作数约束，要么在 clobber 中列出。
- 任何写内存（不通过输出约束指定的变量）都要加 `"memory"` clobber。
- `"cc"` 在修改标志位时必须声明（即使某些指令的标志修改"看起来无害"，编译器也可能在 asm 后依赖标志做条件跳转优化）。

### 使用 `asm volatile` 的时机

只有以下情况才需要 `volatile`：

1. asm 有副作用（改变硬件状态，如写 I/O 端口）。
2. 多次执行有意义（`rdtsc` 测时序差，两次执行不应被合并）。
3. asm 是同步点（内存屏障），不能被移动。

对纯粹根据输入计算输出、无副作用的 asm（如一条 `bswap` 字节序反转），不加 `volatile` 让编译器有优化空间是正确的。

### 裸函数中的 ABI 责任

裸函数跳过编译器生成的 ABI glue，所有责任转移到程序员：栈对齐（x86-64 要求 16 字节）、callee-saved 寄存器保存/恢复（x86-64 的 `rbx/rbp/r12–r15`，AArch64 的 `x19–x30`）、栈展开信息（naked 函数没有 DWARF CFI，异常传播会出错）。裸函数**不应该被 C++ 异常机制跨越**。

## 小结

- GCC/Clang extended asm 通过约束字符串把汇编操作数绑定到编译器的寄存器分配器，做到"汇编精度 + 编译器优化"的折中。
- 约束字符串是核心：`"r"/"m"/"i"/"g"` 决定类型，`"="/"+"/"&"` 决定读写/early-clobber，clobber 中 `"memory"/"cc"` 是隐式副作用的声明。
- 多架构项目需特别注意：x86 有独特的 `"a"/"d"/"A"` 等寄存器约束；AArch64 有 `"w"` 向量约束；RISC-V 有 `"A"` 地址约束（不同于 x86 的 `"A"`）。
- MSVC `__asm{}` 仅限 x86-32，x64 需改用 intrinsics 或独立 MASM 文件。
- `__attribute__((naked))` 裸函数完全跳过编译器栈帧生成，适合中断入口、hook 桩，但全部 ABI 责任由程序员承担。
- 超过约 20 行或需要精确栈帧控制时，拆成独立 `.s` 文件比内联汇编更可维护。
