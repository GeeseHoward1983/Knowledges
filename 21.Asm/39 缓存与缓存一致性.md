# 缓存与缓存一致性

缓存是现代 CPU 性能的命脉，也是并发 bug 的隐秘来源。本页讲 **cache 结构、MESI 一致性协议、缓存维护指令、自修改代码同步、DMA 一致性与 false sharing**——承接 [[21.Asm/30 各架构性能特性对比.md|30 性能特性]] 与 [[21.Asm/37 自旋锁与无锁队列.md|37 并发原语]]。

## 缓存结构基础

- **层次**：L1（分 I-cache/D-cache，最快最小）→ L2 → L3（共享，最大最慢）→ 内存。
- **cache 行（line）**：缓存与内存交换的最小单位，**通常 64 字节**。访问任意一字节都会载入整行。
- **组相联**：N 路组相联在"直接映射"与"全相联"间折中；地址被切成 tag / index / offset。
- **命中/缺失**：缺失代价随层级递增（L1 几周期 → 内存上百周期），是性能优化的首要目标。

## MESI 缓存一致性协议

多核各有私有 cache，同一内存行可能存在多份副本。**MESI** 用四态保证一致：

| 态 | 含义 |
|----|------|
| **M**odified | 本核独占且已改（与内存不一致），其它核无副本 |
| **E**xclusive | 本核独占且未改（与内存一致） |
| **S**hared | 多核共享只读副本 |
| **I**nvalid | 无效（不可用） |

> 核间通过**总线嗅探（snooping）** 或**目录（directory）** 协调：一个核要写某行，须先让其它核的该行变 `I`（获得独占）。这套硬件协议让 [[21.Asm/28 原子操作与内存模型.md|内存模型]] 的"原子读改写"成为可能，但**伪共享**（见下）会让它变成性能杀手。

## 缓存维护指令对照

虽然一致性多由硬件保证，但**自修改代码、DMA、持久内存**等场景需软件显式维护：

| 操作 | x86 | ARM64 | RISC-V | LoongArch | MIPS |
|------|-----|--------|--------|-----------|------|
| 清(写回脏行) | `clwb`/`clflushopt` | `DC CVAC` | `cbo.clean`(Zicbom) | `cacop` | `cache` |
| 失效 | `clflush` | `DC IVAC` | `cbo.inval` | `cacop` | `cache` |
| 清+失效 | `clflush` | `DC CIVAC` | `cbo.flush` | `cacop` | `cache` |
| 写回失效全部 | `wbinvd`（特权） | （逐行/set-way） | — | `cacop` | — |
| I-cache 失效 | （硬件一致） | `IC IVAU` | `fence.i` | `cacop`/`ibar` | `synci` |
| 软件预取 | `prefetcht0/nta` | `PRFM` | `prefetch.r`(Zicbop) | `preld` | `pref` |
| 整行清零 | — | `DC ZVA` | `cbo.zero`(Zicboz) | — | — |

> 核实要点：**LoongArch 的缓存操作指令是 `CACOP`**；架构**允许但不强制**核内 I-cache/D-cache 硬件一致——在一致实现上自修改代码可能只需 `IBAR` 屏障，但**加载新代码镜像到内存仍需 `CACOP` 失效 I-cache**（功能上类比 RISC-V 的 Zicbom）。

## 自修改代码（SMC）同步

写入新指令后，必须确保 I-cache 看到 D-cache 的写——否则执行旧指令：

```asm
// ARM64：标准 SMC 同步序列（最繁琐，要四步）
    dc      cvau, x0       // 清数据 cache 到统一点
    dsb     ish            // 等清完、对其它核可见
    ic      ivau, x0       // 失效指令 cache
    dsb     ish            // 等失效完成
    isb                    // 刷新流水线，重新取指
```

```asm
# RISC-V：本核一条 fence.i；跨核需 IPI 通知各核各自 fence.i
    fence.i
```

> 对照：**x86** I/D 一致由硬件保证（改代码后跨核仅需序列化指令如 `cpuid`）；**ARM** 最繁琐（DC+DSB+IC+DSB+ISB）；**RISC-V** 用 `fence.i`（本核）；**LoongArch** 一致实现用 `ibar`、否则 `cacop`；**MIPS** 用 `synci`。逆向时遇到 SMC（见 [[21.Asm/33 逆向反汇编速查.md|逆向速查]]）要留意这些同步点。

## DMA 一致性

设备 DMA 直接读写内存，可能与 CPU cache 不一致：

- **DMA 写内存（设备→内存，如网卡收包）**：CPU 读前需**失效**对应 cache 行，否则读到旧缓存数据。
- **DMA 读内存（内存→设备，如发包）**：发起前需**清（写回）** cache，否则设备读到旧内存数据。
- x86 多为 cache-coherent DMA（硬件处理）；ARM/RISC-V/LoongArch 嵌入式常需软件 clean/invalidate（用上表的维护指令）。这是驱动开发的高频坑。

## false sharing（伪共享）

两个核各改**同一 cache 行**的不同变量，会因 MESI 反复争夺该行所有权而急剧变慢——即使逻辑上无共享：

```c
struct { int a; int b; } shared;   // a、b 同在一个 64B 行
// 核0 狂写 a、核1 狂写 b → 该行在两核间乒乓，性能崩塌
```

> 解法：**缓存行对齐 + 填充**，把高频独立写的变量隔到不同行（`alignas(64)` / `__cacheline_aligned`）。这是无锁队列、per-CPU 计数器的必备优化（呼应 [[21.Asm/37 自旋锁与无锁队列.md|自旋锁与无锁队列]]）。

## 总结

- cache 以 **64B 行**为单位；MESI 四态（M/E/S/I）经嗅探/目录维护多核一致。
- 维护指令五架构对照：x86 `clflush/clwb/wbinvd`、ARM `DC/IC`、RISC-V `Zicbom(cbo.*)`、**LoongArch `CACOP`**、MIPS `cache/synci`。
- 自修改代码必须同步 I-cache（ARM 四步最繁、RISC-V `fence.i`、x86 硬件一致）；DMA 与 false sharing 是性能/正确性的隐坑。
